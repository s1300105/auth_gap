# 2. 1 件の判定の手順（段 0〜11）

この章は、1 件を判定するときに**横に開いて上から順に**なぞるためのものです。どの件（W-01・T-01〜T-03）も同じ手順です。

- 各段は「目的」「やること」「表とメモに書くこと」「迷ったら」「段の終わりの確認」の順に書いてあります。
- 「迷ったら」の先は、判断の早見表（`04_rules.md` の節）と FAQ（`07_faq.md` の Q の番号）です。規則の正本は手引きの下書き
  `docs/drafts/final_judging_guide_draft.md` で、括弧の中の数字（例 15.1）はその節の番号です。
- 「例題では」は、`06_example.md` の練習用のサーバ（この手順書のために作った架空のコード）での動きです。
- 印の意味（`README.md` の 3 節）: 【実態調査の当てはめ】= 18 節の規則を実態調査の答えに当てはめたもの。【手引きに無い O48 (n)】=
  手引きに規則が無く、練習のための仮の扱い（`docs/open_questions.md` の O48 の (n) 番）。**仮の扱いで答えかラベルが決まったら、
  `note` に「O48 (n) の仮の扱い: …」と書く**（(n) は印の番号をそのまま写す。FAQ の N1〜N9 は「O48 (6) N<k> の仮の扱い: …」）。
  「決まった」は、仮の扱いが無かったら（または別の読みなら）答えかラベルが変わる、という意味です。`違反でない` でも、仮の扱いで
  「反しない」と決めた動作（関数名から読み取りと決めた、など）があれば書きます。仮の扱いで読む範囲に入れたが、そこに反しうる
  動作が無かった（middleware を読んで何も無かった）だけなら、書かなくてよい（書いてもよい）。

**段 1〜9 では AI を使いません**（手引き 18.2 の冒頭、事前登録の下書き (e) の AI の 3、D82）。英語の文書の機械翻訳は AI の利用に
当たらないので使ってかまいません（D86 の 14。使った道具を `note` に書く）。ただし**訳すのは自然言語の文書（README・公式の文書）
だけ**で、コードと宣言（docstring・コメントを含む）は翻訳の道具に貼りません（21 の 6）。

**18 節との違い**【実態調査の当てはめ】: 18.2 の 4（ここで解析器の出力を見る）・6（見落としの原因）と、18.4 の `cause`・`output_found`、
18.3 の `不明（打ち切り）` は、解析器の出力を見ない実態調査には無い。18.2 の 3「反しうる動作を**すべて**書き出す」と D82「最初に見つけた
違反で止めてよい」は、実態調査では最初に見つけた違反で止める（D88。段 7 の 3）。18.2 の 7（手順 G と同じ）の「反する動作が複数あるときは、
条件の一番弱い動作の種類・条件・深さを書く」は使わない（違反を比べない。D88 の 4）。ラベルは止めた違反の動作から取る（段 6 の 2・4、
段 7 の 2）。

**必須の記録は表の 1 行だけです**（D88）。どの欄を書くかは `03_record.md` の 1 節、どの字で書くかは 2・3 節。メモ（`worksheet.md`）は `evidence` を書く
ための任意の下書きで、使わなくてもかまいません。**確かめる手順は省きません**（省くと、違反を見逃して `違反でない` にする向きに
誤る）。確かめた結果は `evidence` に短く書きます。

## 段 2: 対象外でないかを確かめ、本体を見つける（D85）

**目的**: 名簿の件が本当に「ツールの宣言」かを確かめ、判定するツールの本体（関数）を決める。

**やること**

1. **宣言の行を開く**: VS Code で `Ctrl+P`（Mac は `Cmd+P`）→ `roster_relpath` を入れて開く → `Ctrl+G`（Mac は `Ctrl+G`）→
   `decl_lineno` を入れる。
2. 宣言（`readOnlyHint=True`・`read_only_hint=True`・`"readOnlyHint": True`）を確かめる（中身は写さない）。行がずれている・条件つきの式の
   中にある などで確かめられなければ、その行を写して、`note` に「宣言の行: …」と書く（写した行と、確かめられなかった理由）。
3. **登録を確かめる**: 宣言を含む呼び出し（`@mcp.tool(annotations=...)` など）が、MCP のサーバ（`FastMCP(...)`・`Server(...)` など）の
   `.tool(...)` の登録かを見る。サーバを作る行（`mcp = FastMCP(...)` など）を、ファイルの上の方か `import` の先で探す。見つけた
   登録の呼び出し・登録する関数・サーバを作る行が、`evidence` の「登録」の 1 文になる（`03_record.md` の 3.4 の 1。宣言が別の行に
   ある形（`name` など）では、つなぐ名前も）。
   - デコレータの名前がサーバの変数（`mcp`・`server`・`app` など）の `.tool` でなく、自前の関数（`@register_tool(...)` など）なら、その
     関数を開いて、最後に MCP のサーバに登録しているかを確かめる。
   - ツールが関数の中や `class` の中で定義されている（`def register(mcp): @mcp.tool(...) def x(): ...`）こともある。外側の関数が
     どこから呼ばれてサーバに登録されるかを確かめる。
4. **対象外かを決める**（D85）: 名簿の件が**ツールの宣言でない**とき、つまり**ツールとして登録されていない**とき（例: 宣言の辞書が
   設定や例として置かれているだけで、どのサーバにも登録されない）は `対象外` にする。対象外なら段 9 へ進み、`outcome` に
   `対象外`、`evidence` に理由と行（宣言の中身と、登録を探して検索した語も）を書く。
   - 登録が確かめられれば対象外ではありません。サーバが複数ある木でも同じです。
   - 【手引きに無い O48 (4)】サーバを作ってツールを登録しているが、そのサーバを起動する行が木の中に見つからない（別の入口にしか
     無い、テストからだけ作られる）ときも、練習では対象外にせず判定する（宣言は、そのサーバを起動したときのツールの動作に
     ついての主張と読む）。MCP 以外の枠組みにだけ登録しているときは仮の扱いが無いので、`不明`（`手引きで決まらない: …`）にする
     （段 8 の 5）。
5. **本体を決める**: 宣言が付いているツールの関数（`def` の行から関数の終わりまで）。`call_register` なら `import` をたどる（メモを
   使うなら、本体のファイル:行の範囲を 1 の深さ 0 の行に書く）。名簿の `tool` と違う関数に宣言が付いていたら、宣言が付いている方を
   判定し、`note` に「O48 (4) の仮の扱い: …」と書く【手引きに無い O48 (4)】。
6. **同じ名前の関数がほかに無いか**: `Ctrl+Shift+F`（Mac は `Cmd+Shift+F`）でツールの名前を検索する。同じ名前の関数・ツールが木の別の
   場所（別のサーバのファイルなど）にあれば、**名簿の位置（表の `roster_relpath:roster_lineno`）のものだけを判定する**（取り違えると
   別のツールを読むことになる）。見つかったら、その場所を `evidence` の「確かめたこと」に書く（無ければ書かなくてよい）。

**表とメモ**: 対象外なら `outcome`・`evidence`。メモ（任意）は 1 の深さ 0 の行（本体の範囲）。

**迷ったら**: `07_faq.md` の Q01〜Q08（入れ子の定義・クラスのメソッド・宣言の書き方・低水準のサーバ・複数のサーバ・登録が設定しだい・説明文）。

**例題では**: 名簿は `notes_server.py:43`（`decorator`、宣言 `:42`）。`:42` の `@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))`
が `:43` の `search_notes` を登録し、サーバは `:13` の `mcp = FastMCP("notes")`。対象外ではない。本体は `notes_server.py:43-48`。

**段の終わりの確認**: □ 宣言の行を開いて確かめた □ 宣言が登録に付いていることを確かめた（または対象外と決めた）
□ 本体のファイル:行の範囲が分かった

## 段 3: 本体を読む（深さ 0）

**目的**: 本体と、本体と一緒に必ず走るもの（デコレータの wrapper・middleware）を読み、次に読む関数を全部挙げる。

**やること**

1. 本体を `def` の行から関数の終わりまで、**全部**読む。
2. **引数**: ツールの入力（スキーマ）になる引数は**モデルが決める値**です（原理 3: 取りうる値の全体で考える）。名前・型・既定値を
   見る（書かなくてよい）。【手引きに無い O48 (4)】`ctx: Context` など、フレームワークが入れる引数はモデルが決めないものとして扱う
   （原理 3 は「モデルが選べる引数」としか書かない）。
   `Depends(f)` のような依存の注入は `07_faq.md` Q15 を見る。
3. **docstring・コメント・ツールの説明文**は、ツールが何をするかの根拠にしない（「read-only」と書いてあっても、決めるのはコードの行）。
   どこを読むかの手がかりにはしてよい。（手引きにこの文そのものは無いが、11.2「判定するのはコードの動作」と、21 の 6 で AI に貼る前に
   宣言を述べる文を伏せる規則と同じ考え。）
4. **自前のデコレータ**: `@mcp.tool(...)` のようなライブラリのデコレータ以外のデコレータが付いていれば、その定義を開き、wrapper の
   中身を読む。wrapper は**深さに数えない**が、中の動作は呼び出しのたびに走るので**読む範囲に入れる**（18.2 の 2、D86 の 16）。
   【手引きに無い O48 (4)】wrapper の中の文は、ツールの本体と同じ深さ 0 として扱う。wrapper がツールの本体を呼ぶこと（`fn(...)`
   のほか、`asyncio.to_thread(fn, …)` などを通す形も）は段に数えず、本体は深さ 0 のまま。wrapper が本体のほかに呼ぶ木の中の
   関数は深さ 1（D86 の 16「wrapper の分を足さない」の読み）。デコレータが重なっていれば全部。
   - `@mcp.tool` より上に付いたデコレータは登録されず、走らない（`07_faq.md` Q11）。読んだ wrapper は読んだ範囲に入れる（メモの 1 に
     1 行。深さは `04_rules.md` の 1 節）。デコレータの有無は `evidence` の「確かめたこと」に書く（無ければ「デコレータなし」。5 の middleware も無ければ、まとめて「デコレータ・middleware なし」）。
5. **middleware**【手引きに無い O48 (1)】: サーバを作る行（`FastMCP(..., middleware=[...])` など）に middleware があれば、
   **木の中の** middleware のクラス（`on_call_tool` など）と、木の外の middleware に渡した**木の中の関数**（呼び戻し）を、wrapper と
   同じく深さを足さずに読む。そのサーバを別のサーバに `mount()` しているときは、そちらの middleware も同じ。読んだ middleware の
   クラス・呼び戻しの関数は読んだ範囲に入れる（メモの 1 に 1 行ずつ。mount 先の親のものも）。middleware の有無は `evidence` の
   「確かめたこと」に書く（無ければ「middleware なし」）。`note` に書くのは、middleware の中の動作で答えかラベルが決まったとき。
   - 深さ: middleware の中の文と、モジュールの一番上で渡した呼び戻しの関数の中の文は深さ 0（本体と同じ）。そこから呼ぶ木の中の
     関数は深さ 1。関数の中で渡した呼び戻しは、渡した行のある関数と同じ深さ（`04_rules.md` の 1 節）。
   - 【手引きに無い O48 (4)】取り付け先（親のサーバ）の middleware は、親の入口を通した呼び出しでだけ走る。そこにだけある違反の
     `condition_type` は、練習では `運用者の設定`（どの入口で公開するかは運用者が決める）とし、`note` に書く。
6. **条件のメモ**: 本体の `if`・早い `return`・`raise`・`try`/`except` を見て、どの条件でどの呼び出しに届くかを見る（メモを使うなら、
   1 の「どこから呼ばれるか」に「? 条件」と控える）。**空の入力・失敗・前提の崩れ（表が無い、認証が通らない）で効果の前に抜ける
   ものは、条件に数えない**（14.3）。
7. **本体が呼ぶものを全部書き出す**: 呼び出しを 1 つずつ見て、木の中の関数か、木の外のライブラリかに分ける（見分け方は段 4 の 3）。
   木の中の関数は深さ 1 として次に読む（メモの 1 に足す）。木の外の呼び出しは、段 4 の 5 と段 5 で「それ自体が環境を変えるか」を
   見る（変えうるならメモの 2 に足す。変えないと見たものは `evidence` の「木の外:」に書ける）。
8. 本体の中に、環境を変えうる行（ファイル・DB・HTTP・プロセス・ログ）があれば、メモの 2 に足す（段 5 の一覧を見ながら）。

**メモ（任意）**: 1（本体・wrapper・middleware の行と、深さ 1 の関数）、2（本体の中の動作）。

**迷ったら**: `04_rules.md` の 1 節（深さ）、`07_faq.md` の Q09〜Q17（深さ・構築・wrapper・middleware・スレッド・暗黙に走るコード・既定値の関数・コールバック・動的な呼び出し）。

**例題では**: 引数は `query`（モデル）と `save_history`（モデル、既定 `False`）。自前のデコレータ・middleware は無い。`:45-46` の
空の検索語で抜けるのは条件に数えない。呼ぶもの: `log.info`（`:47`、木の外の `logging`。反しうる行としてメモの 2 に）、`_search`（`:48`、
木の中 → 深さ 1）、`json.dumps`（`:48`、木の外、環境を変えない）。docstring の「Read-only」は根拠にしない。

**段の終わりの確認**: □ 本体を全部読んだ □ デコレータ・middleware を確かめた（読んだものは読んだ範囲に）□ 深さ 1 の
関数を全部挙げた □ 木の外の呼び出しを見た

## 段 4: 木の中の呼び出し先を深さ 4 までたどる（18.2 の 2）

**目的**: 呼び出しで実行されうる木の中のコードを、読む順に深さ 4 まで漏れなく読む（違反が決まったら、段 7 の 3 でそこで止める）。

**やること**

1. 深さ 1 の関数を 1 つずつ開いて読む。読んだら、その関数が呼ぶ木の中の関数を深さ 2 として挙げる（メモを使うなら 1 に足す）。
   深さ 2 → 3 → 4 と同じことを繰り返す。**深さ 4 の関数は読むが、その先（深さ 5）は読みに行かない**（18.3。先を読まなかった関数は
   `evidence` の「深さ 4 で止めた:」に書く）。各関数の条件と早い `return`・`raise` は、段 3 の 6 と同じく見る。
   - 【手引きに無い O48 (4)】**読む順**: 浅い深さから順に（深さ 1 を全部 → 深さ 2 を全部 …）、同じ深さでは呼ばれる行の順に読む。
     「最初の違反で止める」（段 7 の 3）で、どれが最初の違反か・どれがそれより前の候補かは、この順で決まる。
   - 読みながら、環境を変えうる行が出たら段 5 の候補にし、読む順に段 6 で「届くか」「反するか」を決める。届いて反すると決まり、
     読む順でそれより前の候補が全部決まったら、段 7 の 3 で止める（その先は読まない）。`違反でない`・`不明`・`違反（深さ 4 の外）` に
     なる件は深さ 4 まで全部読む。
   - 【手引きに無い O48 (4)】深さ 4 までが大きく、20〜30 分では読み切れないときも、練習では読み続けて時間をそのまま記録する。読み切れずに
     やめるなら `不明`（類 `その他`、説明「深さ 4 までを読み切れない（どこまで読んだか）」）にする。
2. **深さの数え方**（解析器の数え方。18.2 の 2）:

| 形 | 数え方 |
|---|---|
| `f(...)`・`await f(...)`・`self.f(...)`・`obj.f(...)` | 呼ばれる関数が 1 段 |
| `Cls(...)`（構築） | `Cls.__init__` が 1 段。【手引きに無い O48 (6) N1】木の中に `__init__` が無くても、構築で走る木の中のコード（dataclass の `__post_init__`、`field(default_factory=f)` の `f`、pydantic の検証子）は `__init__` と同じ 1 段として読む。どれも無ければ読むものは無い |
| `Thread(target=f)` | `f` が 1 段 |
| `asyncio.to_thread(f, …)`・`loop.run_in_executor(None, f, …)`・`Executor.submit(f, …)`・`Process(target=f)`・`functools.partial(f, …)` | `f` が 1 段（解析器は `Thread(target=)` と同じ表 `INDIRECTS` で扱う。O48 (2)）。`f` が木の外なら読まない |
| デコレータの wrapper | 深さに数えない（中身は読む。段 3 の 4） |
| 暗黙に走るコード（`@property`・`cached_property` の属性の読み、`with X:` の `__enter__`/`__exit__`、`obj(...)` の `__call__`） | 【手引きに無い O48 (6) N1】書かれた位置から 1 段（呼び出しと同じに数える。`07_faq.md` Q14） |
| 呼ぶ側が渡さなかった引数の既定値の関数（`def g(q, writer=_write)` の中の `writer(q)`） | 【手引きに無い O48 (6) N9】`writer(q)` を書いた関数から 1 段（既定値の `_write` に降りる。`07_faq.md` Q15） |
| 同じ関数に何度も届く | 【手引きに無い O48 (4)】**いちばん浅い深さ**で数える（深さ 4 の内外を広く取る読み）。後で浅い道を見つけたら、その関数の先を深さ 4 まで読み直す |

3. **木の中か外か**: 呼び出しの名前で木の中を検索する（`def 名前`・`class 名前`。`Ctrl+Shift+F`）。木の中に定義があれば木の中
   （手引きは「木の外のライブラリ（pip で入るもの）」とだけ書く。【手引きに無い O48 (4)】木の中に同梱したライブラリのコード・テストや例の
   ファイルにある定義も、呼ばれていれば木の中として読む）。
   ファイルの上の `import` が、木の中に無いパッケージ（`requests`・`httpx`・`boto3`・`numpy` など）を指していれば木の外。
   **「定義へ移動」（F12）で飛べないことは、木の外の印ではない**（依存を入れていないので、木の中でも飛べないことが多い）。
4. **受け手の型を確かめる**（12.2、E3）: `self.client.fetch()` なら、`self.client` に何が入るか（`__init__` の
   `self.client = ApiClient(...)` など）を見てから `ApiClient.fetch` を開く。変数なら、その変数に代入している行を見る。
   - 組み込みの `set()`・`dict.get()`・`list.append()` などを、木の中の同じ名前のメソッドと取り違えない。
   - 受け手が決まらず、呼び出し先が決められないときは、手引き 19 の「動的な呼び出し」（段 8）。
5. **木の外のライブラリの中は読まない**（18.2 の 2、19 の「調べる範囲」）。ただし、**ライブラリの関数そのもの**が環境を変えるもの
   （`requests.put`・`open(…, "w")`・`sqlite3` の `execute("DELETE …")`・`shutil.rmtree` など）は、呼んでいれば反しうる行の候補に入れる（メモの 2）。
   - 深さ 1〜4 の関数の中の木の外の呼び出しも、本体のもの（段 3 の 7）と同じく見る。決めきれないものは反しうる行の候補に入れ、
     迷った呼び出しを「変えない」に寄せない。
   - 【手引きに無い O48 (3)】**知られていないライブラリの関数**（SDK の `client.get_x(...)` など）は:
     ① 名前が作成・更新・削除・書き出し・送信（`create_`・`update_`・`delete_`・`write`・`save`・`send` など）か、読み取り（`get_`・
     `list_`・`search`・`read`・`fetch` など）を**はっきり示す**なら名前で決め、`evidence` に「関数名から」と書く。② 名前で決まらなければ、
     そのライブラリか相手の API の**公式の文書**を開いて決め、URL を `evidence` に書く。③ それでも決まらず答えが変わるなら `不明`
     （類は、相手のサーバの API なら `相手の API`、それ以外は `外の値`）。④ 文書を読んでライブラリの**中で**書き込み（ファイルの
     書き込みなど）に気づいても、読む範囲の外なので答えは変えず、`note` に「ライブラリの中: …」と書く。呼び出し側の docstring・
     コメントは、どこを調べるかの手がかりにはしてよいが、根拠にはしない。①② の根拠（「関数名から」・文書の URL）は `evidence` に
     書く（メモを使うなら、2 の「D1 に反するか」に控える）。
     - ① は手引きと食い違う扱いです。手引き 19 は、ライブラリの動作を「確かめた」と言えるのを公式の文書かソースを開いたときに限り、
       名前で決めてよい例外を `POST` の API 名（15.1、D86 の 15）だけに置いています。① はその例外をライブラリの関数に広げる
       O48 (3) の推奨 (a) で、学生が封の前に (a) を選ばなければ消えます（そのときは ② から始め、文書で決まらなければ ③）。練習では
       ① を使い、使ったら `note` に「O48 (3) の仮の扱い: <関数> は関数名から <読み取り / 書き込み>」と書きます（README の「手引きを
       採る」は、手引きの規則を写し違えたところの話で、印の付いた仮の扱いには当てません）。
6. **読む範囲を絞ってよいところ**: 1 つの関数が長く、ツールの道筋と関係ない分岐が多いときは、届く分岐だけを読み、読んだ行の範囲を
   控える。届くかどうか迷う分岐は読む。読まなかった枝は、行と理由を `evidence` に「読まなかった枝: …」と書く（`03_record.md` の 3.4）。
7. 深さ 4 より奥で**偶然**違反を見つけたら、控えておく（段 7 の `違反（深さ 4 の外）`。探しに行かない）。答えが
   `違反（深さ 4 の外）` になるなら（段 7 の 1 の順 3）、その動作に段 6 の 1〜4 を付け、ラベルをそこから取る（深さは 5 以上）。

**メモ（任意）**: 1（読んだ関数と範囲。読まなかった枝・深さ 4 で止めた関数）。各関数を読み終えたら、その関数の中の環境を変えうる
行を 2 に足す（段 5）。

**迷ったら**: `04_rules.md` の 1 節（深さ）、`07_faq.md` の Q18〜Q25（ライブラリ・木の中か外か・同じ関数に 2 つの道・受け手の型・同じ名前・遅延 import・`try: import`）。

**例題では**: 深さ 1 = `_search`（`:34-39`）。深さ 2 = `NotesClient.__init__`（`:19-21`、`:35` の構築）、`NotesClient.search`（`:23-26`、
`:36`。受け手は `:35` で作った `NotesClient`）、`_remember_query`（`:29-31`、`:38`。`:37` の `if save_history:` の中）。深さ 3 は無い
（`httpx`・`json`・`time`・`os` は木の外）。深さ 2 の木の外の呼び出しのうち、`:21` の `httpx.Client`、`:24` の GET、`:30-31` の `open`・`write` は
反しうる行の候補（段 5）。

□ 受け手の型を確かめた □ 木の外の呼び出しを、反しうる行の候補にするか決めた

## 段 5: 環境を変えうる行を探す（18.2 の 3、15.1）

**目的**: 呼び出しの後に残るもの（ホストのファイル・DB・相手のサーバの状態・残る設定）を変えうる行を、**全部**拾う。

**やること**

1. 段 3・段 4 で読みながら拾った行を候補にする（メモを使うなら 2 に、1 行 = 1 動作。同じ行で複数の動作があれば分ける）。
   動作の深さは、その行が**書かれている関数**の深さ（木の外の関数を `asyncio.to_thread(f, …)` で呼ぶなら、`to_thread` の行が
   ある関数の深さ）。
2. 読んだ関数の範囲を、下の一覧の形でもう一度目で追う（VS Code の検索で、読んだファイルに絞って探してもよい）。**この一覧は探す
   ための手がかりで、規則ではない**（反するかは段 6 で決める）。

| 種類 | 探す形 |
|---|---|
| ファイル | `open(` のモード（`"w"`・`"a"`・`"x"`・`"+"` は書き込み。`"r"`・`"rb"` は読み取り）、`.write_text(`・`.write_bytes(`・`.touch(`、`mkdir`・`makedirs`、`unlink`・`os.remove`・`rmtree`、`rename`・`replace`・`shutil.copy`・`shutil.move`、`json.dump(`・`pickle.dump(`（ファイルへ）、`to_csv(`・`to_parquet(`・`savefig(`、`tempfile.`、`chmod`・`chown` |
| DB | `.execute(` の SQL（`INSERT`・`UPDATE`・`DELETE`・`CREATE`・`DROP`・`ALTER`・`REPLACE`・残る `PRAGMA`）、`sqlite3.connect(`（無いファイルを作る）、ORM の `.add(`・`.delete(`・`.save(`・`.merge(`（`.commit()` だけでは変更ではない。何を確定するかを見る）、グラフ DB の `CREATE`・`MERGE`・`SET`・`DELETE`、キーと値の DB・検索エンジンへの書き込み |
| HTTP・外部 | `requests` / `httpx` / `aiohttp` の `.post(`・`.put(`・`.patch(`・`.delete(`・`.request("POST", …)`、GraphQL の `mutation`、SDK の `create_*`・`update_*`・`delete_*`・`put_*`・`send_*`・`post_*`、メール・メッセージの送信、外のログ・エラー収集のサービス・syslog への送信 |
| プロセス・コード | `subprocess.`・`os.system(`・`os.popen(`・`asyncio.create_subprocess_`・`pexpect`、`eval(`・`exec(` |
| ログ | ロガーへの出力（`log.info(` など）と、その**出力先の設定**（次の 3） |
| 状態の保存 | トークン・セッションの保存（16.1 の例）、ディスクのキャッシュ（`diskcache`・`requests_cache`・`joblib.Memory`・`shelve`） |

3. **ログの出力先を確かめる**（18.3）: 違反で止めない件（`違反でない`・`不明`・`違反（深さ 4 の外）` にするとき）は、出力先の設定を**毎回**探す（読んだ範囲にロガーへの出力が
   無くても探す。ログの設定の見落としは、誤って `違反でない` にする向きの誤り。D87 の 3）。違反で止めるときは、読む順でその違反より
   前にロガーへの出力があるときだけ探す（段 7 の 3 の「止める時点」。D88）。VS Code の検索で正規表現（`.*`）を押し、
   `FileHandler|basicConfig|logger\.add|dictConfig|fileConfig|addHandler` を**木全体**で検索する。設定は、ツールのパッケージの外
   （木の一番上の `main.py`・`run.py`・`server.py`、`main()` の中、設定のファイル `logging.conf`・`*.yaml` など）にあることが多い。
   検索の語と範囲と結果を、`evidence` の「確かめたこと」に書く（絞ったなら範囲と理由も。`03_record.md` の 3.4 の 5）。
   - 当たったものから、**このサーバの起動で走るもの**を選ぶ: サーバを起動する入口（`if __name__ == "__main__":`・`main()`・
     `pyproject.toml` の `[project.scripts]`）から、その設定の行に着くか。ほかのサーバ・テスト・例のファイルの設定は外す（別の
     サーバがたくさんある木（monorepo）では当たりが多くなるので、ここで絞る）。
   - 走る当たりの出力先（標準エラー / ファイル）と置き場所（モジュールの一番上 / `main()` の中だけ / 設定のファイル）を見る。外した
     当たりは理由と一緒に `evidence` の「確かめたこと」に書く。`basicConfig(level=...)` だけなら標準エラーで、ファイルではない。
     ファイルへの設定が `main()` の中だけにあれば、そのログの違反の `condition_type` は `運用者の設定`（14.3）。
   - 設定が 1 つも無ければ、Python の既定（警告以上を標準エラーへ）で、ファイルには書かない（`evidence` に「当たりなし」と書く）。
   - 【手引きに無い O48 (4)】**手元の木は一部のファイルだけ**です（`.py`・`.toml`・`.txt`・`.lock`・`.json`・`.cfg`。`01_setup.md` の 1.1）。`logging.conf`・
     `*.yaml`・`*.ini`・README などは手元に無くても木の中にありえます。`git -C corpus/<tree> ls-tree -r --name-only HEAD | grep -iE 'log|\.ya?ml$|\.ini$|\.conf$|\.service$|Procfile|Dockerfile|\.sh$'`
     のように木の全部のファイルの名前を見て（`<tree>` は表の `tree` 欄の値。起動の定義（systemd の `*.service`・`Procfile`・`Dockerfile`・
     起動のスクリプト）に `--log-config` などの指定が無いかも見る）、要るものは `git -C corpus/<tree> show HEAD:<パス>` で読む
     （ネットワークが要る）。手元に無いファイルも**木の中**として扱い、
     `evidence` には木の根からのパスで書く。
4. **数えないもの**（15.1）は、拾っても「反しない」とする: プロセスのメモリの中の状態（モジュール水準の辞書・
   `lru_cache`・クラスの属性。D76 の 2）、標準出力・標準エラーへのログ、クライアントへの通知（`ctx.info()`・`ctx.report_progress()`）、
   ファイルの読み取り、HTTP の `GET`・`HEAD`・`OPTIONS`（`GET` で何かを作る API でも反しない。15 の前書き）、DB の読み取り（`SELECT`）、
   DB の接続単位の設定・トランザクション（`BEGIN`・`COMMIT`・`PRAGMA foreign_keys=ON`）。
5. **モジュールの読み込み時に走る行**（関数の外の文。`os.makedirs(...)` がモジュールの一番上にあるなど）は、ツールの呼び出しでは
   届かない（14.4）。`evidence` の「確かめたこと」に「届かない（モジュールの読み込み時）」と書く。
   - ただし、**ツールの中で初めて import するモジュール**（関数の中の `import`・`from . import x`。遅延 import）の一番上の文は、
     最初の呼び出しで走りうる。同じモジュールがサーバの起動時にほかで import されていれば、読み込み時なので届かない。されて
     いなければ 14.4 の表に無い形（手引きの封の前の仕分けで「まれ」として 22 節に回した穴 H-3-20）なので、そこに反する動作が
     あれば `不明`（`手引きで決まらない: …`。`07_faq.md` Q24）。

**表とメモ**: `evidence` の「確かめたこと」（ログの設定の検索、届かない行）。メモ（任意）の 2（候補の動作と深さ）。

**迷ったら**: `04_rules.md` の 2 節（D1 に反するか）、`07_faq.md` の Q36〜Q52（ログ・一時ファイル・DB・HTTP・SDK・コマンド・メモリ・キャッシュ・開くモード）。

**例題では**: 候補は 5 つ: `:15` の `os.makedirs`（モジュールの一番上）、`:21` の `httpx.Client(...)`（構築）、`:24` の `GET`、`:30-31` の
`open(..., "a")` と `write`、`:47` の `log.info`。ログの設定は `:10` の `basicConfig(level=logging.INFO)` だけ（標準エラー）。

**段の終わりの確認**: □ 読んだ全部の関数を一覧で見直した □ ログの出力先の設定を木全体で検索した（違反で止める件は、前に
ロガーへの出力があるときだけ）□ 候補を全部挙げた（反しないものも。違反で止めた件は、読む順で止めた動作まで。段 7 の 3）

## 段 6: 動作ごとに、届くか・反するかを決め、ラベルを付ける

**目的**: 候補の動作 1 つずつに、届くか（14）・D1 に反するか（15.1）を決める。違反の動作には、条件の種類（14.3）と書き込み先の
種類（16）を付ける。段 4・段 5 と行ったり来たりしながら、読む順に決めていく（違反が決まったら段 7 の 3 で止める）。

**やること**（候補の 1 つごとに 1・3・5 をする。2 と 4 は、止めた違反の動作（`違反（深さ 4 の外）` なら、深さ 4 より奥で見つけた動作。
段 4 の 7）だけ）

1. **届くか**（14）: ツールが呼ばれたとき、その行が実行される道が 1 つでもあれば「届く」（毎回でなくてよい。14.1）。
   - ツールが積んだもの・始めたもの（キュー・スレッド・プロセス）を、呼び出しが返った後に別のスレッド・プロセスが書くのも届く（14.1）。
   - **届かない形**（14.2）: 呼び出し先の取り違え／死んだコード（CLI・テストからだけ呼ばれる。木の中を検索して呼び出し元を全部見る）／
     定数で閉じた枝（`if DEBUG:` で `DEBUG = False` がどこでも書き換えられない。運用者が書き換える前提の `config.py` の定数は閉じて
     いない → `運用者の設定`）／効果の前に必ず `return`・`raise` する。
   - **一度だけの初期化**（`if self._x is None:`・`global _initialized`・`@lru_cache` の中）は 14.4 の表で決める: 初期化が `main()` の中
     だけ → 届く（`起動の方法`）。lifespan の中・モジュールの読み込み時 → 届かない。`mcp` を包む部品の起動フックの中 → 届く
     （`起動の方法`、D86）。lifespan が条件つきなら、条件が偽のとき届く。初期化の後に `None` に戻す行があれば再び届く（`atexit`・テストの
     中は数えない）。読み切れなければ不明（`起動・初期化`。5）。
   - 同じ呼び出しの中で作って消すもの（一時ファイル）も届く（14.5）。
2. **条件の種類**（14.3。止めた違反の動作だけ）: どんなときに届くか・環境が変わるかを見て、7 つから選ぶ（`04_rules.md` の 4 節の手順と表）:
   `なし` / `引数` / `初回` / `失敗・期限切れ` / `外部の状態` / `運用者の設定` / `起動の方法`。「かつ」で重なれば全部を `;` で並べる。
   「または」なら一番弱い道の条件だけ。1 つの条件が 2 つの種類に読めるなら、表の上からの順で先の 1 つだけ。中身（どの引数・どの設定・
   どんな状態か）を `condition` に書く。
3. **D1 に反するか**（15 の前書き・15.1。表の行と問いの文が違えば表の行を採る。`04_rules.md` の 2 節）: 反する・反しない・決められない。
   根拠の節（例「15.1 のファイルの行」）を `evidence` に書く（名前や文書で決めたなら「関数名から」・文書の URL も。段 4 の 5。違反で
   ないときは「反しない理由」、違反なら道筋の中に）。
