  規則が無く、練習のための仮の扱い（`docs/open_questions.md` O48）。

## 段 0: 始める前（時計の外）

**目的**: 時計を動かした後に、準備で時間を使わないようにする。

**やること**

1. その件の木を VS Code の**新しい窓**で開く（`code corpus/<tree>`）。ほかの木の窓は閉じるか、別の窓のままにする。
2. 右下の Python の表示（Pylance）の読み込みが終わるまで待つ。窓を開いてから使えるようになるまでの分数を、ワークシートの A 節の
   `t_setup` に書く（本番では件ごとに木が違うので、この手間が毎回かかる）。
3. エディタの AI（Copilot など）が切れていることを確かめる（`01_setup.md` の 3 節）。
4. ワークシートを写して開く（`cp evidence/practice_v4/manual/worksheet.md ~/authgap_practice/worksheets/<pair_id>.md`）。
5. 表（`~/authgap_practice/survey_practice.csv`）のその件の行を開く。
6. ストップウォッチを 0 にする。トイレ・飲み物を済ませる。
7. 「最初の違反で止めるか」を確かめる（W-01 の前に決めて、全部の件で同じにする。段 7 の 3）。

**段の終わりの確認**: □ 窓が開いて読み込みが済んだ □ `t_setup` を書いた □ ワークシートと表の行が開いている □ ストップウォッチは 0

## 段 1: 名簿の行を読む（ここで時計を動かす）

**目的**: 何を判定するかを確かめる。

**やること**

1. **ストップウォッチを動かし、その時刻をワークシートの A 節の `t_start` に書く**（`HH:MM`、24 時間）。手引き 12.3 の起点は「手順 A を
   始めてから」で、実態調査には手順 A が無いので、名簿の行を読み始めた時点を起点にする【実態調査の当てはめ】。
2. 表の行から次を読み、ワークシートの A 節に写す: `pair_id`・`tree`・`tool`・`roster_form`・`roster_relpath`・`roster_lineno`・`decl_lineno`。
3. `roster_form` で、段 2 で何をするかを決める:

| `roster_form` | 名簿の位置（`roster_lineno`）が指すもの | 段 2 ですること |
|---|---|---|
| `decorator` | 関数の `def` の行 | その上のデコレータの中に宣言がある |
| `call_register` | `mcp.tool(annotations=…)(fn)` の登録の行 | `fn` の `import` をたどって本体を探す |
| `name` | 宣言を入れた名前を使うデコレータか `add_tool` の関数 | 名前（`RO = ToolAnnotations(...)`）の定義と、それを使う登録を見る |

## 段 2: 対象外でないかを確かめ、本体を見つける（D85）

**目的**: 名簿の件が本当に「ツールの宣言」かを確かめ、判定するツールの本体（関数）を決める。

**やること**

1. **宣言の行を開く**: VS Code で `Ctrl+P`（Mac は `Cmd+P`）→ `roster_relpath` を入れて開く → `Ctrl+G`（Mac は `Ctrl+G`）→
   `decl_lineno` を入れる。
2. 宣言（`readOnlyHint=True`・`read_only_hint=True`・`"readOnlyHint": True`）を確かめ、その行の中身をワークシートの B 節に写す。
3. **登録を確かめる**: 宣言を含む呼び出し（`@mcp.tool(annotations=...)` など）が、MCP のサーバ（`FastMCP(...)`・`Server(...)` など）の
   `.tool(...)` の登録かを見る。サーバを作る行（`mcp = FastMCP(...)` など）を、ファイルの上の方か `import` の先で探し、その
   ファイル:行を B 節に書く。
   - デコレータの名前がサーバの変数（`mcp`・`server`・`app` など）の `.tool` でなく、自前の関数（`@register_tool(...)` など）なら、その
     関数を開いて、最後に MCP のサーバに登録しているかを確かめる。
   - ツールが関数の中や `class` の中で定義されている（`def register(mcp): @mcp.tool(...) def x(): ...`）こともある。外側の関数が
     どこから呼ばれてサーバに登録されるかを確かめる。
4. **対象外かを決める**（D85）: 名簿の件が**ツールの宣言でない**とき、つまり**ツールとして登録されていない**とき（例: 宣言の辞書が
   設定や例として置かれているだけで、どのサーバにも登録されない）は `対象外` にする。対象外なら段 9 へ進み、`outcome` に `対象外`、
   `evidence` に理由と行を書く。
   - 登録が確かめられれば対象外ではありません。サーバが複数ある木や、別の起動の入口にしか無いサーバでも、登録されていれば対象外では
     ありません。
5. **本体を決める**: 宣言が付いているツールの関数（`def` の行から関数の終わりまで）。`call_register` なら `import` をたどる。名簿の
   `tool` と違う関数に宣言が付いていたら、宣言が付いている方を判定し、`note` に書く【手引きに無い】。
6. **同じ名前の関数がほかに無いか**: `Ctrl+Shift+F`（Mac は `Cmd+Shift+F`）でツールの名前を検索し、同じ名前の関数・ツールが木の別の
   場所（別のサーバのファイルなど）にあれば、**名簿の位置のものだけを判定する**ことを B 節にメモする（取り違えると別のツールを
   読むことになる）。

**ワークシート**: B 節（宣言・登録・対象外か・本体の位置・同じ名前の関数）。

**迷ったら**: `04_rules.md` の 8 節（FAQ の「登録・ツールの形」）。

**例題では**: 名簿は `notes_server.py:43`（`decorator`、宣言 `:42`）。`:42` の `@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))`
が `:43` の `search_notes` を登録し、サーバは `:13` の `mcp = FastMCP("notes")`。対象外ではない。本体は `notes_server.py:43-48`。

**段の終わりの確認**: □ 宣言が登録に付いていることを確かめた（または対象外と決めた）□ 本体のファイル:行の範囲を書いた

## 段 3: 本体を読む（深さ 0）

**目的**: 本体と、本体と一緒に必ず走るもの（デコレータの wrapper・middleware）を読み、次に読む関数を全部挙げる。

**やること**

1. 本体を `def` の行から関数の終わりまで、**全部**読む。
2. **引数**: ツールの入力（スキーマ）になる引数は**モデルが決める値**です（原理 3: 取りうる値の全体で考える）。名前・型・既定値を
   C 節に書く。【手引きに無い】`ctx: Context` など、フレームワークが入れる引数はモデルが決めないものとして扱う（原理 3 は「モデルが
   選べる引数」としか書かない。別に書く）。
3. **docstring・コメント・ツールの説明文**は、ツールが何をするかの根拠にしない（「read-only」と書いてあっても、決めるのはコードの行）。
   どこを読むかの手がかりにはしてよい。（手引きにこの文そのものは無いが、11.2「判定するのはコードの動作」と、21 の 6 で AI に貼る前に
   宣言を述べる文を伏せる規則と同じ考え。）
4. **自前のデコレータ**: `@mcp.tool(...)` のようなライブラリのデコレータ以外のデコレータが付いていれば、その定義を開き、wrapper の
   中身を読む。wrapper は**深さに数えない**が、中の動作は呼び出しのたびに走るので**読む範囲に入れる**（18.2 の 2、D86 の 16）。
   【手引きに無い】wrapper の本体は深さ 0 として扱い、wrapper が呼ぶ関数を深さ 1 と数える（D86 の 16「wrapper の分を足さない」の
   読み）。デコレータが重なっていれば全部。
5. **middleware**【手引きに無い】（O48 (1) の仮の扱い）: サーバを作る行（`FastMCP(..., middleware=[...])` など）に middleware があれば、
   **木の中の** middleware のクラス（`on_call_tool` など）と、木の外の middleware に渡した**木の中の関数**（呼び戻し）を、wrapper と
   同じく深さを足さずに読む。そのサーバを別のサーバに `mount()` しているときは、そちらの middleware も同じ。読んだことと範囲を
   `note` に書く。
6. **条件のメモ**: 本体の `if`・早い `return`・`raise`・`try`/`except` を見て、どの条件でどの呼び出しに届くかを、C 節と D 節に
   「? 条件」として書く。**空の入力・失敗・前提の崩れ（表が無い、認証が通らない）で効果の前に抜けるものは、条件に数えない**（14.3）。
7. **本体が呼ぶものを全部書き出す**: 呼び出しを 1 つずつ見て、木の中の関数か、木の外のライブラリかに分ける（見分け方は段 4 の 3）。
   木の中の関数は D 節に深さ 1 として足す。木の外の呼び出しは C 節に書き、段 5 で「それ自体が環境を変えるか」を見る。
8. 本体の中に、環境を変えうる行（ファイル・DB・HTTP・プロセス・ログ）があれば、F 節に足す（段 5 の一覧を見ながら）。

**ワークシート**: C 節、D 節の深さ 0 の行と深さ 1 の行、F 節（本体の中の動作）。

**迷ったら**: `04_rules.md` の 1 節（深さ）、8 節（FAQ の「関数の形」）。

**例題では**: 引数は `query`（モデル）と `save_history`（モデル、既定 `False`）。自前のデコレータ・middleware は無い。`:45-46` の
空の検索語で抜けるのは条件に数えない。呼ぶもの: `log.info`（`:47`、木の外の `logging`）、`_search`（`:48`、木の中 → 深さ 1）、
`json.dumps`（木の外、環境を変えない）。docstring の「Read-only」は根拠にしない。

**段の終わりの確認**: □ 本体を全部読んだ □ デコレータ・middleware を確かめた □ 深さ 1 の関数を D 節に全部書いた □ 木の外の
呼び出しを C 節に書いた

## 段 4: 木の中の呼び出し先を深さ 4 までたどる（18.2 の 2）

**目的**: 呼び出しで実行されうる木の中のコードを、深さ 4 まで漏れなく読む。

**やること**

1. D 節の深さ 1 の関数を 1 つずつ開いて読む。読んだら、その関数が呼ぶ木の中の関数を深さ 2 として D 節に足す。深さ 2 → 3 → 4 と
   同じことを繰り返す。**深さ 4 の関数は読むが、その先（深さ 5）は読みに行かない**（18.3）。
   - 【手引きに無い】**読む順**: 浅い深さから順に（深さ 1 を全部 → 深さ 2 を全部 …）、同じ深さでは呼ばれる行の順に読む。「最初に反すると
     分かった動作」（段 7）と「最初の違反で止める」は、この順で決まる。
   - 【手引きに無い】深さ 4 までが大きく、20〜30 分では読み切れないときも、練習では読み続けて時間をそのまま記録する。読み切れずに
     やめるなら `不明`（類 `その他`、説明「深さ 4 までを読み切れない（どこまで読んだか）」）にする。
2. **深さの数え方**（解析器の数え方。18.2 の 2）:

| 形 | 数え方 |
|---|---|
| `f(...)`・`await f(...)`・`self.f(...)`・`obj.f(...)` | 呼ばれる関数が 1 段 |
| `Cls(...)`（構築） | `Cls.__init__` が 1 段（木の中に `__init__` が無ければ読むものは無い） |
| `Thread(target=f)` | `f` が 1 段 |
| `asyncio.to_thread(f, …)`・`loop.run_in_executor(None, f, …)`・`Executor.submit(f, …)`・`Process(target=f)`・`functools.partial(f, …)` | `f` が 1 段（解析器は `Thread(target=)` と同じ表 `INDIRECTS` で扱う。O48 (2)）。`f` が木の外なら読まない |
| デコレータの wrapper | 深さに数えない（中身は読む。段 3 の 4） |
| 同じ関数に何度も届く | 【手引きに無い】**いちばん浅い深さ**で数える（深さ 4 の内外を広く取る読み）。後で浅い道を見つけたら、その関数の先を深さ 4 まで読み直す |

3. **木の中か外か**: 呼び出しの名前で木の中を検索する（`def 名前`・`class 名前`。`Ctrl+Shift+F`）。木の中に定義があれば木の中
   （手引きは「木の外のライブラリ（pip で入るもの）」とだけ書く。【手引きに無い】木の中に同梱したライブラリのコード・テストや例の
   ファイルにある定義も、呼ばれていれば木の中として読む）。
   ファイルの上の `import` が、木の中に無いパッケージ（`requests`・`httpx`・`boto3`・`numpy` など）を指していれば木の外。
   **「定義へ移動」（F12）で飛べないことは、木の外の印ではない**（依存を入れていないので、木の中でも飛べないことが多い）。
4. **受け手の型を確かめる**（12.2、E3）: `self.client.fetch()` なら、`self.client` に何が入るか（`__init__` の
   `self.client = ApiClient(...)` など）を見てから `ApiClient.fetch` を開く。変数なら、その変数に代入している行を見る。
   - 組み込みの `set()`・`dict.get()`・`list.append()` などを、木の中の同じ名前のメソッドと取り違えない。
   - 受け手が決まらず、呼び出し先が決められないときは、手引き 19 の「動的な呼び出し」（段 8）。
5. **木の外のライブラリの中は読まない**（18.2 の 2、19 の「調べる範囲」）。ただし、**ライブラリの関数そのもの**が環境を変えるもの
   （`requests.put`・`open(…, "w")`・`sqlite3` の `execute("DELETE …")`・`shutil.rmtree` など）は、呼んでいれば F 節の候補に入れる。
   - 【手引きに無い】（O48 (3) の仮の扱い）**知られていないライブラリの関数**（SDK の `client.get_x(...)` など）は:
     ① 名前が作成・更新・削除・書き出し・送信（`create_`・`update_`・`delete_`・`write`・`save`・`send` など）か、読み取り（`get_`・
     `list_`・`search`・`read`・`fetch` など）を**はっきり示す**なら名前で決め、`evidence` に「関数名から」と書く。② 名前で決まらなければ、
     そのライブラリか相手の API の**公式の文書**を開いて決め、URL を `evidence` に書く。③ それでも決まらず答えが変わるなら `不明`
     （類は、相手のサーバの API なら `相手の API`、それ以外は `外の値`）。④ 文書を読んでライブラリの**中で**書き込み（キャッシュの
     ファイルなど）に気づいても、読む範囲の外なので答えは変えず、`note` に書く。呼び出し側の docstring・コメントは、どこを調べるかの
     手がかりにはしてよいが、根拠にはしない。
6. **読む範囲を絞ってよいところ**: 1 つの関数が長く、ツールの道筋と関係ない分岐が多いときは、届く分岐だけを読み、読んだ行の範囲を
   D 節に書く。届くかどうか迷う分岐は読む。
7. 深さ 4 より奥で**偶然**違反を見つけたら、D 節の下にメモする（段 7 の `違反（深さ 4 の外）`。探しに行かない）。

**ワークシート**: D 節（1 行 = 1 関数）。各関数を読み終えたら、F 節にその関数の中の環境を変えうる行を足す（段 5）。

**迷ったら**: `04_rules.md` の 1 節（深さ）、8 節（FAQ）。

**例題では**: 深さ 1 = `_search`（`:34-39`）。深さ 2 = `NotesClient.__init__`（`:19-21`、`:35` の構築）、`NotesClient.search`（`:23-26`、
`:36`。受け手は `:35` で作った `NotesClient`）、`_remember_query`（`:29-31`、`:38`。`:37` の `if save_history:` の中）。深さ 3 は無い
（`httpx`・`json`・`time`・`os` は木の外）。

**段の終わりの確認**: □ D 節の全部の関数を読んだ（深さ 4 まで）□ 各関数の「読んだ範囲」を書いた □ 受け手の型を確かめた
□ 木の外の呼び出しを F 節の候補にするか決めた

## 段 5: 環境を変えうる行を探す（18.2 の 3、15.1）

**目的**: 呼び出しの後に残るもの（ホストのファイル・DB・相手のサーバの状態・残る設定）を変えうる行を、**全部** F 節に拾う。

**やること**

1. 段 3・段 4 で読みながら拾った行を F 節に書く（1 行 = 1 動作。同じ行で複数の動作があれば分ける）。
2. 読んだ関数の範囲を、下の一覧の形でもう一度目で追う（VS Code の検索で、読んだファイルに絞って探してもよい）。**この一覧は探す
   ための手がかりで、規則ではない**（反するかは段 6 で決める）。

| 種類 | 探す形 |
|---|---|

## 段 6: 動作ごとに、届くか・反するかを決め、ラベルを付ける

**目的**: F 節の動作 1 つずつに、届くか（14）・条件の種類（14.3）・D1 に反するか（15.1）・書き込み先の種類（16）を付ける。

**やること**（F 節の 1 行ごとに 1〜5 をする）

1. **届くか**（14）: ツールが呼ばれたとき、その行が実行される道が 1 つでもあれば「届く」（毎回でなくてよい。14.1）。
   - ツールが積んだもの・始めたもの（キュー・スレッド・プロセス）を、呼び出しが返った後に別のスレッド・プロセスが書くのも届く（14.1）。
   - **届かない形**（14.2）: 呼び出し先の取り違え／死んだコード（CLI・テストからだけ呼ばれる。木の中を検索して呼び出し元を全部見る）／
     定数で閉じた枝（`if DEBUG:` で `DEBUG = False` がどこでも書き換えられない。運用者が書き換える前提の `config.py` の定数は閉じて
     いない → `運用者の設定`）／効果の前に必ず `return`・`raise` する。
   - **一度だけの初期化**（`if self._x is None:`・`global _initialized`・`@lru_cache` の中）は 14.4 の表で決める: 初期化が `main()` の中
     だけ → 届く（`起動の方法`）。lifespan の中・モジュールの読み込み時 → 届かない。`mcp` を包む部品の起動フックの中 → 届く
     （`起動の方法`、D86）。lifespan が条件つきなら、条件が偽のとき届く。初期化の後に `None` に戻す行があれば再び届く（`atexit`・テストの
     中は数えない）。読み切れなければ不明（`起動・初期化`）。
   - 同じ呼び出しの中で作って消すもの（一時ファイル）も届く（14.5）。
2. **条件の種類**（14.3）: 届くなら、どんなときに届くか・環境が変わるかを見て、7 つから選ぶ（`04_rules.md` の 4 節の手順と表）:
   `なし` / `引数` / `初回` / `失敗・期限切れ` / `外部の状態` / `運用者の設定` / `起動の方法`。「かつ」で重なれば全部を `;` で並べる。
   「または」なら一番弱い道の条件だけ。1 つの条件が 2 つの種類に読めるなら、表の上からの順で先の 1 つだけ。中身（どの引数・どの設定・
   どんな状態か）を `condition` に書く。
3. **D1 に反するか**（15 の前書き・15.1。表の行と問いの文が違えば表の行を採る。`04_rules.md` の 2 節）: 反する・反しない・決められない。
   根拠の節（例「15.1 のファイルの行」）を書く。
4. **書き込み先の種類**（16）: 反する動作には、16.1 の順（`相手側の状態` → `データベース` → `利用者のファイル` → `ログ` → `一時ファイル` →
   `キャッシュ・状態の保存` → `プロセスの起動・コードの実行` → `その他・不明`）で**最初に当てはまったもの** 1 つ（`04_rules.md` の 5 節）。
5. **決められないこと**があれば、何が決められないかを書く（段 8）。

**ワークシート**: F 節の全部の欄。

**迷ったら**: `04_rules.md` の 2〜5 節。

**例題では**:

| # | 行 | 届くか | 条件 | 反するか | 書き込み先 |
|---|---|---|---|---|---|
| 1 | `:15` `os.makedirs(STATE_DIR, exist_ok=True)` | 届かない（モジュールの読み込み時。14.4） | — | （届かない） | — |
| 2 | `:21` `httpx.Client(timeout=10)` | 届く | なし | 反しない（接続の準備だけ） | — |
| 3 | `:24` `GET /api/notes` | 届く | なし | 反しない（15.1 の GET の行） | — |
