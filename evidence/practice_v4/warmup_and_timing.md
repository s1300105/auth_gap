1. VS Code で、**木ごとに別の窓**で木を開きます（`code corpus/<木>`）。ほかの木のファイルが検索に混ざらないようにするためです。

   `grep -rnE 'FileHandler|basicConfig|logger\.add|dictConfig' --include=*.py <ディレクトリ>`。

### 段 1: 名簿の行を読む（時計を動かす）

表の 1 行から次を読みます。本番の名簿（`scripts/survey_roster.py`、D85）の 1 件と同じ中身です。

|---|---|

### 段 2: 対象外でないかを確かめ、本体を見つける

1. `roster_relpath:decl_lineno` を開き、宣言の行を見ます。**その宣言が、本当にツールの登録に付いているか**を確かめます。
   - `decorator`: `def` の真上のデコレータの中に宣言がある。そのデコレータが MCP のサーバ（`FastMCP(...)` などのインスタンスの
     `.tool(...)`）の登録か。
   - `call_register`: `mcp.tool(annotations={...})(fn)` の行。`fn` はファイルの上の `import` をたどって本体のファイルを開きます。
   - `name`・`add_tool`・`tool_ctor`・`dict_registry`: D85 の 3 の結びつけ方で、宣言が付いたツールを確かめます。
   - `unmapped`: 判定者がコードを読んでツールを決めます（D85 の 3）。【手引きに無い】1 つの宣言を複数のツールが使っているときに
     どれを判定するかは決まっていません（O48 (5)）。練習の W・T にこの形はありません。
2. **対象外**になるのは、名簿の件がツールの宣言ではないとき（ツールとして登録されていない、例・設定の辞書だけ。D85）。
   対象外なら段 9 へ（`outcome` に `対象外`、`evidence` に理由と行）。
3. 本体の `def` の行（ファイルと行）を、メモの「道筋の表」の最初の行に書きます（段 4）。

### 段 3: 本体を読む（深さ 0）

本体（`def` から関数の終わりまで）を全部読みます。

- **仮引数**: ツールの入力（スキーマ）になる引数はモデルが決める値です。`ctx: Context` など、フレームワークが入れる引数は
  モデルが決めません。既定値も見ます（14.3: 既定値で効果が起きるなら条件は `なし`）。
- **docstring・コメント・ツールの説明文は、ツールが何をするかの根拠にしない**。「read-only」と書いてあっても、決めるのはコードの行
  です（どこを読むかの手がかりにはしてよい）。
- **自前のデコレータ**（`@mcp.tool(...)` のようなライブラリのもの以外）が付いていれば、その定義を開いて wrapper の中身も読みます。
  wrapper は**深さに数えません**が、中の動作はツールの呼び出しで実行されるので**読む範囲に入れます**（手引き 18.2 の 2、D86 の 16）。
  wrapper の本体は本体と同じ深さ 0 として扱い、wrapper が呼ぶ関数を深さ 1 と数えます。
- **サーバ全体の middleware**: 【手引きに無い】（O48 (1)）手引きが読むとしているのは「wrapper（デコレータなど）」で、middleware には
  触れていません。仮の扱い: `FastMCP(..., middleware=[...])` に渡した**木の中の** middleware のクラス（`on_call_tool` など）と、
  木の外のライブラリの middleware に渡した**木の中の関数**（呼び戻し）は、wrapper と同じく深さを足さずに読みます。そのツールの
  サーバを別のサーバに `mount()` していれば、そちらの middleware も同じです。読んだことと範囲を `note` に書きます。
- **早い `return`・`if`・`try`/`except`**: どの条件でどの呼び出しに届くかを、メモに「? 条件」として書きます（段 6 で使う）。
  空の入力・失敗・前提の崩れで効果の前に抜けるものは、条件には数えません（14.3）。
- 本体が呼ぶものを全部書き出し、**木の中の関数**か**木の外のライブラリ**かに分けます（段 4）。

### 段 4: 木の中の呼び出し先を深さ 4 までたどる

**深さの数え方**（手引き 18.2 の 2「深さは解析器の数え方で数える」）:

| 形 | 数え方 |
|---|---|
| 本体 | 深さ 0 |
| 本体が呼ぶ木の中の関数 | 深さ 1。そこから呼ぶ関数が深さ 2 …… 深さ 4 まで |
| `Cls(...)`（構築） | `Cls.__init__` を 1 段と数える |
| `Thread(target=f)` | `f` を 1 段と数える |
| `asyncio.to_thread(f, …)`・`loop.run_in_executor(None, f, …)`・`Executor.submit(f, …)`・`Process(target=f)`・`functools.partial(f, …)` | 1 段と数える。手引きが名前を挙げるのは `Thread` だけですが、「解析器の数え方」の解析器はこれらを `Thread(target=)` と同じ表（`authgap/catalog/transfers.py` の `INDIRECTS`）で扱います（O48 (2) は、この列挙を手引きに書くかだけ）。`f` が木の外の関数なら読まない |
| デコレータの wrapper | 深さに数えない。中身は読む（段 3） |
| `await f(...)` | 普通の呼び出しと同じ |

- **同じ関数に何度も届くときは、いちばん浅い深さで数えます。** 先に深い道で見つけた関数に、あとで浅い道でも届いたら、浅い方の
  深さから数え直して、その関数の呼び出し先を深さ 4 まで読み直します。
- **深さ 4 で止めます。** 深さ 4 より奥（深さ 5 以上）を探しに行く必要はありません（18.3）。読む途中で偶然見つけた深さ 4 より奥の
  違反は、段 7 の `違反（深さ 4 の外）` に使います。
- 1 つの関数が長く、ほとんどがツールの道筋と関係ない分岐なら、届く分岐だけを読み、読んだ行の範囲を表に書きます。

**木の中か外か**: 呼び出しの名前で木の中を検索し（`def <名前>`・`class <名前>`）、木の中に定義があれば木の中です。ファイルの上の
`import` が、木の中に無いパッケージを指していれば木の外です。「定義へ移動」で飛べないことは、木の外の印ではありません（1.3）。

**木の外のライブラリ**の中は読みません。ただし、**ライブラリの関数そのもの**が環境を変えるもの（`requests.put`、`open(…, "w")`、
`sqlite3` の `execute("DELETE …")`、`shutil.rmtree` など）は、呼んでいれば違反の候補として数えます（18.2 の 2）。

- 【手引きに無い】（O48 (3)）**知られていないライブラリの関数**（SDK の `client.get_x(...)`、ほかの人のパッケージの関数など）が
  「環境を変える関数」かどうかの決め方は、手引きに書かれていません（19 は「見落としの判定ではライブラリの中を読まない」と、
  「ライブラリの動作は公式の文書かソースを自分で開けたときだけ確かめたとする」の 2 つを書く）。仮の扱い:
  1. 名前が作成・更新・削除・書き出し・送信（`create_`・`update_`・`delete_`・`write`・`save`・`send` など）か、読み取り
     （`get_`・`list_`・`search`・`read`・`fetch` など）を**はっきり示す**ときは名前で決め、`evidence` に「関数名から」と書く
     （15.1 の POST の「API 名から」（D86）を広げた扱い）。
  2. 名前で決まらなければ、そのライブラリの公式の文書を開いて決め、URL を `evidence` に書く。
  3. それでも決まらず、それで答えが変わるなら `不明`（類は、相手のサーバへの API なら `相手の API`、それ以外は `外の値`）。
  4. 文書を読んでいてライブラリの**中で**書き込み（キャッシュのファイルなど）を見つけても、読む範囲の外なので答えは変えず、
     `note` に書く。
  呼び出し側の docstring・コメントは、どこを調べるかの手がかりにはしてよいが、根拠にはしません（段 3）。

**受け手の型を確かめる**（手引き 12.2、E3）: `self.client.fetch()` なら、`self.client` に何が入るか（`__init__` の
`self.client = ApiClient(...)` など）を見てから `ApiClient.fetch` を開きます。組み込みの `set()`・`dict.get()`・`list.append()` を、
木の中の同じ名前のメソッドと取り違えないようにします。受け手が決まらず、呼び出し先が決められないときは 19 の「動的な呼び出し」です。

**メモの「道筋の表」**（1 行 = 読んだ関数 1 つ）:

```
深さ | 関数              | ファイル:行        | どこから呼ばれるか     | 条件（?）            | 環境を変えうる行
0    | search_notes      | server.py:24-26    | （本体）               |                      |
1    | _lookup           | server.py:16-20    | server.py:26           | なし                 | server.py:17 sqlite3.connect（作成?）
2    | _save_cache       | server.py:10-13    | server.py:19           | なし                 | server.py:11 makedirs、12 open(…,"w")
```

（例は手引き 20.1 の練習用のサーバ。）この表がそのまま `evidence` の材料になります。

### 段 5: 環境を変えうる行を探す

段 4 で読んだ関数の中（と、木の外のライブラリの呼び出し）から、**呼び出しの後に残るものを変えうる行**を全部拾います（15.1 の問い:
ホストのファイル・DB・相手のサーバの状態・残る設定）。読みながら拾い、最後に下の一覧で見落としが無いかを確かめます。**この一覧は
探すための手がかりで、規則ではありません**（反するかは段 6 で 15.1 の表で決める）。

| 種類 | 探す形の例 |
|---|---|
| ファイル | `open(` のモード（`"w"`・`"a"`・`"x"`・`"+"`。`"r"` は読み取り）、`.write_text(`・`.write_bytes(`・`.touch(`、`mkdir`・`makedirs`、`unlink`・`os.remove`・`rmtree`、`rename`・`replace`・`shutil.copy`・`shutil.move`、`json.dump(`・`pickle.dump(`（ファイルへ）、`to_csv(`・`savefig(`、`tempfile.`、`chmod` |
| DB | `.execute(` の SQL（`INSERT`・`UPDATE`・`DELETE`・`CREATE`・`DROP`・`ALTER`・`REPLACE`・残る `PRAGMA`）、`sqlite3.connect(`（無いファイルを作る）、ORM の `.add(`・`.delete(`・`.save(`（`.commit()` だけでは変更ではない。何を確定するかを見る）、グラフ DB の `CREATE`・`MERGE`・`SET`・`DELETE`、キーと値の DB の書き込み |
| HTTP・外部 | `requests` / `httpx` / `aiohttp` の `.post(`・`.put(`・`.patch(`・`.delete(`・`.request("POST", …)`、GraphQL の `mutation`、SDK の `create_*`・`update_*`・`delete_*`・`put_*`・`send_*`、メール・メッセージの送信、外のログ・エラー収集のサービス（Sentry など）・syslog への送信 |
| プロセス・コード | `subprocess.`・`os.system(`・`os.popen(`・`asyncio.create_subprocess_`、`eval(`・`exec(` |
| ログ | `logging.FileHandler`・`RotatingFileHandler`・`basicConfig(filename=…)`・`dictConfig`、loguru の `logger.add(<パス>)`。**モジュールの一番上の設定も確かめる**（18.3）。検索は 1.3 の 4 の形で、**ツールの道筋にあるモジュールと、そのパッケージ**（と、そのモジュールが import するログの設定のモジュール）に絞ります。木の中に別のサーバがたくさんある木（monorepo）で木全体を検索すると、関係のない別のサーバの設定が混ざります |
| 状態の保存 | トークン・セッションの保存（16.1 の例）、ディスクのキャッシュ（`diskcache`・`requests_cache` は SQLite のファイル・`joblib.Memory`） |

**数えないもの**（15.1）: プロセスのメモリの中の状態（モジュール水準の辞書・`lru_cache` など。D76 の 2）、標準出力・標準エラーへの
ログ、クライアントへの通知（`ctx.info()` など）、ファイルの読み取り、HTTP の `GET`・`HEAD`・`OPTIONS`（`GET` で何かを作る API でも
反しない。15 の前書き）、DB の読み取り（`SELECT`）、DB の接続単位の設定・トランザクション（`BEGIN`・`COMMIT`・
`PRAGMA foreign_keys=ON` など）。

### 段 6: 動作ごとに、届くか・反するかを決め、ラベルを付ける

段 5 で拾った動作の 1 つずつについて、メモに次の 6 つを書きます。

1. **行**: `ファイル:行` と、その行が何をするか（例 `cache.py:42 open(path, "w")`）。
2. **深さ**: 段 4 の表の、その行がある関数の深さ（いちばん浅い深さ）。
3. **届くか**（手引き 14）: そのツールが呼ばれたとき、その効果が起きる実行の道が 1 つでもあれば届く（14.1）。
   - ツールが積んだもの・始めたもの（キュー・スレッド・プロセス）を、呼び出しが返った後に別のスレッド・プロセスが書くのも届く（14.1）。
   - **届かない形**（14.2）: 呼び出し先の取り違え、死んだコード（CLI・テストからだけ呼ばれる。木の中を検索して確かめる）、
     定数で閉じた枝（`if DEBUG:` で `DEBUG = False` がどこでも書き換えられない。ただし運用者が書き換える前提の `config.py` の
     定数は `運用者の設定`）、効果の前に必ず `return`・`raise` する。
   - 「一度だけ」の守り（`if self._x is None:`・`global _initialized`・`@lru_cache`）の中なら、14.4 の表で決めます: 初期化が
     `main()` の中だけ → 届く（`起動の方法`）、lifespan・モジュールの読み込み時 → 届かない、`mcp` を包む部品の起動フックの中 →
     届く（`起動の方法`。D86）。lifespan が条件つきなら届きうる。初期化の後にどこかで `None` に戻すなら再び届く（`atexit`・テストの
     中は数えない）。読み切れなければ不明。
   - **条件の種類**は 14.3 の表から選びます: `なし` / `引数` / `初回` / `失敗・期限切れ` / `外部の状態` / `運用者の設定` / `起動の方法`。
     **14.3 の「迷いやすい条件の書き方」の表をそのまま当てます**。とくに:
     - 行は毎回実行されるが環境が変わるのは一部（`makedirs(exist_ok=True)`・`CREATE TABLE IF NOT EXISTS`・`unlink(missing_ok=True)`）
       → 変わる場合の条件（`初回` / `外部の状態`）。
     - 空の入力・失敗・前提の崩れで効果の前に抜ける → 条件に数えない。
     - 引数の既定値で効果が起きる（`save: bool = True`）→ `なし`。
     - 既定では起きるが設定で止められる（`if not NO_CACHE:`）→ `運用者の設定` を書かない。
     - ツールの登録そのものが設定しだい、運用者が置く目印のファイル・任意の依存・`config.py` の定数 → `運用者の設定`。
     - 「または」でつながる条件 → 一番弱い道の条件だけ。「かつ」で重なる条件 → 全部を `;` で並べる。
     - 1 つの条件が 2 つ以上の種類に読めるときは **1 つだけ**、表の上からの順で先のもの（14.3 の最後の段落）。
4. **反するか**（15 の前書きと 15.1。表の行と問いの文が違えば表の行を採る）:
   - ファイルの書き込み・作成・削除・移動・権限の変更（ログ・キャッシュ・一時ファイル・ディレクトリの作成も含む）、DB のデータ・
     スキーマ・残る設定の変更、`PUT`・`PATCH`・`DELETE`、コードの実行は反する。同じ呼び出しの中で作って消す一時ファイルも、
     D1 では反する（15.1、14.5）。
   - `POST` は相手の API の意味で決める（作成・更新・削除なら反する、照会なら反しない、分からなければ不明。名前がはっきり示す
     ときだけ API 名で決めてよく、`evidence` に「API 名から」と書く。D86）。認証・トークン・ログインの `POST`、外のログ・
     エラー収集のサービスへの送信も同じ（相手の文書で決め、無ければ不明）。
   - プロセスの起動: コマンドをモデルが決められるなら反する。定数なら、そのコマンドが実際に何をするかを調べ、環境を変えるなら反する・
     変えないなら反しない・分からなければ不明。コマンドを運用者が設定で決めるなら、既定値・設定の見本・文書で分かればそれで決め、
     分からなければ不明（類は `外の値`。D86）。定数のコマンドにモデルが渡せる引数・オプションに環境を変えるもの（`--output=` など）
     があれば反する。子プロセスに標準入力で渡す形は、子プロセスの動作を全部数える。
5. **書き込み先の種類**（16.1 を**上から順に**当て、最初に当てはまったもの）: `相手側の状態` → `データベース` → `利用者のファイル` →
   `ログ` → `一時ファイル` → `キャッシュ・状態の保存` → `プロセスの起動・コードの実行` → `その他・不明`。「読み返す」の主語は判定
   しているツールだけ。境界は 16.2 の表。名前（`cache` など）ではなく動作で決める（20.1 の例）。決められなければ `その他・不明` にし、
   `note` の先頭に「その他:」か「不明:」を書く。
6. **決められないことがあれば**、何が決められないか（例: 書き先がライブラリの戻り値で決まる）。

### 段 7: 答えを決める

【実態調査の当てはめ】答えは D82・D85 の値です。

| 答え | いつ |
|---|---|
| `違反` | 深さ 4 の中に、届いて D1 に反する動作が 1 つでもある |
| `違反（深さ 4 の外）` | 届いて反する動作が、深さ 4 より奥にだけある（偶然見つけたとき。探しに行かない。D68 の 2・18.3） |
| `不明` | 反しうる動作があるが、届くか・反するかを決められない（段 8）。違反は見つかっていない |
| `違反でない` | 反しうる動作が無い（段 5 で何も拾わなかった、または拾った動作が全部「届かない」か「反しない」と決まった） |
| `対象外` | 名簿の件がツールの宣言ではない（段 2） |

- 1 つのツールに違う結果の動作が混ざるときは、`違反` ＞ `不明` ＞ `違反でない` の順で先のものにします（18.2 の 5 の「見落とし ＞ 不明 ＞
  …」の順を当てはめたもの）。深さ 4 の中に違反があり、外にもあれば、中のものを主にし、外のものは `note` に書きます（18.3）。
- **最初に見つけた違反で止めてかまいません**（D82）。止めてよいのは、段 4〜6 の途中で、ある動作が**届く（段 6 の 3）かつ反する（段 6 の 4）
  と決まった時点**です。そこで段 9 に進み、ラベル（条件の種類・書き込み先の種類・深さ）は**その動作から取り**、`note` に「最初の違反で
  止めた（深さ N まで読んだ）」と書きます。読まなかった位置に条件の弱いものがありうるので、(B)(C) の数は下限として報告されます。
- **止めなかったとき**（違反を複数見つけたとき）は、**条件の一番弱い動作**のラベル・深さを書きます。弱い順は `なし` → `引数` → `初回` →
  `失敗・期限切れ` → `外部の状態` → 運用者が決める条件（`運用者の設定`・`起動の方法`）。同じ強さなら、最初に反すると分かった動作の
  ものです（18.2 の 7、手順 G）。
- **止めるかどうかは、W-01 の前に決めて、T でも同じにします。** どちらにしたかを `stopped_early`（`はい` / `いいえ` / `違反なし`）に
  書きます。D82 は止めることを許しているだけで、どちらがよいかは決めていません。本番でどちらにするかを決めるのは封の前です。

### 段 8: 20〜30 分で決まらないとき

手引き 19: **「調べれば分かるものを不明にしない。目安として、20〜30 分調べても決められなければ不明にし、理由を書く」**。20〜30 分は
目安で、判定の規則は変えません（D76）。

- 20 分・30 分を過ぎた時点で、何に時間を使っていたかを `note` に一言書きます（例「20 分: client.py の受け手を探していた」）。
  30 分を過ぎても続けたら、その理由と、答えが決まった時刻を `note` に書きます。時間を測る練習なので、**分数は打ち切らずにそのまま
  記録します**。
- 理由の類は 1 つ選び、`unknown_reason` の先頭に書きます: `外の値` / `相手の API` / `起動・初期化` / `動的な呼び出し` /
  `手引きで決まらない` / `その他`（`打ち切り` は解析器の打ち切りの類なので、実態調査では使いません。【実態調査の当てはめ】）。
- 実態調査（見落としと同じ手順）では、**木の外のライブラリの中は読みません**（19 の「調べる範囲」）。ライブラリの動作・API の意味は、
  公式の文書かソースを自分で開けたときだけ「確かめた」とし、開いた URL かパスを `evidence` に書きます（19。ライブラリの関数の決め方の
  仮の扱いは段 4）。
- 手引きのどの規則にも当てはまらない事例は `不明` にし、`unknown_reason` に「手引きで決まらない: <事例>」と書きます（22）。

### 段 9: 記録を書く（ラップを取る）

【実態調査の当てはめ】答えごとに書く欄（手引き 18.4 を実態調査の答えに当てはめたもの）:

| 答え | 書く欄 |
|---|---|
| `違反` | `outcome`・`write_target`・`condition_type`・`condition`・`depth`・`evidence` |

`evidence` の書き方の例（練習用のサーバ。手引き 20.1）:

- 違反: `server.py:26 _lookup(query) → server.py:19 _save_cache(query, …) → server.py:12 open(os.path.join(CACHE_DIR, name), "w")。CACHE_DIR は ~/.demo_cache。毎回届く。`
- 違反でない（読んだ範囲を書く）: `読んだ範囲: a.py:10-40（深さ 0）、b.py:5-60（深さ 1 の fetch・get_json）、c.py:12-30（深さ 2）。HTTP は GET だけ（b.py:33 requests.get）。ログは標準エラー（a.py:3 basicConfig(stream=sys.stderr)）。環境を変える行は無い。`
- 不明: `unknown_reason: 相手の API: b.py:45 の POST /api/v1/run の意味が、相手の文書（<URL>）にもコードにも無い。` と、`evidence` に道筋。

段 9 を書き終えたら、ストップウォッチのラップを取り、そこまでの分数を `t_noai` に書きます（AI の点検をしないなら、これがそのまま
`minutes` です）。

### 段 10: （任意）AI に点検させる

段 9 を書き終えてから（手引き 18.2 の 8、事前登録の下書き (e) の AI の 3）。

| 名前 | 例 |

| `引数` | `if output_file:`・`if mode == "save":` |

**書き込み先の種類**（16.1。上から順に当てはめ、最初に当てはまったもの）

`相手側の状態` → `データベース` → `利用者のファイル` → `ログ` → `一時ファイル` → `キャッシュ・状態の保存` →
`プロセスの起動・コードの実行` → `その他・不明`

**不明の理由の類**（19）: `外の値` / `相手の API` / `起動・初期化` / `動的な呼び出し` / `手引きで決まらない` / `その他`

**よくある読み違い**（手引き 11.3・14・15・16・20 から）

- docstring の「read-only」を根拠にする → コードの行で決める。
- 「ログに 1 行足すくらいは違反と言えない」→ 原理を字義どおりに当てる。軽重はラベルで表す（11.3）。
- `sqlite3.connect` を読み取りだと思う → 無いファイルを作る（条件つきで反する。15.1）。
- 一時ファイルは消すから問題ない → D1 では反する（15.1・14.5）。書き込み先の種類は `一時ファイル`。
- 「cache」という名前だから `キャッシュ・状態の保存` → 判定しているツールが読み返すかで決める（20.1）。
- `logging` は全部標準エラー → ツールの道筋のモジュールの一番上の設定（`FileHandler`・`basicConfig(filename=…)`・`logger.add(<パス>)`）を
  確かめる（18.3）。
- 起動時の初期化は全部届かない → `main()` の中だけなら届く。lifespan とモジュールの読み込み時は届かない（14.4）。
- `POST` は全部反する → 照会の `POST`（検索 API など）は反しない。決めた根拠を書く（15.1）。
- プロセスのメモリの中の辞書を変えるのは違反 → 数えない（D76 の 2）。
