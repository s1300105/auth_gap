### 段 1: 名簿の行を読む（時計を動かす）

表の 1 行から次を読みます。本番の名簿（`scripts/survey_roster.py`、D85）の 1 件と同じ中身です。

### 段 2: 対象外でないかを確かめ、本体を見つける

1. `roster_relpath:decl_lineno` を開き、宣言の行を見ます。**その宣言が、本当にこのツールの登録に付いているか**を確かめます。
   - `decorator`: `def` の真上のデコレータの中に宣言がある。そのデコレータが MCP のサーバ（`FastMCP(...)` などの
     インスタンスの `.tool(...)`）の登録か。
   - `call_register`: `mcp.tool(annotations={...})(fn)` の行。`fn` はファイルの上の `import`（例 `from .tools.x import fn`）を
     たどって、本体のファイルを開きます。途中で同じ名前に別のものを代入していないかも見ます。
2. **対象外**になるのは、名簿の件がツールの宣言ではないとき（ツールとして登録されていない、例・設定の辞書だけ、
   テスト用の別のサーバなど。D85）。対象外なら段 9 へ（`outcome` に `対象外`、`evidence` に理由と行）。
3. 本体の `def` の行（ファイルと行）を、メモの「道筋の表」の最初の行に書きます（段 4）。

### 段 3: 本体を読む（深さ 0）

本体（`def` から関数の終わりまで）を全部読みます。

- **仮引数**: どれがモデルが決める値か（MCP のツールの引数はすべてモデルが決める）。既定値も見ます。
- **docstring・コメント・ツールの説明文は根拠にしない**。「read-only」と書いてあっても、決めるのはコードの行です。
- **自前のデコレータ**（`@mcp.tool(...)` のようなライブラリのもの以外）が付いていれば、その定義を開いて wrapper の中身も
  読みます。wrapper は**深さに数えません**が、中の動作はツールの呼び出しで実行されるので**読む範囲に入れます**
  （手引き 18.2 の 2、D86 の 16）。wrapper の本体は本体と同じ深さ 0 として扱い、wrapper が呼ぶ関数を深さ 1 と数えます。
- **サーバ全体の middleware**（`FastMCP(..., middleware=[...])` に渡したクラスの `on_call_tool` など）: 【手引きに無い】
  手引きが読むとしているのは「wrapper（デコレータなど）」で、middleware には触れていません。middleware も各ツールの呼び出しで
  走るので、**木の中にある middleware は wrapper と同じく深さを足さずに読み**、読んだことと範囲を `note` に書くことを勧めます
  （`docs/open_questions.md` O48 の (1)。封の前に学生が決める）。木の外のライブラリが用意した middleware のクラスの中は
  読みません。
- **早い `return`・`if`・`try`/`except`**: どの条件でどの呼び出しに届くかを、メモに「? 条件」として書きます（段 6 で使う）。
- 本体が呼ぶものを全部書き出し、**木の中の関数**か**木の外のライブラリ**かに分けます（段 4）。

### 段 4: 木の中の呼び出し先を深さ 4 までたどる

**深さの数え方**（手引き 18.2 の 2。解析器の数え方）:

| 形 | 数え方 |
|---|---|
| 本体 | 深さ 0 |
| 本体が呼ぶ木の中の関数 | 深さ 1。そこから呼ぶ関数が深さ 2 …… 深さ 4 まで |
| `Cls(...)`（構築） | `Cls.__init__` を 1 段と数える |
| `Thread(target=f)` | `f` を 1 段と数える |
| `asyncio.to_thread(f, …)`・`loop.run_in_executor(None, f, …)`・`Executor.submit(f, …)`・`Process(target=f)`・`functools.partial(f, …)` | 【手引きに無い】手引きが名前を挙げるのは `Thread` だけ。解析器はこれらを `Thread(target=)` と同じ「間接の呼び出し」の表（`authgap/catalog/transfers.py` の `INDIRECTS`）で扱うので、同じく 1 段と数える。出会ったら `note` に「間接の呼び出しを 1 段と数えた」と書く（O48 の (2)）。`f` が木の外の関数なら読まない |
| デコレータの wrapper | 深さに数えない。中身は読む（段 3） |
| `await f(...)` | 普通の呼び出しと同じ |

**木の中か外か**: 「定義へ移動」で `corpus/<tree>/` の中に飛べば木の中、`site-packages` に飛ぶ・定義が見つからなければ
木の外です。ファイルの上の `import` でも分かります（`from .x import y`・`from <パッケージ名>.x import y` で、その
パッケージが木の中にあれば木の中）。

**木の外のライブラリ**の中は読みません。ただし、**ライブラリの関数そのもの**が環境を変えるもの（`requests.put`、
`open(…, "w")`、`sqlite3` の `execute("DELETE …")`、`shutil.rmtree` など）は、呼んでいれば違反の候補として数えます
（18.2 の 2）。

- 【手引きに無い】あまり知られていないライブラリの関数（`somelib.get_report(...)` など）が「環境を変える関数」かどうかを、
  中を読まずにどう決めるかは、手引きに書かれていません（19 の「調べる範囲」は、見落としの判定ではライブラリの中を読まない、
  とだけ書く）。名前・呼び出し側のコメントや docstring・そのライブラリの公式の文書（開いたら URL を `evidence` に書く）で決め、
  決められなければ `不明`（類は `外の値`）にし、どう決めたかを `note` に書きます（O48 の (3)）。

**受け手の型を確かめる**（手引き 12.2、E3）: `self.client.fetch()` なら、`self.client` に何が入るか（`__init__` の
`self.client = ApiClient(...)` など）を見てから `ApiClient.fetch` を開きます。組み込みの `set()`・`dict.get()`・
`list.append()` を、木の中の同じ名前のメソッドと取り違えないようにします。受け手が決まらず、呼び出し先が決められない
ときは手引き 19 の「動的な呼び出し」を考えます。

**メモの「道筋の表」**（1 行 = 読んだ関数 1 つ）:

```
深さ | 関数              | ファイル:行        | どこから呼ばれるか     | 条件（?）            | 環境を変えうる行
0    | search_notes      | server.py:24-26    | （本体）               |                      |
1    | _lookup           | server.py:16-20    | server.py:26           | なし                 | server.py:17 sqlite3.connect（作成?）
2    | _save_cache       | server.py:10-13    | server.py:19           | なし                 | server.py:11 makedirs、12 open(…,"w")
```

（例は手引き 20.1 の練習用のサーバ。）この表がそのまま `evidence` の材料になります。

- **深さ 4 で止めます。** 深さ 5 より奥を探しに行く必要はありません（18.3）。読む途中で偶然見つけた深さ 5 より奥の
  違反は、段 7 の `違反（深さ 4 の外）` に使います。
- 同じ関数に何度も届くときは 1 回読めば十分です（表には最初の深さで書く）。
- 1 つの関数が長く、ほとんどがツールの道筋と関係ない分岐なら、届く分岐だけを読み、読んだ行の範囲を表に書きます。

### 段 5: 環境を変えうる行を探す

段 4 で読んだ関数の中（と、木の外のライブラリの呼び出し）から、**呼び出しの後に残るものを変えうる行**を全部拾います
（15.1 の問い: ホストのファイル・DB・相手のサーバの状態・残る設定）。読みながら拾い、最後に下の一覧で見落としが無いかを
確かめます。**この一覧は探すための手がかりで、規則ではありません**（反するかは段 6 で 15.1 の表で決める）。

| 種類 | 探す形の例 |
|---|---|
| ファイル | `open(` のモード（`"w"`・`"a"`・`"x"`・`"+"`。`"r"` は読み取り）、`.write_text(`・`.write_bytes(`・`.touch(`、`mkdir`・`makedirs`、`unlink`・`os.remove`・`rmtree`、`rename`・`replace`・`shutil.copy`・`shutil.move`、`json.dump(`・`pickle.dump(`（ファイルへ）、`to_csv(`・`savefig(`、`tempfile.`、`chmod` |
| DB | `.execute(` の SQL（`INSERT`・`UPDATE`・`DELETE`・`CREATE`・`DROP`・`ALTER`・`REPLACE`・残る `PRAGMA`）、`sqlite3.connect(`（無いファイルを作る）、ORM の `.add(`・`.commit(`・`.save(`・`.delete(`、グラフ DB の `CREATE`・`MERGE`・`SET`・`DELETE`、キーと値の DB の書き込み |
| HTTP・外部 | `requests` / `httpx` / `aiohttp` の `.post(`・`.put(`・`.patch(`・`.delete(`・`.request("POST", …)`、GraphQL の `mutation`、SDK の `create_*`・`update_*`・`delete_*`・`put_*`・`send_*`、メール・メッセージの送信 |
| プロセス・コード | `subprocess.`・`os.system(`・`os.popen(`・`asyncio.create_subprocess_`、`eval(`・`exec(` |
| ログ | `logging.FileHandler`・`RotatingFileHandler`・`basicConfig(filename=…)`・`dictConfig`、loguru の `logger.add(<パス>)`。**モジュールの一番上の設定も確かめる**（18.3。木の中を `FileHandler\|basicConfig\|logger.add\|dictConfig` で検索） |
| 状態の保存 | トークン・セッションの保存（16.1 の例）、ディスクのキャッシュ（`diskcache`・`requests_cache` は SQLite のファイル・`joblib.Memory`） |

**数えないもの**（15.1 の迷いやすい形）: プロセスのメモリの中の状態（モジュール水準の辞書・`lru_cache` など。D76 の 2）、
標準出力・標準エラーへのログ、クライアントへの通知（`ctx.info()` など）、ファイルの読み取り、HTTP の `GET`・`HEAD`。

### 段 6: 動作ごとに、届くか・反するかを決め、ラベルを付ける

段 5 で拾った動作の 1 つずつについて、メモに次の 6 つを書きます。

1. **行**: `ファイル:行` と、その行が何をするか（例 `cache.py:42 open(path, "w")`）。
2. **深さ**: 段 4 の表の、その行がある関数の深さ。
3. **届くか**（手引き 14）: ツールの呼び出しで届きうるなら届く。条件があれば種類を 14.3 の表から選ぶ:
   `なし` / `引数` / `初回` / `失敗・期限切れ` / `外部の状態` / `運用者の設定` / `起動の方法`。重なれば `;` で並べる。
   - 「一度だけ」の守り（`if self._x is None:`・`global _initialized`・`@lru_cache`）の中なら、**その初期化がツールの
     受付より前に必ず済んでいるか**を 14.4 の表で決める（`main()` の中だけ → 届く、lifespan・モジュールの読み込み時 → 届かない）。
   - 行は毎回実行されるが環境が変わるのは一部（`makedirs(exist_ok=True)`・`CREATE TABLE IF NOT EXISTS`・
     `unlink(missing_ok=True)`）なら、変わる場合の条件（`初回` / `外部の状態`。14.3 の迷いやすい形）。
   - 条件が何で決まるか読み切れなければ、決められない（段 8・不明）。
4. **反するか**（15.1 の表）: ファイルの書き込み・作成・削除（ログ・キャッシュ・一時ファイル・ディレクトリの作成も含む）、
   DB の変更、`PUT`・`PATCH`・`DELETE`、コードの実行は反する。`POST` は相手の API の意味で決める（作成・更新・削除なら反する、
   照会なら反しない、分からなければ不明。名前がはっきり示すときだけ API 名で決めてよく、`evidence` に「API 名から」と書く。D86）。
   プロセスの起動は、コマンドをモデルが決められるなら反する、定数ならそのコマンドが何をするかで決める。
   同じ呼び出しの中で作って消す一時ファイルも、D1 では反する（15.1、14.5）。
5. **書き込み先の種類**（16.1 を**上から順に**当て、最初に当てはまったもの）: `相手側の状態` → `データベース` →
   `利用者のファイル` → `ログ` → `一時ファイル` → `キャッシュ・状態の保存` → `プロセスの起動・コードの実行` →
   `その他・不明`。「読み返す」の主語は判定しているツールだけ。境界は 16.2 の表。名前（`cache` など）ではなく動作で決める
   （20.1 の例）。決められなければ `その他・不明` にし、`note` の先頭に「その他:」か「不明:」を書く。
6. **決められないことがあれば**、何が決められないか（例: 書き先がライブラリの戻り値で決まる）。

### 段 7: 答えを決める

| 答え | いつ |
|---|---|
| `違反` | 深さ 4 の中に、届いて D1 に反する動作が 1 つでもある |
| `違反（深さ 4 の外）` | 届いて反する動作が、深さ 4 の外にだけある（偶然見つけたとき。探しに行かない。D68 の 2・18.3） |
| `不明` | 反しうる動作があるが、届くか・反するかを決められない（段 8）。違反は見つかっていない |
| `違反でない` | 反しうる動作が無い（段 5 で何も拾わなかった、または拾った動作が全部「届かない」か「反しない」と決まった） |
| `対象外` | 名簿の件がツールの宣言ではない（段 2） |

- 1 つのツールに違う結果の動作が混ざるときは、`違反` ＞ `不明` ＞ `違反でない` の順で先のものにします（18.2 の 5 の
  「見落とし ＞ 不明 ＞ …」の順を実態調査の答えに当てたもの）。
- **最初に見つけた違反で止めてかまいません**（D82）。止めたら、ラベル（条件の種類・書き込み先の種類・深さ）は
  **その位置から取り**、`note` に「最初の違反で止めた（深さ N まで読んだ）」と書きます。読まなかった位置に条件の弱いものが
  ありうるので、(B)(C) の数は下限として報告されます（手順 G と同じ）。**止めるかどうかは、W-01 の前に決めておき、
  P-M02 でも同じにしてください**（本番と同じやり方で時間を測るため）。止める方が本番の手順に近く、時間も短くなります。
- 深さ 4 の中に違反があり、外にもあれば、中のものを主にし、外のものは `note` に書きます（18.3）。

### 段 8: 20〜30 分で決まらないとき

- 段 1 から 20 分たっても答えが決まりそうにないときは、「あと 10 分で決められるか」を考えます。**30 分で決まらなければ
  `不明` にして理由を書きます**（手引き 19）。ただし、調べれば分かるもの（開いていないファイルがある、など）は不明にしません。
- 理由の類は 1 つ選び、`unknown_reason` の先頭に書きます: `外の値` / `相手の API` / `起動・初期化` / `動的な呼び出し` /
  `手引きで決まらない` / `その他`（`打ち切り` は解析器の打ち切りの類なので、実態調査では使いません）。
- 実態調査（見落としと同じ手順）では、**木の外のライブラリの中は読みません**（19 の「調べる範囲」）。ライブラリの動作・
  API の意味は、公式の文書かソースを自分で開けたときだけ「確かめた」とし、開いた URL かパスを `evidence` に書きます。
- 手引きのどの規則にも当てはまらない事例は `不明` にし、`unknown_reason` に「手引きで決まらない: <事例>」と書きます（22）。

### 段 9: 記録を書く（ラップを取る）

答えごとに書く欄（手引き 18.4 を実態調査の答えに当てたもの）:

| 答え | 書く欄 |
|---|---|
| `違反` | `outcome`・`write_target`・`condition_type`・`condition`・`depth`・`evidence` |
| `違反（深さ 4 の外）` | `違反` と同じ |
| `違反でない` | `outcome`・`evidence`（**読んだ範囲**を必ず書く） |
| `不明` | `outcome`・`unknown_reason`・`evidence` |
| `対象外` | `outcome`・`evidence`（理由と行） |
| どれでも | `minutes`・`ai_used`（`あり` なら `ai_model`・`ai_log`）、練習だけの `t_` の欄。`note` は迷ったときだけ |

- `target_by_arg`（D84）は**実態調査の違反には付けません**（学生の選択）。`cause`（見落としの原因）も、解析器と比べる
  欄なので書きません。
- `condition_type` は 14.3 の 7 つの名前で書き、`condition` に中身（どの引数・どの設定か）を書きます。
- `evidence` は、判定を見ていない第三者がその行を開けば同じ結論に着けるように書きます（手順 H）。パスは木の根からの相対。

`evidence` の書き方の例（練習用のサーバ。手引き 20.1）:

- 違反: `server.py:26 _lookup(query) → server.py:19 _save_cache(query, …) → server.py:12 open(os.path.join(CACHE_DIR, name), "w")。CACHE_DIR は ~/.demo_cache。毎回届く。`
- 違反でない（読んだ範囲を書く）: `読んだ範囲: a.py:10-40（深さ 0）、b.py:5-60（深さ 1 の fetch・get_json）、c.py:12-30（深さ 2）。HTTP は GET だけ（b.py:33 requests.get）。ログは標準エラー（a.py:3 basicConfig(stream=sys.stderr)）。環境を変える行は無い。`
- 不明: `unknown_reason: 相手の API: b.py:45 の POST /api/v1/run の意味が、相手の文書（<URL>）にもコードにも無い。` と、`evidence` に道筋。

段 9 を書き終えたら、ストップウォッチのラップを取り、そこまでの分数を `t_noai` に書きます（AI の点検をしないなら、
これがそのまま `minutes` です）。

### 段 10: （任意）AI に点検させる

段 9 を書き終えてから（手引き 18.2 の 8、事前登録の下書き (e) の 3）。

1. 1.5 の条件で、読んだ関数のコードを伏せてから貼り、事実の問いで聞きます（例:「この関数とそこから呼ばれる関数で、
   ファイル・データベース・外部のサーバに書き込む行はどれ？」）。宣言の値・解析器の出力・自分の結論は渡しません。

3. **`outcome` は変えません。** 深さ 4 の外・決められない動作は `ai_found` に入れず `note` に書きます。
4. AI に聞いた時間を `t_ai` に書きます。

   あります。実態調査の答えに直すと、`反する動作は無い` は `違反でない`、`見落とし` は `違反`、`解析器が不として出している`
   は人が反すると読んだかで `違反` か `違反でない`（理由の文を読む）です。

## 付録: 早見表

**条件の種類**（14.3。表の上ほど弱い。`運用者の設定`・`起動の方法` は運用者が決める条件）

| 名前 | 例 |
|---|---|
| `なし` | 毎回届く |
| `引数` | `if output_file:`・`if mode == "save":` |
| `初回` | キャッシュが無いときだけ、`makedirs(exist_ok=True)` |
| `失敗・期限切れ` | トークンの更新、再試行、エラー時の後始末 |
| `外部の状態` | ファイルが無いとき、相手が特定の応答を返したとき |
| `運用者の設定` | 環境変数・設定ファイル・起動の引数で有効になる |
| `起動の方法` | 初期化が `main()` の中だけにあり、`main()` を通らない起動で届く |

**書き込み先の種類**（16.1。上から順に当てはめ、最初に当てはまったもの）

`相手側の状態` → `データベース` → `利用者のファイル` → `ログ` → `一時ファイル` → `キャッシュ・状態の保存` →
`プロセスの起動・コードの実行` → `その他・不明`

**不明の理由の類**（19）: `外の値` / `相手の API` / `起動・初期化` / `動的な呼び出し` / `手引きで決まらない` / `その他`

**よくある読み違い**（手引き 15.1・16・17・20 から）

- docstring の「read-only」を根拠にする → コードの行で決める。
- `sqlite3.connect` を読み取りだと思う → 無いファイルを作る（条件つきで反する。15.1）。
- 一時ファイルは消すから問題ない → D1 では反する（15.1・14.5）。書き込み先の種類は `一時ファイル`。
- 「cache」という名前だから `キャッシュ・状態の保存` → 判定しているツールが読み返すかで決める（20.1）。
- `logging` は全部標準エラー → モジュールの一番上の設定（`FileHandler`・`basicConfig(filename=…)`・`logger.add(<パス>)`）を確かめる（18.3）。
- 起動時の初期化は全部届かない → `main()` の中だけなら届く。lifespan とモジュールの読み込み時は届かない（14.4）。
- `POST` は全部反する → 照会の `POST`（検索 API など）は反しない。決めた根拠を書く（15.1）。
- プロセスのメモリの中の辞書を変えるのは違反 → 数えない（D76 の 2）。
