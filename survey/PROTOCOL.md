# 実態調査の判定の規則（核）

D1（`readOnlyHint: true`）を宣言したツールを 1 件ずつ読み、宣言に反する動作（呼んだ後に何かが残る動作）に届くかを決める。
**この文書が実態調査の判定の正本**（D95）。手引きの下書き（`docs/drafts/final_judging_guide_draft.md`）と決定（`docs/decisions.md`）から、
**答えを変える規則だけ**を抜き出した。練習の長い手順書は `archive/practice_survey_manual/` に記録として残してある（例として読んでよいが、
食い違ったらこの文書を採る）。

- 印: 【仮】= 手引きにも決定にも規則が無く、今の仮の扱い（`docs/open_questions.md` の O48 の番号）。封の前に学生が決める。
- 答えを変えない細部（読む順・止める時点など）は、判定者の自由。

---

## 1. 対象と起点

1. 判定するのは、名簿の行（`tool`・`roster_relpath`・`roster_lineno`）が指すツールの関数（**本体**）。
   - 宣言の付いた関数が名簿の `tool` と違えば、宣言の付いた方を判定する【仮 O48 (4)】。
   - 同じ名前のツールが木の別の場所にあっても、名簿の位置のものだけを判定する。
   - 1 つの宣言を複数のツールが使う（`unmapped`）ときの選び方は【未決 O48 (5)】。
2. **対象外**: 名簿の件が MCP のサーバへのツールの登録に付いていない（どのサーバにも登録されない）。
   - 登録されていれば、起動の行が木の中に見つからなくても判定する【仮 O48 (4)】。
   - MCP 以外の枠組みにだけ登録しているときは `不明`。それでも深さ 4 まで読み、後ろに違反があれば `違反`【仮 O48 (8)】。
3. **起点（深さ 0）**: 本体、本体を包む木の中のデコレータの wrapper、サーバに付いた木の中の middleware と、木の外の middleware に
   渡した木の中の関数（mount 先の親のものも）【仮 O48 (1)】。`@mcp.tool` より上に付いたデコレータは走らない。
4. ツールの入力（引数）はモデルが決める値。枠組みが入れる引数（`ctx` など）はモデルが決めない【仮 O48 (4)】。引数で関数を受け取る形
   （`recall_fn=None` の既定で木の中の関数を使う、など）は、本体が渡さなければ既定の関数を呼ぶとして読む【仮 O48 (6) N9】。

## 2. 読む範囲

1. **深さ 4 まで**読む。木の中の関数に 1 回降りるごとに 1 段。深さ 4 の関数の中身は読み、その先（深さ 5）は探しに行かない。
2. 深さの数え方:

   | 形 | 数え方 |
   |---|---|
   | `f(...)`・`await f(...)`・`self.f(...)`・`obj.f(...)` | 呼ばれる関数が 1 段（受け手の型を確かめて、どの関数かを決める） |
   | `Cls(...)`（構築） | `Cls.__init__` が 1 段。木の中に `__init__` が無くても、構築で走る木の中のコード（`__post_init__`・`default_factory` の関数・pydantic の検証子）は 1 段【仮 O48 (6) N1】 |
   | `Thread(target=f)`・`asyncio.to_thread(f, …)`・`run_in_executor(…, f, …)`・`submit(f, …)`・`Process(target=f)`・`partial(f, …)` | `f` が 1 段【仮 O48 (2)】 |
   | `@property` の読み・`with` の `__enter__`/`__exit__`・`obj(...)` の `__call__` | 書かれた位置から 1 段【仮 O48 (6) N1】 |
   | デコレータの wrapper・middleware | 深さに数えない（中は読む。1 の 3） |
   | 同じ関数にいくつもの道で届く | いちばん浅い深さで数える【仮 O48 (4)】 |

3. **木の中か外か**は、名前で木の中を検索して決める（`def 名前`・`class 名前`）。木の中に定義があれば木の中（同梱のコード・テストや
   例のファイルも、呼ばれていれば木の中【仮 O48 (4)】）。「定義へ移動」で飛べないことは、木の外の印ではない。手元に無いファイル
   （`*.yaml`・`logging.conf` など）も木の中として扱う（`git -C corpus/<tree> ls-tree` と `show` で読む）。
4. **木の外のライブラリの中は読まない**。ライブラリの関数は、**その呼び出し自体が**環境を変えるかだけを見る（4 節）。
   ライブラリの中の書き込み（例: ライブラリがキャッシュをファイルに書く）は数えない。数えるかは【未決 O48 (3)】で、数えないなら、
   違反の割合は実際より少なく出る（下限）。
5. **届くか**: ツールが呼ばれたとき、その行が実行される道が 1 つでもあれば届く（毎回でなくてよい）。
   - ツールが積んだもの・始めたもの（キュー・スレッド・プロセス）が呼び出しの後に書くのも届く。
   - 届かない: 呼ばれていない関数（CLI・テストからだけ呼ばれる。呼び出し元を全部検索して確かめる）、定数で閉じた枝、効果の前に必ず
     `return`・`raise` する道、モジュールの読み込み時に走る文（関数の外の文）。
   - ただしツールの中で初めて import するモジュール（遅延 import）の一番上の文は、最初の呼び出しで走りうる（ほかで先に import されて
     いれば届かない）。
   - 一度だけの初期化（`if self._x is None:` など）: `main()` の中だけで済ませる初期化 → 届く。lifespan の中・モジュールの読み込み時 →
     届かない。初期化の後に `None` に戻す行があれば再び届く。

## 3. 環境を変える動作（sink）と、数えないもの

**環境を変える動作 ＝ 呼び出しの後に残る何かを変える動作**（手引き 15.1）。届けば `違反`。

| 種類 | 変える（違反になる） | 変えない（数えない） |
|---|---|---|
| ファイル | 書く・足す・作る・消す・名前を変える・権限を変える（`open` の `w`/`a`/`x`/`+`、`write_text`、`mkdir`、`unlink`、`rename`、`tempfile`、`to_csv` など）。同じ呼び出しの中で作って消す一時ファイルも | 読む（`open` の `r`/`rb`） |
| DB | `INSERT`・`UPDATE`・`DELETE`・`CREATE`・`DROP`・`ALTER`、残る `PRAGMA`、ORM の `add`/`delete`/`save`、無いファイルを作る `sqlite3.connect` | `SELECT`、接続単位の設定、トランザクション（`BEGIN`・`COMMIT`）だけ |
| 相手のサーバ | 作成・更新・削除の要求（`POST`・`PUT`・`PATCH`・`DELETE`。`POST` は **API の意味**で決める。4 節）、メール・メッセージの送信、外のログ収集への送信 | `GET`・`HEAD`・`OPTIONS`（`GET` で何かを作る API でも数えない）、照会の `POST`（検索など） |
| プロセス・コード | プロセスの起動（`subprocess`・`os.system`）、`eval`・`exec` | スレッドの起動だけ |
| ログ | ロガーへの出力で、**このサーバの起動で走るログの設定がファイルに書く**とき | 標準出力・標準エラーへの出力、設定が無いとき（Python の既定は標準エラー） |
| 状態の保存 | トークン・セッションの保存、ディスクのキャッシュ（`diskcache`・`shelve` など） | **プロセスのメモリの中の状態**（モジュール水準の辞書・`lru_cache`・クラスの属性） |
| クライアント | — | クライアントへの通知（`ctx.info()`・`ctx.report_progress()`） |

- **ログの設定は毎回確かめる**（違反で止める件では、その違反より前にロガーへの出力があるときだけ）: 木全体を正規表現
  `FileHandler|basicConfig|logger\.add|dictConfig|fileConfig|addHandler` で検索し、当たりのうち**このサーバの起動で走るもの**を選ぶ。
  手元に無い設定のファイル（`logging.conf`・`*.yaml`・`*.ini`）と起動の定義（`*.service`・`Procfile`・`Dockerfile`・起動のスクリプトの
  `--log-config` など）も `git ls-tree` で探す。ファイルへの設定が `main()` の中だけにあっても届く。
- 判定するのはコードの動作で、docstring・コメント・ツールの説明文は根拠にしない（どこを読むかの手がかりにはしてよい）。

## 4. 木の外の関数・API の意味の決め方

木の外の関数（SDK の `client.sync()` など）が環境を変えるか、`POST` が作成・更新か照会かは、次の順で決める。

1. **名前がはっきり示していれば、名前で決める**【仮 O48 (3)。名前で決めてよいかは未決】。
   - 書き込みを示す: `create_`・`update_`・`delete_`・`write`・`save`・`send`・`put_`・`post_` など
   - 読み取りを示す: `get_`・`list_`・`search`・`read`・`fetch` など
   - `POST` の意味を API 名で決めたら、`evidence` に「API 名から」と添える（手引き 15.1）。
2. 名前で決まらなければ、そのライブラリか相手の API の**公式の文書**を開いて決める。決めた文書の URL を `evidence` に添える。
   - AI に聞いてよい（プロンプト 1。7 節）。ただし **AI の答えだけでは決めない**。AI が挙げた公式の文書の URL を自分で開き、
     文書が答えを支えているときだけ採る。
3. それでも決まらず、それで答えが変わるなら、その動作は「決められない」とする（5 節）。
4. SDK のラッパー（`api_call(...)`・`users_info(...)` など）で HTTP メソッドがコードから見えないときの決め方は【未決】。
   練習では、相手の API の意味（文書）で決めた。

## 5. 答え（`outcome`）の決め方と `不明` の基準

次の順に当て、最初に当てはまったものを答えにする。

| 順 | 当てはまるか | `outcome` |
|---|---|---|
| 1 | 1 節の 2 で対象外 | `対象外` |
| 2 | 深さ 4 の中に、届いて環境を変える動作が 1 つでもある | `違反` |
| 3 | 深さ 4 の中に無く、深さ 4 より奥で**偶然**見つけた環境を変える動作がある（探しに行かない） | `違反（深さ 4 の外）` |
| 4 | 深さ 4 の中に、違反になりうるのに決められない動作がある | `不明` |
| 5 | 上のどれでもない | `違反でない` |

- **決められない**とは: 調べても、届くか、または環境を変えるかが決まらないこと（文書が無い、呼ばれる先が実行時にしか決まらない、
  受け手の型が決まらない など）。調べれば分かるもの（開いていないファイル・文書がある）は決められないにしない。目安は 20〜30 分。
- 届くかを決められなくても、**届いたとしても環境を変えない動作**（`GET`・通知・読み取り）は、`不明` の理由にしない。
- 手引きにも仮の扱いにも規則が無い点で、それで答えが変わるなら、その動作は決められない（`不明` の理由になる）。答えが変わらなければ、
  読み方を決めて進む。
- 「決められない」はその動作についての決め方で、**読むのはやめない**。後ろに違反があれば答えは `違反`。
- 深さ 4 までが大きすぎて読み終えられないときは、やめて `不明` にしてよい【仮 O48 (4)】。
- 違反が 1 つ確かめられたら、そこで読むのをやめてよい（答えは変わらない。D88）。

## 6. 記録（`outcome` と `evidence` だけ）

表は名簿の 9 欄（変えない）＋ `outcome` ＋ `evidence`。段階ごとの考えたこと・時間・ラベル・メモは書かない（D90）。

| `outcome` | `evidence` |
|---|---|
| `違反`・`違反（深さ 4 の外）` | **反する行までの道筋 1 本** |
| `不明` | **決められなかった呼び出しまでの道筋 1 本**（複数あれば読む順で最初のもの） |
| `対象外` | 理由を 1 文（宣言の行と、なぜツールの宣言でないか） |
| `違反でない` | 空 |

- **道筋の形**（D91・D92）: 本体は書かず、本体が呼んだ先から。木の中の関数は定義の行で `ファイル:行 名前`、木の外の関数は
  `名前（外）`、` → ` でつなぎ、最後に `→ ファイル:行: 何をするか`（本体の中の行そのものなら `ファイル:行: 何をするか` だけ）。
  判定した関数が名簿の `tool` と違うときだけ、最初に本体の `ファイル:行 名前` を書く。
  - 例: `notes_server.py:34 _search → notes_server.py:29 _remember_query → notes_server.py:30: open(..., "a") に追記`
  - 例: `client.create_order（外）: 注文を作る／API 名から`
- パスは木の根から（`corpus/<tree>/` は付けない）。1 つのセルに改行を入れない。区切りは全角の「／」。
- 添えてよいのは、公式の文書で決めたときの URL と「API 名から」だけ（最後に「／」で区切る）。
- 書いたら確かめの道具にかける: `.venv/bin/python scripts/check_survey_practice.py <表>`。
- 翌日に見直して答えを変えたら、行を直すだけ（変えたことは書かない）。

## 7. AI の使い方（D95）

AI は判定の材料を集めるのに使ってよい。**記録する答えは人が決める**。プロンプトの文面は `survey/prompts/` に固定し、変えない。

| プロンプト | いつ | 渡すもの | 答えの扱い |
|---|---|---|---|
| 1 木の外の関数（`1_library.txt`） | 4 節の 2 で、木の外の関数・API の意味が分からないとき | パッケージ名、関数の名前、呼び出しの 1 行（引数の中身は伏せる） | 答えに付いた公式の文書の URL を自分で開いて確かめたときだけ採る |
| 2 コード解説（`2_explain.txt`、続けて聞くときは `2_followup.txt`） | 分からないコードに出会ったとき。分からない部分を続けて聞いてよい（同じ件の中は同じ会話） | 分からない部分のコード（行番号つき）と、そのファイルの import の行 | 手がかりにだけ使う。挙げられた行を自分で開いて確かめ、判定は自分でする |
| 3 件の答え（`3_case.txt`） | **人が `outcome` と `evidence` を書いた後**（参考。2 人目の判定者のように使う） | 判定に要るファイルを全部: 本体のファイル、深さ 4 までにたどった木の中の関数のファイル、wrapper・middleware のファイル、ログの設定のファイル | 人の答えと違えば、AI が挙げた行を自分で開いて確かめる。人は答えを変えてよいが、**AI の前の答えはログに残る** |

- **伏せる**: 宣言（`annotations=…`・`readOnlyHint` を含む行）、宣言を述べる docstring・コメント（「read-only」など）、秘密の値。
- **聞かない**: 「読み取り専用か」「宣言に反するか」「正しいか」（プロンプト 3 の決まった文面のほか）。宣言の値・解析器の出力は渡さない。
- **使う AI**: モデルの名前と版【未決（封の前に決める）】。記憶（メモリ）を切る。件ごとに新しい会話（プロンプト 2 の続けての質問は、
  同じ件の中なら同じ会話でよい）。この repo を開いた道具（Claude Code など）は使わない。
- **ログ**（記録はこれだけ）: 1 件 1 ファイル（`ai_logs/<pair_id>.md`）。先頭に件の id・日時・使った AI（名前・版・画面・記憶なし）・
  **AI の前の判定**（プロンプト 3 を使う件のみ。人が書いた `outcome`）を書き、続けて、使ったプロンプトの番号ごとに、渡した入力と答えの
  全文、自分で確かめたか（確かめた URL・行）を書く。消さない。
- 英語の文書の機械翻訳は使ってよい（訳すのは自然言語の文書だけ。コードと宣言は貼らない）。

## 8. 使ってよい道具（D93）

- 使う: 文字の検索（VS Code の検索・`grep`・`git ls-tree`）、エディタの移動（定義へ移動・参照を探す）、AI（7 節のとおり）。
- 使わない: 呼び出しの一覧や書き込みの候補を自動で出す道具（pyan3 などの呼び出しグラフの道具・CodeQL・Semgrep・Bandit・AuthGap）。
  正解（人の判定）を道具に寄せないため。
- 実態調査を全部判定し終えるまで、AuthGap の出力を見ない（D82）。木の中のコードは実行しない。
