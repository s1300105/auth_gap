# 最終評価の手順（学生が行う論文の評価）

作成 2026-09-30。**この文書は手順の地図であって、規則そのものではない。** 規則（分母・抜き取り・判定の基準）は
段階 1 で `docs/preregistration.md` と判定の手引きに書いてコミットし、それが正本になる。

- 下敷き: v4 の中間検証（D66、`docs/population_v4.md`）で実際に踏んだ手順と、最終評価の決め事（D67）。
- 教科書 第 38 章は D67 より前に書いたので、次の 3 点は D67 が優先する: 重大度の列（→ 重みなし・書き込み先のラベル）、
  抜き取りの単位（→ 木ごとに最大 3 件）、報告の単位（→ 木）。
- 解析器は **`analyzer-freeze-3`（9dc3bc3）** のまま使う。**最終評価のどの段階でも `authgap/` を変えない。**

## 全体の流れ

```
 ─── データを見る前（ここで決めたことは後で変えない） ───────────────────────
  段階 0  決めること（学生の判断）
  段階 1  事前登録と判定の手引きを書く                        → コミット
  段階 2  足りない道具を作り、v4 のデータで空回しする          → コミット
 ─── データに触れる（ただし結果はまだ見ない） ─────────────────────────────
  段階 3  抽出と pin                                          → コミット
  段階 4  取得と取得後の条件                                  → コミット
  段階 5  凍結の確認と走査（1 回だけ）                        → コミット
  段階 6  判定の対象の抜き取り                                → コミット
 ─── 結果を見る ─────────────────────────────────────────────────────────
  段階 7  判定（原ソースを読む）                              → コミット
  段階 8  集計
  段階 9  論文に書く
```

**各段階の出力は、次の段階に進む前にコミットする。** 「結果を見てから規則や標本を選んだ」と疑われないための、
この研究の一番大事な約束（CLAUDE.md 規則 5、教科書 第 19 章）。

### 1-b. 判定の手引きを書く（`docs/verification_guide.md` に節を足すか、別の文書）

D67 の 4 のとおり、2 人目がいない分、**第三者が後から同じ判定を再現できる**ように書く。

- **正 / 誤 / 不明の基準**（`docs/contradiction_principles.md` §6 の採った原理どおり。v4 と同じ）:
  - **正**: その経路は実行時に到達し、その動作は宣言に反する。
  - **誤**: 到達しない / 動作が宣言に反しない / 解析器が読み違えた。**原因の分類を書く。**
  - **不明**: 静的に決められない。**理由を書く。黙って正・誤に倒さない**（CLAUDE.md 規則 4）。
- **起動時の初期化**（D67 の 2）:
  - 初期化が `main()` / `if __name__ == "__main__":` の中だけにある → ツールの呼び出しで届きうるので**正**（原理 3）。
  - lifespan の中、またはモジュールの読み込み時にある → **誤**（原因の欄は「起動時の初期化（lifespan / import 時）」）。
  - 読み切れない → **不明**。
- **誤の原因の分類**: v4 で出た類を最初から欄に用意する。起動時の初期化 / 同じ呼び出しで作った一時ファイル・ロックの後始末 /
  末尾名の解決の誤り（組み込みの `set()` を木の中のメソッドに結ぶ等）/ 受け手の型の読み違い / 子プロセスの標準入力を FS_WRITE と
  読んだ / その他（自由記述）。
- **書き込み先の種類**（正の各件に 1 つ。D67 の 1）: 利用者のファイル / データベース / 相手側の状態 / キャッシュ・状態の保存 /
  ログ / 一時ファイル / その他・不明。**境界の例を 1 つずつ添える**（v4 の例: reaper-mcp の IPC 用の mailbox ファイル →
  どの種類にするかを先に決める）。
- **見落としの判定**: 「解析器が不として出している / 見落とし（誤 clear）/ 反する動作は無い / 不明」。見落としの原因は
  「深さ / 呼び出しの解決 / 受け手の型 / 語彙 / その他」。読む範囲はツールの本体と、木の中の呼び出し先を深さ 4 まで。
- **根拠の記録の形**: `evidence/population_v4/v4_judgments.json` と同じ欄にする。
  - 矛: `id, tree, unit, unit_relpath, unit_lineno, site, kind, decl, reasons, verdict, error_class, write_target, evidence, note`
  - 見落とし: `id, tree, unit, decl, relpath, lineno, n_effects, outcome, cause, evidence, note`
  - `evidence` には**ファイルと行**を必ず書く（例 `server.py:549-554`）。

## 段階 3: 抽出と pin

```bash
.venv/bin/python scripts/sample_population_v2.py \
    --n <0-1 で決めた抽出数> --seed <抽出用の seed> \
    --exclude docs/corpus_sample_v2.json \
    --exclude docs/corpus_sample_v3.json \
    --exclude docs/corpus_sample_v4.json \
    --prefix final --out docs/corpus_sample_final.json
```

- pin は抽出時の `git ls-remote <url> HEAD` の SHA（スクリプトが行う）。解決できなかった件は、取得後の条件で件数を出して除く。
- v2・v3・v4 との重なりが 0 であることを確かめる（v4 のコミット 7036aed の確かめ方と同じ）。
- 0-7 で「する」なら、ここか取得後に中身の重複を除き、除いた件数と理由を記録する。
- **`docs/corpus_sample_final.json` をコミットしてから取得する。**

## 段階 5: 凍結の確認と走査（1 回だけ）

```bash
git fetch --tags && git tag -l                  # analyzer-freeze-3 があること
git diff analyzer-freeze-3 -- authgap/          # 出力が空であること（1 行でも出たら止まる）

.venv312/bin/python -u scripts/scan_v2.py \
    --sample evidence/population_final/sample_final_mcp.json \
    --label final_run1 \
    --require-fingerprint docs/fingerprint.json
```

- `docs/fingerprint.json` の `freeze.tag` 欄は `analyzer-freeze-2` と書いてあるが、**正しいタグは `analyzer-freeze-3`**。
  実装の sha256（`35606ba9…`）は freeze-3 の版と一致する（逸脱 #26、教科書 第 38 章）。
- 走査の後、`evidence/scan_v2_final_run1/summary.json` で次を確かめる:
  - `implementation_sha256_combined` が指紋と一致し、`authgap_dirty = False`。
  - **時間上限の打ち切り**（`tree_budget`）の件数と、その木の所要時間。かかる時間はマシンの速さで変わる（D64 の追記）。
    打ち切りがあれば件数を報告に書く（黙って取り直さない）。
  - parse 失敗・例外で落ちた木。
- 走らせたマシン（CPU・メモリ・同時に走らせた本数）も記録しておく。
- 0-10 で深さの感度分析をするなら、`--max-depth 3` と `--max-depth 5` を**同じ条件で**別の label で走らせる
  （`scripts/depth_sensitivity.py` は同時に走らせた run どうしで比べる前提）。
- `summary.json` と `contradictions.json` をコミットする。

## 段階 7: 判定

1 件ずつ、次の順で行う。

1. 対象の欄（木・ユニット・ファイルと行・site・kind・宣言）から、`corpus/<木>/` の原ソースを開く。
2. ツールの入口から、その効果の行まで呼び出しをたどる（manifest の `witness_chain` が道筋の手がかりになる）。
3. **到達するか**（起動時の初期化の規則を含む）、**その動作は宣言に反するか**を判定する。
4. 手引きの欄を埋める。**根拠のファイルと行を必ず書く。** 正なら書き込み先の種類を付ける。
5. 決められなければ「不明」とし、理由を書く。

守ること:

- **手引きを判定の途中で変えない。** 手引きで決まらない事例が出たら、「不明」にしたうえで事例を記録し、
  `docs/preregistration.md` §5 に逸脱として残す（後から規則を足すなら、足した後の判定と前の判定を分けて報告する）。
- **解析器の誤りを見つけても直さない。** `docs/open_questions.md` に限界として書く（O43 と同じ扱い）。
- 判定の記録は `evidence/population_final/final_judgments.json`（形は 1-b）。こまめにコミットする。
