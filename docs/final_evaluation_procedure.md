# 第 1 部 全体像

## 1. 何を確かめる評価なのか

研究の問いは「**MCP サーバのツールが書いている宣言（注釈）は、実装と一致しているか**」である。
たとえば `readOnlyHint: true`（読み取り専用）と宣言したツールが、実際にはファイルを書いていないか。

解析器 AuthGap は、ツールの入口から呼び出しをたどり、宣言に反しうる動作（効果）を見つけると「**矛**」（CONTRADICTION）を出す。
静的に決められないものは「**不**」（不明）として別に数える。

最終評価で確かめるのは次の 3 つである。

| 問い | 名前 | 何をするか |
|---|---|---|
| 解析器が出した「矛」は本当に宣言違反か | **精度**（V2） | 矛を抜き取り、原ソースを読んで「正 / 誤 / 不明」を付ける |
| 解析器が「矛なし」としたツールに、本当は違反が無いか | **見落とし**（V3） | 矛の無いツールを抜き取り、原ソースを読んで違反を探す |
| 解析器が「不」としたものの中身は何か | **不の中身**（V6、D69） | 不の組を抜き取り、原ソースを読んで本当に違反かを決める |
| 解析器は新しいデータで壊れずに動くか | **頑健性**（V1） | 走査の失敗・打ち切りを数える |

加えて、判定しない数（「不」の全件の件数と理由、感度分析、`r_malformed`）を出す。

精度・見落とし・不の中身の 3 つがそろうと、解析器の 3 つの答え（矛・不・何も出さない）のそれぞれが、実際にはどれだけ
当たっていたかを示せる（D69）。

**なぜ人が読むのか**: 静的解析は「通りうる道」を推論するので、実際には通らない道を数えること（誤警報）も、道を見失うこと
（見落とし）もある。人が原ソースで確かめて、はじめて解析器の数字をどこまで信じてよいかが分かる（教科書 第 39 章 Q1）。

## 2. 用語（この文書で使う言葉）

| 言葉 | 意味 |
|---|---|
| **木**（tree） | 解析する 1 つのリポジトリ（1 つの MCP サーバ）。`corpus/<木の名前>/` に取得する |
| **ユニット**（unit） | 1 つのツール。`@mcp.tool(...)` を付けた関数など。manifest の `units[]` の 1 要素 |
| **宣言** | ツールに書かれた注釈。解析器は 4 種を見る（下の D1〜D4） |
| **D1** | `readOnlyHint: true`（環境を変えない） |
| **D2** | `destructiveHint: false`（追加の更新だけをする）。**`readOnlyHint: true` が無いときだけ**当てる |
| **D3** | `openWorldHint: false`（関わる範囲が閉じている） |
| **D4** | `idempotentHint: true`（同じ引数で繰り返しても追加の効果が無い）。**`readOnlyHint: true` が無いときだけ**当てる |
| **効果**（effect） | 解析器が見つけた、環境に作用しうる呼び出し。種類（kind）は `FS_WRITE`（ファイルの書き込み・作成・削除）、`FS_READ`、`DB`、`NET`（HTTP など）、`SPAWN`（プロセスの起動）、`EXEC`（コードの実行）、`DISPATCH` |
| **site** | 効果を起こす関数の名前。例 `builtins.open`、`os.remove`、`requests.post` |
| **slot** | site の引数の役割。例 `path`（書き先）、`sql`、`url.host`、`argv0`（起動するコマンド） |
| **主体**（prin） | slot の値の出どころ。`MODEL`（モデルが渡すツールの引数から来る）/ `OP`（運用者の設定や定数）/ `USER` |
| **確度**（prov） | 値を解析器が読み切れたか。`resolved`（読み切れた）/ `opaque`（途中で見失った） |
| **witness_chain** | ツールの本体から、効果のある関数までにたどった呼び出しの列。例 `_lookup -> _save_cache` |
| **entry_lineno** | ツールの本体の中で、その道筋の最初の呼び出しがある行 |
| **manifest** | 解析器が木ごとに出す JSON（`evidence/scan_v2_<label>/<木>.json`）。大きいので git では追わない |
| **矛 / 内 / 不** | **解析器の**判定。矛 = 宣言に反する、内 = 宣言の範囲内、不 = 静的に決められない |
| **正 / 誤 / 不明** | **人の**判定。正 = 解析器の矛は本当に違反、誤 = 違反ではない、不明 = 人にも決められない |
| **組** | 判定の単位。(木, ユニット, site, kind, 宣言)。同じツールの同じ site・kind の効果が複数の位置にあっても 1 組にまとめる |
| **抜き取り** | 全部を判定できないので、決まった規則と乱数で一部を選ぶこと |
| **seed** | 乱数の種。同じ seed なら誰がやっても同じものが選ばれる（再現できる） |
| **pin** | 取得するリポジトリの版を commit の SHA で固定すること |
| **凍結 / 指紋** | 解析器の版を固定すること / その版のファイルのハッシュ（`docs/fingerprint.json`） |

## 3. 流れと日程の目安

```
 ─── データを見る前（ここで決めたことは後で変えない） ───────────────────────
  段階 0  決めること（学生の判断）                            半日〜1 日
  段階 1  事前登録と判定の手引きを書く            → コミット  2〜4 日
  段階 2  道具を作り、v4 のデータで練習する        → コミット  3〜5 日
 ─── データに触れる（ただし結果はまだ見ない） ─────────────────────────────
  段階 3  抽出と pin                              → コミット  半日
  段階 4  取得と取得後の条件                      → コミット  1〜3 日（約 3,460 repo。D69）
  段階 5  凍結の確認と走査（1 回だけ）            → コミット  1〜2 日
  段階 6  判定の対象の抜き取り                    → コミット  1 時間
 ─── 結果を見る ─────────────────────────────────────────────────────────
  段階 7  判定（原ソースを読む）                  → こまめにコミット  最も長い（第 27 節）
  段階 8  集計                                               1〜2 日
  段階 9  論文に書く
```

日数は**見込み**で、測った値ではない。段階 7 がほかのすべてを合わせたより長くなる見込みなので、日程はそこから逆算する。

**各段階の出力は、次の段階に進む前にコミットする。** 「結果を見てから規則や標本を選んだ」と疑われないための、
この研究の一番大事な約束（CLAUDE.md 規則 5、教科書 第 19 章）。コミットの日時が、何を先に決めたかの証拠になる。

# 第 2 部 データを見る前

## 4. 段階 0: 決めること（学生の判断）

どれも**データを見る前に**決め、段階 1 の事前登録に書く。決めたら変えない。

### 0-1. 解析する木の数 — **決定（D69）: 枠の残りを全部解析する（抽出しない）**

- **決定**: 枠（0-6）から v2・v3・v4 の 300 件を除いた**残りを全部** pin して取得し、全部を走査する（約 3,460 repo。
  v4 の率なら MCP サーバは約 3,000 木の見込み。見込みで、測った値ではない）。
- 理由: 走査は機械なので安い（v4 は 1 木平均 9 秒）。全部を走査すると、機械が出す数（矛・不の件数、宣言の分布、`r_malformed`）
  に抜き取りの誤差が無くなり、めったに出ない D3・D4 の矛も最大限に集まる。手の判定は抜き取りで行う（0-2・0-3・0-14）。
- **ディスク**: v4 の 99 repo で約 1.2 GB だった。同じ割合なら約 40 GB の見込み。一度に取らず、**数百 repo ずつ「取得 → 走査 →
  manifest を残して corpus を消す」**を繰り返してよい（走査の結果は manifest と `summary.json` / `contradictions.json` に残る）。
  判定のときに原ソースが要るので、**判定の対象に選ばれた木は、pin の SHA で取り直せる**（pin があれば同じ中身が得られる）。
  ただし「走査は 1 回」の約束は守る（同じ木を 2 回走査しない）。
- 抽出のスクリプトは `--all` で全部を取る（D73 の 5、2026-10-03）。乱数の種を使わず、出力に `mode: "all"`・`seed: null` と書き、
  件数が「母集団 − 除外」と一致しなければ止まる。
  - （決定の前の文面）「`--n` が母集団より大きいと全部を返すので、段階 3 では `--n 100000` のように大きな値を渡す」。
    この方法では、使っていない既定の種（20260920）が出力に「抽出の種」として残っていた。

### 0-2. 矛の抜き取り:「1 木 3 件まで」の単位 — **決定（D70 の 1）: (a) 宣言ごと**

- (a) **宣言ごとに** 1 木 3 件まで（同じ木から D1 で 3 件、D2 で 3 件、…）
- (b) 宣言をまたいで 1 木 3 件まで
- 推奨: **(a)**。D1〜D4 を宣言ごとに報告する（D62）ので、宣言ごとに抜くと各宣言の数字が独立に出る。
- 3 件より少ない木は全件を判定する。
- **木の数の上限（D69）**: 宣言ごとに、矛の出た木が **200 を超えたら seed で 200 木**を選ぶ（200 以下なら全木）。D3・D4 も同じ
  規則（出る木が少ないので、たいてい全木になる）。200 木で、木の単位の割合の 95% 区間の幅はおよそ ±7 ポイント以内。
- **木の中で 3 件をどう選ぶか**も書く（seed を固定した無作為）。

### 0-3. 見落としの抜き取り

- **決定（D69）: 200 件（1 木 1 件）**。30 件では「見落としは多くても約 1 割」までしか言えない。200 件なら約 ±5 ポイントになる。
- 対象: D1 か D2 を明示し、その宣言に対する矛が 1 件も出ていないユニット（v4 の V3 と同じ）。
- 手順: 対象のユニットを持つ木から seed で 200 木を選び、各木から 1 ユニットを seed で選ぶ。200 木に満たなければ全木。
- **解析器の出力を見る前に判定する**（先に原ソースを読んで自分で決め、その後で解析器の出力と照らす）。先に見ると引っぱられる。
- **打ち切りの印（`truncated`）があるユニットを対象に含めるか** — **決定（D70 の 2）: 含めて、判定で「不明（打ち切り）」に分ける**
  （v3 以降の `v3_miss_sample.py` と同じ扱い）。

### 0-4.「本当の矛が 1 件以上あった木の割合」の分母（D67 の 3） — **決定（D70 の 4）: (a) と (c) を主、(b) を参考**

CLAUDE.md 規則 3（閾値には分母の定義を付ける）のため、先に決める。

| 案 | 分母 | 答える問い |
|---|---|---|
| (a) | その宣言の矛が出た木 | 解析器が「矛あり」とした木のうち、本当に違反があった木の割合（解析器の精度の木版） |
| (b) | 走査した全部の木 | 標本の木のうち、違反が見つかった木の割合 |
| (c) | その宣言を明示したユニットを持つ木 | **宣言を書いたサーバのうち、違反が見つかった木の割合**（研究の問いに一番近い） |

- ~~推奨: (a) を主にし、(b)(c) を併記する。~~
- **決定（D70 の 4）**: **(a) と (c) を主**、(b) を参考にする。
  - (a) は道具の信用度。
  - (c) は研究の問い（宣言がどれだけ当てにならないか、D40）への答えで、論文の結論になる。
  - (b) は宣言していない木も分母に入り薄まるので、参考にとどめる。
- (c) の分母の定義: **その宣言を明示的に書いた（`D_kind.explicit`）ユニットを 1 つ以上持つ木**。既定値で補ったものは数えない
  （見落としの抜き取りの対象と同じ定義）。
- (b)(c) の分子は推定になる。矛の出た木が 200 を超えて抜き取ったときは、判定しなかった木があるため（23.2）。
- **注意**: 1 木 3 件までしか判定しないので、3 件がすべて誤でも、判定しなかった残りに正がある可能性がある。
  (a)〜(c) はどれも「**少なくともこれだけの木に違反があった**」という**下限**になる。論文ではそう書く。

### 0-5. 判定「不明」の扱い — **決定（D70 の 5）: (a) を主、(b) を併記**

- (a) 精度の分母から除き、件数を併記する: 精度 = 正 / (正 + 誤)
- (b) 分母に入れる（不明を誤とみなす）: 精度 = 正 / (正 + 誤 + 不明)
- 推奨: **(a) を主、(b) を併記**。どちらか一方だけにすると、読み手はもう一方を疑う。

### 0-6. 枠（どこから抽出するか）

- (b) GitHub code search で列挙し直す

### 0-7. 中身の重複の除去（フォーク・同梱コード） — **決定（D70 の 6）: する（v2〜v4 との重複と、今回の中の重複）**

- v3 では 100 木中 8 木に、それまでのデータと同一のファイルがあった（教科書 第 38 章）。
- 推奨: **する**。規則の例:「取得した木の `.py` ファイルの sha256 を取り、ツールの定義を含むファイルが v2〜v4 の木のどれかと
  一致した木は除く。除いた木の数と理由を記録する。除いた分は補充しない」。
- v2〜v4 の木の中身を手元に持っていないと比べられない（v2〜v4 の corpus を取り直す手間が要る）。手間が見合わなければ
  「しない」と決め、限界に書く。
- **決定（D70 の 6）の規則**:
  1. 取得した木ごとに、ツールの定義（入口の規則に当たるユニット）を含む `.py` ファイルの sha256 を取る。
  2. **v2〜v4 との重複**: そのファイルの 1 つでも、v2〜v4 の木のどれかのファイルと一致した木は除く。v2・v3 の中身は手元に
     無いので、`docs/corpus_sample_v{2,3,4}.json` の pin から取り直してハッシュだけを残す（中身は保存しなくてよい）。
  3. **今回の中の重複**: ツールの定義を含むファイルが一致する木どうしは、repo 名（小文字）の辞書順で最初の 1 木だけを残し、
     残りを除く。
  4. 除いた木の数と、どの木と一致したかを記録する。全部を走査する設計（D69）なので、補充はしない。
  5. この規則は走査の前（段階 4 の取得後の条件）に当てる。走査の結果を見てから除く木を選ばない。

### 0-8. seed — **決定（D70 の 7）: 日付ベースで 4 つ別々に。D73 の 1・4 で ⑤・⑥ を足した**

- **決定**: 事前登録（§2.12）を書く日を YYYYMMDD として、次の 4 つを使う。
  - ① 矛の抜き取り用: YYYYMMDD1
  - ② 見落としの抜き取り用: YYYYMMDD2
  - ③ 不の中身の抜き取り用: YYYYMMDD3
  - ④ bootstrap 用: YYYYMMDD4
  - 走査の対象は全部（D69）なので、抽出用の seed は要らない。重複を除くときに残す木は repo 名の辞書順で決まり、乱数を使わない（D70 の 6）。
  - **⑤ 判定表の順序の並べ替え用: YYYYMMDD5**（21 の 1。D73 の 4、2026-10-03）
  - **⑥ 判定の一致を確かめる組の抜き取り用: YYYYMMDD6**（21 の 5。D73 の 1）。前の文面は「判定し直しや 2 人目の判定の対象を
    抜くなら ⑤ 以降を足す」で、⑤ を並べ替えに使う案と番号がぶつかっていたので、⑥ にずらした。
  - **§2.12 に書いてコミットしてから**データに触れる。番号そのものに意味はなく、先に書いたことに意味がある。
- （決定の前の文面）3 つを別々に決めて書く: **抽出用**、**矛の抜き取り用**、**見落としの抜き取り用**（と、bootstrap 用）。

- **決定**: 最終評価の判定（矛・見落とし・不の中身）を決めて記録するのは学生。AI（LLM）は、コードについての事実を調べる補助に

### 0-11. 条件つきの到達の扱い — **決定（D68 の 1）**

判定で一番迷うのは「特定の条件のときだけ届く」効果である（例: 引数を渡したときだけ、環境変数が設定されているときだけ）。

- 併記: (B) 運用者が決める条件（運用者の設定・起動の方法）でしか届かないものを除いた数、(C) 条件なしで届くものだけの数。

  守られていない。D67 の 2（起動時の初期化は「届きうる」なら正）と同じ読み方。

### 0-12. 深さ 4 より奥で見つけた違反（見落としの判定） — **決定（D68 の 2）**

### 0-13. 書き込みではない違反のラベル — **決定（D68 の 3）**

D67 のラベルは書き込み先の種類なので、SPAWN / EXEC の矛（例: 読み取り専用のツールがモデルの決めたコマンドを起動する）を

### 0-14. 不の中身を判定する — **決定（D69）**

解析器が「不」（静的に決まらない）と出した組の中に、本当の違反がどれだけあるかは、これまで一度も測っていない。

- **決定**: D1 と D2 のそれぞれで、不の組（ユニット, 効果, 宣言）を持つ木から seed で **50 木**を選び、各木から seed で 1 組
  （計 100 組）。50 木に満たなければ全木。D3・D4 の不は件数と理由だけ（判定しない）。
- 判定: その組の効果について、第 14 節（到達）と第 15 節（宣言に反するか）を当て、**違反 / 違反でない / 不明**を付ける。
  「不明」は、判定者が原ソースを読んでも決められないもの（外部サーバの意味、実行時の値など）。理由を書く。
- 報告: 宣言ごとに、判定した不のうち本当に違反だった割合（木の単位。95% 区間つき）と、不の理由（`contradiction_by_decl.py`
  の理由コード）ごとの内訳。
- 理由: 矛（精度）・何も出さない（見落とし）・不の 3 つがそろって、解析器の答えのそれぞれがどれだけ当たっていたかを示せる。

下は動作を確かめた最小の形（`scripts/show_target.py` などにして使う）。

```python
import json, sys

# 使い方: python show_target.py <manifest> <ユニットの relpath> <ユニットの行> <site>
manifest_path, unit_relpath, unit_lineno, site = sys.argv[1], sys.argv[2], int(sys.argv[3]), sys.argv[4]
m = json.load(open(manifest_path, encoding="utf-8"))
for u in m["units"]:
    info = u["unit"]
    if info["relpath"] != unit_relpath or info["lineno"] != unit_lineno:
        continue
    print("ツール:", info["tool_name"], " 定義:", f'{info["relpath"]}:{info["lineno"]}', " 宣言:", info.get("annotations"))
    print("明示された宣言:", u["D_kind"]["explicit"], " 打ち切り:", u["cap_hits"], " opaque:", u["opaque_reasons"])
    for e in u["effects"]:
        if e["site"] != site:
            continue
        print("---- 効果", e["kind"], e["site"], f'{e["relpath"]}:{e["lineno"]}')
        print("  入口の呼び出し行:", e.get("entry_lineno"), " 道筋:", " -> ".join(e.get("witness_chain", [])) or "(本体の中)")
        for name, s in e.get("slots", {}).items():
            print(f"  slot {name}: 主体={s.get('prin')} 確度={s.get('prov')} 根={s.get('roots', [])}")
    for r in u["rows"]:
        if r["site"] == site:
            marks = [n for n in r["notes"] if n.startswith("contradiction")]
            print("  行", f'{r["relpath"]}:{r["lineno"]}', r["slot"], marks)
```

## 11. 判定とは何をすることか

### 11.1 判定の単位

**組 = (木, ユニット, site, kind, 宣言)**。たとえば「木 X のツール `search_notes` の `builtins.open` の `FS_WRITE` を、
D1 に照らして」で 1 組。同じツールの同じ site・kind の効果が複数の行にあっても 1 組にまとめてある（`locations` に並ぶ）。

### 11.2 矛の判定で答える 2 つの問い

1 組ごとに、次の 2 つに答える。**両方が「はい」のときだけ正。**

1. **到達するか**: その効果は、**ツールの呼び出しによって**実行時に実際に起きうるか（第 14 節）。
2. **宣言に反するか**: 起きたとき、その動作は宣言（D1〜D4）に反するか（第 15 節）。

| 到達する | 宣言に反する | 判定 |
|---|---|---|
| はい | はい | **正** |
| いいえ | — | **誤**（原因: 到達しない） |
| はい | いいえ | **誤**（原因: 宣言に反しない） |
| 決められない | — | **不明** |
| はい | 決められない | **不明** |

解析器の出した**理由（site 名や注記）が間違っていても、2 つの問いの答えが「はい」なら正**である（例: sqlite3 の接続を
psycopg と表示していても、読み取り専用のツールが本当に DB を書き換えるなら正）。判定するのはコードの動作で、解析器の説明ではない。

### 11.3 判定の基準は「採った原理」を字義どおりに当てる

基準は `docs/contradiction_principles.md` の §6（採った原理）と §7（判定表）である。**自分の感覚で「これくらいは違反と言えない」
と判断しない。** 研究の問いは「宣言は正しいか」で「危ないか」ではない（D67 の 1）。たとえば読み取り専用のツールがログファイルに
1 行追記するのは、採った原理（1-i-b: 呼び出しを越えて残るものはすべて環境）では違反である。**軽重は書き込み先の種類のラベルで
表し（第 16 節）、判定の正誤には持ち込まない。**

採った原理の要点:

| 原理 | 採ったもの | 判定での意味 |
|---|---|---|
| 1-i 永続する設定 | b 含める | DB の `PRAGMA journal_mode=…` のように呼び出しを越えて残る設定の変更も「環境の変更」 |
| 1-ii リモートの状態 | b 含める | HTTP で相手のサーバの状態を変えるのも「環境の変更」 |
| 2 静的に決まらないもの | a 不明 | 解析器は「不」を出す。**人の判定でも、決められなければ「不明」にする** |
| 3 モデルが決める値 | a 能力として読む | モデルが選べる引数は「取りうる値の全体」で考える（モデルが既存のファイルを指せば上書きできる） |
| 4 対象の宣言 | a 4 つすべて | D1〜D4 を宣言ごとに判定・報告する |

## 13. 矛の 1 件を判定する手順（手順 A〜H）

### 手順 A: 対象を読む

判定表の 1 行から次を読む。

| 欄 | 例 | 意味 |
|---|---|---|
| `tree` | `final-owner__repo` | 木（`corpus/final-owner__repo/`） |
| `unit`、`unit_relpath`、`unit_lineno` | `search_notes`、`server.py`、24 | ツールの関数と、その定義の位置 |
| `site`、`kind` | `builtins.open`、`FS_WRITE` | 効果を起こす関数と種類 |
| `decl` | `D1` | 照らす宣言 |
| `reasons` | `fs_write` | 解析器が矛とした理由のコード（13.1） |
| `locations` | `server.py:12` など | その組の効果の位置（複数ありうる） |

### 手順 B: 解析器が何を見たかを確かめる

6.5 の道具で、その組の効果の**道筋**（`witness_chain`）、**入口の呼び出し行**（`entry_lineno`）、**slot の主体と確度**、
**行の注記**（`contradiction:D1` など）を出す。これは「解析器の言い分」で、手順 D で自分でたどるときの地図になる。

- `打ち切り`（`cap_hits`）に `depth` などがあれば、解析器はそのユニットの途中で読むのをやめている。
- `opaque` に `receiver` / `unresolved` があれば、解析器は呼び出し先の一部を解決できていない。

### 手順 C: 効果の行を開き、本当にその操作かを確かめる

`locations` の各位置（ファイルと行）を開く。

- その行は本当に書き込み（あるいは削除・DB の変更・HTTP の送信・プロセスの起動）か。
  - 例: `pipe:write` / `pipe:communicate` は子プロセスの標準入力への書き込みで、ファイルの書き込みとは限らない（第 17 節 E5）。
  - 例: `builtins.open` なら開くモード（`'w'`・`'a'`・`'x'`・`'r+'` など）。読み取り（`'r'`）なら書き込みではない。
- 呼び出されている関数は本当に site の関数か。
  - 例: 組み込みの `set()`・`dict.get()`・`list.append()` を、木の中の同名のメソッド（`CacheManager.set` など）と取り違えて
    いないか（第 17 節 E3）。
  - site 名のライブラリが違っていても（sqlite3 を psycopg と表示）、**動作の種類（kind）が合っていれば判定には影響しない**。
    その場合は `note` に書いておく。

ここで「そもそもその操作ではない」と分かれば、**誤**（原因は E3 / E4 / E5 など）で手順 H へ。

### 手順 D: ツールの入口から効果まで、自分で道筋をたどる

1. ツールの関数（`unit_relpath:unit_lineno`）を開く。
2. `entry_lineno` の行から、`witness_chain` の関数を順に開いていく。
   例: `witness_chain = _lookup -> _save_cache` なら、本体の 26 行目で `_lookup` を呼び、`_lookup` の中で `_save_cache` を呼び、
   `_save_cache` の中の 12 行目が効果。
3. 各段で次を見る:
   - 呼び出しは本当にその関数に届くか（同名の別の関数・別のクラスではないか。受け手は何か）。
   - 呼び出しの前に条件（`if`）があるか。あるならどんな条件か（第 14 節）。
   - 例外や `return` で、その呼び出しの前に必ず抜けていないか。
4. 道筋の途中に「一度だけ」の守り（`if self._x is None:`、`@lru_cache`、`global _initialized`）があれば、
   その初期化が**ツールの呼び出しより前に必ず済んでいるか**を確かめる（第 14.4 節、起動時の初期化）。
5. **根拠として、たどった各段のファイルと行を書き留める。** 例: `server.py:26 → server.py:18 → server.py:12`。

### 手順 E: 到達するかを決める

第 14 節の規則で「到達する / 到達しない / 決められない」を決める。

### 手順 F: 宣言に反するかを決める

第 15 節の、その宣言の問いに答える。**モデルが決める値は「取りうる値の全体」で考える**（原理 3-a。D4 だけは除く）。

### 手順 G: 1 組に複数の位置があるとき

`locations` に複数の位置があるときは、**1 つでも「到達する かつ 宣言に反する」位置があれば、その組は正**とする
（v4 の判定と同じ。例: wikimind の `wiki_ask` は 2 つの `mkdir` の片方が起動時の初期化だったが、もう片方が毎回届くので正）。

- 全部の位置が「到達しない」か「反しない」なら誤。
- 正にした位置と、ほかの位置をどう判断したかを `note` に書く。
- 全部を読むのが大変なら、**1 つ正が見つかった時点で止めてよい**（止めたことを `note` に書く）。誤にするときは全部を読む。
- **条件の種類（14.3）は、正にできる位置のうち条件の一番弱いものを記録する**（D68 の 1）。順は「なし」→ 運用者が決めない条件
  （引数・初回・失敗・期限切れ・外部の状態）→ 運用者が決める条件（運用者の設定・起動の方法）。条件つきの位置で正が見つかっても、
  条件なしの位置がありそうなら、そこまで読むと (C) の数が正しくなる。

### 手順 H: 記録する

判定表の 1 行に次を書く。

| 欄 | 書くこと | 例 |
|---|---|---|
| `verdict` | `正` / `誤` / `不明` | `正` |
| `reachable` | `はい` / `いいえ` / `決められない` | `はい` |
| `condition_type` | 条件の種類（14.3）。複数の条件が重なるなら全部を `;` で並べる | `引数` |
| `condition` | 条件の中身を 1 文で（無ければ `なし`） | `引数 output_file を渡したとき` |
| `violates` | `はい` / `いいえ` / `決められない` | `はい` |
| `error_class` | 誤のとき、第 17 節の分類（E1〜E9）と 1 文の説明 | `E1: lifespan の init_db が起動時に済ませる` |
| `write_target` | 正のとき、第 16 節の種類（D1・D2・D4）。D3 は通信先の種類（16.3） | `ログ` |
| `unknown_reason` | 不明のとき、決められない理由 | `書き先のパスが外部ライブラリの戻り値で決まる` |
| `evidence` | **ファイルと行**の連なりと、各段で何が起きるかを 1〜3 文で | 下の例 |
| `note` | 迷った点・ほかの位置の扱い・解析器の読み違い（kind は合っている場合）など | |
| `minutes` | かかった分数 | `18` |

`evidence` の良い例（v4 の M18 を短くしたもの）:

> `server.py:703-826`（generate_cost_report_wrapper、引数 output_file をそのまま generate_cost_report に渡す）→
> `report_generator.py:1164-1186`（format で分岐）→ `report_generator.py:778` `with open(output_file, 'w')`。output_file は
> モデルが決める引数。

悪い例:「open で書いているので正」（どの行か、どう届くかが無く、第三者が確かめられない）。

**`evidence` は、判定を見ていない第三者がその行を開けば同じ結論に着けるように書く。** 2 人目の判定者がいない分、これが
信頼性の担保になる（D67 の 4）。

## 14. 到達するかの決め方

### 14.1 基本

**「そのツールが呼ばれたとき、その効果が起きる実行の道が 1 つでもあるか」**。毎回起きる必要はない。

### 14.2 到達しない形（誤にする形）

| 形 | 見分け方 | 誤の原因 |
|---|---|---|
| **起動時の初期化（lifespan・import 時）** | 14.4 | E1 |
| 呼び出し先の取り違え | 呼んでいるのは別の関数・組み込みのメソッド（13 手順 C） | E3 / E4 |
| 死んだコード | 効果のある関数がツールの道筋からは呼ばれていない（別の入口 = CLI・テスト・スクリプトからだけ呼ばれる） | E6 |
| 定数で閉じた枝 | `if False:`、`if DEBUG:`（`DEBUG = False` が定数で、どこでも書き換えない）の中 | E6 |
| 必ず先に抜ける | 効果の前に必ず `return` / `raise` する | E6 |

**「別の入口からしか呼ばれない」ことは、木の中を検索して確かめる**（関数名で grep し、呼び出し元をすべて見る）。

### 14.3 条件つきで到達する形（D68 の 1）

**ツールの呼び出しで届きうるなら「到達する」とし、条件の種類を `condition_type` 欄に、中身を `condition` 欄に書く。**
D67 の 2（起動時の初期化）と同じ「能力の上界」の読み方（原理 3）である。

| `condition_type` | 条件の例 | 扱い | (B) に数えるか | (C) に数えるか |
|---|---|---|---|---|
| `なし` | 毎回届く | 到達する | 数える | 数える |
| `引数` | モデルが渡す引数の値による（`if output_file:`、`if mode == "save":`） | 到達する（モデルが選べる） | 数える | 数えない |
| `初回` | 初回だけ・キャッシュが無いときだけ（ツールの道筋の中で `if not os.path.exists(d): os.makedirs(d)`） | 到達する（最初の呼び出しで起きる） | 数える | 数えない |
| `失敗・期限切れ` | トークンの更新、再試行、エラー時の後始末 | 到達する | 数える | 数えない |
| `外部の状態` | ファイルが無いとき、相手が特定の応答を返したとき | 到達する | 数える | 数えない |
| `運用者の設定` | 環境変数・設定ファイル・起動の引数で有効になる | 到達する（その設定で起動すれば届く）。設定の名前を `condition` に書く | **数えない** | 数えない |
| `起動の方法` | 初期化が `main()` の中だけにあり、`main()` を通らない起動（`fastmcp run file.py:mcp` など）で届く（14.4） | 到達する | **数えない** | 数えない |
| — | 条件が何で決まるか読み切れない | 決められない → 不明 | — | — |

- **主の数（A）は条件を問わない。** (B) と (C) は併記で、事前登録で決めてあるので、結果を見た後の分析ではない。
- 条件が重なるとき（例: 引数を渡し、かつ環境変数が設定されているとき）は全部を `;` で並べる。**1 つでも運用者が決める条件が
  あれば (B) に数えない。**

### 14.4 起動時の初期化（D67 の 2）

ツールの道筋の途中に「一度だけ初期化する」形があり、効果がその初期化の中にあるとき:

```python
_memory = None

def _ensure_memory():
    global _memory
    if _memory is None:
        _init()            # ← 効果（ディレクトリの作成など）はこの中
    return _memory
```

**その初期化がツールの受付より前に必ず済んでいるか**で決める。起動の方法はコードだけから決める。

| 初期化を先に済ませている場所 | 判定 | 理由 |
|---|---|---|
| `main()` の中だけ、または `if __name__ == "__main__":` の中だけ | **到達する（正になりうる）** | モジュールの一番上の `mcp = FastMCP(...)` は、`fastmcp run file.py:mcp` などで `main()` を通らずに起動できる。そのときは最初のツール呼び出しで初期化が走る（原理 3 と同じ「届きうる」の読み方） |
| lifespan の中（`FastMCP(..., lifespan=app_lifespan)` に渡した関数の中） | **到達しない（誤、E1）** | どの起動方法でも、ツールの受付より前に必ず走る |
| モジュールの読み込み時（モジュールの一番上の文、モジュール水準の変数の初期化） | **到達しない（誤、E1）** | import した時点で走る |
| どこで先に済ませるか読み切れない | **不明** | |

見分け方:

- lifespan: `FastMCP(` / `Server(` の引数の `lifespan=` を探し、その関数（多くは `@asynccontextmanager`）の中を見る。
- lifespan が初期化を**必ず**済ませるか（例外で抜けたら受付が始まらないか、条件つきではないか）も見る。条件つきなら、
  条件が偽のときはツールの呼び出しで届くので「到達する」。
- **初期化が済んでいても、その後にどこかで `None` に戻す（`_memory = None`）なら、ツールの呼び出しで再び届く。**
  戻す箇所が無いかを grep で確かめる。
- ツールの道筋が初期化を**呼ばない**（守りの `if` が無い）なら、そもそもその効果はツールの道筋ではない → 手順 D で確かめる。

この規則では、v4 の ccr（`main()` で初期化）は正、shyhurricane（lifespan で初期化）は誤になる。**解析器に有利な側（ccr）と
不利な側（shyhurricane）の両方がある**ことを論文に書く（O43 の整理）。

### 14.5 同じ呼び出しの中で作って消すもの

ツールが同じ呼び出しの中で一時ファイルを作り（`mkstemp`）、使い、消す（`os.remove`）形は、**到達はする**。
宣言に反するかは宣言による（第 15 節の D1 と D2 で扱いが違う）。

## 15. 宣言に反するかの決め方（D1〜D4）

### 15.1 D1 `readOnlyHint: true` —「環境を変えるか」

**問い**: その動作は、呼び出しの後に残る何かを変えるか（ホストのファイル・DB・相手のサーバの状態・残る設定）。

| 動作 | 反するか | 注意 |
|---|---|---|
| ファイルの書き込み・作成・削除・移動・権限の変更（`FS_WRITE` すべて） | **反する** | ログ・キャッシュ・一時ファイル・ディレクトリの作成も含む（原理 1-i-b）。軽重はラベルで表す |
| コードの実行（`EXEC`） | 反する | 表 D41 で決定済み |
| プロセスの起動（`SPAWN`） | 起動するコマンドをモデルが決められるなら反する。コマンドが定数なら、**そのコマンドが実際に何をするか**を調べ、環境を変えるなら反する・変えないなら反しない・分からなければ不明 | 解析器は定数のコマンドを「不」にする（意味が名前から分からないため）。人は調べられる範囲で調べる |
| DB のデータ・スキーマの変更（`INSERT` / `UPDATE` / `DELETE` / `CREATE` / `DROP` など） | 反する | |
| DB に残る設定・保守（`PRAGMA journal_mode=WAL`、`VACUUM` など） | 反する | 原理 1-i-b |
| DB の接続単位の設定・トランザクション（`BEGIN` / `COMMIT` / `PRAGMA foreign_keys=ON` など） | 反しない | 接続が閉じれば消える |
| DB の読み取り（`SELECT` など） | 反しない | |
| HTTP の `PUT` / `PATCH` / `DELETE` | 反する | 原理 1-ii-b |
| HTTP の `POST` | **相手の API の意味を調べて決める**。相手のドキュメントや API 名から「作成・更新・削除」なら反する、「照会」（検索 API・RPC の読み取り）なら反しない、分からなければ不明 | 解析器は `POST` を「不」にする。人は調べられる範囲で調べる |
| HTTP の `GET` / `HEAD` / `OPTIONS` | 反しない | |
| ファイルの読み取り | 反しない | |

**迷いやすい形**:

- **標準出力・標準エラーへのログ**: ファイルではないので反しない（`logging` の出力先がファイルなら反する。出力先の設定を確かめる）。
- **子プロセスの標準入力への書き込み**: それ自体はファイルを変えない。子プロセスがそれを受けて何をするかで決める（第 17 節 E5）。
- **クライアントへの通知**（`ctx.info()` / `ctx.report_progress()`）: 環境を変えないので反しない。

### 15.2 D2 `destructiveHint: false` —「追加の更新だけか」

**問い**: その動作は、**呼び出しの前からあったもの**を消す・上書きする・変えるか。新しく足すだけなら反しない。

| 動作 | 反するか |
|---|---|
| 新しく作るだけ（`mkdir`、`open('x')`、`open('a')` の追記、DB の `INSERT` / `CREATE`、HTTP の `GET`） | 反しない |
| 既存のものを消す・動かす・変える（`unlink` / `rmtree` / `rename` / `chmod`、DB の `UPDATE` / `DELETE` / `DROP` / `ALTER`、HTTP の `DELETE` / `PATCH`） | **反する** |
| 書き出し（`open('w')` / `write_text` / `copy` など） | **書き先をモデルが決められるなら反する**（既存のファイルを指せば上書きできる。原理 3-a）。書き先が固定なら、そこに**呼び出しの前からファイルがありうるか**で決める（毎回同じファイルを上書きするなら反する、呼び出しごとに新しい名前なら反しない、分からなければ不明） |
| HTTP の `PUT` | 宛先をモデルが決められるなら反する。そうでなければ、既存の資源の置き換えか新規作成かで決める |
| HTTP の `POST` | 相手の API の意味で決める（既存の資源を更新・削除するなら反する） |
| DB に残る設定の変更 | 「追加か破壊か」が当てはまらない → 不明（解析器と同じ） |

**迷いやすい形**:

- **同じ呼び出しで自分が作った一時ファイル・ロックファイルを消す**: 呼び出しの前からあったものではないので**反しない**
  （誤、E2）。v3・v4 で出た類（O41・O43）。ただし**前の呼び出しが残したファイル**を消すなら、それは呼び出しの前からあった
  ものなので反する。
- **キャッシュの上書き**: 同じキャッシュファイルを毎回 `'w'` で書き直すなら、前の内容を上書きするので反する（ラベルは
  キャッシュ・状態の保存）。

### 15.3 D3 `openWorldHint: false` —「関わる範囲が閉じているか」

**問い**: そのツールは、外部の（そのマシンやローカルの網の外の）相手と通信するか、あるいはモデルが決める相手と通信しうるか。

| 動作 | 反するか |
|---|---|
| HTTP などの宛先が local（loopback・RFC 1918・ULA・link-local・未指定・`localhost` などの名前・ドットの無い名前・`〜.internal`。範囲の全部は判定の手引き 15.3 節。D73 の 2） | 反しない |
| 宛先が定数の外部ホスト | 反する |
| 宛先をモデルが決められる | 反する（原理 3-a） |
| 宛先が運用者の設定で決まる（環境変数の URL など） | 設定の既定値や文書で外部を想定しているなら反する、ローカルを想定しているなら反しない、分からなければ不明 |
| 実行するコード・起動するコマンドをモデルが決められる | 反する |
| ファイル・DB のローカルの操作 | 反しない |

### 15.4 D4 `idempotentHint: true` —「同じ引数で繰り返しても追加の効果が無いか」

**問い**: **同じ引数で** 2 回呼んだとき、2 回目が 1 回目の後の状態をさらに変えるか。

**D4 には原理 3 を当てない**（冪等性は「同じ引数で繰り返したとき」の性質で、引数が取りうる値の範囲は関係しない。§7.0 の 1）。

| 動作 | 反するか |
|---|---|
| 定数の `'a'` で追記する | 繰り返すと追記が重なるなら反する。**書く前に内容を確かめて、すでにあれば書かない**なら反しない（v4 の E00） |
| `flock` のために `'a'` で開くだけで書かない | 反しない（O41） |
| 上書き（`'w'`）・作成・削除 | 同じ引数なら同じ状態になるか、2 回目は失敗するので、ふつう反しない |
| DB の `INSERT` | 一意制約で 2 回目が失敗・無視されるなら反しない、行が増えるなら反する。スキーマを見て決める。見られなければ不明 |
| DB の `UPDATE` | `SET x = 1` なら反しない、`SET x = x + 1` や `NOW()` の記録なら反する |
| HTTP の `POST` / `PATCH` | 相手の API の意味で決める |
| 時刻・連番・乱数を含むものを書く（ログの 1 行、タイムスタンプつきのファイル名） | 反する（2 回目でさらに増える） |

## 16. 書き込み先の種類の付け方

**D1・D2・D4 の正の各件に 1 つだけ**付ける（D67 の 1、D68 の 3）。**重みではない**（どれも違反であることは同じ）。読み手が
「見つけた違反は些細では」と問うたときに、事実で答えるための列。D3 の正には付けず、通信先の種類を記録する（16.3）。

### 16.1 種類と定義（下書き）

**上から順に当てはめ、最初に当てはまったものを付ける。**

| 順 | 種類 | 定義 | 例 |
|---|---|---|---|
| 1 | **相手側の状態** | NET の効果で、通信相手のサーバの状態を変える | Jira の課題の更新、Slack への投稿 |
| 2 | **データベース** | DB の行・スキーマ・DB に残る設定を変える | `UPDATE sessions SET revoked_at …`、`PRAGMA journal_mode=WAL` |
| 3 | **利用者のファイル** | 利用者（またはモデル）が指定した場所のファイル、または利用者の文書・データとして扱われるファイル | モデルが決めた `output_file` へのレポートの書き出し、編集対象のファイルの上書き |
| 4 | **ログ** | 記録のためだけに書き、ツールの動作では読み返さない | ログファイル・監査ログ・トレースへの追記 |
| 5 | **一時ファイル** | 同じ呼び出しの中で作って消す、または OS の一時領域（`tempfile`、`/tmp`）に作る | `mkstemp` した受け渡し用のファイルとその削除 |
| 6 | **キャッシュ・状態の保存** | ツールの動作のために自分で保存し、後で読み返す | キャッシュ、トークン・セッションの保存、索引、初回に作る作業ディレクトリ・設定ファイル |
| 7 | **プロセスの起動・コードの実行**（D68 の 3 で足した） | SPAWN / EXEC の正 | モデルが決めたコマンドの起動、`eval` / `exec` |
| 8 | **その他・不明** | 上のどれにも当てはまらない、または決められない | |

### 16.2 境界の例（先に決めておく）

| 事例 | 付ける種類（下書き） | 理由 |
|---|---|---|
| 別のプロセスと話すための受け渡しファイル（v4 の reaper-mcp の mailbox。前の呼び出しが残した応答ファイルの削除、初回のディレクトリの作成） | **一時ファイル**（同じ呼び出しで作って消すもの）/ **キャッシュ・状態の保存**（呼び出しを越えて残る作業ディレクトリ） | 定義 5 と 6 で分ける。1 組に両方あれば、正にした位置で決める |
| OAuth のトークンをファイルに保存 | キャッシュ・状態の保存 | 後で読み返す |
| 初回だけ `~/.app/` を作る | キャッシュ・状態の保存 | 作業ディレクトリ |
| 活動ログ `log.md` への追記（v4 の wikimind） | ログ | 読み返さない |
| モデルが決めたパスへのエクスポート | 利用者のファイル | |
| SQLite のキャッシュ DB への書き込み | データベース | 順 2 が順 6 より先 |

**判定の途中で境界の事例が出て決められないときは「その他・不明」にし、事例を `note` に書く。** 途中で定義を足さない
（第 22 節）。

### 16.3 D3 の正に付ける通信先の種類（D68 の 3）

D3（`openWorldHint: false`）の違反は書き込みではなく外部との通信なので、書き込み先の種類の代わりに次のどれかを `write_target` 欄に書く。

| 種類 | 定義 | 例 |
|---|---|---|
| **定数の外部ホスト** | コードに書かれた外部のホストと通信する | `requests.get("https://api.example.com/…")` |
| **モデルが決める宛先** | 宛先のホストをモデルが決められる | `httpx.get(url)`（`url` はツールの引数） |
| **モデルが決めるコード・コマンド** | 実行するコード・起動するコマンドをモデルが決められる（通信しうる） | `subprocess.run(cmd, shell=True)` |
| **その他・不明** | 上のどれにも当てはまらない、または決められない | 宛先が運用者の設定で、既定値が外部のもの |

## 17. 誤の原因の分類

誤にしたときは、次のどれかを `error_class` に書く（下書き。v3・v4 で出た類を最初から用意した）。
記号の E1〜E9 は誤の原因の分類で、v4 の判定記録の id（`E00` など）とは関係ない。

| 記号 | 類 | 見分け方 | これまでの例 |
|---|---|---|---|
| **E1** | 起動時の初期化（lifespan・import 時） | 第 14.4 節 | shyhurricane（v4） |
| **E2** | 同じ呼び出しで作った一時ファイル・ロックの後始末（D2） | 第 15.2 節 | ccr（v4）、`mkstemp` / atomic write（v3、O41） |
| **E3** | 名前だけの解決の誤り（呼び出し先の取り違え） | 呼んでいるのは組み込みのメソッドや別のクラスの同名メソッド | 組み込みの `set()` を `CacheManager.set` に（v4 の rails-lens）、`bytearray.append`（v3） |
| **E4** | 受け手の型の読み違いで、**動作の種類まで違う** | site のライブラリが違い、その結果 kind も違う | （kind が合っていれば E4 にしない。13 手順 C） |
| **E5** | 子プロセスの標準入力・パイプを書き込みと読んだ | `pipe:write` / `pipe:communicate` で、子が受け取ったものでファイルを変えない | ru-marketplace（v4）、helm / kubectl（v3、O41） |
| **E6** | 到達しない（E1 以外）: 死んだコード・別の入口だけ・定数で閉じた枝・必ず先に抜ける | 第 14.2 節 | |
| **E7** | モデルが決められないのに決められるとした | 固定のコマンドに `shlex.quote` した値だけを渡す spawn など | v3（O41） |
| **E8** | 宣言に反しない（E2 以外）: 冪等な追記（D4）、`flock` のための `'a'`（D4）、読み取りのモード、接続単位の設定など | 第 15 節 | ccr の条件つき追記（v4 の E00） |
| **E9** | その他 | 自由記述 | |

分類に迷ったら E9 にして説明を書く。**分類は集計で「誤の原因の内訳」になり、論文の限界の節の材料になる。**

## 18. 見落としの 1 件を判定する手順

### 18.1 何を判定するのか

対象は「D1 か D2 を明示していて、その宣言への矛が 1 件も出ていないツール」。
**解析器が「違反なし」としたツールに、本当に違反が無いか**を確かめる。

### 18.2 順序（先入観を避けるため、コードを先に読む）

1. **解析器の出力を見る前に**、ツールの本体を読む（`relpath:lineno`）。
2. 本体から、**木の中の**呼び出し先を**深さ 4 まで**たどる（本体 = 深さ 0、本体が呼ぶ関数 = 深さ 1、…）。
   木の外のライブラリ（pip で入るもの）の中は読まない。ただし、**ライブラリの関数そのもの**が環境を変えるもの
   （`requests.put`、`sqlite3` の `execute("DELETE …")`、`shutil.rmtree` など）は、呼んでいれば違反の候補として数える。
3. 宣言（D1 なら 15.1、D2 なら 15.2）に反しうる動作を**すべて**書き出す。到達の条件（第 14 節）も書く。
4. ここで初めて解析器の出力を見る（6.5 の道具。対象の宣言の `contradiction_unknown:<宣言>:…` の注記を探す）。
5. 次の 4 つのどれかに決める。

| 結果 | 条件 |
|---|---|
| **反する動作は無い** | 3 で何も見つからなかった |
| **解析器が不として出している** | 3 で見つけた動作に、解析器が `contradiction_unknown`（不）を出している（例: `net_post`） |
| **見落とし**（誤 clear） | 3 で見つけた、宣言に反する動作に、解析器が矛も不も出していない |
| **不明** | 反するかを決められない（例: 木の外のライブラリが木の中の関数を呼び戻す形、子プロセスの中の動作） |

6. 見落としなら原因を分類する: **深さ**（深さ 4 を超えるところにある）/ **呼び出しの解決**（呼び出し先を解決できていない。
   `opaque` に `receiver` / `unresolved`）/ **受け手の型** / **語彙**（sink の語彙に無いライブラリ。例: loguru の
   `logger.add` のファイル出力）/ **その他**（デコレータの wrapper の中など）。
7. 見落としにも、正と同じく**書き込み先の種類**と**条件の種類**（14.3）を付ける。

### 18.3 注意

- 打ち切りの印（`truncated`）があるユニットで、解析器が途中で読むのをやめた部分に違反があったら、見落としとして原因を
  「深さ」または「その他（打ち切り）」にする。読み切れないなら「不明（打ち切り）」。
- **深さ 4 より奥の違反を偶然見つけたら、`outcome` を「見落とし（深さ 4 の外）」にする**（D68 の 2）。主の見落としの数には
  入れず、別に数えて併記する。深さ 4 より奥を**探しに行く必要はない**（読む範囲は深さ 4 まで）。
- 深さ 4 の中に「反する動作」が無く、深さ 4 の外にだけあるなら `見落とし（深さ 4 の外）`、深さ 4 の中にもあれば、中のものを
  主として `見落とし`（または `解析器が不として出している`）にし、外のものは `note` に書く。
- ログの出力先がファイルかどうかは、`logging.basicConfig(filename=…)`、`FileHandler`、loguru の `logger.add(<パス>)` など、
  **モジュール水準の設定**も確かめる（v4 の R19 はモジュールの一番上で設定していた）。

### 18.4 記録する欄

| 欄 | 書くこと |
|---|---|
| `outcome` | `反する動作は無い` / `解析器が不として出している` / `見落とし` / `見落とし（深さ 4 の外）` / `不明` |
| `cause` | 見落としの原因（深さ / 呼び出しの解決 / 受け手の型 / 語彙 / その他） |
| `write_target` | 見落とし・不として出ている動作の書き込み先の種類 |
| `condition_type`、`condition` | 条件の種類と中身（14.3） |
| `depth` | 見つけた動作の深さ（本体 = 0） |
| `evidence` | 読んだ範囲（ファイルと行）と、見つけた動作の行。**「反する動作は無い」でも、読んだ範囲を書く** |
| `note`、`minutes` | |

## 19.「不明」にするとき

不明は失敗ではない。**分からないものを黙って正や誤に倒さないこと**が、この研究の約束である（CLAUDE.md 規則 4）。
ただし、調べれば分かるものを不明にしない。目安として、**20〜30 分調べても決められなければ不明**にし、理由を書く。

不明にしてよい典型:

- 書き先・宛先・コマンドが、木の外のライブラリの戻り値や実行時の外部の状態で決まり、読み切れない。
- 相手の API（`POST` の先）の意味が、文書にもコードにも無い。
- 起動の方法・初期化の場所が読み切れない（第 14.4 節）。
- 動的な呼び出し（`getattr(obj, name)()`、プラグインの読み込み）で、呼び出し先が決まらない。

不明の理由は、集計で「不明の内訳」として報告する。

解析器の出力（抜粋）:

**組 1: `search_notes` × `builtins.open` × D1**

- 手順 C: 12 行は `open(..., "w")` で書き込み。site は正しい。
- 手順 D: 26 行 `_lookup(query)` → 19 行 `_save_cache(query, ...)` → 12 行。条件は無い。
- 手順 E: 到達する（毎回。条件なし）。
- 手順 F: D1 × FS_WRITE → 反する（ファイルを書く）。

  定義どおりなら「キャッシュ・状態の保存」（後で読み返す）に当てはまらない。読み返しが木のどこにも無いことを grep で
  確かめたうえで、**その他・不明**とし、`note` に「キャッシュの名前だが読み返しが無い」と書く。
  （このように、名前ではなく動作で決める。）
- `evidence`: `server.py:26 → server.py:19 → server.py:12 open(os.path.join(CACHE_DIR, name), "w")。CACHE_DIR は ~/.demo_cache、
  name は引数 query。毎回到達する。`
- 補足: 書き先のファイル名はモデルが決める `query` から作られる（`slot path: 主体=MODEL`）。`query` に `../` を入れれば
  キャッシュの外に書けるかもしれない。これは宣言の正誤とは別の話（パスの注入）なので、判定には入れず `note` に書くだけにする。

**組 2: `export_note` × `builtins.open` × D2**

- 手順 D: 本体の中（道筋なし）。条件なし。

## 21. 判定をぶれさせない工夫

判定者は 1 人なので、1 人の中でのぶれを減らし、減らしたことを示す（2 人目の判定者が段階 6 までに決まれば、5 の (i) で一致を測る。D73 の 1）。

1. **判定の順序を無作為にする**（段階 6）。同じ木の組が続くと、前の判断に引きずられる。
2. **判定の途中で集計を見ない。** 精度が何%になりそうかを見ると、境界の判断が傾く。
3. **1 日の判定の件数に上限を決める**（例: 1 日 10〜15 件）。疲れると判断が雑になる。
4. **迷った件は印を付けて翌日に見直す**（見直したことを `note` に書く）。
5. **判定の一致の確認**（D73 の 1。seed ⑥ で選んだ 10%。2 人目の判定者が段階 6 の時点で決まっていれば、その人が学生のラベルを
   見ずに判定して κ を出す。決まっていなければ下の判定し直し）: 全部を判定し終えて 2 週間以上あけてから、無作為の 10% を
   **元の判定を見ずに**判定し直し、一致率を報告する。これは 2 人目の判定者の代わりにはならないが、「同じ人が同じ手引きで
   同じ結論に着くか」は示せる。食い違った件は元の判定を**直さず**、食い違ったことを報告する。
6. **AI は事実を調べる補助としてだけ使う**（0-9、D70 の 3）。AI に判定させず、AI の答えをそのまま記録しない。AI が示した行は
   自分で開いて確かめ、`evidence` には確かめた行だけを書く。宣言の値と解析器の答えを AI に渡さない。見落としは自分で先に読む。
   使ったら `ai_used`・モデル・ログを記録する（手引き 21 の 6）。

## 22. 手引きで決まらない事例が出たとき

判定の途中で、手引きのどの規則にも当てはまらない事例が出ることがある。そのとき:

1. その件は**「不明」**にし、`unknown_reason` に「手引きで決まらない: <事例の説明>」と書く。
2. `docs/preregistration.md` §5（逸脱の記録）に事例を書く。
3. **手引きを判定の途中で変えない。** どうしても規則を足すなら、足した日時を記録し、**足す前に判定した件と後の件を分けて**
   報告し、足した規則で前の件を付け直した結果も併記する。主の結果は事前登録した手引きのままの判定にする。
4. 解析器の誤りを見つけても直さない。`docs/open_questions.md` に限界として書く（O43 と同じ扱い）。

## 23. 段階 8: 集計（計算のしかた）

### 23.1 V1 頑健性

分母は走査した木の数。`summary.json` から: `ok` の木の数、`ok` 以外の木（全件、原因つき）、時間上限の打ち切りのあった木
（`budget_skipped` > 0。件数と所要時間）、parse 失敗のファイルの数と木の数、`ast_node_cap` などの打ち切りの数。

### 23.2 主指標（宣言ごと）

宣言 d（D1〜D4）ごとに、判定した組を木ごとにまとめる。木 t で判定した組のうち、正の数を c_t、誤の数を w_t、不明の数を u_t とする。

- **本当の矛が 1 件以上あった木の数**（判定した木の中）= c_t ≥ 1 の木の数。これを k、判定した木の数を n、宣言 d の矛が出た木の
  総数を N（n ≤ N。N > 200 なら n = 200、D69）とする。
- **(a) 主** = k / n。判定した木だけで計算するので推定は入らない。
- **推定の木の数** K̂ = (k / n) × N。n = N（全木を判定した）なら K̂ = k。
- **(c) 主** = K̂ / M_d。M_d は宣言 d を明示したユニットを 1 つ以上持つ走査した木の数。「明示した」は矛の判定と同じ条件で決める
  （D73 の 3、2026-10-03）: D1 は `D_kind.explicit` に `readOnlyHint`、D2 は `explicit` に `destructiveHint`、D3 は
  `D_kind.closed_world` が真、D4 は `D_kind.idempotent` が真。
  - （決定の前の文面）「`D_kind.explicit` で数える」。D3 では逆の申告（`openWorldHint: true`）の木を数え、D4 では常に 0 になって
    いた（教科書 第 16 章 16.7 節）。
- **(b) 参考** = K̂ / 走査した木の数。
- どれも**下限**。理由は 2 つ。
  - 1 木 3 件までしか判定しない。
  - 矛の出なかった木の見落としを数えていない。見落としは 200 件の抜き取りで別に示す。
- 区間: (a) は 23.3 の bootstrap。(b)(c) は、bootstrap の各回の (a) の値に N を掛けて分母で割り、その 2.5% と 97.5% を取る。
- **木ごとの精度** p_t = c_t / (c_t + w_t)（c_t + w_t = 0 の木、つまり全部不明の木は除き、その数を書く）。
- **木ごとの精度の平均** = p_t の平均。
- 不明を誤とみなした値（0-5 の併記）: p'_t = c_t / (c_t + w_t + u_t) の平均。

### 23.3 木を単位にした bootstrap（幅の付け方）

「木の選ばれ方がたまたま違ったら、平均はどれくらい動くか」を見る方法。

1. 宣言 d の矛が出て判定した木の一覧を T（木の数 n）とする。
2. T から**重複を許して** n 個の木を無作為に選ぶ（同じ木が 2 回選ばれてもよい）。
3. 選んだ木の p_t の平均を計算する。
4. 2〜3 を B 回（例 10,000 回）繰り返す（seed を固定する）。
5. B 個の平均を小さい順に並べ、2.5% と 97.5% の位置の値を 95% 区間とする。

「割合」（本当の矛があった木の割合）にも同じ方法で区間を付けられる（手順 3 で平均の代わりに割合を計算する）。
**木の数 n が小さい宣言（例: D3・D4 で数木しかない）では区間は信頼できない。** n を必ず併記する。**n が 10 未満の宣言は、区間を
出さずに件数と木ごとの内訳の表を書く**（D73 の 4、2026-10-03。まとまりが少ないと、この方法の幅は実際より狭く出やすい）。

### 23.4 参考（件数）と Wilson 区間

件数の精度 = Σ正 / (Σ正 + Σ誤)。95% Wilson 区間は、判定した件数 n と正の割合 p̂ から:

```
中心 = (p̂ + z²/(2n)) / (1 + z²/n)
幅   = z × sqrt( p̂(1 − p̂)/n + z²/(4n²) ) / (1 + z²/n)
区間 = 中心 ± 幅        （z = 1.96）
```

v4 の値（D1 / D2 計 46 / 60 → 76.7%、64.6〜85.6）で、自分の計算が合うかを確かめられる。
**件数の精度は少数の木に偏りやすい**（v4 では 1 木が 60 件中 38 件を占め、その木を除くと 36.4% だった。事後の分析）。
だから主指標は木の単位にし、件数は参考にする（D67 の 3）。
