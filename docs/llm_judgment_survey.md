# 判定の層に LLM を混ぜる研究の調査と、AuthGap で使えるかの判断

調査日 2026-10-01。学生の問い:「判定の層に LLM を混ぜる研究があるのが気になる。もっと調べて、わたしの研究で使えそうか
使えなさそうかを教えて」。

**調べ方**: ワークフローで 7 体の agent を使った。
- 文献の調査 3 体: R1 一般の SE・セキュリティ、R2 MCP・エージェント、R3 方法論

各報告の全文は `docs/llm_judgment_survey_raw/` にある。本記録者は統合と批判を読み、事実の食い違い 3 点を原文で確かめた（§5）。

**確かさの印**（各報告から引き継ぐ）:
- **高**: repo のコード・プロンプト・結果ファイルを agent が読んだ
- **中**: 第三者の逐語の抜き書き
- **低**: 検索の要約だけ

論文の PDF はプロキシで遮断され、1 本も直接読めていない。数値は確かさの印つきでしか使わない（CLAUDE.md 規則 1）。

## 1. 結論

1. **解析器の判定（矛 / 不 / 何も出さない）に LLM を混ぜるのは、使えない。** 4 つの報告と 2 つの批判がすべて同じ結論。
   - 凍結を破る（`docs/final_evaluation_procedure.md:13,327`、D60 の 2）。
   - 決定性（同じ入力で 3 回バイト一致、`README.md:10`）と、D71 の理由 3（標準ライブラリだけで再現できる）が成り立たなくなる。
   - 仕様書は「LLM を verdict 入力に使わない」を主張の一部にしている（`AUTHGAP_BRIEF_v3.md:82`）。
   - 先行研究の LLM 判定は、決められないものを黙って消すか、どちらかに倒す（§2.3）。原理 2（不明として数える）と規則 4 の逆。
2. **使える余地は、判定の外側だけ。** どれも主指標（矛の精度・木の割合・見落とし・不の中身）を LLM に依存させない形に限る（§3）。
3. **論文の価値を一番上げるのは、LLM を使うことではない。** 先行研究の LLM 判定が「決められないもの」をどう扱うかの
   **対比表**（LLM は使わない）で、AuthGap の差別化の芯（未解決を数える、`docs/related_work.md:24-25`、D40）を、
   LLM 時代の研究にも広げられる（§3 の付記）。
4. **研究にはすでに LLM（本記録者）が深く関わっている**（§4）。論文での開示は、0-9 の選択にかかわらず必要。

## 2. 文献の要約

### 2.1 LLM をどこに置いているか

| 置き場所 | 例（確かさ） | 特徴 |
|---|---|---|
| **(a) 前段**: 仕様・語彙・検出器を作る | IRIS（CodeQL + LLM で source/sink を推論、高）、KNighter（修正パッチから Clang の checker を合成、高）、LLMDFA（抽出器と Z3 のスクリプトを合成、高）、Semia（Datalog の事実を合成、高） | LLM が作ったものを決定的な手段で確かめてから固定し、実行時の判定は決定的に保つ |
| **(b) 後段**: 候補の真偽判定・誤検知の刈り込み | **最多**。IRIS・LLift・BugLens・RepoAudit・KNighter・ZeroFalse・Tencent の産業調査・Vulnhalla（以上 高）。MCP では TaintP2X・antgroup MCPScan・MCP-BiFlow の M3・MalSkills（高） | LLM を外すと、誤検知と棄却の数が大きく動く。確認済みの数はあまり動かない |
| **(c) 解析の代替** | LLMDFA・LLMSAN・RepoAudit（高） | — |
| **(c') 静的に決まらない事実だけを埋める** | MCP-BiFlow の M2（source の確定）、MalSkills、SemTaint（"defers to an LLM to resolve call edges that cannot be resolved statically"、高・写し）、TaintP2X | **AuthGap の「不」に最も近い使い方** |
| **(d) 意味の照合**（記述とコード） | DCIChecker（中）、Cisco の behavioral、TRUSTDESC | 宣言（annotation）ではなく自然言語の記述と照合する |

**機械可読な宣言（readOnlyHint など）と照合するために、LLM に「この POST は相手の状態を変えるか」を決めさせた研究は、
見つかっていない**（R2 の範囲）。

### 2.2 LLM の判断をどう検証しているか

- **正解は LLM の外に置く。** 合成ベンチマーク（Juliet・OWASP Benchmark）、CVE の修正位置という代理指標（IRIS）、
  人手のラベル（Tencent・BugLens・LLift）。**MCP の研究も、最終確認はすべて人手**（MalSkills は 2 人 + 裁定、高）。
- **部品としての LLM の判断を人手と照らした MCP の研究は、見つからない**（R2）。報告されているのは全体の精度とアブレーションだけ。
- **モデルで結果が大きく動く**（高）。
  - Tencent: 同じプロンプトで、誤検知の除去率が 26〜52%。
  - IRIS: 検出数が 41〜55。
  - MalSkills: F1 が 0.76〜0.93。
- **繰り返しはまれ。** 多くは 1 回だけ実行する。LLift は答えが揺れると印を付ける。SecLLMHolmes は 10 回実行する。

### 2.3 報告された弱点と、コードで見つかった弱点

1. **失敗や迷いを、黙って「問題なし」にする**（高）。
   - IRIS: 応答が読めないと警告から消す。
   - RepoAudit: 答えが取れない経路を捨てる。
   - TaintP2X: 解析できないと「脆弱でない」にする。
   - MCPScan: 解析に失敗した記述を落とす。
   - Cisco のプロンプト: "When in doubt, don't flag"。
2. **不明を 2 値に潰すか、どちらかに倒す**（高）。
   - KNighter: "If there is any uncertainty ... classify it as a false positive"。
   - LLift: 定義の無い関数を推測で埋めさせる。
3. **不明を保つ例外**（高）: Vulnhalla の 3 値、MalSkills の "preserve it explicitly as unknown"、Cisco の
   "an errored function is not 'safe', just unknown"。
   ただし Vulnhalla の 3 値は部分一致の先勝ちで、同じ応答が場所によって違う判定になりうる（批判 C1 §1-10）。
4. **決められなかった率を報告した研究は無い**（R2）。
5. **誤検知を刈ると本物も消える。** Tencent の結果ファイルを数え直すと、LLM4PFA は誤検知を 94〜98% 消す一方、
   真の bug の 12〜25% も消す（高。C の bug の例で、MCP の宣言に当てはめるのは外挿）。
6. **答えが揺れる。** SecLLMHolmes では temperature 0 でも、10 回の答えが揃わないマスが gpt-4 で 6/24 あった（高、結果ファイルから数え直し）。
7. **欺かれやすい。** 迎合（sycophancy）が報告されている（Sharma ほか、高）。DCIChecker 自身も対策を書いている（中）。

### 2.4 方法論の文献が求めること（R3）

- **Baltes ほかのガイドライン**（EMSE 2026。原稿の repo を読んだ、高）。
  - 必須: モデルの版・設定・実行日、プロンプトの全文、LLM の役の宣言、汚染と偏りの議論。
  - 人の判断を置き換えるなら、標本を人で検証する。"High inter-model agreement can reflect shared model biases"。
  - "should not treat a temperature of 0 as a guarantee of reproducibility"。
  - **判定者が 1 人で済むのは** "only when judgments depend on widely accepted theories and involve limited value
    conflict"。AuthGap の判定には記録された価値の衝突（D67 の 1）があるので、**LLM を研究に入れるほど、審査者がこの基準を
    判定者 1 人の設計に当ててくる**（C1 §1-11）。
- **NDSS'26 "Chasing Shadows"**（高）: "Disclose when labels or judgments come from LLMs. The ideal mitigation is full manual verification."
- **人と LLM の一致**: 単純な課題では高いが、文脈の大きい課題・セキュリティ固有のコードでは人の代わりにならない（中〜低）。
- **モデルの廃止**: `claude-sonnet-4-5` は 2026-11-30 に廃止予定（SDK の表、高）。最終評価の期間の途中にあたる。

## 3. AuthGap での使い道（候補ごとの最終判断）

統合案の 9 候補を、2 つの批判（C1 妥当性、C2 研究価値）で検討した。2 つの批判が食い違うところは、両方を書く。

| # | 候補 | 判断 | 理由 |
|---|---|---|---|
| 0 | **LLM を使わない**（0-9 の選択肢） | **既定の選択肢として比べる** | 妥当性の面でいちばん単純（C1） |
| 1 | 解析器の判定層に入れる（不を解く・矛を刈る） | **使えない** | §1 の 1。検証すれば候補 2 になる（C2） |
| 2 | 「不」の後段の対照腕（別の列） | **任意。採るなら条件つき** | 下の §3.1。C1 は「価値は小さい」、C2 は「今回入れる価値がある」 |
| 3 | 判定者が原ソースを読む補助（0-9） | **補助のみ。抜き取りの種類ごとに使い方を分ける** | 下の §3.2 |
| 4 | 2 人目の判定者の代わり | **使えない**（参考の κ も出さない） | D67 の 4。同じ系統のモデルで一致が膨らむ。妥当性の証拠にならない |
| 5 | 語彙の見落とし候補の発見 | **補助のみ** | データを見る前に 1 回だけ作って固定するチェックリストにする（C1）。または候補 3 の見落とし点検に吸収する（C2）。解析器には足さない |
| 6 | LLM だけで矛を判定するベースライン | **今後の課題** | 仕様書が予算の都合で削った主張（`AUTHGAP_BRIEF_v3.md:678,951`）。LLM だけが出した矛は標本の外で、判定が上乗せになる。精度で勝てる見込みも薄い（C2） |
| 7 | 記述・宣言・実装の三者照合 | **今後の課題** | 問いが変わり、差別化の軸 4（機械可読な宣言）が薄まる |
| 8 | 判定の手引きの曖昧さの検出 | **補助のみ**（データを見る前に限る） | 益は小さい。手引きの下書きが AI 製なので、使うなら別の系統のモデル（C1） |
| 9 | PPI（人と LLM のラベルを合わせて区間を狭める） | **使えない** | 抜き取りが木の単位のクラスタで、PPI の前提（i.i.d.）と合わない（C1） |
| 付記 | **先行研究の LLM 判定が「不明」をどう扱うかの対比表**（LLM は使わない） | **今回入れる**（C2 の最優先） | 費用はほぼ 0 で、差別化の芯を強める。各セルは学生が原典で確かめてから載せる |

### 3.1 候補 2 の中身（採る場合）

**何をするか**: 最終評価の「不の中身」の 100 組（D69 の 4、D1・D2 で各 50）に、LLM の答え（反する / 反しない / 不明）を
**別の列**として付ける。主指標・不の件数・感度分析には混ぜない。

**C2 の提案（主張の向き）**: 「LLM が不をどれだけ解けたか」を主にしない。事前登録する量は次の 3 つ。
- (i) 学生が「不明」とした組で、LLM が断定した割合（過信の量）。
- (ii) LLM が「反しない」、学生が「違反」とした件数（誤 clear の向き。規則 4 で最も重い）。
- (iii) 繰り返しで答えが食い違った割合（決定性の量）。

こうすると、結果がどちらの向きでも書ける。
- LLM が過信するなら、不を数える設計の裏づけになる。
- LLM がよく当たるなら、後段に LLM を置く余地として今後の課題に書ける。

**C1 の条件**（1 つでも事前登録に先に書けなければ採らない）:
1. **対象**: 0-14 の D1・D2 の 100 組だけ。100 組の外では走らせない（正しさを誰も確かめていない数になる）。
2. **順序**: 学生のラベルを先にコミットし、LLM の出力はその後に開く。その 100 組の判定では候補 3 を使わない。
3. **入力**: pin した SHA の木から、決定的なスクリプトで作る。宣言の引数は AST で取り除く。
   description・docstring・関数名は取り除けないので、限界に書く。
4. **出力**: 3 値。読めない応答・拒否・文脈の上限・タイムアウト・回をまたいだ食い違いは、**すべて不明に数えて件数を出す**（捨てない）。
5. **回数**: 回数と temperature を固定する。項目ごとの答えの分布を出す。
6. **モデル**: 日付つきの ID。廃止が評価と査読の期間の外にあるものを選ぶ。手引きと v4 を作った系統（Claude）とは別の系統を主にするか、系統を記録する。
7. **実行者**: repo の文脈を持たない API で走らせる（本記録者のセッションでは走らせない。§5 の 3）。
8. **報告**: 別の表にする。「学生と LLM の一致」と呼び、評定者間一致とは呼ばない。汚染の議論を限界に書く。

**費用**: API は小さいが、学生の作業は約 20〜40 時間の見込み（C2 の判断。測っていない）。

### 3.2 候補 3（読む補助）の使い方（C1・C2 で一致）

- **矛の判定**: 行を探す役として使ってよい（例:「この関数は lifespan の中か、`main()` の中か、モジュールの読み込み時か」）。
  v4 の誤の大半（起動時の初期化）を、開けば確かめられる事実の問いに落とせる。AI の答えはそのまま記録せず、行を開いて確かめる。
- **見落としの判定**: 最初の読みでは使わない（0-3。先に見ると引っぱられ、見落としの率がモデルに依存する）。
  自分で判定した後に第二の検出器として使い、見つかった見落としは別の列に置く。主の値は人だけの見落とし率にする。
- **不の中身の判定**: 候補 2 を採るなら使わない。
- **採るかどうかの決め方**: 練習 6.8（v4 のデータ）で、AI ありとなしの時間を比べ、データを見る前に決める。
- AI を見る前の判定を記録する。変えたら前後の両方を残す（§21 の 6 との整合は事前登録で決める）。
