## 2. 候補ごとの検討

**候補 1（落とす）。** 統合案に同意します。ほかの根拠も揃っています。

**候補 2（条件つきで残す）。** 次をすべて §2.12 に、段階 3 の前に書けた場合だけ残します。
1. **対象**
   - 0-14 の D1・D2 の 100 組だけ。D3・D4 は外す。
   - 意の類に絞るなら、理由コードの一覧（例：`net_post`、`net_method_unknown`、D1・D2 の `spawn_command`）を先に固定し、見込める組の数を書く。
2. **順序**
   - 学生のラベルをコミットした**後に** LLM を走らせる。またはその前に走らせて出力を封印し、ハッシュをコミットする。順序はコミットの日時で示す（`:1354` と同じ考え方）。
   - その 100 組の判定では候補 3 を使わない。
3. **入力**
   - manifest の witness の file:line から、pin した SHA の木で、決定的に作る。
   - 宣言の引数は AST で取り除く（§1-4）。スクリプトもコミットする。
4. **出力**
   - 3 値（反する / 反しない / 不明）で答えさせる。
   - 次のものは**すべて不明に数え、件数を出す**。捨てない。
     - JSON として読めないもの
     - 拒否
     - 文脈の上限を超えたもの
     - タイムアウト
     - 回をまたいで食い違うもの
   - これは IRIS・RepoAudit・MCPScan の弱点（§1-3 の 1）の裏返しです。統合案は「不明」と「食い違い」しか挙げていません。
5. **回数**
