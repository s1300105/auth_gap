### 候補 1：判定層に LLM を入れる → 入れない

統合案の理由に 1 つ足します。【判断】
- 不の真の中身は、D69 の 4 で学生が 100 組を判定して推定します（`docs/decisions.md:3827-3831`「これまで不の中身は一度も測っていない」）。
- そのため、検証していない LLM の点は、人の推定と競合するだけで情報を足しません。
- 検証すれば、それは候補 2 です。候補 1 を入れる理由は残りません。

差別化への影響も大きいです。【判断】
- 仕様書は「LLM を verdict 入力に使わない」を主張の一部にしています（`AUTHGAP_BRIEF_v3.md:82`）。
- 軸 2「判定の決定性」（`:140`）は先行研究の LLM 判定との対比で、軸 4「機械可読な宣言との照合」（`:142`）と並んでいます。
- 判定層に LLM を入れると、軸 2 が消え、差の芯も消えます。

### 候補 2：「不」の後段分類 → 今回入れる（副次）

**審査員から見た価値（【判断】）**
- 2026 年の審査では「DCIChecker や MCP-BiFlow のように LLM で不を解けばよいのでは」という問いがほぼ確実に来ます。仕様書の答え（出力形式の違い）だけでは主張にとどまります。
- この腕があれば、AuthGap 自身のデータで答えられます。
- しかも結果がどちらの向きでも書けます。
  - LLM が過信する、または誤 clear を出す場合：不を数える設計を裏づけます。
  - LLM がよく当たる場合：「後段に LLM を置く余地がある」と今後の課題に書けます。主指標は人の判定から出すので揺らぎません。
- 結果を見て書き方を選べない設計は、事前登録した副次分析として強いです。
- 置き場所は評価の章の「6. 不と感度分析」（`docs/final_evaluation_procedure.md` 24.1）です。表 1 枚で収まり、焦点はぼけません。

**統合案から変えるべき点（【判断】）**

1. **主な結果の向きを変えます。** 「LLM の解決率」や「一致率」を主にしません。事前登録する主な量は次の 3 つです。
   - (i) 学生の 0-14 の判定で「不明」とした組（`docs/final_evaluation_procedure.md:253`「判定者が原ソースを読んでも決められないもの」）のうち、LLM が「反する / 反しない」と断定した割合。過信の量です。
   - (ii) 学生が決めた組で、LLM が「反しない」、学生が「違反」とした件数。誤 clear の向きで、規則 4 の観点から最も重い誤りです。
   - (iii) 3 回実行で答えが食い違った割合。決定性の量で、MCP のデータで仕様書の軸 2 の材料になります。ただし、測るのは自作のプロンプトであって、先行研究のツールではないと明記します。
2. **対象を意の類に絞らず、100 組すべてで走らせます。** 理由の類（意 / 実 / 定）は、事前登録した層別の列として出します。
   - 絞ると 1 宣言あたり 20 組前後になります。しかも絞り方そのものが分析者の選択になります。
   - 実の類（木の外、運用者の設定）は、LLM が「不明」と答えるべき組です。過信を測るための試金石になります。
   - 定の類は、問いを「事実だけ」にして、宣言との照合を §6 の決定的な規則で行えば、LLM に定義を決めさせずに済みます。
3. **プロンプトは解析器と同じように凍結します。**
   - v2〜v4（最終評価から除く開発用のデータ）だけで作って試します。
   - 最終評価のデータに触れる前に、§2.12 にコミットのハッシュで固定します。
   - §2.12 はまだ書かれていないので（`docs/final_evaluation_procedure.md:264`、`docs/preregistration.md` に §2.12 は無い、高）、今が最後の機会です。
4. **順序を決めます。**
   - 学生は 0-14 を、AI の補助なしで判定してコミットします。
   - LLM の出力は、その後に初めて開きます。

**売り（D40、原理 2）と両立するか**
- 次の条件を満たせば両立します。【判断】
  - 別の列にする。
  - 矛・不の件数と感度分析の上限・下限に混ぜない。
  - 呼び名を「対照腕」にし、「不の解決」とは呼ばない。
  - 原理 2 が禁じているのは「黙って倒すこと」（`docs/contradiction_principles.md:139`）です。事前登録して別に報告する腕は、その逆の行いです。
- 次の場合は売りを損ないます。
  - 主の不の件数を置き換える。
  - 本文の主な数値に「LLM で補正した不」を出す。

**限界として書くこと**
- 1 宣言あたり 50 組で、学生が決めた組はさらに少なくなります。理由ごとでは 10〜20 組になる見込みです。記述統計だけにし、検定はしません。
- モデルが廃止されると再現できなくなります。生の応答はすべて保存します。
- D60 の「本記録者が評価データを見ない」（`docs/decisions.md:3400`）に当たるかは解釈が要ります。
  - D60 の目的は「開発に使わない」ことです。解析器は指紋で凍結済みなので、その目的は保たれると私は見ます。【判断】
  - ただし学生が明示して記録する必要があります。

### 候補 3：読む補助（0-9）→ 今回は補助のみ

論文の価値は上げませんが、0-9 は決めないと事前登録が書けません（`docs/final_evaluation_procedure.md:212-219`）。抜き取りの種類で分けることを推します。【判断】

- **矛の抜き取り（判定の量の大半）**：AI を「行を探す役」として使ってよいとします。
  - 問いの例：「この関数はどこから呼ばれるか。lifespan の中か、`main()` の中か、モジュールの読み込み時か」。
  - これは v4 の誤の大半を占める類（`docs/population_v4.md` V2：誤 14 のうち 9 が起動時の初期化）を、開けば確かめられる事実の問いに落とすものです。時間を減らす効果が最も見込めます。
- **見落としの抜き取り**：自分で判定する前に AI を使うのは不可とします（`:167`「解析器の出力を見る前に判定する」と同じ理由）。
  - 自分で判定した後に、AI を第二の検出器として使うことは事前登録すれば可です。
  - 学生だけの見落とし率と、AI の点検後の率の両方を出します。
  - この点検で動くのは見落としが増える向き（解析器に不利）だけです。誤 clear は作りません。候補 5 はここに吸収できます。
- **不の抜き取り**：候補 2 を採るなら、AI は使いません（R2 と同じ）。
- **採るかどうかの決め方**：練習 6.8 は、もともと v4 で 1 件の時間を測る段です（`docs/decisions.md:3834`）。そこで AI ありとなしの時間を比べ、データを見る前に決めます。

### 候補 4：2 人目の判定者の代わり → 入れない

統合案は「参考なら補助のみ」としていますが、参考の κ も出さないことを推します。【判断】
- 候補 2 を採れば、不の 100 組で学生と LLM の一致は出ます。ただしそれは手法の比較です。
- 判定全体で「学生と LLM の κ」を出すと、判定者間一致として読まれます。D67 の 4（`docs/decisions.md:3784`）とも衝突します。
- v4 の判定と同じ系列の LLM なら、独立でもありません。
- 1 人の判定の弱さを補う手段は、21 の 5 の「同じ人が判定し直したときの一致率」に任せるのが筋です。

### 候補 5：語彙の見落とし候補 → 補助のみ（候補 3 に吸収）

- 解析器は凍結しているので、見つけた語彙は限界の節にしか書けません（`CLAUDE.md` の凍結の項）。
- 母集団全体で語彙の欠けを数える調査は、それ自体に抽出と検証が要る新しい測定です。今回の予算では今後の課題が妥当です。【判断】

### 候補 6：LLM だけのベースライン → 今後の課題

AuthGap が LLM より何を足すかを示せるかを検討しました。【判断】

- **示せそうなこと**
  - 決定性。
  - 不明を数えられること。
  - 3,000 木を API の費用なしで全数走査できること。v4 の 1 木平均 9 秒からの見込みで約 8 時間です（`docs/final_evaluation_procedure.md` 第 27 節）。
  - ただし、これらは実験しなくても論じられます。決定性は候補 2 の (iii) と文献で示せます。
- **示せそうにないこと**
  - 精度で勝つこと。v4 の LLM 判定でも、AuthGap の誤の主因である起動時の初期化は、原ソースを読めば判別できる類です。LLM だけの判定のほうが精度で上回る可能性は十分にあります。
  - 仕様書はその主張をすでに手放しています（`AUTHGAP_BRIEF_v3.md:678,951`）。
- **公平な設計が難しい**
  - AuthGap の呼び出しグラフで LLM の入力を詰めると、「LLM だけ」になりません。
  - repo を丸ごと渡すエージェント型は、費用がかかり、答えが揺れ、事前登録しにくいです。
  - どちらにしても「藁人形だ」という議論に審査が流れ、測定研究の芯から焦点が外れます。
- **採点も部分的にしかできません**
  - 見落としの抜き取り 200 件の対象は「矛が 1 件も出ていないユニット」です（`docs/final_evaluation_procedure.md:164`）。そこでは LLM の誤警報と、AuthGap の見落としを LLM が拾えたかを測れます。
  - 一方、矛の層で LLM だけが出した陽性は、追加の判定がないと採点できません。170〜380 時間の上に判定が乗ります。
- **主の推定は依存しない**
  - 主の推定は人が確かめた標本から出るので、ベースラインが無くても妥当性は崩れません（§1）。
- 今回どうしても入れるなら、最小の形は「見落としの抜き取り 200 件で、学生の判定の後に LLM だけの判定を走らせる」探索的な腕です。それでも私は今後の課題を推します。

### 候補 7：三者照合 → 今後の課題

- 仕様書の軸 4（`AUTHGAP_BRIEF_v3.md:142`）は「宣言 vs 実装を掲げる 3 件はいずれも自然言語 description…を宣言側に置く」と、機械可読な宣言を差にしています。
