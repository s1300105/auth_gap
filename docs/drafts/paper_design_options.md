## 1. 証拠 1: 上流スコープの宣言はどれだけあるか（開発用のデータ）

対象は `corpus/v2-*`・`v3-*`・`v4-*` の MCP の木 266（`post_fetch_check` の `mcp_server`）。

| 何 | 数 |
|---|---|
| 権限を持つ上流スコープの文字列を、MCP サーバのコードで求める木 | **21 / 266（7.9%）**（v2 6/87、v3 9/91、v4 6/88） |
| 同上に、身元の確認だけのスコープ（`openid`・`offline_access` など）の木を足す | 27 / 266（10.2%） |
| スコープを求めず、上流の資格を環境変数のトークン・API キーだけで受け取る木 | 97 / 266（36.5%） |
| 読むだけのツールが、書き込みのスコープの資格を共有する木（照合の候補） | 14。**全部が読むツールと書くツールの混在サーバ** |
| サーバ全体が読むだけなのに、書き込みのスコープを求める木（強い食い違い） | **0** |
| ツール単位で筋の良い候補 | 2（klavis の reddit_search、falcon-mcp の写し） |

- 提供者は Google 7・Microsoft 5 で、ほかは 1〜2 木ずつ散らばる。
- 粒度を表さないスコープが多い（Azure の `.default`、Zammad の `full`、LY Ads の `yahooads`、Ad Manager の `dfp`、dbt の `user_access`）。
  この場合は、スコープからツールごとの権限を決められない。
- ツールごとのスコープを注釈と並べて宣言する実例が 1 つあった（goprofiles。10 ツールすべてで一致）。
- 限界: 取得した木は sparse checkout で、YAML・Markdown・`.env.example` に書いたスコープは見えない（下限）。到達性は import の水準。
  読む・書くの区別は提供者の命名からの推定で、各社の文書とは照合していない。

**3 人とも D を選んだ。** 理由の要約:

  - 上流スコープが当たるのは約 1 割で、強い食い違いは 0 件。
  - 候補の多くは「1 つのトークンを共有する混在サーバ」という構造の話で、開発者の誤りとは読みにくい。
  - 新しさの一部は MiniScope に取られている。
  - 一番強い資産（凍結した解析器・352 件の再現率・事前登録した実態調査）が薄まるか、副に回る。
- **A の減点は言い方にある。** 仕様は注釈を「ヒント」と書き、信頼できないサーバのものは信頼するなと書く。それを「認可の宣言」と呼び、
  事例 1 つで「枠組み」を名乗ると突かれる。仕様の語どおり「ツールの振る舞いの宣言（ヒント）」と書き、一般化は考察で控えめにする。
- B が D に並ぶ条件（評価者が挙げた目安。値は評価者ごとに違う）: 新しいデータで事前登録して測り、上流スコープが当たるサーバが

- 封の後に B を足すと事後の追加になる。B を採るなら封の前しかない。
