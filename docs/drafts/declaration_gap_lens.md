**学生の問い**: 「この MCP で起きる脆弱性の幾つかを一般化して整理し、宣言と実装の Gap としてまとめられない？それを論文として提案できない？」

## 1. 結論

**論文の主張として「MCP の脆弱性は宣言と実装のずれとして一般化できる」と提案するのは、今の材料では勧めない。** 2 人の評価者はどちらも
「枠づけ（framing）にとどめるべき」と判定した。理由は次の 3 つ。

1. **当てはまる脆弱性が少ない。** MCP の脆弱性の記録から無作為に 40 件を選んで分けると、MCP の宣言（注釈・名前・説明・スキーマ・
   スコープなど）とのずれが核のものは **0 件**だった（95% 区間 0〜8.8%）。約 7 割は、宣言と関係ない古典的な欠陥（パス走査・コマンド注入・
   SSRF・認証の欠落）だった。広く読むと 30% まで増えるが、その分は既存の CWE（CWE-284/863 の認可の欠落、CWE-807 の信頼できない入力に
   頼った判断など）の言い換えになる。
2. **言葉と型は先に取られている。**
   - BIV（arXiv 2605.11770）は agent skill について "a pervasive description-implementation gap" と書き [確認]、今後の課題に
     "Cross-registry comparison to MCP servers, the GPT Store, and VS Code extensions" を挙げる [確認]。
   - MCP の説明文とコードのずれは DCIChecker（2606.04769）と MCPDiFF（2602.03580）が測っている（`docs/related_work.md` に記録済み）。
   - 「統一のレンズで MCP を含むエージェントの脆弱性をまとめる」SoK の型は、B-I-P（2512.06914、信頼と認可のずれ）が既に取っている [確認]。
3. **取り出した「壊れ方」には既に名前がある。** 構文の分類で意味を守ろうとして破られる、一覧でだけ絞り呼び出しでは強制しない、初期化に
   失敗すると開いたままになる、symlink を解かない、などは、それぞれ CWE がある。しかも宣言の無い記録にも同じ壊れ方が出る。

## 2. 試しの分類の結果（探索の値）

対象: OSV の PyPI・npm の記録のうち、2025-01-01 以後で MCP に関係するもの 382 群（悪性パッケージ 236 群と取り下げは別）。
`random.Random(20261009)` で 40 件を選んだ。

| 分け方 | 件数 |
|---|---|
| 宣言と関係ない実装の欠陥 | 34 / 40 |
| 運用の設定・プロトコルの設計・クライアントの信頼 | 5 / 40 |
| 何かの宣言とのずれが核 | 1 / 40（MCP の宣言ではない。運用者向けの CLI の表示） |
| **MCP の宣言とのずれが核** | **0 / 40** |

無作為でない追加（repo で既に知っていた記録、OWASP が引く記録、語での篩い）からは、ずれが核の実例が数件見つかった。どれも無作為標本の率には
混ぜない。

| 型 | 実例（advisory の文は agent が照合、うち 2 件は本記録者も照合） |
|---|---|
| 「読むだけ」の宣言で書ける | DBHub（TypeScript、`readOnlyHint: true` を付けた `execute_sql`）、mcp-neo4j-cypher（Python、`readOnlyHint=True` の tool で書き込みの判定が正規表現） |
| 名前・文書で読み取り専用をうたう | ProxySQL（"documented read-only contract"）、executeautomation/database-server |
| read スコープで書ける | mcp-memory-service（"OAuth read-only clients can write and delete memories through MCP tools/call" [確認]） |
| 一覧でだけ絞る | mcp-server-kubernetes（"Tool Access Control Bypass via Presentation-Layer Filtering Without Execution-Layer Enforcement" [確認]） |

評価者の指摘: このうち roots・aud（トークンの宛先）・tools/list の例は、宣言した者と破った者が別（クライアントが宣言しサーバが破る、など）か、
当てにしたのが運用者自身で、「自分の宣言を自分の実装が破る」という定義に合わない。合わせると、篩いの 9 群は 5〜7 群に減る。

## 3. それでも使える形（評価者の提案）

### 3.1 今の論文の枠づけに使う（勧める）

- 序論に 1 段落: ToolAnnotations は、受け手が確認を省くのに使う「自己申告のヒント」の 1 種である。同じ型のずれは、ほかの宣言（名前・
  スコープ）でも advisory に出ている。厳密に確かめた 3〜4 件で示す（mcp-neo4j-cypher、DBHub、mcp-memory-service、ProxySQL など）。
- 考察に 1 節: AuthGap の「不」は、問い合わせ言語（SQL・Cypher）の文字列の中の効果のように、静的には決められないずれを正しく
  示している。欠落（宣言が無い）と偽の主張（宣言があって反する）は別の危険である。
- 守ること:
  - 数は「探索・未検証」と書き、無作為の 0/40 を必ず添える。
  - 「枠組み」「認可の宣言」と名乗らない（仕様の語は「ヒント」）。
  - RQ・指標・事前登録には足さない。
  - ここで挙げた CVE の木に凍結した解析器を走らせない。出力も見ない（判定の公正さのため）。

### 3.2 別の論文にするなら（今は勧めない。段階 D の後）

評価者が「これがあれば強くなる」と挙げた条件:
1. **1 件ごとに 5 つ組を記録する**: 宣言者・宣言・受け手・緩めた統制・強制者。次の 3 類を分ける。
   - (a) 自己申告が偽（宣言者と実装者が同じで、受け手は別）
   - (b) 他者の宣言を強制しない（roots、aud、redirect_uris）
   - (c) 運用者が設定した保護が届かない
2. **MCP の多者構造に固有の、検証できる仮説を立てる**: 「強制者が宣言者から独立しているかで、ずれの向きが決まる」。OS が強制する
   Android の権限のように強制者が独立していれば、宣言より危険な側にはずれにくい。サーバ自身が強制するスコープや一覧のように宣言者が
   自分で強制すれば、危険な側にもずれる。宣言の種類ごとに全数で確かめれば、CWE の言い換えではない知見になりうる。
3. **言い換えでないことを対照つきで示す**: 「公表された宣言を他者が当てにする記録」と「宣言の無い保護の失敗の記録」を、CWE をそろえて
   比べる。重さ・修正の不完全さ・自動承認が重さの理由に入るかなどで差が出なければ、言い換えと結論する。
4. **記録の全数（382 群以上）を、事前登録した手引きで 2 人が独立に分け、κ を出す**。宣言は advisory の文ではなくコードで確かめる
   （DBHub と neo4j は、コードに readOnlyHint があるのに advisory が触れていない）。
5. **レンズから出た静的な検査で、新しい欠陥を見つける**（例: 一覧の条件と呼び出しの検査を並べる、要求スコープと振り分け先の tool の
   効果を並べる）。新しい解析器で、凍結版は変えない。責任ある開示（O3）を先に決める。

行き先は、測定系の会議かワークショップの「MCP の advisory の根本原因の実証研究」で、宣言のずれはその軸の 1 つ、という形が現実的。

## 4. 本記録者の意見（[判断]）

- 「宣言と実装のずれ」は、**MCP の脆弱性全体を一般化する言葉としては弱く、AuthGap の動機と位置づけを説明する言葉としては強い**。
  前者として出すと、0/40 と BIV・B-I-P で反論される。後者として使えば、今の論文の序論と考察が厚くなる。
- 一般化を主張するより、「受け手が統制を緩めるのに使う宣言には、照合する層が要る。注釈はその代表で、AuthGap はその照合をする」と
  1 点に絞るのが安全。
- 別の論文は、段階 D の後に、上の 3.2 の 2（強制者の独立性の仮説）を中心に据えられるかで決めるのがよい。
