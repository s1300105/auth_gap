### 2.2 GAP_INJECT が立つ条件（層の境界がどこにあるか）

`authgap/verdict.py:219-258`（`_inject_coordinate`）を上から読むと次のとおり。

1. 値の主体が MODEL でなければ立たない（:226-227「if value.prin is not Prin.MODEL: return」）。**確度は見ない**ので、G2 は opaque を含む。
2. ゲートが要求の主体を引き上げると立たない。ただし weak なら残る（:231-232「if req is not Req.MODEL and not weak:
   return  # ゲートが引き上げているので GAP ではない」）。引き上げるのは強い値検証（strong-path / strong-token）、
   既定で閉じた allowlist、承認の割り込み。
3. D_op が覆うと INVENTORY になり立たない（:234-237「if inp.d_op.covers(inp.tool_name): row.verdicts.add("INVENTORY")」）。
4. rubric 1c: ツールが rubric 1c の名簿にあり、主 slot で、**検証子が無く**、exposure が供給されていると INVENTORY
   （:243「if not any_validator and inp.exposure_supplied:」）。**v2 では働いていない。** `scripts/scan_v2.py:253-255` の `RunConfig(...)` は
   exposure_file も rubric_1c_path も渡さず、既定は `authgap/runner.py:40`「exposure_file: Optional[str] = None」、:42「rubric_1c_path: Optional[str] = None」、
   :143「exposure_supplied=bool(cfg.exposure_file),」。manifest の行にも `rubric_1c` の値は 0（第 0 節）。
   最終評価の走査が同じ設定かは、最終評価の走査の設定で確かめる（今は見ていない）。
5. kind で絞る（:256-257「if eff.kind in P0_KINDS or eff.kind in ("DB", "NET"): row.verdicts.add("GAP_INJECT")」）。

**層の動機とのずれ**（どちらの向きにも動く）:
- 強い検証・allowlist で消えるもの: strong-path は「root の下」しか保証しない。その範囲の中ではモデルが選べるので、動機の意味では**取りこぼし（FN）**。
- 規則 W で残るもの: 承認ゲートがあっても weak の検証子があれば残る。確認が省かれないので、動機の意味では**誤警報（FP）**。

**定義の 2 案**（第 8 節の 1）:
- 案 A（学生の (a) の文言）: GAP_INJECT を条件にする。凍結済みの判定語で、研究者が後から選べる自由度は小さい。
  ただし、層に入るかどうかをゲートの等級と規則 W が決める。CLAUDE.md の表ではゲート側の語彙は「付録」で、
  「付録の語彙も消さないが、核の説明には使わない」。D36 は 3 座標の統合を降ろしている（`docs/decisions.md:194`「| 2 | 3 座標（trig / val / gate）の統合で
  脆弱版と修正版を判別する | trig + val + gate 全部 | **主張から降ろす** |」）。層を核（矛）の内訳として書くなら、案 A を主にすることは
  この規則からの**逸脱**で、理由を決定の記録に書く必要がある。
- 案 B: 主 slot の値の主体 MODEL を条件にし、ゲートの状態（なし / weak / strong・allowlist / 承認 / D_op / rubric 1c）と GAP_INJECT の有無を列として出す。
  条件は val 側の語彙（CLAUDE.md の表で「核」）だけで書ける。案 A はその部分集合として出せる。
- v2 ではどちらも 8 位置で同じになった（主 slot に MODEL があって GAP_INJECT の無いものは 0。第 0 節、未検証の値）。
  どちらを選んでも v2 の数は変わらないが、両方の数を見た後の選択であることに変わりはない。

  anybox の 1 行（`blender_cli.py:165`）が v2 の G2 の 8 件のうち 5 件を占めた。8 組 = 4 位置 = 4 木。

  手引きも「同じツールの同じ site・kind の効果が複数の行にあっても 1 組にまとめてある（`locations` に並ぶ）」（`docs/drafts/final_judging_guide_draft.md:53`）。

### 2.4 循環（層が新しい情報を足さない部分）

**解析器の側**:

  - `_by_choice` の hit: `spawn_model`（:378・:403・:519。argv0 / shell_string）、`fs_writeout_model_path`・`fs_unknown_model_path`
    （:410「_by_choice(e, ("path",), f"fs_{c}_model_path", (CONTRA_UNKNOWN, f"fs_{c}"))」。D2。`c` は `_fs_class` の writeout / unknown）、

### 3.2 問いの文（案）

> 3. **引数が決めるか**（D1・D2 の正の組だけ。答えは判定を変えない）: 正にした行で、宣言が問う制御位置を、ツールの引数（モデルが渡す値）が決めるか。

**制御位置（宣言ごと）**

### 3.3 判断の規則（案）

ラベルは**制御位置の値だけ**で決める。body・書く中身・`SET` の値・`INSERT` の値に引数が届くかは問わない。

- R1（原理 3-a）: 引数の取りうる値の全体で考える。サーバの認可や包含の検査（例 `require_room(room_id)`、`is_relative_to(save_dir)`）が
  届く範囲を絞っても、その範囲の中で引数が既存のものを選ぶなら `選べる`（D84 の「一部でも」と同じ向き）。絞り方は `note` に書く。
  **この既定は案で、学生が決める**（第 8 節の 14）。
- R2 `選べる`: 引数が制御位置の値に届き、引数の値を変えると、呼び出しの前からある別のもの（ファイル・表・行・資源・ホスト）か別の操作に及ぶ。
  **一部でもよい**（`docs/decisions.md:4367`「**一部でも決めれば `はい`**」と同じ）。フォルダの外に出られるかは `note`。
- R3 `流れ込むだけ`: 引数は制御位置の値に届くが、及ぶ先を変えない。例: プレースホルダの個数、同じ呼び出しで新しく作るものの名前・置き場所（R8）。
- R4 `決まっている`: 引数が制御位置の値に届かない。位置が定数・運用者の設定・コードが作る値（`mkstemp`・`uuid`・時刻）。
  **宛先ホストが定数で、body や URL のパスにだけ引数が届く形はここ**（v2 の nan-fe・asquared の通知）。
- R3 と R4 は、D84 の `target_by_arg` との対応ではどちらも `いいえ` の側になる。区別が要らなければ 1 つのラベルにまとめる（第 8 節の 15）。
- R5 `不明`: 第 19 節の類で出どころを決められない。判定（正）は変えない。`流れ込むだけ` や `決まっている` に倒さない（規則 4）。
  目安は第 19 節と同じ（手引き :717「目安として、**20〜30 分調べても決められなければ不明**にし、理由を書く。」）。理由は第 19 節の類を 1 つ `note` に書く。
- R6: 1 組に行が複数あるときは、手順 G で最初に正と分かった行で答え、その行を `control_line` に書く。
  1 つの行に制御位置が複数あるときは、それぞれに答え、選べる ＞ 不明 ＞ 流れ込むだけ ＞ 決まっている の最上位を `control_by_arg` に、
  それを与えた制御位置を `control_pos` に書く（例: SQL の文は `流れ込むだけ`、行は `選べる` → `選べる`/`DB の行`）。
- R7: 解析器の slot の主体と確度は手がかりにすぎない（D84。`docs/decisions.md:4370`「解析器の slot の出力は手がかりにすぎない」）。
  層の印（G2 / G3）は判定表に載せない。**ただし盲検ではない。** 判定者は手順 B で「**slot の主体と確度**、**行の注記**（`contradiction:D1` など）を出す」
  （手引き :138-139。道具は `docs/final_evaluation_procedure.md:496`「print(f"  slot {name}: 主体={s.get('prin')} 確度={s.get('prov')} 根={s.get('roots', [])}")」）。
  判定表にも理由のコードが載る（`scripts/final_sheet.py:36`「"contradiction": ["tree", "unit", "unit_relpath", "unit_lineno", "site", "kind", "decl", "reasons", "locations"],」）。
  G2 / G3 の材料（主 slot の MODEL・resolved、`net_model_host` などの理由）はそのまま判定者に見える。
- R8: 同じ呼び出しで新しく作るもの（ファイルの名前・置き場所、DB の行）の制御位置を引数が決めても、既存のものに及ばない
  （必ず新しいものになる。例: 未使用の番号つきの名前、`O_EXCL`、同じ呼び出しで `INSERT` した行の更新）なら `流れ込むだけ`。
  既存のものと同じ名前・行を指せるなら `選べる`。

1. **件数が小さい**: v2 では G2 が 4 木、G3 が 1 木。最終評価でも 10 木に届かず、区間が出ない見込みが高い。抜き取りは 1 木 3 件までで層を多めに引かないので、
   層の中の判定済みが 0 になりうる。層は表で読むものになる。
2. **G3 が崩れうる**: v2 の唯一の G3（code-rag）は手で読む限り誤警報に見え、手引きでも誤の見込み（第 2.6 節）。v2 では G3 に人のラベルが付かない見込み。
   最終評価でも G3 は解析の形落ちに弱い。
3. **opaque が多い**: G2−G3 は「不明」で、モデルが選べるとも選べないとも言えない。G0 でも、主 slot の値だけで見ると「モデルの値は届かない」と言えそうなのは
   MODEL を含まず全部 resolved のもの（v2 で 120/221）だが、そのうち 65 は効果そのものが opaque（DB 59、NET 6）で、残りが言える上限である。
   93/221 は不明（第 0 節、未検証の値）。「矛の大半はモデルが制御できない」とは書けない。
4. **O33**: `sql` の MODEL はバインド変数やプレースホルダの個数でも立つ。G2 の DB はこの誤警報を含みうる（ただし godsaeng のように、同じ行で別の制御位置を選ぶこともある）。
5. **降りなかった先**: O50.5・O50.6・深さの外は分子にも分母にも入らない。印が無いので量も見積もれない。
6. **ゲートとのずれ**: 案 A では strong / allowlist で外れ（FN）、規則 W で承認つきの weak が残る（FP）。
7. **循環**: 選択理由の矛は、GAP_INJECT が立ち選べた slot が主 slot なら G3 に入る。v2 の G3 は完全に同語反復で、選択理由に依らない S2 は 0 だった。
   D3 の層は構造上、理由のコードの言い換えに近い。査読では「D3 の層は理由のコードの言い換え。それ以外の層は v2 で G2 が 3 木（anybox・canvas・godsaeng）・
   7 組で、どれも書いた者自身が誤警報らしいと最初に読んだ（godsaeng は読み直しで行を選ぶ形と分かった）」と言われうる。人の側にも同じ循環がある（第 2.4 節）。
8. **人の問いの曖昧さ**: 「制御位置」の範囲（主 slot か、D84 の行・資源 ID まで含むか）、定数の候補から選ぶだけの形（`if mode == "x": path = A else B`）、
   作ったものの名前・置き場所（R8）、認可が絞る範囲（R1）で判定者が割れうる。
   一致の確かめは手引きの既定（:865-871。2 人目がいれば (i)、いなければ (ii) **判定し直し**）で行い、両方の判定が正の組についてラベルの一致率を出す。
   10% の抜き取りのうち両方が正の組だけが比べられるので、件数が小さいことも書く。
9. **D1 以外の動機の裏付け**: 「確認を省く」ことを文書で確かめてあるのは D1 だけ（`docs/decisions.md:4365`「**D1 だけ**を対象にする。」）。
   D2・D3 の層には、この動機の文書の裏付けが無い。v2 では D1 の G3 は 0 件だった。書き方は第 5 節で D1 と D2・D3 を分けた。
10. **順序**: 層は v2 を見た後に考えた。最終評価に対しては事前だが、v2 に対しては事後である（第 0 節）。
11. **盲検ではない**: 層の印は表に載せないが、印を決める slot の主体・確度と理由のコードは判定者に見える（R7）。v2 では主 slot に MODEL がある 8 件がすべて
    GAP_INJECT だったので、印を消しても中身は消えない（code-rag なら「slot url.host: 主体=MODEL 確度=resolved」が出る）。人と解析器の一致は、
    独立な確かめとしては読めない。
12. **構成概念のずれ**: 主 slot の集合は別の目的で作ったもので、宣言と slot の対応が無い（第 2.1 節）。人の問いは宣言ごとに制御位置を決める。
