### 第 24 章

この章の演習は、説明のための作り話を使っています。
「人の判定」の答えは、判定の手引きの下書き（`docs/drafts/final_judging_guide_draft.md`。未承認）に沿った考え方の例で、最終評価の判定の正解ではありません。
最終評価の判定は学生 1 人が行い、AI（LLM）は使いません（D70 の 3）。

#### 演習 24-1（壊しに行く入力を作る）

**(1)** **解決を広げる変更**です。
今まで受け手の型が分からず、解決しない（`opaque(unresolved)` として保留する）か名前だけで降りていた呼び出しを、`resolved`（確か）として 1 つの関数に決めるからです。
`CLAUDE.md` の約束により、敵対的レビューは**必須**です。

**(2)** 「木の中に `send_report` という名前の関数が 1 つしか無いので、`x.send_report(...)` はその関数を指すはずだ」という根拠です。
言い換えると、「同じ名前のものがほかに無い」ことを、「呼び出し先がそれである」ことの証拠にしています。

**(3)** 崩す入力の例と、起こりうる誤りの向き:

| 崩す入力 | 何が起きるか | 誤りの向き |
|---|---|---|
| 受け手 `x` が**木の外のライブラリ**のオブジェクトで、そのライブラリも `send_report` というメソッドを持つ（`client = vendor.Client(); client.send_report(r)`） | 木の中の無関係な `send_report` に `resolved` で降り、その関数の効果を出す。一方、本当の呼び出し先（ライブラリのメソッド）は「確か」に解決済みとされ、保留の印（不）が消える | 木の中の関数が効果を持てば**誤警報**。本当の呼び出し先が環境を変えるのに、木の中の関数が何もしなければ**誤 clear**（保留が「問題なし」に倒れる） |
| 木の中の `send_report` は**クラスに属さない関数**で、`x` はまったく別の型（`resp = requests.get(u); resp.send_report()` のような形） | メソッド呼び出しを、クラス外の関数に `resolved` で結ぶ | 誤警報か誤 clear（上と同じ） |
| `send_report` が `try: from ext import send_report` / `except ImportError: def send_report(...)` のように、**実行時に差し替わる** | 木の中の予備の定義に決めつけ、実際に使われる `ext.send_report` の効果を見ない | 誤 clear |
| 同じ名前の関数が**テストファイルにだけ**ある（偽物の実装） | 本体のコードから、テストの偽物に降りる | 誤警報（偽物の効果）、または誤 clear（本物の効果を見ない） |
| `global send_report; send_report = other` のように、どこかで**名前を書き換える** | 書き換えた先を見ない | 誤 clear |

表の読み方: 1 行が 1 つの崩す入力です。
たとえば 3 行目は「`try` / `except` で実行時に差し替わる関数の場合、解析器が木の中の予備の定義に決めつけると、実際に使われる外部の関数の効果を見ないので、誤 clear になる」と読みます。

2 行目の形は、実際に起きています。
D57 の敵対的レビューで、「属性の呼び出し（`resp.get(...)`）が**クラスに属さない関数**へ確度 `resolved` で降りる経路」が見つかり、決定の記録は「推測の経路を確かな経路として出す誤り」として、`opaque(unresolved)` に直しています（§9.5）。
4 行目の形も、O30（テストファイルの定義に結びつく）として直されました。
3 行目・5 行目の形は、D17 改訂 4・5 や D61 の改訂で扱われた形（同じ名前の束縛が複数ある、読む側で書き換える）に近いものです。

（出典: `docs/decisions.md:3077-3081`（D57 の §9.5）、`:3066-3069`（O30）、`:1710-1731`（D17 改訂 4）、`:3472-3480`（D61 の改訂の G3））

#### 演習 24-2（レビューの結果を読む）

**(1)** 点検役が指摘したが、独立した検証役が最小の入力で**再現できなかった**（または前提が誤っていた）ものが 2 件あった、という意味です。

**(2)** 凍結して**よい**と考えられます。
D19 の規則 1 は、凍結の条件を「直前の修正の差分だけを対象にしたレビューで、**false-clean・効果行の消失・クラッシュの向きの確認済み指摘が 0 件**」としています。

ただし、3 巡目のレビューが「2 巡目の直しの差分」を対象にしていたことが前提です。

**(3)** 記録と論文には、たとえば次のように書きます。

- 3 巡のレビューの経過（各巡の確認・棄却の件数と向き）。
- 凍結の条件（誤 clear・効果行の消失・クラッシュの向きの確認が 0）を満たした巡と、その版。

「欠陥は無い」とは**書けません**。
D19 のとおり、「指摘が 0 件でも欠陥が無いことは示せない。凍結は『この手続きで見つからなかった』ことの記録」と書きます。

#### 演習 24-3（調査の主張を使う）

**(1)**

- (a) [確認]: 本記録者が原文を取り寄せて、引用の文字列があることを確かめたものです。それでも、論文の著者として、学生が原文（URL）を開き、引用の文字列と前後の文脈を確かめてから使います。調査の文書自身が「論文に載せる前に学生が原典で確かめる」としています。
- (b) [agent]: agent が原文を読んだと報告しただけで、本記録者は照合していません。学生が原文（issue のページ）を開いて確かめるまでは、事実として書きません。確かめられなければ、使わないか、「確かめていない」と分かる形で書きます。
- (c) 確かさ 低（検索の要約だけ）: 研究 X の論文本文や公開 repo（依存関係・import）を読んで確かめます。確かめられないうちは、「自前のパーサの上に作っている」と断定して書きません。数値は使いません。

**(2)** 検索の要約は、研究の**自分で作った部分**（その研究の貢献として書かれた層）を説明することが多く、**その下の土台**（どの基盤の上に作ったか）までは言わないことがあります。

確かめるときは、主張と同じ層（パーサ・中間表現・呼び出しグラフ）を見ます。

**(3)** 仕様書 82 行目は、この研究が「**LLM を verdict（判定）の入力に使わない**」ことを主張の一部にしているので、その主張を支える関連研究の記述自体を、LLM の要約に頼ったまま提出しない、と決めています。

#### 確認問題 24-1

間違った相手に確定すると、解析器は**その間違った相手の中だけ**を読み、本当の呼び出し先の中を読みません。
本当の呼び出し先にファイルの書き込みなどの効果があっても、それは出力に現れません。
しかも、相手を「確か」（`resolved`）に決めたので、前なら付いていた保留の印（`opaque(unresolved)` による「不」）も付きません。
宣言に反する動作があるのに、矛も不も出ない。これが誤 clear です。
作例では、D61 の最初の実装（G2）が `DOCS[name].strip().save()` の `.save()` を組込み型のメソッドと決めつけ、本当の相手 `Document.save` の書き込みを消しました。

#### 確認問題 24-3

**7 体**の agent を使い、そのうち **2 体**が「壊しに行く役」（批判的検討）でした。
観点は、**妥当性**（研究として正しく測れるか・再現できるか）と、**研究価値**（論文の価値を本当に上げるか）です。
残りは、文献の調査 3 体（一般の SE・セキュリティ、MCP・エージェント、方法論）、repo の中の差し込み箇所の洗い出し 1 体、統合 1 体でした。

調査の結論を論文に使う前に、**学生が原典で確かめます**。
調査の報告そのもの（批判役のものも含む）が LLM の出力だからです（`docs/llm_judgment_survey.md:20`、仕様書 82 行目）。
確かさの印（高・中・低）を見て、確かめられなかったものは、確かめていないと分かる形でしか使わず、数値は使いません。

#### 確認問題 24-4

- **変わったもの**: 論文に書く**理由づけ**。「新しい分野では自前の解析が多い」は単純化しすぎで、言語の水準（パーサ・呼び出しグラフ）では既存の基盤を使う研究と自作の研究が同じくらいあり、多数派は無い。AgentFlow は自前ではなく YASA の上とされ（検索の要約だけで確かさは低）、前の「一次資料で自前と確認済み」は、確かめた層（ADG）を取り違えた誤りだった。論文では「みんな自前だから」とは書かない。
- **変わらなかったもの**: 「解析器は自前のまま」という**決定**。理由は、AuthGap 自身の 3 つの事情（前身の Pysa 設計が成り立たなかった・率を測るために解析できなかったものを理由つきで数える必要がある・標準ライブラリだけで再現できる）で示す。解析器は凍結のまま（`analyzer-freeze-3`）。
