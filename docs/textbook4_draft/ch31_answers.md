#### 演習 31-1（O34 の前と後）

**(1)**

| ツール | 値の root | O34 の前（`860aa93`） | 凍結版 |
|---|---|---|---|
| `both_checked` | `{name, topic}` | `GAP_INJECT` なし | `GAP_INJECT` なし |
| `one_checked` | `{name, topic}` | `GAP_INJECT` **なし**（誤 clear） | `GAP_INJECT` **あり** |
| `renamed` | `{name}` | `GAP_INJECT` なし | `GAP_INJECT` なし |
| `none_checked` | `{name, topic}` | `GAP_INJECT` あり | `GAP_INJECT` あり |

- `both_checked`: `name` も `topic` も許可リストで検査しているので、root ごとに採点しても、どちらも `OP`。いちばん弱いものも `OP` で、ゲートは効いている（`DOM`）。直す前も後も `GAP_INJECT` は出ない。
- `one_checked`: 直す前は、`name` の検査が root の 1 つと重なるので値全体を `OP` にし、`GAP_INJECT` を出さなかった（誤 clear）。凍結版は、`topic` を主語にした採点が「ゲートなし」（`MODEL`）なので、いちばん弱い `MODEL` を採り、`NODOM`（理由 `non_binding_gate`）で `GAP_INJECT` を出す。
- `renamed`: root は `name` の 1 つだけなので、厳格版の処理（root が 2 つ以上のとき）に入らず、直す前と同じく検査が効く。
- `none_checked`: ゲートの候補が無いので、直す前も後も `NODOM`（理由 `no_gate`）で `GAP_INJECT` を出す。

本書の執筆時に 2 つの版で走らせ、`one_checked` だけが「直す前は `GAP_INJECT` なし、凍結版はあり」になることを確かめました。

**(2)** root は、「その値がどのツール引数から来たか」の印で、名前の書き換え（`who = name`）を越えて保たれます。
`who` の値の root は `{name}` のままなので、`name` を検査するゲートの主語（root `{name}`）と一致し、主語一致が成り立ちます。
`authgap/gate.py` の `subject_ok` の説明の文書も、「root は名前の書き換えを跨いで保たれるので、AST の名前の一致より正確である」と書いています。

#### 演習 31-2（A2 の出力を読む）

**(1)**
- 2 行目: 「`git_diff` の道筋で、`argv[*]` の等級が『なし → `strong-token`』に変わる」という期待（1 か所以上）について、条件に合う変化は **0 か所**だった。実際に観測した変化は `None->None` で、修正の前後どちらも「検査なし」のまま変わらなかった。
- 3 行目: 「`argv[*]` の要求主体が `MODEL → OP` に変わる」という期待（2 か所以上）について、条件に合ったのは **1 か所**だけだった。観測された 2 つの変化のうち、1 つは `MODEL->MODEL`（変わらない）、もう 1 つは `MODEL->OP`（期待どおり）。5〜6 行目から、変わったのは `git_checkout` の道筋だと分かるので、変わらなかったのは `git_diff` の道筋です。

**(2)** `git_checkout` のコマンドの引数は `branch_name` だけで、修正で `branch_name.startswith("-")` の検査と `rev_parse` が入りました（`server.py:186-193`）。root は 1 つで、それが検査されています。
`git_diff` のコマンドの引数は `f"--unified={context_lines}"` と `target` の 2 つで、root は `{target, context_lines}` です。修正の検査は `target` にしか効かず、`context_lines` はハンドラで検査されていません（`GitDiff` の `int` は一覧で知らせるだけ）。
厳格版 O34 は root ごとに採点し、いちばん弱い `context_lines`（検査なし）を採るので、`git_diff` の道筋の等級は「なし」、要求主体は `MODEL` のままです。

**(3)** any-change は、8 つの座標のどれかの値が違えば通ります。A2 では `git_checkout` の道筋で等級と要求主体が変わったので、通ります。
any-change は、逆向きの対（修正後 → 修正前）や、`open` を `Path.read_text` に書き換えただけの対でも通るので（`two_sided.py` の説明の文書）、通ったことは「修正を検出した」ことを意味しません。だから主指標は、向きと位置まで照らす事前登録照合です。

#### 演習 31-3（例外の提案を評価する）

**(1)** 問題点の例（3 つ以上）:

1. **結果を見てから作った規則**です。A2 が落ちたのを見て、A2 を通すために思いついたもので、CLAUDE.md 規則 5（凍結した項目を、凍結後に見た結果で変えない）に反します。第 22 章の「矢を射た後で的を描く」の形です。
2. **形が A2 にぴったり合っています**。`--unified=` の形と `int` の注釈という条件は、A2 の `git_diff` そのものです。ほかの木で何が変わるかを確かめていません。
3. **型の注釈は検査ではありません**。A2 のハンドラでは、`GitDiff` の `int` は `list_tools` で知らせるのに使われるだけで、ハンドラの中では確かめていません（D58 の追記）。注釈を根拠に「数えない」とすると、実際には何でも入る値を見逃します。
4. **A2 で確かめても証拠になりません**。A2 に合わせて作った規則を A2 で確かめて「通った」と言うのは循環です。
5. **開示しても、調整であることは変わりません**。逸脱として書いても、較正の数字が較正に合わせて作られたことは消えません。
6. 一般論としても、値の位置が危険なオプション（`--output=`・`--upload-pack=` など）があるので、「値の位置なら安全」とは言えません（O35）。

**(2)** D58 の追記の決定 3 に沿うと、次の手順です。

1. argv の要素をどう分けるか（先頭のオプション名と `=` の後ろの値）、値の位置を別の座標にするか数えないか、を**規則として文章で書き、実装より先にコミット**する。
2. 反例のテスト（変えてはいけない形を含む）を先に書く（第 23 章）。
3. 実装する。
4. **A2 を含まないデータ**（記録では母集団 v3）で、増える行・消える行と誤りを測る。A2 で作って A2 で確かめても証拠にならないから。
5. 凍結後の変更なので、`docs/preregistration.md` §5 に**逸脱**として、変更前と変更後の両方の値を記録する。

ただし、今は解析器が凍結されていて、最終評価のどの段階でも `authgap/` を変えないと決まっています（手順書の冒頭）。O35 は D59 で「凍結後は直さない」限界に入ったので、最終評価の前に採ることはありません。

**(3)** 入れるべき事実（31.7 節の 7 つ）:

1. 何の数か: 較正対 8 件（木の組は 7 組）の両側比較で、事前登録照合 7/8・座標一致 7/8・any-change 8/8（凍結版で測った値）。
2. 何が落ちたか: A2（CVE-2025-68144、git のフラグ混入）の `git_diff` の道筋。
3. なぜ: 厳格版 O34 で、修正後の `repo.git.diff(f"--unified={context_lines}", target)` の `context_lines` が検査されていない root として残る。
4. それまでの 8/8 は、O34 の誤 clear（`target` の検査が `context_lines` の位置にも付いていた）に一部支えられていた。
5. `--opt=` の値の位置を数えない例外は、A2 の失敗を見てから作る規則になるので足さなかった。

#### 演習 31-4（材料ごとに宛先を考える）

**(1)**

| ツール | 外部にできるか | 例 |
|---|---|---|
| `get_a` | **できない** | `host` は `127.0.0.1` か `localhost` だけ。その後ろは `:8080/` で区切られ、`path` は `/` の後ろのパスにしかならない。たとえば `path` が `@evil.example/x` でも、URL は `http://localhost:8080/@evil.example/x` で、ホストは `localhost` |
| `get_b` | **できる** | `scheme` を `http://evil.example/#` にすると、URL は `http://evil.example/#://127.0.0.1/x` になり、ホストは `evil.example`（`#` の後ろは URL の断片として扱われる）。`host` の検査は効いているが、`scheme` が検査されていない |
| `get_c` | **できる** | `path` を `@evil.example/x` にすると、URL は `http://127.0.0.1:8080@evil.example/x` になり、ホストは `evil.example`（`@` の前は利用者の情報）。`BASE` は定数でも、その直後に `/` 無しで `path` がつながる |

本書の執筆時に `urllib.parse.urlsplit` で、3 つの URL のホストがそれぞれ `localhost`・`evil.example`・`evil.example` になることを確かめました。

**(2)**

| ツール | 判定 | 理由 |
|---|---|---|
| `get_a` | **誤** | 宛先の取りうる値の全体はローカルだけなので、D3 に反しない（原理 3-a、手引きの 15.3 節「宛先が localhost / loopback → 反しない」）。誤の原因は、解析器が「宛先をモデルが決められる」と読んだのに実際は決められないので、**E7**（モデルが決められないのに決められるとした）が近い。迷ったら E9 にして説明を書く（手引きの第 17 節） |
| `get_b` | **正** | `scheme` を使ってモデルが宛先を外部にできるので、D3 に反する。`host` の検査は、`scheme` から入る宛先を止めない（O34 と同じ形） |
| `get_c` | **正** | `path` を使ってモデルが宛先を外部にできるので、D3 に反する。定数の `BASE` は、`/` で区切られていなければ宛先を固定しない |

#### 確認問題 31-1

O34 は、**付録**（ゲート）の判定の、**誤 clear** の向きの誤りでした。
値の root のどれか 1 つが検査されていれば値全体を検査済みにし、出すべき `GAP_INJECT` を出していませんでした。
厳格版がいちばん弱いものを採るのは、攻撃者（モデルを操る人）が、守りのいちばん弱い入口（検査されていない引数）を選んで使うからです。
値全体の守りは、いちばん弱い材料の守りで決まります。

#### 確認問題 31-2

- **較正対**: 公開された本物の脆弱性について、修正前と修正後のコードを並べた組（7 組 14 木、8 件）。
- **両側比較**: 解析器が、較正対の修正前と修正後を、出力の違いで見分けられるかを数える検査（`scripts/two_sided.py`）。
- **事前登録照合**: 先に `docs/expected_tuples.json` に登録した「どこが、どう変わるはず」が、その向きで、その位置に、決めた数以上起きたかの照合。両側比較の主指標。
- **B3a・B3b との違い**: 両側比較 7/8 は本物の CVE の修正前後のコード（較正対）を見分けられるかの検査で、B3a・B3b は付録のゲートの仕組みのために作った小さなプログラム（`fixtures/` の作例）で、ゲートの判定が仕様どおりかを見る検査です。

#### 確認問題 31-3

例外を足さなかったのは、それが「A2 が落ちたのを見てから、A2 の形に合わせて足す規則」になるからです。
CLAUDE.md 規則 5（凍結した項目を結果を見て変えない）に反し、逸脱として開示しても、較正に合わせた調整であることは変わりません。学生が「あまり綺麗ではない」と指摘し、取り下げました。

代わりに決めたこと:

1. 規則は厳格版のまま実装し、A2 の両側比較は 7/8 と報告する。それまでの 8/8 が O34 の誤 clear に一部支えられていたことも結果として書く。期待値ファイルは変えず、A2 を期待する 2 つのテストは `xfail(strict=True)` にする。
2. argv の要素を先頭と値に分けて見るかは、O35 に未決として置く。
3. 採るなら、規則を先にコミットし、A2 を含まないデータ（母集団 v3）で確かめ、逸脱として記録する。
