#### 演習 36-1（時間上限の記録）

**書き出す木**（`budget_skipped` が 0 でない木。全件。`elapsed_s` も書く）:

| 木 | `budget_skipped`（時間上限で解析しなかったユニット） | `elapsed_s`（秒） |
|---|---|---|
| v2-david-li0406__meta-skill-evloving | 716 | 782.2 |
| v2-mcparmory__registry | 197 | 181.2 |
| v2-xorbitsai__xagent | 351 | 185.0 |

4 行目の v4 の木（remote-mcp-adapter）は `budget_skipped` が 0 なので、書き出しません。

読み方の注意が 3 つあります。

1. 4 つの木は、どれも `status` が `ok` です。時間上限で打ち切っても `status` は `ok` のままなので、`status` だけを見ると打ち切りを見落とします。`budget_skipped` を必ず見ます（第 18 章 18.10 節）。
2. meta-skill-evloving の `n_units` は 0 です。ファイルを読んで索引を作り、ユニットを見つけ終えるまでの準備だけで上限を超えていたので、716 ユニットを 1 つも解析しませんでした（`tree_budget_prep`。第 27 章 27.6 節）。
3. `elapsed_s` が 180 を超えているのは、時計を見るのがユニットとユニットの間（と、ユニットを見つけた直後）だけだからです。

**ほかに記録するもの**:

- 走査のとき（9.2）: 走らせたマシン（CPU・メモリ・同時に走らせた本数）と、日時。木ごとの時間はマシンの速さで変わるからです（run23 の xagent 179.1 秒が、同じコンテナの run24 では 89.9 秒）。
- 走査の後（9.3）: `implementation_sha256_combined`（`35606ba9…` と一致するか）、`authgap_dirty`（`False` か）、`max_depth`（4 か）、`ok` 以外の木（全件）、`n_parse_failures`、`n_truncations`。

そして、**取り直しません**。
打ち切りが多いと分かっても、上限を上げたりマシンを変えたりして取り直すと、「結果が気に入らないから取り直した」のと同じになります。
マシンを選ぶのは走らせる前だけです（手順書 26 節）。

最後に、時間上限で解析しなかったユニットは manifest の `units` に入らないので、見落としの抜き取りの元の一覧にも出てこないことを覚えておきます（第 27 章 27.5 節）。

#### 演習 36-3（URL の宛先と D3）

| | 判定 | 理由 |
|---|---|---|
| (a) `https://api.example.com/x?next=http://localhost/&q=` + p | **矛**（`net_external_host`） | scheme `https` は正しい。宛先は権威部の api.example.com（外部）。クエリの中の `http://localhost/` は宛先ではない |
| (b) `git+https://evil.example/repo?q=` + p | **矛**（`net_external_host`） | `git+https` は RFC 3986 の scheme の文法（英字で始まり、英字・数字・`+`・`-`・`.` が続く）に合う。宛先は evil.example（外部） |
| (c) `http://user:pass@localhost:8080/x?q=` + p | **内** | `user:pass@` は利用者の名前とパスワード（userinfo）。宛先は localhost（手元）。U36 の直しの前は外部と読み、矛（誤警報）にしていた |
| (d) `http://localhost:pw@evil.example/x?q=` + p | **矛**（`net_external_host`） | `localhost:pw@` は userinfo。宛先は evil.example（外部）。U36 の直しの前は localhost と読み、内（誤 clear）にしていた |
| (e) `client.get("oauth/authorize?redirect_uri=http://localhost:8080/cb")` | **不**（`net_host_unknown`） | `://` の前の `oauth/authorize?redirect_uri=http` は scheme の文法に合わないので、区切りと読まない（§9.6 の改訂 7''）。`/` で始まらない相対の URL の宛先は読まないので、決められない。N9 の直しの前は宛先を localhost と読み、内（誤 clear）にしていた |

(e) で、文字列にモデルの値をつなげた形（`... + p`）にすると、宛先の位置にモデルの値が入るので、判定は**矛**（`net_model_host`）になります（36.11 節の小さな例 4 の `fix_query_redirect`）。
どちらにしても、N9 の直しの後は**内にはなりません**。

（出典: `docs/contradiction_principles.md:382-385`（§9.6 の 7）、`:422-426`（改訂 7''）、`tests/test_d64_u36_url_authority.py:111,129`、`tests/test_d64_n9_url_scheme.py:33-101`、凍結版の解析器を scratchpad の小さな木に走らせた結果（本書の執筆時））

#### 確認問題 36-1

**判定が変わったからではありません。**
段階 B の追加で解析が遅くなり（87 木の合計で 729 秒 → 1,894 秒。ただし 2 つの数は別のマシンで取った値）、木ごとの時間上限（180 秒）で xagent（352 → 1 ユニット）と mcparmory（646 → 449 ユニット）が打ち切られたためです。
打ち切りで落ちたのは 548 ユニット（xagent 351・mcparmory 197）で、U40 で新しく入口になった 58 ユニットと差し引きして、純減が 490 です（2,231 − 548 + 58 = 1,741）。

誤りの向きは、**誤 clear の向きの数え落とし**です。
打ち切られたユニットは解析されないので、その中に矛があっても見えません。

判定の変化ではないと言える根拠は、消えたユニットが 2 木に集中し、その 2 木の `elapsed_s` が上限をわずかに超え、`budget_skipped` の数と合っていたことです。
run22 では、消えた 131 ユニットが manifest の `tree_budget` の件数と一致し、消えた矛は 0 でした。

#### 確認問題 36-2

止めたのは、止める条件（同じ担当で 2 回続けて新しい所見が 0）を満たしたからではなく、**上限に達したから**です。
新しい所見は第 3 回 25 件、第 4 回 27 件と減っておらず、0 に近づいていませんでした。
だから、この添削で見つからなかった誤りが、まだ残っていると考えるべきです。

さらに、

- 直した段階 B のコードにも、敵対的レビューを 3 巡で打ち切ったので、見つかっていない誤りがありえる（U23 の 3 巡目の直しは別のレビューを通していない）。
- 所見の件数は探索の標本で、母集団での頻度の推定ではない。
- 直したのは、学生が選んだ単位だけで、39 単位は直していない（O42）。

「直すべきものは直した」と書くと、「点検で誤りを見つけ尽くした」という、記録が支えない主張になります。
記録は「『添削で直すものは直した』とは書かない」と明記しています。
論文では、「凍結の前に、決めた手続きで点検し、見つかった誤りのうち選んだものを直した。見つけ尽くしてはおらず、残りは既知の限界として記録した」のように、手続きと限界を一緒に書きます。

（出典: `docs/review_plan.md:149-153`、`docs/decisions.md:3626-3628`、`docs/open_questions.md:1081-1090`）

#### 確認問題 36-3

**新しいタグを選んでよかった条件**は、逸脱 #26 の記録にある次の 2 つです。

1. **学生の最終評価のデータを誰も見ていない時点**だった。データを見た後なら、同じ直しでも「結果を見て解析器を直した」ことになり、凍結の意味が失われる。
2. N9 は**誤 clear の直し**で、しかも「解決率を下げる側だけの変更」だった。危険を見落とす向きの誤りを直すもので、新しい誤 clear を作りにくい。直した後も、全 test・ゲート・較正対の効果の行が同じで、run24 は run23 と全項目で同じだった。

このうえで、変更を逸脱として記録し、`analyzer-freeze-2` も履歴として残しました。

**付け替えを選ばなかった理由**: タグを付け替えると、名前は 1 つで済みますが、「`analyzer-freeze-2` がどのコミット（f3c02e8、run23 の版）を指していたか」という過去の記録が書き換わり、後から誰も確かめられなくなります。この研究は、記録を上書きしないことを優先します（`fingerprint.json` の `freeze.tag` を書き換えなかったのも同じ考え）。

**戻すを選ばなかった理由**: 戻すと、凍結の約束どおりの版にはなりますが、誤 clear の直し（N9）を捨てることになります。最終評価のデータに N9 の形があれば、危険を見落とすことになります。

（出典: `docs/preregistration.md:577`（逸脱 #26）、`docs/decisions.md:3695-3708`）

#### 確認問題 36-4

どちらも、**結果を見てから基準を決める（後出しの）こと**を防ぐためです。

- 添削の計画を所見を見る前にコミットしたので、所見を見た後で「この種類は範囲の外だった」「ここで止める」と、都合よく範囲や止める条件を変えられません。コミットの時刻（2026-09-26 01:32）が所見の最初の記録（09-27 04:26）より前であることが、その証拠になります。
- 反例テストを実装より先にコミットしたので、実装が出した答えに合わせて「正しい答え」を決められません。テストが実装の前に落ちる（§9.6 の改訂で 30 件、N9 で 2 件）ことも、先に書いた証拠になります。

共通する考え方を 1 文で書くと、「**ものごとを測る基準（範囲・止める条件・正しい答え）は、それで測る結果を見る前に決めて、コミットで固定する**」です。
これは事前登録（第 22 章）と同じ考え方で、仕様書の「期待値ファイルは採点器より先にコミットする」とも同じです。
後で基準を改めるときは、理由と向きを記録に残します（36.9 節）。
