## 第 51 章 結果に付ける印 — 書き込み先・通信先のラベルと誤の原因 E1〜E9

> **この章で分かること**:
> - 判定の結果には、正・誤・不明のほかに **2 種類の印**を付けること。正（と見落とし、不の中身の違反）には「**書き込み先の種類**」（D3 は「**通信先の種類**」）を `write_target` 欄に、誤には「**誤の原因**」E1〜E9 を `error_class` 欄に書く。
> - 書き込み先の種類の **8 つの定義**（相手側の状態 / データベース / 利用者のファイル / ログ / 一時ファイル / キャッシュ・状態の保存 / プロセスの起動・コードの実行 / その他・不明）。ラベルは**重みではない**（第 43 章）。
> - 8 つは**上から順に当てはめ、最初に当てはまったものを付ける**こと。たとえば SQLite のキャッシュ DB への書き込みは、2 番の「データベース」が 6 番の「キャッシュ・状態の保存」より先に当たる。
> - 境界の例 6 つと、**名前ではなく動作で決める**こと（練習用サーバの組 1 は、名前はキャッシュだが読み返しが無いので「その他・不明」）。決められないときは「その他・不明」にして `note` に書き、**判定の途中で定義を足さない**こと。
> - D3 の正に付ける通信先の種類 4 つ（定数の外部ホスト / モデルが決める宛先 / モデルが決めるコード・コマンド / その他・不明）。
> - 誤の原因 **E1〜E9** の 9 つの類。1 つずつ、実物のコード（ファイルと行つき）か作例（作例と明記）で見る。とくに **E4 と「site の名前だけが違う」場合の区別**。
> - この分類が集計で「誤の原因の内訳」「書き込み先の内訳」の表になり、論文の限界の節の材料になること。
> - 手引きの下書きにまだ書かれていない境界（本書の指摘。どう扱うかは**未決**で、学生が封の前に決めること）。

### 51.1 判定の結果に付ける 2 種類の印

#### 一言で言うと

判定を決めたら、**正には「何に書き込んだ違反か」、誤には「なぜ解析器が間違えたか」**を、決まった言葉で 1 つ付けます。
前者が書き込み先の種類（D3 は通信先の種類）、後者が誤の原因 E1〜E9 です。

#### たとえ話 — 病院のカルテ

病院の医師は、検査の結果を見て「病気がある・ない」を決めます。
けれども、カルテに書くのはそれだけではありません。
病気があったなら「どこの病気か」（胃・肺・皮膚など）を書きます。
検査で陽性と出たのに病気が無かったなら、「なぜ陽性と出たか」（食事の影響、薬の影響、機械の誤差など）を書きます。

この 2 つの記録は、目の前の患者の診断を変えません。
けれども、病院全体で集めると、「どの部位の病気が多いか」「検査はどんな理由で外れやすいか」が分かります。

判定も同じです。
- 「病気がある」が**正**、「どこの病気か」が**書き込み先の種類**です。
- 「陽性と出たのに病気が無かった」が**誤**（解析器の誤警報）、「なぜ陽性と出たか」が**誤の原因 E1〜E9** です。

#### 小さな例 — 判定表の 3 行（作例）

次は、判定表の 3 行を、この章に関わる欄だけ抜き出したものです（本書の作例。実在の木ではありません）。

| tree | unit | site / kind | decl | verdict | write_target | error_class | unknown_reason |
|---|---|---|---|---|---|---|---|
| final-a__notes | `export_note` | `builtins.open` / FS_WRITE | D2 | 正 | 利用者のファイル | | |
| final-b__search | `find_items` | `os.makedirs` / FS_WRITE | D1 | 誤 | | E1: lifespan の `init_store`（server.py:40-52）が起動時に作る | |
| final-c__sync | `pull` | `requests.post` / NET | D1 | 不明 | | | 相手の API の文書が無く、POST が更新か照会か決められない |

#### 一歩ずつの説明

- **1 行目**: `export_note` は D2（破壊しない）と宣言していますが、モデルが決めたパスに `'w'` で書き出していました。正です。書いた先はモデル（利用者の代わり）が指定した場所のファイルなので、`write_target` に「利用者のファイル」と書きます。`error_class` は空です。
- **2 行目**: `find_items` の `os.makedirs` は、lifespan（起動時の準備）の中で済んでいて、ツールの呼び出しでは届きませんでした。誤です。`error_class` に記号 E1 と、どこで済んでいるかの 1 文を書きます。`write_target` は空です。
- **3 行目**: 不明です。この章の 2 つの欄はどちらも空で、代わりに `unknown_reason` に決められない理由を書きます（不明の書き方は第 52 章）。

つまり、**判定ごとに埋める欄が違います**。
次の表にまとめます。

| 判定の結果 | 付ける印 | 書く欄 | 決め方 |
|---|---|---|---|
| D1・D2・D4 の**正** | 書き込み先の種類（8 つから 1 つ） | `write_target` | 51.2〜51.5 節 |
| D3 の**正** | 通信先の種類（4 つから 1 つ） | `write_target` | 51.6 節 |
| 見落としの判定で、宣言に反する動作が見つかったもの（D1・D2） | 書き込み先の種類 | `write_target` | 同じ定義（第 52 章） |
| 不の中身の判定で「違反」にしたもの（D1・D2） | 書き込み先の種類 | `write_target` | 同じ定義（第 52 章） |
| **誤** | 誤の原因 E1〜E9 と 1 文の説明 | `error_class` | 51.7〜51.16 節 |
| **不明** | 決められない理由 | `unknown_reason` | 第 52 章 |

表の読み方: 1 行が 1 つの判定の結果です。
たとえば 3 行目は「見落としの判定（解析器が何も出さなかったツールを人が読む判定）で、D1 か D2 に反する動作を見つけたら、その動作にも、正と同じ 8 つの書き込み先の種類から 1 つを付ける」と読みます。

（出典: `docs/drafts/final_judging_guide_draft.md:173-174`（`error_class`・`write_target` の欄）、`:379-380`（16 節の前書き）、`:468`（18.2 の 7: 見落としにも付ける）、`:487`（18.4 の `write_target`）、`:519`（18A.2 の 5: 不の中身の違反にも付ける）、`docs/drafts/prereg_2_12_draft.md:83-86`（ラベルを付ける対象））

#### なぜそうするのか

**書き込み先の種類**は、学生の決定 D67 の 1 から来ています。
D67 の 1 は「重大度の重みは付けない。主指標の精度は字義どおりの原理の 1 本だけにする。そのうえで、正の各件に書き込み先の種類を事実のラベルとして記録し、内訳を表で示す。軽重の判断は読み手に任せる」と決めました。
内訳を出すのは、「見つけた違反は些細なものばかりでは」という問いに、事実で答えるためです（第 43 章 43.10 節）。
そのあと D68 の 3 で、「プロセスの起動・コードの実行」が足されて 8 つになり、D3 には通信先の種類を付けると決まりました。

**誤の原因 E1〜E9** は、学生の決定 D67 の 2 から来ています。
D67 の 2 は、起動時の初期化の類（lifespan の形）について、「解析器は変えず、設計の選択による限界（誤警報の向き）として件数を報告する。判定の手引きの誤の原因の欄に、この類を設ける」と決めました。
件数を報告するには、誤の原因を決まった類で記録しなければなりません。
手引きの下書きは、この類（E1）に加えて、v3・v4 で出たほかの誤の類も、最初から分類として用意しました。

（出典: `docs/decisions.md:3767-3772`（D67 の 1）、`:3773-3778`（D67 の 2）、`:3809-3814`（D68 の 3）、`docs/drafts/final_judging_guide_draft.md:424`（17 節の前書き: v3・v4 で出た類を最初から用意した））

#### よくある誤解・つまずき

- **誤解: 「ラベルを付けるのは正だけ」**
  見落としの判定で見つけた違反と、不の中身の判定で「違反」にしたものにも付けます。どれも「本当にあった違反」なので、同じ物差しで内訳を出すためです。
- **誤解: 「誤にも書き込み先の種類を付ける」**
  付けません。誤は「違反ではなかった」ので、違反の中身を表すラベルは要りません。代わりに誤の原因を付けます。
- **つまずき: 不明に E9 を付ける**
  E9 は「誤の原因のその他」です。不明は誤ではないので、E の記号は付けません。`unknown_reason` に理由を書きます。
- **つまずき: 印で判定を変える**
  「ログへの書き込みだから軽い。誤にしておこう」は、してはいけません。印は判定を決めた**後**に付けるもので、判定を決める材料ではありません（第 43 章）。

#### 手作業ではどう使うか

判定表の 1 行を埋めるときは、次の順に進みます。

1. 手順 E・F で、到達するか・宣言に反するかを決め、`verdict` を書く。
2. `verdict` が正なら、`write_target` を書く（D3 なら通信先の種類、ほかは書き込み先の種類）。
3. `verdict` が誤なら、`error_class` を書く。
4. `verdict` が不明なら、`unknown_reason` を書く。
5. 迷った点は、どの場合も `note` に書く。

#### この節のまとめ

判定の後に、正（と見落とし・不の中身の違反）には書き込み先の種類（D3 は通信先の種類）を `write_target` に、誤には E1〜E9 を `error_class` に付ける。
前者は D67 の 1・D68 の 3、後者は D67 の 2 から来ている。印は判定を決める材料ではない。

### 51.2 書き込み先の種類 — 8 つの定義（手引き 16.1 節）

#### 一言で言うと

書き込み先の種類は、違反が「**どこを変えたか**」を表す 8 つの名前です。
相手側の状態 / データベース / 利用者のファイル / ログ / 一時ファイル / キャッシュ・状態の保存 / プロセスの起動・コードの実行 / その他・不明、の 8 つから、1 件に 1 つだけ付けます。

#### たとえ話 — 事務所で「どこに書き込んだか」

事務所で働く人が「この書類には手を触れません」と約束したのに、何かに書き込んでいたとします。
書き込んだ場所は、いろいろありえます。

- 取引先の帳簿に書き込んだ（相手の会社の記録が変わる）。
- 会社の台帳に書き込んだ。
- お客さんから預かった書類に書き込んだ。
- 自分の業務日誌に「何時に何をした」と書いた。
- 付箋にメモして、用が済んだらすぐ捨てた。
- 次に使うために、自分用の控えを作っておいた。
- 機械のスイッチを入れて、機械に仕事をさせた。
- どれとも言えない、よく分からない場所に書いた。

どれも「手を触れない」という約束には反しています。
けれども、聞いた人が受ける印象は、ずいぶん違います。
書き込み先の種類は、この「どこに」を、聞いた人が自分で判断できるように、事実として記録するための名前です。

#### 小さな例 — 8 つの種類の表

| 順 | 種類 | 定義 | 例 |
|---|---|---|---|
| 1 | **相手側の状態** | NET の効果で、通信相手のサーバの状態を変える | Jira の課題の更新、Slack への投稿 |
| 2 | **データベース** | DB の行・スキーマ・DB に残る設定を変える | `UPDATE sessions SET revoked_at …`、`PRAGMA journal_mode=WAL` |
| 3 | **利用者のファイル** | 利用者（またはモデル）が指定した場所のファイル、または利用者の文書・データとして扱われるファイル | モデルが決めた `output_file` へのレポートの書き出し、編集対象のファイルの上書き |
| 4 | **ログ** | 記録のためだけに書き、ツールの動作では読み返さない | ログファイル・監査ログ・トレースへの追記 |
| 5 | **一時ファイル** | 同じ呼び出しの中で作って消す、または OS の一時領域（`tempfile`、`/tmp`）に作る | `mkstemp` した受け渡し用のファイルとその削除 |
| 6 | **キャッシュ・状態の保存** | ツールの動作のために自分で保存し、後で読み返す | キャッシュ、トークン・セッションの保存、索引、初回に作る作業ディレクトリ・設定ファイル |
| 7 | **プロセスの起動・コードの実行**（D68 の 3 で足した） | SPAWN / EXEC の正 | モデルが決めたコマンドの起動、`eval` / `exec` |
| 8 | **その他・不明** | 上のどれにも当てはまらない、または決められない | |

表の読み方: 1 行が 1 つの種類です。左の「順」は、当てはめる順番です（51.3 節）。
たとえば 4 行目は「ログとは、記録のためだけに書き、ツールの動作では読み返さないもの。ログファイル・監査ログ・トレースへの追記がこれにあたる」と読みます。

（出典: `docs/drafts/final_judging_guide_draft.md:382-395`（16.1 節）、`docs/decisions.md:3809-3814`（D68 の 3））

#### 一歩ずつの説明 — 8 つを 1 つずつ

ここからは、8 つの種類を 1 つずつ、言葉の 3 点セット（やさしい言い換え・正確な定義・例）で見ます。
例のコードは、どれも本書の作例です。

**1. 相手側の状態**

- やさしい言い換え: 通信の相手（ほかの会社のサーバなど）の中身を変えること。
- 正確な定義: NET の効果（HTTP などの通信）で、通信相手のサーバの状態を変える。
- 例（作例）:

```python
requests.put(f"https://jira.example.com/rest/api/2/issue/{key}", json={"fields": fields})
```

1 行の意味: Jira（課題管理のサービス）の、`key` という課題を、`fields` の中身で書き換える要求を送ります。
`PUT` は、相手の資源を置き換える HTTP のメソッドです（第 10 章）。
自分のパソコンのファイルは何も変わりませんが、Jira の課題が変わります。
原理 1-ii-b（相手側の状態も環境）を採ったので、これも「環境を変える」違反です（第 17 章）。

**2. データベース**

- やさしい言い換え: データベースの中身や作りを変えること。
- 正確な定義: DB の行・スキーマ（表の作り）・DB に残る設定を変える。
- 例（作例）:

```python
conn.execute("UPDATE sessions SET revoked_at = NOW() WHERE id = %s", (sid,))
```

1 行の意味: `sessions` という表の、`id` が `sid` の行の `revoked_at`（取り消した時刻）を、今の時刻に書き換えます。
これは v4 の task-manager-cloud の `logout`（M00）と同じ形です。
`PRAGMA journal_mode=WAL` のように、DB のファイルに残る設定の変更もここに入ります（原理 1-i-b）。

**3. 利用者のファイル**

- やさしい言い換え: 使う人（またはその代わりのモデル）が「ここに」と指定したファイルや、使う人の文書・データとして扱われるファイル。
- 正確な定義: 利用者（またはモデル）が指定した場所のファイル、または利用者の文書・データとして扱われるファイル。
- 例（作例）:

```python
def export_report(output_file: str, rows: list) -> str:
    with open(output_file, "w") as fh:
        fh.write(render(rows))
```

1 行目: ツールの引数に `output_file`（書き出す先のパス）があります。モデルがこの値を決めます。
2 行目: そのパスを `'w'`（中身を消して書く）で開きます。
3 行目: レポートを書きます。
書き先をモデルが指定しているので、利用者のファイルです。
v4 の mcp-aws の `generate_cost_report_wrapper`（M18）がこの形でした。
もう 1 つの入り方は「利用者の文書・データとして扱われるファイル」です。たとえば、ノートを管理するツールが、利用者のノートのファイルを上書きするなら、場所をモデルが指定していなくても、ここに入ります。

**4. ログ**

- やさしい言い換え: 「いつ・何をした」を残すためだけの記録。ツール自身は、後で読み返さない。
- 正確な定義: 記録のためだけに書き、ツールの動作では読み返さない。
- 例（作例）:

```python
with open(LOG_PATH, "a") as fh:
    fh.write(f"{datetime.now().isoformat()} search {query}\n")
```

1 行目: ログのファイルを `'a'`（後ろに足す）で開きます。
2 行目: 時刻と、何をしたか（search と検索語）を 1 行足します。
ツールのほかの処理は、このファイルを読みません。
v4 の wikimind の `wiki_ask`（M06）が、活動ログ `log.md` に追記する形でした。
定義には 2 つの条件があります。「記録のためだけに書く」と「ツールの動作では読み返さない」です。両方を満たすときだけログです。

**5. 一時ファイル**

- やさしい言い換え: その場で使って、すぐ捨てるファイル。または、OS が「一時置き場」として用意した場所に置くファイル。
- 正確な定義: 同じ呼び出しの中で作って消す、または OS の一時領域（`tempfile`、`/tmp`）に作る。
- 例（作例）:

```python
fd, path = tempfile.mkstemp(suffix=".json")
try:
    run_converter(path)
finally:
    os.remove(path)
```

1 行目: `tempfile.mkstemp` で、OS の一時領域に、名前がほかと重ならない新しいファイルを作ります（第 9 章）。
2〜3 行目: そのファイルを使って、変換の処理をします。
4〜5 行目: 処理が成功しても失敗しても（`finally`）、そのファイルを消します。
同じ呼び出しの中で作って消すので、一時ファイルです。
v4 の ru-marketplace の `ozon_reviews`（M58）がこの形でした（51.9 節）。
定義の「または」に注意します。同じ呼び出しで消さなくても、`/tmp` などの OS の一時領域に作るなら、一時ファイルに入ります。

**6. キャッシュ・状態の保存**

- やさしい言い換え: ツールが自分の仕事のために取っておき、後でまた読むもの。
- 正確な定義: ツールの動作のために自分で保存し、後で読み返す。
- 例（作例）:

```python
TOKEN_FILE = Path.home() / ".myapp" / "token.json"

def get_token():
    if TOKEN_FILE.exists():
        return json.loads(TOKEN_FILE.read_text())
    token = login()
    TOKEN_FILE.parent.mkdir(parents=True, exist_ok=True)
    TOKEN_FILE.write_text(json.dumps(token))
    return token
```

1 行目: トークン（ログインの証明）を置く場所を、ホームディレクトリの `.myapp/token.json` に決めます。
3〜5 行目: すでにファイルがあれば、それを読んで返します。ここが「後で読み返す」部分です。
6 行目: 無ければ、ログインしてトークンをもらいます。
7 行目: 置き場のディレクトリが無ければ作ります（初回に作る作業ディレクトリ）。
8 行目: トークンをファイルに保存します。
保存したものを 3〜5 行で読み返しているので、キャッシュ・状態の保存です。
キャッシュ、トークン・セッションの保存、索引（検索を速くするための表）、初回に作る作業ディレクトリや設定ファイルが、ここに入ります。

**7. プロセスの起動・コードの実行**

- やさしい言い換え: 別のプログラムを動かしたり、文字列をプログラムとして実行したりすること。
- 正確な定義: SPAWN（プロセスの起動）/ EXEC（コードの実行）の正。
- 例（作例）:

```python
@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def run_check(command: str) -> str:
    return subprocess.run(command, shell=True, capture_output=True, text=True).stdout
```

1 行目: 読み取り専用と宣言しています。
2 行目: ツールの引数は `command`（実行するコマンドの文字列）で、モデルが決めます。
3 行目: その文字列を、シェル（コマンドを解釈するプログラム）にそのまま渡して実行します。
モデルは、ファイルを消すコマンドでも何でも実行させられるので、D1 に反します（原理 3-a）。
これは書き込みそのものではありませんが、D68 の 3 で、この種類が足されました（51.3 節で理由を見ます）。

**8. その他・不明**

- やさしい言い換え: 1〜7 のどれにも当てはまらないもの、または、どれか決められないもの。
- 正確な定義: 上のどれにも当てはまらない、または決められない。
- 例: 51.4 節の練習用サーバの組 1（名前はキャッシュだが、読み返しが無い書き込み）。

#### なぜこの 8 つなのか

D67 の 1 で決まったのは、7 番を除いた 7 つ（利用者のファイル / データベース / 相手側の状態 / キャッシュ・状態の保存 / ログ / 一時ファイル / その他・不明）です。
決定の文には、「なぜこの 7 つか」の説明は書かれていません。
第 43 章 43.1 節で見た裏方の書き込みの種類（初回の初期化・キャッシュ・ログ・一時ファイル・IPC のファイル・トークンの保存）と重なる部分が多い、ということが言えるだけです。
決定に書かれている理由は、「重みは付けない」ことの理由と、「内訳を出すのは『些細では』という問いに事実で答えるため」です。
なお、手引きの下書きの表の並び（相手側の状態が 1 番）は、D67 の 1 の文の並び（利用者のファイルが先頭）とは違います。当てはめる順番は、手引きの表の並びです。

7 番（プロセスの起動・コードの実行）は、D68 の 3 で、最終評価のデータを見る前に足されました。
理由は「『その他・不明』に入れると、任意のコマンドを実行できる違反が、分類できなかったものと同じ箱に入って見えなくなる」です。
ラベルの一覧を足したのは最終評価のデータを見る前なので、結果に合わせた変更ではありません。

（出典: `docs/decisions.md:3767-3772`（D67 の 1）、`:3809-3814`（D68 の 3 とその理由））

#### よくある誤解・つまずき

- **誤解: 「8 つは重さの順に並んでいる」**
  並びは**当てはめる順番**です（51.3 節）。重さとは関係ありません。手引きも「重みではない（どれも違反であることは同じ）」と書いています。
- **誤解: 「ログは、ファイル名が `.log` のもの」**
  ログの定義は「記録のためだけに書き、ツールの動作では読み返さない」です。名前ではなく、何を書き、読み返すかで決めます（51.4 節）。
- **誤解: 「キャッシュは、変数名や関数名に cache とあるもの」**
  キャッシュ・状態の保存の定義は「後で読み返す」ことを含みます。読み返していなければ、名前が cache でもここには入りません（51.4 節の組 1）。
- **つまずき: 一時ファイルの「または」を見落とす**
  定義は「同じ呼び出しの中で作って消す」**または**「OS の一時領域に作る」です。`/tmp` に作って消さないものも一時ファイルです。

#### 手作業ではどう使うか

8 つの定義の表を、判定のあいだ手元に置きます（付録 E の早見表にも載せます）。
正にしたら、その位置の書き込みについて、次のことを確かめます。

1. どの kind か（NET・DB・FS_WRITE・SPAWN・EXEC）。
2. 書き先はどこか（相手のサーバ、DB、利用者が指定した場所、OS の一時領域、ツール自身の置き場）。
3. 書いたものを、ツールのどこかで読み返すか（grep で確かめる）。
4. 同じ呼び出しの中で消すか。

この 4 つが分かれば、次の節の「上から順に当てはめる」規則で、1 つに決まります。

#### この節のまとめ

書き込み先の種類は 8 つで、違反が「どこを変えたか」を事実として表す。
定義の中の条件（読み返すか、同じ呼び出しで消すか、誰が場所を指定したか）が、種類を分ける。7 番は D68 の 3 で足された。

### 51.3 上から順に当てはめる — 順番の意味

#### 一言で言うと

1 つの書き込みが、2 つ以上の定義に当てはまることがあります。
そのときは、**表の上（順 1）から順に見ていき、最初に当てはまったものを付けます**。

#### たとえ話 — ごみの分別表

ある町のごみの分別表が、次のように「上から順に見て、最初に当てはまる箱に入れる」決まりになっているとします。

1. 電池
2. びん・缶
3. プラスチック
4. 燃えるごみ

電池の入ったプラスチックのおもちゃは、どの箱でしょうか。
「電池」にも「プラスチック」にも当てはまります。
上から順に見ると、最初に当てはまるのは「電池」なので、電池の箱に入れます。
こう決めておけば、誰が分けても同じ箱に入ります。
「どちらに入れようか」と迷う人も、人によって答えが違うことも、なくなります。

#### 小さな例 — 2 つの定義に当てはまる書き込み

次の表は、2 つの定義に当てはまる書き込みに、上から順の規則を当てた例です。
1 行目は手引きの下書きの境界の例にあるもので、2〜6 行目は本書の当てはめです（作例）。

| 書き込み | 当てはまる定義 | 先に当たる順 | 付ける種類 |
|---|---|---|---|
| SQLite のキャッシュ DB に検索結果を書く | 2 データベース / 6 キャッシュ・状態の保存 | 2 | **データベース** |
| 監査の記録を、DB の `audit` 表に `INSERT` する | 2 データベース / 4 ログ | 2 | **データベース** |
| 外部のログ収集サービスに、記録を `PUT` で送る | 1 相手側の状態 / 4 ログ | 1 | **相手側の状態** |
| モデルが指定したパスに、ログを追記する | 3 利用者のファイル / 4 ログ | 3 | **利用者のファイル** |
| `/tmp/myapp_cache/` に検索結果を保存し、次の呼び出しで読み返す | 5 一時ファイル / 6 キャッシュ・状態の保存 | 5 | **一時ファイル** |
| `/tmp` に作ったファイルを、同じ呼び出しで消す | 5 一時ファイル（2 つの条件の両方） | 5 | **一時ファイル** |

表の読み方: 1 行が 1 つの書き込みです。
たとえば 1 行目は「SQLite（ファイル 1 つで動く小さなデータベース）に、キャッシュとして検索結果を書く。これは『DB の行を変える』ので 2 番のデータベースにも、『後で読み返すために保存する』ので 6 番のキャッシュ・状態の保存にも当てはまる。上から順に見ると 2 番が先なので、データベースを付ける」と読みます。

（出典: `docs/drafts/final_judging_guide_draft.md:384`（上から順に当てはめ、最初に当てはまったものを付ける）、`:406`（SQLite のキャッシュ DB はデータベース。順 2 が順 6 より先））

#### 一歩ずつの説明

- **1 行目（手引きの例）**: SQLite のキャッシュ DB です。キャッシュという目的から見れば 6 番ですが、書いている先は DB の行です。上から見ると、2 番の「DB の行・スキーマ・DB に残る設定を変える」に先に当たります。手引きの下書きの 16.2 節は、この例をはっきり「データベース。順 2 が順 6 より先」と書いています。
- **2 行目**: 監査の記録（誰がいつ何をしたか）を DB の表に足します。目的はログですが、書く先は DB の行なので、2 番が先に当たります。
- **3 行目**: 外部のサービスにログを送ります。目的はログですが、通信の相手の状態（相手のサービスに記録が増える）を変えるので、1 番が先に当たります。
- **4 行目**: モデルが「ここにログを書け」とパスを指定できるなら、3 番の「利用者（またはモデル）が指定した場所のファイル」に先に当たります。モデルが既存の大事なファイルを指せば、そこに追記されてしまいます。
- **5 行目**: `/tmp` の下にキャッシュを置き、次の呼び出しで読み返します。6 番の「後で読み返す」に当てはまりますが、5 番の「OS の一時領域に作る」が先に当たるので、一時ファイルです。**この行は、手引きの下書きの境界の例に無い形**で、定義と順番をそのまま当てるとこうなる、という本書の当てはめです（51.5 節でもう一度取り上げます）。
- **6 行目**: 5 番の 2 つの条件（同じ呼び出しで消す・OS の一時領域）の両方に当てはまります。どちらにしても 5 番です。

#### なぜ順番を決めておくのか

手引きの下書きは、順番を決めた**理由**を書いていません。
書いてあるのは、「上から順に当てはめ、最初に当てはまったものを付ける」という規則と、SQLite のキャッシュ DB の例だけです。
そこで、ここからは**本書の読み方**として、順番が要る理由を 3 つ挙げます。

1. **1 件に 1 つだけ付けるため**: 手引きは「正の各件に 1 つだけ付ける」と決めています。2 つの定義に当てはまるとき、どちらにするかの規則が無いと、1 つに決まりません。
2. **判定者の気分で選ばないため**: 規則が無いと、「これはキャッシュっぽい」「いや DB だ」と、その日の印象で選んでしまいます。同じ形の書き込みに、日によって違うラベルが付くと、内訳の表がぶれます。判定者が 1 人で、2 人目と照らし合わせられないこの研究では（D67 の 4）、1 人の中のぶれを減らす工夫が特に大事です。
3. **ラベルの意味をはっきりさせるため**: 上から順の規則では、「データベース」のラベルは「DB に書いたもの全部」を意味します。キャッシュ目的かどうかで分かれません。こうしておくと、読み手は「データベース」の行を、「DB が変わった違反の数」として、そのまま読めます。

7 番（プロセスの起動・コードの実行）が 8 番（その他・不明）の前に置かれた理由は、D68 の 3 にはっきり書かれています。
任意のコマンドを実行できる違反が、「その他・不明」の箱に入って見えなくなるのを防ぐためです。

（出典: `docs/drafts/final_judging_guide_draft.md:379`（1 つだけ付ける）、`docs/decisions.md:3783-3786`（D67 の 4: 判定者は 1 人）、`:3812-3813`（D68 の 3 の理由））

#### よくある誤解・つまずき

- **誤解: 「目的で選ぶ。キャッシュのための DB なら、キャッシュ」**
  上から順の規則では、先に当たるのは「DB の行を変える」です。目的ではなく、書き先で決まります。
- **誤解: 「上のものほど重い違反だ」**
  順番は当てはめる順です。たとえば 3 行目の「外部のログ収集サービスへの送信」は 1 番の相手側の状態になりますが、それが Jira の課題の更新と同じ重さだという意味ではありません。重みは付けない、というのが D67 の 1 の決定です。
- **つまずき: 下から見てしまう**
  「ログだから 4 番」と、思いついたものから付けると、上の 1〜3 番に先に当たるものを見落とします。必ず 1 番から順に「当てはまるか」を確かめます。
- **つまずき: 2 つ当てはまったので、両方を書く**
  `write_target` には 1 つだけ書きます。もう 1 つの見方は、必要なら `note` に書きます。

#### 手作業ではどう使うか

ラベルを決めるときは、表を上から指でたどり、1 行ずつ「当てはまるか」を自分に問います。

1. NET の効果で、相手のサーバの状態を変えるか → はいなら「相手側の状態」で終わり。
2. DB の行・スキーマ・残る設定を変えるか → はいなら「データベース」で終わり。
3. 利用者（モデル）が指定した場所か、利用者の文書・データか → はいなら「利用者のファイル」で終わり。
4. 記録のためだけに書き、読み返さないか → はいなら「ログ」で終わり。
5. 同じ呼び出しで作って消すか、OS の一時領域か → はいなら「一時ファイル」で終わり。
6. 自分で保存して、後で読み返すか → はいなら「キャッシュ・状態の保存」で終わり。
7. SPAWN / EXEC の正か → はいなら「プロセスの起動・コードの実行」で終わり。
8. どれでもない、または決められない → 「その他・不明」。`note` に事例を書く。

#### この節のまとめ

2 つの定義に当てはまるときは、上（順 1）から見て最初に当たったものを 1 つだけ付ける。SQLite のキャッシュ DB はデータベース。
手引きは順番の理由を書いていないが、1 件 1 つ・ぶれを減らす・ラベルの意味をはっきりさせる、の 3 つの役に立つ（本書の読み方）。

### 51.4 境界の例と、名前でなく動作で決めること（手引き 16.2 節）

#### 一言で言うと

迷いやすい形は、手引きの下書きが**先に答えを決めて**あります（境界の例 6 つ）。
そして、どの場合も、**変数や関数の名前ではなく、コードの動作**（読み返すか、同じ呼び出しで消すか、など）で種類を決めます。

#### たとえ話 — 「保存用」と書かれた箱

台所に「保存用」と書かれた箱があるとします。
けれども、毎日中身を入れるだけで、誰も一度も取り出したことがありません。
これは本当に「保存用」でしょうか。
箱に書かれた名前ではなく、箱が実際にどう使われているかを見ないと、何の箱かは分かりません。
書き込み先の種類も同じで、`cache` という名前は手がかりにすぎず、決め手は「書いたものを後で読み返すか」という動作です。

#### 小さな例 1 — 手引きの下書きの境界の例

- **2 行目（トークンの保存）**: トークンは、次の呼び出しで読み返して使います。だから 6 番です。51.2 節の 6 番の作例が、この形です。
- **3 行目（初回の作業ディレクトリ）**: `~/.app/` のような置き場を、初回だけ作ります。中身は後で使うためのものなので、6 番に入れます。6 番の定義の例に「初回に作る作業ディレクトリ・設定ファイル」とあるとおりです。

#### 小さな例 2 — 練習用サーバの組 1（名前はキャッシュ、動作は？）

手引きの下書きの 20.1 節には、判定の練習のために書かれた小さなサーバがあります（第 53 章で、このサーバを最初から最後まで判定します）。
その一部を、左に行番号を付けて写します。

```

 8
 9
10  def _save_cache(name, text):
11      os.makedirs(CACHE_DIR, exist_ok=True)
12      with open(os.path.join(CACHE_DIR, name), "w") as fh:
13          fh.write(text)
14
15
16  def _lookup(query):
17      conn = sqlite3.connect("notes.db")
18      rows = conn.execute("SELECT body FROM notes WHERE title = ?", (query,)).fetchall()

20      return rows
21
```

（出典: `docs/drafts/final_judging_guide_draft.md:554-600`（練習用サーバ。この写しはその 7〜26 行））

#### 一歩ずつの説明 — 行ごとに

- **7 行目**: `CACHE_DIR` に、ホームディレクトリの下の `.demo_cache` というパスを入れます。`os.path.expanduser` は `~`（ホームディレクトリ）を本当のパスに直す関数です。
- **10 行目**: `_save_cache` という関数を定義します。名前は「キャッシュを保存する」です。
- **11 行目**: `CACHE_DIR` のディレクトリが無ければ作ります（`exist_ok=True` なので、あれば何もしません）。
- **12 行目**: `CACHE_DIR` の下の `name` という名前のファイルを、`"w"`（中身を消して書く）で開きます。
- **13 行目**: そこに `text` を書きます。
- **16〜18 行目**: `_lookup` は、`notes.db` という SQLite のデータベースに接続し、題名が `query` のノートの本文を `SELECT`（読み取り）で取り出します。
- **19 行目**: 取り出した結果を文字列にして、`_save_cache` に渡します。ファイル名は検索語の `query` です。
- **20 行目**: 結果を返します。
- **23〜26 行目**: `search_notes` は読み取り専用（D1）と宣言したツールで、`_lookup` を呼ぶだけです。

手引きの下書きは、この組（`search_notes` × `builtins.open`（12 行）× D1）を正にしたうえで、書き込み先の種類を次のように決めています。

> 書き込み先の種類: 検索結果をキャッシュに保存して…と考えたいが、このコードは書いたものを**読み返していない**。
> 定義どおりなら「キャッシュ・状態の保存」（後で読み返す）に当てはまらない。読み返しが木のどこにも無いことを grep で
> 確かめたうえで、**その他・不明**とし、`note` に「キャッシュの名前だが読み返しが無い」と書く。
> （このように、名前ではなく動作で決める。）

（出典: `docs/drafts/final_judging_guide_draft.md:614-617`（組 1 の書き込み先の種類））

#### 定義を 1 つずつ当ててみる

上から順に当ててみます（本書の説明。結論は手引きと同じ「その他・不明」です）。

1. **相手側の状態**: NET の効果ではありません。当てはまりません。
2. **データベース**: 18 行は DB を使いますが、`SELECT`（読み取り）だけです。この組の書き込み（12 行）は DB ではなくファイルです。当てはまりません。
3. **利用者のファイル**: ファイル名の `query` はモデルが決める値ですが、場所（`~/.demo_cache`）はサーバが決めていて、書く中身も検索結果の写しです。利用者がその場所を指定したわけでも、利用者の文書・データでもありません。当てはまらない、と読めます。
4. **ログ**: ツールは読み返しません。けれども、定義のもう 1 つの条件「記録のためだけに書く」はどうでしょう。書いているのは検索結果そのもの（`str(rows)`）で、「いつ・何をしたか」の記録の行ではありません。当てはまるとは言えません。
5. **一時ファイル**: 同じ呼び出しの中で消していません。場所も OS の一時領域ではなく、ホームディレクトリの下です。当てはまりません。
6. **キャッシュ・状態の保存**: 「後で読み返す」が条件です。`CACHE_DIR` を読む行が木の中に無いので、当てはまりません。
7. **プロセスの起動・コードの実行**: SPAWN / EXEC ではありません。
8. **その他・不明**: 1〜7 のどれにも当てはまらないので、ここに入ります。

6 番の「読み返しが無い」は、grep で確かめます。
たとえば、`grep -n "CACHE_DIR\|demo_cache" server.py` を練習用サーバに当てると、出てくるのは 7・11・12 行だけです（本書が手引きの写しで確かめた）。
読む側の行（`open(..., "r")` や `read_text`）がありません。

**なお、4 番（ログ）を退けた理由は本書の説明です。** 手引きの下書きは、なぜログではないかを書いていません（キャッシュでないことだけを書いています）。
判定のときに「ログにも当てはまるのでは」と迷ったら、それ自体が「決められない」の印なので、「その他・不明」にして `note` に書く、という手引きの規則（16.2 節の最後）に戻ります。

#### なぜ名前ではなく動作で決めるのか

理由は 2 つあります。

1. **名前は書いた人の意図で、事実ではないから**: `_save_cache` という名前は、書いた人が「いつかキャッシュとして使うつもり」だったことを示すだけかもしれません。ラベルは「事実のラベル」（D67 の 1）なので、実際の動作で決めます。
2. **判定者によるぶれを減らすから**: 名前の印象は人によって違います。「読み返す行があるか」は grep で誰でも同じ答えに着けます。2 人目の判定者がいないこの研究では、第三者が同じ行を開けば同じ結論に着ける（D67 の 4）ことが大事です。

#### よくある誤解・つまずき

- **誤解: 「名前がキャッシュなのだから、キャッシュ・状態の保存でよい」**
  定義は「後で読み返す」です。読み返しが無ければ当てはまりません。
- **誤解: 「その他・不明は、判定を間違えたときの箱」**
  違います。この組は正です。「その他・不明」は、正の中身が 1〜7 のどれにも当てはまらないことを、そのまま記録するラベルです。
- **つまずき: 読み返しを探す範囲が狭すぎる**
  読み返しは、同じツールの中とは限りません。別のツールが同じファイルを読むこともあります（ツール A がキャッシュを書き、ツール B が読む）。手引きは「木のどこにも無いことを grep で確かめる」と書いています。木全体を grep します。
- **つまずき: パスの注入の話をラベルに混ぜる**
  組 1 では、ファイル名がモデルの決める `query` から作られるので、`../` を入れればキャッシュの外に書けるかもしれません。手引きは、これを「宣言の正誤とは別の話（パスの注入）なので、判定には入れず `note` に書くだけ」としています。ラベルも、この可能性で「利用者のファイル」に変えたりしません。

（出典: `docs/drafts/final_judging_guide_draft.md:620-621`（パスの注入は note に書くだけ））

#### 手作業ではどう使うか

1. まず 16.2 節の 6 つの事例に、同じ形が無いかを見ます。あれば、その答えに従います。
2. 無ければ、51.3 節の順に 1 番から定義を当てます。
3. 「読み返すか」「同じ呼び出しで消すか」は、grep と道筋で確かめ、確かめた方法を `note` か `evidence` に書きます（例: `grep -rn "demo_cache" . で 7・11・12 行だけ。読む行は無い`）。
4. 名前と動作が食い違ったら、動作で決め、`note` に「キャッシュの名前だが読み返しが無い」のように食い違いを書きます。

#### この節のまとめ

境界の例 6 つは、手引きが先に答えを決めてある。どの場合も、名前ではなく動作（読み返すか、消すか、誰が場所を決めたか）で決める。
練習用サーバの組 1 は、名前はキャッシュだが読み返しが無いので「その他・不明」で、`note` に食い違いを書く。

### 51.5 決められないとき — 「その他・不明」と note、途中で定義を足さない

#### 一言で言うと

判定の途中で、どの種類か決められない事例に出会ったら、**「その他・不明」にして、事例を `note` に書きます**。
その場で新しい種類を作ったり、定義を広げたりは**しません**。

#### たとえ話 — 試合の途中でルールを変えない

サッカーの試合の途中で、審判が「このプレーはルールブックに書いていないから、今から新しいルールを作る」と言い出したら、どうなるでしょう。
前半と後半で、同じプレーの扱いが変わってしまいます。
それに、どちらのチームに有利なルールを作ったのか、疑われます。
ルールで決まらないプレーは、試合の後に記録として残し、次のシーズンの前にルールを直すのが筋です。

#### 小さな例 — note の書き方（v4 の reaper-mcp を例にした作例）

| verdict | write_target | note |
|---|---|---|
| 正 | その他・不明 | 境界の事例: 別のプロセスとの受け渡しディレクトリで、前の呼び出しが残した応答ファイルを消す（reaper_mcp_server.py:368）。同じ呼び出しで作ったものではないので 5（一時ファイル）に当たらず、ツールが自分で保存して読み返すものでもないので 6 にも当たらない。16.2 に扱いが無い |

表の読み方: 判定は正のままで、ラベルを「その他・不明」にし、なぜ決められないかを、定義のどこに当たらないかの形で `note` に書きます。
後で集計する人（学生自身）が、この `note` を読めば、どの境界で迷ったかが分かります。

#### 一歩ずつの説明 — 手引きの規則

手引きの下書きは、16.2 節の最後に次のように書いています。

> 判定の途中で境界の事例が出て決められないときは「その他・不明」にし、事例を `note` に書く。途中で定義を足さない（第 22 節）。

これを 3 つに分けて読みます。

1. **「決められないときは『その他・不明』にし」**: 8 番の定義には、「上のどれにも当てはまらない」だけでなく「**または決められない**」が入っています。だから、迷った件の行き先は 8 番です。
2. **「事例を `note` に書く」**: どの定義のどこで迷ったかを書きます。上の作例のように、「5 に当たらない理由」「6 に当たらない理由」を並べると、後で読む人に伝わります。
3. **「途中で定義を足さない（第 22 節）」**: 手引きの 22 節は、手引きで決まらない事例が出たときの手続きを決めています（くわしくは第 52 章）。どうしても規則を足すなら、足した日時を記録し、足す前と後の件を分けて報告し、主の結果は事前登録した手引きのままの判定にする、という重い手続きです。

（出典: `docs/drafts/final_judging_guide_draft.md:408-409`（16.2 節の最後）、`:664-672`（22 節））

#### なぜ途中で定義を足さないのか

1. **結果を見てから基準を変えないため**: 判定の途中では、すでにいくつもの件のラベルを見ています。そこで定義を足すと、「この種類の件数を増やしたい（減らしたい）」という気持ちが、知らないうちに混ざります。これは CLAUDE.md の規則 5（凍結した項目は、凍結後に見た結果で変えない）と同じ考え方です（第 22 章）。
2. **前と後で物差しが変わるため**: 定義を足す前に付けたラベルと、後に付けたラベルは、違う物差しで測ったことになります。内訳の表の 1 つの列に、違う物差しの数が混ざります。
3. **「決められない」こと自体が情報だから**: 「その他・不明」が多ければ、それは「8 つの種類では分けきれない書き込みが多い」という事実です。黙ってどこかに押し込むと、この事実が消えます（CLAUDE.md の規則 4: 解決できなかったものは不明として記録する）。

#### 手引きにまだ書かれていない境界（本書の指摘。**未決**）

手引きはまだ下書き・未承認です。
封をする**前**なら、境界の例を書き足すことができます。
ここでは、本書が手引きと原典を読み比べて気づいた、まだ書かれていない境界を 4 つ挙げます。
**どれも本書の指摘で、どう扱うかは決まっていません（未決）。決めるのは学生です。**
封の前に決めなければ、判定の途中で出会ったときは、上の規則どおり「その他・不明」と `note` になります。

| # | 境界 | なぜ迷うか |
|---|---|---|
| 1 | 前の呼び出しが残した受け渡しファイルの削除（v4 の reaper-mcp） | 同じ呼び出しで作ったものではないので 5 に当たらない。ツールが保存して読み返すものでもないので 6 にも当たりにくい。第 43 章 43.12 節でくわしく見た |
| 2 | OS の一時領域（`/tmp`）に置き、次の呼び出しで読み返すキャッシュ | 定義と順番をそのまま当てると 5（一時ファイル）。けれども使い方は 6（キャッシュ）そのもの。16.2 の境界の例に無い |
| 3 | SPAWN・EXEC の正で、起動したコマンドが何を書くかが分かっている場合（例: 固定のコマンドが DB を書き換えると調べて分かった） | 7 の定義は「SPAWN / EXEC の正」で、D68 の 3 の文も「D1 / D2 の SPAWN・EXEC の正」に付けると読める。一方、上から順の規則では、2（DB の行を変える）が 7 より先に当たるとも読める |
| 4 | 1 組の複数の位置を正にし、位置ごとに種類が違う場合 | 16.2 は「正にした位置で決める」と書くが、正にした位置が 2 つ以上で種類が違うときの選び方は書いていない。条件の種類は「条件の一番弱い位置」で記録する（D68 の 1）が、ラベルの位置との関係も書いていない |

表の読み方: 1 行が 1 つの境界です。
たとえば 2 行目は「`/tmp` の下に置いて次の呼び出しで読み返すキャッシュは、5 番の『OS の一時領域に作る』に先に当たるので、規則どおりなら一時ファイル。けれども動作はキャッシュそのものなので、規則どおりでよいのかを、封の前に決めておくとよい」と読みます。

ここで大事なのは、**本書はどちらがよいかを決めない**ということです。
本書が勝手に「2 は 6 にすべき」と書けば、それは手引きを読者の知らないところで変えることになります。
学生が封の前に決めるなら、境界の例の表に 1 行足し、事前登録と同じコミットで封をします。
決めないなら、規則どおり（1・4 は「その他・不明」と `note`、2 は 5 番、3 は迷えば「その他・不明」と `note`）になります。

（出典: `docs/drafts/final_judging_guide_draft.md:382-395`（16.1 節の定義）、`:397-409`（16.2 節）、`:152-160`（手順 G: 正にできる位置と条件の一番弱いもの）、`docs/decisions.md:3809-3811`（D68 の 3 の文））

#### よくある誤解・つまずき

- **誤解: 「その他・不明が多いと、判定が下手だと思われる」**
  違います。決められないものを決められないと記録するのが、この研究の約束です。無理に押し込むほうが、結果を歪めます。
- **誤解: 「迷ったら一番近そうな種類にしておき、note に『迷った』と書けばよい」**
  手引きの規則は「その他・不明にし、事例を note に書く」です。近そうな種類に入れると、その種類の件数に、迷った件が混ざります。
- **つまずき: 判定（正誤）まで不明にしてしまう**
  ラベルが決められないことと、判定が決められないことは別です。到達して宣言に反するなら、判定は正です。ラベルだけを「その他・不明」にします。
- **つまずき: 気づいた境界を、その場で手引きに書き足す**
  判定の途中で手引きを書き換えてはいけません。気づいた境界は、`note` と事前登録の逸脱の記録（手引きの 22 節の 2）に書きます。

#### 手作業ではどう使うか

1. 51.3 節の手順で 1 番から当てて、どれとも決められなければ「その他・不明」にします。
2. `note` に、「境界の事例: <何を書いたか>。<定義 X> に当たらない理由、<定義 Y> に当たらない理由」を書きます。
3. 同じ形が何度も出たら、それぞれの件に同じように書きます（後で数えられるように、書き方をそろえます）。
4. 判定が終わった後、集計のときに「その他・不明」の `note` を読み、どんな境界が多かったかを報告の材料にします。

#### この節のまとめ

決められないときは「その他・不明」にし、どの定義のどこで迷ったかを `note` に書く。判定の途中で定義を足さない。
手引きにまだ書かれていない境界が少なくとも 4 つあり（本書の指摘）、扱いは未決。封の前に決めるかどうかは学生が決める。

### 51.6 D3 の正に付ける通信先の種類（手引き 16.3 節）

#### 一言で言うと

D3（`openWorldHint: false`、関わる範囲が閉じている）の正は、書き込みではなく**外との通信**の違反です。
だから書き込み先の種類の代わりに、**通信先の種類**を 4 つから 1 つ、同じ `write_target` 欄に書きます。

#### たとえ話 — 「内線しか使いません」と言った電話番

「この電話番は内線（社内）にしかかけません」と約束した人が、外線でかけていたとします。
外線のかけ方には、いくつかあります。

- 決まった取引先の番号に、毎回かける（番号は電話番が最初から知っている）。
- お客さんに言われた番号に、そのままかける（どこにかかるかはお客さんしだい）。
- お客さんに言われた「手順」のとおりに機械を操作する（機械がどこに電話するかも、お客さんしだい）。
- 上司が設定した番号にかける（どこにかかるかは上司の設定しだいで、外かどうか分からない）。

どれも「内線だけ」の約束には反しえますが、どこにかかるか、誰がそれを決めるかが違います。
通信先の種類は、この違いを記録するためのものです。

#### 小さな例 — 4 つの種類と作例

| 種類 | 定義 | 例 |
|---|---|---|
| **定数の外部ホスト** | コードに書かれた外部のホストと通信する | `requests.get("https://api.example.com/…")` |
| **モデルが決める宛先** | 宛先のホストをモデルが決められる | `httpx.get(url)`（`url` はツールの引数） |
| **モデルが決めるコード・コマンド** | 実行するコード・起動するコマンドをモデルが決められる（通信しうる） | `subprocess.run(cmd, shell=True)` |
| **その他・不明** | 上のどれにも当てはまらない、または決められない | 宛先が運用者の設定で、既定値が外部のもの |

表の読み方: 1 行が 1 つの種類です。
たとえば 2 行目は「`httpx.get(url)` の `url` がツールの引数なら、宛先のホストをモデルが決められる。この形の D3 の正には『モデルが決める宛先』を付ける」と読みます。

（出典: `docs/drafts/final_judging_guide_draft.md:411-420`（16.3 節））

次は、4 つの種類のそれぞれに当たるツールの作例です（本書の作例。どれも D3 を宣言しています）。

```python
 1  @mcp.tool(annotations=ToolAnnotations(openWorldHint=False))
 2  def weather(city: str) -> str:
 3      r = requests.get("https://api.weather.example.com/v1/now", params={"q": city})
 4      return r.text
 5
 6  @mcp.tool(annotations=ToolAnnotations(openWorldHint=False))
 7  def fetch(url: str) -> str:
 8      return httpx.get(url).text
 9
10  @mcp.tool(annotations=ToolAnnotations(openWorldHint=False))
11  def shell(cmd: str) -> str:
12      return subprocess.run(cmd, shell=True, capture_output=True, text=True).stdout
13
14  API_BASE = os.environ.get("NOTES_API", "https://notes.example.com")
15
16  @mcp.tool(annotations=ToolAnnotations(openWorldHint=False))
17  def list_remote_notes() -> str:
18      return requests.get(API_BASE + "/notes").text
```

#### 一歩ずつの説明 — 行ごとに

- **1〜4 行目（定数の外部ホスト）**: 3 行目の宛先 `https://api.weather.example.com/…` は、コードに書かれた定数です。モデルが決めるのは `city`（問い合わせの中身）だけで、ホストは変えられません。けれども、そのホストは外部（そのマシンやローカルの網の外）です。「関わる範囲が閉じている」に反するので D3 の正で、種類は**定数の外部ホスト**です。
- **6〜8 行目（モデルが決める宛先）**: 8 行目の `url` はツールの引数で、モデルが決めます。モデルは、外部のどんなホストでも指せます。原理 3-a（取りうる値の全体で考える）により反するので正で、種類は**モデルが決める宛先**です。
- **10〜12 行目（モデルが決めるコード・コマンド）**: 12 行目は、モデルが決めた `cmd` をシェルで実行します。モデルは `curl` で外部と通信するコマンドも実行させられます。だから正で、種類は**モデルが決めるコード・コマンド**です。表の定義の「（通信しうる）」は、コマンドやコードが通信に使える、という意味です。
- **14〜18 行目（その他・不明）**: 14 行目の `API_BASE` は、環境変数 `NOTES_API`（運用者が決める値）があればそれ、無ければ `https://notes.example.com` という外部の既定値です。宛先は運用者の設定で決まります。手引きの 15.3 節は、この形を「設定の既定値や文書で外部を想定しているなら反する」としています。ここでは既定値が外部なので反する、と読めて正です。けれども、通信先の 4 つの種類のうち、「運用者の設定」を表す種類はありません。だから**その他・不明**です。16.3 節の表の例も、まさにこの形（宛先が運用者の設定で、既定値が外部のもの）です。

（出典: `docs/drafts/final_judging_guide_draft.md:350-359`（15.3 節の D3 の問いと表））

#### 反しない側も確かめる

D3 の正になるのは、宛先が外部か、モデルが決められるときです。
次の形は、D3 に**反しない**ので、そもそも正にならず、通信先の種類も付けません（15.3 節）。

| 形 | D3 に反するか |
|---|---|
| 宛先が `localhost` / private（`127.0.0.1`、`10.x`、`192.168.x`）/ loopback | 反しない |
| ファイル・DB のローカルの操作 | 反しない |
| 宛先が運用者の設定で、既定値や文書がローカルを想定している | 反しない |

表の読み方: たとえば 1 行目は「宛先が自分のマシン（`localhost`・`127.0.0.1`）や家庭・社内の網の中の番地なら、関わる範囲は閉じているので D3 に反しない」と読みます。
ローカルの範囲をどこまでとするか（たとえば社内の網の別のマシン）は、手引きの 15.3 節の書き方に残る課題で、第 46 章で未決の一覧に入れています。

#### なぜ D3 だけ別の種類にしたのか

D68 の 3 の理由は、「D3 の違反は書き込みではなく外部との通信なので、書き込み先の種類が当てはまらない」です。
たとえば、定数の外部ホストに `GET` で問い合わせるだけのツールは、D3 には反しますが、何も書き換えません。
このような正に 8 つの書き込み先の種類を当てようとしても、当てはまる種類がなく、「その他・不明」に入ってしまいます（本書の説明）。
D3 の違反で読み手が知りたいのは「何を書き換えたか」ではなく、「**どこと、誰の決めた相手と通信したか**」です。
だから、宛先を誰が決めるか（コードの定数か、モデルか、運用者か）で分ける種類にしました。

また、決定の文には「v4 の D3 の矛は 0 件だった」と書かれています。
v4 では D3 の正を 1 件も見ていないので、この 4 つの種類は、実例を見る前に、定義から作ったものです。

（出典: `docs/decisions.md:3811-3813`（D68 の 3: D3 には通信先の種類、v4 の D3 の矛は 0 件）、`docs/population_v4.md:87`（D3 は 0 件））

#### 解析器の理由コードとの対応（手がかり）

解析器は、D3 の矛に次の理由コードを付けます（第 48 章 48.13 節）。
通信先の種類を決めるときの手がかりになりますが、**決めるのはコードを読んだ判定者**です。

| 解析器の理由 | 意味 | 手がかりになる通信先の種類 |
|---|---|---|
| `net_external_host` | 宛先が定数の外部ホスト | 定数の外部ホスト |
| `net_model_host` | 宛先をモデルが決められる | モデルが決める宛先 |
| `exec_model` | 実行するコードをモデルが決められる | モデルが決めるコード・コマンド |
| `spawn_model` | 起動するコマンドをモデルが決められる | モデルが決めるコード・コマンド |

表の読み方: たとえば 1 行目は「理由が `net_external_host` なら、まず『定数の外部ホスト』を疑い、コードを開いて宛先が本当に定数の外部ホストかを確かめる」と読みます。
解析器が定数と読んだ宛先が、実は運用者の設定の既定値だった、ということもありえます。そのときは「その他・不明」です。

（出典: `docs/drafts/final_judging_guide_draft.md:198-219`（13.1 節の理由コードの表））

#### よくある誤解・つまずき

- **誤解: 「D3 の正にも書き込み先の種類を付ける」**
  付けません。D3 の正には通信先の種類を、同じ `write_target` 欄に書きます（D68 の 3）。
- **誤解: 「宛先のパスやクエリをモデルが決めるなら、モデルが決める宛先」**
  「モデルが決める宛先」の定義は「宛先の**ホスト**をモデルが決められる」です。ホストが定数で、パス（`/v1/now` の部分）や問い合わせの中身だけをモデルが決めるなら、「定数の外部ホスト」です。
- **つまずき: 運用者の設定の宛先を、無理に「定数の外部ホスト」にする**
  既定値が外部でも、宛先を決めるのは運用者の設定です。4 つの種類に「運用者の設定」は無いので、「その他・不明」です。
- **つまずき: 通信先の種類で、上から順の規則を使う**
  手引きの下書きは、通信先の種類には「上から順に」とは書いていません。ふつう、1 つの位置で宛先を決めるのは「コードの定数」「モデル」「運用者」のどれか 1 つなので、重なることは少ないはずです。重なって迷ったら、「その他・不明」と `note` です。

#### 手作業ではどう使うか

D3 の組を正にしたら、次の順に確かめます。

1. 効果は NET か、SPAWN / EXEC か。
2. NET なら、宛先のホストは何で決まるか（コードの定数 / モデルの引数 / 運用者の設定 / 読み切れない）。
3. SPAWN / EXEC なら、コマンドやコードをモデルが決められるか。決められるなら「モデルが決めるコード・コマンド」です（解析器は、コマンドやコードが定数のときは D3 で不を出すので、矛にはなりません。第 17 章の判定表 7.3）。
4. 4 つの種類から 1 つを `write_target` に書き、宛先が何で決まるかを `evidence` に書く。

#### この節のまとめ

D3 の正には、書き込み先の種類ではなく通信先の種類（定数の外部ホスト / モデルが決める宛先 / モデルが決めるコード・コマンド / その他・不明）を付ける。
分け目は「宛先のホスト（またはコマンド）を誰が決めるか」。運用者の設定で決まる宛先は「その他・不明」。

### 51.7 誤の原因 E1〜E9 — 全体の地図（手引き 17 節）

#### 一言で言うと

誤にしたときは、**解析器がなぜ間違えたか**を、E1〜E9 の 9 つの類から 1 つ選んで `error_class` に書きます。
9 つは、v3・v4 の中間検証で実際に出た誤りの類を、最初から用意したものです。

#### たとえ話 — 火災報知器の誤作動の記録

ビルの火災報知器が鳴ったのに、火事ではなかったとします。
管理人は、「誤作動」と記録するだけでなく、**原因**も記録します。
料理の湯気、たばこの煙、点検の作業、ほこり、機械の故障、などです。
1 年分の記録を集めると、「この報知器は湯気に弱い」「点検の日に鳴りやすい」と分かります。
直せない原因なら、「この報知器にはこういう弱点がある」と、住人に正直に知らせる材料になります。

誤は、解析器の「誤作動」（誤警報）です。
E1〜E9 は、誤作動の原因の分類です。
集めると「解析器はどんな形に弱いか」が分かり、論文の限界の節に書く材料になります（51.17 節）。

4. どれにも当てはまらない、または迷うなら E9 にして説明を書く。

次の節から、E1〜E9 を 1 つずつ、コードで見ていきます。

### 51.8 E1 — 起動時の初期化（lifespan・import 時）

#### 一言で言うと

効果が「一度だけ初期化する」処理の中にあり、その初期化が **lifespan の中かモジュールの読み込み時に、ツールの受付より前に必ず済む**なら、ツールの呼び出しでは届きません。
この誤が E1 です。

#### たとえ話 — 開店前の準備

お店の店員が「お客さんの注文を受けたら、まず棚が無ければ棚を組み立て、それから商品を出す」という手順書を持っているとします。
けれども実際には、棚は**開店前**に必ず組み立て終わっています。
お客さんの注文で棚を組み立てることは、一度もありません。
手順書だけを読んだ人は「注文のたびに棚を組み立てるかもしれない」と思いますが、店の 1 日の流れを知っていれば、そうならないと分かります。
解析器は、ツールの呼び出しを 1 回ずつ、サーバの状態（開店前に済んだこと）を仮定せずに読むので、この「開店前の準備」を見落とします。

#### なぜ E1 を独立した類にするのか

D67 の 2 は、lifespan の形の誤りについて、「解析器は変えず、設計の選択による限界（誤警報の向き）として件数を報告する。判定の手引きの誤の原因の欄に、この類を設ける」と決めました。
解析器は、各ツールの呼び出しを、サーバの状態（lifespan で済んだこと）を仮定せずに、独立に読む設計です。
lifespan の形を正しく扱うには、「lifespan がツールより先に走る」「大域変数に値が入る」「別の場所で `None` に戻されない」「lifespan が失敗して値が入らないまま受付が始まることがない」の 4 つを全部確かめる必要があり、1 つでも外すと誤 clear（本当の違反を消す）を作る危険があります（O43）。
だから解析器は直さず、その代償（誤警報）を E1 として数えて、正直に報告します。
E6（ほかの到達しない形）と混ぜると、この件数が数えられなくなります（第 49 章）。

（出典: `docs/decisions.md:3773-3778`、`docs/open_questions.md:1207-1213`（O43: 「解析器は変えない（限界として残す）」の 4 つの条件）、`docs/final_evaluation_procedure.md:1401`（24.2 節: lifespan の形の誤警報を限界として書く））

#### よくある誤解・つまずき

- **誤解: 「守りの `if ... is None:` があれば、全部 E1」**
  E1 になるのは、初期化を先に済ませる場所が lifespan かモジュールの読み込み時のときだけです。`main()` の中だけなら「到達する」です（ccr）。
- **誤解: 「`None` に戻す行が 1 つでもあれば、到達する」**
  戻す行が、**ツールの呼び出しのあいだに**走るかを見ます。shyhurricane の 203 行は `atexit`（プロセスの終わり）だけなので、ツールの呼び出しで初期化が再び走ることはありません。
- **つまずき: E1 は「ツールが何も書かない」という意味ではない**
  E1 は、**その組の効果**（ここでは 114 行の `os.makedirs`）が届かない、という意味です。たとえば `find_urls` は 207 行で `log_tool_history` を呼び、それは `__init__.py:216-221` → `:198-211` と進んで、履歴のファイル `history.jsonl` に `'ta'`（文字で追記）で書いています（本書が執筆時に読んだ行）。この書き込みは別の道筋で、`os.makedirs` の組の判定には入りません。
- **つまずき: lifespan が条件つきで初期化する形**
  lifespan の中でも、初期化が `if` の中にあって、条件しだいで済まないなら、条件が偽のときはツールの呼び出しで届きます。そのときは「到達する」です（手引き 14.4 節の見分け方）。

#### この節のまとめ

`main()` の中だけで済ませる形（ccr）は到達する側で、E1 にならない。E1 を独立させるのは、D67 の 2 で設計の限界として件数を報告するため。

### 51.9 E2 — 同じ呼び出しで作った一時ファイル・ロックの後始末（D2）

#### 一言で言うと

D2（破壊しない）の組で、解析器が「既存のものを消す」とした削除が、実は**同じ呼び出しの中でツール自身が作った一時ファイルやロックの後始末**だったときの誤が E2 です。

#### たとえ話 — 自分で貼った付箋をはがす

「この机の上のものは捨てません」と約束した人が、作業中に自分で付箋を貼り、作業の終わりにその付箋をはがして捨てたとします。
約束を破ったでしょうか。
机の上に**前からあったもの**は何も捨てていません。
自分がさっき貼ったものを片づけただけです。
D2 の問いは「呼び出しの前からあったものを消す・上書きする・変えるか」なので、自分で作ってすぐ消したものは、これに当たりません（第 50 章）。

#### 小さな例 2 — 同じ形が、D1 では正になる（ru-marketplace、実物）

v4 の ru-marketplace の `ozon_reviews` は、読み取り専用（D1）と宣言したツールで、次の形を通ります。

```
205      fd, out_path = tempfile.mkstemp(prefix="ozon-sync-worker-", suffix=".pkl")
206      os.close(fd)
 ..
231      finally:
232          try:
233              os.remove(out_path)
```

（出典: `corpus/v4-vladimir-human__ru-marketplace-mcp/packages/ozon-connector/src/ozon_connector/server.py:205-206,231-235`。v4 の判定は M58。v4 の記録はこの部分を「:203-204」「:231-235」と書いているが、本書が確かめた `mkstemp` の行は 205 行）

- **205 行**: `tempfile.mkstemp` で、OS の一時領域に新しいファイルを作ります。
- **206 行**: 作ったときに開いた番号（`fd`）を閉じます。ファイルは残ります。
- **231〜235 行**: 処理が終わったら（`finally`）、そのファイルを `os.remove` で消します。

v4 の M58 は、この `os.remove`（233 行）の D1 の組を**正**にしました。
手引きの 15.1 節が、D1 について「ファイルの書き込み・作成・削除・移動・権限の変更（`FS_WRITE` すべて）は反する。ログ・キャッシュ・一時ファイル・ディレクトリの作成も含む（原理 1-i-b）」と決めているからです。
D1 では、一時ファイルを作ることも消すことも、ファイルシステムを書き換える動作として数えます。
ラベルは、同じ呼び出しで作って消すので**一時ファイル**です。
一方、**同じ形が D2 の組なら、誤（E2）**になります。
手引きの 20.2 節も、M58 について「D1 では反する。D2 なら E2 で誤になる形」と書いています。

| 宣言 | 問い | 自分で作った一時ファイルの削除 | 判定 |
|---|---|---|---|
| D1 | 環境を変えるか（FS_WRITE はすべて反する） | 作成も削除も、ファイルシステムへの書き込み | **正**（ラベル: 一時ファイル） |
| D2 | 呼び出しの前からあったものを消すか | 前からあったものではない | **誤**（E2） |

表の読み方: 同じ削除の行でも、照らす宣言で問いが違うので、判定が分かれます。
たとえば 2 行目は「D2 の組なら、自分が同じ呼び出しで作った一時ファイルを消しても、前からあったものは消していないので反しない。誤にして E2」と読みます。

（出典: `docs/drafts/final_judging_guide_draft.md:309`（15.1 の FS_WRITE の行）、`:342-344`（15.2 の迷いやすい形）、`:641`（20.2 の M58））

#### なぜ E2 を独立した類にするのか

この誤は、v3 で 3 件（`mkstemp` / atomic write の後始末）、v4 で 2 件（ccr）と、続けて出ました（どちらも本記録者の判定で、開発用の抜き取りの数です）。
O41 は、この類を「MCP 仕様の『additive か destructive か』で読めば破壊的ではないが、採った原理（§6）の読み替えになるので直さない」と記録しています。
解析器は、`unlink` を「既存のものを消す」と一律に読む表（判定表 7.2）のとおりに動いています。
その表を変えるには原理の読み替えが要るので、解析器は直さず、判定で E2 として数えます。
数えておけば、論文で「この表の一律の読み方が生んだ誤警報は何件か」を示せます。

（出典: `docs/open_questions.md:1061-1062`（O41 の 1 つ目）、`docs/population_v3.md:84-87`、`docs/population_v4.md:99-101`）

#### よくある誤解・つまずき

- **誤解: 「一時ファイルの削除は、どの宣言でも違反ではない」**
  D1 では違反です（FS_WRITE はすべて）。E2 は D2 のときだけの類です。
- **誤解: 「`unlink` の前に `exists` で確かめていれば、自分が作ったもの」**
  確かめるべきは「**同じ呼び出しの中で、ツール自身が作ったか**」です。`exists` で確かめていても、前の呼び出しが残したファイルを消すなら、呼び出しの前からあったものなので**反します**（手引き 15.2）。v4 の reaper-mcp の、前の呼び出しが残した応答ファイルの削除（`unlink(missing_ok=True)`）も、前の呼び出しのものを消す形でした（第 43 章 43.12 節）。
- **つまずき: 同じ名前のファイルを、毎回作り直して消す形**
  名前が毎回同じでも、その呼び出しの中で作って、その呼び出しの中で消すなら、E2 の側です。前の呼び出しのファイルを消すかどうかで分けます。
- **つまずき: キャッシュの上書きを E2 にする**
  同じキャッシュファイルを毎回 `'w'` で書き直す形は、前の内容（前の呼び出しが書いたもの）を上書きするので、D2 に**反します**（手引き 15.2 の迷いやすい形）。E2 ではありません。

#### 手作業ではどう使うか

D2 の組で、消す・動かす効果に出会ったら、次を確かめます。

1. 消す対象のファイルを、**どこで作ったか**を探す（同じ関数の前の行か、同じ呼び出しの道筋か）。
2. 作る行と消す行が、**同じ呼び出しの中**にあるか（`with` の入口と出口、`try` と `finally` など）。
3. 前の呼び出しが残したものを消す道は無いか（起動時の掃除、`exists` で見つけた古いファイルの削除など）。

`error_class` の例: `E2: memory_file_io.py:102 で作った lock_path を、同じ with の終わりの :111 で消す後始末。呼び出しの前からあったものではない`

#### この節のまとめ

E2 は、D2 の組で、同じ呼び出しで自分が作った一時ファイル・ロックの後始末を「既存のものを消す」とした誤。v4 の ccr、v3 の `mkstemp` の後始末が例。
同じ削除でも D1 なら正（ラベルは一時ファイル）。前の呼び出しが残したものを消すなら D2 にも反する。

### 51.10 E3 — 名前だけの解決の誤り（呼び出し先の取り違え）

#### 一言で言うと

解析器が、呼び出しを**名前だけ**で、木の中の同じ名前の関数に結びつけてしまい、本当は呼ばれていない関数の中の効果を、ツールの効果として数えた誤が E3 です。
本当に呼ばれているのは、組み込みの型のメソッドや、別のクラスの同じ名前のメソッドです。

#### たとえ話 — 同姓同名の呼び出し

学校の放送で「佐藤さん、職員室に来てください」と呼んだとします。
校内には、3 年 1 組の佐藤さんと、1 年 2 組の佐藤さんがいます。
放送を聞いた記録係が、名前だけを見て「3 年 1 組の佐藤さんが職員室に行った」と書いたら、それは確かめていない記録です。
本当に呼ばれたのが誰かは、どのクラスの佐藤さんか（受け手）を見ないと分かりません。

#### なぜ解析器を直さなかったのか

O41 は、この類について「D61 G2 で直そうとしたが、値の形は型の証明ではなく誤 clear を作った。取り消した」と記録しています。

けれども O41 によれば、値の形はその変数の型の証明にはならず、この直し方は誤 clear（本当の違反を消す誤り）を作りました。
（たとえば、同じ変数に、別の場所で木の中のクラスの物が入ることもありえます。これは本書の補足です。）
v4 の rails-lens の `set()` は、v4 の記録で「v3 の `bytearray.append` と同じ類」とされています。
誤 clear は、この研究がいちばん避けたい向きの誤りです（第 21 章）。
だから解析器は名前だけの解決を残し、その代償（誤警報）を E3 として数えます。
なお、CLAUDE.md の落とし穴にも「末尾名だけの解決を『やめる』と真の経路が消える。受け手型で裏付けられない解決は、降りたうえで効果の確度に `opaque(unresolved)` を合流する」と書かれています。

#### よくある誤解・つまずき

- **誤解: 「`witness_chain` に出ている関数は、必ず呼ばれている」**
  `witness_chain` は解析器の言い分です。名前だけで結んだ段が混ざっていることがあります。1 段ずつ、本当にその関数が呼ばれているかを、受け手（何の物のメソッドか）で確かめます（第 48 章の手順 D）。
- **誤解: 「エディタの『定義へ移動』で飛べたから、呼ばれている」**
  手引きの 12.2 節は、「エディタの『定義へ移動』も名前で当てていることがある」と注意しています。エディタも同じ取り違えをしうるので、受け手の型で確かめます。
- **つまずき: E3 と E6 の区別**
  ツールの道筋にある呼び出しが、**別の関数を指していた**なら E3 です。ツールの道筋に**そもそも呼び出しが無く**、効果のある関数が別の入口（CLI やテスト）からだけ呼ばれるなら E6 です（第 49 章）。rails-lens は、192 行の `set()` という呼び出しが `CacheManager.set` と取り違えられたので E3 です。

#### 手作業ではどう使うか

`witness_chain` の各段について、次を確かめます。

1. 本体（またはその段の関数）の中で、その名前の呼び出しはどの行か。
2. その呼び出しの受け手（`.` の左）は何か。組み込みの型（`set`・`dict`・`list`・`bytearray`・`str` など）の値ではないか。
3. 木の中で、その関数を本当に呼んでいる場所はどこか（`grep -rn "cache.set(" .` のように、受け手を付けて探す）。

`error_class` の例: `E3: witness_chain の CacheManager.set は dependency_graph.py:192 の組み込みの set() を名前で取り違えたもの。cache.set の呼び出しは本体に無い（grep で 6 か所、どれも別のツール）`

#### この節のまとめ

E3 は、名前だけの解決で、組み込みのメソッドや別のクラスの同名メソッドを、木の中の効果のある関数と取り違えた誤。v4 の rails-lens（`set()` → `CacheManager.set`）、v3 の `bytearray.append` が例。
直すと誤 clear を作るので、解析器は直さず、判定で E3 として数える。`witness_chain` の各段を受け手で確かめる。

### 51.11 E4 — 受け手の型の読み違いで、動作の種類まで違う（「site の名前だけ違う」との区別）

#### 一言で言うと

解析器が、効果の行の受け手（`.` の左の物）を**別のライブラリの物**と読み違え、その結果 **kind（動作の種類）まで違っていた**ときの誤が E4 です。
site の名前（ライブラリの名前）だけが違って、kind は合っているなら、E4 には**しません**。
そのときは 2 つの問いでふつうに判定し、名前の違いは `note` に書きます。

#### たとえ話 — 電話帳の取り違え

会社の電話帳で、「田中さん（経理部）」に電話するつもりが、「田中さん（営業部）」にかけてしまったとします。

- 用件が「来月の会議の日程の確認」なら、どちらの田中さんでも答えられるかもしれません。部署の名前は違っても、**用件（やること）は同じ**です。これは「名前（部署）だけ違う」場合で、用件は果たせています。
- 用件が「経費の精算」なら、営業部の田中さんは精算できません。部署が違うせいで、**やることそのものが違って**しまいます。これが E4 の場合です。

site の名前は「どの部署か」、kind は「やることの種類」です。
大事なのは、やることの種類が合っているかどうかです。

#### 小さな例 1 — site の名前だけ違う（作例。本書の試験）

```python
 1  import sqlite3
 2  from mcp.server.fastmcp import FastMCP
 3  from mcp.types import ToolAnnotations
 4
 5  mcp = FastMCP("site")
 6
 7
 8  @mcp.tool(annotations=ToolAnnotations(destructiveHint=False))
 9  def purge_old(days: int) -> str:
10      """Delete notes older than the given number of days."""
11      conn = sqlite3.connect("notes.db")
12      conn.execute("DELETE FROM notes WHERE age_days > ?", (days,))
13      conn.commit()
14      return "ok"
```

この作例を、凍結版の解析器（`analyzer-freeze-3`。`git diff analyzer-freeze-3 -- authgap/` が空であることを確かめた）で走査すると、次の効果と矛が出ました（本書の試験）。

| 欄 | 解析器の出力 |
|---|---|
| `site` | `psycopg.Cursor.execute` |
| `kind` | `DB` |
| 位置 | `server.py:12` |
| slot | `sql` の主体は `OP`（定数）、`params` の主体は `MODEL`（引数 `days`） |
| 行の注記 | `contradiction:D2`、`contradiction_reason:D2:db_modify` |

- **1・11 行目**: 使っているのは `sqlite3`（Python に付いてくる SQLite のライブラリ）です。
- **12 行目**: `DELETE` で、既存の行を消します。
- **解析器の出力**: site を `psycopg.Cursor.execute`（PostgreSQL のライブラリ psycopg の関数）と表示しています。受け手 `conn` のライブラリを読み違えています。けれども kind は `DB` で合っています。

判定してみます。
- 到達するか: 12 行は本体の中で、条件はありません。到達します。
- 宣言に反するか: D2 で、`DELETE` は既存の行を消します（手引き 15.2）。反します。
- 判定: **正**。ラベルは**データベース**。
- `note`: 「site は psycopg.Cursor.execute と表示されるが、実際は sqlite3 の接続（server.py:11）。kind=DB は合っている」。

つまり、site の名前の読み違いは、判定にも誤の原因にも影響しません。
手引きの 11.2 節は「解析器の出した理由（site 名や注記）が間違っていても、2 つの問いの答えが『はい』なら正である（例: sqlite3 の接続を psycopg と表示していても、読み取り専用のツールが本当に DB を書き換えるなら正）」と書いています。
練習用サーバ（51.4 節）の 18 行の `SELECT` も、site が `psycopg.Cursor.execute` と表示されます（手引き 20.1 節）。

v4 の実物にも、この形がありました。
ccr の M09・M10 は、`sqlite3.Connection` と注釈された接続を `psycopg.Cursor.execute` と表示していましたが、v4 の記録は「site 名 psycopg.Cursor.execute は受け手の型の読み違いだが kind=DB 自体は合っている」と書いています。
M09・M10 が v4 で誤になった理由は、名前の読み違いではなく、到達しないこと（起動時の初期化）でした。

（出典: 本書の試験（作例を `ch51_work/toy_site` として凍結版で走査）、`docs/drafts/final_judging_guide_draft.md:51-52`（11.2 節）、`:123-124`（手順 C: kind が合っていれば判定には影響しない。note に書く）、`:605`（20.1 の解析器の出力）、`evidence/population_v4/v4_judgments.json` の M09 の note）

#### E3 と E4 の分け方（手引きの見分け方の欄から）

E3 と E4 は、どちらも「解析器が、呼ばれている物を取り違えた」誤なので、混ざりやすい類です。
手引きの見分け方の欄を、そのまま並べます。

- **E3**: 「呼んでいるのは**組み込みのメソッドや別のクラスの同名メソッド**」。これまでの例は、組み込みの `set()` を木の中の `CacheManager.set` に、`bytearray.append` を木の中の `AuditLog.append` に結んだもの。
- **E4**: 「**site のライブラリが違い**、その結果 kind も違う」。

ここから、本書は次のように読みます（**本書の読み方**）。

| 実際に呼ばれているもの | kind | 記号 |
|---|---|---|

| 別のライブラリの関数 | 同じ | 誤の原因にならない（`note` に書き、2 つの問いで判定） |

#### なぜ「site の名前」ではなく「kind」で分けるのか

判定するのは、コードの動作です（手引き 11.2 節）。
site の名前は、解析器が「どのライブラリの関数だと思ったか」という説明にすぎません。
一方、kind は「ファイルに書く」「DB を操作する」「通信する」という**動作の種類**で、宣言に反するかどうか（第 50 章の問い）は、この動作の種類で決まります。
だから、名前が違っても kind が合っていれば、判定の材料（動作）は変わらず、誤の原因にもなりません。
kind まで違えば、解析器が主張した動作そのものが起きていないので、それが誤の原因になります。
もう 1 つの理由は集計です。site の名前の読み違いまで E4 に数えると、判定に影響しなかった読み違いが「誤の原因」の表に混ざり、解析器の誤警報の原因の内訳が、実際より多く見えてしまいます（本書の説明）。

  kind が合っていれば E4 にしません。判定にも影響しません。`note` に書きます。
- **誤解: 「site の名前が違うなら、解析器は間違えたのだから誤」**
  誤かどうかは 2 つの問いで決めます。小さな例 1 のように、名前が違っても正になることがあります。
- **つまずき: E4 を探しに行く**
  E4 はめったに出ない類かもしれません。site の名前の違いに気づいたら、まず「kind は合っているか」を確かめ、合っていれば次に進みます。

#### 手作業ではどう使うか

手順 C（効果の行を開く段）で、次の順に確かめます。

### 51.12 E5 — 子プロセスの標準入力・パイプを、書き込みと読んだ

#### 一言で言うと

ツールが起動した子プロセスに、**標準入力**（子が読む入口）を通してデータを渡しているのを、解析器が「ファイルへの書き込み（FS_WRITE）」と読んだ誤が E5 です。
標準入力に流すこと自体は、ファイルを変えません。

#### たとえ話 — 窓口に書類を手渡す

役所の窓口に書類を手渡したとします。
手渡したこと自体は、役所の台帳を書き換えたことにはなりません。
台帳が書き換わるかどうかは、**受け取った職員が、その書類で何をするか**で決まります。
「この書類の内容を確認するだけです」なら、何も書き換わりません。
「この書類で住所を変更します」なら、台帳が書き換わります。

子プロセスの標準入力に書くのは、窓口に書類を手渡すことにあたります。
ファイルが変わるかどうかは、子プロセス（受け取った職員）が何をするかで決まります。

#### なぜ解析器はこう読むのか

解析器の `_pipe` という部分の説明には、次のように書かれています。
「spawn が `shell=True` か argv0 がインタプリタ カタログに載るとき `EXEC(code_text=v)`、それ以外は `FS_WRITE(content=v)` 相当の情報行」。

つまり解析器は、子の標準入力に書くものを、
- 子がシェルや Python のような**コードを実行するプログラム**なら、コードの実行（EXEC）として、
- それ以外なら、ファイルへの書き込みに**相当するもの**（FS_WRITE の情報行）として、

記録します。
ru-marketplace では、起動するのが `sys.executable` で、これは実行するまで決まらない値なので、解析器はインタプリタだと読めず、FS_WRITE の側に落ちました（v4 の記録）。

これは、わざとの保守的な読み方です。
O41 は、v3 でこの類を直そうとして（D61 G1）、取り消した経緯を記録しています。
インタプリタの一覧に無いコマンドでも、標準入力がコードの実行やファイルの書き込みに届くことがあります（`env python3` や、受け取ったものをファイルに書く `tee` など）。
だから「標準入力への書き込みは、子が何をするか分からないので、書き込みの上界として出しておく」のが、解析器の設計として正しい、と判断されました。
その代償の誤警報を、判定で E5 として数えます。

### 51.13 E6 — 到達しない（E1 以外）

#### 一言で言うと

効果の行が、ツールの呼び出しでは**どの道でも実行されない**のに、解析器が届くとした誤のうち、起動時の初期化（E1）と取り違え（E3・E4）を除いたものが E6 です。
死んだコード、別の入口からだけ呼ばれる関数、定数で閉じた枝、必ず先に抜ける形、の 4 つがあります。

#### たとえ話 — 通行止めの道

カーナビが「この道を通れば目的地に着きます」と案内したのに、その道の入口に、ずっと前から「通行止め」の看板が立っていたとします。
地図の上では道がつながっていても、実際には誰も通れません。
カーナビは地図だけを見ていて、看板を読んでいなかったのです。
E6 は、解析器が「道がつながっている」と読んだのに、実際には通れない場合です。

#### 小さな例 — 必ず例外を投げる関数の後ろ（作例。本書の試験）

```python
 1  import json
 2
 3  from mcp.server.fastmcp import FastMCP
 4  from mcp.types import ToolAnnotations
 5

 7  STATS = {"calls": 0}

10  def _removed(feature):
11      raise ValueError(feature + " was removed in v2")
12

14  def _dump_stats(path):
15      with open(path, "w") as fh:
16          json.dump(STATS, fh)

25      return json.dumps(STATS)
```

凍結版の解析器で走査すると、次の矛が出ました（本書の試験）。

| 欄 | 解析器の出力 |
|---|---|
| `site` / `kind` | `builtins.open` / `FS_WRITE` |
| 位置 | `server.py:15` |
| `entry_lineno` | 24 |
| `witness_chain` | `['_dump_stats']` |
| slot | `path` の主体は `MODEL`（引数 `save_to`） |
| 行の注記 | `contradiction:D1`、`contradiction_reason:D1:fs_write` |

#### 一歩ずつの説明 — 行ごとに

- **10〜11 行**: `_removed` は、**必ず** `ValueError` という例外を投げる関数です。`if` も何も無いので、呼ばれたら毎回ここで止まります。
- **14〜16 行**: `_dump_stats` は、渡されたパスに `'w'` で統計を書きます。
- **19〜20 行**: `get_stats` は読み取り専用と宣言したツールで、引数 `save_to` は既定では空です。
- **22 行**: `save_to` が空でなければ、
- **23 行**: `_removed("save_to")` を呼びます。ここで必ず例外が投げられ、ツールの処理はここで終わります。
- **24 行**: そのため、`_dump_stats(save_to)` は**決して実行されません**。
- **25 行**: `save_to` が空なら、統計を文字列で返すだけです。

解析器は、24 行から `_dump_stats` に降りて 15 行の書き込みを見つけ、矛にしました（`entry_lineno` = 24、`witness_chain` = `['_dump_stats']`）。
けれども、23 行の `_removed` が必ず例外を投げるので、24 行には届きません。
`save_to` を渡しても渡さなくても、15 行は実行されません。
**到達しない**ので誤で、原因は E6（必ず先に抜ける）です。

ちなみに、本書の試験では、`raise` を `_removed` に分けずに 23 行に直接書いた形では、解析器は矛を出しませんでした。
この 2 つの試験からは、解析器は同じ関数の中の `raise` の後ろの文は効果として数えないが、呼んだ関数が必ず例外を投げることまでは使っていない、と読めます（2 つの試験からの推測で、解析器のコードで確かめたものではありません）。

（出典: 本書の試験（`ch51_work/toy_e6`）、`docs/drafts/final_judging_guide_draft.md:229-239`（14.2 節））

#### E6 の 4 つの形

| 形 | 見分け方 | 例 |
|---|---|---|
| 死んだコード | 効果のある関数が、どこからも呼ばれていない | 古い関数が残っているだけ |
| 別の入口だけ | 効果のある関数が、ツールの道筋からは呼ばれず、CLI・テスト・スクリプトからだけ呼ばれる | `cli.py` の `main` だけが `export_all()` を呼ぶ |
| 定数で閉じた枝 | `if False:`、`if DEBUG:`（`DEBUG = False` が定数で、どこでも書き換えない）の中 | デバッグ用のログの書き込み |
| 必ず先に抜ける | 効果の前に必ず `return` / `raise` する | 上の作例 |

表の読み方: たとえば 2 行目は「効果のある関数がツールの道筋からは呼ばれておらず、コマンドラインの入口やテストからだけ呼ばれるなら、ツールの呼び出しでは届かない。E6」と読みます。
「別の入口からしか呼ばれない」ことは、関数名で木の中を grep して、呼び出し元をすべて見て確かめます（手引き 14.2）。
4 つの形のくわしい見分け方と作例は、第 49 章 49.2 節で見ました。

#### なぜ E1・E3 と分けるのか

E1・E3・E6 は、どれも「到達しない」で落ちる誤です。
けれども、解析器のどんな弱点から来たかが違います。

| 記号 | 解析器の弱点 | 論文での扱い |
|---|---|---|
| E1 | 各呼び出しを、サーバの状態（起動時に済んだこと）を仮定せずに読む設計 | D67 の 2 で、設計の限界として件数を報告すると決めてある |
| E3 / E4 | 呼び出しの解決（名前だけ・受け手の型） | O41〜O43 の既知の誤りの類 |
| E6 | 道の途中の「通れない」理由（必ず抜ける、定数の枝、別の入口）を読み切らない | それ以外の到達しない形 |

表の読み方: たとえば 1 行目は「E1 は、解析器が起動時の初期化を考えない設計から来る誤で、D67 の 2 で件数を報告すると決めてある」と読みます。
分けて数えておけば、論文の限界の節で、弱点ごとに件数を示せます。

（出典: `docs/decisions.md:3773-3778`（D67 の 2）、`docs/final_evaluation_procedure.md:1400-1402`（24.2 節の限界））

#### よくある誤解・つまずき

- **誤解: 「`if` の中の効果は、条件しだいだから到達しない」**
  条件をモデルの引数や外の状態で満たせるなら、「条件つきで到達する」です（第 49 章 49.3 節）。E6 にするのは、どの呼び出しでも通れないと確かめたときだけです。
- **誤解: 「テストから呼ばれているから、到達する」**
  テストは、サーバとしてツールが呼ばれる場面ではありません。テストからだけ呼ばれるなら「別の入口だけ」で E6 です。
- **つまずき: 「到達しない」の証拠を書かない**
  到達しないとすると、解析器が出した違反を「無い」と言うことになります。間違えると、人の判定が誤 clear を作ります。grep の結果、定数の定義の行、必ず抜ける行など、届かない証拠を `evidence` に書きます（第 49 章）。
- **つまずき: 間接の呼び出しを見落とす**
  `getattr(obj, name)()`、辞書に入れた関数、デコレータでの登録などは、関数名の grep では見つかりません。間接の呼び出しを疑う手がかりがあれば、たどります。読み切れなければ E6 にせず**不明**です。

#### 手作業ではどう使うか

`error_class` には、4 つの形のどれかと、その証拠の要点を書きます。

例: `E6: 必ず先に抜ける。server.py:23 の _removed() は :11 で必ず ValueError を投げるので、:24 の _dump_stats に届かない`

#### この節のまとめ

E6 は、起動時の初期化（E1）と取り違え（E3・E4）を除いた「到達しない」誤。死んだコード・別の入口だけ・定数で閉じた枝・必ず先に抜ける、の 4 つの形。
本書の試験では、呼んだ関数が必ず例外を投げる形で、解析器は届かない書き込みを矛にした。届かない証拠を `evidence` に書く。

### 51.14 E7 — モデルが決められないのに、決められるとした

#### 一言で言うと

起動するコマンド（や実行するコード）を、解析器は「モデルが決められる」と読んだのに、実際には**コマンドは固定**で、モデルの値は安全に加工された引数として渡されるだけだったときの誤が E7 です。
典型は、固定のコマンドに `shlex.quote` した値だけを渡す形です。

#### たとえ話 — 注文用紙の「品名」欄

レストランの注文用紙に、「本日のスープ（味: ____）」という欄があるとします。
お客さんは、味の欄に好きなことを書けます。
けれども、何を書いても、出てくるのは「本日のスープ」です。
味の欄に「ステーキ」と書いても、ステーキは出てきません。厨房は「ステーキ味のスープ」として読むだけです。
お客さんが決められるのは味だけで、料理そのものは決められません。

`shlex.quote` は、お客さんが書いた文字を、必ず「味の欄」の中に閉じ込める仕組みにあたります（第 9 章 9.6 節）。

#### 小さな例 — v3 の clawking（実物）

v3 の M32・M33 は、clawking というサーバの `op_get`・`op_get_raw` × `subprocess.run` × D1 の組で、解析器は理由 `spawn_model`（起動するコマンドをモデルが決められる）で矛にしていました。

```
 95  def _run(cmd: str | list, timeout: int = 60, env_extra: dict | None = None, cwd: str | None = None) -> str:
 96      """Run a subprocess and return combined output."""
 97      env = {**os.environ}
 ..
101          r = subprocess.run(
102              cmd, shell=isinstance(cmd, str),
103              capture_output=True, text=True, timeout=timeout,
104              env=env, cwd=cwd or str(WORKSPACE),
105          )
 ..
427  @mcp.tool(annotations={"title": "1Password Get", "readOnlyHint": True, "openWorldHint": False})
428  async def op_get(item: str, field: str = "password") -> str:
 ..
433      env_extra = _load_op_env()
434      result = _run(
435          f"op item get {shlex.quote(item)} --fields {shlex.quote(field)} --vault '__YOUR_1PASSWORD_VAULT__'",
436          env_extra=env_extra, timeout=15,
437      )
```

（出典: `corpus/v3-muduiclaw__clawking/workspace/mcp-bridge/server.py:95-105,427-437`、`evidence/population_v3/v2_judgments.json` の M32・M33（category `spawn_quoted_fixed_command`、note「固定の `op item get` に shlex.quote した値だけ。読み取り」））

#### 一歩ずつの説明 — 行ごとに

- **95 行**: `_run` は、コマンドを受け取って子プロセスで実行する手伝いの関数です。
- **101〜102 行**: `subprocess.run` で実行します。`cmd` が文字列なら `shell=True`（シェルに解釈させる）になります。
- **427〜428 行**: `op_get` は、読み取り専用（`readOnlyHint: True`）と宣言したツールで、引数 `item`（項目の名前）と `field`（欄の名前）をモデルが決めます。
- **435 行**: 実行する文字列を作ります。先頭の `op item get` は固定です（`op` は 1Password というパスワード管理の道具のコマンドで、`item get` は項目を取り出す命令です）。モデルが決める `item` と `field` は、`shlex.quote` で引用符に包まれてから、引数の位置に入ります。
- **434〜437 行**: その文字列を `_run` に渡して、シェルで実行します。

解析器から見ると、シェルに渡す文字列（slot `shell_string`）に、モデルが決める値（`item`・`field`）が混ざっています。
だから、「シェルの文字列をモデルが決められる」と読んで、`spawn_model` の矛にしました。
けれども、`shlex.quote` で包まれた値は、シェルにとって必ず 1 つの引数です。
たとえばモデルが `item` に `x; rm -rf ~` と書いても、`'x; rm -rf ~'` という 1 つの引数として `op` に渡り、`rm` は実行されません。
モデルは、**起動するコマンドを選べません**。起動されるのは、いつも `op item get` です。

そこで、手引きの 15.1 節の SPAWN の行（コマンドが定数なら、そのコマンドが実際に何をするかを調べる）に従って、`op item get` が何をするかを考えます。
v3 の判定は、これを「読み取り」としました。
環境を変えないので D1 に反しません。
誤で、原因は E7 です。

（出典: `docs/drafts/final_judging_guide_draft.md:311`（15.1 の SPAWN の行）、`:435`（E7 の行）、`docs/population_v3.md:87`、`docs/open_questions.md:1063`（O41））

#### E7 にする前に確かめること — 固定のコマンドが環境を変えるなら正

E7 は、「モデルが決められない」と分かったうえで、**さらに**「その固定のコマンドが宣言に反しない」と分かったときの誤です。
「モデルが決められない」だけでは、誤になりません。

| 固定のコマンドの動作 | 判定 |
|---|---|
| 読み取りだけ（`op item get`、`git log` など） | 誤（E7） |
| 環境を変える（`git commit -m <引用した値>`、`rm <引用したパス>` など） | **正**（モデルがコマンドを選べなくても、固定のコマンドそのものが環境を変える） |
| 何をするか調べても分からない | 不明 |

表の読み方: たとえば 2 行目は「固定の `git commit` に、モデルの値を `shlex.quote` して渡すツールは、モデルがコマンドを選べなくても、`git commit` 自体がリポジトリを書き換えるので、D1 には反する。正」と読みます。
このとき、解析器が付けた理由（`spawn_model`）は外れていますが、2 つの問いの答えが「はい」なので正です（手引き 11.2 節）。

#### もう 1 つの注意 — 引用は「選択肢」までは防がない

`shlex.quote` が防ぐのは、シェルの区切り（`;` や `|` など）で**別のコマンド**を足されることです。
けれども、`-` で始まる値を、そのコマンドの**選択肢**（オプション）として読ませることまでは防ぎません。
たとえばモデルが `item` に `--help` と書けば、`op` は `'--help'` を 1 つの引数として受け取り、選択肢として解釈するかもしれません。
だから、E7 にする前に、「そのコマンドは、引数の位置に入る値（選択肢を含む）しだいで、環境を変える動作に変わりうるか」も見ます。
原理 3-a（モデルが決める値は取りうる値の全体で考える）を、ここにも当てるということです。
変わりうるなら、E7 にはできません（その動作で判定するか、分からなければ不明）。

（出典: 第 9 章 9.6 節（`shlex.quote` の定義）、`docs/contradiction_principles.md` の原理 3）

#### なぜ解析器を直さなかったのか

O41 は、この類を「一般に正しい直し方が無いので直さない誤り」の 1 つとして記録しています（v3 で誤 2）。
「`shlex.quote` で包んだ値はモデルが決められない」と一律に読むと、上の「選択肢」のように、包んでもモデルが動作を変えられる場合を見落とし、誤 clear を作るおそれがあります。
だから解析器は保守的に「モデルが決める」と読み、判定で E7 として数えます。
（O41 の文には、直さない理由の細かい説明は書かれていません。上の「選択肢」の話は本書の説明です。）

#### よくある誤解・つまずき

- **誤解: 「`shlex.quote` があれば、いつも E7」**
  固定のコマンドが環境を変えるなら正です。選択肢で動作が変わりうるなら、E7 にできません。
- **誤解: 「E7 と E8 は同じ（どちらも宣言に反しない）」**
  落ちる問いは同じですが、解析器の読み違いの中身が違います。E7 は「主体（誰が決めるか）の読み違い」、E8 は「その動作が宣言に反するかの読み違い」です。手引きの表は、`shlex.quote` の形を E7 の例に挙げています。
- **つまずき: D3 の組と混ぜる**
  v3 で判定したのは D1 の組です。同じツールが D3（`openWorldHint: False`）も宣言していますが、D3 の組は別の組として、15.3 節の問いで判定します。

#### 手作業ではどう使うか

理由が `spawn_model`（や `exec_model`）の組で、次を確かめます。

1. 起動する文字列や引数の列のうち、**コマンドの位置**（先頭）をモデルが決められるか。
2. モデルの値は、`shlex.quote` や引数の列（`["op", "item", "get", item]` のような形）で、引数の位置に閉じ込められているか。
3. 固定のコマンドは、引数（選択肢を含む）しだいで環境を変えうるか。
4. 変えない → E7。変える → 正。分からない → 不明。

`error_class` の例: `E7: server.py:435 のコマンドは固定の op item get で、item と field は shlex.quote で引数の位置に閉じ込められる。op item get は読み取り`

#### この節のまとめ

E7 は、モデルがコマンドを選べないのに選べると読んだ誤。固定のコマンドに `shlex.quote` した値だけを渡す形（v3 の clawking）が例。
E7 にするのは、固定のコマンドが宣言に反しないと確かめたときだけ。引用は選択肢までは防がないので、そこも見る。

### 51.15 E8 — 宣言に反しない（E2 以外）

#### 一言で言うと

到達はするが、その動作が**宣言に反しない**と分かった誤のうち、E2（D2 の自分の一時ファイルの後始末）・E5・E7 の形を除いたものが E8 です。
手引きは、冪等な追記（D4）、`flock` のための `'a'`（D4）、読み取りのモード、接続単位の設定を例に挙げています。

#### たとえ話 — 「同じ注文を 2 回しても 1 つしか届かない」店

ネットのお店で、「この注文ボタンは、同じものを 2 回押しても、2 つ目は届きません」と書いてあるとします。
本当にそうなっているかを確かめるには、ボタンの仕組みを見ます。
「押すたびに 1 つ届く」仕組みなら約束違反ですが、「すでに注文済みなら何もしない」と確かめてから注文する仕組みなら、約束は守られています。
解析器は「注文ボタン（追記）がある」ことだけを見て約束違反としがちですが、人は「押す前に確かめているか」まで見ます。

#### 小さな例 1 — 冪等な追記（v4 の ccr、実物）

v4 の E00（id）は、ccr の `gcc_todo_update` × `open('a')` × D4 の組でした。
`gcc_todo_update` は `idempotentHint=True` と宣言しています。

```

 79          content = ""
 80          if os.path.isfile(gitignore_path):
 81              content = self._read_file(gitignore_path) or ""
 82          if ".ccr/" not in content and ".ccr" not in content:
 83              with open(gitignore_path, "a", encoding="utf-8") as f:
```

- **79〜81 行**: `.gitignore` があれば、中身を読みます。
- **82 行**: 中身に `.ccr/` も `.ccr` も無いときだけ、

だから最終評価の規則では、到達の理由では誤にならず、冪等の理由だけで誤（E8）になります。
手引きの 20.2 節も「誤 E8（v4 では E1 も重なる）」と、この読み方を書いています。

#### 小さな例 2 — `flock` のための `'a'`（v3 の helios、実物）

v3 の E00（id）は、helios-mcp の `get_drift_report` × `builtins.open` × D4 の組で、v3 の判定は「`flock` のために `"a"` で開くだけで何も書かない」でした。

### 51.16 E9 — その他と、分類に迷ったとき

#### 一言で言うと

E1〜E8 のどれにも当てはまらない誤、または**どれにするか迷う**誤は、E9 にして、説明を自由な文で書きます。

#### たとえ話 — アンケートの「その他（　　）」

アンケートの選択肢に「その他（　　）」の欄があると、どれにも当てはまらない答えを、無理にどれかに入れずに済みます。
括弧の中に書いてもらえば、後で読んで、新しい選択肢を作るべきかを考えられます。
E9 は、誤の原因の「その他（　　）」です。

#### 小さな例 — E9 にする 2 つの場合（作例）

**場合 1: どの類にも当てはまらない**

たとえば次のような形です（本書の作例。v3・v4 で出たものではありません）。
ツールの宣言（`readOnlyHint=True`）がソースに書かれているが、サーバの起動の途中で、別のモジュールがそのツールの宣言を `readOnlyHint=False` に書き換えてから配っている、と原ソースを読んで分かったとします。
解析器はソースに書かれた宣言で D1 の矛を出しましたが、クライアントに配られる宣言は D1 ではありません。
これは、到達や宣言に反するかの問題ではなく、「照らした宣言そのものが違う」という誤です。
E1〜E8 のどれにも当てはまらないので、E9 にして説明を書きます。

| 欄 | 書き方の例 |
|---|---|
| `error_class` | `E9: 宣言の読み違い。ソースの readOnlyHint=True（tools.py:20）は、起動時に registry.py:55 で False に書き換えられてから配られる` |
| `note` | `E1〜E8 のどれにも当てはまらない。到達はする` |

**場合 2: 2 つの類のどちらとも言える**

たとえば、効果のある関数が、ツールの道筋の中の呼び出しから名前だけで結ばれていた（E3 の形）が、同時に、その関数は別の入口からだけ呼ばれる死んだコードでもあった（E6 の形）とします。
第 49 章は、「ツールの道筋にある呼び出しが、別の関数を指していた」なら E3、「ツールの道筋にそもそも呼び出しが無く、別の入口からだけ呼ばれる」なら E6、と分けています。
それでも決めきれないときは、E9 にして、両方の見方を説明に書きます。

（出典: `docs/drafts/final_judging_guide_draft.md:437-439`（E9 と「分類に迷ったら E9 にして説明を書く」））

#### 一歩ずつの説明 — 手引きの規則

手引きの 17 節の最後には、次の 1 文があります。

> 分類に迷ったら E9 にして説明を書く。**分類は集計で「誤の原因の内訳」になり、論文の限界の節の材料になる。**

- **「分類に迷ったら E9」**: 迷った件を、どれか近い類に入れません。入れると、その類の件数に、迷った件が混ざります。
- **「説明を書く」**: E9 だけでは、何の誤か分かりません。集計のときに E9 の説明を読み、どんな誤が多かったかを報告します。
- **「誤の原因の内訳」「論文の限界の節の材料」**: 51.17 節で見ます。

#### なぜ迷ったら E9 なのか

1. **ほかの類の件数を汚さないため**: 迷った件を、近そうな E3 や E8 に入れると、その類の件数に「本当にそうかは分からない件」が混ざります。論文の限界の節で「名前だけの解決による誤警報は X 件」と書くとき、その X が信用できなくなります。
2. **黙って片方に倒さないため**: CLAUDE.md の規則 4（解決できなかったものは不明として記録する。黙って安全側に倒さない）と同じ考え方です。誤の原因の分類でも、決めきれないものは決めきれないと記録します。
3. **後で見直せるため**: E9 に説明を書いておけば、判定が終わった後に E9 の件をまとめて読み、「この形が多かった」と報告できます。2 人目の判定者が用意できた場合（D70 の 8 で保留）にも、迷った件として渡せます。

（出典: `docs/drafts/final_judging_guide_draft.md:439`、`CLAUDE.md`（規則 4）、`docs/decisions.md:3876-3882`（D70 の 8））

#### 手引きが決めていないこと — 原因が 2 つ重なるとき（本書の指摘。**未決**）

v4 の判定では、1 つの誤に、原因が 2 つ重なることがありました。
- v4 の ccr の M09・M10: 到達しない（起動時の初期化）＋ 受け手の型の読み違い（sqlite3 を psycopg と表示。kind は合っている）。

けれども、最終評価のデータで、たとえば「lifespan の初期化の中の、冪等な追記」のように、**E1 と E8 の両方が本当に当てはまる**誤が出るかもしれません。

手引きの下書きは、`error_class` に記号を 1 つ書くのか、`;` で並べるのかを決めていません（条件の種類 `condition_type` については「全部を `;` で並べる」と決めています）。

決まらないまま出会ったら、少なくとも、両方の原因を `error_class` の説明の文に書き、`note` に「原因が重なる」と書いておけば、後でどちらの集計の形にも直せます。

（出典: `docs/drafts/final_judging_guide_draft.md:170`（`condition_type` は `;` で並べる）、`:173`（`error_class` の欄）、`evidence/population_v4/v4_judgments.json` の M09・M10・E00）

#### よくある誤解・つまずき

- **誤解: 「E9 は手抜きの記号」**
  違います。迷った件を無理に分類しないための、正直な記号です。説明を書けば、情報は失われません。
- **誤解: 「E9 が多いと、手引きが悪かったことになるので、なるべく使わない」**
  E9 が多ければ、それは「用意した類で分けきれない誤が多かった」という事実です。論文の限界の材料になります。
- **つまずき: 不明と E9 を混ぜる**
  E9 は「誤」の原因の記号です。判定そのものが決められないなら、誤ではなく**不明**です（第 52 章）。

#### 手作業ではどう使うか

1. E1〜E8 を順に当て、どれにも当てはまらなければ E9。
2. 2 つ以上に当てはまって決めきれなければ E9 にし、両方の見方を書く。
3. 説明は「何の誤か」「なぜ E1〜E8 に入らないか」を 1〜2 文で書く。

#### この節のまとめ

E9 は、E1〜E8 に当てはまらない誤、または迷う誤の記号で、必ず説明を書く。迷った件を近い類に押し込まない。
原因が 2 つ重なるときの書き方は手引きに無く、未決（本書の指摘）。

### 51.17 印は集計でどう使われるか — 2 つの内訳の表と論文の限界
