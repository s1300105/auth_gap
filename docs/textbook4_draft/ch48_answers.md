### 第 48 章

この章の演習と確認問題は、判定の手引きの下書き（`docs/drafts/final_judging_guide_draft.md`。**下書き・未承認**）の 11〜13 節、`docs/decisions.md` の D67〜D70、`docs/contradiction_principles.md` の §6・§7 に基づきます。
問題の作例は本書の作例で、答えは手引きの規則を当てた本書の考え方の例です。
v4 の判定は本記録者（AI）のもので、正解ではありません。v4 の数字は論文に使いません（D66 の 5）。

#### 演習 48-1（到達は「はい」、宣言に反するかは「決められない」）

(1) **到達する**。条件の種類は **なし** です。
- 6〜9 行の道筋に `if` も、先に抜ける `return` もありません。呼び出しのたびに、9 行で引数 `text` を子の標準入力に流し込みます。
- `CONVERTER` は 1 行で環境変数 `DOC_CONVERTER`（運用者の設定）から決まりますが、それは「どのプログラムが起動するか」を変えるだけで、9 行に届くかどうかは変えません。

(2) **不明**。5 行の判定表の **5 行目**（到達: はい、宣言に反する: 決められない）に当たります。
- 子の標準入力への流し込みは、それ自体はファイルを変えません。D1 に反するかは、**子がそれを受けて何をするか**で決まります（手引き 15.1 の迷いやすい形、`docs/drafts/final_judging_guide_draft.md:324`）。
- `conv` の動作は、木の中にも文書にも無く、30 分調べても決められませんでした。手引きの目安（20〜30 分調べても決められなければ不明。19 節）に当たります。
- 黙って正（念のため）や誤（たぶん変換だけ）に倒さないのが、この研究の約束です（CLAUDE.md の規則 4、原理 2-a）。

(3) 必ず書く欄: `verdict`（不明）・`reachable`（はい）・`violates`（決められない）・`unknown_reason`・`evidence`・`minutes`。
到達するので、`condition_type`（なし）と `condition`（なし）も書いておくと、後で数え直すときに困りません（本書の勧め）。

例:

```text
unknown_reason: 子プロセス conv（1 行の環境変数 DOC_CONVERTER、既定 /opt/conv/bin/conv）が、標準入力の文章で何をするか（ファイルを書くか）が、木の中にも文書にも無い（30 分調べた）
evidence: server.py:4 convert_text（readOnlyHint=True）→ server.py:6-8 Popen([CONVERTER, "--stdin"], stdin=PIPE, ...) → server.py:9 communicate(input=text) で、呼び出しのたびに引数 text を子の標準入力に流す。流し込み自体はファイルを変えない。子の動作は確かめられない。
note: 木の中を conv と DOC_CONVERTER で grep したが、説明や既定の設定ファイルは無かった。
```

(4) `violates` が「はい」になり、表の **1 行目**（はい・はい）で **正** に変わります。
- `evidence` に、見つけた文書の場所（URL など）と、該当する文（「結果を `~/.conv/history` にも追記する」）を足します（第三者が同じ文書を開けるように）。
- `unknown_reason` は空にします。
- `write_target` は、第 51 章の書き込み先の種類の定義で決めます。`~/.conv/history` をツールの動作で読み返すかが分からなければ、「その他・不明」にして、事例を `note` に書きます（手引き 16.2 の「決められないときは『その他・不明』」）。
- 調べれば分かったものは、不明にしません。不明は「調べても決められない」ときだけです。

(5) 手引きの表の **4 行目**（到達: 決められない、宣言: —）の字義どおりなら、**不明**です。
本書は 48.2 節で、次のように指摘しました。
- 「両方が『はい』のときだけ正」という規則からは、正にならないことだけは確かです。
- けれども、手引きはこの組み合わせ（到達は決められない・宣言には反しない）を明示していません。
- 承認の前に学生が確かめるとよい点です（**未決**）。決めるまでは不明にし、`note` に「宣言には反しない形」と書いておけば、後からどちらの読み方でも数え直せます。

#### 演習 48-2（`locations` が 3 つあり、1 つ目で正が見つかった）

(1) **必要はありません**。手引きの手順 G は「全部を読むのが大変なら、1 つ正が見つかった時点で止めてよい（止めたことを `note` に書く）」としています（`docs/drafts/final_judging_guide_draft.md:157`）。
止めるなら、次のように書きます。

```text
verdict: 正 / reachable: はい / violates: はい
condition_type: 運用者の設定
condition: 環境変数 APP_TRACE が設定されているとき（app.py:40 の if os.environ.get("APP_TRACE"):）
note: 位置 3 つ。app.py:40 で正。app.py:88 と util.py:15 は読んでいない（正が見つかったので止めた）。
```

(2) 見つけた正の条件「運用者の設定」は、運用者が決める条件で、いちばん強い側です。
- 条件の種類は、**正にできる位置のうち条件の一番弱いもの**を記録します（D68 の 1、手順 G）。弱い順は「なし」→ 運用者が決めない条件 → 運用者が決める条件です。
- 残りの位置に「なし」や「引数」などの位置があれば、記録する条件の種類が変わり、この組を (B)（運用者が決める条件でしか届かないものを除いた数）や (C)（条件なしで届くものだけの数）に数えられるようになります。
- 止めてしまうと、本当は (B)・(C) に入る組を入れずに数えることになります。手引きも「条件つきの位置で正が見つかっても、条件なしの位置がありそうなら、そこまで読むと (C) の数が正しくなる」と書いています（`docs/drafts/final_judging_guide_draft.md:158-160`）。

(3) `condition_type` は **`なし`** です。この組は (A)・(B)・(C) のすべてに数えます。
`note` には、たとえば「位置 3 つ。util.py:15 で正（条件なし。毎回 open(LOG, "a")）。app.py:40 も正（運用者の設定 APP_TRACE）。app.py:88 は …（読んだ結果）。一番弱い条件の util.py:15 で記録」と書きます。

(4) **全部の位置を読み、どの位置も「到達しない」か「宣言に反しない」と確かめた後**です。
- 誤は「正の位置が 1 つも無い」という主張なので、全部を見ないと決まりません。手引きも「誤にするときは全部を読む」と決めています。
- 途中で誤と決めると、読まなかった位置に本当の違反があったとき、解析器が正しかったのに「誤警報」と記録することになり、精度を低く見せます。
- 正の位置が無く、決められない位置が残るなら、組は不明です。
- `note` には、位置ごとの答え（たとえば「app.py:40 は lifespan で先に初期化され到達しない（E1）」）を書きます。

#### 演習 48-3（悪い `evidence` を良い `evidence` に書き直す）

良い `evidence` には、48.12 節で分解した 4 つの要素（出発点・各段の位置・効果の行・判定に効く事実）を入れます。

**(a) 作例 1 の `ask` × `os.makedirs` × D1（正）**

```text
evidence: server.py:35 ask（readOnlyHint=True）→ server.py:38 log_question(q) → server.py:20 os.makedirs(LOG_DIR, exist_ok=True)（LOG_DIR は 7 行の ~/.toy/logs）。道筋に if は無く、呼び出しのたびに実行され、まだ無ければディレクトリを作る。
note: 位置 2 つ（14・20）。20 行で正。14 行は get_store の if _store is None:（13 行）の中で、lifespan の app_lifespan（26-28 行。31 行で FastMCP に渡す）が受付の前に get_store() を呼ぶので、ツールの呼び出しでは到達しない（E1）。20 行は exist_ok=True で、作るのは無いときだけ（条件の種類は道筋の条件だけを数える読み方で「なし」。48.9 節の注意、未決）。
```

ほかの欄は、`reachable` はい・`condition_type` なし・`violates` はい・`write_target` ログ です。
ログのためのディレクトリの作成を「ログ」にするのは、手引きの 20.2 節が、同じ形の v4 の wikimind（M06。活動ログのディレクトリの作成）を「種類はログ」としているのに合わせた、本書の考え方の例です（`docs/drafts/final_judging_guide_draft.md:639`）。

**(b) 作例 5a の `lookup` × `builtins.open` × D1（誤）**

```text
evidence: server.py:14 lookup（readOnlyHint=True）→ server.py:17-18 if not ENABLE_CACHE: return text → server.py:19 の _save_cache（9 行の open(…, "a")）には届かない。ENABLE_CACHE は 5 行の定数 False で、木の中を ENABLE_CACHE で grep しても代入は 5 行だけ（global 宣言も、別のモジュールからの書き換えも無い）なので、17 行の条件はいつも真で、18 行で必ず抜ける。
error_class: E6: 定数 False の ENABLE_CACHE により 18 行で必ず抜け、19 行の _save_cache に届かない
```

ほかの欄は、`reachable` いいえ です。
「到達しないので誤」だけでは、なぜ到達しないのか（どの行で抜けるのか、定数が書き換えられないことをどう確かめたのか）が分からず、第三者が確かめられません。

ほかの欄は、`reachable` はい・`condition_type` 引数・`violates` はい・`write_target` 利用者のファイル（モデルが指定した場所のファイル。手引き 16.1 の 3）です。

#### 確認問題 48-1

- 組の 5 つの要素は、**木・ユニット・site・kind・宣言**です（手引き 11.1、`docs/drafts/final_judging_guide_draft.md:33`）。
- 作例 1 の 20 行は site が `os.makedirs`、21 行は site が `builtins.open` です。kind はどちらも `FS_WRITE` ですが、**site が違うので別の組**になります。組は (site, kind) ごとにまとめるので、同じ関数の隣の行でも、site が違えば別の行として判定表に入ります。
- `contradictions.json` の 1 行の `relpath`・`lineno` は**代表の位置**で、組の位置のうち (relpath, lineno) の対がいちばん小さいものです。`locations` は、その組の**矛の行がある位置の全部**です（不や内の位置は並びません）。判定では、代表だけでなく `locations` の各位置を確かめます（`scripts/scan_v2.py:301-302`）。

#### 確認問題 48-2

- 判定の目的は、**解析器の主張が、現実のコードの動作として当たっているか**を確かめることです。だから、site の名前や理由のような解析器の説明が間違っていても、2 つの問い（到達するか・宣言に反するか）の答えが「はい」なら正です（手引き 11.2、`docs/drafts/final_judging_guide_draft.md:51-52`）。
- 作例 2 では、11 行の接続は `sqlite3` なのに、site は `psycopg.Cursor.execute` と表示されました。site の名前は、受け手の型の候補を並べ替えた先頭から作るためです（第 13 章 13.6 節）。けれども、13 行の動作（DB に `DELETE` を送って行を消す）は同じで、kind（`DB`）も合っています。13 行は毎回届き、読み取り専用のツールが DB の行を消すので、正です。名前の違いは `note` に書きます。
- site の名前の違いが判定に影響するのは、受け手の型の読み違いの結果、**動作の種類（kind）まで違う**ときです。そのときは、解析器の言う操作が実際には起きていないので、誤で、原因は **E4** です（`docs/drafts/final_judging_guide_draft.md:432`）。

#### 確認問題 48-3

- 「この程度は違反と言えない」と感じても、**自分の感覚では判断しません**。D1 の問い「呼び出しの後に残る何かを変えるか」に事実で答えます。ログファイルは呼び出しの後にも残るので、採った原理 1-i-b（呼び出しを越えて残るものはすべて環境）により、**D1 に反します**。届くなら、正です（手引き 11.3）。
- **D67 の 1**: 重大度の重みは付けない。主指標の精度は今の原理の 1 本だけにし、正の各件に「書き込み先の種類」を事実のラベルとして記録して、内訳を表で示す。軽重の判断は読み手に任せる（`docs/decisions.md:3767-3772`）。
- 理由の 3 つ:
  1. 研究の問いは「宣言は正しいか」で、「危ないか」ではない。
  2. 重みの線引きには正解が無い。実世界でも割れている（OpenAI の提出ガイドはログを書くツールを `readOnlyHint: false` にせよと言い、RFC 9110 はアクセスログへの追記を「安全」に含める）。
  3. v4 の結果を見た後の区別で数字を作り直すと、恣意的に見える。
- 違反の軽い・重いは、**書き込み先の種類のラベル**（`write_target`。この例なら「ログ」）で表します。正誤には持ち込みません。`note` には、感想ではなく事実（「`access.log` に 1 行追記。ツールの動作では読み返さない」など）を書きます。

#### 確認問題 48-4

- `evidence` は、**ファイルと行の連なり**と、**各段で何が起きるかを 1〜3 文**で書きます。**判定を見ていない第三者が、その行を開けば同じ結論に着ける**ように書くと決められています（手引き 13 の手順 H、`docs/drafts/final_judging_guide_draft.md:176`、`:188-189`）。
- 悪い例「open で書いているので正」には、**どの行か**（ファイルと行）と、**どう届くか**（ツールの入口から効果までの道筋と条件）がありません。だから、第三者が確かめられません。
- **D67 の 4** は、判定を学生 1 人で行うと決めました。2 人目の判定者は用意できず（2 人目は D70 の 8 で保留）、判定者間の一致（κ）に依存する主張はしません。その代わりに、第三者が後から検証できるように、判定の根拠（ファイルと行）を全件残して公開し、判定の手引きを先にコミットします（`docs/decisions.md:3783-3786`）。2 人目による確かめが無い分、**誰でも後から確かめられる `evidence` が、判定の信頼性の担保**になります。
