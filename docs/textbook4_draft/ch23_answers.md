### 第 23 章

この章の演習は、説明のための作り話と、本書の作例を使っています。
作例の解析器の出力は、本記録者が repo から `git archive` で取り出した 3 つの版（直す前の `289624c`、O31 の最初の実装を含む `7ea8bac`、凍結版 `analyzer-freeze-3`）で、作業用の場所で走査して確かめたものです（2026-10-01。repo は変えていません）。

#### 演習 23-1（順番の証拠）

**(1)** 6 段階の順番は「① 規則 → ② テスト → ③ 実装」です。
この人は「③ 実装（10:00）→ ② テスト（10:30）→ ① 規則（11:00）」と、**ちょうど逆の順**でコミットしています。
また、テストを「直す前の解析器で落ちる」ことを確かめていません（直した後に書いたので、確かめようがありません）。

**(2)** 10:30 のテストは、「直した解析器が、直した解析器と同じ答えを出す」ことしか確かめていません。
期待値を、直した解析器の出力から写したからです。
もし直し方が間違っていても（直しすぎて本当の効果まで消していても）、テストはその間違った答えを「正解」として固定してしまいます。
つまり、正しさについては何も確かめていません。
23.5 節の期待値ファイルの「いずれも解析器の出力ではない」という注意は、まさにこれを防ぐためのものです。

**(3)** 読んだ人は、「実装してみて都合のよかった結果に合わせて、テストの答えと規則を後から書いたのではないか」と疑います。
コミットの日時がこの順で残っているので、**後から晴らすことはできません**。
できるのは、規則とテストを書き直して、正しい順（規則 → テスト → 直す前に落ちることの確認 → 実装）でやり直すことです。
やり直すなら、最初の順番の誤りも記録に残します（隠さない）。

#### 演習 23-2（反例のテストを考える）

**(1)** 「書き込みを数えないのが正しい」呼び方の例:

```python
@mcp.tool(annotations={"readOnlyHint": True})
async def omit(text: str) -> str:
    save(text)          # path を省略 → 既定値 None → 4 行目で return
    return "ok"
```

`path` を省略しているので既定値の `None` が使われ、4 行目の `if path is None:` が必ず真になり、5 行目で `return` します。6 行目には届きません。
`save(text, None)`（リテラルの `None` を渡す）でも同じです。

**(2)** 「書き込みを数えるのが正しい（変えてはいけない）」呼び方の例:

```python
@mcp.tool(annotations={"readOnlyHint": True})
async def model_path(text: str, path: str) -> str:
    save(text, path)    # path はモデルが渡す値。None とは限らない
    return "ok"


@mcp.tool(annotations={"readOnlyHint": True})
async def via_kwargs(text: str, path: str) -> str:
    opts = {"path": path}
    save(text, **opts)  # 辞書を ** で展開して渡す。path は省略されていない
    return "ok"
```

- 1 つ目: `path` はモデルが渡す値なので、`None` 以外を渡せば 6 行目に届きます。
- 2 つ目: `**opts` で `path=path` を渡しています。見た目は `save(text, ...)` で、第 2 引数を位置で渡していないので、解析器が「`path` は省略された」と読み違えやすい形です。実際には `path` は渡されていて、6 行目に届きます。

ほかにも、`*args` で渡す形、`asyncio.to_thread(save, text, path=path)` のような間接の呼び出し、`save` の中で `path` を代入し直す形などが、変えてはいけない形の候補になります（D58 の改訂が挙げた形）。

**(3)** 2 つ目の形は、**誤 clear** の向きを見張るテストです。
規則を素朴に実装すると、`**opts` で渡された値を見落として既定値の `None` を入れ、6 行目に届かないと判断して、本当の書き込みを消してしまいます。
`readOnlyHint: true` のツールが実際にはファイルを書くのに、矛を出さなくなります。

本記録者が 3 つの版で確かめた結果です（書き込みは作業用のファイルの 11 行目）。

| ツール | 直す前（`289624c`） | O31 の最初の実装（`7ea8bac`） | 凍結版 |
|---|---|---|---|
| `omit`（数えないのが正しい） | 数える（**誤警報**の矛） | 数えない | 数えない |
| `model_path`（数えるのが正しい） | 数える（D1 の矛） | 数える | 数える |
| `via_kwargs`（数えるのが正しい） | 数える（D1 の矛） | **数えない（誤 clear）** | 数える（D1 の矛） |

O31 の最初の実装は、まさに `via_kwargs` の形で誤 clear を作っていました。
これは、run15 の後の敵対的レビューで見つかった原因 (A)「呼び出し側の `**kwargs` / `*args`」と同じ形で、D58 の改訂で直されました（第 24 章）。
最初の反例のテストに、この形の「変えてはいけない形」が入っていれば、段階 ② で捕まえられたはずです。

#### 演習 23-3（検査の結果を読み分ける）

**(1)** 言えること（例）:

- テストに書いた形については、期待どおりの答えが保たれている（`pytest`）。
- 付録のゲートの判定は、23 問（B3a 8・B3b 15）で期待どおりで、テストの強さも前と同じ水準（生存 1/15）。

- 較正対 A9 で、効果の行が 3 行**消えた**。

言えないこと（例）:

- 消えた 3 行が、正しく消えた（届かない効果だった）のか、誤って消えた（誤 clear）のか。
- 母集団（v2 の 87 木）で、何が消えて何が増えたか（まだ取り直していない）。
- 矛（CONTRADICTION）の判定が正しく保たれているか（B3a・B3b は矛を見ていない）。

**(2)** まず、`diff_effects.py` が出した**消えた 3 行を 1 件ずつ原ソースで確かめます**。

1 件でも「本当は届く」ものがあれば、それは誤 clear なので、規則か実装を見直します（段階 ① か ③ に戻る）。
その後、段階 ⑤ として母集団を取り直し、`compare_scans.py` で突き合わせます。
変更が解決を広げる向きなら、敵対的レビューも通します。

**(3)** 正しくありません。
B3b は付録 G の 15 問で、**ゲートの判定**（`DOM` / `NODOM` / `OPAQUE`）と理由と証拠の行が期待どおりかを確かめる検査です。
矛（宣言に反する）の判定は見ていません。

#### 演習 23-4（最終評価での健康診断）

**(1)** 直すべきではありません。
最終評価では、どの段階でも `authgap/` を変えません（手順書の冒頭）。
直すと、事前登録した解析器（`analyzer-freeze-3`、指紋 `35606ba9…`）とは別のもので測ることになります。

**(2)** まず**環境**を疑います（本書の提案。手順書は通らなかったときの手当てを書いていません）。

- Python の版: `.venv` は 3.10、走査に使う `.venv312` は 3.12 か（`python --version`）。
- 依存のライブラリ: `requirements.txt` から入れ直したか。
- 取り出した repo の版: `git log -1` と `git status` で、手元が想定のコミットで、変更が無いか。
- 落ちたテストの名前と出力: 何を期待して何が出たか。

凍結のときには B3a 8/8・B3b 15/15 で、全テストが通っていたので、通らないのは「環境が違う」か「手元の repo が凍結の版と違う」可能性が高いと考えます。

**(3)** 走査を**始めません**。

#### 確認問題 23-1

テストが**本当にその誤りを捉えている**ことを確かめるためです。
直す前の解析器でテストが落ちれば、「この入力では、今の解析器は間違える」ことをテストが見分けられていると分かります。
直す前から通るテストは、入力の書き間違いや見る欄の誤りなどで、何も確かめていない可能性があります。
その場合、直した後に通っても、「直したから通った」のか「最初から通っていた」のか区別がつきません。

#### 確認問題 23-2

- **B3a**: 支配だけを問う **8 つの変異プログラム**（`fixtures/dominance_mutants/`）を、8 つとも退けること。8 つは「ゲートしていない」と判定されるべき形（承認の結果を使わない、`or` の極性、検査の向きが逆、無関係な関数の設定、別モジュールの同名クラス、偽の側の分岐の効果など）で、1 件でも `DOM`（ゲートしている）と判定したら不合格。読み込みに失敗するファイルと、上限に当たるほど大きいプログラムの 2 つは、`DOM` にしないことに加えて、その印の行（`parse_failure`、`TRUNCATED` と `OPAQUE(cfg_cap)`）が出ることも求める。
- **B3b**: 付録 G の **G1〜G15**（`fixtures/gates/`）で、**(verdict, 理由の類, witness の行番号) の 3 つ組**が 15 個とも期待と一致すること。

どちらも**付録の仕組み（ゲート）**の検査で、仕様書のために作った小さなプログラムが入力です。
第 31 章の「両側比較 7/8」は、`two_sided.py` で、**実際の CVE の修正前と修正後の本物のコードの組（較正対）**を入力にし、事前登録した変化がその向きで起きたかを数えるもので、別の検査です。
B3b 15/15 と両側比較 7/8 が並んでいても矛盾しません。

#### 確認問題 23-3

**変異**は、支配判定の実装にわざと入れる小さな誤り（15 種類）です。
変異を入れた状態でテスト（`fixtures/gates/` と `fixtures/dominance_mutants/` の期待値）を照らし、1 件も食い違わなければ、その変異は**生存**です。
つまり生存とは、「この誤りが入っても、今のテストでは気づけない」という**テストの弱さの印**です。

「生存 1/15」は、解析器にバグが 1 つあるという意味では**ありません**。
2026-10-01 に走らせたときの生存は `no_finally_copies`（`finally` の複製をやめる変異）で、「`finally` の複製をやめても、今のテストでは気づけない」という意味です。
今の解析器が `finally` の複製をやめているわけではありません。
受け入れの条件は「生存 2 以下」で、仕様書はこの閾値に経験的な根拠は無く、事前に固定したことだけが根拠だと書いています。

#### 確認問題 23-4

**直しません。**
判定ではその件を「誤」にし（矛の判定で、解析器の言い分が間違っているので。見落としの判定で解析器の言わなさすぎに気づいたなら「見落とし」として原因を書く）、`docs/open_questions.md` に、解析器の限界として書きます（手順書 26 節の困ったときの表、22 節の 4。O43 と同じ扱い）。

直さない理由:

- 最終評価のデータを見て解析器を直すと、直した解析器をそのデータで測ることになり、結果が甘くなります（試験問題を見てから答えを直すのと同じ。第 25 章）。
- 直した解析器は、事前登録した凍結の版（`analyzer-freeze-3`、指紋 `35606ba9…`）とは別物になり、「どの解析器で測るか」という事前の約束が崩れます（第 22 章）。
- 限界として記録すれば、読み手はその誤りを知ったうえで結果を割り引いて読めます。直して隠すより、正直です。
