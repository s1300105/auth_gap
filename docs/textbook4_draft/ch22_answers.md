この章の演習は、説明のための作り話の数字と、repo の記録（`docs/preregistration.md`、`docs/population_v4.md`、`git log` など。本書の執筆時に確かめたもの）を使っています。

#### 演習 22-1（コミットの順番を読む）

**(1)** 最終評価のデータに触れる前に決めたのは **(ア)** だけです。
下書きは「封をしてから、最終評価のデータ（抽出・pin・取得）に触れる」と書いているので、(イ) の抽出と pin から先は、データに触れた後です。
ただし、(オ) の抜き取りを判定（(カ)）の前にコミットしているのは、手順書の「対象の一覧をコミットしてから判定を始める」のとおりで、よいことです。

**(2)** (キ) は、走査・抜き取り・判定が始まった**後**に seed を変えています。
これは、§2.12 の下書きの (h)「結果を見て、抜き取り・seed・分母を変える」と、手順書の 0-8「データを見た後に seed を変えない」に反します。
しかも seed ① は矛の抜き取りに使うので、変えると判定の対象そのものが入れ替わり、「判定の途中で対象を差し替えない」にも反します。
この研究の約束では、seed を変えません。
もし道具の故障などで、どうしても変える必要が出たなら、§5 に逸脱として、変更前・変更後・理由・日付・そのとき見ていた数値を書き、主の結果は元の seed での抜き取りで出します（手順書 25 節「変えたら逸脱として記録し、主の数字は変える前の版で出す」）。

**(3)** 「**事後の分析**（事前登録していない。結果を見た後に計算した）」と明記し、主の結果の表とは別の節に置きます（手順書 23.6）。
どの木を除いたか、なぜその木を選んだか（結果を見て選んだこと）も書きます。

**(4)** 下書きの【保留】は、「決めるなら段階 6（抜き取りのコミット）の前に、この節に追記してコミットする。それより後に足すなら §5 に逸脱として書き、事後の分析とする」です。
(カ) は段階 6（(オ)）の後なので、2 人目の判定者を足すなら、§5 に逸脱として理由とともに書き、その結果（一致の度合いなど）は事後の分析として扱います（D70 の 8）。

#### 演習 22-2（封の後に手引きの穴を見つけた）

**(1)** 40 件目は、次のように記録します（手順書 22 節、手引きの下書き 22 節）。

- 判定表の `verdict` を「不明」にする。
- `unknown_reason` に「手引きで決まらない: <どんな形で、どの規則に当てはまらなかったか>」と書く。
- `evidence` には、読んだファイルと行をいつもどおり書く。
- `docs/preregistration.md` の §5（逸脱の記録）に、この事例（木・ツール・形・何が決まらなかったか）を書く。
- 手引きは変えない。

**(2)** 手引きの 22 節に照らすと、前の 2 件も、もともと「手引きで決まらない」事例でした。
自分の感覚で「誤」にしたのは、決められないものを黙って倒したことになります（規則 4）。
手引きを変えるのではなく、封をした手引きの**当て方を揃える**見直しなので、2 件も「不明」（手引きで決まらない）にし、`note` に見直した日と理由（40 件目で同じ形に気づき、手引き 22 節に合わせた）を書くのが、一貫した扱いです。
§5 の事例の記録にも、同じ形が 3 件あったことを書きます。
（これは本書の読みです。手順書は、前に判定した件の見直しについて「迷った件は印を付けて翌日に見直す（見直したことを `note` に書く）」と書いていますが、この場面を名指ししてはいません。）

**(3)** 足すなら、次のことをします（手順書 22 節の 3）。

- 規則を足した**日時**を記録する。
- 足す**前**に判定した件と**後**の件を、**分けて**報告する。
- 足した規則で前の件も**付け直した結果を併記**する。
- §5 に、規則を足したことを逸脱として書く。

主の結果は、**事前登録した（封をした）手引きのままの判定**です。
つまり主の結果では、この形の事例は「不明（手引きで決まらない）」のままで、足した規則での判定は併記にとどまります。

**(4)** 例:

- 途中で作った規則は、それまでに見た事例（結果）に合わせて作られるので、結果を見て基準を選ぶこと（矢を射た後で的を描く）になる。
- 前半と後半で違う規則が当たり、同じ形の事例が、判定した順番という偶然で違う結果になる（判定の順序は無作為にしてある）。
- 封をした手引きが「先に決めた」証拠なので、途中で変えると封の意味が無くなる。

#### 演習 22-3（v4 の 36.4% はなぜ事後の分析か）

**(1)**

- 76.7% = 46 ÷ 60。抜き取った D1・D2 の矛 60 件のうち、正が 46 件（不明は 0）。
- 36.4% = 8 ÷ 22。60 件から reaper-mcp の 38 件（すべて正）を除いた 22 件のうち、正が 46 − 38 = 8 件。

**(2)** v4 の規則は `d6a8245`（2026-09-29 08:15:39）でコミットされ、精度は「判定した件数」を分母に宣言ごとに出すと決めていました。特定の木を除いた精度は、規則にありません。
結果は `4f307b4`（08:50:33）でコミットされ、36.4% はその約 1 時間後の `faccc3d`（09:51:02）で追記されました。
つまり、36.4% は事前登録に無く、結果を見た後に計算したものです。
`docs/population_v4.md` も、追記のコミットのメッセージも、「事後の分析（事前登録していない。結果を見た後に計算した）」「事前登録外と明記」と書いています。

**(3)** 「除くもの」は、結果を左右する「選べるところ」の 1 つです（22.1 節の表）。
reaper-mcp を除いたのは、「60 件中 38 件を占め、しかも全部が正」という結果を見たからです。
結果を見てから除くものを選べば、別の木を除いて数字を上げることも下げることもできます。
これは、矢を射た後で的を描くのと同じで、外からは「結果に合わせて選んだのではない」と示せません。

**(4)** 最終評価の **D67 の 3**（報告の単位を木にし、1 木あたり最大 3 件を抜き取り、件数で数えた精度は参考にする）に生かされました。手順書 23.4 も、v4 の 36.4% を理由に挙げています。
これが「結果を見て規則を選んだ」ことにならないのは、規則を当てる相手が、**まだ誰も見ていない最終評価のデータ**で、その規則を**データを見る前に**決めた（事前登録する）からです。
v4 の数字そのものは書き換えていません。

#### 演習 22-4（分母を先に決める）

**(1)** n = N なので K̂ = k = 54 です。

- (a) = 54 ÷ 120 = **45%**
- (c) = 54 ÷ 600 = **9%**
- (b) = 54 ÷ 2,400 = **2.25%**

**(2)** 結果を見てから主を選ぶことになります。
たとえば (b) は一番小さい値なので、「宣言はほとんど正しい」という印象を作るために選んだのでは、と疑われても反論できません。
22.1 節の「矢を射た後で的を描く」です。
しかも最終評価では、主はすでに D70 の 4 で決まっているので、後から変えれば逸脱です。

**(3)** **(a) と (c) を主**、(b) を参考と決まっています（D70 の 4）。
「下限」と書く理由:

- 1 木 3 件までしか判定しないので、判定しなかった件に正が残っているかもしれない（全部の木を判定しても、木の中の件は全部ではない）。

**(4)** D4（`idempotentHint: true`）は、`D_kind.explicit` に入ることがありません（D4 は `idempotent` の欄に表れる）。

#### 確認問題 22-1

**結果を見てから、都合のよい規則や基準を選んでしまう**失敗です。
矢を射た後で的を描けば、どんな射手でも全部真ん中に当てたように見せられます。
研究でも、結果を見てから分母・除く木・規則を選べば、どんな結果でも「予想どおり」に見せられ、外からは区別できません。
本人に悪意がなくても起きるので、事前登録・凍結・逸脱の記録という仕組みで防ぎます。

#### 確認問題 22-2

- タグ: `analyzer-freeze-1`（1bcace3。中間の区切り）、`analyzer-freeze-2`（f3c02e8。履歴）、`analyzer-freeze-3`（9dc3bc3。今の凍結）。
- 最終評価に使うのは **`analyzer-freeze-3`** です。
- 確かめる方法（どれか 2 つ以上）:
  1. `git fetch --tags && git tag -l` で、`analyzer-freeze-3` があることを確かめる。
  2. `git diff analyzer-freeze-3 -- authgap/` の出力が空であることを確かめる。
  3. `git status --porcelain -- authgap/` の出力が空（未コミットの変更が無い）であることを確かめる。
  4. `scripts/scan_v2.py` を `--require-fingerprint docs/fingerprint.json` で走らせる（指紋が違うか未コミットの変更があれば、走査が始まらない）。
  5. 走査の後、`summary.json` の `implementation_sha256_combined` が `35606ba9…` で、`authgap_dirty` が `False` であることを確かめる。

#### 確認問題 22-3

- `freeze.tag` には **`analyzer-freeze-2`** と書いてあります。
- 正しい凍結のタグは **`analyzer-freeze-3`** です。ファイルの中の実装の結合 sha256（`35606ba9…`）は、freeze-3 の版と一致します。
- 書き換えないのは、このファイルがタグの付いたコミットの中のファイルで、その時点の記録だからです。書き換えると、「その時点で何が書いてあったか」が分からなくなります（仕様書を書き換えないのと同じ考え方）。食い違いは、D64 の記録・逸脱 #26・手順書 9.1・事前登録の下書きに書いてあります。

#### 確認問題 22-4

- **封をする**とは、事前登録の §2.12 を `docs/preregistration.md` に写し、判定の手引きを `docs/final_judging_guide.md` に置いて、**2 つを同じコミット**に入れ、**その後で**最終評価のデータに触れることです。封の後は、判定の途中で手引きを変えません。
- 同じコミットに入れる理由:
  - コミットの日時という 1 つの証拠で、両方がデータより前に決まっていたことを示せる。別のコミットにすると、片方を後から直した疑いが残る。
  - §2.12 は「判定の基準は `docs/final_judging_guide.md`。この節と同じコミットで封をする」と手引きを名指ししていて、2 つは互いを前提にしている。
- **データに触れる**とは、段階 3 の**抽出**（と pin・取得）からのことです（下書き「最終評価のデータ（抽出・pin・取得）に触れる」）。結果を見るのは段階 7 からですが、触れるのはそれより前からです。
