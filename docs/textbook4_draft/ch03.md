## 第 3 章 MCP — 道具をつなぐ共通の決まりと、サーバの起動

> **この章で分かること**: MCP・MCP サーバ・クライアントという 3 つの言葉と、両者のあいだの 2 つの要求（`tools/list` と `tools/call`）。Python でツールを書く典型的な 2 つの形（FastMCP のデコレータの形と、低レベルの形）と、登録の別の書き方。サーバが**どう起動されるか**（起動の 4 つの形）と、それぞれで何が実行され何が実行されないか。サーバの起動時に 1 回だけ走る **lifespan**。ツールからクライアントへの連絡口 **ctx**。そして、これらが最終評価の判定の「起動時の初期化」の規則（第 49 章）と「クライアントへの通知は反しない」という規則（第 50 章）の前提になること。

### 3.1 共通の決まりが要る理由 — MCP

#### 一言で言うと

**MCP**（Model Context Protocol）は、「AI のアプリに道具（ツール）をつなぐときの共通の決まり」です。
決まりが共通なので、1 つの道具を作れば、その決まりに従うどのアプリからでも使えます。

#### たとえ話 — USB と電源のコンセント

パソコンのマウスを思い浮かべてください。
マウスの差し込み口は、たいてい USB という形をしています。
USB の形と、線の中を流れる信号の決まりが共通なので、どの会社のマウスでも、どの会社のパソコンにも差せます。

もし差し込み口の形がパソコンの会社ごとに違っていたら、どうなるでしょうか。
マウスを作る会社は、パソコンの会社の数だけ、違う形のマウスを作らなければなりません。
買う人も、パソコンを替えるたびにマウスを買い直すことになります。

電源のコンセントも同じです。
差し込みの形と電圧が国の中で決まっているので、どの家電も、どの家の壁にも差せます。

MCP は、AI のアプリと道具のあいだの「USB」や「コンセント」にあたるものです。

#### 小さな例 — つなぎ方の数を数える

アプリが 3 つ（A・B・C）、道具が 4 つ（ファイル・メモ・検索・メール）ある、と考えます（説明用の数です）。

| | 共通の決まりが無いとき | 共通の決まりがあるとき |
|---|---|---|
| 作る「つなぎの部品」の数 | アプリ 3 × 道具 4 = **12** | アプリ側 3 + 道具側 4 = **7** |
| 新しいアプリを 1 つ足すと | 道具の数だけ（4 つ）作り直す | アプリ側に 1 つ足すだけ |
| 新しい道具を 1 つ足すと | アプリの数だけ（3 つ）作り直す | 道具側に 1 つ足すだけ |

表の読み方: 1 行目は「決まりが無いと、アプリと道具の組ごとに部品が要るので 12 個。決まりがあると、アプリは決まりに合わせる部品を 1 つ、道具も決まりに合わせる部品を 1 つ持てばよいので 7 個」と読みます。
数が大きくなるほど、この差は広がります。
たとえばアプリが 10、道具が 100 なら、掛け算で 1,000 と、足し算で 110 です。

#### 一歩ずつ

1. 以前は、ツールを LLM につなぐ方法がアプリごとにばらばらでした。
2. そのため、同じツールを別のアプリで使うには、そのアプリ向けに作り直す必要がありました。
3. そこで、**ツールのつなぎ方の共通の決まり**が作られました。それが MCP です。
4. 道具を作る人は、MCP の決まりに従って道具を 1 回作ります。
5. アプリを作る人は、MCP の決まりに従って道具を呼べるようにしておきます。
6. すると、どの道具も、どのアプリからも使えるようになります。

#### 言葉の整理 — プロトコルと MCP

- **プロトコル**
  - やさしい言い換え: やり取りの「お作法」。
  - 正確な定義: 2 つのプログラムが情報をやり取りするときの、手順（何を先に送るか）と形式（どんな形で書くか）の取り決め。
  - 例: 「最初に挨拶を送り、相手が返事をしたら、次に一覧を求める」という手順と、「一覧は JSON の形で書く」という形式。
- **MCP**（Model Context Protocol、モデル・コンテキスト・プロトコル）
  - やさしい言い換え: AI のアプリと道具をつなぐための共通のお作法。
  - 正確な定義: LLM を使うアプリ（クライアント。3.2 節）と、道具を提供するプログラム（MCP サーバ。3.2 節）のあいだのやり取りの手順と形式を定めたプロトコル。
  - 例: 「道具の一覧をください」という要求を `tools/list` という名前で送る、と決めてある（3.2 節）。

#### なぜこの研究は MCP を対象にするのか

この研究（AuthGap）は、MCP の道具（ツール）が「自分はこういう性質です」と申告する欄（第 4 章の宣言）と、実際のコードの動きを照らし合わせます。
MCP は決まりが共通なので、その申告の欄も共通の形をしています。
共通の形をしているから、多くのサーバを**同じ物差しで**調べられます。
もし道具ごとに申告の形がばらばらだったら、サーバごとに読み方を変えなければならず、数を数えて比べることができません。

#### よくある誤解・つまずき

- **誤解: 「MCP は 1 つのアプリの名前だ」**
  違います。MCP は決まり（プロトコル）の名前です。アプリでも、道具でもありません。USB がマウスの名前ではないのと同じです。
- **誤解: 「MCP に従っていれば、道具は安全だ」**
  違います。MCP が決めているのは「つなぎ方」です。道具の中で何をするかは、道具を作った人のコードしだいです。コンセントの形が正しくても、家電の中身が安全とは限らないのと同じです。この研究が調べるのは、まさにその「中身」と「申告」のずれです。
- **つまずき: 「プロトコル」という言葉が難しく聞こえる**
  「お作法」「取り決め」と読み替えてください。この教科書では、MCP の決まりの細かい規則（通信の細部）までは扱いません。判定に要るのは、この章で出てくる数個の言葉だけです。

#### 手作業ではどう使うか

最終評価の判定の対象は、MCP サーバの木（1 つのリポジトリ）です（第 47 章）。
判定の途中で「この木は MCP サーバか」を自分で確かめる場面は、ほとんどありません。
対象を決める段階で、宣言の書かれたファイルが `mcp` や `fastmcp`（MCP のライブラリ。3.3 節）を import しない木は、件数を出したうえで除くと決めてあるからです（import は「別のファイルの部品を読み込む」こと。3.6 節）。
v4 の中間検証（凍結した解析器を、本記録者が新しいデータで確かめた作業。第 37 章）でも同じ手続きで、取得した 99 木のうち 11 木を除き、88 木を MCP サーバとして扱いました（v4 の数字は本記録者の判定で、論文には使いません。D66 の 5）。
判定で大事なのは、次の 3.2 節以降の「サーバの中で何がどう呼ばれるか」です。
（出典: 最終評価の除外の条件は `docs/final_evaluation_procedure.md:308` と `docs/drafts/prereg_2_12_draft.md:28`、v4 は `docs/population_v4.md:70-71`、D66 の 5 は `docs/decisions.md:3754`）

#### この節のまとめ

MCP は、AI のアプリと道具（ツール）をつなぐ共通の決まり（プロトコル）である。
決まりが共通なので、申告の欄も共通の形になり、多くのサーバを同じ物差しで調べられる。
MCP はつなぎ方の決まりで、道具の中身の安全を保証するものではない。

### 3.2 MCP サーバとクライアント — 一覧をもらい、実行を頼む

#### 一言で言うと

MCP では、道具を提供するプログラムを **MCP サーバ**、道具を使う側のアプリを**クライアント**と呼びます。
クライアントは `tools/list` で道具の一覧（申告を含む）をもらい、`tools/call` で道具の実行を頼みます。

#### たとえ話 — 第 2 章のレストランの続き

第 2 章では、レストランのたとえを使いました。
お客さん（LLM）がメニュー（ツールの一覧）を見て、注文票（呼び出しの依頼）を書き、店員（AI のアプリ）が厨房（ツールの関数）に運ぶ、という形でした。

この章では、そのたとえを少し広げます。
店員と厨房が、**別々の建物**にあると考えてください。
店員は、いろいろな厨房と取引しています。
どの厨房とも、同じ形式の伝票でやり取りできるように、2 種類の伝票が決まっています。

- 1 枚目の伝票「メニューをください」。厨房は、作れる料理の一覧を返します。一覧には、料理の名前・説明・選べるもの、そして「この料理は辛くありません」のような**自己申告**も書いてあります。
- 2 枚目の伝票「この料理を、この選び方で作ってください」。厨房は、料理を作って返します。

この「厨房」が MCP サーバ、「店員」がクライアント、1 枚目の伝票が `tools/list`、2 枚目の伝票が `tools/call` です。
店員は厨房の中を見ません。
メニューの自己申告を信じるしかないのは、第 2 章と同じです。

#### 小さな例 — 実際にやり取りされる文

クライアントとサーバは、JSON（第 2 章で見た、機械が読みやすい書き方）の文をやり取りします。
次は、やり取りを短くした説明用の例です（実際には、最初に挨拶の要求 `initialize` があり、ほかの欄も付きます）。

```
(1) クライアント → サーバ:
{"jsonrpc": "2.0", "id": 1, "method": "tools/list"}

(2) サーバ → クライアント:
{"jsonrpc": "2.0", "id": 1, "result": {"tools": [
  {"name": "read_file",
   "description": "ファイルの中身を返す。",
   "inputSchema": {"type": "object", "properties": {"path": {"type": "string"}}},
   "annotations": {"readOnlyHint": true}}
]}}

(3) クライアント → サーバ:
{"jsonrpc": "2.0", "id": 2, "method": "tools/call",
 "params": {"name": "read_file", "arguments": {"path": "report.txt"}}}

(4) サーバ → クライアント:
{"jsonrpc": "2.0", "id": 2, "result": {"content": [{"type": "text", "text": "…ファイルの中身…"}]}}
```

#### 一歩ずつ

- (1) クライアントが「道具の一覧をください」と頼んでいます。`"method": "tools/list"` が要求の名前です。`"id": 1` は「これは 1 番の要求です」という番号で、返事と組み合わせるために使います。`"jsonrpc": "2.0"` は、MCP が下敷きにしている JSON-RPC という書き方の版です。今は「決まり文句」と思って構いません。
- (2) サーバが 1 番の要求に返事をしています。`"tools": [...]` の中に、道具が 1 つずつ並びます。
  - `"name"` は道具の名前です。
  - `"description"` は道具の説明です。
  - `"inputSchema"` は引数の形です。ここでは「`path` という欄があり、文字列を入れる」と書いてあります。
  - `"annotations"` が、道具の**自己申告**の欄です。ここでは `readOnlyHint` が `true`、つまり「読むだけです」と申告しています。この欄の意味は第 4 章で詳しく見ます。
- (3) クライアントが「`read_file` を、`path` に `"report.txt"` を入れて実行してください」と頼んでいます。`"params"` の中の `"name"` と `"arguments"` は、第 2 章で見た呼び出しの依頼と同じ 2 つの欄です。
- (4) サーバが 2 番の要求に、実行の結果を返しています。`"content"` の中に、文字の結果（`"type": "text"`）が入っています。

ここで大事なのは 2 点です。
1 点目は、**申告（`annotations`）は (2) の一覧の中でクライアントに届く**ことです。クライアントは、ここで受け取った申告を見て、確認を省くかどうかを決めます（第 2 章 2.6 節、第 4 章）。
2 点目は、**(3) の `arguments` の中身は LLM が決めた値**だということです。第 2 章で見たとおり、ここにはどんな値でも来えます。
（出典: 要求の名前は MCP Python SDK 1.30.0 の `mcp/types.py:1241-1244`（`tools/list`）と `:1356-1359`（`tools/call`）、`name` と `arguments` は `:1351-1352`、道具の欄（`description`・`inputSchema`・`annotations`）は `:1315-1330`、一覧の返事の `tools` は `:1342-1345`、実行の返事の `content` は `:1363-1366`、`jsonrpc` と `id` は `:152-156`、挨拶の `initialize` は `:681-687`。どれも repo の外のファイルで、SDK 1.30.0 で確かめた）

#### 言葉の整理 — MCP サーバ・クライアント・要求

- **MCP サーバ**
  - やさしい言い換え: 道具を貸し出す側のプログラム。
  - 正確な定義: MCP の決まりに従って、道具（ツール）の一覧を出し、クライアントから頼まれた道具を実行して結果を返すプログラム。
  - 例: 判定の手引きの練習用のサーバ（`demo` という名前のサーバで、`search_notes`・`export_note`・`list_notes` の 3 つの道具を持つ。3.7 節で見る）。
- **クライアント**
  - やさしい言い換え: 道具を借りて使う側のアプリ。
  - 正確な定義: LLM を動かし、MCP サーバにつないで、道具の一覧を LLM に見せ、LLM の依頼に従って道具の実行をサーバに頼むアプリ。第 2 章で「AI のアプリ」と呼んだものの、MCP での呼び名。
  - 例: VS Code（Copilot のエージェントモード）や OpenAI Codex CLI。どちらも、申告を見て確認を省くことが確かめられているクライアントです（どちらも [確認]。第 4 章）。
- **要求**（リクエスト）
  - やさしい言い換え: 伝票。
  - 正確な定義: クライアントがサーバに送る、名前（`method`）の付いた頼みごとの文。
  - 例: `tools/list`（一覧をください）、`tools/call`（実行してください）。

「サーバ」と言っても、大きな計算機のことではありません。
**道具を提供する側のプログラム**、という意味です。
SDK の既定の動かし方（標準入出力でつなぐ形）では、サーバは利用者のパソコンの上で、クライアントと同じマシンで動きます（どうつながるかは 3.7 節）。
（出典: クライアントの例は `docs/incidental_writes_practice.md:96-97`）

#### なぜ 2 つの要求だけを覚えればよいのか

MCP には、ほかにも多くの要求があります（資料を読む、文例をもらう、など）。
けれども、この研究が照らし合わせるのは「道具の申告」と「道具を呼んだときの動き」です。
申告は `tools/list` の返事に入っています。
動きは `tools/call` を受けたときに起きます。
だから、判定に要るのはこの 2 つです。

#### よくある誤解・つまずき

- **誤解: 「サーバはインターネットの向こうにある大きな計算機だ」**
  SDK の既定の動かし方では、MCP サーバは利用者のパソコンの上で動く小さなプログラムです。ネットワーク越しに動かす形もありますが（3.7 節）、どちらでも「道具を提供する側のプログラム」という意味は同じです。
- **誤解: 「クライアントは LLM そのものだ」**
  クライアントは LLM を動かす**アプリ**です。LLM は文章を書くだけで（第 2 章）、`tools/call` を実際に送るのはアプリです。
- **誤解: 「`tools/list` の申告は、サーバが中身を調べて自動で付けている」**
  申告は、道具を作った人がコードに書いた値です（第 4 章）。サーバのプログラムが中身を調べて付けるのではありません。だから、申告と中身がずれることがあり、それをこの研究が調べます。
- **つまずき: 「`id` は何のためにあるのか」**
  要求と返事を組み合わせるための番号です。判定では使いません。

#### 手作業ではどう使うか

判定の 1 つ目の問いは「その効果は、**ツールの呼び出しによって**起きうるか」です（第 48 章）。
この「ツールの呼び出し」とは、クライアントから `tools/call` が届き、サーバがツールの関数を動かすことです。
ですから判定では、**ツールの関数の入口**（`tools/call` を受けて最初に動く関数）から読み始めます（判定の手引きの「手順 D」。第 48 章）。

もう 1 つ覚えておくことがあります。
「`tools/call` が届く**前に**サーバで起きること」は、ツールの呼び出しで起きることではありません。
たとえば、サーバの起動の途中で済んでしまう準備です。
この「前に起きること」と「呼び出しで起きること」の境目を決めるのが、3.7〜3.9 節の話です。
（出典: 判定の 2 つの問いは `docs/drafts/final_judging_guide_draft.md:36-41`、手順 D は同 `:128-140`）

#### この節のまとめ

道具を提供するのが MCP サーバ、使うのがクライアント（AI のアプリ）。
クライアントは `tools/list` で一覧と申告を受け取り、`tools/call` で実行を頼む。`arguments` の中身は LLM が決める。
判定は `tools/call` を受けて動くツールの関数の入口から読む。`tools/call` より前に起きることは、ツールの呼び出しではない。

### 3.3 Python での書き方 1 — FastMCP とデコレータ

#### 一言で言うと

Python では、MCP サーバを作る部品集（SDK）の中の **FastMCP** を使い、関数のすぐ上に `@mcp.tool()` と 1 行書くだけで、その関数をツールにできます。
関数の名前・説明文・引数が、そのまま `tools/list` で見せる名前・説明・引数の形になります。

#### たとえ話 — 名札を付けて受付に登録する

会社の受付を思い浮かべてください。
受付には「外からの問い合わせに答えられる係」の一覧があります。
社員が胸に「問い合わせ係」という名札を付けると、受付の一覧に名前・担当・連絡のしかたが載ります。
外から問い合わせが来ると、受付はその一覧を見て、係につなぎます。

`@mcp.tool()` は、この「名札」です。
名札を付けた関数だけが、受付（MCP サーバ）の一覧に載り、外（クライアント）から呼べるようになります。
名札を付けていない関数は、社内の仕事（サーバの中の下請けの処理）しかしません。

#### 小さな例 — いちばん短い MCP サーバ

```python
# 説明用
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("files")

@mcp.tool()
def read_file(path: str) -> str:
    """ファイルの中身を返す。"""
    return open(path).read()
```

#### 一歩ずつ

- 1 行目 `# 説明用`: この教科書の印です。説明のために作った例で、実在のサーバではありません（第 0 章）。
- 2 行目 `from mcp.server.fastmcp import FastMCP`: 「`mcp` というパッケージの中の `mcp.server.fastmcp` という場所から、`FastMCP` という部品を持ってくる」という意味です。`from A import B` は「A から B を持ってくる」と読みます。
- 3 行目は空行です。読みやすくするための区切りで、意味はありません。
- 4 行目 `mcp = FastMCP("files")`: `"files"` という名前の MCP サーバの本体を作り、`mcp` という名前の変数（値に付ける名札）に入れます。以後、`mcp` と書けばこのサーバのことです。**この行がファイルのどこにあるか**（関数の外の一番上か、関数の中か）が、3.7 節の「起動の形」の話で大事になります。
- 5 行目は空行です。
- 6 行目 `@mcp.tool()`: 次の行の関数を「このサーバのツールとして登録する」という印です。`@` で始まるこの書き方を**デコレータ**と呼びます。
- 7 行目 `def read_file(path: str) -> str:`: `read_file` という関数を作ります。引数は `path` で、`: str` は「文字列を受け取る」、`-> str` は「文字列を返す」という目印（型の注記。第 2 章）です。
- 8 行目 `"""ファイルの中身を返す。"""`: 関数の説明文（docstring。第 2 章）です。
- 9 行目 `return open(path).read()`: `path` のファイルを開き、中身を全部読んで返します。

この 4 行目〜9 行目で、`tools/list` の返事には次のように載ります。
関数の名前 `read_file` がツールの名前に、説明文がツールの説明に、引数 `path: str` が引数の形（「`path` という文字列の欄」）になります。
（出典: MCP Python SDK 1.30.0 の `mcp/server/fastmcp/tools/base.py:59`（名前は関数の名前）、`:66`（説明は説明文）、`:72-77`（引数の形は関数の引数から作る）。repo の外のファイル）

#### 実物の例 — 申告の付いた登録

判定の手引きの練習用のサーバ（手引きのために書いた小さなサーバで、解析器で実際に走査したもの）では、次のように書いています（左の数字は元のファイルの行番号）。

```
 3  from mcp.server.fastmcp import FastMCP
 4  from mcp.types import ToolAnnotations
 ...
 6  mcp = FastMCP("demo")
 ...
23  @mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
24  def search_notes(query: str) -> str:
25      """Search notes."""
26      return str(_lookup(query))
```

- 3 行目は、上の例と同じく `FastMCP` を持ってきます。
- 4 行目は、申告を書くための部品 `ToolAnnotations` を、`mcp.types` という場所から持ってきます。
- 6 行目は、`"demo"` という名前のサーバを作り、`mcp` に入れます。関数の外、ファイルの上のほうにあります。
- 23 行目は、デコレータの丸括弧の中に `annotations=ToolAnnotations(readOnlyHint=True)` と書いています。「このツールは読むだけです」という申告です（第 4 章）。この申告が、3.2 節の `tools/list` の返事の `"annotations"` の欄に入ります。
- 24〜26 行目は、ツールの関数です。引数 `query`（検索の言葉）を受け取り、`_lookup(query)` という下請けの関数の結果を文字列にして返します。

`_lookup` には `@mcp.tool()` が付いていません。
だから `_lookup` はツールではなく、ツールの中から呼ばれる下請けの関数です。
けれども判定では、この下請けの中まで読みます。
練習用のサーバでは、`_lookup` の中でさらに `_save_cache` を呼び、そこでファイルを書いています（第 53 章で一通り判定します）。
（出典: `docs/drafts/final_judging_guide_draft.md:550`（実際に走査した）、`:557-560`（3〜6 行目）、`:577-580`（23〜26 行目）、`:570-573`（`_lookup` の中で `_save_cache` を呼ぶ 19 行目））

#### 言葉の整理 — パッケージ・SDK・FastMCP・デコレータ

- **パッケージ**
  - やさしい言い換え: 配られている部品の箱。
  - 正確な定義: Python で、他の人が使えるようにまとめて配布されているプログラムの集まり。`pip` や `uv` という道具で入れ、`import` で使う。
  - 例: `mcp`、`fastmcp`。
- **SDK**（Software Development Kit、ソフトウェア開発キット）
  - やさしい言い換え: ある仕組みに合うプログラムを作るための部品集。
  - 正確な定義: 特定の仕組み（ここでは MCP）を使うプログラムを書くための部品と道具を、まとめて配布したもの。
  - 例: MCP の公式の Python SDK。パッケージの名前は `mcp`。この教科書では版 1.30.0 の中身を確かめています。
- **FastMCP**
  - やさしい言い換え: MCP サーバを短く書くための部品。
  - 正確な定義: 関数にデコレータを付けるだけでツールを登録でき、`tools/list` や `tools/call` への返事を自動で組み立ててくれる、サーバの部品（クラス）。
  - 例: `FastMCP("files")`。
- **デコレータ**
  - やさしい言い換え: 関数に付ける名札。
  - 正確な定義: 関数の定義のすぐ上に `@式` と書き、その関数を「式」が返す処理に渡す書き方。渡された処理は、関数を登録したり、包んだりできる。
  - 例: `@mcp.tool()` は、すぐ下の関数をサーバのツールとして登録する。

`FastMCP` には 2 つの出どころがあります。
1 つは公式の SDK（パッケージ `mcp`）の中のもので、`from mcp.server.fastmcp import FastMCP` と書きます。`from mcp.server import FastMCP` と短く書くこともできます。
もう 1 つは、別の人たちが配っている `fastmcp` というパッケージのもので、`from fastmcp import FastMCP` と書きます。
解析器の入口の規則でも、この 2 つは別の行で扱われています（第 12 章）。
（出典: `from mcp.server import FastMCP` が書けることは SDK 1.30.0 の `mcp/server/__init__.py:1`、実物では v4 の木 shyhurricane の `corpus/v4-double16__shyhurricane/shyhurricane/mcp_server/__init__.py:14`。入口の規則は `authgap/catalog/entries.py:132-148`）

#### なぜこの形を知っておく必要があるのか

解析器は、「どの関数がツールか」を、この `@mcp.tool()` のような登録の印を探して決めます（第 12 章）。
ツールの関数が分かれば、そこが `tools/call` を受けて動く**入口**です。
判定でも同じで、ツールの関数を見つけることが、読み始めの位置を決めることになります。

#### よくある誤解・つまずき

- **誤解: 「`@mcp.tool()` が付いていない関数は、判定と関係ない」**
  関係あります。ツールの関数から呼ばれる下請けの関数（上の `_lookup`）の中で起きる操作も、ツールの呼び出しで起きる操作です。判定では入口から下請けへと順にたどります（第 48 章の手順 D）。
- **誤解: 「ツールの名前は、いつも関数の名前と同じ」**
  何も指定しなければ同じです。けれども `@mcp.tool(name="search")` のように、別の名前を付けることもできます。判定の対象を探すときは、名前だけに頼らず、ファイルと行で探します（第 12 章）。
- **つまずき: 括弧の有無**
  公式の SDK 1.30.0 では `@mcp.tool()` と丸括弧が要ります。括弧を忘れると、「呼び出すのを忘れていませんか」というエラーになります。一方、`fastmcp` パッケージ 4.0.10 では `@mcp.tool` と括弧なしでも書けます。原ソースでどちらの形を見ても、「ツールの登録の印」と読んで構いません。
- **誤解: 「説明文に書いたことが、ツールの動きを決める」**
  説明文は LLM に見せる文章で、動きを縛りません（第 2 章）。判定の根拠はコードの動作です。
（出典: 括弧の件は SDK 1.30.0 の `mcp/server/fastmcp/server.py:503-507`、`fastmcp` 4.0.10 の `fastmcp/server/server.py:1890-1895`。どちらも repo の外のファイル。`name=` は SDK 1.30.0 の同 `server.py:462-471`）

#### 手作業ではどう使うか

判定表の 1 行には、ツールの関数の位置（`unit_relpath` と `unit_lineno`。たとえば `server.py` の 24 行）が書いてあります（第 48 章の手順 A）。
そのファイルのその行を開くと、すぐ上にこの `@mcp.tool(...)` の行があるはずです。
その行の丸括弧の中に、申告（`annotations=...`）が書いてあることが多いので、ここで「何と申告しているか」を目で確かめます。
そして、関数の本体から、下請けの関数へと順にたどっていきます。
（出典: `docs/drafts/final_judging_guide_draft.md:96-103`（判定表の欄）、`:128-140`（手順 D））

#### この節のまとめ

FastMCP では `@mcp.tool()` という名札（デコレータ）で関数をツールにする。関数の名前・説明文・引数が、ツールの名前・説明・引数の形になる。申告はデコレータの括弧の中に書くことが多い。
`FastMCP` には公式 SDK（`mcp`）のものと `fastmcp` パッケージのものがある。
判定では、ツールの関数を入口として、名札の付いていない下請けの関数の中まで読む。

### 3.4 Python での書き方 2 — 低レベルの書き方

#### 一言で言うと

もっと手作業に近い書き方もあります。
**1 つの関数 `call_tool` がすべてのツールの呼び出しを受け取り**、`if name == ...` でどのツールかを振り分けます。

#### たとえ話 — 窓口が 1 つの役所

3.3 節の書き方は、係ごとに名札を付けて受付の一覧に載せる会社でした。
低レベルの書き方は、**窓口が 1 つしかない役所**に似ています。
どの用件の人も、まず同じ窓口に来ます。
窓口の人は、申請書の「用件」の欄を見て、「転入なら奥の 1 番へ」「証明書なら 2 番へ」と振り分けます。

この「窓口」が `call_tool` という関数で、「用件の欄」が `name`（ツールの名前）です。
役所の入り口の掲示板（用件の一覧）は、別の関数 `list_tools` が作ります。

#### 小さな例

```python
# 説明用
@server.list_tools()
async def list_tools():
    return [Tool(name="read_file", ...), Tool(name="delete_file", ...)]

@server.call_tool()
async def call_tool(name, arguments):
    if name == "read_file":
        return open(arguments["path"]).read()
    elif name == "delete_file":
        os.remove(arguments["path"])
```

#### 一歩ずつ

- 1 行目 `# 説明用`: 説明用の印です。結果の返し方などを簡単にしてあります（実際の SDK では、結果を決まった形の部品に包んで返します）。
- 2 行目 `@server.list_tools()`: 次の関数を「`tools/list` が来たときに答える関数」として登録します。`server` は、低レベルのサーバの本体です（作り方は下で見ます）。
- 3 行目 `async def list_tools():`: `list_tools` という関数を作ります。先頭の `async` は「非同期の関数」という書き方の印です。**ここでは「関数を作る」と同じだと思って読んで構いません**（詳しくは第 9 章）。
- 4 行目: ツールの一覧を返します。`Tool(name="read_file", ...)` が 1 つのツールの情報です。`...` の部分に、説明・引数の形・**申告**（`annotations=ToolAnnotations(...)`）を書きます。つまり、低レベルの書き方では、申告は `list_tools` の側に書きます。
- 5 行目は空行です。
- 6 行目 `@server.call_tool()`: 次の関数を「`tools/call` が来たときに動く関数」として登録します。
- 7 行目 `async def call_tool(name, arguments):`: 窓口の関数です。`name` にはクライアントが頼んだツールの名前が、`arguments` には LLM が決めた引数をまとめた辞書が入ります。
- 8 行目 `if name == "read_file":`: 頼まれたツールが `read_file` なら、次の行を実行します。
- 9 行目: `arguments["path"]` で、引数の辞書から `path` の値を取り出し、そのファイルを読んで返します。
- 10 行目 `elif name == "delete_file":`: そうでなく、`delete_file` なら、次の行を実行します。`elif` は「そうでなく、もし〜なら」です。
- 11 行目 `os.remove(arguments["path"])`: `path` のファイルを消します。

**辞書**という言葉をここで整理します。

- やさしい言い換え: 見出しと中身の組を集めた表。
- 正確な定義: キー（見出し）と値の組を集めた Python の値。`{"path": "report.txt"}` のように書き、`d["path"]` で値を取り出す。
- 例: `arguments = {"path": "report.txt"}` なら、`arguments["path"]` は `"report.txt"`。

#### 低レベルのサーバの起動 — 関数の中に定義が入る形

低レベルの書き方では、サーバの本体と窓口の関数を、**別の関数の中**に書くことがあります。

```python
# 説明用
async def serve():
    server = Server("files")

    @server.call_tool()
    async def call_tool(name, arguments):
        ...

    async with stdio_server() as (read_stream, write_stream):
        await server.run(read_stream, write_stream, server.create_initialization_options())
```

- 2 行目 `async def serve():`: `serve` という関数を作ります。サーバを動かすための関数です。
- 3 行目: 低レベルのサーバの本体 `Server("files")` を作り、`server` に入れます。**関数 `serve` の中**で作っている点に注意してください。
- 5〜7 行目: 窓口の関数 `call_tool` も、`serve` の**中**で定義しています。このように、関数の中に関数の定義が入っている形を**入れ子の定義**と呼びます。
- 9 行目: 標準入出力（3.7 節）という通り道を用意します。
- 10 行目: サーバを動かし、クライアントからの要求を待ちます。`await` は `async` の関数の中で使う印で、ここでは「この処理が終わるまで待つ」と読んで構いません（第 9 章）。

この形は SDK に「低レベルの Server」（`mcp.server.lowlevel` の `Server`）として入っており、実際の MCP サーバにも見られます。
解析器はこの形も読めるようになっています（第 12 章）。
（出典: `Server` は SDK 1.30.0 の `mcp/server/lowlevel/__init__.py:1` と `mcp/server/lowlevel/server.py:137`、登録の印 `list_tools`・`call_tool` は同 `server.py:440,498`、`stdio_server` の使い方の例は `mcp/server/stdio.py:8-17`。どれも repo の外のファイル。解析器の入口の規則の低レベルの行は `authgap/catalog/entries.py:149-150`）

#### なぜこの形を知っておく必要があるのか

低レベルの書き方では、**1 つの関数の中に、複数のツールの処理が並びます**。
`call_tool` の全体を読むと、`read_file` の処理と `delete_file` の処理が混ざって見えます。
けれども判定の対象は「1 つのツール」です。
`read_file` を判定しているなら、読むのは `if name == "read_file":` の枝の中だけです。
`delete_file` の枝の `os.remove` は、`read_file` を呼んだときには起きません。

また、入れ子の定義は、うっかりすると見落とします。
この研究の作業の約束にも、「入れ子定義を落とさない。低レベル MCP のハンドラは `serve()` の中にある。」という、一度踏んだ落とし穴が書いてあります。
（出典: `CLAUDE.md` の「よく踏む落とし穴」の 1 項目め）

#### よくある誤解・つまずき

- **誤解: 「`call_tool` の中に `os.remove` があるから、どのツールもファイルを消す」**
  どの枝の中にあるかを見ます。`os.remove` は `delete_file` の枝の中だけです。
- **誤解: 「申告は `call_tool` の近くに書いてある」**
  低レベルの書き方では、申告は `list_tools` が返す `Tool(...)` の中です。ツールの処理（`call_tool` の枝）と申告（`list_tools` の中）が、離れた場所にあります。名前（`"read_file"`）で両方を結び付けて読みます。
- **つまずき: 「ファイルの一番上を見ても、サーバの本体が見当たらない」**
  `serve()` のような関数の中で作っているのかもしれません。`Server(` で検索すると見つかります。

#### 手作業ではどう使うか

判定の対象が低レベルの書き方のツールなら、まず `call_tool`（名前は違うこともあります。`@server.call_tool()` の付いた関数）を開き、判定するツールの名前の枝を見つけます。
そして、その枝の中から読み始めます。
申告を確かめるときは、`list_tools` の中の、同じ名前の `Tool(...)` を見ます。
`if` の条件が `name` 以外の値（たとえば引数の値）を見ているときは、到達の条件の話になります（第 49 章）。

#### この節のまとめ

低レベルの書き方では、1 つの `call_tool` が全ツールの呼び出しを受け、`if name == ...` で振り分ける。申告は `list_tools` の `Tool(...)` の中に書く。
サーバの本体や窓口が `serve()` のような関数の中に入れ子で定義されることがある。
判定では、判定するツールの名前の枝の中だけを読む。

### 3.5 登録の別の書き方（予告）

#### 一言で言うと

デコレータの `@` を使わずに、関数をツールとして登録する書き方もあります。
見た目は違っても、`@mcp.tool()` と同じく、その関数をツールにします。

#### たとえ話 — 名札を自分で付けるか、受付で登録してもらうか

3.3 節では、社員が胸に名札を付けると受付の一覧に載る、とたとえました。
けれども、名札を付けずに、受付に行って「この人を問い合わせ係として登録してください」と頼むこともできます。
結果は同じで、その人は一覧に載ります。

#### 小さな例

```python
# 説明用
def search(query: str) -> str:
    ...

mcp.tool(annotations=...)(search)   # (A) デコレータを「呼び出しの形」で使う
mcp.add_tool(search)                # (B) 登録用のメソッドを直接呼ぶ
```

#### 一歩ずつ

- 2〜3 行目: ふつうの関数 `search` を定義します。上に `@` の行はありません。
- 5 行目 (A): `mcp.tool(annotations=...)` が返す「登録する処理」に、`search` をそのまま渡しています。`@mcp.tool(...)` と書いたのと同じ意味です。
- 6 行目 (B): `mcp.add_tool(search)` は、サーバの「ツールを足す」という操作を直接呼んでいます。

実は、公式 SDK の `@mcp.tool()` も、中では `add_tool` を呼んで登録しています。
つまり (A) も (B) も、`@` の形も、最後は同じ登録の操作にたどり着きます。
（出典: SDK 1.30.0 の `mcp/server/fastmcp/server.py:509-520`（`tool()` の中の関数が `self.add_tool(...)` を呼ぶ）と `:413-449`（`add_tool`）。repo の外のファイル。解析器のコメントは `authgap/catalog/entries.py:135-141`）

#### なぜ予告しておくのか

原ソースを読んでいて、`@mcp.tool()` の無い関数がツールとして判定表に載っていることがあります。
そのとき「デコレータが無いからツールではない。解析器の誤りだ」と早合点しないためです。
解析器の入口の規則は、この呼び出しの形も同じ規則で読みます（決定 D64 の U40 で足した）。
解析器がこれらをどう見つけるかは、第 12 章で扱います。

#### よくある誤解・つまずき

- **誤解: 「ツールは必ず `@` の行の下にある」**
  ここで見たとおり、そうとは限りません。ファイルの下のほうで、まとめて `mcp.add_tool(...)` を並べている形もあります。
- **つまずき: 「申告はどこに書くのか」**
  (A) では `mcp.tool(annotations=...)` の括弧の中、(B) では `mcp.add_tool(search, annotations=...)` のように、登録する行の括弧の中に書きます。

#### 手作業ではどう使うか

判定では、「ツールの定義がデコレータの形でなくても、ツールの入口でありうる」と知っておけば十分です。
ツールの関数の上に `@` が無ければ、そのファイルの中を関数の名前で検索し、`mcp.tool(...)(関数名)` や `mcp.add_tool(関数名, ...)` の行を探します。
申告は、その登録の行に書いてあります。

#### この節のまとめ

`mcp.tool(...)(fn)` や `mcp.add_tool(fn)` も、`@mcp.tool()` と同じくツールを登録する。公式 SDK の `@mcp.tool()` も中で `add_tool` を呼んでいる。
`@` が無くてもツールでありうる。詳しくは第 12 章。

### 3.6 起動の話の前に — モジュール・一番上の文・`__name__`

#### 一言で言うと

Python のファイルは、**直接実行しても、別のファイルから読み込んでも、関数の外に書いた文（一番上の文）が上から順に 1 回実行されます**。
ただし `if __name__ == "__main__":` の中だけは、**直接実行したときだけ**実行されます。
この 2 つの違いが、次の 3.7 節の「起動の 4 つの形」の違いのもとになります。

#### たとえ話 — 台本の「前書き」と「本番の指示」

演劇の台本を思い浮かべてください。
台本の最初には「登場人物の一覧」「舞台の配置」といった前書きがあります。
本番の舞台で使うときも、別の劇団が「参考に読む」ときも、前書きは必ず読まれます。

台本の最後に「※本番の舞台でだけ、ここで幕を上げること」と書いた指示があったとします。
本番の舞台では幕が上がります。
けれども、別の劇団が参考に読んでいるだけなら、幕は上がりません。

Python のファイルの「一番上の文」が前書き、`if __name__ == "__main__":` の中が「本番でだけの指示」にあたります。

#### 言葉の整理 — モジュール・一番上の文・import・`__name__`

- **モジュール**
  - やさしい言い換え: Python のファイル 1 つ。
  - 正確な定義: Python のプログラムを入れた 1 つのファイル（`.py`）と、それを読み込んで作られる名前の集まり。
  - 例: `server.py` は `server` というモジュール。
- **一番上の文**（モジュールの一番上の文、モジュール水準の文）
  - やさしい言い換え: どの関数の中にも入っていない文。
  - 正確な定義: `def`（関数の定義）や `class` の中ではなく、ファイルの字下げの無い位置に書かれた文。ファイルを実行するときも読み込むときも、上から順に 1 回実行される。
  - 例: 3.3 節の `mcp = FastMCP("files")`。`def` の行そのもの（関数を作ること）も一番上の文だが、関数の**中身**は、その関数が呼ばれたときに初めて実行される。
- **import**（インポート）
  - やさしい言い換え: 別のファイルを読み込んで、その部品を使えるようにすること。
  - 正確な定義: モジュールを読み込み、その一番上の文を実行して、できた名前（関数・変数）を使えるようにすること。同じモジュールを 2 回 import しても、一番上の文が実行されるのは最初の 1 回だけ。
  - 例: `import server` と書くと、`server.py` の一番上の文が実行され、`server.mcp` のように中の名前を使えるようになる。
- **`__name__`**（ネーム。前後に `_` が 2 つずつ）
  - やさしい言い換え: そのファイルが「今どう使われているか」を示す名札。
  - 正確な定義: Python が各モジュールに自動で付ける名前の変数。`python server.py` のようにファイルを**直接実行したときだけ** `"__main__"` になり、import で読み込まれたときは読み込んだ側が付けた名前（ふつうはファイル名から `.py` を除いたもの）になる。
  - 例: `python a.py` なら `"__main__"`、`import a` なら `"a"`。

#### 小さな例 — 3 通りの使い方で、何が出るか

次のファイル `a.py` を考えます。

```python
# 説明用（a.py）
print("一番上の文: __name__ は", __name__)

def main():
    print("main の中")

if __name__ == "__main__":
    print("直接実行されたときだけ")
    main()
```

- 2 行目: 一番上の文です。画面に「一番上の文: __name__ は」と、そのときの `__name__` の値を出します。`print` は画面に文字を出す関数です。
- 4〜5 行目: `main` という関数を作ります。4 行目（関数を作ること）は一番上の文ですが、5 行目（中身）は `main()` が呼ばれたときだけ実行されます。
- 7 行目: `__name__` が `"__main__"` のとき、つまり直接実行されたときだけ、8〜9 行目を実行します。
- 8 行目: 「直接実行されたときだけ」と出します。
- 9 行目: `main()` を呼びます。

このファイルを 3 通りに使うと、画面には次のように出ます。
本記録者が Python 3 で実際に動かして確かめた結果です（2026-10-01。repo の外の作業用の場所で動かした）。

| 使い方 | 画面に出るもの |
|---|---|
| (a) `python a.py`（直接実行） | `一番上の文: __name__ は __main__` → `直接実行されたときだけ` → `main の中` |
| (b) `python -c "import a"`（読み込むだけ） | `一番上の文: __name__ は a` |
| (c) `python -c "import a; a.main()"`（読み込んでから `main()` を呼ぶ） | `一番上の文: __name__ は a` → `main の中` |

表の読み方: (b) の行は「`import a` で読み込むだけなら、一番上の文（2 行目）は実行されるが、`__name__` は `"a"` なので 7 行目の `if` は偽になり、8〜9 行目は実行されない。だから `main()` も呼ばれない」と読みます。
(c) の行は、読み込んだ後で、読み込んだ側が自分で `a.main()` を呼んだので、`main` の中が実行された、ということです。

#### 一歩ずつ — 何が「いつ」実行されるか

1. Python は、ファイルを直接実行するときも import するときも、一番上の文を上から順に実行します。
2. `def` の行に来ると、関数を**作る**だけで、中身はまだ実行しません。
3. `if __name__ == "__main__":` に来ると、`__name__` の値を調べます。直接実行なら真、import なら偽です。
4. 関数の中身は、誰かがその関数を**呼んだとき**に実行されます。呼ぶのは、`if __name__ == "__main__":` の中かもしれないし、読み込んだ側のプログラムかもしれません。

#### なぜこれを先に説明するのか

MCP サーバの起動のしかたには、「ファイルを直接実行する」形と、「外のコマンドがファイルを読み込む」形があります（3.7 節）。
読み込む形では、`if __name__ == "__main__":` の中が実行されません。
そこに書いた準備（初期化）も実行されません。
この違いが、判定の規則（D67 の 2）の前提になっています（3.8 節）。

#### よくある誤解・つまずき

- **誤解: 「`def main():` と書けば、`main` は自動で実行される」**
  されません。Python では `main` という名前に特別な意味はありません。誰かが `main()` と呼んだときだけ実行されます。
- **誤解: 「import しただけでは、何も実行されない」**
  一番上の文は実行されます。上の (b) で、2 行目の `print` が実行されたのがその証拠です。ファイルの一番上でファイルを作ったりすれば、import しただけでファイルができます。
- **つまずき: `__name__` と `"__main__"` の見分け**
  `__name__` は変数の名前、`"__main__"` は文字列の値です。「`__name__` という名札に、`"__main__"` と書いてあるか」を調べている、と読みます。

#### 手作業ではどう使うか

判定で「この準備はいつ実行されるか」を考えるとき、まずその準備の行が**どこにあるか**を見ます。

- 関数の外の一番上にあるなら、読み込んだ時点で実行されます。
- `main()` のような関数の中にあるなら、その関数が呼ばれたときだけ実行されます。
- `if __name__ == "__main__":` の中にあるなら、直接実行したときだけ実行されます。

この区別が、3.8 節の判定の規則の表に対応します。1 つ目（一番上）は表の 3 行目（読み込み時）に、2 つ目と 3 つ目（`main()` の中、`if __name__ == "__main__":` の中）は表の 1 行目にあたります。表の 2 行目の lifespan は 3.9 節で見ます。

#### この節のまとめ

一番上の文は、直接実行でも import でも 1 回実行される。関数の中身は呼ばれたときだけ実行される。
`if __name__ == "__main__":` の中は、直接実行したときだけ実行される。`main` という名前に特別な意味は無い。

### 3.7 サーバの起動のしかた — 4 つの形

#### 一言で言うと

MCP サーバを Python のファイルから起動する形は、大きく 4 つあります。
① ファイルの最後で `mcp.run()`、② `main()` の中で準備してから `mcp.run()`、③ `if __name__ == "__main__":` の中で起動、④ 外のコマンド `fastmcp run server.py:mcp` で起動。
**④ だけは、ファイルを読み込んで一番上の `mcp` を直接使うので、`main()` を通りません。**

#### たとえ話 — 店の開け方

お店の開け方を考えます。

- ① 店に貼り紙「この紙を読んだら、すぐ店を開けること」がある。誰が来ても、貼り紙を読んだら開く。
- ② 店長が来て、「開店前の準備（掃除・釣り銭の用意）」を済ませてから、店を開ける。
- ③ 「店長本人が来たときだけ、準備をして店を開ける」と決めてある。
- ④ 本部の人が合鍵で直接シャッターを開ける。店長の「開店前の準備」は通らない。

④ のとき、釣り銭の用意はまだできていません。
最初のお客さんが来たときに、慌てて釣り銭を用意することになります。
この「最初のお客さんのときに準備が走る」ことが、3.8 節の判定の話の中心です。

#### サーバとクライアントは、どうつながるのか

4 つの形の前に、つながり方を確かめます。
標準入出力でつなぐ形では、クライアントの設定に「このコマンドでサーバを起動する」と書いておきます。
クライアントがそのコマンドを実行してサーバを起動し、**標準入出力**を通じて話します。
この形では、サーバはクライアントと同じマシンの上で、クライアントが起動したプログラムとして動きます。

- **標準入出力**（stdio、エスティーディーアイオー）
  - やさしい言い換え: プログラムの「耳」と「口」。
  - 正確な定義: プログラムが起動したときに最初から用意されている、入力の通り道（標準入力）と出力の通り道（標準出力）。標準出力とは別に、エラーや記録を出す通り道（標準エラー）もある。
  - 例: 端末でキーボードから打った文字が標準入力に入り、画面に出る文字が標準出力から出る。stdio の MCP サーバでは、クライアントがサーバの標準入力に要求（JSON）を書き、サーバの標準出力から返事を読む。

SDK 1.30.0 の `FastMCP` の `run()` は、何も指定しなければ標準入出力で動きます。
ほかに、HTTP（ウェブで使われる通信の決まり。第 10 章）で要求を待ち受ける形もあります。
（出典: SDK 1.30.0 の `mcp/server/fastmcp/server.py:295-317`（`run` の既定は `transport="stdio"`）、`mcp/server/stdio.py:12-13,46-49`（標準入力から読み、標準出力へ書く）、`mcp/client/stdio/__init__.py:72-76,106,124`（クライアントは指定のコマンドと引数でサーバを起動する）。どれも repo の外のファイル）

#### 小さな例 — 4 つの形のコード

どれも説明用の例です。

**① モジュールの最後で `mcp.run()` を呼ぶ**

```python
# 説明用（server.py）
mcp = FastMCP("notes")

@mcp.tool()
def search(q: str) -> str: ...

mcp.run()        # ← 一番上の文として、守り（if）無しで置く
```

- 2 行目: サーバの本体を一番上で作ります。
- 4〜5 行目: ツール `search` を登録します。`...` は「中身は省略」という意味です。
- 7 行目: 一番上の文として `mcp.run()` を置いています。`python server.py` で起動すると、上から順に実行され、ここでサーバが動き出します。

**② `main()` という関数の中で準備してから `mcp.run()` を呼ぶ**

```python
# 説明用（server.py）
mcp = FastMCP("notes")

def main():
    prepare_storage()   # ← 起動の前の準備（初期化）
    mcp.run()
```

- 2 行目: サーバの本体は、やはり一番上で作ります。
- 4 行目: `main` という関数を作ります。`main` は「プログラムを起動する入口の関数」によく使われる名前です（3.6 節で見たとおり、名前に特別な意味はありません）。
- 5 行目: 起動の前の準備をします（`prepare_storage` は説明用の名前で、保存場所の用意をする関数だと思ってください）。
- 6 行目: サーバを動かします。

`main()` は誰かが呼ばないと実行されません。
呼ぶのは、次の ③ か、パッケージの設定です。
パッケージの設定とは、`pyproject.toml` というファイルの `[project.scripts]` という欄に、「このコマンド名で、このモジュールの `main` を呼ぶ」と書く形です。
たとえば `notes-server = "server:main"` と書いておくと、パッケージを入れた後に `notes-server` というコマンドを打つだけで `server` モジュールの `main()` が呼ばれます。

**③ `if __name__ == "__main__":` の中で起動する**

```python
# 説明用（server.py の最後）
if __name__ == "__main__":
    main()          # ② の main() を呼ぶ。直接 mcp.run() を書くこともある
```

- 2 行目: 直接実行されたときだけ、次の行を実行します（3.6 節）。
- 3 行目: ② の `main()` を呼びます。サーバによっては、ここに直接 `mcp.run()` と書きます。

`python server.py` で直接実行したときだけ、中が実行されます。

**④ 外から `fastmcp run server.py:mcp` で起動する**

```
fastmcp run server.py:mcp
```

これは `fastmcp` パッケージのコマンドです。
公式 SDK にも、同じ形の `mcp run server.py:mcp` があります。
`server.py:mcp` は「`server.py` の中の、`mcp` という名前のもの」という意味です。
このコマンドは、次の 3 段で動きます。

1. `server.py` を**モジュールとして読み込みます**。一番上の文が実行されます。
2. その中から `mcp` という名前のもの（サーバの本体）を取り出します。
3. そのサーバを動かします（公式 SDK の `mcp run` は `server.run()` を、`fastmcp` 4.0.10 は `server.run_async()` を呼ぶ）。

読み込むときのモジュールの名前は `"server_module"` で、`"__main__"` ではありません。
したがって **`if __name__ == "__main__":` の中は実行されず、そこから呼ぶはずの `main()` も実行されません**。
これは 3.6 節の表の (b) と同じ状況です。
（出典: 公式 SDK 1.30.0 の `mcp/cli/cli.py:119-141`（`"server_module"` という名前で読み込み、一番上の文を実行する。135・141 行）と `:305-350`（`run` コマンド。350 行で `server.run()`）、`fastmcp` 4.0.10 の `fastmcp/utilities/mcp_server_config/v1/sources/filesystem.py:83-107`（`"server_module"` という名前で読み込む。98・105 行）と `fastmcp/cli/run.py:271`（`server.run_async()`）。どれも repo の外のファイルで、本記録者がコードを読んで確かめた）

#### 4 つの形で、何が実行されるか

| 起動の形 | 一番上の文 | `main()` の中 | `if __name__ == "__main__":` の中 |
|---|---|---|---|
| ① `python server.py`（最後に `mcp.run()`） | 実行される | （`main` が無い） | — |
| ② パッケージの設定から `main()` を呼ぶ | 実行される | 実行される | 実行されない |
| ③ `python server.py`（`if __name__ == "__main__": main()`） | 実行される | 実行される | 実行される |
| ④ `fastmcp run server.py:mcp` | 実行される | **実行されない** | **実行されない** |

表の読み方: 4 行目は「④ で起動すると、一番上の文は実行されるが、`main()` の中と `if __name__ == "__main__":` の中はどちらも実行されない」と読みます。
2 行目の ② で `if __name__ == "__main__":` の中が実行されないのは、パッケージの設定は `main` を**直接**呼ぶので、ファイルを直接実行していないからです（3.6 節の (c) と同じ）。

#### 実際に動かして確かめた結果

本記録者は、③ と ④ の違いを、公式 SDK 1.30.0 で実際に動かして確かめました（2026-10-01。repo の外の作業用の場所で、本物のクライアントからツールを 2 回呼んだ。repo には残していない）。
サーバのファイルには、一番上の文・`main()`・「最初の 1 回だけ準備する」関数・ツールの中に、それぞれ記録の行を入れました。
記録に残った順番は次のとおりです。

| 順 | ③ `python server.py` | ④ `mcp run server.py:mcp` |
|---|---|---|
| 1 | 一番上の文（`__name__` は `__main__`） | 一番上の文（`__name__` は `server_module`） |
| 2 | `main()` に入った | （`main()` は実行されない） |
| 3 | 準備が走った（`main()` から） | — |
| 4 | ツールの 1 回目 | 準備が走った（**ツールの 1 回目の中から**） |
| 5 | ツールの 2 回目 | ツールの 1 回目 |
| 6 | | ツールの 2 回目 |

表の読み方: ④ の列の 4 行目が要点です。④ では `main()` を通らないので、準備は**最初のツールの呼び出しの中で**走りました。2 回目の呼び出しでは、もう準備済みなので走りませんでした。
（この表は、3.9 節の lifespan の行を省いて示しています。lifespan を入れた全体の順番は 3.9 節で見ます。）

#### 実物の例 2 — ② と ③ を両方持つサーバ（v4 の木 ccr）

 69      "ccr",

#### なぜ 4 つも形があるのか

それぞれに便利な場面があるからです。
① は最も短く書けます。
② は、起動の前に準備をしたり、コマンドの引数（ccr の `--project` など）を読んだりできます。
③ は、ファイルを直接実行したときと、別のファイルから部品として読み込んだときで、振る舞いを分けられます。
④ は、サーバを作る人がコマンドの決まりを覚えなくても、ライブラリの側が起動を引き受けてくれます。
1 つのサーバが、②・③・④ のいくつもの形で起動できることもあります（上の ccr のように）。

#### よくある誤解・つまずき

- **誤解: 「サーバは作者が書いた `main()` から必ず起動する」**
  ④ の形では `main()` を通りません。しかも ④ は、作者が何も書かなくても、`mcp` が一番上にあればできてしまいます。作者が ④ を想定していたかどうかは関係ありません。
- **誤解: 「① の形のサーバは ④ では起動できない」**
  起動はします。ただし、④ のコマンドがファイルを読み込む**途中で**、一番上の `mcp.run()` が実行され、そこでサーバが動き出します（3.6 節のとおり、一番上の文は読み込みで実行されるため）。本記録者が SDK 1.30.0 の `mcp run` で試したところ、ツールの呼び出しはふつうに動き、クライアントが接続を閉じた後で、コマンドの側の 2 回目の起動がエラーになりました。① の形にはもともと `main()` が無く、一番上の文は ① でも ④ でも実行されるので、準備がいつ済むかという点では違いが出ません。この教科書ではこれ以上深入りしません。
- **つまずき: 「`server.py:mcp` の `mcp` は、パッケージの `mcp` のことか」**
  違います。ここの `mcp` は、`server.py` の中で `mcp = FastMCP(...)` と名前を付けた**変数**です。もし `app = FastMCP(...)` と書いてあれば、`server.py:app` と指します。
- **つまずき: 「サーバの本体が関数の中で作られている」**
  ④ の形で `server.py:mcp` のように**変数の名前**で指せるのは、`mcp` がモジュールの一番上にあるときだけです。関数の中で作っていたら、外からその名前で取り出せません。公式 SDK 1.30.0 は、サーバの本体が見つからないときのエラーの文で「`main()` などの関数の中で FastMCP を作っているなら、一番上の変数（`mcp`・`server`・`app`）に書き直してください」と案内しています。なお `fastmcp` 4.0.10 には、引数の無い関数を指して、その関数が返すサーバを使う形もありますが、この教科書では扱いません。
- **つまずき: 「低レベルの書き方のサーバも ④ で起動できるか」**
  公式 SDK 1.30.0 の `mcp run` は、低レベルの `Server` は「まだ対応していない」と自分で書いています。低レベルのサーバは、たいてい自分で書いた関数（3.4 節の `serve()` など）から起動します。判定の手引きの下書きは、この形の起動を名指しでは扱っていません。気になる事例に出会ったら、手引きを承認する前の確かめごととして書き留めてください。
（出典: SDK 1.30.0 の `mcp/cli/cli.py:171-179`（見つからないときの案内。175〜177 行）、`:152-157`（低レベルの `Server` は未対応）。`fastmcp` 4.0.10 の `fastmcp/utilities/mcp_server_config/v1/sources/filesystem.py:22-25,169-217`（引数の無い関数を指す形）。どれも repo の外のファイル）

#### 手作業ではどう使うか

判定の途中で「準備がいつ済むか」を考える必要が出たら（3.8 節）、まず起動のしかたをコードから読みます。
探すものは次の 4 つです。

1. `FastMCP(` がどこにあるか（一番上か、関数の中か）。
2. `def main` があるか。あるなら、その中で `mcp.run` より前に何をしているか。
3. `if __name__ == "__main__":` があるか。あるなら、その中で何を呼んでいるか。
4. `pyproject.toml` の `[project.scripts]` に、どの関数が書いてあるか。

木の中を検索するなら、たとえば `grep -rn "FastMCP(\|def main\|__main__\|mcp.run" <木>` のように打ちます（`grep` は文字列を探すコマンド。`-r` はフォルダの中を全部、`-n` は行番号を付ける、`\|` は「または」）。
ただし判定の規則では、「その木が実際にどの形で起動されているか」は調べません。
**起動の方法はコードだけから決めます**（判定の手引き 14.4 節）。
（出典: `docs/drafts/final_judging_guide_draft.md:275`）

#### この節のまとめ

起動の形は ① 最後に `mcp.run()`、② `main()` で準備してから `mcp.run()`、③ `if __name__ == "__main__":`、④ 外から `fastmcp run server.py:mcp`（公式 SDK なら `mcp run`）。
④ はファイルを `"server_module"` という名前で読み込み、一番上の `mcp` を直接使うので、`main()` も `if __name__ == "__main__":` の中も通らない。
このことは SDK 1.30.0 で実際に動かして確かめた。判定では、起動の方法をコードだけから決める。

### 3.8 なぜ起動の形が判定に効くのか — 一度だけの初期化（D67 の 2 の予告）

#### 一言で言うと

起動の形の違いは、「**準備（初期化）を、ツールの受付より前に済ませたか**」の違いになります。
最終評価の判定では、初期化が `main()` や `if __name__ == "__main__":` の中だけにあるなら「ツールの呼び出しで届きうる（到達する）」と扱う、と決めました（D67 の 2）。
その理由が、3.7 節の「④ では `main()` を通らない」ことです。

#### たとえ話 — 釣り銭の用意

3.7 節の店のたとえの続きです。
店長が開ける日（③）は、開店前に釣り銭を用意します。
最初のお客さんが来たときには、もう釣り銭はあります。

本部の人が合鍵で開けた日（④）は、釣り銭の用意がまだです。
最初のお客さんがお会計をするときに、店員が慌てて金庫を開けて釣り銭を用意します。
つまり「金庫を開ける」という動作が、**お客さんの対応の中で**起きます。

判定で問うのは、「お客さんの対応（ツールの呼び出し）の中で、金庫を開ける（環境を変える）ことが起きうるか」です。
店長が開けた日だけを見れば「起きない」、本部の人が開けた日も考えれば「起きうる」になります。

#### 小さな例 — 一度だけの初期化

```python
# 説明用
mcp = FastMCP("memo")
_store = None                       # 最初は「まだ準備していない」

def _ensure_store():
    global _store                   # 関数の外の _store を書き換える、という宣言
    if _store is None:              # まだ準備していなければ
        os.makedirs(DATA_DIR, exist_ok=True)   # ← ディレクトリを作る（環境を変える操作）
        _store = open_store(DATA_DIR)
    return _store

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))   # 「読むだけ」と申告（第 4 章）
def list_memos() -> str:
    return str(_ensure_store().list())

def main():
    _ensure_store()                 # ← 起動の前に準備を済ませておく
    mcp.run()

if __name__ == "__main__":
    main()
```

#### 一歩ずつ — 1 行ずつの意味

- 2 行目: サーバの本体を一番上で作ります。
- 3 行目: `_store`（メモの保存場所を扱う部品）を、最初は `None`（「何も無い」を表す Python の値）にしておきます。「まだ準備していない」という印です。
- 5 行目: 準備をする関数 `_ensure_store` を作ります。名前は「保存場所があることを確かにする」という意味です。
- 6 行目: `global _store` は、「この関数の中で `_store` に値を入れたら、関数の外（一番上）の `_store` を書き換える」という宣言です（詳しくは第 9 章）。
- 7 行目: `_store` がまだ `None` なら、8〜9 行目を実行します。
- 8 行目: `DATA_DIR`（データを置くフォルダの場所。説明用の名前）にディレクトリ（フォルダ）を作ります。`exist_ok=True` は「もうあってもエラーにしない」という指定です。**これはファイルの置き場所を作る操作で、環境を変えます。**
- 9 行目: 保存場所を開いて `_store` に入れます。これで次からは 7 行目の条件が偽になり、8 行目には来ません。
- 10 行目: 準備のできた `_store` を返します。
- 12 行目: ツールの登録です。`readOnlyHint=True` で「読むだけです」と申告しています。
- 13〜14 行目: ツール `list_memos` は、`_ensure_store()` を呼んで、メモの一覧を返します。
- 16〜18 行目: `main()` は、`mcp.run()` の**前に** `_ensure_store()` を呼んで、準備を済ませておきます。
- 20〜21 行目: 直接実行されたときは `main()` を呼びます（③ の形）。

#### 一歩ずつ — ③ と ④ で、何がいつ起きるか

**③ `python server.py` で起動したとき**

1. 一番上の文が実行され、`mcp` ができ、`_store` が `None` になります。
2. 20 行目の `if` が真なので、`main()` が呼ばれます。
3. `main()` の中で `_ensure_store()` が呼ばれ、8 行目でディレクトリが作られます。ここはまだ**ツールの受付の前**です。
4. `mcp.run()` で、サーバがツールの受付を始めます。
5. `list_memos` が呼ばれると、14 行目で `_ensure_store()` が呼ばれます。けれども `_store` はもう `None` ではないので、8 行目には届きません。

**④ `fastmcp run server.py:mcp` で起動したとき**

1. 一番上の文が実行され、`mcp` ができ、`_store` が `None` になります。
2. `__name__` は `"server_module"` なので、20 行目の `if` は偽です。`main()` は呼ばれません。
3. コマンドが `mcp` を取り出して動かし、サーバがツールの受付を始めます。ディレクトリはまだ作られていません。
4. **最初に** `list_memos` が呼ばれると、14 行目で `_ensure_store()` が呼ばれます。`_store` はまだ `None` なので、8 行目でディレクトリが作られます。
5. 2 回目からは、`_store` は準備済みなので、8 行目には届きません。

④ では、「読むだけ」と申告したツールの**最初の呼び出しで**、環境が変わります。
3.7 節の「実際に動かして確かめた結果」の表の ④ の列（準備がツールの 1 回目の中で走った）は、まさにこの流れです。

#### 決めたこと — D67 の 2

最終評価の判定では、この違いを次のように扱うと、学生が最終評価のデータを見る前に決めました（D67 の 2）。

| 初期化を先に済ませている場所 | 判定 | 理由（要約） |
|---|---|---|
| `main()` の中だけ、または `if __name__ == "__main__":` の中だけ | **到達する**（正になりうる） | 一番上の `mcp = FastMCP(...)` は、④ の `fastmcp run file.py:mcp` などで `main()` を通らずに起動できる。そのときは最初のツール呼び出しで初期化が走る |

| どこで先に済ませるか読み切れない | **不明** | |

#### なぜそう決めたのか

理由は 3 つあります。

1 つ目は、**「届きうる」なら数える**という、この研究の読み方に合わせるためです。
この研究は、モデルが決める値を「取りうる値の全体」で考えます（第 17 章の原理 3）。
起動の方法も同じで、「④ の起動がありうる」なら、その起動でツールの呼び出しが初期化に届く、と読みます。
クライアントは「読むだけ」の申告を見て確認を省くので、どれか 1 回の呼び出しで環境が変わるなら、申告は守られていません（D68 の 1 の理由。第 2 章 2.6 節）。

2 つ目は、**判定者の推測を入れないため**です。
「この木は実際には ③ で起動されているはずだ」と考え始めると、判定者ごとに答えが変わります。
だから、起動の方法は**コードだけから**決めます。
この規則は、その木が実際にどの形で起動されているかや、作者が ④ を想定していたかを問いません。

3 つ目は、**解析器に有利な側だけを採らないため**です。
この規則では、ccr（`main()` の形）は正になり、解析器に有利です。
一方、shyhurricane（lifespan の形）は誤のまま残り、解析器に不利です。
両方があることを論文に書きます。
「解析器に都合のよい規則を後から作った」と見られないように、規則が原理 3 から導かれたことも事前登録に書きます。
（出典: `docs/decisions.md:3800-3801`（D68 の 1 の理由）、`docs/drafts/final_judging_guide_draft.md:275`（起動の方法はコードだけから決める）、`:293-294`、`docs/open_questions.md:1214-1216`）

#### 解析器は直さない

この類の誤りは、解析器を直して減らすこともできそうに見えます。
けれども直しません（D67 の 2、O43）。
lifespan の形を正しく扱うには、「lifespan がツールより先に走る」「大域変数に値が入る」「別の場所で `None` に戻されない」「lifespan が失敗して値が入らないまま受付が始まることがない」の 4 つを全部確かめる必要があります。
1 つでも外すと、本当は届く操作を「届かない」と消してしまう誤り（誤 clear。第 21 章）を作ります。
しかも、v4 の結果を見て気づいた変更なので、「結果を元に解析器を変えない」（D66）に当たります。
だから、この類は解析器の設計の限界（誤警報の向き）として件数を報告します。
（出典: `docs/decisions.md:3777-3778`、`docs/open_questions.md:1207-1213`）

#### よくある誤解・つまずき

- **誤解: 「`main()` で初期化しているなら、ツールの呼び出しでは届かない」**
  D67 の 2 では「到達する」です。④ の起動では `main()` を通らないからです。
- **誤解: 「その木の README に『`python server.py` で起動する』と書いてあれば、④ は考えなくてよい」**
  起動の方法はコードだけから決めます。README の書き方で判定を変えません。
- **誤解: 「到達するなら、必ず正（違反）だ」**
  正になるには、もう 1 つの問い「宣言に反するか」にも「はい」と答える必要があります（第 48 章）。たとえば、初期化の中の操作がそもそも宣言に反しない動作なら、到達しても正にはなりません。
- **つまずき: 「`if _store is None:` の守りがあるから、たまにしか起きない」**
  「たまに」でも、ツールの呼び出しで届きうるなら到達するとします（D68 の 1）。何回目で起きるかは、条件の種類として記録します。
- **つまずき: 「初期化の後で、どこかで `_store = None` に戻していたら？」**
  戻した後のツールの呼び出しで、初期化に再び届きます。判定の手引きは、戻す箇所が無いかを検索で確かめるよう書いています（3.9 節の見分け方にも出てきます）。
（出典: `docs/drafts/final_judging_guide_draft.md:36-50`（2 つの問い）、`:289-290`（`None` に戻す形））

#### 手作業ではどう使うか

判定の手順 D（ツールの入口から効果までを自分でたどる段）で、道筋の途中に「一度だけ」の守り（`if self._x is None:`、`@lru_cache`、`global _initialized` など）を見つけたら、その初期化が**ツールの呼び出しより前に必ず済んでいるか**を確かめます。
確かめ方は、3.7 節の「探すもの 4 つ」で起動のしかたを読み、上の D67 の 2 の表のどの行に当たるかを決めることです。

1 行目（`main()` の中だけ）に当たって「到達する」としたときは、条件の種類の欄（`condition_type`）に **`起動の方法`** と書きます。
判定の手引きの条件の種類の表には、この `起動の方法` という行があり、「初期化が `main()` の中だけにあり、`main()` を通らない起動（`fastmcp run file.py:mcp` など）で届く」と書いてあります。
この種類は、主の数（A）には数え、併記の数（B）と（C）には数えません（(A)(B)(C) の意味は第 49 章）。

どこで先に済ませているかを 20〜30 分調べても読み切れなければ、「不明」にして理由を書きます。
（出典: `docs/drafts/final_judging_guide_draft.md:138-139`（手順 D の 4）、`:254`（条件の種類 `起動の方法`）、`:257`（主の数 A は条件を問わない）、`:535,541`（20〜30 分、起動の方法・初期化の場所が読み切れないときは不明））

#### この節のまとめ

「一度だけの初期化」の中の操作は、初期化がツールの受付より前に必ず済んでいるかで、到達するかが決まる。
D67 の 2: `main()`・`if __name__ == "__main__":` の中だけ → 到達する（④ で `main()` を通らないから）。lifespan・読み込み時 → 到達しない（E1）。読み切れない → 不明。起動の方法はコードだけから決める。
v4 では誤 14 件のうち 9 件がこの類（ccr 6・shyhurricane 3）。解析器は直さず、限界として報告する。

### 3.9 lifespan — サーバの起動時に 1 回だけ走る関数

#### 一言で言うと

**lifespan**（ライフスパン、「寿命」の意味）は、サーバを作るときに渡しておく関数で、**サーバがツールの受付を始める前に 1 回走り、サーバが止まるときに後片付けをします**。
どの起動の形（①〜④）でも、lifespan の準備はツールの受付より前に済みます。
だから、lifespan の中で済ませた初期化は、ツールの呼び出しでは届きません（3.8 節の表の 2 行目、誤の原因 E1）。

#### たとえ話 — シャッターの装置に組み込まれた準備

3.7・3.8 節の店のたとえを、もう一度使います。
今度の店では、シャッターの開閉の**装置そのもの**に、「シャッターを上げる前に、照明と空調を入れ、釣り銭の箱を出す」という手順が組み込まれています。
シャッターを閉めるときは、「釣り銭の箱をしまい、照明を消す」手順が自動で走ります。

この店では、店長が開けても（③）、本部の人が合鍵で開けても（④）、シャッターが上がる前に準備が必ず済みます。
誰が開けたかに関係なく、最初のお客さんが来たときには、もう釣り銭があります。

lifespan は、この「シャッターの装置に組み込まれた準備と片付け」です。
3.8 節の `main()` の中の準備は「店長が来たときだけする準備」でしたが、lifespan の準備は「シャッターの装置が必ずする準備」です。

#### 小さな例 — lifespan の形

```python
# 説明用
from contextlib import asynccontextmanager
from mcp.server.fastmcp import FastMCP

@asynccontextmanager
async def app_lifespan(server):
    db = open_database()      # (1) 起動時の処理（ツールの受付より前）
    try:
        yield {"db": db}      # (2) ここでサーバがツールの受付を始める
    finally:
        db.close()            # (3) 終了時の処理

mcp = FastMCP("x", lifespan=app_lifespan)   # ← サーバを作るときに渡す
```

#### 一歩ずつ — 1 行ずつの意味

- 2 行目: `contextlib` という Python に最初から入っている部品の箱から、`asynccontextmanager` という部品を持ってきます。
- 3 行目: `FastMCP` を持ってきます（3.3 節）。
- 5 行目 `@asynccontextmanager`: 次の関数に付ける名札（デコレータ）です。「この関数は、『入るときの処理』と『出るときの処理』を持つ形の関数です」という印です。
- 6 行目 `async def app_lifespan(server):`: lifespan の関数を作ります。名前は何でも構いませんが、`app_lifespan` や `lifespan` がよく使われます。`server` には、サーバの本体が渡されます。
- 7 行目: `open_database()`（説明用の名前。データベースにつなぐ関数だと思ってください）で、データベースにつなぎます。**`yield` より前**なので、これは起動時の処理です。
- 8 行目 `try:`: 「次の部分を実行し、途中で何があっても `finally:` の部分を最後に必ず実行する」という書き方の始まりです。
- 9 行目 `yield {"db": db}`: ここで lifespan は一度止まり、「準備ができました。サーバを動かしてください」と、サーバの側に制御を渡します。`{"db": db}` は、ツールから使えるように渡しておく値です（下の「ツールから lifespan の値を使う」）。サーバがツールの受付をしているあいだ、lifespan はこの行で待っています。
- 10 行目 `finally:`: サーバが止まるとき（クライアントが接続を閉じたときなど）、ここから先が実行されます。
- 11 行目: データベースとの接続を閉じます。終了時の処理です。
- 13 行目: `FastMCP("x", lifespan=app_lifespan)` のように、**サーバを作るときに `lifespan=` で関数を渡します**。これで、このサーバは起動のたびに `app_lifespan` を使います。

低レベルの書き方でも、`Server("x", lifespan=...)` と同じように渡せます。
（出典: SDK 1.30.0 の `mcp/server/fastmcp/server.py:186`（`FastMCP` の `lifespan` の引数）、`:142-153,228`（`FastMCP` は渡された lifespan を包んで低レベルの `Server` に渡す）、`mcp/server/lowlevel/server.py:137-155`（`Server` の `lifespan` の引数）、`:124-134`（何も渡さなければ、何もしない lifespan が使われる）。どれも repo の外のファイル）

#### 言葉の整理 — lifespan と、形だけ覚える 3 つの印

- **lifespan**（ライフスパン）
  - やさしい言い換え: サーバの「開店前の準備と閉店後の片付け」をまとめた関数。
  - 正確な定義: サーバを作るときに `lifespan=` で渡す関数。サーバはクライアントからの要求を読み始める前にこの関数に入り（`yield` の前を実行し）、止まるときに `yield` の後を実行する。
  - 例: 上の `app_lifespan`。
- `async`・`yield`・`@asynccontextmanager` は、**ここでは形だけ覚えてください**。
  - 「`@asynccontextmanager` が付いた `async def` の関数で、中に `yield` が 1 つある」のが lifespan の典型の形です。
  - `yield` の前が起動時の処理、`yield` の後（多くは `finally:` の中）が終了時の処理です。
  - それぞれの正確な意味は第 9 章で説明します。

#### lifespan はいつ走るのか — コードと実験で確かめる

**大事なのは、lifespan がいつ走るか**です。
SDK 1.30.0 のコードでは、サーバは次の順で動きます。

1. `mcp.run()` が呼ばれると、標準入出力の通り道を用意して、低レベルの `Server` の `run` に進みます。
2. `Server` の `run` は、まず **lifespan に入ります**（663 行）。ここで `yield` の前の処理が実行されます。
3. その後で、クライアントから届いた要求を 1 つずつ読んで処理する繰り返しが始まります（681 行）。`tools/list` も `tools/call` も、この繰り返しの中で処理されます。

lifespan に入る行が、要求を読む繰り返しより**前**にあります。
だから、**どの起動の形（①〜④）でも、lifespan の起動時の処理は、ツールの呼び出しより前に必ず済みます**。
④ の `mcp run` も、最後はサーバの `run` を呼ぶので同じです。
（出典: SDK 1.30.0 の `mcp/server/fastmcp/server.py:311-312`（`run` は `run_stdio_async` へ）、`:769-776`（`run_stdio_async` は低レベルの `Server` の `run` へ）、`mcp/server/lowlevel/server.py:662-681`（663 行で lifespan に入り、681 行から要求を読む）。repo の外のファイル）

本記録者は、これを実際に動かしても確かめました（3.7 節と同じ実験。lifespan の中にも記録の行を入れた）。
記録に残った順番の全体は次のとおりです。

| 順 | ③ `python server.py` | ④ `mcp run server.py:mcp` |
|---|---|---|
| 1 | 一番上の文 | 一番上の文 |
| 2 | `main()` に入った | — |
| 3 | 準備が走った（`main()` から） | — |
| 4 | **lifespan の起動時の処理** | **lifespan の起動時の処理** |
| 5 | ツールの 1 回目 | 準備が走った（ツールの 1 回目の中から） |
| 6 | ツールの 2 回目 | ツールの 1 回目 |
| 7 | lifespan の終了時の処理 | ツールの 2 回目 |
| 8 | | lifespan の終了時の処理 |

表の読み方: 4 行目を見てください。③ でも ④ でも、lifespan の起動時の処理は、ツールの 1 回目より前に走っています。
一方、`main()` の中の準備（2〜3 行目）は ④ では走らず、④ では準備がツールの 1 回目の中にずれ込んでいます（5 行目）。
もしこの準備を `main()` ではなく lifespan の中に書いていたら、④ でも 4 行目の時点で済んでいたことになります。
この実験は、本記録者が repo の外の作業用の場所で、公式 SDK 1.30.0 を使って 2026-10-01 に行ったもので、repo には残していません。演習 3-3 では、同じ順番の仕組み（lifespan に入ってから要求を読み始める）を、MCP のパッケージを使わない小さなプログラムで確かめます。

#### 細かい注意 — 標準入出力と HTTP の違い

標準入出力（stdio）で起動したときは、lifespan はプロセスの起動時に 1 回走ります。
HTTP で待ち受ける形では、SDK 1.30.0 のコードを読む限り、接続（セッション）ごとに、または「状態を持たない」設定では要求ごとに、lifespan を含むサーバの `run` が呼ばれます。
**どちらの場合も「その接続でのツール呼び出しより前に走る」ことは同じ**なので、判定の規則（lifespan の中の初期化はツールの呼び出しでは到達しない）には影響しません。
`fastmcp` パッケージの側での細部は、本記録者は確かめていません。
（出典: SDK 1.30.0 の `mcp/server/streamable_http_manager.py:238`（状態を持たない設定では要求ごとに `run`）、`:367`（接続ごとに `run`）。repo の外のファイル）

lifespan が `yield` で渡した値（上の小さな例の `{"db": db}`）は、ツールの中から次の節の `ctx` を通じて取り出せます。
公式 SDK 1.30.0 では `ctx.request_context.lifespan_context["db"]` のように書きます。
本記録者の実験でも、ツールの中から lifespan が渡した値をこの形で読めました。
`fastmcp` 4.0.10 には、短く `ctx.lifespan_context` と書ける形もあります。
（出典: SDK 1.30.0 の `mcp/shared/context.py:24`（`lifespan_context` の欄）、`mcp/server/fastmcp/server.py:1188-1195`（`ctx.request_context`）、`fastmcp` 4.0.10 の `fastmcp/server/context.py:417-451`。repo の外のファイル）

#### なぜ lifespan がこの研究で大事なのか

lifespan は、判定の**誤の原因 E1**（起動時の初期化をツールの経路に数えた解析器の誤り。lifespan・import 時）の**中心の言葉**です。
判定の手引きの誤の原因の表では、E1 の例として v4 の shyhurricane が挙がっています。
v4 の中間検証で、起動時の初期化の類は v3 では見えなかった新しい類として現れ、「最終評価のデータでも同じ類が出る可能性が高い」と記録されています。
第 3 版の教科書では、lifespan という言葉が説明なしに出てきていました（第 3 版 2011 行）。
第 4 版ではここで説明し、第 49・51 章で判定の規則として使います。
（出典: `docs/drafts/final_judging_guide_draft.md:429`（E1）、`docs/open_questions.md:1223`（最終評価でも出る可能性が高い））

#### よくある誤解・つまずき

- **誤解: 「lifespan があるサーバなら、初期化の類は全部 E1（到達しない）」**
  E1 になるのは、その初期化を**lifespan の中で**済ませているときだけです。lifespan があっても、問題の初期化を lifespan が呼んでいなければ、3.8 節の表のほかの行で決めます。
- **誤解: 「lifespan の中で呼んでいれば、どんな書き方でも到達しない」**
  判定の手引きは、lifespan が初期化を**必ず**済ませるかも見る、と書いています。lifespan の中の呼び出しが条件つきなら、条件が偽のときはツールの呼び出しで届くので「到達する」です。また、lifespan の中で失敗しても受付が始まってしまう形（失敗を握りつぶして先に進む形）も、注意して見ます。
- **誤解: 「一度済んだ初期化は、二度と走らない」**
  初期化が済んでいても、その後にどこかで `None` に戻す（`_memory = None`）なら、ツールの呼び出しで再び届きます。戻す箇所が無いかを検索で確かめます。
- **誤解: 「lifespan は、サーバの一生で必ず 1 回だけ走る」**
  標準入出力ではそうですが、HTTP では接続ごと（または要求ごと）に走ります。どちらでも「ツールの呼び出しより前」であることは変わりません。
- **つまずき: 「`async` や `yield` が分からないので、lifespan の中が読めない」**
  判定で要るのは「`yield` より前か後か」だけです。`yield` より前に書いてあれば起動時、後（`finally:` の中など）なら終了時です。
（出典: `docs/drafts/final_judging_guide_draft.md:286-291`（見分け方）、`docs/open_questions.md:1207-1211`（4 つの確かめごと））

#### 手作業ではどう使うか — lifespan の見分け方

3.8 節の判定で、「初期化を先に済ませているのは lifespan か」を確かめるときは、判定の手引きの見分け方に従います。

1. **lifespan を探す**: `FastMCP(` や `Server(` の引数の `lifespan=` を探し、渡している関数（多くは `@asynccontextmanager` の付いたもの）の中を見ます。木の中を検索するなら `grep -rn "lifespan=" <木>` です。
2. **必ず済ませるか**: lifespan の中で、問題の初期化を `yield` より前に、条件なしで呼んでいるかを見ます。例外で抜けたら受付が始まらない形か、失敗しても先に進む形かも見ます。
3. **`None` に戻す箇所が無いか**: 初期化した変数（`_memory` など）に、後で `None` を入れ直している行が無いかを検索します。
4. **ツールの道筋が初期化を呼ぶか**: ツールの道筋が初期化を呼ばない（守りの `if` が無い）なら、そもそもその効果はツールの道筋ではないので、手順 D で確かめ直します。

1〜3 で「lifespan が初期化を必ず済ませ、その後で戻されない」と確かめられたら、3.8 節の表の 2 行目にあたり、その件は「到達しない」（誤、原因 E1）です。
lifespan の中の呼び出しが条件つきで、条件が偽のときにツールの呼び出しで届くなら「到達する」です。
どこで先に済ませるかが読み切れなければ、「不明」にして理由を書きます。
（出典: `docs/drafts/final_judging_guide_draft.md:284-291`、`docs/final_evaluation_procedure.md:957-964`）

#### この節のまとめ

lifespan は `FastMCP(..., lifespan=...)` に渡す関数で、`yield` の前が起動時の処理、後が終了時の処理。形は「`@asynccontextmanager` の付いた `async def` で、中に `yield` が 1 つ」。
サーバは lifespan に入ってから要求を読み始めるので、どの起動の形でも、lifespan の起動時の処理はツールの呼び出しより前に必ず済む（SDK 1.30.0 のコードと実験で確かめた）。
lifespan の中で必ず済ませた初期化は「到達しない」（誤の原因 E1）。条件つき・`None` に戻す形・失敗しても進む形は別に確かめる。

### 3.10 ctx — クライアントへの連絡口

#### 一言で言うと

ツールの関数は、`Context` という型の引数（慣習で `ctx` という名前）を受け取れます。
`ctx.info(...)` や `ctx.report_progress(...)` は、**クライアントへの通知**です。
ファイルにもデータベースにも書かないので、**環境を変えません**。判定では「反しない」と扱います。

#### たとえ話 — 宅配の「ただいま配達中」の通知

荷物を頼むと、スマートフォンに「ただいま配達中です」「あと 3 件で到着します」と通知が来ることがあります。
この通知は、配達の仕事そのものではありません。
通知が来ても来なくても、荷物の中身や、あなたの家の中は何も変わりません。
変わるのは、あなたのスマートフォンの画面に 1 行の知らせが出ることだけです。

`ctx.info` や `ctx.report_progress` は、この「配達中の通知」にあたります。
ツール（配達員）が、クライアント（荷物を頼んだ人のアプリ）に「今こういう状態です」と知らせるだけです。

#### 小さな例

```python
# 説明用
from mcp.server.fastmcp import FastMCP, Context

mcp = FastMCP("notes")

@mcp.tool()
async def search(query: str, ctx: Context) -> str:
    await ctx.info(f"検索中: {query}")          # クライアントへの通知（ログのメッセージ）
    await ctx.report_progress(50, 100)          # 進み具合の通知（100 のうち 50）
    ...
```

#### 一歩ずつ — 1 行ずつの意味

- 2 行目: `FastMCP` と一緒に、`Context` という部品を持ってきます。
- 4 行目: サーバの本体を作ります。
- 6 行目: ツールの登録です（3.3 節）。
- 7 行目 `async def search(query: str, ctx: Context) -> str:`: 引数が 2 つあります。`query` は LLM が決める検索の言葉です。`ctx: Context` は、「`ctx` という引数には `Context` 型の値が入る」という目印です。**この `ctx` は、LLM が決める値ではなく、サーバが自動で渡す値です。**
- 8 行目 `await ctx.info(f"検索中: {query}")`: クライアントに「検索中: …」というログのメッセージを送ります。`f"…{query}…"` は、文字列の中に `query` の値を埋め込む書き方です。`await` は、`async` の関数の中で「この処理が終わるまで待つ」と読みます（第 9 章）。
- 9 行目 `await ctx.report_progress(50, 100)`: クライアントに「100 のうち 50 まで進みました」と送ります。
- 10 行目 `...`: 検索の本体（省略）。

#### 実際に確かめたこと

3.7・3.9 節と同じ実験で、本記録者はツールの中で `await ctx.info("pinging")` を呼びました。
その結果、次の 2 つを確かめました。

1. `tools/list` の返事の引数の形（`inputSchema`）には、ツールのふつうの引数（実験では `q` という文字列の引数）だけが載り、`ctx` は載りませんでした。つまり、LLM には `ctx` という引数があることすら見えません。
2. クライアントの側に、`"pinging"` というログの通知が、ツールを呼んだ回数（2 回）だけ届きました。

SDK 1.30.0 のコードでも、同じことが書いてあります。
ツールを登録するときに `Context` 型の引数を見つけ、引数の形を作るときに除いています。
`ctx.info`・`ctx.debug`・`ctx.warning`・`ctx.error` は、どれも「クライアントにログのメッセージを送る」関数を呼び、`ctx.report_progress` は「進み具合の通知」を送ります（クライアントが進み具合の知らせを求めていないときは、何も送らずに戻ります）。
MCP の決まりでは、ログの通知は `notifications/message`、進み具合の通知は `notifications/progress` という名前の通知です。
（出典: SDK 1.30.0 の `mcp/server/fastmcp/tools/base.py:69-74`（`Context` の引数を見つけて引数の形から除く）、`mcp/server/fastmcp/server.py:1299-1319`（`log` は「Send a log message to the client.」）、`:1376-1390`（`info`・`debug`・`warning`・`error`）、`:1197-1216`（`report_progress`。求められていなければ送らないのは 1205〜1208 行）、`mcp/types.py:1415-1418`（`notifications/message`）、`:745-751`（`notifications/progress`）。どれも repo の外のファイル）

#### 言葉の整理 — Context と通知

- **Context**（コンテキスト、ctx）
  - やさしい言い換え: ツールの中から使える「クライアントへの連絡口」。
  - 正確な定義: ツールの関数が `Context` 型の注記を付けた引数を持つと、サーバが呼び出しのたびに自動で渡す値。クライアントへの通知の送信、lifespan の値（3.9 節）の取り出しなどができる。
  - 例: `ctx.info("検索中")`、`ctx.request_context.lifespan_context["db"]`。
- **通知**（ノーティフィケーション）
  - やさしい言い換え: 返事を求めない「お知らせ」。
  - 正確な定義: MCP で、相手に返事を求めずに送る文。要求（`tools/call` など）と違って、`id` を持たない。
  - 例: ログの通知 `notifications/message`、進み具合の通知 `notifications/progress`。

（出典: SDK 1.30.0 の `mcp/types.py:161-165`（通知は「返事を求めない」もので、`id` の欄が無い）。repo の外のファイル）

#### なぜ「反しない」と言えるのか

第 4 章で見る「読むだけ」の宣言（`readOnlyHint: true`、D1）について、判定で問うのは「その動作は、呼び出しの後に残る何かを変えるか（ホストのファイル・DB・相手のサーバの状態・残る設定）」です。
`ctx.info` が送るのは、クライアントへの 1 行の知らせです。
サーバのファイルにも、データベースにも、相手のサーバにも書きません。
だから、判定の手引きは「クライアントへの通知（`ctx.info()` / `ctx.report_progress()`）: 環境を変えないので反しない」と書いています。
（出典: `docs/drafts/final_judging_guide_draft.md:305`（D1 の問い）、`:325`（クライアントへの通知）、`docs/final_evaluation_procedure.md:998`）

#### よくある誤解・つまずき

- **誤解: 「`ctx.info` はログを書くので、ログファイルへの書き込みだ」**
  「ログ」という言葉に引っぱられないでください。`ctx.info` は、ファイルではなくクライアントへ送る通知です。ファイルに書くログ（Python の `logging` の出力先がファイルのもの）は別の話で、判定の手引きでは「`logging` の出力先がファイルなら反する。出力先の設定を確かめる」と別の行で扱っています（第 9 章・第 50 章）。
- **誤解: 「`ctx` も引数なので、LLM が決める値だ」**
  `ctx` はサーバが自動で渡す値で、`tools/list` の引数の形にも載りません。第 2 章の「引数は信用できない」は、`ctx` には当てはまりません。
- **誤解: 「引数の名前が `ctx` でなければ Context ではない」**
  名前は何でも構いません。`Context` 型の注記が付いていれば Context です。SDK 1.30.0 の説明文にも「引数の名前は、Context の注記が付いていれば何でもよい」とあり、例では `context` という名前も使っています。
- **誤解: 「`ctx` を使うツールは、何か特別なことをしている」**
  `ctx` は連絡口にすぎません。ツールが環境を変えるかどうかは、`ctx` 以外の行（ファイル・DB・HTTP・プロセスの起動など）で決まります。
- **つまずき: 「`ctx` のほかの機能に出会った」**
  この章で扱ったのは、通知（`info` などと `report_progress`）と lifespan の値の取り出しだけです。ほかの機能に出会ったら、その機能が何をするかを確かめてから判断します。
（出典: SDK 1.30.0 の `mcp/server/fastmcp/server.py:1163`（引数の名前は何でもよい）、`:499-500`（`context` という名前の例）、`docs/drafts/final_judging_guide_draft.md:323`（`logging` の出力先））

#### 手作業ではどう使うか

「読むだけ」と申告したツールを読んでいて `await ctx.info(...)` や `await ctx.report_progress(...)` の行に出会ったら、その行は「反しない」と読んで先に進みます。
見落としの判定（第 52 章）で、ツールの中に宣言に反する動作があるかを自分で探すときも同じです。
ただし、**同じツールの中のほかの行**は、それぞれ確かめます。
たとえば、`ctx.info` で「保存しました」と通知していても、その前の行で本当にファイルに書いていれば、その書き込みは環境を変えます。
通知の文面ではなく、コードの動作で決めます。

#### この節のまとめ

ツールは `Context` 型の引数（慣習で `ctx`）を受け取れる。`ctx` はサーバが自動で渡し、LLM には見えない。
`ctx.info()`・`ctx.report_progress()` などはクライアントへの通知で、環境を変えない。判定では反しない。
ファイルに書くログ（`logging` の出力先がファイル）は別の話（第 50 章）。

- `ctx.info()`・`ctx.report_progress()` はクライアントへの通知で、環境を変えない。`ctx` はサーバが自動で渡し、LLM には見えない。
