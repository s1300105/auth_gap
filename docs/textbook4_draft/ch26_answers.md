### 第 26 章

この章の答えは、`docs/decisions.md` の D70 の 3・D71 とその訂正、`docs/implementation_base_survey.md`、`docs/llm_judgment_survey.md`、`docs/open_questions.md` の O45・O46 を元にしています（本書の執筆時に確かめたもの）。
調査の報告は agent（AI）の出力で、論文の PDF は 1 本も直接読めていません。論文に使う前に、学生が原典で確かめます。
論文の文面の例は本書の例文で、実際の文面は学生が決めます。

#### 演習 26-1（置き換えられない部品）

置き換えられない部品は 4 つあります（D71、`docs/decisions.md:3886-3889`）。そのうち 2 つを挙げれば正解です。

- **MCP の入口**: どの関数が「LLM から呼ばれるツール」なのかは、`@mcp.tool()` などの MCP 固有の 14 の規則（第 12 章）で決まります。既存の道具はこれを知りません。実際、CodeQL の既定のクエリは source を Web の入口（Flask・FastAPI など）に置き、MCP のツールの引数を source にしませんでした（`docs/preregistration.md:612-616`、D26）。
- **宣言の読み取り**: `ToolAnnotations(readOnlyHint=True)` のような MCP の宣言を読む部品（第 16 章）は、既存の道具にありません。
- **宣言と効果の照合**: 効果が宣言に反するかを 4 つの原理と判定表で決める部品（第 17 章）は、この研究の問いそのものです。
- **解析できなかったものを理由つきで残すこと**: `opaque(reason)` の 8 語や打ち切りの記録で、決められなかったものを分母に残します（D40）。既存の道具は、解析できなかったものを報告から黙って消します。研究の問いが「宣言がどれだけ当てにならないか」という率なので、これが無いと率が出せません。

置き換えられる部品の例: **呼び出しの追跡**（第 15 章。CodeQL・Pysa・PyCG・Joern など）。
置き換えるなら、気をつけることがあります。その道具が、呼び出し先を解決できなかったときにどうするかです。黙って経路を落とす道具だと、「解決できなかった」という情報が消え、AuthGap の「不」として数えられなくなります。置き換えた部品が `opaque(unresolved)` にあたる情報を返せるかを確かめる必要があります（この最後の文は本書の説明です）。
もう 1 つの例: **値の出どころの追跡**（taint 解析）や**効果の語彙の一部**。ただし語彙は、CodeQL の sink の集合と AuthGap の語彙（git の操作の `cwd` など）が一致しないことが、入口を揃えた比較で分かっています。

#### 演習 26-2（人の判定で LLM を使わない理由）

**理由 1（D70 の 3 に書かれた理由）**: 判定に LLM を混ぜた先行研究は、決められないものを黙って消すか、どちらかに倒しています。答えが揺れ、モデルで結果が変わります（調査 §2.3）。この研究の芯（不明を数える、D40）と、決定性の主張を守るために使いません（`docs/decisions.md:3849-3852`）。

**理由 2（本記録者の範囲）**: 「評価データを本記録者が一度も見ない」という約束があります（D60 の 2、D66 の 3）。この repo の文脈を読み込んだ Claude を判定の補助に使うと、本記録者が評価のデータを見ることになり、約束と字義の上でぶつかります。判定に AI を一切使わない（O45 の案 (a)）ことで、このぶつかりが無くなります（`docs/llm_judgment_survey.md:179-181`、`docs/open_questions.md:1259-1263`）。

**「行を探すだけなら」への答えの例**: D70 の 3 は、原ソースを読む補助にも使わないと決めています。行を探すのは、grep やエディタの検索、「定義へ移動」のような決定的な道具でできます。AI に「この関数は lifespan の中か」と聞けば、行の位置の答えの中に「だから起動時の初期化だ」という判断が混ざりやすく、補助と判断の線が曖昧になります。それに、どの AI でも使えば、本記録者の範囲をどう定義するかという問題がまた出てきます。（後半の 2 文は本書の整理です。）

#### 演習 26-3（2 つの文の書き分け）

**(1)** 例:

- 性質の文:「解析器は Python の標準ライブラリの `ast` だけで実装し、判定に LLM を使わない。同じ入力に対して出力は決定的である（3 回の実行でバイト単位で一致）」。
- 開示の文:「解析器の実装、最終評価の手順書と判定の手引きの下書き、設計の決定の推奨には AI（LLM）を用いた。凍結した解析器の中間検証（v4）の判定も AI が行い、その数値は本論文の評価には用いない。最終評価の判定は著者 1 名が行い、判定・原ソースの読解・記録のいずれにも AI を用いていない」。

**(2)** 事実と違います。研究の遂行（解析器の実装、v4 の判定、手順書と手引きの下書き、決定の推奨、コミットの共著者）には AI を使っています（`docs/llm_judgment_survey.md:157-168`）。「LLM を使っていない」と書くと、開示すべきこと（O45 の 4）を隠すことになり、後で分かったときに研究全体の信用を損ないます。

**(3)** 答えの例:「解析器のコードを書く作業には AI を使いましたが、そのコードは凍結され（`analyzer-freeze-3`、指紋 `35606ba9…`）、走るときには LLM を一度も呼びません。解析器は標準ライブラリだけで書かれ、同じ入力に対して出力は決定的です。誰でも、凍結した版と Python の版を揃えて走らせれば、同じ出力を確かめられます。『作り方』に AI を使ったことは方法の節で開示していますが、『判定』に LLM は使っていません」。

#### 演習 26-4（O46 が確かめられたら）

**(1)** 変わるのは、**先行研究との差別化の書き方**です。仕様書の差別化の軸 2（判定の決定性）は、「最も近い 4 件のうち 3 件が LLM を判定経路に置く」から「4 件とも置く」になり、むしろ強まります。MCP-BiFlow の公表結果と対ごとに並べる比較の計画（仕様書 787・810 行）の書き方にも影響します（`docs/open_questions.md:1274-1275`）。
変わらないのは、**AuthGap の測定の結果**（矛の精度、木の割合、見落とし、不の中身）です。O46 は他の研究の読み方の話で、AuthGap の解析器も判定も変えません。

**(2)** 書き換えません（規則 6。仕様書本体は設計の記録として残す）。確かめた結果は `docs/related_work.md` に、どの版のどの節を読んだかと一緒に書きます。O46 の状態も、確かめた結果に合わせて更新します。

**(3)** 使えるのは、「**LLM が、本来なら決められない候補を棄却に変え、その正しさを人で確かめていない例**」としてです（C1 §1-9。`docs/llm_judgment_survey_raw/C1_validity.md:108-113`）。付記の対比表（26.8 節）の 1 つのセルの材料にもなります。
使えないのは、「人が判定しても 35% は決まらない、だから不明を数える設計は正しい」という**傍証**としてです。M3（LLM）を外すと未解決と棄却の数が動くので、レビューの結果のラベル自体が LLM の段に依存しているからです。
どちらの使い方でも、写しを原本と照らしてからにします。

#### 確認問題 26-1

**変わったもの**: 論文の理由づけ。「新しい分野では自前の解析が多い」をやめ、3 つの層（言語の水準は割れている / 分野固有の部分は例外なく自作 / AuthGap は「既存のパーサ + 自作の解析」の系譜）で言い直し、自前の理由は AuthGap 自身の 3 つ（前身の Pysa の失敗、解析できなかったものを理由つきで数える、標準ライブラリだけで再現できる）で示すことにした。「みんな自前だから」とは書かない。
**変わらなかったもの**: 決定（自前のまま）。解析器も凍結のまま（`analyzer-freeze-3`）。
（出典: `docs/decisions.md:3906-3923`。）

#### 確認問題 26-2

PPI は、項目が互いに独立に同じ分布から選ばれている（i.i.d.）ことを前提にしています。
最終評価の抜き取りは、矛が「宣言ごとに最大 200 木 × 1 木 3 件まで」、見落としと不の中身が「1 木 1 件」で、木を単位にしたまとまり（クラスタ）で選びます。同じ木から選んだ組は、同じ作者・同じ書き方のコードなので、互いに独立ではありません。
しかも主指標は木の単位の割合で、下限として報告するものです。だから、そのまま PPI に乗せられません。
（出典: `docs/llm_judgment_survey.md:115`、`docs/llm_judgment_survey_raw/C1_validity.md:100-105`。）

#### 確認問題 26-3

確かめていたのは AgentFlow の**上の層**（ADG という自作のグラフ）で、その**下の土台**ではありませんでした。土台は YASA（Ant Group の多言語の taint 解析）とされ、AgentFlow は「自前」ではなく「YASA の上」です。ただし、YASA の上だという情報は検索の要約だけで、本文は読めておらず、確かさは低です。
誤りの向きは、「新しい分野では自前が多い」という主張を強く見せる向きでした。
（出典: `docs/decisions.md:3915-3916`、`docs/implementation_base_survey.md:55,120`。）

#### 確認問題 26-4

**問題**: D60 の 2 は「評価データを本記録者が一度も見ない」と約束し、D66 の 3 は本記録者が見た v4 を最終評価から除いています。ところが「本記録者」の範囲は定義されていませんでした。最終評価で学生がこの repo の文脈（`CLAUDE.md`・decisions・v4 の判定）を読み込んだ Claude を読む補助に使うと、本記録者が評価のデータを見ることになり、約束と字義の上でぶつかります。
O45 は、(a) 読む補助を使わない、(b) repo の文脈を持たない別の実行に限る、(c) 本記録者の範囲を定義して別のセッションとして開示する、の 3 案を挙げていました。
**解消**: D70 の 3 で、最終評価の判定では AI（LLM）を一切使わない（読む補助にも使わない）と決めました。これは案 (a) にあたり、本記録者が評価のデータを見る場面が無くなるので、範囲を定義しなくても約束とぶつかりません。
（出典: `docs/llm_judgment_survey.md:179-181`、`docs/open_questions.md:1259-1263`、`docs/decisions.md:3852-3854`。）
