### 29.2 O30 — テストのファイルに結び付く

#### 一言で言うと

受け手の型が分からない呼び出しを、名前の最後の部分（末尾名）だけで木の中から探すと、**テストのファイル**の中の同じ名前の関数に結び付いてしまうことがありました。
実行中のツールがテストのコードを呼ぶことは無いので、**テストのファイルの定義は候補から外す**ようにしました。

#### たとえ話 — 電話帳で同じ名前の人に電話する

「田中さんに連絡して」と頼まれたけれど、どの田中さんか分からないとします。
電話帳をめくると、田中さんは 2 人いました。
1 人は会社の取引先の田中さん、もう 1 人は**避難訓練の練習用の名簿**に載っている架空の田中さんです。

練習用の名簿の田中さんに電話しても、本当の用事は伝わりません。
練習用の名簿は、本番では使わないものだからです。
だから、「本番の連絡では、練習用の名簿を探さない」と決めておきます。

テストのファイルは、プログラムの「練習用の名簿」です。
本番で動くツールが、テストのファイルの中の関数を呼ぶことはありません。

#### 小さな例 — xagent の形をまねた作例

第 27 章で見た xagent の連鎖を、小さくまねた作例です。

```python
# app.py
 1  import logging
 2  from mcp.server.fastmcp import FastMCP
 3
 4  mcp = FastMCP("tasks")
 5  logger = logging.getLogger(__name__)
 6
 7
 8  @mcp.tool(annotations={"idempotentHint": True})
 9  def run_task(name: str) -> str:
10      logger.error("failed: %s", name)
11      return "ok"
```

```python
# tests/test_app.py
1  class _Recorder:
2      def error(self, msg, *args):
3          with open("recorded.log", "a") as f:
4              f.write(msg)
```

行ごとに何をしているかを書きます。

- `app.py` の 5 行目: Python の標準のログの道具から、記録係（`logger`）をもらいます。
- 8 行目: ツールの宣言です。`idempotentHint: True`（D4、「同じ引数で繰り返しても追加の効果が無い」）と申告しています。
- 10 行目: エラーのログを書きます。本物の `logger.error` は、Python の標準のログの道具の中のメソッドです。
- `tests/test_app.py` の 1〜4 行目: テストのために作った記録係の偽物 `_Recorder` です。`error` という同じ名前のメソッドを持ち、呼ばれるとファイル `recorded.log` に追記します。

解析器は `logger` の型（標準のログの道具）を受け手の型として知らないので、`error` という末尾名で木の中を探します。
すると、テストのファイルの `_Recorder.error` が見つかります。

凍結版の解析器と、直す前の解析器（run13 の版、`c3a8c0c`）で走らせた結果です。

| 解析器 | `run_task` の効果 | D4 の答え |
|---|---|---|
| 直す前（`c3a8c0c`） | FS_WRITE 1 件（`tests/test_app.py` の 3 行の `open`、道筋 `_Recorder.error`、確度 `opaque`） | **矛**（理由 `fs_append`） |
| 凍結版 | 効果なし | 何も出ない |

表の読み方: 1 行目は「直す前の解析器は、`logger.error` をテストのファイルの `_Recorder.error` に結び、その中の追記の `open` をツールの効果として数えた。追記は繰り返すと重なるので、D4 に対して矛になった」と読みます。

#### 一歩ずつの説明 — 直した規則（§9.1）

規則は次のとおりです。

> 型の裏付けの無い末尾名の解決（木全体の名前検索）では、**呼び出し元がテストのファイルでなければ、テストのファイルの定義を候補から外す。**

「テストのファイル」は、次のどれかに当てはまるファイルです。

- パスの途中に `tests`・`test`・`testing` という名前のディレクトリがある。
- ファイル名が `test_*.py`・`*_test.py`・`conftest.py` である。

これを判定するコードです。

```python
# authgap/srcindex.py:364-377（説明の文字列は省略）
TEST_DIR_NAMES: frozenset[str] = frozenset({"tests", "test", "testing"})


def is_test_path(relpath: str) -> bool:
    parts = relpath.replace("\\", "/").split("/")
    if any(p in TEST_DIR_NAMES for p in parts[:-1]):
        return True
    name = parts[-1]
    return name == "conftest.py" or (name.startswith("test_") and name.endswith(".py")) or name.endswith("_test.py")
```

- 1 行目: テストのディレクトリの名前の集まり（`tests`・`test`・`testing`）を、変えられない集合として決めます。
- 4 行目: ファイルの相対パス（木の根からの道のり）を受け取り、テストのファイルなら真を返す関数です。
- 5 行目: パスの区切りを `/` にそろえてから、`/` で区切って部品に分けます。`tests/core/test_x.py` なら `["tests", "core", "test_x.py"]` です。
- 6・7 行目: 最後の部品（ファイル名）を除いた部品のどれかが、テストのディレクトリの名前なら、真を返します。
- 8 行目: 最後の部品（ファイル名）を取り出します。
- 9 行目: ファイル名が `conftest.py`、または `test_` で始まり `.py` で終わる、または `_test.py` で終わるなら、真を返します。

この関数を使って、木の中から集めた候補を絞ります。

```python
# authgap/val/engine.py:992-993
if scope is not None and not is_test_path(scope.relpath):
    cands = [c for c in cands if not is_test_path(c.relpath)]
```

- 1 行目: 呼び出し元（`scope`）があり、しかも呼び出し元がテストのファイルで**なければ**、
- 2 行目: 候補（`cands`）から、テストのファイルにある定義を取り除きます。

（出典: `authgap/srcindex.py:364-377`、`authgap/val/engine.py:992-993`、`docs/contradiction_principles.md:269-281`（§9.1））

#### 一歩ずつの説明 — 変えなかったもの

規則は、変えないものもはっきり決めています。

- **呼び出し元がテストのファイルのとき**: テストのファイルの中で定義されたツールもあるからです。v2 の mcp-linkedin には、テストのファイルの中で定義されたツールが 9 件ありました。そのツールから呼ぶ先では、テストのファイルの定義も候補に残します。
- **import の表で明示的に結ばれた定義**: `from tests.helpers import f` と書いてあれば、そのとおりに結びます。名前だけで探したのではないからです。
- **受け手の型で裏付けられた解決**: 型が分かっていれば、その型のメソッドに結びます。
- **ユニットの発見**: テストのファイルの中のツールも、今までどおりユニットにします。
- **候補が 1 つだけ残るとき**: テストの候補を外した結果、本体の候補が 1 つだけ残れば、今までどおり末尾名で降ります（確度に `opaque(unresolved)` を合流する。第 15 章）。

（出典: `docs/contradiction_principles.md:274-281`）

#### なぜそうするのか — 実行時に届かない場所を、候補にしない

規則の根拠は 1 文です。
「実行中のツールのコードがテストのモジュールに届くことは無い（テストは実行時に import されない）。届くのは、ツール自体がテストのファイルで定義されているときだけ」。

一方で、第 15 章で学んだとおり、末尾名の解決を「やめる」と、本当の経路が消えてしまいます（`CLAUDE.md` の落とし穴「末尾名だけの解決を『やめる』と真の経路が消える」）。
だから、末尾名の解決そのものはやめず、**実行時に届かないと分かっている場所だけ**を候補から外しました。
解決を狭める変更なので、消える経路は `compare_scans.py` で 1 件ずつ見る、と O30 の段階で決めていました。

#### 直した結果

run13 → run14 で、**効果の位置が 1,010 件消えました。すべて xagent** のものでした。
xagent の run13 の経路を見ると、**すべての経路が、テストのファイルにしか無い定義を経由していました**（効果の場所はテストのファイル 322、本体 688）。
効果のある（危険な）ユニットも 247 減りましたが、これも xagent の、この連鎖でしか効果の無かったツールでした。
矛の組は、O30 で効果ごと消えたものが 6 件（xagent の `fs_append` 5・`db_model_sql` 1）でした。

較正対（第 8 章）の効果の行も突き合わせました（`diff_effects`）。
A9（praisonai）で 1 行消えて 1 行増えました。

- **消えた行**: tts のツール → `AudioAgent.speech` → テストの偽物 `MockSpeechResponse.stream_to_file`（`tests/test_audio_agent.py`）。本物の `response.stream_to_file` は OpenAI の SDK の中でファイルを書きますが、sink の表に無いので**もともと追えていない効果**で、テストの偽物を経由して**偶然当たっていた**ものでした。
- **増えた行**: テストの候補が外れて、本体の候補（`examples/` の `EXASearchTool.results`）が 1 つだけ残ったもの（確度 `opaque(unresolved)`）。

（出典: `docs/decisions.md:3086-3090`（diff_effects）、`:3105-3108`（消えた効果と矛））

#### よくある誤解・つまずき

- **誤解: 「テストのファイルは解析しなくなった」**
  解析します。テストのファイルの中で定義されたツールは、今もユニットになります。外したのは、本体のコードからの末尾名の解決の**候補**だけです。
- **誤解: 「消えた A9 の行は、本物の効果だったのに消えた（誤 clear）」**
  偶然当たっていただけで、本物の効果（SDK の中の書き込み）は、もともと sink の表に無く追えていませんでした。テストの偽物を経由した経路は、実行時に存在しません。
- **誤解: 「`tests/` という名前のディレクトリの中は全部テスト」**
  規則ではそう扱います。たまたま本番のコードを `tests/` という名前のディレクトリに置いている木があれば、その定義も候補から外れます。これは規則の割り切りです。
- **つまずき: `testing` を「テスト中の」という意味の普通の名前だと思って見落とす**
  `testing` という名前のディレクトリも、テストのディレクトリとして扱います。

#### 手作業ではどう使うか

- 矛の判定の手順 C・D（呼び出し先を開いて、道筋をたどる）で、`witness_chain` の関数が**本当にその関数か**を確かめます。名前が同じ別の関数（とくにテストのファイルや `examples/` の中のもの）に結ばれていたら、誤の原因は **E3**（名前だけの解決の誤り）です（第 51 章）。
- 凍結版では、本体からテストのファイルへの取り違えは起きにくくなりましたが、`examples/` やスクリプトの中の同じ名前の関数への取り違えは、まだ起こりえます（29.5 節の §9.5 も参照）。

#### この節のまとめ

O30 は、末尾名の解決がテストのファイルの中の同じ名前の関数に結び付き、実行時に存在しない効果を数えていた誤警報。
呼び出し元がテストのファイルでなければ、テストのファイルの定義を候補から外すと決めた（§9.1）。run14 で消えた効果の位置 1,010 はすべて xagent の、テストのファイルを経由する経路だった。

### 29.3 O32 — 相対 URL の読み違い

#### 一言で言うと

`client.get("/items/" + item_id)` のように `/` で始まる**相対 URL** を、以前は値の全体ごと「宛先」（`url.host`）と読んでいました。
そのため、パスに入るだけのモデルの値が、宛先を決めているように見えていました。
**相対 URL はパス（`url.path`）として読み、宛先はクライアントを作ったときの `base_url` から取る**ように直しました。

#### たとえ話 — 部屋番号だけの宛名

社内便の封筒に「305 号室」とだけ書いてあるとします。
これは「どの建物の」305 号室かを書いていません。
建物は、社内便を出す係が最初から決めています（本社ビル）。
封筒に書けるのは、部屋番号だけです。

誰かが部屋番号の欄に好きな番号を書けても、荷物が別の建物に届くことはありません。
相対 URL の `/items/…` は、この「部屋番号だけの宛名」です。
建物（ホスト）は、クライアントを作ったときの `base_url` で決まっています。

#### 小さな例 — 宛先とパスの読み分け

第 10 章 10.1 節で見た形を、`openWorldHint: False`（D3、「関わる範囲が閉じている」）のツールにした作例です。

```python
 1  import httpx
 2  from mcp.server.fastmcp import FastMCP
 3
 4  mcp = FastMCP("items")
 5
 6
 7  @mcp.tool(annotations={"openWorldHint": False})
 8  async def get_item(item_id: str) -> str:
 9      client = httpx.AsyncClient(base_url="http://localhost:8080")
10      resp = await client.get("/items/" + item_id)
11      return resp.text
```

- 7 行目: 「関わる範囲が閉じている」（外の世界と関わらない）と申告しています。
- 9 行目: HTTP の要求を送る係（クライアント）を作ります。`base_url` は、同じ機械の上の `localhost:8080` です。
- 10 行目: `/items/` にモデルの値 `item_id` をつないだ相対 URL に、`GET` の要求を送ります。宛先のホストは 9 行目の `localhost` で、モデルが変えられるのはパスの `item_id` の部分だけです。

直す前と、凍結版の解析器で走らせた結果です。

| 解析器 | `url.host` | `url.path` | D3 の答え |
|---|---|---|---|
| 直す前（`c3a8c0c`） | 主体 `MODEL`・確度 `resolved`（`"/items/" + item_id` の全体） | 無し | **矛**（理由 `net_model_host`、宛先をモデルが決められる） |
| 凍結版 | 主体 `OP`・定数 `"http://localhost:8080"`（`base_url` から取った） | 主体 `MODEL`（`"/items/" + item_id`） | 何も出ない（**内**。宛先が localhost） |

表の読み方: 1 行目は「直す前は、相対 URL の全体を宛先として読んだので、宛先にモデルの値が入っているように見え、D3 の矛になった」と読みます。
2 行目は「凍結版は、相対 URL をパスとして読み、宛先は `base_url` の `localhost` から取った。宛先が同じ機械の上なので、関わる範囲は閉じていて、D3 には反しない」と読みます。

（出典: 作例の走査は本記録者が 2026-10-01 に行ったもの。直す前の解析器は `git archive c3a8c0c authgap` で取り出した）

#### 一歩ずつの説明 — 直した規則（§9.2）とコード

規則は次のとおりです。

> URL の値の定数の先頭が `/` で、**その次の文字が `/` でない**（`"/items/" + x`）とき、それは相対 URL なので、値全体を `url.path` にし、`url.host` は置かない。受け手が `base_url` を持つ（`httpx.Client(base_url=…)` の `from_ctor` で `url.scheme` に入っている）ときは、`base_url` を分割して `url.host` を取る。

コードは 2 か所です。

```python
# authgap/effects.py:494, 498（_split_url の中。コメントは省略）
if text is not None and len(text) >= 2 and text[0] == "/" and text[1] != "/" and "://" not in text:
    return {"url.path": v}
```

- 1 行目: URL の値の先頭の部品が定数の文字列 `text` で、長さが 2 以上、1 文字目が `/`、2 文字目が `/` でなく、`://` を含まないなら、
- 2 行目: 値の全体を `url.path`（パス）として返します。`url.host`（宛先）は返しません。

```python
# authgap/effects.py:544-548（_split_url_slots の中）
if "url.host" not in split and "url.scheme" in out:
    # 相対 URL: 宛先は受け手の base_url（`from_ctor` で `url.scheme` に入っている）から取る（D57）。
    base = _split_url(out["url.scheme"]).get("url.host")
    if base is not None:
        out["url.host"] = base
```

- 1 行目: 分けた結果に宛先が無く（相対 URL だった）、しかもクライアントを作ったときの `base_url` が `url.scheme` に入っているなら、
- 2 行目: その理由のコメントです（第 13 章で見たとおり、`from_ctor` の規則で `base_url` は `url.scheme` の slot に入ります）。
- 3 行目: `base_url` の値を、同じ規則で分けて、宛先の部分を取り出します。
- 4・5 行目: 宛先が取り出せたら、それを `url.host` にします。取り出せなければ、`url.host` は置きません（宛先が読めない）。

（出典: `authgap/effects.py:494-498, 544-548`、`docs/contradiction_principles.md:283-294`（§9.2））

#### 一歩ずつの説明 — `"/"` だけ、`"//"` で始まる形は分けない

規則には、大事な例外があります。
先頭が `"/"` だけ（`"/" + x`）や、`"//"` で始まるときは、**分けずに**、今までどおり値の全体を宛先として読みます。

理由は、モデルがパスの代わりに `"/evil.example/x"` を渡すと、`"/" + "/evil.example/x"` は `"//evil.example/x"` になるからです。
`//` で始まる URL は、`urljoin` のような関数では「ホストから書いた URL」と解釈され、宛先が `evil.example` に変わってしまいます。
これを「パスだから宛先は変わらない」と読むと、危ないものを問題なしとする**誤 clear** を作ります。

作例で確かめました。
上の作例の 10 行目を `client.get("/" + path)`（`path` はモデルの値）に変えると、凍結版の解析器でも `url.host` は主体 `MODEL` のままで、D3 は**矛**（理由 `net_model_host`）でした。

（出典: `docs/contradiction_principles.md:291-293`、`authgap/effects.py:495-497`（コメント）。作例の走査は本記録者が 2026-10-01 に行ったもの）

#### なぜそうするのか — 宛先を決めるのは誰か

D3 の判定は、宛先（ホスト）で決まります（第 10・17 章）。
宛先を誰が決めているかを読み違えると、D3 の答えがまるごと変わります。
相対 URL の宛先は、クライアントを作った人（多くは運用者の設定値）が決めています。
モデルが入れられるのは、パスとクエリだけです。
だから、相対 URL をパスとして読むのが、値の意味に合った読み方です。

一方で、この直しは「宛先がモデルの値に見える」ものを減らす向きの変更です。
付録の判定 `GAP_INJECT`（SSRF の座標）も減る向きなので、消える行を 1 件ずつ見る、と決めていました。

#### 直した結果

run14 では、O32 で D3 の矛が 5 件、不に移りました（asquared 3・code-rag 2）。
どれも相対 URL で、しかも `base_url` も読めなかったので、宛先が「読めない」になったものです。
付録の判定 `GAP_INJECT` は、`url.host` の 5 件が同じ位置の `url.path` に移りました。

逆に、**今まで見逃していたもの**も見つかりました。
odoo の `odoo_setup_credentials` は、モデルが渡した Odoo の URL を `base_url` にして、相対パスを送っていました。
以前は、相対パスの定数（主体 `OP`）を宛先と読んでいたので、「宛先をモデルが決める」ことが見えていませんでした。
直した後は、`base_url` から宛先を取るので、モデルの値が宛先に入ることが見えるようになりました（`url.host` の `GAP_INJECT` 2 件）。

（出典: `docs/decisions.md:3109`（O32 で不に移った 5）、`:3113-3114`（`GAP_INJECT` の移動）、`:3120-3121`（odoo））

#### よくある誤解・つまずき

- **誤解: 「`/` で始まる URL は、すべてパスとして読む」**
  `"/"` だけや `"//"` で始まるものは分けません。宛先が変わりうるからです。
- **誤解: 「相対 URL なら、宛先は必ず分かる」**
  `base_url` が読めなければ、宛先は「読めない」になり、D3 は不になります（asquared・code-rag の 5 件）。
- **誤解: 「O32 の直しは、誤警報を減らすだけ」**
  odoo のように、宛先をモデルが決めている本当の形が、直して初めて見えたものもあります。
- **つまずき: 要求を送る行だけを見て、宛先を決める**
  宛先は、クライアントを作った行（`base_url=`）に書かれていることがあります。

#### 手作業ではどう使うか

- D3 の矛や不を判定するときは、要求を送る行から、**クライアントを作った行**までさかのぼって、`base_url` を確かめます。`base_url` が定数か、設定ファイルや環境変数から来るのか、モデルの値から来るのかで、答えが変わります（第 50 章）。
- 相対 URL の先頭が `"/"` だけで、そこにモデルの値がつながる形を見たら、モデルが `//` で始まる値を渡したら宛先が変わるかを考えます。
- 判定表の理由が `net_model_host` なら、本当にモデルが宛先を選べるのか（パスだけではないか）を確かめます。

#### この節のまとめ

O32 は、相対 URL の全体を宛先と読み、パスに入るモデルの値を「宛先を決める値」と見ていた誤警報。
相対 URL はパスとして読み、宛先は `base_url` から取るように直した（§9.2）。`"/"` だけ・`"//"` で始まる形は、誤 clear を作らないために分けない。

### 29.4 O33 — 「流れ込む」と「決められる」の違い

#### 一言で言うと

原理 3（モデルが値を決められるなら、取りうる値の全体を「できること」とみなす）の「決められる」を、以前は**値の主体が `MODEL`** というだけで判定していました。
けれども、解析器の `MODEL` は「モデルの値が**流れ込む**」という意味にすぎません。
そこで、「決められる」（選べる）を「**主体 `MODEL` かつ確度 `resolved`**」と定義し直し、確度が `opaque` なら**不**（理由の末尾に `_opaque`）にしました。

#### たとえ話 — 注文票の「備考」の欄

レストランの注文票に「備考」の欄があり、客が自由に書けるとします。
客は「辛さ控えめ」と書けます。
けれども、備考の欄に何を書いても、**料理そのもの**（メニューの何番か）は変わりません。
料理はメニューの欄で決まり、その欄は店員が書きます。

客の字が注文票に**入っている**ことと、客が料理を**選べる**ことは別です。
SQLAlchemy の `where(Item.id.in_(ids))` の `ids` は、この「備考」にあたります。
モデルの値は SQL の中に入りますが、SQL の**命令の種類**（`SELECT` か `DELETE` か）はコードが決めています。

#### 小さな例 — SQLAlchemy の式

```python
 1  from mcp.server.fastmcp import FastMCP
 2  from sqlalchemy import create_engine, select
 3
 4  from .models import Item
 5
 6  mcp = FastMCP("memory")
 7
 8
 9  @mcp.tool(annotations={"destructiveHint": False})
10  def list_items(ids: list[str]) -> str:
11      engine = create_engine("sqlite:///memory.db")
12      with engine.connect() as conn:
13          rows = conn.execute(select(Item).where(Item.id.in_(ids)))
14      return str(rows)
```

- 2 行目: SQLAlchemy（Python から DB を使うための広く使われるライブラリ）から、DB につなぐ道具と、`SELECT` 文を組み立てる道具を読み込みます。
- 4 行目: 表 `Item` の定義を、別のファイルから読み込みます。
- 9 行目: 「壊さない」（D2）と申告しています。
- 11・12 行目: DB につなぎ、接続 `conn` をもらいます。
- 13 行目: 「`Item` の表から、`id` が `ids` のどれかである行を選ぶ」という `SELECT` 文を組み立てて実行します。`ids` はモデルが渡した値ですが、SQL の文に**直接つながる**のではなく、**バインド変数**（SQL の文とは別に、安全に渡される値）として渡されます。

直す前と、凍結版の解析器で走らせた結果です。

| 解析器 | `sql` の slot | D2 の答え |
|---|---|---|
| 直す前（`c3a8c0c`） | 主体 `MODEL`・確度 `opaque` | **矛**（理由 `db_model_sql`。「モデルが SQL を決められる」） |
| 凍結版 | 主体 `MODEL`・確度 `opaque` | **不**（理由 `db_sql_model_opaque`） |

表の読み方: 1 行目は「直す前は、`sql` の値の主体が `MODEL` だというだけで『モデルが SQL を決められる。だから `DELETE` も書ける』と読み、壊さないという宣言に対して矛にした」と読みます。
2 行目は「凍結版は、確度が `opaque`（解析器が `select(...)` や `where(...)` の中を読めない）なので、モデルが SQL を選べるのか、値が流れ込むだけなのか決められないとして、不にした」と読みます。

slot の値そのもの（主体 `MODEL`・確度 `opaque`）は、直す前も後も同じです。
変わったのは、その値を**判定でどう使うか**です。
これが、run13 で memory-hub の 2 件が誤検出になっていた形です。

（出典: 作例の走査は本記録者が 2026-10-01 に行ったもの。実物は `docs/open_questions.md:957-970`（O33）、`docs/decisions.md:3036-3040`（D56 の memory-hub 2 件））

#### 一歩ずつの説明 — 直した規則（§9.3）とコード

規則は次のとおりです。

> 原理 3-a の「モデルが値を選べる」は、slot の値の**主体が MODEL で、かつ確度が resolved** のときに限る。主体が MODEL でも確度が opaque（モデリングしていない関数を通った値）なら、モデルが選べるのか値が流れ込むだけなのかは静的に決まらないので、**原理 2-a により不明**とする。

確度 `resolved` は、「モデルの入力が、解析器のモデリングした操作（文字列の連結・書式・`Path` の組み立てなど）**だけ**を通って slot に届いた」ことを表します（第 14 章）。
その場合は、モデルが渡した文字がそのまま slot の値の一部になるので、「選べる」と言えます。
途中で中の分からない関数を通ったら、その関数が値を絞ったり置き換えたりしているかもしれないので、「選べる」とは言えません。

これを判定に使うコードです。

```python
# authgap/dparse.py:245-272（説明の文字列は省略）
def _choice(e, *names: str) -> Optional[str]:
    from .ir import Prin

    out: Optional[str] = None
    for n in names:
        v = (getattr(e, "slots", None) or {}).get(n)
        if v is None or v.prin is not Prin.MODEL:
            continue
        if v.prov.kind == "resolved":
            return "chosen"
        out = "influenced"
    return out


def _by_choice(e, names: tuple[str, ...], hit: str, otherwise: tuple[str, str]) -> tuple[str, str]:
    c = _choice(e, *names)
    if c == "chosen":
        return CONTRA, hit
    if c == "influenced":
        return CONTRA_UNKNOWN, f"{hit}_opaque"
    return otherwise
```

行ごとに何をしているかを書きます。

- 1 行目: `_choice` は、効果 `e` の、名前が `names` の slot（たとえば `"argv0"`・`"shell_string"`）を見て、モデルがその値を決められるかを答える関数です。
- 2 行目: 主体の種類（`Prin`）を使えるようにします。
- 4 行目: 答えの入れ物を、最初は「無し」（`None`）にします。
- 5 行目: 見る slot の名前を 1 つずつ取り出します。
- 6 行目: その slot の値を取り出します。
- 7・8 行目: 値が無いか、主体が `MODEL` でなければ、その slot は飛ばします。
- 9・10 行目: 主体が `MODEL` で、確度が `resolved` なら、すぐに `"chosen"`（**選べる**）を返します。
- 11 行目: 主体が `MODEL` でも確度が `resolved` でなければ（`opaque` なら）、答えを `"influenced"`（**流れ込む**）にしておき、ほかの slot も見続けます。
- 12 行目: 最後まで見て、`"influenced"` か `None` を返します。複数の slot のうち 1 つでも「選べる」があれば、そちらが優先されます。
- 15 行目: `_by_choice` は、`_choice` の答えを判定表の答えに直す関数です。`hit` は「選べるときの理由の名前」（たとえば `"spawn_model"`）です。
- 16 行目: `_choice` に聞きます。
- 17・18 行目: 選べるなら、**矛**（`CONTRA`）と、理由 `hit` を返します。
- 19・20 行目: 流れ込むだけなら、**不**（`CONTRA_UNKNOWN`）と、理由 `hit` の末尾に **`_opaque`** を付けたもの（たとえば `"spawn_model_opaque"`）を返します。
- 21 行目: 主体が `MODEL` でなければ、判定表のその行の「それ以外」の答え（`otherwise`）を返します。

（出典: `authgap/dparse.py:245-272`、`docs/contradiction_principles.md:296-316`（§9.3））

#### 一歩ずつの説明 — SQL だけは、判定の順序を決めた（§9.4）

§9.3 の規則だけを入れると、困ることが 1 つありました。
次のような形です（説明用の作例）。

```python
conn.execute("UPDATE reminders SET sent = 1 WHERE id IN (" + placeholders + ")")
```

- 文の先頭は定数の `"UPDATE reminders SET sent = 1 WHERE id IN ("` で、その後ろにモデルの値から作った `placeholders` がつながっています。
- 命令の種類（`UPDATE`）は、モデルの値とは関係なく、定数の部分で決まっています。

もし値が `opaque` になっていたら、§9.3 だけでは「流れ込むだけかもしれない → 不」になり、読むだけのツールが**本当に** `UPDATE` している矛が、不に落ちてしまいます。
そこで、SQL の値は次の順で判定すると決めました（§9.4。後の §9.6 の 5 で理由の名前を改訂）。

1. **全体が定数** → 先頭の語と SQL の分類で判定する（今までどおり）。
2. **主体が MODEL**（どこかにモデルの値が入る）:
   - 確度 `resolved`（モデルが選べる）→ **矛**。文を重ねる注入（1 回の `execute` で複数の文を実行できるライブラリがある）で、任意の文を書けるからです。接頭辞の先頭の語がその宣言の変更の文なら理由は `db_modify`、そうでなければ `db_model_sql`。
   - 確度 `opaque`（流れ込むだけかもしれない）→ 接頭辞の先頭の語が変更の文なら**矛**（`db_modify`。注入があってもなくても変更する）、そうでなければ**不**（`db_sql_model_opaque`）。
3. **主体が MODEL でない** → 接頭辞で先頭の語と分類が決まればそれで判定し、決まらなければ**不**。

run13 の godsaeng（読むだけのツールが `"UPDATE … IN (" + …` を連結していた本物の違反）は、この順序で、run14 でも**矛のまま**残りました。
上の形を読むだけのツールに入れた作例を走らせると、直す前の解析器は理由 `db_model_sql` の矛、凍結版は理由 `db_modify` の矛でした。

（出典: `docs/contradiction_principles.md:318-335`（§9.4）、`docs/decisions.md:3111-3112`（godsaeng は矛のまま）。作例の走査は本記録者が 2026-10-01 に行ったもの）

#### よくある誤解・つまずき

- **誤解: 「主体 `MODEL` = モデルが値を自由に選べる」**
  違います。`MODEL` は「流れ込む」です。「選べる」は主体 `MODEL` かつ確度 `resolved` のときだけです（第 14 章 14.11 節）。
- **誤解: 「`_opaque` の不は、モデルが関係ないという意味」**
  関係はあります。モデルの値は流れ込んでいます。選べるかどうかが決められない、という意味です。
- **誤解: 「O33 の直しで、本物の違反が見えなくなった（誤 clear）」**
  見えなくなったのではなく、矛から不に移りました。不は件数を別に出します。本当にモデルが選べるものが不に移る代償は、原理の文書が先に書いています。
- **誤解: 「`resolved` なら、必ず人の読みと同じ」**
  `resolved` は「解析器が理解できる操作だけで届いた」という意味です。解析器の理解に既知の限界があれば、`resolved` でも人の読みと違うことがあります（第 14 章 14.10 節の `*cmd` の作例では、`resolved` のために誤って矛になった）。
- **つまずき: SQL の不も、ほかの slot と同じ規則だと思う**
  SQL だけは、接頭辞の先頭の語を読む順序（§9.4）があります。`opaque` でも、接頭辞が `UPDATE` などの変更の文なら矛です。

#### 手作業ではどう使うか

最終評価では、解析器の不の中身を人が判定します（D1・D2 で各 50 木、1 木 1 組。D69 の 4）。
判定の手引きの下書きは、不の理由ごとの調べ方を書いていて、`…_opaque` については次のとおりです。

> `…_opaque`: モデルの値が書き先・宛先を選べるところまで届くかを、値の流れをたどって確かめる。

手順にすると、次のようになります。

1. 不の理由の末尾が `_opaque` だと確かめる（たとえば `spawn_model_opaque`）。
2. 効果の行の slot（`argv0` なら起動するプログラム、`path` なら書き先、`url.host` なら宛先）を、原ソースで探す。
3. その値が、ツールの引数（モデルの値）から、どんな関数を通って届いているかを、1 段ずつたどる。
4. 途中の関数が、値を絞る（決まった候補の中から選ばせる、検査して合わなければ止める）か、置き換える（決まった値にする）かを確かめる。
5. モデルが、その slot の値を**実際に選べる**ところまで届くなら「選べる」、届かないなら「選べない」。
6. 「選べる」なら、原理 3 a で取りうる値の全体を考え、宣言に反するかを決める。「選べない」なら、判定表の「それ以外」の行の問い（たとえば SPAWN なら、起動されるプログラムが何をするか）に進む。
7. 20〜30 分調べても決められなければ「不明」にし、理由を書く（手引きの第 19 節）。

逆向きの誤りにも注意します。
解析器が矛（理由 `spawn_model` や `db_model_sql` など、「選べる」を前提にしたもの）を出していて、人が読むとモデルは選べないと分かったら、それは「モデルが決められないのに、決められるとした」誤りで、誤の原因は **E7** の候補です（第 51 章）。

（出典: `docs/drafts/final_judging_guide_draft.md:510`（18A.2 の `…_opaque` の調べ方）、`:493-530`（18A 節）、`docs/decisions.md:3828-3831`（D69 の 4）。判定の手順の 1〜7 の並べ方は、手引きの下書きを本書がかみくだいたもの）

#### この節のまとめ

O33 は、主体 `MODEL`（流れ込む）を「選べる」と取り違えていた誤警報。「選べる」を主体 `MODEL` かつ確度 `resolved` に限り、`opaque` なら不（理由の末尾に `_opaque`）にした（§9.3）。SQL は接頭辞の先頭の語を読む順序を足した（§9.4）。
`…_opaque` の不は、gemini の `spawn_model_opaque` のように「流れ込むが、選べるとまでは読み切れない」形で、人は値の流れをたどって、選べるところまで届くかを確かめる（手引きの 18A 節、第 52 章）。

#### 一歩ずつの説明 — §9.5 の規則
