### 第 10 章

#### 演習 10-1（HTTP の 4 つの呼び出しを判定する）

**1.** 解析器の答え（判定表 §7.1・§7.2・§7.4。本書の執筆時に作例で確かめた形）:

| 行 | 呼び出し | D1 だけを約束 | D2 | D4 |
|---|---|---|---|---|
| 1 | `requests.get(定数)` | 内 | 内 | 内 |
| 2 | `requests.post(定数, json=...)` | **不**（`net_post`） | **不**（`net_post`） | **不**（`net_nonidempotent_method`） |
| 3 | `requests.put(定数, json=...)` | **矛**（`net_modify`） | **不**（`net_put`） | 内 |
| 4 | `requests.delete(定数)` | **矛**（`net_modify`） | **矛**（`net_modify`） | 内 |

- 1 行目: GET は RFC 9110 で安全かつ冪等なので、どこでも内。
- 2 行目: POST は相手の決めた意味で処理されるので、相手を変えるかも、2 回目でさらに変えるかも、静的には決まらない（原理 2-a）。
- 3 行目: PUT は相手の資源を作るか置き換えるので D1 で矛。D2 では、新規作成か置き換えかが分からないので不。PUT は冪等なので D4 は内。
- 4 行目: DELETE は既存の資源を消すので D1・D2 で矛。冪等なので D4 は内。

**2.** 不になったのは 2 行目（D1・D2・D4）と 3 行目（D2）。人は次の順で調べる（10.4 節）。
1. メソッドが本当に POST（PUT）かを原ソースで確かめる。
2. パス（`/v1/search`、`/v1/items/42`）とエンドポイントの名前を読む。
3. ツールの名前と説明文を読む。
4. 送る本体の中身を読む（2 行目は検索語 `q` だけ。3 行目は `item`）。
5. 相手の API の公開の文書を探して読み、URL を `evidence` に書く。
6. 2 行目は「作成・更新・削除」か「照会」か、3 行目は「既存の資源の置き換え」か「新規作成」かを決める。20〜30 分調べても決められなければ「不明」にして理由を書く。
（2 行目は、パスと本体からは検索＝照会らしく見えるが、決めるのは文書を確かめてから。）

**3.** D2 の答えは**矛**（`net_put_model_url`）に変わる。宛先（ホストやパス）をモデルが決められるなら、モデルは既存の資源を指して置き換えさせられるので、原理 3-a（取りうる値の全体を「できること」とみなす）により矛になる。ただし、モデルの値が解析器のモデリングしていない関数を通って流れ込むだけ（確度 opaque）なら、不（`net_put_model_url_opaque`）になる。

**4.** 4 行とも、宛先が定数の外部ホスト `api.example.com` なので、D3 は**矛**（`net_external_host`）。D3 はメソッドではなく宛先で決まるので、1 行目の GET も矛になる。

#### 演習 10-2（一意制約と D4）

**1.** 人の判定（手引きの下書き 15.4 の問い「同じ引数で 2 回呼んだとき、2 回目が 1 回目の後の状態をさらに変えるか」）:

| 場合 | D4 に反するか | 理由 |
|---|---|---|
| (a) | 反しない | 一意制約があるので、2 回目の `INSERT` は失敗し（`sqlite3.IntegrityError`）、行は増えない |
| (b) | **反する** | 一意制約が無いので、2 回目で同じ `name` の行がもう 1 つ増える |
| (c) | 反しない | 一意制約にぶつかった 2 回目は、`OR IGNORE` で何もせずに終わる |
| (d) | **反する** | 主キーはあるが、キーの値が `uuid4()` の乱数で毎回変わるので、2 回目で行が増える |
| (e) | **反する** | 2 回目は同じ `name` の古い行を消して入れ直し、`added_at` が新しい時刻に変わる |

**2.** 解析器は、(a)〜(e) をすべて同じく **不**（`db_nonidempotent_statement`）にする。先頭の語がどれも `INSERT` で、解析器はスキーマも `OR IGNORE`・`OR REPLACE` の修飾も、`?` に入る値の出どころも見ないので、**区別しない**（(e) と同じ形の作例で、D4 の不を本書の執筆時に確かめた）。区別するのは人の仕事。

**3.** 解析器は、先頭の語が `INSERT` なので、D2 では**内**にする（作例で確かめた）。これは凍結の前の添削で見つかり、「表の選択（D55）で、実装の欠陥ではない」として O42 に限界として記録されている（`docs/open_questions.md:1159`）。人の判定では、手引きの下書き 15.2 の表の「DB の `INSERT` → 反しない」の行で機械的に決めず、表の上の問い「呼び出しの前からあったものを消す・上書きする・変えるか」に戻る。同じ `name` の行が呼び出しの前からありうるなら、`INSERT OR REPLACE` はそれを消して置き換えるので、反する側に読める。この形は手引きの表に名指しされていないので、扱いを表に書き足すかを、承認の前に学生が決めておくとよい。

**4.** `grep -rn "CREATE TABLE" corpus/<木>` で木の中を探し、移行用のファイル（`.sql`、`migrations`）や ORM の定義（`unique=True`・`primary_key=True`）も見る。それでも見つからなければ、手引きの下書きどおり「不明」にし、理由（スキーマが木の中に無い）を書く。

#### 演習 10-3（手元の網）

**1.**

| 宛先 | 解析器の類 | D3 の注記 |
|---|---|---|
| (a) `172.20.0.5` | local（`172.16.0.0/12` の中） | なし（内） |
| (b) `172.32.0.1` | external（`172.16.0.0/12` の外で、グローバルなアドレス） | `contradiction:D3`・`contradiction_reason:D3:net_external_host` |
| (c) `qdrant` | external（`localhost`・`.localhost`・`.local` のどれでもない名前） | `contradiction:D3`・`contradiction_reason:D3:net_external_host` |
| (d) `169.254.169.254` | local（`169.254.0.0/16`、link-local） | なし（内） |

（4 つとも、本書の執筆時に凍結版の解析器で確かめた。）

**2.**
- 括弧を「例」と読む場合: `172.20.0.5` は private（RFC 1918 の `172.16.0.0/12`）の 1 つなので、「反しない」。解析器と一致する。
- 括弧を「全部の一覧」と読む場合: `172.20.0.5` は `127.0.0.1`・`10.x`・`192.168.x` のどれでもないので、private とはみなされず、外部の相手として「反する」になる。

**3.** 「全部」と読むと、人は「反する」と判定するのに、解析器は内（何も出さない）なので、これは**解析器の見落とし**として数えることになる。「例」と読むと、人も解析器も反しないで一致し、見落としにならない。つまり、読み方によって見落としの数が変わる。（(c) のような名前の宛先では逆に、人が「手元」と読めば解析器の矛が**誤**になる。）

**4.** 学生が、判定の手引きを**承認する前に**決める（承認したら事前登録 §2.12 と同じコミットで封をし、判定の途中では変えない）。決めるまでは**未決**として扱い、黙ってどちらかに倒さない（CLAUDE.md の規則 4）。決める点は、括弧が例か全部か、`172.16.0.0/12`・`fc00::/7`・link-local・unspecified を含めるか、名前の宛先をどう判定するか、決めた結果を手引きの D3 の表にどう書くか。本書の執筆の時点で、この食い違いは `docs/open_questions.md` にも `docs/decisions.md` にも記録されていない。第 46 章の「まだ決まっていないこと」の一覧に載る。判定の途中で手引きで決まらない形に出会ったら、「不明」にして「手引きで決まらない」と理由を書き、事前登録の逸脱の欄に記録する（手引きの下書き第 22 節）。

#### 演習 10-4（接続ごとの設定と DB に残る設定）

**1.**

| 命令 | ツール A（D1） | ツール B の D2 | ツール B の D4 |
|---|---|---|---|
| `PRAGMA journal_mode=WAL` | `contradiction:D1`・`contradiction_reason:D1:db_persistent`（矛） | `contradiction_unknown:D2:db_persistent`（不） | なし（内） |
| `PRAGMA foreign_keys=ON` | なし（内） | なし（内） | なし（内） |

WAL は DB のファイルに残る設定（`SQL_PERSISTENT`）なので、原理 1-i-b により D1 で矛、D2 では「足すか壊すか」が当てはまらないので不、同じ設定を 2 回しても変わらないので D4 は内。`foreign_keys` は接続を閉じれば消える設定（`SQL_CONNECTION`）なので、どこでも内。

**2.**（D1 について。本書の執筆時に作例で確かめた）
- `PRAGMA journal_mode`（`=` なし）: 今の方式を読むだけの読み取り → 内（注記なし）。
- `PRAGMA table_info(resources)`: 表の列の一覧を読む。括弧の形は `=` と同じに扱うが、`table_info` は設定の名前の一覧に無いので、読み取り → 内（注記なし）。
- `VACUUM`: DB のファイルを作り直す保守（`SQL_PERSISTENT`）→ 矛（`db_persistent`）。
- `BEGIN`: トランザクションの始まりで、接続単位（`SQL_CONNECTION`）→ 内（注記なし）。

**3.** 反する。手引きの下書きの D1 の表は、「DB に残る設定・保守（`PRAGMA journal_mode=WAL`、`VACUUM` など）→ 反する（原理 1-i-b）」と書いている。書き込み先の種類は「**データベース**」（手引きの下書き 16.1 の定義が「DB の行・スキーマ・DB に残る設定を変える」で、例に `PRAGMA journal_mode=WAL` を挙げている）。ただし、正にするには、ツールの呼び出しから `_get_connection` に実際に届くこと（到達）も確かめる必要がある（第 48・49 章）。WAL が実際に DB を変えるのが最初の 1 回だけである点は、条件つきの到達の扱い（条件の種類「初回」）で記録する（第 49 章）。

#### 確認問題 10-1

RFC 9110 の「安全」は、**クライアントが頼んだこと**についての性質で、サーバが裏で行うアクセスログへの追記は、クライアントが**頼んでおらず責任を負えない**振る舞いなので、安全の範囲内とされる（§9.2.1）。解析器が GET を D1 の内にするのは、ツール（クライアント）が相手に頼んだことが「読むだけ」だからで、相手のサーバのログは問わない。一方、ツールが自分のマシンでログのファイルに追記するのは、**ツール自身が行う書き込み**で、呼び出しを越えて残る。この研究は原理 1-i-b（呼び出しを越えて残るものはすべて環境）を選んだので、ツール自身のログの追記は「環境を変える」ことになり、D1 の矛になる。実世界ではこの扱いが割れていて（RFC 9110 は緩い側、OpenAI の提出ガイドはログも状態の変更とする厳しい側）、この研究は重みを付けず、書き込み先の種類（ログ）をラベルとして記録する（D67 の 1。第 43 章）。

#### 確認問題 10-2

- **D1（`readOnlyHint: true`）**: 反していない。GET は RFC 9110 で安全なメソッドで、相手の状態を変えることを頼んでいない。解析器も内（注記なし）。
- **D3（`openWorldHint: false`）**: 反している。宛先が定数の外部ホストなので、関わる範囲が閉じていない。解析器も矛（`net_external_host`）。

仕様の `openWorldHint` の説明は、「Web 検索のツールの世界は開いているが、記憶のツールの世界はそうではない」と例を挙げている。Web 検索は読むだけでも「開いた世界」と関わる、というのが仕様の例そのものなので、このツールの `openWorldHint: false` は誤った申告になる。readOnly（変えるか）と openWorld（外と関わるか）は別の軸なので、同じ 1 つの GET が D1 では内、D3 では矛になる。

#### 確認問題 10-3

- **D1 で矛**: D1 の問いは「環境を変えるか」。行を 1 つ足すのも DB の中身を変えることなので、反する（`db_modify`）。
- **D2 で内**: D2 の問いは「呼び出しの前からあったものを消す・上書きする・変えるか」（宣言の原文は "performs only additive updates"）。ふつうの `INSERT` は新しい行を足すだけなので、反しない（D55。ただし `INSERT OR REPLACE` のような形は別。O42）。
- **D4 で不**: D4 の問いは「同じ引数で 2 回呼んだとき、2 回目がさらに変えるか」。一意制約があれば 2 回目は失敗・無視されて行は増えず、無ければ増える。どちらかはスキーマを見ないと決まらず、解析器はスキーマを読まないので、原理 2-a により不（`db_nonidempotent_statement`）。

#### 確認問題 10-4

理由（`authgap/dparse.py:293-294` のコメントと `docs/contradiction_principles.md:414-420`）:
1. `is_private` は、名前に反して「グローバルでない」に近い意味で、6to4 の `2002::/16` なども含む。そのため、外部の相手を手元と読み、D3 の違反を見逃す誤 clear を作る（以前の実装は、ポートの付いた 6to4 のアドレスを local と読む誤 clear を作っていた）。
2. Python のパッチ版（gh-113171）によって結果が変わることがあり、結果が実行する Python の版に左右される。

食い違う例: `2002:808:808::1`（6to4 の形で、中に `8.8.8.8` を埋め込んだもの）。本書の執筆時に Python 3.10 で確かめると、`is_private` は True（private）と答えたが、解析器は中の IPv4（グローバルな `8.8.8.8`）で決めて external と分類した。ほかに `192.0.2.1`（文書用の網）は、`is_private` が True だが、解析器は unknown（D3 で不）にする。
