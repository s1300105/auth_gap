#### 演習 56-2（Q17 の一般形を使う）

| 形 | 到達するか | 誤の原因 / 条件の種類 | 正か | 書き込み先の種類 |
|---|---|---|---|---|
| (1) | 到達しない | E1 | 誤 | — |
| (2) | 到達する | 起動の方法 | 正 | キャッシュ・状態の保存 |
| (3) | 到達する | 初回（本書の読み） | 正 | キャッシュ・状態の保存 |
| (4) | 到達しない | E1 | 誤 | — |

(1) **到達しない（誤、E1）**。lifespan（16〜18 行）が、条件なしに `_ensure_cache()` を呼びます。lifespan は、どの起動の方法でもツールの受付より前に走ります。`_ensure_cache` が例外で抜ければ lifespan が失敗し、受付は始まりません。`_cache_dir` を `None` に戻す箇所もありません。だから「どの起動の方法でも、必ず先に済んでいて、戻されない」と言えます。ツールの呼び出しのときには、10 行の `if` が偽になり、12 行には届きません。

(2) **到達する**。初期化は `main()` の中だけにあります。モジュールの一番上の `mcp` は `fastmcp run file.py:mcp` などで `main()` を通らずに起動できるので、そのときは最初の `list_cache` の呼び出しで 12 行の `os.makedirs` が走ります。条件の種類は **起動の方法**（初回だけ起きるので「初回」を `;` で並べて書いてもよい。どちらにしても運用者が決める条件が入るので、(B)(C) には数えない）。`readOnlyHint=True` でディレクトリを作るのは環境の変更なので D1 に反し、**正**。書き込み先の種類は、初回に作る作業ディレクトリなので **キャッシュ・状態の保存**（手引き 16.2 節の「初回だけ `~/.app/` を作る」）。

(3) **到達する**。lifespan で一度初期化しても、`reset_cache` が `_cache_dir` を `None` に戻し、ディレクトリも消します。その後の最初の `list_cache` の呼び出しで、10 行の `if` が真になり、12 行でディレクトリを作り直します。「戻されない」と言えないので到達します。条件の種類は、「キャッシュが無いときだけ」に当たるので **初回** と読みます（本書の読み。手引きに直接の例は無いので、`condition` に「`reset_cache` の後の最初の呼び出し」と書き、迷った点を `note` に残す）。初回は運用者の決める条件ではないので (B) には数え、条件つきなので (C) には数えません。D1 に反するので **正**、書き込み先の種類は **キャッシュ・状態の保存**。

(4) **到達しない（誤、E1）**。`main()` を通らない起動でも、lifespan が必ず先に初期化します。`main()` の中の初期化は、あってもなくても結果を変えません。「どの起動の方法でも」の問いに、lifespan が答えています。

(5) **不明**。lifespan に渡しているのは木の外のライブラリが返す関数で、それが `app_lifespan` を必ず呼ぶか（したがって初期化が必ず先に済むか）を、コードからも文書からも確かめられません。手引き 19 節の「起動の方法・初期化の場所が読み切れない」に当たるので不明にし、`unknown_reason` に「`vendor_kit.wrap` が `app_lifespan` を呼ぶか読み切れない（20〜30 分調べた範囲）」と書きます。黙って正や誤に倒しません。

#### 演習 56-3（第 3 版の答えを直す）

(1) 「最終評価で深さ 3・4・5 を比べて、深さによる見落としの量を示します」が食い違っています。
- **D69 の 5**（手順書 0-10）で、深さ 3・5 は**矛の件数だけ**を探索的に出し、**判定しない**と決まりました。見落としは判定しないと数えられないので、「深さによる見落としの量」は示せません。
- **D68 の 2** で、見落としの判定で読むのは深さ 4 までと決まり、それより奥で偶然見つけた違反は「見落とし（深さ 4 の外）」として別に数えます。深さを変えた見落としの比較は、主の結果に入れません。
- （第 3 版の「深い所ほど『本当に通るか』の確かさが下がる」という理由も、D54 の記録（深さ 5 で増えた矛の誤検出 0、当時の手検証）と合わないので、使わないほうがよい。）

(2) 書き直しの例: 「深くすれば見落としは減るかもしれませんが、深さは 4 に凍結済み（D54）なので変えません。最終評価では深さ 3・5 でも走らせますが、出すのは矛の件数だけで、判定はしません（探索的。D69 の 5）。だから、深さによる見落としの量は最終評価では測りません。見落としの判定で深さ 4 より奥に違反を見つけたら、『見落とし（深さ 4 の外）』として主の見落としとは別に数え、併記します（D68 の 2）。」

#### 確認問題 56-1

起動の方法は、コードだけから決めます（D67 の 2）。
ccr は初期化を `main()` の中だけで済ませています。モジュールの一番上の `mcp` は、`fastmcp run file.py:mcp` のように `main()` を通らない**起動の方法**で起動できるので、そのときは最初のツールの呼び出しで初期化の効果が起きます。だから「届きうる」ので到達し、宣言に反すれば正になります（条件の種類は「起動の方法」）。
shyhurricane は初期化を lifespan の中で済ませています。lifespan は**どの起動の方法でも**ツールの受付より前に必ず走るので、ツールの呼び出しでは届きません。だから誤（E1）です。
論文に両方を書く理由: この規則で ccr の件は正になるので、解析器に都合のよい規則に見えうる。規則が原理 3 から導いたものであり、解析器に不利な側（lifespan の形）も誤として残ることを示すためです（O43 の整理、手引き 14.4 節）。

#### 確認問題 56-2

v4 で抜き取った D1・D2 の矛 60 件のうち 38 件は reaper-mcp の 1 木から来ていて、全部が正でした。件数の精度は 76.7% でしたが、reaper-mcp を除くと 8/22 = 36.4% でした（事後の分析）。件数で数えると、1 木が 60 件中 38 件（約 63%）の重みを持ち、その木の性質で精度が大きく動きます。木で数えれば、1 木は 1 票（8 木なら 12.5%）なので、偏りが小さくなります（木ごとの精度の平均は 59.7% → 53.9%、本当の矛があった木の割合は 75.0% → 71.4%。本書の計算）。だから報告の単位を木にしました（D67 の 3）。

論文に使わない理由（2 つ以上）:
- v4 の判定は本記録者（AI）が行ったもので、v4 の数字は論文に使わないと決めている（D66 の 5）。
- 36.4% は事前登録していない事後の分析である。
- （ほかに）v4 のデータは最終評価から除く、抜き取りと判定の規則が最終評価と違う。

#### 確認問題 56-3

**保留**です（O2、D70 の 8）。2 人目の判定者を用意できるかもしれないが、まだ分からないためです。決まるまでは、D67 の 4（判定は学生 1 人）が既定です。
2 人目が用意できたら、判定の一部を独立に判定してもらう案を判定し直しより先に検討し、件数・対象の抜き方・裁定のしかた・一致の指標（κ）を決めます。用意できなければ、判定し直し（2 週間以上あけて 5〜10%）をするかを決めます。
**期限**は、データを見る前、遅くとも段階 6（抜き取りのコミット）の前です。事前登録に書きます。
期限の後に足すなら、事前登録の §5 に逸脱として理由とともに書き、**事後の分析**として扱います。
LLM を 2 人目の代わりにしない理由: D70 の 3 で判定に LLM を使わないと決めた（同じ系統のモデルどうしでは一致が膨らみ、妥当性の証拠にならない、と調査も判断していた）。

#### 確認問題 56-4

- **上限の目安**: 開発中に見た**解析器の生の数**（例: 開発用の v2 で D1 の矛を出した木が 87 木中 13 木）。人が確かめていないので誤警報を含み、本当の数より大きく出る向きにある。ただし見落としもあるので、厳密な上限ではない。
- **下限**: 最終評価で**人が判定して確かめた数**（(a)〜(c)）。1 木 3 件までしか判定しないことと、矛の出なかった木の見落としを数えないことから、本当の数より小さく出る向きにある。K̂ ≤ N なので、いつも解析器の数の内側から出る。

並べて「改善」「悪化」と言えない理由:
1. 向きが逆（片方は上から、片方は下から押さえる数）なので、差は性能の変化を表さない。
2. データ（開発用の v2 と最終評価のデータ）も、解析器の版も違う（さらに分母も、v2 の全部の木と、宣言を明示した木 M_d で違う）。
