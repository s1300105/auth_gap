### 第 33 章

この章の演習は、repo の記録（`docs/decisions.md` の D59・D60・D66・D70、`docs/open_questions.md` の O45、`docs/fingerprint.json` とコミット `1bcace3` の版、`authgap/report.py` の `fingerprint()`、`scripts/freeze_analyzer.py`、`git log`。本書の執筆時に確かめたもの）を使っています。

#### 演習 33-1（指紋の確かめ）

| | 仕様書の指紋 `sink_table` | 結合 sha256 | 理由 |
|---|---|---|---|
| (a) `requests.get` の `url.host` を `A(0)` → `A(0, kw="url")` | **変わらない** | **変わる** | `fingerprint()` は sink 表の行ごとに `kind` と **slot の名前の並び**（`sorted(r.slots)`）しか入れない。`url.host` という名前は同じなので、`sink_table` は同じ。一方、`authgap/catalog/sinks.py` のファイルの中身は変わるので、そのファイルの sha256 と結合 sha256 は変わる |
| (b) proxy の行に、セッションの `.delete` の行を足す | **変わる** | **変わる** | proxy の行は `recv`・`method`・`kind`・slot の名前・`from_ctor` を並べて入れるので、行が 1 つ増えれば `sink_blob` の文字列が変わる（`counts.proxy_rows` も 17 から 18 になる）。ファイルも変わるので結合 sha256 も変わる |
| (c) `engine.py` の説明の文だけを書き換える | **変わらない** | **変わる** | val エンジンは仕様書の指紋の対象ではない。けれども、ファイルの中身が 1 文字でも変われば、そのファイルの sha256 と結合 sha256 は変わる |

(a) は、D59 の追記（`3086043` → `90ef6dd`）で実際に起きたことと同じ形です。
本書の執筆時に計算すると、`sink_table` はどちらも `48554b6446c2…`、結合 sha256 は `0655262dfc93…` から `f2c2bf9edeb8…` に変わりました。
(c) のように、動作の変わらない変更（説明の文だけ）でも結合 sha256 は変わります。
結合 sha256 は「同じかどうか」を厳しく見る道具で、「動作が同じかどうか」を見る道具ではありません。
だから、凍結の後は説明の文も含めて `authgap/` を一切触らないのが安全です。
（出典: `authgap/report.py:57-80`、`scripts/freeze_analyzer.py:4-10`、`scripts/freeze_f0a.py:46-56`（`implementation_hashes`））

#### 演習 33-2（約束の当てはめ）

| | 破る半分 | 理由 |
|---|---|---|
| (a) repo の文脈を読み込んだ AI に評価データのコードを貼る | **前半「本記録者が一度も見ない」** | この repo の文脈を持つ AI は本記録者と同じ文脈を持つので、評価データを本記録者が見ることになる（O45 の 3）。D70 の 3 は、原ソースを読む補助にも AI を使わないと決めている。行を探すには grep やエディタの検索・「定義へ移動」を使う |

| (c) v4 で判定の練習をする | **どちらも破らない** | v4 は最終評価のデータではない（D66 の 3 で除いた）。練習に使うのは手順書が強く勧めていること（6.8 節）。ただし、v4 の判定は本記録者（AI）が付けたもので正解ではない。食い違ったら AI を正しいとみなさず、手引きの穴として扱う |
| (d) 論文に「研究の遂行に AI を使った」と開示する | **どちらも破らない** | 開示は O45 の 4 が求めている作業で、評価データを本記録者に見せることでも、開発に使うことでもない |

(a) は、学生本人は本記録者ではないので、学生がコードを読むことは約束に触れません。
触れるのは、本記録者と同じ文脈を持つ AI にコードを見せることです。
(b) は、学生が自分で直す場合でも、後半を破ります。
誰が直すかではなく、評価データで見つけたことを開発に使うかどうかが問題だからです。

#### 演習 33-3（時刻の順番）

D60 と v3 の手続きを書いたコミット `3aa899e` と、v3 の抽出と pin のコミット `d103051`、v3 の走査のコミット `9c8eb81` を比べます。

| コミット | 時刻（UTC） | 中身 |
|---|---|---|
| `3aa899e` | 2026-09-24 13:07:07 | D60 と `docs/population_v3.md`（v3 の枠・抽出・確かめ方） |
| `d103051` | 2026-09-24 13:08:26 | v3 の抽出と pin |
| `9c8eb81` | 2026-09-24 13:20:28 | v3 の走査と、判定の対象 |

D60 のコミットは、v3 の抽出より前です。
時刻だけでなく、**コミットの親子関係**でも確かめられます。
本書の執筆時に `git merge-base --is-ancestor 3aa899e d103051` を実行すると、`3aa899e` は `d103051` の祖先（先にあったコミット）でした。
時刻はコミットを作るときに書き換えることもできますが、親子関係は後のコミットが前のコミットの番号を含んで作られるので、順番を偽るのは難しくなります。
さらに、`docs/population_v3.md` の冒頭は「抽出・取得・走査の前に書く（2026-09-24）。書いた後で規則を変えない」と書いています。
つまり、D60 は v3 のデータを 1 件も見ていない時点の決定です。
（出典: `git log --date=iso` と `git merge-base --is-ancestor`（本書の執筆時に実行）、`docs/population_v3.md:3-4`）

#### 確認問題 33-1

D59 の「凍結の条件」は、直す作業の**前**（11 時 21 分の規則のコミット）に、次のことを決めていました。

- v2 は開発用のデータで、主張の評価には使わない。評価は凍結後の v3 で行う。
- **いつ**凍結するか: D59 の実装・取り直し・消えた行の確認を終えた時点。
- 凍結の**後**の扱い: 見つけた欠陥は直さず、既知の限界として記録する。直すなら事前登録に逸脱として書き、v3 の結果は凍結時の版を主とする。

先に決めておいたので、D60 で方針を変えるとき、「どの規則を、なぜ変えるのか」を記録の上ではっきり書けました。
D60 は「D59 の凍結の条件を変える（理由を先に書く）」として、その規則が「v3 が評価データになる前提」のものだったこと、前提が変わったことを書いたうえで変えています。
条件を先に書いていなければ、方針の変更は「黙って約束を破った」のと区別できなかったはずです。

#### 確認問題 33-2

仕様書の指紋（`fingerprint()` の `sink_table` など）は、sink 表の「kind と slot の名前」しか見ず、slot の値をどの引数から読むか（`A(1, kw="url")`、`body ← data|json`）や、val エンジンの実装を区別しないからです。
D59 の追記（宛先を `url=` からも読む）は、宛先の無い NET の効果を 1,693 件から 6 件に変える大きな変更でしたが、`sink_table` の指紋は 1 文字も変わりませんでした（本書の執筆時に確かめた）。
凍結の目的は「評価を、凍結した版と**同じ**解析器で測ったこと」を後から確かめられることなので、中身が変わっても指紋が変わらないのでは役に立ちません。
全ファイルの sha256 と結合 sha256 なら、1 文字の変更でも値が変わります。
仕様書の指紋も、仕様書が決めたものなので消さずに残し、実装の指紋を足しました。

#### 確認問題 33-3

D60 の約束は「評価データを**本記録者が一度も見ない**・**開発に使わない**」です。

- **後半「開発に使わない」**は、解析器や判定の決め事が評価データに合わせて育たないことを守ります。評価データで見つけた誤りを直したり、評価データの結果を見て規則を変えたりすれば、評価が甘くなるからです。
- **前半「本記録者が一度も見ない」**は、解析器と手引きの下書きを作った側（本記録者）が評価データを知らないことを守ります。直さなくても、見ただけで、その後の推奨や記録に見た内容が混ざりえ、混ざったかは外から確かめられないからです。

v4 は、**後半を守り、前半を破りました**。
D66 の 1・2 で、解析器・原理・判定表・語彙を変えず、見つけた誤りは直さずに O43 に書くと先に決めたので、開発には使っていません。
けれども、本記録者が 88 木を走査し、矛と見落としを判定したので、本記録者が見たデータです。
だから D66 の 3 は、「本記録者が見たデータなので」と書いて、v4 を最終評価のデータから除きました。
（v4 の結果が、判定の決め事 D67 にも影響したことも、除く理由を強めます。）

#### 確認問題 33-4

D70 の 3 は、最終評価の判定に AI（LLM）を一切使わない（判定・原ソースを読む補助・不の組への対照の腕・2 人目の判定者の代わりのどれにも）と決めました。
D60 の約束とのつながりは、O45 の 3 つ目の問い「本記録者の範囲」です。
この repo の文脈（CLAUDE.md・決定の記録・v4 の判定）を持つ AI を、最終評価で原ソースを読む補助に使えば、本記録者が評価データを見ることになり、D60 の約束の前半と D66 の 3 に字義の上でぶつかります。

O45 の 3 つの案は、次のように違います。

- **(a) 読む補助を使わない**: 本記録者が評価データを見る場面そのものが無くなる。範囲を定義する必要が無い。
- **(b) repo の文脈を持たない別の実行（API、固定のプロンプト）に限る**: AI は使うが、本記録者と同じ文脈を持たせない。「文脈を持たない」ことを示す必要がある。
- **(c) 本記録者の範囲を「解析器の開発と決定に関わった会話」と定義し、最終評価の補助は別のセッションとして開示する**: 範囲を定義して線を引く。その線を守ったことを示す必要がある。

D70 の 3 は案 (a) にあたり、D70 の本文は「最終評価で本記録者（Claude）が評価データを見ることはなく、D60 の 2・D66 の 3 の約束とぶつからない」と書いています（ここでの「D60 の 2」は、本書の言う「D60 の約束」のことです）。
D70 の 3 は、もう 1 つの理由（判定に LLM を混ぜた先行研究は決められないものを消すか倒している。不明を数える芯と決定性を守る）にも支えられています。
（出典: `docs/decisions.md:3849-3856`、`docs/open_questions.md:1246-1266`）
