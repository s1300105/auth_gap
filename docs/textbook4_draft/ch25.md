## 第 25 章 開発に使うデータと評価に使うデータ

> **この章で分かること**:
> - 解析器を直すために**見た**データで、そのまま解析器の出来を測ると、結果が**甘く**なること。だから、データを役割で分けること。
> - **母集団・枠・標本・列挙・抽出・seed** という言葉の意味と、この研究での具体的な数（列挙した repo 4,211 → 枠 3,764 → 標本 100 件ずつ）。
> - この研究で使う **5 種類のデータ**（較正対・v2・v3・v4・最終評価のデータ）と、それぞれの役割。v2・v3・v4 は**本記録者（AI）が見たデータ**なので、最終評価から除くこと（D60 の 2、D66 の 3）。
> - 最終評価のデータは、枠から v2・v3・v4 の 300 件を除いた**残りを全部**走査すること。抽出はしない。列挙もし直さない（D69 の 1）。そのうえで、**中身の重複を除く**こと（D70 の 6）。
> - **seed**（乱数の種）の一覧。v2 は 20260920、v3 は 20260924、v4 は 20260929。最終評価では抽出用の seed は要らず、判定の対象を選ぶための seed を **4 つ別々に**使うこと（D70 の 7）。5 つ目は【確認】で、まだ承認されていないこと。
> - 枠の数の食い違い（3,827 と 3,764。O40）の読み方。
> - 出所を確かめられない記述（「v3 でも 100 木中 8 木に、それまでのデータと同一のファイルがあった」）を**未検証**として扱い、根拠に使わないこと。

### この章の位置づけ

第 22 章では、「先に決めて、後から変えない」ための仕組み（事前登録・凍結・封）を学びました。
そこでは「評価のデータを**見る前に**決める」という言い方を何度も使いました。
けれども、「見る」とは**誰が、どのデータを**見ることなのかは、まだ詳しく説明していませんでした。
この章で、それをはっきりさせます。

1. 解析器を作るときに使ったデータと、解析器の出来を測るデータを、なぜ分けるのか。

### 25.1 なぜデータを分けるのか — 見たデータで測ると甘くなる

#### 一言で言うと

解析器を直すために見たデータで、そのまま解析器の出来を測ると、出来が**実際より良く**見えます。
だから、**直すのに使うデータ**（開発用）と、**出来を測るデータ**（評価用）を分けます。

#### たとえ話 — 過去問だけで勉強して、同じ過去問で試験を受ける

ある試験の過去問を 1 回分だけ手に入れたとします。
その過去問を何度も解いて、間違えた問題の答えを覚えました。
そのあと、**同じ過去問**で模擬試験を受けると、ほぼ満点が取れます。

けれども、その満点は「試験の実力」を表していません。
覚えた問題の答えを書いただけだからです。
本当の実力を知るには、**まだ見ていない問題**で試験を受ける必要があります。

解析器も同じです。
あるデータで誤りを見つけて直すと、そのデータの上では誤りが消えます。
けれども、それは「そのデータに合わせて直した」結果で、まだ見ていないデータでも同じように誤りが少ないとは限りません。

#### 小さな例 — 作り話の数字で、甘さを見る

説明のための作り話の数字で考えます（本当の値ではありません）。
解析器が「宣言に反する」と出した組（矛）を、データ A とデータ B でそれぞれ 100 件ずつ人が確かめたとします。

| | データ A（直すのに使った） | データ B（まだ見ていない） |
|---|---|---|
| 直す前 | 正 70・誤 30 | 正 70・誤 30 |
| A で見つけた誤りの型を直した後 | 正 70・誤 10 | 正 70・誤 22 |
| 精度（正 ÷（正 + 誤）） | 70 ÷ 80 = **87.5%** | 70 ÷ 92 = **約 76.1%** |

表の読み方: 2 行目は「データ A で見つけた誤りの型を直した後、A の上では誤が 30 件から 10 件に減ったが、B の上では 30 件から 22 件にしか減らなかった」と読みます。

#### 一歩ずつの説明

1. 直す前は、A も B も同じくらいの出来です（正 70・誤 30）。
2. A の誤 30 件を 1 件ずつ見ると、そのうち 20 件は、ある 2 つの型（たとえば「名前の末尾だけで呼び出し先を決めてしまう」型）でした。そこで、その 2 つの型を直しました。
3. A の上では、その 20 件がまるごと消えます。A を見ながら直したのですから、当然です。残りは 10 件です。
4. B の誤 30 件のうち、同じ 2 つの型は 8 件しかありませんでした。B には、A に出てこなかった別の型の誤りが多かったのです。だから B の誤は 22 件残ります。
5. 精度を計算すると、A では 87.5%、B では約 76.1% です。
6. **A で測った 87.5% は甘い値**です。解析器の「まだ見ていないデータでの出来」に近いのは、B の約 76.1% のほうです。

数字は作り話ですが、仕組みは本物です。
直す人は、見たデータの誤りを直します。だから、見たデータの上での出来は、どうしても良く見えます。

#### この研究で実際に起きたこと — v3 の場合

この研究でも、同じことが問題になりました。
母集団 v3（25.4 節）は、最初は「凍結した解析器 `analyzer-freeze-1` を、まだ見ていないデータで確かめる」ためのデータでした。
本記録者が v3 の矛を判定すると、D1・D2 の矛は抜き取った 60 件中 49 件が正（81.7%）で、誤が 11 件ありました。見落としも 30 件中 7 件見つかりました。

そのあと、v3 で見つけた欠陥の一部を直しました（D61）。
直した時点で、v3 は**直すのに使ったデータ**になりました。
だから今の解析器（`analyzer-freeze-3`）の出来を v3 で測ると、甘くなります。
v3 は今、開発用のデータとして扱います。
（出典: `docs/population_v3.md:8-14`（役割）、`:78-83`（V2 の結果 49 / 60）、`:90-93`（見落とし 7）、`docs/decisions.md:3392-3406`（D60）、`:3408`（D61 の見出し）。）

#### なぜそうするのか — 直し方が「データに合わせた直し方」になるから

甘くなる理由は、もう 1 つあります。
データを見ながら直すと、**そのデータにだけ効く直し方**を入れてしまうことがあるのです。

実際、v3 の所見を直すときに、学生は次の方針を出しました（D61）。

> 検証データを見て変更するのはきりがなく、研究として良くない。誤りの修正が一般的に役立つものなら改善する。

それでも、直した 5 つのうち 2 つ（G1・G2）は、敵対的レビュー（第 24 章）で「一般には正しくない」と分かり、取り消しました。
つまり、気を付けていても、見たデータに引っぱられた直し方は入りうる、ということです。
だから、最後の評価は、**誰も直すのに使っていないデータ**で行う必要があります。
（出典: `docs/decisions.md:3408-3412`（D61 の方針）、`:3459`（D61 の改訂: G1・G2 を取り消す）。）

#### よくある誤解・つまずき

- **誤解: 「データを見ても、直さなければ評価に使ってよい」**
  そうとは限りません。v4（25.4 節）は解析器を直すのに使っていません。それでも最終評価から除きます。理由の 1 つは、v4 の結果を見て、**判定の決め事**（D67）を決めたからです。決め事が v4 に合わせて作られている以上、v4 で測れば、決め事にとって甘い試験になります（25.5 節）。
- **誤解: 「甘くなるのは、わざと都合よく直したときだけ」**
  違います。悪意がなくても起きます。見た誤りを直すのは自然なことで、その自然な行動が、見たデータの上での出来を押し上げます（第 22 章の「矢を射た後で的を描く」と同じ構図です）。
- **つまずき: 「開発用のデータは、無駄だった」と思う**
  無駄ではありません。開発用のデータは、解析器を良くするために使いました。ただ、**出来を測る**役には使えない、というだけです。役割が違うのです。

#### 手作業ではどう使うか

最終評価の判定をするときは、次のことを守ります。

- 判定するデータは、本記録者も、解析器を直す作業も、一度も見ていないデータです。だから、判定の結果を見て解析器を直すことはしません（凍結。第 22 章）。
- 判定の途中で解析器の誤りを見つけても、直さずに限界として記録します（`docs/open_questions.md` に書く。O43 と同じ扱い）。直すと、最終評価のデータが「直すのに使ったデータ」になってしまうからです。
（出典: `docs/drafts/final_judging_guide_draft.md:672`（解析器の誤りを見つけても直さない）。）

#### この節のまとめ

見たデータで直すと、そのデータの上での出来は良く見える（作り話の例で 87.5% と約 76.1%）。
だから、直すのに使うデータ（開発用）と、出来を測るデータ（評価用）を分ける。
v3 は最初は確かめるためのデータだったが、見つけた欠陥を直したので、今は開発用。

### 25.2 母集団・枠・標本 — 言葉をそろえる

#### 一言で言うと

「何について言いたいのか」の全体を**母集団**、そこから選ぶための一覧を**枠**、実際に選んで調べたものを**標本**と呼びます。
この研究の母集団は「宣言を持つ、公開の Python の MCP サーバ」で、枠は 2026-09-20 の列挙から作った **3,764 の repo** です。

#### たとえ話 — 全国の中学生の平均身長を知りたい

全国の中学生の平均身長を知りたいとします。

- 知りたい全体は「全国の中学生」です。これが**母集団**です。
- 全員を測るのは大変なので、どこかから選びます。選ぶには、名前の一覧が要ります。たとえば「ある日に集めた、全国の中学校の名簿」です。これが**枠**です。
- 名簿から、くじで 100 人を選んで測ります。この 100 人が**標本**です。
- くじで選ぶことを**抽出**と呼びます。

ここで注意が 1 つあります。
名簿は「ある日に集めた」ものです。その日より後に転校してきた生徒は、名簿に載っていません。
つまり、**枠と母集団はぴったり同じではない**ことがあります。

#### 言葉の整理

- **母集団**
  - やさしく言うと: 結論を言いたい相手の全体。
  - 正確な定義: 研究の結論が当てはまると主張する対象の全体。この研究では「宣言（MCP の ToolAnnotations）を持つ、公開の Python の MCP サーバ」（決定 D29）。
  - 例: GitHub に公開されていて、ツールに `readOnlyHint` などの注記を付けている Python の MCP サーバ全部。
- **列挙**
  - やさしく言うと: 条件に合うものを検索して、一覧に書き出すこと。
  - 正確な定義: GitHub の code search（コード検索）で、宣言の書き方を含む `.py` ファイルを探し、その repo を書き出すこと。この研究では 2026-09-20 に 1 回だけ行った。
  - 例: 「`annotations=ToolAnnotations(` を含む Python ファイル」を検索して、見つかったファイルの repo を並べる。
- **枠**
  - やさしく言うと: くじを引く箱に入っている名札の一覧。
  - 正確な定義: 標本を選ぶ元にする、母集団の要素を並べた一覧。この研究では、列挙の結果から決まった規則で作った 3,764 の repo の一覧。
  - 例: `docs/corpus_sample_v2.json` の `n_population` の欄に書かれた 3,764。
- **標本**
  - やさしく言うと: 箱から実際に引いた名札。
  - 正確な定義: 枠から選び、実際に取得して調べたもの。この研究の v2・v3・v4 は、それぞれ枠から 100 件を選んだ標本。
  - 例: v2 の 100 件（そのうち MCP サーバだったのは 87 木）。
- **抽出**
  - やさしく言うと: くじで選ぶこと。
  - 正確な定義: 乱数を使って、枠から決まった数を選ぶこと。乱数の出発点（seed。25.7 節）を記録しておけば、誰がやっても同じものを選び直せる。
  - 例: seed 20260920 で 3,764 から 100 件を選ぶ（v2）。

#### 小さな例 — 列挙から標本までの数

| 段階 | 数 | 何をしたか |
|---|---|---|
| ① 列挙（ファイル単位） | 16,260 行 | 形 A（`annotations=ToolAnnotations(`）9,090 行 + 形 B（`annotations={` と `readOnlyHint`）7,170 行 |
| ② repo で重複を除く | 4,211 repo | 同じ repo の複数のファイルを 1 つにまとめた |
| ③ 規則で除く（文書の集計） | 3,827 repo | SDK 自身 1、宣言が tests や examples などにしか無い 379、同梱コピーだけ 4 を除いた |
| ③' 抽出スクリプトの母集団 | **3,764 repo** | 実際に v2・v3・v4 の抽出に使った枠（③ との差は 25.3 節） |
| ④ 抽出 | 100 件 | seed で無作為に選ぶ（v2・v3・v4 のそれぞれ） |
| ⑤ 取得後の条件 | v2 は 87 木 | 宣言ファイルが `mcp` / `fastmcp` を import しない 13 を除いた |

表の読み方: 3 行目は「repo で重複を除いた 4,211 から、SDK 自身・宣言がテストや例にしか無いもの・同梱コピーだけのものを除くと、文書の集計では 3,827 になる」と読みます。
4 行目の 3,764 は、同じことをするはずの抽出スクリプトが数えた値で、③ と食い違っています。その話は 25.3 節でします。
（出典: `docs/population_v2.md:74-79`（列挙と除外と 87 木）、`docs/corpus_sample_v2.json` の `n_population`（3,764）と `n_enumerated_repos`（4,211）、`evidence/population_v2/post_fetch_check.json` の `counts`。）

#### 一歩ずつの説明

1. **① 列挙**: GitHub のコード検索で、2 つの書き方（形 A・形 B）を探しました。検索の結果はファイル単位なので、同じ repo が何度も出てきます。
2. **② repo でまとめる**: repo の名前（大文字と小文字を区別しない）で重複を除き、4,211 の repo になりました。
3. **③ 規則で除く**: 母集団の定義に合わないものを除きます。SDK 自身（`modelcontextprotocol/python-sdk`）、宣言が `tests` や `examples` や `docs` の下にしか無いもの、同梱コピー（`site-packages` などに入った他人のコード）だけのものです。「自前のサーバ本体に宣言があること」を求めるためです。
4. **④ 抽出**: 枠から乱数で 100 件を選び、その時点の版（SHA）に pin しました。
5. **⑤ 取得後の条件**: 取得してから、宣言を含むファイルが本当に `mcp` か `fastmcp` を import しているかを確かめます。していないものは「宣言はあるが MCP サーバではない」として除きます。v2 では 100 件中 13 件がこれに当たり、87 木が残りました。
（出典: `docs/population_v2.md:12-34`（定義と除外）、`:36-46`（列挙の手段）、`:48-57`（pin と抽出）。）

#### なぜ「宣言を持つもの」に絞ったのか

この研究の問いは、「宣言と、コードが実際にできることを照らし合わせる」ことです。
宣言が無いサーバでは、照らし合わせる相手がありません。
だから母集団を「宣言を持つもの」に絞りました（D29）。

ただし、この絞り方には**偏り**の心配があります。
宣言をきちんと書くような作者は、コードも丁寧に書く傾向があるかもしれません。
選び方のせいで結果が偏ることを**選択効果**と呼びます。
だから、結果は「宣言を持つ公開 Python MCP サーバについて」の主張であり、MCP サーバ全体には一般化しません。
（出典: `docs/population_v2.md:6-10`（D29 の決定）、`:65-69`（書けること / 書けないこと、選択効果）、`docs/decisions.md:589-596`（D29）。）

#### よくある誤解・つまずき

- **誤解: 「3,764 は MCP サーバの数だ」**
  違います。3,764 は「src 側の `.py` に宣言の書き方がある repo」の数です。取得して確かめると、そのうちの一部は MCP サーバではありません（v2 では 100 件中 13 件、v3 では 100 件中 9 件、v4 では取得できた 99 件中 11 件）。
- **誤解: 「枠に入らなかったサーバは、宣言を持っていない」**
  そうとは限りません。たとえば `annotations=spec.annotations` のように、注記を変数に入れて渡す書き方は、検索の形 A・形 B に当たらないので、列挙で拾えません。これは母集団の定義の一部で、後から欠陥として足さないと先に決めてあります。
- **つまずき: 「母集団」と「枠」を同じものだと思う**

（出典: `docs/population_v2.md:16-22`（形 A・形 B 以外は拾えない）、`evidence/population_v{3,4}/post_fetch_check.json` の `counts`、`docs/final_evaluation_procedure.md:204`（0-6 の弱み）。）

#### 手作業ではどう使うか

- 最終評価の論文では、「どの母集団について言えるか」を、この節の言葉で書きます。たとえば「2026-09-20 の列挙から作った枠（3,764 repo）の、v2〜v4 を除いた残りについて」です。

#### この節のまとめ

母集団は結論を言いたい全体（宣言を持つ公開 Python MCP サーバ）、枠は選ぶ元の一覧（2026-09-20 の列挙から作った 3,764 repo）、標本は実際に選んで調べたもの。
枠は母集団とぴったり同じではない（後から作られたサーバ、検索の形に当たらないサーバは入らない）。
宣言を持つものに絞ったので、選択効果の心配があり、結果は「宣言を持つサーバについて」の主張になる。

### 25.3 枠の数の食い違い — 3,827 と 3,764（O40）

#### 一言で言うと

枠の大きさは、文書の集計では **3,827**、抽出に実際に使ったスクリプトでは **3,764** で、63 違います。
63 のうち 4 は説明できますが、**残り 59 は原因が分かっていません**（O40）。
ただし、v2・v3・v4 はどれも同じ 3,764 から選んだので、三者の比較には影響しません。

#### たとえ話 — 名簿の表紙と中身で人数が違う

クラスの名簿の表紙に「38 人」と書いてあるのに、中身を数えると 37 人だったとします。
1 人の違いの理由が分かれば直せます。分からなければ、「表紙と中身で 1 人違う。理由は分からない」と書いておくしかありません。

大事なのは、くじを引いたのが**中身の名簿**からだ、ということです。
同じ名簿から何回くじを引いても、くじどうしを比べる分には、表紙の数字の違いは関係ありません。

#### 小さな例 — 3 つの数

| 数 | 何の数か | どこに書いてあるか |
|---|---|---|
| 3,827 | 文書の集計（src 側に宣言のある repo） | `docs/population_v2.md` の結果、`evidence/population_v2/enumeration.json` |
| 3,768 | 抽出スクリプトの判定のうち、`path_class` の判定だけを使った場合 | `docs/population_v3.md` の抽出の結果 |
| 3,764 | 抽出スクリプトが実際に使った母集団 | `docs/corpus_sample_v2.json` の `n_population` |

表の読み方: 2 行目は「抽出スクリプトの判定から、同梱コピーの判定を外して、`path_class`（ファイルの場所の分類）の判定だけにすると 3,768 になる」と読みます。

#### 一歩ずつの説明

1. 3,827 − 3,764 = 63 の差があります。
2. 抽出スクリプトは、文書の集計に無い判定を 1 つ持っています。ファイルの場所が `site-packages` などの同梱コピーの場所か、`/mcp/server/` を含むかを見て、同梱コピー（`vendored`）として除く判定です。これを外すと 3,768 になります。3,768 − 3,764 = 4 なので、**4 はこの判定で説明できます**。
3. 残りは 3,827 − 3,768 = **59** です。この 59 の原因は分かっていません。列挙のときの集計が、別の手続きだった可能性があります。
4. v2・v3・v4 の抽出は、どれも抽出スクリプトの 3,764 から行いました。v3 の抽出元は 3,764 から v2 の 100 を除いた 3,664、v4 の抽出元は v2 と v3 の 200 を除いた 3,564 です（それぞれの `n_population` の欄）。

コードで見ると、抽出スクリプトの次の部分が同梱コピーを判定しています。

```python
1  VENDORED = ("site-packages", "node_modules", ".venv", "venv", "vendor")
2
3  def cls(p: str) -> str:
4      parts = re.split(r"[/\\]", p)[:-1]
5      if any(x in VENDORED for x in parts) or p.endswith("mcp/types.py") or "/mcp/server/" in "/" + p:
6          return "vendored"
7      return path_class(p)
```

- 1 行目: 同梱コピーが置かれやすいディレクトリの名前を、組（タプル）にして並べています。
- 3 行目: ファイルのパス `p` を受け取り、そのファイルの分類を文字列で返す関数 `cls` を定義します。
- 4 行目: パスを `/` か `\` で区切ってディレクトリの名前の並びにし、最後の要素（ファイル名）を除きます。
- 5 行目: ディレクトリの名前のどれかが 1 行目の一覧に入っているか、パスが `mcp/types.py` で終わるか、パスに `/mcp/server/` を含むなら、
- 6 行目: 「同梱コピー（`vendored`）」と分類します。
- 7 行目: そうでなければ、別のスクリプトの `path_class` に分類を任せます（`src`・`non_src` などを返す）。

母集団に入れるのは、宣言ファイルの分類に `src` が 1 つでもある repo です。
5〜6 行目の判定があるぶん、抽出スクリプトの母集団は、`path_class` の判定だけで数えた 3,768 より 4 件少ない 3,764 になります。
（出典: `scripts/sample_population_v2.py:27-34`（`VENDORED` と `cls`）、`:60-61`（母集団の作り方）、`docs/population_v3.md:64-69`（食い違いの記録）、`docs/open_questions.md:1051-1057`（O40）、`docs/corpus_sample_v3.json`・`docs/corpus_sample_v4.json` の `n_population`。）

#### もう 1 つの訂正 — 計算せずに書いた数

この食い違いには、もう 1 つ記録があります。
v3 の抽出のコミット（`d103051`）のメッセージには「3,827 から 100 を除いた 3,727」と書かれていました。
これは**計算せずに書いた誤り**で、正しくは「3,764 から 100 を除いた 3,664」です。
文書（`docs/population_v3.md`）に訂正が書いてあります。
コミットのメッセージは後から書き換えられないので、正しい値は文書の側に残す、という扱いです。
（出典: `docs/population_v3.md:60-63`。）

#### なぜそう扱うのか — 「不明」として記録する

原因の分からない 59 を、どちらかに「たぶんこうだろう」と決めて片づけることはしません。
この repo の規則 4「解決できなかったものは『不明』として記録する。黙って安全側に倒さない」に従い、O40 に**不明**として書いてあります。

そのうえで、影響を見積もっています。
O40 は「v2 の抽出は 3,764 から行われたので、報告する枠の大きさは 3,764 が正しい可能性が高い。v2 と v3 の比較には効かない」と書き、学生の判断は「無し（最終評価の枠を書くときに、どちらの数を使うかだけ注意する）」としています。
（出典: `CLAUDE.md` の規則 4、`docs/open_questions.md:1055-1057`。）

#### よくある誤解・つまずき

- **誤解: 「原因の分からない差があるなら、枠は信用できない」**
  枠の中身（どの repo が入っているか）は、抽出スクリプトが毎回同じ規則で作るので、再現できます。分からないのは「文書の集計の 3,827 がどう数えられたか」のほうです。くじは中身の一覧から引いているので、標本の選び方そのものは崩れていません。
- **誤解: 「大きいほうの 3,827 を書けばよい」**
  抽出に使ったのは 3,764 です。論文で枠の大きさを書くなら 3,764 を使い、O40 の食い違いを注記するのが正確です（最終評価の事前登録の下書きも「抽出スクリプトの母集団 3,764 repo。O40」と書いています）。
- **つまずき: 「v2 と v4 の結果を比べるとき、59 の差が効く」と思う**
  効きません。v2・v3・v4 は同じ 3,764 から選んでいるので、比べる 2 つの標本は同じ一覧から来ています。

#### 手作業ではどう使うか

- 最終評価の件数の流れを書くとき（段階 3）、出発点は 3,764 です。そこから v2・v3・v4 の 300 件を除きます（25.6 節）。
- 論文の方法の節で枠の大きさを書くときは、3,764 と書き、「文書の集計 3,827 との差 63 のうち 59 は原因不明（O40）」と注記します。
（出典: `docs/drafts/prereg_2_12_draft.md:24`。）

#### この節のまとめ

枠の大きさは文書で 3,827、抽出スクリプトで 3,764。差 63 のうち 4 は同梱コピーの判定で説明でき、残り 59 は原因不明（O40）。
v2・v3・v4 は同じ 3,764 から選んだので、比較には効かない。論文では 3,764 を書き、食い違いを注記する。

### 25.4 5 種類のデータ

#### 一言で言うと

この研究には、役割の違う **5 種類のデータ**があります。
**較正対**・**v2**・**v3** は開発用、**v4** は凍結版の中間検証用（本記録者が確かめた）、そして**最終評価のデータ**だけが論文の評価用です。

#### たとえ話 — 新しい料理を店に出すまで

料理人が新しい料理を店に出すまでを考えます。

1. まず、昔からある有名な失敗例（焦げた、塩が多すぎた）を再現して、自分の作り方がそれを避けられるかを確かめます。→ **較正対**
2. 次に、家族に何度も食べてもらい、そのたびに作り方を直します。→ **v2**
3. 作り方が固まったら、知り合いに食べてもらいます。そこで見つかった問題も、一部は直しました。→ **v3**
4. 作り方を「もう変えない」と決めて、料理人の助手が別の知り合いに試食してもらいました。結果は記録しましたが、作り方は変えていません。ただし、試食の結果を見て、審査で使う採点表の書き方を決めました。→ **v4**
5. 最後に、まだ誰も食べていない新しいお客さんに出し、審査員（料理人本人ではない）が採点表で評価します。→ **最終評価のデータ**

1〜4 は、どれも料理人か助手が「味を知っている」料理です。
本当の評価になるのは 5 だけです。

#### 一歩ずつの説明 — 1 行ずつ

**較正対**は、既知の脆弱性（CVE など）を直したコミットの、直す前と直した後のコードの対です（第 8 章）。
解析器が「直す前は危ない、直した後は安全」を見分けられるかを確かめます。
期待する結果を先に書いてコミットし、解析器を直すたびに機械で採点しました（第 23 章）。
特定の脆弱性の修正を選んだもので、枠から無作為に選んだ標本ではありません。

**v2** は、最初の母集団の標本です（2026-09-20〜21）。
枠から 100 件を選び、100 件とも取得でき、そのうち 87 木が MCP サーバでした。
解析器を直すたびに走査し直し、run（走査の 1 回分）の番号が 24 まで進みました。
同じ 87 木でもユニットの数が run20 の 2,231 から run24 の 2,289 に変わったのは、解析器の版が違うからです。run20 は D61 の直しの後の版、run24 は D64 の添削の後の版で、最終凍結（`analyzer-freeze-3`）の根拠の run です。
v2 は、何度も見て直したデータなので、出来を測るのには使えません。

**v3** は、最初の凍結版 `analyzer-freeze-1` を、まだ見ていないデータで確かめるために選んだ標本です（2026-09-24）。
v2 の 100 件を除いた 3,664 から 100 件を選び、100 件とも取得でき、91 木が MCP サーバでした（9 件は宣言ファイルが `mcp` / `fastmcp` を import しない）。
判定は本記録者が行いました。
そのあと、見つけた欠陥の一部を直したので（D61）、今は開発用です。

**v4** は、最終凍結版 `analyzer-freeze-3` を、まだ見ていないデータで確かめた**中間検証**の標本です（2026-09-29、D66）。
v2・v3 の 200 件を除いた 3,564 から 100 件を選びました。
1 件は pin（SHA）が解決できず、99 件を取得し、そのうち 11 件は宣言ファイルが `mcp` / `fastmcp` を import しなかったので、88 木が残りました。
走査すると 3,696 のユニットがありました。
v3 と違うのは、**結果を見ても解析器を変えない**と先に決めたことです。見つけた誤りと見落としは、直さずに限界として O43 に書きました。
判定は本記録者が行い、数字（たとえば D1・D2 の矛の精度 76.7%）は論文に使いません（D66 の 5）。

**最終評価のデータ**は、学生が論文のために手で評価するデータです。
枠から v2・v3・v4 の 300 件を除いた残りを、抽出せずに全部使います（25.6 節）。
判定は学生 1 人が行い、AI（LLM）は使いません（D67 の 4、D70 の 3）。
（出典: `docs/population_v2.md:72-79`、`docs/decisions.md:3493`（D61 の結果は run20）、`:3702`（凍結の根拠の run は run24）、`docs/population_v3.md:58-63`、`docs/population_v4.md:6-16,64-71`、`docs/decisions.md:3743-3754`（D66）、`:3783-3786`（D67 の 4）、`:3849-3856`（D70 の 3）。）

#### v2・v3・v4 の数を並べて読む

3 つの標本は、同じ枠から、同じ規則で、100 件ずつ選んだものです。
並べると、規則がそろっていることが分かります。

| | 抽出元 | seed | 取得 | MCP サーバ | 除いた理由 |
|---|---|---|---|---|---|
| v2 | 3,764 | 20260920 | 100 | 87 | import しない 13 |
| v3 | 3,664（= 3,764 − 100） | 20260924 | 100 | 91 | import しない 9 |
| v4 | 3,564（= 3,764 − 200） | 20260929 | 99（pin の解決できなかった 1 を除く） | 88 | import しない 11 |

表の読み方: 3 行目は「v4 は、3,764 から v2・v3 の 200 件を除いた 3,564 から seed 20260929 で選んだ。取得できたのは 99 件で、そのうち 11 件は宣言ファイルが `mcp` / `fastmcp` を import しないので除き、88 木が MCP サーバだった」と読みます。

抽出元の数が 100 ずつ減っているのは、前の標本を除いてから選んでいるからです。
だから、v2・v3・v4 の間に重なる repo は 1 つもありません（v3 の抽出の記録には「v2 との重なり 0」とあります）。
除いた分を補充しない（取得できなかったものや MCP サーバでなかったものの代わりを選び直さない）のも、3 つで同じです。補充すると「何件から何件に減ったか」という分母の記録が崩れるからです。
（出典: `docs/corpus_sample_v{2,3,4}.json` の `seed`・`n_population`、`evidence/population_v{2,3,4}/post_fetch_check.json` の `counts`、`docs/population_v3.md:61-62`（重なり 0）、`docs/population_v2.md:53-55`（補充しない）。）

#### なぜ 5 種類に分けるのか

それぞれのデータは、**誰が見たか**と**何に使ったか**が違います。

- 較正対・v2・v3 は、解析器を直すのに使いました。
- v4 は、解析器を直すのには使いませんでしたが、本記録者が見て、判定し、その結果を見て判定の決め事（D67）が決まりました。
- 最終評価のデータは、まだ誰も見ていません。

「評価が甘くならない」ことを保証できるのは、最後の 1 つだけです。
だから、論文の評価は最終評価のデータだけで行います（D60）。

#### よくある誤解・つまずき

- **誤解: 「v4 は解析器を直していないから、論文の評価に使える」**
  使いません。理由は 25.5 節で詳しく見ますが、要点は 2 つです。本記録者が見たデータであること（D66 の 3）と、v4 の結果を見て判定の決め事を決めたこと（D67）。さらに、v4 の判定そのものが AI によるもので、人は見直していません。

  v2 の 87 木で 2,289 ユニット、v4 の 88 木で 3,696 ユニットと、木の数はほぼ同じなのにユニットの数はかなり違います。木ごとのツールの数は大きくばらつくので、ユニットの数は少数の大きな木に引っぱられます。数を比べるなら、木の数と並べて読みます。
（出典: `docs/population_v4.md:60-61,116-117`（「改善」「悪化」と書かない）。）

#### 手作業ではどう使うか

- 最終評価から除く repo の一覧は、`docs/corpus_sample_v2.json`・`docs/corpus_sample_v3.json`・`docs/corpus_sample_v4.json` の 3 つの `targets` です。取得後に除いたもの（MCP サーバでなかったもの、pin が解決できなかったもの）も含めて、**抽出した 100 件ずつ全部**を除きます。

### 25.5 なぜ v2〜v4 を最終評価から除くのか — 「見た」とは誰が何を見たか

#### 一言で言うと

この研究には「**評価のデータを本記録者（AI）が一度も見ない・開発に使わない**」という約束があります（D60 の 2）。
v2・v3・v4 は、どれも本記録者が見たデータです。だから最終評価から除きます（D60 の 3、D66 の 3）。

#### たとえ話 — 試験問題を見たコーチ

ある選手を、コーチが何か月も指導してきたとします。
そのコーチが、もし本番の試験問題を前もって見ていたらどうでしょう。
コーチに悪気がなくても、指導の中身は、知らず知らずのうちに試験問題に寄っていきます。
「この形の問題は出るから練習しておこう」と考えるのは自然だからです。
そうなると、本番の点数は、選手の本当の力を表さなくなります。

この研究では、解析器が選手、本記録者がコーチにあたります。
本記録者は、解析器を作り、直し、判定の手引きの下書きを書いてきました。
その本記録者が評価のデータを見てしまえば、解析器や手引きがそのデータに寄っていても、誰にも分かりません。
だから「本記録者が見ていないデータ」で評価するのです。

#### 小さな例 — 約束を 2 つに分けて当てはめる

D60 の約束は、2 つの部分に分けられます。
(i) 本記録者が**見ない**こと、(ii) **開発に使わない**こと、です。
それぞれのデータに当てはめると、次のようになります。

| データ | (i) 本記録者が見たか | (ii) 開発に使ったか | 結論 |
|---|---|---|---|
| v2 | 見た（何度も） | 使った（解析器を直した） | 除く |
| v3 | 見た（判定した） | 使った（D61 で欠陥を直した） | 除く |
| v4 | 見た（判定した） | 解析器には使っていない。ただし判定の決め事（D67）は v4 の結果を受けて決めた | 除く |
| 最終評価のデータ | 見ない（AI は判定に使わない。D70 の 3） | 使わない（凍結のまま） | 評価に使う |

表の読み方: 3 行目は「v4 は、本記録者が見て判定したデータで、解析器を直すのには使っていないが、判定の決め事は v4 の結果を受けて決めた。だから最終評価からは除く」と読みます。
（出典: `docs/decisions.md:3399-3405`（D60 の約束と 3）、`:3752`（D66 の 3）、`:3764`（D67 は v4 で分かったことを受けて決めた）、`:3849-3854`（D70 の 3）。）

#### 一歩ずつの説明

1. **v2・v3 は、(i) も (ii) も破っています。** どちらも、見て、直すのに使いました。
2. **v4 は、(ii) の「解析器を直すのに使う」は守りました。** D66 で「結果を見て解析器を変えない」と先に決め、見つけた誤りは O43 に限界として書くだけにしました。
3. **それでも v4 は (i) を破っています。** 本記録者が判定したデータだからです。D66 の 3 は、理由をそのまま「本記録者が見たデータなので」と書いています。
4. **さらに、v4 の結果は判定の決め事に影響しました。** D67 は冒頭で「v4（D66）で分かったことを受けて、学生が決めた」と書いています。たとえば、起動時の初期化をどう判定するか（D67 の 2）は、v4 の誤の大半（14 件中 9 件）がこの類だったことから決めた事柄です。v4 で最終評価をすると、v4 に合わせて作った決め事で v4 を採点することになります。
5. **最終評価のデータは、(i) も (ii) も守れます。** 解析器は凍結のままで、判定には AI を使わないので、本記録者が評価のデータを見る場面がありません（第 26 章）。
（出典: `docs/population_v4.md:8-16`（役割）、`:99-104`（誤 14 のうち起動時の初期化 9）、`docs/decisions.md:3762-3778`（D67 の 1・2）。）

#### 「見る」のは誰か — 学生は見てよいのか

ここで疑問がわくかもしれません。
「学生は最終評価のデータを見て判定するのだから、学生も『見た』ことになるのでは」。

答えは、**学生は見てよい。ただし、決め事を先に封をしてから見る**、です。

- 学生は、最終評価のデータを見る前に、事前登録 §2.12 と判定の手引きを同じコミットに入れて封をします（第 22 章）。
- 封の後は、判定の途中で手引きを変えません。結果を見て解析器も直しません。
- だから、学生がデータを見ても、決め事や解析器がそのデータに寄ることはありません。

本記録者を「見ない側」に置くのは、本記録者が解析器と手引きの下書きを**作った側**だからです。
作った側が評価のデータを見てしまうと、作ったものがデータに寄ったかどうかを外から確かめられません。
（出典: `docs/drafts/prereg_2_12_draft.md:3-5`（封をしてからデータに触れる）、`docs/decisions.md:3400`。）

#### なぜそうするのか

この約束の目的は、**評価が甘くならないこと**です（25.1 節）。
D60 は、もともと「凍結の後は直さない」という規則を持っていた D59 を、次のように読み替えたものです。

- D59 の規則は、v3 が評価のデータになる前提で、「評価のデータを見た後に解析器を直すと評価が甘くなる」のを防ぐものだった。
- 評価が学生の別のデータで行われるなら、v3 は開発用で、v3 で直しても評価は汚れない。
- 守るべきことは「評価のデータを本記録者が一度も見ない・開発に使わない」ことに移る。

つまり、「何を守れば評価が甘くならないか」を考え直した結果が、この約束です。
（出典: `docs/decisions.md:3396-3400`。）

#### よくある誤解・つまずき

- **誤解: 「v4 の結果はもう出ているので、論文に参考として載せてもよい」**
  D66 の 5 は「論文には使わない」と決めています。v4 の数字（精度 76.7% や、reaper-mcp という 1 木を除いた 36.4%）は、AI が付けた判定から出た数字でもあります。開発の経緯として触れることと、評価の結果として使うことは別です。どう書くかは、論文を書くときに開示の問題として扱います（第 26 章）。
- **誤解: 「本記録者が見たのは v4 の判定した組だけなので、v4 の他の repo は使える」**
  使いません。除くのは、抽出した 100 件の全部です（`docs/corpus_sample_v4.json` の `targets`）。走査した結果（件数・宣言の分布など）は、本記録者が木の全部について見ています。
- **つまずき: 「練習で v4 を使うのは、v4 を見ることになるから駄目」と思う**
  練習で v4 を使うのは、手順書が勧めていることです（6.8）。v4 は最終評価のデータではないので、学生が見ても約束は破れません。ただし、v4 の判定は AI が付けたもので、正解ではありません。食い違ったら、AI を正しいとみなさず、手引きの穴として扱います（第 26 章）。
（出典: `docs/decisions.md:3754`（D66 の 5）、`docs/population_v4.md:123-127`（36.4% は事後の分析）、`docs/llm_judgment_survey.md:163-164`。）

#### 手作業ではどう使うか

- 判定の前に、判定する木が v2・v3・v4 のどれにも入っていないことを確かめます。抽出のスクリプトの `--exclude` と、取得後の重複除去（25.6 節）が、それを保証する仕組みです。
- 判定の途中で、判定の記録や原ソースを AI に見せません（D70 の 3）。見せれば、本記録者（またはその同類）が評価のデータを見ることになります。

#### この節のまとめ

約束は「評価のデータを本記録者が一度も見ない・開発に使わない」（D60 の 2）。
v2・v3 は見て直したデータ、v4 は直していないが本記録者が判定し、その結果で判定の決め事を決めたデータ。どれも除く。
学生は最終評価のデータを見てよいが、決め事を封をしてから見る。

### 25.6 最終評価のデータ — 残りを全部、重複を除いて

#### 一言で言うと

最終評価のデータは、枠（2026-09-20 の列挙、3,764 repo）から v2・v3・v4 の 300 件を除いた**残りを全部**使います。
**抽出はしません。列挙もし直しません**（D69 の 1）。
そのうえで、走査の前に**中身の重複**を除きます（D70 の 6）。

第 3 版の教科書は、最終評価のデータを「v2・v3 と重ならない新しいデータ」とだけ書いていました。これは古い書き方です。今の決定は、上のとおりです。

#### たとえ話 — 体重計は全員に、問診は抜き取りで

学校の健康診断を考えます。
体重計に乗るのは一瞬なので、**全員**の体重を量ります。
一方、医師の問診は 1 人に時間がかかるので、**抜き取った人だけ**に行います。

最終評価も同じ形です。
解析器の走査は機械なので速く、**全部**の木に走らせます。
人の判定は 1 件に時間がかかるので、**抜き取った組だけ**を判定します（第 47 章）。

#### 小さな例 — 件数の流れ

最終評価のデータは、次の順で絞られていきます。
【 】の数は、段階 3・4 で確定するまで分かりません。

```
① 枠: 抽出スクリプトの母集団 3,764 repo（O40）
② v2・v3・v4 の 300 件を除く            → 残り 3,464 repo（計算。段階 3 で【N】として確定）
③ 全部を pin（git ls-remote の SHA）     → pin が解決できなかったものを除く【 】
④ 取得                                  → 取得できなかったものを除く【 】
⑤ 取得後の条件                          → 宣言ファイルが mcp / fastmcp を import しないもの、
                                           宣言ファイルが無いものを除く【 】
⑥ 中身の重複を除く（D70 の 6）           → v2〜v4 と一致した木、今回の中で一致した木を除く【 】
⑦ 走査（全部を 1 回、--require-fingerprint）
⑧ 判定の対象の抜き取り（seed ①②③。第 47 章）
```

- ① 25.2・25.3 節で見た枠です。
- ② 3,764 − 300 = 3,464 です。v3 の抽出元が 3,664、v4 の抽出元が 3,564 だったことと合います（100 ずつ減る）。手順書は「約 3,460 repo」と書いています。
- ③ 抽出しないので、残りの全部を pin します。pin は、その時点の版（SHA）に固定することでした（第 11 章）。
- ④ 取得に失敗した repo は、件数を出して除きます。補充はしません。
- ⑤ v2〜v4 と同じ取得後の条件です（25.2 節の ⑤）。
- ⑥ この節の後半で見ます。**走査の前に**当てます。
- ⑦ 凍結版の解析器で、残った木を全部走査します。1 つの木を走査するのは 1 回だけです。
- ⑧ 判定する組を、決まった規則と seed で選びます。

なお、手順書の 8.5 には「枠の残り 3,464 → pin の解決できなかった 20 を除き 3,444 を取得（失敗 5）→ … MCP サーバ 252 木」という例が書いてあります。これは**書き方の見本**で、測った値ではありません。とくに「252 木」は、全部を走査する今の規模と合わないので、見込みとしても使わないでください。
（出典: `docs/decisions.md:3822-3825`（D69 の 1）、`docs/final_evaluation_procedure.md:139-150`（0-1）、`:614-617`（8.5 の例）、`docs/drafts/prereg_2_12_draft.md:23-36`（(b) 対象）。）

#### 一歩ずつの説明 — なぜ列挙し直さないのか

最初に考えた案は、2 つありました（手順書 0-6）。

- (a) 2026-09-20 の列挙から、v2・v3・v4 の 300 件を除いて使う。
- (b) GitHub のコード検索で、もう一度列挙し直す。

決定は (a) です（D69 の 1）。
理由は、**列挙のスクリプトが repo に無く、手で回した**からです。
v2 の列挙は、コード検索の 1 回 1,000 件の上限を避けるために、ファイルの大きさの範囲で検索を何度も分けて行いました。その手順は文書には書いてありますが、実行したスクリプトそのものは残っていません。
同じ手順を再現しようとすると手間が大きく、しかも「前と同じ手続きで列挙した」と保証できません。

その代わり、(a) には弱みがあります。
**2026-09-20 より後に作られたサーバは入りません。**
これは論文の限界に書きます。
（出典: `docs/decisions.md:3822-3823`、`docs/final_evaluation_procedure.md:198-204`（0-6）、`docs/population_v2.md:36-46`（列挙の手段）。）

#### 一歩ずつの説明 — なぜ抽出しないのか

v2・v3・v4 では、枠から 100 件ずつ選びました。
最終評価では選ばずに、残りを全部使います。
D69 の 1 は、理由を 3 つ挙げています。

1. **走査は安い。** 走査は機械が行います。v4 では 1 木あたり平均 9 秒、いちばん長い木でも 96.8 秒でした（時間上限 180 秒）。
2. **機械が出す数に、抜き取りの誤差が無くなる。** 矛や不の件数、宣言の分布などは、全部を数えれば「標本からの推定」ではなく「全部の数」になります。
3. **めったに出ない D3・D4 の矛が、最大限に集まる。** v4 の 88 木では、D3 の矛は 0 件、D4 の矛は 3 件（1 木）しかありませんでした。全部を走査すれば、こうした少ない矛をできるだけ多く拾えます。

全部を走査しても、**人の判定の量は増えません**。判定するのは、抜き取った組だけだからです（矛は宣言ごとに最大 200 木・1 木 3 件まで、見落とし 200 件、不の中身 100 組。D69 の 2〜4）。
判定の時間の見込みは約 170〜380 時間ですが、これは**測っていない見込み**です（D69 の 6）。判定の練習で 1 件の時間を測り、段階 6 の前に件数を確かめます。

ディスクの量にも注意が要ります。v4 の 99 repo で約 1.2 GB だったので、同じ割合なら約 40 GB の見込みです（これも見込み）。
一度に全部を取得せず、数百 repo ずつ「取得 → 走査 → manifest（解析器の出力。第 18 章）を残して corpus（取得した木を置く場所）を消す」をくり返してよいと決めてあります。判定のときに原ソースが要れば、pin の SHA で同じ中身を取り直せます。ただし、同じ木を 2 回走査はしません。
（出典: `docs/decisions.md:3822-3833`（D69 の 1〜6）、`docs/final_evaluation_procedure.md:141-150`、`docs/population_v4.md:73,78-83`。）

#### 中身の重複を除く — 言葉の整理

- **中身の重複**
  - やさしく言うと: repo の名前は違うのに、中のファイルがまったく同じこと。
  - 正確な定義: ツールの定義（入口の規則に当たるユニット）を含む `.py` ファイルの sha256 が一致すること（D70 の 6）。
  - 例: 他人の repo を丸ごと複製した repo（フォーク）や、他のプロジェクトのコードをそのまま同梱した repo。

GitHub のコード検索は、既定でフォークを除きます。
けれども、フォークの機能を使わずにコードを写した repo や、他のプロジェクトのコードを同梱した repo は、名前が違っても中身が同じことがあります。
（出典: `docs/population_v2.md:33`（fork は既定で除外）、`docs/final_evaluation_procedure.md:206-220`（0-7）。）

#### 小さな例 — sha256 で比べる

ファイルの sha256 は、たとえば次のような短いコードで計算できます（説明のための例で、最終評価の道具そのものではありません。道具は段階 2 で作ります）。

```python
1  import hashlib
2
3  def file_hash(path):
4      with open(path, "rb") as f:
5          return hashlib.sha256(f.read()).hexdigest()
```

- 1 行目: Python の標準ライブラリの `hashlib`（指紋を計算する道具）を読み込みます。
- 3 行目: ファイルのパス `path` を受け取る関数 `file_hash` を定義します。
- 4 行目: ファイルを `"rb"`（バイト列として読む）で開きます。文字として読むと、改行の書き方などで中身が変わることがあるので、バイト列のまま読みます。
- 5 行目: 読んだバイト列全部の sha256 を計算し、16 進数の文字列（64 桁）にして返します。

中身が 1 文字でも違うと、値はまったく変わります。
本書の執筆時に計算した例です（2 つ目は、行末に空白を 1 つ足しただけ）。

| 中身 | sha256（先頭 16 桁） |
|---|---|
| `def search(q):` ↵ `    return db.find(q)` ↵ | `b265da75614acf2d` |
| `def search(q):` ↵ `    return db.find(q) ` ↵（行末に空白 1 つ） | `0d844ebad24edf49` |

表の読み方: 2 行目は「1 行目と同じコードの行末に空白を 1 つ足しただけで、sha256 の先頭 16 桁は `0d844ebad24edf49` になり、1 行目とまったく違う値になる」と読みます。

だから、sha256 が一致するのは「**バイト単位でまったく同じファイル**」だけです。
逆に言うと、少しでも手を入れたコピーは、この規則では重複として除かれません。

#### 小さな例 — 4 つの木で、除く・残すを決める

作り話の 4 つの木で、D70 の 6 の規則を当ててみます。

| 木（repo 名） | ツールの定義を含むファイル | sha256（略） | 一致する相手 | 結果 |
|---|---|---|---|---|
| `alice/weather-mcp` | `server.py` | `aa11…` | 今回の `zed/weather-copy` | **残す**（辞書順で先） |
| `zed/weather-copy` | `server.py` | `aa11…` | 今回の `alice/weather-mcp` | 除く（今回の中の重複） |
| `bob/notes-mcp` | `tools.py`、`server.py` | `bb22…`、`cc33…` | `server.py` が v3 のある木のファイルと一致 | 除く（v2〜v4 との重複） |
| `carol/db-mcp` | `server.py` | `dd44…` | なし | 残す |

表の読み方: 3 行目は「`bob/notes-mcp` には、ツールの定義を含むファイルが 2 つあり、そのうち `server.py` の sha256 が v3 のある木のファイルと一致した。v2〜v4 との重複は 1 ファイルでも一致すれば除くので、この木は除く」と読みます。

#### 一歩ずつの説明 — D70 の 6 の規則

1. 取得した木ごとに、ツールの定義（入口の規則に当たるユニット）を含む `.py` ファイルの sha256 を取ります。
2. **v2〜v4 との重複**: そのファイルの 1 つでも、v2〜v4 の木のどれかのファイルと一致したら、その木を除きます。v2・v3 の中身は手元に残っていないので、`docs/corpus_sample_v{2,3,4}.json` の pin から取り直し、ハッシュだけを残します（中身は保存しなくてよい）。
3. **今回の中の重複**: ツールの定義を含むファイルが一致する木どうしは、repo 名（小文字）の辞書順で最初の 1 木だけを残し、残りを除きます。
4. 除いた木の数と、どの木と一致したかを記録します。
5. 補充はしません（全部を走査する設計なので、補う元がありません）。
6. この規則は**走査の前**（段階 4 の取得後の条件のところ）に当てます。走査の結果を見てから、除く木を選びません。

辞書順で「最初の 1 木」を残すので、どの木を残すかに**乱数は使いません**。
同じ規則なら、誰がやっても同じ木が残ります。
（出典: `docs/decisions.md:3868-3872`（D70 の 6）、`docs/final_evaluation_procedure.md:213-220`、`docs/drafts/prereg_2_12_draft.md:31-35`。）

#### なぜ重複を除くのか

D70 の 6 は、理由を 2 つ挙げています。

- **同じコードを 2 回数えると、木の単位の数字が水増しされる。** 最終評価の主な数字は「本当の矛が 1 件以上あった木の数と割合」です（D67 の 3）。同じサーバのコピーが 5 つあれば、1 つの違反が 5 つの木の違反として数えられてしまいます。
- **v2〜v4 は本記録者が見たデータで、評価から除く約束（D66 の 3）がある。** repo の名前が違っても、中身が v2〜v4 の木と同じなら、本記録者が見たコードです。名前だけで除くと、この約束が中身の上で破れます。
（出典: `docs/decisions.md:3872`。）

#### 文面から読み切れない点 — 封の前に決める

規則 3（今回の中の重複）の「ファイルが一致する木どうし」は、ツールの定義を含むファイルが**複数**ある木で、**一部のファイルだけ**が一致したときにどうするかを、はっきり書いていません。
規則 2（v2〜v4 との重複）は「1 つでも」と書いてあるので、同じ読み方にそろえるのが自然かもしれません。
けれども、これは**本書の指摘**で、決定には書かれていません。封の前に学生が決めて、事前登録か手順に書いておくのが安全です（**未決**）。

#### よくある誤解・つまずき

- **誤解: 「全部を走査するなら、全部を判定する」**
  違います。全部を走査するのは機械の作業です。人が判定するのは、決まった規則と seed で抜き取った組だけです（第 47 章）。
- **誤解: 「列挙し直したほうが新しいデータになるので、必ず良い」**
  新しくはなりますが、同じ手続きで列挙できると保証できません（スクリプトが無い）。枠が変わると、v2〜v4 と「同じ母集団からの標本」とも言えなくなります。今の決定は「列挙し直さない」で、その弱み（2026-09-20 より後のサーバが入らない）を限界に書きます。
- **誤解: 「重複で除いた分は、別の repo を足して埋める」**
  補充しません。除いた数と理由を記録します。
- **つまずき: 重複を除くのを、走査の後にする**
  走査の後に除くと、「矛が出たから除いた」「出なかったから残した」と疑われる余地が生まれます。規則は走査の前に当てます。
- **つまずき: sha256 が違えば別のサーバだと思う**
  sha256 が違っても、ほとんど同じコードということはありえます（空白 1 つの違いでも値は変わる）。D70 の 6 が除くのは「まったく同じファイル」だけです。この限界は、除いた数と一緒に報告すると正直です（本書の提案）。

#### 手作業ではどう使うか

- 段階 3 で、抽出スクリプトの `--n` に母集団より大きな値（たとえば `--n 100000`）を渡すと、残りを全部返します。手順書はこの使い方を書いています。
- 段階 4 で、取得後の条件と重複除去を当て、件数の流れ（① → ⑦）をコミットしてから走査します。
- 判定の対象を選ぶのは、走査の後（段階 6）です。対象の一覧は、判定の前にコミットします。
（出典: `docs/final_evaluation_procedure.md:149-150`（`--n 100000`）、`docs/drafts/prereg_2_12_draft.md:64`（抜き取りの出力は判定の前にコミット）。）

### 25.7 seed — 乱数の種を先に決めて書く

#### 一言で言うと

**seed**（乱数の種）は、コンピュータの乱数の出発点になる数です。
seed を先に決めて書いておけば、誰がやっても同じものが選ばれ、「都合のよいくじが出るまで引き直した」と疑われません。
v2・v3・v4 の抽出には seed を 1 つずつ使いました。最終評価では**抽出用の seed は要らず**、判定の対象を選ぶための seed を **4 つ別々に**使います（D70 の 7）。

#### たとえ話 — 公開されたシャッフルの手順

トランプでくじを作るとします。
カードを切る前に「この手順で、この回数だけ切る」と紙に書いて、みんなに見せておきます。
そのあとで、その手順どおりに切って、上から 5 枚を引きます。
こうすれば、引いた人が「好きなカードが出るまで切り直した」と疑われることはありません。
同じ手順で切れば、誰がやっても同じ 5 枚になるので、後から確かめることもできます。

コンピュータの乱数では、この「切る手順」にあたるのが seed です。

#### 言葉の整理

- **乱数（擬似乱数）**
  - やさしく言うと: コンピュータが作る、でたらめに見える数の並び。
  - 正確な定義: 決まった計算で次々に作られる、規則性の見えない数の並び。計算が決まっているので、出発点が同じなら、まったく同じ並びになる。
  - 例: Python の `random` モジュールが作る数。
- **seed（乱数の種）**
  - やさしく言うと: 乱数の並びの出発点を決める数。
  - 正確な定義: 擬似乱数の計算に最初に与える値。同じ seed を与えれば、同じ乱数の並びが出る。
  - 例: v2 の抽出に使った 20260920。

#### 小さな例 1 — 同じ seed なら同じものが選ばれる

10 個の作り話の repo から 3 個を選ぶ、短いコードです。

```python
1  import random
2  pop = ["repo-00", "repo-01", "repo-02", "repo-03", "repo-04",
3         "repo-05", "repo-06", "repo-07", "repo-08", "repo-09"]
4  rng = random.Random(20260920)
5  print(sorted(rng.sample(pop, 3)))
```

- 1 行目: Python の標準ライブラリの `random`（乱数の道具）を読み込みます。
- 2〜3 行目: 選ぶ元の一覧（枠のつもり）を、名前の順に並べて `pop` に入れます。
- 4 行目: seed 20260920 を出発点にした乱数の道具 `rng` を作ります。
- 5 行目: `pop` から重ならないように 3 個を選び（`sample`）、名前の順に並べ直して（`sorted`）表示します。

本書の執筆時に Python 3.11 で走らせた結果は、次のとおりでした。

| seed | 選ばれた 3 個 |
|---|---|
| 20260920（1 回目） | `repo-02`、`repo-04`、`repo-09` |
| 20260920（2 回目） | `repo-02`、`repo-04`、`repo-09` |
| 20260924 | `repo-00`、`repo-02`、`repo-08` |

表の読み方: 2 行目は「同じ seed 20260920 でもう一度走らせると、1 回目とまったく同じ 3 個が選ばれた」と読みます。3 行目は「seed を 20260924 に変えると、別の 3 個が選ばれた」と読みます。

実際の抽出スクリプトも、同じ形をしています（`rng = random.Random(args.seed)` と `rng.sample(pop, args.n)`）。
選ぶ元の一覧 `pop` は、先に名前の順に並べてあります。**一覧の並び順が変わると、同じ seed でも違うものが選ばれる**からです。
（出典: `scripts/sample_population_v2.py:60-61`（`pop` を `sorted` で作る）、`:66-67`（seed で抽出）。）

たとえば事前登録を 2026-11-02 に書いて封をするなら（作り話の日付）、① は 202611021、② は 202611022、③ は 202611023、④ は 202611024 です。

④ の **bootstrap** は、ここで一言だけ説明します（詳しくは第 39 章）。
判定した木の中から「木を選び直す」ことを何千回もくり返して、割合がどれくらいぶれるかを見る計算です。選び直しに乱数を使うので、seed が要ります。事前登録の下書きは、反復 10,000 回と書いています。

#### 一歩ずつの説明 — 最終評価で抽出用の seed が要らないのはなぜか

1. v2・v3・v4 では、枠から**100 件を選ぶ**必要がありました。何千もの repo から 100 件を選ぶには乱数が要り、だから seed が要りました。
2. 最終評価では、枠から v2〜v4 を除いた**残りを全部**使います（D69 の 1）。選ばないので、乱数は要りません。
3. 重複を除くときに「どの木を残すか」を決める場面がありますが、これは repo 名の**辞書順で最初の 1 木**と決まっていて、乱数を使いません（D70 の 6）。
4. したがって、走査の対象を決めるところには、乱数が 1 つも入りません。抽出用の seed は要らないのです。
5. 乱数が要るのは、**走査の後**で、人が判定する組を選ぶところ（①②③）と、区間を計算するところ（④）だけです。
（出典: `docs/final_evaluation_procedure.md:229`。）

#### 小さな例 2 — 1 つの seed を使い回すと、選ばれ方がつながる

D70 の 7 は、seed を 4 つ別々にする理由を「1 つの番号を使い回すと、抜き取りどうしの選ばれ方がつながるため」と書いています。
「つながる」とはどういうことか、作り話の木で確かめます。

- 矛の出た木（矛の抜き取りの元）: `t01`〜`t20` の 20 木。
- 見落としの対象を持つ木（見落としの抜き取りの元）: `t01`〜`t18` と `t21`・`t22` の 20 木。2 つの一覧は、18 木が共通です。

それぞれから 5 木を選びます。本書の執筆時に Python 3.11 で `random.Random(seed).sample(一覧, 5)` を走らせた結果です。

| 抜き取り | seed | 選ばれた 5 木（名前の順） |
|---|---|---|
| 矛 | 202611021 | `t04`、`t06`、`t07`、`t14`、`t19` |
| 見落とし（同じ seed を使い回す） | 202611021 | `t04`、`t06`、`t07`、`t14`、`t21` |
| 見落とし（別の seed） | 202611022 | `t01`、`t09`、`t10`、`t13`、`t21` |

表の読み方: 2 行目は「見落としの抜き取りに、矛と同じ seed 202611021 を使い回すと、選ばれた 5 木のうち 4 木（`t04`・`t06`・`t07`・`t14`）が矛の抜き取りと同じになった」と読みます。3 行目は「別の seed 202611022 を使うと、矛の抜き取りと重なる木は 1 つも無かった」と読みます。

#### 一歩ずつの説明 — なぜ重なったのか

1. 同じ seed からは、同じ乱数の並びが出ます。
2. `sample` は、その乱数の並びを使って「一覧の何番目を取るか」を決めます。同じ seed なら、取る**位置**（何番目か）が同じになります。
3. 2 つの一覧は、1〜18 番目が同じ木です。だから、同じ位置を取れば、ほとんど同じ木が選ばれます。19 番目だけが違い（矛の一覧では `t19`、見落としの一覧では `t21`）、そこだけ結果が分かれました。
4. つまり、2 つの抜き取りは、**別々にくじを引いたつもりで、実は同じくじを 2 回見ていた**ことになります。

本当は、矛の抜き取りと見落としの抜き取りは、それぞれ独立に選ばれることを前提にしています。
選ばれ方がつながると、たまたま選ばれた少数の木が両方の数字に効き、2 つの結果を「別々の確かめ」として読めなくなります（この段落は本書の説明です。決定に書かれた理由は「選ばれ方がつながる」の 1 文です）。
4 つを別にすれば、こうしたつながりを避けられます。
（出典: `docs/decisions.md:3873-3875`（D70 の 7）。）

実は、v3 では 1 つの番号を使い回していました。v3 は、repo の抽出・矛の抜き取り（60 件）・見落としの抜き取り（30 件）のどれにも seed 20260924 を使っています。v3 は開発用の確認だったので、この章ではそれを問題として扱いません。最終評価では、D70 の 7 のとおり用途ごとに分けます。
（出典: `docs/population_v3.md:21,40,47`。）

#### ⑤ は【確認】 — まだ承認されていない

事前登録の下書きには、5 つ目の seed ⑤ YYYYMMDD5 が書いてあります。
用途は「判定表の順序の並べ替え」です。判定の手引きの第 21 節の 1 は、「判定の順序を無作為にする。同じ木の組が続くと、前の判断に引きずられる」と書いています。その無作為の並べ替えに使う seed です。

けれども、⑤ は D70 の 7 にはありません。本記録者が下書きの中で提案した細部で、**【確認】**（学生が承認していない）の印が付いています。
下書きを承認するときに、⑤ を採るかどうかを一緒に決めます。

もう 1 つ、番号の振り方に小さな食い違いがあります。
手順書の 0-8 は、「判定し直しや 2 人目の判定の対象を抜くなら、同じ形で ⑤ 以降を足す（D70 の 8 で決める）」と書いています。一方、下書きは ⑤ を判定の順序の並べ替えに使っています。
両方を採るなら、番号がぶつかります。下書きを承認するときに、番号をそろえて書くのが安全です（**本書の指摘**。未決）。
（出典: `docs/drafts/prereg_2_12_draft.md:7-8`（【確認】の説明）、`:52`、`docs/drafts/final_judging_guide_draft.md:655`（21 の 1）、`docs/final_evaluation_procedure.md:230`。）

#### なぜ seed を先に書くのか

seed は、**データに触れる前に**事前登録 §2.12 に書いてコミットします。
コミットの日時が、「seed をデータを見る前に決めた」ことの証拠になります（第 22 章）。

もし seed を後から決められるなら、いくつもの seed を試して、都合のよい組が選ばれる seed を採ることができてしまいます。
本人にそのつもりがなくても、「たまたま試した 2 つ目の seed の結果のほうが筋が良さそうに見えた」ということは起こりえます。
先に書いて変えないことで、この疑いを最初から消します。手順書も「データを見た後に seed を変えない」と書いています。
（出典: `docs/final_evaluation_procedure.md:231-233`。）

#### よくある誤解・つまずき

- **誤解: 「seed は他人に知られないように秘密にする」**
  逆です。seed は公開します。公開するから、誰でも同じ選び方を再現でき、都合よく選んでいないことを確かめられます。
- **誤解: 「大きな数や複雑な数のほうが、良い seed」**

### 25.8 確かめられない記述 — 「v3 でも 100 木中 8 木に同一のファイル」（未検証）

#### 一言で言うと

第 3 版の教科書と、最終評価の手順書の 0-7 には、「v3 でも 100 木中 8 木に、それまでのデータと同一のファイルがあった」と書いてあります。
けれども、この数には**コミット済みの原典に出所がありません**。
だから本書では**未検証**とし、重複除去の根拠には使いません。

#### たとえ話 — 伝言ゲーム

A さんが「昨日、駅で 8 人の知り合いに会った」と B さんに話しました。
B さんはそれを C さんに伝え、C さんは「B さんの話によると」と書き留めました。
C さんのメモを読んだ人は、「8 人」という数を、どこまで信じてよいでしょうか。

C さんのメモには「B さんによると」という出所が書いてあります。けれども B さんも、自分で数えたわけではありません。
元をたどると、A さんの話だけが出所で、A さんがどう数えたかを確かめた人はいません。
こういう引き写しの引き写しを**孫引き**と呼びます。

#### 小さな例 — 出所をたどる

| 順 | どこに書いてあるか | 何と書いてあるか | 出所として何を挙げているか |
|---|---|---|---|
| 1 | 教科書の第 1 版（コミット `b7a78fa`、2026-09-24） | v3 でも 100 木中 8 木に既存データと同一のファイルがあった | なし |
| 2 | 教科書の第 3 版 2442 行 | v3 でも、100 木中 8 木にこれまでのデータと同一のファイルがありました（判定した件には関わっていませんでした） | なし |
| 3 | 最終評価の手順書 208 行（0-7） | v3 では 100 木中 8 木に、それまでのデータと同一のファイルがあった | 「教科書 第 38 章」 |

表の読み方: 3 行目は「手順書の 0-7 は、この数の出所として教科書の第 38 章（第 3 版の章番号）を挙げている。つまり、手順書は教科書から写している」と読みます。

#### 一歩ずつの説明

1. 手順書は、出所を「教科書 第 38 章」としています。手順書は原典ではなく、教科書の写しです。
2. 教科書の第 3 版は、出所を書いていません。この記述は、教科書を最初に書いたコミット（`b7a78fa`）の時点からあります。
3. v3 の記録（`docs/population_v3.md`、`evidence/population_v3/` の下のファイル）を探しても、v3 の木と、それまでのデータ（v2 など）のファイルの一致を数えた記録は見つかりませんでした（本書の執筆時に確かめた）。
4. したがって、この数には、コミット済みの原典に出所がありません。手順書は、教科書の数を孫引きしたことになります。

念のため、`git log -S "100 木中 8 木"` で、この文字列を足したコミットを探すと、`b7a78fa`（教科書の第 1 版）と `80ca5da`（手順書を足したコミット）の 2 つだけが出てきます。どちらも数え方を書いていません。
（出典: `git show b7a78fa`（第 1 版の教科書。該当行は出力の 924 行目）、`docs/textbook.md:2442`、`docs/final_evaluation_procedure.md:208`、`git log -S` の結果（本書の執筆時）。）

#### なぜ「未検証」と書くのか

この repo の規則 1 は「未検証の統計を引用しない」です。
出所を確かめられない数は、どれほどもっともらしくても、根拠には使えません。
この数が正しいかもしれないし、間違っているかもしれません。**分からない**ので、分からないと書きます（規則 4）。

それでも、重複除去の決定（D70 の 6）は揺らぎません。
D70 の 6 の理由は「同じコードを 2 回数えると、木の単位の数字が水増しされる」「v2〜v4 は本記録者が見たデータで、評価から除く約束がある」の 2 つで、「v3 で 8 木あった」には頼っていないからです。
論文で重複除去の理由を書くときも、D70 の 6 の理由を使います。

#### よくある誤解・つまずき

- **誤解: 「手順書に書いてあるのだから、原典だ」**
  手順書は、出所として教科書を挙げています。教科書も、出所を書いていません。文書に書いてあることと、原典で確かめられることは別です。
- **誤解: 「未検証なら、間違っている」**
  間違いとは言っていません。確かめられない、と言っています。確かめるには、v2 と v3 の木を pin から取り直して、ファイルの sha256 を比べる必要があります。最終評価の重複除去で v2・v3 のハッシュを取り直すので（25.6 節）、そのときに確かめることはできます（本書の提案）。
- **つまずき: 未検証の数を「参考」として論文に書く**
  書きません。規則 1 は、参考としての引用も含めて、未検証の統計を引用しないことを求めています。

#### 手作業ではどう使うか

- 論文や事前登録で重複除去の理由を書くときは、「v3 で 8 木」を使わず、D70 の 6 の 2 つの理由を書きます。
- 手順書や教科書の数を使うときは、その文がどの原典を出所にしているかを確かめる習慣をつけます。出所が文書の中で閉じていたら（教科書 → 手順書 → 教科書）、原典に当たっていない可能性があります。
