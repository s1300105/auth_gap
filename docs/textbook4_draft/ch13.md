## 第 13 章 「効果」— 外の世界に触れる操作

> **この章で分かること**:
> - **効果**・**kind**・**sink**・**slot** という 4 つの言葉の意味。解析器が「外の世界に触れる操作」をどう数えるか。
> - 効果の 7 つの種類（kind）と、判定でよく出会う `os.makedirs`（ディレクトリを作る）と `os.replace`（ファイルを置き換える）。
> - manifest の `sub_kind` の欄が、名前から想像する意味と**違う**こと。判定には使わないこと。
> - 解析器が効果を見つけるための一覧（**sink 表**）の 3 つの形（直接・proxy・pipe）と、それぞれが manifest でどう見えるか。proxy の site 名が原ソースのライブラリ名と食い違う理由。
> - sink 表に**載っていない**関数は、どれだけ外の世界に触れていても効果に出ないこと（見落としの原因「語彙」）。
> - ファイルの書き込みが「今あるものを壊す型」か「足すだけの型」かを表す **`destructive`** という印と、それが D2 の判定の根拠になっていること。
> - `open` のモードを解析器がどう読み、D1・D2・D4 でそれぞれどう扱うか（第 9 章のモード表の、解析器版）。
> - `pipe:write`・`pipe:communicate` という site が、**子プロセスの標準入力への書き込み**であって、ファイルの書き込みとは限らないこと（誤の原因 E5）。
> - 「月 3 に凍結」とは何のことか。凍結した語彙を、なぜ判定の途中で直さないのか。

### 13.1 効果 — 外の世界に触れる操作

#### 一言で言うと

**効果**（effect）とは、ツールの中の操作のうち、**ツールの関数の外にある世界に触れるもの**です。
ファイルを書く、通信する、データベースに命令を送る、別のプログラムを起動する、といった操作がこれに当たります。
解析器は、ツールの中から効果を探し出し、それを宣言と比べます。

#### たとえ話 — 部屋に来た作業員

一人暮らしの部屋に、作業員が 1 人来て、1 時間作業して帰ったとします。
作業員が部屋の中でしたことは、いろいろあります。
頭の中で計算した、メモ用紙に下書きした、といったことは、作業員が帰れば何も残りません。
一方で、次のことは、作業員が帰った後にも跡が残るか、部屋の外で何かを起こします。

- 棚の書類を読んだ（書類は変わらないが、中身を見た）
- 棚に新しい書類を置いた、古い書類を捨てた
- 外に電話をかけた
- 台帳に書き込んだ
- 別の業者を呼んだ
- 渡されたメモに書いてある指示を、そのまま実行した

作業員を雇う前に、「この人は棚を見るだけで、何も捨てません」という札を受け取っていたとします。
札が正しいかを確かめるには、作業員の行動のうち**跡が残るもの・外に作用するもの**を書き出して、札と比べればよいはずです。
頭の中の計算は、札と比べる必要がありません。

ツールも同じです。
作業員がツール、札が宣言（第 4 章）、跡が残る行動が効果です。

#### 小さな例

作例です。左の数字は行番号です。

```python
1  def summarize(path: str) -> str:
2      text = open(path).read()                 # ファイルを読む
3      n = len(text.split())                    # 単語を数える（関数の中だけ）
4      requests.get("https://example.com/log", params={"n": n})   # 通信する
5      os.remove(path)                          # ファイルを消す
6      return f"{n} words"                      # 結果を返す
```

#### 一歩ずつ

- 1 行目: `summarize` という関数を定義しています。引数 `path` はファイルの場所です。
- 2 行目: `open(path)` でファイルを開き、`.read()` で中身を読みます。ファイルという**外の世界**に触れるので、効果です。種類は「ファイルを読む」（`FS_READ`）です。
- 3 行目: 読んだ文字列を単語に分けて数えます。関数の中の計算だけで、外の世界には触れません。**効果ではありません。**
- 4 行目: `requests.get(...)` で、`example.com` というサーバに通信します。外の世界に触れるので効果です。種類は「通信する」（`NET`）です。
- 5 行目: `os.remove(path)` でファイルを消します。外の世界（ファイル）を変えるので効果です。種類は「ファイルを書く・消す」（`FS_WRITE`）です。
- 6 行目: 結果の文字列を返します。返した値は呼び出し元（MCP のクライアント）に渡りますが、解析器はこれを効果として数えません。効果を見つけるための一覧（13.4 節の sink 表）に、戻り値の行が無いからです。

この関数には、効果が 3 つ（2・4・5 行目）あります。

#### 効果の 3 つ組

仕様書は、1 つの効果を次の 3 つ組で表すと決めています。

```
e = (kind, site, slots)
     │      │      └─ 値が入る位置ごとの値（13.8 節の slot。中身の読み方は第 14 章）
     │      └─ 効果を起こす関数の名前（例 os.remove）
     └─ 効果の種類（例 FS_WRITE）
```

上の例の 5 行目なら、`kind` は `FS_WRITE`、`site` は `os.remove`、`slots` は「消すファイルの場所 `path` に、引数 `path` の値が入る」です。

manifest（解析器が木ごとに書き出す JSON のファイル。第 11 章で見ました）では、1 つのユニット（ツール 1 つ。第 12 章）の `effects` の欄に、見つけた効果が 1 つずつ並びます。
1 つの効果には、3 つ組のほかに、どの行で見つかったか（`relpath`・`lineno`）、どの形の sink で見つかったか（`form`。13.4 節）などの欄が付きます。
（出典: 3 つ組は `AUTHGAP_BRIEF_v3.md:211`。manifest の効果の欄は `authgap/effects.py:110-145` の `to_json`）

#### なぜ効果という形で調べるのか

第 4 章で見たとおり、宣言は「環境を変えません」（D1）、「前からあるものを壊しません」（D2）、「外の世界とは関わりません」（D3）、「繰り返しても追加の効果がありません」（D4）のように、**外の世界への作用**について約束しています。
だから比べる相手（第 6 章の M、ツールが実際にできること）も、同じ「外の世界への作用」の言葉で表す必要があります。
効果は、その言葉です。

言いかえると、効果は「宣言と比べられる単位」です。
関数の中の計算をいくら細かく調べても、宣言と比べることはできません。
宣言が何も約束していないからです。

#### よくある誤解・つまずき

- **「ツールが値を返すことも効果では」**: 解析器の効果には入りません。効果は sink 表（13.4 節）に載った操作だけで、戻り値の行はありません。判定でも、戻り値を返すこと自体を「環境を変える」とは考えません。
- **「`print` や画面への出力も効果では」**: 標準出力・標準エラーへの出力は、効果に出ません。判定でも「ファイルではないので反しない」とされています（手引きの下書きの D1 の迷いやすい形、`docs/drafts/final_judging_guide_draft.md:323`）。ただしログの出力先がファイルなら話は別です（13.7 節、第 9 章 9.5）。
- **「効果が 1 つでもあれば宣言に反する」**: 反するかは、効果の種類と宣言の組み合わせで決まります。たとえば `FS_READ`（ファイルを読む）は、D1（読み取り専用）の宣言に反しません。判定表は第 17 章で学びます。

#### 手作業ではどう使うか

判定表の 1 行には、`site` と `kind` があります（手順 A）。
`site` は「どの関数の呼び出しが効果を起こしたか」、`kind` は「その効果の種類」です。
手順 C では、`locations` に書かれた位置（ファイルと行）を開き、その行に本当に `site` の関数の呼び出しがあり、本当に `kind` の操作をしているかを確かめます。
つまり判定は、「解析器の言う効果が、本当に外の世界に触れる操作か」を確かめることから始まります。
（出典: `docs/drafts/final_judging_guide_draft.md:92-126`）

#### この節のまとめ

外の世界（ファイル・通信相手・DB・他のプログラム）に触れる操作が効果。関数の中の計算や戻り値は効果ではない。
1 つの効果は (kind, site, slots) の 3 つ組で、manifest の `effects` の欄に並ぶ。
効果は「宣言と比べられる単位」で、判定は効果の行を開いて確かめるところから始まる。

### 13.2 効果の種類（kind）— 7 つの名前

#### 一言で言うと

効果には 7 つの種類があり、種類のことを **kind** と呼びます。
`FS_READ`・`FS_WRITE`・`NET`・`DB`・`SPAWN`・`EXEC`・`DISPATCH` の 7 つです。
この 7 つの名前は解析器の中で決まっていて、これ以外の kind は作れません。

#### たとえ話 — 郵便局の 7 つの仕分け箱

郵便局の窓口に、荷物を入れる仕分け箱が 7 つ並んでいるとします。
「手紙」「小包」「書留」…と箱が決まっていて、窓口の人は荷物を必ずどれか 1 つの箱に入れます。
8 つ目の箱を勝手に作ることはできません。
箱が決まっているから、後で「書留は何通あったか」を誰が数えても同じ答えになります。

kind も同じです。
7 つの箱が決まっているから、どの木を誰が走査しても、効果は同じ 7 つの種類のどれかに分けられます。

#### 小さな例 — 7 つの kind

| kind | 意味 | 例 |
|---|---|---|
| `FS_READ` | ファイルを読む・一覧する | `open(p).read()`、`os.listdir(d)`、`glob.glob(pat)` |
| `FS_WRITE` | ファイルを書く・作る・消す・動かす・置き換える・権限を変える | `open(p, "w")`、`os.makedirs(d)`、`os.remove(p)`、`os.replace(tmp, p)`、`shutil.copy(a, b)`、`os.chmod(p, m)` |
| `NET` | ネットワークに通信する | `requests.get(url)`、`client.post(url)` |
| `DB` | データベースに命令を送る | `cursor.execute("DELETE FROM t")` |
| `SPAWN` | 別のプログラム（子プロセス）を起動する | `subprocess.run(["git", "log"])`、`asyncio.create_subprocess_exec(...)` |
| `EXEC` | 文字列をプログラムとして実行する | `eval(code)`、`exec(code)` |
| `DISPATCH` | 名前（文字列）で関数を呼び分ける | `getattr(obj, name)()` |

表の読み方: 1 行が 1 つの kind です。左から「kind の名前」「意味」「その kind になる呼び出しの例」です。
たとえば 2 行目は「`FS_WRITE` は、ファイルに書くことだけでなく、作る・消す・動かす・置き換える・権限を変えることもすべて含む。`os.makedirs(d)` も `os.replace(tmp, p)` も `FS_WRITE` になる」と読みます。

名前の由来は次のとおりです。
`FS` は File System（ファイルシステム）、`NET` は network（ネットワーク）、`DB` は database（データベース）、`SPAWN` は「産む」（プロセスを起動する）、`EXEC` は execute（実行する）、`DISPATCH` は「振り分ける」の略です。

#### 一歩ずつ — 7 つの名前はどこで決まっているか

7 つの名前は、`authgap/catalog/sinks.py` の `SLOTS` という辞書で決まっています。
辞書のキー（左側の名前）が kind で、値（右側）がその kind の slot（13.8 節）の一覧です。

```python
SLOTS: dict[str, tuple[str, ...]] = {
    "EXEC": ("code_text",),
    "SPAWN": ("argv0", "argv[i]", "argv[*]", "shell_string", "cwd", "env", "stdin"),
    "FS_WRITE": ("path", "content"),
    "FS_READ": ("path",),
    "NET": ("url.scheme", "url.host", "url.path", "url.query", "body", "headers"),
    "DB": ("sql", "params"),
    "DISPATCH": ("callee",),
}
```

- 1 行目: `SLOTS` という名前の辞書を作ります。`dict[str, tuple[str, ...]]` は「文字列から、文字列の並びへの辞書」という型の注記です。
- 2〜8 行目: 1 行に 1 つの kind です。たとえば 4 行目は「`FS_WRITE` という kind には、`path` と `content` という 2 つの slot がある」という意味です。

この辞書に無い kind で効果を作ろうとすると、解析器はその場で例外（エラー）を出して止まります。
`validate_slot` という関数が「未知の効果 kind」として拒むからです。
これは、CLAUDE.md の「語彙外の値は構築時に例外になる」という約束の 1 つです。
（出典: `authgap/catalog/sinks.py:20-28`（`SLOTS`）、`:64-71`（`validate_slot`））

#### sink 表の中の kind の内訳

sink 表（13.4 節）の行を kind ごとに数えると、次のようになります。
本書の執筆時に、凍結版の `authgap/catalog/sinks.py` を読み込んで数えました。

| kind | 直接の sink の行 | proxy の sink の行 | pipe の sink |
|---|---|---|---|
| `FS_WRITE` | 20 | 1 | 子が何者かで `FS_WRITE` か `EXEC` になる（13.11 節） |
| `SPAWN` | 15 | 2 | — |
| `NET` | 12 | 5 | — |
| `FS_READ` | 11 | 0 | — |
| `EXEC` | 9 | 0 | （上の `EXEC` の場合） |
| `DB` | 1 | 9 | — |
| `DISPATCH` | 0 | 0 | — |

表の読み方: 1 行が 1 つの kind で、各列はその kind を生む sink 表の行の数です。
たとえば 1 行目は「`FS_WRITE` を生む行は、直接の sink に 20 行、proxy の sink に 1 行ある」と読みます。
`FS_READ` の 11 行には、`open` の仲間 3 行（`builtins.open`・`io.open`・`pathlib.Path.open`）が入っています。
この 3 行は、モードを読んで `FS_WRITE` に切り替わることがあります（13.10 節）。

**`DISPATCH` は語彙には有りますが、凍結版の sink 表には `DISPATCH` を生む行がありません。**
v4 の 88 木の manifest の `effects` の欄の要素を kind ごとに数えると、`FS_WRITE` 4,293、`DB` 2,304、`FS_READ` 1,875、`NET` 1,778、`SPAWN` 697、`EXEC` 26 で、`DISPATCH` は 0 でした（本書の執筆時に数えた。分母は v4 の 88 木の manifest の `effects` の要素の全体。同じ呼び出しに別の道筋で届くと要素が複数になるので、「呼び出しの数」ではない）。
判定の作業で `DISPATCH` の効果に出会うことは、まず無いと考えてかまいません。
（出典: `evidence/scan_v2_v4_run1/*.json`）

#### 新しく足した例 1 — `os.makedirs`

第 3 版の表には無かった `FS_WRITE` の例を、2 つ足しました。
どちらも判定でよく出会うものです。

1 つ目は **`os.makedirs(d)`** です。
やさしく言うと「ディレクトリ（フォルダ）を作る関数」で、正確には「ディレクトリ `d` を、途中の階層がまだ無ければそれも含めて作る関数」です。
練習用のサーバ（第 53 章で使う、手引きの下書きのために書かれたサーバ）の 11 行目がこれです。

```python
# 練習用のサーバ（docs/drafts/final_judging_guide_draft.md:564-566）
10  def _save_cache(name, text):
11      os.makedirs(CACHE_DIR, exist_ok=True)
12      with open(os.path.join(CACHE_DIR, name), "w") as fh:
13          fh.write(text)
```

- 10 行目: `_save_cache` という関数を定義しています。`name` はファイル名、`text` は書く中身です。
- 11 行目: `CACHE_DIR`（7 行目で `~/.demo_cache` と決めた場所）のディレクトリを作ります。`exist_ok=True` は「もうあっても失敗しない」という指定です。**ディレクトリを作るだけの操作も、解析器は `FS_WRITE` として数えます。**
- 12 行目: そのディレクトリの中のファイル `name` を、`"w"`（中身を消してから書く）で開きます。これも `FS_WRITE` です。
- 13 行目: 開いたファイルに `text` を書きます。書き込み自体は 12 行目の `open` の効果に含まれていて、`fh.write` は別の効果としては出ません。

この練習用のサーバを走査すると、`readOnlyHint=True`（D1）のツール `search_notes` について、11 行目の `os.makedirs` と 12 行目の `builtins.open` が、どちらも矛（理由 `fs_write`）として出ます。
（出典: `docs/drafts/final_judging_guide_draft.md:604-606`）

#### 新しく足した例 2 — `os.replace`

2 つ目は **`os.replace(a, b)`** です。
やさしく言うと「ファイル `a` で、ファイル `b` を置き換える関数」で、正確には「`a` の名前を `b` に変える。`b` が既にあれば、`b` の前の中身は消えて `a` の中身になる」関数です。
**atomic write**（途中で壊れない書き方。第 9 章 9.4 で見ました）の最後の一手として、よく使われます。
第 20 章の通しの例（セッションの保存）でも、最後の行がこの `os.replace` です。

```python
# 作例 — atomic write の典型
1  fd, tmp = tempfile.mkstemp(dir=d)     # 一時ファイルを作る
2  with os.fdopen(fd, "w") as f:
3      f.write(data)                     # 一時ファイルに書く
4  os.replace(tmp, target)               # 一時ファイルで本物を置き換える
```

- 1 行目: `tempfile.mkstemp` は、ディレクトリ `d` の中に、他と重ならない名前の一時ファイルを作ります。戻り値は「開いたファイルの番号 `fd`」と「その名前 `tmp`」の 2 つです。
- 2 行目: `os.fdopen(fd, "w")` は、番号 `fd` のファイルを、書くためのオブジェクト `f` にします。
- 3 行目: 一時ファイルにデータを書きます。
- 4 行目: 一時ファイル `tmp` で、本物のファイル `target` を置き換えます。

**この例で効果として出るのは、4 行目の `os.replace` だけです。**
1 行目の `tempfile.mkstemp` と 2 行目の `os.fdopen` は、sink 表に載っていないからです（13.7 節）。
本書の執筆時に、`destructiveHint=False`（D2）を宣言したツールにこの形を入れた作例を走査すると、効果は `os.replace` の `FS_WRITE` 1 つだけで、D2 の矛（理由 `fs_remove`）になりました。

v3 の確認では、この形の後始末（自分で作った一時ファイルの処理）を、解析器が「壊す」と読んだ誤りが出ました（O41。v3 の抜き取り 60 件のうち誤 3）。
判定で、これをどう扱うか（誤の原因 E2）は、第 50・51 章で学びます。
（出典: `docs/open_questions.md:1061`）

#### なぜ 7 つに分けるのか

宣言ごとに、反するかどうかの決め方が kind で変わるからです。
たとえば D1（読み取り専用）では、`FS_READ` は内、`FS_WRITE` はすべて矛、`NET` はメソッド（GET か POST か）で分かれます。
判定表（第 17 章）は、kind ごとに行を分けて書かれています。
kind が決まらないと、判定表のどの行を見ればよいかが決まりません。

7 つの名前を固定しておくのは、13.12 節で見る「凍結」のためです。
箱の数が走査ごとに変わると、件数を比べられなくなります。
（出典: 判定表は `docs/contradiction_principles.md:160-229`）

#### よくある誤解・つまずき

- **「`FS_WRITE` はファイルに文字を書くことだけ」**: ディレクトリの作成（`makedirs`・`mkdir`）、削除（`remove`・`unlink`・`rmtree`）、名前の変更・置き換え（`rename`・`replace`・`move`）、コピー（`copy`）、権限の変更（`chmod`）も、すべて `FS_WRITE` です。どの操作かは `site` を見て区別します。
- **「`FS_WRITE` なら、どの宣言にも反する」**: D1 では反しますが、D2 では「足すだけ」の書き込み（ディレクトリの作成など）は反しません。D3 ではローカルの操作なので内です。これを区別するのが 13.9 節の `destructive` の印です。
- **「`tempfile.mkstemp` も一時ファイルを作るのだから、出力に出るはず」**: 出ません。sink 表に無いからです。人が判定するときは、出力に無くても書き込みとして気づく必要があります（13.7 節）。

#### 手作業ではどう使うか

判定表の 1 行の `kind` を見たら、まず「判定表（第 17 章）のどの行に当たるか」を思い浮かべます。
`FS_WRITE` は意味の幅が広いので、手順 C で `site` を見て「作るのか、消すのか、置き換えるのか、書くのか」を確かめます。
同じ `FS_WRITE` でも、`os.makedirs` と `os.remove` では、D2 の判定がまったく違うからです（13.9 節）。

#### この節のまとめ

kind は 7 つ（`FS_READ`・`FS_WRITE`・`NET`・`DB`・`SPAWN`・`EXEC`・`DISPATCH`）で、`SLOTS` で決まり、これ以外は作れない。
`FS_WRITE` は作成・削除・置き換え・権限の変更も含む。`os.makedirs` と `os.replace` もその例。`DISPATCH` は凍結版では効果に出ない。
`tempfile.mkstemp` や `os.fdopen` は sink 表に無いので、効果に出ない。

### 13.3 副 kind（`sub_kind`）— 名前に惑わされない

#### 一言で言うと

manifest の効果には、`kind` のほかに `sub_kind`（副 kind）という欄があります。
名前は判定に効きそうに見えますが、**中身は名前から想像する意味と違います。判定には使いません。**

#### たとえ話 — 出席簿の「欠」の印

ある学校の出席簿で、「欠」の印が「欠席した」ではなく「出席カードが読み取り機で読めなかった」という意味で付けられているとします。
出席していても、カードが汚れていれば「欠」が付きます。
この印を見て「この生徒は休んだ」と判断すると、間違えます。

`sub_kind` の `SPAWN_MODEL_ARGV` は、この「欠」の印に似ています。
「モデルがコマンドを決める」ように読めますが、実際の意味は「起動するプログラムの名前が定数として読めなかった」です。

#### 小さな例 — `sub_kind` の値と実際の意味

| `sub_kind` | 実際の意味 | 取り違えやすい読み |
|---|---|---|
| `SPAWN_CONST_ARGV` / `SPAWN_MODEL_ARGV` | 起動するプログラムの名前（`argv0`）が**定数として読めたか / 読めなかったか** | 「モデルが決める」ではない。運用者が決める値でも、定数として読めなければ `SPAWN_MODEL_ARGV` になる |
| `DB_READ` / `DB_WRITE` | SQL の先頭の語が読み取りの語（`SELECT`・`SHOW`・`EXPLAIN`・`DESCRIBE`・`WITH`）で**始まるか / 始まらないか** | 「データを変える」ではない。`PRAGMA`・`BEGIN`・`COMMIT`・`ROLLBACK` も `DB_WRITE` に入る |
| `FS_WRITE`・`FS_READ`・`NET`・`EXEC`・`DISPATCH` | kind と同じ名前が入るだけ | |

表の読み方: 1 行が 1 種類の `sub_kind` です。真ん中の列が、解析器のコードが実際に決めている意味です。
たとえば 2 行目は「`DB_WRITE` は『SQL の最初の語が読み取りの語でない』という意味でしかなく、トランザクションを始める `BEGIN` も `DB_WRITE` になる」と読みます。

#### 一歩ずつ — 解析器のコード

`sub_kind` を決めているのは、`authgap/effects.py` の `_sub_kind` という関数です。
要点だけを抜き出します。

```python
def _sub_kind(kind, slots):
    if kind == "SPAWN":
        argv = slots.get("argv0")
        if argv is not None and argv.is_literal():
            return "SPAWN_CONST_ARGV"
        return "SPAWN_MODEL_ARGV"
    if kind == "DB":
        ...
        return "DB_READ" if head in ("SELECT", "SHOW", "EXPLAIN", "DESCRIBE", "WITH") else "DB_WRITE"
    ...
```

- 2 行目: 効果の kind が `SPAWN`（プロセスの起動）なら、という条件です。
- 3 行目: slot `argv0`（起動するプログラムの名前。13.8 節）の値を取り出します。
- 4〜5 行目: その値が**定数**（`is_literal()`、コードに直接書かれた文字列など）なら `SPAWN_CONST_ARGV` を返します。
- 6 行目: それ以外は**すべて** `SPAWN_MODEL_ARGV` を返します。値の主体（誰が決めた値か。第 14 章）は見ていません。
- 7〜9 行目: kind が `DB` なら、SQL の先頭の語（`head`）を見て、読み取りの語なら `DB_READ`、それ以外は `DB_WRITE` を返します。

同じ関数のコメントには、「`DB_WRITE` は『読み取り語で始まらない』という意味であって『データを変更する』ではない。`PRAGMA` / `BEGIN` / `COMMIT` / `ROLLBACK` もここに入る」「`readOnlyHint` の矛盾判定に**そのまま使ってはならない**」と書かれています。
（出典: `authgap/effects.py:379-409`）

#### 実物 — `SPAWN_MODEL_ARGV` なのに運用者の値

v4 の ru-marketplace の `ozon_reviews` というツールは、内部で子プロセスを次のように起動します。

```python
# corpus/v4-vladimir-human__ru-marketplace-mcp/packages/ozon-connector/src/ozon_connector/server.py:207-208
207      proc = subprocess.Popen(
208          [sys.executable, "-c", _SYNC_WORKER_CODE, out_path],
```

- 207 行目: `subprocess.Popen` で子プロセスを起動します。
- 208 行目: 起動するプログラムは `sys.executable`（今動いている Python 自身の場所）です。引数は `-c`、決まったコード `_SYNC_WORKER_CODE`、一時ファイルの場所 `out_path` です。

`sys.executable` は、モデルが決める値ではありません。
しかし解析器は、その値を定数として読めません（Python の実行時に決まる値だからです）。
そのため、manifest のこの効果は `sub_kind: SPAWN_MODEL_ARGV` になっていて、同時に `argv0` の主体は `OP`（運用者）になっています。
行の注記は `contradiction_unknown:D1:spawn_command`、つまり D1 の**不**（コマンドの意味が名前から分からない）です。
「モデルが決める」なら矛になりうるところですが、そうはなっていません。

もう 1 つ、v4 の gemini の `gemini_prompt` の `asyncio.create_subprocess_exec` も `SPAWN_MODEL_ARGV` です。
こちらは `argv0` の主体が `MODEL` ですが、確度（第 14 章）が `opaque`（追跡が確かでない）なので、行の注記は `contradiction_unknown:D1:spawn_model_opaque`、つまりやはり**不**です。
2 つとも `sub_kind` は同じ `SPAWN_MODEL_ARGV` なのに、解析器の答えの理由は違います。
`sub_kind` が判定の答えを表していないことが、ここから分かります。
（出典: `evidence/scan_v2_v4_run1/v4-vladimir-human__ru-marketplace-mcp.json` と `evidence/scan_v2_v4_run1/v4-ankitdotgg__making-gemini-useful-with-claude.json` の該当ユニットの `effects` と `rows`。本書の執筆時に開いて確かめた）

#### なぜ `sub_kind` があるのか

仕様書は、月 3 の凍結（13.12 節）の対象に「副 kind」を入れています。
`sub_kind` は、付録に降ろした主張（第 8 章。等級づけの比較など）のために作られた欄です。
CLAUDE.md の約束どおり、付録の語彙は消さずに残してありますが、核の主張（宣言と実効の照合）には使いません。
矛・不・内の判定は、`sub_kind` ではなく、効果の別の欄（`sql_head`・`fs_mode`・`http_method`・slot の主体と確度など）から決めています。
（出典: `authgap/catalog/sinks.py:45-55`（`SUB_KINDS`）、`AUTHGAP_BRIEF_v3.md:841`）

#### よくある誤解・つまずき

- **「`SPAWN_MODEL_ARGV` だから、モデルがコマンドを決められる」**: 違います。「起動するプログラムの名前が定数として読めなかった」だけです。上の ru-marketplace の例では、運用者側の `sys.executable` でした。
- **「`DB_WRITE` だから、DB のデータを変えている」**: 違います。`BEGIN` や `PRAGMA foreign_keys=ON` のような、データを変えない命令も `DB_WRITE` になります。データを変えるかは SQL を読んで決めます（第 10 章）。

#### 手作業ではどう使うか

判定で解析器の言い分を確かめるとき（手順 B）は、`sub_kind` ではなく、**行の注記**（`rows[].notes` の `contradiction:D1`・`contradiction_reason:D1:fs_write`・`contradiction_unknown:D1:spawn_command` など）を見ます。
注記の理由のコードの意味は、手引きの下書きの理由コードの表（第 17 章・第 48 章）で引きます。
`sub_kind` は、判定表の記録のどの欄にも書きません。
（出典: 理由コードの表は `docs/drafts/final_judging_guide_draft.md:191-221`）

#### この節のまとめ

`sub_kind` は名前から想像する意味と違う。`SPAWN_MODEL_ARGV` は「argv0 が定数として読めなかった」、`DB_WRITE` は「SQL が読み取りの語で始まらない」というだけ。
付録の主張のための欄で、判定には使わない。判定は行の注記（`rows[].notes`）で見る。

### 13.4 sink と sink 表

#### 一言で言うと

効果を起こす関数の呼び出しを **sink**（シンク）と呼びます。
解析器は、どの呼び出しが sink かを、**sink 表**という一覧で知っています。
sink 表は解析器の中に書かれた一覧で（`authgap/catalog/sinks.py`）、表に載っている呼び出しだけが効果になります。

#### たとえ話 — 台所の流しと、空港の危険物リスト

sink は英語で「台所の流し」のことです。
蛇口から出た水が、いろいろな器を通って、最後に流しに行き着きます。
プログラムの値も、変数から変数へ、関数から関数へと流れて、最後に「ファイルを消す」「通信する」といった操作に行き着きます。
その**行き着く先**が sink です。

sink 表は、空港の保安検査の「持ち込み禁止品リスト」に似ています。
検査員はリストに載っている物を探します。
リストに載っていない物は、どれほど危なそうでも、検査員は止めません。
リストが決まっているから、どの検査員が担当しても同じ判断になります。
その代わり、リストの抜けは、そのまま見逃しになります。

#### 小さな例

```python
def cleanup(name: str) -> str:
    p = "/tmp/work/" + name       # 値 p を作る
    os.remove(p)                  # p が流れ着く先 = sink
    return "ok"
```

- 1 行目: ツールの関数 `cleanup` です。`name` はモデルが決める引数です。
- 2 行目: `name` の前に固定の文字列をつないで、値 `p` を作ります。これは関数の中の計算で、効果ではありません。
- 3 行目: `p` が `os.remove` に渡ります。`os.remove` は sink 表に載っているので、ここが **sink** で、ファイルの削除という効果（`FS_WRITE`）が起きます。
- 4 行目: 結果を返します。

値 `p` は、2 行目で作られ、3 行目の sink に流れ着きます。
「流れ着いた値を、誰が決めたか」（ここでは、モデルが決める `name` を含む）を追うのが第 14 章です。

#### 一歩ずつ — sink 表の中身

sink 表の先頭には、次の説明が書かれています。

> **この表そのものが研究成果である**（§1.5.3）。権威ある「MCP 効果仕様」は存在しないので、表を凍結（月 3 の sink 語彙凍結、月 10 の解析指紋）して再現可能にする。

意味を一文ずつ言いかえます。

- 「この表そのものが研究成果である」: どの関数がどんな効果を持つかを調べて一覧にしたこと自体が、この研究の成果の 1 つだ、という意味です。
- 「権威ある『MCP 効果仕様』は存在しない」: MCP の仕様には、「この関数はファイルを書く」といった公式の一覧がありません。
- 「表を凍結して再現可能にする」: そこで自分で一覧を作り、それを固定して、誰が走査しても同じ結果が出るようにします（凍結は 13.12 節）。

sink 表の各行には、`required_by` という欄があります。
「どの較正対（第 8 章）や仕様の節が、この行に依存しているか」を記録した欄です。
行を消すと何が壊れるかを、表から読めるようにするためです。
たとえば `subprocess.Popen` の行の `required_by` は `("F6",)` で、仕様書の受け入れの例（fixture。期待する出力を先に決めておいた小さな例）の F6 が、この行に依存していることを表します。
manifest の効果にも、同じ `required_by` が写されます。判定では使いません。
（出典: `authgap/catalog/sinks.py:1-8`、`:276-285`（`subprocess.Popen` の行））

#### sink の 3 つの形

sink 表には 3 つの形があります。
manifest の効果の `form` の欄に、どの形で見つかったかが書かれます。

| 形（`form`） | 決め方 | 行の数 | 詳しくは |
|---|---|---|---|
| `direct`（直接の sink） | 呼び出した関数の名前だけで決まる | 67 の名前（68 行） | 13.5 節 |
| `proxy`（proxy の sink） | 呼び出しの**受け手**の型と、メソッドの名前で決まる | 17 行 | 13.6 節 |
| `pipe`（pipe の sink） | 起動した子プロセスへの流し込み | 2 行 | 13.11 節 |

表の読み方: 1 行が 1 つの形です。「行の数」は、その形の sink 表の行の数です。
たとえば 1 行目は「直接の sink は、関数の名前で決まる。名前は 67 個で、`urllib.request.urlretrieve` だけが 2 行（通信と書き込み）を持つので、行は 68 になる」と読みます。

行の数のうち、67・17・2 は、v4 の manifest に解析器自身が書き込んだ値です（manifest の `fingerprint.counts` の `direct_sink_names`・`proxy_rows`・`pipe_rows`）。
68 は、本書の執筆時に凍結版の sink 表を読み込んで数えた値です。
v4 の 88 木の manifest の `effects` の要素を `form` ごとに数えると、`direct` 7,833、`proxy` 3,124、`pipe` 16 でした（本書の執筆時に数えた。分母は 13.2 節と同じ）。
（出典: `evidence/scan_v2_v4_run1/v4-ankitdotgg__making-gemini-useful-with-claude.json` の `fingerprint.counts`、`authgap/catalog/sinks.py:61`（`FORMS`））

#### なぜ表を自分で作り、固定するのか

理由は、上の説明のとおり 2 つです。

1. **公式の一覧が無いから。** 「どの関数が外の世界に触れるか」は、Python やライブラリの文書を 1 つずつ読んで決めるしかありません。その作業の結果を、表として残します。
2. **結果を再現できるようにするため。** 表が走査のたびに変わると、同じ木を走査しても結果が変わります。後から「表を変えたら件数がこう変わった」と比べることもできなくなります。

#### よくある誤解・つまずき

- **「sink 表に載っている関数は、危険な関数だ」**: 載っているのは「外の世界に触れる関数」です。危険かどうか、宣言に反するかどうかは、宣言と値の流れで決まります。`os.listdir` も sink 表に載っていますが、ディレクトリの一覧を読むだけです。
- **「sink 表は、Python で外の世界に触れる関数を全部網羅している」**: 網羅していません。13.7 節で、判定でよく出会う「載っていない関数」を挙げます。

#### 手作業ではどう使うか

manifest の効果の `form` の欄を見れば、その効果が 3 つの形のどれで見つかったかが分かります。
形によって、手順 C で確かめることが違います。

- `direct`: 原ソースの行に、`site` の名前の関数（または、その別名）の呼び出しがあるかを見る（13.5 節）。
- `proxy`: 受け手が本当にその種類のオブジェクトか、動作の種類（kind）が合っているかを見る。site 名のライブラリ名は違っていてよい（13.6 節）。
- `pipe`: 子プロセスが何者で、流し込んだものをどう使うかを見る（13.11 節）。

#### この節のまとめ

効果を起こす呼び出しが sink、その一覧が sink 表（`authgap/catalog/sinks.py`）。公式の一覧が無いので自分で作り、凍結して再現可能にしている。
形は `direct`（67 の名前）・`proxy`（17 行）・`pipe`（2 行）の 3 つで、manifest の `form` の欄に出る。
表に載っている呼び出しだけが効果になる。

### 13.5 直接の sink — 名前で決まる

#### 一言で言うと

**直接の sink** は、呼び出した関数の**正式な名前**だけで決まる sink です。
`os.remove` という名前の関数を呼べば、それだけで「ファイルの削除」の効果になります。

#### たとえ話 — 店の名前で決まる用事

「○○郵便局に行った」と聞けば、郵便の用事だと分かります。
誰が行ったか、何を持っていったかを聞かなくても、行き先の名前だけで用事の種類が決まります。
直接の sink は、この「行き先の名前」で決まる場合です。

#### 小さな例

```python
os.remove(p)              # 名前が os.remove → ファイルの削除（FS_WRITE）
subprocess.run(argv)      # 名前が subprocess.run → プロセスの起動（SPAWN）
open(p, "w")              # 名前が builtins.open → モードで FS_READ / FS_WRITE（13.10 節）
```

#### 一歩ずつ — 「正式な名前」とは

ここで言う名前は、コードに書かれた文字そのままではなく、**`import` をたどって決めた正式な名前**です。
たとえば次の作例を考えます。

```python
1  from os import remove as rm
2
3  def d2_fsops(name: str) -> str:
4      rm("/tmp/e")
```

- 1 行目: `os` モジュールの `remove` という関数を、`rm` という別名で使えるようにしています。
- 4 行目: コードには `rm(...)` と書かれています。

解析器は、1 行目の `import` を見て、`rm` は `os.remove` のことだと決めます。
そのため、manifest の `site` は `os.remove` になります。
本書の執筆時に作例を走査して、4 行目にあたる行の効果が `site: "os.remove"` として出ることを確かめました。

組み込みの `open` は、`import` しなくても使える関数です。
その正式な名前は `builtins.open`（`builtins` は組み込みの関数を集めたモジュールの名前）です。
manifest の `site` にも `builtins.open` と書かれます。

#### 1 つの呼び出しが 2 つの効果を持つことがある

`urllib.request.urlretrieve(url, path)` は、URL の中身を取ってきて、ファイルに保存する関数です。
つまり「通信する（`NET`）」と「ファイルに書く（`FS_WRITE`）」の 2 つを 1 回の呼び出しでします。
sink 表は、この名前に 2 行を持たせていて、解析器は 2 つの効果を出します。

sink 表の作り方のコメントには、「1 つの呼び出しが 2 つの効果を持つことがある。**片方を落とさない**ために値は列にする」と書かれています。
「列にする」とは、1 つの名前に行を 1 つだけでなく、行の並びを対応させる、という意味です。
（出典: `authgap/catalog/sinks.py:170-179`（`_rows`）、`:401-407`（`urlretrieve` の 2 行））

#### 実行の仕方で slot が変わる sink

`subprocess.run` のような子プロセスの起動は、`shell=True` を付けるか付けないかで、値の入り方が変わります（第 9 章 9.6）。

- `shell=True`: 1 本の文字列がシェルに渡る → slot `shell_string` に入る。
- `shell=False`（既定）: リストの最初がプログラム名、残りが引数 → slot `argv0` と `argv[*]` に入る。

sink 表は、この 2 通りを別々に書いています。
`shell=` の値が定数で読めなければ、解析器は**両方の効果を出します**（「確定しないので 2 行出す」）。
片方に決めつけると、もう片方の可能性を消してしまうからです。
（出典: `authgap/catalog/sinks.py:242-252`（`subprocess.run` の行）、`authgap/effects.py:640-651`）

#### なぜ名前で決めるのか

名前だけで意味が決まる関数は、名前で決めるのがいちばん確かだからです。
`os.remove` はどこから呼んでも「ファイルを消す」関数で、受け手や状況によって意味が変わりません。
そのため直接の sink では、受け手の型（13.6 節）を調べる必要がありません。

#### よくある誤解・つまずき

- **「コードに `rm(...)` と書いてあるのに、site が `os.remove` になっているのはおかしい」**: 正式な名前に直して書くからです。原ソースで別名の `import` を探せば、対応が分かります。
- **「`os.remove` という名前のメソッドを、自分のクラスに定義しても当たる」**: 直接の sink は正式な名前で当てるので、木の中の別のクラスの同名のメソッドとは区別されます。ただし、名前の解決そのものを取り違えることはあります（組み込みの `set()` を木の中の `CacheManager.set` と取り違えた v4 の例。誤の原因 E3）。呼び出しのたどり方の話なので、第 15 章で学びます。

#### 手作業ではどう使うか

手順 C で `form` が `direct` の効果を確かめるときは、原ソースの行に、`site` の関数の呼び出しがあるかを見ます。
行に別名しか書かれていなければ、そのファイルの先頭の `import` を見て、別名が `site` の関数を指しているかを確かめます。
`urlretrieve` のように、1 つの行から 2 つの効果（`NET` と `FS_WRITE`）が出ていることもあります。
判定表では、組（木・ユニット・site・kind・宣言）が違えば別の 1 件として出てきます（第 11・18 章）。

#### この節のまとめ

直接の sink は、`import` をたどった正式な名前（`os.remove`・`builtins.open` など）で決まる。別名で呼んでも当たる。
`urlretrieve` は 1 回の呼び出しで `NET` と `FS_WRITE` の 2 つの効果を出す。`shell=` が読めない起動は 2 通りの効果を出す。

### 13.6 proxy の sink — 受け手の型で決まる

#### 一言で言うと

**proxy の sink** は、メソッドを呼ばれた**オブジェクト（受け手）の型**と、メソッドの名前の組み合わせで決まる sink です。
`client.post(url)` は、`client` が HTTP のクライアントなら通信ですが、名前の `post` だけでは決まりません。

#### たとえ話 — 「送って」と頼まれた相手

「これ、送っておいて」と頼まれたとき、頼まれた相手が郵便局員なら郵便を送ります。
同じ言葉でも、相手がパソコンの前の同僚ならメールを送るかもしれません。
相手が誰か（型）が分からないと、「送る」が何を意味するかは決まりません。
proxy の sink は、この「頼まれた相手」で意味が決まる場合です。

#### 言葉の確認 — 受け手と型

**受け手**（receiver）は、やさしく言うと「メソッドを呼ばれる側のオブジェクト」です。
正確には、`X.m(...)` という呼び出しの `X` の部分です。
たとえば `client.post(url)` の受け手は `client`、`conn.execute(sql)` の受け手は `conn` です。

**型**は、やさしく言うと「そのオブジェクトが何者か」です。
正確には、そのオブジェクトを作ったクラスの名前です。
たとえば `s = requests.Session()` の後の `s` の型は `requests.Session` です。

解析器が受け手の型をどうやって知るかは、第 15 章で学びます。

#### 小さな例

作例です。

```python
1  s = requests.Session()
2  r = s.post("https://api.example.com/search", json={"q": q})
```

- 1 行目: `requests.Session()` で、HTTP の通信をまとめて行うためのオブジェクトを作り、`s` に入れます。`s` の型は `requests.Session` です。
- 2 行目: `s` の `post` メソッドを呼んで、`https://api.example.com/search` に、`{"q": q}` を本体として送ります。

`post` という名前だけでは、通信かどうか決まりません。
世の中には `post` という名前のメソッドがいくらでもあるからです（掲示板に投稿する、キューに積む、など）。
解析器は、受け手 `s` の型が `requests.Session` だと分かって、初めて「これは通信（`NET`）だ」と決めます。

#### 一歩ずつ — proxy の sink の 1 行

proxy の sink 表の 1 行は、次のような形をしています。

```python
ProxyRow(
    recv_types=("httpx.Client", "httpx.AsyncClient", "requests.Session"),
    method="post",
    kind="NET",
    slots={"url.host": A(0, kw="url"), "body": HTTP_BODY},
    from_ctor={"url.scheme": "base_url"},
)
```

- 2 行目 `recv_types`: 受け手の型の候補です。この 3 つの型のどれかなら当たります。
- 3 行目 `method`: メソッドの名前です。
- 4 行目 `kind`: 当たったときの効果の種類です。
- 5 行目 `slots`: 呼び出しの引数を、どの slot に入れるかです。`A(0, kw="url")` は「1 番目の引数（なければ `url=` のキーワード）」、`HTTP_BODY` は「`data=` か `json=`」の意味です。
- 6 行目 `from_ctor`: 受け手を**作ったとき**の引数を、slot に入れる規則です。`httpx.Client(base_url=b)` で作ったクライアントなら、`b` を slot `url.scheme` に入れます。

受け手を作ったときの引数を覚えておく仕組みは、仕様書が「proxy カタログの各行は型だけでなく slot 束縛を持つ」と決めたものです。
たとえば GitPython の `repo = git.Repo(repo_path)` → `repo.git.checkout(branch)` では、`git` コマンドを走らせる作業ディレクトリ（slot `cwd`）が、受け手を作ったときの `repo_path` で決まります。
受け手の型だけを知っても、この値は分かりません。
（出典: `authgap/catalog/sinks.py:546-552`、`AUTHGAP_BRIEF_v3.md:226-231`）

#### site の名前の付け方の癖

proxy の sink では、manifest の `site` の名前の付け方に**癖**があります。
解析器は、行の `recv_types`（型の候補）を**アルファベット順に並べ替えた最初の名前**に、メソッドの名前をつないで site にします。

```python
site = f"{sorted(row.recv_types)[0]}.{method}"
```

- `sorted(row.recv_types)`: 型の候補をアルファベット順に並べ替えます。
- `[0]`: その最初の 1 つを取ります。
- `f"{...}.{method}"`: それとメソッドの名前を `.` でつなぎます。

**実際の受け手の型ではなく、行に書かれた候補の先頭**が使われるのが要点です。
そのため、次の食い違いが起きます。

| 原ソースの呼び出し | 実際の受け手の型 | 行の型の候補 | manifest の site |
|---|---|---|---|
| sqlite3 の接続の `conn.execute(...)` | `sqlite3.Connection` | `sqlite3.Cursor`・`sqlite3.Connection`・`psycopg.Cursor`・`psycopg2.cursor` | `psycopg.Cursor.execute` |
| `requests.Session()` の `s.post(...)` | `requests.Session` | `httpx.Client`・`httpx.AsyncClient`・`requests.Session` | `httpx.AsyncClient.post` |

表の読み方: 1 行が 1 つの呼び出しです。右端の site 名は、真ん中の候補をアルファベット順に並べた先頭から作られます。
たとえば 1 行目は「sqlite3 の接続で `execute` を呼んでも、候補を並べ替えると `psycopg.Cursor` が先頭に来るので、site は `psycopg.Cursor.execute` と表示される」と読みます。

1 行目は、練習用のサーバの 18 行目（sqlite3 の `SELECT`）が `psycopg.Cursor.execute` と表示される理由です。
2 行目は、本書の執筆時に作例を走査して確かめました（`site: "httpx.AsyncClient.post"`、`form: "proxy"`）。
同じ作例で、`readOnlyHint=True`（D1）のツールのこの効果には、行の注記 `contradiction_unknown:D1:net_post`（POST は相手を変えるか分からないので不。第 10 章）が付きました。

この癖は、sink 表の中でも意識されています。
psycopg 3 の接続（`psycopg.Connection`）の `execute` を足したとき、上の行に型を足さずに別の行にしました。
上の行に足すと、並べ替えの先頭が変わり、既存の sqlite3 / psycopg のカーソルの効果の site 名が `psycopg.Cursor.execute` から `psycopg.Connection.execute` に付け替わってしまうからです。
実際に、途中の走査（run8）では、site 名が付け替わったことで「42 か所が消えた」ように見え、本当に消えたものは 0 でした。
（出典: `authgap/effects.py:755`、`authgap/catalog/sinks.py:504-510`（sqlite3 と psycopg の行）、`:514-517`（別の行にした理由）、`docs/drafts/final_judging_guide_draft.md:604-605`）

#### なぜ受け手の型で決めるのか

メソッドの名前だけで決めると、2 つの方向の誤りが起きるからです。

- `post`・`get`・`execute`・`run` という名前のメソッドを全部効果にすると、通信でも DB でもない呼び出しまで効果にしてしまう（誤警報）。
- 逆に、名前で決めないと、HTTP のクライアントや DB の接続の呼び出しを見落とす。

受け手の型で絞れば、この両方を減らせます。
その代わり、受け手の型が分からない呼び出しは当たりません。
たとえば型の分からない `.execute()` は DB の効果にせず、`db_unresolved` という別の記録にします（危険な効果には数えない）。
（出典: `authgap/catalog/sinks.py:673-684`（`db_execute_rule`））

#### よくある誤解・つまずき

- **「site が `psycopg.Cursor.execute` なのに、原ソースは sqlite3 だ。解析器の読み違いだから誤（E4）にする」**: しません。手引きは「site 名のライブラリが違っていても、**動作の種類（kind）が合っていれば判定には影響しない**。その場合は `note` に書いておく」と決めています。E4（受け手の型の読み違い）は、「site のライブラリが違い、その結果 **kind も違う**」ときだけです。
- **「`httpx.AsyncClient` と表示されているから、非同期のクライアントだ」**: 表示は候補の並べ替えの先頭にすぎません。原ソースで受け手を作った行を見て、何のクライアントかを確かめます。
- **「proxy の sink 表は、クライアントのメソッドを全部載せている」**: 載せていません。HTTP のクライアントは `get`・`post`・`request` だけです。`put`・`patch`・`delete` などは載っていません（13.7 節、O39）。

#### 手作業ではどう使うか

手順 C で `form` が `proxy` の効果を確かめるときは、次の順で見ます。

1. 原ソースの行で、受け手（`X.m(...)` の `X`）を見つける。
2. その受け手を作った行（`X = sqlite3.connect(...)`・`X = requests.Session()` など）までさかのぼり、何のオブジェクトかを確かめる。
3. その呼び出しの動作の種類が、manifest の `kind` と合っているかを見る（DB に命令を送っているか、通信しているか）。
4. site 名のライブラリが原ソースと違っていたら、`note` に「site は psycopg と表示されるが sqlite3」のように書く。kind が合っていれば、それで判定を変えない。

（出典: `docs/drafts/final_judging_guide_draft.md:120-124`、`:432`（E4））

#### この節のまとめ

proxy の sink は、受け手の型とメソッドの名前で決まる。受け手を作ったときの引数（`base_url` など）も slot に入る。
site 名は「行の型の候補を並べ替えた先頭」＋メソッド名なので、sqlite3 が `psycopg.Cursor.execute`、`requests.Session` が `httpx.AsyncClient.post` と表示される。
kind が合っていれば判定に影響しない（`note` に書く）。kind まで違うときだけ E4。

### 13.7 sink 表に無いものは、効果にならない

#### 一言で言うと

sink 表に載っていない関数は、どれだけ外の世界に触れていても、**効果として出てきません**。
解析器の出力に無いからといって、その操作が無いとは限りません。

#### たとえ話 — リストに無い持ち込み品

13.4 節の空港の検査を思い出してください。
持ち込み禁止品のリストに「スプレー缶」が載っていなければ、検査員はスプレー缶を止めません。
検査を通ったことは「危なくない」の証明ではなく、「リストに無かった」というだけです。

#### 小さな例 — 出ない書き込み

作例です。`destructiveHint=False`（D2）を宣言したツールです。

```python
1  def d2_atomic(data: str) -> str:
2      fd, tmp = tempfile.mkstemp(dir="/tmp")     # 一時ファイルを作る
3      with os.fdopen(fd, "w") as f:              # 開く
4          f.write(data)                          # 書く
5      os.replace(tmp, "/tmp/target.txt")         # 置き換える
6      Path("/tmp/x").touch()                     # 空のファイルを作る
7      return "ok"
```

- 2 行目: 一時ファイルを作ります。ディスクにファイルが 1 つ増えます。
- 3〜4 行目: そのファイルにデータを書きます。
- 5 行目: 一時ファイルで `/tmp/target.txt` を置き換えます。
- 6 行目: `Path.touch` は、ファイルが無ければ空のファイルを作り、あれば更新時刻だけを変えます。

ディスクを変える操作は 2・4・5・6 行目の 4 か所ありますが、本書の執筆時にこの作例を走査すると、**効果は 5 行目の `os.replace` の 1 つだけ**でした。
2 行目の `tempfile.mkstemp`、3 行目の `os.fdopen`、6 行目の `Path.touch` は、sink 表に載っていないからです。

もう 1 つ作例を走査しました。
`readOnlyHint=True`（D1）のツールで、`s = requests.Session()` の後に `s.delete("https://api.example.com/items/" + q)` を呼ぶ形です。
このツールの効果は **0 個**でした。
HTTP の `DELETE` は相手の資源を消す操作ですが、セッションの `.delete` は sink 表に無いので、解析器は何も報告しません。

#### 一歩ずつ — 判定でとくに出会いやすい「載っていないもの」

| sink 表に無いもの | 何が起きるか | 記録 |
|---|---|---|
| `logging` の `FileHandler`、`logging.basicConfig(filename=…)`、loguru の `logger.add(<ファイル>)` によるログの書き込み | ログファイルへの追記が効果に出ない | O43 の mcp-aws（v4 の見落とし 1）。第 9 章 9.5 |
| `httpx.Client`・`AsyncClient`・`requests.Session` の `.put`・`.patch`・`.delete`・`.head`・`.options`、`httpx.put` などのモジュール関数、本体の `content=`・`files=` | その送信、または送る中身が効果に出ない | O39 |
| `tempfile.mkstemp`、`os.fdopen`、`Path.touch`、`Path.rename` | 一時ファイルの作成・ファイルの作成・名前の変更が効果に出ない | 本書の執筆時に sink 表を検索して確かめた（第 9 章 9.4） |
| zvec の `upsert`、arcpy など、表に無いライブラリ | そのライブラリの書き込みが効果に出ない | O41（v3 の見落とし 1） |
| `wave.open(..., "wb")` | 音声ファイルの書き込みが効果に出ない | O43 の audio-transcriber |

表の読み方: 1 行が 1 種類の「載っていないもの」です。右端は、それが記録されている場所です。
たとえば 2 行目は「HTTP のセッションの `.delete` などは表に無く、その送信は効果に出ない。O39 に既知の限界として記録されている」と読みます。

O39 には、影響が次のように書かれています。
「これらを通る送信は効果にならない。**`DELETE` は D2（destructiveHint）の矛盾の典型なので、D2 の矛は下限になる**（誤 clear の向き）。」
「下限」とは、「本当の数は、報告した数より多いかもしれない」という意味です。
（出典: `docs/open_questions.md:1041-1049`（O39）、`:1066`（O41）、`:1193`・`:1197`（O43））

#### なぜ表に足さないのか

「抜けがあるなら足せばよい」と思うかもしれません。
足さない理由は、sink 表が**凍結**されているからです（13.12 節）。
O39 は理由を「sink 語彙は月 3 凍結。足すなら凍結した語彙を結果を見た後に変えることになる」と書いています。
結果を見てから表を変えると、「都合のよい結果が出るように表を選んだ」ことになりかねません。
そこで、抜けは直さずに**限界として記録**し、件数を併記します。

#### よくある誤解・つまずき

- **「解析器の出力に無ければ、そのツールはファイルを書いていない」**: 違います。sink 表に無い関数で書いているかもしれません。
- **「`mkstemp` は一時ファイルだから、書き込みではない」**: 一時ファイルの作成も、ディスクを変える書き込みです。D1 では反します（判定の詳しい規則は第 50 章）。
- **「ログを書くのは、どのツールもしているから問題ない」**: ログの出力先がファイルなら、それは書き込みです。O43 を書いた時点では「ログの枠組みの書き込みを宣言違反に数えるかは原理で明示されていない」とされていましたが、その後の手引きの下書きの D1 の表は、`FS_WRITE` のすべてを反するとし、「ログ・キャッシュ・一時ファイル・ディレクトリの作成も含む」と書いています。軽重は重みではなく、書き込み先の種類「ログ」というラベルで表します（D67 の 1。第 43・51 章）。（出典: `docs/drafts/final_judging_guide_draft.md:309`、`docs/decisions.md` の D67 の 1）

#### 手作業ではどう使うか

この知識は、**見落としの判定**（第 52 章）で使います。
見落としの判定では、解析器が矛を 1 件も出さなかったツールについて、人が原ソースを読み、宣言に反する動作が本当に無いかを確かめます。
手引きは、見落としの原因を 5 つ（深さ / 呼び出しの解決 / 受け手の型 / **語彙** / その他）に分けています。
「語彙」は「sink の語彙に無いライブラリ」の意味で、例として loguru の `logger.add` のファイル出力が挙がっています。
そのため判定では、**解析器の出力に無くても、コードに書いてあれば自分で気づく**必要があります。
上の表は、そのときの点検表として使えます。
ログについては、ツールの関数の中だけでなく、モジュールの一番上の設定（`logging.basicConfig(filename=…)`・`FileHandler`・`logger.add(<パス>)`）も確かめます（v4 の R19 は、モジュールの一番上で設定していました）。
（出典: `docs/drafts/final_judging_guide_draft.md:465-467`、`:478-479`、`:647`（R19））

#### この節のまとめ

sink 表に無い関数（ログの `FileHandler`、HTTP のセッションの `.delete`、`mkstemp`・`fdopen`・`touch`、表に無いライブラリ）は効果に出ない。
凍結した表は結果を見て直さず、限界として記録する（O39・O41・O43）。D2 の矛は下限になる。
見落としの判定では、出力に無い書き込みに自分で気づく（原因「語彙」）。

### 13.8 slot — 効果の中の「位置」

#### 一言で言うと

1 つの効果には、値が入る**位置**がいくつかあります。これを **slot**（スロット、差し込み口）と呼びます。
たとえば通信の効果には「宛先のホスト」「送る中身」などの slot があり、それぞれに別の値が入ります。

#### たとえ話 — 宅配便の伝票

宅配便の伝票には、「お届け先」「ご依頼主」「品名」「お届け日時」などの欄があります。
同じ「荷物を送る」でも、お届け先を決めたのが本人か、見知らぬ人かで、意味がまったく違います。
伝票の欄が slot、欄に書かれた値が slot の値です。
解析器は、欄ごとに「誰がこの値を書いたか」を調べます（第 14 章）。

#### 小さな例 — slot の一覧

kind ごとの slot は、13.2 節で見た `SLOTS` で決まっています。全部を載せます。

| kind | slot | 意味 |
|---|---|---|
| `EXEC` | `code_text` | 実行されるコードの文字列 |
| `SPAWN` | `argv0` | 起動するプログラム（リストの最初の要素） |
| | `argv[*]`（と `argv[i]`） | プログラムに渡す引数の全体（と i 番目） |
| | `shell_string` | `shell=True` などでシェルに渡す 1 本の文字列 |
| | `cwd` | 子プロセスの作業ディレクトリ |
| | `env` | 子プロセスの環境変数 |
| | `stdin` | 子プロセスの標準入力に渡すもの（`input=`） |
| `FS_WRITE` | `path` | どのファイルか |
| | `content` | 何を書くか |
| `FS_READ` | `path` | どのファイルか |
| `NET` | `url.scheme` | `https` などの方式（`httpx.Client(base_url=…)` の `base_url` もここに入る） |
| | `url.host` | 宛先のホスト |
| | `url.path` | 宛先のパス |
| | `url.query` | `?q=…` の部分（`params=`） |
| | `body` | 送る中身（`data=` / `json=`） |
| | `headers` | 送るヘッダ |
| `DB` | `sql` | どんな命令か |
| | `params` | 命令に埋め込む値（バインド変数） |
| `DISPATCH` | `callee` | 呼び分けで選ばれる関数 |

表の読み方: 1 行が 1 つの slot です。左の列が空の行は、上の行と同じ kind です。
たとえば `NET` の 2 行目は「通信の効果の `url.host` の slot には、宛先のホスト（`api.example.com` など）の値が入る」と読みます。
（出典: `authgap/catalog/sinks.py:20-28`）

#### 一歩ずつ — 1 つの呼び出しが slot に分かれる様子

作例 `requests.get("https://example.com/api", params={"q": name})` を走査した結果の slot は、次のとおりでした（本書の執筆時に確かめた）。

| slot | 入った値 | 主体（誰が決めた値か。第 14 章） |
|---|---|---|
| `url.scheme` | `https` | `OP`（運用者） |
| `url.host` | `example.com` | `OP` |
| `url.path` | `/api` | `OP` |
| `url.query` | `{"q": name}` | `MODEL`（モデル） |

表の読み方: 1 行目から 3 行目は、コードに直接書かれた URL を分けたもので、開発者が書いた値なので主体は運用者側（`OP`）です。
4 行目は、モデルが決める引数 `name` を含むので、主体は `MODEL` です。

ここで 2 つのことが分かります。

1. **URL は 4 つの slot に分けて入ります。** sink 表の行には `url.host ← 1 番目の引数` としか書かれていませんが、解析器は URL を分ける規則（仕様書 §2.6 の URL 分割規則）で、方式・ホスト・パスに分けます。
2. **同じ効果の中でも、slot ごとに主体が違います。** 宛先は開発者が決め、問い合わせの中身だけをモデルが決めています。

#### 引数と slot の対応は、関数ごとに違う

slot は「何番目の引数か」ではありません。
関数ごとに、どの引数がどの slot に入るかが sink 表に書かれています。
判定で間違えやすい例を挙げます。

| 呼び出し | slot `path` に入るもの | slot `content` に入るもの |
|---|---|---|
| `os.remove(p)` | `p`（消すファイル） | — |
| `os.rename(a, b)`・`os.replace(a, b)` | **`b`（行き先）** | — |
| `shutil.copy(a, b)`・`shutil.move(a, b)` | **`b`（行き先）** | `a`（元） |
| `os.symlink(a, b)` | **`b`（作るリンク）** | — |
| `Path(p).write_text(s)` | `p`（受け手そのもの） | `s` |

表の読み方: 1 行が 1 つの呼び出しの形です。太字は、2 番目の引数が `path` になるものです。
たとえば 2 行目は「`os.replace(a, b)` の `path` は、1 番目の `a` ではなく、置き換えられる側の `b` である」と読みます。
（出典: `authgap/catalog/sinks.py:336-377`）

これは、13.9 節の D2 の判定で「書き先をモデルが選べるか」を見るときに効きます。
`os.replace(tmp, target)` なら、見るのは `target` の値です。

#### なぜ slot に分けるのか

「**どの位置に、誰の決めた値が入っているか**」を細かく判断するためです。
同じ通信でも、「宛先は開発者が決めた定数で、送る中身だけモデルが決める」のと、「宛先までモデルが決める」のとでは、危険の度合いも、宣言との関係も違います。

判定表は、kind ごとに見る slot を決めています。

- D3（`openWorldHint: false`、外と関わらない）の通信の判定は、宛先の `url.host` の slot だけを見ます。
- D2 の書き出しの判定は、書き先の `path` の slot を見ます（13.9 節）。
- D1・D2・D3 のプロセスの起動の判定は、`argv0` と `shell_string` の slot を見ます。

（出典: `authgap/dparse.py:265-272`（`_by_choice`）、`docs/contradiction_principles.md:160-213`）

#### `open` のモードは slot ではない

`open(path, "w")` の `"w"` は、slot ではありません。
モードは、効果が `FS_READ` か `FS_WRITE` かを決める材料として別に読まれ、manifest では `fs_mode` という欄に書かれます（13.10 節）。
同じように、HTTP のメソッド（GET・POST など）は `http_method`、SQL の先頭の語は `sql_head` という欄に書かれます。

#### よくある誤解・つまずき

- **「slot は、関数の何番目の引数かを表す」**: 違います。slot は「効果の中の役割」です。`os.replace(a, b)` の `path` は 2 番目の引数です。
- **「1 つの効果の値は 1 つ」**: 1 つの効果に slot がいくつもあり、slot ごとに値と主体があります。
- **「`content` がモデルの値なら、D2 の書き出しは矛」**: D2 で見るのは `path` です。中身を誰が決めたかではなく、書き先を誰が選べるかで決まります。

#### 手作業ではどう使うか

解析器の理由コードに `model_path`（例 `fs_writeout_model_path`）や `model_host`（例 `net_model_host`）が付いていたら、それは特定の slot（`path`・`url.host`）の値をモデルが選べると解析器が読んだ、という意味です。
手順 D でツールの入口から効果まで値をたどるとき、**どの引数がその slot に入るか**を上の対応で確かめてから、その値の出どころを追います。
`os.replace(tmp, target)` で、モデルが決めるのが `tmp` だけなら、書き先 `target` をモデルが選べるとは言えません。

#### この節のまとめ

slot は効果の中の値の位置（伝票の欄）。kind ごとに `SLOTS` で決まっている。URL は方式・ホスト・パス・クエリに分かれる。
slot は引数の番号ではない。`os.rename`・`os.replace`・`shutil.copy` の `path` は 2 番目の引数（行き先）。
判定は slot ごとの主体で決まる（D3 は `url.host`、D2 の書き出しは `path`）。`open` のモードは slot ではなく `fs_mode`。

### 13.9 FS_WRITE の性質 — `destructive` という印

#### 一言で言うと

`FS_WRITE` の効果には、kind や slot とは別に、**`destructive`**（破壊的か）という印が付きます。
`true` は「今あるものを消す・上書きする型」、`false` は「足すだけの型」（追記型）、`null` は「行だけでは決まらない」です。
この印が、D2（`destructiveHint: false`、壊さない）の判定の根拠になります。

#### たとえ話 — 本棚

本棚の前で、次の作業をするとします。

- 新しい本を、空いている所に**足す**。前からあった本はそのまま。
- 前からあった本を**捨てる**。
- 前からあった本を、別の本と**差し替える**。
- 本の背に「貸出禁止」のシールを**貼る**（本はあるが、扱いが変わる）。

「本棚を荒らさないでください」と頼まれていたら、1 つ目はかまいませんが、2〜4 つ目は頼みに反します。
`destructive` の印は、この区別を sink 表の行ごとに付けたものです。
`os.makedirs`（ディレクトリを足す）は 1 つ目、`os.remove`（消す）は 2 つ目、`os.replace`（置き換える）は 3 つ目、`os.chmod`（権限を変える）は 4 つ目に当たります。

#### 小さな例 — sink 表の行の定義

sink 表の 1 行の定義（`SinkRow`）に、この欄があります。

```python
#: FS_WRITE の性質（D32 / prereg §5 #7）: True = 削除・上書き型、False = 追記型、
#: None = mode 依存（`open` 系。mode から `effects._mode_destructive` が決める）。
#: **kind / slot の語彙ではなく属性。** `destructiveHint==false` の宣言に対する
#: CONTRADICTION は True（または不明）の行にだけ立てる。
destructive: Optional[bool] = None
```

- 1 行目: この欄は `FS_WRITE` の性質で、決めたのは D32（と事前登録 §5 の #7）だ、と書いています。`True` は削除・上書き型、`False` は追記型です。
- 2 行目: `None` は「モードで決まる」の意味で、`open` の仲間に使います。モードから決めるのは `_mode_destructive` という関数です（13.10 節）。
- 3 行目: **この欄は kind や slot の語彙ではなく、属性（行に付けた追加の情報）だ**、と念を押しています。語彙（13.12 節の凍結の対象）を変えずに足した、という意味です。
- 4 行目: `destructiveHint==false` の宣言に対する矛盾は、`True`（または不明）の行にだけ立てる、という使い道です。
- 5 行目: 欄の定義です。`Optional[bool]` は「`True`・`False`・`None` のどれか」、`= None` は「書かなければ `None`」の意味です。

（出典: `authgap/catalog/sinks.py:156-160`）

#### 一歩ずつ — 実際の行

sink 表の `FS_WRITE` の行を、印ごとに並べます。

| 印 | sink（行） |
|---|---|
| `destructive=True`（削除・上書き型） | `pathlib.Path.write_text`・`write_bytes`、`pathlib.Path.unlink`、`os.remove`・`os.unlink`・`os.rmdir`、`os.rename`・`os.replace`、`os.chmod`、`shutil.rmtree`、`shutil.copy`・`copy2`・`copyfile`・`move`・`unpack_archive` |
| `destructive=False`（追記型） | `pathlib.Path.mkdir`、`os.makedirs`・`os.mkdir`、`os.symlink` |
| モードで決める | `builtins.open`・`io.open`・`pathlib.Path.open`（13.10 節） |
| 印なし（`None`） | `urllib.request.urlretrieve` の `FS_WRITE` の行、proxy の `git.Repo().index.add` の行、pipe の sink（13.11 節） |

表の読み方: 1 行が 1 つの印です。右の列に、その印を持つ sink を並べました。
たとえば 2 行目は「`os.makedirs` や `Path.mkdir` は、新しいディレクトリを足すだけなので、追記型（`False`）の印を持つ」と読みます。
（出典: `authgap/catalog/sinks.py:313-345`、`:363-377`、`:402-407`、`:464-472`（`git.Repo().index.add` の行）、`authgap/effects.py:803-864`）

#### なぜこの印が要るのか — D2 の問い

D2（`destructiveHint: false`）の宣言は、「変えるとしても、追加するだけで、今あるものは壊さない」という約束です（第 4 章）。
手引きの下書きは、D2 の問いを「その動作は、**呼び出しの前からあったもの**を消す・上書きする・変えるか。新しく足すだけなら反しない」と書いています。

この問いに答えるには、`FS_WRITE` を「足すだけ」と「壊す」に分ける必要があります。
kind の `FS_WRITE` だけでは、`mkdir` も `unlink` も同じ箱に入ってしまうからです。
`destructive` の印が、その分け方です。

- `mkdir`・`makedirs`（ディレクトリを足す）や `open(p, "a")`（末尾に足す）は、今あるものを壊さない → D2 の**内**。
- `unlink`・`remove`（消す）、`rename`・`replace`・`move`（動かす・置き換える）、`chmod`（権限を変える）は、今あるものを変える → D2 の**矛**（理由 `fs_remove`）。

この 2 つは、どちらも原理を選ぶより前に決まっていました。
2026-09-20 に学生が「sink カタログで削除・上書き型と追記型の FS_WRITE を分け、`destructiveHint==false` の宣言に対しては削除・上書き型だけを CONTRADICTION に数える」と決めたのが D32 です。
その後の表 D41 も「`mkdir` / `open('a')` は destructive=false に対して宣言内」とし、原理を選んだ文書（`docs/contradiction_principles.md`）でも、これらは「すでに決まっていて動かないもの」に入っています。
（出典: `docs/drafts/final_judging_guide_draft.md:327-329`（D2 の問い）、`docs/decisions.md:449-475`（D32）、`docs/contradiction_principles.md:34-36`、`:121-123`、`:185-186`）

#### `destructive=True` でも、すぐに D2 の矛とは限らない — 4 つの類

ここで 1 つ注意があります。
`write_text`・`copy`・`open("w")` などの「**書き出し**」は、`destructive=True` の印を持ちますが、D2 ですぐに矛にはなりません。

**書き出し**（writeout）は、やさしく言うと「ファイルを丸ごと書く操作」です。
正確には、「書き先に前からファイルがあれば上書き（壊す）、無ければ新しく作るだけ（足す）になる操作」です。
例は `Path(p).write_text(s)`、`open(p, "w")`、`shutil.copy(a, b)` です。
どちらになるかは、走らせてみるまで（書き先にファイルがあるかを見るまで）分かりません。
つまり、静的には決まりません。

そこで解析器は、D2 から見た `FS_WRITE` を 4 つの**類**に分けます。
分けているのは `authgap/dparse.py` の `_fs_class` という関数です。

```python
def _fs_class(e) -> str:
    site = e.site
    destructive = getattr(e, "destructive", None)
    if site in FS_WRITEOUT_SITES:
        if site in FS_OPEN_SITES and destructive is False:
            return "append"
        if site in FS_OPEN_SITES and destructive is None:
            return "unknown"
        return "writeout"
    if destructive is False:
        return "append"
    if destructive is True:
        return "remove"
    return "unknown"
```

- 2〜3 行目: 効果の site と `destructive` の印を取り出します。
- 4 行目: site が「書き出しの一覧」（`FS_WRITEOUT_SITES`。`write_text`・`write_bytes`・`open` の仲間 3 つ・`copy`・`copy2`・`copyfile`・`unpack_archive`・`urlretrieve`）に入っていれば、5〜9 行目へ進みます。
- 5〜6 行目: `open` の仲間で、印が `False`（モードが `'a'`・`'x'`）なら「追記」（`append`）。
- 7〜8 行目: `open` の仲間で、印が `None`（モードが読めない）なら「決まらない」（`unknown`）。
- 9 行目: それ以外の書き出しの一覧のものは「書き出し」（`writeout`）。
- 10〜11 行目: 一覧に無いもので印が `False` なら「追記」。
- 12〜13 行目: 一覧に無いもので印が `True` なら「消す・動かす・変える」（`remove`）。
- 14 行目: それ以外（印が `None`）は「決まらない」。

（出典: `authgap/dparse.py:355-369`、`authgap/catalog/statements.py:241-248`）

4 つの類と、D2 での結果をまとめます。

| D2 から見た類 | 当てはまるもの | D2 の解析器の結果 |
|---|---|---|
| 追記（`append`） | `destructive=False` の行（`mkdir`・`makedirs`・`symlink`）、`open` の `'a'`・`'x'` | 内 |
| 消す・動かす・変える（`remove`） | 書き出しの一覧に無い `destructive=True` の行（`remove`・`unlink`・`rmdir`・`rmtree`・`rename`・`replace`・`move`・`chmod`） | 矛（`fs_remove`） |
| 書き出し（`writeout`） | `write_text`・`write_bytes`・`open('w')` などモードに `w` か `+` を含む `open`・`copy`・`copy2`・`copyfile`・`unpack_archive`・`urlretrieve` | 書き先 `path` をモデルが選べれば矛（`fs_writeout_model_path`）、それ以外は不（`fs_writeout`） |
| 決まらない（`unknown`） | `destructive` が `None` のもの（モードの読めない `open`、pipe など） | 書き先 `path` をモデルが選べれば矛（`fs_unknown_model_path`）、それ以外は不（`fs_unknown`） |

表の読み方: 1 行が 1 つの類です。真ん中が当てはまる sink、右が D2 の解析器の結果です。
たとえば 3 行目は「`shutil.copy(a, b)` は書き出しの類で、行き先 `b` をモデルが選べるなら矛、そうでなければ不になる」と読みます。

「モデルが選べる」の正確な意味は、「その slot の値の主体が `MODEL` で、確度が `resolved`」です（第 14・17 章）。
主体は `MODEL` でも確度が `opaque`（追跡が確かでない）なら、「流れ込むかもしれないが、選べるとまでは言えない」として、理由の末尾に `_opaque` が付いた**不**になります（例 `fs_writeout_model_path_opaque`）。
ここでは「書き先がツールの引数そのまま、なら選べる」くらいに思っておいてください。
（出典: `authgap/dparse.py:245-272`（`_choice`・`_by_choice`）、`:397-410`（`_d2`）、`docs/contradiction_principles.md:185-188`）

本書の執筆時に、`destructiveHint=False`（D2）を宣言したツールに、次の 8 つの呼び出しを並べた作例を走査しました（書き先はどれも定数）。

今の凍結版は、この後の規則に従っています。

#### よくある誤解・つまずき

- **「`destructive: true` だから D2 の矛だ」**: 書き出し（`write_text`・`open('w')`・`copy`）は、書き先によって不にも矛にもなります。
- **「`destructive: false` だから、どの宣言にも反しない」**: D1 では矛です。D4 でも `open('a')` は矛です。印は D2 のためのものです。
- **「`destructive: null` だから安全」**: `null` は「決まらない」です。D2 では不か矛になります（内にはならない）。
- **「`os.replace` は名前を変えるだけで、何も壊さない」**: 置き換えられる側の前の中身が消えます。だから `destructive=True` で、D2 の `fs_remove` の矛です。

#### 手作業ではどう使うか

D2 の判定（第 50 章）では、手引きの下書きの問い「呼び出しの前からあったものを消す・上書きする・変えるか」に、コードを読んで答えます。
`destructive` の印は、解析器がその答えをどう見積もったかの手がかりです。

- 印が `true` で理由が `fs_remove` なら、本当に「呼び出しの前からあったもの」を消しているかを確かめます。**同じ呼び出しで自分が作った一時ファイル・ロックファイルを消すだけ**なら、呼び出しの前からあったものではないので反しません（誤の原因 E2）。前の呼び出しが残したファイルを消すなら反します。
- 理由が `fs_writeout` / `fs_writeout_model_path` なら、書き先に前からファイルがありうるかを確かめます。書き先をモデルが決められるなら、既存のファイルを指せば上書きできるので反します（第 17 章で学ぶ原理 3-a。「モデルが決める値は、取りうる値の全体で考える」という原理）。毎回同じファイルを上書きするなら反し、呼び出しごとに新しい名前なら反しません。
- 印が `false` の操作（`mkdir` など）は、D2 では反しません。

（出典: `docs/drafts/final_judging_guide_draft.md:327-347`、`:430`（E2））

#### この節のまとめ

`FS_WRITE` には `destructive`（`true` = 消す・上書き型、`false` = 追記型、`null` = 決まらない）の印が付く。kind・slot の語彙ではなく属性（D32）。
D2 では `append` は内、`remove` は矛（`fs_remove`）、`writeout` と `unknown` は書き先をモデルが選べれば矛、それ以外は不。D1 は印を見ず `FS_WRITE` はすべて矛。
manifest では効果・`contradictions.json` の行・`locations` に出る。v4 の D2 の `FS_WRITE` の矛はすべて `true` だった。

### 13.10 `builtins.open` のモード — 解析器版のモード表

#### 一言で言うと

解析器は、`open` のモード（2 番目の引数か `mode=`）を読んで、効果を `FS_READ` にするか `FS_WRITE` にするかを決めます。
`FS_WRITE` なら、さらに `destructive` の印と、モードの文字列（`fs_mode`）を付けます。
モードが読めなければ、**`FS_READ` と `FS_WRITE` の 2 つの効果を両方出します**。

#### たとえ話 — ノートの使い方の記録係

第 9 章 9.3 では、`open` のモードを 1 冊のノートの使い方にたとえました。
`'r'` は読むだけ、`'w'` は全ページを破ってから書く、`'a'` は続きに書き足す、`'x'` は新しいノートを買って書く、`'r+'` は上から重ね書きする、でした。

解析器は、そのノートの使い方を、外から見て記録する**記録係**です。
記録係は、ノートを開く人が口にした使い方（モード）を聞いて記録します。
使い方を聞き取れなかったら、「読んだかもしれないし、書いたかもしれない」と、両方を記録します。
片方に決めつけて記録すると、もう片方の可能性が記録から消えてしまうからです。

#### 小さな例 — モードの読み方の 3 つの場合

```python
open(path)                 # (1) モードを書いていない → 既定の 'r' → FS_READ
open(path, "a")            # (2) モードが定数 → 'a' を含むので FS_WRITE
open(path, mode)           # (3) モードが変数で読めない → FS_READ と FS_WRITE の両方
```

#### 一歩ずつ — 解析器のコード

モードから「書くか」を決めるのは、`authgap/effects.py` の `_mode_is_write` です。要点を抜き出します。

```python
def _mode_is_write(ev, row):
    node = None
    if row.mode_kw and row.mode_kw in ev.kwargs:
        node = ev.kwargs[row.mode_kw]
    elif row.mode_pos is not None and row.mode_pos < len(ev.args):
        node = ev.args[row.mode_pos]
    if node is None:
        return False  # 既定は "r"
    const = node.const
    if isinstance(const, str):
        return any(c in const for c in "wax+")
    return None
```

- 3〜4 行目: 呼び出しに `mode=` のキーワードがあれば、その値を取ります。
- 5〜6 行目: なければ、決まった位置（`builtins.open` なら 2 番目、`pathlib.Path.open` なら 1 番目）の引数を取ります。
- 7〜8 行目: どちらも無ければ、モードを書いていないので既定の `'r'`、つまり「書かない」（`False`）です。
- 9 行目: モードの値が定数なら、その文字列を取り出します。
- 10〜11 行目: 定数の文字列なら、`w`・`a`・`x`・`+` のどれかを含めば「書く」（`True`）、含まなければ「書かない」（`False`）。
- 12 行目: 定数として読めなければ「分からない」（`None`）。**推定で片側に倒しません。**

呼び出し側では、`None`（分からない）のとき、`FS_READ` と `FS_WRITE` の 2 つの効果を両方作ります。
コードのコメントは「どちらか分からない。**両方出す**（clean に潰さない）」です。
「clean に潰さない」とは、「分からないものを『問題なし』に数えない」という意味です。
（出典: `authgap/effects.py:246-261`、`:656-663`、`authgap/catalog/sinks.py:313-335`（`open` の仲間 3 行。`builtins.open` と `io.open` は `mode_pos=1`、`pathlib.Path.open` は `mode_pos=0`））

#### `FS_WRITE` に付く 2 つの欄

`FS_WRITE` になった `open` の効果には、さらに 2 つの欄が付きます。

- `destructive`: モードに `w` か `+` を含めば `true`、`a` か `x` だけなら `false`、読めなければ `null`。決めるのは `_mode_destructive` です。
- `fs_mode`: モードの文字列そのもの（`"w"`・`"a"`・`"r+"` など）。読めなければ、**欄そのものが無い**。

（出典: `authgap/effects.py:298-319`（`_mode_destructive`）、`:264-273`（`_mode_const`）、`:139-140`、`:700-702`）

#### 宣言ごとの扱い

判定の手引きの下書きの理由コードの表と、判定表（`docs/contradiction_principles.md` §7）から、`open` の書き込みが宣言ごとにどう扱われるかをまとめます。

- **D1（`readOnlyHint: true`）**: 書き込みは、モードによらず**すべて**矛です。理由は `fs_write`（判定表の「FS_WRITE（すべて。新規作成を含む）」）。**モードが読めないときも矛**です。モードが読めないと `FS_WRITE` の効果も出るので、それが D1 に当たるからです。
- **D2（`destructiveHint: false`）**:
  - `'w'`・`'+'` を含むもの（書き出し）は、書き先 `path` をモデルが選べれば矛（`fs_writeout_model_path`）、そうでなければ不（`fs_writeout`）。
  - `'a'`・`'x'`（追記・新規作成）は内。
  - モードが読めなければ不（`fs_unknown`）。ただし書き先 `path` をモデルが選べれば矛（`fs_unknown_model_path`）。
- **D4（`idempotentHint: true`）**: モードが**定数で `'a'` を含む**なら矛（`fs_append`。2 回呼べば 2 回追記される）。モードが読めなければ不（`fs_mode_unknown`）。それ以外（`'w'`・`'x'` など）は内。

（出典: `docs/drafts/final_judging_guide_draft.md:201-206`、`docs/contradiction_principles.md:166`、`:185-188`、`:220-221`、`authgap/dparse.py:523-533`）

#### 解析器版のモード表

これを 1 つの表にすると、次のようになります。
**本書の執筆時に、凍結版の解析器で、各行の作例を実際に走査して確かめた結果です。**

| モード | kind | `destructive` | `fs_mode` | D1 | D2 | D4 |
|---|---|---|---|---|---|---|
| 書いていない / `'r'` / `'rb'` | `FS_READ` | — | — | 内 | 内 | 内 |
| `'w'` / `'wb'` | `FS_WRITE` | `true` | `"w"` など | 矛 `fs_write` | 書き先をモデルが選べれば矛 `fs_writeout_model_path`、それ以外は不 `fs_writeout` | 内 |
| `'w+'` / `'r+'` | `FS_WRITE` | `true` | `"r+"` など | 矛 `fs_write` | 同上（書き出し） | 内 |
| `'a'` / `'ab'` | `FS_WRITE` | `false` | `"a"`・`"ab"` | 矛 `fs_write` | 内 | 矛 `fs_append` |
| `'a+'` | `FS_WRITE` | **`true`**（`+` を含むので） | `"a+"` | 矛 `fs_write` | **書き出しの扱い**（不 `fs_writeout` など） | 矛 `fs_append` |
| `'x'` / `'xb'` | `FS_WRITE` | `false` | `"x"` など | 矛 `fs_write` | 内 | 内 |
| 読めない（`open(p, mode)`） | `FS_READ` と `FS_WRITE` の 2 つ | `null` | （欄が無い） | 矛 `fs_write` | 不 `fs_unknown`（書き先をモデルが選べれば矛 `fs_unknown_model_path`） | 不 `fs_mode_unknown` |

表の読み方: 1 行が 1 つのモードです。左から、解析器が出す kind、`destructive` と `fs_mode` の欄の値、D1・D2・D4 の解析器の結果です。
たとえば 4 行目は「`'a'` で開くと、`FS_WRITE` で `destructive` は `false`。D1 では矛、D2 では内、D4 では矛（`fs_append`）」と読みます。
「—」は、その欄が無いことを表します。

#### 表の注意 — 迷いやすい 4 つの行

- **`'a+'` は D2 では「書き出し」扱いです。** `_mode_destructive` は `+` があれば `true` にするので、追記なのに「上書きしうる」と読まれます。本書の執筆時の作例でも、`'a+'` の D2 は不（`fs_writeout`）でした。不か矛の側に倒れる（内にはならない）ので、違反を見逃す向きの誤りにはなりません。人が判定するときは、実際の動作（末尾に足すだけか）で決めます。
- **`'x'` は D2 でも D4 でも内です。** 既にファイルがあれば失敗するので、前からあるものを壊しません。2 回目は失敗するので、状態も増えません。
- **`'w'` は D4 では内です。** 同じ引数で 2 回書いても、同じ内容に上書きされるだけだからです。ただし人の判定では、書く内容に時刻・連番・乱数が入れば、2 回目でさらに変わるので反します（第 50 章）。
- **`'r+'` は「読む」の `r` で始まりますが、書き込みです。** `+` を含むので `FS_WRITE`・`destructive: true` になります（第 9 章 9.3 の「消さずに上書き」）。

（出典: `authgap/effects.py:313-314`、`docs/contradiction_principles.md:221`、`docs/final_evaluation_procedure.md:1044`、`:1048`）

#### なぜ、読めないときに両方出すのか

規則 4「解決できなかったものは『不明』として記録する。黙って安全側に倒さない」に従うためです（CLAUDE.md の約束 4、`docs/contradiction_principles.md:33`）。
モードが読めないときに `FS_READ` だけを出すと、本当は書いていても「読むだけ」と報告することになります（誤 clear、見落としの向き）。
逆に `FS_WRITE` だけを出すと、読むだけの呼び出しが D1 の矛として残ります。
両方を出せば、`FS_READ` は D1 で内、`FS_WRITE` は D1 で矛・D2 で不・D4 で不になり、「書くかもしれない」という情報が消えずに残ります。

#### よくある誤解・つまずき

- **「`'r+'` は読むだけ」**: 読み書きです。書いた所は上書きされます。
- **「`'a+'` は追記だから、D2 の解析器の結果は内」**: 解析器は `+` を見て書き出しと読み、不（または矛）にします。人は実際の動作で決めます。
- **「モードが変数なら、解析器は何も出さない」**: `FS_READ` と `FS_WRITE` を両方出します。D1 では矛になります。
- **「`fs_mode` の欄が無いのは、読み取りだから」**: `FS_WRITE` で `fs_mode` が無ければ、モードが読めなかったという意味です。

#### 手作業ではどう使うか

手順 C の例に、「`builtins.open` なら開くモード（`'w'`・`'a'`・`'x'`・`'r+'` など）。読み取り（`'r'`）なら書き込みではない」とあります。
`open` の効果を確かめるときは、次の順で見ます。

1. 原ソースの行で、モードの引数（2 番目か `mode=`）を見る。`Path(p).open(...)` なら 1 番目。
2. モードが定数なら、上の表の行を引く。manifest の `fs_mode` と一致しているかも見る。
3. モードが変数なら、その変数の値を呼び出し元までさかのぼる。取りうる値に `'w'`・`'a'` などがあれば書き込みです。
4. 宣言の問い（D1 は「残る何かを変えるか」、D2 は「前からあったものを壊すか」、D4 は「繰り返すと増えるか」）に、実際のモードと書く内容で答える。

（出典: `docs/drafts/final_judging_guide_draft.md:116-119`）

#### この節のまとめ

解析器はモードを読んで `FS_READ` / `FS_WRITE` を決め、`FS_WRITE` には `destructive` と `fs_mode` を付ける。読めなければ 2 つの効果を両方出す（clean に潰さない）。
D1 は書き込みならすべて矛（`fs_write`）。D2 は `'w'`・`'+'` が書き出し、`'a'`・`'x'` が内、読めなければ `fs_unknown`。D4 は定数の `'a'` が矛（`fs_append`）、読めなければ `fs_mode_unknown`。
`'a+'` は D2 で書き出し扱い、`'r+'` は書き込み、`'x'` は D2・D4 で内。

### 13.11 pipe の sink — `pipe:write`・`pipe:communicate` は manifest でどう見えるか

#### 一言で言うと

起動した子プロセスの**標準入力**にデータを流し込む呼び出しが、pipe の sink です。
manifest では `site` が `pipe:write` か `pipe:communicate`、`form` が `pipe` になります。
子プロセスがシェルやインタプリタなら `EXEC`、それ以外は `FS_WRITE`（`sub_kind: FS_WRITE`、`destructive: null`）として出ます。
**`FS_WRITE` と書かれていても、ファイルの書き込みとは限りません**（誤の原因 E5）。

#### 言葉の確認 — 子プロセス・標準入力・ハンドル

第 9 章 9.6 で見た言葉を、短く言い直します。

- **子プロセス**: やさしく言うと「プログラムの中から起動した、別のプログラム」です。正確には、`subprocess.Popen` などで OS に起動させたプロセスで、起動した側（親）とは別に動きます。例: ツールの中で `subprocess.Popen(["git", "log"])` と書けば、`git` が子プロセスとして動きます。
- **標準入力**（stdin）: やさしく言うと「プログラムが受け取る入力の通り道」です。正確には、プロセスが起動時から持っている入力用の通り道で、キーボードやパイプ（親とつながった管）につながります。例: `sort` は標準入力から受け取った行を並べ替えます。
- **ハンドル**: やさしく言うと「起動した子プロセスを操作するための取っ手」です。正確には、`subprocess.Popen(...)` や `asyncio.create_subprocess_exec(...)` の戻り値のオブジェクトで、`.stdin.write(...)`・`.communicate(...)`・`.wait()` などで子を操作します。例: `proc = subprocess.Popen(...)` の `proc`。

#### たとえ話 — 窓口への伝言

役所の窓口（子プロセス）に、紙に書いた伝言（データ）を渡すことを考えます。
伝言を渡すこと自体は、役所の書類を書き換えることではありません。
しかし、窓口の人が伝言を読んで、書類を書き換えるかもしれません。
受け取った伝言を読み上げるだけかもしれません。
伝言の中身が「この手続きを実行してください」という指示書なら、窓口はそのとおりに実行します。

pipe の sink は、この「伝言を渡す」操作です。
解析器は、窓口の人が誰か（シェルやインタプリタか）だけを見て、「指示書を実行する窓口なら `EXEC`、それ以外なら『書き換えるかもしれない』として `FS_WRITE`」と記録します。
窓口が実際に何をするかは、人が調べます。

#### 小さな例

作例です。`readOnlyHint=True`（D1）のツール 2 つです。

```python
1  def d1_pipe_cat(text: str) -> str:
2      p = subprocess.Popen(["cat"], stdin=subprocess.PIPE, stdout=subprocess.PIPE)
3      out, _ = p.communicate(input=text.encode())
4      return out.decode()
5
6  def d1_pipe_py(code: str) -> str:
7      p = subprocess.Popen(["python3"], stdin=subprocess.PIPE)
8      p.stdin.write(code.encode())
9      return "ok"
```

- 2 行目: `cat` というプログラムを子プロセスとして起動します。`stdin=subprocess.PIPE` は「子の標準入力を、親とつながった管にする」、`stdout=subprocess.PIPE` は「子の出力を親が受け取る」という指定です。`p` がハンドルです。
- 3 行目: `p.communicate(input=...)` で、`text` をバイト列にして子の標準入力に流し込み、子が終わるのを待って、出力を受け取ります。`cat` は受け取ったものをそのまま出力するだけです。
- 7 行目: `python3`（Python のインタプリタ）を子プロセスとして起動します。
- 8 行目: `p.stdin.write(...)` で、`code` を子の標準入力に書き込みます。`python3` は、標準入力から受け取った文字列を**プログラムとして実行**します。

本書の執筆時に、この作例を凍結版の解析器で走査した結果は、次のとおりでした。

| 行 | 効果の `site` | `form` | `kind` | slot | D1 の結果 |
|---|---|---|---|---|---|
| 2 | `subprocess.Popen` | `direct` | `SPAWN` | `argv0` など | 不（`spawn_command`） |
| 3 | `pipe:communicate` | `pipe` | `FS_WRITE` | `content` | 矛（`fs_write`） |
| 7 | `subprocess.Popen` | `direct` | `SPAWN` | `argv0` など | 不（`spawn_command`） |
| 8 | `pipe:write` | `pipe` | `EXEC` | `code_text` | 矛（`exec`） |

表の読み方: 1 行が 1 つの効果です。起動（2・7 行）は直接の sink の `SPAWN`、流し込み（3・8 行）は pipe の sink です。
たとえば 2 行目は「`cat` に流し込む `communicate` は、`pipe:communicate` の `FS_WRITE` になり、D1 では矛（理由 `fs_write`）になる」と読みます。
4 行目は「`python3` に流し込む `stdin.write` は、`pipe:write` の `EXEC` になり、D1 では矛（理由 `exec`）になる」と読みます。

#### 一歩ずつ — 何を pipe の sink と呼ぶか

pipe の sink は、仕様書の Def 3 の (c) で新しく設けられた形です。
`subprocess.Popen(...)`・`asyncio.create_subprocess_shell(...)`・`asyncio.create_subprocess_exec(...)` で起動した子プロセスのハンドル `X` に対して、

- `X.stdin.write(v)`（標準入力に書く）
- `X.communicate(input=v)`（標準入力に流し込んで、終わるのを待つ）

を呼ぶと、pipe の sink に当たります。
sink 表の pipe の行は、この 2 つだけです（13.4 節の「2 行」）。

sink 表の説明には「**導入根拠は構造的理由のみで、CVE の裏付けは無い**」とあります。
CVE（公開された脆弱性の番号）の実例があって足したのではなく、「この形が無いと見えない経路がある」という構造の理由で足した、という意味です。
仕様書が名指しした例は、OpenManus の `Bash` というツールです。
このツールは、起動するプログラムが定数の `/bin/bash` で、モデルの値は起動した**後**の `stdin.write` に入ります。
直接の sink と proxy の sink だけで見ると、起動の効果の slot はすべて運用者の値（`OP`）になり、モデルのコマンドがシェルに届くことが見えなくなります。
（出典: `AUTHGAP_BRIEF_v3.md:232`、`authgap/catalog/sinks.py:610-660`）

#### 2 つの出方 — `EXEC` か `FS_WRITE` か

解析器は、子プロセスが何者かで、pipe の効果の kind を決めます。
決めているのは `authgap/effects.py` の `_pipe` の次の部分です。

```python
if shell is True or is_interpreter(argv0):
    kind, slot_name = "EXEC", "code_text"
else:
    kind, slot_name = "FS_WRITE", "content"
```

- 1 行目: 子を起動したときに `shell=True` だった、または起動したプログラム `argv0` がインタプリタの一覧に載っていれば、
- 2 行目: kind を `EXEC`、slot を `code_text`（実行されるコード）にします。
- 3〜4 行目: それ以外は、kind を `FS_WRITE`、slot を `content`（書く中身）にします。

インタプリタの一覧は、`/bin/sh`・`/bin/bash`・`sh`・`bash`・`python`・`python3`・`node`・`psql`・`/usr/bin/psql` の 9 つと、名前が `python` で始まるもの（`python3.12` など）です。
`argv0` が `None`（定数として読めない）なら、一覧とは照らせないので、`FS_WRITE` の側に入ります。

| 子プロセス | kind | slot | 考え方 |
|---|---|---|---|
| `shell=True` で起動した、または `argv0` がインタプリタの一覧に載る | `EXEC` | `code_text` | 流し込んだものはコードとして実行される |
| それ以外（**`argv0` が定数として読めないときも含む**） | `FS_WRITE` | `content` | 流し込んだものが何に使われるか分からないので、書き込みの一種の**情報行**として記録する |

表の読み方: 1 行が 1 つの場合です。2 行目の「情報行」とは、「確かに書き込みだ」という主張ではなく、「書き込みに届くかもしれない」という情報を残すための行、という意味です。
（出典: `authgap/effects.py:844-847`、`authgap/catalog/sinks.py:622-635`（`INTERPRETER_ARGV0`・`is_interpreter`））

#### manifest での見え方

pipe の効果は、manifest で次のように出ます。

- `site`: **`pipe:write`**（`X.stdin.write(v)` のとき）または **`pipe:communicate`**（`X.communicate(input=v)` のとき）。`pipe:` の後ろは、呼んだメソッドの名前です。
- `form`: `pipe`
- `kind` と `sub_kind`: 上の表の `FS_WRITE`（または `EXEC`）。
- `destructive`: `FS_WRITE` のときは `null`。pipe の行には印が無いからです。
- slot: `FS_WRITE` なら `content`、`EXEC` なら `code_text`。sink 表の pipe の行は slot を `stdin` と書いていますが、効果を作るときに `content` か `code_text` に付け替えます。

（出典: `authgap/effects.py:848-862`、`authgap/catalog/sinks.py:648-651`）

#### D2・D4 では、pipe の `FS_WRITE` はどうなるか

pipe の `FS_WRITE` は、`destructive` が `null` で、書き出しの一覧にも入っていません。
そのため 13.9 節の 4 つの類では「決まらない」（`unknown`）に入ります。
書き先の slot `path` を持たないので、「書き先をモデルが選べる」にもなりません。
本書の執筆時の作例（上の `cat` の形を D2・D4 のツールに入れたもの）では、次のとおりでした。

- D2: 不（`fs_unknown`）。
- D4: 内（行の注記なし。D4 が見るのは `open` の仲間のモードだけだから）。

同じ作例の起動（`subprocess.Popen`）の `SPAWN` は、D2 では不（`spawn_command`）、D4 では不（`exec_or_spawn`）でした。

本記録者の v4 の判定は、**誤 E5** でした（id は M59）。
判定の記録には「`pipe:write` は自分が起こした子プロセスの stdin への書き込み（プロセス間通信）で、ファイルや永続する状態を変えない」「stdin に流すのはコードではなくデータ（pickle）なので EXEC にも当たらない」とあります。
この経路で実際にファイルを変えるのは、一時ファイル（205 行目の作成、子が 193 行目で書く、233 行目で消す）で、それは別の組（M58、`os.remove` × D1）で数えています。
v4 の判定は本記録者が行ったもので、最終評価の判定の正解ではありません。**考え方の例**として読んでください。
（出典: `corpus/v4-vladimir-human__ru-marketplace-mcp/packages/ozon-connector/src/ozon_connector/server.py:188`、`:193`、`:204-218`、`:233`、`evidence/population_v4/v4_judgments.json` の M58・M59、`docs/drafts/final_judging_guide_draft.md:645`）

#### 判定での注意 — ファイルの書き込みとは限らない（E5）

**pipe の `FS_WRITE` は、子プロセスの標準入力への書き込みで、ファイルの書き込みとは限りません。**
手順書と手引きの下書きは、これを手順 C（効果の行を開いて、本当にその操作かを確かめる）の最初の例に挙げています。

> 例: `pipe:write` / `pipe:communicate` は子プロセスの標準入力への書き込みで、ファイルの書き込みとは限らない（第 17 節 E5）。

人の判定で、解析器の矛が実は違反ではなかったとき（**誤**）、その原因を E1〜E9 の記号で記録します（**誤の原因の分類**。第 51 章）。
そのうちの **E5** が「子プロセスの標準入力・パイプを書き込みと読んだ」で、見分け方は「`pipe:write` / `pipe:communicate` で、子が受け取ったものでファイルを変えない」です。
手引きの下書きの D1 の「迷いやすい形」も、「子プロセスの標準入力への書き込み: それ自体はファイルを変えない。子プロセスがそれを受けて何をするかで決める」と書いています。
（出典: `docs/final_evaluation_procedure.md:791`、`:1106`、`docs/drafts/final_judging_guide_draft.md:118`、`:324`、`:433`）

この類の誤りは、これまでに 2 回出ています。

| いつ | どこで | 何が起きたか | 記録 |
|---|---|---|---|
| v3 | helm / kubectl を起動するツール | `communicate(input=None)`（標準入力に**何も流していない**）を `FS_WRITE` の行にしていた。誤 4 | O41 |
| v4 | ru-marketplace の `ozon_reviews` | `sys.executable` に pickle のデータを流すだけの `pipe:write` を D1 の矛にしていた。誤 1（M59） | O43、`v4_judgments.json` |

表の読み方: 1 行が 1 回の確認です。どちらも、子が受け取ったもので（または何も受け取らずに）ファイルを変えない形でした。
`input=None` でも効果が出ることは、本書の執筆時に作例（`["kubectl", "get", "pods"]` に `communicate(input=None)`）を走査して確かめました。`pipe:communicate` の `FS_WRITE` が出て、D1 の矛（`fs_write`）になります。
（出典: `docs/open_questions.md:1068-1070`（O41）、`:1191`（O43））

v4 の矛の一覧 481 行のうち、site が `pipe:` で始まる行は 6 行（`pipe:write` 5、`pipe:communicate` 1。どれも D1）でした（本書の執筆時に `evidence/scan_v2_v4_run1/contradictions.json` を数えた。分母は v4 の矛の一覧の全行）。

#### なぜ、それでも解析器は書き込みとして記録するのか

「誤りが出るなら、この行を出さないように直せばよいのでは」と思うかもしれません。
実際、v3 の後に、この行を出さないように直す案（D61 の G1「子プロセスの標準入力はファイルではない」）を試しました。
しかし敵対的レビュー（第 24 章。自分の修正を壊しに行く点検）で、この前提が一般には成り立たないと分かり、取り消しました（D61 の改訂）。

取り消しの理由は、インタプリタの一覧に無いプログラムでも、標準入力に流したものがコードの実行やファイルの書き込みに届く例がいくらでもあることです。
D61 の改訂は、例として `env python3`・`/usr/bin/env bash`・`sudo sh`・`xargs -0 rm`・`tee /etc/app.conf`・`zsh`・`ruby`・`sqlite3 db`・`ssh host bash -s`・`patch -p1`・`uv run python -` などを挙げています。
たとえば `tee /etc/app.conf` は、標準入力から受け取ったものを、そのままファイルに書きます。
`xargs -0 rm` は、標準入力から受け取った名前のファイルを消します。

そこで「書き込みかもしれない」という情報行は、**子プロセスがデータで何をしうるかの保守的な上界**として正しい、と結論しました。
「上界」とは、「実際にすることは、これを超えない」という見積もりのことです。
解析器は上界を出し、人が子プロセスの中身を調べて決める。これが分担です。
（出典: `docs/decisions.md:3459-3466`（D61 の改訂）、`docs/open_questions.md:1068-1070`）

#### よくある誤解・つまずき

- **「`pipe:communicate` の `FS_WRITE` だから、ファイルを書いている」**: 子プロセスの標準入力に流しているだけです。子が何をするかを調べます。
- **「`communicate(...)` と書いてあれば、何かを流している」**: `input=None` なら何も流していません（v3 の helm / kubectl）。
- **「`sys.executable` は Python だから、解析器は `EXEC` にするはず」**: 解析器は `sys.executable` の値を定数として読めないので、インタプリタの一覧と照らせず `FS_WRITE` にします。
- **「pipe の行は誤りだらけなので、無視してよい」**: `tee`・`xargs rm`・`sqlite3` のように、本当に書き込みに届く子もあります。1 件ずつ子を調べます。
- **「`EXEC` の pipe なら、必ずモデルのコードが実行される」**: 流し込む値を誰が決めたかは、slot `code_text` の主体を見ます（第 14 章）。

#### 手作業ではどう使うか

判定表に `pipe:write` / `pipe:communicate` の行が来たら、次の順で確かめます。

1. **子を起動した行を探す。** 同じハンドル（`proc` など）を作った `subprocess.Popen(...)`・`asyncio.create_subprocess_exec(...)`・`asyncio.create_subprocess_shell(...)` の行です。
2. **子が何者かを決める。** 起動したプログラム（リストの最初の要素）と引数を読みます。変数なら、値をさかのぼります。
3. **何を流しているかを見る。** `input=None` なら何も流していません。分岐ごとに違うこともあります（gemini の例）。
4. **子が、受け取ったものをどう使うかを調べる。** 文書・`--help`・子のコード（同じ木の中なら）を読みます。
   - 受け取ったものを読むだけ・出力するだけ（`sort`・`cat`・pickle を読むだけの子）→ この行は E5 の誤の候補。
   - 受け取ったものでファイルを書く・消す（`tee`・`xargs rm`・`sqlite3` への変更の SQL）→ 宣言に反しうる。
   - 受け取ったものをコードとして実行する → 実行される内容で決める。
5. **判断の根拠を `evidence` に書く。** 起動の行・流し込みの行・子の動作を調べた資料を、ファイルと行で書きます。調べても子の動作が決められなければ、「不明」とし、その理由を書きます（第 52 章）。

子の起動そのもの（`SPAWN` の効果）は、別の組として判定表に出ることがあります。
pipe の行と起動の行を取り違えないように、`site` を見て区別してください。

#### この節のまとめ

pipe の sink は、子プロセスのハンドルの `stdin.write(v)` と `communicate(input=v)`。manifest では `site: pipe:write` / `pipe:communicate`、`form: pipe`。
子がシェル・インタプリタなら `EXEC`（`code_text`）、それ以外（`argv0` が読めないときも）なら `FS_WRITE`（`content`、`sub_kind: FS_WRITE`、`destructive: null`）の情報行。
ファイルの書き込みとは限らない（E5。v3 の誤 4、v4 の M59）。それでも上界として残すのが D61 の改訂の結論。人は子が何をするかを調べて決める。

### 13.12 凍結された語彙

#### 一言で言うと

sink 表と slot の種類は、仕様書が「**月 3** に凍結する」と決めた**語彙**です。
「月 3」は、仕様書の月単位の計画の 3 か月目のことです。
**凍結**とは、決めたものを後から変えないと約束した状態のことです。
だから、判定の途中で sink 表の抜けに気づいても、解析器は直しません。

#### 言葉の確認 — 語彙と凍結

- **語彙**: やさしく言うと「使ってよい言葉の一覧」です。正確には、解析器の中で値として使える名前の集まり（kind の 7 つ、slot の名前、sink 表の行など）で、これ以外の名前は使えないように決めたものです。例: 13.2 節の `SLOTS`。
- **凍結**: やさしく言うと「決めたものを、後から変えないと約束すること」です。正確には、決めたものをコミット（記録）して固定し、以後は変えない約束をした状態です。変えるときは、事前に決めた手続き（逸脱としての記録）を踏みます。例: 最終評価に使う解析器は、`analyzer-freeze-3` というタグで凍結されています。凍結の詳しい扱いは第 22 章で学びます。

#### たとえ話 — 試験の採点基準

試験の採点基準を、答案を見る**前**に決めて封筒に入れておくとします。
答案を見てから基準を変えると、「この生徒を合格させたいから基準を緩めた」と疑われても反論できません。
基準を先に決めて封をしておけば、結果がどうであっても、基準は結果に合わせて作ったものではないと言えます。

sink 表の凍結も同じです。
「どの関数を効果として数えるか」を先に決めて固定しておけば、走査の結果を見た後で「都合のよい数字が出るように表を選んだ」と疑われずにすみます。

#### 小さな例 — 「月 3」とは

仕様書（`AUTHGAP_BRIEF_v3.md`）は、研究の作業を月ごとに区切って計画しています。
その「凍結」の節に、何を何か月目に固定するかが並んでいます。

| 時期 | 仕様書が凍結すると決めたもの（抜粋） |
|---|---|
| **月 3** | **sink 語彙**（直接 + proxy + pipe、slot 語彙、副 kind）、ライブラリのコンストラクタの一覧、ラベルの規則、標本の枠と seed、配備モード、執行表、R2 の例外 |
| 月 6 | ゲートの語彙（付録の側の語彙。第 8 章） |
| 月 10 | 解析の指紋（解析器の版を表す値。第 22 章） |

表の読み方: 1 行が 1 つの時期です。右の列が、その時期に固定すると決めたものです。
たとえば 1 行目は「計画の 3 か月目に、sink 表（3 つの形すべて）と slot の名前と副 kind を固定する」と読みます。

仕様書の本文のあちこちにも、「月 3 の凍結に含める」という書き込みがあります。

- 「kind と **slot 語彙**（月 3 の sink 語彙凍結に含む）」（Def 3 の冒頭）
- 配備モード（運用者とモデルの関係の仮定）は「月 3 の凍結に含める」
- ツールの引数のうちモデルに見せないものの例外（R2 の例外）は「執行表と同じ時点（月 3）で凍結する」

sink 表のファイルの先頭の説明も、「表を凍結（月 3 の sink 語彙凍結、月 10 の解析指紋）して再現可能にする」と書いています。
（出典: `AUTHGAP_BRIEF_v3.md:196`、`:204`、`:211`、`:839-843`、`authgap/catalog/sinks.py:3-4`）

#### 一歩ずつ — 凍結の後に変えたもの・変えなかったもの

凍結は「絶対に変えない」ではありません。
変えるときは、**事前登録**（データを見る前に測り方を書いてコミットしておく文書。`docs/preregistration.md`。第 22 章）に、**逸脱**（決めた計画から外れた変更）として、日付・理由・変更前後の結果を記録します。
CLAUDE.md も「月 6 の凍結後は語彙を動かさず、`docs/preregistration.md` に逸脱として記録する」と書いています。

変えた例を 2 つ挙げます。

1. **逸脱 #15（D50、2026-09-23）**: DB の proxy の行に、`sqlalchemy.ext.asyncio.AsyncSession` などの型を足しました。母集団 v2 で、`AsyncSession` の `.execute()` が受け手の型の一覧に無いために落ちていたからです。事前登録には、変更の前後の走査（run7 と run9）の数と、「消えたユニット 0 / 消えた CONTRADICTION 0」が記録されています。
2. **`destructive` の属性（D32）**: 13.9 節の印は、sink 表の行に足した属性です。D32 は「**kind / slot の語彙は変えない**」と明記し、事前登録 §5 の #7 に逸脱として記録しました。

逆に、**必要そうに見えても足していないもの**があります。
代表が O39（13.7 節）の HTTP のメソッド（セッションの `.delete` など）です。
理由は「sink 語彙は月 3 凍結。足すなら凍結した語彙を結果を見た後に変えることになる」で、その結果「D2 の矛は下限になる」と、限界として書かれています。
（出典: `docs/preregistration.md:566`（逸脱 #15）、`authgap/catalog/sinks.py:474-476`（`AsyncSession` を足したコメント）、`docs/decisions.md:462-464`（D32）、`docs/preregistration.md:558`（§5 の #7）、`docs/open_questions.md:1041-1049`（O39））

#### なぜ凍結するのか

sink 表を凍結する理由は、sink 表の先頭の説明そのものです。
公式の「効果の仕様」が無いので、**表そのものを凍結して再現可能にする**。
表が動くと、同じ木を走査しても結果が変わってしまいます。

もう 1 つの理由は、結果を見た後の変更が、結果をゆがめるからです。
走査の結果を見て「この関数も足そう」と表を変えると、足す関数を選ぶときに、結果が良くなる方向の関数ばかり選んでしまうかもしれません。
本人にそのつもりが無くても、外から見て区別できません。
だから、抜けは直さずに限界として記録し、件数を併記します。

#### 最終評価での凍結

最終評価に使う解析器は、`analyzer-freeze-3` というタグで凍結されています（第 36 章）。
手引きの下書きは、判定の途中で手引きのどの規則にも当てはまらない事例が出たときの扱いの最後に、「解析器の誤りを見つけても直さない。`docs/open_questions.md` に限界として書く（O43 と同じ扱い）」と書いています。
**判定の途中で sink 表の抜けに気づいても、解析器は直しません。**
見落としとして記録し（原因「語彙」）、限界として書きます。
（出典: `docs/drafts/final_judging_guide_draft.md:672`）

#### よくある誤解・つまずき

- **「凍結した表は正しいと保証されている」**: 違います。凍結は「変えない」約束で、「正しい」保証ではありません。抜け（O39 など）は、限界として記録されています。
- **「抜けを見つけたら、直すのが誠実だ」**: この研究では、結果を見た後に直すことのほうが、結果をゆがめるおそれがあります。直さずに記録するのが、ここでの誠実さです。
- **「月 3 は、3 月のこと」**: 暦の 3 月ではなく、仕様書の計画の 3 か月目のことです。
- **「凍結の後は、一切変えられない」**: 変えるときは逸脱として記録し、変更前後の両方を報告します（逸脱 #15 など）。

#### 手作業ではどう使うか

判定の途中で、sink 表に無い書き込み（ログのファイル、`mkstemp` など）に気づいたら、次のようにします。

1. その組やツールの判定は、**コードの動作**で行う（解析器の出力に無くても、書き込みは書き込み）。
2. 見落としの判定なら、原因を「語彙」と記録する（第 52 章）。
3. 解析器を直そうとしない。気づいた抜けは `note` に書き、必要なら限界として残す。

#### この節のまとめ

sink 表・slot・副 kind は、仕様書の月単位の計画の「月 3」に凍結した語彙。凍結は「決めたものを後から変えない約束」（詳しくは第 22 章）。
変えるときは事前登録に逸脱として記録する（逸脱 #15、D32 の属性）。結果を見て足さないもの（O39）は限界として記録する。
最終評価の解析器は `analyzer-freeze-3`。判定の途中で抜けに気づいても直さず、見落とし（原因「語彙」）として記録する。

### この章のまとめ

- 外の世界（ファイル・通信相手・DB・他のプログラム）に触れる操作が**効果**。1 つの効果は (kind, site, slots) の 3 つ組で、manifest の `effects` に並ぶ（13.1）。
- **kind** は 7 つ（`FS_READ`・`FS_WRITE`・`NET`・`DB`・`SPAWN`・`EXEC`・`DISPATCH`）で、`SLOTS` で決まり、これ以外は作れない。`FS_WRITE` は作成・削除・置き換え・権限の変更を含む（`os.makedirs`・`os.replace` もその例）。`DISPATCH` は凍結版では効果に出ない（13.2）。
- `sub_kind` は名前から想像する意味と違う（`SPAWN_MODEL_ARGV` は argv0 が読めなかっただけ、`DB_WRITE` は読み取りの語で始まらないだけ）。判定には使わず、行の注記を見る（13.3）。
- 効果を起こす呼び出しが **sink**、その一覧が **sink 表**。公式の一覧が無いので自分で作り、凍結して再現可能にした。形は `direct`（67 の名前）・`proxy`（17 行）・`pipe`（2 行）（13.4）。
- 直接の sink は `import` をたどった正式な名前で決まる。`urlretrieve` は 2 つの効果を出し、`shell=` の読めない起動は 2 通りの効果を出す（13.5）。
- proxy の sink は受け手の型とメソッド名で決まる。site 名は「型の候補を並べ替えた先頭」なので、sqlite3 が `psycopg.Cursor.execute`、`requests.Session` が `httpx.AsyncClient.post` と表示される。kind が合っていれば判定に影響しない（13.6）。
- sink 表に無いもの（ログのファイル、HTTP のセッションの `.delete` など、`mkstemp`・`touch`）は効果に出ない。見落としの原因「語彙」。D2 の矛は下限（13.7）。
- **slot** は効果の中の値の位置。slot ごとに主体が違い、判定は特定の slot（D3 は `url.host`、D2 の書き出しは `path`）で決まる。`os.replace`・`shutil.copy` の `path` は 2 番目の引数（13.8）。
- `FS_WRITE` の **`destructive`**（`true` / `false` / `null`）が D2 の根拠。D2 では追記は内、消す・動かす・変えるは矛（`fs_remove`）、書き出しと決まらないものは書き先をモデルが選べれば矛・それ以外は不。D1 は印を見ない（13.9）。
- `open` のモードは、D1 ではすべて矛（`fs_write`）、D2 では `'w'`・`'+'` が書き出し・`'a'`・`'x'` が内・読めなければ `fs_unknown`、D4 では定数の `'a'` が矛（`fs_append`）・読めなければ `fs_mode_unknown`。読めなければ `FS_READ` と `FS_WRITE` を両方出す（13.10）。
- `pipe:write`・`pipe:communicate` は子プロセスの標準入力への書き込み。インタプリタ・シェルなら `EXEC`、それ以外は `FS_WRITE`（`form: pipe`、`sub_kind: FS_WRITE`、`destructive: null`）の情報行。ファイルの書き込みとは限らない（E5。v3 の誤 4、v4 の M59）。上界として残すのが D61 の改訂の結論（13.11）。
- sink 表と slot は仕様書の計画の「月 3」に凍結した語彙。凍結は「決めたものを後から変えない約束」（第 22 章）。最終評価の解析器は `analyzer-freeze-3` で、判定の途中で抜けに気づいても直さない（13.12）。
- この章の v4 の例と数は、本記録者（AI）が行った開発用の確認のもので、論文には使わない（D66 の 5）。最終評価の判定は学生 1 人が行い、AI（LLM）は使わない（D70 の 3）。
