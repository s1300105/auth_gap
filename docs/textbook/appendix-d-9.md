### 確認問題 53-1

- 16.1 節の 6 番「キャッシュ・状態の保存」の定義は「ツールの動作のために自分で保存し、**後で読み返す**」です。練習用のサーバは、12 行で `~/.demo_cache/<query>` に書きますが、そのファイル（や `CACHE_DIR`）を読む行が木のどこにもありません。だから 6 番に当たらず、1〜7 番のどれにも当たらないので、8 番の「その他・不明」になります。手引きは「名前ではなく動作で決める」とまとめています。
- 確かめ方: `grep -n "CACHE_DIR\|demo_cache" server.py`（場所の名前が出る行が 7・11・12 行だけ）と、`grep -n "open(\|\.read\|read_text" server.py`（開く行が 12・32 行の `"w"` だけ）を走らせ、読む行が無いことを見ます。
- 本番の木では、`grep -rn '<場所の名前>' corpus/<木> --include='*.py'` のように木の全体を探します。書く関数と読む関数が別のファイルや別のツールにあることがあり、別のツールが読み返していても、サーバの動作のために後で読み返すので 6 番に当たります。

### 確認問題 53-2

- 根拠は**原理 3-a「能力として読む」**です。モデルが値を選べるなら、その引数が取りうる値の全体をツールが「できること」とみなします。`path` はモデルが選べるので、既存のファイルを指して `"w"` で上書きできる → 前からあったものを変えうる → D2 に反する、となります（手引き 15.2 節の書き出しの行、§7.2）。
- それぞれの変種（53.4 節の表。解析器の出力は本記録者が確かめた）:

| 変種 | 解析器 | 人の判定 |
|---|---|---|
| `"a"` | 内（印なし） | 判定の対象外。動作も「足すだけ」で D2 に反しない |
| `"x"` | 内（印なし） | 判定の対象外。すでにあれば失敗するモードで、新しく作るだけ |
| 書き先が定数の 1 つのファイル | 不（`fs_writeout`） | 不の中身として判定するなら、毎回同じファイルを上書きするので違反 |
| `readOnlyHint=True` | D1 の矛（`fs_write`） | 正。D1 では書けば反する。書き込み先の種類は利用者のファイル |

### 確認問題 53-3

- 出力を最後に見るのは、**先入観を避けるため**です（手引き 18.2 節の見出し）。先に出力を見ると「解析器が出していないものは無い」と思い込んで読みが甘くなり、解析器が見ていないもの（語彙に無い操作、深さの外、解決できない呼び出し）を探すという見落としの判定の目的が果たせません。
- 「反する動作は無い」のときに `evidence` に書くもの:
  1. **読んだ範囲**（ファイルと行）: 第三者が同じ範囲を読めば同じ結論に着けるかを確かめられるように。
  2. **本体の呼び出しの一覧**: 何も見落としていないかを第三者が数え直せるように。
  3. **深さ 1 以上が無いこと（または読んだ深さ）の根拠**: 「読まなかった」のではなく「読む先が無かった／深さ 4 まで読んだ」ことを示すため。

- （第 3 版の「深い所ほど『本当に通るか』の確かさが下がる」という理由も、D54 の記録（深さ 5 で増えた矛の誤検出 0、当時の手検証）と合わないので、使わないほうがよい。）

(2) 書き直しの例: 「深くすれば見落としは減るかもしれませんが、深さは 4 に凍結済み（D54）なので変えません。最終評価では深さ 3・5 でも走らせますが、出すのは矛の件数だけで、判定はしません（探索的。D69 の 5）。だから、深さによる見落としの量は最終評価では測りません。見落としの判定で深さ 4 より奥に違反を見つけたら、『見落とし（深さ 4 の外）』として主の見落としとは別に数え、併記します（D68 の 2）。」

### 確認問題 56-1

起動の方法は、コードだけから決めます（D67 の 2）。
ccr は初期化を `main()` の中だけで済ませています。モジュールの一番上の `mcp` は、`fastmcp run file.py:mcp` のように `main()` を通らない**起動の方法**で起動できるので、そのときは最初のツールの呼び出しで初期化の効果が起きます。だから「届きうる」ので到達し、宣言に反すれば正になります（条件の種類は「起動の方法」）。
shyhurricane は初期化を lifespan の中で済ませています。lifespan は**どの起動の方法でも**ツールの受付より前に必ず走るので、ツールの呼び出しでは届きません。だから誤（E1）です。
論文に両方を書く理由: この規則で ccr の件は正になるので、解析器に都合のよい規則に見えうる。規則が原理 3 から導いたものであり、解析器に不利な側（lifespan の形）も誤として残ることを示すためです（O43 の整理、手引き 14.4 節）。

### 確認問題 56-2

v4 で抜き取った D1・D2 の矛 60 件のうち 38 件は reaper-mcp の 1 木から来ていて、全部が正でした。件数の精度は 76.7% でしたが、reaper-mcp を除くと 8/22 = 36.4% でした（事後の分析）。件数で数えると、1 木が 60 件中 38 件（約 63%）の重みを持ち、その木の性質で精度が大きく動きます。木で数えれば、1 木は 1 票（8 木なら 12.5%）なので、偏りが小さくなります（木ごとの精度の平均は 59.7% → 53.9%、本当の矛があった木の割合は 75.0% → 71.4%。本書の計算）。だから報告の単位を木にしました（D67 の 3）。

論文に使わない理由（2 つ以上）:
- v4 の判定は本記録者（AI）が行ったもので、v4 の数字は論文に使わないと決めている（D66 の 5）。
- 36.4% は事前登録していない事後の分析である。
- （ほかに）v4 のデータは最終評価から除く、抜き取りと判定の規則が最終評価と違う。

### 確認問題 56-3

2026-10-01 に**保留**になりました（O2、D70 の 8）。2 人目の判定者を用意できるかもしれないが、まだ分からなかったためです。決まるまでは、D67 の 4（判定は学生 1 人）が既定でした。
期限より前の 2026-10-03 に、**D73 の 1** で決まりました（O2 は「解決」）。判定した全件から seed ⑥ で 10% を選びます。段階 6（抜き取りのコミット）の時点で 2 人目が決まっていれば、2 人目が学生のラベルを見ずに同じ手引きで判定し、判定の種類ごとに Cohen の κ と一致率を出します（食い違いは話し合いで決め、置き換えたときの主指標を併記）。決まっていなければ、全部を判定し終えて 2 週間以上あけ、学生が前のラベルを見ずに判定し直します。どちらでも、主の結果は学生のラベルです。残る作業は、2 人目の候補を探すことです。

### 確認問題 56-4

- **上限の目安**: 開発中に見た**解析器の生の数**（例: 開発用の v2 で D1 の矛を出した木が 87 木中 13 木）。人が確かめていないので誤警報を含み、本当の数より大きく出る向きにある。ただし見落としもあるので、厳密な上限ではない。
- **下限**: 最終評価で**人が判定して確かめた数**（(a)〜(c)）。1 木 3 件までしか判定しないことと、矛の出なかった木の見落としを数えないことから、本当の数より小さく出る向きにある。K̂ ≤ N なので、いつも解析器の数の内側から出る。

並べて「改善」「悪化」と言えない理由:
1. 向きが逆（片方は上から、片方は下から押さえる数）なので、差は性能の変化を表さない。
2. データ（開発用の v2 と最終評価のデータ）も、解析器の版も違う（さらに分母も、v2 の全部の木と、宣言を明示した木 M_d で違う）。
