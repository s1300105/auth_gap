#### 手作業（最終評価）との関係

段階 1〜6 には、機械に任せられない手作業が 4 つあります。

1. **事前登録の下書きを 1 行ずつ読み、自分の判断として承認する**（47.1 節）。下書きを書いたのは本記録者（AI）です。承認するのは学生です。
2. **判定の練習をし、1 件にかかる分数を測る**（47.6 節）。この分数が、段階 6 で件数が日程に合うかを決めます。
3. **段階ごとの確認の結果を自分の目で見る**（47.7〜47.10 節）。重なりが 0 か、HEAD が pin と一致するか、指紋が一致するか、打ち切りが何件か。
4. **件数が日程に合うかを決める**（47.11 節）。減らすなら、段階 6 のコミットの前に逸脱として書きます。

どれも、判定そのもの（第 48〜52 章）より前にある手作業です。
ここで迷いを残すと、判定の途中で「規則を変えたい」「件数を減らしたい」という誘惑に負けやすくなります。

#### この章で使う言葉の思い出し

- **木**（[第 11 章](ch11.md)）: 解析する 1 つのリポジトリ（1 つの MCP サーバ）。`corpus/<木の名前>/` に取得する。
- **ユニット**（第 11・12 章）: 1 つのツール。manifest の `units[]` の 1 要素。relpath（ファイルの場所）と行で探す。
- **組**（[第 18 章](ch18.md)）: 判定の単位。(木, ユニット, site, kind, 宣言)。
- **矛・不・内**（[第 17 章](ch17.md)）: 解析器の 3 つの答え。矛 = 宣言に反する効果がある、不 = 静的には決められない、内 = 宣言の範囲内。
- **正・誤・不明**（第 17・38 章）: 人が矛を原ソースで確かめた結果。
- **pin**（第 11・25 章）: 取得するリポジトリの版を、commit の SHA（40 桁の 16 進数の名前）で固定すること。
- **seed**（[第 25 章](ch25.md)）: 乱数の種。同じ seed なら、誰がやっても同じものが選ばれる。
- **凍結・指紋**（[第 22 章](ch22.md)）: 解析器の版を固定すること / その版の `authgap/` のファイルのハッシュ（`docs/fingerprint.json`）。
- **manifest・`summary.json`・`contradictions.json`**（[第 18 章](ch18.md)）: 走査の出力。木ごとの詳しい記録 / 木ごとの件数と全体の合計 / 矛の行を (ユニット, site, kind) ごとにまとめた表（反した宣言は `declarations` の欄に並ぶ）。
- **封**（[第 22 章](ch22.md)）: 事前登録 §2.12 と判定の手引きを同じコミットに入れ、その後でデータに触れること。
- **逸脱**（[第 22 章](ch22.md)）: 事前登録した定義を後から変えたときに、`docs/preregistration.md` §5 に書く記録。
- **本記録者**（[第 0 章](ch00.md)）: この repo で解析器を作り、決定の推奨と記録を書いてきた AI（Claude）。v3・v4 の判定もした。

この章で新しく、または久しぶりに出てくる言葉も、ここで 3 点セット（言い換え・定義・例）で押さえておきます。

- **宣言ファイル**: 言い換えると「ツールの宣言を書いてあるファイル」。定義は、列挙のときに `annotations=`（`ToolAnnotations(` か dict 形）が見つかった `.py` ファイルで、標本の `declaring_paths` の欄に並ぶもの。例: `server.py` に `@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))` があれば、`server.py` が宣言ファイル。取得後の条件（47.8 節）は、このファイルが `mcp` / `fastmcp` を import するかを見ます。
- **明示された宣言**（`D_kind.explicit`）: 言い換えると「作者が自分の手で書いた宣言」。定義は、manifest のユニットの `D_kind.explicit` に並ぶ注釈の名前で、既定値で補ったものは入らない。例: `readOnlyHint=True` だけを書いたツールなら `['readOnlyHint']`。見落としの対象（47.3 節）と分母 (c) の M_d（47.1 節）は、どちらもこの欄で決めます。
- **tree budget**（木の時間上限）: 言い換えると「1 つの木の解析にかけてよい時間の上限」。定義は、`scan_v2.py` の `--tree-budget`（既定 180 秒）で、これを超えると残りのユニットを解析せずに打ち切り、件数を記録する。例: v4 の最長は 96.8 秒だったので、v4 では打ち切りは 0 でした（47.9 節）。
- **label**（走査の名前）: 言い換えると「走査の 1 回ごとに付ける名札」。定義は、`scan_v2.py --label <名前>` で渡す文字列で、出力先が `evidence/scan_v2_<名前>/` になる。例: `--label final_run1` なら `evidence/scan_v2_final_run1/`。同じ名札でもう一度走らせると、manifest が残っていれば止まり、残っていなければ前の `summary.json` と `contradictions.json` を上書きします（47.5・47.10 節）。

### 47.1 段階 1 — 事前登録 §2.12 と判定の手引きを書いて封をする

#### 一言で言うと

最終評価の規則（対象・走査・抜き取り・判定・分母・やってはいけないこと）を事前登録 §2.12 に書き、判定の手引きと**同じ 1 つのコミット**に入れます。
これが「封」で、封をした後で初めて最終評価のデータに触れます。

#### たとえ話 — 採点基準を封筒に入れて、消印を押す

学校の入試を思い浮かべてください。
採点の基準は、答案を開く**前に**決めておきます。
答案を見てから基準を決めると、「この受験生を合格させたいから、この書き方も正解にしよう」という手心が入りうるからです。

さらに、基準を封筒に入れて封をし、郵便局で消印を押してもらったとします。
消印の日付は、後から誰も書き換えられません。
だから「答案を開く前に、この基準で採点すると決めていた」ことを、第三者に示せます。

この研究では、**git のコミット**が封筒と消印の役をします。
事前登録と手引きをコミットすると、その中身と日時が記録に残ります。
後から最終評価のデータに触れたコミットは、必ずその後の日時になります。
つまり、コミットの並び順が「何を先に決めたか」の証拠になります。

#### 封のコミット — 引用符つきの heredoc で渡す

封は、2 つのファイルを 1 つのコミットに入れることです。
手順書の 5.3 節のコマンドを、ファイル名を下書きの指示（手引きは `docs/final_judging_guide.md`）に合わせて書くと、次のようになります。

```bash
git add docs/preregistration.md docs/final_judging_guide.md
git commit -F - <<'EOF'
最終評価の事前登録（§2.12）と判定の手引き（データを見る前。D67〜D73）

- 対象: 枠の残りを全部（D69 の 1）。中身の重複を除く（D70 の 6）
- seed: 202610151〜202610154（封の日 2026-10-15。架空の例）
- 判定の一致の確認（D73 の 1）: 段階 6 の時点で 2 人目が決まっていれば (i)、いなければ (ii)

Co-Authored-By: ...
EOF
git push
```

1 行ずつ読みます。

- 1 行目: `git add` で、コミットに入れるファイルを 2 つ選びます。事前登録と手引きが**同じコミット**に入ることが封の条件です。
- 2 行目: `git commit -F -` は「コミットメッセージを、ファイル（`-F`）として、標準入力（`-`）から読む」という意味です。`<<'EOF'` は「次の行から `EOF` だけの行までを標準入力として渡す」（heredoc）という意味です。`EOF` を**引用符で囲む**のがポイントです。
- 3〜9 行目: コミットメッセージの本文です。段階 0 で決めたことを箇条書きにします。9 行目の `Co-Authored-By:` は手順書の雛形にある共著者の行で、実際に一緒に書いた人（AI を含む）を正直に書きます。研究の遂行に AI を使ったことは論文で開示する約束です（O45 の 4）。
- 10 行目: `EOF` だけの行で、メッセージが終わります。
- 11 行目: `git push` で、手元のコミットを共有のリポジトリに送ります。送った時点で、第三者もコミットの日時を確かめられます。

なぜ `-m "..."` ではいけないのでしょうか。
二重引用符の中では、バッククォート（`` ` ``）で囲んだ部分を、シェルが**コマンドとして実行**してしまうからです。
本書の試験で確かめました。

```text
$ bash -c 'echo "解析器 `authgap/` は変えない"'
bash: line 1: authgap/: Is a directory
解析器  は変えない
```

1 行目が打ったコマンドで、2〜3 行目が出力です。
シェルは `` `authgap/` `` をコマンドとして走らせようとして失敗し（2 行目）、その部分を空にしてしまいました（3 行目）。
コミットメッセージでこれが起きると、本文の大事な部分が黙って欠けます。
引用符つきの heredoc（`<<'EOF'`）なら、シェルは中身に手を付けないので、バッククォートもそのまま残ります。

（出典: `docs/final_evaluation_procedure.md:383-398`（5.3 のコマンドと注意）、`CLAUDE.md` の「よく踏む落とし穴」の最後から 2 つ目、`docs/drafts/prereg_2_12_draft.md:3-5`（手引きの移し先と封））

#### なぜそうするのか

理由は 3 つあります。

1. **結果を見てから基準を選んだと疑われないため**です。D67 は「文面は最終評価の前に `docs/preregistration.md` と判定の手引きに書き、コミットしてからデータを見る」と決めています。
2. **2 人目の判定者がいないため**です。判定は学生 1 人で行います（D67 の 4）。判定者どうしの一致（κ）を示せない分、「判定の基準を先に固めた」ことと「根拠を全件残す」ことが、信頼性の支えになります。
3. **事前登録と手引きが別々のコミットだと、間に隙ができるため**です。たとえば事前登録だけを先にコミットし、データを見た後で手引きをコミットすると、手引きの中身が結果に合わせて書かれたかもしれないと疑われます。同じコミットに入れれば、その隙がありません。

### 47.2 段階 2 (1) — 環境と、今ある道具・作る道具

### 47.3 段階 2 (2) — 抜き取りのスクリプトに要ること

#### 一言で言うと

抜き取りの道具には、4 つの性質が要ります。
(1) 組を決まった**鍵**で区別する、(2) 鍵で**並べ替えてから**選ぶ、(3) **選ばなかった分も含めた件数**を出す、(4) **同じ入力と seed なら何度走らせても同じ出力**になる。

#### たとえ話 — くじ引きの箱

クラスの 40 人から 3 人を、くじで選ぶとします。
「乱数で 3 つの番号を出し、その番号の人を選ぶ」というやり方にしたとしましょう。

このとき、**名簿の並び順**が決まっていないと困ります。
乱数が「5 番目」を出したとき、名簿が五十音順なら A さん、出席番号順なら B さんになります。
同じ乱数（同じ seed）でも、並び順が違えば選ばれる人が変わってしまいます。
だから、くじを引く前に「名簿は出席番号順に並べる」と決めておきます。
これが性質 (2) です。

また、選んだ 3 人の名前だけを記録して、「全部で何人いたか」を書き忘れると、後で「40 人中 3 人」なのか「400 人中 3 人」なのかが分かりません。
これが性質 (3) です。

そして、同じ名簿と同じ seed なら、誰が引いても同じ 3 人になる必要があります。
後から第三者が「本当にこの規則で選んだのか」を確かめられるからです。
これが性質 (4) です。

#### 小さな例 — 矛の抜き取りの最小の形（本書の作例）

下は、矛の抜き取りの規則（宣言ごとに 200 木まで、1 木 3 件まで）を最小の形で書いたものです。
**本書の作例で、repo の道具ではありません**。
考え方を見るためのもので、学生が作る道具はこれと同じである必要はありません。

```python
import json
import random
import sys

sys.path.insert(0, "scripts")
from contradiction_by_decl import load_reasons

run_dir, seed = sys.argv[1], int(sys.argv[2])
rs = load_reasons(run_dir)
out = {"seed": seed, "per_decl": {}, "targets": []}
rng = random.Random(seed)
for decl in ("D1", "D2", "D3", "D4"):
    by_tree = {}
    for key in sorted(rs, key=str):
        if any(s == "contradiction" for s, _ in rs[key].get(decl, set())):
            by_tree.setdefault(key[0], []).append(key)
    trees = sorted(by_tree)
    chosen = sorted(rng.sample(trees, 200)) if len(trees) > 200 else trees
    for t in chosen:
        pairs = by_tree[t]
        picked = sorted(rng.sample(pairs, 3), key=str) if len(pairs) > 3 else pairs
        out["targets"] += [{"decl": decl, "key": list(k)} for k in picked]
    out["per_decl"][decl] = {"n_pairs": sum(len(v) for v in by_tree.values()), "n_trees": len(trees),
                             "n_trees_chosen": len(chosen),
                             "n_picked": sum(1 for x in out["targets"] if x["decl"] == decl)}
print(json.dumps(out["per_decl"], ensure_ascii=False))
json.dump(out, open(sys.argv[3], "w", encoding="utf-8"), ensure_ascii=False, indent=1)
```

v4 の走査（`evidence/scan_v2_v4_run1`）に、例の seed 202610011 で 2 回走らせると、2 回とも次の 1 行を出し、出力のファイルも 1 バイトも違いませんでした（本書の試験）。

```text
{"D1": {"n_pairs": 323, "n_trees": 17, "n_trees_chosen": 17, "n_picked": 41}, "D2": {"n_pairs": 155, "n_trees": 14, "n_trees_chosen": 14, "n_picked": 27}, "D3": {"n_pairs": 0, "n_trees": 0, "n_trees_chosen": 0, "n_picked": 0}, "D4": {"n_pairs": 3, "n_trees": 1, "n_trees_chosen": 1, "n_picked": 3}}
```

#### 一歩ずつの説明 — コードを 1 行ずつ

- 1〜3 行目: 道具を読み込みます。`json` は JSON の読み書き、`random` は乱数、`sys` はコマンドの引数を読むための部品です。
- 5〜6 行目: repo の `scripts/` にある `contradiction_by_decl.py` から、`load_reasons` という関数を借ります。この関数は、manifest の行の注記（`contradiction_reason:D1:fs_write` や `contradiction_unknown:D1:net_post`）を読み、組ごとに「どの宣言で、矛か不か、理由は何か」をまとめて返します。
- 8 行目: コマンドの引数から、走査の出力のディレクトリと seed を受け取ります。
- 9 行目: `load_reasons` を呼びます。返ってくる `rs` は、鍵が `(木, ユニットの relpath, ユニットの行, qualname, site, kind)` の辞書です。**これが組の鍵**です（宣言は辞書の中の側にある）。
- 10 行目: 出力の入れ物を作ります。seed も出力に残します。
- 11 行目: seed から乱数の発生器を 1 つ作ります。この 1 つを、D1→D2→D3→D4 の順に使い回します。
- 12 行目: 4 つの宣言を、**決まった順**に 1 つずつ処理します。
- 13 行目: 「木の名前 → その木の矛の組の一覧」の辞書を作ります。
- 14 行目: **組を鍵で並べ替えてから**見ていきます（`key=str` は「鍵を文字列にしたもので並べる」）。ここで並び順が固定されます。
- 15〜16 行目: その宣言で「矛」の印がある組だけを、木ごとに集めます。
- 17 行目: 矛の出た木の名前を並べ替えます。
- 18 行目: 木が 200 を超えたら、乱数で 200 木を選びます（選んだ後も並べ替える）。200 以下なら全木です。
- 19〜21 行目: 選んだ木ごとに、組が 3 件を超えれば乱数で 3 件を選び、3 件以下なら全件を採ります。
- 22 行目: 選んだ組を、宣言とともに出力に足します。
- 23〜25 行目: **選ばなかった分も含めた件数**を、宣言ごとに残します。`n_pairs` は矛の組の総数、`n_trees` は矛の出た木の総数、`n_trees_chosen` は選んだ木の数、`n_picked` は選んだ組の数です。
- 26〜27 行目: 件数を画面に出し、全部をファイルに書きます。

出力の 1 行は、こう読みます。
D1 は矛の組が 323、矛の出た木が 17 で、200 以下なので 17 木全部を選び、1 木 3 件までで 41 組になった。
D2 は 155 組・14 木で、27 組になった。
D3 は 0。
D4 は 3 組・1 木で、3 組全部。

（出典: `scripts/contradiction_by_decl.py:40-57`（`load_reasons` と鍵）、`scripts/runlib.py:61-63`（`unit_key`）、`docs/final_evaluation_procedure.md:443-450`（矛の抜き取りに要ること））

#### 4 つの性質を、作例で確かめる

**(1) 組の鍵**。
手順書は、鍵を (木, ユニットの relpath, ユニットの行, qualname, site, kind, 宣言) と決めています。
作例では、9 行目の辞書の鍵が最初の 6 つで、宣言は 12 行目の繰り返しで分けています。
relpath と行を鍵に入れるのは、別のファイルにある同じ名前のツールを 1 件に潰さないためです（D64 の U50。[第 12 章](ch12.md)）。

**(2) 並べ方の固定**。
作例では、14 行目（組）、17 行目（木）、18 行目と 21 行目（選んだ後）で並べ替えています。
乱数は「何番目を選ぶか」を決めるだけなので、並び順が変わると選ばれるものが変わります。
辞書の中の順番や、ファイルを読んだ順番は、作り方で変わりうるので頼りません。

**(3) 選ばなかった分の件数**。
作例の 23〜25 行目です。
なぜ要るのでしょうか。
[第 39 章](ch39.md)で見たとおり、分母 (b)(c) の分子は K̂ = (k / n) × N で推定します。
この **N（宣言 d の矛が出た木の総数）** は、選ばなかった木も含めた数です。
200 木を超えて抜き取ったときは、N を出しておかないと K̂ が計算できません。
また、(g) の「宣言ごとの矛の総数」「判定した件数」も、ここから取ります。

**(4) 同じ入力と seed で同じ出力**。
作例は 2 回走らせて、出力のファイルが同じでした。
手順書は、これを**試験で確かめる**よう求めています（たとえば、同じ引数で 2 回走らせて出力を比べる試験を `tests/` に足す）。

（出典: `docs/final_evaluation_procedure.md:443-450`、`docs/decisions.md:3910-3912`（D70 の 4。K̂ の推定））

#### 見落としと不の中身の抜き取りに要ること

見落としと不の中身の道具も、同じ 4 つの性質が要ります。
違うのは、何を対象にし、どう選ぶかです。

| 道具 | 対象 | 選び方 | seed | 出力に残す件数 |
|---|---|---|---|---|
| 見落とし | D1 か D2 を**明示**し（`D_kind.explicit`）、その宣言への矛が 1 件も無いユニット | 対象を持つ木から 200 木、各木 1 ユニット | ② | 対象のユニットの総数、木の数 |
| 不の中身 | D1・D2 のそれぞれで、不の組 | 不の組を持つ木から 50 木、各木 1 組 | ③ | 宣言ごと・理由ごとの不の総数 |

表の読み方: 1 行目は「見落としの道具は、D1 か D2 を明示していて、その宣言に対する矛が 1 件も出ていないユニットを対象にする。対象を持つ木を seed ② で 200 木選び、各木から 1 ユニットを選ぶ。対象のユニットの総数と木の数を出力に残す」と読みます。

注意が 2 つあります。

- **見落としの対象に、打ち切りの印のあるユニットも含めます**（D70 の 2）。出力には `truncated` の印を付けておき、判定で打ち切りが原因と分かったものを「不明（打ち切り）」に分けられるようにします。除いてしまうと、解析器が苦手な大きいツールが抜き取りから消え、見落としの率を低く見せる向き（誤 clear を隠す向き）に偏ります。
- **「不の組」は、その宣言で矛の印が無く、不の印がある組**です。`contradiction_by_decl.py` は、1 つの組に矛と不の両方の理由があれば「矛」と数えます。不の中身の道具も同じ数え方にしないと、件数が `contradiction_by_decl.py` の「不」の列と合わなくなります。

（出典: `docs/final_evaluation_procedure.md:451-458`、`docs/decisions.md:3846-3848`（D70 の 2）、`scripts/contradiction_by_decl.py:60-78`（矛が優先する数え方）、`scripts/v3_miss_sample.py:47-55`（対象の決め方と `truncated`））

#### なぜそうするのか

- **再現できるように**です。抜き取りが再現できれば、第三者が同じ対象を選び直して、判定を確かめられます。2 人目の判定者がいないこの研究では、これが信頼性の支えの 1 つです（D67 の 4）。
- **分母を正しく出すために**です。選ばなかった分の件数が無いと、K̂ も「宣言ごとの矛の総数」も出せません。
- **選び方を結果から切り離すために**です。seed と規則を先に決め、並べ方を固定すれば、「どの組が選ばれるか」に人の判断が入りません。

#### よくある誤解・つまずき

- **誤解 1: 「乱数で選ぶのだから、並べ方はどうでもよい」**。いいえ。乱数は「何番目」を決めるだけです。並べ方が変われば、同じ seed でも選ばれるものが変わります。
- **誤解 2: 「seed が同じなら、道具を少し直しても同じ対象が選ばれる」**。いいえ。作例では 1 つの乱数の発生器を D1→D2→D3→D4 の順に使い回しています。D1 の処理で乱数を 1 回多く引くように直すと、D2 以降で選ばれるものが全部変わります。だから道具は v4 で固め、最終評価のデータの前にコミットして、その後は変えません。
- **誤解 3: 「選んだものだけ出力すればよい」**。いいえ。選ばなかった分の件数は、分母と参考の件数に要ります。
- **つまずき 4: 見落としの対象から打ち切りを除く**。除くと見落としの率を低く見せる向きに偏ります。含めて印を付けます（D70 の 2）。
- **つまずき 5: 不の組に「矛でもある組」を混ぜる**。矛と不の両方の理由を持つ組は、`contradiction_by_decl.py` では矛です。不の中身の対象には入れません。
- **つまずき 6: 不の組を `contradictions.json` から拾おうとする**。手順書の 6.3 節は、不の抜き取りの対象を「`contradictions.json` の不の行」と書いています。けれども `contradictions.json` は、判定が `CONTRADICTION` の行だけを (ユニット, site, kind) ごとに畳んだ表です（[第 18 章](ch18.md)）。不は manifest の行の注記 `contradiction_unknown:<宣言>:<理由>` にしか現れません。v4 の manifest を数えると、不の注記を持つ行は 3,763 で、そのどれも判定に `CONTRADICTION` を含んでいませんでした（本書の計算）。だから、不の抜き取りの道具は、`contradiction_by_decl.py` の `load_reasons` と同じように **manifest を読みます**。手順書のこの一文は、そのまま写すと道具が不の組を 1 つも見つけられない書き方です。

（出典: `docs/final_evaluation_procedure.md:456`（「`contradictions.json` の不の行」）、`scripts/scan_v2.py:59-61`（`CONTRADICTION` の行だけを畳む）、`scripts/contradiction_by_decl.py:40-57`（manifest の注記を読む））

#### 手作業ではどう使うか

道具を作ったら、次の 3 つを手で確かめます。

1. 宣言ごとの `n_pairs` が、`contradiction_by_decl.py` の表の「矛」の列と同じか（v4 なら D1 323・D2 155・D3 0・D4 3）。
2. 宣言ごとの `n_trees` が、同じ表の「矛の木」の列と同じか（v4 なら 17・14・0・1）。
3. 同じ引数で 2 回走らせた出力が、1 バイトも違わないか（たとえば `cmp` で比べる）。

この 3 つは、次の 47.5 節の空回しでそのまま使います。

#### この節のまとめ

- 抜き取りの道具には、組の鍵・並べ方の固定・選ばなかった分の件数・同じ入力と seed で同じ出力、の 4 つが要る。
- 見落としは打ち切りの印のあるユニットも含める。不の組は「矛の印が無く不の印がある組」。
- 道具を少し直すだけで選ばれるものは変わる。だから v4 で固めてコミットし、その後は変えない。

### 47.4 段階 2 (3) — 判定表の雛形、1 件を出す道具、`.gitignore`

#### 一言で言うと

抜き取りの出力から、**判定の欄が空の表（CSV）**を作る道具と、1 組について解析器が見たものを 1 画面に出す道具（`show_target.py`）を作ります。
そして、最終評価の記録を git で追い、大きな manifest は追わないように、`.gitignore` に規則を 2 行足します。

#### たとえ話 — 答案用紙を先に印刷しておく

試験の前に、答案用紙を印刷しておきます。
用紙には、受験番号・問題番号が**先に刷ってあり**、答えを書く欄は空です。
採点する人は、空の欄を埋めるだけです。
こうしておけば、「どの問題に答えるか」を答える人が選び直すことはできません。

判定表の雛形も同じです。
どの組を判定するか（木・ユニット・site・kind・宣言）は、抜き取りの出力から**先に刷ってあり**、判定の欄（正 / 誤 / 不明、根拠、分数など）が空です。

#### 小さな例 — 矛の判定表の 1 行（CSV）

v4 の M18 の組を例に、矛の判定表の見出しと 1 行を書くと、次のようになります（本書の作例。判定の欄は空）。

```text
order,id,decl,tree,unit,unit_relpath,unit_lineno,site,kind,reasons,verdict,condition_type,error_class,write_target,unknown_reason,evidence,note,minutes,ai_used,ai_model,ai_log
7,M18,D1,v4-ryxmarcus__mcp-aws,generate_cost_report_wrapper,src/aws-pricing-mcp-server/awslabs/aws_pricing_mcp_server/server.py,703,builtins.open,FS_WRITE,fs_write,,,,,,,,,,,
```

#### 一歩ずつの説明 — 欄を 2 つに分ける

見出しの欄は、**抜き取りの出力から写す欄**と、**判定者が書く欄**の 2 つに分かれます。

| 種類 | 欄 | どこから来るか |
|---|---|---|
| 写す欄 | `order` | 判定の順序（47.11 節で並べ替えた後の番号） |
| 写す欄 | `id`・`decl`・`tree`・`unit`・`unit_relpath`・`unit_lineno`・`site`・`kind`・`reasons` | 抜き取りの出力（組の鍵と、解析器の理由） |
| 書く欄 | `verdict`・`condition_type` | 判定の結果と、正のときの条件の種類（第 48〜50 章） |
| 書く欄 | `error_class`・`write_target`・`unknown_reason` | 誤の原因・書き込み先の種類・不明の理由（第 51・52 章） |
| 書く欄 | `evidence`・`note`・`minutes` | 根拠のファイルと行、迷った点、かかった分数（AI に聞いた時間を含む） |
| 書く欄 | `ai_used`・`ai_model`・`ai_log` | AI を使ったか（`なし` / `あり`）、使ったならモデル名と版・使った画面、やりとりのログの置き場所（D70 の 3。2026-10-02 に足された欄） |

表の読み方: 1 行目は「`order` の欄は、判定する順番の番号で、47.11 節で順序を並べ替えた後に振る」と読みます。
書く欄のうち、どれを埋めるかは判定ごとに決まります（D83。2026-10-06 に欄を減らした）。
正は `verdict`・`evidence`・`write_target`・`condition_type`、誤は `verdict`・`evidence`・`error_class`、不明は `verdict`・`evidence`・`unknown_reason` です。
どの判定でも `minutes`・`ai_used`（`あり` なら `ai_model`・`ai_log`）を書き、`note` は迷ったときだけ書きます。
前の形にあった `reachable`・`violates`・`condition` の欄は、矛の表から無くしました。到達するか・反するかは `verdict` と `error_class` から分かり、条件の中身は `evidence` の文に書きます。
書く欄の並びは、手引きの下書きの手順 H の表（`verdict` から `ai_log` まで）と同じにしてあります。手順書の 6.4 節も、AI の利用の欄は手引きの下書きの手順 H・18.4・18A.3 にある、と書いています。

見落としの判定表と不の中身の判定表は、書く欄が少し違います。
見落としは `outcome`・`cause`・`write_target`・`condition_type`・`condition`・`depth`・`evidence`・`ai_found`・`note`・`minutes`・`ai_used`・`ai_model`・`ai_log`、不の中身は `outcome`・`reachable`・`violates`・`write_target`・`condition_type`・`condition`・`unknown_reason`・`evidence`・`note`・`minutes`・`ai_used`・`ai_model`・`ai_log` です（手引きの下書きの 18.4 節と 18A.3 節）。この 2 つの表は D83 で変わっていません（不の中身の表には `reachable`・`violates` が残ります）。`ai_found` は、見落としの判定を自分で終えた後に AI に点検させて、新しく見つかった動作を書く欄です。
欄の意味は[第 52 章](ch52.md)で見ます。

CSV を作るときの実際のつまずきが 3 つあります。

1. **文字コード**。Windows の表計算ソフトは、印の無い UTF-8 の CSV を別の文字コードとして開き、日本語が化けることがあります。UTF-8 の先頭に印（BOM）を付けて書く（Python なら `encoding="utf-8-sig"`）と避けられます。集計のスクリプトで読むときも `utf-8-sig` で読みます。
2. **カンマと改行**。`evidence` の欄には、カンマや改行が入ります。手で文字列をつなげて CSV を作ると、列がずれます。Python の `csv` モジュールで書けば、必要なところに引用符を付けてくれます。
3. **見落としの表の「解析器の欄」**。見落としは、**解析器の出力を見る前に判定する**決まりです（D69 の 3）。ところが、見落としの抜き取りの出力には、効果の数や打ち切りの印など、解析器の出力から来る欄が入りえます（v3 の道具 `v3_miss_sample.py` は `n_effects` と `truncated` を出します）。判定表のすぐ見えるところにこれらがあると、読む前に先入観が入ります。**本書の提案**として、これらの欄は判定表の右端に寄せるか、別のファイルに分けておき、手引きの 18.2 節の手順 4（解析器の出力を見る）に来てから開くとよいでしょう。この扱いは手順書に書かれていないので、採るなら道具を作るときに決め、事前登録か道具の説明に書いておきます。

（出典: `docs/final_evaluation_procedure.md:460-464`（6.4）、`docs/drafts/final_judging_guide_draft.md:191-238`（手順 H の欄。D83）、`:493-505`（18.4）、`:535-545`（18A.3）、`:454-481`（18.2 の順序）、`scripts/v3_miss_sample.py:52-55`（`n_effects` と `truncated`））

#### 1 件を出す道具 `show_target.py`

判定の手順 B（[第 48 章](ch48.md)）で、対象の組について解析器が何を見たか（道筋・slot の主体・注記）を 1 画面で見るための道具です。
手順書の 6.5 節に、動作を確かめた 20 行あまりの最小の形が載っています。
この道具の中身と、出力の各行が manifest のどの欄から来るかは、[第 19 章](ch19.md)の 19.10 節で 1 行ずつ見ました。

ここで思い出してほしいのは、[第 19 章](ch19.md)で見た**3 つの癖**です。

2. `D_kind.explicit` しか出さないので、D3・D4 の宣言が見えない。
3. `notes` の欄が無い行で止まる。

この癖を直すなら、**段階 2 のうちに**直します。

ユニットは relpath と行で探します（qualname だけでは、別のファイルにある同じ名前のツールを取り違える。D64 の U50）。

（出典: `docs/final_evaluation_procedure.md:466-507`（6.5）、本書の[第 19 章](ch19.md) 19.10 節）

#### `.gitignore` に足す行

手順書の 6.6 節は、既存の `evidence/*` の下に、次の 3 行（コメント 1 行と規則 2 行）を足すよう書いています。

```gitignore
# - 最終評価（docs/final_evaluation_procedure.md）
!evidence/population_final/
evidence/scan_v2_*/final-*.json
```

1 行ずつ読みます。

- 1 行目: コメントです（`#` で始まる行は無視される）。
- 2 行目: `!` は「除外の例外」です。`evidence/population_final/`（標本・spec・抜き取りの出力・判定の記録の置き場）を**追跡する**ようにします。
- 3 行目: 走査の出力のディレクトリにある、`final-` で始まる木ごとの manifest を**追跡しない**ようにします。manifest は 1 木で十数 MB になりうるからです。`summary.json` と `contradictions.json` は `final-` で始まらないので、既存の `!evidence/scan_v2_*/` の行によって追跡されます。

本書の試験で、repo の今の `.gitignore` の末尾にこの 3 行を足した写しを、空の git の作業場に置いて確かめました。

| ファイル | 結果 |
|---|---|
| `evidence/population_final/final_judge_targets.json` | 追跡される |
| `evidence/scan_v2_final_run1/summary.json` | 追跡される |
| `evidence/scan_v2_final_run1/contradictions.json` | 追跡される |
| `evidence/scan_v2_final_run1/final-alice__notes.json`（manifest） | 追跡されない（足した 3 行目による） |
| `evidence/scan_v2_final_run1/progress.jsonl` | 追跡されない（既存の行による） |

同じ写しで、5 行目の `evidence/*` を `evidence/` に書き換えると、`evidence/population_final/final_judge_targets.json` も `evidence/scan_v2_final_run1/summary.json` も**追跡されなくなりました**（`!` の例外が効かない）。
git は、親のディレクトリごと除外されたものの下を、例外で拾い直せないからです。
CLAUDE.md の「`.gitignore` で親ディレクトリごと除外すると `!` の例外が効かない。`evidence/*` と書く」は、これのことです。

（出典: `docs/final_evaluation_procedure.md:509-520`（6.6）、`.gitignore:1-30`（既存の行）、`CLAUDE.md` の「よく踏む落とし穴」の最後）

#### なぜそうするのか

- **判定表を雛形にするのは、選ぶ自由をなくすため**です。どの組を判定するかが先に刷ってあれば、判定の途中で対象を差し替えられません（手順書の 10 節「判定の途中で対象を差し替えない」）。
- **CSV にするのは、手で書きやすく、機械でも読めるため**です。表計算ソフトで開いて書き、最後に集計のスクリプトが読みます。
- **`population_final/` を追跡するのは、監査できるようにするため**です。抜き取りの出力と判定の記録がコミットに残れば、「いつ、何を選び、どう判定したか」を第三者が確かめられます。

#### よくある誤解・つまずき

- **誤解 1: 「判定表は判定しながら作ればよい」**。いいえ。判定表は段階 6 で、判定を始める**前に**コミットします。
- **誤解 2: 「manifest も追跡したほうが安全だ」**。manifest は大きく、git で追うと repo が重くなります。v4 の 88 木の走査の出力のディレクトリは、本書の計算（`du -sh`）で 170 MB でした。約 3,000 木なら、同じ割合で数 GB になりえます（本書の粗い見込み。測っていない）。manifest は手元に残し、`summary.json` と `contradictions.json` だけを追跡します。
- **つまずき 3: `evidence/` と書いてしまう**。上の試験のとおり、`!` の例外が効かず、記録が黙って追跡されなくなります。`git status` に出てこないので、気づきにくい失敗です。足した後で `git check-ignore -v <ファイル>` を使うと、どの行で除外されたかが分かります。
- **つまずき 4: `show_target.py` の癖を判定の途中で直す**。直すなら段階 2 のうちに直します。

#### 手作業ではどう使うか

- 判定表の雛形を作ったら、v4 の抜き取りの出力から一度作ってみて、表計算ソフトで開き、日本語が化けないか、列がずれないかを目で確かめます。
- `.gitignore` に規則を足したら、`evidence/population_final/` に試しのファイルを置き、`git status` に出てくることを確かめます。
- `show_target.py` を v4 の木で走らせ、[第 19 章](ch19.md)の 3 つの癖が出ないか（直したなら直っているか）を確かめます。

#### この節のまとめ

- 判定表は、抜き取りの出力から写す欄と、判定者が書く欄に分かれる。CSV は `utf-8-sig` と `csv` モジュールで書く。見落としの表では、解析器の出力から来る欄を判定の後半まで見ないよう分けるとよい（本書の提案）。
- `show_target.py` の癖は段階 2 のうちに直す。
- `.gitignore` は既存の `evidence/*` の下に規則を 2 行足す。`evidence/` と書くと `!` が効かない。

### 47.5 段階 2 (4) — v4 のデータで空回しする

#### 一言で言うと

作った道具を v4 のデータで走らせ、**3 つの数**が v4 の記録と一致するかを確かめます。
(1) 宣言ごとの矛の総数 D1 323 / D2 155 / D3 0 / D4 3、(2) 宣言ごとの矛の木の数 17 / 14 / 0 / 1、(3) 集計の道具に v4 の判定を読ませたときの件数の精度 46 / 60。
あわせて、2 回走らせて出力が同じことを確かめます。

#### たとえ話 — 重さの分かったおもりで、はかりを確かめる

新しいはかりを買ったら、まず重さの分かったおもり（1 kg のおもり）を載せます。
針が 1 kg を指せば、はかりは正しいと分かります。
指さなければ、本番の材料を量る前に直します。

v4 は「重さの分かったおもり」です。
v4 の矛の総数や判定の結果は、すでに `docs/population_v4.md` に記録されています。
新しい道具に v4 を通して、記録と同じ数が出れば、道具の数え方が正しいと分かります。
しかも v4 は最終評価に使わないデータなので、道具を何度直してもかまいません。

#### 小さな例 — 確かめる 3 つの数と、作例の出力

| 確かめる数 | v4 の記録 | どの道具で出すか |
|---|---|---|
| (1) 宣言ごとの矛の総数 | D1 323 / D2 155 / D3 0 / D4 3 | 矛の抜き取りの道具（選ばなかった分の件数） |
| (2) 宣言ごとの矛の木の数 | D1 17 / D2 14 / D3 0 / D4 1 | 同上 |
| (3) 件数の精度（D1・D2 計） | 46 / 60（76.7%） | 木の単位の集計の道具に `evidence/population_v4/v4_judgments.json` を読ませる |

表の読み方: 1 行目は「矛の抜き取りの道具が出す『選ばなかった分を含む矛の総数』が、v4 の記録の D1 323・D2 155・D3 0・D4 3 と同じになるかを確かめる」と読みます。

47.3 節の作例を v4 に走らせた出力では、(1) の `n_pairs` が 323 / 155 / 0 / 3、(2) の `n_trees` が 17 / 14 / 0 / 1 で、どちらも記録と一致しました（本書の試験）。

さらに、v4 では**seed に依らずに決まる数**があります（本書の計算）。

| 抜き取り | v4 での数 | なぜ seed に依らないか |

| 矛（1 木 3 件まで） | D1 41 / D2 27 / D3 0 / D4 3 | どの宣言も矛の木が 200 以下なので全木が選ばれ、各木の件数は min(3, その木の組の数) で決まる |

学生の道具がこれと違う数を出したら、数え方のどこかが違います。
選ばれる組の**中身**は seed で変わりますが、**数**は変わりません。

**(3) 件数の精度 46 / 60** の確かめ方も見ておきます。
`evidence/population_v4/v4_judgments.json` には、`v2` と `v3` という 2 つの欄があります。
これは**母集団の v2・v3 ではなく、問いの V2（精度）と V3（見落とし）**です。
`v2` の欄に矛の判定が 63 件（D1 42・D2 18・D4 3）、`v3` の欄に見落としの判定が 30 件あります。
D1・D2 の 60 件のうち `verdict` が「正」のものが 46 件です（本書の計算でも 46 / 60 になりました）。
作った集計の道具にこのファイルを読ませ、件数の精度が 46 / 60 になれば、件数の数え方は正しいと分かります。

ただし、**木の単位の値は v4 と比べられません**。
v4 の抜き取りは「D1・D2 を合わせて一様に 60 件」で、最終評価の「宣言ごとに 1 木 3 件まで」とは規則が違うからです。
比べられるのは、件数の数え方だけです。

#### なぜそうするのか

- **道具の誤りを、評価のデータで見つけないため**です。評価のデータで見つけて直すと、結果を見て道具を変えたことになります（手順書の 6.7 節）。
- **答えの分かった問題で試すため**です。v4 には記録された数があるので、道具の出す数が正しいかを判断できます。新しいデータでは、正しい数が分からないので試せません。
- **再現性を確かめるため**です。2 回走らせて同じ出力になることは、47.3 節の性質 (4) そのものです。

#### よくある誤解・つまずき

- **誤解 1: 「v4 は見たデータだから、道具の試験にも使ってはいけない」**。いいえ。最終評価に使わないのは、本記録者が結果を見たからです（D66 の 3）。道具の試験と判定の練習には、むしろ使うべきデータです。
- **誤解 2: 「木の単位の値も v4 と合うはず」**。いいえ。抜き取りの規則が違うので比べられません。比べるのは、総数・木の数・件数の精度の 3 つです。
- **つまずき 3: 走査し直すときに label を `v4_run1` にする**。追跡している v4 の `summary.json` と `contradictions.json` が上書きされます。必ず別の label にします。
- **つまずき 4: `v4_judgments.json` の `v2`・`v3` を母集団の名前と読む**。問いの V2・V3 です。
- **つまずき 5: 一致しなかったときに、記録のほうを疑う**。まず道具を疑います。記録は v4 のときにコミットされた数で、道具は今作ったばかりです。それでも記録のほうが誤っていると分かったら、黙って片方に合わせず、`docs/open_questions.md` に書きます（CLAUDE.md の規則 4）。

#### 手作業ではどう使うか

空回しの結果を、次の形でメモに残し、道具と一緒にコミットします。

```text
空回し（v4、2026-MM-DD）
- 矛の総数   D1 323 / D2 155 / D3 0 / D4 3   記録と一致: はい
- 矛の木     D1 17 / D2 14 / D3 0 / D4 1     記録と一致: はい
- 選ばれた組 D1 41 / D2 27 / D3 0 / D4 3     （seed に依らない数。本書の計算と一致: はい）
- 件数の精度 46 / 60                          記録と一致: はい
- 2 回走らせた出力                             同じ: はい
```

この形は本書の作例です。
大事なのは、「何と何を比べ、一致したか」を、後から第三者が読める形で残すことです。

#### この節のまとめ

- 空回しで一致を確かめる数は 3 つ: 矛の総数（323 / 155 / 0 / 3）、矛の木（17 / 14 / 0 / 1）、件数の精度（46 / 60）。2 回走らせて同じ出力になることも確かめる。
- v4 では、選ばれる組の数（41 / 27 / 0 / 3）などが seed に依らずに決まる（本書の計算）。道具の確かめに使える。
- manifest が手元に無ければ、v4 を取り直して**別の label** で走査する。`v4_run1` にすると記録が上書きされる。

### 47.6 段階 2 (5) — 判定の練習

#### 一言で言うと

最終評価のデータに触れる前に、v4 の判定済みの組を 10 件ほど、**v4 の判定を見ずに**自分で判定し、後で v4 の判定と比べます。
食い違ったら、それを**手引きの穴**として扱い、手引きを直します。
v4 の判定は本記録者（AI）が付けたもので、**正解ではありません**。
あわせて、1 件にかかった分数を測ります。

#### たとえ話 — 先輩の答えが付いた練習問題

本番の試験の前に、先輩が解いた過去問で練習するとします。
先輩の答えは参考になりますが、先輩も間違えることがあります。
自分の答えが先輩と違ったとき、「先輩が正しいはず」と自分の答えを書き換えるのは危険です。
先輩の間違いを、自分の答えに写してしまうからです。

正しいやり方は、食い違った問題で「**採点基準（手引き）を読むと、どちらが正しいと言えるか**」を考えることです。
基準を読んでも決まらないなら、それは基準の書き方に穴があるということです。
穴は、本番の前に基準を書き直して埋めます。

この研究の「先輩」は本記録者（AI）で、「採点基準」は判定の手引きです。

- **手引きの穴を、データを見る前に埋めるため**です。最終評価の判定の途中で穴が見つかると、その件は「不明（手引きで決まらない）」にし、§5 に逸脱として記録するしかありません（手引きの 22 節）。練習で見つければ、封の前の手引きを直すだけで済みます。
- **AI の解釈を正解に入れないため**です。`docs/llm_judgment_survey.md` は、「練習 6.8 は、AI の v4 判定を答え合わせに使う手順。学生の判定を AI に合わせると、正解に AI の解釈が入る。**食い違いは手引きの穴として扱い、AI を正しいとみなさない**」と書いています。最終評価の判定で、AI に判定させず、AI の答えをそのまま記録しない（D70 の 3）のと同じ考え方です。
- **日程を測るため**です。D69 の 6 は、判定の時間（約 170〜380 時間）を**測っていない見込み**とし、「練習で 1 件の時間を測り、段階 6 の前に件数を確かめる」と決めています。

（出典: `docs/llm_judgment_survey.md:163-164`、`docs/decisions.md:3833-3834`（D69 の 6）、`docs/drafts/final_judging_guide_draft.md:701-709`（22 節））

#### よくある誤解・つまずき

- **誤解 1: 「v4 の判定は答えだから、合わせればよい」**。いいえ。v4 の判定は本記録者（AI）のもので、正解ではありません。食い違ったら、手引きに照らして考えます。
- **誤解 2: 「練習で手引きを直すと、規則を後から変えたことになる」**。いいえ。練習は最終評価のデータに触れる前（段階 2）です。直してコミットし直すのは、手順書が求めているやり方です。
- **つまずき 3: v4 の判定を先に見てしまう**。一度見ると、自分の判定が引っぱられます。表の列を隠してから始めます。
- **つまずき 4: AI に v4 の判定や手引きを見せる**。見せません。v4 の判定は解析器の答えと同じく「渡さないもの」で、この repo の文書を読み込ませた会話は使いません（D70 の 3 の条件 2・5）。AI に渡すのは、コードと事実の問いだけです。
- **つまずき 5: 時間を測り忘れる**。分数が無いと、段階 6 で日程に合うかを判断できません。1 件ごとに、始めた時刻と終えた時刻を書くだけで十分です。
- **つまずき 6: 規則の変更による食い違いを、手引きの穴と取り違える**。E00 と R04 のように、v4 の後で規則が変わった件は、穴ではありません。

#### 手作業ではどう使うか

練習の後に、次の 3 つを残します。

1. 練習の記録の表（上の形）。自分の判定・根拠・分数が入ったもの。
2. 見つけた手引きの穴と、直した箇所の一覧（直した手引きのコミットと一緒に）。
3. 1 件の平均の分数（矛・見落とし・不の中身で分ける）。47.11 節の計算に使います。

手順書は「練習で判定がぶれなくなってから段階 3 に進む」と書いています。
ぶれなくなった、とは「同じ形の組に、手引きの同じ規則を当てて、同じ結論が出せる」ことです。

#### この節のまとめ

- v4 の判定済みの組を 10 件ほど、v4 の判定を見ずに判定し、後で比べる。食い違いは**手引きの穴**として扱い、AI（本記録者）の判定を正解とみなさない。
- v4 の判定には、D67〜D70 より前の規則で付けたものがある（`severity`、E00、R04）。規則の変更による食い違いは穴ではない。
- 1 件の分数を測る。段階 6 で件数が日程に合うかを決める材料になる。
- 予備調査（D74）の候補（矛 75 組・見落とし 10 件）でも練習する（D75 の 5）。答えは無いので、手引きの曖昧な点と 1 件の時間を見る。主の深さは練習の前に 4 と決めたので、練習の結果で変えない。

### 47.7 段階 3 — 抽出と pin

#### 一言で言うと

列挙の生データから、v2・v3・v4 を除いた**残りを全部**選び、1 件ずつ `git ls-remote` で今の版の SHA を取って**pin** します。
v2・v3・v4 との重なりが 0 であることを確かめ、**pin をコミットしてから**取得に進みます。

#### たとえ話 — 本の「版と刷」を書き留める

図書館で本を何冊も借りて調べものをするとします。
同じ書名の本でも、版や刷が違うと、ページの中身が少し違うことがあります。
後で誰かが同じ調べものをやり直せるように、借りた本の「第何版・第何刷」を書き留めておきます。

GitHub の repo も、毎日のように中身が変わります。
「repo の名前」だけでは、いつの中身を解析したかが分かりません。
そこで、選んだ瞬間の版を、commit の SHA（40 桁の 16 進数の名前）で書き留めます。
これが pin です。
pin があれば、後で何度取り直しても、同じ中身が得られます。

#### 小さな例 — 手順書の §7 のコマンド（D73 の 5 の後）

手順書の §7 のコマンドは、今は次のとおりです（2026-10-03 の D73 の 5 で直されました）。

```bash
.venv/bin/python scripts/sample_population_v2.py --all \
    --exclude docs/corpus_sample_v2.json \
    --exclude docs/corpus_sample_v3.json \
    --exclude docs/corpus_sample_v4.json \
    --prefix final --out docs/corpus_sample_final.json
```

前の文面は、`--n <0-1 で決めた抽出数> --seed <抽出用の seed>` でした。
これは D69（全部を走査する）と D70 の 7（抽出用の seed は要らない）より**前**に書かれたものです。
D69 の後、D73 の前は、手順書の 0-1 が「`--n` に母集団より大きな値（`--n 100000` など）を渡して、全部を返させる」と書いていました。

`--all` のときに、スクリプトが何をするかは、次の行で分かります。

```python
42  def choose(pop: list[str], n: int | None, seed: int | None, take_all: bool) -> list[str]:
43      """母集団（除外の後）から対象を選ぶ。`take_all` なら全部（抽出しない）。"""
44      if take_all:
45          return sorted(pop)
46      rng = random.Random(seed)
```

### 47.8 段階 4 — 取得、取得後の条件、中身の重複の除去

#### 一言で言うと

pin の解決できたものだけを並べた取得用の spec を作り、pin の SHA どおりに取得します。
取得した木のうち、MCP サーバでないもの（宣言ファイルが `mcp` / `fastmcp` を import しない、など）を件数つきで除き、さらに**中身の重複**を D70 の 6 の規則で除きます。
残った木を走査の標本にし、**件数の流れ**を書いてコミットしてから、走査に進みます。

#### たとえ話 — 届いた荷物を検品する

通販でたくさんの荷物を注文したとします。
届いたら、次の順に検品します。

1. **伝票と中身が合っているか**（注文した版が届いたか）。違う版なら受け取らず、「届かなかった」と記録します。
2. **注文した品物の種類か**（MCP サーバか）。違う種類なら、件数を数えて脇に置きます。
3. **同じ中身の荷物が 2 つ来ていないか**（重複）。箱のラベルが違っても、中身が同じなら 1 つだけを数えます。前に受け取って使ったことのある品物と同じなら、それも除きます。

そして、「何個注文し、何個届き、何個を何の理由で脇に置き、何個が残ったか」を帳面に書きます。
これが件数の流れです。

#### 取得と、取得後の条件

取得と取得後の条件のコマンドは、次の 2 つです。

**取得**（1 行目）では、`fetch_corpus.py` が 1 つの repo ごとに次のことをします。

1. repo を `corpus/_cache/` の下に 1 回だけ部分クローンします（ファイルの中身は必要になったときに取る）。
2. pin の SHA を `git rev-parse` で確かめ、その SHA で作業木（worktree）を `corpus/<木の名前>/` に作ります。
3. sparse checkout で、`.py`・`.toml`・`.txt`・`.lock`・`.json`・`.cfg` のファイルだけを取り出します。
4. 取り出した後の HEAD が pin の SHA と一致することを確かめます。一致しなければ失敗として記録します。
5. 失敗は `docs/fetch_failures.md` に、取得できた木は `docs/frame.csv` に書きます。

CLAUDE.md の落とし穴にあるとおり、**浅い fetch は黙って既定のブランチに落ちる**ことがあります。
4 の確かめは、それを防ぐためのものです。
また、**中断した worktree は HEAD が一致したまま中身が空**のことがあります。
`fetch_corpus.py` は、すでにある作業木を使う前に、sparse のパターンが設定済みで作業木が index と一致していること（`_checkout_complete`）も確かめ、満たさなければ消して取り直します。
取得が途中で止まったら、もう一度同じコマンドを走らせれば、空の作業木は取り直されます。

| `declaring_file_missing` | 標本の `declaring_paths` のどれにも宣言（`annotations=`）が見つからない | 0 |
| `declares_but_not_mcp_import` | 宣言はあるが、そのファイルが `mcp` / `fastmcp` を import しない | 11 |
| `mcp_server` | 宣言があり、そのファイルが `mcp` / `fastmcp` を import する → **走査する** | 88 |

1. 取得した木ごとに、**ツールの定義（入口の規則に当たるユニット）を含む `.py` ファイル**の sha256 を取る。
2. **v2〜v4 との重複**: そのファイルの 1 つでも、v2〜v4 の木のどれかのファイルと一致した木は除く。v2・v3 の中身は手元に無い前提で、`docs/corpus_sample_v{2,3,4}.json` の pin から取り直して**ハッシュだけ**を残す（中身は保存しなくてよい）。
3. **今回の中の重複**: ツールの定義を含むファイルが一致する木どうしは、**repo 名（小文字）の辞書順で最初の 1 木だけを残し**、残りを除く。
4. 除いた木の数と、どの木と一致したかを記録する。全部を走査する設計（D69）なので、**補充はしない**。
5. この規則は**走査の前**（段階 4 の取得後の条件）に当てる。走査の結果を見てから除く木を選ばない。

#### なぜそうするのか

- **pin の SHA と HEAD の一致を確かめるのは、解析した中身を特定できるようにするため**です。浅い fetch が黙って既定のブランチに落ちると、記録した pin と違う中身を解析したことになり、誰も同じ結果を再現できません。
- **MCP サーバでない木を件数つきで除くのは、黙って落とさないため**です（CLAUDE.md の規則 4）。除いた数は論文の「標本」の記述に入ります。
- **重複を除くのは、同じコードを 2 回数えないため**です。フォーク（他人の repo を複製したもの）や、他のプロジェクトのコードを同梱した repo は、名前が違っても中身が同じことがあります。同じコードを 2 回数えると、木の単位の数字（D67 の 3）が水増しされます。
- **v2〜v4 との重複を除くのは、v2〜v4 が本記録者の見たデータだから**です（D66 の 3）。名前で除いても、中身が同じ木が別の名前で入ってくれば、見たデータが評価に紛れ込みます。
- **走査の前に当て、補充しないのは、結果を見て除く木を選んだと疑われないため**です。全部を走査する設計なので、補充する「残り」もありません。

（出典: `docs/decisions.md:3921`（D70 の 6 の理由）、`docs/final_evaluation_procedure.md:206-209`）

#### よくある誤解・つまずき

- **誤解 1: 「手順書の 8.1 節のコードは、そのまま写せばよい」**。`if t.get("ref")` では `"UNRESOLVED"` が除かれません。`t["ref"] != "UNRESOLVED"` で除きます。除かないと、取得のスクリプトが `rev-parse` で失敗し、「pin の解決できなかったもの」が「取得の失敗」として数えられて、件数の流れの分類が混ざります。

- **誤解 3: 「重複で減った分は、別の repo で補う」**。いいえ。補充しません（規則 4）。全部を走査する設計です。
- **誤解 4: 「v3 でも 100 木中 8 木にこれまでのデータと同一のファイルがあった」**。第 3 版の 2442 行はそう書いていましたが、原典（`docs/population_v3.md`・`docs/decisions.md`・`docs/open_questions.md`）で確かめられません（**未検証**）。手順書の 0-7 も同じ数を書いていますが、その出典は第 3 版の[第 38 章](ch38.md)そのものです。重複の除去をする理由は、この数ではなく、D70 の 6 の理由（水増しと、見たデータの紛れ込み）です。
- **つまずき 5: 前の版の手順書の「MCP サーバ 252 木」を見込みだと思う**。古い例でした（今は【】の形に直されている）。見込みは約 3,000 木です。
- **つまずき 6: `docs/fetch_failures.md` が積み上がると思う**。`fetch_corpus.py` は、走らせるたびにこのファイルを**書き直します**（前の失敗の記録は消える）。数百 repo ずつ取得するなら、1 回ごとに別の名前で写しておきます（47.10 節）。`docs/frame.csv` のほうは、前の行を残したまま足していきます。

（出典: `scripts/fetch_corpus.py:129-134`（`rev-parse` で解決できないと失敗）、`:210-257`（`frame.csv` は足し、`fetch_failures.md` は書き直す）、`docs/textbook_v3.md:2442`（第 3 版の記述）、`docs/final_evaluation_procedure.md:208`（0-7 の同じ数））

### 47.9 段階 5 — 凍結の確認と走査（1 回だけ）

#### 一言で言うと

走らせる前に、凍結のタグがあること、`authgap/` が凍結の版と 1 文字も違わないこと、未コミットの変更が無いことを確かめます。
そのうえで `--require-fingerprint` を付けて、**1 回だけ**走査します。
走らせたマシンと日時を記録し、走査の後に `summary.json` を表に沿って確かめてから、`summary.json` と `contradictions.json` をコミットします。

#### たとえ話 — 公式記録の前に、ストップウォッチを検める

陸上競技の公式記録を取る前に、係の人はストップウォッチを検めます。
検定済みの印があるか、製造番号が登録と合うか。
合わなければ、そのストップウォッチでは公式記録を取りません。
そして、走った日時・天候・風速を記録に添えます。
風が強い日の記録は、条件が違うからです。

走査も同じです。
「検定済みの印」が凍結のタグ、「製造番号」が指紋（実装のハッシュ）です。
「天候・風速」がマシンと日時で、木ごとの解析の時間がマシンの速さで変わるので、記録に添えます。

#### 小さな例 — 走らせる前の 3 つのコマンドと、走査のコマンド

```bash

git diff analyzer-freeze-3 -- authgap/          # 出力が空であること（1 行でも出たら止まる）
git status --porcelain -- authgap/              # 未コミットの変更が無いこと
```

この本を書いている時点（2026-10-01）の repo で走らせると、1 行目は `analyzer-freeze-1`・`analyzer-freeze-2`・`analyzer-freeze-3` の 3 つを出し、2 行目と 3 行目は何も出しませんでした（本書の試験）。

```bash
    --sample evidence/population_final/sample_final_mcp.json \
```

#### 一歩ずつの説明 — 確かめのコマンド

- 1 行目: `git fetch --tags` で共有のリポジトリからタグを取り寄せ、`git tag -l` でタグの一覧を出します。`analyzer-freeze-3` があることを確かめます。CLAUDE.md は「`authgap/` を変える前に `git fetch --tags && git tag -l` で凍結のタグを確かめる」と書いています。最終評価では `authgap/` を変えませんが、凍結の版がどれかを、走らせる前に自分の目で確かめます。
- 2 行目: `git diff analyzer-freeze-3 -- authgap/` は、「タグ `analyzer-freeze-3` の時点の `authgap/` と、今の作業場の `authgap/` の違い」を出します。何も出なければ、追跡しているファイルは凍結の版と同じです。1 行でも出たら、走らせずに止まります。
- 3 行目: `git status --porcelain -- authgap/` は、`authgap/` の中の未コミットの変更と、**追跡していない新しいファイル**（`??` の行）を出します。2 行目は追跡していないファイルを出さないので、3 行目で補います。

3 つのコマンドは、互いに穴を埋め合います。
そして最後の砦が、走査のコマンドの `--require-fingerprint` です。

#### 一歩ずつの説明 — 走査のコマンド

- 1 行目: 走査は `.venv312`（Python 3.12）で走らせます。`-u` は「出力をためずにすぐ画面に出す」で、長い走査の進み具合が見えます。
- 2 行目: `--sample` に、段階 4 で作った走査の標本を渡します。**これを忘れると、既定の `evidence/population_v2/sample_v2_mcp.json`（v2 の標本）を走査してしまいます**。
- 3 行目: `--label final_run1` で、出力先が `evidence/scan_v2_final_run1/` になります。`--max-depth` は付けません。主の深さは凍結の設定の 4 です（D54。D75 の 1 で 4 のままと確かめた）。
- 4 行目: `--require-fingerprint docs/fingerprint.json` で、凍結の記録と照らします。

`--require-fingerprint` が確かめるのは、次の 2 つです。

1. `authgap/` の下のすべての `.py` ファイルの sha256 をまとめたハッシュ（結合 sha256）が、`docs/fingerprint.json` の `implementation_sha256_combined`（35606ba9…）と一致すること。

#### 走査は 1 回。`--resume` は故障のときだけ

走査は**1 回**です。
途中で止まったとき（マシンの停止など）だけ、`--resume` で続きから走らせてよいとされています。
`--resume` は、出力先の `progress.jsonl`（木ごとの結果を 1 行ずつ足していくファイル）にある木を解析し直さず、manifest から件数を数え直します。
そのとき、所要時間は元の run の値のまま残ります。

**結果が気に入らないという理由で取り直してはいけません**。
`--resume` なしで同じ label をもう一度走らせようとすると、`scan_v2.py` は「すでに manifest が N 件ある」と言って止まります。
古い木の manifest を今の結果として数えないための作りです。

#### メモリ超過で止められたとき（D75 の 4）

1 つの木の結果が大きすぎて、走査ごとメモリ超過で止められることがあります。
v4 の予備調査（D74）では、`v4-tsekennykl1__mytradingagentsbackend` が深さ 5〜8 でそうなりました（終了コード 137）。同じ木は深さ 4 ではメモリの最大値 1.05 GB で済みました。深さ 5 では、解析そのものは 2.63 GB で最後まで終わりましたが、結果の書き出し（全体を 1 本の文字列にする `canonical_json`。結果は約 4.4 GB）でメモリが溢れました。
予備調査で溢れたのは深さ 5 以上なので、いちばん起こりやすいのは深さ 5 の感度分析の走査です（下の「深さ 3・5」）。ただし最終評価の標本は v4 よりずっと大きいので、主の走査（深さ 4）で起きないとは言えません（本書の読み）。D75 の 4 は、主の走査にも感度分析の走査にも同じ扱いを当てます。
（出典: `evidence/v4pilot_depth/memory_probe.md`、`docs/decisions.md:4081-4087`（D75 の 4）、`:4098-4100`（材料のメモリ））

D75 は、これに対応する新しい仕組み（書き出しを少しずつ流す・巨大な部分を省く・木ごとにメモリの上限を掛ける）を**作らない**と決めました（D75 の 3）。
代わりに、止まったら次のようにします（手順書 9.2）。

1. 止まったのを確かめる（終了コード 137、または `Killed`）。
2. 標本の順で `evidence/scan_v2_final_run1/progress.jsonl` に行の無い最初の木が、止まったときに解析していた木です。
3. その木を除いた標本ファイルを**別に**作ります（元の標本は書き換えない）。予備調査の `evidence/v4pilot_depth/sample_v4_minus_oom.json` と同じやり方です。

主の走査（深さ 4）で除いた木は走査した木に入らないので、分母 (b)(c) の木の数にも入りません。そのことを限界に書きます（D75 の 4）。
これは「結果が気に入らないので取り直す」のとは違います。止まった理由は道具の故障（メモリ）で、除く木は結果を見ずに、止まった事実だけで決まります。
時間の上限（1 木 180 秒）のほうは、今までどおり `TRUNCATED(tree_budget)` として記録され、件数を報告します（下の表の `budget_skipped`）。
（出典: `docs/decisions.md:4079-4087`（D75 の 3・4）、`docs/final_evaluation_procedure.md:672-677`（9.2）、`docs/drafts/prereg_2_12_draft.md:45-47`）

#### マシンと日時を記録する

手順書は、走らせたマシン（CPU・メモリ・同時に走らせた本数）と日時を記録するよう書いています。
木ごとの時間がマシンの速さで変わるからです。
実際、D64 の追記には、**同じコンテナで、後に取り直した run で、同じ木の時間が約半分になった**例があります（xagent が run23 の 179.1 秒 → run24 の 89.9 秒。解析器の差は N9 の修正だけで、run24 は run23 と全項目で同じ結果でした）。
つまり、時間の差は解析器の違いではなく、マシンの速さの違いから来ています。
tree budget は 180 秒なので、遅い日に走らせれば、この木は打ち切られていたかもしれません。

記録のしかたの例です（Linux の場合。本書の作例）。

```bash
date -u +%Y-%m-%dT%H:%M:%SZ      # 走らせ始めた日時（UTC）
uname -a                          # OS とマシンの名前
nproc                             # CPU の数
free -g                           # メモリ（GB）
.venv312/bin/python --version     # Python の版
```

macOS なら、CPU の数は `sysctl -n hw.ncpu`、メモリは `sysctl -n hw.memsize`（バイト）で見られます。
「同時に走らせた本数」は、たとえば深さ 3・4・5 の走査を同時に走らせたか、です。
同時に走らせると、1 つあたりが遅くなります。

（出典: `docs/final_evaluation_procedure.md:654-655`、`docs/decisions.md:3699-3702`（D64 の追記。マシンの速さが時間で変わる）、`scripts/scan_v2.py:204-216`（`progress.jsonl` と `--resume`）、`:144-152`（`--resume` なしで止まる））

#### なぜそうするのか

- **凍結を確かめるのは、評価しているのが凍結した解析器そのものだと示すため**です。解析器が 1 文字でも違えば、論文に書く「`analyzer-freeze-3` の性能」ではなくなります。
- **1 回だけ走査するのは、走査を選べないようにするため**です。何度も走らせて都合のよい run を選べるなら、それは結果を見て選んだのと同じです。
- **マシンと日時を記録するのは、打ち切りの件数を解釈できるようにするため**です。打ち切りはマシンの速さで変わります。

- **誤解 8: 「深さ 5 の走査で除いた木も、深さ 3・4 の件数には入れたままでよい」**。いいえ。深さ 3・4・5 の件数は、全部の深さで解析できた木だけで比べ、除いた木を書きます（D75 の 4）。

#### 手作業ではどう使うか

1. 走らせる前の 3 つのコマンドの出力を、そのままメモに写します（タグの一覧、`git diff` が空、`git status` が空）。
2. マシンと日時を記録します。
3. 走査を 1 回走らせます。止まったときは理由を書いて `--resume` します。メモリ超過なら、止まった木を除いた標本で続け、`evidence/population_final/oom_excluded.md` に書きます。
4. 走査の後の表を 1 欄ずつ確かめ、`ok` 以外の木、打ち切りのあった木（と所要時間）、parse の失敗を書き出します。
5. `summary.json` と `contradictions.json` をコミットします（manifest は追わない）。深さ 3・5 も、終わったら同じようにコミットします。

#### この節のまとめ

- 走らせる前に、`git fetch --tags && git tag -l`、`git diff analyzer-freeze-3 -- authgap/` が空、`git status --porcelain -- authgap/` が空、を確かめる。`--require-fingerprint` はハッシュと未コミットの変更を照らし、疑わしければ止まる。
- `docs/fingerprint.json` の `freeze.tag` は freeze-2 と書いてあるが、正しくは freeze-3（逸脱 #26）。
- 走査は 1 回。`--resume` は故障のときだけ。マシンと日時を記録する。走査の後は表に沿って確かめ、打ち切りは summary の `budget_skipped` と manifest の `tree_budget` の両方に出る。メモリ超過の木は除いて `--resume`、全件書いて限界にする（D75 の 4）。深さ 3・5 は件数だけで、全部の深さで解析できた木で比べる。

### 47.10 ディスクが足りないとき — 数百 repo ずつ回す

#### 一言で言うと

約 3,460 repo を一度に取得するとディスクが足りないかもしれません。
手順書と D69 は、**数百 repo ずつ「取得 → 走査 → manifest を残して corpus を消す」を繰り返してよい**としています。
ただし、**1 木は 1 回だけ走査**します。
判定の対象に選ばれた木の原ソースは、後で pin の SHA から取り直せます。
その回し方の細部（`scan_v2.py` をどう呼ぶか）は手順書に書かれていないので、この節で動きを確かめ、決めておくべきことを挙げます。

#### たとえ話 — 小さな冷蔵庫で、大人数の料理を作る

冷蔵庫が小さいと、1 週間ぶんの食材を一度に買えません。
そこで、何回かに分けて買い、そのつど料理し、冷蔵庫を空けてから次を買います。
料理の**レシピの控え**（manifest）は残しておき、食材（corpus）だけを片付けます。

このとき、気をつけることが 2 つあります。
1 つは、**同じ料理を 2 回作らない**こと（1 木 1 回だけ走査）。
もう 1 つは、**最後に全部の控えを 1 冊の帳面にまとめる**ことです。
回ごとの帳面がばらばらだと、全体で何を作ったかが分かりません。

#### 小さな例 — 同じ label で 2 回に分けたときの動き（本書の試験）

`authgap/` と `scripts/` を写した作業場に、作り物の木を 3 つ置き、`scan_v2.py` を同じ label で 2 回に分けて走らせました。
1 回目は 2 木（alice・bob）、2 回目は 1 木（carol）です。

| 手順 | 走らせ方 | 起きたこと |
|---|---|---|
| 1 | 1 回目の 2 木を `--label t1` で | 2 木を解析。`summary.json` の `trees` は 2 木 |
| 2 | 2 回目の 1 木を同じ `--label t1` で、`--resume` なし | 「すでに manifest が 2 件ある」と言って**止まる** |
| 3 | 2 回目の 1 木を同じ `--label t1` で、`--resume` あり | 1 木を解析。**`summary.json` の `trees` は 1 木だけ**になり、1 回目の 2 木が消える。`contradictions.json` も 0 件になる。`progress.jsonl` は 3 行 |
| 4 | 3 木全部を並べた標本を同じ `--label t1` で、`--resume` あり | 3 木とも「resumed」（解析し直さず manifest から数え直す）。`summary.json` は 3 木、`n_trees_resumed` 3、`contradictions.json` は 2 件 |

表の読み方: 3 行目は「2 回目を `--resume` 付きで走らせると、新しい 1 木は解析されるが、`summary.json` と `contradictions.json` はその回の標本の木だけで書き直される。全体の記録は `progress.jsonl` にだけ積み上がる」と読みます。
4 行目は「最後に全部の木を並べた標本で `--resume` 付きで走らせると、どの木も解析し直さずに、全体の `summary.json` と `contradictions.json` ができる」と読みます。

さらにもう 1 つ試しました。
まだ取得していない木（erin）を標本に入れて `--resume` 付きで走らせると、その木は `missing`（corpus に無い）として `progress.jsonl` に記録されました。
その後で erin を取得し、もう一度 `--resume` 付きで走らせても、erin は**`missing` のまま**で、解析されませんでした。

（出典: `scripts/scan_v2.py:144-152`（`--resume` なしで止まる）、`:207-216`（`progress.jsonl` を読む）、`:235-247`（`done` にある木は解析し直さない。`ok` 以外の状態もそのまま使う）、`:248-250`（corpus に無い木は `missing`）、`:284-303`（その回の標本の木だけで `summary.json` と `contradictions.json` を書く））

#### 一歩ずつの説明 — なぜそうなるのか

`scan_v2.py` の作りを、3 つに分けて見ます。

1. **`summary.json` と `contradictions.json` は、その回に渡した標本の木だけで作られます**。スクリプトは、`--sample` の `targets` を 1 つずつ処理し、その一覧から `summary.json` の `trees` を作ります。前の回の木は、今回の標本に入っていなければ数えられません。
2. **`progress.jsonl` は積み上がります**。木を 1 つ処理するたびに、その結果を 1 行足します。`--resume` のときは、このファイルにある木を「処理済み」とみなします。
3. **「処理済み」には、失敗した状態も含まれます**。`progress.jsonl` に `missing` や `analysis_failed` と書かれた木は、`--resume` のときに解析し直さず、その状態をそのまま使います。だから、取得する前に標本に入れてしまった木は、後で取得しても `missing` のままになります。

もう 1 つ、集計の道具の側にも安全装置があります。
`contradiction_by_decl.py` や `r_malformed.py` が使う `runlib.run_manifests` は、`summary.json` の `ok` の木だけを数え、`summary.json` に無い manifest があると「`summary.json` に無いファイル N（数えない）」という警告を出します。
最後の回の `summary.json` に一部の木しか無ければ、この警告が出て、数えられない木があることに気づけます。

（出典: `scripts/runlib.py:26-53`（`summary.json` の `ok` の木で manifest の集合を決め、警告を出す））

#### 回すときに決めておくこと（本書の指摘。未決）

手順書と D69 は「数百 repo ずつ回してよい」と書いていますが、`scan_v2.py` をどう呼ぶかは書いていません。
また、手順書は `--resume` を「途中で止まったとき」のためのものとしています。
数百ずつ回すのに `--resume` を使うのは、それとは別の使い方です。
上の動きから、決めておくべきことを挙げます。
**どれも本書の指摘で、未決**です。

- **(i) label と `--resume` の使い方**。たとえば「全部の回を同じ label `final_run1` で走らせ、2 回目からは `--resume` を付け、最後に全部の木を並べた標本で `--resume` 付きの回を 1 回走らせて全体の `summary.json` を作る」という回し方は、上の試験のとおりに動きます。回ごとに別の label にするなら、全体をまとめる道具が別に要ります（今の repo には無い）。
- **(ii) 回ごとの標本には、取得を終えた木だけを入れる**。取得していない木を入れると、`missing` として残り、後で取得しても解析されません。
- **(iii) 回ごとに残すもの**。`docs/fetch_failures.md` は取得のたびに書き直されるので、回ごとに別の名前で写しておきます。取得後の条件の結果（`post_fetch_check.json`）も、corpus を消す前に作ります（`check_population_v2.py` は corpus の中のファイルを読むので、消した後では `not_fetched` になる）。重複の除去のためのハッシュも、消す前に取ります。
- **(iv) 深さ 3・5 も、消す前に走らせる**。深さ 3・5 の走査にも corpus が要ります。消した後に取り直して走らせると、取得をもう一度することになります。
- **(v) 今回の中の重複は、全部の木のハッシュがそろわないと決まらない**（47.8 節の (iv)）。数百ずつ回すなら、たとえば「まず全部の木を取得してハッシュだけ取り、消す。重複を決めてから、残す木だけを数百ずつ取り直して走査する」という順にするか、repo 名の辞書順に回して、前の回までのハッシュと比べるか、などを決めます。
- **(vi) 判定の対象の木を取り直せないとき**。pin があっても、repo が消されたり非公開になったりすると、後で取り直せません。そのときは、黙って別の木に差し替えず、件数と理由を記録します（CLAUDE.md の規則 4）。ディスクが許すなら、corpus を消さずに残すほうが安全です。

これらは、**走査の前に**決めて、事前登録 §2.12 の (c) か、走査の記録に書いておきます。
走査を始めてから決めると、「どの木をどう走らせたか」を途中で選んだことになりかねません。

#### ディスクの見込み

手順書の 0-1 は、v4 の 99 repo で約 1.2 GB だったことから、同じ割合なら約 40 GB の見込みと書いています。
このほかに、manifest もディスクを使います。
v4 の 88 木の走査の出力のディレクトリは 170 MB でした（本書の計算、`du -sh`）。
約 3,000 木なら、同じ割合で数 GB になりえます（本書の粗い見込み。測っていない）。
manifest は判定の手順 B で使うので、corpus を消しても manifest は残します（手順書の 26 節）。
また、`fetch_corpus.py` は `corpus/_cache/` の下にも repo の部分クローンを置くので、corpus を消すときは、木の作業場（`corpus/<木の名前>/`）と一緒に、こちらも片付けます。

（出典: `docs/final_evaluation_procedure.md:145-148`、`:1452`（26 節。manifest は残す）、`scripts/fetch_corpus.py:80-102`（`corpus/_cache/`））

#### なぜそうするのか

- **数百ずつ回してよいのは、走査の結果が manifest に残るから**です。corpus を消しても、走査の結果は失われません。判定に要る木の原ソースは、pin から同じ中身を取り直せます。
- **1 木 1 回だけ走査するのは、走査を選べないようにするため**です（47.9 節と同じ理由）。
- **回し方を先に決めるのは、記録が欠けたり、木が黙って `missing` になったりするのを防ぐため**です。どちらも、件数を黙って落とす向きの失敗です（CLAUDE.md の規則 4）。

#### よくある誤解・つまずき

- **誤解 1: 「回ごとの `summary.json` を足せば全体になる」**。回ごとの `summary.json` は、次の回で上書きされます。最後に全部の木を並べた標本で全体の `summary.json` を作ります。
- **誤解 2: 「取得前の木を標本に入れておいても、後で `--resume` すれば解析される」**。いいえ。`missing` のまま残ります（上の試験）。
- **誤解 3: 「corpus を消すと、判定できなくなる」**。判定の対象の木は、pin の SHA から取り直せます。ただし、repo が消されていれば取り直せないので、記録します。
- **つまずき 4: `docs/fetch_failures.md` を最後に 1 回見れば足りると思う**。取得のたびに書き直されるので、最後の回の失敗しか残りません。
- **つまずき 5: 深さ 3・5 を後回しにして corpus を消す**。もう一度取得することになります。

#### 手作業ではどう使うか

1. 走査の前に、ディスクの空きを確かめます（`df -h`）。全部を一度に置けるなら、数百ずつに分けないのがいちばん簡単です。
2. 分けるなら、上の (i)〜(vi) を決め、事前登録か走査の記録に書いてから始めます。
3. 回ごとに、取得の失敗の記録・取得後の条件の結果・ハッシュを残し、深さ 3・4・5 を走らせてから corpus を消します。
4. 最後に全体の `summary.json` を作り、`n_trees` が走査の標本の木の数と一致すること、`contradiction_by_decl.py` が「`summary.json` に無いファイル」の警告を出さないことを確かめます。

#### この節のまとめ

- ディスクが足りなければ、数百 repo ずつ「取得 → 走査 → manifest を残して corpus を消す」を繰り返してよい。1 木は 1 回だけ走査し、判定の対象は pin から取り直す。
- `scan_v2.py` は、`summary.json` と `contradictions.json` をその回の標本の木だけで書き直し、`progress.jsonl` だけが積み上がる。取得前の木は `missing` のまま残る（本書の試験）。
- 回し方（label・`--resume`・回ごとに残すもの・深さ 3・5・重複の除去の順番・取り直せない木）は手順書に無く、**未決**。走査の前に決めて書く。

### 47.11 段階 6 — 判定の対象を抜き取る

#### 一言で言うと

走査の結果から、宣言ごとの件数と感度分析（`contradiction_by_decl.py`）と `r_malformed` を出し、3 つの抜き取り（矛・見落とし・不の中身）を seed ①②③ で行います。
判定表の雛形を作り、**判定の順序を無作為に並べ替え**ます。
ここが、**件数が日程に合うかを確かめる最後の機会**です。
対象の一覧をコミットしてから、判定（段階 7）を始めます。

#### たとえ話 — 採点する答案を抽選し、束を切り混ぜる

答案が多すぎて全部は採点できないので、抽選で一部を選ぶとします。
抽選の規則と種（seed）は、答案を見る前に決めてあります。
選んだ答案の束は、提出された順のままにせず、よく切り混ぜてから採点します。
同じクラスの答案が続くと、前の答案の印象に引きずられるからです。

そして、採点を始める前に、「この束を全部採点するのに何時間かかるか」を数えます。
間に合わないと分かったら、**採点を始める前に**、規則を変えたことを記録してから束を減らします。
採点を始めた後で減らすと、「採点してみて都合の悪い答案を外した」と疑われます。

#### 判定の順序を無作為に並べ替える

手引きの下書きの 21 節は、「判定の順序を無作為にする（段階 6）。同じ木の組が続くと、前の判断に引きずられる」と書いています。

そのまま判定すると、たとえば同じ木の 3 件を続けて読むうちに、1 件目の判断が 2 件目・3 件目に引きずられます。

並べ替えに使う seed は、事前登録の下書きの **⑤ YYYYMMDD5** です。前の版では【確認】（本記録者の提案、未承認）でしたが、2026-10-03 の D73 の 4 で学生が採りました。
たとえば次の形で並べ替えられます（本書の作例）。

```python
import random

def shuffle_rows(rows, seed5):
    rows = sorted(rows, key=lambda r: (r["decl"], r["tree"], r["unit_relpath"], r["unit_lineno"], r["site"], r["kind"]))
    random.Random(seed5).shuffle(rows)
    for i, r in enumerate(rows, start=1):
        r["order"] = i
    return rows
```

- 1 行目: 乱数の部品を読み込みます。
- 3 行目: 判定表の行の一覧と seed ⑤ を受け取る関数を作ります。

- 6〜7 行目: 切り混ぜた後の順番を、`order` の欄に 1 から振ります。
- 8 行目: 並べ替えた一覧を返します。

#### 件数が日程に合うかを確かめる — 最後の機会

D69 の 6 は、判定の時間（約 170〜380 時間）を**測っていない見込み**とし、「練習で 1 件の時間を測り、段階 6 の前に件数を確かめる。合わなければ事前登録に逸脱として書いてから減らす」と決めています。

計算は、次の式です。

> 要る時間 = 矛の件数 × 矛 1 件の分数 + 見落としの件数 × 見落とし 1 件の分数 + 不の中身の件数 × 不の中身 1 件の分数

**架空の数**で計算してみます（どれも測った値ではありません）。
抜き取りの出力で、矛が D1 550・D2 520・D3 20・D4 30 件、見落としが 200 件、不の中身が 100 組だったとします。
練習で測った 1 件の分数が、矛 8 分、見落とし 30 分、不の中身 15 分だったとします。

```text
矛:       (550 + 520 + 20 + 30) × 8 分 = 1,120 × 8 = 8,960 分 ≈ 149 時間
見落とし:  200 × 30 分                  = 6,000 分 = 100 時間
不の中身:  100 × 15 分                  = 1,500 分 =  25 時間
合計                                               ≈ 274 時間
```

週 20 時間を判定にあてられるなら、約 14 週（3 か月あまり）です。
これが論文の締め切りまでの日程に収まるかを確かめます。
判定の一致の確認（D73 の 1）の 10% の分も足します。(ii) 判定し直しなら学生の時間に、(i) 2 人目の判定者なら 2 人目の時間に入ります（手順書の 27 節）。

#### なぜそうするのか

- **対象を先にコミットするのは、判定を見てから対象を選び直したと疑われないため**です。
- **順序を並べ替えるのは、1 人の判定者の中のぶれを減らすため**です。判定者は学生 1 人なので、1 人の中のぶれを減らす工夫が大事です（手引きの 21 節）。慣れや疲れの揺れを、特定の木に偏らせないためでもあります（D73 の 4）。
- **日程を段階 6 で確かめるのは、ここが判定の前の最後の地点だから**です。判定を始めた後で減らすと、判定の結果を見て減らしたと疑われます。

#### よくある誤解・つまずき

- **誤解 1: 「`contradiction_by_decl.py` の件数を見たら、結果を見たことになる」**。段階 6 で見るのは機械の件数で、判定の結果ではありません。ただし、この件数を見た後で抜き取りの規則や seed を変えてはいけません。
- **誤解 2: 「日程に合わなければ、判定しながら減らせばよい」**。いいえ。減らせるのは段階 6 のコミットの前までで、逸脱として書いてからです。
- **誤解 3: 「D3・D4 は少ないので、抜き取らずに全部を判定する（だから規則は要らない）」**。結果として全木になることが多いだけで、規則は D1・D2 と同じです（D69 の 2）。
- **誤解 4: 「不の中身は D3・D4 も判定する」**。いいえ。D1・D2 だけです。D3・D4 の不は件数と理由だけです。
- **つまずき 5: 判定表を鍵の順のまま判定する**。同じ木の組が続き、前の判断に引きずられます。並べ替えてから判定します。
- **つまずき 6: 判定の一致の分かれ道を書き忘れる**。段階 6 のコミットに、(i) か (ii) かと、seed ⑥ で選んだ組を入れます（D73 の 1）。

#### 手作業ではどう使うか

1. 段階 6 のコマンドを走らせ、`contradiction_by_decl` の矛の総数と、抜き取りの道具の `n_pairs` が一致することを確かめます。
2. 3 つの抜き取りの件数を、練習で測った分数に掛けて、要る時間を計算します。
3. 合わなければ、逸脱を書いてから、同じ規則の数を減らして選び直します。
4. seed ⑥ で判定の一致を確かめる組を選び、2 人目の判定者が決まっているかで (i) か (ii) かを決めて記録します（D73 の 1）。
5. 判定表を並べ替え、全部をコミットしてから、[第 48 章](ch48.md)の手順で 1 件目に入ります。

#### この節のまとめ

- 段階 6 では、`contradiction_by_decl.py`・`r_malformed.py`・3 つの抜き取り（矛 = 宣言ごとに 200 木・1 木 3 件・seed ①、見落とし = 200 木・1 木 1 ユニット・seed ②・打ち切りを含める、不の中身 = D1・D2 で各 50 木・1 木 1 組・seed ③）を走らせる。
