## 第 18 章 出力の読み方 — manifest・組・summary

> **この章で分かること**:
> - 解析器が 1 回の走査（run）で書き出す 3 種類のファイル（木ごとの **manifest**、run 全体の **`summary.json`** と **`contradictions.json`**）の役割と、どれを git で追跡しているか。
> - manifest のいちばん外側の欄と、ユニットの欄。とくに **`D_kind`** の正しい読み方。第 3 版の「`explicit` が明示された宣言」は不正確でした。`explicit` に入るのは上界を動かす明示と `openWorldHint: true` だけで、**D3 は `closed_world`、D4 は `idempotent`** に出ます。
> - 効果の欄と、**`entry_lineno`**（ツールの本体の中で、その道筋の最初の呼び出しがある行）。
> - 行（`rows`）の **`verdicts`** の欄と、核の答え（矛・不・内）が**別物**であること。核の「不」は、行の `notes` の **`contradiction_unknown:<宣言>:<理由>`** にしか現れないこと。
> - 行の注記の 3 種類（矛・矛の理由・不）の読み分けと、ユニットの注記に出る**打ち切りの印** `TRUNCATED(...)`。
> - 判定の単位 **組 = (木, ユニット, site, kind, 宣言)** と、`contradictions.json` の 1 行 = (ユニット, site, kind) との関係。v4 では 481 行で、宣言ごとに D1 323 + D2 155 + D4 3 = 481 組でした。
> - `summary.json` の欄と、走査の後に確かめること。**`verdict_rows` は行の数で、組の数ではない**こと。
> - 時間上限の打ち切りが、`summary.json` の `budget_skipped` と、manifest の `truncations` の `tree_budget`（または `tree_budget_prep`）の **2 か所**に出ること。
> - ユニットを relpath と行で探すこと。run の名前の付け方（`scan_v2_v4_run1`、これから作る `scan_v2_final_run1`）。

### この章の位置づけ

[第 11 章](ch11.md)で、解析器が 1 本の木を処理する 7 つの段階を見ました。
入口を探す（①）→ 中をたどる（②）→ 効果を見つける（③）→ 値を追いかける（④）→ 宣言を読む（⑤）→ 照合する（⑥）→ **書き出す（⑦）**、です。
第 12〜17 章で、①〜⑥の中身を 1 つずつ学びました。
この章は、最後の **⑦ 書き出す** の章です。
書き出されたものを、**どう読むか**を学びます。

[第 11 章](ch11.md) 11.5 節では、manifest の欄と 7 つの段階の対応を「地図」にしました。
11.6 節では、判定の単位「組」を予告しました。
この章では、その地図の 1 つ 1 つの欄を、**辞書のように引ける**ようにします。
次の[第 19 章](ch19.md)では、この章で学ぶ欄を、実物の manifest の 1 ユニットで 1 つずつ確かめます。
この章は「欄の辞書」、[第 19 章](ch19.md)は「辞書を引きながら実物を読む練習」と思ってください。

最終評価の判定は、解析器の出力を「**解析器の言い分**」として読み、それを原ソースで確かめる作業です（[第 48 章](ch48.md)の手順 B）。
言い分が読めなければ、確かめようがありません。
しかも、出力には**似た名前の別物**がいくつもあります。
たとえば、`verdicts` の `UNKNOWN` と核の「不」、行の `notes` とユニットの `notes`、行の数と組の数です。
取り違えると、判定の対象を数え間違えたり、「不」を見落としたりします。
だから、この章は「判定の道具の取扱説明書」の章でもあります。

#### この章で使う言葉の思い出し

この章は、前の章で定義した言葉をたくさん使います。
忘れていたら、ここで思い出してください。

- **木**（[第 11 章](ch11.md)）: 1 つのリポジトリ（1 つの MCP サーバ）。`corpus/<木の名前>/` に取得したもの。
- **走査**と **run**（[第 11 章](ch11.md)）: たくさんの木に解析器を 1 本ずつ走らせること。1 回の走査を run と呼び、名前（ラベル）を付ける。
- **manifest**（[第 11 章](ch11.md)）: 解析器が木ごとに書き出す結果の JSON ファイル。
- **JSON**（[第 2 章](ch02.md)、[第 11 章](ch11.md) 11.5 節）: `{ }` の中に「名前: 値」を並べ、`[ ]` の中に値の列を並べる書き方。
- **ユニット**（[第 12 章](ch12.md)）: 解析の単位になる 1 つのツール。**relpath** は、木の根からのファイルの道筋。
- **効果**・**kind**・**site**・**slot**（[第 13 章](ch13.md)）: 外の世界に触れる操作、その種類、それを起こす関数の名前、その引数の位置。
- **主体**（`prin`）・**確度**（`prov`）（[第 14 章](ch14.md)）: slot の値を誰が決めたか、解析器が読み切れたか。
- **`witness_chain`**・**深さ**（[第 15 章](ch15.md)）: ツールの本体から効果まで通った関数の列と、その段数。
- **`D_kind`**（[第 16 章](ch16.md)）: 解析器が宣言から作る「約束のまとめ」。
- **D1〜D4**（第 4・16 章）: D1 = `readOnlyHint: true`、D2 = `destructiveHint: false`、D3 = `openWorldHint: false`、D4 = `idempotentHint: true`。
- **矛・不・内**（第 11・17 章）: 解析器の 3 つの答え。宣言に反する・静的に決められない・宣言の範囲内。
- **理由コード**（[第 17 章](ch17.md)）: 解析器が矛や不にした理由を表す短い名前（`fs_write`・`net_post` など）。
- **正・誤・不明**（[第 11 章](ch11.md)）: 人の判定の答え。解析器の答えとは別の層。
- **V1 頑健性**（[第 6 章](ch06.md)）: 解析器が新しいデータで壊れずに動いたかを数える問い。人は判定せず、件数を数えるだけ。

### 18.1 3 種類の出力ファイル — 全体の地図

#### 一言で言うと

1 回の run で、解析器は**木ごとの manifest** と、**run 全体の `summary.json` と `contradictions.json`** を書き出します。
manifest は大きいので git で追跡せず、`summary.json` と `contradictions.json` だけを追跡します。

#### たとえ話 — 建物の点検の書類

たくさんの建物をまとめて点検する仕事を思い浮かべてください。
点検が終わると、3 種類の書類ができます。

- 建物 1 棟ごとの**点検報告書の本文**: 部屋ごとに、何を見たか、何が気になったかが全部書いてあります。分厚い書類です。
- 全部の棟をまとめた**表紙の集計表**: 何棟を点検したか、何棟で点検が途中で終わったか、全体で何時間かかったかが 1 枚にまとまっています。
- 「掲示と違う」と指摘した所だけを抜き出した**指摘事項の一覧**: 後で人が現地へ確かめに行くための一覧です。

解析器の出力も同じ形です。
manifest が報告書の本文、`summary.json` が表紙の集計表、`contradictions.json` が指摘事項の一覧にあたります。
判定は、指摘事項の一覧から対象を選び（抜き取り。[第 47 章](ch47.md)）、報告書の本文を開いて解析器の言い分を読み、最後に現地（原ソース）へ行って確かめる、という順で進みます。

#### 小さな例 — v4 の run のフォルダ

v4 の run のフォルダの中身を、一部だけ写します。

```
evidence/scan_v2_v4_run1/
├── summary.json                                       ← run 全体の表紙（git で追跡する）
├── contradictions.json                                ← 矛の一覧（git で追跡する）
├── progress.jsonl                                     ← 途中経過の記録（追跡しない）
├── v4-aakashh242__remote-mcp-adapter.json             ← 木ごとの manifest（追跡しない）
├── v4-abi-jey__simple-rdp.json                        ← 木ごとの manifest
├── v4-ankitdotgg__making-gemini-useful-with-claude.json
├── v4-appachhi__bugasura-mcp-server.json
└── …（manifest は全部で 88 個）
```

#### 一歩ずつ

- 1 行目: run のフォルダの名前は `evidence/scan_v2_<ラベル>/` です。v4 のラベルは `v4_run1` なので、`scan_v2_v4_run1` になります（18.13 節）。
- 2 行目: `summary.json` は、run 全体で 1 つです。
- 3 行目: `contradictions.json` も、run 全体で 1 つです。
- 4 行目: `progress.jsonl` は、木を 1 本解析するたびに 1 行ずつ足していく途中経過の記録です。走査が途中で止まったときに、続きから再開するために使います。
- 5 行目以降: `v4-` で始まるファイルが、木ごとの manifest です。ファイルの名前は「木の名前 + `.json`」です。木の名前の頭の `v4-` は、どの母集団の木かを表す接頭辞です。

本書の執筆時に数えると、このフォルダのファイルは 91 個でした。
manifest が 88 個（`summary.json` の `n_trees` の 88 と一致）、残りが上の 3 つのファイルです。
`git ls-files evidence/scan_v2_v4_run1` で確かめると、git で追跡しているのは `summary.json` と `contradictions.json` の 2 つだけでした。
（出典: `scripts/scan_v2.py:4-8`（出力の 3 つのファイルの説明）、`:186`（フォルダの名前）、`:204-216`（`progress.jsonl`）、`.gitignore:25-30`）

4 種類のファイルを表にまとめます。

| ファイル | 単位 | 中身 | git で追跡するか | 判定で使う場面 |
|---|---|---|---|---|
| `<木の名前>.json`（**manifest**） | 木 1 本に 1 つ | その木のすべてのユニットについて、効果・値・注記・打ち切りなど、解析器が見たものすべて | **しない**（大きいので） | 手順 B（解析器の言い分を読む）で毎回 |
| `summary.json` | run 全体に 1 つ | 木ごとの状態・件数・所要時間と、run 全体の合計。解析器の指紋 | する | 走査の後の確認（V1 頑健性）、集計 |
| `contradictions.json` | run 全体に 1 つ | **矛**（CONTRADICTION）の行を (ユニット, site, kind) ごとにまとめた「手で確かめる候補の表」 | する | 矛の抜き取りの入力 |
| `progress.jsonl` | run 全体に 1 つ | 木ごとの状態を 1 行ずつ足した途中経過 | しない | 使わない（再開のときだけ） |

表の読み方: 1 行が 1 種類のファイルです。
たとえば 3 行目は「`contradictions.json` は run 全体で 1 つあり、解析器が矛を出した所を一覧にしたもの。git で追跡しているので、後から誰でも同じ一覧を見られる。最終評価では、矛の抜き取りの入力になる」と読みます。

#### なぜそうするのか

**manifest を追跡しない理由**は、大きさです。
`.gitignore` の説明には「母集団 v2 の full scan は要約だけ残す（manifest 本体 13MB は追跡しない）」とあります。
手順書も、最終評価の manifest は「1 木で十数 MB になりうる」と書いています。
数千本の木の manifest を git に入れると、リポジトリが扱えないほど大きくなります。

**`summary.json` と `contradictions.json` を追跡する理由**は、論文に書く数の根拠になるからです。
追跡しておけば、「この run ではこの件数だった」という記録が履歴に残り、後から誰でも確かめられます。
手順書の段階 5 の最後も、「`summary.json` と `contradictions.json` をコミットする（manifest は追わない）」です。

**ファイルを 3 つに分ける理由**は、読む人と目的が違うからです。
走査が壊れずに済んだかを見るには、表紙（`summary.json`）だけで足ります。
判定の候補を選ぶには、指摘の一覧（`contradictions.json`）が要ります。
1 件を深く確かめるときだけ、分厚い本文（manifest）を開きます。
（出典: `.gitignore:25-30`、`docs/final_evaluation_procedure.md:498-508`（6.6 の `.gitignore`）、`:673-675`（9.5 のコミット））

#### よくある誤解・つまずき

- **つまずき: 「manifest が git の履歴に無い。消えてしまったのか」**
  消えていません。git で追跡していないだけで、手元のフォルダにあります。別のマシンに repo を写しただけでは、manifest は付いてきません。
- **誤解: 「`contradictions.json` を見れば、判定に要ることは全部分かる」**
  分かりません。`contradictions.json` には、道筋（`witness_chain`）も、slot の主体と確度も、理由コードも入っていません。それらは manifest にしかありません（18.9 節）。
- **誤解: 「`contradictions.json` に、解析器の答えが全部入っている」**
  入っているのは**矛だけ**です。「不」は入っていません（18.9 節）。
- **誤解: 「`progress.jsonl` も結果の一部だから、集計に使う」**
  使いません。再開のための途中経過で、最後に `summary.json` が同じ情報をまとめて書きます。

#### 手作業ではどう使うか

- 最終評価の run の出力は `evidence/scan_v2_final_run1/` に入ります（18.13 節）。
- 最終評価の manifest のために、`.gitignore` に `evidence/scan_v2_*/final-*.json` の 1 行を足す予定です（手順書 6.6）。これで manifest は追跡されず、`summary.json` と `contradictions.json` だけが追跡されます。
- ディスクが足りなくなっても、**manifest は消しません**。手順書の「困ったとき」の表は、「走査を終えた木の manifest 以外（ビルドの残りなど）を消す。manifest は判定で使うので残す」と書いています。判定の手順 B で、毎回 manifest を開くからです。
- 判定の準備として手元にそろえるものは、原ソース（`corpus/<木>/`）、manifest、判定表、判定の手引きです（手順書 12.1）。

（出典: `docs/final_evaluation_procedure.md:498-508`（6.6）、`:642`（出力先）、`:746-752`（12.1 の手元に用意するもの）、`:1440`（ディスクが足りないとき））

#### この節のまとめ

1 回の run で、木ごとの manifest と、run 全体の `summary.json`・`contradictions.json`（と途中経過の `progress.jsonl`）ができる。
manifest は大きいので追跡せず、手元に残す。`summary.json` と `contradictions.json` は論文の数の根拠なので追跡する。
判定は「一覧から選び、manifest で言い分を読み、原ソースで確かめる」順に進む。

<a id="s18-3"></a>
### 18.2 manifest のいちばん外側

#### 一言で言うと

manifest は、1 本の木についての 1 つの JSON です。
いちばん外側には 12 個の欄があり、判定で読むのは主に **`units`**（ユニットごとの結果）です。
木の単位の打ち切りの記録 **`truncations`** と、読めなかったファイルの一覧 **`parse_failures`** も、見落としの判定の前に読みます。

#### たとえ話 — 報告書の表紙・目次・本文

点検報告書には、本文の前に表紙と目次があります。
表紙には「いつ、誰が、どの建物を、どの基準の版で点検したか」が書いてあります。
本文の前に「鍵が開かずに入れなかった部屋の一覧」が付いていることもあります。
本文を読む前にこの一覧を見ておかないと、「この部屋は何も問題が無い」と書いてあるのか、「この部屋には入っていない」のかを取り違えます。

manifest の `run_meta` と `fingerprint` が表紙、`parse_failures` と `truncations` が「入れなかった部屋の一覧」、`units` が本文にあたります。

#### 小さな例 — v4 の gemini の manifest の外側

v4 の making-gemini-useful-with-claude の木（以下「gemini の木」）の manifest から、いちばん外側の欄を写します。
`units` の中身と、長い欄は「…」で省きました。
実物では、欄は名前のアルファベット順に並んでいます（解析器が名前で並べ替えて書き出すため）。

```json
{
  "d_op": {"allow": null, "ask": [], "bottom": true, "deny": [], ...},
  "dispatch_sites": [ ... ],
  "fingerprint": {"caps": {"AST_NODE_CAP": 20000, "MAX_DEPTH": 4, "WALL_CLOCK_CAP": 10.0, ...},
                  "sha256": {"sink_table": "48554b64...", ...}, ...},
  "gate_verdict_counts": {"NODOM(non_binding_gate)": 5},
  "mcp_version": {"class": "lt2", "evidence": ["lt2:import:server.py:mcp.server.fastmcp"]},
  "parse_failures": [],
  "population": "mcp_server",
  "run_meta": {"elapsed_s": 0.09, "run_id": "v4_run1", "src_root": ".../corpus/v4-ankitdotgg__making-gemini-useful-with-claude"},
  "schema": "authgap/v1",
  "truncations": [],
  "units": [ ...ユニットが 2 つ... ],
  "unresolved_handler": {"count": 0, "sites": []}
}
```

（出典: `evidence/scan_v2_v4_run1/v4-ankitdotgg__making-gemini-useful-with-claude.json`（本書の執筆時に確かめた）、`authgap/report.py:40-42`（キーを並べ替えて書き出す `canonical_json`）、`:270-301`（`manifest_json`））

#### 一歩ずつ — 12 個の欄

| 欄 | 中身 | 判定で読むか |
|---|---|---|
| `units` | **ユニットごとの結果の列**。判定で読むのはほぼここ（18.3 節） | **読む** |
| `truncations` | 木の水準の打ち切りの記録。1 要素が `{"relpath": …, "cap": …, "count": …}` | **読む**（V1 頑健性と、見落としの判定の前） |
| `parse_failures` | Python として読めなかった（parse に失敗した）ファイルの relpath の列 | **読む**（そのファイルの中は見えていない） |
| `run_meta` | 走らせたときの情報（run の名前 `run_id`、木の場所 `src_root`、解析にかかった秒数 `elapsed_s`） | 参考 |
| `fingerprint` | 解析器の**表**（sink 表など）の指紋と、上限の値（`caps`） | 参考（下の注意） |
| `mcp_version` | 木が使う MCP の SDK の版の見立て（snake_case の宣言の読み方を決める。[第 16 章](ch16.md)） | 参考 |
| `schema` | 書式の版（`authgap/v1`） | 読まない |
| `population` | 母集団の種別（MCP サーバの木なら `mcp_server`） | 読まない |
| `gate_verdict_counts`・`d_op`・`dispatch_sites` | 付録の仕組み（[第 8 章](ch08.md)）のための欄 | 読まない |
| `unresolved_handler` | 低レベルの書き方で、ユニットにできなかったハンドラの登録の数と位置 | 参考（[第 12 章](ch12.md)） |

表の読み方: 1 行が 1 つの欄です（`gate_verdict_counts`・`d_op`・`dispatch_sites` は 1 行にまとめたので、行は 10 行です）。
たとえば 2 行目は「`truncations` は、木の水準で読むのを打ち切った記録の列。V1 頑健性の材料で、見落としの判定の前にも見る」と読みます。

**`truncations` の要素**をもう少し詳しく見ます。
v4 の bugasura-mcp-server の木（以下「bugasura の木」）には、次の 2 つがありました。

```json
"truncations": [
  {"cap": "ast_node_cap", "count": 29649, "relpath": "tools/knowledge_base.py"},
  {"cap": "ast_node_cap", "count": 21715, "relpath": "tools/testpert.py"}
]
```

- `cap` は、どの上限に当たったかです。`ast_node_cap` は「1 つのファイルの構文木の節の数が上限 20,000 を超えた」という意味です。
- `count` は、その上限で数えた量です。`ast_node_cap` では、そのファイルの構文木の節の数です。29,649 は 20,000 を超えています。
- `relpath` は、打ち切ったファイルです。

大事なのは、**`ast_node_cap` に当たったファイルは、中身を丸ごと読まない**ことです。
解析器は、そのファイルの構文木を捨てて先へ進みます。
ですから、そのファイルの中にある関数の効果は、解析器には見えていません。
さらに、**ツールの定義そのものがそのファイルの中にあれば、そのツールはユニットとして見つかりません**（manifest の `units` に入らず、件数にも出ない）。
母集団 v2 では、`@tool` 系のデコレータの 77.2%（12,713 個のうち 9,816 個）が、こうして切られたファイルの中にありました。ただし、そのうち 9,524 個は 1 本の木（mcparmory/registry）のもので、分母の扱いは O21 に記録されています。
v4 の 44 個の `ast_node_cap` では、ユニットは落ちていませんでした（`docs/population_v4.md:74`「ユニットは落ちていない」）。
時間上限の打ち切りも、同じ `truncations` に `relpath` が空の要素として入ります（18.11 節）。
（出典: `evidence/scan_v2_v4_run1/v4-appachhi__bugasura-mcp-server.json`、`authgap/srcindex.py:147-152`（節の数が上限を超えたら構文木を捨てる）、`authgap/ir.py:30-31`（`AST_NODE_CAP = 20000`）、`authgap/report.py:279-284`、`docs/open_questions.md:425-436`（O21）、`docs/decisions.md:1860-1862`）

**`fingerprint` の注意**も書いておきます。
manifest の `fingerprint` は、解析器のコード全体の指紋**ではありません**。
sink 表などの「表」の指紋と、上限の定数の値です。
解析器のコード全体の指紋（`implementation_sha256_combined`）は、`summary.json` のほうにあります（18.10 節）。
さらに、`fingerprint.caps.MAX_DEPTH` は**定数の値をそのまま写したもの**です。
深さの感度分析で `--max-depth 3` を付けて走らせても、manifest には `MAX_DEPTH: 4` と書かれます。
実際に使った深さは、`summary.json` の `max_depth` で確かめます。
（出典: `authgap/report.py:50-56, 105-121`（`fingerprint` の中身）、`scripts/scan_v2.py:176-178`（`--max-depth` の説明「manifest の fingerprint は定数の値のままなので、実際に使った深さは summary.json の max_depth に残す」））

**`run_meta` の注意**です。
`run_meta` は、走らせるたびに変わりうる値（run の名前、木の置き場所、秒数）を**ここだけに**閉じ込めた欄です。
同じ解析器で同じ木を 3 回走らせて、`run_meta` を除いた manifest が 1 字も違わないかを確かめる（決定的かの確認。[第 7 章](ch07.md)）ために、変わる値を 1 か所に集めています。
`run_meta.elapsed_s` は解析だけの秒数です。
`summary.json` の木ごとの `elapsed_s` は、manifest を書き終えるまでの秒数なので、少し大きくなります。
たとえば v2 の run24 の meta-skill-evloving の木では、`run_meta` が 415.848 秒、`summary.json` が 423.7 秒でした。
（出典: `authgap/report.py:271, 295-300, 312-320`（`run_meta` と、それを除いて比べる `strip_volatile`）、`scripts/scan_v2.py:248, 268`、`evidence/scan_v2_run24/summary.json` と同じフォルダの manifest（本書の執筆時に確かめた））

#### なぜそうするのか

いちばん外側の欄を「木の単位」と「ユニットの単位」に分けているのは、**欠けの単位が違う**からです。
ファイルが読めない（`parse_failures`）、ファイルが大きすぎる（`ast_node_cap`）、木の時間が足りない（`tree_budget`）は、どれもユニットより大きい単位の欠けです。
これらをユニットの欄に混ぜると、「どのユニットにも書かれていない欠け」が見えなくなります。
この研究の約束「解決できなかったものは『不明』として記録する。黙って安全側に倒さない」（`CLAUDE.md` の規則 4）を、木の単位で守るための欄です。

#### よくある誤解・つまずき

- **誤解: 「`truncations` が空なら、解析器は木の中を全部読んだ」**
  いいえ。`parse_failures` は別の欄です。ユニットの中の打ち切り（`cap_hits` の `depth` など。[第 15 章](ch15.md)）や、ユニットの `TRUNCATED(...)` の印（18.7 節）も別の所にあります。
- **誤解: 「`ast_node_cap` の `count` は、打ち切ったユニットの数」**
  いいえ。`ast_node_cap` の `count` は、そのファイルの構文木の節の数です。落ちるのは、そのファイルの中身の全部です。そこにツールの定義があればユニットも落ちますが、何個落ちたかは `count` からは分かりません（v4 では落ちていなかった）。
- **誤解: 「manifest の `fingerprint` に `MAX_DEPTH: 4` とあるから、この run は深さ 4 で走った」**
  深さの感度分析の run でも 4 と書かれます。`summary.json` の `max_depth` を見ます。
- **誤解: 「`run_meta` の秒数が違うから、2 つの run の結果は違う」**
  秒数はマシンの速さで変わります。結果が同じかは、`run_meta` を除いて比べます。

#### 手作業ではどう使うか

- **V1 頑健性の確認（段階 5）**: `parse_failures` と `truncations` の件数は、`summary.json` の `n_parse_failures`・`n_truncations` に木ごとに写されています（18.10 節）。まず `summary.json` で見て、0 でない木だけ manifest を開きます。
- **見落としの判定の前**: 抜き取られたユニットの道筋が、`parse_failures` や `ast_node_cap` のファイルの中に入っていくなら、解析器はそこを読んでいません。そのユニットの `notes` に `depends_on_dropped:<relpath>` の印があるかも見ます（18.7 節）。
- **深さの感度分析の run を読むとき**: 深さは manifest の `fingerprint` ではなく、`summary.json` の `max_depth` で確かめます。

#### この節のまとめ

manifest のいちばん外側は 12 個の欄。判定で読むのは主に `units` で、`truncations` と `parse_failures` も見落としと V1 の前に読む。
`ast_node_cap` のファイルは中身を丸ごと読んでいない。manifest の `fingerprint` は表の指紋と定数で、実際の深さは `summary.json` の `max_depth`。
`run_meta` は走らせるたびに変わる値だけを閉じ込めた欄。

### 18.3 ユニットの欄と、`D_kind` の正しい読み方

#### 一言で言うと

`units` の 1 要素が 1 ユニット（1 つのツール）です。
判定で読むのは、`unit`・`D_kind`・`effects`・`rows`・`notes`・`cap_hits`・`opaque_reasons`・`unresolved_in_tree_calls` の 8 つの欄です。
そのうち `D_kind` は、**どの宣言（D1〜D4）で照らすかを決める欄**です。
`D_kind.explicit` は「作者が書いたキーの一覧」ではありません。D3 は `closed_world`、D4 は `idempotent` という別の欄に出ます。

#### たとえ話 — カルテの欄

病院のカルテには、たくさんの欄があります。
今日の診察に要るのは、「名前と生年月日」「問診の結果」「検査の結果」「医師の所見」などの欄です。
昔の研究のために作られて、今は使っていない欄も残っています。
今日の診察では、要る欄だけを読み、要らない欄は読み飛ばします。

manifest のユニットも同じです。
核（宣言と効果の照合）に要る欄と、付録の仕組み（[第 8 章](ch08.md)）のための欄が混ざっています。
判定では、核の欄だけを読みます。

#### 小さな例 — ユニットの欄の一覧

v4 の 3,696 ユニットのすべてに出ていた欄と、一部のユニットにだけ出ていた欄を数えました（本書の執筆時に数えた）。

| 欄 | 出ていたユニット | 中身 | 核か | 詳しく |
|---|---|---|---|---|
| `unit` | 3,696（全部） | ツールの名前（`tool_name`）、関数の修飾名（`qualname`）、定義のファイル（`relpath`）と `def` の行（`lineno`）、宣言の原文（`annotations`）と書き方（`annotation_form`）、識別子（`unit_id`）など | 核 | [第 12 章](ch12.md) |
| `D_kind` | 3,696 | 解析器が宣言を**どう読み取ったか**のまとめ（下で詳しく） | 核 | [第 16 章](ch16.md) |
| `effects` | 3,696（空の列もある） | 見つけた効果の列（18.4 節） | 核 | 第 13〜15 章 |
| `rows` | 3,696（空の列もある） | 効果 × slot ごとの行。行ごとの `verdicts` と `notes`（18.5・18.6 節） | 核 | [第 17 章](ch17.md) |
| `notes` | 3,696（多くは空） | **ユニットの**注記。打ち切りの印 `TRUNCATED(...)` など（18.7 節）。行の `notes` とは別の欄 | 核 | この章 |

| `unresolved_in_tree_calls` | 3,696（2,173 で中身あり） | 名前が木の中の定義に当たるのに、どれか 1 つに決められなかった呼び出しの列 | 核（判定には使わない手がかり） | 第 15・35 章 |
| `db_unresolved` | 180 | 受け手の型を DB に決められなかった `.execute()` の記録。効果には数えていない | 手がかり | 第 13・15 章 |
| `annotation_typed` | 138 | 型注釈から受け手の型を与えた箇所 | 手がかり | [第 15 章](ch15.md) |
| `D_kind_by_tool`・`dispatch_join` | 2 | 低レベルの書き方で、1 つのハンドラが受け持つツールごとの `D_kind` | 核 | 第 12・16 章 |
| `trig`・`gate`・`gate_occ`・`gate_occ_by_effect`・`grades`・`req_occ`・`req_occ_by_effect`・`req_val`・`validator_shapes`・`config_atoms`・`alias_facts`・`gate_predicate_present`・`enforcement`・`d_prev_joined` | ほぼ全部 | 付録の仕組みの欄 | 付録 | [第 8 章](ch08.md)（**判定では読まない**） |

表の読み方: 1 行が 1 つの欄です。2 列目は、v4 の 3,696 ユニットのうち、その欄が出ていたユニットの数です。
たとえば 9 行目は「`db_unresolved` は 180 ユニットにだけ出ていた。`.execute()` という名前のメソッドを呼んでいるが、受け手が DB だと決められなかった所の記録で、効果には数えていない。見落としの判定で、DB の書き込みを探すときの手がかりになる」と読みます。
（出典: `evidence/scan_v2_v4_run1/` の 88 個の manifest（本書の執筆時に数えた）、`authgap/analyze.py:133-187`（ユニットの欄を書き出す `to_json`）、`authgap/analyze.py:104-106`（`db_unresolved` の説明「効果でも verdict でもない」））

#### 一歩ずつ — 「いつも出る欄」と「出ないことがある欄」

上の表で、ほとんどの欄は v4 の全部のユニットに出ていました。
けれども、解析器のコードを読むと、**出ないことがある欄**があります。

- `cap_hits`・`opaque_reasons`・`unresolved_in_tree_calls` は、値を追う解析が走ったときだけ書かれます。解析器が Python の再帰の上限で止まったユニット（`TRUNCATED(recursion)`。18.7 節）や、ユニットの定義のファイルが見つからなかったユニット（`notes` に `module unresolved`）では、この 3 つの欄そのものが**ありません**。v4 にはそういうユニットは 1 つもありませんでしたが、最終評価のデータで出ることはありえます。
- 行の `notes` も、注記が 1 つも無い行では欄そのものがありません（18.5 節）。

これは、判定の道具を作るときに効きます。
手順書の 6.5 節の道具は、`u["cap_hits"]` や `r["notes"]` のように、欄があると決めつけて読んでいます。
欄が無いと、Python は `KeyError` という例外で止まります。
道具を作るときは、`u.get("cap_hits", [])` や `r.get("notes", [])` のように、無いときの値を決めて読むのが安全です（[第 19 章](ch19.md)で道具を読むときに、もう一度見ます）。
（出典: `authgap/analyze.py:169-172`（`cap_hits`・`opaque_reasons` は値の解析があるときだけ）、`:203-206`（`module unresolved`）、`authgap/runner.py:154-157`（再帰で止まったユニットは注記だけの報告になる）、`authgap/verdict.py:74-75`（行の `notes` は空なら書かない）、`docs/final_evaluation_procedure.md:461-482`（6.5 の道具））

#### `D_kind` — 第 3 版の説明を直す

第 3 版の表は、`D_kind` を「読み取った宣言（`explicit` が明示された宣言）」と 1 行で説明していました。
これは**不正確**でした。
「明示された宣言」と読むと、「作者が書いたキーが全部 `explicit` に入る」と思ってしまうからです。

[第 16 章](ch16.md)で学んだ正確な説明を、ここで短く思い出します。

| 欄 | 中身 | 効く宣言 |
|---|---|---|
| `explicit` | **上界を動かす明示**の名前（`readOnlyHint: true`、`readOnlyHint: true` が無いときの `destructiveHint: false`）と、`openWorldHint: true` の名前。**入るのはこの 3 つだけ** | `readOnlyHint` があれば **D1**、`destructiveHint` があれば **D2** |
| `closed_world` | `openWorldHint: false` を明示したとき `true`（false なら欄が無い） | **D3** |
| `idempotent` | `idempotentHint: true` を明示し、`readOnlyHint: true` が無いとき `true`（そうでなければ欄が無い） | **D4** |
| `upper` | 宣言が許す効果の kind の上界。D1 なら `["FS_READ", "NET"]` | — |
| `bottom` | 上界が無いなら `true` | — |
| `present_no_bound` | 書いてあるが上界を動かさないキーの名前（`readOnlyHint: false`、`destructiveHint: true`、`readOnlyHint: true` と一緒の `destructiveHint: false`、`openWorldHint: false`、`idempotentHint`、`title`） | （記録だけ） |
| `open_world` | `openWorldHint: true` を明示したとき `true`（付録の仕組みのための印） | — |
| `malformed`・`unknown` | 届かない snake_case のキー・読めない形（[第 16 章](ch16.md) 16.8 節） | — |

表の読み方: 1 行が `D_kind` の 1 つの欄です。

（出典: `authgap/dparse.py:55-105`（`DKind` の欄と書き出し方）、`:179-237`（`d_kind_from`。キーごとの振り分け）。詳しくは[第 16 章](ch16.md) 16.2・16.3 節）

1. **`explicit` の `openWorldHint` は D3 ではありません。** `explicit` に入るのは、値が **true** の `openWorldHint: true`（外の世界と関わる、という申告）です。D3 は逆の `openWorldHint: false` で、`closed_world` に出ます。

`explicit` を「上界を動かす明示」に絞っているのは、仕様書が「上界を動かさないフィールドは D_kind を構成しない」と定めているからです。
`closed_world` と `idempotent` は、D3・D4 の判定規則を作ったとき（D56）に、上界とは別の欄として足されました。

この経緯のせいで、「`explicit` = 明示された宣言」という短い説明は、D3・D4 と `openWorldHint` の 3 か所で外れます。

#### よくある誤解・つまずき

- **誤解: 「`explicit` には、作者が書いたキーが全部入る」**
  入るのは `readOnlyHint`（true）・`destructiveHint`（false で、readOnly true が無いとき）・`openWorldHint`（true）の 3 つだけです。
- **誤解: 「`explicit` に `openWorldHint` がある = D3 のツール」**
  逆です。D3 は `closed_world: true` を見ます。
- **誤解: 「`closed_world` の欄が無いのは、解析器の書き忘れ」**
  `closed_world` と `idempotent` は true のときだけ書かれます。欄が無いのは false という意味です。
- **誤解: 「`D_explicit` が空の矛の行は、宣言の無いツールの行」**
  D3・D4 の矛では、`D_explicit` が空でも行が出ます。`declarations` を見ます。
- **誤解: 「`unit.annotations` に書いてあるとおりに照合される」**
  照合は `D_kind` で決まります。読めない形（`unknown: true`）のユニットは照合されません（[第 16 章](ch16.md)）。

#### 手作業ではどう使うか

- **手順 A**: 判定表の `decl` の欄（D1〜D4）と、原ソースの宣言を見比べます。`decl` が D3 なら原ソースに `openWorldHint=False`、D4 なら `idempotentHint=True` があり `readOnlyHint=True` が**無い**ことを確かめます。
- **手順 B**: 6.5 節の道具は、2 行目に「明示された宣言:」として `D_kind.explicit` を出します。D3・D4 の組では、ここにその宣言が出てこないのがふつうです。慌てずに、manifest の `D_kind` の `closed_world`・`idempotent` を見るか、「宣言:」の行（`annotations`）と原ソースで確かめます。

- **集計（段階 8）の注意**: 手順書は、主指標 (c) の分母を「その宣言を明示的に書いた（`D_kind.explicit`）ユニットを 1 つ以上持つ木」と書いています。D1・D2 はこれで数えられますが、D3・D4 は `explicit` に出ないので、この文面のままでは数えられません。`"openWorldHint" in explicit` で D3 を数えると、**反対の宣言のユニット**を数えてしまいます。D3・D4 の分母をどう数えるかは**未決**です（[第 16 章](ch16.md) 16.7 節、[第 46 章](ch46.md)）。

### 18.4 効果の欄と `entry_lineno`

#### 一言で言うと

`effects` の 1 要素が、解析器の見つけた 1 つの効果です。
効果には**位置が 2 つ**あります。
`relpath`・`lineno` は**効果そのもの**の位置で、`entry_lineno` は**ツールの本体の中で、その道筋の最初の呼び出しがある行**です。
判定の手順 D では、`entry_lineno` から始めて、`witness_chain` の関数を順に開いていきます。

#### たとえ話 — 宅配便の配達記録

宅配便の配達記録には、2 つの場所が書いてあります。
「荷物を受け付けた窓口」と「荷物を届けた家」です。
途中で通った中継所も、順に並んでいます。
荷物がどう運ばれたかを確かめたいときは、窓口から始めて、中継所を 1 つずつたどり、最後に家に着きます。

効果も同じです。
`entry_lineno` が「受け付けた窓口」（ツールの本体の中の行）、`witness_chain` が「中継所の列」（通った関数）、`relpath`・`lineno` が「届けた家」（効果そのものの行）です。

#### 小さな例 — 練習用のサーバの `search_notes`

練習用のサーバ（手順書 20.1 節。[第 11 章](ch11.md) 11.3 節）のコードの一部です。

```python
10  def _save_cache(name, text):
11      os.makedirs(CACHE_DIR, exist_ok=True)
12      with open(os.path.join(CACHE_DIR, name), "w") as fh:
13          fh.write(text)
 …
16  def _lookup(query):
17      conn = sqlite3.connect("notes.db")
18      rows = conn.execute("SELECT body FROM notes WHERE title = ?", (query,)).fetchall()
19      _save_cache(query, str(rows))
20      return rows
 …
23  @mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
24  def search_notes(query: str) -> str:
25      """Search notes."""
26      return str(_lookup(query))
```

このサーバを凍結版の解析器で走らせると、`search_notes` の 12 行の書き込みの効果は、次のように書き出されました（slot の `shape` を省いた）。

```json
{
  "kind": "FS_WRITE",
  "site": "builtins.open",
  "form": "direct",
  "relpath": "server.py",
  "lineno": 12,
  "entry_lineno": 26,
  "witness_chain": ["_lookup", "_save_cache"],
  "slots": {"path": {"prin": "MODEL", "prov": "resolved", "roots": ["query"]}},
  "resolution": "resolved",
  "sub_kind": "FS_WRITE",
  "destructive": true,
  "fs_mode": "w",
  "required_by": ["P0"]
}
```

（出典: `docs/final_evaluation_procedure.md:1182-1239`（練習用のサーバ）。出力は本記録者が凍結版の解析器で走らせて確かめた（2026-10-01））

#### 一歩ずつ — 効果の欄を 1 つずつ

まず、コードの行の意味です。

- 24〜26 行目: ツールの本体です。26 行目で `_lookup(query)` を呼びます。
- 16〜20 行目: `_lookup` は、18 行目で DB を読み、19 行目で `_save_cache` を呼びます。
- 10〜13 行目: `_save_cache` は、11 行目でフォルダを作り、12 行目でファイルを `"w"`（書き出し）で開きます。

次に、JSON の欄の意味です。

- `"kind": "FS_WRITE"`: 効果の種類はファイルの書き込みです（[第 13 章](ch13.md)）。
- `"site": "builtins.open"`: 効果を起こす関数は、Python の組み込みの `open` です。
- `"form": "direct"`: sink を関数の名前で決めた、という印です（`proxy` は受け手の型で決めたもの、`pipe` は起動した子プロセスへの流し込み。[第 13 章](ch13.md)）。
- `"relpath": "server.py"`・`"lineno": 12`: **効果そのもの**の位置です。`_save_cache` の中の 12 行目です。
- `"entry_lineno": 26`: **ツールの本体の中で、この道筋の最初の呼び出しがある行**です。本体が `_lookup` を呼ぶ 26 行目です。
- `"witness_chain": ["_lookup", "_save_cache"]`: 本体から効果までに通った関数の列です。本体 → `_lookup`（深さ 1）→ `_save_cache`（深さ 2）の中で効果が起きる、と読みます（[第 15 章](ch15.md)）。
- `"slots"`: slot ごとの値です。`path` の主体は `MODEL`（LLM が渡す引数から来る）、確度は `resolved`（読み切れた）、根は `query`（ツールの引数 `query` から来た）です（[第 14 章](ch14.md)）。
- `"resolution": "resolved"`: 効果そのものに届いた道筋の確度です。道筋の途中で呼び出し先を見失っていれば `opaque` になり、理由が `resolution_reasons` に入ります。
- `"sub_kind": "FS_WRITE"`: kind をもう少し細かく分けたものです（[第 13 章](ch13.md) 13.3 節）。
- `"destructive": true`: `FS_WRITE` にだけ付く印です。`true` は削除・上書き型、`false` は追記型、`null` は分からない、です（[第 13 章](ch13.md) 13.9 節）。
- `"fs_mode": "w"`: 開くモードです。定数に読めたときだけ付きます（[第 13 章](ch13.md) 13.10 節）。
- `"required_by": ["P0"]`: この効果が、sink 表のどの行に頼っているかの印です（参考）。

#### 効果の欄の一覧と、出るとき

効果の欄には、いつも出る欄と、条件があるときだけ出る欄があります。
v4 の 10,973 個の効果で、欄ごとに出ていた数を数えました（本書の執筆時に数えた）。

| 欄 | v4 で出ていた効果の数（分母 10,973） | 出る条件・中身 |
|---|---|---|
| `kind`・`site`・`form`・`relpath`・`lineno`・`entry_lineno`・`slots`・`resolution` | 10,973（全部） | いつも出る |
| `witness_chain` | 10,731 | 効果が本体の外（呼び出し先）にあるときだけ。**欄が無ければ、効果はツールの本体の中にある** |
| `sub_kind` | 10,175 | kind を細かく分けられたとき |
| `resolution_reasons` | 8,422 | `resolution` が `resolved` でないとき、その理由 |
| `required_by` | 6,594 | sink 表の行に頼っているとき（参考） |
| `destructive` | 4,293 | kind が `FS_WRITE` のとき（値は `true` / `false` / `null`） |
| `db_rule` | 2,123 | DB の効果を決めた機械の規則（参考） |
| `http_method` | 1,657 | HTTP のメソッドが読めたとき（`GET`・`POST` など） |
| `shape_from` | 1,561 | slot の形が型注釈から来たとき（参考） |

たとえば 2 行目は「`witness_chain` は 10,973 個のうち 10,731 個の効果に出ていた。出ていない 242 個は、効果がツールの本体の中にある。手順 D では、道筋をたどらずに本体を読めばよい」と読みます。
（出典: `authgap/effects.py:60-108`（`Effect` の欄の定義と説明）、`:110-146`（`to_json`。条件つきで欄を書く所）、`evidence/scan_v2_v4_run1/` の manifest（本書の執筆時に数えた））

#### `entry_lineno` — 道筋の入口の行

`entry_lineno` を、もう少し丁寧に見ます。
手順書の用語の表は、`entry_lineno` を「**ツールの本体の中で、その道筋の最初の呼び出しがある行**」と定義しています。
解析器の側の説明は、「`lineno` は効果そのものの行（別ファイルでありうる）、`entry_lineno` は入口から見た呼び出し位置」です。
2 つの説明は同じことを言っています。

同じ練習用のサーバの `export_note` で比べてみます。

```python
29  @mcp.tool(annotations=ToolAnnotations(destructiveHint=False))
30  def export_note(path: str, body: str) -> str:
31      """Export a note to a file."""
32      with open(path, "w") as fh:
33          fh.write(body)
34      return "ok"
```

この 32 行の書き込みの効果は、`lineno` も `entry_lineno` も 32 で、`witness_chain` の欄がありませんでした。
効果が本体の中にあるので、「道筋の最初の呼び出し」が効果そのものの行になるのです。

`search_notes` と `export_note` を並べます。

| ツール | 効果の `lineno` | `entry_lineno` | `witness_chain` | 読み方 |
|---|---|---|---|---|
| `search_notes` | 12 | 26 | `["_lookup", "_save_cache"]` | 本体の 26 行から 2 段降りた 12 行 |
| `export_note` | 32 | 32 | （欄が無い） | 本体の中の 32 行 |

表の読み方: 1 行が 1 つの効果です。
1 行目は「`search_notes` の書き込みは 12 行にあるが、ツールの本体の中でその道筋が始まるのは 26 行。そこから `_lookup`、`_save_cache` の順に降りる」と読みます。
（出典: `docs/final_evaluation_procedure.md:98`（`entry_lineno` の定義）、`:1444`（「`witness_chain` が無い効果」は本体の中）、`authgap/effects.py:68-71`（解析器の側の説明）。出力は本記録者が走らせて確かめた）

#### 同じ効果に、別の道筋で何度も届く

**同じ位置の効果に、別の道筋で届くと、`entry_lineno` や `witness_chain` だけが違う要素が、`effects` にいくつも並びます。**
v4 の bugasura の木の `update_project`（ツールの名前は `bugasura_update_project`）がその例です。
同じ `client.py:482` の `httpx.AsyncClient.request`（HTTP の送信。`NET`）に、5 つの要素が並んでいました。

| `entry_lineno` | `witness_chain` | `http_method` | `url.path` の値 |
|---|---|---|---|
| 388 | `validate_api_key` → `make_api_request` | `GET` | `/v1/teams/get` |
| 405 | `find_project_by_name` → `_fetch_user_context` → `make_api_request` | `GET` | `/v1/teams/get` |
| 405 | `find_project_by_name` → `_fetch_user_context` → `make_api_request` | `GET` | `/v1/teams/getApps` |
| 432 | `list_teams` → `make_api_request` | `GET` | `/v1/teams/get` |
| 483 | `make_api_request` | `POST` | `/v1/projects/update` |

表の読み方: 1 行が `effects` の 1 要素です。
たとえば 5 行目は「本体の 483 行で `make_api_request` を直接呼び、その中の `client.py:482` で `/v1/projects/update` へ `POST` を送る道筋」と読みます。
5 つのうち 4 つは `GET`（読むだけの問い合わせ）で、1 つだけが `POST` です。
2 行目と 3 行目は、`entry_lineno` も `witness_chain` も同じですが、`url.path` の値が違います。同じ道筋の途中で、`make_api_request` が 2 回、別の宛先で呼ばれているためです。
（出典: `evidence/scan_v2_v4_run1/v4-appachhi__bugasura-mcp-server.json` の `update_project`（本書の執筆時に確かめた）、`corpus/v4-appachhi__bugasura-mcp-server/auth.py:124, 145`（`_fetch_user_context` の中の 2 回の呼び出し））

このように、**効果の要素の数は「操作の数」ではありません**。
1 つの操作に、道筋の数だけ要素が並びます。
これが、18.8 節で「組」にまとめる理由の 1 つです。

#### 効果の数と、一意の効果の数

`summary.json` には、効果の数が 2 通り書かれています（18.10 節）。
`n_effects` は要素をそのまま数えた数、`n_effects_unique` は**中身がすべて同じ要素**を 1 つにまとめた数です。
v4 では、`n_effects` が 10,973、`n_effects_unique` が 8,365 でした。

極端な例が、v2 の run24 の teamplay-talk の木の `apply_daily_checkin`（qualname は `register.apply_daily_checkin`）です。
このツールの `httpx.AsyncClient.request` の効果は、`effects` に 8 つ並んでいました。
8 つは、`entry_lineno`（728）も `witness_chain`（`clear_todo` → `_delete` → `delete_task`）も含めて、**全部同じ中身**でした。
一意に数えると 1 つです。
解析器は同じ効果を重ねて書き出すことがあり、それを解析器の側では畳まず、数えるときに一意の数を併記する、と決めています（D64 の U32）。
（出典: `scripts/scan_v2.py:25, 108-124`（一意の数え方）、`docs/decisions.md:3580`（U32「解析器は変えない」）、`evidence/scan_v2_v4_run1/summary.json`、`evidence/scan_v2_run24/v2-hbg1345__teamplay-talk.json`（本書の執筆時に確かめた））

#### なぜそうするのか

**位置を 2 つ持つ理由**は、効果がツールの本体の外にあることが多いからです。
v4 では、効果の約 97.8%（10,973 個のうち 10,731 個）に `witness_chain` があり、本体の外で起きていました。
効果の位置（`lineno`）だけでは、「ツールのどの行から、そこへ行くのか」が分かりません。
`entry_lineno` があれば、ツールの本体のどの行から読み始めればよいかが分かります。
解析器の側でも、`entry_lineno` は「支配判定」（付録の仕組み。ある行の前に必ず検査が通るか）に使う行です。

**同じ効果を道筋ごとに別の要素にする理由**は、道筋ごとに条件や値が違いうるからです。
bugasura の例では、同じ `client.py:482` でも、道筋によって `GET` と `POST` が分かれていました。
道筋をまとめてしまうと、どの道筋が `POST` を送るのかが分からなくなります。
（出典: `authgap/effects.py:68-71`（「支配判定は後者で行う」））

#### よくある誤解・つまずき

- **誤解: 「`lineno` はツールの行」**
  `lineno` は効果そのものの行で、別のファイルのこともあります。ツールの行は `unit.lineno`、本体の中の入口の行は `entry_lineno` です。
- **誤解: 「`effects` の要素の数 = そのツールの危ない操作の数」**
  同じ操作に、道筋の数だけ要素が並びます。中身が全部同じ要素が重なることもあります。
- **誤解: 「`witness_chain` が無いのは、解析器が道筋を記録し忘れたから」**
  欄が無いのは、効果が本体の中にあるという意味です。
- **誤解: 「`destructive` の欄が無い効果は、壊さない効果」**
  `destructive` は `FS_WRITE` にだけ付く欄です。`NET` や `DB` には、そもそも付きません。
- **誤解: 「`http_method` が無い `NET` の効果は、`GET`」**
  `http_method` は読めたときだけ付きます。無ければ「読めなかった」で、`GET` とは限りません。

#### 手作業ではどう使うか

- **手順 C**: `locations` の位置（効果そのものの `relpath:lineno`）を開き、本当にその操作かを確かめます。`fs_mode`・`http_method`・`sql_head` があれば、解析器がどう読んだかの手がかりになります。ただし、判定は自分で原ソースを読んで行います。
- **手順 D**: ツールの関数（`unit_relpath:unit_lineno`）を開き、`entry_lineno` の行から、`witness_chain` の関数を順に開いていきます。手順書の例では「`witness_chain = _lookup -> _save_cache` なら、本体の 26 行目で `_lookup` を呼び、`_lookup` の中で `_save_cache` を呼び、`_save_cache` の中の 12 行目が効果」です。根拠として、たどった各段のファイルと行を書き留めます。
- **道筋が何本もあるとき**: 同じ組の効果に道筋が何本もあれば、どの道筋で判定したかを `note` に書きます。bugasura の例のように、道筋によって動作（`GET` と `POST`）が違うことがあります。

（出典: `docs/drafts/final_judging_guide_draft.md:113-141`（手順 C・D）、`docs/final_evaluation_procedure.md:801-810`）

#### この節のまとめ

効果には、効果そのものの位置（`relpath`・`lineno`）と、本体の中の入口の行（`entry_lineno`）の 2 つの位置がある。`witness_chain` が無ければ効果は本体の中。
同じ効果に別の道筋で届くと、`effects` に要素がいくつも並ぶ。要素の数は操作の数ではない。中身が全部同じ要素もあり、`n_effects_unique` で一意に数える。
手順 D は `entry_lineno` から `witness_chain` を順にたどる。

### 18.5 行（`rows`）と `verdicts` — 核の「不」は `verdicts` に出ない

#### 一言で言うと

`rows` は、**効果 1 つの slot 1 つごとに 1 行**の表です。
行には `verdicts`（判定の名前の一覧）と `notes`（注記）の 2 つの欄があります。
核の答えのうち、**矛は `notes` の `contradiction:<宣言>` で、不は `notes` の `contradiction_unknown:<宣言>:<理由>` で読みます。**
`verdicts` の `UNKNOWN` は付録の判定で、核の「不」とは**別物**です。

#### たとえ話 — 2 つの欄がある点検表

ある建物の点検表を思い浮かべてください。
部屋ごと、窓ごとに 1 行あり、各行に欄が 2 つあります。

- 左の欄は、**昔の点検の基準**の印です。「A」「B」「判定不能」などが書いてあります。昔の点検をした人が作った欄で、今の点検の主な結果ではありません。
- 右の欄は、**今の点検の所見**です。「掲示に反する」「調べないと決められない」と、理由つきで書いてあります。

左の欄の「判定不能」と、右の欄の「調べないと決められない」は、言葉が似ています。
けれども、意味が違います。
左は「昔の基準で測る値が読み取れなかった」、右は「掲示に反するかどうかが決まらない」です。
値は読み取れても掲示に反するかが決まらないこともあれば、値が読み取れなくても掲示に反するのが確かなこともあります。

manifest の行の `verdicts` が左の欄、`notes` の `contradiction…` が右の欄にあたります。

#### 小さな例 — v4 の gemini の `gemini_prompt` の行

v4 の gemini の木の `gemini_prompt`（宣言は `readOnlyHint: true` ほか。効く宣言は D1 だけ。18.3 節）には、効果が 2 つあります。

- 195 行の `asyncio.create_subprocess_exec`（子プロセスの起動。`SPAWN`）。slot は `argv0`・`argv[*]`・`cwd`・`env` の 4 つ。
- 204 行の `pipe:communicate`（起動した子プロセスに文字を流し込む。`FS_WRITE` として数えられる）。slot は `content` の 1 つ。

行は 4 + 1 = **5 行**です（`summary.json` の、この木の `n_rows` の 5 と一致します）。
そのうち 2 行を、欄を減らして写します。

```json
{"site": "asyncio.create_subprocess_exec", "kind": "SPAWN", "slot": "argv0",
 "relpath": "server.py", "lineno": 195,
 "verdicts": ["GAP_INJECT", "UNKNOWN"],
 "notes": ["select_manifest_only(assumed_trig)",
           "contradiction_unknown:D1:spawn_model_opaque"]}

{"site": "pipe:communicate", "kind": "FS_WRITE", "slot": "content",
 "relpath": "server.py", "lineno": 204,
 "verdicts": ["CONTRADICTION", "GAP_INJECT", "UNKNOWN"],
 "notes": ["select_manifest_only(assumed_trig)",
           "contradiction:D1", "contradiction_reason:D1:fs_write"]}
```

（出典: `evidence/scan_v2_v4_run1/v4-ankitdotgg__making-gemini-useful-with-claude.json` の `gemini_prompt` の `rows`、`evidence/scan_v2_v4_run1/summary.json` の、この木の `n_rows`（本書の執筆時に確かめた））

#### 一歩ずつ — 2 つの行を読む

**1 つ目の行（195 行の起動）**:

- `"site"`・`"kind"`・`"slot"`: どの効果の、どの位置の行かです。`argv0` は「起動するコマンドの名前」の位置です。
- `"relpath"`・`"lineno"`: 効果そのものの位置です。効果の欄と同じです。
- `"verdicts": ["GAP_INJECT", "UNKNOWN"]`: 付録の判定が 2 つ付いています。`CONTRADICTION` はありません。
- `"notes"` の 1 つ目 `select_manifest_only(assumed_trig)`: 付録の仕組みの注記です。読み飛ばします。
- `"notes"` の 2 つ目 `contradiction_unknown:D1:spawn_model_opaque`: **核の答え**です。D1 について**不**で、理由は `spawn_model_opaque`（起動するコマンドに LLM の値が流れ込むが、LLM が選べるとまでは読み切れない）です。

**2 つ目の行（204 行の流し込み）**:

- `"verdicts": ["CONTRADICTION", "GAP_INJECT", "UNKNOWN"]`: `CONTRADICTION` があります。`UNKNOWN` も付いています。
- `"notes"` の `contradiction:D1` と `contradiction_reason:D1:fs_write`: **核の答え**です。D1 について**矛**で、理由は `fs_write`（ファイルの書き込み）です。

ここで大事なのは、**矛の行にも `UNKNOWN` が付いている**ことです。
「`UNKNOWN` があるから不」ではありません。
1 つ目の行が不なのは、`UNKNOWN` があるからではなく、`notes` に `contradiction_unknown:` があるからです。

なお、2 つ目の行が本当に違反か（人の判定で正か誤か）は、別の話です。
`pipe:communicate` は子プロセスの標準入力への書き込みで、ファイルの書き込みとは限りません（誤の原因 E5。[第 8 章](ch08.md) 8.6 節、[第 51 章](ch51.md)）。
ここでは、欄の読み方の例としてだけ使います。

#### 行の欄の一覧

| 欄 | 中身 | 判定で読むか |
|---|---|---|
| `unit_id` | どのユニットの行か | 参考 |
| `kind`・`site`・`form` | どの効果の行か（効果の欄と同じ値） | 読む |
| `relpath`・`lineno` | 効果そのものの位置 | 読む |
| `slot` | どの位置の行か（slot の無い効果の行には、この欄が無い） | 読む |
| `notes` | 注記の列。**核の答え（`contradiction` で始まるもの）はここ**。注記が無い行には、この欄が無い | **読む** |
| `verdicts` | 判定の名前の列（下の表）。`CONTRADICTION` だけが核で、ほかは付録 | `CONTRADICTION` の有無だけ |
| `covered_by`・`D_layer_present`・`rule_w` | 付録の仕組みの欄 | 読まない |

表の読み方: 1 行が行（`rows` の要素）の 1 つの欄です。
たとえば 5 行目は「`notes` が核の答えの置き場所。ただし注記が 1 つも無い行では、`notes` の欄そのものが無い」と読みます。
v4 では、15,630 行のうち 185 行に `notes` の欄がありませんでした（本書の執筆時に数えた）。
（出典: `authgap/verdict.py:41-76`（`Row` の欄と書き出し方）、`evidence/scan_v2_v4_run1/`（本書の執筆時に数えた））

#### 行の数は「効果 × slot」で増える

行は、効果の slot ごとに 1 行ずつ作られます。
slot の無い効果は 1 行です。
`verdicts` も `notes` も空になる行は書き出されませんが、v4 ではそういう行は 1 つもありませんでした。
v4 の全部の効果について「slot の数（無ければ 1）」を足すと 15,630 になり、`summary.json` の `n_rows` の 15,630 とちょうど一致しました（本書の執筆時に数えた）。

ですから、**行の数を数えても「違反がいくつあるか」にはなりません。**
`SPAWN` の効果 1 つは 4 行になり、同じ効果に道筋が 5 本あれば、その 5 倍になります。
（出典: `authgap/verdict.py:133-185`（`decide`。slot ごとに行を作る）、`evidence/scan_v2_v4_run1/summary.json` の `n_rows`）

#### `verdicts` に入る名前

`verdicts` に入る名前は、解析器の語彙として 6 つ決まっています。

| verdict | 意味 | 位置づけ |
|---|---|---|
| `CONTRADICTION` | その効果が、明示された宣言の**どれか**に反する | **核**（ただし、どの宣言かは `notes` で読む） |
| `GAP_INJECT` | 危険な slot に、検査で絞られていない LLM の値が入る | 付録 |
| `GAP_SELECT` | 危険な効果を実行するかどうかを LLM が選べる | 付録 |
| `UNKNOWN` | その行の効果の確度か、その slot の値の確度が `resolved` でない | 付録 |
| `INVENTORY` | 運用者の許可の一覧などで覆われている | 付録 |
| `GAP_DRIFT` | 前の版の manifest と比べて変わった（前の版を渡したときだけ） | 付録（v4 では 0 行） |

表の読み方: 1 行が 1 つの verdict の名前です。
たとえば 4 行目は「`UNKNOWN` は、その行の効果か slot の値を、解析器が読み切れなかった（確度が `resolved` でない）という付録の印。宣言に反するかどうかとは関係ない」と読みます。
`GAP_DRIFT` は、前の版の manifest を解析器に渡したときだけ出ます。`scripts/scan_v2.py` は前の版を渡さないので、走査の結果には出ません。
（出典: `authgap/verdict.py:24-32`（verdict の語彙）、`:151`（矛の印は宣言を区別しない 1 つの印）、`:172, 181`（`UNKNOWN` を付ける条件）、`:212-215`（`GAP_DRIFT`）、`authgap/analyze.py:606-611`（前の版との比べ）。付録の判定の意味は[第 8 章](ch08.md) 8.6 節）

#### `verdicts` の欄と、核の「不」は別物

ここが、この章でいちばん取り違えやすい点です。
[第 8 章](ch08.md) 8.6 節で予告したことを、もう一度整理します。

- **核の答えは矛・不・内の 3 つ**です（第 11・17 章）。
- **矛**は、`verdicts` に `CONTRADICTION` が入り、**同時に** `notes` に `contradiction:<宣言>` と `contradiction_reason:<宣言>:<理由>` が付きます。
- **不は `verdicts` には出ません。** 不は、行の `notes` の **`contradiction_unknown:<宣言>:<理由>`** という注記にしか現れません。
- **内はどこにも書かれません。** その宣言について、矛の注記も不の注記も無いことが、内です。
- `verdicts` の **`UNKNOWN` は付録の判定**で、核の「不」とは関係ありません。名前が似ているだけです。第 3 版の verdict の表（第 3 版 1101 行）にあった `UNKNOWN` も、この付録の判定のことです。

実物の数で確かめます。
v4 の 88 個の manifest のすべての行を読み、`notes` と `verdicts` を数えました（本書の執筆時に数えた。分母は v4 の全部の行 15,630）。

| 行の種類 | 行の数 | その行の `verdicts` の内訳 |
|---|---|---|
| 不の注記（`contradiction_unknown:`）を持つ行 | 3,763 | `UNKNOWN` だけ 2,716 / **空** 862 / `GAP_INJECT` と `UNKNOWN` 174 / `INVENTORY` と `UNKNOWN` 10 / `GAP_INJECT` だけ 1 |
| 矛の注記（`contradiction:`）を持つ行 | 2,707 | 全部に `CONTRADICTION` がある。そのうち 2,382 には `UNKNOWN` も付く |
| `verdicts` に `UNKNOWN` がある行（`summary.json` の `verdict_rows`） | 11,937 | — |

表の読み方: 1 行目は「不の注記を持つ行は 3,763 行あった。そのうち 862 行は `verdicts` が空で、1 行は `GAP_INJECT` だけだった。つまり 863 行の不は、`verdicts` の `UNKNOWN` を数えても見つからない」と読みます。
3 行目からも分かるとおり、`UNKNOWN` の行（11,937）は不の注記を持つ行（3,763）よりずっと多く、`UNKNOWN` を数えても不の数にはなりません。

もう 1 つ、木の単位の例があります。
v4 の bugasura の木は、`summary.json` の木ごとの `verdicts` が `{}`（空）でした。
けれども、18.4 節で見た `update_project` の行には、D2 と D4 の不の注記が付いていました。
**`verdicts` の数だけを見ていると、この木の不はまるごと見えません。**
（出典: `evidence/scan_v2_v4_run1/` の manifest と `summary.json`（本書の執筆時に数えた））

#### なぜそうするのか

`verdicts` の `CONTRADICTION` は、「この効果は、宣言の**どれか**に反する」という 1 つの印です。
どの宣言に反したのかを区別しません。
一方、この研究は D1〜D4 を**宣言ごとに**報告すると決めています（D62）。
同じ効果が、D1 では内、D3 では矛、ということもあります。
だから、宣言ごとの答え（矛か不か）と理由は、`notes` にだけ、宣言の名前つきで書くようにしました（D56）。
`UNKNOWN` を含む付録の判定は、最初の計画（[第 8 章](ch08.md)）の名残で、解析器は今も出しますが、論文の主張の中心ではありません。
（出典: `docs/decisions.md:3511`（D62）、`authgap/verdict.py:158-163`（宣言ごとの結果を注記に残す所。「D56。宣言ごとに分けて数えるため」））

#### よくある誤解・つまずき

- **誤解: 「`verdicts` に `UNKNOWN` があれば、その行は不」**
  違います。不は `notes` の `contradiction_unknown:` で決まります。v4 では矛の行の 2,382 行にも `UNKNOWN` が付いていました。
- **誤解: 「`verdicts` が空なら、その行には何も無い」**
  違います。v4 では、不の注記を持つ行のうち 862 行の `verdicts` が空でした。
- **誤解: 「`verdict_rows` の `UNKNOWN` の数 = 不の数」**
  違います。11,937 と 3,763 で、まったく別の数です。
- **誤解: 「行の数 = 違反の数」**
  行は slot ごと・道筋ごとに増えます。数える単位は組です（18.8 節）。
- **誤解: 「`CONTRADICTION` があれば、D1 の矛」**
  どの宣言の矛かは、`notes` の `contradiction:<宣言>` で読みます。

#### 手作業ではどう使うか

- **手順 B**: 手順書の 6.5 節の道具は、行ごとに次の 1 行で、核の注記だけを取り出しています。

  ```python
  marks = [n for n in r["notes"] if n.startswith("contradiction")]
  ```

  `r["notes"]` はその行の注記の列、`n.startswith("contradiction")` は「`contradiction` で始まるものだけ残す」です。これで `contradiction:`・`contradiction_reason:`・`contradiction_unknown:` の 3 種類が残り、`select_manifest_only(...)` などの付録の注記は捨てられます。`verdicts` は見ていません。ただし、18.3 節で見たとおり、`notes` の欄が無い行で止まらないよう、道具を作るときは `r.get("notes", [])` にしておくのが安全です。
- **不を数える・不の組を選ぶとき**: `notes` の `contradiction_unknown:` を数えます。`verdicts` の `UNKNOWN` を数えてはいけません。解析器の側の宣言ごとの集計（`scripts/contradiction_by_decl.py`）も、行の注記だけを読んで矛・不を決めています。
- **見落としの判定の 4 番目の段**: 「ここで初めて解析器の出力を見る（対象の宣言の `contradiction_unknown:<宣言>:…` の注記を探す）」とあります。探すのは `verdicts` ではなく `notes` です。

（出典: `docs/final_evaluation_procedure.md:480-482`（道具の該当行）、`scripts/contradiction_by_decl.py:40-57`（`load_reasons`）、`docs/drafts/final_judging_guide_draft.md:455`（見落としの手順の 4））

#### この節のまとめ

行は効果 × slot ごと（v4 は 15,630 行）。行には `verdicts`（付録の判定と `CONTRADICTION`）と `notes`（核の注記）がある。
核の矛は `notes` の `contradiction:<宣言>`、核の不は `notes` の `contradiction_unknown:<宣言>:<理由>` にしか出ない。内は書かれない。
`verdicts` の `UNKNOWN` は付録の判定で、矛の行にも付く。v4 では不の行のうち 863 行は `UNKNOWN` を持たなかった。不は `notes` で数える。

### 18.6 行の注記の 3 種類 — 矛・矛の理由・不

#### 一言で言うと

行の `notes` のうち、核の判定に関わるのは **`contradiction` で始まる 3 種類**だけです。
`contradiction:<宣言>` は**矛**、`contradiction_reason:<宣言>:<理由>` は**その矛の理由**、`contradiction_unknown:<宣言>:<理由>` は**不とその理由**です。
ほかの注記は付録の仕組みのもので、読み飛ばします。

#### たとえ話 — 診断書の書き方の決まり

病院の診断書に、決まった書き方があるとします。
「診断: 骨折」と書いたら、必ず次の行に「根拠: レントゲン」と書く。
「診断保留: 検査待ち」のように、決められなかったときは 1 行で理由まで書く。
何も問題が無いときは、何も書かない。

解析器の注記も、この決まりに従っています。
矛は「診断」と「根拠」の 2 行の対、不は「診断保留」の 1 行、内は何も書かない、です。

#### 小さな例 — 3 種類の注記

| 注記の形 | 意味 | 例 | 核の答え |
|---|---|---|---|
| `contradiction:<宣言>` | この行は、その宣言に反する | `contradiction:D1` | **矛** |
| `contradiction_reason:<宣言>:<理由>` | 上の矛の理由のコード（同じ 1 つの矛の説明。別の矛ではない） | `contradiction_reason:D1:fs_write` | （矛の理由） |
| `contradiction_unknown:<宣言>:<理由>` | 反するかどうかが静的に決められない。理由のコードつき | `contradiction_unknown:D1:spawn_model_opaque` | **不** |

表の読み方: 1 行が 1 種類の注記です。
たとえば 3 行目は「`contradiction_unknown:D1:spawn_model_opaque` という注記があれば、その行は D1 について不で、理由は `spawn_model_opaque`」と読みます。

#### 一歩ずつ — 注記を分解する

注記は、コロン（`:`）で区切られた 2 つか 3 つの部分でできています。
1 つ分解してみます。

```
contradiction_unknown : D1 : spawn_model_opaque
└─ 種類（不）           └ 宣言 └ 理由のコード
```

- 1 つ目の部分は**種類**です。`contradiction`（矛）、`contradiction_reason`（矛の理由）、`contradiction_unknown`（不）のどれかです。
- 2 つ目の部分は**宣言**です。`D1`〜`D4` のどれかです。
- 3 つ目の部分は**理由のコード**です。`contradiction:` には 3 つ目がありません。

理由のコードの意味は、[第 17 章](ch17.md)で判定表と一緒に学びました。
手順書の 13.1 節にも一覧表があります。
たとえば `…_opaque` で終わる理由は、「モデル（LLM）の値が**流れ込む**が、モデルが**選べる**とまでは読み切れない」という意味です。
[第 17 章](ch17.md)の原理 3 で、「選べる」= 主体が `MODEL` **かつ** 確度が `resolved`、と決めたことの表れです。
（出典: `authgap/verdict.py:158-163`（注記を作る所）、`docs/final_evaluation_procedure.md:864-894`（13.1 の理由コードの表。`…_opaque` は `:894`））

#### 注記の 3 つの決まり

**決まり 1: 矛の 2 つの注記は、必ず対で出ます。**
解析器は、ある宣言について矛と判定すると、`contradiction:<宣言>` と `contradiction_reason:<宣言>:<理由>` を**同時に**足します。
v4 でも、`contradiction:` を持つ行と `contradiction_reason:` を持つ行は、どちらも 2,707 行で、行ごとに必ずそろっていました（本書の執筆時に数えた）。
判定表の `reasons` の欄は、この理由のコードを写したものです。

**決まり 2: 不の注記は 1 つだけです。**
不には「`contradiction_unknown:`」の 1 種類しかありません。
理由は、その注記の 3 つ目の部分に入っています。

**決まり 3: 1 つの行に、別々の宣言の注記が並ぶことがあります。**
1 つの効果が、2 つ以上の宣言で照らされるときです（[第 16 章](ch16.md) 16.5 節）。
たとえば v4 の bugasura の木の `update_project`（宣言は D2 と D4）の `POST` の行には、次の 2 つが並んでいました。

```
contradiction_unknown:D2:net_post
contradiction_unknown:D4:net_nonidempotent_method
```

D2 については不（`POST` が相手の状態をどう変えるかは静的に決まらない）、D4 についても不（`POST` は繰り返して同じ結果になるとは限らない）です。
**宣言ごとに別々に読みます。**
v4 では、2 つ以上の宣言の注記が並んだ行が 904 行ありました（D1 と D3 が 784 行、D2 と D4 が 88 行、D2 と D3 が 28 行、D2・D3・D4 が 4 行。どれも不の注記。本書の執筆時に数えた）。
（出典: `authgap/verdict.py:158-163`、`evidence/scan_v2_v4_run1/v4-appachhi__bugasura-mcp-server.json`、`evidence/scan_v2_v4_run1/` の manifest（本書の執筆時に数えた））

#### 核ではない注記

行の `notes` には、`contradiction` で始まらない注記も出ます。
v4 で多かったのは次の 2 つです（本書の執筆時に数えた）。

- `select_manifest_only(assumed_trig)`: 15,435 行。付録の SELECT の座標の注記です（[第 8 章](ch08.md)）。
- `D_layer_present:…`（例 `D_layer_present:kind:FS_WRITE`）: 334 行。付録の仕組みの、宣言の層の記録です。

どちらも、**核の判定では読みません**。
手順書の道具も、`contradiction` で始まる注記だけを取り出します（18.5 節）。

#### なぜそうするのか

**矛に理由のコードを付ける理由**は、人が確かめるときの手がかりにするためと、感度分析のためです。
理由のコードは、判定表のどの分岐を通ったかを表します。
ですから、「原理を 1 つ反対にしたら、矛がいくつ増減するか」を、走査をやり直さずに注記だけから計算できます（[第 17 章](ch17.md)の感度分析）。

**不にも理由を付ける理由**は、不の中身を確かめるときに、何を調べればよいかが理由で決まるからです。
`net_post` なら相手の API の意味を、`spawn_command` なら起動するコマンドの中身を、`fs_writeout` なら書き先に前からファイルがありうるかを調べます（手引きの 18A.2）。

**内に何も書かない理由**は、内が「矛でも不でもない」という残りだからです。
内を書くと、行ごと・宣言ごとに大量の注記が増えるだけで、新しい情報になりません。
（出典: `scripts/contradiction_by_decl.py:18-24`（理由のコードから感度分析を出す説明）、`docs/drafts/final_judging_guide_draft.md:500-515`（18A.2 の理由ごとの調べ方））

#### よくある誤解・つまずき

- **誤解: 「`contradiction_reason:` を、もう 1 つの矛として数える」**
  `contradiction_reason:` は、同じ矛の理由の説明です。数えるときは、矛 1 つにつき 1 回です。
- **誤解: 「1 つの行には、宣言の注記が 1 つだけ」**
  宣言が 2 つ以上当たるツールでは、1 行に別々の宣言の注記が並びます。
- **誤解: 「理由のコードで判定する」**
  手順書は「判定の手がかりになるが、**判定は理由ではなくコードで行う**」と書いています。理由のコードは解析器の言い分で、正しいとは限りません。
- **誤解: 「`D_layer_present:` も宣言の注記だから読む」**
  付録の仕組みの注記です。核の判定では読みません。

#### 手作業ではどう使うか

- **手順 A**: 判定表の `decl` の欄と同じ宣言の注記を探します。ほかの宣言の注記は、その組とは別の話です。
- **手順 B**: 矛の組なら `contradiction:<decl>` と `contradiction_reason:<decl>:<理由>`、不の組なら `contradiction_unknown:<decl>:<理由>` を探し、理由のコードを手順書 13.1 の表で引きます。
- **不の中身の判定（手引き 18A）**: 理由のコードごとに、調べることが決まっています。理由のコードは、どこを調べるかの「道しるべ」として使い、答えは原ソースで決めます。

（出典: `docs/final_evaluation_procedure.md:866-867`（「判定は理由ではなくコードで行う」）、`docs/drafts/final_judging_guide_draft.md:92-112`（手順 A・B））

#### この節のまとめ

核の注記は `contradiction:<宣言>`（矛）、`contradiction_reason:<宣言>:<理由>`（矛の理由。必ず対で出る）、`contradiction_unknown:<宣言>:<理由>`（不）の 3 種類。内は書かれない。
1 つの行に、別々の宣言の注記が並ぶことがあり、宣言ごとに別々に読む。
`select_manifest_only(...)` や `D_layer_present:…` は付録の注記で、読まない。判定は理由ではなくコードで行う。

### 18.7 ユニットの注記 — 打ち切りの印 `TRUNCATED(...)`

#### 一言で言うと

**行**の `notes` とは別に、**ユニット**にも `notes` の欄があります。
ここに出る大事な注記が、**打ち切りの印** `TRUNCATED(...)` です。
「このユニットの解析は、どこかで途中までしかできなかった（または時間がかかりすぎた）」という印です。
見落としの抜き取りでは、この印が `truncated` という欄に写され、判定者が「不明（打ち切り）」に分けられるようにしています。

#### たとえ話 — 点検員の作業メモ

点検報告書の部屋ごとの欄の横に、点検員の作業メモが付いているとします。
「この部屋は途中で懐中電灯が切れた」「この部屋は時間がかかりすぎた」「この部屋の奥の倉庫には鍵がかかっていた」。
メモがある部屋の「問題なし」は、ほかの部屋の「問題なし」と同じ重さでは信じられません。

ユニットの `notes` は、この作業メモです。
行の `notes`（所見）と、置き場所も意味も違います。

#### 小さな例 — v4 の zozi の `zozi_cancel_order`

v4 の zozi の木には、`zozi_cancel_order` というツールが、3 つのファイルの、どれも 584 行にあります（同じファイルを 3 か所に写しているため。[第 12 章](ch12.md) 12.10 節）。
そのうち 1 つのユニットだけに、打ち切りの印が付いていました。

```json
{
  "unit": {"qualname": "zozi_cancel_order", "relpath": "_extra_files/_legacy.bak/services/mcp/zozi_mcp.py", "lineno": 584, ...},
  "notes": ["TRUNCATED(wall_clock)"],
  "cap_hits": [],
  "opaque_reasons": ["receiver", "unresolved"],
  "effects": [],
  "rows": []
}
```

ほかの 2 つ（`backend/jobs/mcp_marketplace_server.py:584` と `backend/providers/ai/zozi_mcp.py:584`）は、`notes` が空で、`effects` も空でした。
（出典: `evidence/scan_v2_v4_run1/v4-makfuncky__zozi.json`（本書の執筆時に確かめた））

#### 一歩ずつ

- `"notes": ["TRUNCATED(wall_clock)"]`: このユニットの解析に、10 秒（`WALL_CLOCK_CAP`）を超える時間がかかった、という印です。
- `"effects": []`・`"rows": []`: 効果は見つかっていません。同じコードの写しの 2 つも効果が無かったので、結果は写しどうしで同じでした。
- `"cap_hits": []`・`"opaque_reasons"`: 欄が出ているので、値を追う解析は走っています。

`TRUNCATED(wall_clock)` について、大事な点が 1 つあります。
本書の執筆時に `authgap/` の中を検索したかぎり、解析の途中で時計を見て**止める**仕組みは、木の時間上限（18.11 節）だけでした。
ユニットの解析の中には、時計を見て止める所がありません。
解析器は、1 つのユニットの解析を**終えてから**時間を測り、10 秒を超えていたら印を付けます。
ですから、`TRUNCATED(wall_clock)` は「時間がかかった」という印で、そのユニットの解析そのものは最後まで済んでいると読めます。
なお、`authgap/ir.py` の `WALL_CLOCK_CAP` の説明文は「1 ファイルあたりの壁時計上限」ですが、`authgap/runner.py` は 1 ユニットの解析の前後で時計を見ています。
本書は、コードの動き（1 ユニットあたり）を採ります。
（出典: `authgap/runner.py:134, 169-171`（ユニットの解析の後で時間を測って印を付ける）、`authgap/ir.py:36-37`（`WALL_CLOCK_CAP = 10.0` と説明文）。検索は `authgap/` の中の `time.monotonic` などの呼び出しを本書の執筆時に調べた）

#### ユニットの注記の一覧

| 印 | いつ付くか | 何が欠けるか | `truncated` に写るか |
|---|---|---|---|
| `TRUNCATED(recursion)` | ユニットの解析の途中で、**解析器自身**が Python の再帰の上限（`RecursionError`）に当たり、そのユニットを解析できなかった | 効果が**全部**欠ける（`effects` が空）。宣言（`D_kind`）だけは残す。`cap_hits`・`opaque_reasons` の欄も無い | 写る |
| `TRUNCATED(recursion:self_fields)` | クラスの `__init__` が自分のフィールドを読むところで再帰が打ち切られ、打ち切られたフィールドの値を使った | そのフィールドを通る値の追跡 | 写る |
| `TRUNCATED(wall_clock)` | 1 ユニットの解析に 10 秒を超えてかかった | 欠けは無いと読める（上の説明） | 写る |
| `depends_on_dropped:<relpath>` | ユニットが、parse に失敗したファイルか `ast_node_cap` で捨てたファイルの中の定義を呼んだ | そのファイルの中の効果 | **写らない** |
| `module unresolved` | ユニットの定義のファイルが見つからなかった | 効果が全部欠ける | 写らない |
| `D_kind_unread(recursion)` | 再帰で止まったユニットで、宣言を読むところでも再帰の上限に当たった | 宣言も欠ける（⊥ に見える） | 写らない |

表の読み方: 1 行が 1 つの印です。
たとえば 4 行目は「`depends_on_dropped:app/store.py` のような印があれば、そのユニットは、読まなかったファイル `app/store.py` の中の関数を呼んでいる。そのファイルの中で起きることは、解析器には見えていない。この印は `TRUNCATED` で始まらないので、見落としの抜き取りの `truncated` の欄には写らない」と読みます。
（出典: `authgap/runner.py:154-166`（`TRUNCATED(recursion)` と `D_kind_unread(recursion)`）、`authgap/analyze.py:203-212`（`module unresolved` と `TRUNCATED(recursion:self_fields)`）、`:224-228`（`depends_on_dropped`）、`:356-358`（`SELF_FIELDS_TRUNCATED`）、`scripts/v3_miss_sample.py:9-10, 52-55`（`TRUNCATED` で始まる注記だけを `truncated` に写す））

#### v4 での数

v4 の 3,696 ユニットのユニットの `notes` を数えました（本書の執筆時に数えた）。

- `TRUNCATED(...)` の印のあるユニット: **1 つ**（上の zozi の `zozi_cancel_order` の `TRUNCATED(wall_clock)`）。
- `depends_on_dropped:` の印のあるユニット: **2 つ**。どちらも ceo-agent-service の木で、`app/dws_client.py`（構文木の節 25,900）と `app/store.py`（同 108,447）の 2 つのファイルを呼んでいました。2 つのファイルは、どちらも `ast_node_cap` で捨てられていました。
- `module unresolved`・`D_kind_unread(recursion)`: 0。

ceo-agent-service の 2 つのユニットのうち、`send_approved_dingtalk_message_tool`（ツールの名前は `send_approved_dingtalk_message`）は `destructiveHint: false`（D2）と `idempotentHint: true`（D4）を明示していて、効果は 0 でした。
効果が 0 なので、D2 の矛は出ていません。
つまりこのユニットは、**見落としの抜き取りの対象になりうる**のに、`truncated` の印は付きません。
（出典: `evidence/scan_v2_v4_run1/v4-callzhang__ceo-agent-service.json`（本書の執筆時に確かめた））

#### なぜそうするのか

**打ち切りを印として残す理由**は、この研究の約束「黙って落とさない」です。
大きな木の 1 つのユニットで解析器が止まると、以前は木全体が落ちていました。
そこで、そのユニットだけを `TRUNCATED(recursion)` として残し、件数に数えるように直しました（コードの説明に「D17 改訂 4」とあります）。
さらに凍結の前の添削（D64 の U49）で、打ち切ったユニットでも宣言（`D_kind`）を残すように直しました。
以前は宣言が ⊥ に見えて、見落としの抜き取りの対象から消えていたからです。

**打ち切りのあるユニットを見落としの抜き取りに含める理由**は、学生の決定（D70 の 2）です。
除くと、解析器が苦手な大きいツールが抜き取りから消え、見落としの率を低く見せてしまいます（誤 clear の向きを隠す）。
（出典: `authgap/runner.py:154-161`（コードの説明「1 ユニットの深い AST で木全体を落とさない」「宣言は解析の成否と関係なく残す」）、`docs/decisions.md:3574`（U49）、`:3846-3848`（D70 の 2））

#### よくある誤解・つまずき

- **誤解: 「ユニットの `notes` と行の `notes` は同じもの」**
  別の欄です。行の `notes` には核の答え（矛・不）が、ユニットの `notes` には打ち切りなどの作業メモが入ります。
- **誤解: 「`TRUNCATED(recursion)` は、解析するコードが再帰しているという意味」**
  違います。**解析器自身**が Python の再帰の上限で止まった、という意味です。解析するコードの再帰は、`opaque_reasons` の `recursion` です（[第 15 章](ch15.md) 15.5 節）。
- **誤解: 「`TRUNCATED(wall_clock)` のユニットは、途中までしか解析されていない」**
  コードを読むかぎり、解析は最後まで済んでいて、時間がかかったという印です。
- **誤解: 「`truncated` の印が無ければ、解析器はユニットの中を全部見た」**
  `depends_on_dropped:` は `truncated` に写りません。`cap_hits` の `depth`（深さ 4 での打ち切り）も別の欄です。

#### 手作業ではどう使うか

- **見落としの判定**: 抜き取られたユニットに `truncated` の印があれば、手引きの下書きの 18.3 節に従います。解析器が途中で読むのをやめた部分に違反があれば、見落としとして原因を「深さ」または「その他（打ち切り）」にし、読み切れなければ「不明（打ち切り）」にします。
- **`depends_on_dropped:` の印**: 手引きの下書きは `truncated` の印のことしか書いておらず、`depends_on_dropped:` の扱いは書いていません（本書の執筆時に気づいた点。**未決**）。抜き取られたユニットの manifest を見たときにこの印があれば、読まなかったファイルの中を自分で読み、扱いに迷ったら `note` に書いておきます。
- **手順 B**: 矛の組でも、ユニットの `notes` を一度は見ます。`TRUNCATED(recursion:self_fields)` があれば、値の追跡の一部が打ち切られています。

（出典: `docs/drafts/final_judging_guide_draft.md:470-473`（18.3 の注意）、`docs/drafts/prereg_2_12_draft.md:61`（事前登録の下書きの見落としの抜き取り）、`docs/final_evaluation_procedure.md:441-443`（見落としの抜き取りの出力に `truncated` の印を含める））

#### この節のまとめ

ユニットの `notes` は行の `notes` とは別の欄で、打ち切りの印 `TRUNCATED(recursion)`・`TRUNCATED(recursion:self_fields)`・`TRUNCATED(wall_clock)` などが出る。見落としの抜き取りでは `TRUNCATED` で始まる印が `truncated` に写る。
`TRUNCATED(wall_clock)` は時間がかかった印で、解析は最後まで済んでいると読める。
`depends_on_dropped:<relpath>` は `truncated` に写らない。読まなかったファイルの中の効果は見えていない。扱いは未決。

### 18.8 判定の単位「組」

#### 一言で言うと

人の判定の単位は、**組 = (木, ユニット, site, kind, 宣言)** です。
同じツールの、同じ site・同じ kind の効果は、位置がいくつあっても、道筋が何本あっても、slot がいくつあっても、**宣言ごとに 1 組**にまとめます。
組の答えは、組の中の行の注記で決まります。どれか 1 行にでもその宣言の矛があれば矛、矛が無くて不があれば不、どちらも無ければ内です。

#### たとえ話 — 図書館の注意の通知

図書館が、利用者に注意の通知を出すとします。
通知は「利用者 1 人 × 本 1 冊 × 規則 1 つ」で 1 件です。

- 同じ本の返却が遅れて、督促の電話を 3 回かけても、「延滞」の通知は 1 件です。
- 同じ本が、遅れたうえに汚れていたら、「延滞」と「汚損」は別の規則なので、通知は 2 件です。
- 2 つの図書館が同じ名前の利用者に通知を出すときは、どの図書館の利用者かを書き添えます。

組も同じです。
「利用者 × 本」が「ユニット × site × kind」、「規則」が「宣言」、「どの図書館か」が「木」にあたります。
督促の電話の回数（道筋の本数）や、汚れのページの数（slot や位置の数）では、件数は増えません。

ここでは、組の数え方の例としてだけ使います。

#### 一歩ずつ — 組の答えの決め方

組の答えは、次の規則で決まります。

1. 組の行のどれか 1 つにでも、その宣言の**矛**の注記があれば → 組は**矛**。
2. 矛が無く、どれか 1 つにでも、その宣言の**不**の注記があれば → 組は**不**。
3. どちらも無ければ → 組は**内**。

この規則は、宣言ごとに矛と不を数える道具 `scripts/contradiction_by_decl.py` の最後の 1 行に、そのまま書かれています。

```python
return "矛" if "矛" in res else ("不" if "不" in res else "内")
```

1 行を読みます。

- `res` は、その組のすべての行の注記から集めた答えの集まり（「矛」「不」の入った集合）です。
- `"矛" if "矛" in res`: 集まりに「矛」があれば、答えは「矛」です。
- `else ("不" if "不" in res else "内")`: 「矛」が無ければ、「不」があれば「不」、それも無ければ「内」です。

（出典: `scripts/contradiction_by_decl.py:60-78`（`apply_flip`。採った原理のときは `flip` が `None` で、上の規則だけが働く）、`:11-15`（数え方の説明））

#### 一歩ずつ — 組の 5 つの成分と、道具の鍵

組の 5 つの成分を、道具はもう少し細かい**鍵**で区別しています。

| 組の成分 | 道具の鍵での書き方 | なぜ細かくするか |
|---|---|---|
| 木 | 木の名前（`v4-ankitdotgg__making-gemini-useful-with-claude` など） | — |
| ユニット | ユニットの relpath・ユニットの行・qualname の 3 つ | 同じ qualname の別のツールを取り違えないため（18.12 節。D64 の U50） |
| site | site の名前 | — |
| kind | kind の名前 | — |
| 宣言 | D1〜D4 | — |

表の読み方: 2 行目は「組の『ユニット』は、道具の中では relpath・行・qualname の 3 つで区別している」と読みます。
手順書の矛の抜き取りの組の鍵も、(木, ユニットの relpath, ユニットの行, qualname, site, kind, 宣言) です。
（出典: `docs/final_evaluation_procedure.md:435`（組の鍵）、`scripts/runlib.py:61-63`（ユニットの鍵 `unit_key`）、`scripts/contradiction_by_decl.py:11-12`）

#### 第 3 版の「数え方の単位」とのつながり

第 3 版の[第 16 章](ch16.md)（この版の第 18 章）は、組を「数え方の単位」として書いていました。
「矛の件数を数えるときは、多くの場合『**ユニット × site × kind**』の組を 1 件と数える」「宣言ごとに数えるときは『**ユニット × site × kind × 宣言**』を 1 件とする」です。

この版の**組**は、**宣言ごとに数えるほうの単位に、木を足したもの**です。

- **木を足す理由**: 最終評価では数千本の木を同時に扱います。ユニットの名前（`search` や `add_comment` など）は、木をまたいでいくらでも重なります。どの木のユニットかを区別しなければ、別の木のツールが 1 件に潰れます。
- **宣言を入れる理由**: この研究は D1〜D4 を宣言ごとに判定し、報告すると決めています（D62）。ですから、判定の単位にも宣言が入ります。

第 3 版の「ユニット × site × kind」（宣言を入れない単位）は、次の節の `contradictions.json` の 1 行の単位として、今も残っています。

#### なぜ組で判定するのか

- **道筋の本数で数えると、同じ問題を何重にも数えます。** 1 つのツールが同じ `os.remove` に 3 本の道筋で届いても、「このツールはファイルを消す」という事実は 1 つです。
- **行の数で数えると、slot の数で数が膨らみます。** `SPAWN` の効果 1 つは 4 行になります（gemini の例）。
- **宣言を分けないと、意味の違う主張が混ざります。** 「読むだけ（D1）に反する」と「何度呼んでも同じ（D4）に反する」は別の主張です。bugasura の例のように、同じ効果が D2 と D4 で別々の答えになりえます。

組にまとめると、「このツールのこの操作は、この宣言に反するか」という、判定したい問いと単位がそろいます。

#### よくある誤解・つまずき

- **誤解: 「組 = manifest の 1 行」**
  違います。slot ごと・位置ごと・道筋ごとの複数の行が、1 組にまとまります。
- **誤解: 「組 = ツール 1 つ」**
  違います。1 つのツールに、site や kind や宣言の違う組がいくつもありえます。gemini の `gemini_prompt` には 2 組ありました。
- **誤解: 「組の中に不の位置が混ざっていたら、組は不」**
  矛の位置が 1 つでもあれば矛です（ccr の `gcc_todos`）。
- **誤解: 「1 つのツールの組の答えを、宣言をまたいで足せば、そのツールの違反の数になる」**
  宣言ごとに別の約束なので、足しません（D62）。

#### 手作業ではどう使うか

- **手順 A**: 判定表の 1 行が 1 組です。欄の `tree`・`unit`・`unit_relpath`・`unit_lineno`・`site`・`kind`・`decl` が、組の成分です。
- **手順 G**: 1 組に複数の位置があるときは、1 つでも「到達する かつ 宣言に反する」位置があれば、その組は正です。全部の位置が「到達しない」か「反しない」なら誤です。解析器の組の答え（矛があれば矛）と、人の判定の決め方（正の位置が 1 つあれば正）は、同じ考え方でそろえてあります。
- **数を言うとき**: 「矛が何件」と言うときは、何の単位で数えたかを必ず添えます（`CLAUDE.md` の規則 3「閾値には必ず測定手続きと分母の定義を付ける」）。

（出典: `docs/final_evaluation_procedure.md:704-707`（11.1 判定の単位）、`docs/drafts/final_judging_guide_draft.md:31-34`（同じ定義）、`:92-103`（手順 A の欄）、`:150-160`（手順 G））

#### この節のまとめ

組 = (木, ユニット, site, kind, 宣言)。位置・道筋・slot がいくつあっても、宣言ごとに 1 組。道具の鍵では、ユニットを relpath・行・qualname で区別する。
組の答えは、どれか 1 行に矛があれば矛、無くて不があれば不、どちらも無ければ内（`contradiction_by_decl.py` の最後の 1 行）。
第 3 版の「ユニット × site × kind × 宣言」に木を足したものが組。gemini は 5 行で 2 組、bugasura は 10 行で 2 組、ccr の `gcc_todos` は矛・不・内の混ざった 1 組で、答えは矛。

### 18.9 `contradictions.json` の 1 行と組

#### 一言で言うと

`contradictions.json` は、矛の行を一覧にした「手で確かめる候補の表」です。
ただし、**1 行の単位は組と少し違います**。
1 行 = **(ユニット, site, kind)** で、反した宣言は **`declarations`** の欄に並びます。
だから、**組の数 = 各行の `declarations` の数を足したもの**です。
このファイルには**矛だけ**が入っていて、**不は入っていません**。

#### たとえ話 — 指摘事項の一覧の「反した規則」の欄

点検の指摘事項の一覧が、「部屋 × 設備 × 種類」で 1 行になっているとします。
1 行の中に「反した規則」の欄があり、規則の番号が並びます。
同じ設備が 2 つの規則に反していれば、1 行の中に規則が 2 つ並びます。

後で人が確かめるときは、規則ごとに別々に確かめます。
ですから、確かめる件数は「行の数」ではなく「規則の欄に並んだ番号の数の合計」です。

#### 小さな例 1 — v4 の gemini の行

v4 の `contradictions.json` の、gemini の `gemini_prompt` の行を、そのまま写します。

```json
{
 "tree": "v4-ankitdotgg__making-gemini-useful-with-claude",
 "unit": "gemini_prompt",
 "unit_relpath": "server.py",
 "unit_lineno": 251,
 "tool": "gemini_prompt",
 "relpath": "server.py",
 "effect_kind": "FS_WRITE",
 "site": "pipe:communicate",
 "lineno": 204,
 "destructive": null,
 "D_explicit": ["openWorldHint", "readOnlyHint"],
 "declarations": ["D1"],
 "locations": [
  {"relpath": "server.py", "lineno": 204, "declarations": ["D1"], "destructive": null}
 ]
}
```

同じツールの `SPAWN` の組（D1 の不。18.8 節）は、このファイルに**ありません**。
不は入らないからです。
（出典: `evidence/scan_v2_v4_run1/contradictions.json`（本書の執筆時に確かめた））

#### 一歩ずつ — 欄を 1 つずつ

| 欄 | 中身 | 例の値 |
|---|---|---|
| `tree` | 木の名前 | `v4-ankitdotgg__making-gemini-useful-with-claude` |
| `unit` | ユニットの qualname | `gemini_prompt` |
| `unit_relpath`・`unit_lineno` | ユニット（ツールの関数）の定義の位置 | `server.py`・251 |
| `tool` | ツールの名前（`tool_name`） | `gemini_prompt` |
| `effect_kind` | 効果の kind（判定表では `kind` という欄の名前になる） | `FS_WRITE` |
| `site` | 効果を起こす関数の名前 | `pipe:communicate` |
| `relpath`・`lineno` | **代表の位置**。`locations` の中で (relpath, lineno) の対が最小のもの | `server.py`・204 |
| `destructive` | `locations` の `destructive` のまとめ。どれか 1 つでも `true` なら `true`、全部 `false` なら `false`、それ以外（欄が無い・`null` を含む）は `null` | `null` |
| `D_explicit` | ユニットの `D_kind.explicit` の写し（18.3 節の注意のとおり、D3・D4 は出ない） | `["openWorldHint", "readOnlyHint"]` |
| `declarations` | この行が反した宣言の一覧（全部の位置の和） | `["D1"]` |
| `locations` | 矛の行のある位置の全部。位置ごとに、反した宣言と `destructive` が付く | 1 つ |

表の読み方: 1 行が `contradictions.json` の 1 行の中の 1 つの欄です。
たとえば 7 行目は「`relpath`・`lineno` は、`locations` に並んだ位置のうち、ファイルの名前と行の番号の対がいちばん小さいものを代表として写したもの。組の全部の位置ではない」と読みます。
（出典: `scripts/scan_v2.py:50-96`（`_contradiction_rows`）、`:99-105`（`_any_destructive`）、`:301-302`（ファイルの説明「relpath / lineno は組の中の (relpath, lineno) の対の最小、全位置は locations」））

teamplay-talk の木の `apply_daily_checkin`（qualname は `register.apply_daily_checkin`）の行です（欄を減らして写す）。

たとえば位置 A は D1 だけ、位置 B は D1 と D3 なら、D1 の組の位置は A と B、D3 の組の位置は B だけです。

#### v4 で数える

v4 の `contradictions.json` を数えました（本書の執筆時に数えた）。

不の組は manifest の注記から作る。手順書 6.3 の「`contradictions.json` の不の行」は実データと食い違う（未決）。

### 18.10 `summary.json` の欄

#### 一言で言うと

`summary.json` は run 全体の**表紙**です。
解析器の指紋・Python の版・深さの上限・件数の合計と、木ごとの状態・件数・所要時間が入っています。
走査の後に、手順書 9.3 節の表のとおりに確かめます（V1 頑健性の材料）。
**`verdict_rows` は行の数で、組の数ではありません。** 矛の件数には使いません。

#### たとえ話 — 健康診断の会場の記録

学校の健康診断の会場では、最後に記録の表紙を作ります。
「使った体重計の型番と校正の記録」「受診した人数」「途中で帰った人の数」「1 人あたりの時間」などです。
表紙を見れば、「正しい機器で、全員をちゃんと測れたか」が 1 枚で分かります。
ただし、表紙の「測った項目の数の合計」は、「病気の人の数」ではありません。

`summary.json` も同じです。
解析器の指紋は「機器の校正記録」、木ごとの状態と打ち切りは「途中で帰った人の数」です。
`verdict_rows` は「測った項目の数」にあたり、矛の組の数ではありません。

#### 一歩ずつ — いちばん外側の欄

| 欄 | 意味 | v4 の値 | 確かめること |
|---|---|---|---|
| `implementation_sha256_combined` | 解析器（`authgap/` の実装のファイル）から計算した**結合の指紋**（sha256） | `35606ba9…` | `docs/fingerprint.json` の同じ欄と一致すること。一致すれば、凍結した解析器と同じものを走らせた |

| `authgap_last_commit` | `authgap/` を最後に変えたコミット | `b87c0228…` | 参考（`docs/fingerprint.json` の凍結の記録の `analyzer_commit` と同じ） |
| `analyzer_commit` | 走らせたときの repo 全体の HEAD（いま取り出しているコミット） | `455169c2…` | 参考。文書だけのコミットでも変わるので、**解析器が同じかは指紋で比べる** |

| `n_trees` | 走らせた木の数 | 88 | 標本の木の数と一致すること |
| `n_trees_resumed` | `--resume` で前回の結果を使った木の数 | 0 | 0 でなければ、再開した理由を記録する |
| `n_units` | ユニットの総数 | 3,696 | — |
| `n_dangerous_units` | 効果を 1 つ以上持つユニットの数 | 1,347 | — |
| `n_rows` | 行の総数（効果 × slot） | 15,630 | — |
| `n_effects` | 効果の要素の総数（重なりを含む） | 10,973 | — |
| `n_effects_unique` | 中身がすべて同じ効果の要素を 1 つにまとめた数（D64 の U32） | 8,365 | — |
| `verdict_rows` | verdict ごとの**行の数** | 上の例 | **矛の件数に使わない**（下） |
| `trees` | 木ごとの記録の列（下の表） | 88 要素 | — |
| `_note` | 説明の文 | 上の例 | 気にしない。スクリプトの既定の文なので、v4 でも「母集団 v2 の full scan」と書かれる |

表の読み方: 1 行が 1 つの欄です。
たとえば 1 行目は「`implementation_sha256_combined` は、解析器のコードの全部のファイルの中身から計算した 1 つの値。1 文字でも変われば値が変わる。凍結の記録の値（`35606ba9…`）と一致すれば、凍結した解析器を走らせたと言える」と読みます。
（出典: `scripts/scan_v2.py:155-167`（指紋・dirty・最後のコミット・Python の版）、`:284-298`（`summary.json` の欄）、`:122`（`n_dangerous_units` は効果を持つユニットの数）、`docs/fingerprint.json`（`implementation_sha256_combined` と `freeze.analyzer_commit`）、`docs/final_evaluation_procedure.md:406`（Python 3.12 で走らせる）、`:646-660`（9.3 の確かめること））

`n_dangerous_units` の「危険な」は名前だけで、中身は「効果を 1 つ以上持つ」です。
`FS_READ` の効果しか無いユニットも数えます。

#### 一歩ずつ — 木ごとの欄（`trees[]`）

| 欄 | 意味 | 確かめること（手順書 9.3） |
|---|---|---|
| `tree` | 木の名前 | — |
| `status` | `ok` / `missing`（木のフォルダが無い）/ `analysis_failed`（解析が例外で止まった）/ `write_failed`（manifest を書けなかった） | `ok` 以外の木を全件書き出す |
| `n_units`・`n_rows`・`n_effects`・`n_effects_unique`・`verdicts` | その木の件数。`verdicts` は verdict ごとの行の数 | — |
| `budget_skipped` | **時間上限で解析しなかったユニットの数**（18.11 節） | 0 でない木を全件書き出し、その木の `elapsed_s` も書く |
| `n_parse_failures` | parse に失敗したファイルの数（manifest の `parse_failures` の長さ） | 件数を報告する |
| `n_truncations` | manifest の `truncations` の要素の数 | 件数を報告する |
| `elapsed_s` | その木にかかった秒数（manifest を書き終えるまで） | 打ち切りのあった木では必ず書く |

表の読み方: 1 行が `trees[]` の 1 要素の中の 1 つの欄です。
たとえば 4 行目は「`budget_skipped` が 0 でない木は、時間上限でユニットを解析しなかった木。全件を書き出し、その木にかかった秒数も書く」と読みます。
`status` が `ok` 以外の木では、件数の欄は書かれません。`missing` なら `tree` と `status` だけ、`analysis_failed`・`write_failed` なら、それに `error`（例外の名前と中身）を足した 3 つだけです。
（出典: `scripts/scan_v2.py:249-276`（木ごとの記録の作り方）、`docs/final_evaluation_procedure.md:655-658`）

**`n_truncations` の数え方の注意**です。
手順書 9.3 の表は、`n_truncations` を「`ast_node_cap` などで打ち切ったファイルの数」と説明しています。
けれども、スクリプトは manifest の `truncations` の要素の数を数えています。
時間上限の打ち切りがあった木では、`truncations` に `relpath` が空の要素（`tree_budget` か `tree_budget_prep`）が 1 つ足されるので、その 1 つも数に入ります。
たとえば v2 の run24 の meta-skill-evloving の木は、`n_truncations` が 33 で、その内訳は `ast_node_cap` が 32、`tree_budget_prep` が 1 でした。
「ファイルの数」として報告するときは、この 1 つを引きます（本書の執筆時に気づいた点）。
（出典: `scripts/scan_v2.py:274`、`docs/final_evaluation_procedure.md:658`、`evidence/scan_v2_run24/summary.json` と同じフォルダの manifest（本書の執筆時に数えた））

#### v4 の値で V1 頑健性を読む

v4 の `summary.json` を、手順書 9.3 の表のとおりに読みます（本書の執筆時に数えた。`docs/population_v4.md` の記録と一致します）。

- `budget_skipped` が 0 でない木は無い（時間上限の打ち切り 0）。

#### `status: ok` は「全部のユニットを解析した」ではない

`status` は、木の解析が**例外で止まらず**、manifest を**書けた**かどうかの印です。
時間上限でユニットを飛ばしても、`status` は `ok` です。
v2 の run24 の meta-skill-evloving の木は、`status` が `ok` なのに、`n_units` が 0、`budget_skipped` が 716 でした。
716 ユニットを 1 つも解析していません。
`status` だけを見て「全部 ok」と書くと、この 716 ユニットが報告から消えます。
**`status` と `budget_skipped` は、必ず両方見ます。**
（出典: `evidence/scan_v2_run24/summary.json`（本書の執筆時に確かめた）、`scripts/scan_v2.py:252-276`）

#### `verdict_rows` は組の数ではない

`verdict_rows` は、verdict ごとの**行の数**です。
v4 の `CONTRADICTION` の 2,707 は、矛の注記を持つ**行**の数で、矛の**組**の数（481）ではありません。
行は slot ごと・道筋ごと・位置ごとに増えるので、2,707 は 481 の 5 倍以上になっています。
`UNKNOWN` の 11,937 も、18.5 節で見たとおり、不の数ではありません。

**矛の件数を言うときは、`contradictions.json` の `declarations` の数（と、宣言ごとの集計の `scripts/contradiction_by_decl.py`）を使います。**
`verdict_rows` は、走査が壊れずに動いたかを見る材料（前の run と大きく違わないか）として読む程度にします。
（出典: `scripts/scan_v2.py:108-124`（`_tally`。行ごとに verdict を数える）、`:296`）

#### なぜそうするのか

**指紋を `summary.json` に残す理由**は、「どの解析器で走らせたか」を、HEAD のコミットの文字列ではなく**実装の中身**で比べるためです（D64 の U54）。
文書だけのコミットでも HEAD は変わります。
一方、`implementation_sha256_combined` は `authgap/` の実装のファイルの中身だけで決まります。
最終評価では、走査を `--require-fingerprint docs/fingerprint.json` を付けて走らせます。
指紋が凍結の記録と違うか、`authgap/` に未コミットの変更があれば、走査そのものが始まりません。

**`max_depth` を `summary.json` に残す理由**は、18.2 節で見たとおり、manifest の `fingerprint` には定数の値しか書かれないからです。
（出典: `scripts/scan_v2.py:155-156`（「比べるのは HEAD の文字列ではなくこの値」）、`:181-199`（`--require-fingerprint`）、`docs/decisions.md:3579`（U54））

#### よくある誤解・つまずき

- **誤解: 「`verdict_rows` の `CONTRADICTION` = 矛の件数」**
  行の数です。v4 で 2,707 行、組は 481 です。
- **誤解: 「`status` が全部 `ok` なら、打ち切りは無い」**
  時間上限で飛ばしても `ok` です。`budget_skipped` を見ます。
- **誤解: 「`analyzer_commit` が凍結のコミットと違うから、凍結した解析器ではない」**
  `analyzer_commit` は repo 全体の HEAD で、文書のコミットでも変わります。解析器が同じかは `implementation_sha256_combined` で比べます。v4 では `analyzer_commit` が `455169c2…` でしたが、指紋は凍結の記録と一致していました。
- **誤解: 「`_note` に『母集団 v2』とあるから、v4 の run ではない」**
  スクリプトの既定の文です。v4 でもそう書かれます。
- **誤解: 「`n_truncations` = 打ち切ったファイルの数」**
  時間上限の打ち切りがあった木では、その 1 要素も数に入ります。

#### 手作業ではどう使うか

- **段階 5 の走査の後（V1 頑健性）**: 手順書 9.3 の表のとおり、`implementation_sha256_combined`・`authgap_dirty`・`max_depth`・`trees[].status`・`trees[].budget_skipped`・`trees[].n_parse_failures`・`trees[].n_truncations` を確かめます。打ち切りがあっても**取り直しません**。件数を報告に書きます。

- **深さの感度分析の run**: `max_depth` が 3・5 になっているかを確かめます。

（出典: `docs/final_evaluation_procedure.md:646-660`（9.3）、`:1315-1318`（23.1 V1 頑健性））

#### この節のまとめ

`summary.json` は run の表紙。指紋（`implementation_sha256_combined`）・`authgap_dirty`・`python`・`max_depth` で「凍結した解析器を正しい設定で走らせたか」を、木ごとの `status`・`budget_skipped`・`n_parse_failures`・`n_truncations`・`elapsed_s` で V1 頑健性を確かめる。
`status: ok` でも時間上限でユニットを飛ばしていることがある。`n_truncations` には時間上限の 1 要素も入る。
`verdict_rows` は行の数で、矛の件数には使わない（v4 は 2,707 行に対して 481 組）。

### 18.11 時間上限の打ち切りは 2 か所に出る

#### 一言で言うと

1 本の木にかける時間には、**上限**（tree budget）が 180 秒あります。
上限を超えると、残りのユニットを解析せずに飛ばし、**飛ばしたユニットの数**を記録します。
その数は、**同じ 1 つの値**から、`summary.json` の **`trees[].budget_skipped`** と、manifest の **`truncations`** の `tree_budget`（または `tree_budget_prep`）の **2 か所**に書かれます。
飛ばしたユニットは manifest に**入りません**。件数だけが残ります。

#### たとえ話 — 試験の監督と時計

試験の監督が、問題の区切りごとにだけ時計を見るとします。
1 問を解いている途中では止めません。
次の問題に移るときに時計を見て、時間を過ぎていたら、残りの問題は白紙のまま回収します。
白紙だった問題の数は、答案の表紙と、クラスの成績の一覧表の 2 か所に書きます。

解析器の時間上限も、この監督と同じです。
「次のユニットに移るとき」（と、ユニットを見つけ終えたとき）にだけ時計を見ます。
飛ばしたユニットの数は、manifest（答案の表紙）と `summary.json`（成績の一覧表）の 2 か所に書きます。
1 問の途中では止めないので、時計の上では上限の 180 秒を大きく超えることもあります。

#### 小さな例 — v2 の run24 の meta-skill-evloving

v2 の最終凍結の根拠の run（`scan_v2_run24`）で、時間上限に当たった木があります。
david-li0406/meta-skill-evloving という木で、`.py` のファイルが 36,900 個ある大きな木です。

`summary.json` の、この木の記録です。

```json
{"tree": "v2-david-li0406__meta-skill-evloving", "status": "ok",
 "n_units": 0, "n_rows": 0, "n_effects": 0, "n_effects_unique": 0, "verdicts": {},
 "budget_skipped": 716, "n_parse_failures": 84, "n_truncations": 33, "elapsed_s": 423.7}
```

同じ木の manifest の `truncations` には、33 個の要素がありました。
32 個は `ast_node_cap` で、残りの 1 個が次の要素です。

```json
{"cap": "tree_budget_prep", "count": 716, "relpath": ""}
```

manifest の `units` は空（0 個）でした。
（出典: `evidence/scan_v2_run24/summary.json`、`evidence/scan_v2_run24/v2-david-li0406__meta-skill-evloving.json`（本書の執筆時に確かめた）、`docs/decisions.md:364-365`（.py 36,900 ファイル））

#### 一歩ずつ — 例を読む

- `"status": "ok"`: 木の解析は例外で止まらず、manifest も書けました。
- `"n_units": 0`: manifest に入ったユニットは 0 個です。
- `"budget_skipped": 716`: 時間上限で、716 個のユニットを解析しませんでした。
- `"elapsed_s": 423.7`: この木に 423.7 秒かかりました。上限の 180 秒を大きく超えています。理由は下の「時計を見る 2 つの時点」で見ます。
- manifest の `{"cap": "tree_budget_prep", "count": 716, "relpath": ""}`: 同じ 716 が、manifest にも書かれています。cap の名前が `tree_budget` ではなく **`tree_budget_prep`** なのは、ユニットを見つけた直後（前処理の段階）で上限を超えていたからです。`relpath` が空なのは、特定のファイルではなく木全体の打ち切りだからです。

この木は、v2 のどの run でも同じように 716 ユニットを飛ばしていました。
`elapsed_s` は run ごとに違い、run1 で 565.9 秒、run4 で 511.6 秒、run20 で 264.3 秒、run23 で 615.5 秒、run24 で 423.7 秒でした（本書の執筆時に各 run の `summary.json` で確かめた）。
（出典: `evidence/scan_v2_run1/summary.json`、`scan_v2_run4`、`scan_v2_run20`、`scan_v2_run23`、`scan_v2_run24` の `summary.json`）

#### 一歩ずつ — 時計を見る 2 つの時点

解析器（`authgap/runner.py`）が時計を見るのは、次の 2 つの時点だけです。

**時点 1: ユニットを見つけた直後**

```python
88  if cfg.prep_budget_exit and cfg.max_tree_seconds and (time.monotonic() - started) > cfg.max_tree_seconds:
 …
91      res.tree_budget_skipped = len(units)
 …
94      tree.cap_hits = sorted(index.cap_hits) + [("", "tree_budget_prep", len(units))]
 …
96      return res
```

- 88 行目: 「前処理で打ち切る設定が有効で、上限が決まっていて、走り始めてからの時間（`time.monotonic() - started`）が上限を超えていたら」という条件です。
- 91 行目: 見つけたユニットの**全部**の数を、飛ばした数にします。
- 94 行目: 木の打ち切りの記録に、`("", "tree_budget_prep", ユニットの数)` を足します。これが manifest の `truncations` の要素になります。
- 96 行目: 残りの前処理もユニットの解析もせずに、すぐ戻ります。

この時点 1 の打ち切りは、`scripts/scan_v2.py` だけが有効にしています（`prep_budget_exit=True`）。
meta-skill-evloving では、ファイルを読んで索引を作るだけで 225 秒、ユニットを見つけるのに 60 秒かかったと記録されています（D52 で、この木だけを走らせて測った値）。
ユニットを見つけた時点で、すでに 180 秒を超えていたわけです。
以前は、ここで超えていても残りの前処理を続けていたので、さらに時間を使っていました（D52 で直した）。

**時点 2: 次のユニットの解析に移るとき**

```python
128  budget_hit = False
129  for unit in units:
130      if cfg.max_tree_seconds and (time.monotonic() - started) > cfg.max_tree_seconds:
131          res.tree_budget_skipped += 1
132          budget_hit = True
133          continue
```

- 129 行目: 見つけたユニットを 1 つずつ取り出します。
- 130 行目: 次のユニットに移る前に、走り始めてからの時間が上限を超えていないかを見ます。
- 131 行目: 超えていたら、飛ばした数に 1 を足します。
- 132 行目: 「上限に当たった」という印を立てます。
- 133 行目: `continue` は「このユニットの残りの処理をせずに、次のユニットへ進む」という意味です。つまり、このユニットは解析せず、**結果の列にも足しません**。

上限を超えた後のユニットは、全部この 130〜133 行目を通って飛ばされます。
1 つのユニットの解析を始めてしまえば、途中では止めません。
だから、木の `elapsed_s` は 180 秒を超えることがあります。
（出典: `authgap/runner.py:48-60`（`max_tree_seconds` と `prep_budget_exit` の説明）、`:80-96`（時点 1）、`:128-133`（時点 2）、`:175-176`、`scripts/scan_v2.py:174`（既定の 180 秒）、`:253-255`（`prep_budget_exit=True`）、`docs/decisions.md:2768-2795`（D52 の測定と直したこと））

#### 2 つの置き場所

飛ばしたユニットの数（`tree_budget_skipped` という 1 つの値）は、次の 2 か所に書かれます。

| 置き場所 | 欄 | 書く所 |
|---|---|---|
| `summary.json` | `trees[].budget_skipped` | `scripts/scan_v2.py:272` |
| その木の manifest | `truncations` の要素 `{"relpath": "", "cap": "tree_budget", "count": <数>}`。前処理で打ち切ったときは cap が `tree_budget_prep` | `authgap/report.py:279-284`、`authgap/runner.py:91-94` |

表の読み方: 1 行が 1 つの置き場所です。
2 行目は「manifest では、`truncations` の列の中に、`relpath` が空で cap が `tree_budget`（前処理で打ち切ったときは `tree_budget_prep`）の要素として、同じ数が書かれる」と読みます。
manifest を書く関数は、前処理で打ち切った木では `tree_budget_prep` の要素だけを残し、`tree_budget` の要素を重ねて書きません（二重に数えないため）。

原典では、どちらの置き場所で確かめるかの書き方が割れています。

- **manifest の `tree_budget` を見る**と書くもの: 第 3 版 2462 行（手順 3「走らせた後、manifest で時間上限による打ち切り（`tree_budget`）の件数を確かめる」）、事前登録の下書き（`docs/drafts/prereg_2_12_draft.md:40`「走査の後、manifest の `tree_budget` で時間上限による打ち切りの件数を確かめ」）、v4 の規則（`docs/population_v4.md:41`「tree budget で打ち切った木（manifest の `tree_budget` の件数）」）。
- **`summary.json` の `budget_skipped` を見る**と書くもの: 手順書（`docs/final_evaluation_procedure.md:656`「`trees[].budget_skipped` … 時間上限で打ち切ったユニットの数」、`:1318`）。

**どちらも同じ事実の 2 つの置き場所**なので、どちらで確かめても同じ数になります。
食い違いではなく、書き方の違いです。
実際の作業では、次の順が確実です。

1. まず `summary.json` で、`budget_skipped` が 0 でない木を一覧にします（1 つのファイルで全部の木が見られるので速い）。
2. その木の manifest を開いて、`truncations` の `tree_budget`（または `tree_budget_prep`）の `count` が同じ数かを確かめます。

「manifest の `tree_budget` を探したが無い」ときは、**`tree_budget_prep`** も探します。
run24 の meta-skill-evloving のように、前処理で打ち切った木では、`tree_budget` という名前の要素は無いからです。

#### 飛ばしたユニットは manifest に無い

大事な点がもう 1 つあります。
**時間上限で飛ばしたユニットは、manifest の `units` に入りません。**
上の時点 2 の `continue` のとおり、解析器はそのユニットを結果の列に足さないからです。
残るのは**件数だけ**です。

- だから、飛ばしたユニットは、**矛の抜き取りにも、見落としの抜き取りにも、不の抜き取りにも出てきません**。判定のしようがありません。
- その代わり、件数は V1 頑健性として報告します。
- 打ち切った木を**取り直すことはしません**。手順書は「打ち切りがあっても取り直さない。件数を報告に書く」「取り直さない。件数と所要時間を記録する。遅いマシンなら、走らせる前に速いマシンを選ぶ（走らせた後に選び直さない）」と書いています。

#### 打ち切りはマシンの速さで変わる

時間上限は「時計の時間」なので、**同じ木でも、マシンの速さで打ち切りが変わりえます**。
実際に、凍結の直前の記録に次の例があります。
v2 の xagent の木は、run23 では 179.1 秒かかり、上限の 180 秒にあと 1 秒でした。
同じ解析器の run24 では 89.9 秒で、約半分でした。
記録は「同じコンテナでもマシンの速さは時間で変わる」「学生の最終評価のマシンが遅ければ打ち切られうる」と書いています。
（出典: `docs/decisions.md:3686-3689`、`:3699-3702`（D64 の追記））

#### 打ち切りの 4 つの水準

ここまでに出てきた「打ち切り」を、水準ごとに整理しておきます。

| 水準 | 印 | 置き場所 | 何が欠けるか |
|---|---|---|---|
| 木 | `tree_budget` / `tree_budget_prep` | `summary.json` の `budget_skipped`、manifest の `truncations`（`relpath` が空） | 飛ばしたユニットが**丸ごと**欠ける（manifest に無い） |
| ファイル | `ast_node_cap`、parse の失敗 | manifest の `truncations`（`relpath` つき）・`parse_failures`、`summary.json` の `n_truncations`・`n_parse_failures` | そのファイルの中身の全部。中の関数を呼んだユニットには `depends_on_dropped:` が付く。ツールの定義がそのファイルにあれば、そのツールはユニットにならない（O21） |
| ユニット | `TRUNCATED(recursion)` など | ユニットの `notes` | そのユニットの効果（`recursion` なら全部） |
| 追跡の深さ | `depth` | ユニットの `cap_hits`・`opaque_reasons` | 深さ 4 より奥の効果（[第 15 章](ch15.md)） |

表の読み方: 1 行が 1 つの水準です。
たとえば 4 行目は「ユニットの中で深さ 4 より奥に降りなかったときは、`cap_hits` に `depth` が付く。深さ 4 より奥の効果は見えていない」と読みます。
v4 では、3,696 ユニットのうち 1,022 ユニットの `cap_hits` に `depth` がありました（本書の執筆時に数えた。[第 15 章](ch15.md) 15.5 節と同じ数）。

どの水準の打ち切りでも、**欠けた所に違反があれば、それは解析器には見えていません**。
見落としの判定で打ち切りの印を気にするのは、このためです（[第 21 章](ch21.md)・[第 52 章](ch52.md)）。

#### なぜそうするのか

**時間上限を置く理由**は、1 本の木が走査全体を止めないためです。
**飛ばした数を必ず記録する理由**は、それが分母に効くからです。
解析器の説明は「黙って止めない — 野外走査で 1 本が全体を止めないための cap であり、打ち切った件数は母集団の分母に効くので必ず出す」と書いています。
**打ち切った木を取り直さない理由**は、「結果を見てから条件を選び直した」と疑われないためです。
以前、母集団 v2 の別の測定（付録の仕組みのための測定。[第 8 章](ch08.md)）で 716 ユニットが打ち切られたときも、上限を 900 秒にした再走は感度分析として併記するだけにし、主の結果は 180 秒のままにしました（事前登録の逸脱 #8）。打ち切られたユニットがすべて 1 本の木のもので、欠け方が偶然ではなかったからです。
（出典: `authgap/runner.py:48-52`、`docs/preregistration.md:559`（逸脱 #8）、`docs/decisions.md:358-372`（D34））

#### よくある誤解・つまずき

- **誤解: 「時間上限は 180 秒だから、どの木も 180 秒以内に終わる」**
  時計を見るのは区切りの時点だけなので、180 秒を大きく超えることがあります（run24 の meta-skill-evloving は 423.7 秒）。
- **誤解: 「manifest に `tree_budget` が無いから、打ち切りは無い」**
  前処理で打ち切った木では `tree_budget_prep` です。`summary.json` の `budget_skipped` でも確かめます。
- **誤解: 「`summary.json` と manifest で、打ち切りの数が食い違うことがある」**
  同じ 1 つの値から書かれるので、同じ数になります。原典の書き方が割れているだけです。
- **誤解: 「打ち切られたユニットも、manifest のどこかに名前だけ残る」**
  残りません。件数だけです。
- **誤解: 「打ち切りがあったら、速いマシンで取り直せばよい」**
  走らせた後に取り直しません。マシンは走らせる前に選びます。

#### 手作業ではどう使うか

- **段階 5 の後**: `summary.json` で `budget_skipped` が 0 でない木を全件書き出し、その木の `elapsed_s` も書きます。manifest の `truncations` で `tree_budget`（または `tree_budget_prep`）の `count` が同じかを確かめます。
- **走らせる前**: 走らせるマシン（CPU・メモリ・同時に走らせた本数）と日時を記録します。木ごとの時間はマシンの速さで変わるからです。
- **見落としの判定**: 抜き取られたユニットの木に `ast_node_cap` や parse の失敗があれば、そのファイルの中を自分で読みます。
- **論文**: 時間上限で飛ばしたユニットは判定できないので、その数を V1 頑健性として書きます。

（出典: `docs/final_evaluation_procedure.md:644`（マシンと日時の記録）、`:656, 660`（9.3）、`:1318`（23.1）、`:1439`（困ったとき））

#### この節のまとめ

時間上限（180 秒）を超えると、残りのユニットを飛ばす。時計を見るのはユニットを見つけた直後と、次のユニットに移るときだけで、木の時間は 180 秒を超えうる。
飛ばした数は `summary.json` の `budget_skipped` と manifest の `truncations` の `tree_budget`（前処理で打ち切ったら `tree_budget_prep`）の 2 か所に、同じ値から書かれる。原典の書き方の違いは、同じ事実の 2 つの置き場所。
飛ばしたユニットは manifest に無く、判定できない。取り直さず、件数と所要時間を報告する。

### 18.12 ユニットは relpath と行で探す

#### 一言で言うと

判定表の 1 行から manifest のユニットを探すときは、**`unit.relpath` と `unit.lineno` が両方一致するもの**を選びます。
qualname（関数の修飾名）やツールの名前だけで探すと、別のファイルにある同じ名前のツールを取り違えます（D64 の U50）。
詳しい理由と実例は、[第 12 章](ch12.md) 12.10 節で見ました。
ここでは、出力を読む場面での使い方を確かめます。

#### たとえ話 — 3 つの棟にある「101 号室」

大きな団地に、同じ形の棟が 3 つあるとします。
どの棟にも「101 号室」があります。
「101 号室の人に届けて」とだけ言われたら、どの棟の 101 号室か分かりません。
「B 棟の 101 号室」と、**棟と部屋番号の両方**で言われて、初めて 1 つに決まります。

ユニットの `relpath`（どのファイルか）が「棟」、`lineno`（何行目か）が「部屋番号」です。
qualname は「部屋に住んでいる人の名前」のようなもので、同姓同名がいます。

#### 小さな例 — zozi の 3 つの `zozi_cancel_order`

18.7 節で見た v4 の zozi の木では、`zozi_cancel_order` が 3 つのファイルの、どれも 584 行にありました。

| relpath | lineno | ユニットの `notes` | `unit_id` |
|---|---|---|---|
| `_extra_files/_legacy.bak/services/mcp/zozi_mcp.py` | 584 | `["TRUNCATED(wall_clock)"]` | `mcp:zozi_cancel_order:9774137cf09a` |
| `backend/jobs/mcp_marketplace_server.py` | 584 | `[]` | （同じ） |
| `backend/providers/ai/zozi_mcp.py` | 584 | `[]` | （同じ） |

表の読み方: 1 行が 1 つのユニットです。
qualname も行の番号も `unit_id` も 3 つとも同じで、違うのは `relpath` だけです。
そして、打ち切りの印は 1 行目のユニットにだけ付いています。
qualname で探して最初に見つかったものを開くと、別のユニットの印を読んだり、印を見落としたりします。
（出典: `evidence/scan_v2_v4_run1/v4-makfuncky__zozi.json`（本書の執筆時に確かめた）。[第 12 章](ch12.md) 12.10 節にも同じ例がある）

#### 一歩ずつ — 道具の探し方を読む

手順書の 6.5 節の道具は、ユニットを次のように探しています（必要な行だけを写す）。

```python
manifest_path, unit_relpath, unit_lineno, site = sys.argv[1], sys.argv[2], int(sys.argv[3]), sys.argv[4]
m = json.load(open(manifest_path, encoding="utf-8"))
for u in m["units"]:
    info = u["unit"]
    if info["relpath"] != unit_relpath or info["lineno"] != unit_lineno:
        continue
```

- 1 行目: コマンドの引数から、manifest のファイル、ユニットの relpath、ユニットの行、site の 4 つを受け取ります。`int(...)` は、行の番号を文字から数に直す関数です。
- 2 行目: manifest を読み込みます。
- 3 行目: ユニットを 1 つずつ取り出します。
- 4 行目: ユニットの `unit` の欄を `info` という名前で使えるようにします。

### 18.13 run の名前

#### 一言で言うと

run には名前（ラベル）を付け、結果は `evidence/scan_v2_<ラベル>/` に入ります。
開発用のデータ v2 の run は `run1`〜`run24`、v3 は `v3_run1`・`v3_run2`、v4 は `v4_run1` です。
最終評価の run は **`final_run1`**（フォルダは `evidence/scan_v2_final_run1/`）で、**これから作ります**。
同じラベルで取り直すことはできません。

#### たとえ話 — 実験ノートの通し番号

実験ノートには、実験ごとに通し番号を付けます。
同じ番号の実験を 2 回書くと、どちらが本当の結果か分からなくなります。
条件を変えたら、新しい番号を付けます。

run のラベルは、この通し番号です。

#### 小さな例 — これまでの run とこれからの run

| ラベル | フォルダ | データ | 役割 |
|---|---|---|---|
| `run1`〜`run24` | `evidence/scan_v2_run1/`〜`scan_v2_run24/` | 母集団 v2（開発用） | 解析器を直すたびに取り直した。`run24` が最終凍結 `analyzer-freeze-3` の根拠の run（[第 36 章](ch36.md)） |
| `v3_run1`・`v3_run2` | `evidence/scan_v2_v3_run1/` など | 母集団 v3（開発用の中間確認） | [第 34 章](ch34.md) |
| `v4_run1` | `evidence/scan_v2_v4_run1/` | 母集団 v4（凍結版の中間検証） | [第 37 章](ch37.md)。本記録者（AI）が判定した。数字は論文に使わない（D66 の 5） |
| **`final_run1`** | **`evidence/scan_v2_final_run1/`** | 最終評価のデータ | **これから作る**。走査は 1 回だけ |
| `final_depth3`・`final_depth5` | `evidence/scan_v2_final_depth3/` など | 最終評価のデータ | 深さの感度分析。矛の件数だけを出し、判定しない（下の注） |

表の読み方: 1 行が 1 つの run（または run の並び）です。
たとえば 4 行目は「最終評価の走査は `final_run1` というラベルで 1 回だけ走らせ、結果は `evidence/scan_v2_final_run1/` に入る。まだ走らせていない」と読みます。

深さの感度分析について補足します。
D69 の 5 は「手順書の 0-10 のとおり（件数だけ、探索的）」としています。
手順書の 0-10 は「時間があれば深さ 3・5 でも走らせ」と書き、事前登録の下書き（§2.12、未承認）は「深さの感度分析: **する**」と書いています。
下書きは学生が承認して封をするまで確定ではないので、ここでは「下書きでは、する」と書いておきます。
（出典: `docs/final_evaluation_procedure.md:248-251`（0-10）、`:621-645`（9.1・9.2 の走査）、`:662-669`（9.4 深さの感度分析）、`docs/drafts/prereg_2_12_draft.md:41`、`docs/decisions.md:3831`（D69 の 5）、`evidence/` の中のフォルダの名前（本書の執筆時に確かめた））

#### 一歩ずつ — 名前の決まり

- **フォルダの名前**: `scripts/scan_v2.py` の `--label` に渡した文字に、`scan_v2_` を頭に付けたものです。`--label final_run1` なら `evidence/scan_v2_final_run1/` です。スクリプトの名前に「v2」が入っているのは、母集団 v2 のために作ったスクリプトだからで、どのデータの run でも頭は `scan_v2_` です。
- **manifest のファイルの名前**: 木の名前 + `.json` です。木の名前の頭には、どの母集団の木かを表す接頭辞が付きます（v2 は `v2-`、v3 は `v3-`、v4 は `v4-`、最終評価は `final-`）。最終評価の木の名前は、抽出のスクリプトの `--prefix` で付けます。
- **manifest の中の run の名前**: manifest の `run_meta.run_id` には、ラベルがそのまま入ります（v4 なら `v4_run1`）。

（出典: `scripts/scan_v2.py:186`（フォルダの名前）、`:238`（manifest のファイルの名前）、`:260`（`run_id` にラベルを渡す）、`docs/final_evaluation_procedure.md:412, 556`（抽出の `--prefix`）、`.gitignore:27-29`（`v2-`・`v3-`・`v4-` の manifest））

#### 同じラベルで取り直せない

`scripts/scan_v2.py` は、出力先のフォルダにすでに manifest があると、走らせずに止まります。
止まるときの言葉は「同じ label で取り直すなら別の label にするか、中身を確かめて消してから走らせる（--resume は途中で止まった run の再開用）」です。
古い木の manifest を、今の結果として数えないための仕組みです。
例外は `--resume` で、途中で止まった run を続きから走らせるときだけ使います。
手順書も「途中で止まったとき（マシンの停止など）は `--resume` で続きから走らせてよい。**結果が気に入らないという理由で取り直さない。**」と書いています。
（出典: `scripts/scan_v2.py:144-152`（`_check_out_dir`）、`:179-180`（`--resume`）、`docs/final_evaluation_procedure.md:643`）

#### なぜそうするのか

ラベルを run ごとに変えるのは、**どの数字がどの run から来たか**を、後から誰でも追えるようにするためです。
最終評価の数字は、`scan_v2_final_run1` の `summary.json` と `contradictions.json`（とコミットした抜き取りの出力）から来た、と言えるようにします。
最終評価の走査を 1 回だけにするのは、何度も走らせて都合のよい結果を選んだ、と疑われないためです。

#### よくある誤解・つまずき

- **誤解: 「`scan_v2_` で始まるから、母集団 v2 の run」**
  スクリプトの名前から来た頭の文字です。v4 の run も `scan_v2_v4_run1` です。
- **誤解: 「結果がおかしければ、同じラベルで走らせ直せばよい」**
  スクリプトが止まります。最終評価では、そもそも取り直しません（道具の故障で止まったときの `--resume` だけ）。
- **誤解: 「`final_depth3`・`final_depth5` の矛も判定する」**
  深さの感度分析の run は件数だけを出し、判定しません。

#### 手作業ではどう使うか

- **段階 5**: `--label final_run1 --require-fingerprint docs/fingerprint.json` を付けて走らせます。走らせたマシンと日時を記録します。
- **段階 6・7**: 抜き取りと判定の道具には、`evidence/scan_v2_final_run1` を渡します。判定の手順 B で開く manifest は `evidence/scan_v2_final_run1/<木>.json` です。
- **練習**: v4 はすでに見たデータで、最終評価には使わないので、道具の試験には `evidence/scan_v2_v4_run1` を使ってよい、と手順書は書いています（6.7）。

（出典: `docs/final_evaluation_procedure.md:632-645`（9.2）、`:510-520`（6.7 の空回し））

#### この節のまとめ

run の結果は `evidence/scan_v2_<ラベル>/` に入る。v2 は `run1`〜`run24`、v3 は `v3_run1`・`v3_run2`、v4 は `v4_run1`、最終評価は `final_run1`（これから作る。1 回だけ）。

(1) この行から、組はいくつできますか。組を書き出してください。

**演習 18-3**（`verdicts` に `UNKNOWN` がある行は核の不か）: 次の 4 つの行（v4 の実物の形をもとにした作例）について、核の答え（どの宣言について矛・不か。どちらでもなければそう書く）を答えてください。

**演習 18-4**（`summary.json` と manifest から打ち切りを読む）: 最終評価の run を走らせた後、`summary.json` に次の木の記録がありました（作例）。

### 確認問題

**確認問題 18-1**: 1 つのツールから同じ `os.remove` に 3 本の道筋で届き、ツールの宣言は `readOnlyHint: true` だけです。manifest の `effects` には、この `os.remove` の要素がいくつ並びえますか。また、組はいくつですか。

**確認問題 18-2**: v4 の `summary.json` の `verdict_rows` では `CONTRADICTION` が 2,707、`contradictions.json` の `n` は 481 でした。論文に「矛の件数」として書くのはどちらの系統の数ですか。理由と、添えるべき単位を答えてください。

**確認問題 18-3**: あるユニットの `D_kind` が `{"bottom": true, "explicit": ["openWorldHint"], "open_world": true, "present_no_bound": ["readOnlyHint"]}` でした。このユニットに効く宣言は D1〜D4 のどれですか。理由も答えてください。

**確認問題 18-4**: あるツールの D2 の「不」を確かめたいとき、manifest のどの欄の何を見ますか。`contradictions.json` や `verdicts` の `UNKNOWN` では足りないのはなぜですか。
