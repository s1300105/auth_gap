### 前の分冊から持ってくる知識

この分冊を読むのに要る知識を、1 文ずつ言い直しておきます（詳しくは前の分冊と、括弧の中の章）。

- **組**: 判定の単位 = (木, ユニット, site, kind, 宣言)。同じ効果でも、宣言が違えば別の組です（手引き 11.1、L36-39。[付録 H-1](appendix-h-1.md#ah-1-5)）。
- **2 つの問い**: 矛の 1 組ごとに「到達するか」と「宣言に反するか」に答え、**両方が「はい」のときだけ正**です。到達するが反しないなら**誤**（原因: 宣言に反しない）、反するかを決められなければ**不明**です（11.2、L41-54。[付録 H-1](appendix-h-1.md#ah-1-6)）。この分冊は 2 つ目の問いの答え方です。1 つ目は手引き 14 節（[付録 H-3](appendix-h-3.md)、[第 49 章](ch49.md)）。
- **判定するのはコードの動作**: 解析器の理由（site 名や注記）が間違っていても、2 つの問いの答えが「はい」なら正です（L56-57）。
- **採った原理**（11.3、L59-74。[第 17 章](ch17.md)）: 1-i-b（呼び出しを越えて残る設定も環境）、1-ii-b（相手のサーバの状態も環境）、2-a（決まらないものは不明）、3-a（モデルが選べる値は「取りうる値の全体」で読む）、4-a（4 つの宣言すべて）。**「これくらいは違反と言えない」と自分の感覚で決めない。軽重はラベルで表す**（L61-64。[付録 H-1](appendix-h-1.md#ah-1-7)・[H-1.8](appendix-h-1.md#ah-1-8)）。
- **手順 F**（L152-154。[付録 H-2](appendix-h-2.md#ah-2-6)）: 第 15 節のその宣言の問いに答える。モデルが決める値は「取りうる値の全体」で考える。**D4 だけは除く**。
- **記録の欄**: 手順 H の `violates` 欄に `はい` / `いいえ` / `決められない` を書きます（L178）。誤なら `error_class` に E1〜E9（L179。分類は 17 節 L451-468）、決められないなら `unknown_reason`（L181）（[付録 H-2](appendix-h-2.md#ah-2-8)）。
- **矛・不・内**（解析器の答え）と**正・誤・不明**（人の判定）は別の層です。解析器が「不」にした組は、人が調べて決めてよい（[第 17 章](ch17.md) 17.12 節）。
- **理由コード**（13.1、L200-230）: `fs_write`・`net_post` など、解析器が矛・不に付ける短い名前。判定の手がかりですが、判定はコードで行います（L203。[付録 H-2](appendix-h-2.md#ah-2-9)）。

### H-4.1 第 15 節の見出し — 宣言ごとに 1 つの問い（手引き L310）

> 【原文 L310】
> ## 15. 宣言に反するかの決め方（D1〜D4）

**一言で言うと**: 第 15 節は、矛の判定の 2 つ目の問い「宣言に反するか」の答え方を、**宣言ごとに**決めた節です。4 つの小節は、どれも「**問い**（太字の 1 文）→ **表**（よく出る動作の答え）→（迷いやすい形などの補足）」の形をしています。

**ことばの確認**:

- **宣言 D1〜D4**: MCP のツールの注記（`ToolAnnotations`）のうち、ツールの振る舞いを縛る 4 つの値です。D1 = `readOnlyHint: true`、D2 = `destructiveHint: false`、D3 = `openWorldHint: false`、D4 = `idempotentHint: true`（[第 4 章](ch04.md) 4.2 節）。決定の記録の「決定 D1」とは別物です（[第 0 章](ch00.md)）。
- **反する**: その動作が、宣言の約束を破ること。判定表の `violates` 欄に `はい` と書きます。
- **問い**: 宣言の原文を、判定で答えやすい 1 文に言い換えたもの。
- **表**: よく出る動作について、問いの答えを先に書いておいたもの。表に無い形は、問いに戻って決めます。

**1 文ずつ読む**:

- 「15. 宣言に反するかの決め方（D1〜D4）」: 4 つの宣言のそれぞれについて、「反する / 反しない / 決められない」の決め方を書く、という見出しです。
- 第 15 節の小節は 4 つです: 15.1 D1（L312）、15.2 D2（L336）、15.3 D3（L357）、15.4 D4（L390）。どれも見出しの後に「**問い**:」で始まる太字の 1 文があります（L314、L338、L359、L392）。

**なぜこう決めたのか**: 宣言ごとに問いを分けるのは、MCP の仕様が 4 つの値に**別々の文**を書いているからです。原文（2026-07-28 版。2025-06-18・2025-11-25・draft でも同じ）を並べます。

| 宣言 | 仕様の原文 | 既定値 | 手引きの問い |
|---|---|---|---|
| D1 | "If true, the tool does not modify its environment." | `false` | 呼び出しの後に残る何かを変えるか（L314） |
| D2 | "If true, the tool may perform destructive updates to its environment. If false, the tool performs only additive updates." "(This property is meaningful only when `readOnlyHint == false`)" | `true` | 呼び出しの前からあったものを消す・上書きする・変えるか（L338） |
| D3 | "If true, this tool may interact with an "open world" of external entities. If false, the tool's domain of interaction is closed. For example, the world of a web search tool is open, whereas that of a memory tool is not." | `true` | 外部の相手、またはモデルが決める相手と通信しうるか（L359） |
| D4 | "If true, calling the tool repeatedly with the same arguments will have no additional effect on its environment."（`readOnlyHint == false` のときだけ意味を持つ） | `false` | 同じ引数で 2 回呼んだとき、2 回目が 1 回目の後の状態をさらに変えるか（L392） |

表の読み方: 1 行目は「仕様は `readOnlyHint` が true なら『ツールは環境を変えない』と書く。何も書かなければ false（変えるかもしれない）とみなす。手引きはこれを『呼び出しの後に残る何かを変えるか』という問いに言い換えた」と読みます。
（出典: 原文は `docs/annotations_official_survey.md:87-90`（同じ文書の :92 に「すべて [確認]」）、`docs/contradiction_principles.md:24-30`。版の比較は `docs/decisions.md:1889-1891`（D41）。）

4 つすべてを、宣言ごとに分けて判定・報告するのは、採った原理 4-a です（`docs/contradiction_principles.md:141`。D62 で 4 つとも主指標）。
「宣言側は閉じているので網羅できる」（同じ行）、つまり仕様が縛りを作る値は 4 つしかないので、4 つの問いを決めれば定義は全部そろう、という考え方です（D41、`docs/decisions.md:1892-1896`）。

**D2 と D4 の前提**（手引きの第 15 節には書かれていないが、解析器と判定表の前提）: 仕様は D2 と D4 を「`readOnlyHint == false` のときだけ意味を持つ」としています。解析器も、`readOnlyHint: true` があるツールには D2 と D4 を当てません（`authgap/dparse.py:212`・`:236`（宣言の読み取り）、`:584-600`（D1 なら D2 を見ない。D4 は読み取り専用でないときだけ）。判定表では `docs/contradiction_principles.md:179`・`:214` の見出し）。D3 は `readOnlyHint` と関係なく当てます（`dparse.py:593-596`）。だから、判定表に D2・D4 の組が出てくるのは、読み取り専用と宣言していないツールだけです。

**例で確かめる**（作った例）: 1 つのツールに宣言を 2 つ書いた形です。

```python
@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True, idempotentHint=True, openWorldHint=False))
def note(text: str) -> str:
    with open("/srv/app/notes.txt", "a") as fh:   # 定数のファイルに 1 行追記
        fh.write(text + "\n")
    return "ok"
```

- 照らす宣言は D1 と D3 です。D4 は `readOnlyHint: true` があるので当てません（上の前提）。
- D1: 追記はファイルの書き込みなので**反する**（15.1 の表の 1 行目）。
- D3: 通信していないので**反しない**（15.3 の表の最後の行）。解析器も D3 では何も出しません。
- もし `readOnlyHint=True` を消すと、D4 も当たり、「2 回呼べば 2 行になる」ので**反する**（15.4 の表の 1 行目）。D2 も書いていれば、追記は「足すだけ」なので**反しない**（15.2 の表の 1 行目）。

同じ 1 行の追記でも、宣言で答えが分かれます。だから組は宣言ごとに分け、答えも宣言ごとに出します。

**迷いやすいところ**:

- 「反する」は「危ない」ではありません。問いは「宣言は正しいか」で、「危ないか」ではない（L61-62、D67 の 1）。
- 「反しない」と決めたら、その組は**誤**になります（到達はするが反しない、L52）。誤の原因は多くが E2 か E8 です（L459・L465）。
- 表に答えが書いてあっても、最後に**問い**に戻って確かめます。表に無い形は、問いに当てて決めます。それでも決まらなければ「決められない」（不明）にし、「手引きで決まらない: …」と書きます（22 節、L729-735）。

**承認の前に自分に問うこと**:

1. 4 つの問いは、それぞれ仕様の原文の言い換えとして自然か。自分ならどう言い換えるか。
2. 同じ動作を、宣言ごとに別の組として別に答えることに納得できるか。
3. 表と問いが食い違って見えたら、どちらを採るか（この分冊の各節で、そういう箇所を挙げます）。

**この節で手引きが決めていないこと**: 見つからなかった（D2・D4 が `readOnlyHint: true` のツールに当たらないことは、手引きの第 15 節には書かれていませんが、判定表に組が出ないので、判定では困りません）。

### H-4.2 15.1 D1 `readOnlyHint: true` の問いと表（手引き L312-328）

> 【原文 L312-328】
> ### 15.1 D1 `readOnlyHint: true` —「環境を変えるか」
>
> **問い**: その動作は、呼び出しの後に残る何かを変えるか（ホストのファイル・DB・相手のサーバの状態・残る設定）。
>
> | 動作 | 反するか | 注意 |
> |---|---|---|
> | ファイルの書き込み・作成・削除・移動・権限の変更（`FS_WRITE` すべて） | **反する** | ログ・キャッシュ・一時ファイル・ディレクトリの作成も含む（原理 1-i-b）。軽重はラベルで表す |
> | コードの実行（`EXEC`） | 反する | 表 D41 で決定済み |
> | プロセスの起動（`SPAWN`） | 起動するコマンドをモデルが決められるなら反する。コマンドが定数なら、**そのコマンドが実際に何をするか**を調べ、環境を変えるなら反する・変えないなら反しない・分からなければ不明 | 解析器は定数のコマンドを「不」にする（意味が名前から分からないため）。人は調べられる範囲で調べる |
> | DB のデータ・スキーマの変更（`INSERT` / `UPDATE` / `DELETE` / `CREATE` / `DROP` など） | 反する | |
> | DB に残る設定・保守（`PRAGMA journal_mode=WAL`、`VACUUM` など） | 反する | 原理 1-i-b |
> | DB の接続単位の設定・トランザクション（`BEGIN` / `COMMIT` / `PRAGMA foreign_keys=ON` など） | 反しない | 接続が閉じれば消える |
> | DB の読み取り（`SELECT` など） | 反しない | |
> | HTTP の `PUT` / `PATCH` / `DELETE` | 反する | 原理 1-ii-b |
> | HTTP の `POST` | **相手の API の意味を調べて決める**。相手のドキュメントや API 名から「作成・更新・削除」なら反する、「照会」（検索 API・RPC の読み取り）なら反しない、分からなければ不明 | 解析器は `POST` を「不」にする。人は調べられる範囲で調べる |
> | HTTP の `GET` / `HEAD` / `OPTIONS` | 反しない | |
> | ファイルの読み取り | 反しない | |

**一言で言うと**: D1 の問いは「**その動作は、呼び出しの後に残る何かを変えるか**」です。ファイルを書く・作る・消す動作は、ログ・キャッシュ・一時ファイルでも、すべて反します。DB の変更と DB に残る設定、HTTP の `PUT`・`PATCH`・`DELETE` も反します。読み取りと `GET` は反しません。解析器が「不」にする**定数のコマンド**と **`POST`** は、人が中身を調べて決めます。

**ことばの確認**:

- **環境**（environment）: 仕様の原文の言葉。手引きは「ホストのファイル・DB・相手のサーバの状態・残る設定」と具体化しています。
- **`FS_WRITE`**: 解析器の効果の種類（kind）の 1 つ。ファイルの書き込み・作成・削除・移動・権限の変更をまとめた名前です（[第 13 章](ch13.md)）。
- **`EXEC`**: コードの実行（`eval`・`exec` など）。**`SPAWN`**: プロセスの起動（`subprocess.run` など）。
- **定数のコマンド**: 起動するプログラム（`argv0`。コマンドの列の先頭）やシェルの文字列が、コードに書かれた決まった値のもの。たとえば `["git", "log"]`。
- **DB の接続単位の設定**: DB とのつながり（接続）を閉じれば消える設定。`PRAGMA foreign_keys=ON` など。**DB に残る設定**: DB のファイルに記録され、接続を閉じても残る設定。`PRAGMA journal_mode=WAL` など（[第 10 章](ch10.md) 10.8 節）。
- **トランザクション**: 複数の変更をひとまとめにする仕組み。`BEGIN` で始め、`COMMIT` で確定、`ROLLBACK` で取り消します。
- **HTTP のメソッド**: 相手に何を頼むかの種類。`GET`（ください）、`POST`（処理して）、`PUT`（置いて・置き換えて）、`PATCH`（一部を変えて）、`DELETE`（消して）など（[第 10 章](ch10.md) 10.2 節）。
- **照会**: 相手の状態を変えずに、情報を問い合わせること（検索、読み出し、計算の依頼）。**RPC**: 遠くの関数を呼ぶ形の API。読み取りの問い合わせも `POST` で送ることが多い。
- **不**: 解析器の答えの 1 つ。静的に決められない、という意味です（原理 2-a）。

**1 文ずつ読む**:

- **見出し（L312）**: D1 は `readOnlyHint: true`、問いの要約は「環境を変えるか」です。
- **問い（L314）**: 「その動作は、呼び出しの後に残る何かを変えるか」。括弧の 4 つが「残る何か」の中身です。
  - ホストのファイル（ツールが動いているマシンのファイル）
  - DB（行・表・スキーマ）
  - 相手のサーバの状態（原理 1-ii-b で環境に含める）
  - 残る設定（原理 1-i-b。DB の `journal_mode` など）
- **表の 1 行目（L318）**: ファイルの書き込み・作成・削除・移動・権限の変更は、`FS_WRITE` の**すべて**が反します。注意の欄は「ログ・キャッシュ・一時ファイル・ディレクトリの作成も含む（原理 1-i-b）。軽重はラベルで表す」。新しく作るだけでも反します（「壊すか」は D2 の問いで、D1 は「変えるか」）。どれほど小さな書き込みでも反し、その軽さは第 16 節の書き込み先の種類（ログ・一時ファイルなど）で表します。
- **2 行目（L319）**: コードの実行（`EXEC`）は反します。「表 D41 で決定済み」は、原理を選ぶより前に決めてあったマスで、原理の選択では動かさない、という意味です（`docs/contradiction_principles.md:34-36`、`:121-123`）。
- **3 行目（L320）**: プロセスの起動（`SPAWN`）は 2 つに分かれます。
  - 起動するコマンドを**モデルが決められる**なら反する（原理 3-a。モデルは何でも起動できる）。
  - コマンドが**定数**なら、「そのコマンドが実際に何をするか」を調べ、環境を変えるなら反する・変えないなら反しない・分からなければ不明。
  - 注意の欄: 解析器は定数のコマンドを「不」にする（意味が名前から分からないため）。人は調べられる範囲で調べる。
- **4 行目（L321）**: DB のデータ・スキーマの変更（`INSERT` / `UPDATE` / `DELETE` / `CREATE` / `DROP` など）は反します。
- **5 行目（L322）**: DB に残る設定・保守（`PRAGMA journal_mode=WAL`、`VACUUM` など）は反します（原理 1-i-b）。
- **6 行目（L323）**: DB の接続単位の設定・トランザクション（`BEGIN` / `COMMIT` / `PRAGMA foreign_keys=ON` など）は反しません。理由は「接続が閉じれば消える」。
- **7 行目（L324）**: DB の読み取り（`SELECT` など）は反しません。
- **8 行目（L325）**: HTTP の `PUT` / `PATCH` / `DELETE` は反します（原理 1-ii-b）。手元のファイルは何も変わらなくても、相手のサーバの状態が変わるからです。
- **9 行目（L326）**: HTTP の `POST` は「**相手の API の意味を調べて決める**」。相手の文書や API の名前から「作成・更新・削除」なら反する、「照会」（検索 API・RPC の読み取り）なら反しない、分からなければ不明。注意の欄: 解析器は `POST` を「不」にする。人は調べられる範囲で調べる。
- **10 行目（L327）**: HTTP の `GET` / `HEAD` / `OPTIONS` は反しません。
- **11 行目（L328）**: ファイルの読み取りは反しません。

**なぜこう決めたのか**:

- **ファイルの書き込みはすべて反する**: 原文は "does not modify its environment"（環境を変えない）で、ログや一時ファイルを除く根拠が原文に無いからです。原理 1-i-b の理由は「"does not modify its environment" の字義。データに限る根拠は文言に無い」（`docs/contradiction_principles.md:137`）。`FS_WRITE` を新規作成も含めて矛にするのは、原理を選ぶ前から決まっていたマスです（`:121`）。
- **相手のサーバの状態も含める**: 原理 1-ii-b の理由は「readOnly は『変更するか』、openWorld は『外と関わるか』で別の軸（仕様の例: web 検索は open world かつ読み取り）」（`:138`）。
- **`PUT`・`PATCH`・`DELETE` は調べずに反する、`POST` は調べる**: HTTP の標準の意味（RFC 9110）で、`PUT`・`DELETE` は相手を変えることを頼むメソッドだからです。`POST` は「処理して」で、作成にも照会にも使われます（`:62` の例「RPC の照会も `POST` で送る」、§7.1 の `:173-175`、[第 10 章](ch10.md) 10.2・10.4 節）。
- **接続単位の設定は反しない**: 「呼び出しを越えて残るか」で線を引いているからです（1-i-b は「接続単位のものだけ除く」、`:49`）。
- **定数のコマンドと `POST` を人が調べる**: 解析器はコードだけを動かさずに読むので、コマンドや相手の API の意味を決められず、原理 2-a で「不」にします（`:62-66`、§7.1 の `:165`・`:175`）。人の判定は「本当はどうか」を確かめる作業なので、調べられる範囲で調べます。調べ方は[第 50 章](ch50.md) 50.3 節、目安は 20〜30 分（19 節、L573）。
- 手引きの表は、解析器の判定表 §7.1（`docs/contradiction_principles.md:160-177`）を、人の問いに直したものです。解析器の答えの全体は `authgap/dparse.py:372-394`（`_d1`）。

```python
import fcntl, os, sqlite3, subprocess, tempfile
import requests

def scratch(text: str) -> str:                     # (A) 一時ファイルを作って消す
    fd, path = tempfile.mkstemp()
    os.close(fd)
    try:
        with open(path, "w") as fh:
            fh.write(text)
        return str(os.path.getsize(path))
    finally:
        os.remove(path)

def locked_read(name: str) -> str:                 # (B) 錠のためにファイルを 'a' で開くだけ
    with open("/srv/h4/app.lock", "a") as lock:
        fcntl.flock(lock, fcntl.LOCK_EX)
        with open(os.path.join("/srv/h4/data", name)) as fh:
            return fh.read()

def git_log() -> str:                              # (C) 定数のコマンド（表示だけ）
    return subprocess.run(["git", "log", "-1"], capture_output=True, text=True).stdout

def search(q: str) -> str:                         # (D) POST（検索の API）
    return requests.post("https://api.example.com/v1/search", json={"q": q}).text

def calc() -> str:                                 # (E) 定数のコードの実行

def mem_db(rows: str) -> str:                      # (F) メモリの中だけの DB
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE t (v TEXT)")
    conn.execute("INSERT INTO t VALUES (?)", (rows,))
    return str(conn.execute("SELECT count(*) FROM t").fetchone())
```

- (A): `tempfile.mkstemp()` は、OS の一時領域に新しい空のファイルを作り、その番号（`fd`）と場所（`path`）を返します。`with open(path, "w")` で書き、`finally:` の中の `os.remove(path)` で必ず消します。
- (B): 錠（`flock`）をかけるためだけに、ロック用のファイルを `'a'` で開きます。`'a'` はファイルが無ければ作り、あっても中身を消しません。このツールは錠のファイルに何も書きません。
- (C): `git log -1` を起動し、最新の記録を 1 件表示させて、その出力を返します。
- (D): 検索語を本体に入れて、検索の API に `POST` します。
- (E): 決まった文字列 `"1 + 1"` を Python のコードとして実行します。
- (F): `":memory:"` はファイルを作らない、メモリの中だけの SQLite の DB です。接続を閉じれば（関数を抜けて捨てられれば）中身ごと消えます。

### H-4.3 15.1 D1 の迷いやすい形 — ログ・子の標準入力・クライアントへの通知（手引き L330-334）

> 【原文 L330-334】
> **迷いやすい形**:
>
> - **標準出力・標準エラーへのログ**: ファイルではないので反しない（`logging` の出力先がファイルなら反する。出力先の設定を確かめる）。
> - **子プロセスの標準入力への書き込み**: それ自体はファイルを変えない。子プロセスがそれを受けて何をするかで決める（第 17 節 E5）。
> - **クライアントへの通知**（`ctx.info()` / `ctx.report_progress()`）: 環境を変えないので反しない。

**一言で言うと**: どれも「何かを書いている」ように見えるが、**行き先がファイルではない**形です。標準出力・標準エラーへのログとクライアントへの通知は反しません。ログの出力先がファイルなら反します。子プロセスの標準入力への書き込みは、子が何をするかで決めます。

**ことばの確認**:

- **標準出力・標準エラー**: プログラムが文字を出す 2 つの出口。ファイルではなく、プロセスの出入り口です。stdio で動く MCP サーバでは、標準出力は MCP のやりとりに使うので、ログはふつう標準エラーに出します（[第 9 章](ch09.md) 9.5 節）。
- **`logging` の出力先**: Python の `logging` は、ロガー（記録係）に付けたハンドラ（出し口）で行き先が決まります。`StreamHandler(sys.stderr)` なら標準エラー、`FileHandler(<パス>)` や `basicConfig(filename=…)` ならファイルです。
- **子プロセスの標準入力**: `subprocess` で起動した子に、こちらから管（パイプ）で文字を流し込む口。解析器はこれを `pipe:write` / `pipe:communicate` という site で表します。
- **E5**: 誤の原因の記号。「子プロセスの標準入力・パイプを書き込みと読んだ」（L462）。
- **`ctx`**: FastMCP のツールが受け取る、クライアント（ツールを呼んだ AI のアプリ）への連絡口。`ctx.info()` はログのメッセージを、`ctx.report_progress()` は進み具合をクライアントに送ります（[第 3 章](ch03.md)）。

**1 文ずつ読む**:

- **見出し（L330）**: 「迷いやすい形」。表の行のどれに当たるか迷いやすい 3 つの形です。
- **1 つ目（L332）**: 標準出力・標準エラーへのログは、ファイルではないので反しない。括弧の中で「`logging` の出力先がファイルなら反する。出力先の設定を確かめる」と、例外と確かめ方を書いています。ログを書く行（`log.info(...)`）を見ただけでは決まらず、**そのロガーの出力先の設定**を見て決める、という意味です。
- **2 つ目（L333）**: 子プロセスの標準入力への書き込みは、それ自体はファイルを変えない。子がそれを受けて何をするかで決める（第 17 節 E5）。子が `sort` のように並べ替えて出すだけなら反しない、子が `tee <ファイル>` のように受け取ったものをファイルに書くなら反する、ということです。
- **3 つ目（L334）**: クライアントへの通知（`ctx.info()` / `ctx.report_progress()`）は、環境を変えないので反しない。

**なぜこう決めたのか**:

- 問い（L314）は「呼び出しの後に残る何かを変えるか」です。標準エラーに流れた文字は、ツールのコードの側では何も残しません。だから反しません。ファイルの出し口があれば、ファイルに行が残るので反します。
- 子の標準入力は、流すこと自体はファイルを変えません。けれども子がファイルを書けば、ツールの呼び出しによってファイルが変わったことになります。だから子で決めます。解析器はこの区別をせず、子の標準入力への流し込みを一律に `FS_WRITE` にします。O41 はこれを「インタプリタの一覧に無い argv0 でも標準入力はコード実行・ファイル書き込みに届く（`env python3`・`tee` など）ので、情報行は保守的な上界として正しい」として、直さないと記録しています（`docs/open_questions.md:1070-1072`）。
- `ctx` の通知は、クライアントへのメッセージです。クライアントがそれをどう扱うかは、クライアントの側の動作です。
- 理由は手引きに 1 文ずつしか書かれていません。「起動した側が標準エラーをファイルにつなぐのは、ツールのコードの動作ではない」という説明は、[第 50 章](ch50.md) 50.4 節の本書の説明です（手引き 11.2 の「判定するのはコードの動作」、L56-57 と同じ考え方）。

**例で確かめる**（作った例。どれも `readOnlyHint=True`）:

```python
import logging, subprocess, sys
from mcp.server.fastmcp import Context

logging.basicConfig(stream=sys.stderr, level=logging.INFO)      # ルートの出し口は標準エラー
log = logging.getLogger("h4d1")
audit = logging.getLogger("h4d1.audit")
audit.addHandler(logging.FileHandler("/var/log/h4d1/audit.log"))  # audit にだけファイルの出し口

def stderr_only(q: str) -> str:            # (G)
    log.info("q=%s", q)
    return q

def audited(q: str) -> str:                # (H)
    audit.info("q=%s", q)
    return q

def sort_text(text: str) -> str:           # (I) 子は sort
    p = subprocess.Popen(["sort"], stdin=subprocess.PIPE, stdout=subprocess.PIPE, text=True)
    out, _ = p.communicate(input=text)
    return out

def tee_text(text: str) -> str:            # (J) 子は tee -a <ファイル>
    p = subprocess.Popen(["tee", "-a", "/var/tmp/h4_copy.txt"], stdin=subprocess.PIPE, stdout=subprocess.PIPE, text=True)
    out, _ = p.communicate(input=text)
    return out

async def progress(q: str, ctx: Context) -> str:   # (K)
    await ctx.info("start " + q)
    await ctx.report_progress(1, 2)
    return q
```

- `logging.basicConfig(stream=sys.stderr, ...)` の行: 、ルートのロガーの出し口を標準エラーにします。`log` はルートの子なので、記録は標準エラーに出ます。
- `audit` には `FileHandler` を足しています。`audit.info(...)` は、そのファイルに 1 行足します（親のルートにも回るので、標準エラーにも出ます）。
- (I)(J): `Popen(..., stdin=subprocess.PIPE)` で子の標準入力に管をつなぎ、`communicate(input=text)` で `text` を流し込みます。`tee -a <ファイル>` は、受け取ったものを標準出力に出しながら、そのファイルの末尾にも書き足すコマンドです。

| 例 | 本書の試験（解析器、D1） | 人の答え（D1） | 判定 |
|---|---|---|---|
| (G) | 効果なし | 反しない（行き先は標準エラーだけ） | —（矛が無い） |
| (H) | **効果なし** | **反する**（行き先にファイルがある） | —（矛が無い。見落としの判定でなら「見落とし」、原因は語彙。v4 の R19 と同じ類、L685） |
| (I) | **矛** `pipe:communicate` × `FS_WRITE`（`fs_write`）、不 `spawn_command`（起動） | 反しない（`sort` は並べ替えて出すだけ） | **誤、E5**（[第 50 章](ch50.md) 50.4 節の試験と同じ） |
| (J) | **矛** `pipe:communicate` × `FS_WRITE`（`fs_write`）、不 `spawn_command`（起動） | **反する**（子の `tee -a` がファイルに書き足す） | **正** |
| (K) | 効果なし | 反しない（クライアントへの通知） | — |

表の読み方: 3 行目と 4 行目は、解析器の答えが同じなのに、人の答えが分かれる対です。違いは**子が何をするか**だけです。

もう 1 つ、本書の試験で見えたことがあります。`subprocess.run(["sort"], input=text, ...)` の形（`Popen` と `communicate` ではなく `run` の `input=`）では、`pipe:communicate` の行は出ず、起動の `SPAWN` の不（`spawn_command`）だけが出ました。子が `tee` のようにファイルを書く形をこの書き方で書くと、矛は出ず、見落としの判定の側で見つかることになります。

**迷いやすいところ**:

- **ログの出力先は、ツールの関数の外で決まることが多い**: モジュールの一番上、`__init__.py`、`main()`、設定ファイル（`dictConfig`）を探します。手引き 18.3（L513-514）も「モジュール水準の設定も確かめる」と書いています。親のロガーへ回るか（`propagate`）、その水準の記録が実際に出るか（ロガーの水準）も見ます。確かめ方の 5 点は[第 50 章](ch50.md) 50.4 節。
- **ログの出力先が設定で決まる**（環境変数 `LOG_FILE` があればファイル、など）: 到達の条件として扱い、条件の種類は `運用者の設定`（14.3、L262）。`main()` の中だけで設定する形は 14.4 の考え方で決めます（[第 50 章](ch50.md) 50.11 節の候補 6 も参照）。
- **起動した側が標準エラーをファイルに保存する**ことがあります（AI のアプリが、サーバの標準エラーをログファイルに写すなど）。手引きは「ファイルではないので反しない」とだけ書いています。本書の読み: 判定するのはツールのコードの動作で、起動した側の選択は数えない。
- **`pipe:write` の矛でも、子がインタプリタ（`python -`、`sh`）で、流すのがコードなら**、子はそのコードを実行します。コードが何をするかで決めます（L333「子プロセスがそれを受けて何をするかで決める」）。
- **1 つのツールに、反する組と反しない組が並ぶ**ことがあります。v4 の ru-marketplace では、一時ファイルの削除（M58）は正、子の標準入力（M59）は誤 E5 でした（L679・L683）。組ごとに、その組の動作だけで決めます。

**承認の前に自分に問うこと**:

1. 標準エラーへのログは反しない、ファイルへのログは反する。この線引きに納得できるか。
2. 子の標準入力の矛で、子のコマンドの意味を調べるとき、どこまで調べるか（オプション・子が読むスクリプトの中身）。
3. 下の【穴 H-4-8】のように、標準エラーでもファイルでもない「残る出力先」を、自分ならどちらに読むか。

**この節で手引きが決めていないこと**:

【穴 H-4-8】**標準出力・標準エラーでもファイルでもない、残る出力先**
- 何が決まっていないか: L332 は「標準出力・標準エラー → 反しない」「ファイル → 反する」の 2 つだけを書いています。システムのログ（syslog・journald への `SysLogHandler`）、OS のイベントログ、外のログ・エラー収集のサービスへの送信（HTTP で送るハンドラ）は、どちらにも当たりません。syslog はファイルではありませんが、呼び出しの後に記録が残ります。
- 困る事例（作った例）:

  ```python
  def via_syslog(q: str) -> str:            # readOnlyHint=True
      lg = logging.getLogger("h4d1.sys")
      lg.addHandler(logging.handlers.SysLogHandler(address="/dev/log"))
      lg.info("q=%s", q)
      return q
  ```

  解析器は効果を出しません（本書の試験）。
- 選択肢: (a) 「残る何か」なので反する（ファイルと同じ）。(b) ファイルでないので反しない（標準エラーと同じ）。(c) 行き先のサービスの設定まで読み切れなければ不明。外のサービスへの送信なら、15.1 の `POST` の行で決める、という分け方もありえます。
- 関係する決定: 問い（L314）、原理 1-i-b（`docs/contradiction_principles.md:49`）、18.3（L513-514）。最終評価で出る場面: D1 の見落とし。

### H-4.4 15.2 D2 `destructiveHint: false` の問いと表（手引き L336-347）

> 【原文 L336-347】
> ### 15.2 D2 `destructiveHint: false` —「追加の更新だけか」
>
> **問い**: その動作は、**呼び出しの前からあったもの**を消す・上書きする・変えるか。新しく足すだけなら反しない。
>
> | 動作 | 反するか |
> |---|---|
> | 新しく作るだけ（`mkdir`、`open('x')`、`open('a')` の追記、DB の `INSERT` / `CREATE`、HTTP の `GET`） | 反しない |
> | 既存のものを消す・動かす・変える（`unlink` / `rmtree` / `rename` / `chmod`、DB の `UPDATE` / `DELETE` / `DROP` / `ALTER`、HTTP の `DELETE` / `PATCH`） | **反する** |
> | 書き出し（`open('w')` / `write_text` / `copy` など） | **書き先をモデルが決められるなら反する**（既存のファイルを指せば上書きできる。原理 3-a）。書き先が固定なら、そこに**呼び出しの前からファイルがありうるか**で決める（毎回同じファイルを上書きするなら反する、呼び出しごとに新しい名前なら反しない、分からなければ不明） |
> | HTTP の `PUT` | 宛先をモデルが決められるなら反する。そうでなければ、既存の資源の置き換えか新規作成かで決める |
> | HTTP の `POST` | 相手の API の意味で決める（既存の資源を更新・削除するなら反する） |
> | DB に残る設定の変更 | 「追加か破壊か」が当てはまらない → 不明（解析器と同じ） |

**一言で言うと**: D2 の問いは「**呼び出しの前からあったものを消す・上書きする・変えるか**」です。新しく足すだけなら反しません。削除・移動・権限の変更・`UPDATE`・`DELETE`・HTTP の `DELETE`・`PATCH` は反します。書き出し（`'w'` など）は書き先で分かれます: **モデルが書き先を決めるなら反する**。固定の書き先なら、そこに**呼び出しの前からファイルがありうるか**で決めます。

**ことばの確認**:

- **destructiveHint**: 仕様は「true なら破壊的な更新をしうる。false なら追加だけの更新をする（additive updates）」と書きます（`docs/annotations_official_survey.md:88`）。
- **追加の更新**: 前からあるものを消さず、新しいものを足すだけの変更。
- **書き出し**: ファイルの中身を書く操作のうち、前の中身を消して書き直すもの。`open(p, 'w')`、`Path.write_text`、`shutil.copy` など。ファイルが無ければ新しく作り（追加）、あれば上書きします（破壊）。
- **`open('x')`**: ファイルが無いときだけ作って書く。あればエラーになるので、上書きはしません。**`open('a')`**: 末尾に足す。前の中身は消しません。
- **書き先をモデルが決める**: 書き先のパスの値の主体が MODEL で、確度が resolved（モデルの入力がモデリングした操作だけで届く）。解析器の理由は `fs_writeout_model_path`（L212）。
- **`PUT`**: 相手に「この URL にこの中身を置いて（あれば置き換えて）」と頼むメソッド。
- **DB に残る設定**: `PRAGMA journal_mode=WAL` など（[H-4.2](#ah-4-2)）。

**1 文ずつ読む**:

- **見出し（L336）**: D2 は `destructiveHint: false`、要約は「追加の更新だけか」。
- **問い（L338）**: 「呼び出しの前からあったものを消す・上書きする・変えるか」。後半「新しく足すだけなら反しない」が、仕様の "additive updates" の言い換えです。
- **表の 1 行目（L342）**: 新しく作るだけ（`mkdir`、`open('x')`、`open('a')` の追記、DB の `INSERT` / `CREATE`、HTTP の `GET`）は反しない。`GET` は作りもしませんが、何も壊さないので同じ行に入れてあります（本書の読み）。
- **2 行目（L343）**: 既存のものを消す・動かす・変える（`unlink` / `rmtree` / `rename` / `chmod`、DB の `UPDATE` / `DELETE` / `DROP` / `ALTER`、HTTP の `DELETE` / `PATCH`）は反する。
- **3 行目（L344）**: 書き出し（`open('w')` / `write_text` / `copy` など）は 2 段で決めます。
  1. **書き先をモデルが決められるなら反する**（既存のファイルを指せば上書きできる。原理 3-a）。
  2. 書き先が固定なら、そこに**呼び出しの前からファイルがありうるか**で決める。毎回同じファイルを上書きするなら反する（2 回目からは前の呼び出しの中身を消す）。呼び出しごとに新しい名前なら反しない。分からなければ不明。
- **4 行目（L345）**: HTTP の `PUT` は、宛先をモデルが決められるなら反する。そうでなければ、既存の資源の置き換えか新規作成かで決める。
- **5 行目（L346）**: HTTP の `POST` は、相手の API の意味で決める。既存の資源を更新・削除するなら反する。作成は「足すだけ」なので反しません（L338 の後半）。
- **6 行目（L347）**: DB に残る設定の変更は、「追加か破壊か」が当てはまらない → 不明（解析器と同じ）。人が調べても答えは変わらない、と先に決めてある行です。

**なぜこう決めたのか**:

- **追記・作成は反しない、削除・移動・変更は反する**: 仕様の "performs only additive updates" の字義です。`mkdir` / `open('a')` を D2 で宣言内、削除・上書きを矛とするのは、原理を選ぶ前から決まっていたマスです（`docs/contradiction_principles.md:34-36`、`:121-123`）。DB の `INSERT` / `CREATE` は内、`UPDATE` / `DELETE` / `DROP` などは矛（D55、`:189-190`）。
- **書き出しは書き先で分ける**: `'w'` は、書き先にファイルがあるかで追加にも破壊にもなります。解析器は動かさずに読むので、書き先が固定なら決められず「不」（`fs_writeout`）にします（§5 の #7、`:109`。§7.2、`:187`）。人は、名前が毎回同じか・前の呼び出しが残すかを読んで決められます。
- **モデルが書き先を決めるなら反する**: 原理 3-a「モデルが既存ファイルを指せば上書きでき…るので矛盾」（`:77-79`）。実際にモデルがそうするかは問いません。D2 の宣言を見て、クライアントは確認を省くことがあるからです（D68 の 1 の理由、`docs/decisions.md:3800-3801`）。
- **`PUT` を `'w'` と同じに扱う**: 「作成か置換か分からない。#7 と同じ理屈」（§7.2、`docs/contradiction_principles.md:196`）。
- **DB に残る設定を不明にする**: 「1-i-b だが『追記か破壊か』が設定の変更に当てはまらない」（§7.2、`:191`。§5 の `:106`）。
- 解析器の答えの全体は `authgap/dparse.py:397-427`（`_d2`）と `:355-369`（`_fs_class`。追記型・削除型・書き出し型の分け方）。

**例で確かめる**（作った例。どれも `destructiveHint=False`）:

```python
import json, os, uuid
import requests

CACHE = "/srv/h4/cache.json"
OUT = "/srv/h4/out"
CONFIG = "/srv/h4/config.json"

def export(path: str, body: str) -> str:          # (L) モデルが書き先を決める
    with open(path, "w") as fh:
        fh.write(body)
    return "ok"

def export_new(path: str, body: str) -> str:      # (M) 書く前に「あれば止める」
    if os.path.exists(path):
        raise ValueError("already exists")
    with open(path, "w") as fh:
        fh.write(body)
    return "ok"

def reset_config() -> str:                        # (N) 毎回同じ設定ファイルを書き直す
    with open(CONFIG, "w") as fh:
        json.dump({"theme": "light"}, fh)
    return "ok"

def save_new(body: str) -> str:                   # (O) 毎回新しい名前
    name = os.path.join(OUT, uuid.uuid4().hex + ".txt")
    with open(name, "w") as fh:
        fh.write(body)
    return name

def put_profile(name: str) -> str:                # (P) 定数の宛先に PUT
    return requests.put("https://api.example.com/v1/profile/me", json={"name": name}).text
```

- (L): モデルが渡した `path` を `'w'` で開いて書きます。
- (M): `os.path.exists(path)` は「そこにファイル（かディレクトリ）があれば真」。あればエラーにして止め、無いときだけ書きます。
- (N): 定数の `CONFIG` を毎回 `'w'` で書き直します。
- (O): `uuid.uuid4().hex` は、呼ぶたびに違う、重ならない長い番号です。毎回新しい名前のファイルを作ります。
- (P): 決まった URL の資源（`/v1/profile/me`）に、名前を入れた中身を `PUT` します。

| 例 | 本書の試験（解析器、D2） | 人の答え（D2） | 判定 |
|---|---|---|---|
| (L) | **矛** `fs_writeout_model_path` | **反する**（モデルが既存のファイルを指せば上書きできる） | **正**（手引き 20.1 の組 2 と同じ形） |
| (M) | **矛** `fs_writeout_model_path` | **反しない**側（あるファイルには書かない。前からあるものを上書きしない） | **誤**（E8 か、モデルは既存のファイルを選べないので E7 か。迷ったら E9、L468） |
| (N) | 不 `fs_writeout` | **反する**（2 回目からは前の中身を消す。利用者が設定を書き換えていれば、それも消す） | —（不の中身の判定で「違反」） |
| (O) | 不 `fs_writeout` | 反しない（前からあるものを上書きしない） | —（不の中身の判定で「違反でない」） |
| (P) | 不 `net_put` | 調べて決める（【穴 H-4-11】） | — |

表の読み方: 2 行目は「(M) も解析器は (L) と同じ矛にする。解析器は `if` の中身を見て書き先を絞らないから。人が読むと、すでにあるファイルには書かないので、前からあったものを上書きしない。だから反しない側で、組は誤」と読みます。ただし、`exists` を確かめてから開くまでの短い間に、別の誰かがファイルを置く可能性（本書の補足）までは手引きは書いていません。本書の読みでは、ふつうの流れで決めます。

`'x'` で開く形（`open(path, "x")`）は、本書の試験で解析器は何も出しませんでした（追記型として内）。手引きの表の 1 行目のとおりです。

`POST` の例は v4 にあります。bugasura の `update_project`（`POST /v1/projects/update` で既存のプロジェクトを更新）は、人の判定では D2 に反する動作です（R01、L686）。

**迷いやすいところ**:

- **`'w'` は D2 でいつも反する、ではない**: 毎回新しい名前（O）や、無いときだけ書く形は反しません。
- **モデルが決める `path` は「ふつうは新しい名前を渡すはず」と考えない**: 原理 3-a は取りうる値の全体で読みます。
- **`POST` の作成は D2 では反しない**: D1 では反します（[H-4.2](#ah-4-2)）。同じ調べた結果でも、宣言で答えが違います。
- **追記（`'a'`）は前の中身を消さないので反しない**: たとえ書き先をモデルが決めても、表の 1 行目のとおり反しません（追記型）。本書の補足: 設定ファイルのように、後の行が前の行を打ち消す形式のファイルに足すと、意味の上では前の設定が変わります。手引きと決定済みのマス（`docs/contradiction_principles.md:34-36`）は、追記を「足すだけ」としています。
- **DB に残る設定を、調べて決めたくなる**: D2 では、問いそのものが当てはまらないので「決められない」と決まっています。`unknown_reason` に「手引き 15.2: DB に残る設定の変更は『追加か破壊か』が当てはまらない」と書けば足ります（本書の試験: `PRAGMA journal_mode=WAL` は解析器も不 `db_persistent`）。

**承認の前に自分に問うこと**:

1. 「毎回同じファイルを上書きするなら反する」に、自分は同意するか。前の呼び出しの中身を消すのを「前からあったものを変える」と読むことに納得できるか。
2. 書く前に「あれば止める」形（M）を、反しない（誤）としてよいか。
3. `PUT` で決まった 1 つの資源を毎回置き換える形を、`'w'` の上書きと同じに読むか（【穴 H-4-11】）。
4. 一覧の全体を読んで 1 つ足して書き戻す形を、反する・反しないのどちらに読むか（【穴 H-4-9】）。

**この節で手引きが決めていないこと**:

【穴 H-4-9】**読んで・足して・書き戻す**
- 何が決まっていないか: 一覧を読み、1 項目を足し、一覧の全体を同じファイルに `'w'` で書き直す形です。ファイルの単位では「毎回同じファイルを上書き」（3 行目どおりなら反する）、データの単位では「新しく足すだけ」（問いの後半なら反しない）です。どちらで読むかが書かれていません。
- 困る事例: v4 の crypto-price-tracker の `add_to_watchlist`（[第 50 章](ch50.md) 50.6 節の実物 4。v4 の判定記録には無い組）。
- 選択肢: (a) 字義どおり反する（ファイルの単位）。(b) 前からあった項目がすべて残り 1 つ足すだけなら反しない（データの単位）。(c) 不明（手引きで決まらない）。
- 関係する決定: 11.3（L59-64）、D53 の「規則どおりだが意味は非破壊」の先例（`docs/decisions.md:2874`）。[第 50 章](ch50.md) 50.11 節の候補 2。最終評価で出る場面: D2 の不の中身・見落とし。

【穴 H-4-10】**同じ中身での上書き**
- 何が決まっていないか: 3 行目の「毎回同じファイルを上書きするなら反する」は、書く中身が毎回違うことを暗に前提にしているように読めます。書く中身が毎回同じで、そのファイルをこのツールしか書かないなら、2 回目以降の上書きは何も変えません。これを「上書き」（反する）と読むか、「変えていない」（反しない）と読むかが書かれていません。
- 困る事例: 上の (N) で、`CONFIG` を書くのがこのツールだけで、利用者は手で直さない場合。ほかに、既定のテンプレートを毎回同じ場所に書き出すツール。
- 選択肢: (a) 3 行目どおり、同じファイルへの `'w'` は反する（中身を問わない）。(b) 前の中身と同じなら反しない。ただし利用者や別のツールが書き換えうるなら反する。(c) 誰が書き換えうるか読み切れなければ不明。
- 関係する決定: 3 行目（L344）、原理 2-a（`docs/contradiction_principles.md:66`）。最終評価で出る場面: D2 の不の中身（`fs_writeout`）・見落とし。

【穴 H-4-11】**定数の宛先への `PUT` で、毎回同じ資源を置き換える**
- 何が決まっていないか: 4 行目は「既存の資源の置き換えか新規作成かで決める」とだけ書いています。決まった 1 つの資源（`/v1/profile/me`）に毎回 `PUT` すると、1 回目が作成でも、2 回目からは前の呼び出しが置いた中身を置き換えます。3 行目の「毎回同じファイルを上書きするなら反する」を `PUT` にも当てるかが書かれていません。相手が `PUT` を「無ければ作る、あれば置き換える」の両方に使う場合（よくある形）も同じです。
- 困る事例: 上の (P)。解析器は不 `net_put`（本書の試験）。
- 選択肢: (a) `'w'` と同じに、同じ資源を毎回置き換えるなら反する。(b) その資源が呼び出しの前から（利用者の側に）あるかを相手の API の意味で調べ、新規作成だけなら反しない。(c) 相手の API で決まらなければ不明。
- 関係する決定: §7.2 の `PUT`（`docs/contradiction_principles.md:196`「#7 と同じ理屈」）、[第 50 章](ch50.md) 50.5 節（本書の読み方として「反する側」）。最終評価で出る場面: D2 の不の中身（`net_put`）。

【穴 H-4-12】**置き換えを含む作成の SQL**
- 何が決まっていないか: 1 行目は DB の `INSERT` / `CREATE` を「新しく作るだけ」の例にしています。けれども `INSERT OR REPLACE`・`INSERT … ON CONFLICT DO UPDATE`（同じ鍵の行があれば置き換える・更新する）や `CREATE OR REPLACE VIEW`（同じ名前があれば置き換える）は、前からあるものを変ええます。先頭の語（`INSERT` / `CREATE`）で決めるか、文の全体で決めるかが書かれていません。

- 選択肢: (a) 先頭の語どおり反しない。(b) 前からある行・ビューを置き換えうるので反する（問いに戻る）。(c) 鍵の衝突がありうるかをスキーマで調べ、決まらなければ不明。
- 関係する決定: D55（§7.2 の `:189`）、O42 の「§7.5 の表の選択（`INSERT OR REPLACE`…）」（`docs/contradiction_principles.md:429-430`）。[第 50 章](ch50.md) 50.11 節の候補 11。最終評価で出る場面: D2 の見落とし（解析器は内）。

### H-4.5 15.2 D2 の迷いやすい形 — 自分で作ったもの・前の呼び出しが残したもの・キャッシュ（手引き L349-355）

> 【原文 L349-355】
> **迷いやすい形**:
>
> - **同じ呼び出しで自分が作った一時ファイル・ロックファイルを消す**: 呼び出しの前からあったものではないので**反しない**
>   （誤、E2）。v3・v4 で出た類（O41・O43）。ただし**前の呼び出しが残したファイル**を消すなら、それは呼び出しの前からあった
>   ものなので反する。
> - **キャッシュの上書き**: 同じキャッシュファイルを毎回 `'w'` で書き直すなら、前の内容を上書きするので反する（ラベルは
>   キャッシュ・状態の保存）。

**一言で言うと**: D2 で一番迷うのは「**消している（上書きしている）ものは、呼び出しの前からあったか**」です。同じ呼び出しで自分が作った一時ファイル・ロックファイルを消すのは、前からあったものではないので**反しない**（誤、E2）。前の呼び出しが残したファイルを消すのは**反する**。同じキャッシュファイルを毎回 `'w'` で書き直すのは**反する**。

**ことばの確認**:

- **一時ファイル**: 作業のために一時的に作るファイル。`tempfile.mkstemp()` などで作ります。
- **ロックファイル**: 「今、誰かが使っている」ことを示すために作るファイル。終わったら消します。
- **E2**: 誤の原因の記号。「同じ呼び出しで作った一時ファイル・ロックの後始末（D2）」（L459）。
- **O41・O43**: 解析器の既知の限界の記録。同じ類の誤が v3・v4 で出た、という記録です（`docs/open_questions.md:1063-1064`、`:1191`）。
- **キャッシュ**: 後で使うために、結果を保存しておくもの。

**1 文ずつ読む**:

- **見出し（L349）**: 「迷いやすい形」。
- **1 つ目（L351-353）**: 同じ呼び出しで自分が作った一時ファイル・ロックファイルを消すのは、呼び出しの前からあったものではないので**反しない**（誤、E2）。v3・v4 で出た類（O41・O43）。ただし**前の呼び出しが残したファイル**を消すなら、それは呼び出しの前からあったものなので反する。
  - 「誤、E2」とあるのは、解析器がこの削除を D2 の矛（`fs_remove`）にするからです。人の答えが「反しない」なので、組は誤になります。
  - 「前の呼び出しが残したファイル」は、たとえば前の呼び出しが途中で止まって消し損ねたもの、相手のプログラムが置いていったものです。
- **2 つ目（L354-355）**: キャッシュの上書き。同じキャッシュファイルを毎回 `'w'` で書き直すなら、前の内容を上書きするので反する（ラベルはキャッシュ・状態の保存）。キャッシュは消えても困らない、という軽さは、正誤ではなくラベル（第 16 節）で表します。

**なぜこう決めたのか**:

- **E2 を反しないとする**: 仕様の原文は「追加の更新だけをする」です。自分が同じ呼び出しで作ったものを消しても、呼び出しの前と後で、前からあったものは何も変わっていません。O41 はこの形を「MCP 仕様の『additive か destructive か』で読めば破壊的ではないが、採った原理（§6）の読み替えになるので直さない」と記録しています（`docs/open_questions.md:1063-1064`）。解析器は削除を一律に「既存のものを消す」類にするので（`dparse.py:367-368`）、人の判定で E2 の誤として数え、限界の材料にします。
- **D1 との違い**: 同じ形が、D1 では反します（[H-4.2](#ah-4-2) の (A)。M58、L679）。D1 は「変えるか」、D2 は「前からあったものを変えるか」だからです。
- **キャッシュの上書きを反するとする**: 3 行目（L344）の「毎回同じファイルを上書きするなら反する」を、キャッシュにも同じく当てたものです。軽重を正誤に持ち込まない（11.3、L63-64）。

**例で確かめる**（作った例。どれも `destructiveHint=False`）:

```python
import os, tempfile
import requests

CACHE = "/srv/h4/cache.json"
STALE = "/srv/h4/reply.json"     # 相手のプログラムが置く応答のファイル
OUT = "/srv/h4/out"

def own_tmp(text: str) -> str:                     # (Q) 自分が作った一時ファイルを消す
    fd, path = tempfile.mkstemp()
    os.close(fd)
    try:
        with open(path, "w") as fh:
            fh.write(text)
        return str(os.path.getsize(path))
    finally:
        os.remove(path)

def ask_peer(text: str) -> str:                    # (R) 前からある応答のファイルを消す
    if os.path.exists(STALE):
        os.remove(STALE)
    with open(OUT + "/request.txt", "a") as fh:
        fh.write(text + "\n")
    return "sent"

def refresh_cache(base: str) -> str:               # (S) 毎回キャッシュを書き直す
    data = requests.get("https://rates.example.com/latest", params={"base": base}).text
    with open(CACHE, "w") as fh:
        fh.write(data)
    return data

def cache_once(base: str) -> str:                  # (T) キャッシュが無いときだけ書く
    if os.path.exists(CACHE):
        with open(CACHE) as fh:
            return fh.read()
    data = requests.get("https://rates.example.com/latest", params={"base": base}).text
    with open(CACHE, "w") as fh:
        fh.write(data)
    return data
```

| 例 | 本書の試験（解析器、D2） | 人の答え（D2） | 判定 |
|---|---|---|---|
| (Q) `os.remove(path)` | **矛** `fs_remove` | 反しない（同じ呼び出しで `mkstemp` したもの） | **誤、E2** |
| (Q) `open(path, "w")` | 不 `fs_writeout` | 反しない（`mkstemp` が作った空のファイルに書くだけ） | —（不の中身で「違反でない」） |
| (R) `os.remove(STALE)` | **矛** `fs_remove` | **反する**（このツールは `STALE` を作らない。前から、相手か前の呼び出しが置いたもの） | **正** |
| (S) `open(CACHE, "w")` | 不 `fs_writeout` | **反する**（2 回目からは前のキャッシュを上書き） | —（不の中身で「違反」。ラベルはキャッシュ・状態の保存） |
| (T) `open(CACHE, "w")` | 不 `fs_writeout` | 反しない（あるときは書かない） | —（不の中身で「違反でない」） |

表の読み方: 1 行目と 3 行目は、解析器の答えがまったく同じ（`fs_remove` の矛）なのに、人の答えが分かれる対です。違いは「消すものが同じ呼び出しで作られたか」だけです。解析器は、消すものの出どころを呼び出しをまたいで区別しません。

`error_class` の書き方の例（(Q)）: `E2: 同じ呼び出しで mkstemp した一時ファイルを finally で消す（server.py の mkstemp の行と os.remove の行）`。作る行と消す行の両方を書くと、第三者が確かめやすくなります。

**迷いやすいところ**:

- **`finally` で消していれば E2、ではない**: 消すものが同じ呼び出しで作ったものなら E2 です。前の呼び出しの残り物や、別のツール・相手のプログラムが作ったものを消すなら反します。v4 の reaper-mcp は、放棄された前の呼び出しの応答ファイルを消していて、正でした（[第 50 章](ch50.md) 50.6 節の実物 3）。
- **atomic write**（一時ファイルに書き終えてから、`os.replace` で本当の書き先に差し替える書き方）には 2 つの動作が入っています。失敗したときに一時ファイルを消す部分は E2、本当の書き先を置き換える部分は、書き先に前からファイルがありうるなら反します（[第 50 章](ch50.md) 50.6 節の実物 2、v4 の M15）。
- **期限つきのキャッシュ**: 期限が切れたときだけ書き直す形も、書き直すときには前の呼び出しが書いた中身を上書きします。反する側で、条件の種類は `失敗・期限切れ`（L260）と読めます（本書の読み）。
- **1 組に位置が複数あるとき**: 全部が E2 なら誤、1 つでも前からあるものを消す位置があれば正です（手順 G、L158-163）。誤にするときは全部の位置を読みます。

**承認の前に自分に問うこと**:

1. 自分が作った一時ファイルの削除を、D2 では「反しない」、D1 では「反する」とすることに納得できるか。
2. 「同じ呼び出しで作った」の範囲を、ファイル以外（DB の表、相手のサーバの資源）にも広げるか（【穴 H-4-13】）。
3. 呼び出しの間に相手のプログラムが作ったファイルを、同じ呼び出しで消す形をどう読むか（【穴 H-4-14】）。

**この節で手引きが決めていないこと**:

【穴 H-4-13】**E2 の範囲 — ファイル以外の「同じ呼び出しで作ったもの」**
- 何が決まっていないか: L351 と E2（L459）は「一時ファイル・ロックファイル」を消す形だけを書いています。同じ呼び出しで作った DB の作業用の表を `DROP` する、相手のサーバに作った資源を同じ呼び出しで `DELETE` する、`mkstemp` したファイルに `chmod` や `rename` をする形は、表の 2 行目（`DROP`・`DELETE`・`chmod`・`rename` → 反する）と、問い（前からあったものか）で答えが分かれます。
- 困る事例（作った例）:

  ```python
  def scratch_table(v: str) -> str:            # destructiveHint=False
      conn = sqlite3.connect("/srv/h4/app.db")
      conn.execute("CREATE TABLE scratch_x (v TEXT)")
      conn.execute("INSERT INTO scratch_x VALUES (?)", (v,))
      n = conn.execute("SELECT count(*) FROM scratch_x").fetchone()
      conn.execute("DROP TABLE scratch_x")
      return str(n)
  ```

  解析器は `DROP` に D2 の矛 `db_modify` を出し、`CREATE`・`INSERT` には何も出しません（本書の試験）。
- 選択肢: (a) E2 を「同じ呼び出しで作ったもの」全体に広げ、反しない（誤、E2）。(b) 手引きの文面どおり、E2 はファイルだけ。ほかは表の 2 行目どおり反する。(c) 反しないとするが、記号は E8 か E9 にする（E2 の定義を変えない）。
- 関係する決定: E2（L459）、O41（`docs/open_questions.md:1063-1064`）、§7.2 の `SQL_DESTRUCTIVE_HEADS`（`docs/contradiction_principles.md:190`）。最終評価で出る場面: D2 の矛（`db_modify`・`net_modify`・`fs_remove`）。

【穴 H-4-14】**呼び出しの間に相手が作ったものを、同じ呼び出しで消す**
- 何が決まっていないか: 手引きは「自分が作った」（反しない）と「前の呼び出しが残した」（反する）の 2 つを書いています。ツールが要求のファイルを置き、相手のプログラム（別のプロセス）が**同じ呼び出しの間に**応答のファイルを置き、ツールがそれを読んで消す形は、どちらにも当たりません。呼び出しの前には無かったが、ツール自身が作ったものでもありません。
- 困る事例（作った例）: `write(request)` → 相手が `response_7.json` を書くのを待つ → 読む → `os.remove(response_7.json)`。v4 の reaper-mcp の郵便受け（mailbox）のやりとりと同じ形です（[第 50 章](ch50.md) 50.6 節）。
- 選択肢: (a) 呼び出しの前に無かったので反しない（誤、E2 の扱い）。(b) 自分が作ったものではないので反する。(c) 相手が作る時点を読み切れなければ不明。
- 関係する決定: L351-353、16.2 の受け渡しファイルの境界の例（L430）。最終評価で出る場面: D2 の矛（`fs_remove`）。

【穴 H-4-15】**前の呼び出しが途中で止まって残したロック・同時に動く別の呼び出しのロック**
- 何が決まっていないか: 毎回作って毎回消すロックファイルは、ふつうの流れでは E2 です。けれども、前の呼び出しが途中で止まってロックを残していたり、同時に動く別の呼び出しのロックがあったりすると、「呼び出しの前からあったもの」を上書き・削除しうることになります。ふつうの流れで決めるか、こうした場合まで考えるかが書かれていません。
- 困る事例（作った例）: `open(LOCK, "w")` でロックを作り、`finally: os.unlink(LOCK)` で消す。前の呼び出しが強制終了されると `LOCK` が残る。
- 選択肢: (a) ふつうの流れで決める（反しない、E2）。(b) 残り物・同時の呼び出しのものに触れうるので反する。(c) 不明。
- 関係する決定: L351-353、v4 の ccr の M12（[第 50 章](ch50.md) 50.6 節の実物 1）。[第 50 章](ch50.md) 50.11 節の候補 4。最終評価で出る場面: D2 の矛（`fs_remove`）・不の中身（`fs_writeout`）。

### H-4.6 15.3 D3 `openWorldHint: false` の問いと表（手引き L357-369）

> 【原文 L357-369】
> ### 15.3 D3 `openWorldHint: false` —「関わる範囲が閉じているか」
>
> **問い**: そのツールは、外部の（そのマシンやローカルの網の外の）相手と通信するか、あるいはモデルが決める相手と通信しうるか。
>
> | 動作 | 反するか |
> |---|---|
> | HTTP などの宛先が local（下の「local の範囲」） | 反しない |
> | 宛先が local でもグローバルでもない IP（`100.64.0.0/10`、文書用・予約のアドレスなど） | 不明 |
> | 宛先が定数の外部ホスト | 反する |
> | 宛先をモデルが決められる | 反する（原理 3-a） |
> | 宛先が運用者の設定で決まる（環境変数の URL など） | 設定の既定値や文書で外部を想定しているなら反する、ローカルを想定しているなら反しない、分からなければ不明 |
> | 実行するコード・起動するコマンドをモデルが決められる | 反する |
> | ファイル・DB のローカルの操作 | 反しない |

**一言で言うと**: D3 の問いは「**外部の（そのマシンやローカルの網の外の）相手と通信するか、あるいはモデルが決める相手と通信しうるか**」です。決め手は**宛先**で、メソッド（`GET` か `POST` か）は関係ありません。定数の外部ホストと、モデルが決める宛先・コード・コマンドは反します。手元（local）の宛先と、ファイル・DB のローカルの操作は反しません。宛先が環境変数などの運用者の設定で決まるときは、既定値と文書で決めます。

**ことばの確認**:

- **openWorldHint**: 仕様は「true なら外部の『開かれた世界』とやりとりしうる。false なら、やりとりの範囲は閉じている。たとえば web 検索のツールの世界は開いていて、記憶（memory）のツールの世界は閉じている」と書きます（`docs/annotations_official_survey.md:90`）。「外部」がどこからかは、仕様には定義がありません（`docs/textbook/appendix-g-1.md:362` の補足）。
- **宛先**: 通信の相手。URL の中のホスト（`https://api.example.com/v1/x` なら `api.example.com`）や IP アドレスです。
- **local**: 手元の範囲。そのマシンの中か、ローカルの網の中。何を local とするかは次の [H-4.7](#ah-4-7) の表で決まっています。
- **グローバルな IP**: インターネットで使われる番地。**グローバルでも local でもない IP**: `100.64.0.0/10`（通信事業者の中の網で使う番地）、文書の例に使う番地、予約された番地など。
- **運用者**: サーバを起動して動かす人。**環境変数**: 起動のときに外から渡す設定の値。`os.getenv("SEARCH_URL", "https://…")` は「`SEARCH_URL` があればその値、無ければ 2 つ目の既定値」です。
- **定数の外部ホスト**: コードに書かれた、local でない宛先のホスト。解析器の理由は `net_external_host`（L226）。

**1 文ずつ読む**:

- **見出し（L357）**: D3 は `openWorldHint: false`、要約は「関わる範囲が閉じているか」。
- **問い（L359）**: 2 つの部分があります。
  1. 外部の相手と通信するか。「外部」は「そのマシンやローカルの網の外」です。
  2. モデルが決める相手と通信**しうる**か。実際に外と通信したかではなく、モデルが外を選べるか（原理 3-a）。
- **表の 1 行目（L363）**: HTTP などの宛先が local（[H-4.7](#ah-4-7) の範囲）なら反しない。
- **2 行目（L364）**: 宛先が local でもグローバルでもない IP（`100.64.0.0/10`、文書用・予約のアドレスなど）なら不明。どちらとも言えないので、決めずに不明にします。
- **3 行目（L365）**: 宛先が定数の外部ホストなら反する。
- **4 行目（L366）**: 宛先をモデルが決められるなら反する（原理 3-a）。
- **5 行目（L367）**: 宛先が運用者の設定で決まる（環境変数の URL など）なら、設定の既定値や文書で外部を想定しているなら反する、ローカルを想定しているなら反しない、分からなければ不明。
- **6 行目（L368）**: 実行するコード・起動するコマンドをモデルが決められるなら反する。そのコードやコマンドの中で、外と通信できるからです（「通信しうる」）。
- **7 行目（L369）**: ファイル・DB のローカルの操作は反しない。

**なぜこう決めたのか**:

- **宛先で決め、メソッドを問わない**: 仕様の例「web 検索のツールの世界は open」の web 検索は、読むだけです。だから D3 は「変えるか」ではなく「誰と関わるか」の軸です。原理 1-ii-b の理由「readOnly は『変更するか』、openWorld は『外と関わるか』で別の軸」（`docs/contradiction_principles.md:138`）。
- **モデルが決める宛先・コード・コマンドは反する**: 原理 3-a（`:77-79`）。モデルが外を選べるなら、範囲は閉じていません。解析器も同じです（§7.3、`:208`・`:210-211`）。
- **local でもグローバルでもない IP は不明**: 規則 7'「それ以外の IP は `is_global` なら external、そうでなければ不（unknown）（`100.64.0.0/10`・文書用・予約などは local とも external とも言えない）」（`:418-419`）。
- **運用者の設定は既定値と文書で決める**: 運用者の設定の値はコードからは分かりません（解析器は不 `net_host_unknown`。§7.3 の「宛先が読めない」、`:209`）。けれども既定値と文書は、そのツールがどこと関わるように作られたかを示します。人はそれを読んでよい、というのが手引きの考え方です。理由は手引きに書かれていません（本書の読み: 15.1 の `POST` と同じく「人は調べられる範囲で調べる」の当て方）。
- **ローカルの操作は反しない**: 表 D41 で「ローカルの操作は閉じた範囲」とされています（§7.3、`:212`）。
- 解析器の答えの全体は `authgap/dparse.py:502-520`（`_d3`）。解析器が D3 で**矛**を出す理由は `net_external_host`・`net_model_host`・`exec_model`・`spawn_model` の 4 つだけです（同じ関数と `_by_choice`、`:265-272`）。

**最終評価で、どの行を人が使うか**: D3 は、見落としの判定と不の中身の判定の対象ではありません（L474、L535）。人が D3 を判定するのは**矛の判定だけ**で、矛は上の 4 つの理由でしか出ません。だから、実際に使うのは主に 3・4・6 行目（反する側）と、1 行目（解析器が外部と読んだ名前が、本当は local かどうか。[H-4.7](#ah-4-7)）です。2・5 行目の形は、解析器が不（`net_host_unknown`）にするので、最終評価で人が使う場面はほとんどありません（[第 50 章](ch50.md) 50.7 節も同じ整理）。

**例で確かめる**（作った例。どれも `openWorldHint=False`）:

```python
import os
import requests

OLLAMA = os.getenv("OLLAMA_URL", "http://localhost:11434")
SEARCH = os.getenv("SEARCH_URL", "https://search.example.com")

def t_external() -> str:                 # (U) 定数の外部ホスト
    return requests.get("https://api.example.com/v1/weather").text

def t_model(url: str) -> str:            # (V) 宛先をモデルが決める
    return requests.get(url).text

def local_path(path: str) -> str:        # (W) 宛先は手元、モデルが決めるのはパスだけ
    return requests.get("http://127.0.0.1:8080/" + path).text

def local_port(port: int) -> str:        # (X) 宛先は手元、モデルが決めるのはポート番号（整数）だけ
    return requests.get(f"http://127.0.0.1:{port}/status").text

def t_cgnat() -> str:                    # (Y) local でもグローバルでもない IP
    return requests.get("http://100.64.1.2/status").text

def t_env_local() -> str:                # (Z1) 運用者の設定。既定値は手元
    return requests.get(OLLAMA + "/api/tags").text

def t_env_ext(q: str) -> str:            # (Z2) 運用者の設定。既定値は外部
    return requests.get(SEARCH + "/api", params={"q": q}).text
```

表の読み方: 4 行目は「(X) は URL にモデルの値（ポート番号）が入るので、解析器は宛先をモデルが選べると読んで矛にする。人が読むと、入るのは整数のポートだけで、ホストは `127.0.0.1` に固定。だから外は選べず、反しない側で、組は誤」と読みます。

(X) の対になる形を見ておきます。もし `port` が整数ではなく文字列（`port: str`）なら、モデルは `80@evil.example` を渡せます。URL は `http://127.0.0.1:80@evil.example/status` になり、`@` の前は利用者の名前とパスワードの欄（userinfo）と読まれ、宛先は `evil.example` になります（本書の補足。URL の書き方の規則による）。そのときはモデルが外を選べるので**反する**（正）です。「手元の宛先にモデルの値を足すだけ」に見えても、**モデルの値で宛先のホストが変わりうるか**を確かめます。[第 50 章](ch50.md) 50.7 節の `local_fetch`（検証してから送る形）も同じ教訓です。

**迷いやすいところ**:

- **D3 は変更のメソッドだけを見る、ではない**: 定数の外部ホストへの `GET` も反します。逆に、手元への `POST` は D3 には反しません（D1・D2 の問題にはなりえます）。
- **モデルが決めるのがパスだけなら反しない**: ホストが定数の手元なら反しません（W）。ホストが定数の外部なら、モデルが決めるのがパスだけでも、3 行目で反します。
- **運用者の設定の宛先で、既定値が無いとき**: README・`.env.example`・`docker-compose.yml` などの文書で、どこを想定しているかを探します。見つからなければ不明です（[第 50 章](ch50.md) 50.7 節）。
- **既定値がドットの無い名前**（`http://ollama:11434`）なら、[H-4.7](#ah-4-7) により手元を想定していると読めます（[第 10 章](ch10.md) 10.10 節の本書の読み）。
- **6 行目は「モデルが決められる」ときだけ**: 定数のコマンドが外と通信するもの（`git fetch`・`curl <定数の URL>`）は、表に行がありません（【穴 H-4-19】）。
- **D3 の正には書き込み先の種類を付けず、通信先の種類を付ける**（16.3、L440-449）。

**承認の前に自分に問うこと**:

1. 「外部」を「そのマシンやローカルの網の外」と読むことに同意するか（会社の網の中の別のサーバは local か）。
2. 宛先が運用者の設定で決まるとき、既定値と文書で決めることに同意するか。既定値と文書が食い違ったらどうするか（【穴 H-4-16】）。
3. HTTP 以外の通信（外のホストの DB・メールの送信）を、D3 でどう読むか（【穴 H-4-17】）。
4. 手元の相手が、その先で外と通信する場合（ローカルの中継）を、閉じていると言えるか（【穴 H-4-18】）。

**この節で手引きが決めていないこと**:

【穴 H-4-16】**運用者の設定の宛先の細部**
- 何が決まっていないか: 5 行目は「設定の既定値や文書」で決めるとしますが、(i) 既定値と文書が食い違うとき（既定値は手元、README は「クラウドの URL を設定せよ」）にどちらを採るか、(ii) 環境変数ではなく設定ファイル（YAML など）の値のときも同じか、(iii) 反するとしたときの条件の種類（14.3）を `なし` と `運用者の設定` のどちらにするか（既定値のまま外へ行くなら `なし`、運用者が外の URL を設定したときだけなら `運用者の設定` で (B) に数えない、L262・L267-268）が書かれていません。

- 関係する決定: 5 行目（L367）、14.3（L262、L266-268）、D68 の 1（`docs/decisions.md:3796-3804`）。最終評価で出る場面: ほとんど無い（解析器は不 `net_host_unknown`、本書の試験）。運用者の設定の値とモデルの値が混ざる形で矛が出たときに効きます。

【穴 H-4-17】**HTTP 以外の外との通信と、名前の問い合わせ（DNS）だけの動作**
- 何が決まっていないか: 表の 1 行目は「HTTP **など**の宛先」、7 行目は「ファイル・DB の**ローカルの**操作」です。外のホストの DB への接続（`psycopg.connect("host=db.example.com")`）、メールの送信（`smtplib.SMTP("smtp.example.com")`）、Redis などへの接続は、どの行に当たるかが名指しされていません。名前を IP に引くだけの動作（`socket.gethostbyname(host)`）も、外の DNS のサーバに問い合わせますが、表にありません。
- 困る事例: 本書の試験では、外のホストの DB の `SELECT` は内（DB は D3 で一律に内、`docs/contradiction_principles.md:212`）、`smtplib` での送信と `gethostbyname` は効果なしでした。
- 選択肢: (a) 宛先で決める（外のホストなら反する）。(b) 表どおり、HTTP 以外の通信は D3 の表の外として扱わない。(c) 不明。DNS の問い合わせだけは、(a') 通信として反する / (b') 宛先との通信の準備として数えない、で分かれます。
- 関係する決定: §7.3（`:206-212`）、7 行目（L369）。[第 50 章](ch50.md) 50.11 節の候補 7。最終評価で出る場面: なし（解析器は内か効果なし。D3 の見落としは判定しない）。論文の限界に書くかの材料です。

【穴 H-4-18】**手元の相手が、その先で外へ中継する**
- 何が決まっていないか: 1 行目は宛先が local なら反しないとします。けれども、手元で動く中継のサーバ（LLM の API を外のサービスに取り次ぐもの）、手元のプロキシ、環境変数 `HTTP_PROXY` で外のプロキシを通す設定などでは、ツールの要求は結局外へ届きます。宛先だけで決めるか、その先まで見るかが書かれていません。

- 選択肢: (a) 宛先だけで決める（反しない）。(b) 中継先が外だと文書やコードで分かれば反する。(c) 不明。
- 関係する決定: 1 行目（L363）、5 行目（L367。運用者の設定の考え方）。最終評価で出る場面: なし（解析器は内）。

【穴 H-4-19】**定数のコマンドが外と通信する**
- 何が決まっていないか: 6 行目は、コマンドやコードを「モデルが決められる」ときだけを書いています。コマンドは定数で、そのコマンドが外と通信するもの（`git fetch origin`、`pip install <定数>`、`curl <定数の URL>`）は名指しがありません。D1 の 3 行目（定数のコマンドは調べる）のような行が D3 には無いのです。
- 困る事例: 本書の試験では、`subprocess.run(["git", "fetch", "origin"])` は不 `spawn_command` でした。
- 選択肢: (a) D3 の問いに当て、外と通信するコマンドなら反する。(b) 表に無いので不明。(c) 起動するものの文書で決め、決まらなければ不明。
- 関係する決定: §7.3 の SPAWN（`docs/contradiction_principles.md:211`）。[第 50 章](ch50.md) 50.11 節の候補 8、[第 17 章](ch17.md) 17.12 節。最終評価で出る場面: なし（解析器は不。D3 の不は判定しない）。

【穴 H-4-20】**外から接続を待ち受ける**

**一言で言うと**: 「手元（local）の宛先」の範囲を、IP の網と名前で決めた表です。loopback・private（RFC 1918）・ULA・link-local・未指定の IP と、`localhost`・`〜.localhost`・`〜.local`・`〜.internal`・**ドットの無い名前**が local です。どれでもない IP は、グローバルなら外部（反する）、そうでなければ不明です。**ドットの無い名前と `〜.internal` は、解析器では外部になります。解析器がそれで D3 の矛を出していたら、判定は誤です**（解析器に合わせない）。

**ことばの確認**:

- **IP アドレスの網**（`10.0.0.0/8` など）: `/8` は「先頭の 8 ビットが同じ番地の全部」の意味です。`10.0.0.0/8` は `10.` で始まる番地の全部（[第 10 章](ch10.md) 10.9 節）。
- **loopback**: 自分のマシン自身を指す番地。`127.0.0.0/8`（ふつうは `127.0.0.1`）と IPv6 の `::1`。
- **private（RFC 1918）**: 家庭や会社の中の網で使う番地。インターネットから直接は届きません。
- **ULA**（Unique Local Address）: IPv6 の、中の網で使う番地 `fc00::/7`。
- **link-local**: 同じ網の線の中だけで使う番地。`169.254.0.0/16`・`fe80::/10`。
- **未指定**（unspecified）: 「どの番地でもない」を表す `0.0.0.0`・`::`。
- **`〜.localhost`・`〜.local`**: 名前の末尾が `.localhost`・`.local` のもの。`.localhost` は RFC 6761 で自分のマシンのための名前として取り置かれています（手引きの括弧）。`.local` は同じ網の中の機器が名乗り合う仕組み（mDNS）で使う名前です（本書の補足）。
- **`〜.internal`**: 組織の中だけで使う名前として取り置かれ、公開の DNS では引けない名前（D73 の 2 の追記）。
- **ドットの無い名前**: `ollama`・`db` のように `.` を含まない名前。docker-compose（複数のコンテナをまとめて動かす道具）のサービス名などです。
- **IPv4 を埋め込んだ IPv6**: IPv6 の番地の中に IPv4 の番地を入れた書き方。`::ffff:10.0.0.7`（IPv4-mapped）など。
- **語彙・定義の差**: 解析器の定義（何を local とするか）と、手引きの定義が違うこと。

**1 文ずつ読む**:

- **L371-372**: local の範囲は D73 の 2 で決めた。`docs/contradiction_principles.md` の規則 7' と同じ。手引きの前の版の `127.0.0.1`・`10.x`・`192.168.x` は、この一部を例に挙げたものだった。つまり、前の版の括弧を「全部」と読んで `172.20.0.5` を外部とする読み方は、もう採らない、ということです。

### H-4.8 15.4 D4 `idempotentHint: true` の問いと、原理 3 を当てないこと（手引き L390-394）

> 【原文 L390-394】
> ### 15.4 D4 `idempotentHint: true` —「同じ引数で繰り返しても追加の効果が無いか」
>
> **問い**: **同じ引数で** 2 回呼んだとき、2 回目が 1 回目の後の状態をさらに変えるか。
>
> **D4 には原理 3 を当てない**（冪等性は「同じ引数で繰り返したとき」の性質で、引数が取りうる値の範囲は関係しない。§7.0 の 1）。

**一言で言うと**: D4 の問いは「**同じ引数で 2 回呼んだとき、2 回目が 1 回目の後の状態をさらに変えるか**」です。1 回目が状態を変えるのはかまいません。問われるのは 2 回目です。D4 にだけは**原理 3 を当てません**。冪等性は「同じ引数で繰り返したとき」の性質で、引数が取りうる値の範囲は関係しないからです。

**ことばの確認**:

- **冪等**（べきとう、idempotent）: 同じことを何回しても、1 回したときと同じ結果になる性質。照明の「オン」ボタンは冪等（何回押してもついたまま）、「切り替え」ボタンは冪等ではありません（[第 50 章](ch50.md) 50.8 節のたとえ）。
- **1 回目の後の状態**: 1 回目の呼び出しが終わった直後の、環境（ファイル・DB・相手のサーバ）の様子。これを S1、2 回目の後を S2 と書くと、問いは「S2 は S1 と違うか」です。違えば反します。
- **同じ引数で**: 2 回の呼び出しで、モデルが渡す引数の値がすべて同じ、という前提。
- **原理 3**: モデルが決める値をどう読むか。3-a は「取りうる値の全体」で読む（D1〜D3 で使う）。
- **§7.0 の 1**: 判定表の導出の文書の「§5 から直した 2 点」の 1 つ目（`docs/contradiction_principles.md:153-155`）。

**1 文ずつ読む**:

- **見出し（L390）**: D4 は `idempotentHint: true`、要約は「同じ引数で繰り返しても追加の効果が無いか」。仕様の "no additional effect"（追加の効果が無い）の言い換えです。
- **問い（L392）**: 「**同じ引数で** 2 回呼んだとき、2 回目が 1 回目の後の状態をさらに変えるか」。
  - 比べるのは「呼ぶ前」と「1 回目の後」ではなく、「1 回目の後」と「2 回目の後」です。だから、1 回目でファイルを作っても、2 回目が同じ状態のままなら反しません。
  - 「同じ引数で」なので、違う引数で呼んだら違う状態になる、ということは問いません。
- **L394**: D4 には原理 3 を当てない。理由は「冪等性は『同じ引数で繰り返したとき』の性質で、引数が取りうる値の範囲は関係しない」。出典は §7.0 の 1。手順 F の「D4 だけは除く」（L154）と同じことです。

**なぜこう決めたのか**:

- §7.0 の 1 は「D4（idempotent）には原理 3 を当てない。冪等性は**同じ引数で**繰り返したときの性質なので、引数が取りうる値の範囲（能力）は関係しない。モデル由来のコマンドや SQL も、繰り返しの間は同じ値で、それが冪等かはコマンドの意味による → 不」と書いています（`docs/contradiction_principles.md:153-155`）。原理を選んだ後、表を導く途中で見つけて直した点で、原理の選択は変えていません（`:151`）。
- 仕様の原文も "calling the tool repeatedly **with the same arguments**" です（`docs/annotations_official_survey.md:89`）。
- 解析器も、D4 では値の主体（MODEL かどうか）で矛にしません（`authgap/dparse.py:523-553`。`_d4` の説明文に「原理 3 は当てない（§7.0 の 1）」）。

**例で確かめる**（作った例）— 原理 3 を当てるとどうなるか:

```python
@mcp.tool(annotations=ToolAnnotations(destructiveHint=False, idempotentHint=True))
def write_file(path: str, content: str) -> str:
    with open(path, "w") as fh:
        fh.write(content)
    return "ok"
```

- D2: 書き先 `path` をモデルが決めるので、既存のファイルを指せば上書きできる（原理 3-a）→ **反する**。
- D4: 同じ `path` と同じ `content` で 2 回呼べば、2 回目は同じ中身を同じ場所に書くだけで、S2 = S1 → **反しない**。モデルが「どんな値でも選べる」ことは、ここでは関係ありません。繰り返しの間、引数は同じだと決まっているからです。
- もし D4 にも原理 3 を当てると、「モデルは 1 回目と 2 回目で違う `content` を選べる」ので反する、という読みになってしまいます。それは「同じ引数で」という仕様の前提を壊します。

[第 50 章](ch50.md) 50.8 節の試験でも、この形に解析器は D2 の矛（`fs_writeout_model_path`）を出し、D4 には何も出しませんでした。

**冪等をもう少していねいに — S1 と S2 で考える**（作った例。どれも `idempotentHint=True`）:

| ツールの動作 | 1 回目の後（S1） | 2 回目の後（S2） | S2 は S1 と違うか | D4 |
|---|---|---|---|---|
| `notes.txt` に `'a'` で `text` を 1 行足す | `notes.txt` の末尾に `text` が 1 行 | 同じ `text` が 2 行 | 違う | 反する |
| `notes.txt` に `text` が無いときだけ `'a'` で足す | 末尾に `text` が 1 行 | 1 行のまま（2 回目は書かない） | 同じ | 反しない |
| `state.json` に `'w'` で `{"value": v}` を書く | `{"value": v}` | `{"value": v}` | 同じ | 反しない |
| `state.json` に `'w'` で `{"value": v, "at": 今の時刻}` を書く | 時刻 t1 | 時刻 t2 | 違う | 反する |
| `count.json` を読んで `n + 1` を `'w'` で書く | `n = 1` | `n = 2` | 違う | 反する |
| `os.makedirs(d, exist_ok=True)` | `d` がある | `d` があるまま | 同じ | 反しない |
| `open(p, "x")`（無いときだけ作る） | `p` ができる | 2 回目は「もうある」で失敗、何も変わらない | 同じ | 反しない |
| `os.remove(p)` | `p` が消える | 2 回目は「もう無い」で失敗、何も変わらない | 同じ | 反しない |
| `snap/<今の時刻>.txt` に `'w'` で書く | ファイルが 1 つ | ファイルが 2 つ | 違う | 反する |

表の読み方: 5 行目は「`count.json` の数を読んで 1 足して書き直すツールは、`'w'` の上書きだが、書く中身が前の状態で決まる。2 回目は 2 になるので、S2 は S1 と違い、反する」と読みます。上書き（`'w'`）でも、中身が時刻（4 行目）や前の値（5 行目）で変われば反します。

**迷いやすいところ**:

- **1 回目が変えるのは問題ない**: 1 回目にファイルを作る・行を足すのは、D4 の問いの外です（D1 なら反します）。
- **「同じ引数」でも、ツールが中で引数以外のものを読むことがある**: 今の時刻、乱数、連番、外のデータ（為替の値など）です。時刻・連番・乱数は 15.4 の表の最後の行で「反する」と決まっています（[H-4.9](#ah-4-9)）。
- **D4 には「取りうる値の全体」を当てない**: D1〜D3 の癖で「モデルなら何でも渡せる」と考えないこと。
- **D4 も `readOnlyHint: true` のツールには当てません**（[H-4.1](#ah-4-1)。`authgap/dparse.py:236`・`:597`）。
- **2 回目が失敗すること**（`open(p, "x")` で `FileExistsError`、`os.remove(p)` で `FileNotFoundError`）は、環境を変えないので反しません（15.4 の表の 3 行目「2 回目は失敗するので、ふつう反しない」）。

**承認の前に自分に問うこと**:

1. 「S1 と S2 を比べる」という読み方に同意するか（1 回目の変化は問わない）。
2. D4 にだけ原理 3 を当てない理由（同じ引数で）に納得できるか。
3. 2 回の呼び出しの間に時間が経つ・外の状態が変わる場合を、どう扱うか（【穴 H-4-25】）。

**この節で手引きが決めていないこと**:

【穴 H-4-25】**2 回の呼び出しの「間」— 時間・外の状態・別の呼び出し**
- 何が決まっていないか: 問いは「同じ引数で 2 回呼んだとき」ですが、2 回の間に何が起きてよいか（すぐ続けて呼ぶのか、日をまたいでもよいのか、その間に別の誰かが状態を変えてよいのか）が書かれていません。日付や期限で書くかどうかが変わるツールでは、答えが割れます。
- 困る事例（作った例）:

  ```python
  def daily_mark(text: str) -> str:              # idempotentHint=True
      today = time.strftime("%Y-%m-%d")
      content = ""
      if os.path.exists(NOTES):
          with open(NOTES) as fh:
              content = fh.read()
      if (today + " " + text) not in content.splitlines():
          with open(NOTES, "a") as fh:
              fh.write(today + " " + text + "\n")
      return "ok"
  ```

  同じ日に 2 回呼べば、2 回目は書きません。日が変われば、同じ引数でも 1 行足します。本書の試験では、解析器は D4 の矛 `fs_append` を出しました。期限つきのキャッシュ（期限が切れたら書き直す）や、外のデータを取って書き直すツールも同じ形です。
- 選択肢: (a) 間を置かず、間に何も起きない 2 回で考える（`daily_mark` は反しない、誤 E8）。(b) いつ繰り返してもよいと考える（日が変われば足すので反する、正）。(c) 時間や外の状態で答えが変わるなら不明。
- 関係する決定: 問い（L392）、15.4 の表の最後の行（L404「時刻・連番・乱数を含むものを書く → 反する」）。[第 50 章](ch50.md) 50.8 節は「間に何も起きない」として考えるのを本書の読み方としています。最終評価で出る場面: D4 の矛（`fs_append`）。

### H-4.9 15.4 D4 の表（手引き L396-404）

> 【原文 L396-404】
> | 動作 | 反するか |
> |---|---|
> | 定数の `'a'` で追記する | 繰り返すと追記が重なるなら反する。**書く前に内容を確かめて、すでにあれば書かない**なら反しない（v4 の E00） |
> | `flock` のために `'a'` で開くだけで書かない | 反しない（O41） |
> | 上書き（`'w'`）・作成・削除 | 同じ引数なら同じ状態になるか、2 回目は失敗するので、ふつう反しない |
> | DB の `INSERT` | 一意制約で 2 回目が失敗・無視されるなら反しない、行が増えるなら反する。スキーマを見て決める。見られなければ不明 |
> | DB の `UPDATE` | `SET x = 1` なら反しない、`SET x = x + 1` や `NOW()` の記録なら反する |
> | HTTP の `POST` / `PATCH` | 相手の API の意味で決める |
> | 時刻・連番・乱数を含むものを書く（ログの 1 行、タイムスタンプつきのファイル名） | 反する（2 回目でさらに増える） |

**一言で言うと**: 定数の `'a'` の追記は、ふつう反します。ただし、**書く前に確かめてすでにあれば書かない**追記と、**`flock` のために `'a'` で開くだけ**の形は反しません。上書き・作成・削除は、ふつう反しません。`INSERT`・`UPDATE`・`POST`・`PATCH` は中身で決めます。時刻・連番・乱数を含むものを書くのは反します。

**ことばの確認**:

- **`flock`**: ファイルに錠をかける仕組み。同時に書かないための印で、ファイルの中身は変えません（[第 9 章](ch09.md) 9.3 節）。
- **一意制約**: 表のある列に、同じ値の行を 2 つ入れさせない約束。主キー（`PRIMARY KEY`）や `UNIQUE`。ぶつかると `INSERT` は失敗し、`INSERT OR IGNORE` なら無視されます（[第 10 章](ch10.md) 10.6 節）。
- **スキーマ**: 表の定義（列と制約）。`CREATE TABLE` の文や、移行（migration）のファイルに書かれています。
- **`SET x = x + 1`**: 今の値に 1 を足す更新。**`NOW()`**: 今の時刻を返す SQL の関数（[第 10 章](ch10.md) 10.7 節）。
- **連番**: 呼ぶたびに 1 ずつ増える番号。**乱数**: 呼ぶたびに違う、でたらめな値（`uuid4()` など）。
- **E8**: 誤の原因の記号。「宣言に反しない（E2 以外）: 冪等な追記（D4）、`flock` のための `'a'`（D4）…」（L465）。
- **v4 の E00**: v4 の判定記録の番号（誤の原因の E1〜E9 とは別）。ccr の `.gitignore` への、書く前に確かめる追記（L681）。

**1 文ずつ読む**:

- **表の 1 行目（L398）**: 定数の `'a'` で追記する形は、繰り返すと追記が重なるなら反する。**書く前に内容を確かめて、すでにあれば書かない**なら反しない（v4 の E00）。
- **2 行目（L399）**: `flock` のために `'a'` で開くだけで書かないなら反しない（O41）。`'a'` で開くと、無ければ空のファイルを作りますが、2 回目は開くだけで何も変えません。
- **3 行目（L400）**: 上書き（`'w'`）・作成・削除は、同じ引数なら同じ状態になるか、2 回目は失敗するので、**ふつう**反しない。「ふつう」は、7 行目（時刻などを含む）に当たるときを除く、という含みです。
- **4 行目（L401）**: DB の `INSERT` は、一意制約で 2 回目が失敗・無視されるなら反しない、行が増えるなら反する。スキーマを見て決める。見られなければ不明。
- **5 行目（L402）**: DB の `UPDATE` は、`SET x = 1`（その値にする）なら反しない、`SET x = x + 1`（今の値に足す）や `NOW()` の記録なら反する。
- **6 行目（L403）**: HTTP の `POST` / `PATCH` は、相手の API の意味で決める。
- **7 行目（L404）**: 時刻・連番・乱数を含むものを書く（ログの 1 行、タイムスタンプつきのファイル名）は反する。2 回目でさらに増えるからです。

**なぜこう決めたのか**:

- **追記はふつう反する**: 「2 回呼べば 2 回追記される（静的に確定）」（§5 の #5、`docs/contradiction_principles.md:117`）。解析器が D4 で矛にするのは、`open` の仲間で開くモードの定数に `a` が入っているときだけです（`authgap/dparse.py:526-532`、理由 `fs_append`）。
- **書く前に確かめる追記と `flock` は反しない**: 問いは「2 回目がさらに変えるか」です。2 回目が何も書かないなら、さらに変えていません。解析器はモードだけで矛にするので、この区別は人がします。`flock` の形は v3 で D4 の誤が出た類（O41、`docs/open_questions.md:1069`）、確かめる追記は v4 の E00（L681）です。
- **上書き・作成・削除はふつう反しない**: 同じ中身になるか、2 回目は「もうある」「もう無い」になるからです（§7.4、`docs/contradiction_principles.md:221`）。
- **`INSERT`・`UPDATE`・`POST`・`PATCH` は中身で決める**: 一意制約の有無、`x = 1` か `x = x + 1` か、相手の API の意味で変わります。解析器はこれらを「不」にします（§7.4 の `:222`・`:225`。§5 の #5 の `:118-119`）。
- **時刻・連番・乱数を含むものは反する**: 同じ引数でも、2 回目に書く中身や名前が変わるからです。この行は判定表 §7.4（`docs/contradiction_principles.md:218-229`）には無く、人の判定のために手引きに書かれた行です（本書の読み。解析器は `'w'` の上書きを内にするので、この形は矛にも不にもなりません。本書の試験）。

**最終評価で、どの行を人が使うか**: D4 は、見落としの判定と不の中身の判定の対象ではありません（L474、L535）。人が D4 を判定するのは矛の判定だけで、D4 の矛は `fs_append` だけです。だから最終評価の D4 の判定は、**すべて「`'a'` で開く行」の判定**で、使うのは 1・2 行目（と、確かめの中身に時刻などが入るかを見るための 7 行目）です。3〜6 行目は、問いの意味を定める行として読みます（[第 50 章](ch50.md) 50.8 節も同じ整理）。

**例で確かめる**（作った例。どれも `idempotentHint=True` で、`readOnlyHint` は書かない）:

```python
import fcntl, json, os, time

NOTES = "/srv/h4/notes.txt"

def add_note(text: str) -> str:                     # (ア) ただの追記
    with open(NOTES, "a") as fh:
        fh.write(text + "\n")
    return "ok"

def add_note_once(text: str) -> str:                # (イ) 書く前に確かめる追記
    lines = []
    if os.path.exists(NOTES):
        with open(NOTES) as fh:
            lines = fh.read().splitlines()
    if text not in lines:
        with open(NOTES, "a") as fh:
            fh.write(text + "\n")
    return "ok"

def add_note_stamped_once(text: str) -> str:        # (ウ) 確かめるが、書く中身に時刻が入る
    content = ""
    if os.path.exists(NOTES):
        with open(NOTES) as fh:
            content = fh.read()
    if text not in content.splitlines():
        with open(NOTES, "a") as fh:
            fh.write(f"{time.time()} {text}\n")
    return "ok"

def locked_read(name: str) -> str:                  # (エ) flock のために 'a' で開くだけ
    with open("/srv/h4/app.lock", "a") as lock:
        fcntl.flock(lock, fcntl.LOCK_EX)
        with open(os.path.join("/srv/h4/data", name)) as fh:
            return fh.read()
```

- (イ): ファイルがあれば全行を読み、`text` と同じ行が無いときだけ足します。
- (ウ): 確かめるのは「`text` だけの行があるか」ですが、書くのは「時刻と `text`」の行です。書いた行は確かめの形と一致しないので、確かめは毎回「無い」になり、毎回書き足します。

| 例 | 本書の試験（解析器、D4） | 人の答え（D4） | 判定 |
|---|---|---|---|
| (ア) | **矛** `fs_append` | 反する（2 回で 2 行） | **正** |
| (イ) | **矛** `fs_append` | 反しない（2 回目は書かない） | **誤、E8**（v4 の E00 と同じ形） |
| (ウ) | **矛** `fs_append` | 反する（確かめと書く中身がずれていて、毎回書き足す。7 行目にも当たる） | **正** |
| (エ) | **矛** `fs_append` | 反しない（何も書かない） | **誤、E8**（O41 の類） |

表の読み方: 1〜4 行目は、解析器の答えがまったく同じ（`fs_append` の矛）なのに、人の答えが分かれる 4 つです。(イ) と (ウ) は見た目がよく似ていますが、**確かめる中身と書く中身が一致しているか**で分かれます。

(エ) は、[H-4.2](#ah-4-2) の (B) と同じコードです。D1（読み取り専用）では「ファイルが無ければ作る」ので反する側、D4 では「2 回目は何も変えない」ので反しません。宣言で答えが分かれます。

`error_class` の書き方の例（(イ)）: `E8: 書く前に notes.txt の中身を確かめ、同じ行があれば書かない（確かめの行と書く行）`。

**表のほかの行の例**（作った例。最終評価では判定の場面がないが、問いの意味をつかむため）:

```sql
CREATE TABLE tags (name TEXT PRIMARY KEY);                -- name に一意制約がある
INSERT OR IGNORE INTO tags (name) VALUES ('red');         -- 2 回目は無視される → 反しない
CREATE TABLE events (id INTEGER PRIMARY KEY, name TEXT);  -- name に一意制約が無い
INSERT INTO events (name) VALUES ('red');                 -- 2 回目で行が増える → 反する
UPDATE settings SET enabled = 1 WHERE id = 7;             -- その値にする → 反しない
UPDATE counters SET n = n + 1 WHERE id = 7;               -- 今の値に足す → 反する
UPDATE sessions SET seen_at = NOW() WHERE id = 7;         -- 今の時刻を書く → 反する
```

- 本書の試験では、`INSERT OR IGNORE INTO tags …` は解析器で不 `db_nonidempotent_statement` でした。人はスキーマ（`tags` の `name` に一意制約があるか）を探して決め、見つからなければ不明です（4 行目）。
- `INSERT` で主キーを呼ぶたびに乱数で作る形（`VALUES (uuid4(), 'red')`）は、一意制約があっても行が増えます（7 行目にも当たる。[第 10 章](ch10.md) 10.6 節）。

`POST` の例（作った例）:

```python
def charge(amount: int) -> str:                     # idempotentHint=True
    return requests.post("https://pay.example.com/v1/charges", json={"amount": amount},
                         headers={"Idempotency-Key": uuid.uuid4().hex}).text
```

- 支払いの API には、「同じ `Idempotency-Key` の要求は 1 回だけ処理する」という仕組みを持つものがあります（本書の補足）。けれどもこのツールは、呼ぶたびに `uuid4()` で新しい鍵を作るので、同じ `amount` で 2 回呼べば 2 回請求されます。**反する**です。鍵を引数から決める（同じ引数なら同じ鍵）なら、相手の API の意味によっては反しません。6 行目の「相手の API の意味で決める」は、相手の文書と、ツールが送る中身の両方を見る、ということです。本書の試験では、解析器は不 `net_nonidempotent_method` でした。

**問 7**: D4 にだけ原理 3 を当てないのはなぜですか。`write_file(path, content)`（`'w'` で書く）を例に、D2 と D4 で答えが分かれる理由を説明してください。

<details><summary>答え</summary>

冪等性は「同じ引数で繰り返したとき」の性質で、引数が取りうる値の範囲は関係しないからです（L394、`docs/contradiction_principles.md:153-155`）。D2 は原理 3-a で、モデルが既存のファイルを指せば上書きできるので反します。D4 は、同じ `path` と `content` で 2 回呼べば 2 回目は同じ中身を書くだけで状態が変わらないので、反しません。

</details>

**問 8**: `idempotentHint=True` のツールが、`notes.txt` に `text` だけの行が無いときだけ、`f"{time.time()} {text}\n"` を `'a'` で足します。解析器は `fs_append` の矛を出しました。判定は何ですか。

<details><summary>答え</summary>

**正**です。書く前に確かめてはいますが、確かめるのは「`text` だけの行」で、書くのは「時刻つきの行」です。書いた行は確かめに引っかからないので、毎回書き足します。2 回目が状態をさらに変えるので反します（L398、L404）。見た目は「書く前に確かめる追記」（E8 の形）ですが、確かめと書く中身が一致しているかを読む必要があります。

</details>

**問 9**: `'a'` で錠のファイルを開いて `flock` するだけのツールがあります。`readOnlyHint=True` のときと、`idempotentHint=True`（読み取り専用ではない）のときで、答えはどう変わりますか。

<details><summary>答え</summary>

D1 では、錠のファイルが無ければ最初の呼び出しで**作る**ので、反する側です（作成も「変える」。条件の種類は `初回`。起動時に必ず作ってあれば到達しない）。解析器は D1 の矛 `fs_write` を出します。D4 では、2 回目は開くだけで何も変えないので**反しない**、`fs_append` の矛は**誤、E8** です（L399、O41）。

</details>

**問 10**: 最終評価で、D3 と D4 について人が判定するのは、どの場面のどんな組ですか。

<details><summary>答え</summary>

**矛の判定だけ**です（見落としの判定は D1・D2 を明示したツールだけ、L474。不の中身の判定も D1・D2 だけで、D3・D4 の不は件数と理由だけ、L535）。D3 の矛は `net_external_host`・`net_model_host`・`exec_model`・`spawn_model` の 4 つの理由（`authgap/dparse.py:502-520`）、D4 の矛は `fs_append` だけです（`:526-532`）。

</details>
