## 第 50 章 宣言に反するかの決め方 — D1〜D4 の問いと迷いやすい形

> **この章で分かること**:
> - 矛の判定の 2 つ目の問い「**宣言に反するか**」の答え方（手引き 15 節、手順 F）。4 つの宣言のそれぞれに、**1 つの問い**と、動作ごとの**表**があること。
> - **D1**（`readOnlyHint: true`）の問い「呼び出しの後に残る何かを変えるか」と表。迷いやすい 3 つの形（標準出力・標準エラーのログ / 子の標準入力 / `ctx` の通知）。解析器が「不」にする `POST` と定数のコマンドを、**人は調べて決めてよい**こと。
> - **D2**（`destructiveHint: false`）の問い「呼び出しの前からあったものを消す・上書きする・変えるか」と表。書き出し（`'w'`）の 3 つの分かれ道（モデルが書き先を決める / 毎回同じファイル / 毎回新しい名前）。自分が同じ呼び出しで作った一時ファイル・ロックを消すのは反しない（E2）が、前の呼び出しが残したファイルを消すのは反すること。キャッシュの上書きは反すること。
> - **D3**（`openWorldHint: false`）の問いと表。local の範囲が手引きと解析器でずれていて未決だったが、D73 の 2（2026-10-03）で決まったこと（原理の規則 7' の全部、ドットの無い名前は local）。運用者の設定の URL の読み方。
> - **D4**（`idempotentHint: true`）には**原理 3 を当てない**こと。追記・`flock`・上書き・`INSERT`・`UPDATE`・`POST`・時刻を含む書き込みの読み方。
> - 宣言ごとに、解析器の「不」を**人がどこまで決められるか**の表。最終評価の 3 つの判定の場面（矛・不の中身・見落とし）のうち、**どの表の行がどの場面で実際に使われるか**。
> - **本書の試験**: 凍結版の解析器で走らせた作例で、解析器の答え（矛・不・内）と人の答え（反する・反しない・決められない）がどこで分かれるか。
> - 手引きに書かれていない境目（本書が書きながら気づいたもの）を、封の前に決めておく候補として並べたもの。

### 50.1 宣言に反するかを決める — 4 つの問いと、答え方の共通の手順

#### 一言で言うと

4 つの宣言には、それぞれ **1 つの問い**があります。
人は、効果の動作をその問いに当て、「反する / 反しない / 決められない」のどれかを答えます。
手引きの表は、よく出る動作について問いの答えを先に書いておいたものです。
表に無い形に出会ったら、**表の上の問いに戻って**決めます。

#### たとえ話 — 4 種類の「お願いの貼り紙」

ある建物の部屋に、4 種類の貼り紙があるとします。

- 「**見るだけにしてください**」（D1）。部屋の物を動かしても、足しても、消してもいけません。
- 「**足すのはよいが、元からある物を壊さないでください**」（D2）。新しい物を置くのはよく、元からある物を捨てたり作り変えたりするのはいけません。
- 「**この建物の中の人とだけ話してください**」（D3）。建物の外に電話をかけてはいけません。
- 「**何度やっても同じ結果になることだけをしてください**」（D4）。2 回目で、1 回目の後の様子がさらに変わってはいけません。

同じ「部屋の本棚に本を 1 冊足す」という動作でも、貼り紙ごとに答えが違います。
「見るだけ」には反します（本棚が変わる）。
「壊さない」には反しません（足しただけ）。
「建物の中だけ」には反しません（電話をかけていない）。
「何度やっても同じ」には反します（2 回やれば 2 冊になる）。

つまり、**動作と貼り紙の両方を見ないと、答えは決まりません**。
これが、宣言ごとに問いを分ける理由です。

#### 小さな例 — 同じ動作を 4 つの宣言で

よく出る 6 つの動作を、4 つの問いに当てた表です（手引きの 15 節の表から本書がまとめた）。

| 動作 | D1 環境を変えるか | D2 前からあるものを壊すか | D3 外と関わるか | D4 繰り返すとさらに変わるか |
|---|---|---|---|---|
| ① 定数のファイルに `'a'` で 1 行追記（毎回） | **反する** | 反しない | 反しない | **反する** |
| ② モデルが決めた `path` に `'w'` で書き出し | **反する** | **反する**（原理 3-a） | 反しない | 反しない（同じ引数なら同じ中身） |
| ③ 自分が同じ呼び出しで作った一時ファイルを消す | **反する** | 反しない（E2） | 反しない | 反しない |
| ④ 定数の外部ホストに `GET` | 反しない | 反しない | **反する** | 反しない |
| ⑤ チャットのサービスに `POST` でメッセージを送る | **反する**（相手に新しい投稿ができる） | 反しない（足すだけ） | 宛先で決まる | **反する**（2 回送れば 2 通） |
| ⑥ DB で `UPDATE t SET n = n + 1` | **反する** | **反する**（既存の行を変える） | 反しない（ローカルの DB なら） | **反する** |

表の読み方: 1 行目は「定数のファイルに毎回 1 行追記するツールは、読むだけと宣言していれば反し（ファイルが変わる）、壊さないと宣言していれば反しない（足すだけ）、閉じていると宣言していれば反しない（通信しない）、繰り返しても同じと宣言していれば反する（2 回で 2 行）」と読みます。
5 行目の D3 の欄は「宛先で決まる」です。D3 は、メソッドではなく**宛先**（定数の外部ホストか、手元か、モデルが決めるか）で決まるからです（50.7 節）。

#### 一歩ずつ — 4 つの問いの原文と言い換え

4 つの問いは、MCP の仕様の原文を、判定で答えやすい形に言い換えたものです。

| 宣言 | 仕様の原文（[第 4 章](ch04.md)） | 手引きの問い |
|---|---|---|
| D1 | If true, the tool does not modify its environment. | その動作は、呼び出しの後に残る何かを変えるか（ホストのファイル・DB・相手のサーバの状態・残る設定） |
| D2 | If false, the tool performs only additive updates. | その動作は、**呼び出しの前からあったもの**を消す・上書きする・変えるか。新しく足すだけなら反しない |
| D3 | If false, the tool's domain of interaction is closed. | そのツールは、外部の（そのマシンやローカルの網の外の）相手と通信するか、あるいはモデルが決める相手と通信しうるか |
| D4 | If true, calling the tool repeatedly with the same arguments will have no additional effect on its environment. | **同じ引数で** 2 回呼んだとき、2 回目が 1 回目の後の状態をさらに変えるか |

表の読み方: 2 行目は「仕様の原文は『追加の更新だけをする』。手引きはこれを『呼び出しの前からあったものを消す・上書きする・変えるなら反する。新しく足すだけなら反しない』と言い換えた」と読みます。

言い換えのそれぞれに、原理の選択が入っています。

- D1 の「呼び出しの後に残る何か」に「残る設定」と「相手のサーバの状態」が入っているのは、原理 1-i-b と 1-ii-b を採ったからです。
- D3 の「モデルが決める相手と通信しうるか」は、原理 3-a（取りうる値の全体）を宛先に当てたものです。
- D4 の「**同じ引数で**」は、原理 3 を当てない理由そのものです（50.8 節）。

（出典: `docs/contradiction_principles.md:24-30`（仕様の原文）、`:135-141`（§6 の選択）、`docs/drafts/final_judging_guide_draft.md:311, 335, 356, 369`（4 つの問い））

#### 一歩ずつ — 答え方の共通の手順

どの宣言でも、手順 F は次の 5 段で進めると迷いにくくなります（手引きの手順 F と 15 節を、本書が順序に直したもの）。

1. **照らす宣言を確かめる。** 判定表の行の `decl` 欄です。同じ効果でも、宣言が違えば別の組で、別に答えます（原理 4）。
2. **動作の種類を、コードで決める。** 手順 C で確かめた「本当の動作」を使います。解析器の site 名や理由ではありません。たとえば「`'a'` の追記」「固定の書き先への `'w'`」「`POST`」「定数のコマンドの起動」のように、表の行に当たる言葉で言えるところまで決めます。
3. **表の行を引く。** その宣言の表で、動作に当たる行を探します。答えが「反する」「反しない」と書いてあれば、それが答えの候補です。
4. **「調べて決める」行なら、調べる。** 表の答えが「相手の API の意味で決める」「そのコマンドが実際に何をするかを調べる」「呼び出しの前からファイルがありうるかで決める」のような行は、解析器が「不」にする行です。人は、文書やコードを読んで決めてよいのです。目安は 20〜30 分です。
5. **問いに戻って確かめる。** 表の答えが、表の上の**問い**と食い違っていないかを、最後に確かめます。表に無い形なら、ここで問いに当てて決めます。それでも決まらなければ「決められない」（判定は不明）にし、理由を書きます。

モデルが決める値は、「取りうる値の全体」で考えます（原理 3-a）。
ただし D4 だけは除きます。
（出典: `docs/drafts/final_judging_guide_draft.md:149-151`（手順 F）、`:547-559`（19 節。20〜30 分の目安）、`:701-708`（22 節。手引きで決まらない事例））

#### なぜそうするのか — 問いを 1 つにし、表を添える理由

手引きが「問い」と「表」の 2 段にしているのには、理由があります。

1 つ目は、**判定をぶれさせない**ためです。
判定者が 1 人で数百件を判定するとき、毎回ゼロから考えると、日によって答えが揺れます。
よく出る形の答えを表で先に決めておけば、同じ形には同じ答えが出ます。

2 つ目は、**表に無い形に出会ったときの拠り所**を残すためです。
実際のコードには、表の作者が思いつかなかった形が必ず出ます。
そのとき、表の行を無理に当てはめると、問いの意味とずれた答えが出ることがあります。
問いが 1 つに書かれていれば、そこへ戻って決められます。

3 つ目は、**採った原理を字義どおりに当てる**ためです（手引き 11.3 節、D67 の 1）。
問いは原理から導いたものなので、問いに忠実に答えれば、原理に忠実な判定になります。
「これくらいは違反と言えない」という自分の感覚は、問いには入っていません。
軽重は、書き込み先の種類のラベルで別に表します（[第 51 章](ch51.md)）。
（出典: `docs/drafts/final_judging_guide_draft.md:56-61`（11.3）、`:666-699`（21 節。ぶれさせない工夫）、`docs/decisions.md:3767-3772`（D67 の 1））

#### 解析器の答えとの関係

この章の表は、[第 17 章](ch17.md)で見た解析器の判定表（§7）と、ほとんど同じ行を持っています。
違うのは 2 点です。

1. 解析器が「不」にする行で、人は**調べて決めてよい**（[第 17 章](ch17.md) 17.12 節）。
2. 解析器が「矛」にする行でも、人がコードを読むと**反しない**ことがある。たとえば、書く前に内容を確かめる追記（D4。50.8 節）、自分で作った一時ファイルの削除（D2。50.6 節）、子の標準入力への書き込み（D1。50.4 節）です。

つまり、解析器の表は「コードだけを動かさずに読むと、どこまで言えるか」を表し、この章の表は「人が調べて、本当はどうか」を決めるための表です。
2 つを取り違えないことが、判定の第一歩です。

#### よくある誤解・つまずき

- **誤解: 「1 つの効果には、1 つの答えがある」**
  答えは宣言ごとに違います。上の表の ① のように、同じ追記が D1 と D4 では反し、D2 と D3 では反しません。判定表には宣言ごとに別の行があり、それぞれ別に答えます。
- **誤解: 「表に無い形は、判定できない」**
  表の上の問いに戻って決めます。それでも決まらなければ不明にし、「手引きで決まらない: …」と理由を書きます（手引き 22 節）。
- **誤解: 「解析器の理由コードが D1 の `fs_write` なら、答えは『反する』で決まり」**
  手順 C で、本当にファイルを書く動作かを確かめてからです。子の標準入力への書き込み（E5）や、組み込みのメソッドの取り違え（E3）なら、そもそも表の「ファイルの書き込み」の行に当たりません。
- **つまずき: 「危なそうな動作だから反する、と答えたくなる」**
  問いは「危ないか」ではありません。モデルが決めた URL への `GET` は危なそうに見えますが、D1 には反しません（相手を変えない）。D3 なら反します。

（出典: `docs/drafts/final_judging_guide_draft.md:116-129`（手順 C）、`:701-708`（22 節））

#### 手作業ではどう使うか

判定表の 1 行を開いたら、まず `decl` 欄を見て、この章のどの節を使うかを決めます（D1 → 50.2〜50.4 節、D2 → 50.5〜50.6 節、D3 → 50.7 節、D4 → 50.8 節）。
次に、上の 5 段の手順で答えを出し、`violates` 欄に `はい` / `いいえ` / `決められない` を書きます。
「調べて決める」行で調べたときは、調べた資料（相手の API の文書の URL、コマンドの文書など）を `evidence` 欄に書きます。
「決められない」にしたときは、`unknown_reason` 欄に理由を書きます。

「調べて決める」行は、AI に事実を聞くのが役に立つところです（D70 の 3。AI に判定はさせない）。
たとえば「この POST 先の API は、作成・更新・削除・照会のどれをする？」「`open(path, "a")` は、ファイルが無ければどうなる？」は聞いてよい問いです。
「これは D2 に反するか」「`readOnlyHint` に反するか」は聞きません。宣言の値と解析器の答えも渡しません。
AI が示した資料や行は、自分で開いて確かめたものだけを `evidence` に書きます（不の中身の 18A.3 も「AI が示した資料は自分で開いたものだけ」と書いています）。
AI に聞いたら、`ai_used`・`ai_model`・`ai_log` を書きます。
（出典: `docs/drafts/final_judging_guide_draft.md:169-184`（手順 H の欄）、`:543`（18A.3 の `evidence`）、`:681-692`（21 の 6））

#### この節のまとめ

4 つの宣言には 1 つずつ問いがあり、表はよく出る形の答えを先に書いたもの。表に無い形は問いに戻って決める。
答え方は 5 段: 宣言を確かめる → 動作をコードで決める → 表の行を引く → 「調べて決める」行なら調べる → 問いに戻って確かめる。
解析器の表（矛・不・内）と人の表（反する・反しない・決められない）は別のもの。人は不を調べてよく、矛でも反しないことがある。

### 50.2 D1 `readOnlyHint: true` —「呼び出しの後に残る何かを変えるか」（手引き 15.1 節）

#### 一言で言うと

D1 の問いは、「**その動作は、呼び出しの後に残る何かを変えるか**」です。
残る何かとは、ホストのファイル・DB・相手のサーバの状態・残る設定です。
ファイルを書く・作る・消す動作は、ログ・キャッシュ・一時ファイルでも、すべて反します。
`POST` と定数のコマンドは、解析器は「不」にしますが、**人は調べて決めます**（50.3 節）。

#### たとえ話 — 部屋の内覧

引っ越し先を探して、空き部屋を内覧するとします。
不動産屋さんは「見るだけにしてください」と言います。

- 戸棚を開けて中を見るのは、かまいません。閉めれば元どおりです（ファイルの読み取り、DB の `SELECT`、`GET`）。
- 壁に画びょうで紙を 1 枚貼って帰るのは、だめです。小さな紙でも、次の人が来たときに残っています（ログファイルへの 1 行追記）。
- 部屋に置いてあった古い段ボールを捨てるのも、だめです（ファイルの削除）。
- 自分で持ち込んだメモ用紙を、帰る前に自分で持ち帰るのは？ 部屋には何も残りません。けれども「見るだけ」の約束は、部屋の中で物を出し入れすること自体を含みます（一時ファイルの作成と削除。D1 では反する。49.5 節）。
- 管理会社に電話して「エアコンを新しいものに替えてください」と頼むのも、だめです。部屋の中は今は変わりませんが、管理会社の側で手配が始まります（相手のサーバの状態を変える `PUT`・`PATCH`・`DELETE`）。

「見るだけ」は、思ったより厳しい約束です。
これが、採った原理 1-i-b（呼び出しを越えて残るものはすべて環境）と 1-ii-b（相手側の状態も環境）の読み方です。

#### 小さな例 — 手引きの D1 の表

手引きの 15.1 節の表を、そのまま載せます。

| 動作 | 反するか | 注意 |
|---|---|---|
| ファイルの書き込み・作成・削除・移動・権限の変更（`FS_WRITE` すべて） | **反する** | ログ・キャッシュ・一時ファイル・ディレクトリの作成も含む（原理 1-i-b）。軽重はラベルで表す |
| コードの実行（`EXEC`） | 反する | 表 D41 で決定済み |
| プロセスの起動（`SPAWN`） | 起動するコマンドをモデルが決められるなら反する。コマンドが定数なら、**そのコマンドが実際に何をするか**を調べ、環境を変えるなら反する・変えないなら反しない・分からなければ不明 | 解析器は定数のコマンドを「不」にする（意味が名前から分からないため）。人は調べられる範囲で調べる |
| DB のデータ・スキーマの変更（`INSERT` / `UPDATE` / `DELETE` / `CREATE` / `DROP` など） | 反する | |

5 行目と 6 行目は対になっています。どちらも `PRAGMA` ですが、DB のファイルに残る設定（`journal_mode`）は反し、接続を閉じれば消える設定（`foreign_keys`）は反しません（[第 10 章](ch10.md) 10.8 節）。

#### 一歩ずつ — 表の行を 3 つの群に分けて読む

12 の行は、答えの形で 3 つの群に分かれます。

**群 1: いつも「反する」行**（ファイルの書き込み、`EXEC`、DB の変更、DB に残る設定、`PUT`・`PATCH`・`DELETE`）。
動作の種類が決まれば、答えも決まります。
人がすることは、手順 C で「本当にその動作か」を確かめることだけです。
たとえば `open` のモードが本当に `'w'` か（`'r'` なら読み取りの行に移る）、`execute` の SQL の先頭の語が本当に `INSERT` か、を確かめます。

**群 2: いつも「反しない」行**（接続単位の設定、DB の読み取り、`GET`・`HEAD`・`OPTIONS`、ファイルの読み取り）。
解析器はこれらを「内」にするので、矛の判定には出てきません。
人がこれらの行を使うのは、主に**見落としの判定**で、ツールの本体を読んで「反しうる動作」を書き出すときです。
「この `SELECT` は反しない」と判断して、書き出しから外すために使います。

**群 3: 「調べて決める」行**（定数のコマンドの `SPAWN`、`POST`）。
解析器はこれらを「不」にします。
人は調べて、「反する / 反しない / 決められない」を決めます（50.3 節）。
この群は、**不の中身の判定**と**見落としの判定**でよく出てきます。

この 3 つの群の分け方は、本書が読みやすさのために付けたもので、手引きには書かれていません。

#### 反する例と反しない例の対 3 — 相手のサーバ

```python

`DELETE` は、相手の資源を消すことを頼みます。手元のファイルは何も変わりませんが、相手のサーバの状態が変わります。**反します**（原理 1-ii-b）。

#### なぜそうするのか — D1 の行ごとの理由

- **ファイルの書き込みはすべて反する**: 仕様の原文は "does not modify its environment"（環境を変えない）です。ログや一時ファイルを除く根拠は、原文にありません。だから、原理 1-i-b（呼び出しを越えて残るものはすべて環境）を採り、ファイルの作成・書き込み・削除をすべて環境の変更とします。一時ファイルは呼び出しの後に残らないこともありますが、作る・消すという動作がファイルシステムを変えることに違いはありません（v4 の M58 の考え方）。
- **DB の接続単位の設定は反しない**: 接続を閉じれば消え、次の呼び出しから見えないからです。「呼び出しを越えて残るか」で線を引いています。
- **`PUT`・`PATCH`・`DELETE` は反する**: 原理 1-ii-b で、相手側の状態も環境に含めるからです。理由は「readOnly は『変えるか』、openWorld は『外と関わるか』で別の軸」（§6）。もし 1-ii-a（含めない）を採ると、相手のデータを消すツールが「読み取り専用」でよいことになり、D1 の約束の意味が薄れます。
- **`POST` と定数のコマンドは調べる**: 同じ `POST` でも、作成にも照会にも使われます。同じ `git` でも、`status` と `commit` で動作が違います。名前やメソッドだけでは決まらないので、解析器は「不」にし（原理 2-a）、人は調べて決めます。

### 50.3 D1 で人が調べるもの — `POST` の先と、定数のコマンドの中身

#### 一言で言うと

解析器は、`POST` と「定数のコマンドの起動」を、意味が名前から分からないとして「不」にします。
人は、**相手の API の意味**と、**そのコマンドが実際に何をするか**を調べて決めてよいのです。
変えるなら反する、変えないなら反しない、調べても分からなければ「決められない」です。
ただし、調べた範囲と資料を必ず記録します。

#### たとえ話 — 同じ形の封筒と、同じ名前の道具箱

会社の受付に、同じ形の封筒がたくさん届くとします。
封筒の表には「申請書」としか書いてありません。
中を開けると、「住所の変更」の申請もあれば、「資料の取り寄せ」の申請もあります。
受付の機械は表しか読めないので、全部を「分からない」の箱に入れます。
人は封筒を開けて、中を読んで決めます。
これが `POST` です（メソッドは同じ `POST` でも、中身は作成にも照会にも使われる）。

道具も同じです。
「git」というラベルの道具箱には、中身を見るだけの道具（`status`・`log`）も、記録を書き換える道具（`commit`・`reset`）も入っています。
ラベル（コマンドの名前）だけでは、どの道具を使ったか分かりません。
人は、取り出した道具（サブコマンドとオプション）まで見て決めます。
これが定数のコマンドです。

#### 一歩ずつ — 定数のコマンドの調べ方（本書の手順）

手引きは「そのコマンドが実際に何をするかを調べ」と書いていますが、調べ方の手順は書いていません。
本書は、次の 5 段で調べることを勧めます（手引きの文面から本書が組み立てた手順です）。

1. **起動の行を開き、渡している列（argv）を全部読む。** 先頭（argv0）だけでなく、サブコマンド（`git` の後の `status`・`commit`）とオプション（`-am`）まで読みます。`shell=True` のシェル文字列なら、文字列の全体を読みます。値が変数なら、その値がどこから来るかもたどります。
2. **起動するものが木の中のスクリプトなら、そのスクリプトを読む。** `python scripts/x.py`、`bash setup.sh`、`node tool.js` などです。スクリプトの中でファイルを書いていれば、反します。
3. **起動するものが外のプログラムなら、その公式の文書を読む。** man ページや公式サイトの、そのサブコマンドとオプションの説明です。読んだ文書の URL を `evidence` に書きます。
4. **出力の行き先を確かめる。** 結果を標準出力に返すだけか、ファイルに書くオプション（`--output=…`、`-o …`）を渡しているか。
5. **決められなければ「決められない」にする。** 起動するものの中身が手元に無い、文書が無い、などです。理由を `unknown_reason` に書きます。

よく出るコマンドの、一般的な意味の例を挙げます（判定では、その木で**実際に渡している引数**で確かめてください）。

| 一般に、環境を変えない例 | 一般に、環境を変える例 |
|---|---|
| `git status`・`git log`・`git show` | `git commit`・`git add`・`git checkout`・`git pull` |
| `ls`・`cat`・`grep`・`wc`・`sort`（出力先を指定しないとき） | `rm`・`mv`・`cp`・`mkdir`・`touch`・`tee <ファイル>` |
| `kubectl get`・`kubectl describe` | `kubectl apply`・`kubectl delete` |
| `docker ps`・`docker images` | `docker run`・`docker rm`・`docker pull` |
| `pip list`・`pip show` | `pip install`・`npm install` |

13      return subprocess.run(cmd, shell=True, capture_output=True, text=True).stdout
```

- 10〜11 行目: 読み取り専用のツール `grep_notes` で、検索語 `q` をモデルが渡します。
- 12 行目: シェルに渡す文字列を組み立てます。`shlex.quote(q)` は、`q` をシェルの 1 つの引数として扱われるように引用符で囲む関数です（[第 9 章](ch09.md) 9.6 節）。たとえば `q` が `a; rm -rf ~` でも、`'a; rm -rf ~'` という 1 つの検索語になり、`rm` は実行されません。
- 13 行目: その文字列をシェルで実行し（`shell=True`）、出力を返します。

本書の試験では、解析器はこの起動を**矛**（`spawn_model`）にしました。
シェル文字列にモデルの値が入っているので、「モデルがコマンドを決められる」と読んだのです。

人が読むと、起動するコマンドは `grep` に固定されています。
モデルが決められるのは検索語だけで、`shlex.quote` のおかげで別のコマンドをつなげることはできません。
だから「コマンドをモデルが決められる」の行には当たらず、「コマンドが定数」の行で調べます。
`grep` は検索して結果を標準出力に出すだけなので、**反しません**。
判定は誤で、原因は **E7**（モデルが決められないのに決められるとした）です。v3 でも同じ類が 2 件ありました（O41）。

1 つ注意があります。
`shlex.quote` は、`-` で始まる値をそのまま通します（本書の執筆時に確かめると、`shlex.quote('-r')` は `-r` のままでした）。
だから、モデルは `grep` に**オプションを足す**ことはできます。
本書の執筆時に GNU grep 3.11 の `--help` を見た限りでは、結果をファイルに書くオプションは見当たりませんでした。
だから、この例では答えは変わりません。
けれども、コマンドによっては、オプションでファイルを書けるものがあります（次の形）。
（出典: 本書の試験（作例 `toy_d1c/server.py` の 10〜13 行）、`docs/drafts/final_judging_guide_draft.md:441`（E7）、`docs/open_questions.md:1063`（O41 の `shlex.quote`））

#### 迷いやすい形 2 — 固定のコマンドの「引数」をモデルが決める

```python
16  @mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
17  def git_diff(path: str) -> str:
18      return subprocess.run(["git", "diff", path], capture_output=True, text=True).stdout
```

- 16〜17 行目: 読み取り専用のツール `git_diff` で、モデルが `path` を渡します。
- 18 行目: `git diff <path>` を起動し、差分の表示を返します。列で渡しているので、シェルは通りません。

解析器は、先頭が定数の `git` なので「不」（`spawn_command`）にしました。
`git diff` は、ふつうは差分を表示するだけです。
けれども、`git diff` には `--output=<ファイル>` というオプションがあり、差分を標準出力ではなくファイルに書きます。
本書の執筆時に、作業用の場所で `git diff "--output=via_arg.patch"` を 1 つの引数として渡すと、`via_arg.patch` が作られました（git 2.43.0）。
つまり、モデルが `path` に `--output=…` を渡せば、このツールはファイルを書けます。

手順 F は「モデルが決める値は『取りうる値の全体』で考える」と書いています（原理 3-a）。
これを引数にも当てると、`git_diff` はファイルを書く能力を持つので、**反する側**に読めます。
一方で、手引きの `SPAWN` の行は「起動するコマンドをモデルが決められるなら」と、**コマンド**のことしか書いていません。
コマンドが定数で、引数だけをモデルが決める形について、どこまで調べるか（そのコマンドのすべてのオプション）を決めていません。

本書の読み方は、「手順 F の『取りうる値の全体』に従い、引数でファイルを書けるオプションがあると確かめられたら反する。確かめられなければ、ふつうの意味で決める」です。
けれども、これは手引きに書かれていない境目です。
封の前に学生が決めておく候補として、50.11 節に挙げます。
なお、オプションの混入の危険は、別の問い（注入の座標）として O35 にも記録があり、そこでも `--output=` が例に挙がっています（O35 は未決）。
（出典: 本書の試験（作例 `toy_d1c/server.py` の 16〜18 行）、`docs/drafts/final_judging_guide_draft.md:151`（手順 F）、`:317`（SPAWN の行）、`docs/open_questions.md:988-1004`（O35））

#### なぜそうするのか — 人が調べてよい理由と、調べる範囲

解析器は、コードだけを、動かさずに読みます。
相手のサーバのコードや文書、起動するプログラムの中身は読みません。
だから、`POST` の意味や、コマンドの意味は、解析器にとっては原理的に決められません（原理 2-a で「不」）。

人の判定は、解析器の答えが**実際に当たっていたか**を確かめる作業です。
そのためには、使える情報を使って、本当の振る舞いに近づく必要があります。
手引きが「人は調べられる範囲で調べる」と書いているのは、このためです。

ただし、2 つの約束を同時に守ります。
1 つは、**調べれば分かるものを「不明」にしない**ことです。
もう 1 つは、**分からないものを黙って「反する」「反しない」に倒さない**ことです（CLAUDE.md の規則 4）。
目安は、20〜30 分調べても決められなければ「決められない」です。
（出典: `docs/drafts/final_judging_guide_draft.md:317, 323`（「人は調べられる範囲で調べる」）、`:547-559`（19 節））

#### よくある誤解・つまずき

- **誤解: 「`POST` は作成だから、D1 なら必ず反する」**
  照会の `POST`（検索の API、言語モデルへの問い合わせ、GraphQL の `query`）は反しません。メソッドではなく中身で決めます。
- **誤解: 「`git` は開発の道具だから、何をしても環境を変える」**
  サブコマンドで違います。`git status` は表示だけ、`git commit` は記録を作ります。
- **誤解: 「`shlex.quote` があれば、モデルは何もできない」**
  別のコマンドをつなげることはできませんが、`-` で始まる値でオプションを足すことはできます。そのコマンドにファイルを書くオプションがあるかを確かめます（迷いやすい形 2）。
- **つまずき: 「調べるために、そのコマンドを自分のパソコンで動かしてよいか」**
  手引きは、動かして確かめることを求めていません。文書を読むのが基本です。動かすなら、判定対象の木のコードではなく、手元の安全な場所で、そのコマンドの振る舞いだけを確かめます（本書も、`git diff --output` を作業用の場所で確かめました）。確かめたことは `evidence` に書きます。
- **つまずき: 「API の文書が英語で長い」**
  エンドポイント（パス）の一覧の、その 1 行の説明を探せば足りることが多いです。見つからなければ、パス・ツールの説明文・本体の項目から決め、それでも決まらなければ「決められない」にします。

#### 手作業ではどう使うか

`POST` と定数のコマンドに出会うのは、主に**不の中身の判定**（D1 で 50 木）と、**見落としの判定**です。
v4 では、D1 の不の理由の上位 2 つが `net_post`（78 組）と `spawn_command`（64 組）でした（v4 の数で、論文には使わない）。
最終評価でも、この 2 つが不の中身の判定の多くを占める見込みです（見込みで、測っていません）。

記録の例（不の中身の判定、`search_api` の作例）:

> `outcome`: 違反でない / `reachable`: はい / `violates`: いいえ / `evidence`: `server.py:67 requests.post("https://api.example.com/v1/search", json={"q": q})`。パスは search、本体は検索語だけ。相手の API 文書（<URL>）で検索のエンドポイントと確認。

（出典: `evidence/population_v4/contradiction_by_decl_v4_run1.md:20-31`、`docs/drafts/final_judging_guide_draft.md:537-544`（18A.3 の欄））

#### この節のまとめ

`POST` は相手の API の意味（パス・本体・文書）で、定数のコマンドはサブコマンド・オプション・スクリプトの中身・文書で決める。
D1 では、作成・更新・削除・ファイルを書くコマンドは反し、照会・表示だけのコマンドは反しない。調べても分からなければ「決められない」。
`shlex.quote` の形は E7 になりうる。引数でファイルを書けるオプション（`git diff --output`）は手引きに書かれていない境目。

### 50.4 D1 の迷いやすい 3 つの形 — ログの出力先・子の標準入力・`ctx` の通知（手引き 15.1 節の続き）

#### 一言で言うと

手引きは、D1 で迷いやすい形を 3 つ挙げています。

1. **標準出力・標準エラーへのログ**は、ファイルではないので反しない。ただし、ログの出力先がファイルなら反する。出力先の設定を確かめる。
2. **子プロセスの標準入力への書き込み**は、それ自体はファイルを変えない。子がそれを受けて何をするかで決める（E5）。
3. **クライアントへの通知**（`ctx.info()`・`ctx.report_progress()`）は、環境を変えないので反しない。

3 つに共通するのは、「**書いているように見えるが、行き先はファイルではない**」ことです。
行き先を確かめるのが、判定の仕事です。

#### たとえ話 — 声・伝言・電話

会議の記録係を思い浮かべます。

- 会議中に「今、議題 2 に入りました」と**声に出して言う**のは、何も残りません（標準エラーへのログ）。
- 同じことを**議事録のノートに書く**のは、ノートに残ります（ファイルへのログ）。声に出すか書くかは、記録係ではなく、会議の前の取り決め（ログの出力先の設定）で決まります。
- 隣の人に「この紙を読んで」と**紙を渡す**のは、渡したこと自体は何も残しません。けれども、受け取った人がその紙をファイル棚にしまえば、棚が変わります（子の標準入力。子が何をするかで決まる）。
- 会議の様子を、外にいる依頼主に**電話で伝える**のは、部屋の中を何も変えません（クライアントへの通知）。

どれも「何かを書いている」ように見えますが、残るかどうかは行き先で決まります。

この試験から分かることを 3 つ挙げます。

1. 解析器は、`logging` のログの書き込みを、出力先がファイルでも標準エラーでも、効果にしませんでした。だから、ログの出力先の判断が要るのは、主に**見落としの判定**です。
2. 解析器は、`ctx.info` などのクライアントへの通知を効果にしませんでした。手引きの答え（反しない）と一致します。
3. 解析器は、子の標準入力への流し込みを、子が何であっても同じ `fs_write` の矛にしました。O41 は、これを「保守的な上界として残した」と記録しています（子が `tee` や `python` なら、標準入力はファイルの書き込みやコードの実行に届くため）。だから、人は子が何をするかを見て決めます。

もう 1 つ、本書の試験で気づいたことがあります。
`communicate(text)` と、流し込む値を**位置で**渡した形では、`pipe:communicate` の行が出ませんでした（`input=text` と名前で渡すと出た）。
起動そのもの（`spawn_command` の不）は、どちらでも出ました。
この違いは、記録（O41〜O43）には書かれていない、本書の試験での観察です（本書の検証のときにも、同じ凍結版で 2 つの形を並べて走らせ直し、位置で渡した形だけ `pipe:communicate` の行が出ないことを確かめました）。
判定への影響は、矛が出ないので**見落としの判定**の側に出ます。位置で渡した形の子が `tee` のようにファイルを書くなら、本体を読んで書き出したときに、解析器の出力に矛が無い反する動作として見つかります。

#### 一歩ずつ — ログの出力先を確かめる 5 つの点

ログを書く行（`logger.info(...)` など）を見つけたら、次の 5 点を確かめます（[第 9 章](ch09.md) 9.5 節の知識を、判定の手順に直したもの。本書の手順）。

1. **ロガーはどれか**: `logging.getLogger(名前)` の名前、または loguru の `logger`。
2. **出し口は何か**: そのロガーに付いたハンドラ（`FileHandler`・`RotatingFileHandler` ならファイル、`StreamHandler()` なら標準エラー）、`logging.basicConfig(filename=…)`、loguru の `logger.add(<パス>)`、`logging.config.dictConfig(...)` の設定。
3. **どこで設定しているか**: ツールの関数の中だけでなく、**モジュールの一番上**、`__init__.py`、`main()`、設定ファイルまで探します（v4 の R19 はモジュールの一番上でした。手引き 18.3 節もこの点を名指ししています）。
4. **親に回るか**: `logging` のロガーは、`propagate` が `False` でなければ、親（最後はルート）のロガーの出し口にも記録を回します。ルートにファイルの出し口があれば、そこにも書かれます。
5. **その水準の記録が実際に出るか**: ロガーの水準が WARNING なら、`logger.info(...)` は書かれません（[第 9 章](ch09.md) 9.5 節の事実 4）。水準が環境変数などで決まるなら、運用者の設定で書かれることがある、と読みます（条件の種類は `運用者の設定`。[第 49 章](ch49.md)）。

5 点を確かめて、行き先にファイルが 1 つでもあれば、**反します**。
行き先が標準出力・標準エラー・クライアントだけなら、**反しません**。
設定が読み切れなければ、「決められない」にして理由を書きます。

#### なぜそうするのか — 「ファイルではない」を理由にする意味

D1 の問いは「呼び出しの後に残る何かを変えるか」です。

だから、子が何をするかで決めます。

`ctx` の通知は、クライアントへのメッセージです。
クライアントがそれを画面に出すか、どこかに保存するかは、クライアントの側の動作です。
ツールの環境（ホストのファイル・DB・相手のサーバ）は変わりません。

#### よくある誤解・つまずき

- **誤解: 「`logger.info(...)` があれば、ログファイルに書いているので反する」**
  ログを書く行だけでは決まりません。出力先の設定を 5 点で確かめます。標準エラーだけなら反しません。
- **誤解: 「解析器がログに何も出していないから、ログは反しない」**
  解析器は `logging` のログの書き込みを効果にしません（本書の試験）。loguru の `logger.add(<ファイル>)` も、v4 では語彙に無いとして見落としになりました（R19）。人が出力先を確かめます。
- **誤解: 「`pipe:communicate` の矛は、いつも誤（E5）」**
  子がファイルを書くなら正です（`tee` の例）。子が Python やシェルで、流し込むのがコードなら、コードの実行（`EXEC` と同じ動作）にもなりえます。子が何かを確かめます。
- **誤解: 「`ctx.info` はログだから、ファイルに残る」**
  クライアントへの通知です。ツールの側では何も残しません。
- **つまずき: 「`print(...)` は標準出力では？ stdio のサーバで大丈夫？」**
  stdio で動く MCP サーバでは、標準出力は MCP のやり取りに使われるので、ログはふつう標準エラーに出します（[第 9 章](ch09.md) 9.5 節）。どちらにしても、ファイルではないので D1 には反しません。

#### 手作業ではどう使うか

- **矛の判定**: `pipe:write`・`pipe:communicate` の矛に出会ったら、子のコマンドを見て、子がファイルを書くか（`tee`・`dd of=…`）、コードを実行するか、何も残さないか（`sort`・`wc`）を決めます。何も残さないなら誤、`error_class` は `E5: 子の sort の標準入力に流すだけ（server.py:21）` のように書きます。
- **見落としの判定**: ログを書く行を見つけたら、5 点で出力先を確かめます。ファイルなら「反しうる動作」として書き出し、解析器の出力に何も無ければ見落とし（原因は語彙）になります。書き込み先の種類は「ログ」です（[第 51 章](ch51.md)）。
- **`note` に書くこと**: 標準エラーだけと判断したなら、その根拠の行（`StreamHandler(sys.stderr)` の行、`propagate = False` の行）を書いておくと、第三者が確かめやすくなります。

（出典: `docs/drafts/final_judging_guide_draft.md:439`（E5）、`:473-476`（見落としの原因と書き込み先の種類））

#### この節のまとめ

標準出力・標準エラーへのログと、`ctx` の通知は反しない。ログの出力先がファイルなら反する。出力先は、モジュールの一番上・親への回り方・水準まで 5 点で確かめる。
子の標準入力への書き込みは、子が何をするかで決める。`sort` なら誤（E5）、`tee <ファイル>` なら正。
解析器は `logging` のログも `ctx` の通知も効果にしない。ログの判断が要るのは、主に見落としの判定。

### 50.5 D2 `destructiveHint: false` —「呼び出しの前からあったものを消す・上書きする・変えるか」（手引き 15.2 節）

#### 一言で言うと

D2 の問いは、「**その動作は、呼び出しの前からあったものを消す・上書きする・変えるか**」です。
新しく足すだけなら反しません。
書き出し（`'w'` など）は、書き先で 3 つに分かれます。
**書き先をモデルが決められるなら反する**（既存のファイルを指せば上書きできる）。
書き先が固定なら、**毎回同じファイルを上書きするなら反する、毎回新しい名前なら反しない、分からなければ決められない**です。

#### たとえ話 — 寄せ書きの色紙

卒業する先生に、クラスで寄せ書きの色紙を作るとします。
係の人が言います。「書き足すのはいいけれど、人が書いたものは消したり上から書いたりしないでね」。

- 空いている場所に自分のメッセージを書くのは、かまいません（新しく足すだけ）。
- 新しい色紙をもう 1 枚用意して書くのも、かまいません（新しいファイルを作る）。
- 誰かのメッセージを修正液で消すのは、だめです（既存のものを消す）。
- 誰かのメッセージの上に重ねて書くのは、だめです（上書き）。
- 「好きな場所に書いていいよ」と言われた人が、人のメッセージの上に書くこともできてしまう場合は？ 実際に重ねて書くかどうかに関係なく、**重ねて書ける**こと自体が約束に反する、と考えます（原理 3-a。書き先をモデルが決められる）。
- 自分で貼った付箋を、自分ではがすのは？ 元からあったものではないので、かまいません（自分が作った一時ファイルの削除。50.6 節）。

D1 の「見るだけ」と違い、D2 は「**元からあるものを守る**」約束です。

#### 小さな例 — 手引きの D2 の表

手引きの 15.2 節の表を、そのまま載せます。

| 動作 | 反するか |
|---|---|
| 新しく作るだけ（`mkdir`、`open('x')`、`open('a')` の追記、DB の `INSERT` / `CREATE`、HTTP の `GET`） | 反しない |
| 既存のものを消す・動かす・変える（`unlink` / `rmtree` / `rename` / `chmod`、DB の `UPDATE` / `DELETE` / `DROP` / `ALTER`、HTTP の `DELETE` / `PATCH`） | **反する** |
| 書き出し（`open('w')` / `write_text` / `copy` など） | **書き先をモデルが決められるなら反する**（既存のファイルを指せば上書きできる。原理 3-a）。書き先が固定なら、そこに**呼び出しの前からファイルがありうるか**で決める（毎回同じファイルを上書きするなら反する、呼び出しごとに新しい名前なら反しない、分からなければ不明） |
| HTTP の `PUT` | 宛先をモデルが決められるなら反する。そうでなければ、既存の資源の置き換えか新規作成かで決める |

表の読み方: 3 行目は「`'w'` で書き出すツールは、書き先をモデルが決められるなら、モデルが既存のファイルを指せば上書きできるので反する。書き先が固定なら、そこに呼び出しの前からファイルがありうるかで決める。毎回同じ名前のファイルを書き直すなら、2 回目からは前の内容を上書きするので反する。呼び出しごとに新しい名前を作るなら、前からあったものを上書きしないので反しない」と読みます。
1 行目の「追記」は、ファイルの末尾に書き足すだけで、前の内容を消さないので、反しません。
最後の行は、この章の表で唯一、**人が調べても「決められない」と決まっている行**です（理由は下の「なぜ」）。

本書の執筆時に、`destructiveHint=False` を付けた 3 つのツールを書き、凍結版の解析器で走査しました。

#### 一歩ずつ — 「呼び出しの前からファイルがありうるか」の確かめ方

書き先が固定のときの規則は、「そこに呼び出しの前からファイルがありうるか」です。
本書は、次の 4 つの問いで確かめることを勧めます（手引きの規則から本書が組み立てた手順）。

1. **名前は毎回同じか。** 定数のパス、定数のディレクトリ＋定数のファイル名なら、毎回同じです。`uuid4()`・`mkstemp()`・連番のように、呼び出しごとに必ず違う名前なら、毎回新しいです。
2. **同じツール（または同じ木の別のツール）の前の呼び出しが、そのファイルを残すか。** 書いた後に消さないなら、次の呼び出しの前にはファイルがあります。
3. **書く前に、ファイルがあるかを確かめているか。** `if not os.path.exists(p):` の中だけで書くなら、前からあるファイルを上書きしません（下の対）。
4. **ほかの誰か（利用者・別のプログラム）が、そこにファイルを置くか。** 利用者のホームの設定ファイルの場所などは、利用者が前から持っていることがあります。

1 で「毎回同じ」、2 で「残る」なら、2 回目から上書きするので**反する**です。
1 で「毎回新しい」なら**反しない**です。
3 で「ある時は書かない」なら**反しない**です。
どれとも決められなければ「決められない」です。

#### 反する例と反しない例の対 — 毎回書き直すか、無いときだけ作るか

```python
# (ア) 反する: 毎回同じ設定ファイルを書き直す（作例）
@mcp.tool(annotations=ToolAnnotations(destructiveHint=False))
def save_settings(theme: str) -> str:
    with open(SETTINGS_FILE, "w") as fh:
        json.dump({"theme": theme}, fh)
    return "ok"

# (イ) 反しない: 無いときだけ、既定の設定ファイルを作る（作例）
@mcp.tool(annotations=ToolAnnotations(destructiveHint=False))
def ensure_settings() -> str:
    if not os.path.exists(SETTINGS_FILE):
        with open(SETTINGS_FILE, "w") as fh:
            json.dump({"theme": "light"}, fh)
    return "ok"
```

（`SETTINGS_FILE` は、モジュールの一番上で定数 `"/srv/app/settings.json"` と決めてある。下の説明は、コードの中の文で行を指す。）

- (ア) の `with open(SETTINGS_FILE, "w") as fh:` と `json.dump(...)` の 2 行: 定数の `SETTINGS_FILE` を、毎回 `'w'` で開いて書き直します。前の呼び出しで書いた設定は消えます。
- (イ) の `if not os.path.exists(SETTINGS_FILE):` の行: ファイルが**無いときだけ**、次に進みます。`os.path.exists(p)` は「`p` にファイル（かディレクトリ）があれば真」を返す関数です。
- (イ) の `with open(...)` と `json.dump(...)` の 2 行: 無いときだけ、既定の設定（`theme` は `light`）を書きます。

(ア) は、2 回目の呼び出しで、1 回目の設定（呼び出しの前からあったもの）を上書きします。**反します。**
(イ) は、ファイルがあれば何もしません。前からあるものを上書きしません。**反しません。**
解析器は、どちらも書き先が定数の書き出しなので、同じ `fs_writeout` の不にしました（`if` の中身を見て区別はしません。本書の試験）。

（作例。手引きの規則を当てた本書の考え方。解析器の答えは本書の試験（作例 `toy_d2b/server.py`）で確かめた。）

#### 一歩ずつ — `PUT`・`POST`・DB に残る設定

**`PUT`**（置く・置き換える）: 本書の試験では、宛先をモデルが決める `requests.put(url, ...)` は**矛**（`net_put_model_url`）、定数の宛先 `requests.put("https://cfg.example.com/api/config/main", ...)` は**不**（`net_put`）になりました。
人は、定数の宛先なら「既存の資源の置き換えか、新規作成か」を調べます。
`/api/config/main` のように、決まった 1 つの資源を毎回置き換えるなら、2 回目からは前の内容を置き換えるので、`'w'` の上書きと同じ理屈で**反する側**に読めます（本書の読み方）。

**`POST`**: 相手の API の意味で決めます。
D2 では、**作成は「足すだけ」なので反しません**。
更新・削除なら反します。
v4 の bugasura の `update_project`（`POST /v1/projects/update`）は、既存のプロジェクトを書き換えるので、v4 の判定（R01）は「人の判定では D2 に反する動作」と書き留めています（[第 10 章](ch10.md) 10.4 節）。
本書の試験の `create_ticket`（`POST .../api/tickets` で新しい課題を作る）は、文書で「新しい課題を作る」と確かめられれば、D2 には反しない側です。

**DB に残る設定**（`PRAGMA journal_mode=WAL` など）: 解析器は不（`db_persistent`）にし、人も「決められない」にします。
これは、調べれば分かるのに不明にするのではありません。
**問いそのものが当てはまらない**ので、手引きが先に「不明」と決めているのです（下の「なぜ」）。

（出典: 本書の試験（作例 `toy_d2/server.py:104, 110, 115, 120`）、`docs/drafts/final_judging_guide_draft.md:342-344`、`evidence/population_v4/v4_judgments.json:1161`（R01））

#### なぜそうするのか — D2 の行ごとの理由

- **追記・作成は反しない**: 仕様の原文は "performs only additive updates"（追加の更新だけをする）です。新しく作る・末尾に足すのは、まさに「追加の更新」です。表 D41 でも、`mkdir` と `open('a')` は D2 に対して宣言内と決めてあります。
- **削除・移動・権限の変更・`UPDATE`・`DELETE` は反する**: 前からあるものを消したり変えたりするので、「追加だけ」ではありません。
- **書き出しは書き先で分ける**: `'w'` は、ファイルが無ければ新しく作り（追加）、あれば中身を消して書き直します（破壊）。どちらになるかは、書き先にファイルがあるかで決まります。解析器は動かさずに読むので、これを決められず、書き先が固定なら不にします（原理 2-a）。人は、名前が毎回同じか・前の呼び出しが残すかを読んで決められます。
- **書き先をモデルが決められるなら反する**: 原理 3-a（取りうる値の全体）により、モデルが既存のファイル（利用者の文書など）を指せば上書きできる、と読みます。実際にモデルがそうするかは問いません。D2 の宣言を信じてクライアントが確認を省いたとき、上書きが起きうることが問題だからです。
- **DB に残る設定は不明**: `PRAGMA journal_mode=WAL` は、データを足すのでも消すのでもなく、DB の設定を変えます。「追加か破壊か」という D2 の物差しが、設定の変更には当てはまりません。D1 なら「変えるか」で答えられますが（反する）、D2 ではどちらとも言えないので、§7.2 は不にし、手引きも「不明（解析器と同じ）」としています。

（出典: `docs/contradiction_principles.md:24-27`（原文）、`:34-36`（表 D41）、`:72-81`（原理 3）、`:105-109`（§5 の #1 と #7）、`:179-200`（§7.2）、`docs/decisions.md:3796-3800`（D68 の 1 の理由: クライアントは確認を省く））

#### よくある誤解・つまずき

- **誤解: 「`'w'` は上書きだから、D2 ではいつも反する」**
  書き先が毎回新しい名前なら、前からあったものを上書きしないので反しません。書き先が無いときだけ書く形も反しません。
- **誤解: 「モデルが決めた `path` でも、ふつうは新しいファイルの名前を渡すはず」**
  原理 3-a は「取りうる値の全体」で考えます。モデルが既存のファイルを指せば上書きできるので、反します。
- **誤解: 「`POST` で新しい課題を作るのは、相手を変えるので D2 に反する」**
  D2 の問いは「前からあったものを変えるか」です。新しい課題を足すだけなら反しません。D1 なら反します（作成も環境の変更）。宣言で答えが違います。
- **誤解: 「`'a'` の追記は、ファイルの中身を変えるので D2 に反する」**
  前の内容を消さずに末尾に足すだけなので、反しません（手引きの表の 1 行目）。
- **つまずき: 「DB に残る設定を、調べて決めたくなる」**
  D2 では、問いが当てはまらないので「決められない」と決まっています。調べても答えは変わりません。`unknown_reason` には「手引き 15.2: DB に残る設定の変更は『追加か破壊か』が当てはまらない」と書けば足ります。

#### 手作業ではどう使うか

- **矛の判定**: D2 の矛は、v4 では `fs_remove` がほとんど（144 組。v4 の数で、論文には使わない）でした。`fs_remove` の矛に出会ったら、**消しているものが呼び出しの前からあったものか**を確かめます（50.6 節）。`fs_writeout_model_path` の矛なら、書き先を本当にモデルが選べるかを、値の流れで確かめます。
- **不の中身の判定**: D2 の不は、v4 では `fs_writeout`（121 組）と `net_post`（93 組）が上位でした。`fs_writeout` は上の 4 つの問いで、`net_post` は相手の API の意味で決めます。
- **見落としの判定**: 本体を読んで書き出すとき、`'a'`・`mkdir`・`INSERT`・`GET` は「反しない」として外し、`'w'`・削除・`UPDATE`・`DELETE`・`PATCH`・`POST`（更新・削除）を書き出します。ただし `INSERT OR REPLACE` などは「足すだけ」とは限りません（[第 10 章](ch10.md) 10.6 節。50.11 節の候補 11）。

（出典: `evidence/population_v4/contradiction_by_decl_v4_run1.md:32-45`（v4 の D2 の理由の内訳））

#### この節のまとめ

D2 の問いは「呼び出しの前からあったものを消す・上書きする・変えるか」。追記・作成・`INSERT`・`GET` は反しない。削除・移動・`UPDATE`・`DELETE`・`PATCH` は反する。
書き出しは書き先で分かれる: モデルが決める → 反する / 毎回同じファイル → 反する / 毎回新しい名前・無いときだけ書く → 反しない / 分からない → 決められない。
`POST` は D2 では「作成は反しない、更新・削除は反する」。DB に残る設定は、問いが当てはまらないので決められない。

### 50.6 D2 の迷いやすい形 — 自分で作ったもの・前の呼び出しが残したもの・キャッシュ・書き戻し

#### 一言で言うと

D2 で一番迷うのは、「**消している（上書きしている）ものは、呼び出しの前からあったか**」です。
手引きは 2 つの形を名指ししています。

1. **同じ呼び出しで自分が作った一時ファイル・ロックファイルを消す**のは、前からあったものではないので**反しない**（誤、E2）。ただし、**前の呼び出しが残したファイル**を消すなら、それは前からあったものなので**反する**。
2. **キャッシュの上書き**: 同じキャッシュファイルを毎回 `'w'` で書き直すなら、前の内容を上書きするので**反する**（ラベルはキャッシュ・状態の保存）。

本書は、これに 2 つの形を足して説明します。
**atomic write**（一時ファイルに書いてから置き換える）と、**読んで・足して・書き戻す**形です。

#### たとえ話 — 給湯室の冷蔵庫

職場の給湯室の冷蔵庫に、「人の物を捨てないでください」と貼ってあるとします。

- 自分が朝入れたお弁当を、昼に取り出して食べ、容器を捨てる。自分の物なので、かまいません（自分が作った一時ファイルを消す）。
- 昨日の誰かが置き忘れたお弁当を、「もう古いから」と捨てる。それは人の物で、今日より前からあった物です。張り紙に反します（前の呼び出しが残したファイルを消す）。
- 冷蔵庫のホワイトボードの「今日の当番」の欄を、毎朝書き直す。昨日の誰かが書いた字を消して書くので、「人の物を消す」に当たります（キャッシュの上書き）。

自分の物か、前からあった物か。
それだけで答えが変わります。

- 71〜72 行目: `STATE_FILE` が**あれば**消します。このツールは `STATE_FILE` を作りません。あるとすれば、別のツールか前の呼び出しが残したものです。
- 78〜80 行目: `STATE_FILE.tmp` という一時の名前に書きます。
- 81 行目: `os.replace(tmp, STATE_FILE)` で、一時のファイルを `STATE_FILE` の名前に置き換えます。`STATE_FILE` が前からあれば、**その中身は新しいものに置き換わります**（[第 9 章](ch09.md) 9.4 節）。

表の読み方: 1 行目は「`tmp_roundtrip` の 56 行の削除は、同じ呼び出しの 49 行で自分が作った一時ファイルを消すだけなので、呼び出しの前からあったものを消していない。D2 に反しないので誤で、原因は E2」と読みます。
3 行目と 4 行目は、どちらも `STATE_FILE` という、呼び出しの前からありうるファイルに触れます。3 行目は消し、4 行目は置き換えます。どちらも前からあったものを変えるので反します。

4 つとも解析器の答えは同じ `fs_remove` の矛です。
解析器は「何を消すか」の出どころを、呼び出しをまたいで区別しないからです。

表の読み方: 2 行目は「`os.replace` は、置き換え先にファイルがあれば、その中身を新しいものに差し替える。だから、毎回同じ書き先を置き換えるなら、2 回目からは前の内容を置き換えるので反する」と読みます。

つまり、**同じツールでも、`os.unlink` の組は誤、`os.replace` の組は（前からあるファイルを置き換えるなら）正になりうる**、という読み方です。
組は site ごとに分かれているので、組ごとに、その site の動作だけで決めます。
（v4 の M15 の記録は、一時ファイルを作った行を 132 行と書いていますが、本書の執筆時の原ソースでは 134 行で名前を決め、136 行で開いていました。）

本来の動作かどうかは、正誤には持ち込まず、書き込み先の種類のラベルで表します（D67 の 1。[第 51 章](ch51.md)）。

#### 一歩ずつ — 「前からあったか」を確かめる手順

`fs_remove` の矛や、`'w'`・`os.replace` に出会ったら、次の順で確かめます（本書の手順）。

1. **消す（置き換える）ファイルの名前が、どこで決まるかを読む。** `mkstemp()`・`uuid4()`・その呼び出しの中で作った名前か、定数か、引数か。
2. **同じ呼び出しの中で、そのファイルを作っているかを読む。** 作る行（`mkstemp`・`open(…, 'w')`）と消す行が、同じ関数の `try` / `finally` や `with` の中で対になっているか。
3. **作る行が無いなら、誰が作るかを grep で探す。** 同じツールの前の呼び出し、別のツール、外のプログラム（REAPER のような相手）など。見つかれば、それは「前からあったもの」です。
4. **毎回作って毎回消す形でも、残ることがあるかを考える。** 途中で失敗して消し損ねた残り物を、次の呼び出しが消す形（reaper-mcp の 368 行）は、前からあったものを消しています。
5. **決められなければ「決められない」にする。** 誰がいつ作るか読み切れないときです。

#### なぜそうするのか — E2 を「反しない」にする理由

仕様の原文は「追加の更新だけをする」です。
自分が同じ呼び出しで作った一時ファイルを消しても、呼び出しの前と後で、前からあったものは何も変わっていません。
呼び出しの全体で見れば、何も足さず、何も壊していません。
だから、D2 の問い（呼び出しの前からあったものを消すか）には「いいえ」です。

O41 は、この形を「MCP 仕様の『additive か destructive か』で読めば破壊的ではないが、採った原理の読み替えになるので（解析器は）直さない」と記録しています。
解析器は、削除（`unlink` など）を一律に「既存のものを消す」類に入れ、矛にします（表 D41 で決定済み）。
呼び出しの中で作ったかどうかを区別するには、値の出どころを呼び出しの中で追う必要があり、一般に正しい直し方が無いので、凍結版では直していません。
その代わり、人の判定で E2 として誤にし、件数を限界の材料にします。

D1 では、同じ形が**反する**ことに注意します（49.5 節）。
D1 の問いは「変えるか」で、作る・消すという動作そのものがファイルシステムを変えるからです。

（出典: `docs/open_questions.md:1061-1062`（O41 の 1 つ目）、`:1189`（O43 の同じ類）、`docs/contradiction_principles.md:121-123`（決定済みのマス）、`docs/drafts/final_judging_guide_draft.md:656`（M58: D1 では反する、D2 なら E2））

#### よくある誤解・つまずき

- **誤解: 「一時ファイルなら、どの宣言でも反しない」**
  D2 では反しません（E2）。D1 では反します。宣言で違います。
- **誤解: 「`finally` で消しているなら、いつも E2」**
  消すものが同じ呼び出しで作ったものなら E2 です。前の呼び出しが残したもの（reaper-mcp）や、別のツールが作ったものを消すなら反します。
- **誤解: 「atomic write は安全な書き方だから、反しない」**
  安全かどうかは問いではありません。置き換え先に前からファイルがあれば、前の中身を置き換えるので反します。反しないのは、失敗時に一時ファイルを消す部分（E2）です。
- **誤解: 「キャッシュは消えても困らないから、上書きしても反しない」**
  手引きは「同じキャッシュファイルを毎回 `'w'` で書き直すなら、前の内容を上書きするので反する」と書いています。困るかどうかは問いではありません。ラベル（キャッシュ・状態の保存）で表します。
- **つまずき: 「ロックファイルを `'w'` で作る 61 行の組は？」**
  `with_lock` の 61 行は、解析器は `fs_writeout` の不にします。人が読むと、ロックファイルは毎回作って毎回消すので、ふつうは呼び出しの前にはありません。前からあるものを上書きしないので、反しない側です。ただし、前の呼び出しが途中で止まって残したロックや、同時に動く別の呼び出しのロックを上書きしうるか、という点は手引きに書かれていません（50.11 節）。

#### 手作業ではどう使うか

- **矛の判定（`fs_remove`）**: 上の 5 段で「前からあったか」を確かめます。自分が同じ呼び出しで作ったものなら誤で、`error_class` は `E2: 同じ呼び出しで mkstemp した一時ファイルを finally で消す（server.py:49,56）` のように、**作る行と消す行の両方**を書きます。前からあったものなら正で、書き込み先の種類を付けます（一時ファイルの掃除でも、前の呼び出しの残り物を消すなら、境界の例に従う。[第 51 章](ch51.md)）。
- **1 組に位置が複数あるとき**: v4 の M15 のように、`os.unlink` の位置が 4 つあって全部が E2 なら誤です。1 つでも前からあるものを消す位置があれば正です（手引きの手順 G）。誤にするときは全部の位置を読みます。
- **不の中身の判定（`fs_writeout`）**: キャッシュの毎回の書き直しは違反、毎回新しい名前は違反でない、読んで・足して・書き戻す形は決めた読み方で、と決めます。

（出典: `docs/drafts/final_judging_guide_draft.md:153-163`（手順 G）、`:176`（`error_class` の例）、`:403-415`（16.2 の境界の例））

#### この節のまとめ

D2 の迷いやすい形は「消すものが前からあったか」で決める。同じ呼び出しで自分が作った一時ファイル・ロックの削除は反しない（E2）。前の呼び出しの残り物の削除は反する。
キャッシュの毎回の書き直しと、atomic write の置き換え（書き先に前からファイルがあるとき）は反する。atomic write の失敗時の一時ファイルの削除は E2。
読んで・足して・書き戻す形は、文面どおりなら反するが、データの単位では足すだけとも読める。承認の前に確かめる候補。

### 50.7 D3 `openWorldHint: false` —「関わる範囲が閉じているか」（手引き 15.3 節）

#### 一言で言うと

D3 の問いは、「**そのツールは、外部の（そのマシンやローカルの網の外の）相手と通信するか、あるいはモデルが決める相手と通信しうるか**」です。
決め手は**宛先**で、メソッド（`GET` か `POST` か）は関係ありません。
定数の外部ホストと、モデルが決める宛先・コード・コマンドは反します。
手元の宛先と、ファイル・DB のローカルの操作は反しません。
**手元（local）の範囲**は、手引きと解析器でずれていて未決でしたが、**D73 の 2（2026-10-03）で決まりました**。手引き 15.3 は原理の規則 7' の全部に合わせ、ドットの無い名前（docker-compose のサービス名など）も local とみなします。

#### たとえ話 — マンションのインターホン

[第 10 章](ch10.md)で、網の範囲を「家の中・マンションの中・町の外」にたとえました。
D3 の宣言は、「**このマンションの中の人とだけ話します**」という約束です。

- 家の中の家族と話す（`127.0.0.1`、`localhost`）。かまいません。
- 同じマンションの別の部屋とインターホンで話す（手元の網の中の機械。`10.x`・`172.16.x`〜`172.31.x`・`192.168.x` など。部屋番号だけで呼べる隣の部屋、つまりドットの無い名前（`db`・`ollama` など）も含む）。かまいません。
- 町の外の会社に電話する（定数の外部ホスト）。だめです。
- 「誰にでも好きなところに電話していいよ」と、子ども（モデル）に電話を渡す（モデルが決める宛先）。実際にどこにかけるかに関係なく、**町の外にかけられる**こと自体が約束に反します（原理 3-a）。
- 管理人さんが決めた番号にかける（運用者の設定の宛先）。管理人さんがマンションの中の番号を決めたのか、外の番号を決めたのかで決まります。

D1 の「変えるか」とは、まったく別の物差しです。
電話で天気を聞くだけ（`GET`）でも、町の外にかければ D3 に反します。
逆に、マンションの中でなら、物を書き換えるお願い（`POST`）をしても D3 には反しません（D1・D2 の問題にはなりえます）。

#### 小さな例 — 手引きの D3 の表

手引きの 15.3 節の表を、そのまま載せます（D73 の 2 の後の版）。

| 動作 | 反するか |
|---|---|
| HTTP などの宛先が local（下の「local の範囲」） | 反しない |
| 宛先が local でもグローバルでもない IP（`100.64.0.0/10`、文書用・予約のアドレスなど） | 不明 |
| 宛先が定数の外部ホスト | 反する |

| `net_model_host` | 宛先のホストをモデルが選べる | 本当に選べるか（検証で手元に絞っていないか。その検証は抜けられないか） |

| `spawn_model` | 起動するコマンドをモデルが選べる | 本当に選べるか（`shlex.quote` の形は E7） |

表の読み方: 1 行目は「`net_external_host` の矛を判定するときは、定数のホストが本当に外部か（`host.docker.internal` のように手元を指す名前ではないか）と、その通信にツールの呼び出しで届くかを確かめる」と読みます。

ここから、2 つのことが言えます。

1. 手引きの表の「運用者の設定で決まる宛先」の行は、解析器が**不**（`net_host_unknown`）にする形です。本書の試験でも、3 つの書き方（`os.environ.get` の既定値、`or` の後の値、`if` で差し替える形）がすべて不でした。D3 の不は最終評価で判定しない（件数と理由だけ）ので、**この行を人が使う場面は、最終評価にはほとんどありません**。ただし、この行の考え方は、名前の宛先（下）を読むときにも使います。
2. 解析器が手元（local）と読む宛先（`172.20.0.5` など）は、内なので**人の目に触れません**。local の範囲の決め方（下）が判定に効くのは、主に、解析器が**外部と読んだ名前**（コンテナの中の名前、`host.docker.internal`）の矛を、人がどう読むかです。

この 2 点は、本書が `_d3` の関数と手引き・決定の対象の定めを突き合わせて導いたもので、手引きには書かれていません。

#### 迷いやすい形 1 — 宛先を検証してから送る（`local_fetch`）

```python
11  @mcp.tool(annotations=ToolAnnotations(openWorldHint=False))
12  def local_fetch(url: str) -> str:
13      if urlparse(url).hostname not in ("localhost", "127.0.0.1"):
14          raise ValueError("local only")
15      return requests.get(url).text
```

- 11〜12 行目: 閉じた範囲（`openWorldHint=False`）と宣言したツールで、モデルが `url` を渡します。
- 13 行目: Python の標準の `urlparse` で `url` のホスト名を取り出し、`localhost` か `127.0.0.1` でなければ、
- 14 行目: エラーにして止めます。
- 15 行目: 通れば、`requests` でその `url` に `GET` します。

解析器は、15 行を**矛**（`net_model_host`）にしました。
13〜14 行の検証は、D3 の判定では見ていません。

人が最初に読むと、「検証で手元に絞っているので、モデルは外部を選べない。だから反しない（誤）」と考えたくなります。
けれども、**検証が値を読む方法と、送る側が値を読む方法が同じか**を確かめる必要があります。
本書の執筆時に、作業用の場所で次を確かめました（Python 3.10.20、requests 2.32.3、urllib3 2.8.0）。

- `http://evil.example\@localhost/x`（`\` を含む URL）を `urlparse` で読むと、ホスト名は `localhost` でした。13 行の検証を**通ります**。
- 同じ URL を `requests` の要求として組み立てると、宛先は `evil.example` になりました（urllib3 も、ホストを `evil.example` と読みました）。

つまり、モデルは検証を抜けて、外部のホストに送れます。
原理 3-a（取りうる値の全体）で読むと、**反する**です。
解析器自身も、定数の URL に `\` が入っているときは「クライアントで読みが割れる」として宛先を読めないことにしています（`dparse.py` の注記）。
この例は、その読みの割れを、検証と送信の間で使ったものです。

この形の教訓は、「**検証があるから反しない、と即断しない**」です。
検証が本当にすべての値を手元に絞るかを確かめ、確かめられなければ「決められない」にします。
逆に、検証が確かに絞っている（たとえば、モデルにはポート番号の整数だけを渡させ、ホストは定数の `127.0.0.1` にする）なら、反しません。
そのとき解析器が矛を出していれば誤で、原因は E7（モデルが決められないのに決められるとした）か E8（宣言に反しない）か迷うところです。
手引きは「分類に迷ったら E9 にして説明を書く」と定めています。

（出典: 本書の試験（作例 `toy_d3b/server.py:11-15`、URL の読みの確かめ）、`authgap/dparse.py:330-332`（`\` の注記）、`docs/drafts/final_judging_guide_draft.md:441-445`（E7・E8・E9 と「迷ったら E9」））

v4 の木から、既定値の向きが違う 2 行を見ます（行の形だけを例に使います。これを使うツールが D3 を宣言しているかは、ここでは問いません）。

#### なぜそうするのか — D3 の行ごとの理由

- **宛先で決め、メソッドを問わない**: 仕様の原文は "the tool's domain of interaction is closed"（関わる範囲が閉じている）で、例に「web 検索のツールの世界は open、記憶のツールの世界は閉じている」を挙げています。web 検索は読むだけでも open です。だから「変えるか」ではなく「誰と関わるか」で決めます（原理 1-ii の理由と同じ、2 つの別の軸）。
- **モデルが決める宛先・コード・コマンドは反する**: 原理 3-a で、モデルが選べる値は取りうる値の全体で読みます。モデルが外部を選べるなら、閉じていません。
- **運用者の設定は既定値と文書で決める**: 運用者の設定の値は、コードからは分かりません。けれども既定値と文書は、そのツールがどこと関わるように作られたかを示します。人はそれを読んでよい、というのが手引きの考え方です。
- **ローカルの操作は反しない**: ファイルやローカルの DB は、そのマシンの中で閉じています（表 D41）。

#### よくある誤解・つまずき

- **誤解: 「D3 は `POST` のような変更のメソッドだけを見る」**
  宛先だけで決まります。定数の外部ホストへの `GET` も反します。
- **誤解: 「モデルが決めるのがパスだけでも、`net_model_host` の矛なら正」**
  解析器の理由が違っても、ホストが定数の外部なら反するので正です（理由ではなく動作で決める）。けれども、ホストが定数の手元で、モデルが決めるのがパスだけなら、反しません。その場合は誤です。
- **誤解: 「検証の `if` があるから、モデルは外部を選べない」**
  検証と送信で値の読み方が違えば、抜けられます（`local_fetch`）。確かめられなければ「決められない」です。
- **誤解: 「`host.docker.internal` は手元だから反しない」**
  手引きはこの名前を名指ししていません。どう読むかは未決です。決まるまでは、出会ったら不明にして「手引きで決まらない」と書きます。
- **つまずき: 「D3 の正に、書き込み先の種類を付ける？」**
  付けません。代わりに、**通信先の種類**（定数の外部ホスト / モデルが決める宛先 / モデルが決めるコード・コマンド / その他・不明）を付けます（D68 の 3。[第 51 章](ch51.md)）。

（出典: `docs/drafts/final_judging_guide_draft.md:53-54`、`:417-426`（16.3）、`docs/decisions.md:3809-3815`（D68 の 3））

#### 手作業ではどう使うか

- **矛の判定**: `net_external_host` なら、定数のホストを開いて、本当に外部かを確かめます（名前なら、同じ木の `docker-compose.yml` などで何を指すかも見ます。決まらない名前は不明）。`net_model_host`・`exec_model`・`spawn_model` なら、モデルが本当に選べるかを値の流れでたどり、検証があればその強さを確かめます。正なら、通信先の種類を `write_target` 欄に書きます。
- **到達**: 外部への通信が、設定（`if API_KEY:`）や失敗時の再試行の中だけにあることもあります。条件の種類を[第 49 章](ch49.md)の規則で書きます。
- **不（`net_host_unknown`・`spawn_command`）**: 最終評価では判定しません。件数と理由だけが集計に出ます。

#### この節のまとめ

D3 の問いは「外部の相手、またはモデルが決める相手と通信しうるか」。宛先で決まり、メソッドは関係ない。
定数の外部ホスト・モデルが決める宛先・コード・コマンドは反する。手元の宛先とローカルの操作は反しない。運用者の設定の宛先は既定値と文書で決める。
最終評価で人が D3 を判定するのは矛（4 つの理由）だけ。local の範囲は D73 の 2 で決まった（規則 7' の全部とドットの無い名前）。主に「外部と読まれた名前」の判定に効き、ドットの無い名前で出た解析器の矛は誤。`host.docker.internal` のような名前は表に名指しが無い。

### 50.8 D4 `idempotentHint: true` —「同じ引数で繰り返しても追加の効果が無いか」（手引き 15.4 節）

#### 一言で言うと

D4 の問いは、「**同じ引数で 2 回呼んだとき、2 回目が 1 回目の後の状態をさらに変えるか**」です。
D4 には**原理 3 を当てません**。
冪等（べきとう）は「同じ引数で繰り返したとき」の性質で、引数が取りうる値の範囲は関係しないからです。
定数の `'a'` の追記は、ふつう反します。
ただし、**書く前に内容を確かめ、すでにあれば書かない**追記と、`flock` のために `'a'` で開くだけの形は、反しません。

#### たとえ話 — 照明の「オン」ボタンと「切り替え」ボタン

部屋の照明に、2 種類のボタンがあるとします。

- 「**オン**」ボタン: 押すと照明がつきます。もう一度押しても、ついたままです。何回押しても結果は同じです。これが冪等です。
- 「**切り替え**」ボタン: 押すたびに、つく・消えるが入れ替わります。2 回押すと、1 回目の後の状態がさらに変わります。冪等ではありません。

ノートで言えば、こうなります。

- 「今日の天気: 晴れ」と、決まった欄に**書き直す**のは、何回やっても同じです（上書き。冪等）。
- 日記の最後に「晴れ」と**書き足す**のは、2 回やれば 2 行になります（追記。冪等ではない）。
- ただし、「まだ書いていなければ書き足す」と決めておけば、2 回目は何もしません（書く前に確かめる追記。冪等）。
- 「書いた時刻」まで書き直すなら、同じ欄でも 2 回目で時刻が変わります（時刻を含む書き込み。冪等ではない）。

D4 の判定は、このどれに当たるかを、コードで見分けることです。

#### 小さな例 — 手引きの D4 の表

手引きの 15.4 節の表を、そのまま載せます。

| 動作 | 反するか |
|---|---|
| 定数の `'a'` で追記する | 繰り返すと追記が重なるなら反する。**書く前に内容を確かめて、すでにあれば書かない**なら反しない（v4 の E00） |
| `flock` のために `'a'` で開くだけで書かない | 反しない（O41） |
| 上書き（`'w'`）・作成・削除 | 同じ引数なら同じ状態になるか、2 回目は失敗するので、ふつう反しない |
| DB の `INSERT` | 一意制約で 2 回目が失敗・無視されるなら反しない、行が増えるなら反する。スキーマを見て決める。見られなければ不明 |
| DB の `UPDATE` | `SET x = 1` なら反しない、`SET x = x + 1` や `NOW()` の記録なら反する |
| HTTP の `POST` / `PATCH` | 相手の API の意味で決める |
| 時刻・連番・乱数を含むものを書く（ログの 1 行、タイムスタンプつきのファイル名） | 反する（2 回目でさらに増える） |

表の読み方: 3 行目の「ふつう」に注意します。上書きは、同じ引数なら同じ中身になるので、ふつうは反しません。けれども、7 行目のように、書く中身に時刻・連番・乱数が入ると、同じ引数でも 2 回目に中身が変わります。そのときは 7 行目が先に当たり、反します。
4 行目は「`INSERT` は、同じ値の行を 2 つ入れさせない約束（一意制約）があれば、2 回目は失敗か無視で、状態が変わらない。約束が無ければ行が増える。どちらかはスキーマ（表の定義）を見て決め、見つからなければ決められない」と読みます。

（出典: `docs/drafts/final_judging_guide_draft.md:367-381`、`docs/final_evaluation_procedure.md:1045-1059`）

#### 一歩ずつ — なぜ D4 には原理 3 を当てないのか

原理 3-a は、「モデルが選べる値は、取りうる値の全体で読む」でした。
D2 では、モデルが書き先を選べれば、既存のファイルを指して上書きできるので反する、と読みました。

D4 で同じ読み方をすると、おかしなことになります。
作例で考えます。

```python
@mcp.tool(annotations=ToolAnnotations(destructiveHint=False, idempotentHint=True))
def write_file(path: str, content: str) -> str:
    with open(path, "w") as fh:
        fh.write(content)
    return "ok"
```

- 1 行目: 「壊さない」（D2）と「繰り返しても同じ」（D4）の両方を宣言したツールです。
- 2〜4 行目: モデルが決めた `path` に、モデルが決めた `content` を `'w'` で書きます。

**D2**: 書き先をモデルが決められるので、既存のファイルを指せば上書きできます。原理 3-a で**反します**。

**D4**: 問いは「**同じ引数で** 2 回呼んだら、2 回目がさらに変えるか」です。
同じ `path` と同じ `content` で 2 回呼べば、2 回目は同じ中身を同じ場所に書くだけで、状態は 1 回目の後と同じです。
モデルが「どんな値でも選べる」ことは、ここでは関係ありません。
繰り返しの間、引数は**同じ**だと決まっているからです。
だから**反しません**。

本書の試験でも、この作例に解析器は D2 の**矛**（`fs_writeout_model_path`）を出し、D4 には何も出しませんでした（内）。

判定表の導出の文書は、この点を「D4（idempotent）には原理 3 を当てない。冪等性は『同じ引数で』繰り返したときの性質なので、引数が取りうる値の範囲（能力）は関係しない」と書いています（§7.0 の 1）。
手引きの手順 F も「モデルが決める値は『取りうる値の全体』で考える（原理 3-a。D4 だけは除く）」と書いています。

#### 一歩ずつ — 最終評価で、人が D4 を判定するのはどこか

D3 と同じく、**D4 を人が判定するのは矛の判定だけ**です（見落としと不の中身は D1・D2 だけ）。
そして、解析器が D4 で**矛**を出すのは、`_d4` の関数を読むと、**`fs_append` の 1 つだけ**です。
`open` の仲間（`builtins.open`・`io.open`・`pathlib.Path.open`）で、開くモードの定数に `a` が入っているときです。

つまり、**最終評価の D4 の判定は、すべて「`'a'` で開く行」の判定**になります。
人がすることは、次の 3 つのどれかを見分けることです。

1. **毎回書き足す**（`remember`）→ 反する → 正。
2. **書く前に確かめ、あれば書かない**（`ignore_cache`、v4 の ccr の E00）→ 反しない → 誤、E8。
3. **開くだけで書かない**（`flock` のため。`locked_read`、v3 の O41）→ 反しない → 誤、E8。

手引きの表のほかの行（`INSERT`・`UPDATE`・`POST`・時刻を含む上書き）は、解析器が不か内にする形です。
D4 の不は件数と理由だけを報告し、D4 には見落としの判定がないので、**これらの行を人が使う場面は、最終評価にはありません**。
それでも、これらの行は D4 の問いの意味を定めるもので、上の 3 つを見分けるときの考え方の土台になります（たとえば、書く前に確かめる追記で、確かめる中身に時刻が入っていれば、確かめが空振りして毎回書き足すことになる）。

もう 1 つの帰結があります。
`stamp_state` や `snapshot` のような「解析器が内にする D4 の違反」は、最終評価では**数えられません**。
見落としの判定が D1・D2 だけだからです。
これは、最終評価の設計の範囲の話で、記録（O41〜O43）には挙がっていない本書の気づきです（50.11 節）。

#### 反しない例 — `flock` のために `'a'` で開くだけ

#### 表のほかの行の対 — `INSERT`・`UPDATE`・`PATCH`（問いの意味を確かめるために）

最終評価では判定の場面がありませんが、D4 の問いの意味をつかむために、表のほかの行も対で見ておきます（作例。DB の意味は[第 10 章](ch10.md) 10.6・10.7 節）。

```sql
-- INSERT の対
1  CREATE TABLE tags (name TEXT PRIMARY KEY);              -- name に一意制約がある表
2  INSERT OR IGNORE INTO tags (name) VALUES ('red');       -- (ア) 2 回目は無視される
3  CREATE TABLE events (id INTEGER PRIMARY KEY, name TEXT); -- name に一意制約が無い表
4  INSERT INTO events (name) VALUES ('red');               -- (イ) 2 回目で行が増える

-- UPDATE の 3 つの形
5  UPDATE settings SET enabled = 1 WHERE id = 7;           -- (ウ) その値にする
6  UPDATE counters SET n = n + 1 WHERE id = 7;             -- (エ) 今の値に足す
7  UPDATE sessions SET seen_at = NOW() WHERE id = 7;       -- (オ) 今の時刻を書く
```

- 1〜2 行目: `name` が主キー（同じ値の行を 2 つ入れられない）なので、`'red'` を 2 回入れようとしても、2 回目は `OR IGNORE` で無視されます。2 回目は状態を変えません。**反しない**。
- 3〜4 行目: `id` は自動で振られ、`name` には一意制約がありません。同じ `'red'` で 2 回呼べば、行が 2 つになります。**反する**。
- 5 行目: 2 回目も `enabled` は 1 のままです。**反しない**。
- 6 行目: 呼ぶたびに `n` が 1 増えます。**反する**。
- 7 行目: 呼ぶたびに、そのときの時刻が書かれます。**反する**（ただし、`WHERE ... AND seen_at IS NULL` のように 2 回目を空振りにする条件があれば、問いに戻ると反しないと読める。[第 10 章](ch10.md) 10.7 節の罠。50.11 節の候補 12）。

HTTP の `PATCH`（一部を変える）も、中身で同じように分かれます。
`{"status": "done"}` のように「その値にする」なら 2 回目は変えないので反しない側、「数を 1 増やす」「配列に 1 つ足す」のような指示なら 2 回目でさらに変わるので反する側です。
どちらの意味かは、相手の API の文書で決めます（手引きの「相手の API の意味で決める」）。

（作例。出典: `docs/drafts/final_judging_guide_draft.md:378-380`）

#### 一歩ずつ — `'a'` の矛を判定する 4 つの問い

D4 の `fs_append` の矛に出会ったら、次の 4 つを順に確かめます（本書の手順）。

1. **本当に `'a'` で開いているか。** モードの定数を開いて確かめます（`'a'`・`'ab'`・`'a+'` など）。
2. **開いたファイルに書いているか。** `with ... as fh:` の中に `fh.write(...)` があるか。`flock` だけなら書いていません。`'a+'` で開いて読むだけ、という形もありえます（何も書かなければ反しない）。
3. **書く前に、すでに書いたかを確かめているか。** 確かめの条件（`if X not in content:`）を読みます。確かめる中身と書く中身が一致しているかも見ます（たとえば、時刻つきの行を書くのに、時刻なしの文字列で確かめていると、確かめは毎回「無い」になり、毎回書き足します）。
4. **確かめの条件が、2 回目には必ず偽になるか。** 1 回目に書いたものが、2 回目の確かめで見つかるか。別の場所で消されたり、書く先と読む先が違ったりしないか。

1〜4 で「毎回書き足す」なら反する（正）、「2 回目は書かない」「書かない」なら反しない（誤、E8）、読み切れなければ「決められない」（不明）です。

#### なぜそうするのか — D4 の行ごとの理由

- **追記は、ふつう反する**: 2 回呼べば 2 回追記されることが、コードから確定するからです（§5 の #5）。
- **書く前に確かめる追記と `flock` は反しない**: 問いは「2 回目がさらに変えるか」です。2 回目が何も書かないなら、さらに変えていません。解析器は `'a'` のモードだけで矛にするので、この区別は人がします。
- **上書き・作成・削除はふつう反しない**: 上書きは同じ中身になり、作成は 2 回目に「もうある」で失敗するか何もせず、削除は 2 回目に「もう無い」です。
- **`INSERT`・`UPDATE`・`POST`・`PATCH` は中身で決める**: 一意制約の有無、`x = 1` か `x = x + 1` か、相手の API の意味で、冪等かどうかが変わります（[第 10 章](ch10.md) 10.6・10.7 節）。
- **時刻・連番・乱数を含む書き込みは反する**: 同じ引数でも、2 回目に書く中身や名前が変わるからです。

（出典: `docs/contradiction_principles.md:117-119`（§5 の #5）、`:218-229`（§7.4）、`docs/drafts/final_judging_guide_draft.md:373-381`）

#### よくある誤解・つまずき

- **誤解: 「D4 でも、モデルが選べる値は取りうる値の全体で読む」**
  D4 だけは当てません。同じ引数で繰り返すことが前提だからです。
- **誤解: 「`fs_append` の矛なら、いつも正」**
  書く前に確かめる追記と、`flock` のために開くだけの形は、誤（E8）です。
- **誤解: 「`'w'` の上書きは、D4 ではいつも反しない」**
  書く中身や名前に時刻・連番・乱数が入れば反します（`stamp_state`・`snapshot`）。解析器は内にするので、気づくのは人だけです（ただし最終評価では判定の場面がありません）。
- **誤解: 「`INSERT OR IGNORE` だから冪等」**
  `IGNORE` が効くのは、一意制約にぶつかったときだけです。一意制約が無ければ、行は増えます。スキーマを確かめます。また、主キーを呼び出しのたびに乱数で作る形は、一意制約があっても行が増えます（[第 10 章](ch10.md) 10.6 節の罠 1）。
- **つまずき: 「同じ引数で 2 回呼んでも、相手のデータが変わっていたら？」**
  D4 の問いは、ツールの 2 回目の呼び出しが状態を**さらに**変えるかです。間に別の誰かが状態を変えた場合のことは、手引きは書いていません。判定では、「間に何も起きない」として 2 回続けて呼んだときを考える、というのが本書の読み方です。

#### 手作業ではどう使うか

- **矛の判定**: D4 の矛は `fs_append` だけです。上の 4 つの問いで、毎回書き足すか・確かめるか・書かないかを決めます。反しないなら `error_class` に `E8: 書く前に .gitignore の中身を確かめ、あれば書かない（memory_file_io.py:82-84）` のように、**確かめの行と書く行**を書きます。
- **正の書き込み先の種類**: D4 の正にも書き込み先の種類を付けます（D1・D2・D4 に付ける）。毎回の追記なら、多くは「ログ」です（[第 51 章](ch51.md)）。
- **件数の見込み**: v4 では D4 の矛は 3 組（どれも ccr の `fs_append`）でした。最終評価は全部を走査するので、もっと集まる見込みですが、件数は測っていません（D69 の 1）。

（出典: `docs/drafts/final_judging_guide_draft.md:385-386`（書き込み先の種類は D1・D2・D4 に付ける）、`evidence/population_v4/contradiction_by_decl_v4_run1.md:14, 54`、`docs/decisions.md:3822-3825`（D69 の 1））

#### この節のまとめ

D4 の問いは「同じ引数で 2 回呼んだとき、2 回目がさらに変えるか」。原理 3 は当てない。
最終評価で人が判定する D4 は、解析器の `fs_append` の矛だけ。毎回の追記は正、書く前に確かめる追記と `flock` のための `'a'` は誤（E8）。

### 50.9 解析器の「不」を、人はどこまで決められるか — 宣言ごとの表

#### 一言で言うと

解析器の「不」は、「**コードだけを動かさずに読んでも決められない**」という意味で、「人にも決められない」ではありません（[第 17 章](ch17.md) 17.12 節）。
人は、不の理由ごとに決まった調べ方で、多くを「反する / 反しない」に決められます。
ただし、**手引きが先に「決められない」と決めている行**（D2 の DB に残る設定）と、**最終評価で判定しない宣言**（D3・D4 の不）があります。
この節では、それを宣言ごとの 1 枚の表にまとめます。

#### たとえ話 — 落とし物の「持ち主不明」の箱

駅の落とし物係には、機械が仕分けた「持ち主不明」の箱があります。
機械は、名札が読めない物を全部この箱に入れます。

係の人が箱を開けて、1 つずつ調べます。

- 定期入れなら、中の定期券の名前で持ち主が分かります（調べれば分かる）。
- 傘なら、名前が無ければ分かりません（調べても分からない）。
- 「この箱の物は持ち主を探さない」と規則で決まっている種類もあります（判定しない）。
- 中には、そもそも「持ち主」という考えが当てはまらない物もあります（駅の備品の一部が紛れ込んだ。問いが当てはまらない）。

解析器の「不」の箱も同じです。
理由ごとに、調べれば分かるもの・分からないもの・判定しないもの・問いが当てはまらないものがあります。

#### 一歩ずつ — 理由の群ごとの調べ方

不の理由は、調べ方で 5 つの群に分かれます（本書の分け方）。

**群 A: 相手の API を調べる**（`net_post`・`net_put`・`net_method_unknown`）
50.3 節の手順（[第 10 章](ch10.md) 10.4 節の 6 つの手順）で、相手の資源を作るか・変えるか・消すか・読むだけかを決めます。
宣言で答えが違うことに注意します。作成は、D1 では反し、D2 では反しません。
`net_method_unknown` は、まずメソッドを確かめます。呼び出し元から `"GET"` が渡されていれば、D1・D2 とも反しません。

**群 B: コマンドの中身を調べる**（`spawn_command`）
50.3 節の 5 段で、サブコマンド・オプション・スクリプト・文書を読みます。
D2 では、問いが「前からあるものを壊すか」になります。たとえば、新しいディレクトリを作るだけの `mkdir <新しい名前>` は D2 には反しない側、ファイルを消す `rm` や、作業中の変更を捨てる `git reset --hard` は反する側、と読めます（本書の読み方）。同じコマンドでも、D1 と D2 で答えが分かれることがあります。

**群 C: 書き先が前からありうるかを調べる**（`fs_writeout`・`fs_unknown`）
50.5 節の 4 つの問いで決めます。`fs_unknown` は、まず実際のモードを確かめます。

**群 D: 実行される SQL を読む**（`db_sql_unreadable`・`db_unknown_statement`・`db_sql_unsplittable`・`db_sql_model_opaque`）
SQL の文字列が、変数や関数の戻り値で組み立てられているときです。
組み立てに使う値を、取りうる値も含めてたどり、どんな文が実行されうるかを読みます。
変更の文（D1 なら `INSERT` も含む）がありうるなら反する、読み取りだけなら反しない、読み切れなければ不明です。

**群 E: 値の流れをたどる**（`…_opaque`）
「モデルの値が流れ込むが、モデルが選べるとまでは読み切れない」という不です（[第 17 章](ch17.md)、§9.3）。
値の流れを、モデルの引数から効果の slot（書き先・コマンド・宛先）まで、自分でたどります。
モデルが値を**選べる**（任意の書き先を指せる）と分かれば、原理 3-a で反します。
選べない（値は使われるが、書き先そのものは定数で決まる）と分かれば、`_opaque` を外した理由（`fs_writeout` など）の調べ方に移ります。
50.6 節の crypto-price-tracker は、解析器は `fs_writeout_model_path_opaque` にしましたが、人が読むと書き先は定数の `watchlist.json` で、群 C の調べ方に移る例でした。

#### 一歩ずつ — 人が調べても決められない典型

手引きの 19 節は、「不明」にしてよい典型を 4 つ挙げています。

1. 書き先・宛先・コマンドが、木の外のライブラリの戻り値や、実行時の外部の状態で決まり、読み切れない。
2. 相手の API（`POST` の先）の意味が、文書にもコードにも無い。
3. 起動の方法・初期化の場所が読み切れない（[第 49 章](ch49.md)）。
4. 動的な呼び出し（`getattr(obj, name)()`、プラグインの読み込み）で、呼び出し先が決まらない。

この章の例で言えば、v4 の R07（rails-lens の Ruby のスクリプトが手元に無い）は 1 に近く、`tag_add` の `INSERT OR IGNORE`（スキーマが見つからない）も、手引きの D4 の表が「見られなければ不明」と書く形です。
目安は、**20〜30 分調べても決められなければ不明**です。
調べれば分かるものを不明にしないこと、分からないものを黙って倒さないこと、の両方が約束です。

### 50.10 通しの例 — 1 つのツールを 3 つの宣言と 3 つの場面で

#### 一言で言うと

- **手順 F**: D3 の問い「外部の相手と通信するか」。宛先のホストは定数の `feeds.example.com` で、手元ではありません。モデルが決めるのはパスの `feed` だけです。表の「宛先が定数の外部ホスト」の行に当たり、**反する**。
- **判定**: **正**。通信先の種類は「定数の外部ホスト」（[第 51 章](ch51.md)）。
- **記録の例**: `evidence`: `server.py:15 requests.get("https://feeds.example.com/" + feed)`。ホストは定数の feeds.example.com（外部）。モデルが決めるのはパスだけ。本体で毎回届く。

#### 場面 2 — 矛の判定: D4 × `builtins.open`（18 行）

- **手順 C**: 18 行は `open(LOG_FILE, "a")` で、19 行で 1 行書きます。本当の追記です。
- **手順 D・E**: 毎回届きます。到達は `はい`、条件の種類は `なし`。
- **手順 F**: D4 の問い「同じ引数で 2 回呼んだとき、2 回目がさらに変えるか」。50.8 節の 4 つの問いで確かめます。
  1. 本当に `'a'` か → はい。
  2. 書いているか → はい（19 行）。
  3. 書く前に確かめているか → いいえ。
  4. （3 が「いいえ」なので不要。）
  しかも、書く中身に**時刻**（`time.time()`）が入っています。同じ `feed` で 2 回呼べば、時刻の違う行が 2 行になります。**反する**。
- **判定**: **正**。書き込み先の種類は、記録のためだけに書き、木の中で読み返していなければ「ログ」です（`LOG_FILE` を grep して、読む行が無いことを確かめます。[第 51 章](ch51.md)）。
- **記録の例**: `evidence`: `server.py:18-19 open(LOG_FILE, "a") で f"{time.time()} {feed}\n" を追記`。書く前の確かめは無い。同じ feed で 2 回呼ぶと 2 行になる。`LOG_FILE` を読む行は木に無い（grep で確かめた）。

#### 場面 3 — 見落としの判定: D2

このツールは D2 を明示していて、D2 の**矛は 1 件もありません**（16 行は不、ほかは内）。
だから、見落としの判定の対象になりえます（抜き取りで選ばれれば）。
見落としの判定は、**解析器の出力を見る前に**本体を読みます（手引き 18.2 節）。

1. 本体（14〜23 行）を読み、D2 の問い（前からあったものを消す・上書きする・変えるか）に反しうる動作を書き出します。

| 行 | 動作 | D2 | 理由 |
|---|---|---|---|
| 15 | 外部への `GET` | 反しない | 相手の資源を読むだけ |
| 16 | 定数の `CACHE_FILE` への `'w'` | **反する** | 毎回同じファイルを書き直し、消す行も無い。2 回目からは前の呼び出しの内容を上書きする（50.5 節の 4 つの問い） |
| 18 | `LOG_FILE` への `'a'` | 反しない | 末尾に足すだけ |
| 21 | `INSERT OR IGNORE` | 反しない | 行を足すか、何もしない。既存の行を変えない（`INSERT OR REPLACE` とは違う） |

   表の読み方: 2 行目は「16 行の `'w'` は、定数の `CACHE_FILE` を毎回書き直し、消す行も無いので、2 回目の呼び出しからは前の呼び出しが書いた内容を上書きする。だから D2 に反しうる動作として書き出す」と読みます。ほかの 3 行は「反しない」なので、書き出したうえで「反しない」と理由を添えておけば、読んだ範囲の記録にもなります。

2. ここで初めて解析器の出力を見ます。16 行に `contradiction_unknown:D2:fs_writeout` があります。
3. 書き出した「反する動作」（16 行）に、解析器は**不**を出しているので、結果は「**解析器が不として出している**」です（見落としではありません）。
4. 書き込み先の種類は、別のツール `cached_feed`（28 行）が読み返すので「キャッシュ・状態の保存」です。条件の種類は `なし`。

（見落としの判定の手順と結果の 5 つは、[第 52 章](ch52.md)で詳しく扱います。）

#### 判定しない場面 — D4 の不（21 行）と、D3 の内

21 行の `INSERT OR IGNORE` は、D4 で不（`db_nonidempotent_statement`）でした。
人が読むと、`feeds` 表の `name` に一意制約があれば 2 回目は無視されて反しない、無ければ行が増えて反する、です。
けれども、D4 の不は最終評価で判定しないので、この点を決める場面はありません（50.8・50.9 節）。

16 行の `'w'` は、D4 では内でした。
同じ `feed` で 2 回呼んだとき、相手のフィードの中身が変わっていなければ同じ中身を書くだけで、反しません。
この点も、判定の場面はありません。

#### なぜそうするのか — 宣言ごとに分ける理由

この例では、16 行の `'w'` が、D2 では反し、D4 では反しません。
18 行の `'a'` は、D2 では反さず、D4 では反します。
同じ行の答えが宣言で入れ替わるので、宣言をまとめて「このツールは違反か」と問うと、答えが混ざってしまいます。
D62 は、D1〜D4 を宣言ごとに報告し、合算しないと決めました。
判定も、宣言ごとの組で、その宣言の問いだけに答えます。

（出典: `docs/contradiction_principles.md:141`（D62 の改訂）、`docs/decisions.md:3836-3848`（D70 の 1: 宣言ごとに抜き取る））

#### よくある誤解・つまずき

- **誤解: 「同じツールなら、D3 が正なら D4 も正」**
  宣言ごとに別の組で、別の問いです。答えは独立です。
- **誤解: 「D4 の組の位置に 16 行も入るはず（同じ `open`）」**
  位置は矛の行だけです。16 行は D4 では内なので、D4 の組には入りません。
- **誤解: 「D2 の見落としの判定で、16 行は解析器が不を出しているから、見落としではない。だから書き出さなくてよい」**
  書き出すのは、解析器の出力を見る**前**です。書き出した後に出力を見て、「解析器が不として出している」に分類します。順序を守ることで、先入観を避けます。

#### 手作業ではどう使うか

実際の判定表では、この 2 つの矛の組は、別々の行として、無作為の順序で出てきます。
同じツールの組が続けて出るとは限りません。
それぞれの行を開いたときに、その行の `decl` の問いだけに答えます。
前に同じツールの別の宣言を判定していても、その答えを持ち込みません。

#### この節のまとめ

1 つのツールが複数の宣言を持てば、組は宣言ごとに分かれ、答えも宣言ごとに独立。同じ行が D2 では反し D4 では反しない（`'w'`）、その逆（`'a'`）もある。
矛の判定は D3・D4 の組、見落としの判定は D2 で、それぞれの問いと手順で答える。
D4 の不（`INSERT OR IGNORE`）は判定しない。

### 50.11 手引きに書かれていない境目 — 封の前に決めておく候補

#### 一言で言うと

この章を書きながら、手引きの第 15 節の文面だけでは答えが 1 つに決まらない形が、いくつか見つかりました。
これらは、本書の気づきで、`docs/decisions.md` や `docs/open_questions.md` に「決めること」として記録されているものではありません（本書の執筆時に 2 つの文書を検索して確かめました）。1 つ目の local の範囲だけは、[第 10 章](ch10.md)で見つけ、[第 46 章](ch46.md)の「まだ決まっていないこと」の一覧に**未決**として載せています。
**決めるのは学生です。**
本書はどちらかに倒さず、候補として並べます。
判定の途中で、決まっていない形に出会ったら、手引きの 22 節に従って「不明」にし、「手引きで決まらない: …」と書きます。

#### たとえ話 — 試合の前のルールの確認

サッカーの試合の前に、審判団が集まって「こういう場面はどう判定するか」を確かめ合うことがあります。

試合の途中で決めると、前半と後半で判定が変わってしまうからです。
この節は、その「試合の前の確認」の材料です。

#### 一歩ずつ — 決めるときの考え方

候補を決めるときに、本書が役に立つと考える問いを 3 つ挙げます（決めるのは学生です）。

- **誤解: 「『最終評価で出る場面: なし』なら、気にしなくてよい」**

- **封の前**: この一覧を手引きの「承認の前に学生が確かめること」と並べて読み、決めた項目は手引きの第 15 節に書き足します（決めた理由も `docs/decisions.md` に）。

- **集計**: 「手引きで決まらない」の件数と中身を、不明の内訳として報告します（手引き 19 節）。

手引きの文面だけでは答えが割れる形が、少なくとも 12 ある（本書の気づき。local の範囲は[第 46 章](ch46.md)の未決の一覧にも載せ、D73 の 2 で大部分が決まった）。

<a id="s50-14"></a>
### この章のまとめ

- 手順 F（宣言に反するか）は、宣言ごとの**問い**に答えること。表はよく出る形の答えを先に書いたもので、表に無い形は問いに戻って決める。答えは `はい` / `いいえ` / `決められない` で、`violates` 欄に書く。
- 答え方は 5 段: 宣言を確かめる → 動作をコードで決める → 表の行を引く → 「調べて決める」行なら調べる → 問いに戻って確かめる。モデルが決める値は取りうる値の全体で考える（D4 だけ除く）。
- **D1**（呼び出しの後に残る何かを変えるか）: ファイルの書き込み・作成・削除はすべて反し、DB の変更と残る設定、`PUT`・`PATCH`・`DELETE` も反する。読み取り・`GET`・接続単位の設定は反しない。`POST` は相手の API の意味、定数のコマンドはその中身を調べて決める。
- **D1 の迷いやすい形**: 標準出力・標準エラーのログと `ctx` の通知は反しない。ログの出力先がファイルなら反する（5 点で確かめる）。子の標準入力は子が何をするかで決める（`sort` なら E5、`tee` なら正）。
- **D2**（呼び出しの前からあったものを消す・上書きする・変えるか）: 追記・作成・`INSERT`・`GET` は反しない。削除・移動・`UPDATE`・`DELETE`・`PATCH` は反する。書き出しは、モデルが書き先を決める・毎回同じファイルなら反し、毎回新しい名前・無いときだけ書くなら反しない。`POST` は作成なら反せず、更新・削除なら反する。DB に残る設定は決められない。
- **D2 の迷いやすい形**: 同じ呼び出しで自分が作った一時ファイル・ロックの削除は反しない（E2）。前の呼び出しの残り物の削除、キャッシュの書き直し、atomic write の置き換え（前からある書き先）は反する。
- **D3**（外部の、またはモデルが決める相手と通信しうるか）: 宛先で決まる。定数の外部ホストとモデルが決める宛先・コード・コマンドは反する。運用者の設定の宛先は既定値と文書で決める。local の範囲は D73 の 2 で決まった（規則 7' の全部とドットの無い名前。前は未決）。
- **D4**（同じ引数で 2 回呼んだとき、2 回目がさらに変えるか）: 原理 3 を当てない。毎回の追記は反し、書く前に確かめる追記と `flock` のための `'a'` は反しない（E8）。時刻・連番・乱数を含む書き込みは反する。
- 最終評価で人が判定するのは、D1・D2 の矛・不の中身・見落としと、**D3・D4 の矛だけ**。D3 の矛は 4 つの理由、D4 の矛は `fs_append` だけ。D3・D4 の不は件数と理由だけ。
- 解析器の「不」は、理由ごとの調べ方（API・コマンド・書き先・SQL・値の流れ）で人が決める。20〜30 分調べても決められなければ不明。D2 の DB に残る設定は、手引きが先に不明と決めている。
- 手引きの文面だけでは割れる形が少なくとも 12 ある（本書の気づき）。決めるのは学生で、データを見る前に決めて手引きに書く。決めないなら「不明（手引きで決まらない）」にする。
- この章の作例の答えは、手引きの規則を当てた本書の考え方の例。v4 の例は本記録者（AI）の判定で、正解ではなく、v4 の数字は論文に使わない。最終評価の判定は学生 1 人で、AI は使わない。
