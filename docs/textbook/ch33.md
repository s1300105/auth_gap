### 33.1 最初の凍結 — D59 が先に決めた「凍結の条件」

#### 一言で言うと

D59 は、直し方の規則と一緒に「凍結の条件」を**先に**書いていました。
「v2 は開発用。直し終えたら凍結し、評価は凍結後の v3 で行う。凍結後に見つけた欠陥は直さず、限界として記録する」。
その条件どおり、run18 で D59 を終えた時点で、解析器を凍結しました（`analyzer-freeze-1`）。

#### たとえ話 — 入稿した原稿

本を出すとき、著者は原稿を何度も直します。
けれども、印刷所に**入稿**したら、もう本文は直しません。
入稿の後で誤字を見つけたら、本文を刷り直すのではなく、「正誤表」を別に付けます。
こうすると、「どの版の本に何が書いてあるか」がはっきりし、読者は自分の持っている本が入稿した原稿どおりだと信じられます。

解析器の凍結は、この入稿にあたります。
凍結の後に見つけた誤りは、解析器を直すのではなく、`docs/open_questions.md` に「既知の限界」（正誤表）として書きます。

ただし、この章の後半で見るとおり、最初の凍結は「本当の入稿」ではなくなりました。
評価の方針が変わり、「ゲラ刷り（校正用の試し刷り）」の位置づけに変わったのです。

#### 小さな例 — D59 の「凍結の条件」

D59 の規則の冒頭に、次の段落があります（実装より先、11 時 21 分にコミット）。

> **凍結の条件（先に決めておく）**
> 母集団 v2 は誤りを探すのに何度も使ったので開発用のデータであり、主張の評価には使わない。評価は凍結後の母集団 v3 で行う。D59 の実装・取り直し・消えた行の確認を終えた時点で解析器を凍結する。凍結後に見つかった欠陥は直さず、既知の限界として記録する（直すなら `docs/preregistration.md` に逸脱として書き、v3 の結果は凍結時の解析器のものを主とする）。

（出典: `docs/decisions.md:3290-3295`）

#### 一歩ずつの説明 — 条件の 1 文ずつ

1. **「母集団 v2 は誤りを探すのに何度も使ったので開発用のデータであり、主張の評価には使わない」**
   v2 は、run13 から run18 まで、解析器の誤りを探すために何度も走らせ、原ソースと突き合わせてきました（第 27〜32 章）。誤りを見つけるたびに直したので、解析器は v2 に合わせて育っています。そのデータで「解析器はこれだけ当たる」と言えば、甘い評価になります（[第 25 章](ch25.md) 25.1 節）。
2. **「評価は凍結後の母集団 v3 で行う」**
   v3 は、まだ誰も見ていない新しい標本です。凍結した解析器を v3 に当てれば、「育てたデータ」ではない所での成績が分かる、という計画でした。
3. **「D59 の実装・取り直し・消えた行の確認を終えた時点で解析器を凍結する」**
   いつ凍結するかを、作業の前に決めています。「結果がよくなったら凍結しよう」のように、結果を見て凍結の時期を選ばないためです。
4. **「凍結後に見つかった欠陥は直さず、既知の限界として記録する」**
   これが入稿の約束です。評価のデータ（v3）を見た後に解析器を直すと、評価のデータに合わせて解析器を育てることになるからです。
5. **「直すなら `docs/preregistration.md` に逸脱として書き、v3 の結果は凍結時の解析器のものを主とする」**
   どうしても直す場合の決まりも、先に書いています。直したことを隠さず記録し、主の結果は直す前の版で出す、という決まりです（[第 22 章](ch22.md)の逸脱の記録）。

#### 一歩ずつの説明 — 凍結までの作業と、凍結の中身

D59 の結果の記録は、凍結を次のように書いています。

> 上の run18 で D59 を終えたので、D59 の凍結の条件どおり解析器を凍結する。`docs/fingerprint.json` に `fingerprint()`・`authgap/` の全ファイルの sha256・commit を書いた（`scripts/freeze_analyzer.py`）。タグは学生が打つ。

凍結は、次の 3 つでできています。

| 凍結の中身 | 何をしたか | いつ（UTC） |
|---|---|---|
| ① 記録を書く | `scripts/freeze_analyzer.py` で `docs/fingerprint.json` を書いた（33.2 節） | 2026-09-24 12:22（`1bcace3`） |
| ② コミットする | ①の記録を git にコミットした | 同上 |
| ③ タグを打つ | 学生が GitHub の Release 画面で `analyzer-freeze-1` を作った（33.3 節） | 13:01 に記録（`f88c33b`） |

表の読み方: 1 行目は「凍結の 1 つ目の作業として、12 時 22 分に、解析器の指紋を `docs/fingerprint.json` に書いた。そのコミットが `1bcace3`」と読みます。

仕様書は、凍結を「**コミットしてタグを打つこと**」と定義しています（月 10 の「解析指紋」の項）。
同じ項は、「凍結後の実行は指紋を evidence に書き、不一致は held-out 結果を無効にする」とも書いています。
held-out（ホールドアウト）とは、開発に使わずに取っておいた、評価のためのデータのことです。
つまり、凍結の目的は「評価のデータを、凍結した版と同じ解析器で測ったことを、後から誰でも確かめられるようにする」ことです。

#### なぜそうするのか — 凍結の時期と条件を先に決める

[第 22 章](ch22.md)で見た「先に決めて、後から変えない」の当てはめです。

- **凍結の時期を先に決める**: 結果を見ながら「ここで止めよう」と決めると、都合のよい時点で止めることになりかねません。D59 は、作業の前に「D59 を終えた時点」と決めました。
- **凍結後の扱いを先に決める**: 凍結の後に誤りを見つけたとき、直したくなるのは自然です。そのときに迷わないよう、「直さず限界に書く」「直すなら逸脱として書き、主の結果は直す前の版」と先に決めました。

この「先に決める」が、次の 33.4 節で、方針が変わったときにも役に立ちます。
D60 は、D59 の条件を**黙って**破ったのではなく、「D59 の凍結の条件を変える。理由を先に書く」と、記録の上で変えたからです。

#### よくある誤解・つまずき

- **誤解: 「凍結したのは、解析器が正しいと分かったから」**
  違います。凍結は「この版から変えない」という約束で、「正しい」という保証ではありません（[第 13 章](ch13.md) 13.12 節）。D59 の結果は、凍結の時点で残した限界（O35・O38・O39 など）を、凍結の記録と一緒に書いています。
- **誤解: 「凍結の後に見つけた誤りは、隠しておく」**
  隠しません。`docs/open_questions.md` に既知の限界として書き、論文の限界の節に載せます。直さないことと、隠すことは違います。
- **つまずき: 「凍結したのに、この後も解析器を直している」**
  そのとおりです。直後の D60 で、`analyzer-freeze-1` は「中間の区切り」に変わり、v3 で見つけた欠陥は直してよいことになりました（33.4 節）。最後の凍結は `analyzer-freeze-3` です（[第 36 章](ch36.md)）。

#### 手作業ではどう使うか

- 最終評価に使う解析器は、`analyzer-freeze-1` ではなく **`analyzer-freeze-3`** です（第 22・36 章）。`analyzer-freeze-1` は、v3 の走査に使った版として記録に出てきます。
- 最終評価の手順書は、「最終評価のどの段階でも `authgap/` を変えない」と書いています。これは、D59 が最初に決めた「凍結後は直さない」が、最終評価で文字どおりに当てはめられた形です。判定の途中で解析器の誤りを見つけても、直さずに `docs/open_questions.md` に書きます（手引きの下書き 22 節）。

（出典: `docs/final_evaluation_procedure.md:13`、`docs/drafts/final_judging_guide_draft.md:672`）

### 33.2 凍結の記録 — `docs/fingerprint.json` と、全ファイルの sha256

#### 一言で言うと

凍結の記録には、仕様書が決めた指紋（sink 表などの sha256）だけでなく、**解析器（`authgap/`）の全ファイルの sha256** と、それをまとめた**結合 sha256** を入れました。
仕様書どおりの指紋は、sink 表の「slot の名前」しか見ないので、D59 の追記のような「引数の読み方」の変更を見分けられないからです。

#### 言葉の確認 — 仕様書の指紋と、実装の指紋

- **仕様書の指紋**（`fingerprint()` の `sha256` の欄）
  - やさしい言い換え: 解析器の「一覧表」の部分だけを要約した番号。
  - 正確な定義: `authgap/report.py` の `fingerprint()` が作る値。sink 表・入口の規則・ゲートの語彙・執行表を、決まった形の JSON に直して sha256 を計算したもの（`sink_table`・`entry_catalog`・`gate_vocabulary`・`enforcement_table` の 4 つ）。仕様書の月 10 の「解析指紋」にあたる。
  - 例: `sink_table` の値は、凍結版で `48554b6446c2…`。
- **実装の指紋**（`implementation_sha256` と `implementation_sha256_combined`）
  - やさしい言い換え: 解析器の**プログラムの全ファイル**を要約した番号。
  - 正確な定義: `authgap/` の下の全 `.py` ファイルの、ファイルごとの sha256（`implementation_sha256`）と、その一覧を決まった形の JSON に直してもう一度 sha256 を計算した値（`implementation_sha256_combined`）。
  - 例: `analyzer-freeze-1` の結合 sha256 は `f2c2bf9e…`、`analyzer-freeze-3` は `35606ba9…`。

#### たとえ話 — 本の目次と本文

2 冊の本が同じ版かを確かめたいとします。
目次だけを比べると、章の名前が同じなら「同じ」に見えます。
けれども、本文の 1 行が書き換わっていても、目次は変わりません。
本文の誤字の直しは、目次を比べても分からないのです。

仕様書の指紋は、この「目次」にあたります。
sink 表に「どの関数が、どの名前の slot を持つか」は見ますが、「その slot の値を、どの引数から読むか」は見ていません。
だから、本文（実装）まで比べる指紋が要ったのです。

#### 小さな例 — 本書の執筆時に計算して確かめたこと

本書の執筆時に、D59 の 2 つの実装のコミットから `authgap/` を取り出し、両方の指紋を計算しました。

| コミット | 中身 | 仕様書の指紋 `sink_table` | `sinks.py` の sha256 | 結合 sha256 |
|---|---|---|---|---|
| `3086043` | O36・O37 の実装（`url=` の追記の前） | `48554b6446c2…` | `7de0547176ce…` | `0655262dfc93…` |
| `90ef6dd` | 追記の実装（`url=` を読む。凍結した版） | `48554b6446c2…`（**同じ**） | `27db3ebf1ef6…`（違う） | `f2c2bf9edeb8…`（違う） |

表の読み方: 2 行目は「`url=` を読むように sink 表を直した版でも、仕様書の指紋 `sink_table` は直す前と同じ `48554b…` だった。けれども、`sinks.py` というファイルの sha256 と、解析器全体の結合 sha256 は変わった」と読みます。

2 つのコミットの差は、`authgap/catalog/sinks.py` の 15 行だけです（`git diff 3086043 90ef6dd -- authgap/` で確かめた）。
たとえば、`requests.request` の行が、次のように変わりました。

```python
- SinkRow("requests.request", "NET", {"url.host": A(1), "body": HTTP_BODY}),
+ SinkRow("requests.request", "NET", {"url.host": A(1, kw="url"), "body": HTTP_BODY}),
```

- 1 行目（`-` の行）: 直す前。宛先 `url.host` を、位置の 2 つ目（`A(1)`）からだけ読む。
- 2 行目（`+` の行）: 直した後。位置に無ければ、キーワード `url=` からも読む（`A(1, kw="url")`）。

[第 32 章](ch32.md) 32.5 節で見たとおり、この直しで、宛先の無い NET の効果は 1,693 件から 6 件になりました。
解析器の振る舞いは大きく変わったのに、仕様書の指紋は 1 文字も変わらなかったのです。

（出典: `git archive 3086043 authgap`・`git archive 90ef6dd authgap` で取り出し、`authgap.report.fingerprint()` と全ファイルの sha256 を本書の執筆時に計算した。`git diff 3086043 90ef6dd --stat -- authgap/`（`sinks.py` の 15 行の変更だけ））

#### 一歩ずつの説明 — なぜ仕様書の指紋は変わらなかったのか

仕様書の指紋を作る関数の、sink 表の部分です。

```python
57      sink_blob = canonical_json(
58          {
59              "slots": {k: list(v) for k, v in sorted(SLOTS.items())},
60              "sub_kinds": {k: list(v) for k, v in sorted(SUB_KINDS.items())},
```

- 57 行: `sink_blob` という、sink 表を要約した文字列を作ります。`canonical_json` は、同じ中身なら必ず同じ文字列になるように、決まった順序と形で JSON を書く関数です。
- 59 行: slot の種類の一覧（kind ごとに、どの名前の slot があるか）を入れます。
- 60 行: 副 kind の一覧を入れます。

だから、`url.host` の読み方を変えても、`url.host` という名前が同じなら、`sink_blob` は同じ文字列になり、sha256 も同じになります。
D59 の本体（O37）で `body ← data=` を `body ← data|json` に変えた所も、`body` という名前の slot が前からあった行では、同じ理由で指紋に出ません。

#### なぜそうするのか

1. **凍結の目的は「同じ解析器で測ったこと」を確かめられること。** 指紋が変わらないのに中身が変わりうるなら、指紋を照合しても「同じ解析器」とは言えません。全ファイルの sha256 なら、1 文字の変更でも値が変わります。
2. **仕様書の指紋も残す。** 仕様書の指紋は仕様書が決めたものなので、消さずに残しました。実装の指紋は、それに**足した**ものです。仕様書と実際が食い違うときは、両方を記録するのがこの repo の規則です（CLAUDE.md 規則 6）。
3. **見つけたのは、自分の直しからだった。** D59 の追記は、まさに「指紋に出ない変更」でした。自分のした変更が既存の指紋に出ないことに気づいたので、凍結の記録の作り方を強めました。

#### よくある誤解・つまずき

- **誤解: 「指紋が一致すれば、解析器は正しい」**
  指紋の一致が保証するのは、「凍結した版と**同じ**」ことだけです。凍結した版に誤りがあれば、その誤りも同じです。
- **誤解: 「`sink_table` の指紋が同じなら、sink 表は同じ」**
  slot の名前と kind が同じなら、引数の読み方が変わっていても同じ値になります。sink 表のファイルが同じかは、`implementation_sha256` の `authgap/catalog/sinks.py` の値で確かめます。
- **つまずき: 「`implementation_sha256` は 26 ファイルなのに、[第 22 章](ch22.md)では 27 ファイルと書いてある」**
  [第 22 章](ch22.md)の 27 は `analyzer-freeze-3` の記録の数です。最初の凍結の後に `authgap/entry_seed.py` が足されたので、1 つ増えています。

#### 手作業ではどう使うか

最終評価の走査（手順書の段階 5）の前に、解析器が凍結版と同じかを確かめます。
そのときに照合するのは、**結合 sha256**（`35606ba9…`）です。
`scripts/scan_v2.py` を `--require-fingerprint docs/fingerprint.json` を付けて走らせると、今の `authgap/` から計算した結合 sha256 が記録と違うとき、または未コミットの変更があるときに、走査が止まります（[第 22 章](ch22.md) 22.3 節）。
この仕組みの土台が、最初の凍結で入れた「全ファイルの sha256」です。

（出典: `docs/final_evaluation_procedure.md:621-628`（9.1 の確認）、`docs/population_v4.md:66-67`（v4 の走査の前に確かめた例））

#### この節のまとめ

最初の凍結の記録には、仕様書の指紋（sink 表など 4 つ）に加えて、`authgap/` の全ファイルの sha256 と結合 sha256 を入れた。
仕様書の指紋は sink 表の slot の名前しか見ないので、`url=` の追記（`A(1)` → `A(1, kw="url")`）では `sink_table` が変わらず、ファイルの sha256 と結合 sha256 だけが変わった（本書の執筆時に確かめた）。
最終評価の前の照合も、結合 sha256 で行う。

### 33.3 タグ — 学生が打った名札

#### 一言で言うと

凍結の記録をコミットした `1bcace3` に、学生が GitHub の Release 画面でタグ `analyzer-freeze-1` を付けました。
本記録者の作業環境からはタグを GitHub に送れなかったうえに、この repo には「タグは人が打つ」という決まりがあります。

#### 言葉の確認 — タグ・軽量タグ

- **タグ**（[第 22 章](ch22.md)で見た言葉）
  - やさしい言い換え: 特定のコミットに付けた名札。
  - 正確な定義: git で、ある 1 つのコミットを名前で指せるようにしたもの。`git tag -l` で一覧を、`git rev-parse <タグ>` で指すコミットを見られる。
  - 例: `analyzer-freeze-1` は `1bcace3` を指す。
- **軽量タグ**
  - やさしい言い換え: 名前だけの名札。誰がいつ付けたかのメモは付かない。
  - 正確な定義: git のタグの 2 つの種類のうち、コミットを指す名前だけのもの。もう 1 つの**注釈つきタグ**（`git tag -a`）は、付けた人・日時・説明の文を持つ別の物（タグのオブジェクト）を作る。
  - 例: `git cat-file -t analyzer-freeze-1` は `commit` を返す（タグのオブジェクトではなく、直接コミットを指している）ので、軽量タグ。

#### たとえ話 — 本の帯は出版社が付ける

本の原稿を書くのは著者ですが、「初版」「第 2 刷」の帯を付けて世に出すのは出版社です。
著者が自分で帯を付けて回ると、どの原稿が正式に出たものなのか、外から分かりにくくなります。

この repo でも、解析器を作って凍結の記録を書くのは本記録者ですが、「これを凍結の版とする」というタグを付けるのは学生です。
研究の責任者が、正式な版に印を付ける形です。

#### 小さな例 — タグを確かめるコマンド

本書の執筆時に、次のコマンドで `analyzer-freeze-1` を確かめました。

```bash
git rev-parse analyzer-freeze-1          # → 1bcace3678c8415328a12ec03a904a6954b6d5be
git cat-file -t analyzer-freeze-1        # → commit
git show --stat 1bcace3                  # → docs/fingerprint.json | 63 ++++
```

行ごとに見ます。

- 1 行目: タグ `analyzer-freeze-1` が指すコミットの番号を出します。`1bcace3…` でした。
- 2 行目: タグの名前が指している物の種類を出します。`commit` なので、注釈つきタグのオブジェクトを経ずに、直接コミットを指す軽量タグです。D59 の記録の「軽量タグ」と合います。
- 3 行目: そのコミットで変わったファイルを出します。`docs/fingerprint.json` が 63 行足されただけでした。つまり、このコミットは凍結の記録を足すだけのコミットです。

（出典: 本書の執筆時に実行した。`docs/decisions.md:3388-3390`（タグ））

#### 一歩ずつの説明 — タグのコミットと、記録の中のコミットが違う理由

D59 の記録は、次のように書いています。

> `analyzer-freeze-1` は `1bcace3` を指す（学生が GitHub の Release 画面で作成。軽量タグ）。`docs/fingerprint.json` の `git_commit` は `2562293` だが、両者の差は `docs/fingerprint.json` の追加だけで、`authgap/` は同一（`freeze.analyzer_commit` = `90ef6dd`、結合 sha256 `f2c2bf9e…`）。

3 つのコミットが出てくるので、順に整理します。

| コミット | 時刻（UTC） | 何のコミットか |
|---|---|---|
| `90ef6dd` | 12:07 | `authgap/` を最後に変えたコミット（D59 の追記の実装）。凍結した解析器の中身はこれ |
| `2562293` | 12:22 | D59 の結果（run18）と逸脱 #22 の記録。`authgap/` は変えていない |
| `1bcace3` | 12:22 | 凍結の記録 `docs/fingerprint.json` を足したコミット。**タグはここを指す** |

表の読み方: 2 行目は「`2562293` は記録の文書だけを変えたコミットで、解析器の中身は `90ef6dd` と同じ」と読みます。

凍結の記録を書くスクリプトは、書いた時点の HEAD（今いるコミット）を `git_commit` に書きます。
記録を書いたとき、HEAD は `2562293` でした。
その記録をコミットしたのが `1bcace3` なので、記録の中の `git_commit`（`2562293`）と、記録を含むコミット（`1bcace3`）が 1 つずれるのです。
ファイルは、自分を含むコミットの番号を、書く時点では知りえません。
だから、このずれは仕組みの上で避けられないもので、誤りではありません。

大事なのは、`authgap/` の中身がどれも同じことです。
`freeze.analyzer_commit` の `90ef6dd` は、「`authgap/` を最後に変えたコミット」を指していて、`2562293` と `1bcace3` の `authgap/` は、どちらも `90ef6dd` と同じです。

（出典: `docs/decisions.md:3388-3390`、`git log`（本書の執筆時に確かめた）、`scripts/freeze_analyzer.py:89-99`（`git_commit` と `analyzer_commit` の書き方））

#### 一歩ずつの説明 — なぜ学生が打ったのか

理由は 2 つあります。

1. **作業環境からタグを送れなかった。** タグを記録したコミット（`f88c33b`、13:01）のメッセージは、「学生が GitHub の Release 画面でタグを作成した（このセッションからのタグの push は 403）」と書いています。403 は、送り先のサーバが「この操作は許されていない」と断ったことを表す番号です。本記録者の作業環境は、タグを GitHub に送る権限を持っていなかったのです。
2. **「タグは人が打つ」という決まり。** D59 の記録は「タグは学生が打つ」、凍結の記録を書くスクリプトは「タグは人が打つ（このスクリプトは打たない）」と書いています。CLAUDE.md の手順の欄にも「解析器の凍結（D59。凍結後は直さず限界として記録。タグは人が打つ）」とあります。スクリプトは、最後に「次に人が打つ: `git tag -a …`」と、打つべきコマンドを表示するだけです。

2 つ目の決まりには意味があります。
凍結は、研究の主張の土台を固める決定です。
解析器を作った本記録者が自分で「これが凍結の版」と印を付けるのではなく、研究の責任者である学生が印を付けることで、「どの版を正式とするか」の決定が人の手に残ります。

なお、スクリプトが表示するコマンドは注釈つきタグ（`git tag -a`）ですが、学生が Release 画面で作ったタグは軽量タグでした。
どちらでも、指すコミットは同じで、凍結の確かめ方（指紋の照合）には影響しません。

（出典: `git show f88c33b`（コミットメッセージ。本書の執筆時に読んだ）、`docs/decisions.md:3386`、`scripts/freeze_analyzer.py:15, 115`、`CLAUDE.md` の手順の欄）

#### よくある誤解・つまずき

- **誤解: 「タグが指すコミットと、記録の `git_commit` が違うのは誤り」**
  誤りではありません。記録は書いた時点の HEAD を書き、その記録をコミットすると 1 つ先のコミットになるからです。`authgap/` の中身はどちらも同じです。
- **誤解: 「タグを打つと、解析器の中身が固まる」**
  タグは名札で、中身を変えたり守ったりはしません。後で `authgap/` を変えても、タグは古いコミットを指したままです。だから、走査の前に `git diff <タグ> -- authgap/` が空かを確かめます（[第 22 章](ch22.md)）。
- **つまずき: 「凍結のタグは 3 つあるが、どれを使うのか」**
  最終評価に使うのは `analyzer-freeze-3` です。`analyzer-freeze-1` は中間の区切り、`analyzer-freeze-2` は履歴として残したものです（第 22・36 章）。

#### 手作業ではどう使うか

- 最終評価の前に、`git fetch --tags && git tag -l` でタグの一覧を取り込み、`analyzer-freeze-3` があることを確かめます。CLAUDE.md の落とし穴にも、「`authgap/` を変える前に `git fetch --tags && git tag -l` で凍結のタグを確かめる」とあります。
- 走査の記録（summary）の結合 sha256 と、`docs/fingerprint.json` の結合 sha256（`35606ba9…`）が一致することを確かめます。タグの名前ではなく、**中身の指紋**で照合するのが基本です。
- `docs/fingerprint.json` の `freeze.tag` の欄は `analyzer-freeze-2` と書いてありますが、正しい凍結のタグは `analyzer-freeze-3` です。理由は[第 36 章](ch36.md)で見ます。

#### この節のまとめ

タグ `analyzer-freeze-1` は、凍結の記録を足したコミット `1bcace3` を指す軽量タグで、学生が GitHub の Release 画面で作った（作業環境からのタグの送信は 403 で断られた。決まりとしても「タグは人が打つ」）。
記録の中の `git_commit`（`2562293`）とタグのコミット（`1bcace3`）は 1 つずれるが、`authgap/` はどちらも `90ef6dd` と同じ。
照合はタグの名前ではなく、結合 sha256 で行う。

### 33.4 方針の変更 — D60

#### 一言で言うと

凍結から 45 分後の 13 時 7 分、学生の決定が記録されました（D60）。
「論文用の比較表は本記録者では作らない。システムの完成後に、学生が別の新しいデータで、手動で評価する。本記録者は、新しいデータ（v3）で解析器を確かめる」。
これで、v3 は「評価のデータ」から「開発用の確認のデータ」に変わり、`analyzer-freeze-1` は「中間の区切り」になりました。

#### たとえ話 — 模試と本番

受験生とコーチの関係で考えます。
最初の計画では、コーチが作った模試（v3）の点数を、そのまま「実力」として報告するつもりでした。
だから、模試を解く前に勉強の内容を固め（凍結）、模試を解いた後は勉強の内容を変えない、と決めていました。

ところが、方針が変わりました。
「実力」は、コーチとは別の人（学生）が作る本番の試験で、別の問題を使って測ることになったのです。
そうなると、コーチの模試は「本番に向けた練習」になります。
練習の模試で間違えた所は、勉強し直してよいことになります。
ただし、本番の問題は、コーチが前もって見てはいけませんし、練習に使ってもいけません。

この研究では、コーチが本記録者、模試が v3、本番が学生の最終評価です。

#### 小さな例 — D60 の記録

D60 の本文は、次のとおりです（`docs/decisions.md:3392-3406`）。

> **学生の決定**: 論文用の比較表はこちら（本記録者）では作らない。システムの完成後に、学生が別の新しいデータで手動で評価する。本記録者は新しいデータ（v3）で解析器を確かめる。
>

### 33.6 約束の中身 — 「本記録者が一度も見ない」と「開発に使わない」

#### 一言で言うと

D60 の約束は、「評価データを**本記録者が一度も見ない**・**開発に使わない**」の 2 つの半分でできています。
第 3 版は、このうち後半（「評価に使うデータを、開発に一度も使わない」）しか書いていませんでした。
前半の「本記録者が一度も見ない」は、後半とは別の、独立した約束です。

#### 言葉の確認 — 「見る」と「使う」

- **見る**
  - やさしい言い換え: データの中身（コード・走査の結果・判定の対象）に目を通すこと。
  - 正確な定義: ここでは、本記録者（この repo の文脈を持って解析器を作り、決定の推奨と記録を書いてきた AI）が、評価データの原ソースや走査の結果に触れること。
  - 例: v4 では、本記録者が 88 木を走査し、矛と見落としを判定しました。これは v4 を「見た」ことになります。
- **開発に使う**
  - やさしい言い換え: そのデータを手がかりに、解析器や判定の決め事を作ったり直したりすること。
  - 正確な定義: データで見つけた誤りを直す、データの結果を見て規則を足す・変える、など。
  - 例: v3 で見つけた誤りから、一般に正しい直し方を入れた（D61）。これは v3 を開発に使ったことになります。

#### たとえ話 — 審査用の皿を、料理人は味見しない

料理のコンテストで、審査員が食べる皿を考えます。
守るべきことは 2 つあります。

- 料理人は、審査用の皿で**練習しない**（開発に使わない）。
- 料理人は、審査用の皿を、出す前に**味見もしない**（見ない）。

2 つ目は、1 つ目より厳しく見えるかもしれません。
「味見しただけで、作り方は変えていない」と言えば、許されそうに思えます。
けれども、一度味を知ってしまうと、次に何かを決めるとき、その味の記憶が知らず知らずのうちに混ざります。
しかも、混ざったかどうかは、外からは確かめられません。
だから、「見ない」ことそのものを約束にするのです。

（出典: `docs/decisions.md:3397-3400`、`git show 3aa899e`、`docs/textbook_v3.md:1747`（第 3 版））

#### 一歩ずつの説明 — 2 つの半分は、別々のことを守る

1. **後半「開発に使わない」が守ること**: 解析器や決め事が、評価データに合わせて育たないこと。評価データで見つけた誤りを直したり、評価データの結果に合わせて規則を変えたりすれば、評価は甘くなります。これは、D59 の「凍結後は直さない」と同じ目的です。
2. **前半「本記録者が一度も見ない」が守ること**: 作った側が評価データを知らないこと。たとえ直さなくても、作った側が評価データを見れば、その後の推奨や記録や判定の決め事に、見た内容が混ざりえます。混ざったかどうかは外から確かめられません。だから、「見ない」ことを約束にします。
3. **2 つは独立している**: 「見たが使っていない」は後半を守っても前半を破ります。「見ていないが、別の経路で使った」（たとえば、誰かがまとめた評価データの結果を開発の参考にする）は前半を守っても後半を破ります。どちらか片方だけでは足りません。

ここで、「本記録者」の範囲に注意します。
本記録者は、この repo の文脈（CLAUDE.md・決定の記録・判定の記録）を持って作業してきた AI です（[第 0 章](ch00.md)）。
学生は、本記録者ではありません。
学生は、最終評価のデータを見て判定します。
ただし、見る前に決め事を事前登録と手引きに書いて封をし、見た後は決め事も解析器も変えません（第 22・25 章）。
本記録者を「見ない側」に置くのは、本記録者が解析器と手引きの下書きを**作った側**だからです。

#### 呼び名についての注意

この約束は、記録によって呼び名が違います。
O45 と、D70 の 3 の本文と、AI の判定の調査（`docs/llm_judgment_survey.md`）は、この約束を「**D60 の 2**」と呼んでいます。
ところが、D60 の本文では、約束は番号つきの箇条（1〜4）の**前の段落**にあり、箇条の 2 は「学生の最終評価の前に解析器をもう一度凍結する」です。
原典どうしで呼び名が揃っていないので、本書では「**D60 の約束**」と呼びます。
原典で「D60 の 2」と出てきたら、文脈から、この約束のことか、最終凍結のことかを読み分けてください。

（出典: `docs/open_questions.md:1259`（O45 の 3）、`docs/decisions.md:3853`（D70 の 3）、`docs/llm_judgment_survey.md:27`、`docs/decisions.md:3402-3404`（D60 の箇条の 1・2））

#### なぜそうするのか

評価が甘くならないためです。
D60 は、「何を守れば評価が甘くならないか」を考え直した結果として、この約束を書きました。
評価が学生の別のデータで行われるなら、v3 で直しても評価は汚れません。
汚れるのは、評価のデータが、作る側に**見られる**か、作る側の開発に**使われる**ときです。
だから、この 2 つを約束にしたのです。

#### よくある誤解・つまずき

- **誤解: 「開発に使わなければ、本記録者が見てもよい」**
  よくありません。前半の「一度も見ない」は、後半とは別の約束です。見ただけでも、その後の推奨や記録に影響が混ざりえ、外から確かめられないからです。
- **誤解: 「学生も最終評価のデータを見てはいけない」**
  学生は見てよいのです。見る前に決め事を封をし、見た後は変えない、という形で守ります（[第 22 章](ch22.md)の封、[第 25 章](ch25.md) 25.5 節）。
- **誤解: 「D60 の 2 は、いつもこの約束のこと」**
  原典によって指すものが違います。D60 の本文の箇条の 2 は最終凍結です。文脈で読み分けます。

#### 手作業ではどう使うか

- 最終評価の判定の記録や、判定の対象の原ソースを、AI に見せません。見せれば、本記録者（またはその同類）が評価データを見ることになります（33.7 節、[第 26 章](ch26.md)）。
- 判定の途中で困ったときに、この repo の文脈を持つ AI に「この件はどう判定すべきか」と相談するのも、評価データを見せることになるので、しません。手引きで決まらなければ、手引きの 22 節に従って「不明」にし、「手引きで決まらない」と書きます（[第 52 章](ch52.md)）。

#### この節のまとめ

D60 の約束は「評価データを本記録者が一度も見ない・開発に使わない」の 2 つの半分。第 3 版とコミットメッセージは後半しか書いていなかったが、本文には最初から両方あった。
後半は「評価データに合わせて育てない」、前半は「作った側が評価データを知らない」を守る。2 つは独立で、片方だけでは足りない。
原典はこの約束を「D60 の 2」と呼ぶことがあるが、D60 の本文の箇条の 2 は最終凍結なので、本書では「D60 の約束」と呼ぶ。

### 33.7 約束がその後に生んだ決定 — D66 の 3 と D70 の 3

家族で「冷蔵庫のプリンは、名前を書いた人のもの」と決めたとします。

v4 をどう扱うか、判定で AI を使ってよいか、という新しい問いに、その場の都合ではなく、D60 の約束から答えたのです。

2. もし最終評価で、学生がこの repo の文脈（CLAUDE.md・決定の記録・v4 の判定）を読み込んだ AI（Claude）を、原ソースを読む補助に使ったらどうなるか。

#### なぜそうするのか — 約束から導くこと

後から出てきた問い（v4 をどう扱うか、AI を使ってよいか）に、その場の都合で答えると、決め事どうしが食い違っていきます。
D60 の約束という「最初のルール」から導けば、決め事の筋が通り、論文で「なぜそうしたか」を一貫して説明できます。
しかも、D66 の 3 も D70 の 3 も、**最終評価のデータを誰も見ていない時点**で決めています。
だから、結果に合わせて決めたのではないことも示せます。

#### よくある誤解・つまずき

- **誤解: 「v4 は解析器を直すのに使っていないので、最終評価に使ってよい」**
  使いません。後半（開発に使わない）は守っても、前半（本記録者が見ない）を破っているからです。D66 の 3 の理由は「本記録者が見たデータなので」です。
- **誤解: 「AI に原ソースの行を探させるだけなら、約束に触れない」**
  触れます。この repo の文脈を持つ AI に評価データの原ソースを見せれば、本記録者が評価データを見ることになります。D70 の 3 は、読む補助にも使わないと決めています。
- **誤解: 「repo の文脈を持たない別の AI なら使ってよい」**
  それは案 (b) で、採りませんでした。D70 の 3 は、どの AI も判定に使わないと決めています。
- **つまずき: 「研究の遂行には AI を使ってきたのに、矛盾しないか」**
  矛盾しません。解析器の実装・v3 と v4 の判定・手順書と手引きの下書き・決定の推奨には AI（本記録者）を使ってきました。それは論文で開示します（O45 の 4）。D70 の 3 が禁じるのは、**最終評価の判定**に AI を使うことです。

#### 手作業ではどう使うか

最終評価の作業の前に、次を確かめておきます。

1. 判定する木が、v2・v3・v4 のどれにも入っていない（抽出の除外、中身の重複の除去）。
2. 判定・原ソースを読むこと・記録のどれにも AI を使わない。行を探すには grep やエディタの検索・「定義へ移動」を使う（第 9・26 章）。
3. 判定の途中の記録や、評価データの原ソースを、AI に見せない。
4. 判定の途中で解析器の誤りを見つけても、直さない。`docs/open_questions.md` に限界として書く。

この 4 つは、どれも D60 の約束の 2 つの半分を、最終評価で守るための具体的な形です。

#### この節のまとめ

D60 の約束の前半「本記録者が一度も見ない」が、D66 の 3（v4 は本記録者が見たデータなので最終評価から除く）と D70 の 3（判定で AI を使わない。O45 の案 (a)）の根拠になった。
v4 は後半（開発に使わない）を守っても前半を破るので除く。D70 の 3 は、この約束と研究の芯（不明を数える・決定性）の両方に支えられている。
どちらも、最終評価のデータを誰も見ていない時点の決定。

### 33.8 凍結の意味の移り変わり — 「直さない」から「見ていないデータで測る」へ

#### 一言で言うと

最初の凍結（D59）は「凍結の後は直さない」という約束でした。
D60 で、守る中心が「評価データとの距離」に移り、凍結は「最終評価の前にもう一度」行うものになりました。
その後、D61・D64・D66 を経て、最終評価では「どの段階でも解析器を変えない」という、最初より厳しい形に戻っています。

#### 小さな例 — 凍結と約束の移り変わり

| 時点 | 決定 | 解析器を直してよいか | 守る中心 |
|---|---|---|---|
| 2026-09-24 12:22 | D59（`analyzer-freeze-1`） | 凍結の後は直さない（直すなら逸脱） | 凍結の時期 |
| 同 13:07 | D60 | v3 で見つけた欠陥は直してよい（同じ手順で） | 評価データを本記録者が見ない・開発に使わない |
| 同 13:33 | D61 | 一般に正しい直し方だけ。v3 に合わせて直さない | 検証データに合わせて育てない（[第 35 章](ch35.md)） |
| 2026-09-28〜29 | D64（`analyzer-freeze-2`、`analyzer-freeze-3`） | 凍結の前の添削で選んだものだけを直し、最終凍結 | 最終評価の前に固める（[第 36 章](ch36.md)） |
| 2026-09-29 | D66（v4） | 結果を見て解析器を変えない | 凍結版のまま新しいデータで確かめる（[第 37 章](ch37.md)） |
| 最終評価 | 手順書・D71 | **どの段階でも `authgap/` を変えない** | 凍結版で、見ていないデータを、AI を使わずに測る |

表の読み方: 2 行目は「13 時 7 分の D60 で、v3 で見つけた欠陥は直してよいことになった。守る中心は、凍結の時期ではなく、評価データとの距離（本記録者が見ない・開発に使わない）に移った」と読みます。

（出典: `docs/decisions.md:3290-3295`（D59）、`:3397-3406`（D60）、`:3408-3410`（D61 の方針）、`:3743-3754`（D66）、`:3900`（D71: 解析器は凍結のまま）、`docs/final_evaluation_procedure.md:13`）

#### 一歩ずつの説明

1. **D59 は「時期」で守った。** 凍結の時点を境に、その後は直さない。v3 を評価データにする前提での守り方でした。
2. **D60 は「データとの距離」で守った。** 評価データを別にしたので、開発のデータ（v3）では直してよくなりました。代わりに、評価データを本記録者が見ない・開発に使わないことを約束にしました。
3. **D61 で、直し方に歯止めをかけた。** 学生の方針は「検証データを見て変更するのはきりがなく、研究として良くない。誤りの修正が一般的に役立つものなら改善する」でした。開発のデータでも、そのデータに合わせて直すことは禁じたのです。
4. **D64 で最終凍結した。** 凍結の前の添削で選んだ所だけを直し、`analyzer-freeze-3` で固めました。
5. **D66 と最終評価は「変えない」に戻った。** v4 も最終評価も、凍結版のまま測り、見つけた誤りは直さずに限界として書きます。

つまり、D60 は凍結の約束を緩めたのではなく、**守る対象を正しい所に移した**のです。
そのうえで、最終評価に向かうにつれて、守り方は再び厳しくなっていきました。

#### なぜそうするのか

評価の数字を信じてもらうには、「評価のデータに合わせて解析器を育てていない」ことを示す必要があります。
そのために一番確かな方法は、「評価のデータを、作る側が見ない・使わない」ことと、「評価の間は解析器を変えない」ことの両方です。
最終評価は、この両方を満たす形で設計されています。

#### よくある誤解・つまずき

- **誤解: 「凍結を何度もやり直したのは、約束を守れなかったから」**
  D60 による `analyzer-freeze-1` の位置づけの変更は、評価の方針が変わったことに合わせて、理由を書いて記録の上で行ったものです。`analyzer-freeze-2` の後に解析器を直してしまったのは本記録者の手違いで、逸脱 #26 として記録し、学生の判断で `analyzer-freeze-3` を打ち直しました（第 22・36 章）。どちらも、隠さずに記録されています。
- **誤解: 「最終評価で解析器の誤りを見つけたら、直してから測り直すのが正確」**
  直しません。直せば、評価のデータに合わせて解析器を育てることになり、D60 の約束の後半を破ります。

#### 手作業ではどう使うか

最終評価のあいだ、解析器について学生がすることは、「凍結版と同じかを確かめる」ことだけです（タグ、`git diff`、結合 sha256 の照合。第 22・36 章）。
直したくなる誤りを見つけたら、`docs/open_questions.md` に限界として書き、論文の限界の節の材料にします。

#### この節のまとめ

D59 は時期で守り（凍結の後は直さない）、D60 はデータとの距離で守った（評価データを本記録者が見ない・開発に使わない）。
D61 で直し方に歯止めをかけ、D64 で最終凍結し、D66 と最終評価では「解析器を変えない」に戻った。
D60 は凍結を緩めたのではなく、守る対象を正しい所に移した。

### この章のまとめ

- D59 は、直し方の規則と一緒に「凍結の条件」を先に書いていた（v2 は開発用、評価は凍結後の v3、凍結後の欠陥は直さず限界に書く）。run18 で D59 を終えた 2026-09-24 12:22（UTC）に凍結した（`analyzer-freeze-1`、コミット `1bcace3`）。
- 凍結の記録 `docs/fingerprint.json` には、仕様書の指紋（sink 表など 4 つ）に加えて、`authgap/` の全ファイルの sha256 と結合 sha256 を入れた。仕様書の指紋は slot の名前しか見ないので、`url=` の追記では `sink_table` が変わらなかった（本書の執筆時に計算して確かめた）。最終評価の前の照合も結合 sha256 で行う。
- タグ `analyzer-freeze-1` は、学生が GitHub の Release 画面で作った軽量タグ（作業環境からのタグの送信は 403。決まりとしても「タグは人が打つ」）。記録の `git_commit`（`2562293`）とタグのコミット（`1bcace3`）は 1 つずれるが、`authgap/` は同じ（`90ef6dd`）。
- D60（13:07）: 論文の評価は学生が別の新しいデータで手動で行う。v3 は開発用の確認、`analyzer-freeze-1` は中間の区切り、最終評価の前にもう一度凍結、評価データから v2・v3 を除く。D60 と v3 の手続きは、v3 の抽出より前にコミットした。
- D60 の約束は「評価データを**本記録者が一度も見ない**・**開発に使わない**」。第 3 版は後半しか書いていなかった。2 つは独立の約束で、前半が D66 の 3（v4 を最終評価から除く）と D70 の 3（判定で AI を使わない。O45 の案 (a)）の根拠になった。
- 凍結の守り方は、D59 の「時期」から D60 の「データとの距離」に移り、D61 の歯止めと D64 の最終凍結を経て、最終評価では「どの段階でも解析器を変えない」になった。
