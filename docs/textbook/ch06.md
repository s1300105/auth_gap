# 第 2 部 研究の問い — この研究は何をするのか

## 第 6 章 この研究の一文 — 不明を数える測定研究

> **この章で分かること**: この研究の問いを一文で言うと何か。その一文に出てくる 2 つの記号、D（宣言）と M（実効の権限）。解析器が報告する「矛」。この研究が「道具の研究」ではなく「測定研究」であり、その芯が「解析できなかったものを、理由をつけて数える（不明を数える）」ことにある理由。最も近い先行の道具 HintLint と、何が同じで何が違うか。解析器の 3 つの答え（矛・不・何も出さない）と、最終評価でそれぞれを人がどう確かめるか（精度 V2・不の中身 V6・見落とし V3）。論文の結論になる数（宣言を書いたサーバのうち、少なくとも何割に違反があったか）の予告。

### 6.1 一文で言うと

#### 一言で言うと

この研究（名前は **AuthGap**）は、Python で書かれた MCP サーバのツールについて、「ツールが自分について書いた約束（宣言）」と「そのツールが実際にできること」を、プログラムを動かさずに照らし合わせ、**約束より多くのことができる所**を見つけます。

#### たとえ話 — メニューの表示と、厨房のレシピ

あるレストランのメニューには、料理ごとに「卵不使用」「乳不使用」といった表示が付いています。
卵のアレルギーがある客は、この表示を信じて料理を選びます。
ところが、表示はお店が自分で付けたもので、誰も確かめていません。

そこで、検査員が来ることになりました。
検査員は、料理を**作らずに**、厨房のレシピのカードを読みます。
レシピに「ソースはカード 12 番のものを使う」と書いてあれば、12 番のカードもめくって読みます。
そして、「卵不使用」と表示した料理のレシピに、卵が入りうるかを確かめます。
カードが汚れていて読めなかったら、勝手に「卵は入っていない」とは決めず、「このカードは読めなかった」と書き残します。

この研究がしていることは、この検査員の仕事とほとんど同じです。

| たとえ話 | この研究 |
|---|---|
| メニューの「卵不使用」の表示 | ツールの宣言（D） |
| レシピから分かる「この料理に入りうるもの」 | ツールが実際にできること（M） |
| 料理を作らずにレシピを読む | プログラムを動かさずに読む（静的解析。[第 7 章](ch07.md)） |
| 「カード 12 番を使う」をたどる | 呼び出した先の関数をたどる（[第 15 章](ch15.md)） |
| 「このカードは読めなかった」と書き残す | 読み切れなかったものを「不」として理由つきで残す（6.4 節） |

表の読み方: 3 行目は「検査員が料理を作らずにレシピを読むのは、この研究がプログラムを動かさずにコードを読むことにあたる」と読みます。

#### 小さな例 — 一文を部品に分ける

この研究の問いを一文で書くと、こうなります。

> **Python で書かれた MCP サーバについて、各ツールの宣言（D）と、そのツールが実際にできること（M）を、プログラムを動かさずに照らし合わせ、食い違いを見つける。**

一文を 5 つの部品に分けて、表にします。

| 部品 | 意味 | 詳しくは |
|---|---|---|
| ① Python で書かれた MCP サーバ | 調べる対象。MCP サーバ（AI が使う道具をまとめて提供するプログラム）のうち、Python で書かれたもの | [第 3 章](ch03.md) |
| ② 各ツールの宣言（D） | ツールが ToolAnnotations の欄に書いた約束のうち、D1〜D4 の 4 つ | [第 4 章](ch04.md)、この章の 6.2 節 |
| ③ そのツールが実際にできること（M） | LLM が入れうる値の全体で、そのツールが外の世界に何をできるか | この章の 6.2 節 |
| ④ プログラムを動かさずに | 静的解析。コードを読んで、何が起こりうるかを推論する | [第 7 章](ch07.md) |
| ⑤ 照らし合わせ、食い違いを見つける | M が D を超えている所を「矛」として報告する | この章の 6.3 節、[第 17 章](ch17.md) |

表の読み方: ③の行は「一文の『そのツールが実際にできること』は、記号では M と書く。中身は『LLM が入れうる値の全体で、外の世界に何をできるか』で、6.2 節で詳しく見る」と読みます。

#### 一歩ずつ — 部品を 1 つずつ

1. **①対象**: 調べるのは、MCP サーバのうち Python で書かれたものだけです。MCP サーバは、TypeScript など別の言語でも書かれますが、この研究の解析器は Python のコードしか読みません。だから、一文の最初で対象を絞っています。
2. **②宣言**: 宣言は、[第 4 章](ch04.md)で見た 4 つの約束です。D1 は `readOnlyHint: true`（環境を変えない）、D2 は `destructiveHint: false`（前からあるものを壊さない）、D3 は `openWorldHint: false`（外の世界と関わらない）、D4 は `idempotentHint: true`（同じ引数で繰り返しても追加の効果が無い）でした。作者がはっきり書いたものだけを数え、何も書いていないものを「約束した」とは読みません（[第 4 章](ch04.md)の既定値の話）。
3. **③できること**: ツールが「ふだんやっていること」ではなく、「できること」を考えます。理由は 6.2 節で見ます。
4. **④動かさずに**: 解析器は、調べるサーバを起動しません。コードを読んで、「この経路を通れば、ここでファイルが書かれうる」と推論します。なぜ動かさないのか、動かさないと何が苦手になるのかは、[第 7 章](ch07.md)で見ます。
5. **⑤照らし合わせ**: ②と③を比べて、③が②を超えている所（約束より多くのことができる所）だけを報告します。逆向き（約束より少なくしかやらない所）は報告しません。これも 6.3 節で見ます。

#### なぜ、この一文なのか — 主張を 1 本に絞った（D36）

実は、この研究の仕様書（`AUTHGAP_BRIEF_v3.md`）の冒頭の一文は、もっと広いことを言っていました。
仕様書は、「AuthGap は、コードがモデルに実際に渡している権限（実効権限 M）を静的に推論し、宣言された権限（D）**または明示ベースライン P0** を超える箇所を報告する」と書き、さらに 3 つの別々の見方（座標）を組み合わせる大きな主張を立てていました。
ところが、開発用のデータ（[第 5 章](ch05.md)で見た母集団 v2）で測ってみると、その大きな主張を支えるために事前に決めておいた条件が満たされませんでした。
そこで学生は 2026-09-21 に、主張を「**宣言 D と実効 M の照合**」の 1 本に絞ると決めました（決定 D36）。
この章の一文は、その絞った主張を書いたものです。

ここで、仕様書の本体は書き換えていません。
仕様書と実際が食い違ったときは、実際を採り、仕様書の値も設計の記録として残す、というのがこの研究の約束だからです（`CLAUDE.md` の規則 6）。
どういう経緯で絞ったのかは、[第 8 章](ch08.md)で詳しく見ます。
（出典: `AUTHGAP_BRIEF_v3.md:32`（仕様書の一文）、`:36`（3 つの座標を組み合わせる主張）、`docs/decisions.md:185-194`（D36 の決定の表）、`:201-213`（母集団 v2 で測った値が事前登録の条件を満たさなかったこと））

#### よくある誤解・つまずき

- **誤解: 「AuthGap は、危ないツールを見つける研究だ」**
  違います。問いは「**宣言は正しいか**」で、「危ないか」ではありません（決定 D67 の 1）。たとえば、どんなファイルでも消せるのに何も宣言していないツールは、とても危ないかもしれません。けれども、何も約束していないので、この研究の「食い違い」には当たりません。
- **誤解: 「ツールを実際に動かして、何が起きるかを確かめる」**
  解析器は動かしません。最終評価の人の判定も、ツールを動かすのではなく、原ソース（調べる相手の、手を加えていないコード）を読んで決めます（`docs/final_evaluation_procedure.md:68-70`）。
- **誤解: 「食い違いなら、どちらの向きでも報告する」**
  報告するのは、「約束より多くできる」向きだけです（6.3 節）。
- **つまずき: 「MCP サーバなら、どの言語で書かれていても対象」**
  対象は Python で書かれたものだけです。先行の道具との比べ方にも、この絞り込みが効いてきます（6.5 節）。

#### 手作業ではどう使うか

判定の手引き（下書き・未承認）は、解析器が出した 1 件ごとに、次の 2 つの問いに答えるよう求めています。

1. **到達するか**: その動作は、ツールの呼び出しによって、実行時に実際に起きうるか。
2. **宣言に反するか**: 起きたとき、その動作は宣言（D1〜D4）に反するか。

両方が「はい」のときだけ、解析器の答えは当たっていた（**正**）とします。
この 2 つの問いは、一文の③と⑤をそのまま人の目でやり直すものです。
1 つ目の問いは「その動作は本当に M に入るか」、2 つ目の問いは「それは D を超えるか」と言い換えられます。
判定で迷ったら、この一文に戻って「自分は今、M を確かめているのか、D との比べ方を確かめているのか」を考えると、整理しやすくなります。
（出典: `docs/drafts/final_judging_guide_draft.md:38-52`（11.2 節）。手順は[第 48 章](ch48.md)）

#### この節のまとめ

この研究は、Python の MCP サーバのツールについて、宣言 D と実際にできること M を、動かさずに照らし合わせ、M が D を超える所を見つける。
仕様書はもっと広い主張を立てていたが、測った結果を受けて、学生が「D と M の照合」1 本に絞った（D36）。判定の 2 つの問い（到達するか・宣言に反するか）は、この一文を人の目でやり直すもの。

### 6.2 2 つの記号 — D と M

#### 一言で言うと

**D** は宣言（ツールの自己申告）、**M** は実効の権限（そのツールで実際にできること全部）です。
M は、ツールが「ふだんやっていること」ではなく、「**LLM が入れうる値の全体で、できること**」で考えます。

#### たとえ話 — 入館証の印刷と、カードで開く扉

ある会社の入館証には、「1 階のみ入館可」と印刷してあります。
ところが、カードの設定を調べると、実際には 1 階から 3 階までの扉が開きます。
持ち主は、ふだん 1 階にしか行きません。

この入館証について、「ふだん 1 階にしか行かないのだから、1 階のカードだ」と言ってよいでしょうか。
もしカードを落として誰かに拾われたら、拾った人は 3 階まで入れます。
警備の担当者が気にするのは、持ち主がふだんどこへ行くかではなく、**そのカードでどの扉が開くか**です。

この研究の D と M は、ちょうどこの関係です。

- 入館証に印刷された「1 階のみ」が、**D**（宣言）です。
- カードで実際に開く扉の全体（1〜3 階）が、**M**（実効の権限）です。
- カードを拾った人が LLM にあたります。LLM は、操られたり取り違えたりすれば、ツールの引数にどんな値でも入れうるからです（[第 2 章](ch02.md)の考え方 1）。

#### 小さな例 — 宣言 1 つと、できること 2 つ

この章のために書いた説明用のツールを見ます（このツールは 6.6 節でも使います）。

```python
@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def export_note(name: str, path: str) -> str:
    text = show_note(name)
    with open(path, "w") as f:
        f.write(text)
    return "ok"
```

1 行ずつ見ます。

- 1 行目: このツールの宣言です。`readOnlyHint=True`、つまり D1（環境を変えない）と約束しています。`@mcp.tool(...)` は「この関数を MCP のツールとして登録する」という印です（第 3・4 章）。
- 2 行目: `export_note` という関数を作ります。引数は `name`（メモの名前）と `path`（書き出す場所）の 2 つで、どちらも LLM が決める値です。`-> str` は「文字列を返す」という意味の目印です。
- 3 行目: `show_note(name)` という別の関数を呼び、メモの中身を読んできて、`text` という名前で覚えておきます。`show_note` の中では、メモのファイルを読むだけです（6.6 節で全体を見ます）。
- 4 行目: `path` の場所のファイルを、`"w"`（書き込み用）で開きます。`"w"` で開くと、ファイルが無ければ新しく作られ、あれば中身が消えて上書きされます（[第 9 章](ch09.md)で、開き方の一覧を見ます）。
- 5 行目: 開いたファイルに、メモの中身を書き込みます。
- 6 行目: `"ok"` という文字列を返して終わります。

このツールの D と M を並べます。

| 記号 | このツールでは | コードのどこから読むか |
|---|---|---|
| D | D1（`readOnlyHint: true`。環境を変えない） | 1 行目の宣言 |
| M | ① メモのファイルを読める ② **LLM が選んだ場所に、ファイルを作れる・上書きできる** | 3 行目（の先の `show_note`）と、4〜5 行目 |

表の読み方: M の行は「このツールでできることは 2 つある。1 つはメモを読むこと、もう 1 つは LLM が選んだ場所にファイルを作ったり上書きしたりすること」と読みます。

#### 一歩ずつ — M をどう読み取るか

M は、次の順で読み取ります。

1. **外の世界に触れる操作を探す**: 3 行目の先の `show_note` の中に「ファイルを読む」操作が、4〜5 行目に「ファイルを書く」操作があります。このように、ファイル・データベース・ネットワーク・プロセスなど、ツールの外の世界に触れる操作を、この研究では**効果**と呼びます（[第 13 章](ch13.md)）。
2. **その操作の中身を誰が決めるかを見る**: 書く場所 `path` は、ツールの引数です。つまり LLM が決めます。書く場所が作者の書いた定数だったら、M はずっと狭くなります（[第 2 章](ch02.md)の `delete_file` と `clear_work` の比較を思い出してください）。
3. **取りうる値の全体で考える**: LLM は `path` にどんな値でも入れられます。だから M は「`exports/memo.txt` に書ける」ではなく、「**このプログラムが書ける場所なら、どこにでも書ける・上書きできる**」になります。
4. **ふだんの使い方で狭めない**: 利用者がふだん `exports/` の下の名前しか頼まないとしても、M は狭くなりません。入館証のたとえで言えば、持ち主がふだん 1 階にしか行かなくても、カードで開く扉は 3 階まであるのと同じです。

#### 言葉の整理 — D

- **やさしい言い換え**: ツールの自己申告。
- **正確な定義**: ツールの ToolAnnotations の欄に、作者がはっきり書いた 4 つの約束 D1〜D4 のどれか。D は Declared（宣言された）の頭文字。何も書いていない項目を、既定値で補って「約束した」とは数えない（[第 4 章](ch04.md)）。
- **例**: 上の `export_note` の `readOnlyHint=True` は D1。

#### 言葉の整理 — M（実効の権限）

- **やさしい言い換え**: そのツールで、実際にできること全部。
- **正確な定義**: ツールの呼び出しによって起きうる、外の世界への作用（ファイルの書き込み・外部との通信・プロセスの起動など）の全体。値を LLM が決める所は、その値が取りうる範囲の全体で考える。M は effective permissions（実効の権限）の頭文字。
- **例**: `export_note` の M には、「LLM が選んだ場所のファイルを上書きできる」が入る。

「**実効の**」は、「書類の上ではなく、実際に効いている」という意味です。
「**権限**」は、[第 2 章](ch02.md)で見た「ツールを通じて LLM に与えた、外の世界に働きかける力」のことで、パソコンの OS のファイルの権限とは別の言葉です。
仕様書は M を「コードがモデルに実際に渡している権限（実効権限 M）」と書いています。
（出典: `AUTHGAP_BRIEF_v3.md:32`）

#### なぜ「やっていること」ではなく「できること」なのか

理由は 3 つあります。

1. **LLM が引数を決めるから**: [第 2 章](ch02.md)の考え方 1 で見たとおり、LLM は文書に仕込まれた指示に操られたり、単純に取り違えたりして、引数にどんな値でも入れえます。ふだんの値だけで考えると、操られたときに起きることを見落とします。
2. **原理として、そう決めてあるから（原理 3-a）**: この研究は、宣言に反するかを決める 4 つの原理を、データを見る前に学生が選んでいます（[第 17 章](ch17.md)）。その 3 つ目は「モデルが決める値をどう読むか」で、学生は「**能力として読む**」（取りうる値の全体で考える）を選びました。理由は「AuthGap の M は『できること』の上界。b（もう一方の案）にすると M の定義が 2 つになる」です。ただし、D4（繰り返しても追加の効果が無い）にだけは、この原理を当てません。D4 は「同じ引数で繰り返したとき」の性質なので、取りうる値の範囲は関係しないからです。
3. **条件つきでも、確認を省かれた 1 回で起きるから（D68 の 1）**: [第 5 章](ch05.md)で見たとおり、クライアントは `readOnlyHint: true` を見て呼び出しごとの確認を省きます。だから、ある条件のときだけ起きる動作も、条件を満たす呼び出しが 1 回でも来れば起きます。「たまにしか起きない」は「起きない」ではありません。

（出典: `docs/contradiction_principles.md:140`（原理 3 の選択と理由）、`:153-155`（D4 には原理 3 を当てない）、`docs/decisions.md:3796-3801`（D68 の 1））

#### もう 1 つの区別 — 本当の M と、解析器が推論した M

ここで、とても大事な区別をしておきます。

- **本当の M** は、コードの性質そのものです。コードが決まれば、本当の M も決まっています。
- **解析器が出すのは、本当の M を推論したもの**です。解析器は、コードを動かさずに読んで「ここでファイルが書かれうる」と推論します。

推論には、2 つの向きの誤りがありえます（[第 21 章](ch21.md)）。
1 つは、実際には起きない操作を M に入れてしまう誤り（誤警報）です。
もう 1 つは、実際に起きる操作を M から落としてしまう誤り（見落とし）です。
さらに、読み切れずに「ここから先は分からない」となる所も出ます。
この「読み切れない所」をどう扱うかが、6.4 節で見る研究の芯につながります。
そして、推論が本当の M にどれだけ近かったかを人が確かめるのが、6.6 節で見る最終評価です。

#### よくある誤解・つまずき

- **誤解: 「M は、ツールがふだんやっていること」**
  M は「できること」です。ふだんの使われ方では狭めません。
- **誤解: 「M は、解析器の出力そのもの」**
  解析器の出力は、M を推論したものです。誤警報も見落としも、読み切れない所もありえます。だから人が確かめます。
- **誤解: 「宣言に書いていないことは、しないと約束したこと」**
  違います。書いていない項目は、何も約束していません（[第 4 章](ch04.md)の既定値）。D には、はっきり書かれた約束だけが入ります。
- **つまずき: 「M に『読む』が入っているから、D1 のツールは全部おかしい」**
  D1 は「環境を変えない」約束なので、読むだけなら D1 の範囲内です。M に入っているかどうかと、M が D を超えるかどうかは、別の問いです。

#### 手作業ではどう使うか

判定では、自分の頭の中で M を組み立て直します。

1. 解析器が示した効果の行を開き、本当にその操作かを確かめる。
2. ツールの入口からその行まで、呼び出しを自分でたどる。
3. その操作の中身（書く場所・送り先・起動するコマンド）を誰が決めるかを確かめる。LLM が決めるなら、取りうる値の全体で考える。
4. ツールの呼び出しで、1 回でも起きうるかを確かめる。条件があれば、その種類を記録する（条件の種類は[第 49 章](ch49.md)）。

この 4 つは、判定の手引きの手順 C〜E にあたります。
「ふだんはそんな値は来ないだろう」という感覚で、M を狭めないでください。
（出典: `docs/drafts/final_judging_guide_draft.md:116-148`（手順 C〜E）。詳しくは第 48・49 章）

#### この節のまとめ

D は宣言（作者がはっきり書いた約束 D1〜D4）、M は実効の権限（LLM が入れうる値の全体で、ツールができること）。M を「できること」で考えるのは、LLM が引数を決めること、原理 3-a、D68 の 1 の 3 つの理由から。
解析器が出すのは M の推論で、誤警報・見落とし・読み切れない所がありうる。判定では、自分で M を組み立て直して確かめる。

### 6.3 何を報告するか — 矛

#### 一言で言うと

**D と M を比べて、M が D を超えている所（宣言より多くのことができる所）を報告します。**
この食い違いを、英語の出力では **CONTRADICTION**（矛盾）、この教科書では短く「**矛**」と呼びます。

#### たとえ話 — 「卵不使用」の表示（続き）

6.1 節のレストランの検査員に戻ります。
検査員が報告するのは、次のような場合です。

- メニューに「卵不使用」と表示しているのに、レシピに卵が入りうる。→ **報告する。**

一方、次の場合は報告しません。

- メニューに「卵を含む」と表示しているのに、実はレシピに卵が入っていない。→ 客が余計に避けるだけで、表示を信じた客が困ることはない。
- メニューに何も表示していない。→ お店は何も約束していない。卵が入っていても、表示の嘘ではない。

検査員の仕事は「表示を信じた客が、困る食い違い」を見つけることです。
この研究の矛も、同じ考え方でできています。

#### 小さな例 — 4 つの組み合わせ

| # | D（宣言） | M（コードから分かる、できること） | 解析器の報告 | 理由 |
|---|---|---|---|---|
| 1 | D1（読むだけ） | LLM が選んだ場所にファイルを書ける | **矛** | 「環境を変えない」約束を超えている |
| 2 | D1（読むだけ） | ファイルを読むだけ | 報告しない | 読むことは D1 の範囲内 |
| 3 | 何も宣言していない | ファイルを消せる | 報告しない | 何も約束していないので、超える約束が無い |
| 4 | D1（読むだけ） | 外部のサーバに POST という種類の要求を送る | 「決められない」（**不**） | POST で相手のサーバの状態が変わるかは、相手しだいで、コードだけでは決まらない |

（1・2・4 行目の解析器の報告は、6.6 節の作例のサーバを凍結版と同じ解析器で走らせて確かめたもの。）

#### 一歩ずつ — 1 行ずつ読む

1. **1 行目**: 6.2 節の `export_note` です。D1 は「環境を変えない」約束です。M には「ファイルを作る・上書きする」が入っています。ファイルが変わるのは環境の変更なので、M が D を超えています。だから矛です。
2. **2 行目**: 読むだけなら、環境は変わりません。M は D の範囲に収まっているので、報告しません。このような「宣言の範囲内」を、この研究では「**内**」と呼びます。
3. **3 行目**: 何も宣言していないツールは、[第 4 章](ch04.md)の既定値のとおり「環境を変えうる、壊しうる」ツールとして扱われ、何も約束していません。だから、どれだけ危ないことができても、矛にはなりません。危なさを測るのは、この研究の問いではないからです（6.1 節の誤解）。
4. **4 行目**: POST は、ウェブの通信で「データを送る」ときに使う要求の種類です（[第 10 章](ch10.md)）。送った先で何かが作られる（相手の状態が変わる）こともあれば、検索の問い合わせに使われるだけ（相手の状態は変わらない）こともあります。どちらなのかは、相手のサーバの作り次第で、こちらのコードだけでは決まりません。そこで解析器は、矛とも内とも言わず「**不**」（決められない）と答えます。不は 6.4 節で詳しく見ます。

#### 言葉の整理 — 矛

- **やさしい言い換え**: 解析器が見つけた、「宣言より多くのことができる」食い違い。
- **正確な定義**: 解析器の答えの 1 つ。ある宣言（D1〜D4）について、ツールの入口から届く効果が、その宣言に反すると判定したもの。反するかどうかは、学生が選んだ原理から導いた判定表で決まる（[第 17 章](ch17.md)）。出力の英語の名前は CONTRADICTION。
- **例**: `export_note` の `open(path, "w")` は、D1 の矛。

1 つ注意があります。
**矛は、解析器の「答え」であって、確定した事実ではありません。**
解析器が矛と言ったものが本当に宣言に反するかは、人が原ソースを読んで確かめます。
人が確かめて「本当に反していた」と決めたものを「**正**」、「反していなかった」と決めたものを「**誤**」と呼びます（6.6 節）。

#### なぜ「超える」向きだけを報告するのか

[第 5 章](ch05.md)の 5.2 節で見たとおり、宣言と実装のずれには、「言うより多くやる」（過小申告）と「言うより少なくやる」（過大申告）の 2 つの向きがあります。
D1〜D4 は、どれも「〜しない」「〜だけ」という控えめな約束です。
控えめな約束が破れるのは、「しないと言ったことを、した（できる）」とき、つまり M が D を超えるときだけです。
だから矛は、過小申告を探す仕組みになっています。
過大申告は、宣言を信じた人を困らせない（余計に確認されるだけの）向きなので、探しません。

#### よくある誤解・つまずき

- **誤解: 「矛と出たら、それは違反だ」**
  矛は解析器の答えです。誤警報が混ざりえます。本当に違反かは、人の判定（正 / 誤 / 不明）で決まります。
- **誤解: 「矛の件数 = 違反しているツールの数」**
  違います。矛の 1 件は、(木, ツール, 効果を起こす関数, 効果の種類, 宣言) の組 1 つです（[第 5 章](ch05.md)・[第 18 章](ch18.md)）。1 つのツールから何件も出ることがあり、1 つの木から何十件も出ることもあります。だから報告は木（サーバ）の単位で束ねます（決定 D67 の 3）。
- **誤解: 「宣言の無い危ないツールも矛になる」**
  なりません。超えるべき約束が無いからです。
- **つまずき: 「矛盾」を論理学の矛盾（A であり、かつ A でない）と同じ意味に取る**
  この研究の矛（CONTRADICTION）は、「宣言とコードの食い違い」に付けた名前です。

#### 手作業ではどう使うか

最終評価の判定の中心は、解析器が出した矛を 1 組ずつ確かめる作業です。
宣言ごとに、矛の出た木から最大 200 木を選び、各木から最大 3 件を判定します（決定 D69 の 2、D70 の 1）。
1 件ごとに、6.1 節の 2 つの問い（到達するか・宣言に反するか）に答え、正 / 誤 / 不明を付けます。
解析器が付けた理由の名前（どんな操作だと思ったか）が間違っていても、2 つの問いの答えが「はい」なら正です。
判定するのはコードの動作で、解析器の説明ではないからです。
（出典: `docs/decisions.md:3826`（D69 の 2）、`:3841-3845`（D70 の 1）、`docs/drafts/final_judging_guide_draft.md:53-54`）

#### この節のまとめ

M が D を超える所を「矛」（CONTRADICTION）として報告する。範囲内は「内」、決められないものは「不」。何も宣言していないツールは矛にならない。
矛は解析器の答えで、人が正 / 誤 / 不明で確かめる。探すのは過小申告の向きだけ。

<a id="s6-5"></a>
### 6.4 研究の芯 — 不明を数える測定研究

#### 一言で言うと

この研究が測りたいのは、「**MCP サーバの宣言は、どれだけ当てにならないか**」という**率**です。
率を正しく測るには、解析器が読み切れなかったものを、黙って「違反なし」に数えたり、黙って分母から消したりしてはいけません。
だからこの研究は、**解析できなかったものを、理由をつけて数えます**（不明を数える）。
これが、この研究のいちばん大事な芯です。

#### たとえ話 — 宿題の提出率

先生が、クラス 40 人のうち何割が宿題をやってきたかを知りたいとします。
集めたノートを調べると、30 人分は中身を確かめられ、そのうち 24 人がやってきていました。
残りの 10 人分は、欠席でノートが無かったり、字が読めなかったりして、確かめられませんでした。

この 10 人をどう扱うかで、報告する率が大きく変わります。

- 10 人を「やってこなかった」に数えると、24 ÷ 40 = 60% です。
- 10 人を「やってきた」に数えると、(24 + 10) ÷ 40 = 85% です。
- 10 人を分母から消すと、24 ÷ 30 = 80% です。

どれも、確かめていないことを確かめたように扱っています。
正直な報告は、「**確かめた 30 人のうち 24 人がやってきた。10 人は確かめられなかった**」です。
こう書けば、聞いた人は「本当の率は 60% から 85% の間のどこかだ」と自分で判断できます。
（数はたとえ話のための架空のものです。）

#### 小さな例 — 架空の 100 個のツール

同じことを、ツールの宣言で考えます（説明用の架空の数です）。
宣言を書いたツールが 100 個あるとします。
解析器は 60 個を読み切り、そのうち 6 個に違反を見つけました。
残りの 40 個は、途中で読み切れませんでした。

| 扱い方 | 計算 | 報告する率 | 何が問題か |
|---|---|---|---|
| (1) 読み切れなかった 40 個を「違反なし」に数える | 6 ÷ 100 | 6% | 40 個の中に隠れた違反が、黙って消える。甘く見える |
| (2) 読み切れなかった 40 個を分母から消す | 6 ÷ 60 | 10% | 40 個が「無かったこと」になる。数は正確そうに見えるが、答えている問いが「読み切れたツールのうち」にすり替わっている |
| (3) 分けて数える | 6 ÷ 60、ほかに不明 40 | 6% 〜 46% の間 | 読み手が、偏りの向きと大きさを自分で判断できる |

表の読み方: 3 行目の「46%」は、読み切れなかった 40 個が全部違反だったときの率で、(6 + 40) ÷ 100 = 46% と計算します。「6%」は、40 個に違反が 1 つも無かったときの率です。本当の率は、この間のどこかにあります。

#### 一歩ずつ — 3 つの扱い方を比べる

1. **率は「分子 ÷ 分母」**: 分子は違反があったもの、分母は調べたもの全体です。分子だけを正しく数えても、分母がゆがめば率はゆがみます。
2. **(1) は「黙って安全側に倒す」**: 読み切れなかったものを「違反なし」に数えると、率は低く出ます。危険を見落とす向きの誤りです（[第 21 章](ch21.md)で「誤 clear」と呼ぶもの）。
3. **(2) は「黙って分母から消す」**: 一見公平に見えますが、読み切れないものと読み切れるものの違反の率が同じだとは限りません。たとえば、大きくて複雑なツールほど読み切れず、しかも違反が多いなら、(2) は率を低く見せます。逆もありえます。どちらに偏るかは、数えていないので分かりません。
4. **(3) は「分けて、理由をつけて数える」**: 読み切れなかった件数を報告すれば、読み手は率の幅を知ることができます。さらに、**なぜ**読み切れなかったのか（呼び出し先が分からなかった、深すぎた、など）の理由を付けておけば、どこが解析器の苦手なのかも分かります。

#### 言葉の整理 — 測定研究

- **やさしい言い換え**: 世の中で、ある現象がどれくらいの割合で起きているかを測る研究。
- **正確な定義（この教科書での意味）**: 調べる対象の全体（母集団）を先に定義し、そこから選んだものを、先に決めた手続きで調べ、現象の率とその不確かさを報告する研究。「新しい道具が、既存の道具よりよく見つける」ことを示す**道具の研究**と対比して使う。
- **例**: 「宣言を書いた公開の Python の MCP サーバのうち、少なくとも何割に宣言の違反があったか」を測る。

道具の研究なら、「見つけた件数が多い」「見つける力（検出力）が高い」ことが成果になります。
測定研究では、見つけた件数の多さよりも、**分母を正しく定義し、数え方を先に決め、決められなかったものも報告する**ことが成果の中身になります。

#### 言葉の整理 — 不（と内）

- **やさしい言い換え**: 解析器の「決められない」。
- **正確な定義**: 解析器の答えの 1 つ。ある宣言について、効果は見つけたが、それが宣言に反するかがコードからは決まらないもの。「違反」とも「違反なし」とも言わず、理由の名前を付けて別に数える（[第 17 章](ch17.md)の原理 2）。
- **例**: 6.3 節の 4 行目。D1 のツールが POST を送るとき、解析器は D1 の不を出し、理由の名前に `net_post`（POST の意味が決まらない）を付ける。

ついでに、**内**も定義しておきます。
内は、効果が宣言の範囲に収まっている、という解析器の答えです（6.3 節の 2 行目）。
矛・不・内の 3 つの正確な決め方は、[第 17 章](ch17.md)で見ます。

#### 解析器の中の約束 — 「決して潰さない、決して捨てない」

この芯は、解析器のコードの中にも、約束として書き込まれています。
値を読み切れなかったときの理由の一覧と、値の「確度」（読み切れたかどうか）を表す部品を見ます。

```python
VAL_OPAQUE_REASONS = frozenset(
    {
        "depth",  # Def 4 の下向き深さ超過
        "unresolved",  # 木内で解決できない呼び出し
        "receiver",  # 受け手アクセスパスが深さ 2 を超える
        "recursion",  # 再帰
        "dynamic",  # 動的な属性 / 添字アクセス
        "cap",  # §5.2 の cap 到達
        "loop",  # 2 周固定点が安定しなかったループ本体
        "context",  # ゲート条件が呼び出し元引数に依存し文脈非依存サマリでは決まらない
    }
)
```

```python
class Prov:
    """確度。``resolved`` / ``opaque(reason)`` / ``remote`` の 3 値。

    `reasons` は val 側語彙（:data:`VAL_OPAQUE_REASONS`）のみを取る。
    **決して clean に潰さない。決して drop しない。**
    """
```

1 つ目のコードから、1 行ずつ見ます。

- 1 行目: `VAL_OPAQUE_REASONS` という名前で、「値を読み切れなかった理由」の一覧を作ります。`frozenset` は、後から中身を足したり消したりできない集まりです。一覧を勝手に増やせないようにしています。
- 3〜10 行目: 理由の名前が 8 つ並んでいます。`#` の後ろは人のためのメモ（コメント）で、プログラムの動きには関係しません。たとえば `depth` は「呼び出しをたどる深さの上限を超えた」、`unresolved` は「木の中で、呼び出し先の関数を突き止められなかった」、`dynamic` は「取り出す属性の名前や、`[]` の中の添字が実行時に決まるので、何が取り出されるか分からない」という意味です。8 つの意味は[第 14 章](ch14.md)で 1 つずつ見ます。

2 つ目のコードは、値の確度を表す部品の説明文です。

- 1 行目: `Prov` という部品（クラス）を定義します。Prov は provenance（出どころ、確かさ）の略です。
- 2 行目: 確度は 3 つの値のどれかだ、と説明しています。判定で出会うのは、`resolved`（読み切れた）と `opaque`（途中で見失った）の 2 つです（[第 14 章](ch14.md)）。`opaque` には、括弧の中に理由が付きます。
- 4 行目: 理由には、1 つ目のコードの一覧の名前しか使えない、と言っています。一覧に無い理由を付けようとすると、プログラムが止まって知らせます（説明文のすぐ後に、そう確かめるコードがあります。ここでは省きました）。
- 5 行目: 「**決して clean に潰さない。決して drop しない。**」これが約束です。clean は「問題なし」、drop は「捨てる」という意味です。読み切れなかった値を「問題なし」に変えない、記録から捨てない、と言っています。

この約束のほかに、解析器は、大きすぎるファイルや時間切れで処理を打ち切ったことも、打ち切りの記録として出力に残します。
読み切れなかった所を、理由と一緒に全部残すわけです。
宣言に反するかの「不」にも、別に理由の名前（`net_post` など）が付きます。不の理由の名前の一覧は[第 17 章](ch17.md)で見ます。
（出典: `authgap/ir.py:126-137`（理由の一覧）、`:165-182`（`Prov` と、一覧に無い理由を拒む確かめ）、`docs/related_work.md:27`（理由と打ち切りの記録で残し、率を報告する））

#### なぜ、これが芯なのか

理由は 3 つあります。

1. **問いが「率」だから**: この研究の問いは、「宣言がどれだけ当てにならないか」という率の問いです（決定 D40）。上の架空の例のとおり、読み切れなかったものを黙って処理すると、率そのものがゆがみます。率の問いに答えるには、読み切れなかったものを数えることが欠かせません。
2. **「当てにならない」こと自体は、もう分かっているから**: [第 4 章](ch04.md)の 4.6 節で見たとおり、MCP の資料自身が「注記はヒントで、振る舞いを忠実に表している保証は無い」と書いています。本記録者は先行研究の調査で、この点を「宣言が当てにならないことは公式に認知済みで、残る問いは『**実際にどれだけ当てにならないか**』である。これは測定研究の問いである」とまとめています。だから、この研究の価値は「ずれがある」と言うことではなく、「どれだけあるか」を正直に測ることにあります。
3. **最も近い先行の道具が、ここを持っていないから**: 次の 6.5 節で見る HintLint には、「読み切れなかった」を表す言葉がありません。この研究と先行の道具との差は、「解決できなかったものをどう扱うか」に尽きる、と本記録者は先行研究の記録に書いています。これを受けて、この研究は「**測定研究として立て直す**」と判断されました（O19 の判断 (a)、決定 D40。決定の記録には、誰が判断したかは書かれていません）。

（出典: `docs/related_work.md:24-27`（差は解決できなかったものの扱い）、`:320-329`（公式の立場と「残る問い」）、`docs/decisions.md:1866-1868`（D40 の決定 1））

#### よくある誤解・つまずき

- **誤解: 「不は解析器の失敗だから、少ないほどよい」**

- **誤解: 「不を全部『違反』に数えれば、安全側だからよい」**
  それも「倒す」ことです。規則 4 は「黙って安全側に倒さない」と書いています。原理 2 の理由も「b / c（ほかの 2 つの案）は測定を既知の向きに偏らせる」です。違反の側に倒しても、違反なしの側に倒しても、率はゆがみます。
- **誤解: 「測定研究なのだから、道具の出来はどうでもよい」**
  逆です。測定の道具（解析器）がどれだけ当たるかが分からなければ、測った率も信じられません。だから最終評価で、解析器の答えを人が確かめます（6.6 節）。
- **誤解: 「不明を数えるのは、解析器だけの話」**
  人の判定にも同じ約束があります。人が原ソースを読んでも決められないものは、判定でも「不明」にします（次の「手作業ではどう使うか」）。

#### 手作業ではどう使うか

判定の手引きは、「不明」について次のように書いています。

> 不明は失敗ではない。**分からないものを黙って正や誤に倒さないこと**が、この研究の約束である（CLAUDE.md 規則 4）。
> ただし、調べれば分かるものを不明にしない。目安として、**20〜30 分調べても決められなければ不明**にし、理由を書く。

判定では、この 2 つの文を両方守ります。

1. **分からないものを、正にも誤にも倒さない**: たとえば、相手のサーバの API の意味が、文書にもコードにも無いなら、「たぶん読むだけだろう」と誤にせず、不明にして理由を書きます。
2. **調べれば分かるものを、不明に逃がさない**: 20〜30 分調べれば決められるものは、決めます。不明を「迷ったときの逃げ道」にすると、不明の件数が判定者の根気の量を表すだけになってしまいます。

集計では、不明の件数と理由の内訳を報告します。
精度は、不明を除いた値（正 ÷ (正 + 誤)）を主にし、不明を誤とみなした値（正 ÷ (正 + 誤 + 不明)）と不明の件数を併記します（D70 の 5。計算は[第 39 章](ch39.md)）。
（出典: `docs/drafts/final_judging_guide_draft.md:549-550`（第 19 節）、`docs/decisions.md:3910-3911`（D70 の 5））

#### この節のまとめ

この研究は「宣言がどれだけ当てにならないか」という率を測る測定研究。率を正しく測るため、読み切れなかったものを「違反なし」にも「分母の外」にもせず、理由つきで別に数える。これが研究の芯で、解析器のコードにも「決して潰さない、決して捨てない」と書かれている。
同じ芯から、原理 2・D69 の 4・D70 の 2・3・5・D71 の理由 2 などが出てくる。判定でも、分からないものは理由つきの「不明」にし、調べれば分かるものは決める。

### 6.5 最も近い先行の道具 — HintLint との違い

#### 一言で言うと

**HintLint** は、MCP の宣言と実装の食い違いを静的に見つける、この研究に最も近い先行の道具です。
けれども、Python を行単位の文字の型（正規表現）で読み、ツールの関数の本体だけを見て、呼び出しを追わず、「読み切れなかった」を表す言葉を持ちません。
しかも、比べられた指摘の大半は「宣言が**無い**」ツールについてのものでした。
つまり、**問いが違います**。この研究は、HintLint より先に照合したとも、HintLint よりよく見つけるとも主張しません。

#### たとえ話 — 2 人の検査員

6.1 節のレストランに、2 人の検査員がいたとします。

**検査員 A** は、毎日の仕込みの前に、手早く点検する係です。
各レシピのカードの 1 枚目だけを見て、「卵」という文字が決まった書き方で出てくる行を探します。
「ソースはカード 12 番」と書いてあっても、12 番はめくりません。
「卵」という文字が見つからなければ、何も書きません。
そして、A がいちばん多く指摘するのは「この料理には、アレルギーの表示がありません」という点です。

**検査員 B** は、地域の何割の店の表示が正しいかを調べる調査員です。
「卵不使用」と表示した料理だけを対象にし、参照されたカードを何枚もたどります。
読めないカードがあれば、「読めなかった」と書いて数えます。

A と B のどちらが優れている、という話ではありません。
A は毎日の点検の道具として、手早く確かなものだけを指摘します。
B は、表示の正しさの**率**を調べるために、読めなかったものまで数えます。
仕事が違うのです。
HintLint は A に、この研究の解析器は B に近い立場にあります。

#### 小さな例 — 本体だけを、行の型で読むと

[第 1 章](ch01.md)で見た説明用のコードを、もう一度見ます。

```python
# 説明用（第 1 章）
def get_weather(city):
    """天気を調べて返すだけ。"""
    data = fetch_forecast(city)
    remember(city)                # ← 別の関数を呼んでいる
    return data

def remember(city):
    with open("history.txt", "a") as f:   # ← その先で、ファイルに追記している
        f.write(city + "\n")
```

`get_weather` がツールだとします。
書き込みは、ツールの本体ではなく、呼んだ先の `remember` の中にあります。
**ツールの関数の本体だけを読む道具には、この書き込みは見えません。**

もう 1 つ、HintLint がファイルの書き込みを探すときに使う型を見ます。
本記録者が HintLint のソースを読んで写したものです。

```
/\bopen\s*\([^)]*(?:destination|path|file|artifact)[^)]*["'](?:w|a|wb|ab)["']/i
```

記号が多いので、左から部品に分けて読みます。

- `\b` は「単語の切れ目」です。`reopen` のような別の単語の途中に当たらないようにしています。
- `open` は、文字どおり `open` という文字の並びです。
- `\s*` は「空白が 0 個以上」、`\(` は開き括弧 `(` そのものです。
- `[^)]*` は「閉じ括弧 `)` 以外の文字が 0 個以上」です。括弧の中身を、閉じるまで読み進めます。
- `(?:destination|path|file|artifact)` は、「`destination`・`path`・`file`・`artifact` の 4 つの語のどれか」です。
- `["'](?:w|a|wb|ab)["']` は、引用符で囲んだ `w`・`a`・`wb`・`ab` のどれか、つまり書き込み用の開き方です。
- 最後の `/i` は、大文字と小文字を区別しない、という指定です。

つまりこの型は、「`open(` の括弧の中に、4 つの語のどれかと、書き込み用の開き方が書いてある行」に当たります。
だから `open(path, "w")` には当たりますが、`open(f, "w")` には当たりません。
どちらも同じようにファイルに書き込むのに、**変数の名前しだいで、見えたり見えなかったりする**のです。
（出典: `docs/related_work.md:140-143`）

#### 言葉の整理 — 正規表現

- **やさしい言い換え**: 文字の並びの「型」。
- **正確な定義**: 文字列の中から、決まった並び方の部分を探すための書き方。`\s*`（空白が 0 個以上）や `[^)]*`（`)` 以外の文字が 0 個以上）のように、記号で型を表す。
- **例**: 上の型は、「`open(` の後に `path` などの語と、引用符つきの `w` などがある」並びを探す。

正規表現は、文字の並びを見るだけで、プログラムの意味（どの変数に何が入っているか、どの関数が呼ばれるか）は見ません。
この研究の解析器は、プログラムを文法の構造として読み、値の出どころを追い、呼び出しを何段もたどります（今の設定では深さ 4 まで。第 4 部、とくに[第 15 章](ch15.md)）。

#### 一歩ずつ — 一次資料で確かめた 3 つの事実

本記録者は、HintLint（`complira/hintlint`）のソースを読み、母集団 v2 の 87 木（[第 5 章](ch05.md)）のすべてで実際に走らせました（決定 D40、2026-09-22）。
ホームページの説明ではなく、ソースと実行結果から確かめたことは、次の 3 つです。

1. **Python は、行単位の正規表現で読む。** ツールの印（`@...tool`）を正規表現で探し、そこから次の `def` か次の `@tool` までの行を集めます。だから、判定に使う文字は**そのツールの関数の本体だけ**になります。プログラムを文法の構造として読むことはしません。
2. **呼び出しを追わない。** HintLint には、呼び出しの先をたどる仕組み（到達解析）がありますが、それは TypeScript 用で、Python 側には使われていません。上の `get_weather` → `remember` のような書き込みは見えません。
3. **「読み切れなかった」を表す言葉が無い。** 確かさを表す言葉は `source-backed`（ソースに根拠がある）と `needs-review`（見直しが要る）の 2 つだけです。正規表現に当たらなければ、何も残りません。読み切れなかったものは、記録にも分母にも現れないのです。

3 つ目が、6.4 節の芯とまっすぐ対立する点です。
HintLint には、「宣言がどれだけ当てにならないか」という率の問いに答えるための数え方が、そもそもありません。
（出典: `docs/decisions.md:1807-1814`（3 つの事実）、`docs/related_work.md:68-77`（同じ内容の詳しい記録）、`:24-26`（率の問いには答えられない））

### 6.6 解析器の 3 つの答えと、最終評価での確かめ方

#### 一言で言うと

解析器は、ツールと宣言の組ごとに、「**矛**」（宣言に反する）、「**不**」（決められない）、「**何も出さない**」（宣言の範囲内か、効果が見つからない）の 3 つのどれかを答えます。
最終評価では、3 つの答えのそれぞれを人が原ソースで確かめます。
矛は「**精度**」（V2）、不は「**不の中身**」（V6）、何も出さなかったものは「**見落とし**」（V3）として確かめます。

#### たとえ話 — 空港の手荷物検査

空港の手荷物の検査機は、かばんを通すと 3 つのどれかを答えるとします。
「危険物あり」「判別できない（係員が開けて確かめる）」「何も言わない（通ってよい）」の 3 つです。

この検査機がどれだけ信用できるかを調べるには、3 つの答えをそれぞれ確かめる必要があります。

- 「危険物あり」と言ったかばんを開けて、本当に危険物が入っていたかを見る。→ 当たりの割合（精度）。
- 「判別できない」と言ったかばんを開けて、中身が何だったかを見る。→ 判別できなかったものの中身。
- 「何も言わない」で通したかばんのいくつかを、手で開けて調べる。→ 見逃しが無いか（見落とし）。

1 つだけを確かめても、検査機の信用度は分かりません。
たとえば、「危険物あり」をめったに言わない検査機は、言ったときの当たりの割合は高いかもしれませんが、たくさん見逃しているかもしれません。
3 つをそろえて、初めて「この検査機の答えのそれぞれが、どれだけ当たっていたか」が言えます。
加えて、検査機そのものが途中で止まったり壊れたりしないか（頑健性）も数えます。

#### 小さな例 — 作例のサーバを、実際に解析器にかける

この章のために、4 つのツールを持つ説明用のサーバを書きました。
どのツールも、`readOnlyHint=True`（D1）と宣言しています。

```python
# 説明用（この章の作例）
import os

import requests
from loguru import logger
from mcp.server.fastmcp import FastMCP
from mcp.types import ToolAnnotations

mcp = FastMCP("notes")
logger.add("count.log")


@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def show_note(name: str) -> str:
    with open("notes/" + name) as f:
        return f.read()


@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def export_note(name: str, path: str) -> str:
    text = show_note(name)
    with open(path, "w") as f:
        f.write(text)
    return "ok"


@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def share_note(name: str, url: str) -> str:
    text = show_note(name)
    requests.post(url, data=text)
    return "sent"


@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def count_notes() -> int:
    n = len(os.listdir("notes"))
    logger.info(f"counted {n}")
    return n
```

#### 一歩ずつ — 表の 3 行を作例に当てはめる

1. **精度**: 作例の `export_note` の矛は、矛の判定の対象になりえます。判定すると正です。
2. **不の中身**: `share_note` の不は、不の中身の判定の対象になりえます（D1 の不の組を持つ木から 50 木を選ぶので、この木が選ばれれば）。
3. **見落とし**: 見落としの対象は「D1 か D2 を明示し、その宣言への矛が 1 件も出ていないツール」です。作例では、`show_note`・`share_note`・`count_notes` の 3 つが当たります。`export_note` は矛が出ているので対象外です。
   - `show_note` が選ばれたら、結果は「反する動作は無い」。
   - `share_note` が選ばれたら、人が読んで見つける POST に解析器が不を出しているので、結果は「解析器が不として出している」。
   - `count_notes` が選ばれたら、ログの書き込みに解析器が矛も不も出していないので、結果は「見落とし」（原因は語彙）。

見落としの対象に、不を出したツールも入っていることに注意してください。
参考までに、v4 の見落としの抜き取り 30 件では、「反する動作は無い」14、「解析器が不として出している」10、「見落とし」4、「不明」2 でした（本記録者の判定で、論文には使わない数です）。
「解析器が不として出している」は、珍しい結果ではないのです。
（出典: `docs/population_v4.md:106-107`）

#### 言葉の整理 — 精度・不の中身・見落とし・頑健性

- **精度**
  - やさしい言い換え: 解析器が「違反だ」と言ったもののうち、本当に違反だった割合。
  - 正確な定義: 判定した矛の組のうち、人が正と判定したものの割合。主の値は 正 ÷ (正 + 誤) で、不明を除く（D70 の 5）。報告は木の単位で束ねる（D67 の 3。[第 39 章](ch39.md)）。
  - 例: 矛を 3 件判定して、正 2・誤 1 なら、件数で数えた精度は 2 ÷ 3。
- **不の中身**
  - やさしい言い換え: 解析器が「決められない」と言ったものの、本当の姿。
  - 正確な定義: 解析器が不を出した組を抜き取り、人が到達と宣言違反を判定して、違反 / 違反でない / 不明を付けたものの内訳。
  - 例: 作例の `share_note` の POST の送り先が何かを作るなら違反、検索するだけなら違反でない。
- **見落とし**
  - やさしい言い換え: 本当は違反があるのに、解析器が何も言わなかったこと。
  - 正確な定義: 宣言に反する動作があるのに、解析器がその動作に矛も不も出していないこと。誤りの向きで言えば、危険を見落とす向き（[第 21 章](ch21.md)の「誤 clear」）。
  - 例: 作例の `count_notes` のログの書き込み。
- **頑健性**
  - やさしい言い換え: 解析器が、新しいデータで壊れずに最後まで動くか。
  - 正確な定義: 走査で、読めなかったファイル・時間の上限で打ち切った木・途中で止まった木を全部数え、原因を書いたもの。
  - 例: v4 の走査では、88 木すべてが最後まで動き、時間の上限による打ち切りは 0 でした（`docs/population_v4.md:73`）。

#### 言葉の整理 — 機械の言葉と、人の言葉

ここで、取り違えやすい言葉を区別しておきます。
**解析器（機械）の言葉と、人の判定の言葉は、別の言葉です。**

| 場面 | 解析器（機械）が言うこと | 人が付けること |
|---|---|---|
| 矛の判定 | 矛（宣言に反する） | 正 / 誤 / 不明 |
| 不の中身の判定 | 不（静的に決められない） | 違反 / 違反でない / 不明 |
| 見落としの判定 | 矛を出していない（不・内・効果なし） | 反する動作は無い / 解析器が不として出している / 見落とし / 見落とし（深さ 4 の外）/ 不明 |

表の読み方: 1 行目は「解析器が矛と言った組に、人は正・誤・不明のどれかを付ける」と読みます。

とくに、**解析器の「不」と、人の「不明」は違います。**
解析器の「不」は、「機械が、コードの字面からは決められなかった」という意味です。
人の「不明」は、「人が原ソースを読み、調べても決められなかった」という意味です。
解析器が不と言ったものでも、人が調べれば違反か違反でないかを決められることがよくあります（POST の送り先の文書を読む、など）。
逆に、解析器が矛と言ったものでも、人が読んで決められず不明になることもあります。
この対照は、[付録 F](appendix-f.md) に表でまとめてあります。
（出典: `docs/final_evaluation_procedure.md:100-101`（矛・内・不と、正・誤・不明））

#### なぜ 3 つとも確かめるのか — D69 の 4

最終評価の規模を決めたとき（決定 D69、2026-09-30）、本記録者が示した 3 つの規模の案から学生が選んだ案 C には、不の中身の判定が新しく入っていました。
理由は、「**精度・見落とし・不の中身がそろえば、解析器の 3 つの答えのそれぞれがどれだけ当たっていたかを示せる。これまで不の中身は一度も測っていない**」です。
v3・v4 の検証では、不は件数と理由を数えるだけで、中身を人が確かめたことはありませんでした。

これは、6.4 節の芯（不明を数える）を、解析器自身の評価にも当てたものです。
解析器の不を「数えて終わり」にせず、その中身がどれくらい違反だったかまで確かめれば、読み手は「解析器の不のうち、どれくらいが本当は違反だったのか」を知ることができます。
6.4 節の架空の例で言えば、「6% 〜 46% の間」の幅を、人の判定で狭めることにあたります。

もう 1 つ、見落としの判定は「**解析器の出力を見る前に**」行います。
先に解析器の答えを見ると、人の目がそれに引っぱられるからです。
まず自分で原ソースを読み、宣言に反しうる動作を全部書き出してから、解析器の出力と照らします。
（出典: `docs/decisions.md:3828-3831`（D69 の 4）、`docs/final_evaluation_procedure.md:167`（出力を見る前に判定する）、`docs/drafts/final_judging_guide_draft.md:454-463`（見落としの判定の順序））

#### よくある誤解・つまずき

- **誤解: 「解析器の『不』と、人の『不明』は同じ」**
  違います。機械が決められなかったものと、人が調べても決められなかったものです。
- **誤解: 「見落としの対象は、効果が 1 つも無いツールだけ」**
  違います。その宣言への矛が出ていなければ、不を出したツールも対象です。結果が「解析器が不として出している」になることも多くあります。
- **誤解: 「見落としの抜き取りでは、D3・D4 のツールも選ぶ」**
  見落としの対象は、D1 か D2 を明示したツールです。
- **誤解: 「V4 の不と V6 の不の中身は同じもの」**
  V4 は不の件数と理由の内訳で、人は判定しません。V6 は不の組を人が判定した結果です。
- **誤解: 「精度が高ければ、よい解析器だ」**
  精度だけでは分かりません。めったに矛を言わない解析器は精度が高くても、見落としが多いかもしれません。3 つをそろえて初めて判断できます。

#### 手作業ではどう使うか

最終評価の判定では、3 種類の判定表を使い分けます。

1. **矛の判定表**: 1 組ごとに、到達するか・宣言に反するかを答え、正 / 誤 / 不明を付ける（第 48〜51 章）。
2. **見落としの判定表**: 解析器の出力を見る前に、ツールの本体から深さ 4 までを読み、反しうる動作を書き出す。その後で解析器の出力と照らし、5 つの結果のどれかを付ける（[第 52 章](ch52.md)）。
3. **不の中身の判定表**: 不の理由の名前を手がかりに、何を調べるかを決め（POST なら相手の API の意味、など）、違反 / 違反でない / 不明を付ける（[第 52 章](ch52.md)）。

どの表でも、付ける言葉が違うことに注意してください。
矛の表に「違反」と書いたり、不の中身の表に「正」と書いたりしないようにします。
迷ったら、[付録 F](appendix-f.md)（判定の言葉の対照表）と[付録 E](appendix-e.md)（判定の早見表）を引いてください。

#### この節のまとめ

解析器の答えは、矛・不・何も出さないの 3 つ。最終評価では、矛を精度（V2）、不を不の中身（V6）、何も出さなかったもの（D1・D2 を明示したツール）を見落とし（V3）として人が確かめ、頑健性（V1）も数える。
解析器の「不」と人の「不明」は別の言葉。3 つをそろえるのは、不明を数える芯を解析器自身の評価にも当てるため（D69 の 4）。

<a id="s6-8"></a>
### 6.7 論文の結論になる数（予告）

#### 一言で言うと

最終評価で、論文の結論になる数は、「**宣言を書いたサーバのうち、少なくとも何割に違反があったか**」です。
宣言（D1〜D4）ごとに別々に出し、「少なくとも」と付けて書きます（決定 D70 の 4）。

#### たとえ話 — 抜き打ち検査の報告

ある地域で、「卵不使用」の表示をしている店が 500 軒あるとします。
検査の機械が「怪しい」と言った店が 100 軒あり、検査員がその 100 軒のそれぞれで、怪しいと言われた料理を最大 3 品だけ確かめました。
すると、60 軒で本当に表示の違反が見つかりました。

このとき、報告書には「表示をしている店のうち、**少なくとも** 60 ÷ 500 = 12% に違反があった」と書きます。
「少なくとも」と付けるのは、確かめなかった料理（4 品目以降）や、機械が「怪しい」と言わなかった店の中にも、違反があるかもしれないからです。
（数はたとえ話のための架空のものです。）

#### 小さな例 — 架空の数で、結論の文を作る

D1 について、最終評価で次の数が出たとします（説明用の架空の数です）。

| 記号 | 意味 | 架空の値 |
|---|---|---|
| 分母 (c) | D1 を明示したツールを 1 つ以上持つ、走査した木の数 | 500 |
| N | D1 の矛が出た木の数 | 100 |
| n | そのうち判定した木の数（N が 200 以下なので全部） | 100 |
| k | 判定した木のうち、正が 1 件以上あった木の数 | 60 |

- (a) = k ÷ n = 60 ÷ 100 = 60%。「解析器が D1 の矛を出した木のうち、本当に違反があった木の割合」です。
- (c) = 60 ÷ 500 = 12%。「D1 を宣言したサーバのうち、違反が見つかった木の割合」です。
- 論文の文: 「`readOnlyHint: true` を宣言したサーバのうち、少なくとも約 12% に、その宣言に反する動作があった」。

表の読み方: 3 行目の n は、判定した木の数です。N が 200 を超えたときは、200 木だけを抜き取って判定するので n = 200 になり、(c) の分子は推定になります（[第 39 章](ch39.md)）。

#### 一歩ずつ — 3 つの分母

この研究は、「違反があった木の割合」に 3 つの分母を用意しています。

1. **(a) 矛の出た木**: 解析器が矛を出した木のうち、本当に違反があった木の割合です。解析器（道具）の信用度を表します。**主**の数の 1 つです。
2. **(c) その宣言を明示したツールを持つ木**: 宣言を書いたサーバのうち、違反が見つかった木の割合です。研究の問い（宣言がどれだけ当てにならないか）への答えで、**論文の結論**になります。これも**主**です。
3. **(b) 走査した木全部**: 宣言を書いていない木も分母に入るので、数が薄まります。**参考**にとどめます。

(c) の分母は、その宣言を明示的に書いたツールを 1 つ以上持つ木です。
[第 4 章](ch04.md)で見たとおり、既定値で補ったものは数えません。
何も約束していないツールばかりの木を分母に入れたら、「宣言を書いたサーバのうち」という問いに答えていないことになるからです。
ただし、D3・D4 について「明示した」をどの欄で数えるかには、まだ決まっていない点があります（**未決**。[第 4 章](ch04.md)・[第 46 章](ch46.md)）。

#### なぜ「少なくとも」なのか — 下限

この数は**下限**です。理由は 2 つあります。

1. **1 木あたり、1 つの宣言について最大 3 件しか判定しない**: 3 件がすべて誤でも、判定しなかった残りに正があるかもしれません。
2. **矛の出なかった木の見落としを数えていない**: 解析器が矛を出さなかった木にも、違反があるかもしれません。見落としは、200 件の抜き取りで別に示します。

[第 5 章](ch05.md)の 5.4 節で見た「開発用の v2 で、解析器が D1 の矛を出した木が 87 木中 13 木」という数は、機械の生の数で、誤警報を含みうる「上限の目安」でした。
この節の数は、人が判定した「下限」です。
同じ「違反のある木の割合」でも、向きが逆です。
（出典: `docs/decisions.md:3901-3909`（D70 の 4）、`docs/final_evaluation_procedure.md:171-190`（0-4）、`:1332-1345`（23.2 の式と下限の理由）、`docs/drafts/prereg_2_12_draft.md:99-107`（事前登録の下書き。未承認））

#### なぜ (c) を結論にするのか — D70 の 4

決定 D70 の 4（2026-10-01）は、(a) と (c) を主、(b) を参考と決めました。
理由は、(a) は道具の信用度、(c) は研究の問い（D40）への答え、(b) は宣言していない木で薄まる、です。
この研究は測定研究なので、論文の結論は「道具がよく当たる」ではなく、「**宣言はこれだけ当てにならない**」という率になります。
その率に一番近いのが (c) です。
また、D1〜D4 は別々の約束なので、足し合わせず宣言ごとに出します（決定 D62）。

#### よくある誤解・つまずき

- **誤解: 「最終評価の (c) を、v2 の 13 ÷ 87 と比べて、増えた・減ったと言える」**
  言えません。片方は機械の上限の目安、片方は人の判定の下限で、データも版も違います（[第 5 章](ch05.md)）。
- **誤解: 「D1〜D4 を合わせて、1 つの『違反の率』を出す」**
  合わせません。宣言ごとに約束の中身が違うからです（D62）。
- **誤解: 「『少なくとも約 12%』は、『12%』と書いても同じ」**
  違います。「少なくとも」を落とすと、下限を「ちょうどの値」のように見せてしまいます。
- **つまずき: [第 39 章](ch39.md)で出てくる記号 M_d と、この章の M（実効の権限）を混同する**
  [第 39 章](ch39.md)では、(c) の分母（その宣言を明示したツールを持つ木の数）に M_d という記号を使います。名前は似ていますが、この章の M（実効の権限）とは関係のない、別の記号です。

#### 手作業ではどう使うか

- **木の単位で考える**: 判定は 1 件ずつですが、結論の数は木の単位です。1 つの木で 1 件でも正があれば、その木は k に数えられます。それでも、選ばれた件（最大 3 件）はすべて判定します。木ごとの精度（[第 39 章](ch39.md)）にも使うからです。
- **「3 件とも誤」は「違反なし」ではない**: ある木で 3 件がすべて誤でも、その木に違反が無いとは言えません。判定表には判定した結果だけを書き、「この木は違反なし」とまとめて書かないでください。
- **集計と論文**（段階 8・9）: 計算のしかたは[第 39 章](ch39.md)、論文での書き方は[第 55 章](ch55.md)で見ます。どちらでも「少なくとも」を落とさないでください。

#### この節のまとめ

論文の結論になる数は、「その宣言を明示したツールを持つ木」を分母 (c) にした、違反が見つかった木の割合。宣言ごとに出し、下限なので「少なくとも約 X%」と書く（D70 の 4）。
(a) は道具の信用度で、これも主。(b) は参考。開発用の v2 の数（上限の目安）とは向きが逆なので比べない。

### 6.8 名前の由来

**一言で言うと**: AuthGap の Auth は authority（権限）、Gap は「ずれ・すき間」で、「**権限のずれ**」を見つける研究、という意味です。

**たとえ話と例**: 6.2 節の入館証で言えば、印刷された「1 階のみ」（宣言）と、カードで実際に開く「1〜3 階」（実効の権限）の間の「2〜3 階」の部分が gap です。
作例の `export_note` なら、「読むだけ」の宣言と、「LLM が選んだ場所に書ける」実効の権限の間の、書き込みの部分が gap にあたります。

**注意**: 名前の由来は、仕様書には書かれていません。
これは、この教科書が第 3 版から使っている説明です（第 3 版 409 行）。
研究の中身に関わる話ではないので、覚え方の目安として使ってください。

**なぜ知っておくのか**: 名前は、研究が何を測るのかを一言で思い出す手がかりになります。「権限のずれ」と覚えておけば、「危なさ」ではなく「宣言と実効の権限の差」を見る研究だ、という 6.1 節の要点に戻れます。

**よくあるつまずき**: Auth を authentication（認証。ログインして本人だと確かめること）と読んでしまう。この研究は、ログインの仕組みを調べる研究ではありません。ここでの Auth は authority（権限）で、[第 2 章](ch02.md)で見た「ツールを通じて LLM に与えた力」のことです。

**手作業ではどう使うか**: 判定で迷ったら、「この件の gap（宣言と、できることの間のすき間）は何か」と自分に問うと、2 つの問い（到達するか・宣言に反するか）に戻りやすくなります。

**この節のまとめ**: AuthGap は「権限のずれ」。宣言と実効の権限の間のすき間を探す、という名前。

| 見落としの対象は効果の無いツールだけ | 宣言への矛が出ていなければ、不を出したツールも対象 | 6.6 |
| 論文の数は「12%」のように言い切る | 下限なので「少なくとも約 12%」と書く | 6.7 |

表の読み方: 7 行目は「『AuthGap は HintLint より優れている』とは言えない。比べられた 4 件は 2 勝 2 敗で、違うのは優劣ではなく問いと読み切れないものの扱いだ。詳しくは 6.5 節」と読みます。
左の列を読んで、「自分もそう思っていなかったか」を確かめるのに使ってください。

### この章のまとめ

- この研究（AuthGap）の一文: Python の MCP サーバについて、各ツールの宣言（D）と実際にできること（M）を、動かさずに照らし合わせ、食い違いを見つける。仕様書のもっと広い主張から、学生が「D と M の照合」1 本に絞った（D36）。
- D は作者がはっきり書いた約束 D1〜D4。M は LLM が入れうる値の全体で、ツールができること（原理 3-a）。解析器が出すのは M の推論。
- M が D を超える所を「矛」（CONTRADICTION）として報告する。範囲内は「内」、決められないものは「不」。宣言の無いツールは矛にならない。
- この研究は「宣言がどれだけ当てにならないか」という率を測る測定研究。芯は、解析できなかったものを、違反なしにも分母の外にもせず、理由つきで数えること（不明を数える）。解析器のコードにも「決して潰さない、決して捨てない」と書かれている。
- 最も近い先行の道具 HintLint は、Python を行単位の正規表現で本体だけ読み、呼び出しを追わず、読み切れないものを表す言葉が無い。比べられた 65 件のうち 61 件は宣言の無いツールへの指摘で、問いが違う。この研究は「初めて照合した」とも「よりよく見つける」とも書かない（O19 の (a)、D40）。
- 解析器の答えは矛・不・何も出さないの 3 つ。最終評価で、精度（V2）・不の中身（V6）・見落とし（V3）として人が確かめ、頑健性（V1）も数える。解析器の「不」と人の「不明」は別の言葉。
- 論文の結論になる数は「宣言を書いたサーバのうち、少なくとも何割に違反があったか」（分母 (c)、宣言ごと、下限。D70 の 4）。
