# 第 1 部 背景 — そもそも何が問題なのか

## 第 1 章 「言っていること」と「やっていること」

> **この章で分かること**: この研究が扱う問題の、いちばん根っこの形。ものごとには「言っていること」（説明）と「やっていること」（実際の動き）があり、両者はずれることがあること。ずれが悪意なしに生まれる 3 つの理由。ずれには 2 つの向きがあること。そして「どこまでを『やった』と数えるか」という、後の章で何度も戻ってくる問い。

<a id="s1-1"></a>
### この章の位置づけ

第 1 部（第 1〜5 章）は、「そもそも何が問題なのか」を説明する部です。第 1 章はその入口で、専門の言葉をほとんど使わずに、問題の形だけを取り出します。

この後の章とのつながりは、次のとおりです。

- [第 2 章](ch02.md)では、この問題が「AI が使う道具」で起きると何が特別なのかを見ます。
- 第 3・4 章では、AI の道具が「自分は何をするか」を書く決まった書き方（この章の「言っていること」にあたるもの）を見ます。
- [第 5 章](ch05.md)では、言っていることとやっていることがずれると、誰がどう困るかを見ます。

手作業（最終評価の手動判定）との関係も、ここから始まります。判定で毎回やることは、つまるところ「**言っていること**（ツールの宣言）と**やっていること**（原ソースに書かれた実際の動き）を見比べ、ずれているかを決める」ことです。この章の身近な例は、その見比べ方の練習にもなっています。

<a id="s1-2"></a>
### 身近な例 — 説明と実際の動き

**一言で言うと**: ものごとには「自分は何をするか」という説明（言っていること）と、実際の動き（やっていること）の 2 つがあり、両者が一致する保証はありません。

**たとえ話**: 次の 3 つの場面を思い浮かべてください。

- 家電の説明書に「この掃除機は自動で充電台に戻ります」と書いてあるのに、実際には戻らない。
- スマートフォンのアプリが「位置情報は使いません」と言いながら、実は使っている。
- お店の看板に「全品 500 円」とあるのに、レジでは一部の品が 700 円だった。

**小さな例**: 3 つの場面を、「言っていること」と「やっていること」に分けて表にします。

| 場面 | 言っていること | やっていること |
|---|---|---|
| 掃除機 | 自動で充電台に戻る | 戻らない |
| アプリ | 位置情報は使わない | 位置情報を使っている |
| お店 | 全品 500 円 | 一部の品は 700 円 |

**一歩ずつ**: この表の 2 つの列を、この教科書では次のように呼び分けます。

- **言っていること**: 作った人や売る人が、外に向けて示している説明です。説明書、看板、ラベル、プログラムの説明文などがこれにあたります。たとえば表の 1 行目なら「自動で充電台に戻る」です。
- **やっていること**: 実際に起きる動きです。説明書を読むだけでは分からず、実物を観察して初めて分かります。表の 1 行目なら「戻らない」です。

表の 3 行とも、左の列と右の列が食い違っています。この食い違いを、この教科書では「**ずれ**」と呼びます。

**なぜこれが大事なのか**: ふだん私たちは、**「言っていること」を見て判断しています**。掃除機を買うとき、毎回分解して中を確かめる人はいません。説明書や箱の表示を信じて選びます。アプリを入れるときも、説明を読んで「位置情報を使わないなら安心だ」と決めます。だから、言っていることとやっていることがずれていると、**判断そのものが狂います**。「安心だ」と思って入れたアプリが、実は位置情報を使っていた、ということが起きます。

つまり、ずれの怖さは、ずれそのものよりも、「説明を信じた人が、確かめるのをやめてしまう」ところにあります。この点は第 2・5 章で、AI の道具の話としてもう一度出てきます。

**よくあるつまずき**:

- **「ずれ」を「嘘」と同じだと思う。** ずれは、説明と実際の動きが食い違っている、という事実だけを指します。わざとかどうかは問いません。次の節で見るように、悪意が無くても、ずれは自然に生まれます。
- **「やっていること」は説明を読めば分かると思う。** 説明を読んで分かるのは「言っていること」だけです。やっていることを知るには、実物を見なければなりません。ソフトウェアなら、実物はプログラムのコードです。

**手作業ではどう使うか**: 最終評価の判定は、この表を 1 件ずつ作る作業だと思ってください。左の列には「ツールの宣言」（[第 4 章](ch04.md)で説明する、ツールが自分について書く短い約束）、右の列には「原ソースを読んで分かった実際の動き」が入ります。判定では、右の列を**説明から推測せず、必ずコードを読んで**埋めます。判定の手引きも、判定するのは「コードの動作で、解析器の説明ではない」と書いています（出典: `docs/drafts/final_judging_guide_draft.md:51-52`。[第 48 章](ch48.md)）。

**この節のまとめ**: ものごとには「言っていること」と「やっていること」があり、ずれることがある。人はふだん言っていることを見て判断するので、ずれると判断が狂う。判定では、やっていることを必ず実物（コード）で確かめる。

<a id="s1-3"></a>
### ソフトウェアでも同じことが起きる

**一言で言うと**: ソフトウェアにも説明がたくさん付いていて、説明と実際の動きがずれることがあります。

**たとえ話**: 引き出しに「文房具」とラベルが貼ってあるのに、開けてみると電池も入っていた、という場面を考えてください。ラベル（説明）を書いた人は、そのときは文房具しか入れていなかったのかもしれません。けれども、ラベルを見ただけでは中身は分かりません。開けて（コードを読んで）初めて分かります。

**小さな例**: 次は、説明のために作った Python のコードです。

```python
# 説明用
def load_settings(path):
    """設定ファイルを読むだけ。何も書き換えない。"""
    data = open(path).read()
    open(path + ".bak", "w").write(data)   # ← 実はバックアップを書いている
    return data
```

**一歩ずつ**: 1 行ずつ読んでみます。

- 1 行目の `# 説明用` は、コメント（実行されないメモ）です。[第 0 章](ch00.md)で見たとおり、この教科書では、実在のサーバのものではないコードにこの印を付けます。
- 2 行目の `def load_settings(path):` は、「`load_settings` という名前の**関数**（処理のまとまりに名前を付けたもの）を作る。外から `path` という値を受け取る」という意味です。外から受け取る値を**引数**（ひきすう）と呼びます。ここでは `path` が引数で、中身はファイルの場所（たとえば `"settings.txt"`）です。
- 3 行目の `"""..."""` で囲んだ部分は、関数の**説明文**です。Python では **docstring**（ドックストリング）と呼びます。正確には、関数の本体のいちばん最初に置いた文字列で、プログラムの動きには何の影響もありません。ここには「読むだけ。何も書き換えない」とあります。これが「**言っていること**」です。
- 4 行目の `data = open(path).read()` は、`path` のファイルを開いて、中身を全部読み、`data` という名前の入れ物（変数）に入れます。`open(path)` のように開き方を書かないと、**読み取り用**で開きます。
- 5 行目の `open(path + ".bak", "w").write(data)` が問題の行です。`path + ".bak"` は、ファイルの場所の後ろに `.bak` をつないだ、**別のファイルの名前**です（`"settings.txt"` なら `"settings.txt.bak"`）。`"w"` は「**書き込み用**に開く」という指定です。書き込み用に開くと、そのファイルが無ければ新しく作り、あれば中身を消して書き直します。`.write(data)` は、読んだ中身をそのファイルに書き込みます。これが「**やっていること**」の一部です。
- 6 行目の `return data` は、読んだ中身を、この関数を呼んだ側に返します。

説明には「読むだけ」とありますが、実際には `.bak` という別のファイルを**作って書いて**います。書いた結果は、関数が終わった後も、プログラムが終わった後も、ディスク（コンピュータの記憶装置）に残ります。

**なぜこれが問題になるのか**: docstring は、プログラムとして実行されません。だから、中身がコードと食い違っていても、Python は何も文句を言いません。誰かが読んで気づかない限り、ずれは残り続けます。この研究が「説明を読む」のではなく「コードを読む」解析器を作ったのは、このためです（[第 7 章](ch07.md)）。

**よくあるつまずき**:

- **「元の設定ファイルは書き換えていないから、『何も書き換えない』は守られている」と考える。** 確かに、`path` のファイルそのものは書き換えていません。けれども、`.bak` という別のファイルを作り、もし前からあれば上書きしています。ディスクの上に、呼ぶ前には無かった変化が残ります。「何も書き換えない」と言っている以上、元のファイル以外に**何を書いたか**も、見比べる対象に入ります。
- **`open(...)` を見ただけで「書いている」と決める。** `open` は読むときにも使います。書くかどうかは、開き方で決まります。たとえば `"w"` や `"a"` なら書き、何も書かないか `"r"` なら読むだけです（ほかの開き方は[第 9 章](ch09.md)）。4 行目と 5 行目は、同じ `open` でも意味が逆です。

**手作業ではどう使うか**: 判定の手順 C は「効果の行を開き、本当にその操作かを確かめる」です（出典: `docs/drafts/final_judging_guide_draft.md:113`。[第 48 章](ch48.md)）。解析器が「この行で書いている」と言ってきたら、あなたはその行を開き、上の 4 行目と 5 行目のように、**開き方まで見て**本当に書いているかを確かめます。Python のファイルの開き方の一覧は[第 9 章](ch09.md)で説明します。

**この節のまとめ**: ソフトウェアの説明（docstring など）は実行されないので、コードとずれても誰も気づかないことがある。書いているかどうかは、関数の名前や説明ではなく、コードの 1 行 1 行（開き方まで）で決まる。

<a id="s1-4"></a>
### ずれはどこから来るのか

**一言で言うと**: ずれは、悪意が無くても、3 つの理由で自然に生まれます。①説明を書いた後で実装が変わった、②呼び出した先で起きていることを説明の書き手が知らなかった、③説明がもともと雑だった、の 3 つです。

**たとえ話**: 引っ越しの段ボールを思い浮かべてください。箱に「本」と書いてテープを貼ったあと、家族の誰かが空いた隙間に食器を詰めた（①後から変わった）。箱の中にさらに小さな箱があり、その中身は詰めた本人しか知らない（②中の箱）。そもそも最初から、細かいことは気にせず「雑貨」とだけ書いた（③雑な説明）。どれも、誰かがだまそうとしたわけではありません。

**小さな例 ①: 説明を書いた後で、誰かが実装を変えた。** 次の 2 つは、同じ関数の、前の版と後の版です。

```python
# 説明用（版 1）
def count_lines(path):
    """ファイルの行数を数えるだけ。"""
    with open(path) as f:
        return len(f.readlines())
```

```python
# 説明用（版 2。誰かが後から記録の処理を足した）
def count_lines(path):
    """ファイルの行数を数えるだけ。"""
    with open(path) as f:
        n = len(f.readlines())
    with open("stats.log", "a") as log:
        log.write(f"{path}: {n}\n")
    return n
```

1 行ずつ読みます。

- 版 1 の `with open(path) as f:` は、「`path` のファイルを読み取り用に開き、`f` という名前で扱う。`with` の中が終わったら自動で閉じる」という意味です。
- 版 1 の `return len(f.readlines())` は、ファイルの行を全部読み、その数（`len` は個数を数える関数）を返します。版 1 は、本当に「数えるだけ」です。
- 版 2 では、数えた結果をいったん `n` に入れます。
- 版 2 の `with open("stats.log", "a") as log:` は、`stats.log` というファイルを `"a"`（**追記**用。ファイルの終わりに書き足す。無ければ作る）で開きます。
- 版 2 の `log.write(f"{path}: {n}\n")` は、「ファイルの場所: 行数」という 1 行を書き足します。`f"..."` は、中の `{...}` に変数の値を埋め込んだ文字列です。`\n` は改行です。
- docstring は版 1 のまま「数えるだけ」です。

誰かが「どのファイルが何行か、記録を残しておこう」と思って記録の処理を足し、説明文は直し忘れました。説明文は実行されないので、直し忘れてもプログラムは問題なく動き、誰も気づきません。

**小さな例 ②: 呼び出した先で書き込みが起きているのを、説明の書き手が知らなかった。**

```python
# 説明用
def get_weather(city):
    """天気を調べて返すだけ。"""
    data = fetch_forecast(city)
    remember(city)                # ← 別の関数を呼んでいる
    return data

def remember(city):
    with open("history.txt", "a") as f:   # ← その先で、ファイルに追記している
        f.write(city + "\n")
```

- `get_weather` の中の `fetch_forecast(city)` は、天気予報を取ってくる別の関数を**呼び出し**ています（関数の名前の後ろに `(...)` を付けると、その関数が実行されます。これを「呼び出す」と言います）。ここでは、その中身は省いています。
- `remember(city)` も、別の関数の呼び出しです。
- `remember` の中で、`history.txt` を追記用（`"a"`）に開き、都市の名前を 1 行書き足しています。

`get_weather` だけを読むと、書き込みは見えません。書き込みは、呼び出した先の `remember` の中にあります。実際のプログラムでは、この「呼び出した先」がさらに別のファイルの別の関数を呼び、その先で……と何段も続きます。**説明を書いた人が、全部の段を読んでいるとは限りません。**

**実物に近い例**: 判定の手引きの下書きにある練習用のサーバ（手引きのために書いた小さなサーバで、解析器で実際に走査したもの）にも、同じ形があります。行番号つきで抜き出します（出典: `docs/drafts/final_judging_guide_draft.md:550,561,564-580`）。

```

10  def _save_cache(name, text):
11      os.makedirs(CACHE_DIR, exist_ok=True)
12      with open(os.path.join(CACHE_DIR, name), "w") as fh:
```

上から順にではなく、**呼ばれる順**に読みます。

1. 23 行目は、24 行目の関数を AI が使う道具として登録し、「読むだけ」という約束を付ける行です。書き方の詳しい意味は第 3・4 章で説明します。ここでは「この道具は『読むだけ』と言っている」とだけ読んでください。これが「言っていること」です。
2. 24〜26 行目の `search_notes` は、メモを検索する道具です（25 行目の docstring は「メモを検索する」）。本体は 26 行目の 1 行だけで、`_lookup(query)` を呼び、結果を文字列（`str`）にして返します。
3. 呼ばれた `_lookup`（16〜20 行目）は、17 行目で `notes.db` というデータベース（データを表の形でためておく仕組み。[第 10 章](ch10.md)）のファイルにつなぎ、18 行目で `SELECT`（データベースから**読むだけ**の命令。[第 10 章](ch10.md)）を実行して、結果を `rows` に入れます。
4. 19 行目で、`_lookup` はさらに `_save_cache` を呼びます。
5. 呼ばれた `_save_cache`（10〜13 行目）は、11 行目でディレクトリを作り、12〜13 行目でファイルを書き込み用（`"w"`）に開いて書き込みます。書き込む場所は、7 行目の `CACHE_DIR`（利用者のホームディレクトリの下の `.demo_cache`）の中です。

つまり、26 行目 → 19 行目 → 12 行目という順に呼び出しが進み、3 段目でファイルに書いています。24〜26 行目だけを読むと、書き込みは見えません。

この書き込みが「読むだけ」の約束に反するかどうかは、この章の最後に出てくる図書館の問いと同じ形をしています。ここでは答えを出しません。[第 53 章](ch53.md)で、このサーバを使って実際に判定の練習をします。

**小さな例 ③: 説明がもともと雑だった。** 「だいたい読むだけ」のつもりで「読むだけ」と書いた、ということもあります。書き手にとっては、記録を 1 行書くくらいは「読むだけ」の範囲だったのかもしれません。この「くらい」をどう扱うかは、この章の最後の問いにつながります。

**一歩ずつ**: 3 つの理由を、「誰が、いつ、何を知らなかったか」で並べます。

| 理由 | 誰が | いつ | 何を知らなかったか（何をしなかったか） | 例 |
|---|---|---|---|---|
| ① 実装が変わった | 後から直した人 | 説明を書いた後 | 説明文を直さなかった | `count_lines` の版 2 |
| ② 呼び出した先 | 説明を書いた人 | 説明を書いたとき | 呼び出した先の、さらに先の動き | `get_weather` → `remember`、`search_notes` → `_lookup` → `_save_cache` |
| ③ 雑な説明 | 説明を書いた人 | 説明を書いたとき | 「読むだけ」の範囲を細かく考えなかった | 記録を 1 行書くのも「読むだけ」のつもり |

表の 2 行目を例に読むと、「説明を書いた人が、書いたときに、呼び出した先のさらに先の動きを知らなかったので、ずれた」となります。どの行にも「だまそうとした人」は出てきません。

**なぜこれが大事なのか**: 悪意が要らないということは、**ずれはどこにでも、普通に起こりうる**ということです。だから、「この開発者は信頼できるから大丈夫」とは言えません。信頼できる開発者でも、①〜③は起こります。この研究が、作った人の意図ではなく、**コードの動きだけ**を見るのはこのためです。

とくに②は、ずれを見つける道具の作り方にも効きます。ツールの関数の本体だけを読む道具は、②の形のずれを見逃します。[第 6 章](ch06.md)で見る先行研究の道具の 1 つは、Python のツールについて、ツールの関数の本体だけを読み、呼び出しを追いません（出典: `docs/decisions.md:1807-1811`、D40）。この研究の解析器が呼び出しをたどるのは、②の形を見逃さないためです（[第 15 章](ch15.md)）。

**よくあるつまずき**:

- **「説明を書いた人が悪い」と考える。** ①〜③のどれも、責める相手がいるとは限りません。この研究は、誰かを責めるためではなく、ずれがどれくらいあるかを測るために行います（[第 6 章](ch06.md)）。
- **関数の本体だけを読んで「書き込みは無い」と決める。** `search_notes` の本体は 1 行で、書き込みは見えません。呼び出した先まで読まないと、やっていることは分かりません。
- **関数の名前で中身を決める。** `_save_cache`（キャッシュ＝後で使うための控え、を保存する）という名前から「キャッシュだろう」と決めつけず、実際に何をしているかで考えます。名前は、説明文と同じく「言っていること」の一種です。

**手作業ではどう使うか**: 判定の手順 D は「ツールの入口から効果まで、自分で道筋をたどる」です（出典: `docs/drafts/final_judging_guide_draft.md:128`。[第 48 章](ch48.md)）。上の `search_notes` で、26 行目 → 19 行目 → 12 行目とたどったのが、まさにこの作業です。解析器も「道筋」（どの関数を通って書き込みに着いたか）を出しますが、それは「解析器の言い分」で、自分でたどるときの地図にすぎません（出典: `docs/drafts/final_judging_guide_draft.md:105-108`）。たどった結果は、判定表の `evidence` 欄に、たとえば `server.py:26 → server.py:19 → server.py:12` のようにファイルと行の連なりで書きます（出典: `docs/drafts/final_judging_guide_draft.md:618-619`）。

見落としの判定（解析器が何も出さなかったツールに、本当にずれが無いかを確かめる作業。[第 52 章](ch52.md)）では、解析器の出力を見る前にコードを先に読みます。先入観を避けるためです（出典: `docs/drafts/final_judging_guide_draft.md:448`）。説明文や名前を信じず、呼び出した先まで読む、というこの節の姿勢がそのまま使えます。

**この節のまとめ**: ずれは、①実装の変更、②呼び出した先の動き、③雑な説明、から悪意なしに生まれる。とくに②は、関数の本体だけを読んでも見えない。判定では、入口から書き込みまでの道筋を自分でたどり、ファイルと行で記録する。

<a id="s1-5"></a>
### ずれには向きがある

**一言で言うと**: ずれには 2 つの向きがあります。「**言っているより多くのことをやっている**」と「**言っているより少ないことしかやっていない**」です。この研究が探すのは、前者の向きです。

**たとえ話**: ホテルの部屋の札を考えてください。「清掃不要」の札を掛けたのに、清掃係が入って部屋の物を動かした。これは「言っているより多くやった」向きです。反対に、「清掃してください」の札を掛けたのに、誰も来なかった。これは「言っているより少なくしかやらなかった」向きです。どちらも札と実際が食い違っていますが、困り方が違います。前者では、知らないうちに自分の物が動かされます。後者では、部屋が散らかったままになるだけで、知らないうちに何かが変わることはありません。

**小さな例**: これまでの例に、向きの列を足します。

| 例 | 言っていること | やっていること | 向き |
|---|---|---|---|
| 掃除機 | 自動で充電台に戻る | 戻らない | 少なくやる |
| アプリ | 位置情報は使わない | 使っている | **多くやる** |
| お店 | 全品 500 円 | 一部は 700 円取る | **多くやる** |
| `load_settings` | 読むだけ | `.bak` を書く | **多くやる** |
| `count_lines`（版 2） | 数えるだけ | `stats.log` に追記する | **多くやる** |
| 下の `save_note` | 保存する | 画面に出すだけ | 少なくやる |

最後の行の `save_note` は、次の説明用のコードです。

```python
# 説明用
def save_note(text):
    """メモをファイルに保存する。"""
    print(text)        # 実際には画面に出すだけで、保存していない
```

- 2 行目で、`save_note` という関数を作り、`text`（メモの中身）を受け取ります。
- 3 行目の docstring は「保存する」と言っています。
- 4 行目の `print(text)` は、`text` を画面に表示するだけです。ファイルには何も書きません。

**一歩ずつ**: 表の「向き」の列を、困り方で読みます。

1. **多くやる**向き（アプリ、お店、`load_settings`、`count_lines`）では、説明を信じた人が**思わぬ被害**にあいます。位置情報が知らないうちに使われる、知らないうちに多く払う、知らないうちにファイルが作られる・上書きされる、といった被害です。共通するのは、「説明を信じて確かめなかったせいで、知らないうちに何かが起きた」ことです。
2. **少なくやる**向き（掃除機、`save_note`）では、説明を信じた人が**期待した仕事をしてもらえない**か、**必要以上に用心する**だけです。メモが保存されていないのは困りますが、それは「頼んだことがされなかった」困り方で、「頼んでいないことが勝手に起きた」困り方ではありません。

**なぜこの研究は「多くやる」向きを探すのか**: 理由は、AI の道具が書く約束の形にあります。[第 4 章](ch04.md)で見るように、AI の道具が自分について書く約束（**宣言**。[第 4 章](ch04.md)で詳しく説明します）のうち、この研究が調べる 4 つは、どれも「〜しない」「〜だけ」という**控えめな約束**です。

- 読むだけ（自分の外の何かを変えない）
- 壊さない（新しく足すだけ）
- 外の世界と関わらない（関わる範囲が閉じている）
- 何度呼んでも同じ（同じ頼み方で繰り返しても、追加の変化が無い）

この 4 つを、この研究では D1〜D4 と呼び、4 つとも主な指標として報告します（D62。[第 16 章](ch16.md)）。控えめな約束が破れるのは、「しないと言ったことを、した」ときだけです。つまり、調べるべきなのは「多くやる」向きのずれです。そして、この向きのずれが困る理由（説明を信じて確認を省いた人が被害にあう）は、[第 5 章](ch05.md)で詳しく見ます。

**よくあるつまずき**:

- **「少なくやる」向きは、ずれではないと思う。** ずれではあります。ただ、この研究の問い（控えめな約束が守られているか）の外にあるので、探さないだけです。
- **「多い」かどうかを、ふだんの感覚で決める。** 「多くやる」かどうかは、**約束の中身**で決まります。たとえば「壊さない（新しく足すだけ）」という約束なら、新しいファイルを作るだけのことは約束の範囲内で、多くやったことにはなりません。同じ約束でも、前からあるファイルを消すことは範囲の外で、多くやったことになります（出典: `docs/drafts/final_judging_guide_draft.md:329-334`。[第 50 章](ch50.md)）。
- **何も約束していない道具も、ずれていると考える。** 何も約束していなければ、破れる約束もありません。約束を書かなかった道具の扱いは[第 4 章](ch04.md)で見ます。

**手作業ではどう使うか**: 判定では、1 件ごとに 2 つの問いに答えます。「その動作は、ツールの呼び出しによって実際に起きうるか（到達するか）」と、「起きたとき、その動作は宣言に反するか」です。両方が「はい」のときだけ、解析器の指摘は正しい（正）とします（出典: `docs/drafts/final_judging_guide_draft.md:36-49`。[第 48 章](ch48.md)）。2 つ目の問いは、この節の言葉で言えば「**約束より多くやっているか**」です。判定のたびに、「この道具は何を約束していて、この動作はその約束より多いか」と自分に問いかけてください。

**この節のまとめ**: ずれには「多くやる」と「少なくやる」の 2 つの向きがある。この研究が調べる 4 つの約束（D1〜D4）はどれも控えめな約束なので、探すのは「多くやる」向き。「多い」かどうかは、約束の中身で決まる。

<a id="s1-6"></a>
### どこまでを「やった」と数えるか — 図書館のたとえ

**一言で言うと**: 「何かをやった」と数える範囲には、すぐには答えの出ない境目があります。この節では、その境目を問いとして置いておきます。答えはここでは出しません。

**たとえ話**: ある図書館では、本を棚から出して閲覧席で読むだけでも、「この本が閲覧された」という記録が図書館のシステムに残るとします。本を借りれば、もちろん貸出の記録も残ります（たとえ話です）。

あなたは図書館の入口で「今日は**見るだけ**です。何も持ち出しませんし、何も変えません」と言って入り、本を 1 冊読んで帰りました。本はもとの棚に戻し、1 ページも汚していません。けれども、図書館のシステムには「閲覧 1 回」の記録が増えました。

**小さな例**: ソフトウェアでは、同じ形が次のように現れます。

```python
# 説明用
def show_book(book_id):
    """本の中身を見せるだけ。何も変えない。"""
    text = read_book(book_id)
    with open("access.log", "a") as log:
        log.write(f"viewed {book_id}\n")
    return text
```

**一歩ずつ**: 1 行ずつ読みます。

- 2 行目で、`show_book` という関数を作り、`book_id`（本の番号）を受け取ります。
- 3 行目の docstring は「見せるだけ。何も変えない」と言っています。
- 4 行目の `read_book(book_id)` は、本の中身を読んでくる別の関数の呼び出しです（中身は省いています）。読んだ中身を `text` に入れます。
- 5 行目で、`access.log` というファイルを追記用（`"a"`）に開きます。このようなファイルを**ログ**（何が起きたかを順に書き残す記録）と呼びます。
- 6 行目で、「viewed 本の番号」という 1 行を書き足します。図書館の「閲覧 1 回」の記録にあたります。
- 7 行目で、本の中身を返します。

本の中身（`read_book` が読むもの）は、まったく変わっていません。変わったのは、`access.log` に 1 行が増えたことだけです。

**この問いを考える手がかり**: 人によって答えが分かれるはずです。次の問いを、自分に投げてみてください。

- 記録を書いたのは誰か。あなたが頼んだことか。
- 記録は、本の中身を変えたか。
- 記録は、後で誰かに見えるか。次に来た人の利用に影響するか。
- 「見るだけ」と言われた図書館の職員は、その言葉を信じて何を省くか。

**なぜこの問いを、ここで置くのか**: この問いは、ソフトウェアでは「**読むだけのはずの処理が、ログやキャッシュ（後で使うための控え）を書くのは、約束違反か**」という形で現れます。そして、実世界でも答えは割れています。ある AI の会社が道具を登録する人向けに出している案内は、「ログを書く道具は、読み取り専用と名乗ってはいけない」という向きのことを書いています **[確認]**。一方、ウェブの通信の決まり（HTTP。[第 10 章](ch10.md)）の文書は、「アクセスの記録をログに書き足すことは、安全な（何も変えない）操作の範囲内」と書いています **[確認]**（出典: `docs/incidental_writes_practice.md:22-26`）。どちらも本記録者が原文で照合したもので（[第 0 章](ch00.md)の確かさの印）、互いに逆を向いています。

この研究では、この問いへの答えを、最終評価のデータを見る前に決めてあります（[第 17 章](ch17.md)の原理）。けれども、それがなぜなのか、ほかの分野ではどう扱われているのかを理解するには、まだ道具がそろっていません。だから、ここでは問いだけを置きます。

**よくあるつまずき**:

- **すぐに「当たり前だから問題ない」と答える。** 記録が残るのは確かにありふれたことです。けれども、ありふれていることと、約束の範囲内であることは別の問いです。
- **すぐに「何か書いたのだから違反だ」と答える。** これも、約束の「何も変えない」が何を指すのかを決めないと言えません。
- **「違反か」と「どれくらい困るか」を混ぜる。** 「約束に反するか」と「反したとして、どれくらい困るか」は、別々の問いです。この研究でも、2 つを分けて扱います（第 43・51 章）。

**手作業ではどう使うか**: 判定の最中に、この形の件に必ず出会います。そのとき、**自分の感覚で「これくらいは違反と言えない」「これは違反だ」と決めてはいけません**。判定の手引きは、判定の基準を「採った原理」を字義どおりに当てることとし、自分の感覚で判断しないよう求めています（出典: `docs/drafts/final_judging_guide_draft.md:56-57`。[第 48 章](ch48.md)）。どの原理を採ったのかは[第 17 章](ch17.md)で、その理由は[第 43 章](ch43.md)で説明します。それまでは、「自分の感覚で答えを出さない問いがある」ことだけを覚えておいてください。

**この節のまとめ**: 本を「見るだけ」でも、閲覧の記録が残ることがある。ソフトウェアなら、「読むだけ」の処理がログやキャッシュを書くことがある。実世界でも扱いは割れていて、判定では自分の感覚で答えを出さない。

**「見るだけ」の約束は、破れたのでしょうか。** この問いは、[第 43 章](ch43.md)（裏方の書き込みは違反か）への伏線です。

<a id="s1-7"></a>
### この研究の的

**一言で言うと**: この研究は、「言っていること」と「やっていること」のずれを、**自動で見つける**ことを目指しています。的は「**AI が使う道具**」に絞っています。

**たとえ話**: 食品の成分表示を思い浮かべてください。箱には「保存料不使用」と書いてあります。ふつうの買い物客は、その表示を信じて買います。けれども、表示が正しいかを、誰かが中身を調べて確かめないと、表示は「言っているだけ」です。何千もの商品を人が 1 つずつ確かめるのは大変なので、検査の機械を作り、機械で広く調べ、機械が「怪しい」と言ったものの一部を人が詳しく確かめる。この研究がしているのは、AI の道具について、この検査の機械を作り、その機械がどれだけ当たるかを確かめることです。

**小さな例**: この研究の流れを、ごく大まかに書きます。

```
言っていること（道具の宣言）   ─┐
                                ├─→ 解析器 ─→ ずれている / 決められない / 何も出さない
やっていること（道具のコード） ─┘
```

- 左上の「言っていること」は、道具が自分について書いた約束です（[第 4 章](ch04.md)）。
- 左下の「やっていること」は、道具のコードです。解析器は、コードを動かさずに読みます（静的解析。[第 7 章](ch07.md)）。
- 解析器は、2 つを見比べて、「ずれている」「決められない」「何も出さない」のどれかを答えます。この 3 つの答えは、[第 6 章](ch06.md)で詳しく見ます。

**一歩ずつ**: なぜ「自動で」なのか、なぜ「AI が使う道具」なのかを、順に見ます。

1. **自動で見つける理由**: 道具の数が多すぎて、人が全部を読むことはできないからです。たとえば最終評価では、2026-09-20 の列挙をもとにした枠（3,764 件のリポジトリ）から、開発や中間検証に使った v2・v3・v4 の 300 件を除いた残りを、全部解析器で調べます（出典: `docs/decisions.md:3822`、D69 の 1）。人が確かめるのは、その中から決まった規則で抜き取った一部です（[第 47 章](ch47.md)）。
2. **AI が使う道具に絞る理由**: AI が使う道具では、「言っていること」を見て、人の確認を省くかどうかが決まることがあるからです。たとえば、ある AI のアプリは、「読むだけ」と宣言された道具を、利用者に「実行してよいですか」と尋ねずに実行します（出典: `docs/incidental_writes_practice.md:29-30,96`。詳しくは第 2・4 章）。説明がずれていると、人が確認すべき操作が、確認されずに走ります。この章の最初の節で見た「説明を信じた人が、確かめるのをやめてしまう」ことが、AI の道具では仕組みとして起きているのです。

**なぜこの的なのか**: この研究は、主張を「**宣言と、コードから読み取った実際の効果の照合**」の 1 本に絞ると決めています（D36。出典: `docs/decisions.md:185-194`）。それ以外の、もっと大きな主張は降ろしました（経緯は[第 8 章](ch08.md)）。この章の言葉で言えば、「言っていること」と「やっていること」を見比べる、という 1 点に絞ったということです。

**よくあるつまずき**:

- **「自動で見つける」から、人の判定は要らないと思う。** 解析器は、実際には通らない道を数えたり（誤警報）、道を見失ったり（見落とし）します。人が原ソースで確かめて、初めて解析器の数字をどこまで信じてよいかが分かります（出典: `docs/final_evaluation_procedure.md:78-79`。第 21・45 章）。
- **「AI が使う道具」を、AI そのものだと思う。** 調べるのは AI（言葉を扱うモデル）ではなく、AI が呼び出す道具のプログラムです。この区別は[第 2 章](ch02.md)で説明します。

**手作業ではどう使うか**: 最終評価の手動判定は、この「検査の機械」がどれだけ当たっているかを、人が確かめる作業です。機械が「ずれている」と言ったものが本当にずれているか（精度）、機械が何も言わなかったものに本当にずれが無いか（見落とし）、機械が「決められない」と言ったものの中身は何か（不の中身）を、原ソースを読んで確かめます（出典: `docs/final_evaluation_procedure.md:64-70`。[第 45 章](ch45.md)）。この章で見た「言っていることと、やっていることを見比べる」が、その 1 件 1 件の芯です。

**この節のまとめ**: この研究は、AI が使う道具について、言っていることとやっていることのずれを自動で見つける。AI の道具では、言っていることを見て人の確認が省かれることがあるので、ずれが実害につながる。人の判定は、その自動の検査がどれだけ当たるかを確かめる作業。

<a id="s1-8"></a>
### よくある誤解のまとめ

| 誤解 | 本当は | 詳しくは |
|---|---|---|
| ずれは嘘や悪意から生まれる | 実装の変更・呼び出した先の動き・雑な説明から、悪意なしに自然に生まれる | この章「ずれはどこから来るのか」 |
| 説明文（docstring）を読めば、関数が何をするか分かる | 説明文は実行されないので、コードとずれていても誰も気づかない。動きはコードで決まる | この章「ソフトウェアでも同じことが起きる」 |
| 関数の本体に書き込みが無ければ、書き込みは無い | 呼び出した先の、さらに先で書いていることがある | この章「ずれはどこから来るのか」 |
| `open` があれば書いている | 開き方で決まる（たとえば `"w"`・`"a"` なら書く、`"r"` か無指定なら読むだけ） | この章、[第 9 章](ch09.md) |
| 元のファイルを書き換えていなければ「何も書き換えない」は守られている | 「何も書き換えない」と言う以上、別のファイルを作った・上書きしたことも見比べる対象に入る | この章「ソフトウェアでも同じことが起きる」 |
| 「少なくやる」向きもこの研究で探す | この研究が調べる 4 つの約束は控えめな約束なので、探すのは「多くやる」向き | この章「ずれには向きがある」、第 4・5 章 |
| 「見るだけ」なのに記録が残るのは、当然 OK（または当然違反） | 実世界でも答えは割れている。判定では自分の感覚で決めず、先に決めた原理を当てる | この章の図書館の節、第 17・43 章 |
| 自動で見つけるなら、人の判定は要らない | 解析器には誤警報も見落としもある。人が確かめて初めて数字の信用度が分かる | この章「この研究の的」、[第 45 章](ch45.md) |

この表は、左の列を読んで「自分もそう思っていなかったか」を確かめるために使います。たとえば 4 行目なら、`open` という文字だけを見て「書いている」と思わなかったかを振り返ります。

<a id="s1-9"></a>
### この章のまとめ

- ものごとには「言っていること」（説明）と「やっていること」（実際の動き）があり、ずれることがある。人はふだん言っていることを見て判断するので、ずれると判断が狂う。
- ソフトウェアの説明（docstring など）は実行されないので、コードとずれても気づかれにくい。
- ずれは、①実装の変更、②呼び出した先の動き、③雑な説明、から悪意なしに自然に生まれる。②は、関数の本体だけを読んでも見えない。
- ずれには「多くやる」と「少なくやる」の 2 つの向きがある。この研究が調べる 4 つの約束（D1〜D4）は控えめな約束なので、探すのは「多くやる」向き。
- 「見るだけ」なのに記録が残るのは約束違反か、という問いは答えが割れる。判定では自分の感覚で答えを出さない。[第 43 章](ch43.md)で戻ってくる。
- この研究は、AI が使う道具について、このずれを自動で見つける。人の判定は、その自動の検査がどれだけ当たるかを確かめる作業。

### 演習

**演習 1-1（言っていることとやっていることを分ける）**: 次の説明用のコードについて、(1)「言っていること」、(2)「やっていること」、(3) ずれの向き（多くやる / 少なくやる）、(4) ずれが起きている行、を答えてください。

```python
# 説明用
def show_balance(user):
    """残高を表示するだけ。何も変更しない。"""
    balance = get_balance(user)
    with open("last_seen.txt", "w") as f:
        f.write(user)
    return balance
```

**演習 1-2（呼び出した先をたどる）**: 次の説明用のコード（`import` の行は省いています）で、`list_files` を呼ぶと、どこかでファイルが書かれます。`list_files` から書き込みの行までの道筋を、「関数の名前 → 関数の名前 → …」と、行番号（左端の数字）の連なりの 2 通りで書いてください。

```
 1  def list_files(folder):
 2      """フォルダの中のファイル名を一覧にするだけ。"""
 3      names = _scan(folder)
 4      return names
 5
 6  def _scan(folder):
 7      names = os.listdir(folder)
 8      _note(folder, len(names))
 9      return names
10
11  def _note(folder, n):
12      with open("scan_history.txt", "a") as f:
13          f.write(f"{folder} {n}\n")
```

**演習 1-3（図書館の問いに、今の自分の答えを書く）**: この章の図書館の問いについて、「約束は破れた / 破れていない / どちらとも言えない」のどれかと、その理由を 3 行以内で書いてください。理由には、この章の「この問いを考える手がかり」の 4 つの問いのうち、少なくとも 2 つへの自分の答えを使ってください。書いたものには日付を付けて取っておき、[第 43 章](ch43.md)を読んだ後に読み返してください。

**演習 1-4（ずれの理由を見分ける）**: 次の 3 つの場面は、この章の「ずれの 3 つの理由」（①実装の変更、②呼び出した先、③雑な説明）のどれにあたりますか。

- (a) 半年前に「一覧を返すだけ」と説明を書いた関数に、先月、別の人が「結果を一時ファイルに保存する」処理を足した。説明はそのまま。
- (b) 「検索するだけ」と説明した関数が、外部のライブラリの関数を呼んでいて、そのライブラリの関数が中で利用回数をファイルに記録していた。説明を書いた人は、そのライブラリの中身を読んでいなかった。
- (c) 「読むだけ」と説明した人に聞くと、「ログを 1 行書くのは知っていたけれど、それくらいは読むだけのうちだと思っていた」と答えた。
