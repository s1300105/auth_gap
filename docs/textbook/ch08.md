### 8.1 前身のプロジェクト — 既存の道具 Pysa に頼る設計

#### 一言で言うと

AuthGap には**前身のプロジェクト**がありました。前身は、既存の taint 解析（値に「汚れ」の印を付けて、その行き先を追う解析。すぐ下で説明します）の道具 **Pysa** を手直しせずに使い、「フレームワークの中の振り分けの壁」を手で書き下して越えさせる設計でした。
けれども、実際のアプリでは成り立ちませんでした。

仕様書の §1 は、それを次のように書いています。

> 前身プロジェクトは「呼び出し側の動的ディスパッチの壁を書き下して、無改変の Pysa に越えさせる」設計だった。

（出典: `AUTHGAP_BRIEF_v3.md:56`。）

この 1 文には、説明の要る言葉がいくつもあります。順に見ます。

#### たとえ話 — 川に色水を流して、水の行き先を調べる

川の水が、どの取水口に流れ込むかを調べたいとします。
上流で、色の付いた水（色水）を少し流します。色水は川の水と混ざり、混ざった水にも色が付きます。
下流の取水口で色が見つかれば、「上流のあの場所の水が、この取水口まで届いた」と分かります。

この「色を付けて、行き先を追う」やり方が、**taint 解析**の考え方です。
上流で色を入れる場所が「汚れの出どころ」、取水口が「危険な操作」に当たります。

#### 小さな例 — 汚れの印を追う

次は作例です。

```python
1  def tool(path):
2      target = "/data/" + path
3      os.remove(target)
```

taint 解析は、このコードを次のように読みます。

- 1 行目: `path` はツールの引数で、LLM が決める値です。ここに「**汚れ**」の印を付けます。これが汚れの出どころです。
- 2 行目: `target` は、`"/data/"` という定数と、汚れた `path` をつないで作った値です。汚れた値を混ぜて作った値も汚れている、と考えるので、`target` にも印が付きます（色水が混ざった水にも色が付くのと同じです）。
- 3 行目: `os.remove`（ファイルを消す操作）に、汚れた `target` が渡されます。汚れが危険な操作に届いたので、「LLM の値が、ファイルの削除に届く流れがある」と報告します。

#### 言葉の整理 — taint 解析・source・sink・Pysa・Pyre・無改変

- **taint（テイント）解析**
  - やさしく言うと: 値に「汚れ」の印を付けて、その印がどこまで流れるかを追う解析。
  - 正確には: 信用できない値の出どころ（source）を決め、その値から作られた値にも印を伝えながら、危険な操作（sink）に印のある値が届く道を探す静的解析。
  - 例: 上の作例で、`path` の印が `target` を通って `os.remove` に届く。
- **source（ソース）と sink（シンク）**
  - やさしく言うと: source は汚れの出どころ、sink は汚れが届くと困る場所。
  - 正確には: source は、信用できない値が入ってくる所（ここではツールの引数）。sink は、その値が届くと危険な操作（ファイルの削除、コマンドの実行など）。
  - 例: 作例の `path` が source、`os.remove` が sink。この研究では、sink に当たる操作を[第 13 章](ch13.md)で「効果」として扱います。
- **Pysa（パイサ）**
  - やさしく言うと: Python のための、既存の taint 解析の道具。
  - 正確には: 型検査器 Pyre の上に作られた、Python の taint 解析の道具。使うには、解析する対象のライブラリを入れて、型を調べられる状態（型の環境。[第 7 章](ch07.md)）を整える必要がある。
  - 例: 仕様書の第 0 週の作業に、`pip install pyre-check==0.9.25 && pyre analyze --no-verify` という疎通の確認の手順が書かれている（`AUTHGAP_BRIEF_v3.md:1061`）。
- **Pyre（パイア）**
  - やさしく言うと: Python の変数や関数の「型」を調べる道具。
  - 正確には: 型検査器（ソースコードを読み、値の型の食い違いを見つける道具）の 1 つ。`pyre-check` という名前で配られている。
- **無改変**
  - やさしく言うと: 手直しせずに、そのまま使うこと。
  - 正確には: 道具の中身（解析の規則や型の情報）を作り替えずに、配られたままの形で使うこと。

#### 前身の設計 — 「動的ディスパッチの壁」を書き下す

MCP のサーバでは、LLM が「このツールを呼んで」と頼むと、**フレームワーク**（サーバを作るための既製の部品の集まり）の中で、名前に合う関数が選ばれて呼ばれます。
その振り分けは、たとえば次のような形をしています（作例です。実際の SDK のコードではありません）。

```python
1  TOOLS = {"search": search, "delete": delete}
2
3  def call_tool(name, args):
4      fn = TOOLS[name]
5      return fn(**args)
```

- 1 行目: ツールの名前と関数を対応させた表（辞書）を作ります。
- 3 行目: `call_tool` は、ツールの名前 `name` と引数 `args` を受け取ります。
- 4 行目: 表から、`name` に合う関数を取り出します。どの関数が取り出されるかは、`name` という**文字列の中身**で決まります。
- 5 行目: 取り出した関数に、引数を渡して呼びます。

「どの関数を呼ぶか」を、実行中に名前（文字列）で決めるこの書き方を、**動的ディスパッチ**（実行中の振り分け）と呼びます。
読んだだけでは呼び出し先が決まらないので、静的な解析はここで先に進めなくなります。これが「**壁**」です（[第 7 章](ch07.md)の 7.5 節で見た `getattr` の例と同じ種類の難しさです）。

前身は、この壁の先を**手で書き下して**（「名前が `search` ならこの関数、`delete` ならこの関数」と教えて）、Pysa に越えさせようとしました。
LLM の値を壁の手前で汚れとして印を付け、その印が壁を越えてツールの本体の危険な操作まで届くかを、Pysa に追わせる、という設計です。

#### 仕様書が決めていた Pysa の扱い

仕様書は、AuthGap でも Pysa を**比べる相手**（baseline）の 1 つにする計画でした。ただし、環境の構築が難しいことを見越して、「第 2 週の 3 日目までに環境が立つリポジトリが 0 なら、比べる相手から外し、『pyre に依存する比べる相手は、環境の費用のために成り立たなかった』と報告する」と先に決めていました。
D71 は、Pysa との比較を「環境構築の費用で未実施のまま」とし、仕様書の取り決めどおり「環境が立たず不成立」と報告する、としています。
（出典: `AUTHGAP_BRIEF_v3.md:127, 812, 1061`、`docs/decisions.md:3950-3952`。）

#### よくある誤解・つまずき

- **誤解: 「Pysa は悪い道具だった」**
  そうではありません。成り立たなかったのは「**無改変の** Pysa に、フレームワークの壁を越えさせる」という**設計**です。実際、TaintP2X という研究は Pysa を使っていますが、LLM の SDK の stub（8.2 節）を 30 個以上自作して Pysa を通しています。手を大きく入れれば使える、ということです。
  （出典: `docs/implementation_base_survey.md:53, 106-107`。）
- **誤解: 「taint 解析と、この研究の解析は同じもの」**
  考え方は似ています。この研究の解析器も、値の出どころ（その値を LLM が決めたのか、運用者が決めたのか）を追います（[第 14 章](ch14.md)）。けれども、Pysa のような既存の道具は使わず、ツールの関数の中から読み始める点が違います（8.2 節）。
- **つまずき: 「動的ディスパッチの壁」と「動的解析」を混ぜる**
  「動的解析」は[第 7 章](ch07.md)の、動かして調べる方法です。「動的ディスパッチ」は、プログラムの中で呼び出し先を実行中に決める書き方です。「動的」という言葉が同じだけで、別の話です。

#### 手作業ではどう使うか

この話は、判定の手順に直接は出てきません。けれども、次の 2 つで役に立ちます。

- 解析器が manifest に書く道筋（`witness_chain`）は、**ツールの本体から**始まります（第 12・18 章）。フレームワークの中の振り分けは読みません。それは、前身の失敗を受けた設計だからです（8.2 節）。判定でも、ツールの本体から読み始めます。
- 論文を書くとき、「なぜ既存の道具を使わなかったのか」に答える材料になります（D71 の理由 1。[第 26 章](ch26.md)）。

#### この節のまとめ

前身は、既存の taint 解析の道具 Pysa を無改変で使い、フレームワークの動的ディスパッチの壁を手で書き下して越えさせる設計だった。taint 解析は、値に汚れの印を付けて、危険な操作に届くかを追う解析。
仕様書は Pysa を比べる相手にする計画だったが、環境が立たなければ外すと先に決めていた。

### 8.2 前身はなぜ成り立たなかったか — そろわなかった 4 つの条件

#### 一言で言うと

前身の設計が動くには、**4 つの条件が全部そろう**必要がありました。実際に測ってみると、実際のアプリでは 4 つがそろいませんでした。
AuthGap は、そのうち 3 つの条件を「要らない」設計にしました。

#### たとえ話 — 4 つの鍵が全部そろわないと開かない金庫

ある金庫は、4 つの鍵を全部差し込まないと開きません。
3 つそろっても、1 つ欠ければ開きません。
前身の設計は、この金庫のようなものでした。4 つの条件のどれか 1 つでも欠けると、全体が成り立たないのです。
こうした「全部がそろって初めて成り立つ」ことを、仕様書は「4 条件の連言」と呼んでいます（連言は「かつ」でつないだもの、という意味です）。

#### 小さな例 — 4 つの条件と、何が起きたか

仕様書は、実際に測った結果、次の 4 つの条件が実際のアプリではそろわないと分かった、と書いています。

| 必要だった条件 | 何が起きたか（仕様書の言葉を言い換えたもの） | 平たく言うと |
|---|---|---|
| 1. 解析の道具が壁を記録する | pyre の環境構築と費用のために、多くの対象が解析までたどり着かない | **環境が立たない** |
| 2. stub にされたフレームワークを越えて、LLM の汚れが届く | SDK が型を消した stub の境界で、汚れの出どころが切れる | **汚れの印が途中で消える** |
| 3. ツールの本体が危険な操作に届く | ツールの実行が、別のプロセスや HTTP の向こう側にある | **本体が手元に無い** |
| 4. 検査（ガード）が無い | 検査の無いシェルの実行は、多くのアプリで**仕様**であり、報告しても「意図どおり」と返される | **報告しても意味が無い** |

（出典: `AUTHGAP_BRIEF_v3.md:56-63`。）

表の読み方: 2 行目は「前身の設計には、フレームワークの stub を越えて LLM の汚れの印が届くことが必要だった。しかし実際には、SDK の型を消した stub の所で汚れの出どころが切れてしまった。平たく言えば、汚れの印が途中で消えた」と読みます。

#### 一歩ずつ — 4 つの条件を 1 つずつ

**条件 1（環境が立たない）**: Pysa は Pyre の上で動くので、解析する対象ごとに型の環境（ライブラリを全部入れて、型を調べられる状態）を整える必要があります。実際のアプリでは、その構築に失敗したり、時間がかかりすぎたりして、多くの対象が解析の段階までたどり着きませんでした。

**条件 2（汚れの印が途中で消える）**: ここで「**stub**（スタブ）」という言葉が出てきます。

- **stub**
  - やさしく言うと: ライブラリの代わりに置く、型の情報だけを書いた身代わりのファイル。
  - 正確には: 関数やクラスの名前と、引数・戻り値の型だけを書き、中身（処理）は書かないファイル。型検査器は、本物のライブラリの代わりにこれを読んで型を知る。Python では `.pyi` という拡張子が多い。
  - 例: 次の作例のように、中身の代わりに `...` を書く。

```python
1  # SDK の stub の作例（実物ではない）
2  def call_tool(name: str, arguments: Any) -> Any: ...
```

- 1 行目: 説明のための注記です。
- 2 行目: `call_tool` という関数があり、`name` は文字列、`arguments` と戻り値は `Any`（何でも入る型）だ、とだけ書いています。最後の `...` は「中身は書かない」という印です。

型が `Any` のように**消されている**と、型検査器や Pysa には、その関数の中で値がどう流れるかが分かりません。
仕様書の言葉では「SDK が型消去された stub 境界で source が切れる」。つまり、LLM の値に付けた汚れの印が、SDK を通り抜けるところで途切れてしまったのです。印が途切れれば、その先で危険な操作に届いても、「LLM の値だ」とは分かりません。

**条件 3（本体が手元に無い）**: ツールの本当の処理が、別のプロセス（別に動いているプログラム）や、HTTP の向こうのサーバで行われることがあります。手元のソースコードには、要求を送る行しか無く、その先で何が起きるかは読めません。

**条件 4（報告しても意味が無い）**: 「検査（ガード）が無いまま、LLM の値でシェルのコマンドを実行する」ことは、多くのアプリで**意図した仕様**です。たとえば「好きなコマンドを実行できるツール」は、それが目的です。そうしたものを「危ない」と報告しても、作者からは「意図どおりです」と返ってきます。

#### AuthGap はどう外したか

AuthGap は、4 つの条件のうち 3 つを、設計の段階で「要らない」ものにしました。

| 前身の条件 | AuthGap の設計 | なぜ要らなくなるか |
|---|---|---|
| 2. 汚れが stub を越える | 汚れの出どころを**ツールの引数**（と LLM の出力）に置く | ツールの関数の中から始めるので、SDK の stub を越える必要が無い |
| 1. 道具が壁を記録する | 解析を**ツールの関数の中から**始める（呼ばれる側から読む） | フレームワークの壁を越えないので、壁も、型の環境も要らない |
| 4. 検査が無い | 「検査が無い」ではなく「**宣言を超える**」を判定する（仕様書の言葉では「宣言または P0（明示のベースライン）を超える」） | 仕様どおりにシェルを実行するツールは、宣言が正直なら問題なしとして分けられる |
| 3. 本体が手元に無い | （外せなかった） | 確度 `remote`（相手側で起きる）や `UNKNOWN` の印として残す |

表の読み方: 3 行目は「前身の条件 4（検査が無いことを報告する）は、AuthGap では『宣言を超えるか』を判定することで要らなくなった。シェルを実行することが目的のツールでも、宣言が正直なら問題なしとして分けられるから」と読みます。

ここで「ツールの関数の中から読む」とは、[第 12 章](ch12.md)の「入口」を見つけて、そこから読み始めることです。

（出典: `AUTHGAP_BRIEF_v3.md:65, 67`。確度は[第 14 章](ch14.md)。）

- **誤解: 「AuthGap は 4 つの条件を全部外した」**
  外したのは 3 つです。「本体が別のプロセスや HTTP の向こう」は外せず、`remote` などの印として残っています。

人が判定するときは、相手の API の文書や API の名前・パスを調べて、相手の状態を変えるかを決めます。v4 の判定では、既存のプロジェクトを更新する要求だと読まれました（本記録者の判定）。
（出典: `evidence/population_v4/v4_judgments.json` の R01。調べ方は第 10・50 章。）

前身の設計は、環境が立つ・汚れが stub を越える・本体が手元にある・検査が無い、の 4 つが全部そろう必要があり、実際のアプリではそろわなかった。AuthGap は、ツールの関数の中から読み、「宣言を超えるか」を判定することで 3 つを外した。外せなかった 1 つは `remote` などの印で残る。

### 8.3 最初の計画 — 3 つの座標 trig・val・gate

#### 一言で言うと

AuthGap の最初の計画では、危険な操作の 1 つ 1 つについて、**3 つのこと**を推論するつもりでした。
その操作が起きるかを誰が決めるか（**trig**）、操作の各位置に入る値を誰が決めるか（**val**）、どの検査がどれくらいの強さでその値を確かめるか（**gate**）です。
そして、この 3 つの組み合わせで、**既知の脆弱性の修正前と修正後のコードを見分けられる**ことを主張する予定でした。

#### たとえ話 — 銀行の振込

銀行の振込で、「危ない振込」かどうかを調べるとします。見るべきことは 3 つあります。

1. **振込を実行するかどうか**を、誰が決めたか（本人か、知らない誰かか）。
2. **金額と振込先**を、誰が決めたか。
3. 窓口の**本人確認**は、どれくらい厳しいか（身分証まで見るのか、名前を聞くだけか）。

修正前の窓口では、名前を聞くだけで振り込めたとします。修正後は、身分証を確かめるようになったとします。
3 つ目の「確認の厳しさ」を見れば、修正前と修正後の違いが分かります。

最初の計画の trig・val・gate は、この 1・2・3 に当たります。

#### 小さな例 — 3 つの座標をコードの上で見る

次は作例です。

```python
1  @mcp.tool()
2  def run(cmd: str, confirm: bool) -> str:
3      if confirm:
4          if cmd in ALLOWED_COMMANDS:
5              subprocess.run(cmd, shell=True)
6      return "done"
```

- 2 行目: ツール `run` は、実行するコマンド `cmd` と、実行するかどうかの `confirm` を受け取ります。どちらも LLM が決める引数です。
- 3 行目: `confirm` が真のときだけ、先に進みます。つまり、5 行目の操作が**起きるかどうか**を決めているのは `confirm`、つまり LLM です。これが **trig** の見るところです。
- 4 行目: `cmd` が、許可されたコマンドの一覧（`ALLOWED_COMMANDS`）に入っているかを確かめます。これが**検査**で、**gate** の見るところです。gate では、この検査がどれくらい強いか（**等級**）も評価します。
- 5 行目: `subprocess.run(cmd, shell=True)` で、`cmd` をシェルのコマンドとして実行します。ここに入る値 `cmd` を決めているのは LLM です。これが **val** の見るところです。

3 つは、1 つの危険な操作について**別々に計算される値**です。地図の上の点を「x・y・z」の 3 つの数で表すように、3 つの値で 1 つの操作を表すので、仕様書は**座標**と呼びました。

#### 言葉の整理 — trig・val・gate・等級・両側

- **trig**（trigger = 引き金）
  - やさしく言うと: その危険な操作が起きるかどうかを、誰が決めるか。
  - 正確には: 仕様書の言葉で「発生を誰が決めるか」。1 つ 1 つの危険な操作が起きるかどうかを決める主体（LLM か、運用者か、など）。
  - 例: 上の作例では、`confirm`（LLM の値）が 5 行目の発生を決める。
- **val**（value = 値）
  - やさしく言うと: 危険な操作の各位置に入る値を、誰が決めるか。
  - 正確には: 仕様書の言葉で「各制御位置の値を誰が決めるか」。制御位置とは、操作の結果を左右する引数の位置（コマンド、ファイルの場所など。[第 13 章](ch13.md)の slot）。
  - 例: 作例では、5 行目のコマンドの位置に入る `cmd` を LLM が決める。
- **gate**（門）
  - やさしく言うと: その値を確かめる検査と、その検査の強さ。
  - 正確には: 仕様書の言葉で「どのゲートがどの等級で要求主体を引き上げるか」。検査（ゲート）が値をどれだけ確かに絞り込むかを、等級で表す。
  - 例: 作例では、4 行目の許可リストによる検査。
- **等級**
  - やさしく言うと: 検査の強さのランク。
  - 正確には: 仕様書は、検査を `strong-path`・`strong-token`・`strong-enum`・`weak(理由)` のように等級付けると書いている。`weak` には、なぜ弱いかの理由が付く。
  - 例: 「パスの前の部分を比べるが、`..` を正規化する前に比べている」検査は弱い（`weak`）。
- **両側**（脆弱版と修正版）
  - やさしく言うと: 脆弱性が見つかった版と、それを直した版の 2 つ。
  - 正確には: 公開された脆弱性（CVE と呼ばれる番号で管理される）の、修正前のコードと修正後のコードの組。
  - 例: あるファイル操作のツールで、修正前はパスの検査が弱く、修正後は強くなった、という組。

（出典: `AUTHGAP_BRIEF_v3.md:36, 40`。）

#### 最初の計画が言おうとしたこと

仕様書の考えは、こうでした。
既存の検出の道具は、脆弱な版を見つけることはできます。けれども、検査の**有無**しか見ないので、修正した版でも同じように「危ない」と言ってしまいます（修正版を「問題なし」と言えない）。
AuthGap は検査の**強さ**（等級）まで見るので、修正前は `weak`、修正後は強い等級、という**変化**を捉えられるはずです。だから、脆弱版と修正版の両方で正しく答えられる、と主張する計画でした。
（出典: `AUTHGAP_BRIEF_v3.md:40-42`。）

#### 第 3 版からの訂正

第 3 版の教科書では、trig を「誰がツールを起動できるか」と書いていました。
けれども仕様書の言葉では、trig は「**発生を誰が決めるか**」です。ツール全体を起動する話ではなく、**1 つ 1 つの危険な操作が起きるかどうか**の話なので、この版で直しました。

#### よくある誤解・つまずき

- **誤解: 「trig は、誰がツールを呼べるか（起動できるか）」**
  違います。trig は、ツールの中の 1 つの危険な操作が「起きるかどうか」を誰が決めるかです。
- **誤解: 「gate は、利用者のログインや認証のこと」**
  この研究の gate は、危険な操作に入る**値**を確かめる検査（許可リスト、パスの正規化と比較など）のことです。
- **つまずき: 「3 つの座標は、今も研究の主張の中心」**
  今は違います。次の 8.4 節で見るとおり、3 つを組み合わせる主張は降ろしました。

#### 手作業ではどう使うか

最終評価の判定では、trig と gate は使いません（8.5・8.6 節）。val の考え方（その値を LLM が決められるか）だけは、判定でも使います。たとえば[第 7 章](ch07.md)の `save_to` のように、「LLM が選べる値なら、取りうる値の全体で考える」という読み方です（[第 17 章](ch17.md)の原理 3）。

#### この節のまとめ

最初の計画は、危険な操作ごとに trig（発生を誰が決めるか）・val（値を誰が決めるか）・gate（検査とその等級）の 3 つの座標を推論し、検査の等級の変化で脆弱版と修正版を見分けることだった。
trig は「発生を誰が決めるか」で、「誰がツールを起動できるか」ではない。

### 8.4 測ってみたら — trig をたどれたのは 0.6%

#### 一言で言うと

実際の MCP サーバで測ると、trig を**コードの上でたどれた**ツールは、2,231 個のうち 14 個（**0.6%**）しかありませんでした。
仕様書は、測る**前に**「20% 未満なら主張を格下げする。この条項は撤回しない」と書いていました。そこで、**その決まりに従って主張を絞りました**（D36）。

#### たとえ話 — 先に決めておいた合格点

ある先生が、新しい採点の方法を試す前に、「この方法で 20% 以上の答案を最後まで読み取れなければ、この方法は使わない。この決まりは後から取り消さない」と、職員室の掲示板に書いておいたとします。
試してみると、読み取れたのは 0.6% でした。
先生は、掲示板に書いたとおり、その方法を使うのをやめます。「もう少しで届きそうだから、基準を 0.5% に下げよう」とは言いません。基準を先に書いておいたのは、まさにそういう「後から都合よく変える」ことを防ぐためだからです。

#### 小さな例 — 測った値と、事前の条件

| 項目 | 実測 | 仕様書が事前に決めていた条件 |
|---|---|---|
| trig を**たどれた**（`traced`）ユニット | **14 / 2,231 = 0.6%** | 20% 以上 |
| 交差行の候補 | 5 行 | 3 行以上 |
| 交差行の由来のプロジェクトの数 | 2（`fanfan-de/anybox`、`ariffazil/wealth`） | 3 以上 |

表の読み方: 1 行目は「trig をコードの上でたどれたユニット（ツール）は 2,231 個のうち 14 個で、0.6% だった。仕様書は 20% 以上を条件にしていたので、届かなかった」と読みます。

測ったのは、母集団 v2（宣言を持つ MCP サーバ 87 木。[第 25 章](ch25.md)）の走査の 1 つ（`evidence/scan_v2_run4`）です。
14 ÷ 2,231 = 0.00627… なので、約 0.6% です。
（出典: `docs/decisions.md:200-211`（D36 の根拠）。）

#### 一歩ずつ — 「たどれた」とはどういうことか

「trig をたどれた」（`traced`）とは、「LLM がこのツールを選んだから、この操作が起きる」という因果を、**コードの上で実際に追えた**という意味です。
追えなかったものは、「LLM が決めたと**仮定**した」（`assumed`）扱いになります。

今の manifest にも、この印が残っています。たとえば、v4 で走査した making-gemini-useful-with-claude という木のツール `gemini_prompt` には、次のように書かれています。

```
"trig": {"label": "MODEL", "mode": "assumed"}
```

- `label: "MODEL"`: 発生を決めるのはモデル（LLM）だ、とする。
- `mode: "assumed"`: ただし、それはコードの上でたどれたのではなく、**仮定した**ものだ。

本書の執筆時に作った小さな作例のサーバでも、3 つのツールすべてが `"mode": "assumed"` でした。
（出典: `evidence/scan_v2_v4_run1/v4-ankitdotgg__making-gemini-useful-with-claude.json` の `gemini_prompt` の `trig`。）

#### 一歩ずつ — なぜたどれないのか

D36 は、「MCP サーバは dispatch がフレームワーク内にあるため木の中で『モデルがこのツールを選んだ』を追跡できない。これは実装の不足ではなく構造的な事実」と書いています。dispatch は、8.1 節で見た「どのツールの関数を呼ぶかの振り分け」のことです。
8.1 節の前身が突き当たった「動的ディスパッチの壁」と、同じ場所です。AuthGap はツールの関数の中から読むので、その手前（フレームワークの中の振り分け）は読みません。だから、「LLM がこのツールを選んだ」ことは、たどれないのが普通なのです。

実は仕様書自身も、この可能性を先に書いていました。「MCP サーバでは dispatch が framework 内にあるので trig は常に `assumed` になり、（中略）traced 率が 20% 未満なら（中略）格下げする。この条項は撤回しない」。
（出典: `docs/decisions.md:213-217`、`AUTHGAP_BRIEF_v3.md:556`。）

#### 一歩ずつ — 交差行とは

「交差行」は、3 つの座標を**組み合わせて初めて見える**行のことです。仕様書は、3 つの座標を 1 つの研究として統一する「唯一の証拠」を、この交差行の数だと事前に決めていました。
具体的には、manifest の同じ行（ツール × 操作 × 位置）が、trig の側の判定（GAP_SELECT など）と val の側の判定（GAP_INJECT など）を**同時に**持つ行です（判定の名前は 8.6 節と[第 18 章](ch18.md)）。
仕様書の条件は「3 行以上、かつ 3 つ以上の異なるプロジェクトから」で、実測は 5 行・2 プロジェクトでした。

なお D36 は、この 5 行は仕様書の特徴づけで数えたもので、仕様書が測り方として決めていた「3 腕のアブレーション」（解析器の部品を 1 つずつ止めて比べる実験）を回した値ではない、と注意を書いています。ただし、腕を回して行が増えても、プロジェクトの数が 3 に届く保証は無いので、絞る決定には不利に働かない、としています。
（出典: `AUTHGAP_BRIEF_v3.md:547-554`、`docs/decisions.md:202-211, 222-226`。）

#### なぜそう決めたのか — D36

仕様書は、結果を見る**前に**、「traced 率が 20% 未満なら、この主張は野外（実際のデータ）では成り立たないので格下げする。この条項は撤回しない」と書いていました。実測の 0.6% は、この条項に当たります。
そこで、2026-09-21、学生は「**下の行は必要ない**」と決めました。「下の行」とは、次の表の 2 行目のことです。

| # | 主張 | 使う仕組み | 決定 |
|---|---|---|---|
| 1 | 宣言 D と実効 M が食い違う | 効果の種類の検出と、宣言の読み取りだけ | **主軸にする** |
| 2 | 3 つの座標（trig・val・gate）の統合で、脆弱版と修正版を見分ける | trig・val・gate の全部 | **主張から降ろす** |

表の読み方: 2 行目は「3 つの座標を組み合わせて脆弱版と修正版を見分けるという主張は、trig・val・gate の全部を使うものだが、主張から降ろした」と読みます。

（出典: `docs/decisions.md:185-194`（D36 の学生の決定）。）

#### よくある誤解・つまずき

- **誤解: 「0.6% だったのは、解析器の作りが下手だったから」**
  D36 は「実装の不足ではなく構造的な事実」と書いています。MCP サーバでは、振り分けがフレームワークの中にあるからです。
- **誤解: 「主張を降ろしたのは、失敗を隠したことになる」**
  逆です。先に書いた決まりに従って降ろし、その理由と数字を決定 D36 に残しました。降ろした仕組みのコードも消していません（8.5 節）。
- **つまずき: 「`assumed` の印は、解析器が何かを読み損ねた印」**
  `assumed` は、MCP サーバでは普通の状態です。判定では気にしなくて構いません。

#### 手作業ではどう使うか

manifest を開くと、どのユニットにも `"trig": {"label": "MODEL", "mode": "assumed"}` があり、多くの行の注記に `select_manifest_only(assumed_trig)` があります。
後者は、「trig が仮定なので、trig の側の判定（GAP_SELECT）は出さず、manifest に記録するだけにした」という印です。
どちらも付録の仕組みの印なので、**判定では読み飛ばして構いません**。
（出典: `authgap/verdict.py:209-211`。）

#### この節のまとめ

母集団 v2 で測ると、trig をたどれたユニットは 14 / 2,231 = 0.6%（条件は 20% 以上）、交差行は 5 行・2 プロジェクト（条件は 3 行以上・3 プロジェクト以上）だった。MCP サーバでは振り分けがフレームワークの中にあるので、これは構造的な事実。
仕様書が先に書いた「撤回しない」条項に従い、2026-09-21 に主張を「宣言 D と実効 M の照合」に絞った（D36）。

### 8.5 今の主張 — 宣言 D と実効 M の照合（核と付録）

#### 一言で言うと

今の主張は、[第 6 章](ch06.md)の一文、つまり「**宣言 D と実効 M の照合**」の 1 本です。
その照合に要る仕組みを「**核**」、降ろした主張のための仕組みを「**付録**」と呼び分けます。trig と gate は付録ですが、val の「値を誰が決めたか」は核でも使います。

#### たとえ話 — 大きな家の計画から、1 部屋を仕上げる計画へ

大きな家を一度に建てる計画が、途中で「まず 1 部屋をしっかり仕上げる」計画に変わったとします。
使わなくなった資材は、捨てずに倉庫にしまいます。後で「なぜ計画を変えたのか」を説明するときの材料になるし、いつか使うかもしれないからです。
ただし、1 部屋を仕上げるのに必要な資材（たとえば柱や配線）は、もとの計画の資材でも、そのまま使います。

AuthGap の「核」は仕上げる 1 部屋、「付録」は倉庫の資材です。val は、倉庫からではなく、今の部屋でも使っている資材です。

#### 小さな例 — 核と付録の語彙

この repo の約束（`CLAUDE.md`）は、語彙（決まった言葉の一覧）ごとに、核か付録かを表にしています。数は、本書の執筆時に解析器を読み込んで数え、表と一致することを確かめました。

| 語彙 | 数 | 役割 | 何のための言葉か |
|---|---|---|---|
| ツールの入口の規則（`ENTRY_RULES`） | 14 | **核** | ツールを見つける規則（[第 12 章](ch12.md)） |
| 効果の種類（kind）と位置（slot）（`SLOTS`） | 7 種類 | **核** | 危険な操作の種類と、その引数の位置（[第 13 章](ch13.md)） |
| 値の側で読み切れなかった理由（`VAL_OPAQUE_REASONS`） | 8 | **核** | 値を追えなかった理由（[第 14 章](ch14.md)） |
| 矛盾の判定の類（SQL 文・HTTP のメソッド・ファイルの書き込み） | — | **核** | 宣言に反するかの判定表（[第 17 章](ch17.md)） |
| 検査の形（`VALIDATOR_SHAPES`） | 12 | 付録 | gate の側 |
| 弱い理由（`WEAK_REASONS`） | 22 | 付録 | gate の等級の `weak` の理由 |
| 格下げの属性（`DOWNGRADES`） | 4 | 付録 | gate の側 |
| 設定の値の出どころ（`CONFIG_ATOM_SOURCES`） | 4 | 付録 | gate の側 |
| ゲートの側で読み切れなかった理由（`GATE_OPAQUE_REASONS`） | 8 | 付録 | gate の側 |
| ゲートの側の「支配しない」理由（`GATE_NODOM_REASONS`） | 4 | 付録 | gate の側 |
| パスの領域の位置（`PATH_DOMAIN_SLOTS`） | 5 | 付録 | gate の等級（strong-path）が効く位置 |

表の読み方: 3 行目は「値の側で読み切れなかった理由の語彙は 8 つあり、核に属する。値を追えなかった理由を表す言葉で、[第 14 章](ch14.md)で詳しく見る」と読みます。5 行目は「検査の形の語彙は 12 あり、付録に属する。gate の側の言葉」と読みます。

（出典: `CLAUDE.md` の「語彙は 1 か所でしか定義しない」の表。数は `authgap/catalog/entries.py`・`authgap/catalog/sinks.py`・`authgap/ir.py`・`authgap/catalog/validators.py` を読み込んで数えた。）

#### 一歩ずつ — 3 つの座標の今

- **trig**: 付録です。8.4 節で見たとおり、MCP サーバではいつも `assumed` で、判定には使いません。
- **gate**: 付録です。検査の形や等級（`strong-...`、`weak(理由)`）は、manifest の属性として出し続けていますが、今の主張には使いません。
- **val**: 「値を誰が決めたか」（主体。`MODEL`・`OP`・`USER`）を追う仕組みは、**核でも使います**。宣言に反するかを決めるとき、「その値を LLM が**決められる**か」が効くからです。たとえば、コマンドを起動する操作（`SPAWN`）では、起動するコマンドを LLM が選べるかどうかで、矛になるか不になるかが変わります（[第 14 章](ch14.md)の主体と確度、[第 17 章](ch17.md)の原理 3）。

第 3 版の教科書は、trig・val・gate を並べて「付録の仕組み」のように書いていました。正しくは、**3 つを組み合わせる主張**が降ろされたもので、その中の val の「主体」は核に残っています。

#### 一歩ずつ — D36 が「主軸に残る」としたもの

D36 は、主軸に残るものを次のように挙げています。

- ツールの入口のカタログ（入口の規則）
- 効果の種類の検出（sink のカタログ、7 種類）と、位置（slot）の結び付け
- 宣言の読み取り（`readOnlyHint` などから、上限を作る）
- 矛盾（CONTRADICTION）の判定（当時は、効果ごとに、削除・上書きの型だけを見ていた）
- 測定の規律（決定的であること、事前登録、読み切れないものを「問題なし」に潰さないこと、など）

D36 を書いた時点（2026-09-21）の矛盾の判定は、宣言の上限と効果の種類を比べるだけで、「gate の等級も val の主体も使わない」と D36 自身が書いています。
その後、矛盾の判定の規則は、原理を先に選んでから決める形に作り直されました（D56。[第 17 章](ch17.md)）。今の規則の中では、値の主体（val）が使われています。たとえば D1 の判定では、コマンドの起動（`SPAWN`）について、起動するコマンドを LLM が選べるかどうかで結果を分けています。
（出典: `docs/decisions.md:228-239`（D36 の「主軸に残るもの」）、`authgap/dparse.py:372-394`（D1 の判定の規則）。）

#### なぜコードを消さないのか

D36 は、「**コードは消さない**」と決めています。gate と val の仕組みは、付録の判定の行と manifest の属性を出し続け、その試験（fixture と mutant のカタログ）も回帰試験として残します。
理由は、「消すと、後から『なぜその設計を降ろしたか』を示す材料が無くなる」からです。
（出典: `docs/decisions.md:254-259`。）

#### よくある誤解・つまずき

- **誤解: 「付録になった仕組みは、解析器から消えた」**
  消えていません。付録の判定（`GAP_INJECT` など）や属性（`gate`、`grades` など）は、今も manifest に出ます。だから、判定のときに目に入ります（8.6 節）。
- **誤解: 「val も降ろした」**
  降ろしたのは「3 つを組み合わせて脆弱版と修正版を見分ける」主張です。val の「主体」は、矛と不を決める規則の中で使われています。
- **誤解: 「付録の判定（`GAP_INJECT` の件数など）も、論文の主な結果になる」**
  なりません。論文の主な結果は、宣言ごとの矛と、その人の判定（精度・見落とし・不の中身）です（D62、[第 45 章](ch45.md)）。

#### 手作業ではどう使うか

判定で manifest を読むときは、**核の欄だけ**を見ます。どの欄が核かは、次の 8.6 節で具体的に見ます。
val の情報（効果の位置ごとの主体 `prin` と確度 `prov`）は核なので、読みます。「この書き先を LLM が決められるか」を考える手がかりになります。

#### この節のまとめ

今の主張は「宣言 D と実効 M の照合」の 1 本。trig と gate は付録で、判定には使わない。val の「値を誰が決めたか」は、矛と不を決める規則の中で核として使う。
付録の仕組みは消さずに残し、manifest に出し続ける（降ろした理由を示す材料として）。

### 8.6 判定で読む欄と読まなくてよい欄 — `UNKNOWN` と「不」を取り違えない

#### 一言で言うと

manifest には、核の欄と付録の欄が混ざっています。判定に要るのは**核の欄だけ**です。
とくに、verdict（解析器が出す判定の名前の一覧）の `UNKNOWN` と、核の照合の答えの「**不**」は**別物**です。「不」は `notes`（注記）の `contradiction_unknown:<宣言>:<理由>` で読みます。

#### たとえ話 — 古い検査の欄が残った結果票

ある健康診断の結果票には、今年はもう使わない古い検査の欄も、まだ印刷されているとします。
今年の判定に要るのは、新しい検査の欄だけです。古い欄に何か書いてあっても、気にしなくて構いません。
ただし困るのは、古い欄の「判定保留」と、新しい欄の「要再検査」のように、**似た言葉**があることです。読み違えると、結果を取り違えます。

manifest の `UNKNOWN`（古い欄の言葉）と「不」（新しい欄の言葉）が、ちょうどこの関係です。

#### 小さな例 1 — 判定に要る欄と、要らない欄

最終評価の手順書は、判定のために、manifest から 1 件の情報を取り出す小さな道具を用意しています。その道具が取り出すのは、次の欄だけです。

| 欄 | 何が書いてあるか | 核か |
|---|---|---|
| `unit`（の `relpath`・`lineno`・`tool_name`・`annotations`） | ツールの場所と名前と宣言 | 核 |
| `D_kind` の `explicit` | 明示された宣言の一覧 | 核 |
| `cap_hits`、`opaque_reasons` | 上限に当たったか、読み切れなかった理由 | 核 |
| `effects`（`kind`・`site`・`relpath`・`lineno`・`entry_lineno`・`witness_chain`・`slots` の `prin`・`prov`・`roots`） | 効果の種類と場所、ツールからの道筋、位置ごとの値の主体と確度 | 核 |
| `rows` の `notes` のうち `contradiction` で始まるもの | 宣言ごとの照合の答え（矛・不） | 核 |

表の読み方: 4 行目は「`effects` の欄には、効果の種類と場所、ツールからそこまでの道筋、各位置の値を誰が決めたか（主体）と読み切れたか（確度）が書いてある。これは核の欄なので、判定で読む」と読みます。

一方、manifest には次のような欄もあります。これらは付録の仕組みのための欄で、**判定では読まなくて構いません**。

- `trig`、`gate`、`gate_occ`、`gate_occ_by_effect`、`gate_predicate_present`、`grades`、`req_occ`、`req_occ_by_effect`、`req_val`、`validator_shapes`、`config_atoms`
- `rows` の `verdicts` のうち、`CONTRADICTION` 以外のもの（`GAP_INJECT`、`GAP_SELECT`、`UNKNOWN`、`INVENTORY` など）
- `rows` の `notes` のうち、`contradiction` で始まらないもの（`select_manifest_only(assumed_trig)`、`D_layer_present:kind:NET` など）

（出典: `docs/final_evaluation_procedure.md:466-494`（6.5 節の道具）。欄の詳しい意味は第 18・19 章。）

#### 小さな例 2 — 実物の 3 つの行

v4 の 2 つの manifest から、3 つの行を、欄を減らして写します。

```
（1）making-gemini-useful-with-claude のツール gemini_prompt の行。宣言は readOnlyHint: true
     site: pipe:communicate   kind: FS_WRITE
     "verdicts": ["CONTRADICTION", "GAP_INJECT", "UNKNOWN"],
     "notes": ["select_manifest_only(assumed_trig)", "contradiction:D1", "contradiction_reason:D1:fs_write"]

（2）同じツールの別の行
     site: asyncio.create_subprocess_exec   kind: SPAWN   slot: argv0
     "verdicts": ["GAP_INJECT", "UNKNOWN"],
     "notes": ["select_manifest_only(assumed_trig)", "contradiction_unknown:D1:spawn_model_opaque"]

（3）bugasura-mcp-server のツール bugasura_update_project（関数名 update_project）の行。宣言は destructiveHint: false、idempotentHint: true ほか
     site: httpx.AsyncClient.request   kind: NET   slot: url.host
     "verdicts": [],
     "notes": ["select_manifest_only(assumed_trig)", "contradiction_unknown:D2:net_post", "contradiction_unknown:D4:net_nonidempotent_method"]
```

（出典: `evidence/scan_v2_v4_run1/v4-ankitdotgg__making-gemini-useful-with-claude.json`、`evidence/scan_v2_v4_run1/v4-appachhi__bugasura-mcp-server.json`。注記の中の `D1`・`D2`・`D4` は宣言の記号で、`D1` は `readOnlyHint: true`、`D2` は `destructiveHint: false`、`D4` は `idempotentHint: true`。[第 4 章](ch04.md)で見たもので、[第 16 章](ch16.md)で正式に扱う。）

#### 一歩ずつ — 3 つの行を読む

まず、注記（`notes`）の 3 つの書き方を整理します。

| 注記の形 | 意味 | 照合の答え |
|---|---|---|
| `contradiction:<宣言>` | この効果は、その宣言に反する | **矛** |
| `contradiction_reason:<宣言>:<理由>` | 上の矛の理由（同じ 1 つの矛の説明。別の矛ではない） | （矛の理由） |
| `contradiction_unknown:<宣言>:<理由>` | 反するかどうかが、静的に決められない | **不** |

表の読み方: 3 行目は「注記が `contradiction_unknown:<宣言>:<理由>` の形なら、その宣言に反するかどうかを解析器は静的に決められなかった、つまり『不』で、理由も書いてある」と読みます。

次に、3 つの行を読みます。

- **行（1）**: 注記に `contradiction:D1` があるので、D1（読むだけ）について**矛**です。理由は `fs_write`（ファイルの書き込み）。`verdicts` にも `CONTRADICTION` があります。同じ `verdicts` にある `GAP_INJECT` と `UNKNOWN` は付録の判定なので、ここでは無視します。
- **行（2）**: 注記に `contradiction_unknown:D1:spawn_model_opaque` があるので、D1 について**不**です。理由は、コマンドを起動する操作（`SPAWN`）の起動するコマンドに LLM の値が流れ込むが、LLM が選べると言い切れない（確度が `opaque`）、というものです。`verdicts` には `CONTRADICTION` はありません。
- **行（3）**: `verdicts` は**空**です。けれども、注記に `contradiction_unknown` が 2 つあるので、D2 と D4 のそれぞれについて**不**です。理由は、D2 は `net_post`（HTTP の POST。相手を変えるかは静的に決まらない）、D4 は `net_nonidempotent_method`（繰り返して同じ結果になるとは限らない HTTP のメソッド）です。

ここから分かる大事なことは 2 つです。

1. **「不」は、`verdicts` ではなく `notes` に書かれる。** 行（3）のように、`verdicts` が空でも「不」はありえます。
2. **`verdicts` の `UNKNOWN` は、「不」とは別のもの。** 行（1）は `UNKNOWN` を持ちますが「矛」です。行（2）は `UNKNOWN` を持ち、たまたま「不」でもあります。行（3）は `UNKNOWN` を持ちませんが「不」です。

#### 一歩ずつ — 付録の verdict は何を意味するのか

付録の verdict は、最初の計画（8.3 節）の判定の名前です。短く意味だけ見ておきます（詳しくは[第 18 章](ch18.md)）。

| verdict | 意味 | 役割 |
|---|---|---|
| `CONTRADICTION` | その効果は、明示された宣言のどれかに反する | **核**（ただし宣言ごとの区別は注記で読む） |
| `GAP_INJECT` | 危険な操作の位置に、検査で絞られていない LLM の値が入る | 付録（val と gate の座標） |
| `GAP_SELECT` | 危険な操作が起きるかを LLM が選べる | 付録（trig の座標。`assumed` では出ない） |
| `UNKNOWN` | その行の効果や値を、解析器が読み切れなかった（確度が `resolved` でない） | 付録 |
| `INVENTORY` | 運用者の許可の一覧などで覆われている | 付録 |

表の読み方: 4 行目は「`UNKNOWN` は、その行の効果や値が読み切れなかった（確度が解決済みではない）という印で、付録の判定の名前。宣言に反するかを決められなかった『不』とは別」と読みます。

`UNKNOWN` が付くのは、行の効果か、その位置の値の確度が `resolved`（読み切れた）でないときです。だから「読み切れなかった」という点では「不」と似ています。けれども「不」は「**宣言に反するかどうか**が静的に決まらない」という、照合の答えです。値は読み切れていても、HTTP の POST のように意味が決まらなければ「不」になります（行（3））。逆に、値が読み切れていなくても、ファイルの書き込みのように D1 に必ず反する操作なら「矛」になります（行（1））。
（出典: `authgap/verdict.py:24-32`（verdict の語彙）、`:168-182`（`UNKNOWN` を付ける条件）、`:160-165`（宣言ごとの注記を付ける所）。）

#### 注意 — 行（1）が本当に違反かは、別の話

行（1）の site は `pipe:communicate` です。これは、起動した子プロセス（ここでは Gemini のコマンド）の標準入力に、文字を渡す操作です（`server.py:204` の `proc.communicate(input=stdin_data)`）。ファイルを書く操作ではありません。
判定の手引きは、「子プロセスの標準入力・パイプを書き込みと読んだ」誤りを、誤の原因 E5 にしています。行（1）はこの形に当たりうるので、人が判定すれば誤になるかもしれません。
v4 ではこの行は判定の対象に選ばれておらず、本書でも判定はしていません。ここでは、**欄の読み方の例**としてだけ使っています。
（出典: `corpus/v4-ankitdotgg__making-gemini-useful-with-claude/server.py:194-206`、`docs/drafts/final_judging_guide_draft.md:428-446`（17 節の E5）。）

#### なぜ注記で読むのか

D62 は、D1〜D4 の 4 つの宣言をすべて主な指標にし、**宣言ごとに**報告すると決めました。
ところが、`verdicts` の `CONTRADICTION` は「どれかの宣言に反する」という 1 つの印で、どの宣言に反するのかを区別しません。宣言ごとの答え（矛か不か）と理由は、注記にだけ書かれます。だから、数えるときも判定するときも、注記で読みます。
（出典: `docs/decisions.md:3511`（D62）、`authgap/verdict.py:150-151, 197-198`（どれかの宣言に反すれば `CONTRADICTION` を 1 つ立てる所）。）

#### 判定の道具が「矛・不」を拾う 1 行

手順書の道具は、行ごとに次の 1 行で、照合の答えだけを取り出しています。

```python
marks = [n for n in r["notes"] if n.startswith("contradiction")]
```

- `r["notes"]`: その行の注記の一覧です。
- `for n in ...`: 一覧の注記を 1 つずつ `n` として取り出します。
- `if n.startswith("contradiction")`: `n` が `contradiction` という文字で始まるときだけ残します。`contradiction:`・`contradiction_reason:`・`contradiction_unknown:` の 3 つの形が残り、`select_manifest_only(...)` などは捨てられます。
- `marks = [...]`: 残ったものを一覧にして `marks` に入れます。

`verdicts` は見ていないことに注意してください。
（出典: `docs/final_evaluation_procedure.md:490-493`。）

#### よくある誤解・つまずき

- **誤解: 「`verdicts` に `UNKNOWN` があれば、その行は『不』」**
  違います。「不」は注記の `contradiction_unknown:...` で決まります。`UNKNOWN` は付録の判定です。
- **誤解: 「`verdicts` が空なら、判定することは何も無い」**
  違います。行（3）のように、`verdicts` が空でも注記に「不」があります。
- **誤解: 「`GAP_INJECT` は宣言違反のこと」**
  違います。`GAP_INJECT` は「検査されていない LLM の値が危険な位置に入る」という付録の判定で、宣言とは関係ありません。宣言の無いツールにも出ます。
- **つまずき: 「`contradiction_reason:...` を、もう 1 つの矛として数える」**
  `contradiction_reason` は、同じ矛の理由の説明です。矛の数には入れません。

#### 手作業ではどう使うか

判定の対象の 1 件（組）について、解析器が何を見たかを確かめるとき（手順 B）は、次の順で読みます。

1. 手順書の道具で、その組の行と効果を出す。
2. 注記の `contradiction:<対象の宣言>` か `contradiction_unknown:<対象の宣言>:<理由>` を探す。対象の宣言以外の注記は、その組とは別の話です。
3. `effects` の道筋（`witness_chain`）と、位置ごとの主体（`prin`）・確度（`prov`）を見る。
4. `trig`・`gate`・`grades`・`GAP_INJECT`・`UNKNOWN` などは読み飛ばす。

宣言ごとに矛と不を数える道具（`scripts/contradiction_by_decl.py`）も、`verdicts` ではなく注記を読みます。同じ組（木・ツール・site・kind の組。[第 18 章](ch18.md)）のどれかの行に `contradiction:<宣言>` があれば「矛」、無くて `contradiction_unknown:<宣言>:…` があれば「不」と数えます。
（出典: `docs/drafts/final_judging_guide_draft.md:108-115`（手順 B）、`scripts/contradiction_by_decl.py:4-15`。詳しくは第 18・19・48 章。）

#### この節のまとめ

判定に要るのは核の欄（`unit`、`D_kind.explicit`、`cap_hits`、`opaque_reasons`、`effects`、注記の `contradiction...`）だけ。trig・gate などの付録の欄は読み飛ばしてよい。
「不」は注記の `contradiction_unknown:<宣言>:<理由>` で読む。verdict の `UNKNOWN` は付録の判定で、「不」とは別物。`verdicts` が空でも「不」はありうる。

<a id="s8-8"></a>
### 8.7 仕様書の計画 — 2 人目の判定者と κ

#### 一言で言うと

仕様書は、判定（ラベル付け）を**2 人**で独立に行い、2 人の一致の度合いを **κ（カッパ）** という数で示す計画でした。AI は κ に含めず、2 人目が確保できなければ、同じ人が時間をあけて判定し直す方法（**test-retest**）で代える、と決めていました。

#### たとえ話 — 2 人の先生が別々に採点する

入試の記述問題を、2 人の先生が、相談せずに別々に採点するとします。
2 人の点がよく一致すれば、「この採点は、採点する人の癖に左右されていない」と言えます。
けれども、一致の度合いを「同じ点を付けた答案の割合」だけで測ると、落とし穴があります。たとえば、ほとんどの答案が満点なら、2 人とも満点ばかり付けるので、ろくに読まなくても高い割合で一致してしまいます。
そこで、「**たまたまでも起きる一致**」を差し引いて考えます。これが κ の考え方です。

#### 言葉の整理 — 判定者・独立・一致率・κ・裁定・test-retest

- **判定者**（仕様書の言葉では**ラベラー**）
  - やさしく言うと: コードを読んで、1 件ずつ印（ラベル）を付ける人。
  - 正確には: 抜き取った件のそれぞれについて、決まった手引きに従って、正・誤・不明などの値を付ける人。
  - 例: 最終評価では、学生が判定者。
- **独立に**
  - やさしく言うと: 相談せず、相手の答えも見ずに。
  - 例: 2 人目は、1 人目の判定を見ないで判定する。
- **一致率**
  - やさしく言うと: 2 人が同じ答えを付けた件の割合。
  - 例: 100 件のうち 90 件で同じなら 90%。
- **κ（カッパ）**
  - やさしく言うと: 2 人の判定が、偶然を超えてどれだけ一致したかを表す数。
  - 正確には: 2 人の判定者のときによく使う形（Cohen の κ）では、κ = (実際の一致率 − 偶然に起きる一致率) ÷ (1 − 偶然に起きる一致率)。1 なら完全に一致、0 なら偶然と同じ程度、負なら偶然より一致していない。
  - 例: 下の作例。
- **裁定**
  - やさしく言うと: 2 人の答えが分かれたとき、どちらにするかを決めること。
  - 例: 3 人目（指導教員など）が決める。
- **test-retest**（テスト・リテスト）
  - やさしく言うと: 同じ人が、時間をあけて、同じものをもう一度判定すること。
  - 正確には: 同じ判定者が、前の判定を見ずに、一定の期間（たとえば 2 週間）をあけて同じ件を判定し直し、前の自分との一致を測る方法。この教科書では「判定し直し」とも呼ぶ。
  - 例: 判定し終えた件から無作為に 10% を選び、2 週間後に判定し直す。

#### 小さな例 1 — κ を計算する

次は作例です（説明のための数で、この研究のデータではありません）。

2 人の判定者 A と B が、同じ 100 件を「正」か「誤」で判定しました。結果を表にします。

| | B が正 | B が誤 | 計 |
|---|---|---|---|
| **A が正** | 75 | 5 | 80 |
| **A が誤** | 5 | 15 | 20 |
| **計** | 80 | 20 | 100 |

表の読み方: 左上の 75 は「A も B も正と判定した件が 75 件」、右上の 5 は「A は正、B は誤と判定した件が 5 件」と読みます。右の「計」の 80 は「A が正と判定した件は全部で 80 件」です。

#### 一歩ずつ — 計算の手順

1. **実際の一致率**: 2 人が同じ答えを付けたのは、左上（2 人とも正）の 75 件と、右下（2 人とも誤）の 15 件で、合わせて 90 件です。90 ÷ 100 = **0.90**。
2. **偶然に起きる一致率**: A は 80% を正、20% を誤と答え、B も 80% を正、20% を誤と答えました。2 人が互いに無関係に、この割合で答えたとすると、
   - 2 人とも正になる確率は 0.8 × 0.8 = 0.64、
   - 2 人とも誤になる確率は 0.2 × 0.2 = 0.04、
   - 合わせて 0.64 + 0.04 = **0.68**。
   つまり、中身を読まずにこの割合で答えても、68% は一致してしまいます。
3. **κ**: (0.90 − 0.68) ÷ (1 − 0.68) = 0.22 ÷ 0.32 = 0.6875 ≈ **0.69**。

一致率は 90% ですが、偶然を差し引くと κ は 0.69 になりました。

#### 小さな例 2 — 一致率が高いのに κ がほぼ 0

もう 1 つ作例を見ます。今度は、2 人とも 95% を正と答えました。

| | B が正 | B が誤 | 計 |
|---|---|---|---|
| **A が正** | 90 | 5 | 95 |
| **A が誤** | 5 | 0 | 5 |
| **計** | 95 | 5 | 100 |

1. 実際の一致率: 90 + 0 = 90 件なので **0.90**（さっきと同じ）。
2. 偶然に起きる一致率: 0.95 × 0.95 + 0.05 × 0.05 = 0.9025 + 0.0025 = **0.905**。
3. κ: (0.90 − 0.905) ÷ (1 − 0.905) = −0.005 ÷ 0.095 ≈ **−0.05**。

一致率は同じ 90% なのに、κ はほぼ 0（わずかに負）です。よく見ると、2 人が「誤」で一致した件は 1 件もありません。2 人とも「ほとんど正」と答えているので一致しているように見えるだけで、「どれが誤か」については、まったく意見が合っていないのです。
一致率だけでなく κ を見るのは、こうした見かけの一致を見抜くためです。

#### 仕様書の計画

仕様書は、2 人目の判定者について、次のように計画していました。

| 仕様書の行 | 計画の中身 |
|---|---|

| `:918`（作業 C2） | 受け入れの条件は「2 人目のラベラーの独立したラベルがそろい、裁定の手続きが記録されている」。**AI は κ に含めない**。作業は学生と 2 人目のラベラー（別に 20〜40 時間） |

#### なぜ「AI を κ に含めない」のか

κ は、**独立した人間の判定者**どうしの一致を測るためのものです。AI は、ここでいう独立した人間の判定者ではありません。AI と人の一致を κ に混ぜると、「別の人が判定しても同じ結論になる」という主張が、AI の答え方の癖に左右されてしまいます。
今は、さらに D70 の 3（[第 7 章](ch07.md)）で、AI に判定させず、AI を 2 人目の判定者の代わりにもしないと決めています（AI は、コードについての事実を調べる補助にだけ使えます）。だから、v4 の AI の判定を 2 人目の代わりにすることもできません。

なお、仕様書のラベル付けの計画は、最初の大きな計画（ゲートの等級などを含む、60 ツール × 4 次元）のためのものでした。今の最終評価の判定（矛の正誤など）とは、対象が違います。けれども「2 人目をどうするか」という問いは、同じ形で引き継がれています。

#### よくある誤解・つまずき

- **誤解: 「一致率が 90% なら、十分に信頼できる」**
  作例 2 のように、一致率が高くても、偶然と変わらないことがあります。だから κ を見ます。
- **誤解: 「κ が 1 なら、判定は正しい」**
  κ は 2 人が**同じ答えを出したか**を測るだけです。2 人とも同じように間違えていれば、κ は高くても判定は正しくありません。
- **誤解: 「test-retest は、2 人目の判定者の代わりになる」**
  なりません。test-retest で示せるのは「同じ人が、同じ手引きで、同じ結論に着くか」です。「別の人でも同じ結論になるか」は示せません。手順書もそう書いています。
  （出典: `docs/final_evaluation_procedure.md:1304-1306`。）

#### 手作業ではどう使うか

もし 2 人目の判定者を用意できたら、その人に判定の一部を独立に判定してもらい、κ のような一致の指標を出すことになります。そのとき決めることは、件数・対象の抜き方・裁定のしかた・一致の指標です（D70 の 8。次の 8.8 節）。
κ の計算そのものは、この節の作例と同じ手順でできます。区間（幅）の付け方などは、第 38・39 章で学びます。

#### この節のまとめ

仕様書は、2 人目のラベラーを確保し、次元ごとに κ を出し、AI は κ に含めず、確保できなければ同じ 60 ツールの test-retest で代える、と計画した。
κ は、偶然に起きる一致を差し引いて、2 人の判定がどれだけ一致したかを表す数。一致率が高くても κ が低いことがある。test-retest は 2 人目の代わりにはならない。

### 8.8 今の実際 — 判定者は 1 人、2 人目は保留

#### 一言で言うと

今の既定は、**判定者は学生 1 人**です（D67 の 4）。κ に依存する主張はしません。
2 人目の判定者と、判定し直し（test-retest）をするかどうかは **保留**（D70 の 8）で、**データを見る前**（遅くとも段階 6 の抜き取りのコミットの前）に決めることになっています。

この研究の決まり（`CLAUDE.md` の規則 6）は、「仕様書と実際が食い違ったら、実際を採り、仕様書の値も残す」です。8.7 節で仕様書の計画を見たので、この節では実際を見て、両方を並べます。

#### たとえ話 — 1 人で採点するしかない先生

ある先生は、2 人目の採点者を頼めず、1 人で採点するしかありません。
そこで先生は、次のように工夫します。採点の基準を、答案を見る前に掲示板に貼り出しておく。答案ごとに「なぜこの点にしたか」を、答案のどの行を見たかとともに書き残す。疲れて雑にならないよう、1 日に採点する枚数を決める。迷った答案は翌日に見直す。
こうしておけば、2 人目がいなくても、後から誰でも「この採点は基準どおりか」を確かめられます。
それでも、「別の先生が採点したら同じ点になったか」は分かりません。だから先生は、そのことを正直に「限界」として書きます。

この研究の今の形は、この先生のやり方です。

表の読み方: 2 行目は「D70 の 8 は、判定し直す量を 5〜10% と書いている」と読みます。

D70 の 8 で全体が**保留**なので、どの量を採るかも**未決**です。判定し直しをすると決めるときに、量も揃えて決めます（[第 46 章](ch46.md)の「まだ決まっていないこと」）。
手順書は、判定し直しのやり方も書いています。全部を判定し終えて 2 週間以上あけてから、無作為に選んだ件を**元の判定を見ずに**判定し直し、一致率を報告する。食い違った件は、元の判定を**直さず**、食い違ったことを報告する、というものです。
（出典: `docs/final_evaluation_procedure.md:1304-1306`。）

#### 2 人目がいない分を、何で支えるか

2 人目がいない分、この研究は**別の方法で信頼性を支えます**。

1. **判定の根拠を全件残して公開する**（D67 の 4）。1 件ごとに、ファイルと行の連なりを書きます。第三者が開けば、同じ結論に着けるかを確かめられます。
2. **判定の手引きを先にコミットする**（D67 の 4）。事前登録の §2.12 と同じコミットで封をし、判定の途中で変えません。
3. **1 人の中でのぶれを減らす工夫**（手順書・手引きの第 21 節）。
   - 判定の順序を無作為にする（同じ木の組が続くと、前の判断に引きずられる）。
   - 判定の途中で集計を見ない（精度が何% になりそうかを見ると、境界の判断が傾く）。
   - 1 日の判定の件数に上限を決める（例: 1 日 10〜15 件。疲れると判断が雑になる）。
   - 迷った件は印を付けて翌日に見直す（見直したことを記録に書く）。

（出典: `docs/decisions.md:3783-3786`、`docs/drafts/prereg_2_12_draft.md:69-81`、`docs/drafts/final_judging_guide_draft.md:666-699`。詳しくは[第 52 章](ch52.md)。）

#### なぜこうしたのか

2 人目を確保できないのに、仕様書の計画どおりに書いておくと、実際にはできないことを約束したことになります。逆に、黙って計画を消すと、「なぜ κ が無いのか」を読み手が知れません。
そこで、実際（判定者 1 人）を採り、仕様書の計画も残し、その差を限界として論文に書く、という形にしました。2 人目の可能性が出てきたので、決めつけずに保留にし、期限を決めました。これは、CLAUDE.md の規則 4（分からないものは「不明」として記録する。黙って安全側に倒さない）と規則 6 の実践です。

#### よくある誤解・つまずき

- **誤解: 「判定者が 1 人なら、結果は信頼できない」**
  信頼性が下がることは認めて、限界に書きます。けれども、根拠を全件公開し、手引きを先に固定し、ぶれを減らす工夫をすることで、第三者が確かめられる形にします。「信頼できない」ではなく、「この範囲で信頼できる、と示す」のです。
- **誤解: 「v4 の AI の判定を、2 人目の判定者として使えばよい」**
  使えません。仕様書は AI を κ に含めないとし、D70 の 3 は 2 人目の判定者の代わりに AI を使わないと決めています。
- **誤解: 「判定し直しは 10% に決まっている」**
  手順書と手引きの下書きは 10% と書いていますが、D70 の 8 は 5〜10% で、全体が保留です。量は未決です。
- **誤解: 「2 人目の件は、判定を始めてから決めてもよい」**
  期限は、データを見る前（遅くとも段階 6 の抜き取りのコミットの前）です。後から足すなら、逸脱として記録し、事後の分析になります。

#### 手作業ではどう使うか

段階 6（抜き取りのコミット）の前に、次を確かめてください。

1. 2 人目の判定者を用意できたか。できたなら、件数・対象の抜き方・裁定のしかた・一致の指標を決め、事前登録の §2.12 に書く。
2. できなければ、判定し直しをするか、するならその量（5〜10% のどれか）を決め、事前登録に書く。
3. どちらもしないなら、「判定者 1 人、判定し直しなし」で進むことを確認する（D67 の 4 が既定）。
4. 決めたことを事前登録に書いてコミットしてから、抜き取りをコミットする。

判定の最中は、毎回の判定で根拠のファイルと行を記録し、かかった分数も書きます（事前登録の下書き 81 行）。迷った件は翌日に見直します。

#### この節のまとめ

今の既定は判定者 1 人（D67 の 4）で、κ に依存する主張はしない。2 人目の判定者と判定し直しは保留（D70 の 8、O2）で、データを見る前（遅くとも段階 6 の抜き取りのコミットの前）に決める。判定し直す量は、仕様書（60 ツール全部）・D70 の 8（5〜10%）・手順書（10%）で違い、未決。
2 人目がいない分は、根拠の全件公開、手引きの先のコミット、ぶれを減らす工夫で支える。

### 8.9 この経緯から学べること — 3 つの作法

#### 一言で言うと

この章の話には、共通の作法が 3 つあります。**先に決めた条件に従って下げる**、**計画と実際を両方記録する**、**うまくいかなかった経験も設計の理由として残す**、です（第 5 部で詳しく扱います）。

#### たとえ話 — 実験ノート

理科の実験で、きちんとした実験ノートには 3 つの特徴があります。
実験の前に「こうなったら仮説は外れ」と書いておき、外れたら外れたと書く。予定していた手順と、実際にやった手順が違ったら、両方を書く。失敗した試みも消さずに残し、なぜ失敗したかを書く。
こうしたノートは、後から読んだ人が「この結論はどこまで信じてよいか」を自分で判断できます。この研究の決定の記録（`docs/decisions.md`）は、この実験ノートに当たります。

#### 作法 1 — 結果を見る前に「こうなったら主張を下げる」と決め、そうなったら決めたとおりに下げる

trig の 0.6% がそうでした。仕様書は、結果を見る前に「20% 未満なら格下げする。撤回しない」と書いていました。実際に 0.6% だったので、決めたとおりに主張を絞りました（D36）。
都合の悪い結果が出たときに、後から条件を変えて主張を守ることはしません。それをすると、どんな結果が出ても主張が守られることになり、測ったことの意味が無くなるからです。

**手作業での使い方**: 判定の手引きは、データを見る前にコミットして封をします。判定の途中で「この規則だと、なんだか結果がおかしい」と感じても、規則を変えません。手引きで決まらない事例が出たら、その件は「不明」にして記録し、手引きを直すなら事前登録に逸脱として書きます（第 22・52 章）。

#### 作法 2 — 計画と実際が違ったら、両方を記録する

仕様書は書き換えず、決定（D36、D67、D70、D71）に「何を、なぜ変えたか」を書きます。
2 人目の判定者の件のように、まだ決まっていないものは「保留」「未決」と書き、黙ってどちらかに倒しません。前身の話を論文に書くかの食い違い（8.2 節）も、未決として残しています。

**手作業での使い方**: 判定で、手引きの規則と原典（決定など）が食い違って見える所に出会ったら、自分で黙ってどちらかに決めず、食い違いとして記録します。たとえば、手順書の第 21 節の 5（判定の一貫性の確認）は D70 の 8 より前の文面で、D70 の 8 は判定し直しを保留にしています（正本は D70 の 8。[第 52 章](ch52.md)）。

#### 作法 3 — うまくいかなかった経験も、設計の理由として残す

前身の Pysa の失敗は、AuthGap が「ツールの関数の中から読む」設計を選んだ理由になり、D71 の理由 1 になりました。
D36 で降ろした仕組みのコードも消さずに残しました。「なぜ降ろしたか」を後から示す材料になるからです。

**手作業での使い方**: 判定で「誤」にした件は、誤の原因（E1〜E9）を必ず記録します。誤の原因の内訳は、論文の限界の節の材料になります（[第 51 章](ch51.md)）。「不明」にした件も、理由を書いて残します。うまく判定できなかった件こそ、記録が役に立ちます。

#### よくある誤解・つまずき

- **誤解: 「計画どおりにいかなかったことは、研究の弱さなので書かない方がよい」**
  逆です。書かないと、読み手は結果をどこまで信じてよいか判断できません。計画と実際の差は、限界として書くことで、結果の信頼の範囲を示します。
- **誤解: 「保留にしておけば、後でいつ決めてもよい」**
  保留には期限があります（D70 の 8 なら、データを見る前、遅くとも段階 6 の抜き取りのコミットの前）。期限を過ぎて決めたものは、逸脱として記録し、事後の分析になります。

#### この節のまとめ

先に決めた条件に従って下げる（D36）。計画と実際を両方記録し、決まっていないものは保留・未決と書く（D67・D70・D71、規則 4・6）。うまくいかなかった経験も設計の理由として残す（前身の失敗、消さないコード）。どれも、判定の作業でそのまま使う作法。

### この章のまとめ

- 前身は、既存の taint 解析の道具 **Pysa**（Pyre の上で動く）を無改変で使い、フレームワークの動的ディスパッチの壁を手で書き下して越えさせる設計だった。**taint 解析**は、値に汚れの印を付けて、危険な操作に届くかを追う解析。
- 前身は、環境が立たない・SDK の **stub**（型の情報だけの身代わりのファイル）の境界で汚れの印が切れる・本体が HTTP の向こう・検査の無い実行は仕様、の 4 つの条件がそろわず、成り立たなかった。AuthGap は、ツールの関数の中から読み、「宣言を超えるか」を判定することで 3 つを外した。これが D71 の理由 1。ただし仕様書は前身の話を「論文には書かない」としており、論文での扱いは**未決**。
- 最初の計画は、trig（発生を誰が決めるか）・val（値を誰が決めるか）・gate（検査とその等級）の 3 つの座標で、脆弱版と修正版を見分けることだった。
- 母集団 v2 で測ると、trig をたどれたのは 14 / 2,231 = 0.6%（条件 20% 以上）、交差行は 5 行・2 プロジェクト（条件 3 行以上・3 プロジェクト以上）。仕様書が先に書いた「撤回しない」条項に従い、主張を「宣言 D と実効 M の照合」に絞った（D36、2026-09-21）。
- trig と gate は**付録**で、判定には要らない。val の「値を誰が決めたか」は、矛・不の規則の中で**核**として使う。付録の仕組みは消さずに残している。
- 判定で読むのは核の欄（`unit`、`D_kind.explicit`、`cap_hits`、`opaque_reasons`、`effects`、注記の `contradiction...`）だけ。「不」は注記の `contradiction_unknown:<宣言>:<理由>` で読む。verdict の `UNKNOWN` は付録の判定で、「不」とは別物。
- 仕様書は、2 人目のラベラー、次元ごとの **κ**（偶然を超えた一致の度合い）、AI を κ に含めない、確保できなければ test-retest、と計画した。今の既定は判定者 1 人（D67 の 4）で、2 人目と判定し直しは**保留**（D70 の 8、O2）。データを見る前（遅くとも段階 6 の抜き取りのコミットの前）に決める。判定し直す量は文書で違い、未決。
- 学べる作法は 3 つ: 先に決めた条件に従って下げる、計画と実際を両方記録する、うまくいかなかった経験も設計の理由として残す。
