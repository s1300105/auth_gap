## 第 24 章 自分の仕事を壊しに行く — 敵対的レビュー

> **この章で分かること**:
> - 「今まで分からなかった呼び出し先や値を、分かるようにする」変更（**解決を広げる変更**）は、前と後の突き合わせ（[第 23 章](ch23.md)の段階 ⑤）だけでは正しさが分からないこと。その理由（間違った相手に確定すると、**本当の相手の効果が消える**）。
> - **敵対的レビュー**とは何か。普段の確認（うまく動くことを確かめる）と何が違うか。どう組み立てたか（観点を分けた点検役、独立した検証役、再現のための小さなプログラム）。
> - 実例: O31 の最初の実装の誤 clear 23 行、D61 の G1・G2 の取り消し、最終凍結の前の添削（D64）の 3 巡、それより前の D17・D21・D35。どれも、テストと突き合わせは通っていた。本記録者が、直す前・最初の実装・凍結版の 3 つの解析器で確かめた小さな例。
> - いつ止めるか（D19 の止める規則）と、「**指摘が 0 件でも、欠陥が無いことは示せない**」という限界。
> - 調査にも「壊しに行く役」を置いた例: LLM 判定の調査は 7 体の agent（文献 3、repo の洗い出し 1、統合 1、**批判役 2**）で行った。**報告そのものが LLM の出力なので、論文に載せる前に学生が原典で確かめる**。裏方の書き込みの調査（3 体）と実装の土台の調査（3 体）も同じ。
> - 理由づけを壊しに行った例: D71 の「新しい分野では自前の解析が多い」を一次資料で調べ直し、単純化しすぎていたと訂正した（決定は変えず、理由だけを直した）。
> - 最終評価の判定で、この考え方をどう使うか（自分の「正」や「誤」を、記録する前に崩しに行く）。

### 24.1 突き合わせだけでは分からない変更

#### 一言で言うと

解析器の変更には、「**今まで分からなかった呼び出し先を、分かるようにする**」種類のものがあります（**解決を広げる変更**）。
この種類の変更は、前と後の突き合わせだけでは、正しさが分かりません。
増えた結果の中に、正しく分かったものと、**間違った相手に決めつけてしまった**ものが混ざるからです。
しかも、間違った相手に決めつけると、**本当の相手の効果が消える**ことがあります。それは誤 clear です。

#### 言葉の確認 — 解決を広げる変更

- **解決を広げる変更**（解決率を上げる変更）
  - やさしい言い換え: 解析器が「分からない」と言っていたものを、「分かった」と言えるようにする変更。
  - 正確な定義: 呼び出し先や値の確度を `opaque`（確かめられなかった）から `resolved`（確かめられた）に変える、または、今まで降りなかった呼び出し先に降りるようにする、解析器の変更。`CLAUDE.md` の言葉では「解決率を上げる変更（opaque → resolved）」。
  - 例: 「受け手の値が文字列やリストの形をしていれば、`x.save()` を組込み型のメソッドと決める」（D61 の G2）。「省略された引数の既定値を定数として入れ、取られない枝を捨てる」（O31）。

#### たとえ話 — 名前だけで荷物を届ける

ある配送センターでは、宛先の住所がかすれて読めない荷物を、「宛先不明」の棚に保管していました。
これを「名前が読めれば、同じ名前の家に届ける」というやり方に変えたとします。
配達できた件数は、ぐっと増えるでしょう。

けれども、その中には 3 種類の荷物が混ざっています。

1. 正しい家に届いた荷物（よいこと）。
2. **同じ名前の別の家**に届いた荷物（悪いこと）。
3. そして 2. の裏返しとして、**本当の宛先の家には、荷物が届かなくなった**。前は「宛先不明」の棚にあったので、問い合わせれば見つかったのに、今は「配達済み」になっているので、誰も探しません。

「配達できた件数」を前と比べるだけでは、1. と 2. の区別はつきません。
3. に至っては、記録の上では何も起きていないように見えます。

解析器でも同じことが起きます。
「宛先不明の棚」が `opaque`（解析器はその効果を「不」として保留していた）、「配達済み」が `resolved` です。
間違った相手に `resolved` で決めつけると、本当の相手の効果が消え、しかも「保留」の印も消えるので、誤 clear になります。

#### 小さな例 — 間違った相手に確定して、本当の効果が消える

説明のために、小さなサーバを書きました（この章の作例。repo には入れていません）。
本記録者が、repo から 3 つの版の解析器を `git archive` で作業用の場所に取り出し、同じ入力で走らせて確かめました（2026-10-01）。

- **D61 の前**: `1100319`（D61 の反例のテストだけを足した版）
- **D61 の最初の実装**: `672f0f0`（G1〜G5 を実装した版。G2 を含む）
- **凍結版**: `analyzer-freeze-3`

```python
 1  from mcp.server.fastmcp import FastMCP
 2
 3  mcp = FastMCP("toy4")
 4
 5
 6  class Document:
 7      def __init__(self, path):
 8          self.path = path
 9
10      def strip(self):
11          return self
12
13      def save(self):
14          with open(self.path, "w") as f:
15              f.write("tidy")
16
17
18  DOCS = {}
19
20
21  @mcp.tool(annotations={"readOnlyHint": True})
22  async def tidy(name: str) -> str:
23      clean = DOCS[name].strip()
24      clean.save()
25      return "ok"
```

行ごとに見ます。

- 6〜8 行目: 文書を表すクラス `Document`。作るときにファイルの場所 `path` を覚えます。
- 10〜11 行目: `strip` というメソッド。ここでは自分自身を返すだけです（文字列の `strip` と**同じ名前**ですが、別物です）。
- 13〜15 行目: `save` というメソッド。14 行目で `self.path` のファイルを**書き込み用に開き**、15 行目で書き込みます。
- 18 行目: 文書を名前で引くための辞書 `DOCS`。中身は実行時に入るので、コードを読むだけでは分かりません。
- 21 行目: ツール `tidy` は「読むだけ」（`readOnlyHint: True`。D1）と宣言しています。
- 23 行目: 辞書から文書を取り出し、`strip()` を呼びます。
- 24 行目: その結果の `save()` を呼びます。これは 13 行目の `Document.save` で、14 行目でファイルを書きます。

人が読むと、`tidy` は「読むだけ」と宣言しながら、ファイルを書いています。D1 に反します。

3 つの版の答えです。

| 版 | `tidy` の効果 | 判定 |
|---|---|---|
| D61 の前（`1100319`） | `builtins.open`（14 行目） | D1 の矛（`fs_write`） |
| D61 の最初の実装（`672f0f0`） | **無し** | 何も出さない（**誤 clear**） |
| 凍結版（`analyzer-freeze-3`） | `builtins.open`（14 行目） | D1 の矛（`fs_write`） |

表の読み方: 1 行が 1 つの版です。
たとえば 2 行目は「D61 の最初の実装では、`tidy` の効果が 1 つも出ず、矛も出なかった。本当はファイルを書くので、誤 clear である」と読みます。

何が起きたのでしょうか。
D61 の G2 は、「受け手の値がリテラルや組込みの構築子から来ると分かっているとき、`x.append(...)` を木の中のクラスのメソッドに解決しない」という、**一見もっともな**直し方でした。
ところが、23 行目の `DOCS[name].strip()` の結果は、解析器の中で「文字列の `strip` の結果」と同じ**形**（文字列の形）に見えてしまいました。
すると G2 は、24 行目の `.save()` を「組込み型（文字列）のメソッド」と**決めつけ**、木の中の `Document.save` に降りなくなりました。
組込みの文字列には `save` などありませんが、解析器は「組込みのメソッドなので効果なし」として、何も出しません。
つまり、**間違った相手（組込み型）に確定したので、本当の相手（`Document.save`）の効果が消えた**のです。

決定の記録は、この形を、G2 を取り消した理由の 1 つとして挙げています。
「値の形（Seq / Map / Str / 文字列の定数）は型の証明ではない。未知の受け手への `strip()` などの TRANSFER の結果（`DOCS[name].strip().save()`）、（中略）で、本当の効果を消した（誤 clear）。取り消す（コードを戻す）」。

（出典: 本記録者が 2026-10-01 に `git archive 1100319 authgap`・`git archive 672f0f0 authgap`・`git archive analyzer-freeze-3 authgap` で取り出した版で走査したもの、`docs/decisions.md:3428-3431`（D61 の G2）、`:3468-3471`（D61 の改訂の G2））

#### 一歩ずつ — 解決を広げると何が混ざるか

| 変更の後に起きること | 突き合わせでの見え方 | 正しいか |
|---|---|---|
| 正しい相手に解決できて、新しい効果が見えるようになる | 「増えた」 | 正しい |
| 間違った相手に確定して、その相手の（無関係な）効果が出る | 「増えた」 | **誤警報** |
| 間違った相手に確定して、本当の相手の効果が消える | 「消えた」、または前から出ていなければ**何も変わらない** | **誤 clear** |
| 前は `opaque` で「不」だったものが、`resolved` で「内」になる | 「不が減った」 | 正しいとは限らない（根拠が誤っていれば**誤 clear**） |

表の読み方: 1 行が 1 つの起きうることです。
たとえば 3 行目は「間違った相手に確定して、本当の相手の効果が消えると、突き合わせでは『消えた』と見える。その効果が前から出ていなかった場合は、何も変わらないように見える。どちらも誤 clear である」と読みます。

3 行目の「前から出ていなければ何も変わらない」が、とくに怖いところです。
[第 23 章](ch23.md)の段階 ⑤ の突き合わせは「前に出ていたものが消えたか」を見ます。
けれども、新しく書かれたコードや、前の版でもたまたま見えていなかった形では、「消えた」ことすら記録に現れません。

4 行目も同じ種類の危険です。
[第 21 章](ch21.md) 21.5 節で見た D17 改訂 2 は、モジュール水準の変数や `os.environ` の値を「定数（運用者が決めた値）で `resolved`」と読むようにした変更でしたが、関数の中の `global` による書き換えなどを見落とし、本当はモデルが書き換えられる値を定数と読んでいました。
前は「分からない（不）」と正直に保留していたものを、間違って「問題なし（内）」に倒したのです。

（出典: `docs/decisions.md:1667-1678`（D17 改訂 2 の表））

#### なぜ突き合わせでは分からないのか

突き合わせの道具（`compare_scans.py`・`diff_effects.py`）は、**前と後の差**を正確に出します。
けれども、差の**意味**（正しく分かったのか、間違って決めつけたのか）は出しません。
D17 改訂 2 の記録は、この点をはっきり書いています。

> **opaque → resolved に変わった行が正しく resolved かは、突き合わせだけでは分からない**（`diff_effects.py` は「slot 変化」として出すが、向きの判断は読む人に任せている）。
> 解決率を上げる変更は、敵対的レビューで「resolved にしてよい根拠」を 1 件ずつ崩しに行く必要がある。

「resolved にしてよい根拠」とは、たとえば「この名前の関数は木の中に 1 つしか無い」「この値は定数から来ている」「この受け手は文字列だ」といった、解析器が「分かった」と言うための理由のことです。
この理由が成り立たない入力を、わざと作って崩しに行く。それが次の 24.2 節の敵対的レビューです。

（出典: `docs/decisions.md:1684-1690`（D17 改訂 2 の「どうして最初に見落としたか」）、`CLAUDE.md` の「よく踏む落とし穴」）

#### よくある誤解・つまずき

- **「解決率が上がったのだから、解析器はよくなった」**: 上がった分の一部は、間違った決めつけかもしれません。解決率は、正しさの証拠になりません。
- **「消えたものが 0 なら、誤 clear は作っていない」**: 本当の相手の効果が**前から出ていなかった**場合、消えたものは 0 のままです。
- **「`resolved` の印が付いていれば確か」**: `resolved` は「解析器が確かだと判断した」という印で、その判断の根拠が崩れていれば、確かではありません。

#### 手作業ではどう使うか

- 判定で解析器の道筋（`witness_chain`）を地図にするとき、途中の呼び出しが**名前だけで決めた解決**でないかを気にします。手引きの手順 C は、組み込みの `set()` を木の中の `CacheManager.set` と取り違えた例（v4 の rails-lens）を挙げ、誤の原因 E3（名前だけの解決の誤り）としています。上の作例は、その逆向き（木の中のメソッドを組込みと取り違えて、効果を消した）です。
- 見落としの判定（解析器が何も出さなかったものを探す）では、上の作例のように「同じ名前の組込みのメソッドがあるクラスのメソッド」（`strip`・`save`・`get`・`set`・`append` など）に出会ったら、解析器が見えていない可能性を考えて、自分で呼び出し先を確かめます。

（出典: `docs/drafts/final_judging_guide_draft.md:116-129`（手順 C）、`:434`（E3））

#### この節のまとめ

解決を広げる変更は、正しい解決と間違った決めつけを同時に増やす。間違った相手に確定すると、本当の相手の効果が消え、「不」の印も消えるので誤 clear になる（作例: D61 の G2 で `DOCS[name].strip().save()` の書き込みが消えた）。
突き合わせは差を出すが、差の意味は出さない。だから「resolved にしてよい根拠」を崩しに行く確認が要る。

### 24.2 敵対的レビューとは

#### 一言で言うと

**敵対的レビュー**は、**変更を壊しに行く立場**で確かめる作業です。
わざと紛らわしい小さなプログラムを作り、変更の前と後の解析器で走らせ、変更のせいで悪くなった所（**退行**）を探します。
普段の確認が「うまく動くことを確かめる」のに対して、敵対的レビューは「**うまく動かない場合を探す**」確認です。

#### 言葉の確認 — 敵対的レビュー・退行・agent・確認と棄却

- **敵対的レビュー**（てきたいてき・レビュー）
  - やさしい言い換え: 自分の仕事の「穴」を、敵の目で探す点検。
  - 正確な定義: 解析器の変更（とくに解決を広げる変更）について、その変更が「分かった」と言う根拠を崩す入力を作り、変更の前と後の版で走らせて比べ、変更が新しく作った誤り（とくに誤 clear・効果の行の消失・クラッシュ）を見つける作業。`CLAUDE.md` は「『resolved にしてよい根拠』を 1 件ずつ崩しに行く敵対的レビューを通す」と書く。
  - 例: O31 の直しに対して、`**kwargs` で値を渡す呼び出しを作り、直した版が本当の書き込みを消すことを示す。
- **退行**（たいこう）
  - やさしい言い換え: 変更のせいで、前より悪くなったこと。
  - 正確な定義: 変更の前の版では正しく扱えていた入力を、変更の後の版では誤って扱うこと。[第 23 章](ch23.md)の「回帰」とほぼ同じ意味で、この repo の文書では両方の言い方が出てくる。
  - 例: D21 が新しく入れた誤 clear 25 件（「D21 が新たに入れた退行」）。
- **agent**（エージェント）
  - やさしい言い換え: 1 つの調べ物や点検を任された AI の作業者。
  - 正確な定義: この repo の記録では、本記録者がワークフローの中で起動し、決まった観点と指示で作業させる、別の AI の実行のこと。点検役（観点ごとに穴を探す）、検証役（指摘を最小の入力で再現する）、実装役、調査役などがある。多くは**読み取り専用**（repo を変えない）で動かした。
  - 例: D35 の敵対的レビューは「2 本、読み取り専用の agent、反証木 24 本」。
- **確認・棄却**
  - やさしい言い換え: 指摘が本当だった（確認）か、本当ではなかった（棄却）か。
  - 正確な定義: 点検役の指摘を、独立した検証役が最小の入力で再現できたものを「確認」、再現できなかったり前提が誤っていたりしたものを「棄却」として数える。
  - 例: D17 改訂 2 は「独立の検証者が最小 fixture で再現した 8 件（棄却 0）」。

（出典: `CLAUDE.md` の「よく踏む落とし穴」、`docs/decisions.md:287`（D35）、`:1667-1670`（D17 改訂 2）、`:1157-1161`（D21 の結果））

#### たとえ話 — 侵入テスト

銀行は、自分の金庫の守りを確かめるために、わざと専門家を雇って「侵入を試みてもらう」ことがあります（侵入テスト）。
鍵がちゃんと閉まることを確かめる点検（普段の確認）だけでは、裏口の窓が開いていることには気づけません。
「どこから入れるか」を本気で探す人がいて初めて、守りの穴が見つかります。

敵対的レビューの点検役は、この侵入の専門家です。
解析器の変更が「分かった」と言っている所に、わざと紛らわしい入力を送り込んで、間違った答えを引き出そうとします。

#### 小さな例 — 敵対的レビューの 3 つの手順

第 3 版から引き継いだ、敵対的レビューの手順です。

1. **わざと紛らわしい入力（小さなプログラム）を作る。**
   例: 同じ名前の関数を 2 つ置く、import した名前を後で書き換える、`try` / `except` で別の関数に差し替える、`**kwargs` で値を渡す、`global` で値を書き換える、など。
2. **変更の前と後の解析器で走らせ、結果を比べる。**
3. **変更のせいで悪くなった所（退行）を探す。**

24.1 節の作例（`DOCS[name].strip().save()`）は、まさにこの手順の 1 つの例です。

1. 「受け手が文字列の形なら組込みのメソッド」という G2 の根拠を崩すために、**文字列の形に見えるが、本当は木の中のクラスのオブジェクト**という入力を作った。
2. D61 の前（`1100319`）と後（`672f0f0`）で走らせた。
3. 前は出ていた書き込みが、後では消えた（退行。誤 clear）。

#### なぜ「壊しに行く」立場が要るのか

理由は 2 つあります。

1. **作った人は、自分の作ったものの「うまくいく場合」を思い浮かべやすい。** 反例のテスト（[第 23 章](ch23.md)）も、作った人が思いついた形しか入りません。O31 の最初の反例のテストには、「刈ってはいけない形」が 8 つ入っていましたが、`**kwargs` で渡す形は入っていませんでした。別の立場から「どこで壊れるか」だけを考える人がいると、作った人の思い込みの外にある形が見つかります。
2. **解決を広げる変更は、誤 clear を作りやすい。** [第 21 章](ch21.md)で見たとおり、誤 clear は出力に現れないので、出力を眺めていても見つかりません。「こういう入力なら消えるはず」と狙って入力を作らないと見つかりません。

`CLAUDE.md` の約束は、このレビューを**解決率を上げる変更（opaque → resolved）に必須**としています。
D64 の手順も、6 番目に「解決率を上げる変更（U09 / U23 / U38 / U40 / U33 / U36）は敵対的レビューを通す」と書いています。
逆に、解決率を下げる側の変更（分かったことにしていたものを、分からない側に戻す変更）は、新しい誤 clear を作らない向きなので、必須ではありません（[第 21 章](ch21.md) 21.8 節の N9 のコミットの「解決率を下げる側だけの変更」）。

（出典: `CLAUDE.md` の「よく踏む落とし穴」、`docs/decisions.md:3602`（D64 の手順の 6））

#### よくある誤解・つまずき

- **「レビューは、コードを読んで感想を言うこと」**: この repo の敵対的レビューは、**再現の入力**を作って、前と後の版で実際に走らせ比べます。「ここが怪しい」という感想は、再現されて初めて「確認」になります。
- **「点検役が指摘したことは、そのまま事実」**: 指摘は、独立した検証役が再現して初めて確認になります。再現できないもの、前提が誤っていたものは棄却されます。点検役も AI（agent）なので、間違えることがあります。
- **「敵対的レビューは、自分の仕事を否定すること」**: 否定ではなく、**凍結の前に誤りを見つけるための投資**です。誤りを入れたまま凍結するほうが、ずっと悪い結果になります（24.6 節）。

#### 手作業ではどう使うか

最終評価の判定でも、同じ立場の切り替えができます。
ある組に「正」を付けようとしたとき、一度だけ、**判定を壊しに来る人の立場**に立って、「この正を崩す入力（読み方）はないか」を考えます。
具体的な問いの一覧は 24.10 節にまとめます。

#### この節のまとめ

敵対的レビューは、変更を壊しに行く立場で、紛らわしい入力を作り、前と後の版で走らせ、退行を探す確認。この repo では、観点ごとの点検役・独立した検証役・再現の木・反例のテストへの固定、の形で組み立てた。
解決率を上げる変更には必須（`CLAUDE.md`、D64 の手順の 6）。指摘は再現されて初めて確認になる。

### 24.3 実例 1 — O31 の最初の実装が作った誤 clear 23 行

#### 一言で言うと

O31（到達しない枝の誤警報）を直した最初の実装は、テストと較正対の突き合わせを通っていました。
けれども、母集団で取り直した run15 で消えた効果を、独立したレビューで原ソースと突き合わせると、**23 行が誤 clear**（本当は届く効果を消していた）でした。

#### たとえ話 — 「使わない部屋」の電気を切る

省エネのために、「使っていない部屋の電気を自動で切る」仕組みを入れたとします。
「人がいない」と判断する根拠は、「入口のセンサーが最後に反応してから 10 分」でした。
ところが、裏口から入った人は入口のセンサーを通りません。
その人がいる部屋の電気まで切れてしまいます。

O31 の直しは、「定数で決まる `if` の、取られない枝を切る」仕組みでした。
「定数だ」と判断する根拠が、裏口（`**kwargs`、`not`、`try` の中の `import` など）から入ってくる値を見落としていたのです。

#### 小さな例 — `**kwargs` で渡した値を見落とす

[第 23 章](ch23.md)の演習 23-2 と同じ形の作例です。
本記録者が 3 つの版で確かめました（2026-10-01）。

```python
 1  from pathlib import Path
 2
 3  from mcp.server.fastmcp import FastMCP
 4
 5  mcp = FastMCP("toy2")
 6
 7
 8  def save(text, path=None):
 9      if path is None:
10          return None
11      Path(path).write_text(text)
12
13
14  @mcp.tool(annotations={"readOnlyHint": True})
15  async def keep_note(text: str, path: str) -> str:
16      opts = {"path": path}
17      save(text, **opts)
18      return "ok"
```

行ごとに見ます。

- 8〜11 行目: `save` は、`path` が `None` なら何もせずに戻り、そうでなければ 11 行目でファイルを書きます。
- 14 行目: ツール `keep_note` は「読むだけ」（D1）と宣言しています。
- 16 行目: モデルが渡した `path` を、辞書 `opts` に入れます。
- 17 行目: `save(text, **opts)` で呼びます。`**opts` は「辞書の中身を、名前つきの引数として渡す」書き方で、`save(text, path=path)` と同じ意味です。つまり `path` は**省略されていません**。モデルが `None` 以外を渡せば、11 行目に届きます。

3 つの版の答えです。

| 版 | `keep_note` の効果 | 判定 |
|---|---|---|
| O31 の前（`289624c`） | `pathlib.Path.write_text`（11 行目） | D1 の矛（`fs_write`） |
| O31 の最初の実装を含む版（`7ea8bac`） | **無し** | 何も出さない（**誤 clear**） |
| 凍結版（`analyzer-freeze-3`） | `pathlib.Path.write_text`（11 行目） | D1 の矛（`fs_write`） |

表の読み方: 2 行目は「O31 の最初の実装を含む版では、`keep_note` の効果が出ず、矛も出なかった。本当はファイルを書くので誤 clear」と読みます。

最初の実装は、`**opts` の実引数を捨て、省略された `path` に既定値の `None` を入れていました。
すると 9 行目の `if path is None:` が「必ず真」に見え、11 行目の書き込みを「届かない枝」として捨ててしまいました。

さらに、[第 23 章](ch23.md) 23.3 節の作例のテスト（`test_prepare_drops_rmtree` と `test_reset_keeps_rmtree`）を、この最初の実装を含む版（`7ea8bac`）で走らせると、**2 つとも通りました**。
テストは通っているのに、テストに書いていない形（`**kwargs`）で誤 clear が起きていたのです。

（出典: 本記録者が 2026-10-01 に `git archive 289624c authgap`・`git archive 7ea8bac authgap`・`git archive analyzer-freeze-3 authgap` で取り出した版で走査し、`pytest` で確かめたもの）

#### 一歩ずつ — どう見つけ、どう直したか

決定の記録（D58 の改訂）によると、見つけ方は次のとおりでした。

1. run14 → run15 で消えた効果 **2,424 件**を全件見た。
2. そのうち canvas-mcp の **2,076 件**は、`make_canvas_request` の `files=None` / `use_form_data=False`（既定値）で届かない POST の枝で、本記録者が原ソースで確かめた（正しく消えた）。
3. 残り **348 件**を、**木ごとに独立した 3 つのレビュー**で原ソースと突き合わせた。

その結果の表です。

| 群 | 消えた行 | 正しい | 誤 clear |
|---|---|---|---|
| canvas-mcp | 2,076 | 2,076 | 0 |
| memory-hub | 110 | 88 | **22** |
| teamplay-talk ほか 7 木 | 127 | 126 | **1**（auto_grocer） |
| claude-replay / cohort / release-kit / xagent | 69 | 69 | 0 |

表の読み方: 1 行が 1 つの群です。
たとえば 2 行目は「memory-hub では 110 行が消え、そのうち 88 行は正しく消えたが、22 行は本当は届く効果を消していた（誤 clear）」と読みます。
誤 clear は合計 22 + 1 = 23 行です。

原因は、どれも「定数に見える値」の出どころを問わなかったことでした。

| 原因 | 何が起きたか |
|---|---|
| (A) 呼び出し側の `**kwargs` / `*args` | `**` の実引数を捨て、省いた仮引数に既定値を入れたので、実際には渡される値が `None` / `False` の定数になった（memory-hub） |
| (A') 間接の降下 | `asyncio.to_thread` などは位置の引数だけを渡し、キーワード引数を渡さないので、残りが既定値の定数になった |
| (B) `not` の代入 | `cache_optimized = not raw_results` が、`raw_results` と同じ真偽になった（逆なのに） |
| (C) `None` との合流 | `if` の後の合流で、モデルの値が定数 `None` に化けた（順序で結果が変わる） |
| (D) 片側だけの束縛 | `try: from m import f` / `except: f = None` の後の `f` が定数 `None` になり、`if f and f(url):` の枝が捨てられた（auto_grocer の `requests.get`） |

表の読み方: 1 行が 1 つの原因です。
たとえば 5 行目は「`try` の中の `import` が成功したときの `f` を解析器が記録せず、`except` 側の `f = None` だけが残ったので、`f` が定数 `None` に見え、`if f and ...` の中の HTTP の GET を捨ててしまった」と読みます。

直し方は、**規則を狭める**ことでした。
「静的な名前は、いま実行している呼び出し先の仮引数に限る。局所変数・大域の名前・import した名前は、値が定数に見えても静的にしない」。
さらに、仮引数でも、`*` や `**` の無い直接の呼び出しで、値の出どころがリテラル（または呼び出し元で静的な名前）で、本体のどこでも束縛し直さないときだけ静的にする、と決めました。
(B)(C)(D) の値の欠陥そのものは、O31 より前からあったもので、この時点では直さず O36 に記録しました（後に D59 で直した）。

改訂後の run16 では、**誤 clear だった 23 行は、経路の単位ですべて戻りました**。
run16 で消えた 2,346 件は、すべて「レビューで正しいと確かめた集合」に入っていました（run15 で消えず run16 で消えた効果は 0）。
（「経路の単位」の意味は[第 30 章](ch30.md)で詳しく説明します。）

（出典: `docs/decisions.md:3190-3203`（D58 の改訂の「見つかったこと」）、`:3202-3216`（誤 clear の原因）、`:3218-3238`（改訂した規則）、`:3260-3270`（D58 の結果の「消えた効果の確かめ方」））

#### なぜそうするのか

- 消えた 2,424 件を**全件**見たのは、O31 が「効果を捨てる」変更で、捨てた中に誤 clear が混ざる危険があったからです（D58 の規則が先に「誤 clear の危険」と書いていた。[第 23 章](ch23.md) 23.2 節）。
- 残り 348 件を**独立した 3 つのレビュー**で見たのは、1 人（1 つの agent）の見落としに頼らないためです。
- 直し方を「狭める」にしたのは、新しい誤 clear を作らない向きだからです。広げる直しは、また新しいレビューを要します。

#### よくある誤解・つまずき

- **「23 行は 2,424 行のうちの 1% 程度なので、気にしなくてよい」**: 誤 clear は、1 件でも「読むだけ」のツールのファイルの書き込みを隠します。しかも、比べる相手のない新しいデータでは、同じ形の誤 clear が何件起きるか分かりません。
- **「run15 は失敗だったので、記録から消す」**: 消しません。決定の記録は「run15（改訂前の O31）は敵対的レビューで誤 clear が見つかったので採らない。記録として残す」と書いています。

#### 手作業ではどう使うか

- O31 の直しは、凍結版に入っています。だから凍結版は、「定数で閉じた枝」の中の効果を数えないことがあります。見落としの判定で、`if` の中の書き込みを見つけたのに解析器が何も出していなかったら、その `if` の条件が**本当に定数で閉じているか**を、自分で確かめます。手引き 14.2 の「定数で閉じた枝」（`DEBUG = False` が定数で、どこでも書き換えない）は、grep で書き換えの有無を確かめる、という手順です。
- 逆に、矛の判定で、解析器が `if` の中の効果を数えていたら、その `if` が定数で閉じていないか（E6）を確かめます。

（出典: `docs/drafts/final_judging_guide_draft.md:235-245`（14.2 到達しない形））

#### この節のまとめ

O31 の最初の実装は、テストも較正対の突き合わせも通っていたが、run15 で消えた 2,424 件をレビューすると誤 clear が 23 行あった。原因は「定数に見える値」の出どころ（`**kwargs`・`not`・`None` との合流・`try` の中の `import`）を問わなかったこと。
規則を「束縛し直さない仮引数」に狭め、run16 で 23 行はすべて戻った。作例でも、最初の実装を含む版だけが `**opts` の書き込みを消すことを確かめた。

D61 は「検証データ（v3）に合わせて直さず、**一般に正しい**直し方だけを入れる」という方針で、5 つの修正（G1〜G5）を選びました。
敵対的レビューにかけると、そのうち **G1 と G2 は「一般に正しい」が成り立たない**と分かり、取り消しました。
G3 と G4 には、見つかった穴を塞ぐ条件を足して残しました（詳しい経緯は[第 35 章](ch35.md)）。

#### たとえ話 — 「どの家でも効く」と言った防犯の工夫

「玄関の鍵を 2 つにすれば、どの家でも空き巣に入られにくくなる」は、だいたい正しそうです。
けれども、「窓の鍵は要らない。空き巣は玄関から入るものだ」は、一見もっともらしくても、一般には成り立ちません。
窓から入る空き巣の例を 1 つ示せば、崩れます。

D61 の G1・G2 は、この「一見もっともらしいが、一般には成り立たない」主張でした。
レビューは、崩す例を次々に示しました。

#### 小さな例 — G1「子プロセスの標準入力はファイルではない」を崩す例

G1 は、「子プロセスの標準入力への書き込み（`communicate(input=...)` や `stdin.write(...)`）はパイプへの書き込みで、ファイルシステムを変えない。だから、ファイルの書き込み（FS_WRITE）の効果にしない」という直し方でした。
v3 では、`helm` や `kubectl` に標準入力で設定を渡すコードが、ファイルの書き込みとして誤って矛になっていたからです。

レビューは、**インタプリタ（コードを実行するプログラム）の一覧に無いコマンドでも、標準入力のデータがコードの実行やファイルの書き込みに届く**例を、次々に示しました。
次は、そのうちの 1 つを短く書いたものです（説明のための作り話。走らせてはいません）。

```python
1  import subprocess
2
3  def save_config(data):
4      p = subprocess.Popen(["tee", "/etc/app.conf"], stdin=subprocess.PIPE)
5      p.communicate(input=data.encode())
```

- 4 行目: `tee` というコマンドを、`/etc/app.conf` を引数にして起動します。`tee` は、**標準入力で受け取ったものを、そのままファイルに書く**コマンドです。`stdin=subprocess.PIPE` は、標準入力をこちらから流し込めるようにする指定です。
- 5 行目: `data` を標準入力に流し込みます。

`tee` は `python` や `bash` のようなインタプリタではありません。
けれども、5 行目の流し込みで、`/etc/app.conf` というファイルが書き換わります。
G1 の「標準入力への書き込みはファイルを変えない」は、ここで崩れます。

決定の記録が挙げた例は、ほかにも `env python3`・`/usr/bin/env bash`・`sudo sh`・`xargs -0 rm`・`zsh`・`ruby`・`sqlite3 db`・`ssh host bash -s`・`patch -p1`・`executable="/bin/bash"`・`uv run python -` などがあります。
結論は、「以前の『FS_WRITE(content) 相当の情報行』は、**子プロセスがデータで何をしうるかの保守的な上界**として正しかった。取り消す（コードを戻す）」でした。
v3 の helm / kubectl の誤警報は、既知の限界（O41）に戻しました。

（出典: `docs/decisions.md:3420-3427`（D61 の G1）、`:3463-3467`（D61 の改訂の G1））

#### 小さな例 — G2 を崩す例

G2 を崩した例の 1 つが、24.1 節の作例（`DOCS[name].strip().save()`）でした。
本記録者が確かめたとおり、D61 の最初の実装（`672f0f0`）では、この書き込みが消えました。
決定の記録は、ほかにも「`+` の結果、`self.remote = ""` / 大域の `SINK = ""` の後で木の中のオブジェクトに束縛し直す形、閉包・`global`・`builtins.list =`・`for list in` による `list` の束縛し直し」で本当の効果を消した、と書いています。
「値の**形**は型の**証明**ではない」が、G2 を取り消した理由です。

#### 一歩ずつ — レビューの進め方と、その後

| 段階 | したこと | 結果 |
|---|---|---|
| 最初の実装 | G1〜G5 を実装（`672f0f0`） | — |
| 実装の途中 | G1 の最初の形は、argv0 や shell が決まらないときも行を消していた | 既存のテスト `test_known_pipe_precondition` が落ちて気づいた（新しい誤 clear）。決まるときだけに狭めた |
| 敵対的レビュー | 入力を作って `1100319`（D61 の前）と `672f0f0`（D61 の後）を走らせ比べた。再現の木は作業用の場所の `advd61/trees` | G1 は前提が誤り、G2 は健全でない、G3 と G4 に穴 |
| 改訂（規則を先にコミット） | G1・G2 を取り消し、G3・G4 に健全性の条件を足す（`a0d9304`） | — |
| 改訂の追記 | 改訂版を、レビューの再現の木**すべて**で `1100319` と比べた | 注釈の名前を import 表だけで解く穴（同じモジュールでのクラスの定義し直し、木の中のモジュールの相対 import）を見つけ、条件を足した（`155aa7d`） |

表の読み方: 1 行が 1 つの段階です。
たとえば 5 行目は「改訂した版を、レビューで作った再現の木の全部にかけ直して D61 の前の版と比べたところ、新しい穴がまた見つかったので、条件を足した」と読みます。

5 行目のように、**直した後にもう一度、同じ再現の木すべてで比べ直す**ことで、直しが作った新しい穴も拾っています。

（出典: `docs/decisions.md:3420-3427`（G1 の実装の形と、最初の実装の新しい誤 clear）、`:3459-3491`（D61 の改訂と追記）、`:3493-3509`（D61 の結果と経過））

#### なぜそうするのか

D61 の方針（「一般に正しい直し方だけを入れる」）は、「この直し方は一般に正しい」という**主張**に支えられています。
主張である以上、崩す例を探す価値があります。
「一般に正しい」と言うなら、1 つの反例で崩れます。
逆に、本気で崩しに行っても崩れなかったものだけを残せば、「一般に正しい」と言う根拠が強くなります。

#### よくある誤解・つまずき

- **「v3 の誤警報を直すための修正なのだから、v3 で誤警報が減れば成功」**: D61 は、v3 の数字を改善として報告しないと決めています（v3 は見た後に直したので、評価には使えない。[第 35 章](ch35.md)）。成功かどうかは、「一般に正しいか」で決まり、v3 の件数では決まりません。
- **「取り消した G1・G2 は、時間の無駄だった」**: 取り消したことで、凍結版に誤 clear を入れずに済みました。取り消しも、記録に残る成果です。

#### 手作業ではどう使うか

- G1 を取り消したので、凍結版は、子プロセスの標準入力への書き込み（`pipe:write`・`pipe:communicate`）を、保守的に「ファイルの書き込みかもしれない」として扱うことがあります。矛の判定で、この形に出会ったら、子プロセスが受け取ったデータで本当にファイルを変えるか（`tee` のように変えるのか、`helm` のように変えないのか）を確かめます。変えないなら誤で、原因は E5（子プロセスの標準入力・パイプを書き込みと読んだ）です。
- G2 を取り消したので、凍結版は、組込み型のメソッド（`bytearray.append` など）を木の中の同名のメソッドに結ぶことがあります。矛の判定でこれに出会ったら、誤の原因 E3（名前だけの解決の誤り）を疑います。

（出典: `docs/drafts/final_judging_guide_draft.md:434-436`（E3〜E5））

#### この節のまとめ

D61 の「一般に正しい」修正のうち、G1（標準入力はファイルではない）は `tee` や `xargs rm` などの反例で、G2（値の形が組込みなら組込みのメソッド）は `DOCS[name].strip().save()` などの反例で崩れ、取り消した。G3・G4 は条件を足して残した。
直した後も、再現の木すべてで比べ直し、直しが作った穴まで拾った。

### 24.5 実例 3 — 最終凍結の前の添削で、巡を重ねた

#### 一言で言うと

最終凍結の前の添削（D64）では、直した所に敵対的レビューを何度も通しました。
1 回のレビューで見つかった所見を直すと、**その直しがまた新しい誤りを作る**ことがあったので、「直す → レビュー」を 1 巡として、**3 巡**で打ち切りました。
巡ごとに所見は減りましたが、0 にはなりませんでした（詳しい経緯は[第 36 章](ch36.md)）。

#### たとえ話 — 原稿の校正

原稿の校正では、赤字を直すと、直した箇所に新しい誤字が入ることがあります。
だから、直した後にもう一度読みます（再校）。
再校でも見つかれば、三校、四校と続けます。
けれども、締め切りがあるので、どこかで止めます。
止めるときは、「三校まで見た。四校はしていない」と書いておきます。

#### 小さな例 — 段階 B の 3 巡

D64 の段階 B（4 つの単位の直し: U09・U23・U38・U40）のレビューの経過です。

| 巡 | やったこと | 結果 |
|---|---|---|
| 1 | 実装の差分の敵対的レビュー | 所見 25（誤 clear 13・誤警報 11・数え落とし 1）。どれもこの差分が新しく作ったもの |
| 2 | 23 件を直す（単位ごとに反例テストを先にコミット）。2 件は既存の限界と同じ形なので記録 | 再点検で 23 件とも閉じた。新しい所見 12（直しが作ったもの 6、既存 6） |
| 3 | 直しが作ったもの 6 件と、段階 B の新しいコードの中の変種 3 件を直す | 9 件とも閉じた |

表の読み方: 1 行が 1 巡です。
たとえば 2 行目は「2 巡目では、1 巡目の所見のうち 23 件を直し（2 件は記録に回した）、再点検で 23 件とも閉じたことを確かめた。けれども、新しい所見が 12 件見つかり、そのうち 6 件は 2 巡目の直しが作ったものだった」と読みます。

25 → 12 → （3 巡目は新しい所見を探さず、閉じたことだけを確かめた）と、減ってはいますが、0 にはなっていません。

決定の記録は、打ち切りについて次のように書いています。
「3 巡目は反例テストで閉じたことだけを確かめ、新しい所見の探索はしない（添削の探索の上限と同じ考え。巡ごとに所見は減っているが 0 にはなっていないので、**段階 B の新しいコードも見つけ尽くしてはいない**）」。
さらに、3 巡目の直しのうち解決率を上げる側のもの（U23 の R1・R2）は、本記録者が差分を読んで条件を確かめただけで、「**別の敵対的レビューを通していない**（限界として記録する）」と書き、`docs/open_questions.md` にも残しています。

（出典: `docs/decisions.md:3617-3628`（D64 の追記の段階 B の表と探索の打ち切り）、`:3664-3671`（3 巡目の結果と、別のレビューを通していないこと）、`docs/open_questions.md:1177`（段階 B の限界の行））

#### 一歩ずつ — 1 巡の中で何が起きるか

決定の記録から、1 巡の流れを順に書き出すと、次のようになります。

1. **点検する**: 直した差分を、敵対的レビューにかける。所見には、誤りの向き（誤 clear・誤警報・数え落とし）を付ける。
2. **仕分ける**: 所見を「この差分が新しく作ったもの」と「前からあるもの」に分ける。前からある限界と同じ形のものは、直さずに記録に回すことがある（2 巡目の 2 件。U38 ADV-5、U40 R7）。
3. **反例のテストを先に書く**: 直すと決めた所見ごとに、反例のテストを**実装より先に**コミットする（[第 23 章](ch23.md)の段階 ②）。
4. **直す**: 規則の範囲で直す。
5. **閉じたかを確かめる**: 反例のテストが通り、所見が閉じたことを確かめる（再点検）。
6. **次の巡へ**: 直した差分には新しい誤りが入りうるので、再点検で新しい所見を探す（2 巡目の「新しい所見 12」）。

3 巡目では、6 の「新しい所見を探す」を行わず、5 の「閉じたか」だけを確かめて止めました。
これが「打ち切り」です。
止めたので、「3 巡目の直しには、新しい所見の探索をしていない」ことが、そのまま限界として残ります。

もう 1 つ、記録が正直に書いていることがあります。
3 巡目の直しの多くは「解決率を下げる側（opaque・決めない・見過ぎる側）」だけでしたが、U23 の R1・R2 は「解決率を上げる側」でした。
解決率を上げる直しにはレビューが必須（24.2 節）なのに、ここでは本記録者が差分を読んで条件を確かめただけでした。
記録は、それを隠さず「別の敵対的レビューを通していない（限界として記録する）」と書いています。

（出典: `docs/decisions.md:3617-3628`、`:3662-3672`）

#### 小さな例 — 段階 A の 1 回のレビュー

段階 A（SQL の先頭語と URL の宛先の直し: U33・U36）にも、1 回のレビューを通しました。
見つかったのは、**直しが新しく作った**誤 clear 3 種（入れ子のコメント、MariaDB の `/*M!`、`\r` で終わる行コメント）、矛を不に落とす退行 1 種、IPv6 の一部の書き方（6to4 など）を手元宛てと読む誤 clear でした。
規則の改訂（`docs/contradiction_principles.md` の §9.6 の改訂 1'・2'・7'）を先にコミットしてから直しました。
直しの範囲の外にあった古い穴（N9〜N11、A1、A2）は O42 に記録しました（そのうち N9 は、後に凍結の前に直しました。[第 36 章](ch36.md)）。

（出典: `docs/decisions.md:3610-3615`（D64 の追記の段階 A））

#### なぜ巡を重ね、なぜ打ち切るのか

- **巡を重ねる理由**: 直しは、それ自体が新しい変更です。1 巡目の所見を直した差分にも、新しい誤りが入りえます（2 巡目の「直しが作ったもの 6」）。だから、直した差分をまた点検します。
- **打ち切る理由**: 所見が 0 になるまで続けると、終わりが決まりません。しかも、終わりを決めずに続けると、「都合のよい回で止める」ことができてしまいます（24.7 節）。だから上限を決め、止めたことと、止めた時点で残っているものを記録します。

#### よくある誤解・つまずき

- **「3 巡で 0 にならなかったのは、レビューが下手だったから」**: そうとは限りません。新しいコードには、新しい誤りが入りうるものです。大事なのは、「見つけ尽くしていない」と正直に書くことです。
- **「打ち切った後に残った誤りは、無いことにしてよい」**: 無いことにはしません。記録に回した所見（U38 ADV-5、U40 R7 など）と、別のレビューを通していない差分（U23 R1・R2）を、限界として O42 に書いています。

#### 手作業ではどう使うか

- 判定でも、迷った件を見直すと、見直しで別の迷いが生まれることがあります。手順書 21 節の工夫（迷った件は印を付けて翌日に見直す、見直したことを `note` に書く）は、巡を 1 回だけ足す工夫と言えます。何度でも見直すのではなく、見直したことを記録して先へ進みます。
- 判定に使える時間には上限があります。手引き 19 節の「20〜30 分調べても決められなければ不明」は、1 件ごとの打ち切りの規則です。打ち切ったら、理由を `unknown_reason` に書きます。

（出典: `docs/final_evaluation_procedure.md:1303`（21 の 4）、`docs/drafts/final_judging_guide_draft.md:547-559`（19 「不明」にするとき））

#### この節のまとめ

最終凍結の前の添削では、直した所に敵対的レビューを巡として重ねた。段階 B は 25 → 12 と所見が減ったが 0 にならず、3 巡で打ち切った。直しが新しい誤りを作るので巡を重ね、終わりを決めるために上限を置く。
止めたこと、見つけ尽くしていないこと、別のレビューを通していない差分を、限界として記録した。

### 24.6 それより前の実例 — 関門を通ったのに見つかった誤り

#### 一言で言うと

新しい薬は、試験を通ってから使われ始めます。
それでも、使う人が増えると、試験では見えなかった副作用が報告されることがあります。
過去の薬の副作用の記録を並べると、「この種類の薬では、この種類の副作用が出やすい」という傾向が見えてきます。

（出典: `docs/decisions.md:1667-1757`（D17 の改訂 2〜5）、`:1518-1586`（D19 の結果、確認件数 8 → 5 → 6 → 6 → 4）、`:1151-1172`（D21 の結果）、`:269-304`（D35）、`:3077-3081`（D57 の §9.5）、`docs/preregistration.md:561`（逸脱 #10 の日付））

#### 一歩ずつ — 表から読み取れること

1. **見つかったものの多くは誤 clear**です。誤警報（言いすぎ）より、誤 clear（言わなさすぎ）が多く見つかっています。解決を広げる変更は、「分かった」と言いすぎて、本当の効果や保留の印を消す向きに誤りやすいからです（24.1 節）。
2. **関門を通った後に見つかっている**ものが多いです。D21 は関門を全部通っていました（[第 23 章](ch23.md) 23.8 節）。D58 の O31 も、テストと較正対の突き合わせを通っていました。
3. **直しがまた誤りを作る**ことが、繰り返し起きています。D17 は 5 回、D64 の段階 B は 3 巡でした。
4. **棄却が 0 の回が多い**ことにも注目してください。指摘が本当だった割合が高い、つまり点検役が見当違いの指摘をすることは少なかった、ということです。

#### なぜ実例を並べて知っておくのか

実例を知っておくと、「関門を通ったから大丈夫」「テストが全部通ったから大丈夫」と言いたくなったときに、立ち止まれます。
また、凍結版にも、まだ見つかっていない誤 clear が残っている可能性が高いことが分かります（24.7 節）。
最終評価の見落としの判定（V3）は、その残りを測る手続きです。

#### よくある誤解・つまずき

- **「レビューのたびに誤りが見つかったのは、作り方が悪かったから」**: 解決を広げる変更は、本質的に誤 clear を作りやすい変更です。見つかったことは、手順が機能した証拠でもあります。第 3 版の「よくある疑問」も、「誤りを入れたまま凍結するのが失敗で、凍結の前に見つけて直せたのは、手順が機能した証拠」と答えています（[第 56 章](ch56.md)）。
- **「レビューで見つかったものは全部直した」**: 全部ではありません。直さずに既知の欠陥・限界として記録したもの（D19 の K1〜K7、D64 の O42 の一部）もあります。

#### 手作業ではどう使うか

- 見落としの判定で、表に出てくる形（モジュール水準の変数を関数の中で書き換える、`os.environ` に書いてから読む、別名つきの import、同じ名前の関数・クラス、`try` / `except` の予備の import など）に出会ったら、解析器が見えていない可能性を考えて、とくに丁寧に読みます。
- 矛の判定で、解析器の道筋が名前だけの解決を通っているとき（`opaque(unresolved)` の印など）は、誤の原因 E3 を疑って、呼び出し先を自分で確かめます。

D17（5 回のレビュー、確認 8 → 5 → 6 → 6 → 4）、D21（関門を全部通ったのに false-clean 29 件）、D35（false-clean 13 形）、D57（§9.5）、D58、D61、D64 と、解決を広げる変更には、ほぼ毎回レビューで誤 clear が見つかった。

<a id="s24-8"></a>
### 24.7 いつ止めるか — 止める規則と、レビューの限界

#### 一言で言うと

敵対的レビューと修正の繰り返しは、**止める規則を先に決めて**から行います（D19）。
止める規則が無いと、数字がよく見える回で止めて、その回を選べてしまうからです。
そして、レビューで**指摘が 0 件でも、欠陥が無いことは示せません**。凍結は「この手続きで見つからなかった」ことの記録にすぎません。

#### たとえ話 — くじを引き直す

「当たりが出るまで引いてよいくじ」は、くじではありません。
レビューと修正も、「よい結果が出るまで繰り返し、よい回で止める」なら、止めた回の数字は信用できません。
だから、「何回まで」「どんな条件で止める」を、先に決めておきます。

#### 小さな例 — D19 の止める規則

D19 は、4 回目のレビューを走らせる**前に**、次のように決めました（決定の記録から、一部を短くして引用します）。

```
1. 凍結の条件: 直前の修正の差分だけを対象にしたレビューで、false-clean・効果行の消失・
   クラッシュの向きの確認済み指摘が 0 件になったら、その解析器を凍結する。
2. 精度の損失（誤警報の向き、opaque を増やす向き）の指摘は凍結を妨げない。
3. 上限: 4 回目で上の向きの指摘が確認されたら、テストを先に固定して直し、その差分だけを
   5 回目のレビューにかける。5 回目でもなお確認されたら、繰り返しを止め、残った指摘を
   向きと件数つきで既知の欠陥として報告する（その版を「欠陥が無い」とは書かない）。
4. 各回の run を残す。
この規則の限界: 敵対的レビューで指摘が 0 件でも欠陥が無いことは示せない。凍結は
「この手続きで見つからなかった」ことの記録であり、論文にもそう書く。
```

#### 一歩ずつ — 規則の各項が何を決めているか

- 1: 止める条件を「**誤 clear の向き・効果行の消失・クラッシュ**が 0 件」としています。[第 21 章](ch21.md)で見たとおり、この研究がとくに警戒する向きの誤りです。
- 2: 誤警報の向き（精度の損失）の指摘は、凍結を妨げないとしています。直すと解決を広げる変更になり、またレビューが要るからです。限界として件数と形を記録します。
- 3: 繰り返しの**上限**を 5 回目と決めています。5 回目でも見つかれば、止めて、残りを既知の欠陥として報告します。
- 4: 各回の run を残し、どの回の数字かを分かるようにします。
- 限界: 指摘が 0 件になっても、「欠陥が無い」とは言わない、と先に書いています。

結果はどうだったでしょうか。
5 回目のレビューでも 4 件が確認された（false-clean 1、効果行の消失 3）ので、D19 の 3 に従って**繰り返しを止め、直さず**、その版を「5 回目のレビューで既知の欠陥が確認された版」として報告することにしました（凍結しない、タグも打たない）。
確認件数は 8 → 5 → 6 → 6 → 4 で、0 に近づきませんでした。
決定の記録は、さらにこう書いています。

> 回ごとの指摘の多くは直前の修正が作った退行だったが、K7 のように**最初からあって影響の大きい欠陥が 5 回目で初めて見つかった。** 各回のレビューは直前の差分に焦点を当てたので、差分の外にある欠陥を系統的には拾わない。

K7 は「別名つきの import（`from .net import fetch_url as http_get`）で木の中の関数へ降りず、その先の効果が全部消える」欠陥でした。
後に D61 の G3 で直されました（[第 20 章](ch20.md)、[第 35 章](ch35.md)）。

（出典: `docs/decisions.md:1494-1516`（D19 の決定と限界）、`:1518-1528`（D19 の結果）、`:1584-1587`（手続きの限界として書くこと）、`:3434-3437`（D61 の G3 と K7））

#### なぜ止める規則を先に決めるのか

- **都合のよい回を選ばないため**: 止める規則が無いと、関門の数字がよく見えた回で止めて、それを報告できてしまいます。D19 は「止める規則が無いと、関門の数字を好きな回で止めて選べてしまう」と、決めた理由を書いています。これは[第 22 章](ch22.md)の事前登録と同じ考え方です。
- **終わらせるため**: 上の表のとおり、指摘は 0 に近づかないことがあります。上限が無いと、終わりません。

#### レビューの限界 — 何が見えて、何が見えないか

D19 の記録から、敵対的レビューの限界を 3 つにまとめます。

1. **0 件でも欠陥が無いことは示せない。** 点検役が思いつかなかった形の誤りは、見つかりません。
2. **差分に焦点を当てると、差分の外の古い欠陥は系統的には拾わない。** K7 は最初からあったのに、5 回目で初めて見つかりました。
3. **レビューは、レビューした範囲のことしか言えない。** D64 の段階 B の 3 巡目の差分のように、別のレビューを通していない範囲があれば、それを限界として書きます。

だから、凍結版の解析器にも、まだ見つかっていない誤りがあると考えます。
最終評価の見落としの判定と矛の判定は、凍結版の誤りを、**解析器を作った側とは別の立場（学生）で、別のデータ（最終評価のデータ）で**測る手続きです。

#### よくある誤解・つまずき

- **「最後のレビューで指摘が 0 件なら、論文に『欠陥は無い』と書ける」**: 書けません。「この手続きで見つからなかった」と書きます。
- **「上限に達して止めたのは、失敗を認めたこと」**: 失敗ではなく、先に決めた規則に従ったことです。残った欠陥を、向きと件数つきで報告していれば、読み手は割り引いて読めます。
- **「誤警報の向きの指摘も、全部直してから凍結するべき」**: D19 は、精度の損失（誤警報の向き）の指摘は凍結を妨げないとしています。直すと解決を広げる変更になり、また誤 clear の危険が生まれるからです。

#### 手作業ではどう使うか

- 判定の手引きも、判定を始める前に封をして、判定の途中で変えません（手順書 22 節）。手引きの穴を見つけても、「よい規則を思いついたので、その場で足す」ことはしません。これは D19 の「止める規則を先に決める」と同じ考え方です。
- 論文に解析器の性質を書くときは、「凍結の前に、解決を広げる変更には敵対的レビューを通し、見つかった誤りを直した。見つけ尽くしたとは言えず、残りは既知の限界として記録した」のように、手続きと限界を一緒に書きます。

#### この節のまとめ

レビューと修正の繰り返しは、止める規則を先に決めてから行う（D19: 誤 clear・効果行の消失・クラッシュの向きの確認が 0 になったら凍結、5 回目でも見つかれば止めて既知の欠陥として報告）。D17 では 8 → 5 → 6 → 6 → 4 で 0 に近づかず、規則どおり止めた。
指摘が 0 件でも欠陥が無いことは示せず、差分の外の古い欠陥（K7）は系統的には拾わない。凍結は「この手続きで見つからなかった」ことの記録。

### 24.8 調査にも「壊しに行く役」を置く — そして、報告そのものを確かめる

#### 一言で言うと

壊しに行く考え方は、解析器の変更だけでなく、**調査**にも使いました。
LLM 判定の調査（判定の層に LLM を混ぜる研究を調べ、AuthGap で使えるかを判断する調査）は、7 体の agent のうち **2 体を「批判役」**にして、まとめた結論を崩しに行かせました。
ただし、調査の報告は、批判役のものも含めて、**それ自体が LLM の出力**です。
だから、論文に載せる前に、学生が原典で確かめます。

#### たとえ話 — 会議の「悪魔の代弁者」

大事な決定をする会議で、わざと反対の立場から意見を言う役（「悪魔の代弁者」）を決めておくことがあります。
みんなが賛成している案ほど、見落としがあっても誰も言い出さないからです。

ただし、悪魔の代弁者の意見も、ひとりの人の意見です。
正しいとは限りません。
最後に決めるのは、意見を聞いたうえで、根拠を自分で確かめた人です。

#### 小さな例 — LLM 判定の調査の組み立て

調査の文書（`docs/llm_judgment_survey.md`）の冒頭は、調べ方を次のように書いています。

```
調べ方: ワークフローで 7 体の agent を使った。
- 文献の調査 3 体: R1 一般の SE・セキュリティ、R2 MCP・エージェント、R3 方法論
- repo の中の差し込み箇所の洗い出し 1 体: R4
- 統合 1 体
- 批判的検討 2 体: 妥当性の観点、研究価値の観点

各報告の全文は docs/llm_judgment_survey_raw/ にある。本記録者は統合と批判を読み、
事実の食い違い 3 点を原文で確かめた（§5）。
```

行ごとに見ます。

- 1 行目: 7 体の agent（24.2 節で見た、作業を任された AI の作業者）で調べた。
- 2 行目: 文献を調べる役が 3 体。一般のソフトウェア工学・セキュリティ、MCP とエージェント、方法論（研究の作法）に分けた。
- 3 行目: この repo の中で、LLM を差し込めそうな箇所を洗い出す役が 1 体。
- 4 行目: 4 体の報告をまとめる役（統合）が 1 体。
- 5 行目: **まとめた案を崩しに行く役（批判役）が 2 体**。1 体は「妥当性」（研究として正しく測れるか、再現できるか）、もう 1 体は「研究価値」（論文の価値を本当に上げるか）の観点。
- 7〜8 行目: 報告の全文を残し、本記録者は統合と批判を読んで、事実の食い違い 3 点を原文で確かめた。

（出典: `docs/llm_judgment_survey.md:6-12`）

#### 一歩ずつ — 批判役は何を崩したか

批判役の 1 体（妥当性の観点）の報告の題は、「批判的検討：統合案の候補を、研究の妥当性と再現性から**崩しにいく**」です。
この批判役は、少なくとも 2 つの大事なことを見つけました。

1. **「使わない」という選択肢が、統合案の一覧に無かった。** 統合案は LLM の使い道の候補を 9 つ並べていましたが、「LLM を使わない」を比べる相手として入れていませんでした。批判役は、「『使わない』を既定の選択肢として表に入れる」と指摘し、調査の最終の表には「候補 0: LLM を使わない（既定の選択肢として比べる）」が入りました。そして学生は、2026-10-01 にこの「使わない」を選びました（D70 の 3）。2026-10-02 には、判定者が Python とライブラリに慣れていないことから、「判定は人が行い、AI は事実を調べる補助にだけ使う」に改めています。
2. **研究にすでに LLM が深く関わっていることを、統合案が数えていなかった。** v4 の中間検証の判定は本記録者（AI）が行ったこと、手順書と判定の手引きの下書きを本記録者が書いたこと、など。調査の文書は「C1 §1-1 の指摘。本記録者が確かめた」として、論文での開示が要ることを §4 に書きました。

2 体の批判役は、いつも同じ意見ではありませんでした。
たとえば候補 2（「不」の組に LLM の対照腕を付ける案）について、妥当性の批判役は「価値は小さい」、研究価値の批判役は「今回入れる価値がある」としました。
調査の文書は、食い違うところは両方を書き、決めるのは学生としました。
学生は候補 2 を採らず、2026-10-01 には最終評価の判定で LLM をどの形でも使わないと決めました（D70 の 3）。2026-10-02 の改訂でも、候補 2（対照腕）は置かないままです。

#### 一歩ずつ — 報告そのものが LLM の出力

ここで、いちばん大事な注意があります。
調査の文書は、冒頭近くにこう書いています。

> 論文の PDF はプロキシで遮断され、1 本も直接読めていない。数値は確かさの印つきでしか使わない（CLAUDE.md 規則 1）。
> **この調査の報告そのものが LLM の出力**なので、論文に載せる前に学生が原典で確かめる（`AUTHGAP_BRIEF_v3.md:82`）。

批判役を置いても、批判役も LLM です。
統合役が見落としたことを批判役が見つけても、批判役の言うことが正しいとは限りません。
だから、論文に使う前に、**学生が原典（論文の本文、repo のコード）で確かめる**のです。

引かれている仕様書の 82 行目は、この研究が「LLM を判定（verdict）の入力に使わない」ことを主張の一部にしているので、「その主張を支える関連研究の記述自体を、LLM の要約に頼ったまま提出しない」と決めています。
そして、実際に起きた例を書いています。
ある道具（mcp-sec-audit）について、最初の自動の要約は「AST パターンマッチと意味的データフロー解析」と述べていましたが、PDF の原文は "TOML-driven keyword/regex matching"（設定ファイルで決めたキーワードと正規表現の照合）でした。
仕様書は、「要約が本節の判断を左右する方向に誤っていた」と書いています。
相手の道具を実際より高度に見せる要約は、比べたときの AuthGap の差を小さく見せる（あるいは誤った比べ方をさせる）方向に効きます。

（出典: `docs/llm_judgment_survey.md:19-20`、`AUTHGAP_BRIEF_v3.md:82`）

#### 一歩ずつ — 確かさの印

調査の報告には、主張ごとに**確かさの印**が付いています。
同じ考え方で行った調査が、ほかに 2 つあります。

| 調査 | agent の数 | 確かさの印 | 注意 |
|---|---|---|---|
| LLM 判定の調査（`docs/llm_judgment_survey.md`、2026-10-01） | 7（文献 3・repo 1・統合 1・批判 2） | **高**: repo のコード・プロンプト・結果ファイルを agent が読んだ / **中**: 第三者の逐語の抜き書き / **低**: 検索の要約だけ | 論文の PDF は 1 本も直接読めていない。報告そのものが LLM の出力 |
| 裏方の書き込みの調査（`docs/incidental_writes_practice.md`、2026-09-29） | 3（一次資料を読み、逐語の引用と URL を返した） | **[確認]**: 本記録者が原文を取得して、引用の文字列が原文にあることを確かめた / **[agent]**: agent が原文を読んだと報告したもので、本記録者は照合していない / **[未確認]**: 検索結果の抜粋だけ、または開けなかった（論文の数値などは使わない） | 多くのサイトはプロキシで遮断され、公式文書のソース（GitHub の raw）で読んだものが多い |
| 実装の土台の調査（`docs/implementation_base_survey.md`、2026-10-01） | 3 | **高**: repo のコードや依存関係、または論文本文を読んだ / **中**: 第三者の逐語の抜き書きなど / **低**: 検索結果の要約だけ | 論文の PDF は 1 本も直接読めていない。他研究の検出数などの数値は引用しない |

表の読み方: 1 行が 1 つの調査です。
たとえば 2 行目は「裏方の書き込みの調査は 3 体の agent で行い、本記録者が原文で引用を確かめたものに [確認]、agent の報告だけのものに [agent]、検索の抜粋だけのものに [未確認] を付けた」と読みます。

確かさの印は、**どこまで壊しに行ったか**の記録でもあります。
[確認] は、本記録者が原文を取り寄せて、引用が本当にあるかを確かめた（崩しに行って、崩れなかった）ものです。
[agent] は、agent の言葉だけで、まだ誰も崩しに行っていないものです。
たとえば裏方の書き込みの調査では、OpenAI の ChatGPT Apps の提出ガイドが「ログを書く」ツールは `readOnlyHint: false` にせよと書いていることは [確認]、MCP の参照サーバ sequentialthinking について open の issue で誤りと指摘されていることは [agent] でした。
同じ表の中でも、確かさは行ごとに違います。

（出典: `docs/llm_judgment_survey.md:14-17`、`docs/incidental_writes_practice.md:10-14`、`:22-24`（結論の 2 の印）、`:34-37`（結論の 6 の印）、`docs/implementation_base_survey.md:1-20`）

#### なぜそうするのか

- **批判役を置く理由**: まとめた人（統合役）は、まとめた案の「うまくいく面」を見やすいからです。解析器の敵対的レビューと同じで、別の立場から崩しに行く人がいると、まとめた人の思い込みの外にあるもの（「使わない」という選択肢、すでにある LLM の関与）が見つかります。
- **報告を原典で確かめる理由**: 報告が LLM の出力である以上、LLM の誤り（要約の誤り、引用の取り違え）が入りえます。この研究は「LLM を verdict（解析器の判定）の入力に使わない」ことを主張の一部にしているので（仕様書 82 行目）、その主張を支える記述を LLM の要約に頼るのは筋が通りません。
- **確かさの印を付ける理由**: どの主張がどこまで確かめられているかを、読み手（学生）が一目で分かるようにするためです。`CLAUDE.md` の規則 1（未検証の統計を引用しない。未検証と明示する）を、調査の記述にも当てはめたものです。

#### よくある誤解・つまずき

- **「批判役を置いたのだから、調査の結論は確か」**: 批判役も LLM です。批判役の言うことを鵜呑みにしても、確かさは上がりません。確かさを上げるのは、原典で確かめることです。
- **「[agent] の印の付いた引用は、agent が原文を読んだのだから確か」**: 本記録者は照合していません。論文に使う前に、学生が原文を開いて、引用の文字列が本当にあるかを確かめます。
- **「確かさが『低』のものは、捨ててよい」**: 捨てる必要はありませんが、論文では「確かめていない」と分かる形でしか使わず、数値は使いません。

#### 手作業ではどう使うか

- 論文の関連研究の節を書くとき、3 つの調査の文書から引く主張は、1 つずつ原典で確かめてから使います。確かめられなかったものは、確かさの印をそのまま書くか、使いません。調査の文書の「確かめられなかったもの」の節（LLM 判定の調査の §7、実装の土台の調査の §5）に、確かめるべきものの一覧があります。
- 最終評価の判定では、AI（LLM）に判定させません。ただし AI は、コードについての事実を調べる補助としてだけ使えます（D70 の 3。2026-10-02 に改訂）。だから判定でも「AI の出力を確かめる」場面があります。AI が示したファイルと行や文書は、この節の調査の報告と同じく、鵜呑みにせず自分で開いて確かめます。`evidence` には確かめた行だけを書き、AI の説明と行が合わなければ行を採ります。
- ただし、判定の練習（手順書 6.8）では、v4 の判定（本記録者（AI）が付けたもの）と自分の判定を比べます。このとき、**AI の判定を正解とみなしません**。調査の §4 も、「食い違いは手引きの穴として扱い、AI を正しいとみなさない」と書いています（24.10 節）。

（出典: `docs/llm_judgment_survey.md:163-164`、`:199-206`（§7）、`docs/implementation_base_survey.md:116-122`（§5）、`docs/drafts/final_judging_guide_draft.md:677-680`（21 の 6））

#### この節のまとめ

LLM 判定の調査は 7 体の agent（文献 3、repo 1、統合 1、批判 2）で行い、批判役が「使わない」という選択肢の欠落と、すでにある LLM の関与を見つけた。本記録者は食い違い 3 点を原文で確かめ、誤りの向きも書いた。
ただし**報告そのものが LLM の出力**なので、論文に載せる前に学生が原典で確かめる（仕様書 82 行目。mcp-sec-audit の要約の誤りの例）。裏方の書き込みの調査（3 体、[確認] / [agent] / [未確認]）と実装の土台の調査（3 体、高 / 中 / 低）も同じ。

### 24.9 理由づけを壊しに行く — D71 の訂正

#### 一言で言うと

決定そのものだけでなく、**決定の理由**も壊しに行く対象です。
D71（解析器は自前のまま）の理由の 1 つ「新しい分野では自前の解析が多い」を、学生の依頼で一次資料で調べ直したところ、**単純化しすぎていた**と分かりました。
**決定は変えず、理由だけを直しました**（詳しくは[第 26 章](ch26.md)）。

#### たとえ話 — 答えは合っているが、途中の式が違う

数学の試験で、答えは合っているのに、途中の式が間違っていることがあります。
採点する先生は、答えだけでなく途中の式も見ます。
途中の式が間違っていれば、次の問題では答えも間違えるかもしれないからです。

論文の査読も同じです。
「自前で作った」という結論が正しくても、その理由が間違っていれば、査読者はそこを突きます。

#### 小さな例 — D71 の理由と、その訂正

D71（2026-10-01）は、学生の問い（「使える部分は既存のツールを使ったほうがよいのでは」）に対して、学生が「自前」を選んだ決定です。
最初の記録には、論文に書く 3 つの理由に続けて、次の一文がありました（今は取り消し線が引かれています）。

```
似た系統の研究でも、新しい分野では自前の解析が多い（ReactAppScan・AgentFlow・HintLint は
一次資料で確認済み。docs/related_work.md）。
```

学生は、「本当に他の研究でも自前で行っているかをもう一度深く分析して」と依頼しました。
本記録者は、3 体の agent で 30 余りの研究の土台を一次資料で調べ直し（`docs/implementation_base_survey.md`）、次のように訂正しました。

| 訂正の点 | 中身 |
|---|---|
| 言語の水準は割れている | MCP やエージェントの研究でも、既存の基盤を使うもの（VIPER-MCP は CodeQL、TaintP2X は Pysa、LLMSmith は PyCG、MCP-in-SoS は Joern）と、パーサの上に自作するもの（Agent Audit・MCP-SecLint・HintLint・DoubleX・Packj）が同じくらいある |
| AgentFlow は自前ではない | **YASA の上**とされる（検索の要約で、本文は読んでいない）。前の記述「一次資料で自前と確認済み」は誤り。**確かめていたのは ADG（AgentFlow が自作した上の層）で、その下の土台ではなかった** |
| 分野固有の部分は例外なく自作 | 入口の規則、API と効果の対応表、宣言の読み取りは、どの研究も自分で書く。AuthGap はこの点で標準的 |
| 決定は変えない | 変えるのは論文の理由づけだけ。「みんな自前だから」とは書かず、AuthGap 自身の 3 つの理由（前身の Pysa 設計が成り立たなかった・率を測るために解析できなかったものを理由つきで数える・標準ライブラリだけで再現できる）で示す |

表の読み方: 1 行が 1 つの訂正の点です。
たとえば 2 行目は「AgentFlow は自前で解析していると書いていたが、実は YASA という既存の基盤の上に作られているとされる。前に『一次資料で確認済み』と書いたのは、AgentFlow が自分で作った上の層（ADG）を確かめただけで、その下の土台は確かめていなかった」と読みます。

（出典: `docs/decisions.md:3942-3943`（D71 の取り消し線の付いた理由）、`:3950-3968`（D71 の訂正）、`docs/implementation_base_survey.md:91-110`（§4 結論と D71 の理由づけの訂正））

#### 一歩ずつ — 何が崩れ、何が残ったか

1. **崩れたもの**: 「新しい分野では自前の解析が多い」という一般化。実際は、言語の水準では割れていて、多数派は無い。
2. **崩れたもの**: 「AgentFlow は一次資料で自前と確認済み」という事実の記述。確かめた**層**を取り違えていた。
3. **残ったもの**: 「自前のまま」という決定。理由を AuthGap 自身の事情に置き換えても、決定は支えられる。
4. **新しく分かったこと**: 分野固有の部分は例外なく自作であること。そして、査読で最も突かれやすいのは VIPER-MCP（CodeQL と MCP 専用のクエリ）との対比であること。

2. の誤りの形は、覚えておく価値があります。
「一次資料で確認済み」と書いてあっても、**何を**確認したのかが、主張とずれていることがあるのです。
「AgentFlow の論文を読んだ」は本当でも、「AgentFlow の解析の土台が自前だと確かめた」は本当ではありませんでした。

もう 1 つ注意があります。
訂正のほうの「AgentFlow は YASA の上」も、**検索の要約だけ**で、本文は読んでいません（確かさは低）。
訂正の記録は、そのことも書いています。
壊しに行った結果も、どこまで確かめたかの印つきで残すのです。

（出典: `docs/implementation_base_survey.md:116-122`（§5 確かめられなかったもの: 「AgentFlow が YASA を使うことは検索要約だけ」））

#### なぜ理由まで壊しに行くのか

- **査読で突かれるのは理由だから**: 「自前で作った」こと自体より、「なぜ既存で足りないか」の説明が問われます（D71 の記録も「審査で求められるのは、なぜ既存で足りないかの説明と、既存のツールとの比較」と書いています）。
- **間違った理由は、次の判断を誤らせるから**: 「みんな自前だから」という理由のままだと、VIPER-MCP のような「基盤 + 分野固有のクエリ」という強い比較相手を見落とします。
- **結論が正しくても、理由が誤っていれば記録として不正確だから**: `CLAUDE.md` の規則 1（未検証の統計を引用しない）と同じく、確かめていない一般化を、確かめたかのように書かない。

#### よくある誤解・つまずき

- **「決定が変わらないなら、理由を直す必要はない」**: 論文に書くのは理由です。理由が誤っていれば、論文が誤ります。
- **「訂正したのだから、今度の記述は確か」**: 訂正の記述にも、確かさの低いもの（AgentFlow と YASA）が含まれます。印を見て読みます。

#### 手作業ではどう使うか

- 判定の `evidence` や `note` に書く理由も、同じように「何を確かめたか」と「何を確かめていないか」を分けて書きます。たとえば「lifespan で初期化している」と書くなら、lifespan の関数の中を読んで、初期化が**必ず**済むこと（例外で抜けたら受付が始まらないか、条件つきではないか）まで確かめたのかを書きます（手引き 14.4 の見分け方）。
- 論文の方法の節で「自前で作った理由」を書くときは、D71 の訂正後の 3 つの理由を使い、「みんな自前だから」とは書きません（[第 26 章](ch26.md)）。

（出典: `docs/drafts/final_judging_guide_draft.md:290-296`（14.4 の見分け方））

#### この節のまとめ

D71 の理由「新しい分野では自前の解析が多い」を一次資料で調べ直すと、単純化しすぎで、AgentFlow については確かめた層を取り違えていた（ADG を確かめただけで、土台は YASA とされる）。決定（自前のまま）は変えず、理由を AuthGap 自身の 3 つの事情に直した。
結論が正しくても理由は壊しに行く対象。「一次資料で確認済み」でも、何を確認したかが主張とずれていないかを見る。

<a id="s24-11"></a>
### 24.10 手作業ではどう使うか — 自分の判定を壊しに行く

#### 一言で言うと

最終評価の判定は、学生 1 人で行い、AI には判定させません（D70 の 3。AI は事実を調べる補助だけ）。2 人目の判定者は保留です（D70 の 8）。
だから、判定を別の誰かが壊しに来てくれる仕組みは、今のところありません。
**記録する前に、自分で自分の判定を一度だけ壊しに行く**習慣が、判定の質を支えます。

#### たとえ話 — 提出前の見直し

試験で答えを書いたら、提出する前に「この答えが間違っているとしたら、どこが間違っているか」と考えて見直します。
「合っているはず」と思って見直すと、同じ思い込みのまま読んでしまいます。
「間違っているとしたら」と考えると、別の読み方が見えてきます。

#### 小さな例 — 「正」を崩す読み方を探す

次の作り話のツールで考えます（説明のための作り話で、走らせてはいません）。
解析器は、`os.makedirs` について D1 の矛を出したとします。

```python
 1  import os
 2  from mcp.server.fastmcp import FastMCP
 3
 4  CACHE = os.path.expanduser("~/.cache/notes")
 5  _ready = False
 6
 7  def _ensure_cache():
 8      global _ready
 9      if not _ready:
10          os.makedirs(CACHE, exist_ok=True)
11          _ready = True
12
13  mcp = FastMCP("notes")
14
15  @mcp.tool(annotations={"readOnlyHint": True})
16  def search(q: str) -> str:
17      _ensure_cache()
18      return "..."
```

行ごとに見ます。

- 4 行目: キャッシュのディレクトリの場所を決めます。
- 5 行目: 「準備済みか」の印 `_ready` を `False` で始めます。
- 7〜11 行目: まだ準備していなければ（9 行目）、ディレクトリを作り（10 行目）、印を立てます（11 行目）。「一度だけ初期化する」形です（手引き 14.4）。
- 15〜18 行目: 「読むだけ」と宣言したツール `search` が、17 行目で `_ensure_cache()` を呼びます。

最初の読み: 「`search` を最初に呼んだとき、10 行目でディレクトリを作る。`readOnlyHint: true` に反する。正」。

ここで、**この「正」を崩す読み方**を探します。

| 崩す問い | 確かめること | 崩れたら |
|---|---|---|
| 初期化は、ツールの受付より前に必ず済んでいないか | `FastMCP("notes")` に `lifespan=` が無いか。モジュールの一番上で `_ensure_cache()` を呼んでいないか | lifespan や読み込み時に必ず済んでいれば、ツールの呼び出しでは届かない → 誤（E1） |
| `main()` の中だけで先に済ませていないか | `if __name__ == "__main__":` や `main()` の中の呼び出し | `main()` の中だけなら、`main()` を通らない起動で届くので「到達する」のまま（条件の種類は「起動の方法」） |
| 一度済んだ後に、印を戻す所はないか | `_ready = False` を grep | 戻す所があれば、何度でも届く（到達するのまま） |
| 10 行目は本当にディレクトリを作るか | `os.makedirs` か、同じ名前の別の関数ではないか | 別の関数なら誤（E3） |
| 宣言に反するか | 手引き 15.1 の D1 の表に照らす。この表は、ファイルの書き込み・作成について「ログ・キャッシュ・一時ファイル・ディレクトリの作成も含む」として「反する」としている | 表に照らして反しない動作なら誤（E8）。ディレクトリの作成は反するので、ここでは崩れない |

表の読み方: 1 行が 1 つの崩す問いです。
たとえば 1 行目は「初期化がツールの受付より前に必ず済んでいないかを、`lifespan=` やモジュールの一番上の呼び出しで確かめる。必ず済んでいるなら、ツールの呼び出しでは届かないので、正ではなく誤（原因 E1）になる」と読みます。

この作り話では、`lifespan=` も一番上の呼び出しも無いので、最初の呼び出しで 10 行目に届きます。
崩しに行って、崩れなかったので、正のまま記録します。
条件の種類は「初回」（初回だけ・キャッシュが無いときだけ）、書き込み先の種類は「キャッシュ・状態の保存」です（手引き 14.3、16.1 の順に当てはめる）。
`evidence` には、崩す問いで確かめたこと（`lifespan=` が無いこと、`_ready = False` に戻す所が無いこと）も書いておきます。

（出典: `docs/drafts/final_judging_guide_draft.md:247-265`（14.3 条件つきで到達する形）、`:267-300`（14.4 起動時の初期化）、`:428-445`（17 誤の原因の分類）、`:309-317`（15.1 の D1 の表）、`:388-401`（16.1 書き込み先の種類））

#### 一歩ずつ — 判定の種類ごとの「崩しに行く」使い方

| 判定 | 記録する前に崩しに行くこと | 手引き・手順書 |
|---|---|---|
| 矛の判定で「正」を付ける前 | 上の表の問い（その操作か・届くか・反するか・モデルが決められるか） | 手順 C〜F、14、15、17 |
| 矛の判定で「誤」を付ける前 | **組の位置を全部読んだか**（1 つでも「届く かつ 反する」位置があれば正）。「別の入口からしか呼ばれない」は、関数名で grep して呼び出し元をすべて見たか | 手順 G（「誤にするときは全部を読む」）、14.2 |
| 見落としの判定 | 解析器の出力を**見る前に**原ソースを読み、反しうる動作を全部書き出す。解析器の言い分に引っぱられないための、解析器を壊しに行く立場 | 18.2（D69 の 3。[第 21 章](ch21.md)） |

| どの判定でも | `evidence` を、判定を見ていない第三者がその行を開けば同じ結論に着けるように書く（壊しに来る人が確かめられる形で残す） | 手順 H |

表の読み方: 1 行が 1 つの場面です。
たとえば 2 行目は「矛の判定で誤を付ける前には、その組の位置を全部読んだかを確かめる。正なら 1 つ見つけた時点で止めてよいが、誤にするときは全部を読む」と読みます。

2 行目の非対称（正は 1 つで止めてよいが、誤は全部を読む）にも、この章の考え方が表れています。
「誤」は「解析器が言いすぎた」と結論することで、それが間違っていれば、本当の違反を数えそこねます（矛の判定の誤り）。
だから「誤」の側にこそ、崩しに行く手間をかけます。

#### 一歩ずつ — 練習で AI の判定と比べるとき

手順書 6.8 の判定の練習は、v4 の判定済みの組で行います。
v4 の判定は、本記録者（AI）が付けたものです。

1. v4 の判定から 10 件ほど選ぶ（正・誤・見落としを混ぜる）。
2. **v4 の判定を見ずに**、手順どおりに判定する。
3. v4 の判定と比べる。食い違ったら、**どちらが手引きに合っているか**を考える。
4. 手引きが曖昧で食い違ったなら、段階 1 に戻って手引きを直す（まだ最終評価のデータを見ていないので直してよい）。

ここで大事なのは、3 の「どちらが手引きに合っているか」です。
v4 の判定は、正解ではありません。
LLM 判定の調査の §4 は、「練習 6.8 は、AI の v4 判定を答え合わせに使う手順。学生の判定を AI に合わせると、正解に AI の解釈が入る。食い違いは手引きの穴として扱い、AI を正しいとみなさない」と書いています。
食い違ったときは、**AI の判定も、自分の判定も、両方を壊しに行く**つもりで、手引きの文面に照らします。

（出典: `docs/final_evaluation_procedure.md:540-557`（6.8 判定の練習）、`docs/llm_judgment_survey.md:163-164`）

#### 手作業ではどう使うか — 1 件の判定の流れのどこに入れるか

崩しに行く確認は、手引きの手順 A〜H の中では、**手順 F（宣言に反するかを決める）の後、手順 H（記録する）の前**に入れると、流れを崩さずに済みます（本書の提案）。

1. 手順 A〜F をいつもどおり進め、仮の結論（正・誤・不明）を出す。
2. 仮の結論が**正**なら、上の「崩す問い」の表を上から順に当てる。**誤**なら、組の全部の位置を読んだか、「別の入口からしか呼ばれない」を grep で確かめたかを見直す。
3. 崩れなければ、確かめたこと（`lifespan=` が無い、書き換えが無い、など）を `evidence` に書き足して、手順 H で記録する。
4. 崩れたら、結論を改め、何で崩れたかを `note` に書く（誤の原因 E1〜E9 のどれか、など）。
5. 20〜30 分たっても決めきれなければ、不明にして `unknown_reason` を書く。迷った件には印を付け、翌日に見直す（見直したことを `note` に書く）。

（出典: `docs/drafts/final_judging_guide_draft.md:93-195`（13 手順 A〜H）、`:547-559`（19）、`:666-699`（21））

#### なぜそうするのか

- 判定者が 1 人なので、**判定の誤りを外から見つける仕組みが、今は無い**からです（2 人目の判定者と判定し直しは保留。D70 の 8）。
- 判定の誤りにも、向きがあります。「正」の付けすぎは精度を高く見せ（解析器を実際よりよく見せる）、「誤」の付けすぎは精度を低く見せます。見落としの判定で「反する動作は無い」を付けすぎると、誤 clear が測定から消えます（[第 21 章](ch21.md)）。どちらの向きにも倒れないよう、記録の前に一度崩しに行きます。
- `evidence` を第三者が確かめられる形で書くのは、手引きが「2 人目の判定者がいない分、これが信頼性の担保になる（D67 の 4）」と書いているとおり、**後から誰かが壊しに来られるようにしておく**ためです。

#### よくある誤解・つまずき

- **「崩しに行くと、いつまでも決められない」**: 崩す問いは、表のように決まった数だけです。全部確かめて崩れなければ、記録します。決められなければ、20〜30 分を目安に不明にします（手引き 19 節）。
- **「v4 の判定と食い違ったら、v4 に合わせる」**: 合わせません。v4 は AI の判定で、正解ではありません。手引きに照らして決め、手引きの穴なら段階 1 で直します。
- **「AI に『この判定は正しいか』と聞けば、手軽に崩しに行ける」**: 聞きません。AI に聞いてよいのは事実（「この関数はどこから呼ばれる？」など）だけで、「正か誤か」は聞きません。宣言の値と解析器の答えも渡しません（D70 の 3 の条件 2）。崩しに行くのは自分です。崩す問いのうち「届くか」を確かめるために、呼び出し元を AI に聞くのはかまいませんが、示された行は自分で開きます。

#### この節のまとめ

最終評価の判定は学生 1 人で、AI には判定させず（事実の補助だけ）、2 人目は保留なので、記録する前に自分で自分の判定を一度崩しに行く。正の前には「その操作か・届くか・反するか」を、誤の前には「全部の位置を読んだか」を確かめ、見落としは解析器の出力を見る前に読む。
練習で v4（AI）の判定と比べるときは、AI を正解とみなさず、両方を手引きに照らす。`evidence` は第三者が壊しに来られる形で書く。

### この章のまとめ

- **解決を広げる変更**（opaque → resolved、今まで降りなかった呼び出し先に降りる）は、正しい解決と間違った決めつけを同時に増やす。間違った相手に確定すると、本当の相手の効果が消え、「不」の印も消えるので**誤 clear**になる。突き合わせは差を出すが、差の意味は出さない（D17 改訂 2）。
- **敵対的レビュー**は、変更を壊しに行く立場で、紛らわしい入力を作り、前と後の版で走らせて退行を探す確認。観点ごとの点検役・独立の検証役・再現の木・反例のテストへの固定で組み立てた。解決率を上げる変更には必須。
- 実例: O31 の最初の実装は誤 clear 23 行（`**kwargs`・`not`・`None` との合流・`try` の中の `import`）。D61 の G1・G2 は「一般に正しい」が崩れて取り消し。D64 の添削は 3 巡（25 → 12）で打ち切り。それより前にも D17（確認 8 → 5 → 6 → 6 → 4）、D21（関門を全部通ったのに 29 件）、D35（13 形）。本記録者は、作例で、最初の実装の版だけが本当の書き込みを消すことを確かめた（O31 の `**opts`、D61 の G2 の `DOCS[name].strip().save()`）。
- **止める規則を先に決める**（D19）。指摘が 0 件でも欠陥が無いことは示せず、差分の外の古い欠陥（K7）は系統的には拾わない。凍結は「この手続きで見つからなかった」ことの記録。
- 調査にも壊しに行く役を置いた: LLM 判定の調査は **7 体**（文献 3、repo 1、統合 1、**批判 2**）。批判役が「使わない」という選択肢の欠落と、すでにある LLM の関与を見つけた。ただし**報告そのものが LLM の出力**なので、論文に載せる前に学生が原典で確かめる（仕様書 82 行目）。裏方の書き込みの調査（3 体）と実装の土台の調査（3 体）も確かさの印つき。
- 理由づけも壊しに行く: D71 の「新しい分野では自前の解析が多い」は単純化しすぎで、AgentFlow については確かめた層を取り違えていた。**決定は変えず、理由だけを直した**（[第 26 章](ch26.md)）。
- 最終評価の判定は学生 1 人・AI に判定させない（事実の補助だけ）・2 人目は保留なので、**記録する前に自分の判定を一度崩しに行く**。正の前には届くか・反するかを、誤の前には全部の位置を読んだかを確かめる。練習では v4（AI）の判定を正解とみなさない。
