## 第 34 章 新しいデータで確かめる（v3）

> **この章で分かること**:
> - v3 は、D60（[第 33 章](ch33.md)）で「開発用の確認」と位置づけられた、v2 と重ならない 100 repo の標本で、そのうち MCP サーバは 91 木だったこと。論文の評価のデータではないこと。
> - v3 の作り方（枠・除外・seed・pin・取得後の条件）と、「規則 → 抽出と pin → 取得 → 走査と判定の対象 → 判定」をこの順にコミットしたこと。
> - pin に使う**コミットの SHA**（版の名前）と、[第 22 章](ch22.md)で見た**ファイルの sha256**（中身の指紋）の違い。どちらを何に使うか。
> - 確かめた 3 つのこと（V1 頑健性・V2 矛の精度・V3 見落とし）と、それぞれの分母。V4〜V6 という呼び名が、原典ごとに揃っていないこと。
> - 判定の基準（正・誤・不明）と、「解析器が読み違えた」の読み方。**動作の種類（kind）まで違うときだけ誤（E4）**にし、site の名前だけが違って kind が合っていれば、判定には影響しないこと。
> - 結果（完走 91/91、D1・D2 の矛の抜き取り 60 件で正 49、見落としの抜き取り 30 件で見落とし 7）と、判定したのが本記録者（AI）であること。v3 の判定は**考え方の例で、正解ではない**こと。
> - 誤 11 件が 4 つの決まった形に集中していたこと。その形が、最終評価の誤の原因 E2・E3・E5・E7 の元になったこと。

### この章の位置づけ

[第 33 章](ch33.md)で、解析器を初めて凍結し（`analyzer-freeze-1`）、その 45 分後に学生が評価の方針を決めたこと（D60）を見ました。
D60 は「論文の評価は、学生が別の新しいデータで手動で行う」と決め、v3 を**開発用の確認**に位置づけました。
この章は、その v3 で何をして、何が分かったかの話です。

v3 は、この研究で初めて「解析器を作るときに一度も見ていないデータ」に解析器を当てた場面でした。
v2 は、誤りを探すために何度も走らせたデータで、解析器は v2 に合わせて育っていました（[第 25 章](ch25.md) 25.1 節）。
v3 は、その解析器が「知らないデータ」でも同じように動くかを確かめるためのデータです。
つまり、v2 が「練習問題」なら、v3 は「初めて解く問題」にあたります。
ただし、本番の試験（最終評価）ではありません。

### 34.1 v3 の役割と、作業の順番

#### 一言で言うと

v3 は、凍結したばかりの解析器（`analyzer-freeze-1`）を、v2 と重ならない新しい 100 repo に当てて、**壊れずに動くか・誤った矛を出していないか・見落としが無いか**を確かめた、開発用の確認です。
見つけた欠陥は直してよい、と決めてありました（D60 の 1）。
そして、規則から判定まで、作業の 1 つずつをコミットしてから次へ進みました。

#### たとえ話 — 新しいレシピを、初めて食べる友人に出す

新しい料理のレシピを作っているとします。
家族には何度も試食してもらい、そのたびに味を直してきました。
家族はもう、この料理の「くせ」に慣れています。
だから、家族が「おいしい」と言っても、初めて食べる人も同じように感じるかは分かりません。

そこで、まだこの料理を食べたことのない友人を呼んで、出してみます。
友人の感想で直したい所が見つかれば、まだ店に出す前なので、直してかまいません。
ただし、友人の感想で直した後は、その友人の感想は「店の評判」の証拠には使えません。
店の評判は、開店してから来る、まったく新しいお客さんで測ります。

v2 が家族、v3 が初めて食べる友人、最終評価が開店後のお客さんです。
v3 で見つけた欠陥は直してよい（D60 の 1）。
けれども、直した後の v3 の数字は、評価の証拠には使えません（[第 35 章](ch35.md)で見る D61 の約束）。

#### 一歩ずつの説明 — 順番の意味

1. **規則が先（13:07）**: `docs/population_v3.md` の冒頭には「**抽出・取得・走査の前に書く**（2026-09-24）。書いた後で規則を変えない。変えるなら `docs/preregistration.md` §5 に逸脱として記録する」とあります。枠・除外・seed・確かめ方・分母を、データに触れる前に決めています。
2. **抽出と pin が次（13:08）**: どの 100 件を選んだか、どの版に固定したかを、取得より前にコミットしています。取得してから「この repo は扱いにくいので別の repo に替えよう」とできないようにするためです。
3. **取得と取得後の条件（13:11）**: 取得してみて、宣言のあるファイルが本当に MCP を使っているかを確かめ、使っていない 9 件を件数つきで除きました（34.2 節）。
4. **走査と、判定の対象（13:20・13:22）**: 走査の後、V2 で判定する矛と、V3 で判定するユニットを、**判定の前に**コミットしています。判定の結果を見てから対象を選び直せないようにするためです。
5. **判定（13:25・13:29）**: 対象が固定された後で、判定をしました。
6. **直し方の規則（13:33）**: 判定の結果を見て、何をどう直すかの規則（D61）を、**実装より先に**コミットしました（[第 35 章](ch35.md)）。

（出典: `docs/population_v3.md:1-4`（前に書く約束）、`evidence/population_v3/v2_judge_targets.json` と `v3_miss_targets.json` の `_note`「判定の前にコミットする」）

#### なぜそうするのか — 開発用でも、先に決める

v3 は開発用なので、見つけた欠陥は直してよいデータです（D60 の 1）。
それでも、作り方と確かめ方を先に決めたのは、**確かめの結果そのもの**を信じられるようにするためです。

たとえば、抜き取りの対象を判定の後で選べるなら、都合のよい件だけを選んで「精度は高い」と言えてしまいます。
直してよいデータかどうかと、確かめの手続きが公正かどうかは、別の話です。
[第 22 章](ch22.md)の「結果を見てから基準を選ぶ」失敗は、開発用のデータでも起こりえます。

#### よくある誤解・つまずき

- **「v3 は新しいデータだから、評価のデータだ」**: 違います。D60 で、v3 は開発用の確認と決まりました。論文の評価は、学生が v2・v3（と後の v4）を含まない別のデータで行います（[第 25 章](ch25.md) 25.5 節）。
- **「開発用なのだから、手順はいい加減でよい」**: 違います。直してよいかどうかと、確かめの手続きが公正かどうかは別の話です。v3 でも、対象は判定の前にコミットしました。
- **「v3 の判定は数分おきにコミットされているのだから、最終評価もすぐ終わる」**: 表の時刻はコミットの時刻で、作業の時間ではありません。しかも v3 の判定は、本記録者（AI）が原ソースを読む作業をエージェントに分けて行いました（34.6 節）。最終評価は学生 1 人が AI を使わずに判定するので（D70 の 3）、まったく別の作業量になります。見込みは[第 46 章](ch46.md)で扱います。

#### 手作業ではどう使うか

最終評価も、同じ順番で進みます（第 45・47 章）。
事前登録と判定の手引きに封をし、対象を決めて pin をコミットし、取得・走査し、判定の対象をコミットしてから判定します。
**各段階の出力を、次の段階に進む前にコミットする**という約束は、v3 の作業の順番と同じ考え方です。
判定の途中で「この件は対象から外したい」と思っても、対象の一覧はコミット済みなので外しません。
外すなら、事前登録に逸脱として理由を書きます（[第 22 章](ch22.md)）。

#### この節のまとめ

v3 は、凍結したばかりの解析器を v2 と重ならない新しいデータに当てた、開発用の確認です。見つけた欠陥は直してよかった（D60 の 1）。
それでも、規則 → 抽出と pin → 取得 → 走査と判定の対象 → 判定の順に、1 つずつコミットしてから進んだ。最終評価も同じ順番で進む。

### 34.2 v3 の作り方 — 枠から 91 木まで

#### 一言で言うと

v2 と同じ枠（抽出スクリプトの母集団 3,764 repo）から、v2 で抽出した 100 件を除いた 3,664 repo を抽出元にし、seed 20260924 で 100 件を選び、その時点の版に pin しました。
100 件すべてを取得でき、宣言のあるファイルが `mcp` / `fastmcp` を import しない 9 件を除いて、**MCP サーバは 91 木**でした。

#### たとえ話 — 名簿から、くじで選ぶ

学校の全校生徒の名簿から、アンケートの相手を選ぶとします。
去年アンケートに答えた 100 人は、今年は外します（同じ人に 2 回聞くと、去年の答えに引きずられるからです）。
残りの名簿から、くじで 100 人を選びます。
くじの番号（seed）を記録しておけば、後で誰でも同じ 100 人を選び直せます。

選んだ 100 人のうち、実は転校していた人や、対象の学年でなかった人がいれば、件数を記録して外します。
外した人の代わりに別の人を選び足すことはしません（選び足すと、「誰を足すか」で結果を動かせてしまうからです）。

#### 小さな例 — 件数の流れ

| 段階 | 件数 | 何をしたか |
|---|---|---|
| ① 枠 | 3,764 repo | v2 と同じ抽出スクリプトの母集団（src 側に宣言のある repo） |
| ② 除外 | − 100 | v2 で抽出した 100 件（取得後に除いた 13 件を含む全部） |
| ③ 抽出元 | 3,664 repo | ① − ② |
| ④ 抽出 | 100 件 | seed 20260924 で無作為に選んだ。v2 との重なり 0 |
| ⑤ pin | 100 件 | 抽出時の `git ls-remote <url> HEAD` の SHA で固定。解決できなかったもの 0 |
| ⑥ 取得 | 100 件 | 取得できなかったもの 0 |
| ⑦ 取得後の条件 | − 9 | 宣言のあるファイルが `mcp` / `fastmcp` を import しない |
| ⑧ MCP サーバ | **91 木** | 走査の対象。ユニットは 3,065 |

表の読み方: 1 行が 1 つの段階です。
たとえば 7 行目は「取得した 100 件のうち 9 件は、宣言（`readOnlyHint` など）を書いたファイルが `mcp` も `fastmcp` も import していなかったので、MCP サーバではないとして除いた」と読みます。

#### 一歩ずつの説明 — 1 行ずつ

1. **① 枠は v2 と同じ**: 規則には「列挙はやり直さない（枠を同じにして、違いを『解析器が見ていない repo』だけにする）」とあります。枠まで変えると、v2 と v3 の違いが「枠の違い」なのか「解析器が見たかどうか」の違いなのか、分けられなくなるからです。
2. **枠の数の食い違い（O40）**: 規則を書いた時点の文書は、枠を 3,827 repo としていました。けれども、v2 と v3 の抽出に実際に使った抽出スクリプトの母集団は 3,764 でした。差の 63 のうち 4 は説明できましたが、残りの 59 の原因は**不明**のまま記録されています。v2 と v3 は同じ 3,764 から抽出しているので、両者の比較には効きません。詳しくは[第 25 章](ch25.md) 25.3 節です。
3. **② 除外は「抽出した 100 件の全部」**: v2 では 100 件を抽出し、取得後に 13 件を除いて 87 木を走査しました。v3 の除外は、走査した 87 木だけでなく、除いた 13 件も含めた 100 件の全部です。
4. **訂正の記録**: 抽出のコミット `d103051` のメッセージには「3,827 から 100 を除いた 3,727」と書かれていました。これは計算せずに書いた誤りで、正しくは 3,764 − 100 = 3,664 です。誤りは消さず、`docs/population_v3.md` に訂正として残しました（次のコミット `8c6b5f9`）。
5. **④ 抽出と seed**: 抽出スクリプトに `--exclude docs/corpus_sample_v2.json` を渡し、seed 20260924 で 100 件を選びました。seed は日付で、事前に規則に書いてあります。除外で減った分は補充しません。
6. **⑤ pin**: 選んだ時点の、各 repo の既定のブランチの先頭のコミットの SHA を `git ls-remote <url> HEAD` で調べ、`docs/corpus_sample_v3.json` に書きました。この pin を、取得・走査より先にコミットしています。SHA については 34.3 節で詳しく見ます。
7. **⑦ 取得後の条件**: v2 の定義と同じ条件です。宣言のあるファイルが `mcp` / `fastmcp` を import しないもの、宣言のあるファイルが見つからないもの、取得できないものを、件数を出して除きます。v3 では、import しないものが 9 件、ほかは 0 件でした。
8. **⑧ 走査**: 91 木を、`analyzer-freeze-1` の解析器で、Python 3.12・木ごとの時間の上限 180 秒・深さ 4（v2 と同じ設定）で走査しました。走査の記録（`summary.json`）の `analyzer_commit` は `65650a8` ですが、本書の執筆時に `git diff 90ef6dd 65650a8 -- authgap/` を確かめると差は 0 行で、`authgap/` は凍結の記録の `analyzer_commit`（`90ef6dd`）と同じでした。

（出典: `docs/population_v3.md:17-33`、`:60-68`、`docs/open_questions.md:1051-1057`（O40））

#### 「重なり 0」は何を確かめたのか — 確かめられない記述の扱い

`docs/population_v3.md` は、抽出の結果として「**v2 との重なり 0**」と書いています。
これは、v3 の 100 件の repo の名前が、v2 の 100 件のどれとも同じでない、という意味です。
抽出スクリプトに v2 の一覧を除外として渡したので、名前の重なりが 0 になるのは当然の結果でもあります。

第 3 版の教科書は、ここに 2 つの文を足していました。

- 「v3 の repo は、これまでの**どの**データとも重なりが 0」
- 「判定した件が触れたファイルにも、これまでのデータと**中身が同一のもの**はありませんでした」

どちらも、原典（`docs/population_v3.md`・`evidence/population_v3/`）には見つかりません。
記録にあるのは「v2 との（名前の）重なり 0」だけです。
とくに 2 つ目の「中身が同一のファイルは無い」は、ファイルの中身を比べた記録（ハッシュを並べた結果のファイル）が repo のどこにも無いので、本書では**未検証**として扱い、根拠に使いません。

同じ種類の記述に、第 3 版の[第 38 章](ch38.md)と手順書の 0-7 の「v3 でも 100 木中 8 木に、それまでのデータと同一のファイルがあった」があります。
これも出所の記録が無く、[第 25 章](ch25.md) 25.8 節で**未検証**と扱いました。
「重なりがある」も「重なりが無い」も、ファイルの中身については確かめられていない、ということです。

（出典: `docs/population_v3.md:60-62`、第 3 版の教科書 `docs/textbook_v3.md:1766`・`:2442`、`docs/final_evaluation_procedure.md:208`）

#### なぜそうするのか — 枠を同じにし、除いた分を補充しない

枠を v2 と同じにしたのは、v2 と v3 の違いを「解析器が見ていない repo かどうか」の 1 点に絞るためです。
除外で減った分を補充しないのは、「何を足すか」を後から選べないようにするためです。
取得後に除いた 9 件を件数つきで記録するのも、同じ理由です。
読み手は「100 件のうち 9 件は MCP サーバでなかった」と分かれば、91 木がどこから来たかを確かめられます。

#### よくある誤解・つまずき

- **「v3 は 100 木」**: 抽出は 100 件ですが、走査した MCP サーバは 91 木です。分母を書くときは、どちらの数かをはっきりさせます。
- **「3,827 と 3,764 のどちらかが間違いなので、どちらかに直せばよい」**: 原因が分からない差は、黙ってどちらかに揃えず、「不明」として記録します（`CLAUDE.md` の規則 4。O40）。
- **「v2 と名前が重ならないのだから、中身も重ならない」**: 名前が違っても、フォーク（他人の repo を複製したもの）や、他のプロジェクトのコードを同梱した repo は、中身が同じことがあります。v3 では、中身の重なりは確かめられていません。最終評価では、中身の重なりも除くと決めました（D70 の 6。34.3 節と[第 47 章](ch47.md)）。

#### 手作業ではどう使うか

- 最終評価のデータを作るときも、件数の流れを 1 段ずつ記録します（[第 47 章](ch47.md)）。v3 の表は、その書き方の見本です。
- 最終評価では、v3 の 100 件（`docs/corpus_sample_v3.json` の `targets`）を、v2・v4 の分と一緒に**全部**除きます。取得後に除いた 9 件も含めます（[第 25 章](ch25.md) 25.4 節）。
- 枠の数を論文に書くときは、O40 の食い違いに注意し、抽出に実際に使った数（3,764）を基準に書きます。

#### この節のまとめ

v3 は、枠 3,764 から v2 の 100 を除いた 3,664 から seed 20260924 で 100 件を選び、pin し、取得後の条件で 9 件を除いた 91 木（3,065 ユニット）。
記録にある重なりは「v2 との名前の重なり 0」だけで、ファイルの中身の重なりは確かめられていない（未検証）。

### 34.3 pin のコミットの SHA と、ファイルの sha256 — 2 つの「長い英数字」

#### 一言で言うと

この研究には、見た目の似た「長い英数字」が 2 種類出てきます。
1 つは pin に使う**コミットの SHA**（40 桁）で、「repo のどの版か」を指す**版の名前**です。
もう 1 つは[第 22 章](ch22.md)で見た**ファイルの sha256**（64 桁）で、「ファイルの中身そのもの」を表す**中身の指紋**です。
pin は前者、凍結の確認と中身の重複の除去は後者を使います。

#### 言葉の確認

- **コミットの SHA**
  - やさしい言い換え: repo の「何版目か」を表す名前。
  - 正確な定義: git がコミット（その時点の repo 全体の状態の記録）ごとに付ける識別子。16 進数 40 桁で、git の既定では SHA-1 という計算で作ります。計算のもとは、そのコミットの中身全体（すべてのファイルの状態、親のコミット、作者、日時、メッセージ）です。
  - 例: v3 の 1 件目の pin `4b410305e1b9fa4b738ac8362ad4dc6bc0c255ac`。
- **ファイルの sha256**
  - やさしい言い換え: ファイル 1 つの中身の指紋。
  - 正確な定義: ファイルの中身（バイトの並び）だけから、sha256 という計算で作る 16 進数 64 桁の値。中身が 1 文字でも違えば、まったく違う値になります。ファイルの名前や置き場所、どの repo に入っているかは計算に入りません。
  - 例: 同じ木の `sqlite_reader_mcp/__main__.py` の sha256 は `fe469141b2f7563a2b4a7533e820332ec7a0ce6f1cb44cc36e1a703313662d7f`。

#### たとえ話 — 本の「版と刷」と、1 ページの文章

本には「第 2 版第 3 刷」のような、版と刷の表示があります。
これは「どの本の、どの時点の刷りか」を指す名前です。
同じ本でも、刷が変われば表示が変わります。
コミットの SHA は、この「版と刷」にあたります。

一方、本の 1 ページに書かれた文章そのものを考えます。
同じ文章が、別の出版社の別の本（たとえば引用集）に、そのまま載っていることがあります。
本の名前も版も違いますが、そのページの文章は同じです。
ファイルの sha256 は、この「ページの文章そのもの」の指紋です。
文章が同じなら、どの本に載っていても同じ指紋になります。

だから、「同じ本の同じ刷を手に入れたいとき」は版と刷の表示（SHA）を使い、「同じ文章が別の本に紛れ込んでいないかを調べたいとき」はページの指紋（sha256）を使います。

#### 小さな例 — v3 の 1 件目で、2 つを並べる

`docs/corpus_sample_v3.json` の `targets` の最初の 1 件は、次のとおりです。

```json
{"name": "v3-abhinavnatarajan__sqlite-reader-mcp",
 "repo": "abhinavnatarajan/sqlite-reader-mcp",
 "ref": "4b410305e1b9fa4b738ac8362ad4dc6bc0c255ac",
 "population": "mcp_server",
 "note": "母集団 v3（seed=20260924）",
 "declaring_paths": ["sqlite_reader_mcp/__main__.py"]}
```

（実物は 1 行です。読みやすいように改行しました。）

- `name`: 木の名前。`v3-` の後に、`持ち主__repo の名前` が続きます。
- `repo`: GitHub の上の repo の名前（持ち主 / 名前）。
- `ref`: **pin の SHA**。抽出したときの既定のブランチの先頭のコミットです。40 桁あります。
- `population`: どの種類の母集団から選んだか。`mcp_server` は MCP サーバの母集団です。
- `note`: 人が読むための注記。seed が書いてあります。
- `declaring_paths`: 宣言（`readOnlyHint` など）を書いたファイルの場所。取得後の条件（34.2 節）は、このファイルが `mcp` / `fastmcp` を import しているかを見ました。

本書の執筆時に、手元に取得してある同じ木で、2 つの値を確かめました。

```bash
1  git -C corpus/v3-abhinavnatarajan__sqlite-reader-mcp rev-parse HEAD
2  sha256sum corpus/v3-abhinavnatarajan__sqlite-reader-mcp/sqlite_reader_mcp/__main__.py
```

- 1 行目: 取得した木の、今の版（HEAD）のコミットの SHA を表示します。`git -C <場所>` は「その場所の repo で git を動かす」という指定です。結果は `4b410305e1b9fa4b738ac8362ad4dc6bc0c255ac` で、pin（`ref`）と一致しました。つまり、取得した木は pin した版そのものです。
- 2 行目: 宣言のあるファイル 1 つの中身から sha256 を計算します。結果は `fe469141…`（64 桁）でした。この値は、同じ中身のファイルなら、別の repo に入っていても同じになります。

#### 一歩ずつの説明 — 2 つの違いを表で

| | コミットの SHA（pin） | ファイルの sha256（指紋） |
|---|---|---|
| 桁 | 16 進数 40 桁 | 16 進数 64 桁 |
| 何から計算するか | そのコミットの全体（全ファイルの状態・親のコミット・作者・日時・メッセージ） | ファイル 1 つの中身だけ |
| 何を見分けるか | repo の**どの版か** | ファイルの**中身が同じか** |
| 同じファイルが別の repo にあると | 別のコミットなので、ふつうは SHA も違う | 中身が同じなら、同じ値 |
| この研究での使い道 | pin（取得する版を固定する。後で同じ版を取り直せる） | 凍結の確認（`authgap/` の全ファイルの sha256 から作る結合 sha256。[第 22 章](ch22.md)）、中身の重複の除去（D70 の 6。[第 47 章](ch47.md)） |
| 例 | `4b410305…`（v3 の 1 件目の pin） | `35606ba9…`（凍結版 `analyzer-freeze-3` の結合 sha256） |

表の読み方: 1 行が 1 つの観点です。
たとえば 4 行目は「同じ中身のファイルが別々の repo に入っていると、コミットの SHA はふつう違うが、ファイルの sha256 は同じになる」と読みます。
4 行目に「ふつうは」と書いたのは、フォークした直後でまだ 1 つもコミットを足していない repo は、元の repo と同じコミットを持つので、SHA も同じになるからです。
フォークの後に 1 つでもコミットを足せば、SHA は変わります。
それでも、ツールの定義のファイルを書き換えていなければ、そのファイルの sha256 は元と同じままです。

#### なぜ 2 つが要るのか

pin の目的は、「後で、まったく同じ版を取り直せる」ことです。
GitHub の repo は、持ち主が毎日コミットを足していきます。
「`abhinavnatarajan/sqlite-reader-mcp` を走査した」と書くだけでは、どの日の版かが分かりません。
コミットの SHA を記録しておけば、何か月後でも同じ版を取り直せます。
判定のときに原ソースが要れば、pin の SHA で同じ中身を取り直せる、というのが、最終評価で木を消しながら走査してよい理由でもあります（[第 25 章](ch25.md) 25.6 節）。

一方、中身の重複の除去の目的は、「同じコードを 2 回数えない」ことです。
フォークや同梱のコピーは、repo の名前も SHA も違うのに、ツールの定義のファイルの中身は同じ、ということが起こります。
これは SHA では見分けられません。
ファイルの sha256 を比べて、初めて見分けられます。
D70 の 6 は「ツールの定義を含む `.py` の sha256 で比べる」と決めました。

凍結の確認も、中身で比べる必要があります。
凍結の目的は「解析器のコードが凍結したときと同じか」を確かめることなので、`authgap/` の全ファイルの sha256 を並べ、その並びからもう一度 sha256 を計算した結合 sha256 を使います（[第 22 章](ch22.md) 22.3 節）。

（出典: `docs/population_v3.md:23-24`（pin）、`docs/decisions.md:3868-3872`（D70 の 6）、`docs/fingerprint.json` の `implementation_sha256_combined`）

#### よくある誤解・つまずき

- **「SHA と sha256 は同じもの」**: 名前が似ていて、どちらも「中身から計算する長い英数字」ですが、計算のもとと使い道が違います。コミットの SHA は repo 全体の版、ファイルの sha256 はファイル 1 つの中身です。
- **「pin の SHA が違えば、中身も違う」**: 違います。別々の repo のコミットは SHA が違いますが、その中のツールのファイルの中身が同じことはあります。だから重複の除去は sha256 で行います。
- **「pin の SHA を見れば、どの版の解析器で走査したかが分かる」**: pin の SHA は**走査される側の木**の版です。**走査する側の解析器**の版は、別に記録します（`summary.json` の `analyzer_commit` と `implementation_sha256_combined`、`docs/fingerprint.json`）。v3 の走査では、記録の `analyzer_commit`（`65650a8`）と凍結の記録の `analyzer_commit`（`90ef6dd`）が違って見えますが、`authgap/` の中身は同じでした（34.2 節の 8）。
- **「取得した木は、pin の版に決まっている」**: 取得のしかたによっては、黙って既定のブランチの最新に落ちることがあります（`CLAUDE.md` の落とし穴「浅い fetch は黙って default branch に落ちる」）。取得した木の HEAD が pin の SHA と一致するかを、必ず確かめます。

#### 手作業ではどう使うか

- **段階 4（取得）**: 取得した木ごとに、`git rev-parse HEAD` が pin の SHA と一致するかを確かめます。中断した作業木は HEAD が一致したまま中身が空のことがあるので、取得が最後まで終わったか（作業木が index と一致するか）も確かめます（`CLAUDE.md` の落とし穴）。
- **段階 4（中身の重複の除去）**: ツールの定義を含む `.py` ファイルの sha256 を取り、v2〜v4 の木のファイルや、今回の中のほかの木のファイルと比べます（D70 の 6。[第 47 章](ch47.md)）。ここで比べるのは SHA ではなく sha256 です。
- **走査の前と後（凍結の確認）**: `git diff analyzer-freeze-3 -- authgap/` が空であることと、`summary.json` の `implementation_sha256_combined` が `docs/fingerprint.json` の値（`35606ba9…`）と一致することを確かめます（第 22・36 章）。
- **判定の記録**: 判定の根拠の行番号は、pin した版のファイルの行番号です。後で取り直しても同じ行を指すように、pin の版のまま読みます。

#### この節のまとめ

コミットの SHA（40 桁）は repo の版の名前で、pin に使う。ファイルの sha256（64 桁）はファイル 1 つの中身の指紋で、凍結の確認と中身の重複の除去に使う。
同じ中身のファイルでも、別の repo なら SHA はふつう違うので、重複は SHA ではなく sha256 で見分ける。

### 34.4 確かめた 3 つのこと — V1・V2・V3 と、その分母

#### 一言で言うと

v3 では、解析器について 3 つのことを確かめました。
**V1 頑健性**（91 木すべてで落ちずに最後まで走るか）、**V2 矛の精度**（解析器が出した矛は、本当に宣言に反するか）、**V3 見落とし**（矛の出なかったツールに、本当は宣言に反する動作が無いか）です。
どれも、手続きと分母を抽出の前に決めてありました。

#### たとえ話 — 新しい体温計を確かめる

新しく作った体温計を、病院で使う前に確かめるとします。
確かめることは 3 つです。

1. **壊れずに動くか**: いろいろな人に当てても、電源が落ちたり表示が止まったりしないか。
2. **「熱あり」と出た人は、本当に熱があるか**: 「熱あり」と出た人を何人か選び、昔ながらの水銀の体温計で測り直す。
3. **「平熱」と出た人の中に、熱のある人が混じっていないか**: 「平熱」と出た人を何人か選び、同じく測り直す。

1 が V1、2 が V2、3 が V3 にあたります。
2 だけを確かめても、体温計が「熱あり」をほとんど出さないなら、熱のある人を見逃しているかもしれません。
だから 2 と 3 を両方確かめます。
これは[第 21 章](ch21.md)で見た、誤りの 2 つの向き（誤警報と誤 clear）を両方数える、ということです。

#### 小さな例 — 確かめ方と分母

| 確認 | 手続き | 単位 | 分母 |
|---|---|---|---|
| **V1 頑健性** | parse 失敗・時間の上限での打ち切り・例外で落ちた木を全件列挙し、原因を 1 件ずつ書く | 木（parse 失敗はファイル） | 走査した木の数（91） |
| **V2 矛の精度** | D1・D2 の矛は全件を判定する。60 件を超えたら seed 20260924 で 60 件を抜き取る。D3・D4 の矛は別に 30 件まで | 組（木, ユニット, site, kind, 宣言） | 判定した件数 |
| **V3 見落とし** | D1 か D2 を明示し、その宣言への矛が 1 件も出ていないユニットから、seed 20260924 で 30 件を抜き取る。ツールの本体と、木の中の呼び出し先を深さ 4 まで読む | （ユニット, 宣言） | 30（足りなければ全数） |

表の読み方: 1 行が 1 つの確認です。
たとえば 2 行目は「V2 では、解析器が出した D1・D2 の矛を 1 件ずつ原ソースで判定する。60 件を超えたら seed 20260924 で 60 件を選ぶ。単位は組で、分母は実際に判定した件数」と読みます。

（出典: `docs/population_v3.md:35-50`）

#### 一歩ずつの説明 — 3 つの確認の中身

1. **V1 の「全件列挙」**: 失敗を「何件あった」で終わらせず、1 件ずつ原因を書きます。失敗の原因が解析器の欠陥なら直す対象になり、ファイル自体の書き間違いなら解析器の責任ではありません。原因を書かないと、この 2 つが区別できません。

#### なぜそうするのか — 3 つの答えのそれぞれを確かめる

- V3 は「何も出さない」が当たっているかを確かめます。外れていれば誤 clear（見落とし）です。

- **「V4 は母集団 v4 のこと」**: 違います。大文字の **V4** は「確認の 4 番目（不の件数と理由）」で、小文字の **v4** は「母集団の 4 番目（凍結版の中間検証のデータ）」です。v3 の規則にも V4 があります。文書を読むときは、大文字か小文字かを必ず見ます。

#### 手作業ではどう使うか

- 最終評価の判定は、V2（精度）・V3（見落とし）・V6（不の中身）の 3 つです（[第 45 章](ch45.md)）。v3 の V2・V3 は、そのうち 2 つのひな形です。
- 最終評価の見落としの対象は、v3 と同じく「D1 か D2 を明示し、その宣言への矛が 1 件も出ていないユニット」です（手順書の 0-3。抜き取るのは段階 6）。ただし件数と抜き方は変わりました（30 件から 200 件・1 木 1 件へ。第 46・47 章）。
- 判定の記録を書くとき、どの確認（V2・V3・V6）の判定なのかを取り違えないようにします。同じツールが、V2 の対象（ある宣言の矛）にも V3 の対象（別の宣言の矛なし）にもなりえます。

#### この節のまとめ

v3 は V1 頑健性・V2 矛の精度・V3 見落としを、手続きと分母を先に決めて確かめた。V2 の単位は組、V3 の単位は（ユニット, 宣言）。

### 34.5 判定の基準 — 「解析器が読み違えた」は、いつ誤になるのか

#### 一言で言うと

v3 の判定の基準は、正（その経路は実行時に到達し、その動作は宣言に反する）・誤（到達しない / 動作が宣言に反しない / 解析器が読み違えた）・不明（静的に決められない）の 3 つでした。
このうち誤の 3 つ目「解析器が読み違えた」は、**読み違いのせいで、2 つの問い（到達するか・宣言に反するか）の答えが変わるときだけ**誤にする、と読みます。
とくに受け手の型の読み違いは、**動作の種類（kind）まで違うときだけ誤（E4）**で、site の名前（どのライブラリの関数か）だけが違って kind が合っていれば、判定には影響しません。

#### v3 の基準の文面

`docs/population_v3.md` の V2 の基準は、次のとおりです。

> - **正**: その経路は実行時に到達し、その動作は宣言に反する。
> - **誤**: 到達しない / 動作が宣言に反しない / 解析器が読み違えた（原因の分類を書く）。
> - **不明**: 静的に決められない（理由を書く。黙って正・誤に倒さない）。

（出典: `docs/population_v3.md:42-44`）

ここで、最終評価の判定の手引き（下書き）の 11.2 節と並べると、ぶつかって見える所があります。
手引きは、矛の判定で答える問いを 2 つに絞り、こう書いています。

> 解析器の出した**理由（site 名や注記）が間違っていても、2 つの問いの答えが「はい」なら正**である（例: sqlite3 の接続を psycopg と表示していても、読み取り専用のツールが本当に DB を書き換えるなら正）。判定するのはコードの動作で、解析器の説明ではない。

（出典: `docs/drafts/final_judging_guide_draft.md:51-52`）

v3 の基準の「解析器が読み違えた → 誤」を字面どおりに読むと、「site 名が間違っていたら誤」になりそうです。
手引きは「site 名が間違っていても、2 つの問いが『はい』なら正」と言います。
この 2 つは、どう両立するのでしょうか。

#### たとえ話 — 宅配の伝票

「〇〇運輸で、冷蔵の荷物が届きました」という知らせが来たとします。
確かめたいのは「冷蔵の荷物が本当に届いたか」です。

- 実際には △△便で届いていたが、冷蔵の荷物は確かに届いていた。運送会社の名前は間違っていますが、確かめたいことの答えは「はい」です。知らせは「正しかった」と判定し、運送会社の名前の誤りはメモに書いておきます。
- 実際には、不在票が入っていただけで、荷物は届いていなかった。これは「荷物が届いた」という中身そのものが違います。知らせは「誤り」です。
- 実際には、冷蔵ではなく常温の荷物が届いていた。届いたものの種類が違うので、「冷蔵の荷物が届いたか」の答えは「いいえ」です。これも「誤り」です。

運送会社の名前が site の名前（どのライブラリの関数か）、荷物の種類が kind（ファイルの書き込みか、DB の変更か、通信か）にあたります。
判定で確かめるのは「その種類の動作が本当に起き、宣言に反するか」です。
site の名前の誤りだけなら判定は変わらず、kind が違えば誤です。

#### 小さな例 1 — site の名前だけが違う（v3 の lore、正）

v3 の判定 M44 は、lore という木のツール `search` の組 `psycopg.Cursor.execute` × `DB` × D1 で、判定は**正**でした。

- 149 行目: DB のファイルを置くディレクトリを作ります（このディレクトリの作成も、別の組 M43 として正になっています）。

#### 小さな例 2 — 理由のコードが違っても、宣言によって答えが変わる（v3 の clawking）

v3 の clawking という木のツール `op_get` には、同じ `subprocess.run` に対して、宣言の違う 2 つの組がありました。
コードは次のとおりです（抜粋。中国語の説明の文は省きました）。

```python

428  async def op_get(item: str, field: str = "password") -> str:
...
433      env_extra = _load_op_env()

435          f"op item get {shlex.quote(item)} --fields {shlex.quote(field)} --vault '__YOUR_1PASSWORD_VAULT__'",
```

- 427 行目: ツールの登録です。`readOnlyHint: True`（D1）と `openWorldHint: False`（D3）を宣言しています。
- 428 行目: ツールの関数です。`item` と `field` は、モデル（LLM）が渡す引数です。

解析器は、この `subprocess.run` を「**モデルがコマンドを決められる**起動」（理由のコード `spawn_model`）と読みました。
モデルの渡す値がシェルの文字列に入っているからです。
けれども、`shlex.quote` で囲んであるので、モデルが変えられるのは `op item get` に渡す引数の中身だけで、起動するコマンドは変えられません。
理由のコードは読み違いです。

それでも、宣言ごとに判定すると、答えは分かれます。

| 組 | 到達するか | 宣言に反するか | v3 の判定 |

表の読み方: 1 行が 1 つの組です。

「読み違いがあったら誤」ではなく、「読み違いのせいで 2 つの問いの答えが変わるなら誤」と読む理由が、ここにあります。

3. 判定は**誤**で、原因は **E4**（受け手の型の読み違いで、動作の種類まで違う）です。

#### 一歩ずつの説明 — 2 つの基準をつなぐ読み方

手順書の手順 C は、効果の行を開いたときに 2 つのことを確かめる、と書いています。

1. **その行は本当にその操作か**（書き込み・削除・DB の変更・HTTP の送信・プロセスの起動か）。
2. **呼び出されている関数は本当に site の関数か**。組み込みの `set()` を木の中の `CacheManager.set` と取り違えていないか。

そして、2 の後に、こう続けます。

> site 名のライブラリが違っていても（sqlite3 を psycopg と表示）、**動作の種類（kind）が合っていれば判定には影響しない**。その場合は `note` に書いておく。
> ここで「そもそもその操作ではない」と分かれば、**誤**（原因は E3 / E4 / E5 など）で手順 H へ。

（出典: `docs/final_evaluation_procedure.md:786-799`、同じ文面が `docs/drafts/final_judging_guide_draft.md:113-126`）

これで、v3 の基準と手引きの 11.2 節はつながります。

| 読み違いの種類 | 2 つの問いへの影響 | 判定 | 例 |
|---|---|---|---|
| site の名前（ライブラリ）だけ違い、kind は合っている | 影響しない | 2 つの問いのとおり（正になりうる）。`note` に書く | lore の M44（sqlite3 を psycopg と表示） |
| 理由のコードが違うが、宣言に照らすと答えは「はい」 | 影響しない | 正 | clawking の E01（D3） |
| 理由のコードが違い、宣言に照らすと答えが「いいえ」 | 「宣言に反するか」が「いいえ」になる | 誤（E7 など） | clawking の M32（D1） |
| 受け手の型を読み違え、kind まで違う | 解析器の言う操作が起きない | 誤（E4） | 作り話の `Outbox` |
| 名前だけで呼び出し先を取り違えた | 解析器の言う操作が起きない | 誤（E3） | v3 の `bytearray.append`（34.7 節） |
| 子プロセスの標準入力をファイルの書き込みと読んだ | 書き込みが起きない | 誤（E5） | v3 の helm / kubectl（34.7 節） |

表の読み方: 1 行が 1 つの読み違いの種類です。
たとえば 4 行目は「解析器が受け手の型を読み違えた結果、kind まで違っていた（通信だと言ったが、実際は通信しない）なら、解析器の言う操作は起きないので誤で、原因は E4」と読みます。

まとめると、v3 の「解析器が読み違えた」は、2 つの問いとは別の 3 つ目の理由ではありません。
読み違いが誤になるのは、そのせいで「到達しない」（その操作が起きない）か「宣言に反しない」になるときだけです。
手引きの 14.2 節も、呼び出し先の取り違え（E3・E4）を「到達しない形」の表に入れています。

（出典: `docs/drafts/final_judging_guide_draft.md:229-237`（14.2 節））

#### なぜそうするのか — 判定するのはコードの動作

研究の問いは「ツールの宣言は、実際の動作と一致しているか」です（[第 6 章](ch06.md)）。
解析器の説明（site の名前・理由のコード）は、人がコードをたどるための**地図**で、判定の対象ではありません。
地図に書かれた町の名前が間違っていても、目的の建物が本当にそこにあれば、「建物はあった」が答えです。

もし「site の名前が違えば誤」にすると、解析器の表示の細かな誤りで、本当の違反が「誤」に数えられてしまいます。
精度は低く出ますが、それは解析器の**判断**の誤りではなく**表示**の誤りです。
逆に、kind まで違うなら、解析器は「起きない動作」を違反と言ったことになり、判断そのものが誤りです。
この 2 つを分けることで、精度の数字が「判断の当たり方」を正しく表します。

#### よくある誤解・つまずき

- **「解析器の理由のコードが間違っていたら、その矛は誤」**: 違います。理由のコードが違っても、2 つの問いが「はい」なら正です（clawking の E01）。
- **「site の名前が違えば E4」**: 違います。E4 は、受け手の型の読み違いで **kind まで違う**ときだけです。kind が合っていれば E4 にせず、判定は 2 つの問いのとおりにし、`note` に書きます。
- **「kind が合っていれば必ず正」**: 違います。kind が合っていても、到達しない（E1・E6）、宣言に反しない（E2・E8）なら誤です。kind が合っているのは、手順 C を通過したというだけです。
- **「読み違いを見つけたら、解析器を直す」**: 最終評価では解析器を直しません（第 22・36 章）。見つけた読み違いは、`note` と、必要なら `docs/open_questions.md` の限界に書きます（手引きの第 22 節の 4）。

#### 手作業ではどう使うか

- **手順 C** で、効果の行を開いたら、まず「その種類の操作が本当に起きるか」（kind）を確かめます。次に「呼んでいる関数は本当に site の関数か」を確かめます。
- site の名前だけが違い、kind が合っているときは、判定は手順 D〜F で決め、`note` に「site は X と表示、実際は Y。kind は合っている」と書きます。
- kind まで違うときは誤で、原因を E3（名前だけの解決の取り違え）か E4（受け手の型の読み違い）から選び、`error_class` に 1 文の説明を書きます。迷ったら E9 にして説明を書きます。
- 同じ site に宣言の違う組が複数あるときは、組ごとに別々に判定します（clawking のように、D1 は誤・D3 は正、がありえます）。

#### この節のまとめ

v3 の基準の「解析器が読み違えた → 誤」は、読み違いのせいで 2 つの問いの答えが変わるときだけ誤、と読む。
site の名前だけ違って kind が合っていれば判定に影響しない（`note` に書く）。受け手の型の読み違いで kind まで違うときだけ E4 で、判定するのはコードの動作であって解析器の説明ではない。

#### 誰が判定したか — 本記録者（AI）

第 3 版の教科書は、判定について「エージェント（AI の補助）に分担させ、その根拠（ファイルと行）を**私**が見直して採りました」と書いていました。

> 判定は本記録者（原ソースの確認は木ごとにエージェントに分け、根拠のファイルと行を見直して採った。M19・M10・R11 は本記録者が原ソースで確認）。

つまり、次のような分担でした。

1. 原ソースを読む作業は、木ごとに**エージェント**（本記録者が作業を分けて任せた、別の AI の実行単位）に分けた。
2. エージェントが挙げた根拠（ファイルと行）を、本記録者が見直して判定を採った。
3. M19・M10・R11 の 3 件は、本記録者が自分で原ソースを開いて確かめた。

v3 の規則は、判定を「本記録者 1 人が行う（開発用の確認なので二重判定はしない）」と決めていました。
v3 の記録には、学生（人）が判定を見直したという記録はありません。

### 34.7 誤 11 件の 4 つの形 — 最終評価の E2・E3・E5・E7 の元

#### 一言で言うと

D1・D2 の誤 11 件は、ばらばらではなく、**4 つの決まった形**に集中していました。
子プロセスの標準入力への書き込みをファイルの書き込みとみなした 4 件、同じ呼び出しで作った一時ファイルの削除を破壊的とみなした 3 件、組み込みの `bytearray.append` を木の中の `AuditLog.append` に結んだ 2 件、固定のコマンドに `shlex.quote` した値だけを渡す起動を「モデルが決めるコマンド」とみなした 2 件です。

#### たとえ話 — 同じ所でつまずく

自転車で毎日同じ道を走っていて、転ぶのがいつも同じ段差なら、原因は「運が悪い」ではなく「その段差」です。
段差の場所が分かれば、そこを通るときに気をつけられます。
誤りも同じで、同じ形に集中しているなら、その形を覚えておけば、判定のときに「ここは怪しい」と気づけます。

#### 小さな例 — 5 つの形の一覧

| 形 | 宣言 | 件 | 木 | 記録の分類名 | 最終評価の分類 |

| 子プロセスの標準入力への `communicate(input=None)` を `FS_WRITE` にした | D1 | 4 | agentic-infra | `pipe_stdin_as_fs_write` | E5 |

#### 形 1 — 子プロセスの標準入力（E5）

**標準入力**とは、起動したプログラムに、外から流し込むデータの入り口のことです。
キーボードで打った文字が届く口、と考えると分かりやすいでしょう。
プログラムの中から子プロセス（別のプログラム）を起動するとき、その標準入力に文字列を流し込めます。

agentic-infra のコマンドを走らせる補助の関数は、次のとおりです（抜粋）。

```python
57          proc = await asyncio.create_subprocess_exec(
58              *cmd,
59              stdout=asyncio.subprocess.PIPE,
60              stderr=asyncio.subprocess.PIPE,
61              env=env,
62              stdin=asyncio.subprocess.PIPE if input_data else None,
63          )
64
65          stdout_bytes, stderr_bytes = await asyncio.wait_for(
66              proc.communicate(input=input_data.encode() if input_data else None),
67              timeout=timeout,
68          )
```

- 57〜63 行目: `cmd`（たとえば `["helm", "history", ...]`）を子プロセスとして起動します。`stdout`・`stderr` は、子の出力を受け取る口です。62 行目は「流し込むデータ（`input_data`）があるときだけ、標準入力の口を開く」という指定です。
- 65〜68 行目: `communicate` で、子が終わるのを待ち、出力を受け取ります。66 行目の `input=` は標準入力に流すデータで、`input_data` が無ければ `None`（何も流さない）です。

`helm_get_values` や `kubectl_get` などの読み取りのツールは、`input_data` を渡さずにこの関数を呼びます。
だから実際には何も流し込んでいません。
解析器は 66 行目の `communicate` を、標準入力へ流すデータが「ファイルの書き込み相当」になりうるとして `FS_WRITE` の行にし、D1 の矛にしました。
判定は、起動する `helm` / `kubectl` は値を読むコマンドで、標準入力にも何も送っていないので、宣言に反しない → **誤**です。

解析器がこの形を保守的に扱う理由は、[第 35 章](ch35.md)で見ます（`tee /etc/app.conf` のように、標準入力のデータをそのままファイルに書くコマンドもあるからです）。

（出典: `corpus/v3-clcc2019__agentic-infra/legacy/mcp-servers/deploy-mcp/tools/_command_runner.py:57-68`（本書の執筆時に確かめた）、`evidence/population_v3/v2_judgments.json` の M10〜M13）

#### 形 2 — 同じ呼び出しで作った一時ファイルの削除（E2）

comfypilot のツール `comfy_install_workflow_deps` の一部です（抜粋）。

```python
59      fd, tmp_path = tempfile.mkstemp(suffix=".json", prefix="comfypilot_deps_")
...
64              f = os.fdopen(fd, "w", encoding="utf-8")
...
78      finally:
79          try:
80              os.unlink(tmp_path)
81          except OSError:
82              pass
```

- 59 行目: `tempfile.mkstemp` で、**新しい**一時ファイルを作ります。名前は毎回ちがう、他と重ならない名前です。`fd` はそのファイルを開いた番号、`tmp_path` はその場所です。
- 64 行目: その一時ファイルを書き込み用に開き、ワークフローの中身を書きます（間の行は省略）。
- 78〜80 行目: `finally`（途中で何が起きても最後に必ず走る部分）で、一時ファイルを `os.unlink` で消します。
- 81〜82 行目: 消すのに失敗しても無視します。

D2（`destructiveHint: false`）は「呼び出しの前からあったものを消したり上書きしたりしない」という宣言です。
80 行目で消しているのは、59 行目で**同じ呼び出しの中で自分が作った**ファイルです。
呼び出しの前からあったものではないので、宣言に反しません → **誤**（E2）です。

ここで注意が要ります。
手引きの 15.1 節は、D1（`readOnlyHint: true`）では「一時ファイルの作成・削除も含めて、ファイルの書き込み・作成・削除はすべて環境の変更（反する）」としています。
つまり、**同じコードでも、D1 に照らせば正、D2 に照らせば誤**になります。
v4 の M58（ru-marketplace の `ozon_reviews` × `os.remove` × D1）は、同じ呼び出しで作った一時ファイルの削除でしたが、D1 なので正でした（手引きの 20.2 節）。

（出典: `corpus/v3-dreamrec__comfypilot/src/comfy_mcp/tools/auto_fix_deps.py:59-82`（本書の執筆時に確かめた）、`evidence/population_v3/v2_judgments.json` の M14、`docs/drafts/final_judging_guide_draft.md:309`（15.1 節）・`:342-344`（15.2 節）・`:641`（M58））

#### 形 3 — 組み込みの `bytearray.append` の取り違え（E3）

pressure-harness の `spike_return_image` は、PNG の画像をその場で作って返すだけのツールです。
画像を作る補助の関数の一部は次のとおりです（抜粋）。

```python
162      rows = bytearray()
163      for y in range(height):
164          rows.append(0)  # PNG filter type 0 for this scanline
```

- 162 行目: `bytearray()` で、空のバイトの並び（Python の組み込みの型）を作ります。
- 163 行目: 画像の行の数だけ繰り返します。
- 164 行目: バイトの並びの最後に `0` を 1 つ足します。メモリの中の操作で、ファイルには何も書きません。

解析器は、164 行目の `rows.append` を、**末尾の名前 `append` だけ**を手がかりに、木の中のクラス `AuditLog` のメソッド `append` に結びました（[第 15 章](ch15.md)の「末尾名の解決」）。
`AuditLog.append` の先では、さらに `FileTools.write` に結ばれ、ファイルのディレクトリの作成と書き込み（`files.py:144-145`）が道筋の先に現れました。
道筋（`witness_chain`）は `_test_png → AuditLog.append → FileTools.write` で、効果の確度は `opaque`（理由 `unresolved`・`depth`）でした。
つまり解析器自身も「型で裏付けられない解決」と印を付けていました。

実際に呼ばれるのは組み込みの `bytearray.append` で、ファイルには何も書きません。
解析器の言う書き込みは起きないので → **誤**（E3: 名前だけの解決の誤り）です。

（出典: `corpus/v3-p-v1shnu__pressure-harness/spike/m0_spike.py:148-164`・`:190-193`、`evidence/scan_v2_v3_run1/v3-p-v1shnu__pressure-harness.json` の `spike_return_image` の効果（本書の執筆時に確かめた）、`evidence/population_v3/v2_judgments.json` の M37・M38）

#### 形 4 — 固定のコマンドと `shlex.quote`（E7）

34.5 節の clawking の `op_get` / `op_get_raw` です。
D1 に照らした 2 件が誤（E7: モデルが決められないのに決められるとした）でした。

#### 形 5 — `flock` のための `"a"`（E8、D4）

helios-mcp のロックの関数の一部です（抜粋）。

```python
67      Path(key).mkdir(parents=True, exist_ok=True)
68      with open(Path(key) / "helios.lock", "a") as lock:
69          fcntl.flock(lock.fileno(), fcntl.LOCK_EX)
```

- 67 行目: ロックのファイルを置くディレクトリを、無ければ作ります。
- 68 行目: `helios.lock` というファイルを、`"a"`（追記）のモードで開きます。追記のモードは、ファイルが無ければ作り、あれば中身を消さずに開きます。

#### なぜそうするのか — 形を覚えると、判定が速く正確になる

形ごとにまとめておくと、2 つの使い道があります。

1. **直すとき**: 同じ形なら、1 つの直し方でまとめて直せるかもしれません。ただし、その直し方が「一般に正しい」かを確かめる必要があります（[第 35 章](ch35.md)）。
2. **判定するとき**: 同じ形に出会ったら、「この形は誤になりやすい」と気づけます。ただし、形が同じでも宣言によって答えが変わる（形 2 は D1 なら正、D2 なら誤）ので、最後は手引きの規則で決めます。

#### よくある誤解・つまずき

- **「v3 の誤 11 件は、その後の修正で全部なくなった」**: なくなっていません。誤の 5 つの形は、どれも凍結版に残っています（[第 35 章](ch35.md)）。
- **「同じ呼び出しで作った一時ファイルの削除は、いつでも誤」**: D2 では誤（E2）ですが、D1 では正です。D1 は「環境を変えない」なので、一時ファイルの作成・削除も環境の変更に数えます。
- **「`shlex.quote` があれば、いつでも安全」**: `shlex.quote` は、値を 1 つの引数に閉じ込めるだけです。起動するコマンドそのものをモデルが決められる形（たとえば `cmd = shlex.quote(prog) + " --help"` で `prog` がモデルの引数）なら、モデルはコマンドを選べます。どの部分をモデルが決められるかを、材料ごとに見ます（[第 31 章](ch31.md) 31.7 節の考え方）。
- **「`"a"` で開いていれば追記」**: 開くモードだけでは決まりません。その後に何を書くか（書かないか）を見ます。

#### 手作業ではどう使うか

- 判定の手順 C で、効果の行が次の形なら、まず誤を疑います。
  - `pipe:write` / `pipe:communicate` → 子が受け取ったデータでファイルを変えるかを確かめる（E5 の候補）。
  - `os.unlink` / `os.remove` で、消す対象が同じ呼び出しの `mkstemp` などで作ったもの → **D2 なら** E2 の候補。D1 なら反する。
  - 道筋に組み込みの型（`list`・`dict`・`set`・`bytearray`）のメソッドと同じ名前の木の中のメソッドがある → 受け手の正体を確かめる（E3 の候補）。
  - シェルの文字列に `shlex.quote` された値だけが入る固定のコマンド → コマンドが何をするかを調べる（D1 なら E7 の候補）。
  - `open(..., "a")` の直後が `flock` だけ → D4 なら E8 の候補。
- 「疑う」は「誤にする」ではありません。疑ったら、手順 D〜F で 2 つの問いに答えてから決めます。

#### この節のまとめ

誤 11 件は 4 つの形（標準入力 4・同じ呼び出しの一時ファイルの削除 3・組み込みの `bytearray.append` の取り違え 2・`shlex.quote` の固定コマンド 2）に集中し、D4 の誤 1 件（`flock` の `"a"`）と合わせた 5 つの形は、最終評価の E5・E2・E3・E7・E8 の例になった。
どの形も凍結版に残っている。形 2 のように、同じコードでも宣言によって正と誤が分かれるので、最後は手引きの規則で決める。

### 34.8 見落とし 7 件と、構造的な所見 — 概要（詳しくは第 41 章）

#### 一言で言うと

V3 の見落とし 7 件の原因は、呼び出しの解決 3 件、深さの上限 2 件、受け手の型 1 件、sink の語彙に無いライブラリ 1 件でした。
そして、「呼び出しを解決できなかったツールは、宣言に対して何の印も残さず『矛盾なし』に見える」という構造的な所見が得られました。
ただし、未解決のものを一律に「不」にすることはできない、ということも数字で分かりました。

#### たとえ話 — 地図に載っていない道

カーナビが「この先に危険な場所はありません」と言ったとします。
けれども、カーナビの地図に載っていない道を通る場合、カーナビはその先を知りません。
知らないのに「ありません」と言うのは、黙って安全側に倒しています。
一方で、「地図に載っていない道が 1 本でもあれば、すべて『分からない』と表示する」ことにすると、ほとんどの道が「分からない」になり、役に立ちません。

#### 小さな例 — 見落とし 7 件の原因

| 原因 | 件 | 内容（概要） |
|---|---|---|
| 呼び出しの解決 | 3 | 関数が返すモジュール 1（synapse-s2）、パッケージの `__init__.py` の再公開 2（inkscape） |
| 深さの上限 | 2 | 深さ 7（トークンの更新での書き込み。期限切れのときだけ）、深さ 5〜6（再接続のときの DB の作成） |
| 受け手の型 | 1 | 補助の関数の戻り値の注釈 `-> httpx.AsyncClient` を使えず、`POST` を見落とした（rovo） |
| sink の語彙に無いライブラリ | 1 | zvec の `upsert`（モデルが選ぶ ID で上書き） |

表の読み方: 1 行が 1 つの原因です。
たとえば 3 行目は「1 件は、補助の関数が返す値の型の注釈（httpx のクライアント）を解析器が使えなかったので、その先の `POST` を見落とした」と読みます。

`docs/population_v3.md` は、さらに「見つかっていれば矛になったのは 5（うち 1 は深さ 7 の条件つき）、不が 1、弱いものが 1」と書いています。
不明 2 件は、`lifespan` の受け手を通す形（overleaf）と、木に無い外部のライブラリの中の動作（abraflexi）でした。

（出典: `docs/population_v3.md:90-93`、`evidence/population_v3/v3_miss_judgments.json` の `cause`・`note`）

#### 構造的な所見

`docs/population_v3.md` は、見落としの判定から、次の所見を書いています（要約）。

1. 呼び出しを解決できなかったツールは、宣言に対して何の印も残さず「矛盾なし」に見える。これは `CLAUDE.md` の規則 4 の「黙って安全側に倒す」形である。
2. ただし一律に不明にはできない。D1・D2 を明示したユニットのうち、何らかの未解決を持つものは、v2 の run18 で 1,026 / 1,036、v3 で 846 / 859 ある。
3. 同じように、確度 `opaque(unresolved)` の効果だけに支えられた矛は、run18 で 114 / 190、v3 で 64 / 89 あるが、v3 の判定での誤はそのうち 2 だけ。一律に不へ落とすと、正しい矛の大半を捨てる。

2 の数字は、「D1・D2 を明示したユニットのほとんど（v3 では 859 のうち 846）が、どこかに未解決の呼び出しを持つ」という意味です。
もし「未解決が 1 つでもあれば不」にすると、ほとんどすべてが不になり、解析器は何も言わなくなります。
3 の 89 は、宣言ごとに数えた v3 の矛（D1 75・D2 11・D3 2・D4 1）の合計です。
そのうち 64 は未解決の解決に支えられていますが、判定で誤だったのは 2 件（形 3 の `bytearray.append`）だけでした。

この所見から、D61 の G5「解決できなかった木の中の呼び出しを、ツールごとの列として出す（判定は変えない）」が生まれました（[第 35 章](ch35.md)）。
判定は変えずに、読み手が「矛盾なし」の確からしさを自分で判断できる材料を出す、という折り合いです。

（出典: `docs/population_v3.md:95-98`、`evidence/population_v3/contradiction_by_decl_v3_run1.md`（宣言ごとの矛の件数））

#### よくある誤解・つまずき

- **「見落とし 7/30 だから、見落としの率は 23%」**: 30 件の抜き取りで、しかも開発用のデータです。30 件では区間が広く、「見落としは多くても何割か」までしか言えません。最終評価で見落としの抜き取りを 200 件にしたのは、このためです（D69。[第 46 章](ch46.md)）。
- **「未解決があるなら不にすれば安全」**: v3 の数字のとおり、ほとんどすべてが不になり、正しい矛の大半を捨てます。安全でも、役に立たない解析器になります。

#### 手作業ではどう使うか

- 見落としの判定（手引きの 18 節）では、見落としを見つけたら原因を 5 つ（深さ・呼び出しの解決・受け手の型・語彙・その他）のどれかに分類します。v3 の 4 つの原因は、そのうち 4 つにあたります（第 41・52 章）。
- 判定のときに manifest の `unresolved_in_tree_calls`（G5 の列）を見ると、解析器がどこで道を見失ったかが分かります。違反に届く道がその行を通っていれば、見落としの原因は「呼び出しの解決」です（[第 15 章](ch15.md) 15.6 節）。

#### この節のまとめ

見落とし 7 件の原因は、呼び出しの解決 3・深さ 2・受け手の型 1・語彙 1。不明は 2。
未解決のツールは黙って「矛盾なし」に見えるが、一律に不にすると正しい矛の大半を捨てる（v3 で 846/859 が未解決を持ち、未解決に支えられた矛 64/89 のうち誤は 2）。この折り合いが D61 の G5 になった。

### この章のまとめ

- v3 は、D60 で開発用の確認と位置づけた、v2 と重ならない新しいデータ。凍結したばかりの `analyzer-freeze-1` を当て、見つけた欠陥は直してよかった。規則 → 抽出と pin → 取得 → 走査と判定の対象 → 判定の順に、1 つずつコミットしてから進んだ。
- 枠 3,764 から v2 の 100 を除いた 3,664 から seed 20260924 で 100 件を選び、pin し、取得後の条件で 9 件を除いて 91 木（3,065 ユニット）。記録にあるのは「v2 との名前の重なり 0」だけで、ファイルの中身の重なりは未検証。
- コミットの SHA（40 桁）は repo の版の名前で pin に使い、ファイルの sha256（64 桁）は中身の指紋で、凍結の確認と中身の重複の除去に使う。
- 確かめたのは V1 頑健性・V2 矛の精度（単位は組）・V3 見落とし（単位は（ユニット, 宣言））。V4（不の件数と理由）は v3 の規則にすでにあり、V5 は v4 の規則、V6 は手順書で加わった。原典ごとに呼び名が揃っていない。
- 判定の基準の「解析器が読み違えた → 誤」は、読み違いのせいで 2 つの問いの答えが変わるときだけ誤、と読む。site の名前だけ違って kind が合っていれば判定に影響せず、受け手の型の読み違いで kind まで違うときだけ E4。
- 結果は、V1 が 91/91 完走、V2 が D1・D2 の抜き取り 60 件で正 49（81.7%）・誤 11・不明 0（D3・D4 は 3 件で正 2・誤 1）、V3 が 30 件中 見落とし 7・不明 2。正のうち lore・synapse-s2 の 16 件は条件つき。
- 判定したのは本記録者（AI）で、人が見直したという記録は無い（v4 は手順書が「人は見直していない」と明記）。v3・v4 の判定は考え方の例で、正解ではない。v3 の数字は論文に使わない。
- 誤 11 件は 4 つの形に集中し、D4 の誤 1 件と合わせた 5 つの形が、最終評価の誤の原因 E5・E2・E3・E7・E8 の例になった。どの形も凍結版に残っている。
- 見落とし 7 件の原因は、呼び出しの解決 3・深さ 2・受け手の型 1・語彙 1。未解決は黙って「矛盾なし」に見えるが、一律に不にはできない。この折り合いが D61 の G5 になった（[第 35 章](ch35.md)）。
