## 第 4 章 道具の「自己申告」— 宣言と、その使われ方

> **この章で分かること**: MCP のツールが自分の性質を申告する欄（ToolAnnotations）と、この研究が扱う 4 つの申告（D1〜D4）の意味。コードの上での書き方と、何も書かないときの扱い（既定値）。実際の AI のアプリ（クライアント）が申告をどう使っているか（確かさの印つき）。MCP の仕様自身が申告を「信じるな」と書いていること。仕様が何も言っていないこと（裏方の書き込み）。そして `destructiveHint: false`（D2）の判定で迷いやすいところの予告。

### 4.1 ツールの注記 — 自己申告の欄

#### 一言で言うと

MCP のツールには、名前や説明と並んで、**自分の性質を自分で申告する欄**があります。
これを **ToolAnnotations**（ツールの注記）と呼びます。
この研究では、これを短く**宣言**と呼びます。

#### たとえ話 — 宅配便の荷札

宅配便の荷物には、送り主が自分で貼る札があります。「ワレモノ」「天地無用」「なまもの」といった札です。

配達する人は、箱を開けて中身を確かめたりしません。
札を見て、「ワレモノなら静かに置こう」「なまものなら早く届けよう」と扱いを決めます。

札を貼るのは送り主です。
運送会社は、札が中身と合っているかを調べません。
中にガラスのコップが入っているのに「ワレモノ」の札を貼り忘れても、逆に本しか入っていないのに「ワレモノ」と貼っても、荷物はそのまま運ばれます。

ツールの注記は、この荷札に似ています。
ツールの作者が自分で書き、受け取る側（クライアント）は中身（コード）を開けずに、それを見て扱いを決めます。

#### 小さな例 — `tools/list` の返事の中の注記

[第 3 章](ch03.md)で見たとおり、クライアントは `tools/list` という要求で、サーバからツールの一覧を受け取ります。
一覧の中の 1 つのツールは、たとえば次のような形をしています（説明用の例です）。

```json
{
  "name": "list_courses",
  "description": "登録中の授業の一覧を返す。",
  "inputSchema": {"type": "object", "properties": {}},
  "annotations": {"readOnlyHint": true}
}
```

#### 一歩ずつ

- 1 行目と 6 行目の `{` と `}` は、1 つのツールの情報のまとまりの始まりと終わりです。この書き方を JSON と呼びます（`"名前": 値` の組を並べる、データの書き方です）。
- 2 行目の `"name"` は、ツールの名前です。LLM はこの名前でツールを呼びます。
- 3 行目の `"description"` は、ツールの説明です。LLM が「このツールを使うか」を考える材料になります。
- 4 行目の `"inputSchema"` は、引数の形です。この例は引数を 1 つも取りません（`"properties": {}` が空）。
- 5 行目の `"annotations"` が**注記**です。この例では「`readOnlyHint` は `true`」、つまり「このツールは読むだけです」と申告しています。

この 5 行目だけが、ツールの**性質**についての申告です。
2〜4 行目は、ツールの名前と使い方の説明です。

#### 言葉の整理 — ToolAnnotations と宣言

- **やさしい言い換え**: ツールが自分について書く「私はこういう性質です」という札。
- **正確な定義**: MCP の決まりで、ツールの情報に付けることができる注記の欄。MCP Python SDK 1.30.0 では `ToolAnnotations` という型で、`title`・`readOnlyHint`・`destructiveHint`・`idempotentHint`・`openWorldHint` の 5 つの項目を持つ。ツールの情報（`Tool`）の中の `annotations` という欄に入る。この欄は省略してよい。
- **例**: 上の JSON の 5 行目 `"annotations": {"readOnlyHint": true}`。
- **この研究での呼び方**: ToolAnnotations を短く**宣言**と呼ぶ。研究の説明では「宣言 D」と書くこともある（[第 6 章](ch06.md)）。

（出典: MCP Python SDK 1.30.0 の `mcp/types.py:1247-1293`（`ToolAnnotations`）、`:1315-1330`（`Tool`。`annotations` の欄は `:1329` で `ToolAnnotations | None = None`、つまり書かなくてよい）。repo の外のファイルで、この教科書を書くときに開いて確かめた。）

#### 5 つの項目の役割

5 つの項目を、役割で分けます。

| 項目 | 役割 | この研究で扱うか |
|---|---|---|
| `title` | 人に見せる表示名 | 扱わない（性質の申告ではない） |
| `readOnlyHint` | 環境を変えないか | 扱う |
| `destructiveHint` | 壊す更新をするか | 扱う |
| `idempotentHint` | 繰り返しても追加の効果が無いか | 扱う |
| `openWorldHint` | 外の世界と関わるか | 扱う |

表の読み方: 1 行目は「`title` は、画面に出す名前を書く欄で、ツールが何をするかの約束ではない。だからこの研究では扱わない」と読みます。
残りの 4 行は、どれもツールの**振る舞い**についての申告です。
この研究が照合するのは、この 4 つです。

名前の最後に付いている `Hint` は「ヒント」、つまり「目安」という意味です。
「強制する決まり」ではなく「参考にしてください」という書き方です。
この名前の意味は、4.6 節でもう一度大事になります。

#### なぜこの欄が大事なのか

ツールを使う側から見ると、ツールについて分かることは `tools/list` で届く情報だけです（[第 2 章](ch02.md)）。
コードは届きません。
だから、「このツールは安全か」を決めたいとき、使う側が頼れるのは、この注記の欄くらいしかありません。

この研究は、まさにこの「使う側が頼るしかない欄」が、コードの実際の動きと合っているかを調べます。

#### よくある誤解・つまずき

- **誤解: 「説明文（`description`）に『読むだけ』と書けば、それが宣言になる」**
  なりません。この研究が照合するのは注記の欄（`annotations`）の値だけです。説明文は人や LLM が読む文章で、決まった形の申告ではありません。
- **誤解: 「`title` も宣言の 1 つ」**
  `title` は表示名です。「Logout」と書いてあっても、それはツールが何をするかの約束ではありません。
- **誤解: 「どのツールにも注記がある」**
  注記の欄は省略してよい欄です。何も書かないツールもたくさんあります。何も書かないとどう扱われるかは、4.4 節で見ます。

#### 手作業ではどう使うか

判定では、まず判定表の 1 行を読み、`decl` 欄で「どの宣言に照らすか」を確かめます（手順 A）。
次に、ツールの定義の位置（`unit_relpath` と `unit_lineno`）を開くと、多くの場合、関数のすぐ上のデコレータの中に注記が書いてあります（書き方は 4.3 節）。
`decl` 欄の記号と、原ソースの注記を見比べておくと、その後に何を問えばよいか（4.2 節）がはっきりします。
（出典: `docs/drafts/final_judging_guide_draft.md:92-103`）

#### この節のまとめ

MCP のツールは、注記（ToolAnnotations）の欄で自分の性質を申告できる。この研究ではこれを宣言と呼ぶ。
5 つの項目のうち、振る舞いを申告する 4 つ（readOnly・destructive・idempotent・openWorld）を扱い、表示名の `title` は扱わない。

### 4.2 4 つの宣言と、D1〜D4 という記号

#### 一言で言うと

4 つの宣言は、それぞれ「はい（`true`）/ いいえ（`false`）」で答える形の申告です。
この研究は、そのうち「**〜しない**」という控えめな約束をしている側の値に、D1〜D4 という記号を付けて扱います。

#### たとえ話 — 部屋を借りるときの約束

友だちの部屋を、少しの間だけ使わせてもらう場面を考えてください。あなたは、次のような約束をするかもしれません。

- 「**見るだけ**。何も動かさないし、何も置いていかない」
- 「物を**足すだけ**。前からある物は捨てないし、動かさない」
- 「**外の人は呼ばない**。部屋の中だけで済ませる」
- 「**何度来ても同じ**。2 回目に来ても、1 回目の後と何も変わらない」

どれも「〜しない」「〜だけ」という、控えめな約束です。
控えめな約束は、「しないと言ったことを、した」ときに破れます。
4 つの宣言は、この 4 つの約束にあたります。

「何度来ても同じ」は、少し分かりにくいかもしれません。
エレベーターの呼び出しボタンを思い浮かべてください。何度押しても、エレベーターは 1 回呼ばれるだけです。2 回目に押しても、状態は変わりません。
自動販売機のボタンは違います。押すたびに、飲み物が 1 本ずつ出てきます。
エレベーターのボタンのような性質を、**冪等**（べきとう）と呼びます。

#### 小さな例 — SDK の説明文

4 つの宣言の意味は、SDK の説明文（docstring。関数や型の中に書く説明の文章）に英語で書かれています。原文と、その日本語を並べます。

| 宣言 | SDK の説明文（原文） | 意味（日本語で） | 「はい」になりそうな例 |
|---|---|---|---|
| `readOnlyHint: true` | "If true, the tool does not modify its environment." | 「私は環境を変えません。読むだけです」 | 検索、一覧表示、状態の確認 |
| `destructiveHint: false` | "If true, the tool may perform destructive updates to its environment. If false, the tool performs only additive updates." | 「変えるとしても、追加するだけで、今あるものは壊しません」 | メモの追加、ログの追記 |
| `idempotentHint: true` | "If true, calling the tool repeatedly with the same arguments will have no additional effect on the its environment." | 「同じ引数で何度呼んでも、2 回目以降は何も変わりません」 | 設定を同じ値に上書き |
| `openWorldHint: false` | "If true, this tool may interact with an "open world" of external entities. If false, the tool's domain of interaction is closed." | 「外の世界（インターネットの向こうの相手など）とはやり取りしません。関わる範囲は閉じています」 | 手元の計算だけ、手元のメモ帳 |

（`idempotentHint` の原文の "the its" は、原文の表記のまま写しています。）
（出典: MCP Python SDK 1.30.0 の `mcp/types.py:1262-1291`）

#### 一歩ずつ — 1 行ずつ読む

表の 4 行を、1 つずつ読みます。

1. **`readOnlyHint`**: `true` なら「環境を変えない」。`false` なら「変えうる」（約束していない）。
2. **`destructiveHint`**: 原文は `true` の側から書いてあります。`true` なら「壊す更新をしうる」、`false` なら「追加の更新だけをする」。約束しているのは `false` の側です。
3. **`idempotentHint`**: `true` なら「同じ引数で繰り返し呼んでも、追加の効果が無い」。エレベーターのボタンの側です。
4. **`openWorldHint`**: これも原文は `true` の側から書いてあります。`true` なら「外の世界と関わりうる」、`false` なら「関わる範囲は閉じている」。約束しているのは `false` の側です。SDK の説明文には、例として「ウェブ検索のツールの世界は開いているが、メモリ（記憶）のツールの世界は閉じている」とあります（出典: `mcp/types.py:1288-1289`）。

ここで出てくる「**環境**」とは、ツールの外にあって、呼び出しが終わった後も残るもののことです。
ファイル、データベース、外部のサービスの状態などが入ります。
ただし後の 4.7 節で見るとおり、**MCP の仕様自身は「環境」を定義していません**。
この研究は、環境の範囲を原理として先に決めています（[第 17 章](ch17.md)）。

#### D1〜D4 という記号

この研究では、4 つの宣言のうち「約束をしている側」の値に、記号を付けて呼びます。

| 記号 | 宣言 | 約束の中身 |
|---|---|---|
| **D1** | `readOnlyHint: true` | 環境を変えない |
| **D2** | `destructiveHint: false`（`readOnlyHint: true` が無いときだけ） | 前からあるものを壊さない（足すだけ） |
| **D3** | `openWorldHint: false` | 外の世界と関わらない |
| **D4** | `idempotentHint: true`（`readOnlyHint: true` が無いときだけ） | 同じ引数で繰り返しても追加の効果が無い |

表の読み方: 2 行目は「`destructiveHint: false` と書いてあり、しかも `readOnlyHint: true` が書かれていないツールは、D2 の約束をしている」と読みます。

D2 と D4 に「`readOnlyHint: true` が無いときだけ」と付くのは、SDK の説明文がこの 2 つについて "(This property is meaningful only when `readOnlyHint == false`)"（この項目は `readOnlyHint` が false のときだけ意味を持つ）と書いているからです（出典: `mcp/types.py:1272, 1280`）。
読むだけのツールに「壊すか」「繰り返すと増えるか」を問う意味は無い、ということです。

「`readOnlyHint: true` が無い」には、2 つの場合が入ります。
`readOnlyHint: false` と書いた場合と、`readOnlyHint` を何も書かなかった場合です。
どちらでも D2・D4 を当てる点は同じです（何も書かなかったときの扱いは 4.4 節）。
判定の手引きも「`readOnlyHint: true` が無いとき」という書き方をしています。

#### 実物で確かめる

ここで、この研究が実際に調べた MCP サーバのコードから、2 つの宣言を見ます（どちらも v4 の中間検証の木。[第 37 章](ch37.md)）。

1 つ目は、タスク管理のサーバ（task-manager-cloud）の `logout` というツールの宣言です。

```python
@mcp.tool(
    name="logout",
    annotations={
        "title": "Logout",
        "readOnlyHint": False,
        "destructiveHint": False,
        "openWorldHint": True,
    },
)
```

- 1 行目の `@mcp.tool(` から 9 行目の `)` までが、「この下の関数をツールとして登録する」という印（デコレータ。[第 3 章](ch03.md)）です。
- 2 行目は、ツールの名前を `logout` にしています。
- 3 行目から 8 行目の `annotations={...}` が注記（宣言）です。
- 4 行目の `title` は表示名で、宣言としては扱いません。
- 5 行目は `readOnlyHint` が `False`（Python では真偽を `True` / `False` と大文字で書きます）。「読むだけ」とは言っていません。
- 6 行目は `destructiveHint` が `False`。「壊さない」と約束しています。5 行目で `readOnlyHint: true` が無いので、これは **D2** です。
- 7 行目は `openWorldHint` が `True`。「外の世界と関わりうる」なので、D3 の約束ではありません。
- `idempotentHint` は書かれていないので、D4 の約束もありません。

つまり、このツールの宣言は **D2 だけ**です。
（出典: `corpus/v4-criscode2022__task-manager-cloud/mcp-server/server.py:384-392`）

2 つ目は、AWS の料金を調べるサーバ（mcp-aws）の `generate_cost_report_wrapper` というツールの宣言です。

```python
    annotations=ToolAnnotations(readOnlyHint=True),
```

- これは `@mcp.tool(` の中の 1 行で、`readOnlyHint` を `True` にしています。
- ほかの 3 つは書かれていません。

つまり、このツールの宣言は **D1 だけ**です。
（出典: `corpus/v4-ryxmarcus__mcp-aws/src/aws-pricing-mcp-server/awslabs/aws_pricing_mcp_server/server.py:701`）

この 2 つのツールは、[第 5 章](ch05.md)でもう一度出てきます。
どちらも、v4 で本記録者が「宣言とコードの動きが食い違っている」と判定したツールです（v4 の判定は論文には使わない。[第 5 章](ch05.md)・[第 37 章](ch37.md)）。

#### なぜ「約束をしている側」だけに記号を付けるのか

[第 1 章](ch01.md)で見たとおり、この研究が探すのは「**言っているより多くやっている**」向きのずれです。
控えめな約束（「〜しない」）が破れるのは、「しないと言ったことを、した」ときだけです。

反対側の値（`readOnlyHint: false`、`destructiveHint: true` など）は、「〜しうる」と言っているだけで、何も約束していません。
「変えうる」と言ったツールが実際に何かを変えても、約束は破れていません。
だから、照らす相手は約束をしている側の値だけでよいのです。

もう 1 つ、この研究は D1〜D4 の 4 つを**別々の主張**として、宣言ごとに報告し、足し合わせません（決定 D62。[第 16 章](ch16.md)）。
4 つは意味が違うので、足した数は何を数えたのか説明できないからです。

#### よくある誤解・つまずき

- **誤解: 「`destructiveHint: false` は『何も書かない』という意味」**
  違います。「壊さない」だけで、新しいものを足すのは約束の範囲内です。メモを新しく 1 つ追加するのは、D2 に反しません。
- **誤解: 「`openWorldHint: false` なら、手元のファイルも変えない」**
  違います。D3 が問うのは「外の相手と関わるか」だけです。手元のファイルを書き換えても、D3 には反しません（それは D1 の問いです）。判定の手引きの D3 の表でも、「ファイル・DB のローカルの操作」は「反しない」です（出典: `docs/drafts/final_judging_guide_draft.md:359`）。
- **誤解: 「冪等 = 何も変えない」**
  違います。「設定を『オン』にする」ツールは 1 回目に設定を変えますが、2 回目は何も変えません。これは冪等です。冪等は「繰り返したときに**追加の**効果が無い」という性質です。
- **誤解: 「`readOnlyHint: false` と書いたツールは、何かを約束している」**
  約束していません。「変えうる」と言っているだけです。D1〜D4 のどれにも当たりません。
- **つまずき: 「`readOnlyHint: true` と `destructiveHint: false` の両方を書いたら D1 と D2 の両方」**
  D1 だけです。`readOnlyHint: true` があるので、`destructiveHint` は意味を持ちません。

#### 手作業ではどう使うか

判定では、`decl` 欄の記号によって、自分に問う**問いそのもの**が変わります。
判定の手引き（下書き・未承認）は、宣言ごとの問いを次のように書いています。

| `decl` | 判定で問うこと |
|---|---|
| D1 | その動作は、呼び出しの後に残る何かを変えるか |
| D2 | その動作は、呼び出しの前からあったものを消す・上書きする・変えるか |
| D3 | そのツールは、外部の相手と通信するか、あるいはモデルが決める相手と通信しうるか |
| D4 | 同じ引数で 2 回呼んだとき、2 回目が 1 回目の後の状態をさらに変えるか |

表の読み方: 1 行目は「`decl` が D1 の組では、『その動作で、呼び出しの後に何かが変わったまま残るか』を問う」と読みます。

同じ動作でも、`decl` が違えば答えが違うことがあります。
たとえば、新しいファイルを 1 つ作る動作は、D1 には反します（残るものが変わる）が、D2 には反しません（前からあったものは壊していない）。
判定のたびに、まず `decl` を見て、問いを選んでください。詳しい規則は[第 50 章](ch50.md)で見ます。
（出典: `docs/drafts/final_judging_guide_draft.md:305, 329, 350, 363`（15.1〜15.4 の問い）、`:333`（新しく作るだけなら D2 に反しない））

#### この節のまとめ

4 つの宣言は「はい / いいえ」の申告で、約束をしている側の値を D1〜D4 と呼ぶ。D2・D4 は `readOnlyHint: true` が無いときだけ当たる。
判定では `decl` の記号ごとに問いが変わる。同じ動作でも、宣言が違えば答えが違うことがある。

### 4.3 書き方 — コードの上で宣言を見つける

#### 一言で言うと

宣言の書き方は 1 つではありません。
専用の型で書く形、辞書で書く形、低レベルの一覧の中に書く形があります。
判定では、どの形で書かれていても、原ソースの上で宣言を見つけられるようにしておきます。

#### たとえ話 — 同じ住所の、いろいろな書き方

同じ家の住所でも、「東京都千代田区…」と漢字で書くこともあれば、郵便番号だけを大きく書くこともあり、ローマ字で書くこともあります。
郵便局の人は、どの書き方でも同じ家だと分かります。
宣言も同じで、書き方が違っても意味は同じです。

#### 小さな例 — 3 つの書き方

```python
# 説明用
from mcp.types import ToolAnnotations

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))   # 書き方 1: 専用の型で書く
def list_courses() -> str:
    """登録中の授業の一覧を返す。"""
    ...

@mcp.tool(annotations={"readOnlyHint": True})               # 書き方 2: 辞書で書く
def list_rooms() -> str:
    """教室の一覧を返す。"""
    ...

Tool(name="list", annotations=ToolAnnotations(readOnlyHint=True))   # 書き方 3: 低レベルの書き方
```

#### 一歩ずつ

- 1 行目の `# 説明用` は、説明のために作った例であることを示すメモです。
- 2 行目は、SDK から `ToolAnnotations` という型を使えるようにしています。
- 4 行目の `@mcp.tool(...)` は、すぐ下の関数をツールとして登録する印（デコレータ。[第 3 章](ch03.md)）です。その中の `annotations=ToolAnnotations(readOnlyHint=True)` が宣言です。専用の型 `ToolAnnotations` に、`readOnlyHint=True` を渡して作っています。
- 5〜7 行目は、ツールの関数そのものです。関数の名前・説明文・引数が、ツールの名前・説明・引数の形になります（[第 3 章](ch03.md)）。`...` は中身を省いたという印です。
- 9 行目は、同じ宣言を**辞書**で書いています。辞書は `{名前: 値}` の組を並べたものです。中身は書き方 1 と同じ「`readOnlyHint` は `True`」です。
- 14 行目は、低レベルの書き方（[第 3 章](ch03.md)）で、ツールの一覧を返す関数の中に `Tool(...)` を並べる形です。ここでも `annotations=` の後ろが宣言です。

3 つとも、言っていることは同じ「このツールは読むだけです」です。

4.2 節で見た実物も、この形のどれかです。
task-manager-cloud の `logout` は書き方 2（辞書）、mcp-aws の `generate_cost_report_wrapper` は書き方 1（専用の型）でした。

#### ほかにも知っておくとよい形

- 辞書で書く形は、`fastmcp` の 2 系などが受け付けます（出典: `docs/population_v2.md:18-19` の定義 1 の形 B）。
- `read_only_hint=True` のように、単語を `_` でつなぐ書き方（snake_case）もあります。これは SDK の版によって扱いが違い、宣言として届く版と届かない版があります。解析器がこれをどう読むかは[第 16 章](ch16.md)で見ます。
- 注記を変数に入れておいて、`annotations=spec.annotations` のように渡す形もあります。この形は、この研究の母集団（[第 25 章](ch25.md)）を列挙するときの検索では拾えないので、母集団の定義の外になっています（出典: `docs/population_v2.md:16-22`）。

#### なぜ書き方を知る必要があるのか

解析器は、いろいろな書き方の宣言を読んで、作者が**はっきり書いた**宣言を取り出します（[第 16 章](ch16.md)）。
判定をする人も、解析器が取り出した宣言が原ソースのどこに書いてあるかを、自分の目で見つけられる必要があります。
書き方を 1 つしか知らないと、辞書の形や低レベルの形を見落として「宣言がどこにも無い」と思い込んでしまいます。

#### よくある誤解・つまずき

- **誤解: 「デコレータの中に `annotations=` が無ければ、宣言は無い」**
  低レベルの書き方では、宣言はデコレータの中ではなく、ツールの一覧を作る関数の中にあります。1 か所だけ見て決めないでください。
- **誤解: 「辞書の形と専用の型の形は、意味が違う」**
  意味は同じです。違うのは書き方だけです。
- **つまずき: Python の `True` と JSON の `true`**
  Python のコードでは `True`（大文字の T）、`tools/list` の返事の JSON では `true`（小文字）です。同じ「はい」です。

#### 手作業ではどう使うか

原ソースで宣言を探すときは、ツールの定義の行（`unit_relpath:unit_lineno`）を開き、そのすぐ上を見ます。
見つからなければ、同じファイルの中で `annotations` という語を検索します（エディタの検索や `grep -n "annotations" <ファイル>`）。
低レベルの書き方なら、`list_tools` のような名前の関数の中に `Tool(...)` が並んでいるはずです（[第 3 章](ch03.md)）。

宣言を見つけたら、`decl` 欄の記号と合っているかを見ます。
たとえば `decl` が D2 なのに、宣言に `readOnlyHint: True` が書いてあったら、何かがおかしいはずです（`readOnlyHint: true` があれば D2 は当たらないので）。
そう感じたら、その場で自分で決めず、気づいたことを記録に書いてください（判定の手引きの「手引きで決まらない事例」の扱い。[第 52 章](ch52.md)）。

#### この節のまとめ

宣言には、専用の型・辞書・低レベルの一覧の中、という書き方がある。意味は同じ。
判定では、ツールの定義の近くと、同じファイルの `annotations` を探して、原ソースの上で宣言を見つける。

### 4.4 既定値 — 何も書かないとどう扱われるか

#### 一言で言うと

宣言の項目を書かなかったとき、その項目は「**いちばん約束しない側**」の値として扱われます。
だから、何も書かないツールは、何も約束していません。
AuthGap は、この既定値を補わず、作者がはっきり書いた宣言だけを数えます。

#### たとえ話 — 申込書の空欄

アパートの申込書に、「ペットを飼いますか。飼わない場合は『飼わない』に丸をつけてください」という欄があったとします。
あなたがこの欄を空欄のまま出したら、大家さんはどう受け取るでしょうか。
「飼わないと約束した」とは受け取りません。
「飼うかもしれない人」として、慎重に扱うはずです。

空欄は「約束しなかった」という意味です。
「安全だと言った」という意味ではありません。
宣言の既定値も、これと同じ考え方でできています。

#### 小さな例 — SDK の説明文の「Default」

SDK の `ToolAnnotations` の説明文は、項目ごとに「Default」（既定値）を書いています。
該当する行を抜き出します。

```python
    readOnlyHint: bool | None = None
    """
    If true, the tool does not modify its environment.
    Default: false
    """

    destructiveHint: bool | None = None
    """
    If true, the tool may perform destructive updates to its environment.
    If false, the tool performs only additive updates.
    (This property is meaningful only when `readOnlyHint == false`)
    Default: true
    """
```

（出典: MCP Python SDK 1.30.0 の `mcp/types.py:1262-1274`。この教科書を書くときに開いて確かめた。repo の外のファイルなので、版を変えると行や文言が変わりうる。）

#### 一歩ずつ

- 1 行目の `readOnlyHint: bool | None = None` は、「`readOnlyHint` は真偽（`bool`）か、何も無い（`None`）かのどちらか。書かなければ `None`」という意味です。
- 2〜5 行目は、その項目の説明文です。3 行目が意味（環境を変えない）、4 行目が既定値（`false`）です。
- 7 行目の `destructiveHint` も、書かなければ `None` です。
- 9 行目と 10 行目が意味、11 行目が「`readOnlyHint` が false のときだけ意味を持つ」という注意、12 行目が既定値（`true`）です。

ここで 1 つ注意があります。
コードの上では、書かなかった項目は `None`（何も無い）のままです。SDK が勝手に `false` や `true` を入れるわけではありません。
説明文の「Default」は、「**書いていないとき、クライアントはこう受け取るべきだ**」という意味です。

4 つの項目の既定値を、表にまとめます。第 3 版には無かった表です。

| 宣言 | 既定値（書かなかったとき） | 既定値の意味 | 注意 |
|---|---|---|---|
| `readOnlyHint` | **false** | 環境を変えうる | |
| `destructiveHint` | **true** | 壊す更新をしうる | `readOnlyHint` が false のときだけ意味を持つ |
| `idempotentHint` | **false** | 繰り返すと追加の効果がありうる | `readOnlyHint` が false のときだけ意味を持つ |
| `openWorldHint` | **true** | 外の世界と関わりうる | |

（出典: SDK 1.30.0 の `mcp/types.py:1262-1291` の docstring で確かめた。`readOnlyHint` の既定値が false であることは、MCP の schema（仕様を機械が読める形で書いたもの）でも確かめられている [確認: draft]（`docs/incidental_writes_practice.md:44`）。仕様書も同じ既定値を書き、「`destructiveHint` と `idempotentHint` は `readOnlyHint==false` のときしか意味を持たない」としている（`AUTHGAP_BRIEF_v3.md:316`）。）

表の読み方: 2 行目は「`destructiveHint` を書かなかったら、『壊す更新をしうる』ツールとして扱う。ただしそれが意味を持つのは、`readOnlyHint` が false（書いていない場合を含む）のとき」と読みます。

#### 4 つをつなげて読む

表の「既定値の意味」の列を、上から続けて読んでみます。

> 環境を変えうる。壊す更新をしうる。繰り返すと追加の効果がありうる。外の世界と関わりうる。

これが、**何も宣言を書かないツール**の扱いです。
どの項目も、最も用心すべき側に置かれています。
つまり、**宣言の無いツールは、何も約束していません**。

ここで、4.2 節の D1〜D4 の表と見比べてください。
D1〜D4 は、どれも既定値の**反対側**の値です。

| 項目 | 既定値 | D1〜D4 の値 |
|---|---|---|
| `readOnlyHint` | false | D1 は true |
| `destructiveHint` | true | D2 は false |
| `idempotentHint` | false | D4 は true |
| `openWorldHint` | true | D3 は false |

表の読み方: 1 行目は「`readOnlyHint` の既定値は false だが、D1 は true。既定値のままでは D1 にならない」と読みます。

つまり、**既定値を補っても、D1〜D4 は 1 つも生まれません**。
D1〜D4 は、作者がわざわざ既定値の反対側を書いたときにだけ現れる約束です。

#### なぜこの表が大事なのか — 2 つの取り決め

この表から、この研究の 2 つの取り決めが出てきます。

**取り決め 1: 解析器は既定値を補わない。**
解析器は、作者がはっきり書いた宣言だけを「明示された宣言」として取り出し、何も書いていなければ「宣言は無い」とみなします。
仕様書の言い方では、「既定値による補完を禁止し、当該フィールドが明示的に存在する場合のみ D_kind とする。annotation の不在は『非破壊の宣言』ではない」です。
解析器のコードの中にも、宣言を表す型の説明に「既定値による補完を禁止する」と書いてあります。
（出典: `AUTHGAP_BRIEF_v3.md:316`、`authgap/dparse.py:55-60`、第 3 版 917-918 行。解析器の欄の詳しい意味は[第 16 章](ch16.md)。）

既定値を補っても D1〜D4 が生まれないなら、「補わない」と決める意味はどこにあるのでしょうか。
意味は、**「書いていない」を「安全だと言った」と読み違えない**ことにあります。
「`destructiveHint` を書いていないのだから、壊さないツールなのだろう」と読むのは、申込書の空欄を「ペットは飼わない」と読むのと同じ誤りです。
仕様書の「annotation の不在は『非破壊の宣言』ではない」は、まさにこの読み違えを禁じています。

**取り決め 2: 最終評価の分母 (c) も、明示した宣言だけを数える。**
論文の結論になる数は、「宣言を書いたサーバのうち、少なくとも何割に違反があったか」です（[第 6 章](ch06.md)・[第 39 章](ch39.md)）。
この割合の分母 (c) は、「その宣言を明示的に書いた（`D_kind.explicit`）ユニットを 1 つ以上持つ木」で、「既定値で補ったものは数えない」と決まっています（決定 D70 の 4）。
ここで**ユニット**は 1 つのツール、**木**は 1 つのサーバ（1 つのリポジトリ）のことです（[第 5 章](ch05.md)・[第 12 章](ch12.md)）。
何も約束していないツールばかりのサーバを分母に入れたら、「宣言を書いたサーバのうち」という問いに答えていないことになります。
（出典: `docs/decisions.md:3860`（D70 の 4）、`docs/final_evaluation_procedure.md:186-187`。）

ただし、D3 と D4 について「明示した」をどの欄で数えるか（分母 M_d の定義）は、まだ決まっていません（**未決**）。
解析器の欄の上で、D3・D4 は D1・D2 と別の場所に記録されるためです。詳しくは[第 16 章](ch16.md)で見て、[第 46 章](ch46.md)の未決の一覧に載せます。

#### よくある誤解・つまずき

- **誤解: 「何も書いていないツールは、読むだけのツールだ」**
  逆です。既定値では「環境を変えうる」ツールです。何も書いていないツールは、何も約束していません。
- **誤解: 「既定値は SDK が自動で入れてくれる」**
  コードの上では、書かなかった項目は `None` のままです。既定値は「クライアントはこう受け取るべきだ」という説明文の約束です。
- **誤解: 「宣言を書いていないツールが何かを書き換えたら、違反だ」**
  違反ではありません。約束していないものは破れません。この研究は、そういうツールを判定の対象にしません。
- **誤解: 「`readOnlyHint: false` と明示したツールは、宣言を書いたツールとして分母に入る」**
  書いたことは確かですが、それは「何も約束しない側」の値です。どの値を「明示した宣言」として数えるかは、解析器の欄（`explicit` と `present_no_bound` の区別）で決まります。[第 16 章](ch16.md)で詳しく見ます。

#### 手作業ではどう使うか

- **判定の対象**: 何も宣言を書いていないツールには、D1〜D4 のどれも当たりません。だから、矛（解析器が「宣言に反する」と出した結果。第 6・17 章）の判定の組にも、見落としの抜き取り（解析器が何も出さなかったツールに、本当に違反が無いかを確かめる作業。[第 52 章](ch52.md)）の対象にも入りません。見落としの抜き取りの対象は「D1 か D2 を明示していて、その宣言への矛が 1 件も出ていないツール」です（出典: `docs/drafts/final_judging_guide_draft.md:443-446`）。
- **判定の最中**: 原ソースを読んでいて、宣言の無いツールが何かを書き換えているのを見つけても、それは違反として記録しません。約束していないからです。
- **集計のとき**: 分母 (c) の木を数えるときに、「宣言を書いたかどうか」を既定値で補って数えないでください。[第 39 章](ch39.md)で計算のしかたを見ます。

#### この節のまとめ

既定値は readOnlyHint false、destructiveHint true、idempotentHint false、openWorldHint true で、どれも約束しない側。だから何も書かないツールは何も約束しておらず、既定値を補っても D1〜D4 は生まれない。
解析器は既定値を補わず（「書いていない」を「安全だと言った」と読まない）、分母 (c) も明示した宣言だけを数える。D3・D4 の分母の定義は未決。

### 4.5 宣言の使い道 — クライアントは実際にどう使っているか

#### 一言で言うと

宣言は、ツールを使う側（クライアント）が「このツールは、利用者に確認せずに動かしてよいか」を決める材料として、**実際に使われています**。
少なくとも VS Code と OpenAI の Codex CLI は、`readOnlyHint: true` を見て確認を省きます [確認]。
ただし、すべてのクライアントがそうしているわけではありません。

#### たとえ話 — 空港の税関の「申告なし」レーン

海外から帰ってきた空港の税関には、多くの場合、2 つの通り道があります。
「申告するものがあります」の通り道と、「申告するものはありません」の通り道です。
後者を選んだ人は、ほとんど荷物を開けられずに通り抜けます。

ここで大事なのは、どちらの通り道を選ぶかを、**旅行者が自分で申告している**ことです。
税関は、申告を手がかりにして、どこに手間をかけるかを決めています。

AI のアプリにも、これと同じ作りのものがあります。
ツールが「読むだけです」と申告していれば、確認の画面を出さずに通すクライアントがあるのです（次の表）。
ただし、申告の無いツールや「読むだけ」でないツールをどう扱うかは、クライアントごとに違い、この調査の記録に書かれていないものもあります。たとえ話の税関ほど、きれいに 2 つに分かれているとは限りません。

#### 小さな例 — クライアントごとの使い方

本記録者が 2026-09-29 に調べた結果を、確かさの印（[第 0 章](ch00.md)）つきで並べます。

| クライアント | 宣言の使い方 | 確かさ |
|---|---|---|
| VS Code（Copilot のエージェントモード） | v1.100 のリリースノート: "tools marked with `readOnlyHint: true` in their annotations will be allowed to run without requiring user confirmation."（`readOnlyHint: true` のツールは、利用者の確認なしで実行される） | **[確認]** |
| OpenAI Codex CLI | 承認が要るかを決める関数 `requires_mcp_tool_approval` で、`destructiveHint == Some(true)` なら承認を求め、`readOnlyHint` が true なら `return false`（承認なし） | **[確認: codex-rs/core/src/mcp_tool_call.rs]** |
| Goose | readOnly と注記されたツールを SmartApprove（自動で許可する機能）で許可する | [agent] |
| Claude の connectors | "Read-only tools can run without per-call confirmation, and destructive tools always prompt."（読むだけのツールは呼び出しごとの確認なしで動き、壊すツールは必ず尋ねる） | [agent] |
| GitHub Copilot coding agent | "auto-approves tool calls only when the underlying tool is annotated with `ReadOnlyHint: true`"（`ReadOnlyHint: true` と注記されたツールの呼び出しだけを自動で許可する。issue #2483） | [agent] |
| GitHub MCP server の read-only モード | どのツールを出すかを `ReadOnlyHint` だけで決める | [agent] |

| Claude Code | 公式文書に `readOnlyHint` の記述が無い。第三者の報告は食い違う | [未確認] |

（出典: `docs/incidental_writes_practice.md:94-103`。調べた時点は 2026-09-29 で、クライアントの動きは版で変わりうる。）

#### 一歩ずつ — 印ごとに読む

[第 0 章](ch00.md)で見た確かさの印を、もう一度短く言い直します。
**[確認]** は本記録者が原文を取り寄せて、引用の文字列が原文にあることを照合したもの、**[agent]** は本記録者が仕事を分けて渡した別の AI の実行（agent）が「原文を読んだ」と報告したもので、本記録者は照合していないもの、**[未確認]** は検索の抜粋だけか、開けなかったもので、使わないものです。

この印に沿って、表を上から読みます。

1. **VS Code** の行は [確認] です。リリースノートの英文がそのまま原文にあることを照合済みです。「`readOnlyHint: true` のツールは、利用者の確認なしで実行が許される」と書いてあります。
2. **Codex CLI** の行も [確認] で、照合したのはソースコードのファイル（`codex-rs/core/src/mcp_tool_call.rs`）です。`requires_mcp_tool_approval` は「MCP のツールに承認が要るか」を返す関数で、2 つの規則が記録されています。
   - `destructiveHint == Some(true)` なら承認を求める。`Some(true)` は、Codex の書かれている言語（Rust）で「値が書かれていて、それが true」という意味です。
   - `readOnlyHint` が true なら `return false`、つまり「承認は要らない」と返す。
   - どちらにも当たらないときにどうなるかは、この記録には書かれていません。
3. **Goose・Claude の connectors・GitHub Copilot coding agent・GitHub MCP server** の 4 行は [agent] です。どれも「読むだけの印を見て確認を省く（または出すツールを決める）」という同じ傾向を示していますが、本記録者は原文を照合していません。
4. **Gemini CLI** の行も [agent] です。こちらは「既定では自動で許可しない」という、反対向きの報告です。
5. **Claude Code** の行は [未確認] です。公式の文書に記述が見つからず、第三者の報告も食い違っています。

#### この表から言えること・言えないこと

確かさに合わせて、言えることを書き分けます。

- **言えること**: [確認] の 2 つ（VS Code と Codex）だけでも、「`readOnlyHint: true` を見て、利用者の確認を省くクライアントが実際にある」ことは確かめられています。
- **傾向として言えること**: [agent] の行は、同じ使い方が他のクライアントにも広がっていることを示唆します。ただし、論文に書くなら、学生が原文で確かめて [確認] に上げてからにします。
- **言えないこと 1**: 「すべてのクライアントが確認を省く」とは言えません。Gemini CLI のように、既定では自動で許可しないクライアントもあります（[agent]）。
- **言えないこと 2**: Claude Code がどうしているかは、確かめられていません（[未確認]）。この教科書では、どちらとも書きません。

調査の結論は、次のとおりでした。

> クライアントは、readOnlyHint を「確認なしで実行してよい」の印として使っている。（中略）書き込みの種類で区別する層はどこにも無い。

「書き込みの種類で区別する層はどこにも無い」とは、たとえば「ログを 1 行書くだけなら確認を省いてよいが、利用者のファイルを書き換えるなら尋ねる」といった区別をするクライアントは見つからなかった、という意味です。
クライアントにとっては、`readOnlyHint: true` か、そうでないか、だけが手がかりです。
（出典: `docs/incidental_writes_practice.md:29-31`（結論 4））

#### なぜ第 4 版で書き直したのか

第 3 版では、ここを「`readOnlyHint: true` のツールなら利用者に確認せずに実行する、といった使い方が**できます**」と、仮定の形で書いていました。
仮定の形だと、「本当にそうしているクライアントがあるのか」が分かりません。
第 4 版では、本記録者の調査に基づいて、確かめた事実（[確認]）と、確かめていない報告（[agent]・[未確認]）を分けて書きました。
この研究の規則「未検証のものを、確かめたもののように書かない」（`CLAUDE.md` の規則 1）に合わせるためです。

#### よくある誤解・つまずき

- **誤解: 「どの AI のアプリも、`readOnlyHint: true` なら確認を省く」**
  言えません。[確認] は 2 つだけで、反対向きの報告（Gemini CLI）もあります。
- **誤解: 「[agent] の行も、確かめた事実として論文に書ける」**
  書けません。[agent] は本記録者が照合していないものです。論文に使うなら、先に学生が原文を開いて確かめます。
- **誤解: 「この表は、いつまでも正しい」**
  クライアントの動きは、版が上がると変わりえます。表は 2026-09-29 の時点の調査です。論文で使うときは、調べた日付も書きます。
- **つまずき: 「`destructiveHint` を書かなければ、Codex は承認を求めない」**
  記録から言えるのは「`destructiveHint` が true と書いてあれば承認を求める」ことだけです。書いていないときにどうなるかは、この記録には書かれていません。記録に無いことを推測で埋めないでください。

#### 手作業ではどう使うか

この節の事実は、判定の規則の**理由**として使われています。
[第 2 章](ch02.md)で見たとおり、決定 D68 の 1 は、条件つきで起きる動作も「ツールの呼び出しで起きうるなら到達する」と決めました。
その理由が、この節の調査の結論 4 です。

> クライアントは `readOnlyHint: true` を見て呼び出しごとの確認を省く（`docs/incidental_writes_practice.md` の結論 4）。確認を省いたどれか 1 回で起きるなら宣言は守られていない。

判定で条件つきの動作に出会ったら、「確認を省かれた呼び出しのどれか 1 回で、これは起きうるか」と問い、起きうるなら到達するとして、条件の種類を記録します（詳しくは[第 49 章](ch49.md)）。

もう 1 つ、論文を書くとき（[第 55 章](ch55.md)）にも使います。
最終評価の手順書は、違反の意味づけに「クライアントが `readOnlyHint` を『確認なしで実行してよい』の印として使っていること」が使える、と書いています。
見つけた違反を「確認を省かれた呼び出しで、何が書き換わるか」として示せる、ということです。
このとき引けるのは [確認] の 2 つ（VS Code と Codex）です。
（出典: `docs/decisions.md:3800-3801`（D68 の 1 の理由）、`docs/final_evaluation_procedure.md:1412-1414`（24.3 節））

#### この節のまとめ

VS Code と Codex は `readOnlyHint: true` を見て確認を省く [確認]。ほかにも同じ使い方の報告がある [agent]。既定では自動で許可しないクライアントもある [agent]。Claude Code は [未確認]。
クライアントは書き込みの種類で区別しない。この事実が、D68 の 1（確認を省いたどれか 1 回で起きるなら守られていない）の理由になっている。

### 4.6 宣言は検査されていない — 仕様自身が「信じるな」と書いている

#### 一言で言うと

宣言は自己申告で、**誰も検査していません**。
MCP の資料自身が「注記はヒントで、振る舞いを忠実に表している保証は無い」「信頼できないサーバの注記は信じるな」と書いています。
それでも、4.5 節で見たとおり、宣言を見て確認を省くクライアントがあり、**宣言が正しいかを確かめる層はどこにも無い**のです。

#### たとえ話 — 履歴書の資格欄

アルバイトの応募で、履歴書の資格欄に「普通自動車免許」と書いたとします。
多くの店は、免許証を見せてもらわずに、その欄を信じて採用を決めるかもしれません。
店が「資格欄は本人の申告です。必要なら原本を確かめてください」という注意書きを持っていたとしても、忙しい日には確かめずに配達を頼んでしまうかもしれません。

注意書きはある。けれども、確かめる手順は無い。
そして、申告を信じて仕事を任せている。
MCP の宣言は、ちょうどこの状態にあります。

#### 小さな例 — 資料の 4 つの文

MCP の資料から、4 つの文を引きます。

| 資料 | 原文 | 日本語で | 確かさ |
|---|---|---|---|
| schema の注記 | "all properties in ToolAnnotations are **hints**. They are not guaranteed to provide a faithful description of tool behavior" | ToolAnnotations の項目はすべてヒントで、ツールの振る舞いを忠実に記述している保証は無い | [確認: draft] |
| SDK の説明文 | "Clients should never make tool use decisions based on ToolAnnotations received from untrusted servers." | クライアントは、信頼できないサーバから受け取った ToolAnnotations に基づいてツールの使用を決めてはならない | SDK 1.30.0 で照合 |
| 仕様の本文 | "clients MUST consider tool annotations to be untrusted unless they come from trusted servers." | クライアントは、信頼できるサーバから来たものでない限り、注記を信頼できないものとして扱わなければならない | [agent] |
| 公式ブログの表 | "`readOnlyHint: true` \| Skip the confirmation dialog" | `readOnlyHint: true` なら、確認の画面を省く | [確認] |

（出典: schema・仕様の本文・公式ブログは `docs/incidental_writes_practice.md:44-46`。SDK の説明文は MCP Python SDK 1.30.0 の `mcp/types.py:1251-1256` で、この教科書を書くときに開いて照合した。公式ブログは "Tool Annotations as Risk Vocabulary"（2026-03-16）で、注記を信頼できないヒントとして扱う立場を書いている（`AUTHGAP_BRIEF_v3.md:181`）。）

#### 一歩ずつ

1. **schema の注記**は、「項目はすべてヒント（目安）」と言い切っています。4.1 節で見た名前の `Hint` は、この意味です。「振る舞いを忠実に記述している保証は無い」とまで書いています。SDK の説明文にも、同じ注意が `title` のような表示用の項目まで含めて書かれています。
2. **SDK の説明文**の 2 文目は、「信頼できないサーバから受け取った注記で、ツールの使い方を決めるな」と言っています。`should never`（決してすべきでない）という強い言い方です。
3. **仕様の本文**は、`MUST`（しなければならない）という、仕様の文書で最も強い言い方を使っています。ただし、この行は [agent] で、本記録者は原文を照合していません。
4. **公式ブログの表**は、`readOnlyHint: true` の行に「確認の画面を省く」と書いています。つまり、**信頼できるサーバの宣言なら、それを見て確認を省く**という使い方を、公式の側が示しているのです。

#### 状況をまとめると

4 つの文と 4.5 節の表を合わせると、次のような状況です。

1. 仕様と SDK は「信頼できないサーバの宣言は信じるな」と言う。
2. 一方で公式ブログは、（信頼できるサーバの）宣言を見て確認を省く使い方を示している。
3. 実際のクライアントの一部は、宣言を見て確認を省いている（[確認] は VS Code と Codex）。
4. **宣言が正しいかを確かめる層は、どこにも無い。**

調査の記録も、「MCP のツールでは、クライアントは宣言をそのまま信じる。宣言が正しいかを確かめる層は無い。一方で仕様とブログは、信頼できないサーバの注釈を信じるなと書いている」とまとめています。
（出典: `docs/incidental_writes_practice.md:115-116`）

#### 「信頼できるサーバなら信じてよい」の落とし穴

「信頼できるサーバ」の宣言なら信じてよい、という書き方にも注意が要ります。

- サーバを「信頼できる」と判断するのは、結局はサーバをインストールする利用者です。その判断の材料に、宣言そのものが使われることもあります。
- 信頼できる作者でも、[第 1 章](ch01.md)で見たように、**悪意なしに宣言を間違える**ことがあります。たとえば、後から誰かがキャッシュの処理を足したのに、宣言を直し忘れる、といった形です。

だから、「信頼できるサーバだから宣言は正しい」とは言えません。
この研究が測るのは、まさにこの「**信じられて使われている宣言が、実装とどれだけ食い違っているか**」です（[第 6 章](ch06.md)）。

#### なぜ、それでも食い違いを測るのか

「仕様が『信じるな』と言っているのに、食い違いを測って何になるのか」という問いが出るかもしれません。
答えは 2 つあります。

1. **実際には信じられているから。** 4.5 節のとおり、確認を省くクライアントがあります。仕様の注意書きと実際の使われ方が離れているなら、その間にどれだけの食い違いがあるかを測る意味があります。
2. **作者を助けられるから。** 食い違いを見つける道具は、作者がより正確な宣言を書くのを助けられます。学生はこれを論文の応用の 1 つとして書くと決めました（決定 D63）。ただし言うのは安全側の向きだけで、「`readOnlyHint: false` にすべき」とは言えても、「効果が見つからなかったから `readOnlyHint: true` を付けてよい」とは言いません。

詳しい見通しは[第 44 章](ch44.md)で見ます。
（出典: `docs/decisions.md:3542-3556`（D63））

#### よくある誤解・つまずき

- **誤解: 「仕様が『信じるな』と書いているのだから、宣言が間違っていても問題ない」**
  問題はあります。実際に信じて確認を省くクライアントがあり、公式ブログもその使い方を示しています。注意書きがあることと、被害が起きないことは別です。
- **誤解: 「MCP のどこかで、宣言が正しいかを検査している」**
  検査する層はどこにもありません。だから、この研究のような外からの測定が要ります。
- **誤解: 「AuthGap は、クライアントの中で宣言を検査する道具だ」**
  違います。AuthGap は、公開のサーバのコードを読んで、宣言と食い違う動作がどれくらいあるかを**測る**研究の道具です（[第 6 章](ch06.md)）。実行中に呼び出しを止める道具ではありません。
- **つまずき: 「`Hint` だから、多少ずれていても約束違反ではない」**
  この研究は、宣言を字義どおりの約束として照合します。「ヒントだから甘く見る」という読み方はしません（判定の基準は[第 17 章](ch17.md)の原理）。

#### 手作業ではどう使うか

判定では、「このサーバは信頼できそうか」「このクライアントなら確認を省くか」を考えません。
判定の手引きは、基準を「採った原理」を字義どおりに当てることとし、自分の感覚で「これくらいは違反と言えない」と判断しないよう求めています。
判定するのはコードの動作と宣言の関係だけです。
クライアントの使い方は、研究の**動機**と、D68 の 1 のような規則の**理由**であって、1 件ごとの判定の基準ではありません。
（出典: `docs/drafts/final_judging_guide_draft.md:54-60`（11.3 節））

#### この節のまとめ

schema・SDK・仕様は「注記はヒントで、信頼できないサーバのものは信じるな」と書くが、公式ブログは確認を省く使い方を示し、実際に確認を省くクライアントがある。宣言を確かめる層はどこにも無い。
この研究は、信じられて使われている宣言と実装の食い違いを測る。判定では、サーバの信頼度やクライアントの動きではなく、コードと宣言だけを見る。

### 4.7 仕様が何も言っていないこと — 裏方の書き込み

#### 一言で言うと

MCP の仕様は、ツールの本来の仕事ではない「裏方の書き込み」（ログ・キャッシュ・一時ファイルなど）が `readOnlyHint: true` の範囲に入るかについて、**何も言っていません**。
「環境」という言葉の定義も例もありません。
この研究は、この空白を原理で先に埋めています。

#### たとえ話 — 図書館の閲覧記録（第 1 章の続き）

[第 1 章](ch01.md)で、図書館に「見るだけです」と言って入り、本を読んで帰ったのに、閲覧の記録が 1 行増えた、という話をしました。
「見るだけ」の約束は破れたのか、という問いでした。

この問いに図書館の規則が答えていなければ、人によって答えが分かれます。
MCP の仕様は、ちょうど「答えていない規則」の状態にあります。

#### 小さな例 — 裏方の書き込みを 4 つ持つツール

```python
# 説明用
import os, tempfile

DATA_DIR = os.path.expanduser("~/.notes_app")
CACHE = os.path.join(DATA_DIR, "cache.txt")

@mcp.tool(annotations={"readOnlyHint": True})
def search_notes(query: str) -> str:
    """メモを検索する。"""
    os.makedirs(DATA_DIR, exist_ok=True)                   # (a)
    with open(os.path.join(DATA_DIR, "search.log"), "a") as f:
        f.write(query + "\n")                               # (b)
    old = open(CACHE).read() if os.path.exists(CACHE) else ""
    result = do_search(query, previous=old)
    with open(CACHE, "w") as f:
        f.write(result)                                     # (c)
    fd, tmp = tempfile.mkstemp()                            # (d)
    with os.fdopen(fd, "w") as f:
        f.write(result)
    summary = summarize_file(tmp)
    os.remove(tmp)
    return summary
```

#### 一歩ずつ

- 2 行目は、ファイルやフォルダを扱う道具（`os`）と、一時ファイルを作る道具（`tempfile`）を使えるようにしています。
- 4 行目は、データを置くフォルダの場所を決めています。`~` は利用者のホームフォルダのことで、`os.path.expanduser` がそれを実際の場所に置き換えます。
- 5 行目は、そのフォルダの中の `cache.txt` というファイルの場所を、`CACHE` という名前で覚えています。
- 7 行目は、このツールを `readOnlyHint: True`（読むだけ。D1）と宣言しています。
- 8〜9 行目は、ツールの関数と説明文です。説明文は「メモを検索する」です。
- 10 行目 **(a)**: `os.makedirs(DATA_DIR, exist_ok=True)` は、フォルダが無ければ作ります（`exist_ok=True` は「もうあれば何もしない」という意味）。つまり、**初回だけ**フォルダが作られます。
- 11〜12 行目 **(b)**: `search.log` を追記用（`"a"`）に開き、検索語を 1 行書き足します。**ログ**です。このファイルは、ツールの中では読み返されません。
- 13 行目: `cache.txt` があれば、前回の結果を読み込みます（無ければ空の文字列）。
- 14 行目: ここが本来の仕事、検索です。前回の結果を手がかりに渡しています（`do_search` の中身は省いています）。
- 15〜16 行目 **(c)**: `cache.txt` を書き込み用（`"w"`）に開き、今回の結果を保存します。13 行目で次の呼び出しが読み返す、後で使うための控え、つまり**キャッシュ**です。毎回、前の内容は消えて上書きされます。
- 17〜21 行目 **(d)**: `tempfile.mkstemp()` で新しい**一時ファイル**を作り、結果を書いて、別の関数 `summarize_file` に読ませ、最後に `os.remove(tmp)` で消します。
- 22 行目: 要約を返します。

ツールの本来の仕事は「検索して、要約を返す」です。
(a)〜(d) は、どれも本来の仕事のための**裏方の書き込み**です。
一方で、`readOnlyHint: true` の説明文 "does not modify its environment"（環境を変えない）を字義どおりに読めば、(a)〜(d) のどれも、ファイルやフォルダという環境を変えています。

#### 言葉の整理 — 裏方の書き込み

- **やさしい言い換え**: ツールの本来の仕事ではないのに、裏で起きる書き込み。
- **正確な定義**: 付随的な書き込み（incidental writes）。調査の記録では、初回の初期化・キャッシュ・ログ・一時ファイル・IPC のファイル（別のプログラムとやり取りするための受け渡しのファイル）・トークン（ログインの証明のデータ）の保存を対象にしている。この教科書では「裏方の書き込み」と呼ぶ。
- **例**: 上のコードの (a)〜(d)。
（出典: `docs/incidental_writes_practice.md:1-5`）

#### 仕様は何と言っているか — 何も言っていない

本記録者の調査は、MCP の資料について次のように結論しています。

> MCP の仕様は、付随的な書き込みについて何も言っていない。"environment" の定義も例も無い。schema の全版・本文・公式ブログ（2026-03）・IG の憲章・SEP のどれにも、ログ・キャッシュ・一時ファイルの扱いは無かった。

（出典: `docs/incidental_writes_practice.md:20-21`）

つまり、「(a)〜(d) は `readOnlyHint: true` に反するか」という問いに、仕様から答えを引き出すことはできません。
実世界の他の資料は、互いに逆を向いています。
[第 1 章](ch01.md)で少し触れたとおり、ある AI の会社の提出ガイドは「ログを書くツールは読み取り専用と名乗るな」の向きで、HTTP の文書（RFC 9110）は「アクセスログへの追記は安全な操作の範囲内」の向きです（どちらも [確認]。`docs/incidental_writes_practice.md:22-26`）。

#### なぜ、この研究は先に決めておくのか

仕様が決めていないまま判定を始めると、判定する人の感覚で答えが変わります。
同じ (b) のログでも、ある日は「これくらいは違反でない」、別の日は「違反だ」となりかねません。
そうなると、出てきた数が何を数えたのか説明できません。

そこでこの研究は、データを見る前に原理で決めました。
**字義どおりに読む**、つまり、呼び出しを越えて残るものを変えるなら、裏方の書き込みも違反に数える、という原理です（[第 17 章](ch17.md)の原理 1）。
さらに、最終評価では、違反に**重みを付けない**かわりに、正とした件ごとに「書き込み先の種類」（ログ・一時ファイル・キャッシュ・状態の保存など）を事実のラベルとして記録すると決めました（決定 D67 の 1、D68 の 3。ラベルは[第 51 章](ch51.md)）。
なぜ重みを付けないのか、実世界の資料はこの問いをどう扱っているのかは、[第 43 章](ch43.md)で詳しく見ます。
（出典: `docs/decisions.md:3767-3772`（D67 の 1）、`:3809-3814`（D68 の 3））

#### よくある誤解・つまずき

- **誤解: 「仕様が、裏方の書き込みは `readOnlyHint` に反しないと言っている」**
  言っていません。仕様は何も言っていません。「反しない」とも「反する」とも書いていないのです。
- **誤解: 「AuthGap は、裏方の書き込みを軽い違反として数える」**
  軽重の重みは付けません。違反は違反として数え、書き込み先の種類をラベルとして記録するだけです。軽重の判断は読み手に任せます。
- **つまずき: 「違反か」と「どれくらい困るか」を混ぜる**
  [第 1 章](ch01.md)でも見たとおり、2 つは別の問いです。この研究の問いは「宣言は正しいか」で、「危ないか」ではありません。

#### 手作業ではどう使うか

判定で裏方の書き込みに出会ったら、次の順に考えます。

1. **到達するか**: その書き込みは、ツールの呼び出しで起きうるか（[第 49 章](ch49.md)）。
2. **宣言に反するか**: 宣言の問い（4.2 節）を字義どおりに当てる。D1 なら、判定の手引きの表のとおり、ファイルの書き込み・作成・削除は、ログでもキャッシュでも一時ファイルでも反する。
3. **ラベル**: 正にしたら、書き込み先の種類を 1 つ付ける。

判定の手引き（下書き・未承認）は、この点をはっきり書いています。
「たとえば読み取り専用のツールがログファイルに 1 行追記するのは、採った原理（1-i-b: 呼び出しを越えて残るものはすべて環境）では違反である。軽重は書き込み先の種類のラベルで表し（第 16 節）、判定の正誤には持ち込まない。」
（出典: `docs/drafts/final_judging_guide_draft.md:56-60`）

#### この節のまとめ

MCP の仕様は、裏方の書き込み（ログ・キャッシュ・一時ファイルなど）について何も言わず、「環境」も定義していない。実世界の資料は逆を向いている。
この研究は字義どおりに読むと原理で先に決め、最終評価では重みを付けずに書き込み先の種類をラベルとして記録する（第 43・51 章）。

### 4.8 D2 の微妙なところ（予告）

#### 一言で言うと

D2（`destructiveHint: false`、「足すだけで、前からあるものは壊さない」）の判定は、「**呼び出しの前からあったもの**を消す・上書きする・変えるか」で決まります。
この問いで考えると、「ファイルを書く」「ファイルを消す」といった同じ見た目の動作でも、反する場合と反しない場合に分かれます。

#### たとえ話 — 共有の冷蔵庫

職場の共有の冷蔵庫に、「自分の物を**足すだけ**。前から入っている物は捨てない・入れ替えない」という約束があるとします。

- 今朝自分で入れたお弁当を、昼に食べ終えて容器を捨てるのは、約束の範囲内です。捨てたのは、今日自分が入れた物だからです。
- 先週から入っている誰かのヨーグルトを捨てたら、約束違反です。
- 「どの棚に入れるかは、頼んだ人が決める」という仕組みで、頼んだ人が他人の物が入っている棚を指定し、そこにあった物を押し出して入れ替えたら、やはり約束違反です。

D2 の判定は、この「前から入っていた物か」を問うことに当たります。

#### 小さな例 1 — ファイルを開くときのモード

まず、ファイルを開くときの「モード」を短く見ます（詳しくは[第 9 章](ch09.md)）。

| 書き方 | 意味 | 前からあったファイルは |
|---|---|---|
| `open(p, "w")` | 書き込み用に開く | **中身が消されて**から書かれる（上書き） |
| `open(p, "a")` | 追記用に開く | 残り、後ろに足される |
| `open(p, "x")` | 新しく作る用に開く | 既にあれば失敗する（壊さない） |

表の読み方: 1 行目は「`"w"` で開くと、そのファイルが前からあった場合、中身が消えて上書きされる」と読みます。だから `"w"` は、前からあったものを壊しうる書き方です。

#### 小さな例 2 — 3 つの形

```python
# 説明用（形 1。destructiveHint=False と宣言したツール）
def export_report(path: str, text: str) -> str:
    with open(path, "w") as f:      # 書き先 path は LLM が引数で決める
        f.write(text)
    return "saved"
```

```python
# 説明用（形 2。destructiveHint=False と宣言したツール）
def convert(data: str) -> str:
    fd, tmp = tempfile.mkstemp()    # この呼び出しの中で、新しい一時ファイルを作る
    with os.fdopen(fd, "w") as f:
        f.write(data)
    out = run_converter(tmp)        # 別の関数に一時ファイルを読ませる
    os.remove(tmp)                  # 自分で作った一時ファイルを、後始末で消す
    return out
```

```python
# 説明用（形 3。destructiveHint=False と宣言したツール）
RESPONSE = "/tmp/app/response.json"

def ask(question: str) -> str:
    if os.path.exists(RESPONSE):
        os.remove(RESPONSE)         # 前の呼び出しが残した応答ファイルを消す
    ...
```

#### 一歩ずつ

**形 1**:
- 2 行目で、`path`（書き先）と `text`（中身）を引数で受け取ります。どちらも LLM が決める値です。
- 3 行目で、`path` を `"w"` で開きます。`path` が既にあるファイルなら、その中身は消えます。
- 4 行目で、`text` を書きます。
- **判定**: D2 に**反する**。書き先を LLM が決められるので、LLM は既存のファイルを指すこともできます。指せば、そのファイルは上書きされて壊れます。[第 2 章](ch02.md)の「モデルが決める値は、取りうる値の全体で考える」（[第 17 章](ch17.md)の原理 3）により、反すると判定します。

**形 2**:
- 3 行目の `tempfile.mkstemp()` は、毎回**新しい名前**の一時ファイルを作ります。
- 4〜5 行目で、そこにデータを書きます。
- 6 行目で、別の関数に読ませます。
- 7 行目で、その一時ファイルを消します。
- **判定**: D2 に**反しない**。消したのは「同じ呼び出しの中で自分が作ったもの」で、呼び出しの前からあったものではないからです。v3・v4 では、解析器がこの形を誤って違反と出した例があり、判定では「誤」（解析器の指摘は正しくなかった、という判定。[第 48 章](ch48.md)）とし、誤の原因 E2 として記録します（O41・O43。誤の原因の分類は[第 51 章](ch51.md)）。

**形 3**:
- 1 行目で、応答ファイルの場所を決まった 1 か所にしています。
- 4 行目で、そのファイルがあるかを調べます。
- 5 行目で、あれば消します。このファイルは、**前の呼び出しが残したもの**です。
- **判定**: D2 に**反する**。形 2 と同じ「消す」でも、消したのは呼び出しの前からあったものだからです。

#### もう 1 つの比較 — 同じ形 2 でも、D1 なら反する

形 2 のコードが、もし `readOnlyHint: true`（D1）と宣言したツールだったらどうでしょうか。
判定の手引きの D1 の表では、「ファイルの書き込み・作成・削除・移動・権限の変更（`FS_WRITE` すべて）」が「反する」で、注意の欄に「ログ・キャッシュ・一時ファイル・ディレクトリの作成も含む」と書かれています。
一時ファイルを作って消すのも、ファイルシステムへの書き込みに数えるので、**D1 には反します**。
D2 が「前からあったものか」を問うのに対して、D1 は「ファイルシステムを書き換えたか」を問う、と言い換えてもよいでしょう。

v4 の判定にも、この形の例があります。
ru-marketplace というサーバの `ozon_reviews` は、同じ呼び出しで `mkstemp` した一時ファイルを `os.remove` で消していました。
宣言は D1 だったので、判定は**正**（解析器の指摘どおり、本当に宣言に反する）でした。
判定の手引きは、この例に「D1 では反する。D2 なら E2 で誤になる形」と注記しています。
（出典: `docs/drafts/final_judging_guide_draft.md:309`（D1 の表の 1 行目）、`:641`（v4 の M58））

#### なぜこう決めるのか

D2 の約束は「追加の更新だけをする」（"performs only additive updates"）です。
追加だけなら、前からあるものは残ります。
だから、壊したかどうかは「前からあるもの」に何が起きたかで決まります。
判定の手引きは、D2 の問いを「その動作は、**呼び出しの前からあったもの**を消す・上書きする・変えるか。新しく足すだけなら反しない」と書いています。

書き出し（`"w"` など）については、次の規則です。
「書き先をモデルが決められるなら反する（既存のファイルを指せば上書きできる。原理 3-a）。書き先が固定なら、そこに呼び出しの前からファイルがありうるかで決める（毎回同じファイルを上書きするなら反する、呼び出しごとに新しい名前なら反しない、分からなければ不明）」。
（出典: `docs/drafts/final_judging_guide_draft.md:327-346`（15.2 節））

#### よくある誤解・つまずき

- **誤解: 「`"w"` で書いたら、いつでも D2 違反」**
  書き先が固定で、呼び出しごとに新しい名前なら反しません。書き先をモデルが決められる場合や、毎回同じファイルを上書きする場合は反します。
- **誤解: 「一時ファイルの削除は、いつでも違反ではない」**
  D2 では、自分が同じ呼び出しで作ったものなら反しませんが、前の呼び出しが残したものなら反します。D1 では、どちらでも反します。
- **誤解: 「同じコードなら、宣言が違っても判定は同じ」**
  違います。判定は宣言ごとの問いで決まります。形 2 は、D1 なら反する（解析器が矛を出していれば判定は正）、D2 なら反しない（解析器が矛を出していれば判定は誤）です。

#### 手作業ではどう使うか

D2 の組を判定するときは、消された・上書きされたものについて「**それは呼び出しの前からあったか**」を必ず問います。

- 書き先を LLM が決められるなら、「前からあるファイルを指せる」ので反する。
- 同じ呼び出しで作って消すなら反しない（解析器が矛を出していれば、判定は誤で原因 E2）。
- 前の呼び出しの残りなら反する。
- 決められなければ「不明」にし、理由を書く。

詳しい規則と、反する例・反しない例の対は[第 50 章](ch50.md)で見ます。

#### この節のまとめ

D2 は「呼び出しの前からあったものを消す・上書きする・変えるか」を問う。モデルが書き先を決める書き出しは反し、同じ呼び出しで自分が作った一時ファイルの後始末は反しないが、前の呼び出しが残したファイルの削除は反する。
同じ一時ファイルの後始末でも、D1 では反する。判定は宣言ごとの問いで決まる（[第 50 章](ch50.md)）。

### この章のまとめ

- MCP のツールは、注記（ToolAnnotations）の欄で自分の性質を申告できる。この研究ではこれを宣言と呼ぶ。扱うのは振る舞いを申告する 4 つ（readOnly・destructive・idempotent・openWorld）で、約束をしている側の値を D1〜D4 と呼ぶ。D2・D4 は `readOnlyHint: true` が無いときだけ当たる。
- 宣言の書き方には、専用の型・辞書・低レベルの一覧の中、などがある。意味は同じ。
- 既定値は readOnlyHint false、destructiveHint true、idempotentHint false、openWorldHint true で、どれも約束しない側。何も書かないツールは何も約束しておらず、既定値を補っても D1〜D4 は生まれない。解析器は既定値を補わず、分母 (c) も明示した宣言だけを数える（D3・D4 の分母の定義は未決）。
- VS Code と Codex は `readOnlyHint: true` を見て利用者の確認を省く [確認]。ほかにも同じ使い方の報告がある [agent]。既定では自動で許可しないクライアントもある [agent]。Claude Code は [未確認]。クライアントは書き込みの種類で区別しない。
- schema・SDK・仕様は「注記はヒントで、信頼できないサーバのものは信じるな」と書くが、公式ブログは確認を省く使い方を示す。宣言を確かめる層はどこにも無い。
- 仕様は裏方の書き込みについて何も言わず、「環境」も定義していない。この研究は字義どおりに読むと先に決め、重みは付けずに書き込み先の種類を記録する（第 43・51 章）。
- D2 は「呼び出しの前からあったものを壊すか」を問う。モデルが書き先を決める書き出しは反し、同じ呼び出しで作った一時ファイルの後始末は反しない（D1 なら反する）。判定は宣言ごとの問いで決まる（[第 50 章](ch50.md)）。
