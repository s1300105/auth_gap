# 付録 D 演習と確認問題の答え — 第 2 部（第 6〜8 章）

## 第 6 章 この研究の一文 — 不明を数える測定研究 の答え

### 演習 6-1（不明の扱いで率が変わる）

1. **6%**。読み切れなかった 50 個を「違反なし」に数えると、分母は 200 のまま、分子は 12。12 ÷ 200 = 0.06。
2. **8%**。50 個を分母から消すと、分母は 150、分子は 12。12 ÷ 150 = 0.08。
3. **6% 〜 31% の間**。読み切れなかった 50 個に違反が 1 つも無ければ 12 ÷ 200 = 6%。50 個が全部違反なら (12 + 50) ÷ 200 = 62 ÷ 200 = 31%。本当の率は、この間のどこかにある。
4. **3 の「分けて数える」**。1 は、読み切れなかったものを黙って「違反なし」に倒すので、隠れた違反が消え、率が甘く出る（危険を見落とす向き）。2 は、答えている問いを「読み切れたツールのうち」にすり替えるので、読み切れないものと読み切れるものの違反の率が違えば、率がどちらかにゆがむ。3 なら、読み手が率の幅を自分で判断でき、読み切れなかった理由から解析器の苦手も分かる。

考え方: 1 と 2 の数（6% と 8%）は、どちらも「正確そうな 1 つの数」に見える。けれども、どちらも確かめていないものを確かめたように扱っている。6.4 節の宿題のたとえと同じ。

### 演習 6-2（HintLint と AuthGap の問いの違い）

1. 解答の例: 「HintLint は主に宣言が**無い**ツールの危険を、確かなものだけ指摘する開発用の点検の道具（linter）で、AuthGap は宣言を**明示した**ツールがその宣言に**反する**率を、読み切れなかったものも理由つきで数えて測る測定研究である。」
   - 採点の目安: 「宣言が無い / 宣言があって反する」の対比と、「読み切れないものを残さない / 理由つきで数える（率を測る）」の対比の、少なくとも片方が入っていればよい。両方入っていればなおよい。
2. HintLint の規則 `DESTRUCTIVE-001` は、`destructiveHint` が**書かれていない**ことで発火する。実際に 61 件は、宣言を何も書いていない（`declared_annotations` が `{}`）ツールへの指摘だった。AuthGap の矛は、はっきり書かれた宣言に**反する**ことを求めるので、宣言の無いツールは矛にならない。つまり 61 件は、そもそも同じ現象を数えていない（`docs/decisions.md:1822-1825`）。
3. - `open(output_file, "w")` は**当たる**。括弧の中の `output_file` に `file` という語が含まれ、引用符つきの `w` もあるから。
   - `open(out, "w")` は**当たらない**。括弧の中に `destination`・`path`・`file`・`artifact` のどれも無いから。
   - どちらも同じようにファイルに書き込むのに、変数の名前しだいで見えたり見えなかったりする。これが、文字の並びだけを見る正規表現の限界。

### 演習 6-3（どの確かめ方か）

| | 確かめ方 | 人が付ける結果 | 理由 |
|---|---|---|---|
| (a) | 精度（V2） | **正** | ツールの呼び出しで起き（到達する）、ファイルの書き込みは D1 に反する。2 つの問いの答えがどちらも「はい」 |
| (b) | 見落とし（V3） | **見落とし** | 呼び出しの前からあるファイルを消すのは D2（前からあるものを壊さない）に反する。深さ 2 は読む範囲（深さ 4 まで）の中で、解析器は矛も不も出していない。原因（呼び出しの解決・受け手の型・語彙・その他）は、解析器がなぜ見落としたかを調べて付ける。この問題文だけでは決まらない |
| (c) | 不の中身（V6） | **違反でない** | POST の送り先が検索をするだけの API なら、相手の状態は変わらないので D1 に反しない（判定の手引き 15.1 節の POST の行: 「照会」なら反しない） |
| (d) | 頑健性（V1） | 判定しない | 打ち切った木として件数を数え、原因と所要時間を書く |
| (e) | 精度（V2） | **不明**（理由を書く） | 20〜30 分調べても到達するかを決められないので、正にも誤にも倒さず不明にする。理由に「木の外のライブラリが木の中の関数を呼び戻す形で、到達を決められない」と書く |

考え方: (c) は解析器が不と言ったもので、人が調べると決められた例。(e) は解析器が矛と言ったもので、人が調べても決められなかった例。解析器の「不」と人の「不明」が別の言葉であることを確かめる組み合わせになっている。

### 演習 6-4（結論の文を作る）

1. **(a) = 54 ÷ 120 = 45%**。矛の出た 120 木を全部判定したので、n = N = 120。
2. **(c) = 54 ÷ 400 = 13.5%**。全木を判定したので、推定の木の数は k そのまま（54）。分母は D2 を明示したツールを持つ木の数 400。
3. 解答の例: 「`destructiveHint: false` を宣言したサーバのうち、少なくとも約 13.5%（54 / 400）に、その宣言に反する動作があった。」
4. この数は下限だから。理由は 2 つ。
   - 1 木あたり、1 つの宣言について最大 3 件しか判定しない。3 件がすべて誤の木でも、判定しなかった残りに正があるかもしれない。
   - 矛の出なかった木（400 − 120 = 280 木）の見落としを数えていない。解析器が矛を出さなかった木にも、違反があるかもしれない。

### 確認問題 6-1

**矛です。** `destructiveHint: false`（D2。`readOnlyHint: true` が無いとき）は、「前からあるものを壊さない（足すだけ）」という約束です。既存のファイルを消せるなら、前からあるものを壊せるので、M が D を超えています。

### 確認問題 6-2

- **道具の研究**は、新しい道具が既存の道具よりよく見つけること（見つけた件数・検出力）を示す研究。**測定研究**は、調べる対象の全体（母集団）を先に定義し、決めた手続きで、ある現象の率とその不確かさを報告する研究。
- この研究の問いは「宣言がどれだけ当てにならないか」という率の問いなので、分子だけでなく分母を正しく数える必要がある。静的解析には読み切れないものが必ず出るので、それを黙って「違反なし」に数えたり、分母から消したりすると、率そのものがゆがむ。だから、読み切れなかったものを理由つきで別に数えること（不明を数える）が、測定研究としてのこの研究の芯になる（D40）。

### 確認問題 6-3

| 解析器の答え | 最終評価で確かめる量 |
|---|---|
| 矛 | 精度（V2）: その矛は本当に宣言違反か（正 / 誤 / 不明） |
| 不 | 不の中身（V6）: 不の中身は実際には違反か（違反 / 違反でない / 不明） |
| 何も出さない（その宣言への矛を出していない） | 見落とし（V3）: 本当は違反があるのに見逃していないか。D1 か D2 を明示したツールが対象 |

- 解析器の「**不**」は、機械がコードからは、宣言に反するかを静的に決められなかったという意味。
- 人の判定の「**不明**」は、人が原ソースを読み、調べても（目安は 20〜30 分）決められなかったという意味。
- 解析器が不としたものでも、人が調べれば違反か違反でないかを決められることがある（POST の送り先の API の文書を読む、など）。逆に、解析器が矛としたものが、人には決められず不明になることもある。

### 確認問題 6-4

- **分母**: その宣言を明示的に書いたツール（ユニット）を 1 つ以上持つ、走査した木の数（分母 (c)）。既定値で補ったものは数えない。宣言（D1〜D4）ごとに別々に出す（D70 の 4、D62）。
- **「少なくとも」と付く理由**: この数は下限だから。1 木あたり 1 つの宣言について最大 3 件しか判定しないので、判定しなかった残りに正があるかもしれない。また、矛の出なかった木の見落としを数えていない。

## 第 7 章 静的解析 — プログラムを動かさずに読む の答え

### 演習 7-1（2 つの方法で調べる）

**1.** 5〜6 行目の書き込みは**見えません**。`mode` を渡していないので既定の `"show"` になり、4 行目の `mode == "save"` が偽になるからです。
8〜9 行目の書き込みは、**その時の環境しだい**です。サーバを動かしている環境で環境変数 `REPORT_LOG` が設定されていれば見え、設定されていなければ見えません。同じ呼び出しでも、環境によって観察の結果が変わる例です（7.2 節の理由 4）。

**2.** **2 つ**見つかります。
- 道 (i): 5〜6 行目。`mode == "save"` のとき、`/srv/reports/<month>.txt` を `"w"`（中身を消して書く）で開いて書く。
- 道 (ii): 8〜9 行目。環境変数 `REPORT_LOG` が設定されているとき、その場所のファイルを `"a"`（末尾に足す）で開いて 1 行書く。

どちらもファイルの書き込みなので、`readOnlyHint: true`（D1）の宣言に反しうる動作です（D1 ではファイルの書き込みはすべて反する。判定の手引き 15.1 節）。

**3.** 道 (i) は、`mode` と `month` がツールの引数なので、**LLM が決める値**で通ります。最終評価なら条件の種類は `引数` です。
道 (ii) は、環境変数を設定する**運用者**（サーバを動かす人）が決める値で通ります。条件の種類は `運用者の設定` で、主の数 (A) には数えますが、併記の (B)（運用者が決める条件でしか届かないものを除いた数）には数えません（D68 の 1。`docs/drafts/final_judging_guide_draft.md:241-259`。詳しくは[第 49 章](ch49.md)）。

### 演習 7-2（AI の 3 つの話を分ける）

**同じ決定ではありません。**

- 「解析器は LLM を使わない」（①）は、**解析器が走るときの性質**です。原典は仕様書の `AUTHGAP_BRIEF_v3.md:36`（「LLM を判定入力に使わず決定的に」）と `:82`（「LLM を verdict 入力に使わない」ことを主張の一部にしている）。`README.md:10` にも書かれています。仕様書の最初からの決まりです。

3 つ目の話（③ 研究の進め方に AI を使ったこと）は、**論文の方法の節で開示します**。原典は **O45 の 4**（`docs/open_questions.md:1264-1266`）と `docs/llm_judgment_survey.md` §4（157-168 行）。そのとき、「解析器は LLM を使わず、決定的に動く」（走らせたときの性質）と「研究の遂行に AI を使った」（開示が要る）を分けて書きます。開示の対象は、v4 の判定、手順書と手引きの下書き、決定の推奨、コミットの共著者などです。

### 演習 7-3（抽象構文木を出してみる）

本書の執筆時に Python 3.10 で出力した結果です（Python の版によって、`ctx=Load()` や `keywords=[]` のような細かい表示が省かれることがあります）。

**(a)** `shutil.rmtree(target)`

```
Call(func=Attribute(value=Name(id='shutil', ctx=Load()), attr='rmtree', ctx=Load()), args=[Name(id='target', ctx=Load())], keywords=[])
```

- 呼び出すもの（`func`）: `shutil` という名前の `rmtree` という属性（`Attribute`）。つまり `shutil.rmtree`（フォルダを中身ごと消す関数）。
- 引数（`args`）: `target` という名前が 1 つ。

**(b)** `open(path, mode)`

```
Call(func=Name(id='open', ctx=Load()), args=[Name(id='path', ctx=Load()), Name(id='mode', ctx=Load())], keywords=[])
```

- 呼び出すもの（`func`）: `open` という名前そのもの（`Name`）。
- 引数（`args`）: `path` と `mode` の 2 つの名前。

**増えている「決められないこと」**: **開くモード（読むのか書くのか）**です。`open(save_to, "w")` では 2 つ目の引数が `Constant(value='w')`（定数）なので、木だけから「書き込み用」と分かりました。(b) では 2 つ目も `Name(id='mode')` なので、`mode` に何が入るかを別に追いかけないと、読むのか書くのかが決まりません。
値を追っても決まらなければ、原理 2 により「不」になりえます（`docs/contradiction_principles.md:63` の例「開くモードが読めない」）。`mode` を LLM が決められるなら、原理 3（能力として読む）により「書くこともできる」と読みます（第 14・17 章）。

### 演習 7-4（誤警報か見落としか）

（出典: `docs/drafts/final_judging_guide_draft.md:229-239, 261-294, 422-440, 441-480, 532-544`。）

### 確認問題 7-1

ツールの動きが**引数の値によって変わる**場合です。
`search` の例では、`save_to` を渡さずに呼ぶと、`if save_to:` の中に入らないので、ファイルの書き込みは起きません。動的解析で `search(query="mcp")` と呼んで観察すると、「読むだけ」に見えます。
静的解析でコードを読めば、`if save_to:` の中に `open(save_to, "w")` があるので、「`save_to` が渡されれば書く道がある」と分かります。`save_to` は LLM が決める引数なので、この道は M（できること）に入ります。

### 確認問題 7-2

**決定的**とは、同じ入力に必ず同じ結果を返す性質です。この解析器では、同じ木を解析した manifest が、走らせるたびに変わってよい欄（`run_meta`: 解析の時間・走査の名前・木の場所）を除いて、バイト単位で一致します（`authgap/report.py:312-320`）。

直す前と後の結果を比べるとき、決定的なら、違いは「直したせい」だと言えます。決定的でなければ、毎回少しずつ違う結果が出るので、違いが直したせいなのか、たまたまなのかを区別できません（[第 23 章](ch23.md)）。

`--determinism 3` では見つけられない例: **U25**。解析器はクラスの中身を調べた結果を、データの番地（`id(index)`）で引く表に入れて使い回していたので、1 つのプログラムの中で木を続けて解析すると、前の木の同じ名前のクラスの中身を流用することがありました。`--determinism` は同じ木を繰り返すだけなので、「前に別の木を解析したか」で変わる誤りは見えません。D64 で直されました（`authgap/analyze.py:363-370`）。

### 確認問題 7-3

解析器の矛は「通りうる道」で、実際に通る道とは限りません。その差を 3 つの量で測ります。
- **精度（V2）**: 解析器が矛を出した組を抜き取り、人が「到達するか（実際に通るか）」と「宣言に反するか」を確かめる。通らない道を数えた誤警報は「誤」になる。精度は、矛のうち本当に違反だった割合。
- **見落とし（V3）**: 解析器が矛を出さなかったツールを抜き取り、人が先にコードを読んで、実際に通る道に宣言違反が無いかを探す。解析器が道を見失った分が分かる。
- **不の中身（V6）**: 解析器が「静的に決められない」とした組を抜き取り、人が実際には違反か、違反でないかを決める。

3 つがそろうと、解析器の 3 つの答え（矛・不・何も出さない）のそれぞれが、実際にはどれだけ当たっていたかを示せます（`docs/final_evaluation_procedure.md:64-79`）。

### 確認問題 7-4

**書いてはいけません。**
v4 は、凍結版の解析器を新しいデータで確かめた**中間検証**で、判定は**本記録者（AI）**が行いました（`docs/population_v4.md:15-16, 68`）。決定 **D66 の 5** が「論文には使わない」と決めています（`docs/decisions.md:3754`）。
論文の評価は、学生が別の新しいデータで、AI を使わずに行います（D60、D70 の 3）。
さらに、76.7% は 1 つの木（reaper-mcp。正 38 件）に引っぱられた値で、その木を除くと 36.4%（22 件中 8 件）でした。この 36.4% も、結果を見た後に計算した事後の分析です（`docs/population_v4.md:123-125`）。

## 第 8 章 研究が今の形になるまで の答え

### 演習 8-1（taint の印を追う）

汚れの出どころは、ツールの引数 `name` と `keep` です。

| 行 | 何をしているか | 汚れの印 |
|---|---|---|
| 2 | `base` に定数 `"/srv/data"` を入れる | **付かない**（定数だけで作った値） |
| 3 | `path` を、`base` と `name` をつないで作る | **付く**（汚れた `name` を混ぜた） |
| 4 | `backup` を、`path` と `".bak"` をつないで作る | **付く**（汚れた `path` を混ぜた） |

**1.** 汚れているのは `path` と `backup`。`base` は定数だけなので汚れていません。

**2.**
- 6 行目: `os.remove(path)` に汚れた `path` が渡されるので、**届いています**（LLM の値で決まる場所のファイルを消す流れ）。
- 7 行目: `shutil.copy(path, backup)` に、汚れた `path`（コピー元）と `backup`（コピー先。ここに新しいファイルが書かれる）が渡されるので、**届いています**。

**3.** 6 行目の削除が起きるかどうかは、5 行目の `if not keep:` で決まります。`keep` はツールの引数なので、**LLM の値**が決めています。これは「発生を誰が決めるか」なので、**trig** に当たります。
（ちなみに、削除する場所 `path` を決めているのも、`name` を通じて LLM です。こちらは「値を誰が決めるか」なので **val** に当たります。）

### 演習 8-2（2 人目のラベラーの今）

**1. 仕様書の計画**
- 2 人目のラベラーを置く。ラベル付けは 4 つの次元で、次元ごとに κ を出す。**AI アシスタントは κ に含めない**（`AUTHGAP_BRIEF_v3.md:837`）。
- 受け入れの条件は、2 人目の独立したラベルがそろい、裁定の手続きが記録されていること。AI は κ に含めない（`:918`）。
- 第 0 週に 2 人目の書面での確約（氏名、20〜40 時間）を取り、予備のラベラーを確保するか、離脱したときの縮退の設計（30 ツールに縮め、指導教員による裁定の標本 20 行）を書く（`:1058`）。
- 2 人目が確保できなければ、同じ 60 ツールを 2 週間あけて再ラベルする **test-retest** で κ を代え、その置き換えを事前登録に書き、判定者間の一致に依存する主張を全部落とす（`:1066`）。

**2. 今の既定**: **判定者は学生 1 人**（**D67 の 4**、2026-09-29。`docs/decisions.md:3783-3786`）。κ に依存する主張はしない。判定の根拠を全件公開し、判定の手引きを先にコミットする。

**3. 今の状態と期限**: **保留**（**D70 の 8**、2026-10-01。`docs/decisions.md:3876-3882`。**O2** = `docs/open_questions.md:10`）。2 人目を用意できるかもしれないが、まだ分からない。決まるまでは D67 の 4 が既定。
- 用意できたら、判定の一部を独立に判定してもらう案を、判定し直しより先に検討する（件数・対象の抜き方・裁定のしかた・一致の指標 κ を決める）。
- 用意できなければ、判定し直し（2 週間以上あけて 5〜10%）をするかを決める。
- 期限: どちらも、**データを見る前（遅くとも段階 6 の抜き取りのコミットの前）**に事前登録へ書く。

**4. 期限を過ぎてから足す場合**: 判定や集計の結果を見た後に足すなら、事前登録に**逸脱**として理由とともに書き、**事後の分析**として扱う（D70 の 8、`docs/drafts/prereg_2_12_draft.md:67-68`）。

### 演習 8-3（κ を計算する）

表を、計を足して書き直します。

| | B が正 | B が誤 | 計 |
|---|---|---|---|
| **A が正** | 30 | 5 | 35 |
| **A が誤** | 5 | 10 | 15 |
| **計** | 35 | 15 | 50 |

**1.** 一致したのは、2 人とも正の 30 件と、2 人とも誤の 10 件で、40 件。40 ÷ 50 = **0.80**。

**2.** A が正と答えた割合は 35 ÷ 50 = 0.70、誤は 0.30。B も正 0.70、誤 0.30。
2 人とも正: 0.70 × 0.70 = 0.49。2 人とも誤: 0.30 × 0.30 = 0.09。合わせて **0.58**。

**3.** κ = (0.80 − 0.58) ÷ (1 − 0.58) = 0.22 ÷ 0.42 = 0.5238… ≈ **0.52**。

**4.** 「よく一致している」とは言い切れません。一致率は 80% ですが、2 人とも 70% を正と答えているので、偶然でも 58% は一致します。偶然を差し引いた κ は約 0.52 で、完全な一致（1）からはかなり離れています。一致率だけでなく、κ を添えて報告する必要があります。
（κ をどの程度なら「よい」とみなすかの目安は、この研究では決めていません。2 人目の判定者を用意できたときに、一致の指標と一緒に決めることになります。D70 の 8。）

### 演習 8-4（manifest の行を読む）

**1.** D1 について**矛**は**行 b**（注記に `contradiction:D1`）。**不**は**行 c**（注記に `contradiction_unknown:D1:net_post`）。`verdicts` ではなく注記で読みます。

**2.** 行 a と行 d は、照合の答え（`contradiction` で始まる注記）を持たないので、**矛の判定や不の中身の判定の対象にはなりません**。
- 行 a の `UNKNOWN` は、その行の効果や値を読み切れなかったという付録の印で、「不」ではありません。
- 行 d の `GAP_INJECT` は付録の判定（検査されていない LLM の値が危険な位置に入る）で、宣言とは関係ありません。`D_layer_present:kind:NET` も `contradiction` で始まらない注記です。
- なお、このツールは行 b で D1 の矛を持つので、D1 の見落としの判定の対象（D1 を明示し、D1 への矛が 1 件も無いツール）にもなりません（`docs/drafts/final_judging_guide_draft.md:443-446`）。

**3.** **数えてはいけません。** `contradiction_reason:D1:fs_write` は、行 b の矛（`contradiction:D1`）の理由の説明です。同じ 1 つの矛です。

### 確認問題 8-1

きっかけになった数字は、**trig をコードの上でたどれた（`traced`）ユニットの割合 14 / 2,231 = 0.6%**（母集団 v2 の 87 木、`evidence/scan_v2_run4`）。比べられた条件は「**20% 以上**」です。あわせて、交差行が 5 行（条件は 3 行以上）で、由来のプロジェクトが 2 つ（条件は 3 つ以上）だったことも、事前の条件を満たしませんでした。

条件は、仕様書（`AUTHGAP_BRIEF_v3.md` §3、556 行）に、**結果を見る前に**書かれていました。「traced 率が 20% 未満なら SELECT の野外評価は成立しないので、格下げする。この条項は撤回しない」。実測が 0.6% だったので、2026-09-21 に学生が「下の行は必要ない」と決め、主張を「宣言 D と実効 M の照合」に絞りました（**D36**、`docs/decisions.md:185-217`）。

### 確認問題 8-2

- 前者（`verdicts` に `UNKNOWN`、注記に `contradiction_unknown` が無い）: **「不」に数えません。** `UNKNOWN` は、その行の効果や値の確度が `resolved` でないことを表す付録の判定で、照合の答えの「不」ではありません。「不」は注記の `contradiction_unknown:<宣言>:<理由>` で読みます（`authgap/verdict.py:160-165, 168-182`）。
- 後者（`verdicts` が空、注記に `contradiction_unknown:D2:net_post`）: **D2 について「不」に数えます。** 理由は `net_post`（HTTP の POST が相手を変えるかは静的に決まらない）。`verdicts` が空でも「不」はありえます（v4 の bugasura の `bugasura_update_project` の行がこの形）。

### 確認問題 8-3

D71 の理由 1 は、前身が「無改変の Pysa の上に作り、**pyre の環境が立たず**、**SDK の stub の境界で taint が切れて**成立しなかった」ことです（`docs/decisions.md:3892-3894`）。

AuthGap の避け方:
- **環境が立たない** → 解析器は標準ライブラリの `ast` だけでソースコードを読み、ライブラリをインストールせず、型の環境も作らない（`AUTHGAP_BRIEF_v3.md:36`、`README.md:9`）。解析を**ツールの関数の中から**始めるので、フレームワークの壁を越える必要も無い。
- **stub の境界で汚れの印が切れる** → 汚れの出どころ（値の主体が LLM であること）を**ツールの引数**に置く。ツールの関数の中から始めるので、SDK の stub を越える必要が無い（`AUTHGAP_BRIEF_v3.md:65`）。

### 確認問題 8-4

- **示せること**: 同じ判定者が、同じ手引きで、時間をあけても**同じ結論に着くか**（1 人の中での一貫性）。
- **示せないこと**: **別の人が**判定しても同じ結論になるか（判定者の間での一致）。これは、2 人目の判定者が独立に判定し、κ などで一致を測らないと示せません。

手順書も、判定し直しは「2 人目の判定者の代わりにはならないが、『同じ人が同じ手引きで同じ結論に着くか』は示せる」と書いています。また、判定し直しで食い違った件は、元の判定を直さず、食い違ったことを報告します（`docs/final_evaluation_procedure.md:1293-1295`）。
なお、判定し直しをするかどうかと、その量（5〜10% か 10% か）は、今は保留・未決です（D70 の 8）。
