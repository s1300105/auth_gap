### H-3.1 第 14 節の見出しと 14.1 基本（手引き L232-236）

> 【原文 L232-236】
> ## 14. 到達するかの決め方
>
> ### 14.1 基本
>
> **「そのツールが呼ばれたとき、その効果が起きる実行の道が 1 つでもあるか」**。毎回起きる必要はない。

**一言で言うと**: 「到達するか」は、**そのツールが呼ばれたときに、その効果が起きる道が 1 つでもあるか**で決めます。100 回に 1 回でも、特定の引数のときだけでも、道があれば「到達する」です。

**ことばの確認**:

- **到達**: 効果の行が、ツールの呼び出しをきっかけに、実行時に実際に実行されうること。判定表の `reachable` 欄に `はい` / `いいえ` / `決められない` で書きます（`docs/drafts/final_judging_guide_draft.md:175`）。
- **効果**: ファイルの書き込み・削除、DB の変更、HTTP の送信、プロセスの起動など、解析器が kind（`FS_WRITE` など）で分類した動作。組の 4 つ目の要素の kind が、その効果の種類です。
- **実行の道**: プログラムを実際に動かしたときに通りうる文の並び。解析器の**道筋**（`witness_chain`。解析器が静的にたどった関数の列）とは別のものです。道筋は地図で、実行の道は本当に通れる道です（[第 49 章 49.1 節](ch49.md#s49-2)）。
- **ツールが呼ばれたとき**: クライアントが `tools/call` でそのツールを呼んだとき。11.2 節では「**ツールの呼び出しによって**実行時に実際に起きうるか」と書かれています（同 `:45`）。

**1 文ずつ読む**:

1. 「## 14. 到達するかの決め方」: 第 14 節は、11.2 節の 1 つ目の問い（到達するか）の答え方の節です。手順 E（同 `:148-150`）は「第 14 節の規則で決める」とだけ書いているので、手順 E の中身はこの節に全部あります。
2. 「### 14.1 基本」: 以下の 14.2〜14.5 は、すべてこの基本の問いの当てはめです。迷ったら、この 1 文に戻ります。
3. 「**『そのツールが呼ばれたとき、その効果が起きる実行の道が 1 つでもあるか』**」: 問いの形は「あるか / ないか」です。「どれくらい起きるか」（頻度）や「起きそうか」（確率）は問いません。「1 つでも」なので、道を 1 つ見つければ「はい」です。逆に「いいえ」と言うには、**どの道も無い**ことを示す必要があります。
4. 「毎回起きる必要はない。」: 3 の言い直しです。どんなときに起きるかは「到達するか」の答えを変えず、14.3 の条件の種類の欄に分けて記録します。

**なぜこう決めたのか**:

- 根拠は D68 の 1 の理由です。「クライアントは `readOnlyHint: true` を見て呼び出しごとの確認を省く（…結論 4）。確認を省いたどれか 1 回で起きるなら宣言は守られていない」（`docs/decisions.md:3800-3801`）。結論 4 は「クライアントは、readOnlyHint を『確認なしで実行してよい』の印として使っている」です（`docs/incidental_writes_practice.md:29-31`）。
- もう 1 つは原理 3-a（能力として読む）です。「モデルが値を選べるなら、その引数が取りうる値の全体をツールが『できること』とみなす」（`docs/contradiction_principles.md:77-79`）。手引きはこれを「能力の上界」の読み方と呼びます（`docs/drafts/final_judging_guide_draft.md:253`）。「取りうる呼び出しのどれかで届くか」と問うのは、この読み方を到達に当てたものです。
- 「毎回起きるものだけ」にすると、引数しだいの書き込みなどが全部「到達しない」になり、人が本当にある違反を消す向き（誤 clear）の誤りになります。これは本書の読みで、同じ説明が[第 49 章](ch49.md#s49-2)の「なぜ『1 つでも』なのか」にあります。

**例で確かめる**:

（作った例）3 つのツールを並べます。どれも `readOnlyHint=True` と宣言しているとします。

```python
HISTORY = "/var/tmp/weather_history.txt"

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def weather(city: str) -> str:
    with open(HISTORY, "a") as fh:          # (a) 毎回
        fh.write(city + "\n")
    return _fetch(city)

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def forecast(city: str, keep: bool = False) -> str:
    text = _fetch(city)
    if keep:
        with open(HISTORY, "a") as fh:      # (b) keep=True のときだけ
            fh.write(text)
    return text

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def alerts(city: str) -> str:
    if False:
        with open(HISTORY, "a") as fh:      # (c) 決して通らない
            fh.write(city)
    return _fetch_alerts(city)
```

- (a) は毎回届くので「到達する」。14.1 の問いの「1 つでもあるか」に、すべての呼び出しが当たります。
- (b) はモデルが `keep=True` を渡した呼び出しで届きます。毎回ではありませんが、道が 1 つあるので「到達する」。条件は 14.3 で `引数` と記録します。
- (c) は `if False:` の中で、どの呼び出しでも通りません。道が 1 つも無いので「到達しない」。14.2 の「定数で閉じた枝」です（誤、E6）。

**迷いやすいところ**:

- **「起きそうにない」は「到達しない」ではありません。** モデルがその引数をめったに使わなさそうでも、使えるなら到達します。作者の意図や README の説明も問いません（[第 49 章](ch49.md#s49-2)の「よくある誤解」）。
- **解析器が道筋を出したことは、到達の証拠ではありません。** 道筋は、サーバの状態（変数に何が入っているか）を仮定せずに読んだ地図です。第 49 章の試験では、`if DEBUG:`（`DEBUG = False`）の中の書き込みにも、凍結版の解析器は矛を出しました（[第 49 章](ch49.md#s49-4)、`docs/textbook/ch49.md:768-776`）。
- **到達するだけでは正になりません。** 2 つ目の問い（宣言に反するか）にも「はい」が要ります（`docs/drafts/final_judging_guide_draft.md:43`）。
- **「ツールが呼ばれたとき」の外で起きるものは、この問いの対象ではない**と本書は読みます。たとえば、サーバの起動時に始めた見張りのスレッドが 1 分ごとにログを書くのは、どのツールを呼ばなくても起きます。ただし、ツールが原因になって、効果がツールの戻った**後**に起きる形は決まっていません（下の【穴 H-3-1】）。

**承認の前に自分に問うこと**:

1. 「1 回でも起きうるなら到達する」に、自分は納得できるか。クライアントが確認を省くこと（`docs/incidental_writes_practice.md:29-31`）を理由として受け入れるか。
2. 「到達しない」と書くには「どの道も無い」ことを示す必要がある、という非対称を、判定の時間の見積もりに入れているか。
3. 頻度や確率を、判定ではなく `condition` 欄にだけ書く、という分け方を守れそうか。

**この節で手引きが決めていないこと**:

【穴 H-3-1】**効果がツールの呼び出しの「後」に起きる形を、「ツールの呼び出しによって起きる」に入れるか。**

- 何が決まっていないか: 14.1 は「ツールが呼ばれたとき、その効果が起きる実行の道」、11.2 は「ツールの呼び出しによって実行時に実際に起きうるか」（`:45`）と書きます。ツールが**きっかけ**を作り、効果そのものは呼び出しが返った後に、別のスレッド・別のタスク・プロセスの終了時に起きる形を、どちらに入れるかは書かれていません。
- 困る事例（作った例）:

  ```python
  # (i) ツールがスレッドを起こし、戻った後でスレッドが書く
  @mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
  def watch(path: str) -> str:
      threading.Thread(target=_watch_loop, args=(path,), daemon=True).start()
      return "watching"

  def _watch_loop(path):
      while True:
          with open(WATCH_LOG, "a") as fh:     # ← 呼び出しが返った後に、何度も
              fh.write(_snapshot(path))
          time.sleep(60)

  # (ii) 起動時に作ったスレッドが、ツールの積んだものを書く
  _q = queue.Queue()
  def _flusher():
      while True:
          item = _q.get()
          with open(AUDIT_LOG, "a") as fh:     # ← ツールが積んだときだけ書く
              fh.write(item)
  threading.Thread(target=_flusher, daemon=True).start()   # 読み込み時に起動

  @mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
  def lookup(key: str) -> str:
      _q.put(key + "\n")
      return _STORE.get(key, "")

  # (iii) ツールが状態を変え、プロセスの終了時に書く
  _dirty = False
  @atexit.register
  def _save():
      if _dirty:
          with open(CACHE_FILE, "w") as fh:
              json.dump(_CACHE, fh)

  @mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
  def fetch(url: str) -> str:
      global _dirty
      _CACHE[url] = _get(url)
      _dirty = True
      return _CACHE[url]
  ```

  (i) の書き込みは `watch` を呼ばなければ起きません。(ii) は `lookup` が積まなければ書きません。(iii) は `fetch` が `_dirty` を立てなければ書きません。どれも「ツールが原因」ですが、効果はツールの呼び出しの最中には起きません。
- 考えられる選択肢:
  1. 「ツールの呼び出しが原因で、いつか必ず（あるいは起きうる形で）起きる」なら到達する。条件の種類は書き分ける（たとえば (iii) は終了時なので別の印）。
  2. 「呼び出しの最中に、呼び出しの中の実行の道で起きる」ものだけを到達とする。(i)〜(iii) は到達しない（誤なら E6 か E9）。
  3. 手引きで決まらない事例として、出会ったら第 22 節（`:733-736`）で不明にする。
- 関係する決定: D68 の 1（`docs/decisions.md:3796-3801`）。なお凍結版の解析器が (i)〜(iii) の道筋を出すかは、本書は確かめていません。見落としの判定（18.2）で人が見つける形として出会うことが多いと考えられます（本書の読み）。

### H-3.2 14.2 到達しない形（誤にする形）（手引き L238-248）

> 【原文 L238-248】
> ### 14.2 到達しない形（誤にする形）
>
> | 形 | 見分け方 | 誤の原因 |
> |---|---|---|
> | **起動時の初期化（lifespan・import 時）** | 14.4 | E1 |
> | 呼び出し先の取り違え | 呼んでいるのは別の関数・組み込みのメソッド（13 手順 C） | E3 / E4 |
> | 死んだコード | 効果のある関数がツールの道筋からは呼ばれていない（別の入口 = CLI・テスト・スクリプトからだけ呼ばれる） | E6 |
> | 定数で閉じた枝 | `if False:`、`if DEBUG:`（`DEBUG = False` が定数で、どこでも書き換えない）の中 | E6 |
> | 必ず先に抜ける | 効果の前に必ず `return` / `raise` する | E6 |
>
> **「別の入口からしか呼ばれない」ことは、木の中を検索して確かめる**（関数名で grep し、呼び出し元をすべて見る）。

**一言で言うと**: 解析器が道筋を出していても、実際には届かない形が 5 つあります。起動時の初期化（E1）、呼び出し先の取り違え（E3 / E4）、死んだコード・定数で閉じた枝・必ず先に抜ける（どれも E6）。「別の入口からしか呼ばれない」は、木の中を grep して確かめます。

**ことばの確認**:

- **誤の原因**（`error_class`）: 誤にしたときに書く記号。第 17 節の E1〜E9 です（`docs/drafts/final_judging_guide_draft.md:451-468`）。この表に出るのは E1・E3・E4・E6 です。
- **起動時の初期化**: サーバがツールの受付を始める前に 1 回だけ済ませる準備。lifespan（サーバを作るときに `lifespan=` で渡す関数）や、モジュールの読み込み（import）のときに走るもの（[第 3 章 3.9 節](ch03.md#s3-10)）。
- **別の入口**: ツールの呼び出し以外で、プログラムが動き始める場所。CLI（コマンドで動かす管理用の入口）・テスト・スクリプトなど。
- **死んだコード**（この研究での意味）: 効果のある関数が、ツールの道筋からは呼ばれていない形（`:244`）。
- **定数で閉じた枝**: `if` の条件が、プログラムのどこでも書き換えられない定数で決まり、決して真にならない枝（`:245`）。
- **grep**: 文字列でファイルを検索するコマンド。`grep -rn "名前" <木>` で、木の中の全部のファイルから行番号つきで探します。

**1 文ずつ読む**:

1. 見出し「到達しない形（誤にする形）」: この表のどれかに当たると確かめた位置は「到達しない」です。組の全部の位置が到達しない（か反しない）なら、組は誤です（手順 G、`:161`）。
2. 表の見出し行「形 / 見分け方 / 誤の原因」: 1 行が 1 つの形です。2 列目が手がかり、3 列目が `error_class` に書く記号です。
3. 1 行目「**起動時の初期化（lifespan・import 時）** / 14.4 / E1」: 太字なのは、v4 で一番多かった誤の類だからと読めます（本書の読み。v4 の抜き取りの誤 14 件のうち 9 件がこの類だった。`docs/population_v4.md:93,99`、`docs/open_questions.md:1190`。v4 の数字は論文に使わない）。見分け方は 14.4 節（この分冊の [H-3.6〜H-3.9](#ah-3-6)）。lifespan と import 時だけが E1 で、`main()` の中の初期化は E1 になりません（14.4 の表の 1 行目）。
4. 2 行目「呼び出し先の取り違え / 呼んでいるのは別の関数・組み込みのメソッド（13 手順 C）/ E3 / E4」: 解析器が名前で当てた関数が、実際に呼ばれる関数と違う形です。手順 C（`:126-132`）で効果の行を開いたときに気づくことが多い形です。E3 は名前だけの解決の誤り、E4 は受け手の型の読み違いで**動作の種類（kind）まで違う**ものです（`:460-461`）。
5. 3 行目「死んだコード / …別の入口 = CLI・テスト・スクリプトからだけ呼ばれる / E6」: 効果の関数は木の中にあるが、ツールからたどっても着かない形です。
6. 4 行目「定数で閉じた枝 / `if False:`、`if DEBUG:`（`DEBUG = False` が定数で、どこでも書き換えない）の中 / E6」: 括弧の中の「どこでも書き換えない」が条件です。書き換える行があれば、定数ではありません。
7. 5 行目「必ず先に抜ける / 効果の前に必ず `return` / `raise` する / E6」: 「必ず」は、エラーが起きた場合も含めて、どの道でも抜けるという意味です。
8. 表の下の文「**『別の入口からしか呼ばれない』ことは、木の中を検索して確かめる**（関数名で grep し、呼び出し元をすべて見る）」: 死んだコードと言うには、呼び出し元を**すべて**見る必要があります。1 か所でもツールの道筋から呼んでいれば、死んだコードではありません。

**なぜこう決めたのか**:

- 「到達しない」と決めると、解析器が報告した違反を人が「無い」と言うことになります。間違っていれば人が誤 clear を作ります。だから、形を 5 つに限り、それぞれに確かめ方を付けている、と本書は読みます（理由は手引きに書かれていない。本書の読み）。
- E1 を E6 から分けるのは、D67 の 2 が「lifespan の形の誤りは設計の選択による限界（誤警報の向き）として件数を報告する。判定の手引きの誤の原因の欄に、この類を設ける」と決めたからです（`docs/decisions.md:3777-3778`）。E6 にまとめると、その件数を数えられません。
- 「別の入口」を grep で確かめるのは、第 22 節・第 19 節と同じく、根拠を `evidence` に残して第三者が同じ結論に着けるようにするためです（`:197-198`、D67 の 4 は `docs/decisions.md:3783-3786`）。

**例で確かめる**:

（作った例）5 つの形を、「到達しない形」と「よく似ているが到達する形」の対で並べます。

**形 1 — 起動時の初期化**は 14.4 で詳しく扱います（[H-3.7](#ah-3-7)）。ここでは対だけです。

```python
# 到達しない（E1）: lifespan が受付の前に必ず済ませる
@asynccontextmanager
async def app_lifespan(server):
    _init()
    yield {}
mcp = FastMCP("memo", lifespan=app_lifespan)

# 到達する（起動の方法）: main() の中だけで済ませる
def main():
```

> ### 14.3 条件つきで到達する形（D68 の 1）

**ことばの確認**:

- **条件つきの到達**: 効果の前に `if` などがあり、ある場合にだけ効果に届くこと。

- **能力の上界**: 「最大でどこまでできるか」で読むこと。原理 3-a（`docs/contradiction_principles.md:77-79`）の言い換えで、§0 の「M は上界」と同じ読み方とされています。

**1 文ずつ読む**:

1. 見出し「14.3 条件つきで到達する形（D68 の 1）」: この節の規則の出どころは D68 の 1 です（`docs/decisions.md:3796-3804`）。

### H-3.4 14.3 の条件の種類の表（手引き L255-264）

> 【原文 L255-264】
> | `condition_type` | 条件の例 | 扱い | (B) に数えるか | (C) に数えるか |
> |---|---|---|---|---|
> | `なし` | 毎回届く | 到達する | 数える | 数える |
> | `引数` | モデルが渡す引数の値による（`if output_file:`、`if mode == "save":`） | 到達する（モデルが選べる） | 数える | 数えない |
> | `初回` | 初回だけ・キャッシュが無いときだけ（ツールの道筋の中で `if not os.path.exists(d): os.makedirs(d)`） | 到達する（最初の呼び出しで起きる） | 数える | 数えない |
> | `失敗・期限切れ` | トークンの更新、再試行、エラー時の後始末 | 到達する | 数える | 数えない |
> | `外部の状態` | ファイルが無いとき、相手が特定の応答を返したとき | 到達する | 数える | 数えない |
> | `運用者の設定` | 環境変数・設定ファイル・起動の引数で有効になる | 到達する（その設定で起動すれば届く）。設定の名前を `condition` に書く | **数えない** | 数えない |
> | `起動の方法` | 初期化が `main()` の中だけにあり、`main()` を通らない起動（`fastmcp run file.py:mcp` など）で届く（14.4） | 到達する | **数えない** | 数えない |
> | — | 条件が何で決まるか読み切れない | 決められない → 不明 | — | — |

**一言で言うと**: 条件の種類は 7 つです。最後の行（読み切れない）を除いて、どれも「到達する」です。違うのは併記の数 (B)・(C) に数えるかどうかだけで、(B) は運用者が決める 2 つ（運用者の設定・起動の方法）だけを数えず、(C) は `なし` だけを数えます。

**ことばの確認**:

- **(A)・(B)・(C)**: 条件つきの正をどこまで正として数えるかの 3 つの読み方です。(A) は主の数で、条件を問いません（`:266`）。(B) は「運用者が決める条件（運用者の設定・起動の方法）でしか届かないもの」を除いた数、(C) は「条件なしで届くものだけ」の数です（`docs/decisions.md:3798-3799`）。
- **数える / 数えない**: 表の (B)(C) の列は、「その読み方で、その正を正として数えるか」です。数えない正は、精度を計算し直すとき**誤に置き換えます**（`docs/decisions.md:3804`、`docs/final_evaluation_procedure.md:1414`）。手引きの 14.3 にはこの「誤に置き換える」は書かれていません（下の「迷いやすいところ」）。
- **運用者**: サーバを自分のマシンで起動する人。環境変数・設定ファイル・起動の引数・起動の方法を決めます。モデルでも、ツールの作者でもありません（[第 49 章 49.3 節](ch49.md#s49-4)の「言葉の整理」）。
- **モデル**: ツールを呼ぶ AI。引数の値を決めます。
- **大文字と小文字**: 大文字の (A)(B)(C) は「到達の読み方」、小文字の (a)(b)(c) は木の割合の分母です（第 39・46 章）。混ぜないでください（[第 49 章](ch49.md#s49-4)）。

**1 文ずつ読む**（表の 1 行ずつ。各行に作った例を付けます。どれも `readOnlyHint=True` を宣言し、効果は D1 に反する書き込みだとします。だから「到達する」なら正です）:

#### 表の見出し行

「`condition_type` / 条件の例 / 扱い / (B) に数えるか / (C) に数えるか」: 1 行が 1 つの種類です。「扱い」は到達の答えで、「(B)(C) に数えるか」は、その種類の正を併記の数に入れるかです。

#### 行 1: `なし` — 毎回届く → 到達する / (B) 数える / (C) 数える

（作った例）

```python
@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def read_note(name: str) -> str:
    with open(ACCESS_LOG, "a") as fh:      # 前に if が無い
        fh.write(name + "\n")
    with open(os.path.join(NOTES, name)) as fh:
        return fh.read()
```

- 効果の前に条件が無く、どの呼び出しでも届きます。`condition_type` は `なし`、`condition` も `なし` です。
- (A)(B)(C) のすべてで正に数えます。
- 注意: 引数の値を**使う**だけで、`if` で分かれていなければ `なし` です。たとえば `open(path, "w")` の `path` がモデルの引数でも、毎回その行に届くなら条件は `なし` です（書き先がモデルしだいかどうかは、第 15 節の 2 つ目の問いの話です）。

#### 行 2: `引数` — モデルが渡す引数の値による → 到達する（モデルが選べる）/ (B) 数える / (C) 数えない

（作った例）

```python
@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def report(month: str, mode: str = "show") -> str:
    text = _build(month)
    if mode == "save":
        with open(f"report_{month}.md", "w") as fh:   # mode="save" のときだけ
            fh.write(text)
    return text
```

- `mode` はモデルが決める引数です。`"save"` を渡せば届くので到達します。`condition` は「引数 mode に "save" を渡したとき」。
- 扱いの括弧「モデルが選べる」が理由です。原理 3-a で、モデルが選べる値は取りうる値の全体で読みます。
- (A) と (B) では正に数え、(C) では数えません（誤に置き換えます）。
- 手引きの例は `if output_file:` と `if mode == "save":` の 2 つです。v4 の M18（mcp-aws の `generate_cost_report_wrapper`。引数 `output_file` を渡したときだけ届く）が、手引き 20.2 で `引数` の例として挙がっています（`:675`）。

#### 行 3: `初回` — 初回だけ・キャッシュが無いときだけ → 到達する（最初の呼び出しで起きる）/ (B) 数える / (C) 数えない

（作った例）

```python
CACHE_DIR = os.path.expanduser("~/.myapp/cache")

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def lookup(word: str) -> str:
    if not os.path.exists(CACHE_DIR):
        os.makedirs(CACHE_DIR)            # 最初の呼び出しだけ
    path = os.path.join(CACHE_DIR, word)
    if not os.path.exists(path):
        with open(path, "w") as fh:       # その語が初めてのときだけ
            fh.write(_define(word))
    with open(path) as fh:
        return fh.read()
```

- `os.makedirs` はディレクトリがまだ無い最初の呼び出しで起きます。`condition` は「~/.myapp/cache がまだ無いとき（最初の呼び出し）」。
- 2 つ目の `open(path, "w")` は、その語が初めて引かれたときに起きます。語はモデルが決めるので、`引数;初回` と書く読み方もあります（[付録 D-8](appendix-d-8.md#ad-8-5) の演習 49-3 の答えは、モデルが選ぶ場所での「初回」を `引数;初回` と書けるとしています）。どちらでも (B) に数え、(C) に数えないことは変わりません。
- 手引きの例「ツールの道筋の中で `if not os.path.exists(d): os.makedirs(d)`」の「ツールの道筋の中で」が大事です。同じ初期化が lifespan の中にあれば、14.4 の規則で到達しません。

#### 行 4: `失敗・期限切れ` — トークンの更新、再試行、エラー時の後始末 → 到達する / (B) 数える / (C) 数えない

（作った例）

```python
def _token() -> str:
    tok = json.load(open(TOKEN_FILE))
    if tok["expires_at"] < time.time():
        tok = _refresh(tok)                       # 期限切れのとき
        with open(TOKEN_FILE, "w") as fh:         # ← 保存（効果）
            json.dump(tok, fh)
    return tok["access_token"]

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def list_issues(project: str) -> str:
    try:
        return _get(f"/projects/{project}/issues", token=_token())
    except TimeoutError:
        with open(ERROR_LOG, "a") as fh:          # ← 失敗したときの記録（効果）
            fh.write(f"timeout {project}\n")
        raise
```

- トークンの保存は、保存したトークンの期限が切れたときに届きます。`condition` は「保存したトークンの期限が切れたとき」。
- エラーの記録は、問い合わせが時間切れになったときに届きます。`condition` は「問い合わせが時間切れになったとき」。
- どちらもふつうに使っていれば起きうることで、運用者の選択ではないので (B) に数え、条件があるので (C) に数えません。
- v4 の R04（mcp-atlassian。OAuth のトークンの更新と保存が深さ 7）は、手引き 20.2 で条件の種類 `失敗・期限切れ` の例として挙がっています（`:684`）。

#### 行 5: `外部の状態` — ファイルが無いとき、相手が特定の応答を返したとき → 到達する / (B) 数える / (C) 数えない

（作った例）

```python
@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def get_item(item_id: str) -> str:
    resp = httpx.get(f"{API}/items/{item_id}")
    local = os.path.join(MIRROR, item_id + ".json")
    if resp.status_code == 404 and os.path.exists(local):
        os.remove(local)                 # 相手が「もう無い」と返したら、手元の写しを消す
    return resp.text
```

- 相手のサーバが 404 を返し、手元に写しがあるときだけ届きます。どちらもツールの外のもの（相手のサーバ、手元のファイル）で決まります。`condition` は「相手のサーバが 404 を返し、手元に写しがあるとき」。
- (B) に数え、(C) に数えません。
- 手引きの例「ファイルが無いとき」は、行 3（初回）の「キャッシュが無いときだけ」と似ています。分け方は手引きに書かれていません（下の【穴 H-3-7】）。

#### 行 6: `運用者の設定` — 環境変数・設定ファイル・起動の引数で有効になる → 到達する（その設定で起動すれば届く）。設定の名前を `condition` に書く / (B) **数えない** / (C) 数えない

（作った例）3 つの書き方です。

```python
# (i) 環境変数
@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def find(q: str) -> str:
    if os.environ.get("FIND_AUDIT") == "1":
        with open(AUDIT, "a") as fh:
            fh.write(q + "\n")
    return _find(q)

# (ii) 設定ファイル（運用者が書く TOML）
SETTINGS = tomllib.load(open(os.path.expanduser("~/.findtool.toml"), "rb"))
@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def find2(q: str) -> str:
    if SETTINGS.get("keep_history"):
        with open(HISTORY, "a") as fh:
            fh.write(q + "\n")
    return _find(q)

# (iii) 起動の引数（main() で読む）
LOG_PATH = None
def main():
    global LOG_PATH
    ap = argparse.ArgumentParser(); ap.add_argument("--log-file")
    LOG_PATH = ap.parse_args().log_file
    mcp.run()

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def find3(q: str) -> str:
    if LOG_PATH:
        with open(LOG_PATH, "a") as fh:
            fh.write(q + "\n")
    return _find(q)
```

- どれも、運用者がそう設定して起動すれば届くので「到達する」です。`condition` には設定の名前を書きます: (i)「環境変数 FIND_AUDIT=1 で起動したとき」、(ii)「設定ファイル ~/.findtool.toml の keep_history が真のとき」、(iii)「起動の引数 --log-file を渡したとき」。
- (A) では正に数えます。(B) と (C) では数えません（誤に置き換えます）。
- (iii) は `main()` が書き換えるので、`LOG_PATH = None` は 14.2 の「定数」ではありません（「どこでも書き換えない」に当たらない）。

#### 行 7: `起動の方法` — 初期化が `main()` の中だけにあり、`main()` を通らない起動（`fastmcp run file.py:mcp` など）で届く（14.4）→ 到達する / (B) **数えない** / (C) 数えない

（作った例）

```python
mcp = FastMCP("memo")
_store = None

def _init():
    global _store
    os.makedirs(DATA_DIR, exist_ok=True)      # ← 効果
    _store = {}

def _ensure():
    if _store is None:
        _init()
    return _store

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def list_memos() -> str:
    return str(sorted(_ensure()))

def main():
    _init()
    mcp.run()

if __name__ == "__main__":
    main()
```

- `python server.py` で起動すれば `main()` が先に `_init()` を済ませます。けれども `fastmcp run server.py:mcp`（公式 SDK なら `mcp run server.py:mcp`）で起動すると `main()` を通らず、最初の `list_memos` の呼び出しで `_init()` に届きます（[第 3 章 3.7 節](ch03.md#s3-8)。SDK 1.30.0 で本記録者が動かして確かめた順番がある）。
- `condition` は「main() を通らない起動（fastmcp run server.py:mcp など）での最初の呼び出し」。
- どの起動の方法を使うかは運用者が決めるので、(B) に数えません。(C) にも数えません。
- 第 49 章の試験では、この形にも凍結版の解析器は lifespan の形と同じ矛を出しました（`docs/textbook/ch49.md:1327-1331`）。

#### 行 8: `—` — 条件が何で決まるか読み切れない → 決められない → 不明 / (B) — / (C) —

（作った例）

```python
backend = _load_plugin(os.environ.get("NOTE_BACKEND", "default"))   # 名前でプラグインを読み込む

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def notes(q: str) -> str:
    if backend.wants_persist(q):          # ← 何で決まるかは、読み込まれたプラグインしだい
        backend.persist(q)
    return backend.search(q)
```

- `wants_persist` の中身が木の外のプラグイン（実行時に名前で読み込む）にあり、20〜30 分調べても決められなければ、`reachable` は `決められない`、判定は不明です（第 19 節 `:573`、`:580`）。`unknown_reason` に「条件 wants_persist の中身が、実行時に読み込むプラグインで決まる」などと書きます。
- この行は種類ではないので `condition_type` は書きません。(B)(C) の列が `—` なのは、不明は正でも誤でもないからです。

**なぜこう決めたのか**:

- 7 つの種類そのものは D68 の 1 が決めています（`docs/decisions.md:3796-3798`）。
- (B) が運用者の 2 つだけを除くのは、引数（モデルが決める）や初回・失敗・外部の状態（ふつうに使っていれば起きる）と違い、運用者の設定と起動の方法は「サーバを動かす人の選択」で決まるからです。手引きと D68 にはこの理由は書かれていません。本書の読み: 「運用者がそうしなければ起きない書き込みは、宣言の責任の外では」という読み手の問いに、事前に決めた数で答えるため（[第 49 章 49.3 節](ch49.md#s49-4)の「なぜそう決めたのか」の 3 つ目、[第 46 章](ch46.md)）。
- (C) は「何も特別なことが起きなくても、毎回起きるもの」だけの数で、一番厳しい読み方です。

**例で確かめる**（7 つをまとめて (A)(B)(C) を数える）:

上の行 1〜7 の作った例で、各 1 組が正だったとします（行 8 は不明）。判定した 8 組の件数の精度は次のとおりです（件数の練習。最終評価の主指標は木の単位です。`docs/final_evaluation_procedure.md:1358-1378`）。

| 読み方 | 正として数える | 誤に置き換える | 正 | 誤 | 不明 | 精度 = 正 / (正 + 誤) |
|---|---|---|---|---|---|---|
| (A) | 行 1〜7 の 7 組 | なし | 7 | 0 | 1 | 7 / 7 |
| (B) | 行 1〜5 の 5 組 | 行 6・7 | 5 | 2 | 1 | 5 / 7 |
| (C) | 行 1 の 1 組 | 行 2〜7 | 1 | 6 | 1 | 1 / 7 |

表の読み方: 2 行目は「(B) の読み方では、運用者の設定と起動の方法でしか届かない 2 組を誤に置き換えるので、正 5・誤 2」と読みます。**分母（正 + 誤 = 7）は 3 つの読み方で変わりません。** 正を数から除くと (B) が 5 / 5 になり、精度が高く見えてしまいます。不明の 1 組は、どの読み方でも不明のままです。

**迷いやすいところ**:

- **(B)(C) の「数えない」は「誤に置き換える」です。** これは D68 の 1（`docs/decisions.md:3804`）と手順書（`docs/final_evaluation_procedure.md:1414`）に書かれていて、手引きの 14.3 の本文には書かれていません。判定者が数え方を決めるわけではない（集計は段階 8）ので判定には影響しませんが、承認のときに知っておくとよい点です。
- **`なし` と `引数` の境目**: 引数を「使う」だけなら `なし`、引数の値で「分かれる」なら `引数` です。ただし、既定値で分かれる形は決まっていません（【穴 H-3-4】）。
- **`初回` と `外部の状態` の境目**: 手引きの例が重なります（「キャッシュが無いときだけ」と「ファイルが無いとき」）。どちらも (B) に数え (C) に数えないので、数は変わりません（【穴 H-3-7】）。
- **`運用者の設定` と `定数`**: 環境変数・設定ファイル・起動の引数で決まるなら運用者の設定です。コードのどこでも書き換えない定数なら、14.2 の定数で閉じた枝で、到達しません。
- **`起動の方法` は 14.4 の `main()` の形のためだけの種類**として書かれています（`:263`）。ほかの「起動のしかたで変わる」条件（HTTP で起動したときだけ、など）は、起動の引数で決まるなら `運用者の設定` に当たると読めます（本書の読み）。

**承認の前に自分に問うこと**:

1. (B) が「運用者の設定」と「起動の方法」の 2 つだけを除く線引きに納得できるか。「失敗・期限切れ」や「外部の状態」も (B) から除くべきだと感じないか。
2. (C) を「`なし` だけ」とする厳しさは、読み手の問い（「毎回起きるものだけならどうか」）に答える数として適切か。
3. 7 つの種類のどれにも当てはまらない条件に出会ったとき、自分はどうするか（下の【穴 H-3-8】〜【穴 H-3-11】）。
4. 「行は毎回実行されるが、環境が変わるのは一部の呼び出しだけ」の形（【穴 H-3-6】）を、自分は `なし` と書くか `初回` と書くか。

**この節で手引きが決めていないこと**:

【穴 H-3-4】**引数の既定値で効果が起きる形は `なし` か `引数` か。**（[第 49 章](ch49.md#s49-4)の境目 1、`docs/textbook/ch49.md:1065-1079` と同じ）

- 何が決まっていないか: `引数` の行は「モデルが渡す引数の値による」です。モデルが何も渡さなくても既定値で効果が起きる形は、引数で分かれてはいますが、モデルが何もしなくても起きます。
- 困る事例（作った例）: `def export(q: str, save: bool = True): if save: _write(q)`。モデルが `save` を省けば毎回書きます。
- 考えられる選択肢: (1) `なし`（既定値で起きるので (C) に数える）、(2) `引数`（引数で分かれるので (C) に数えない）、(3) `引数` と書き、`condition` に「既定値で起きる」と書いて、集計で別に数える。
- 関係する決定: D68 の 1。

【穴 H-3-5】**おかしな入力や途中の失敗で「早く抜ける」だけの形は、条件に数えるか。**（第 49 章の境目 2、`docs/textbook/ch49.md:1081-1097`）

- 何が決まっていないか: 効果の前に `if not q: return …` や、失敗すれば例外で抜ける呼び出しがある形です。ふつうに成功する呼び出しなら毎回届きます。
- 困る事例（作った例）:

  ```python
  @mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
  def ask(question: str) -> str:
      if not question.strip():
          return "empty"                 # 空なら抜ける
      answer = _call_llm(question)       # 失敗すれば例外で抜ける
      _append_log(question, answer)      # ← 効果
      return answer
  ```

- 考えられる選択肢: (1) `なし`（届くための特別な条件ではない）、(2) `引数;外部の状態` など、抜けない側に進む条件を全部書く、(3) 入力の検査は無視し、外の失敗だけを書く。(1) と (2) で (C) の数が変わります。
- 関係する決定: D68 の 1。v4 の M06（wikimind）の記録は「質問が空でなく LLM 呼び出しが例外にならなければ毎回到達する」と書いています（[第 49 章](ch49.md#s49-4)）。

【穴 H-3-6】**行そのものは毎回実行されるが、環境が実際に変わるのは一部の呼び出しだけの形は、`なし` か、変わる場合の条件か。**

- 何が決まっていないか: 14.1 の問いは「その効果が起きる実行の道」です。「効果が起きる」を「その行が実行される」と読むか、「環境が実際に変わる」と読むかが書かれていません。
- 困る事例（作った例）:

  ```python
  @mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
  def stats(table: str) -> str:
      os.makedirs(WORK_DIR, exist_ok=True)                              # 毎回実行。作るのは初回だけ
      conn = sqlite3.connect(DB)
      conn.execute("CREATE TABLE IF NOT EXISTS hits (t TEXT)")          # 毎回実行。作るのは初回だけ
      Path(LOCK).unlink(missing_ok=True)                                # 毎回実行。消すのは残っていたときだけ
      return str(conn.execute(f"SELECT count(*) FROM {table}").fetchone())
  ```

  3 行とも、`if` は無く毎回実行されます。けれども、ディレクトリや表が実際に作られるのは最初の 1 回、ファイルが実際に消えるのは前の呼び出しが残したときだけです。
- 考えられる選択肢: (1) 行が毎回実行されるので `なし`（[第 49 章 49.5 節](ch49.md#s49-6)は `unlink(missing_ok=True)` をこう読んでいる。`docs/textbook/ch49.md:1804`）、(2) 環境が変わる場合で書く（`exist_ok` と `IF NOT EXISTS` は `初回`、`missing_ok` は `外部の状態`）、(3) 宣言の問い（第 15 節）で「その呼び出しで環境が変わったか」を見るので、到達は (1)、条件は (2) と分ける。(1) と (2) で (C) の数が変わります。`CREATE TABLE IF NOT EXISTS` はよくある形なので、件数に効きうると本書は考えます。
- 関係する決定: D68 の 1、14.5（作って消すもの）。

【穴 H-3-7】**`初回` と `外部の状態` の分け方。**（第 49 章 `docs/textbook/ch49.md:851-864` の本書の読み方）

- 何が決まっていないか: 手引きの例が「キャッシュが無いときだけ」（初回）と「ファイルが無いとき」（外部の状態）で重なります。
- 困る事例（作った例）: ツールが `~/.app/index.db` が無ければ作る形で、利用者がそのファイルを手で消すこともある。
- 考えられる選択肢: (1) ツール自身の前の呼び出しが作るものが無いときは `初回`、ほかの誰かしだいなら `外部の状態`（第 49 章の読み方）、(2) どちらも `外部の状態` にまとめ、`初回` は「プロセスの中の最初の呼び出し」だけにする、(3) 両方書く（`初回;外部の状態`）。どれでも (B)(C) は変わらず、条件の種類の内訳の表だけが変わります。
- 関係する決定: D68 の 1、手順書 23.5 の「条件の内訳」（`docs/final_evaluation_procedure.md:1414`）。

【穴 H-3-8】**誰が決めるかで種類が分かれる条件 — モデル・人（利用者）・クライアント・運用者・環境のどれか。**

- 何が決まっていないか: 7 つの種類は、モデル（引数）と運用者（設定・起動の方法）を区別しますが、そのほかの「決める人」を名指ししていません。(B) は運用者の条件かどうかで決まるので、分け方が数に効きます。
- 困る事例（作った例）:

  ```python
  # (i) 前に別のツールを呼んだかで決まる（どのツールを呼ぶかはモデルが選べる）
  @mcp.tool()
  def connect(dsn: str) -> str:
      global _conn; _conn = _open(dsn); return "ok"

  @mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
  def query(sql_name: str) -> str:
      if _conn is not None and _conn.is_writable():
          _conn.execute("INSERT INTO audit VALUES (?)", (sql_name,))
      return _run(sql_name)

  # (ii) クライアントの機能や、人の応答で決まる
  @mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
  async def pick(ctx: Context) -> str:
      ok = await _ask_user(ctx, "保存しますか？")   # クライアントを通じて、画面の前の人が答える
      if ok:
          _save_selection()
      return "done"

  # (iii) 運用者が置いた目印のファイルで決まる
  @mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
  def status() -> str:
      if os.path.exists("/etc/myapp/enable_metrics"):
          _write_metrics()
      return _status()

  # (iv) OS や、入っている任意の依存で決まる
  try:
      import fcntl               # Windows には無い
  except ImportError:
      fcntl = None
  @mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
  def peek(name: str) -> str:
      if fcntl is None:
          open(name + ".lock", "w").close()    # 代わりにロックのファイルを作る
      return _read(name)
  ```

- 考えられる選択肢:
  1. (i) はモデルが選べるので `引数`、(ii) は `外部の状態`、(iii)(iv) は運用者が選ぶので `運用者の設定`（(B) に数えない）。
  2. (i)(ii) は `外部の状態`（第 49 章は「作業メモに項目がある（項目は別のツールの呼び出しで入る）」を `外部の状態` と読んでいる。`docs/textbook/ch49.md:965`）、(iii)(iv) も「ファイルが無いとき」の例に合わせて `外部の状態`（(B) に数える）。
  3. 「運用者の設定」を「運用者がそのために用意した設定の仕組み（環境変数・設定ファイル・起動の引数）」だけに限り、それ以外はすべて `外部の状態`。
- 関係する決定: D68 の 1（「運用者が決める条件（運用者の設定・起動の方法）」`docs/decisions.md:3798`）。

【穴 H-3-9】**どの種類にも当てはまりにくい条件 — 回数・乱数・時刻。**

- 何が決まっていないか: 7 つの種類の例に、呼び出しの回数・乱数・時刻で決まる条件がありません。
- 困る事例（作った例）:

  ```python
  _calls = 0
  @mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
  def search(q: str) -> str:
      global _calls
      _calls += 1
      if _calls % 100 == 0:
          _flush_stats()                         # 100 回ごと
      if random.random() < 0.01:
          _vacuum_cache()                        # 1% の確率
      if date.today() != _last_rotated:
          _rotate_log()                          # 日付が変わった最初の呼び出し
      return _search(q)
  ```

- 考えられる選択肢: (1) 回数は `初回` に寄せる（「何回目か」で決まる）、乱数と時刻は `外部の状態`、(2) 時刻は `失敗・期限切れ`（期限が来た）に寄せる、(3) 7 つに無いので第 22 節で不明にし、事例を記録する。どれも運用者の条件ではないので、(1)(2) なら (B) に数え、(C) に数えないことは同じです。(3) だと不明が増えます。
- 関係する決定: D68 の 1、第 22 節（`:729-736`）。

【穴 H-3-10】**運用者の設定で「止められる」効果（既定の状態では起きる）は `運用者の設定` に入るか。**（第 49 章の境目 3、`docs/textbook/ch49.md:1099-1114` を広げたもの）

- 何が決まっていないか: `運用者の設定` の行は「環境変数・設定ファイル・起動の引数で**有効になる**」です。何も設定しなければ起き、設定すれば止まる形は、名指しされていません。
- 困る事例（作った例）:

  ```python
  # (i) lifespan の中の初期化が、環境変数で条件つき

  async def app_lifespan(server):
      if os.environ.get("PREBUILD") == "1":
          _ensure_index()                # 設定すれば起動時に済む。しなければ最初のツールの呼び出しで走る

  # (iii) Python の __debug__（`python -O` で起動すると偽になる）

      if __debug__:

      return str(_eval(expr))
  ```

- 考えられる選択肢: (1) 運用者の選択で起きるかが決まるのは同じなので `運用者の設定` を重ね、(B) に数えない、(2) 何も設定しない既定の状態で起きるので、運用者の条件は書かない（(i) は `初回`、(ii)(iii) は `なし`）、(3) 既定で起きるかどうかを `condition` に書き、集計で別に数える。(1) と (2) で (B) の数が変わり、(ii)(iii) では (C) の数も変わります。
- 関係する決定: D68 の 1、D67 の 2。(i) のように「運用者が別のコマンド（`myapp init`）を先に走らせれば、ツールの中の初期化に届かない」形も同じ問いに入ると本書は読みます。

【穴 H-3-11】**ツールの登録そのものが運用者の設定で決まるとき、その中の効果の条件の種類。**

- 何が決まっていないか: 条件の種類は「ツールが呼ばれたとき、効果に届く条件」です。ツールが登録されるかどうか自体が運用者の設定で決まる形は、書かれていません。
- 困る事例（作った例）:

  ```python

      @mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
      def export_all(path: str) -> str:
          with open(path, "w") as fh:          # ツールが在れば毎回
  ```

- 考えられる選択肢: (1) ツールが呼ばれた時点で条件は満たされているので `なし`（(B)(C) に数える）、(2) 運用者が有効にしなければツールが無いので `運用者の設定`（(B)(C) に数えない）、(3) 宣言の照合の単位（ユニット）として扱うか自体を別に決める。

### H-3.5 14.3 の (A)(B)(C) と、条件が重なるとき（手引き L266-268）

> 【原文 L266-268】
> - **主の数（A）は条件を問わない。** (B) と (C) は併記で、事前登録で決めてあるので、結果を見た後の分析ではない。
> - 条件が重なるとき（例: 引数を渡し、かつ環境変数が設定されているとき）は全部を `;` で並べる。**1 つでも運用者が決める条件が
>   あれば (B) に数えない。**

**一言で言うと**: 主の数 (A) は条件を問いません。(B)(C) は併記で、データを見る前に決めた数です。条件が重なるときは全部を `;` で並べ、**1 つでも運用者が決める条件があれば (B) に数えません**。

**ことばの確認**:

- **主の数**: 論文の主な結果として出す数。ここでは (A)。
- **併記**: 主の数と並べて出す数。主の数を置き換えるものではありません。
- **事前登録**: 結果を見る前に、何をどう数えるかを書いて封をしておくこと（`docs/preregistration.md` §2.12。今は下書き `docs/drafts/prereg_2_12_draft.md`）。
- **結果を見た後の分析**（事後の分析）: 結果を見てから足した分析。都合のよい数を選んだと見られうるので、事前に決めたものとは分けて報告します（[第 22 章](ch22.md)）。
- **`;`（セミコロン）**: `condition_type` 欄で、重なる条件を並べる区切り。「かつ」の意味で使います（例: `引数;運用者の設定`）。

**1 文ずつ読む**:

1. 「**主の数（A）は条件を問わない。**」: 条件の種類が何であっても、到達して宣言に反するなら、主の数では正です。
2. 「(B) と (C) は併記で、」: (B)(C) は主の数の代わりではなく、横に並べる数です。
3. 「事前登録で決めてあるので、結果を見た後の分析ではない。」: D68 の 1 の「B・C を事前に併記と決めておくことで、後から出しても結果を見て選んだことにならない」（`docs/decisions.md:3802`）と同じ意味です。事前登録の下書きにも書かれています（`docs/drafts/prereg_2_12_draft.md:103-105`）。
4. 「条件が重なるとき（例: 引数を渡し、かつ環境変数が設定されているとき）は全部を `;` で並べる。」: 1 つに絞らず、届くのに要る条件を全部書きます。
5. 「**1 つでも運用者が決める条件があれば (B) に数えない。**」: 運用者がその設定にしなければ、モデルがどんな引数を渡しても起きないからです（本書の読み。D68 の (B) の定義「運用者が決める条件…**でしか**届かないもの」`docs/decisions.md:3798` から出てくる）。

**なぜこう決めたのか**:

- (A) を主にするのは、D68 の 1 が「案 A を主」としたからです（`docs/decisions.md:3796`）。手順書 0-11 も同じです（`docs/final_evaluation_procedure.md:271`）。
- (B)(C) を事前に決めたのは、「運用者の設定まで違反に数えるのか」「毎回起きるものだけならどうか」という問いが必ず出るので、その答えを結果の前に固めておくためです（`docs/decisions.md:3802`）。
- 「全部を並べる」のは、1 つに絞ると「1 つでも運用者の条件があれば」の判断ができなくなるからです（本書の読み）。

**例で確かめる**:

（作った例）条件が重なる 3 つの形です。

```python
@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def render(doc: str, out: str = "") -> str:
    html = _render(doc)
    if out and os.environ.get("ALLOW_EXPORT") == "1":     # (a) 引数 かつ 運用者の設定
        Path(out).write_text(html)
    if os.environ.get("RENDER_CACHE") == "1" and not os.path.exists(_cache_path(doc)):
        Path(_cache_path(doc)).write_text(html)            # (b) 運用者の設定 かつ 初回
    if out and not os.path.exists(out):
        Path(out + ".new").write_text(html)                # (c) 引数 かつ 外部の状態
    return html
```

| 位置 | `condition_type` | (A) | (B) | (C) |
|---|---|---|---|---|
| (a) | `引数;運用者の設定` | 数える | 数えない | 数えない |
| (b) | `運用者の設定;初回` | 数える | 数えない | 数えない |
| (c) | `引数;外部の状態` | 数える | 数える | 数えない |

表の読み方: (a) と (b) は運用者の条件が 1 つ入っているので (B) に数えません。(c) は運用者の条件が無いので (B) に数えます。どれも条件があるので (C) には数えません。

この 3 つが 1 組の 3 つの位置だったら、手順 G（`:164-166`）で「正にできる位置のうち条件の一番弱いもの」を記録します。運用者の条件を含まない (c) が一番弱いので、組の `condition_type` は `引数;外部の状態` で、(B) に数えます。D68 の 1 にも「1 組に複数の位置があるときは、B・C もそれぞれ『条件を満たす位置が 1 つでもあれば数える』」とあります（`docs/decisions.md:3803`）。

実物の重なりの例は v4 の ccr の `_get_project_memory` です。`project` 引数・`.ccr` が無い・環境変数 `CCR_AUTO_INIT` の 3 つがそろったときだけ作るので、`引数;外部の状態;運用者の設定` と読めます（[第 49 章 49.3 節](ch49.md#s49-4)、`corpus/v4-qbit-glitch__ccr/ccr/mcp/server.py:557-575`）。

**迷いやすいところ**:

- **`;` は「かつ」です。** 「または」でつながる条件をどう書くかは決まっていません（【穴 H-3-12】）。
- **「事前登録で決めてある」は、今はまだ下書きです。** D68 の 1 は決定済みですが、事前登録の §2.12 は下書きで、手引きと同じコミットで封をする段取りです（`docs/drafts/final_judging_guide_draft.md:3-4`）。封の前に、手引きの 14.3 と事前登録の下書きの文面（`docs/drafts/prereg_2_12_draft.md:101-105`）を見比べておくと安心です。本書が見比べた範囲では、7 つの種類と (A)(B)(C) の定義は同じでした。
- **「一番弱い」の順は、手順 G に書かれています**（`:164-166`）。「なし」→ 運用者が決めない条件 → 運用者が決める条件、の 3 段です。同じ段の中の順は決まっていません（【穴 H-3-13】）。

**承認の前に自分に問うこと**:

1. 「1 つでも運用者の条件があれば (B) に数えない」を、自分は (B) の定義（運用者の条件**でしか**届かない）と同じ意味だと納得できるか。
2. 条件を全部 `;` で並べる手間（重なる条件を全部読み切る）を、1 件の時間に見込んでいるか。
3. 見落とし（18.2）と不の中身（18A）にも条件の種類を付けるが、(B)(C) で数え直すのは矛の精度だけでよいか（【穴 H-3-14】）。

**この節で手引きが決めていないこと**:

【穴 H-3-12】**「または」でつながる条件の書き方と、(B) の数え方。**

- 何が決まっていないか: 手引きは「重なるとき」（かつ）の書き方だけを決めています。どれか 1 つで届く「または」の形は書かれていません。
- 困る事例（作った例）:

  ```python
  @mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
  def query(q: str, trace: bool = False) -> str:
      if trace or os.environ.get("QUERY_TRACE") == "1":
          _append_trace(q)              # モデルが trace=True を渡しても、運用者が設定しても届く
      return _query(q)
  ```

  `引数;運用者の設定` と並べると、「1 つでも運用者の条件があれば (B) に数えない」で (B) から外れます。けれども、運用者が何もしなくても、モデルだけで届きます。
- 考えられる選択肢: (1) 「または」は別々の道とみなし、手順 G と同じく一番弱い道の条件だけを書く（ここでは `引数`。(B) に数える）、(2) 全部を `;` で並べ、`condition` に「または」と書いて、集計で読み分ける、(3) 区切りを別に決める（例: `|`）。
- 関係する決定: D68 の 1（`docs/decisions.md:3803`。位置が複数のときは 1 つでも満たせば数える）。

【穴 H-3-13】**運用者が決めない条件どうしで、どれを「一番弱い」とするか。**（第 49 章の境目 4、`docs/textbook/ch49.md:1116-1122`）

- 何が決まっていないか: 手順 G の順は 3 段（なし / 運用者が決めない / 運用者が決める）で、同じ段の中の順が無い。
- 困る事例（作った例）: 1 組に `引数` の位置と `失敗・期限切れ` の位置がある。
- 考えられる選択肢: (1) どちらか 1 つを書き、もう一方を `note` に、(2) 両方を書く（ただし `;` は「かつ」なので意味が変わる）、(3) 7 つの種類の表の上からの順（引数 → 初回 → 失敗・期限切れ → 外部の状態）を弱い順とみなす。(B)(C) は変わらず、条件の種類の内訳だけが変わります。
- 関係する決定: D68 の 1、手順 G（`:164-166`）。

【穴 H-3-14】**見落とし・不の中身に付けた条件の種類を、(B)(C) の数え直しに使うか。**

- 何が決まっていないか: 条件の種類は、見落とし（18.2 の 7、`:499`）と不の中身の違反（18A.2 の 5、`:556`）にも付けます。けれども、(B)(C) で計算し直すのは「主指標（23.2）」で（`docs/final_evaluation_procedure.md:1414`）、見落としの数や不の中身の違反の割合を (B)(C) の読み方でも出すかは、手引きにも手順書にも書かれていません。
- 困る事例（作った例）: 見落としの判定で、環境変数で有効になるログの追記だけが見つかった（`運用者の設定`）。(B) の読み方では、これは見落としに数えるのか、「反する動作は無い」に数えるのか。
- 考えられる選択肢: (1) 矛の精度だけを (B)(C) で数え直し、見落とし・不の中身は条件の種類の内訳だけを出す、(2) 見落とし・不の中身も (B)(C) で数え直して併記する、(3) 集計（段階 8）の前に決めて事前登録に書く。
- 関係する決定: D68 の 1、D69 の 3・4（`docs/decisions.md:3827-3831`）。

### H-3.6 14.4 起動時の初期化 — 前置きと「一度だけ」の形（手引き L270-284）

> 【原文 L270-284】
> ### 14.4 起動時の初期化（D67 の 2）
>
> ツールの道筋の途中に「一度だけ初期化する」形があり、効果がその初期化の中にあるとき:
>
> ```python
> _memory = None
>
> def _ensure_memory():
>     global _memory
>     if _memory is None:
>         _init()            # ← 効果（ディレクトリの作成など）はこの中
>     return _memory
> ```
>
> **その初期化がツールの受付より前に必ず済んでいるか**で決める。起動の方法はコードだけから決める。

**一言で言うと**: ツールの道筋の途中に「一度だけ初期化する」守りがあり、効果がその初期化の中にあるときは、**その初期化がツールの受付より前に必ず済んでいるか**で決めます。どう起動されるかは、**コードだけ**から読みます。

**ことばの確認**:

- **一度だけの初期化**: `if _x is None: _init()` のような「守り」で、最初の 1 回だけ準備をする書き方（[第 9 章](ch09.md)）。手順 D の 4 は、守りの形として `if self._x is None:`・`@lru_cache`・`global _initialized` を挙げています（`:144`）。
- **守り**（ガード）: 「もう準備したか」を見る `if` や、結果を覚えておく仕組み（`@lru_cache`）。
- **大域変数**（モジュール水準の変数）: ファイルの一番上の段で作る変数。`global` 宣言をした関数の中から書き換えられます。
- **受付**: サーバが、クライアントから届いた `tools/call` を処理し始めること。
- **起動の方法**: サーバのプログラムを動かし始める方法。① 最後に `mcp.run()`、② `main()` で準備してから `mcp.run()`、③ `if __name__ == "__main__":`、④ 外から `fastmcp run server.py:mcp` の 4 つの形があります（[第 3 章 3.7 節](ch03.md#s3-8)）。

**1 文ずつ読む**:

1. 見出し「14.4 起動時の初期化（D67 の 2）」: 規則の出どころは D67 の 2 です（`docs/decisions.md:3773-3778`）。
2. 「ツールの道筋の途中に『一度だけ初期化する』形があり、効果がその初期化の中にあるとき:」: この節が扱う場面の条件は 2 つです。(i) 守りがある、(ii) 効果が守りの中の初期化にある。守りが無ければ、この節の問題ではありません（毎回届くか、14.3 の条件で決めます）。
3. コードの 1 行目 `_memory = None`: 大域変数を「まだ準備していない」の印で始めます。
4. 空行の後 `def _ensure_memory():`: 「準備があることを確かにする」関数です。ツールの道筋の途中で呼ばれるとします。
5. `global _memory`: この関数の中で `_memory` に代入すれば、一番上の `_memory` が書き換わる、という宣言です。この抜粋には代入の行がありませんが、実際の木では `_init()` の中で入れるのがふつうです（[第 46 章](ch46.md)の注記と同じ）。
6. `if _memory is None:`: まだ準備していなければ。これが守りです。
7. `_init()            # ← 効果（ディレクトリの作成など）はこの中`: 初期化の関数を呼びます。効果はこの中です。
8. `return _memory`: 準備したものを返します。
9. 「**その初期化がツールの受付より前に必ず済んでいるか**で決める。」: 「必ず」が要です。ある起動の方法で済んでいても、別の起動の方法で済んでいなければ、「必ず」ではありません。
10. 「起動の方法はコードだけから決める。」: README・運用の様子・作者の想定は見ません。コードから読める起動のしかたを全部考えます。

**なぜこう決めたのか**:

- 解析器は、各呼び出しをサーバの状態（大域変数に何が入っているか）を仮定せずに読むので、守りの `if` の中の `_init()` にも「届く道がある」と読みます。その結果、起動時に済んでいる初期化の中の効果にも矛を出します（`docs/open_questions.md:1190`。v4 の抜き取りで誤 9 件だった類）。第 49 章の試験でも、`main()`・lifespan・読み込み時の 3 つの書き方に、凍結版の解析器は同じ矛を出しました（`docs/textbook/ch49.md:1327-1331`）。
- 解析器は lifespan の**本体の中の**効果はツールに付けません（`authgap/entry_seed.py:20-21`「lifespan 本体の起動時の効果はツールに付けない」）。けれども、ツールの道筋の守りから同じ初期化に届く道は、ツールの効果として出します。だから人が「先に済んでいるか」を確かめる必要があります（本書の読み）。
- 「コードだけ」にするのは、判定者の推測（「この木は実際には ③ で起動されているはずだ」）を入れないためです（[第 49 章 49.4 節](ch49.md#s49-5)の「なぜそう決めたのか」の 2 つ目）。D67 の 2 は「起動方法をコードだけで決める（O43 の整理）」と書いています（`docs/decisions.md:3773`）。

**例で確かめる**:

（作った例）守りの 4 つの形です。どれも「一度だけ」の守りで、この節の問題になります。

```python
# (1) 大域変数が None か
_db = None
def get_db():
    global _db
    if _db is None:
        _db = _open_and_migrate()      # ← 効果（表を作る）
    return _db

# (2) @lru_cache で 1 回だけ
@functools.lru_cache(maxsize=1)
def get_index():
    os.makedirs(INDEX_DIR, exist_ok=True)   # ← 効果
    return _load(INDEX_DIR)

# (3) 済んだかの印
_initialized = False
def ensure_ready():
    global _initialized
    if not _initialized:
        _prepare_workspace()           # ← 効果
        _initialized = True

# (4) インスタンスの属性
class Client:
    def __init__(self):
        self._session = None
    def session(self):
        if self._session is None:
            self._session = _login_and_save_cookie()   # ← 効果
        return self._session
```

(4) は、**インスタンスがどこで作られるか**で答えが変わります。

```python
_client = Client()                     # モジュールの一番上で 1 つだけ作る → 守りは 1 回だけ働く

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def me() -> str:
    return _client.session().whoami()

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def me2() -> str:
    return Client().session().whoami() # 呼び出しのたびに新しいインスタンス → 毎回ログインして保存する
```

- `me` は、一番上の `_client` の守りなので、この節の表で決めます（`_client.session()` を先に呼ぶ場所がどこにも無ければ、最初の呼び出しで届く形です。この形の扱いは【穴 H-3-16】）。
- `me2` は、呼び出しのたびに新しい `Client` を作るので、守りは毎回「まだ」になり、毎回届きます。これは「一度だけ」ではないので、この節の表ではなく 14.3 の `なし` です（本書の読み）。

**迷いやすいところ**:

- **守りの `if` が、ツールの道筋の中にあるか**を先に確かめます。同じ `_init()` が lifespan の中だけで呼ばれ、ツールの道筋には呼ぶ行が無いなら、そもそもツールの効果ではありません（[H-3.8](#ah-3-8) の 4 つ目の見分け方）。
- **「必ず」は、どの起動の方法でも、です。** 1 つでも済んでいない起動の方法がコードから読めれば、「必ず」ではありません。
- **`@lru_cache` は、引数があれば引数ごとに 1 回です。** `@lru_cache def get_db(path)` なら、新しい `path` のたびに初期化が走ります。`path` をモデルが選べるなら、起動時に既定の `path` で済ませていても、別の `path` では届きます（条件は 14.3 の `引数`。本書の読み）。

**承認の前に自分に問うこと**:

1. 「コードだけから決める」を守れそうか。README に「`python server.py` で起動してください」と書いてあっても、④ の起動を考えるか。
2. 守りの形（大域変数・`@lru_cache`・印・インスタンスの属性）を、自分は見分けられるか。
3. 「コードだけ」の「コード」に、`pyproject.toml` や Dockerfile を含めるか（【穴 H-3-15】）。

**この節で手引きが決めていないこと**:

【穴 H-3-15】**「起動の方法はコードだけから決める」の「コード」の範囲。**

- 何が決まっていないか: Python のソースだけか、`pyproject.toml` の `[project.scripts]`、Dockerfile の `CMD`、`fastmcp.json`・`smithery.yaml` のような起動の設定ファイル、README の起動の例までを含むかが書かれていません。
- 困る事例（作った例）: Python のソースでは `mcp` が一番上にあり、`main()` で初期化している（14.4 の表の 1 行目なら到達する）。一方、Dockerfile は `CMD ["python", "server.py"]` で、`fastmcp.json` は無い。あるいは逆に、サーバの本体が関数の中で作られていて（【穴 H-3-17】）、`fastmcp.json` がその関数を指している。

### H-3.7 14.4 の表 — 初期化を先に済ませている場所（手引き L286-291）

> 【原文 L286-291】
> | 初期化を先に済ませている場所 | 判定 | 理由 |
> |---|---|---|
> | `main()` の中だけ、または `if __name__ == "__main__":` の中だけ | **到達する（正になりうる）** | モジュールの一番上の `mcp = FastMCP(...)` は、`fastmcp run file.py:mcp` などで `main()` を通らずに起動できる。そのときは最初のツール呼び出しで初期化が走る（原理 3 と同じ「届きうる」の読み方） |
> | lifespan の中（`FastMCP(..., lifespan=app_lifespan)` に渡した関数の中） | **到達しない（誤、E1）** | どの起動方法でも、ツールの受付より前に必ず走る |
> | モジュールの読み込み時（モジュールの一番上の文、モジュール水準の変数の初期化） | **到達しない（誤、E1）** | import した時点で走る |
> | どこで先に済ませるか読み切れない | **不明** | |

**一言で言うと**: 初期化を先に済ませる場所が `main()` / `if __name__ == "__main__":` の中だけなら**到達する**（条件は `起動の方法`）。lifespan の中か、モジュールの読み込み時なら**到達しない**（誤、E1）。読み切れなければ**不明**です。

**ことばの確認**:

- **`main()`**: 起動の入口としてよく使われる関数の名前。名前に特別な意味は無く、誰かが呼ばないと実行されません（[第 3 章 3.7 節](ch03.md#s3-8)）。
- **`if __name__ == "__main__":`**: ファイルを直接実行したとき（`python server.py`）だけ中を実行する書き方（[第 3 章 3.6 節](ch03.md#s3-7)）。
- **`fastmcp run file.py:mcp`**: ファイルをモジュールとして読み込み、一番上の `mcp` を取り出して動かすコマンド。読み込むときの名前は `"server_module"` なので、`if __name__ == "__main__":` の中も `main()` も通りません（[第 3 章 3.7 節](ch03.md#s3-8)。公式 SDK 1.30.0 の `mcp/cli/cli.py:119-141` と、`fastmcp` 4.0.10 のコードを本記録者が読んで確かめた）。
- **lifespan**: `FastMCP(..., lifespan=…)` や低レベルの `Server(..., lifespan=…)` に渡す関数。サーバは lifespan に入って（`yield` の前を実行して）から要求を読み始めます（[第 3 章 3.9 節](ch03.md#s3-10)。SDK 1.30.0 の `mcp/server/lowlevel/server.py:662-681`）。
- **モジュールの読み込み時**: `import` されたとき。モジュールの一番上の文は、そのとき上から順に実行されます。

**1 文ずつ読む**（表の 1 行ずつ）:

1. 見出し行「初期化を先に済ませている場所 / 判定 / 理由」: 1 行が場所の 1 つの形です。
2. 1 行目「`main()` の中だけ、または `if __name__ == "__main__":` の中だけ / **到達する（正になりうる）** / モジュールの一番上の `mcp = FastMCP(...)` は、`fastmcp run file.py:mcp` などで `main()` を通らずに起動できる。そのときは最初のツール呼び出しで初期化が走る（原理 3 と同じ『届きうる』の読み方）」:
   - 「だけ」が大事です。同じ初期化をモジュールの一番上や lifespan でも済ませていれば、この行ではありません。
   - 「正になりうる」は「到達はする。正かどうかは 2 つ目の問いしだい」の意味です。
   - 理由の前提は「モジュールの一番上に `mcp = FastMCP(...)` がある」ことです。この前提が崩れる形は決まっていません（【穴 H-3-17】【穴 H-3-18】）。
3. 2 行目「lifespan の中（`FastMCP(..., lifespan=app_lifespan)` に渡した関数の中）/ **到達しない（誤、E1）** / どの起動方法でも、ツールの受付より前に必ず走る」: ① 〜 ④ のどの形でも、最後はサーバの `run` に入り、`run` は lifespan に入ってから要求を読みます。HTTP で起動したときは接続ごと（状態を持たない設定では要求ごと）に lifespan が走りますが、どれも「その接続のツールの呼び出しより前」です（[第 3 章 3.9 節](ch03.md#s3-10)の「細かい注意」）。
4. 3 行目「モジュールの読み込み時（モジュールの一番上の文、モジュール水準の変数の初期化）/ **到達しない（誤、E1）** / import した時点で走る」: どの起動の形でも、サーバのファイルは読み込まれるので、一番上の文はツールの受付より前に走ります。ただし、この理由は「そのモジュールが受付より前に読み込まれる」ことと「一番上の文が受付より前に実行される」ことを前提にしています（【穴 H-3-19】【穴 H-3-20】）。
5. 4 行目「どこで先に済ませるか読み切れない / **不明** / （空）」: 第 19 節の不明の典型「起動の方法・初期化の場所が読み切れない（第 14.4 節）」と同じです（`:579`）。

**なぜこう決めたのか**:

- D67 の 2: 「初期化が `main()` / `if __name__ == "__main__":` の中だけにある形は、ツールの呼び出しで届きうるので正（原理 3）。lifespan の中やモジュールの読み込み時にある形は誤。読み切れないときは不明」（`docs/decisions.md:3774-3776`）。
- O43 の整理: 「モジュールの一番上にある `mcp = FastMCP(...)` は、`fastmcp run file.py:mcp` などで `main()` を通らずに起動できる」（`docs/open_questions.md:1202-1203`）。
- ④ の起動で初期化が最初のツールの呼び出しの中にずれ込むことは、本記録者が SDK 1.30.0 で実際に動かして確かめています（[第 3 章 3.7 節](ch03.md#s3-8)の「実際に動かして確かめた結果」）。

【食い違い】**D67 の 2 と O43 は `main()` の形を「正」と書き、手引きは「到達する（正になりうる）」と書いています。**

- D67 の 2: 「…中だけにある形は、ツールの呼び出しで届きうるので正（原理 3）」（`docs/decisions.md:3774`）。O43 の整理も「ツールの呼び出しで届きうるので **正**」（`docs/open_questions.md:1204`）。
- 手引き: 「**到達する（正になりうる）**」（`docs/drafts/final_judging_guide_draft.md:288`）。手引きの 20.2 も、ccr の E00 を「最終評価の規則（14.4）では…『到達する』になるので、到達の理由では誤にならず、冪等の理由で誤」としています（`:681`）。
- 本書の読み: D67 の 2 の「正」は「宣言に反する効果なら」を省いた言い方で、手引きはそれを 2 つの問いに分けて書き直したと読めます。判定は手引き（11.2 の 2 つの問い）で行います。どちらの文面を正とするかは学生が確かめてください。

**例で確かめる**:

（作った例）共通の部分は次のとおりです。ツール `list_memos` は `readOnlyHint=True` で、道筋に守り `_ensure()` を持ちます。効果は `_init()` の中の `os.makedirs` で、D1 に反するとします。

```python
DATA_DIR = os.path.expanduser("~/.memo")
_store = None

def _init():
    global _store
    os.makedirs(DATA_DIR, exist_ok=True)   # ← 効果
    _store = {}

def _ensure():
    if _store is None:
        _init()
    return _store

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def list_memos() -> str:
    return str(sorted(_ensure()))
```

違うのは、`_init()` を先に呼ぶ場所と、起動の書き方だけです。

**形 A — ② `main()` の中だけ → 到達する**

```python
mcp = FastMCP("memo")        # 一番上
# …共通の部分…
def main():
    _init()
    mcp.run()
```

④ で起動すれば `main()` を通らないので、最初の `list_memos` で `_init()` に届きます。`condition_type` は `起動の方法`。(A) に数え、(B)(C) に数えません。

**形 B — ③ `if __name__ == "__main__":` の中だけ → 到達する**

```python
mcp = FastMCP("memo")
# …共通の部分…
if __name__ == "__main__":
    _init()
    mcp.run()
```

形 A と同じです。④ では `__name__` が `"server_module"` なので中を通りません。`condition_type` は `起動の方法`。

**形 C — ① 一番上で `_init()` してから `mcp.run()` → 到達しない（E1）**

```python
mcp = FastMCP("memo")
# …共通の部分…
_init()                      # 一番上の文
mcp.run()                    # 一番上の文（① の形）
```

`_init()` は一番上の文なので、`python server.py` でも ④ でも、読み込みのときに走ります（④ では読み込みの途中で `mcp.run()` が実行されてサーバが動き出す、と[第 3 章 3.7 節](ch03.md#s3-8)が書いています）。どちらでもツールの受付より前に済むので、到達しない、E1 です。

**形 D — lifespan の中 → 到達しない（E1）**

```python
@asynccontextmanager
async def app_lifespan(server):
    _init()                  # yield の前、条件なし
    yield {}

mcp = FastMCP("memo", lifespan=app_lifespan)
# …共通の部分…
if __name__ == "__main__":
    mcp.run()
```

どの起動の形でも、`yield` の前の `_init()` はツールの受付より前に済みます。`_init()` が失敗すれば lifespan は例外で抜け、受付は始まりません。到達しない、E1 です。低レベルの書き方で `Server("memo", lifespan=app_lifespan)` と渡しても同じです（[第 3 章 3.9 節](ch03.md#s3-10)）。

**形 E — モジュール水準の変数の初期化 → 到達しない（E1）**

```python
mcp = FastMCP("memo")
_store = _make_store()       # 一番上で作る（中で os.makedirs）

def _ensure():
    global _store
    if _store is None:
        _store = _make_store()
    return _store
```

`_store` は読み込みのときに作られ、`None` に戻す行が無ければ、ツールの道筋の守りは偽のままです。到達しない、E1 です。

**形 F — 読み切れない → 不明**

```python
mcp = FastMCP("memo")
# …共通の部分…
for ep in importlib.metadata.entry_points(group="memo.plugins"):
    ep.load()(mcp)           # 入っているプラグインが、何をするか分からない
```

`_init()` を先に呼ぶ場所が、木の外のプラグインの中にあるかもしれず、20〜30 分調べても決められなければ不明です。`unknown_reason` は「初期化を先に済ませるかが、実行時に読み込むプラグインで決まる」など。

**形 G — どこでも先に済ませていない → 到達する（`初回`）**

```python
mcp = FastMCP("memo")
# …共通の部分…（_init() を先に呼ぶ行がどこにも無い）
if __name__ == "__main__":
    mcp.run()
```

どの起動でも、最初の `list_memos` の呼び出しで `_init()` が走ります。手引きの表にこの行はありません。第 49 章は「49.3 節の表の `初回` にそのまま当たる」と読んでいます（`docs/textbook/ch49.md:1372-1374`）。手引きの 4 行目（読み切れない → 不明）と取り違えないように、【穴 H-3-16】に挙げます。

**低レベルの書き方 — `serve()` の中の入れ子のハンドラ**

```python
async def serve():
    db = _open_and_migrate(DB_PATH)          # ← 効果（表を作る）。serve() の中で先に済ませる
    server = Server("notes")

    @server.list_tools()
    async def list_tools():
        return [Tool(name="count", inputSchema={...}, annotations=ToolAnnotations(readOnlyHint=True))]

    @server.call_tool()
    async def call_tool(name, arguments):
        if name == "count":
            return [TextContent(type="text", text=str(db.count()))]

    async with stdio_server() as (r, w):
        await server.run(r, w, server.create_initialization_options())

def main():
    asyncio.run(serve())
```

- この形では、`count` の枝（入れ子の `call_tool` の中）は `_open_and_migrate` を**呼びません**。`db` は外側の `serve()` が作ったものを使うだけです。だから、ツールの道筋に初期化は無く、そもそも 14.4 の問題ではありません（[H-3.8](#ah-3-8) の 4 つ目の見分け方）。もし解析器がこの効果を `count` に付けていたら、手順 D で道筋を確かめ直します。
- 入れ子のハンドラの**中に**守りがある形（`if state.db is None: state.db = _open_and_migrate(...)`）で、`serve()` が先に済ませているときは、表のどの行かが決まっていません（【穴 H-3-17】）。

**迷いやすいところ**:

- **② と ③ は、どちらも ④ で通らない**ので、同じ扱いです（1 行目）。
- **① の形（一番上で `mcp.run()`）**は `main()` がもともと無いので、`main()` を通らない起動を考える必要がありません。一番上で済ませた初期化は 3 行目（読み込み時）です。
- **同じ初期化が `main()` と lifespan の両方にある**なら、lifespan が「必ず」済ませるので 2 行目です（1 行目は「だけ」）。
- **`main()` で済ませた初期化が「到達する」でも、組が正とは限りません。** v4 の ccr の E00 は、到達はするが冪等な追記なので D4 に反せず誤（E8）です（`:681`）。
- **v4 の判定とは逆になる**ことがあります。v4 では本記録者が ccr の `main()` の形を「到達しない」で誤にしていました。v4 の判定は D67 の 2 の前のもので、付け直していません（`docs/open_questions.md:1201`）。判定の練習で v4 と食い違っても、手引きの曖昧さではありません（[第 49 章](ch49.md#s49-5)）。

1. ④ の起動を「ありうる」と数えることに納得できるか。作者が ④ を想定していなくても、`mcp` が一番上にあれば到達する、でよいか。

**この節で手引きが決めていないこと**:

【穴 H-3-16】**初期化をどこでも先に済ませていない形（最初のツールの呼び出しで初めて走る遅延の初期化）の扱い。**

- 何が決まっていないか: 14.4 の表は「先に済ませている場所」の 3 つと「読み切れない」の 4 行で、「どこでも済ませていない」行がありません。
- 困る事例: 上の形 G。
- 考えられる選択肢: (1) 14.3 の `初回` として到達する（第 49 章の読み、`docs/textbook/ch49.md:1372-1374`）、(2) 「どこで先に済ませるか読み切れない」の行に入れて不明にする、(3) 14.4 の表に行を足す（封の前なら手引きを直せる）。(1) と (2) で正の数が変わります。
- 関係する決定: D67 の 2、D68 の 1。

【穴 H-3-17】**サーバの本体が関数の中で作られる形 — `main()` の中で `FastMCP` を作る・ツールを登録する、ファクトリ関数、低レベルの `serve()`。**（第 49 章の境目 6、`docs/textbook/ch49.md:1642-1660` を広げたもの）

- 何が決まっていないか: 1 行目の理由は「モジュールの一番上の `mcp = FastMCP(...)` は…`main()` を通らずに起動できる」です。本体が関数の中で作られると、④ でその名前を指せません（公式 SDK 1.30.0 は、見つからないときに「`main()` などの中で FastMCP を作っているなら、一番上の変数に書き直して」と案内する。`mcp/cli/cli.py:171-179`、[第 3 章 3.7 節](ch03.md#s3-8)）。そのとき「`main()` を通らない起動」が無いかもしれません。文字どおりには「`main()` の中だけ」に当たるので 1 行目（到達する）ですが、理由の前提が崩れます。
- 困る事例（作った例）:

  ```python
  # (i) main() の中で本体を作り、登録し、初期化する
  def main():
      mcp = FastMCP("memo")
      register_tools(mcp)        # ツールの関数は別のモジュールの一番上にあり、守りを持つ
      _init()
      mcp.run()

  # (ii) ファクトリ関数（fastmcp 4.0.10 には、引数の無い関数を指してサーバを作らせる形がある。第 3 章 3.7 節）
  def create_server():
      _init()
      mcp = FastMCP("memo")
      register_tools(mcp)
      return mcp

  # (iii) 低レベルの serve() の中で先に済ませ、入れ子のハンドラの中にも守りがある
  async def serve():
      state.db = _open_and_migrate(DB_PATH)
      server = Server("notes")
      @server.call_tool()
      async def call_tool(name, arguments):
          if state.db is None:
              state.db = _open_and_migrate(DB_PATH)
          ...
      async with stdio_server() as (r, w):
          await server.run(r, w, server.create_initialization_options())
  ```

  (i)(iii) では、サーバを動かす道がどれも初期化を通るように読めます。(ii) は、ファクトリを指して起動すれば、サーバを作る前に初期化が済みます。
- 考えられる選択肢: (1) 文字どおり 1 行目（`main()` の中だけ → 到達する、`起動の方法`）、(2) 理由の前提が崩れるので「どの起動でも受付より前に必ず済む」として到達しない（E1 か E6 か、も決める必要がある）、(3) 読み切れない（4 行目）として不明、または第 22 節で不明。
- 関係する決定: D67 の 2、O43 の整理。[第 3 章 3.7 節](ch03.md#s3-8)も「判定の手引きの下書きは、この形の起動を名指しでは扱っていません」と書いています。

【穴 H-3-18】**モジュールの一番上にある低レベルの `Server` と、`main()` の中だけの初期化。**

- 何が決まっていないか: 公式 SDK 1.30.0 の `mcp run` は低レベルの `Server` に対応しておらず（`mcp/cli/cli.py:152-157`。「Low level Server class is not yet supported」）、④ の起動ができないと読めます。`fastmcp` の側の対応は本書は確かめていません。1 行目の理由は `FastMCP` を前提にしています。
- 困る事例（作った例）:

  ```python
  server = Server("notes")            # 一番上。低レベル
  @server.call_tool()
  async def call_tool(name, arguments):
      if name == "count":
          return [TextContent(type="text", text=str(_ensure_db().count()))]   # 守りの中で初期化
  async def main():
      _ensure_db()                    # main() の中だけで先に済ませる
      async with stdio_server() as (r, w):
          await server.run(r, w, server.create_initialization_options())
  ```

- 考えられる選択肢: (1) 文字どおり 1 行目で到達する（`起動の方法`）、(2) この SDK では `main()` を通らない起動が無いとして到達しない、(3) 「起動できるか」は SDK の版や別のパッケージで変わりうるので、読み切れないとして不明。
- 関係する決定: D67 の 2。

【穴 H-3-19】**モジュールの一番上の初期化が「必ず」受付より前に済まない形 — `mcp.run()` より後ろの文、失敗を握りつぶす、条件つき。**

- 何が決まっていないか: lifespan については「必ず済ませるか（例外で抜けたら受付が始まらないか、条件つきではないか）も見る」と書かれていますが（`:296-297`）、3 行目（読み込み時）には同じ確かめが書かれていません。また、lifespan や読み込み時の初期化が失敗しても受付が始まる形で「到達する」としたときの条件の種類も書かれていません。
- 困る事例（作った例）:

  ```python
  # (i) 一番上の文だが、mcp.run() の後ろにある
  mcp.run()                     # ここでサーバが動き、止まるまで戻らない
  _init()                       # ← 受付より前には走らない

  # (ii) 一番上の初期化が、失敗を握りつぶす
  try:
      _init()
  except Exception:
      pass                      # 失敗しても読み込みは続き、受付が始まる

  # (iii) 一番上の初期化が、条件つき
  if os.environ.get("EAGER_INIT") == "1":
      _init()
  ```

- 考えられる選択肢: (1) 3 行目にも lifespan と同じ「必ず」の確かめを当て、(i)〜(iii) は到達する（条件の種類は (i) `初回`、(ii) `失敗・期限切れ`（[付録 D-8](appendix-d-8.md#ad-8-5) の演習 49-1 (3) の答えが lifespan の同じ形をこう読んでいる）、(iii) は【穴 H-3-10】の問い）、(2) 文字どおり「一番上の文」なので 3 行目で到達しない（E1）、(3) 第 22 節で不明。
- 関係する決定: D67 の 2、O43 の「失敗しない」の確かめ（`docs/open_questions.md:1213`）。

【穴 H-3-20】**ツールの中で初めて import するモジュールの、一番上の初期化（遅延 import）。**（第 49 章の境目 5、`docs/textbook/ch49.md:1620-1640`）

- 何が決まっていないか: 3 行目の理由「import した時点で走る」は、import がツールの受付より前に起きることを前提にしています。ツールの関数の中で初めて import する形では、最初のツールの呼び出しの中で一番上の文が走ります。
- 困る事例（作った例）: ツールの中に `from . import heavy_index` があり、`heavy_index.py` の一番上で `os.makedirs(INDEX_DIR, exist_ok=True)` をする。
- 考えられる選択肢: (1) 理由に従い、ツールの呼び出しの中で走るので到達する（`初回`）、(2) 文字どおり「モジュールの読み込み時」なので 3 行目で到達しない（E1）、(3) 第 22 節で不明。
- 関係する決定: D67 の 2。凍結版の解析器が、ツールの中の import から読み込み先の一番上の文の効果を拾うかは、第 49 章も確かめていません。

【穴 H-3-21】**MCP のサーバに渡した lifespan ではない「別のアプリの lifespan」（Starlette・FastAPI など）での初期化。**

- 何が決まっていないか: 2 行目は「`FastMCP(..., lifespan=app_lifespan)` に渡した関数の中」です。MCP のサーバを HTTP のアプリ（Starlette・FastAPI）に組み込み、そのアプリの lifespan で初期化する形は、標準入出力で起動したときには走りません。
- 困る事例（作った例）:

  ```python
  mcp = FastMCP("notes")                      # MCP のサーバ自身には lifespan が無い
  @asynccontextmanager
  async def web_lifespan(app):
      _init()                                 # ← Web アプリとして起動したときだけ走る
      yield
  app = FastAPI(lifespan=web_lifespan)
  app.mount("/mcp", mcp.streamable_http_app())

  if __name__ == "__main__":
      mcp.run()                               # 標準入出力で起動すると web_lifespan は走らない
  ```

  v4 の wikimind にも、MCP のサーバの lifespan とは別に FastAPI のアプリの lifespan がありました（[第 49 章 49.4 節](ch49.md#s49-5)の実物 3。そこでは別のアプリの lifespan は `cache_clear()` の側だった）。
- 考えられる選択肢: (1) 2 行目の「lifespan」に入れて到達しない（E1）、(2) その lifespan は起動の方法によって走らないので、1 行目と同じく到達する（`起動の方法`）、(3) どの起動で走るか読み切れないとして不明。
- 関係する決定: D67 の 2。

【穴 H-3-22】**`起動の方法` の位置に、`初回` も重ねて書くか。**

- 何が決まっていないか: `main()` を通らない起動で届くのは、その起動の後の**最初の**呼び出しだけです（形 A）。`;` で全部並べる規則（`:267`）を当てると `起動の方法;初回` とも書けます。初期化の中の効果がさらに「ディレクトリが無いときだけ」なら `起動の方法;初回;外部の状態` とも書けます。
- 困る事例: 上の形 A・形 B。
- 考えられる選択肢: (1) `起動の方法` だけ（手引きの表の例のとおり。最初の 1 回であることは `起動の方法` に含まれるとみなす）、(2) `起動の方法;初回` と重ねる、(3) 中の効果の条件まで全部重ねる。どれでも (B)(C) に数えないことは変わらず、条件の種類の内訳だけが変わります。
- 関係する決定: D68 の 1。

### H-3.8 14.4 の見分け方（手引き L293-300）

> 【原文 L293-300】
> 見分け方:
>
> - lifespan: `FastMCP(` / `Server(` の引数の `lifespan=` を探し、その関数（多くは `@asynccontextmanager`）の中を見る。
> - lifespan が初期化を**必ず**済ませるか（例外で抜けたら受付が始まらないか、条件つきではないか）も見る。条件つきなら、
>   条件が偽のときはツールの呼び出しで届くので「到達する」。
> - **初期化が済んでいても、その後にどこかで `None` に戻す（`_memory = None`）なら、ツールの呼び出しで再び届く。**
>   戻す箇所が無いかを grep で確かめる。
> - ツールの道筋が初期化を**呼ばない**（守りの `if` が無い）なら、そもそもその効果はツールの道筋ではない → 手順 D で確かめる。

**一言で言うと**: lifespan を探し、それが**必ず**初期化を済ませるかを見ます。済ませた後で `None` に戻す箇所が無いかを grep します。そもそもツールの道筋が初期化を呼ぶかも確かめます。

**ことばの確認**:

- **`@asynccontextmanager`**: lifespan によく付く印。「入るときの処理と出るときの処理を持つ関数」の印です。`yield` より前が起動時、後が終了時の処理です（[第 3 章 3.9 節](ch03.md#s3-10)）。
- **例外で抜ける**: 処理の途中でエラーが起き、残りを実行せずに関数から出ること。
- **`None` に戻す**: 守りの変数に `None` を入れ直し、「まだ準備していない」状態に戻すこと。`@lru_cache` なら `cache_clear()` が同じ働きです。

**1 文ずつ読む**:

1. 「見分け方:」: 以下の 4 つは、表の行を選ぶための手がかりです。
2. 1 つ目「lifespan: `FastMCP(` / `Server(` の引数の `lifespan=` を探し、その関数（多くは `@asynccontextmanager`）の中を見る。」: `grep -rn "lifespan=" <木>` で探し、渡している関数を開きます。`Server(` が入っているので、低レベルの書き方の lifespan も同じ扱いです。
3. 2 つ目「lifespan が初期化を**必ず**済ませるか（例外で抜けたら受付が始まらないか、条件つきではないか）も見る。」: lifespan の中にあるだけでは足りません。(i) `yield` より前か、(ii) 条件なしか、(iii) 失敗したら受付が始まらないか、の 3 つを見ます。
4. 同じ 2 つ目の続き「条件つきなら、条件が偽のときはツールの呼び出しで届くので『到達する』。」: lifespan が条件つきで初期化するなら、条件が偽の起動では最初のツールの呼び出しで届きます。そのときの条件の種類は書かれていません（【穴 H-3-10】）。
5. 3 つ目「**初期化が済んでいても、その後にどこかで `None` に戻す（`_memory = None`）なら、ツールの呼び出しで再び届く。**」: 一度済んでも、戻されれば次の呼び出しで守りが真になります。
6. 同じ 3 つ目の続き「戻す箇所が無いかを grep で確かめる。」: 型注釈つきの定義（`_memory: X | None = None`）も拾える命令が[第 49 章](ch49.md#s49-5)にあります（`grep -rnE '\b<変数名>\s*(:[^=]*)?=\s*None' corpus/<木> --include='*.py'`。`@lru_cache` なら `grep -rn 'cache_clear'`）。
7. 4 つ目「ツールの道筋が初期化を**呼ばない**（守りの `if` が無い）なら、そもそもその効果はツールの道筋ではない → 手順 D で確かめる。」: 解析器が、ツールから初期化への道筋を出していても、実際のツールの道筋に初期化を呼ぶ行が無いなら、道筋そのものを疑います（14.2 の形 2・形 3）。

**なぜこう決めたのか**:

- 3 つの確かめは、O43 の整理が「lifespan の形を正しく扱うには、4 つを全部確かめる必要がある」とした 4 つ（順序・状態・戻らない・失敗しない）のうち、人が 1 件ずつ見るものです（`docs/open_questions.md:1209-1213`）。「1 つでも外すと誤 clear を作る」ので、解析器には自動でさせず、判定で人が見ます（同 `:1214`）。
- 「必ず」を見るのは、14.4 の基準そのもの（「ツールの受付より前に**必ず**済んでいるか」`:284`）だからです。

**例で確かめる**:

（作った例）lifespan があるが、答えが分かれる 4 つの形です。どれも、ツールの道筋に `if _store is None: _init()` の守りがあるとします。

```python
# (1) 必ず済ませる → 到達しない（E1）
@asynccontextmanager
async def ls1(server):
    _init()
    yield {}

# (2) 条件つき → 到達する（条件が偽のとき、最初のツールの呼び出しで）
@asynccontextmanager
async def ls2(server):
    if os.environ.get("WARM") == "1":
        _init()
    yield {}

# (3) 失敗を握りつぶす → 到達する（初期化が失敗し _store が None のまま残ったとき）
@asynccontextmanager
async def ls3(server):
    try:
        _init()
    except Exception:
        logging.warning("init failed; will retry lazily")
    yield {}

# (4) yield の後ろ（終了時）にある → 先に済ませていない
@asynccontextmanager
async def ls4(server):
    yield {}
    _init()                     # 終了時。受付の前には走らない
```

- (1) は表の 2 行目で到達しない、E1。
- (2) は 2 つ目の見分け方の「条件つきなら…到達する」。条件の種類は【穴 H-3-10】の問いです。
- (3) は「例外で抜けたら受付が始まらないか」が「いいえ」なので、「必ず」ではありません。到達します。条件の種類は書かれていません（【穴 H-3-19】の選択肢 (1) と同じ問い）。
- (4) は lifespan の中ですが `yield` の後ろなので、受付の前には走りません。ほかで先に済ませていなければ、最初のツールの呼び出しで届く形です（本書の読み。H-3.7 の形 G と同じで、扱いは【穴 H-3-16】）。

（作った例）`None` に戻す形を 3 つ並べます。どれも lifespan で `_init()` を必ず済ませているとします。

```python
# (a) 別のツールが戻す
@mcp.tool()
def reset() -> str:
    global _store
    _store = None
    return "reset"

# (b) 一定時間で戻す（守りの関数の中）
def _ensure():
    global _store, _loaded_at
    if _store is not None and time.time() - _loaded_at > 3600:
        _store = None                   # 1 時間で読み直す
    if _store is None:
        _init(); _loaded_at = time.time()
    return _store

# (c) 終了時に戻す
@atexit.register
def _close():
    global _store
    _store = None
```

- (a) は、モデルが `reset` を呼んだ後の最初の呼び出しで届きます。到達します。条件の種類は手引きに書かれていません（【穴 H-3-23】）。
- (b) は、1 時間たった後の呼び出しで届きます。到達し、条件は `失敗・期限切れ`（期限切れ）と読めます。
- (c) は、プロセスが終わるときにだけ走るので、受付の途中では戻りません。[第 49 章](ch49.md#s49-5)はこの形を「戻す箇所がツールの呼び出しの中で走りうるか」で読み、到達しない（E1）としています（v4 の shyhurricane の `close_server_context()` が `@atexit.register` の中で `None` に戻す形。`corpus/v4-double16__shyhurricane/shyhurricane/mcp_server/server_context.py:198-203`）。ただし、手引きの文面は「どこかで」です（【穴 H-3-23】）。

**迷いやすいところ**:

- **lifespan があれば全部 E1、ではありません。** 問題の初期化を lifespan が**必ず**済ませているときだけです。lifespan が別のことだけをしているなら、表のほかの行で決めます。
- **grep で `= None` が見つかっても、必ずもう一度届くとは限りません。** その行が**いつ**走るか（ツールの中か、終了時か、テストか、コメントか）を 1 行ずつ確かめます。v4 の ccr では、戻す行はテストとコメントだけでした（[第 49 章 49.4 節](ch49.md#s49-5)）。
- **4 つ目の見分け方の括弧「（守りの `if` が無い）」は、2 通りに読めます**（本書の読み）。(i) ツールの道筋に初期化を呼ぶ行そのものが無い → 道筋を疑う。(ii) ツールの道筋が守り無しで初期化を直接呼ぶ → これは「呼ばない」ではなく、毎回届く形（14.3 の `なし`）です。[第 49 章](ch49.md#s49-5)のフローチャートの段 1 は、この 2 つを分けて書いています（`docs/textbook/ch49.md:1360`）。
- **HTTP で接続ごとに lifespan が走っても**、その接続のツールの呼び出しより前なので、扱いは同じです（[第 3 章 3.9 節](ch03.md#s3-10)）。

**承認の前に自分に問うこと**:

1. lifespan が失敗を握りつぶす形（上の (3)）を「到達する」とすることに納得できるか。そのときの条件の種類を、自分は何と書くか。
2. 「どこかで `None` に戻す」の「どこか」に、終了時（`atexit`）やテストのコードを含めるか（【穴 H-3-23】）。
3. 戻す箇所を探す grep を、型注釈つきの形も拾える命令で打てるか。

**この節で手引きが決めていないこと**:

【穴 H-3-23】**「どこかで `None` に戻す」の「どこか」の範囲と、戻された後に届くときの条件の種類。**

- 何が決まっていないか: 手引きは「その後にどこかで `None` に戻すなら、ツールの呼び出しで再び届く」と書きます（`:298`）。文字どおりには、終了時の `atexit`・テスト・別のスクリプトの中の行も「どこか」に入ります。[第 49 章](ch49.md#s49-5)は「それが**ツールの呼び出しの中で**走りうるか」と絞って読んでいます（`docs/textbook/ch49.md:1364`）。また、別のツール（上の (a)）が戻すときの条件の種類は書かれていません。
- 困る事例: 上の (a) と (c)。(c) を文字どおりに読むと、shyhurricane も「到達する」になり、手引きの 14.4 の最後の段落（shyhurricane は誤）と合わなくなります。
- 考えられる選択肢:
  1. 「どこか」を「ツールの受付の途中で走りうる場所」に限る（第 49 章の読み）。(a) は到達する、(c) は到達しない。
  2. 文字どおり、木の中のどこでも（テストは除く、など限りを付けて）。
  3. 別のツールが戻す (a) の条件の種類を決める: `外部の状態`（別の呼び出しで変わった状態しだい）か `初回`（戻った後の最初の 1 回）か `引数`（どのツールを呼ぶかはモデルが選べる）。[付録 D-8](appendix-d-8.md#ad-8-5) の演習 49-4 の答えは `外部の状態` と `初回` の両方の読み方を挙げています。どれも運用者の条件ではないので (B) には数え、(C) には数えません。
- 関係する決定: D67 の 2、O43 の「戻らない」の確かめ（`docs/open_questions.md:1212`）。

### H-3.9 14.4 の最後の段落 — 解析器に有利な側と不利な側（手引き L302-303）

> 【原文 L302-303】
> この規則では、v4 の ccr（`main()` で初期化）は正、shyhurricane（lifespan で初期化）は誤になる。**解析器に有利な側（ccr）と
> 不利な側（shyhurricane）の両方がある**ことを論文に書く（O43 の整理）。

**ことばの確認**:

### H-3.10 14.5 同じ呼び出しの中で作って消すもの（手引き L305-308）

> 【原文 L305-308】
> ### 14.5 同じ呼び出しの中で作って消すもの
>
> ツールが同じ呼び出しの中で一時ファイルを作り（`mkstemp`）、使い、消す（`os.remove`）形は、**到達はする**。
> 宣言に反するかは宣言による（第 15 節の D1 と D2 で扱いが違う）。

**一言で言うと**: ツールが 1 回の呼び出しの中で一時ファイルを作り、使い、消す形は、**到達はします**。呼び出しの後に何も残らなくても、作る・消すという動作は起きているからです。反するかは宣言で違います（D1 では反する、D2 では反しない）。

**ことばの確認**:

- **一時ファイル**: 処理の途中で一時的に使うファイル。
- **`mkstemp`**: Python の `tempfile.mkstemp`。OS の一時領域に、名前の重ならない新しい空のファイルを作ります。
- **`os.remove`**: ファイルを消す関数。
- **D1・D2**: `readOnlyHint: true`（環境を変えない）と `destructiveHint: false`（呼び出しの前からあったものを壊さない）の宣言です。

**1 文ずつ読む**:

1. 見出し「14.5 同じ呼び出しの中で作って消すもの」: 「同じ呼び出しの中で」が条件です。作るのも消すのも、1 回のツールの呼び出しの中です。
2. 「ツールが同じ呼び出しの中で一時ファイルを作り（`mkstemp`）、使い、消す（`os.remove`）形は、**到達はする**。」: 作る行も消す行も、その呼び出しの実行の道にあるので、14.1 の問いに「はい」です。「到達は」の「は」は、「到達の問いの答えはこうだが、判定はまだ決まらない」という含みです。
3. 「宣言に反するかは宣言による（第 15 節の D1 と D2 で扱いが違う）。」: 2 つ目の問いは第 15 節で決めます。D1 では、ファイルの作成・削除はすべて環境の変更で、一時ファイルも含みます（`:318`）。D2 では、同じ呼び出しで自分が作ったものを消すのは「呼び出しの前からあったもの」ではないので反しません（`:351-353`。誤、E2 `:459`）。

**なぜこう決めたのか**:

- 「到達」と「宣言に反するか」を分けておけば、同じ一時ファイルの作成・削除が、D1 では正、D2 では誤（E2）と、宣言ごとに正しく分かれます。「呼び出しの後に何も残らないから到達しない」としてしまうと、D1 の正まで誤になり、誤 clear を作ります（本書の読み。[第 49 章 49.5 節](ch49.md#s49-6)の「なぜ『到達』と『反するか』を分けるのか」）。
- D2 で誤にするときの原因を E6（到達しない）ではなく E2（同じ呼び出しで作った一時ファイル・ロックの後始末）にできるのも、この分け方のおかげです。E2 は v3・v4 で何度も出た類（O41・O43）で、論文の限界の材料になります（`:459`、`:468`）。

**例で確かめる**:

（作った例）

```python
@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True, destructiveHint=False))
def convert(doc: str) -> str:
    fd, tmp = tempfile.mkstemp(suffix=".md")      # ← 作る
    os.close(fd)
    try:
        Path(tmp).write_text(doc)                  # ← 使う
        return subprocess.run(["pandoc", tmp, "-t", "html"],
                              capture_output=True, text=True).stdout
    finally:
        os.remove(tmp)                             # ← 消す（finally なので必ず）
```

| 宣言 | 到達するか | 宣言に反するか（第 15 節） | 判定 |
|---|---|---|---|
| D1 `readOnlyHint: true` | はい（毎回。`condition_type` は `なし`） | 反する（作成・書き込み・削除はすべて環境の変更） | 正（書き込み先の種類は「一時ファイル」`:421`） |
| D2 `destructiveHint: false` | はい | 反しない（消したのは同じ呼び出しで自分が作ったもの） | 誤、E2 |

（`subprocess.run` の `pandoc` の起動は、別の組（kind が SPAWN）です。ここでは考えません。）

v4 の実物では、ru-marketplace の `ozon_reviews` × `os.remove` × D1（M58）が「同じ呼び出しで `mkstemp` した一時ファイルを消す。D1 では反する。D2 なら E2 で誤になる形」とされています（`:679`）。

（作った例）似ているが、14.5 に当たらない形:

```python
@mcp.tool(annotations=ToolAnnotations(destructiveHint=False))
def poll() -> str:
    for old in glob.glob("/tmp/myapp-*.json"):
        os.remove(old)                  # ← 前の呼び出しが残したものを消す
    path = f"/tmp/myapp-{uuid.uuid4()}.json"
    Path(path).write_text(_fetch())
    return Path(path).read_text()       # 作ったものは消さずに残す
```

ここで消しているのは前の呼び出しが残したファイルなので、「同じ呼び出しの中で作って消す」ではありません。到達はします（`glob` が何か見つけたとき。条件は 14.3 の `外部の状態` などと読めます）。D2 では、呼び出しの前からあったものを消すので反します（`:352-353`）。

**迷いやすいところ**:

- **「何も残らない」は到達の答えを変えません。** 到達は「起きるか」、宣言は「起きたことが約束に反するか」で、別の問いです。
- **`finally:` の中の削除は毎回です。** `finally:` はエラーが起きても起きなくても最後に必ず実行されます。条件の種類は「失敗」ではありません。`except:` の中だけなら失敗のときだけです（[第 49 章 49.5 節](ch49.md#s49-6)）。
- **D1 では一時ファイルも反します。** 「一時ファイルだからどの宣言でも反しない」は誤りです（`:318`）。
- **前の呼び出しが残したファイルを消すなら、14.5 の形ではありません**（D2 でも反します。`:352-353`）。v4 の reaper-mcp（M20）は、前の中断した呼び出しが残した応答のファイルを `unlink(missing_ok=True)` で毎回消す形でした（[第 49 章 49.5 節](ch49.md#s49-6)）。

**承認の前に自分に問うこと**:

1. 「呼び出しの後に何も残らない作成・削除も、D1 では違反」に納得できるか（軽重は書き込み先の種類の「一時ファイル」で表す。`:63-64`）。
2. D2 で一時ファイルの削除を誤にするとき、原因を E6 ではなく E2 と書けるか。
3. 「同じ呼び出しの中で」の範囲をどこまでとするか（【穴 H-3-24】）。

**この節で手引きが決めていないこと**:

【穴 H-3-24】**「同じ呼び出しの中で作って消す」の「同じ呼び出しの中で」の範囲。**

- 何が決まっていないか: 14.5 は作るのと消すのが同じ呼び出しの中にある形を名指しします。消すのが呼び出しの後になる形や、うまくいったときだけ消す形は書かれていません。到達の答えはどれも「はい」ですが、D2 の判定（15.2 の「同じ呼び出しで自分が作った一時ファイルを消す → 反しない」）に当てはまるかが変わります。
- 困る事例（作った例）:

  ```python
  # (i) 成功したときだけ消す（失敗すると残り、次の呼び出しが残ったものを消すこともある）
  fd, tmp = tempfile.mkstemp(); os.close(fd)
  _work(tmp)
  os.remove(tmp)                 # _work が例外を出せば実行されない

  # (ii) 呼び出しの中で作り、プロセスの終了時に消す
  d = tempfile.mkdtemp()
  atexit.register(shutil.rmtree, d)

  # (iii) 呼び出しの中で作り、次の呼び出しの最初で消す
  if _last_tmp: os.remove(_last_tmp)
  _last_tmp = _make_tmp()
  ```

- 考えられる選択肢: (1) 消す行が同じ呼び出しの実行の道にあり、消すものがその呼び出しで作ったものなら 14.5 の形（(i) の成功の道は当たる。(ii)(iii) は当たらない）、(2) 「呼び出しの後に残らない」ことを条件にして、(i) の失敗の道で残るなら 14.5 に当たらない、(3) 「同じプロセスが作ったものを消す」まで広げる（(ii)(iii) も 14.5 に当たる）。
- 関係する決定: 15.2 の迷いやすい形（`:351-353`）、E2（`:459`）。D2 の扱いは[付録 H-4](appendix-h-4.md) で読む第 15.2 節の範囲でもあります。

### H-3.x この分冊のまとめ

- 到達するかは「ツールが呼ばれたとき、効果が起きる実行の道が **1 つでもあるか**」で決める。毎回でなくてよい（14.1）。理由はクライアントが確認を省くこと（D68 の 1）と、原理 3-a の「能力の上界」の読み方。
- 到達しない形は 5 つ: 起動時の初期化（E1）、呼び出し先の取り違え（E3 / E4）、死んだコード・定数で閉じた枝・必ず先に抜ける（E6）。「別の入口からしか呼ばれない」は grep で呼び出し元を全部見て確かめる（14.2）。
- 条件つきでも届きうるなら到達する。条件の種類は 7 つ（なし / 引数 / 初回 / 失敗・期限切れ / 外部の状態 / 運用者の設定 / 起動の方法）。条件が何で決まるか読み切れなければ不明（14.3）。
- 主の (A) は条件を問わない。(B) は運用者の 2 つ（運用者の設定・起動の方法）でしか届かない正を、(C) は条件つきの正を、誤に置き換えて数え直す（D68 の 1、手順書 23.5）。条件が重なるときは `;` で全部並べ、1 つでも運用者の条件があれば (B) に数えない。
- 起動時の初期化: 初期化がツールの受付より前に**必ず**済んでいるかで決める。`main()` / `if __name__ == "__main__":` の中だけなら到達する（`起動の方法`）、lifespan・読み込み時なら到達しない（E1）、読み切れなければ不明。起動の方法はコードだけから決める（14.4、D67 の 2）。
- 見分け方: `lifespan=` を探す → 必ず済ませるか（条件つき・失敗の握りつぶし）→ `None` に戻す箇所とそれがいつ走るか → そもそもツールの道筋が初期化を呼ぶか。
- ccr（解析器に有利）と shyhurricane（不利）の両方を論文に書く。
- 同じ呼び出しの中で作って消すものは到達する。D1 では反する（正）、D2 では反しない（誤、E2）（14.5）。
- この分冊で 24 の穴を挙げた。とくに (B)(C) の数に効くのは、【穴 H-3-4】（既定値）、【穴 H-3-5】（早く抜ける）、【穴 H-3-6】（行は毎回だが変化は一部）、【穴 H-3-8】（誰が決める条件か）、【穴 H-3-10】（止められる設定）、【穴 H-3-11】（ツールの登録が設定しだい）、【穴 H-3-12】（「または」の条件）。正の数そのものに効くのは、【穴 H-3-1】（呼び出しの後に起きる効果）、【穴 H-3-2】（設定用の Python の定数）、【穴 H-3-16】〜【穴 H-3-21】（起動の形）、【穴 H-3-23】（`None` に戻す「どこか」）。

<a id="ah-3-z"></a>
### H-3.z 確認問題

**問 1**: 14.1 の基本の問いを 1 文で書いてください。「毎回起きる必要はない」とする理由を 1 つ挙げてください。

<details><summary>答え</summary>

「そのツールが呼ばれたとき、その効果が起きる実行の道が 1 つでもあるか」（`docs/drafts/final_judging_guide_draft.md:236`）。理由の例: クライアントは `readOnlyHint: true` を見て呼び出しごとの確認を省くので、確認を省いたどれか 1 回で起きるなら宣言は守られていない（D68 の 1、`docs/decisions.md:3800-3801`）。ほかに、原理 3-a の「能力の上界」の読み方に揃えるため（`:253`）。

</details>

**問 2**: 次の（作った例）の書き込みは到達しますか。到達しないなら誤の原因の記号を書いてください。

```python
VERBOSE = False            # 木のどこでも書き換えない
@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def ping() -> str:
    if VERBOSE:
        open(LOG, "a").write("ping\n")
    return "pong"
```

<details><summary>答え</summary>

到達しません。定数で閉じた枝で、誤の原因は E6 です（14.2、`:245`）。`evidence` には、`VERBOSE` を書き換える行が木に無いことを grep で確かめた結果を書きます。もし `VERBOSE = os.environ.get("VERBOSE") == "1"` なら、運用者の設定で到達します。

</details>

**問 3**: 次の 4 つの位置の `condition_type` を書き、(B)・(C) に数えるかを答えてください（どれも正だとします）。
(a) `if out_path:` の中の書き出し（`out_path` はツールの引数）。(b) 環境変数 `TRACE=1` のときだけの追記。(c) 保存したトークンの期限が切れたときの保存。(d) `main()` の中だけで済ませる初期化の中のディレクトリの作成（`mcp` は一番上）。

<details><summary>答え</summary>

(a) `引数`: (B) 数える、(C) 数えない。(b) `運用者の設定`: (B)(C) とも数えない。(c) `失敗・期限切れ`: (B) 数える、(C) 数えない。(d) `起動の方法`: (B)(C) とも数えない（14.3 の表 `:257-263`）。

</details>

**問 4**: 判定した 10 組のうち、正が 6 組（なし 2、引数 1、初回 1、運用者の設定 1、起動の方法 1）、誤が 3 組、不明が 1 組でした。件数の精度を (A)(B)(C) で計算してください。

<details><summary>答え</summary>

分母は正 + 誤 = 9 で、3 つの読み方で同じです（数えない正は誤に置き換える。`docs/decisions.md:3804`）。(A) 6 / 9。(B) 運用者の設定と起動の方法の 2 組を誤に置き換えて 4 / 9。(C) なしの 2 組だけが正で 2 / 9。不明の 1 組はどの読み方でも不明のままです。

</details>

**問 5**: 条件が `引数;運用者の設定` と重なる正は (B) に数えますか。理由も書いてください。

<details><summary>答え</summary>

数えません。手引きは「1 つでも運用者が決める条件があれば (B) に数えない」としています（`:267-268`）。運用者がその設定にしなければ、モデルがどんな引数を渡しても起きないので、「運用者が決める条件でしか届かない」（`docs/decisions.md:3798`）に当たります。

</details>

**問 6**: 一度だけの初期化を、(i) `main()` の中だけ、(ii) lifespan の `yield` の前で条件なし、(iii) モジュールの一番上、で先に済ませている 3 つのサーバがあります（`mcp` はどれも一番上）。それぞれ到達しますか。到達するなら条件の種類、しないなら誤の原因を書いてください。

<details><summary>答え</summary>

(i) 到達する。`fastmcp run file.py:mcp` などで `main()` を通らずに起動できるので、最初のツールの呼び出しで初期化が走る。条件の種類は `起動の方法`。(ii) 到達しない。どの起動方法でもツールの受付より前に必ず走る。E1。(iii) 到達しない。import した時点で走る。E1（14.4 の表 `:286-291`）。

</details>

**問 7**: 問 6 の (ii) の lifespan が `try: _init() except Exception: pass` の形だったら、答えはどう変わりますか。

<details><summary>答え</summary>

到達する、に変わります。手引きは「lifespan が初期化を必ず済ませるか（例外で抜けたら受付が始まらないか…）も見る」としています（`:296-297`）。失敗を握りつぶすと、初期化が済まないまま受付が始まりうるので、最初のツールの呼び出しで届きえます。このときの条件の種類は手引きに書かれていません（[付録 D-8](appendix-d-8.md#ad-8-5) の演習 49-1 (3) の答えは `失敗・期限切れ` と読んでいます。この分冊の【穴 H-3-19】）。

</details>

**問 8**: lifespan で初期化した守りの変数を、`@atexit.register` の付いた関数の中で `None` に戻しています。ツールの呼び出しで初期化に再び届きますか。手引きの文面と第 49 章の読み方の違いにも触れてください。

<details><summary>答え</summary>

第 49 章の読み方では届きません（誤、E1）。`@atexit.register` の関数はプロセスの終了時にだけ走り、ツールの受付の途中では戻らないからです（v4 の shyhurricane と同じ形。`docs/textbook/ch49.md:1364`）。ただし手引きの文面は「その後に**どこかで** `None` に戻すなら、ツールの呼び出しで再び届く」（`:298`）で、「どこか」の範囲は書かれていません（【穴 H-3-23】）。

</details>

**問 9**: D2（`destructiveHint: false`）を宣言したツールが、同じ呼び出しの中で `mkstemp` した一時ファイルを `finally:` で消します。到達しますか。判定と誤の原因はどうなりますか。D1 ならどうなりますか。

<details><summary>答え</summary>

到達します（14.5、`:307`。`finally:` の中なので毎回、条件は `なし`）。D2 では、消したのは同じ呼び出しで自分が作ったもので、呼び出しの前からあったものではないので反しません。判定は誤、原因は E2 です（`:351-353`、`:459`）。D1 では、作成・削除はすべて環境の変更なので反し、正です（`:318`）。書き込み先の種類は「一時ファイル」（`:421`）。

</details>

**問 10**: 「`main()` の中で初期化しているが、`FastMCP` も `main()` の中で作っている」サーバに出会いました。手引きの 14.4 の表のどの行に当たるか、なぜ迷うのかを説明してください。

<details><summary>答え</summary>

文字どおりには「`main()` の中だけ」なので 1 行目（到達する）に当たります。けれども 1 行目の理由は「モジュールの一番上の `mcp = FastMCP(...)` は、`fastmcp run file.py:mcp` などで `main()` を通らずに起動できる」で、本体が `main()` の中にあると、その名前を外から指せず、`main()` を通らない起動が無いかもしれません（公式 SDK 1.30.0 の `mcp run` は、本体が見つからなければ一番上に書き直すよう案内する。[第 3 章 3.7 節](ch03.md#s3-8)）。理由の前提が崩れるので、手引きでは決まっていません（【穴 H-3-17】）。決まらないまま出会ったら、第 22 節に従って不明にし、事例を記録します（`:733-736`）。

</details>
