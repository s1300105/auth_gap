# 第 3 部 コードと外の世界を読む基礎

第 4 部では解析器の仕組みを、第 8 部では最終評価の判定の規則を学びます。
どちらも、2 つのことを前提にしています。

1 つ目は、**実際の Python のコードを読めること**です。
2 つ目は、**HTTP・SQL・ネットワークの基本的な意味を知っていること**です。

第 3 版では、この 2 つを説明しないまま判定の話に進んでいました。
そのため、たとえば「`open(p, "a")` と `open(p, "w")` は何が違うのか」「解析器はなぜ POST を『分からない』と答えるのか」といった所で、判定の理由を自分の言葉で説明できなくなっていました。

第 3 部は、その土台を作る部です。
プログラミングの講座ではありません。**判定の場面で実際に出てくる形だけ**を扱います。

## 第 9 章 判定に要る Python の読み方

> **この章で分かること**:
> - Python のコードを読むための最小限の言葉（変数・関数・引数・オブジェクト・メソッド・受け手・`None`・`with`・`try`）。
> - サーバの起動の 4 つの形の復習と、lifespan の中身を読むための `async def`・`await`・`yield`・`@asynccontextmanager` の意味。実物の木で lifespan を探す方法と、そのときの落とし穴。
> - 「一度だけの初期化」の 4 つの書き方（`global` と `is None`、`@lru_cache`、シングルトン、キャッシュを返す関数）と、それが**もう一度走る**場合。
> - `open` のモード（`'r'`・`'w'`・`'a'`・`'x'`・`'r+'` など）が、前からある中身にどう効くか。
> - ファイルとディレクトリの作成・削除・置き換えの関数と、途中で壊れない書き方（atomic write）。解析器の一覧に**載っていない**関数。
> - ログの出力先がファイルか標準エラーかを見分ける方法と、設定がモジュールの一番上にあることが多い理由。
> - 子プロセスの起動、子の標準入力への書き込み、`shlex.quote`。
> - DB（sqlite3）と HTTP（requests・httpx）の呼び出しの形。
> - デコレータの wrapper が、ツールの本体より**先に**走ること。
> - 組み込みのメソッドと、木の中の同名のメソッドの取り違え。解けない受け手（モジュール水準のインスタンス、コールバック）。
> - grep とエディタで呼び出し元・定義を探すときの手順と注意。

### 9.0 Python を読むための最小限の言葉

#### 一言で言うと

判定で読むコードは、ほとんどが「**名前に値を入れる**」「**関数を呼ぶ**」「**オブジェクトのメソッドを呼ぶ**」の 3 つの組み合わせです。
この 3 つが読めれば、この章の残りの節は読めます。

#### たとえ話 — 料理のレシピ

料理のレシピを思い浮かべてください。

- 「玉ねぎ 1 個を **A** とする」のように、材料に名前を付けます。これが **変数**（名前に値を入れること）です。
- 「切る」「炒める」のような、決まった手順のまとまりがあります。これが **関数** です。「何を切るか」は手順に渡す材料で、これが **引数** です。
- 「鍋で炒める」の「鍋」は道具です。鍋には「炒める」「煮る」のように、その道具でできることが決まっています。道具が **オブジェクト**、道具でできることが **メソッド** です。

レシピを読むとき、「どの道具で、何を、どうするか」を読みます。
コードを読むときも同じで、「**どのオブジェクトの、どのメソッドに、何を渡しているか**」を読みます。

#### 小さな例 — 11 行のコード

作例です。

```python
1  import os
2
3  CACHE_DIR = "/tmp/cache"            # 名前に値を入れる（代入）
4
5  def save(name, text):               # 関数を作る（定義）。name と text は引数
6      path = os.path.join(CACHE_DIR, name)
7      with open(path, "w") as f:      # ファイルを開き、f という名前で使う
8          f.write(text)               # f のメソッド write を呼ぶ
9      return path                     # 戻り値
10
11 result = save("a.txt", "hello")     # 関数を呼ぶ
```

#### 一歩ずつ — 1 行ずつの意味

- 1 行目: `os` という部品の箱（モジュール）を読み込みます。`os` は Python に最初から入っている、ファイルやディレクトリを扱う部品の箱です。
- 3 行目: `CACHE_DIR` という名前に、文字列 `"/tmp/cache"` を入れます。`=` は「等しい」ではなく「**右の値を左の名前に入れる**」という意味です。`#` から行の終わりまでは**コメント**（人のためのメモ）で、Python は無視します。
- 5 行目: `save` という関数を作ります。`def` は「関数を作る」という印です。かっこの中の `name` と `text` は、呼ばれたときに渡される値を受け取る名前（引数）です。**この行では、関数の中身はまだ実行されません**（[第 3 章](ch03.md) 3.6 節）。
- 6 行目: `os.path.join(CACHE_DIR, name)` で、ディレクトリの名前とファイルの名前をつないで、ファイルの場所（パス）を作ります。その結果を `path` に入れます。行の先頭が字下げ（4 文字の空白）されているのは、「この行は `save` の中身だ」という印です。
- 7 行目: `open(path, "w")` でファイルを書き込み用に開きます（`"w"` の意味は 9.3 節）。`with ... as f:` は、開いたファイルを `f` という名前で使い、下の字下げのまとまりを抜けたら自動で閉じる書き方です。
- 8 行目: `f.write(text)` で、ファイルに `text` を書きます。`f` がオブジェクト（開いたファイル）、`write` がそのメソッドです。
- 9 行目: `return path` で、作ったパスを呼び出し元に返します（戻り値）。
- 11 行目: `save("a.txt", "hello")` で関数を呼びます。`name` に `"a.txt"`、`text` に `"hello"` が入り、5〜9 行目が実行されます。返ってきた値が `result` に入ります。

このコードは、11 行目まで実行すると `/tmp/cache/a.txt` というファイルに `hello` と書きます（`/tmp/cache` が無いと 7 行目で失敗しますが、ここでは気にしなくて構いません）。

#### 言葉の整理

この章でくり返し使う言葉を、やさしい言い換え・正確な定義・例の 3 点で整理します。

- **変数と代入**
  - やさしい言い換え: 値に付けた名札。
  - 正確な定義: `名前 = 式` と書くと、右の式を計算した値に、左の名前が付く。同じ名前に後で別の値を入れ直せる。
  - 例: `CACHE_DIR = "/tmp/cache"`。
- **関数・引数・戻り値**
  - やさしい言い換え: 名前の付いた手順と、手順に渡す材料と、手順の結果。
  - 正確な定義: `def 名前(引数, ...):` で作る処理のまとまり。`名前(値, ...)` と書くと呼ばれ、中身が実行される。`return 値` で呼び出し元に値を返す。
  - 例: `save("a.txt", "hello")`。
- **モジュールと import**（[第 3 章](ch03.md) 3.6 節の復習）
  - やさしい言い換え: 部品の箱と、それを持ってくること。
  - 正確な定義: モジュールは 1 つの `.py` ファイル（またはライブラリの部品）。`import 名前` で読み込み、`名前.部品` の形で中の関数などを使う。読み込んだ時点で、そのモジュールの一番上の文が 1 回実行される。
  - 例: `import os` の後の `os.path.join(...)`。
- **クラスとオブジェクト（インスタンス）**
  - やさしい言い換え: 道具の設計図と、設計図から作った道具。
  - 正確な定義: `class 名前:` で作る設計図をクラス、`名前(...)` でクラスから作ったものをオブジェクト（インスタンス）と呼ぶ。Python では、文字列や開いたファイルも、どれも何かのクラスのオブジェクトである。
  - 例: `requests.Session()` は `Session` というクラスのオブジェクトを作る。
- **メソッドと属性**
  - やさしい言い換え: 道具でできることと、道具が持っている値。
  - 正確な定義: オブジェクトに付いた関数をメソッド、オブジェクトに付いた値を属性と呼ぶ。どちらも `オブジェクト.名前` の形で使う。メソッドは `オブジェクト.名前(...)` と呼ぶ。
  - 例: `f.write(text)` の `write` はメソッド。`proc.stdin` の `stdin` は属性。
- **受け手**
  - やさしい言い換え: メソッドを呼ばれている側のオブジェクト。
  - 正確な定義: `X.m(...)` という呼び出しの `X` の部分。どの `m` が呼ばれるかは、`X` が**何のクラスのオブジェクトか（型）**で決まる。
  - 例: `client.post(url)` の受け手は `client`。`client` が `httpx.AsyncClient` のオブジェクトなら httpx の `post` が、木の中の別のクラスのオブジェクトなら、そのクラスの `post` が呼ばれる。
- **型**
  - やさしい言い換え: その値が何の種類か。
  - 正確な定義: 値が属するクラス。`"abc"` は文字列（`str`）、`set()` は集合（`set`）、`open(...)` の結果はファイルのオブジェクト。
  - 例: `visited = set()` なら、`visited` の型は組み込みの `set`（9.9 節）。
- **`None`**
  - やさしい言い換え: 「何も無い」を表す特別な値。
  - 正確な定義: Python に 1 つだけある「値が無い」ことを表すオブジェクト。`x is None` で「`x` が `None` か」を調べる。
  - 例: `_memory = None` は「まだ準備していない」という印によく使われる（9.2 節）。
- **`with` 文**
  - やさしい言い換え: 「入るときの準備」と「出るときの後片付け」をセットにする書き方。
  - 正確な定義: `with 式 as 名前:` の下の字下げのまとまりを実行する前に、式の「入る処理」を、まとまりを抜けた後に（途中で失敗しても）「出る処理」を実行する。
  - 例: `with open(path, "w") as f:` は、抜けたときにファイルを自動で閉じる。
- **`try` / `except` / `finally`**
  - やさしい言い換え: 「失敗したらこうする」「最後に必ずこうする」の印。
  - 正確な定義: `try:` の下を実行し、途中で失敗（例外）が起きたら、合う `except` の下を実行する。`finally:` の下は、成功しても失敗しても最後に必ず実行する。`raise` は失敗（例外）を起こす命令。
  - 例: 9.4 節の atomic write は、失敗したら一時ファイルを消してから失敗を伝え直す。

#### なぜこの言葉が要るのか

判定では、解析器の説明ではなく、**コードの動作**で決めます。
手引きの下書きは、判定の根拠として、たどった各段のファイルと行を書き留めるよう求めています。
つまり、あなたは「この行で、このオブジェクトの、このメソッドが呼ばれ、こういう値が渡る」と自分の言葉で書ける必要があります。
そのための最小限の言葉が、上の 11 個です。
（出典: `docs/drafts/final_judging_guide_draft.md:143`（手順 D の 5「根拠として、たどった各段のファイルと行を書き留める」））

#### よくある誤解・つまずき

- **誤解: 「`def` の行を読んだら、中身が実行される」**
  実行されません。`def` は関数を作るだけです。中身は、誰かがその関数を呼んだときに初めて実行されます（[第 3 章](ch03.md) 3.6 節）。
- **誤解: 「`f.write(text)` の `f` はファイルの名前」**
  `f` は開いたファイルの**オブジェクト**に付けた名前です。ファイルの名前（場所）は、`open` の 1 つ目の引数 `path` のほうです。書き込み先を調べるときは、`open` の 1 つ目の引数を見ます。
- **誤解: 「同じ名前のメソッドなら、同じ処理」**
  違います。`visited.add(x)` と `cache.add(x)` は、受け手の型が違えば別の処理です。9.9 節でくわしく見ます。
- **つまずき: 字下げを見落とす**
  Python では、字下げ（行の先頭の空白）が「どのまとまりの中か」を決めます。`if` の下で字下げされた行は、条件が成り立ったときだけ実行されます。字下げが 1 段違うだけで、意味が変わります。

#### 手作業ではどう使うか

判定で 1 行を読むときは、次の 3 つを問います。

1. **何を呼んでいるか**: 関数の名前と、メソッドなら受け手。受け手の型は、その名前に何が代入されたかをさかのぼって確かめます。
2. **何を渡しているか**: 引数。とくに、書き込み先のパスや開くモードのような、動作を決める引数。
3. **結果をどこに入れているか**: 戻り値を受けた名前。その名前を後でどう使うかで、次にたどる行が決まります。

この 3 つを、手引きの手順 D の各段で書き留めます（[第 48 章](ch48.md)）。

#### この節のまとめ

コードは「名前に値を入れる」「関数を呼ぶ」「オブジェクトのメソッドを呼ぶ」の組み合わせでできている。
`X.m(...)` の `X` を受け手と呼び、どの `m` が呼ばれるかは受け手の型で決まる。
判定では、各行で「何を呼び、何を渡し、結果をどこに入れたか」を読む。

### 9.1 サーバの起動と lifespan — `async def`・`await`・`yield`・`@asynccontextmanager`

#### 一言で言うと

lifespan は、「`@asynccontextmanager` の付いた `async def` の関数で、中に `yield` が 1 つある」形をしています。
`yield` の**前**がサーバの起動時（ツールの受付の前）に、**後**が終了時に走ります。
どの起動の形でも、`yield` の前はツールの受付より前に必ず済みます。
この節では、その形を作っている 4 つの印の意味を説明し、実物の木で lifespan を探す方法と、そのときの落とし穴を学びます。

#### 復習 — 起動の 4 つの形（第 3 章 3.7 節）

[第 3 章](ch03.md)で、MCP サーバを Python のファイルから起動する形は、大きく 4 つあると見ました。

| 起動の形 | 一番上の文 | `main()` の中 | `if __name__ == "__main__":` の中 | lifespan の `yield` の前 |
|---|---|---|---|---|
| ① `python server.py`（ファイルの最後で `mcp.run()`） | 実行される | （`main` が無い） | — | ツールの受付の前に実行される |
| ② パッケージの設定（`[project.scripts]`）から `main()` を呼ぶ | 実行される | 実行される | 実行されない | ツールの受付の前に実行される |
| ③ `python server.py`（`if __name__ == "__main__": main()`） | 実行される | 実行される | 実行される | ツールの受付の前に実行される |
| ④ `fastmcp run server.py:mcp`（公式 SDK なら `mcp run`） | 実行される | **実行されない** | **実行されない** | ツールの受付の前に実行される |

表の読み方: 4 行目は「④ の形で起動すると、一番上の文は実行されるが、`main()` の中と `if __name__ == "__main__":` の中は実行されない。それでも lifespan の `yield` の前は、ツールの受付の前に実行される」と読みます。
右端の列がどの行でも同じなのが、この節の要点です。

補足を 1 つ足します。
`python -m パッケージ名` という起動のしかたもあります。
これは、パッケージの中の `__main__.py` というファイルを、`__name__` が `"__main__"` の状態で実行します。
だから `__main__.py` の中の `if __name__ == "__main__":` は真になり、③ の仲間として読めます。
（出典: 表の 1〜4 列目は[第 3 章](ch03.md) 3.7 節の表。lifespan の列は[第 3 章](ch03.md) 3.9 節。SDK 1.30.0 の `mcp/server/lowlevel/server.py:662-681` で、lifespan に入る行（663 行）が要求を読む繰り返し（681 行）より前にある。repo の外のファイル）

#### たとえ話 — ホテルのチェックインとチェックアウト

ホテルに泊まるときを考えます。
フロントで**チェックイン**すると、部屋の鍵を受け取ります。
そのあと、部屋で好きなだけ過ごします。
帰るときに**チェックアウト**して、鍵を返します。

「チェックイン → 滞在 → チェックアウト」は必ずこの順で、チェックアウトを忘れることはありません（フロントが必ず手続きをします）。

lifespan も同じ形です。

- チェックイン = `yield` の前（データベースにつなぐ、ディレクトリを作る、ログインする、などの準備）。
- 滞在 = `yield` で止まっているあいだ（サーバがツールの呼び出しを受け付けている時間）。
- チェックアウト = `yield` の後（接続を閉じるなどの後片付け）。

この「入る・滞在・出る」の形を作る道具が `@asynccontextmanager` で、「滞在」の位置を示す印が `yield` です。
`async` と `await` は、「待っているあいだ、ほかの仕事をしてよい」という印です。

#### 小さな例 1 — `async def` と `await`

作例です。

```python
1  import asyncio
2
3  async def fetch_number():
4      print("  fetch_number の中身が走った")
5      return 3
6
7  async def main():
8      coro = fetch_number()          # 呼んだだけ。中身はまだ走らない
9      n = await coro                 # ここで中身が走り、結果 3 を受け取る
10     print("結果:", n)
11
12 asyncio.run(main())
```

#### 一歩ずつ — 1 行ずつの意味

- 3 行目: `async def` で関数を作ります。ふつうの `def` との違いは、「この関数の中では、時間のかかる処理を**待つ**ことができる」という点です。
- 4〜5 行目: 中身です。説明のために、走ったことが分かるように `print` で文字を出します。
- 8 行目: `fetch_number()` と呼びます。`async def` の関数は、**呼んだだけでは中身が走りません**。代わりに「これから走る予定の処理」（コルーチンと呼ばれるオブジェクト）が返ってきます。
- 9 行目: `await coro` で、その処理を実際に走らせ、終わるのを待って、結果を受け取ります。ここで 4 行目の文字が出ます。
- 12 行目: `asyncio.run(main())` で、`main` を最初から最後まで走らせます。`async def` の関数を、ふつうのプログラムから動かすための入口です。

本記録者が動かして確かめたところ、`fetch_number()` を呼んだだけの時点で返ってくるのは `coroutine` という種類のオブジェクトで、中身の `print` は `await` したときに初めて実行されました（2026-10-01、Python 3.11）。

実際の MCP サーバでは、8 行目と 9 行目をまとめて、`n = await fetch_number()` と 1 行で書くのがふつうです。
判定のために読むときは、**`await f(...)` は「`f` を呼んで、終わるのを待つ」**と読めば十分です。
呼び出しが起きることに変わりはありません。

#### 小さな例 2 — `yield` で一時停止する関数

作例です。

```python
1  def steps():
2      print("  前半が走った")
3      yield 1
4      print("  後半が走った")
5      yield 2
6
7  g = steps()          # 呼んだだけ。中身はまだ走らない
8  print(next(g))       # 3 行目まで進み、1 を受け取る
9  print(next(g))       # 続きから 5 行目まで進み、2 を受け取る
```

#### 一歩ずつ — 1 行ずつの意味

- 1 行目: 中に `yield` を含む関数を作ります。こういう関数を**ジェネレータ**と呼びます。
- 3 行目: `yield 1` は、「呼び出し元に 1 を渡して、**ここで一時停止する**」という意味です。`return` と違って、関数は終わりません。止まった位置を覚えています。
- 7 行目: `steps()` と呼ぶと、ジェネレータのオブジェクトが返ってくるだけで、中身はまだ走りません。
- 8 行目: `next(g)` で「次の `yield` まで進めて」と頼みます。2 行目の文字が出て、3 行目で 1 が渡されます。
- 9 行目: もう一度 `next(g)` を呼ぶと、**止まった位置の続き**（4 行目）から進みます。4 行目の文字が出て、5 行目で 2 が渡されます。

本記録者が動かして確かめた出力の順番は、「前半が走った」→ `1` →「後半が走った」→ `2` でした（2026-10-01、Python 3.11）。

`yield` は「**しおりを挟んで本を閉じる**」ようなものです。
次に開いたときは、しおりの位置から読み始めます。

#### 小さな例 3 — `@asynccontextmanager` で「入る・出る」を作る

作例です。

```python
1  import asyncio
2  from contextlib import asynccontextmanager
3
4  @asynccontextmanager
5  async def life(server):
6      print("  yield の前（入るとき）")
7      try:
8          yield {"db": "接続"}
9      finally:
10         print("  yield の後（出るとき）")
11
12 async def main():
13     async with life(None) as ctx:
14         print("  中の仕事。ctx =", ctx)
15
16 asyncio.run(main())
```

#### 一歩ずつ — 1 行ずつの意味

- 2 行目: Python に最初から入っている `contextlib` という部品の箱から、`asynccontextmanager` を持ってきます。
- 4 行目: `@asynccontextmanager` は、次の関数に付ける**デコレータ**（[第 3 章](ch03.md)で見た「名札」。正確には 9.8 節）です。「この関数を、`with` 文で使える『入る・出る』の形に変えてください」という意味です。
- 5 行目: `async def` の関数で、中に `yield` が 1 つあります。
- 6 行目: `yield` より前の部分です。`async with` で**入るとき**に走ります。
- 7〜8 行目: `try:` の中で `yield` します。ここで関数は一時停止し、`{"db": "接続"}` を `with` の側に渡します。
- 9〜10 行目: `finally:` の中は、`with` のまとまりを**抜けるとき**に必ず走ります。途中で失敗が起きても走ります。
- 13 行目: `async with life(None) as ctx:` で「入り」ます。6 行目が走り、`yield` で渡された値が `ctx` に入ります。`async with` は、`async` の付いた `with` 文です。
- 14 行目: 中の仕事をします。このあいだ、`life` は 8 行目で止まって待っています。
- 13〜14 行目のまとまりを抜けると、`life` が 8 行目の続きから再開し、10 行目が走ります。

本記録者が動かして確かめた出力の順番は、「yield の前（入るとき）」→「中の仕事。ctx = {'db': '接続'}」→「yield の後（出るとき）」でした（2026-10-01、Python 3.11）。

#### 言葉の整理 — 4 つの印

- **`async def`**
  - やさしい言い換え: 「待つ」ことができる関数を作る印。
  - 正確な定義: コルーチン関数を定義する。呼ぶとコルーチン（これから走る処理）が返り、`await` されたときに中身が走る。
  - 例: `async def fetch_number(): ...`。MCP のツールにも `async def` で書かれたものが多い。
- **`await`**
  - やさしい言い換え: 「呼んで、終わるまで待つ」。
  - 正確な定義: `async def` の関数の中で使い、コルーチンなどの処理を走らせて、その結果を受け取るまで待つ。待っているあいだ、プログラムはほかの仕事を進められる。
  - 例: `resp = await client.get(url)`。判定では「`client.get(url)` を呼んでいる」と読む。
- **`yield`**
  - やさしい言い換え: 値を渡して一時停止する印（しおり）。
  - 正確な定義: 関数の途中で値を呼び出し元に渡し、その位置で止まる。`yield` を含む関数はジェネレータになり、呼ぶと中身が走らずにジェネレータのオブジェクトが返る。
  - 例: 小さな例 2 の `steps`。
- **`@asynccontextmanager`**
  - やさしい言い換え: 「入る・出る」の形を作る道具。
  - 正確な定義: `yield` を 1 回だけ含む `async def` の関数を、`async with` 文で使える形に変えるデコレータ。`yield` の前が入るときの処理、後が出るときの処理になる。`try:` と `finally:` で `yield` を囲めば、中で失敗が起きても後片付けが走る。
  - 例: 小さな例 3 の `life`。lifespan の典型の形。

`async` の無い版の `@contextmanager`（`contextlib.contextmanager`）もあり、同じく `yield` の前と後で入る・出るを作ります。
v4 の wikimind のように、`@contextlib.asynccontextmanager` と、箱の名前を付けたまま書くこともあります。意味は同じです。

#### lifespan は、これらの印の組み合わせ

[第 3 章](ch03.md) 3.9 節で見た lifespan は、小さな例 3 と同じ形です。
違いは、`with` 文を書くのが自分ではなく、**サーバの側**だということです。

`FastMCP("x", lifespan=app_lifespan)` のように、サーバを作るときに `lifespan=` で関数を渡しておきます。
サーバが動き出すと、SDK の中のコードが、小さな例 3 の 13 行目にあたる処理を行います。
公式 SDK 1.30.0 では、低レベルの `Server` の `run` の中で、次の順に進みます。

1. 662 行: `async with AsyncExitStack() as stack:`（入る・出るをまとめて管理する入れ物を用意する）。
2. 663 行: `lifespan_context = await stack.enter_async_context(self.lifespan(self))`（lifespan に**入る**。`yield` の前が走る）。
3. 681 行: `async for message in session.incoming_messages:`（クライアントから届いた要求を 1 つずつ読む繰り返し。`tools/call` もここで処理される）。

つまり、**lifespan の `yield` の前が終わらないと、要求を読む繰り返しが始まりません**。
もし `yield` の前で失敗（例外）が起きたら、663 行で失敗が伝わり、681 行には進みません。
そのときサーバはツールを 1 つも受け付けずに止まります。
（出典: SDK 1.30.0 の `mcp/server/lowlevel/server.py:662-663,681`（本記録者が 2026-10-01 に開いて確かめた。repo の外のファイル）。`FastMCP` の `lifespan` の引数は[第 3 章](ch03.md) 3.9 節）

#### 実物の例 1 — v4 の wikimind の lifespan

v4 の木 wikimind（最終評価のデータではありません）の MCP サーバの lifespan です。

```python

63  async def _lifespan(_server: FastMCP) -> AsyncIterator[dict[str, Any]]:
64      """Initialize database on MCP server startup."""
65      settings = get_settings()
66      settings.ensure_dirs()
67      await init_db()
68      log.info("WikiMind MCP server started")
69      yield {}
 ...
72  mcp = FastMCP(
73      name="wikimind",
 ...
81      lifespan=_lifespan,
```

- 62 行: `@contextlib.asynccontextmanager` です。`contextlib.` が付いているだけで、小さな例 3 の `@asynccontextmanager` と同じです。
- 63 行: `async def` の関数です。名前は `_lifespan` です。`-> AsyncIterator[...]` は「この関数が何を返すか」の注釈（型の注釈）で、動作には影響しません。
- 64 行: 説明文（docstring）です。「MCP サーバの起動時にデータベースを初期化する」と書いてあります。
- 65〜66 行: 設定を読み、`ensure_dirs()` で必要なディレクトリを作ります。
- 67 行: `await init_db()` でデータベースを初期化します。
- 68 行: ログに「起動した」と書きます（出力先は 9.5 節の方法で確かめます）。
- 69 行: `yield {}` で一時停止し、サーバに「準備ができた」と伝えます。ここから、ツールの受付が始まります。`yield` の後に何も書いていないので、終了時の後片付けはありません。
- 72〜81 行: サーバの本体を作るときに `lifespan=_lifespan` と渡しています。

だから、66 行と 67 行の初期化は、**どの起動の形でも、最初のツールの呼び出しより前に済みます**。
67 行の `init_db` は、9.2 節で見る `@lru_cache` の付いた関数を通ってディレクトリを作ります。その話は 9.2 節で続けます。
（出典: `corpus/v4-manavgup__wikimind/src/wikimind/mcp/server.py:62-69,72-73,81`）

v3 の木 overleaf の lifespan は、もっと長い準備をしています（短くしたものです）。

#### 実物で lifespan を探す方法 — grep と、その落とし穴

木の中で lifespan を探すには、文字列を探すコマンド `grep` を使います（`grep` の使い方は 9.10 節でまとめます）。
手引きの下書きは、「`FastMCP(` / `Server(` の引数の `lifespan=` を探し、その関数の中を見る」と書いています。

```bash
grep -rn 'lifespan=' corpus/<木> --include='*.py'          # lifespan= を渡している行を探す
grep -rn 'FastMCP(\|Server(' corpus/<木> --include='*.py'  # サーバを作っている行を探す
```

- `-r`: フォルダの中を全部探す。`-n`: 行番号を付ける。`--include='*.py'`: Python のファイルだけを探す。
- `'FastMCP(\|Server('` の `\|` は「または」です。`FastMCP(` か `Server(` を含む行を探します。

本記録者が 2026-10-01 に v4 の木で実際に走らせた結果を 3 つ示します。

**shyhurricane で `lifespan=` を探す**:

```
corpus/v4-double16__shyhurricane/mcp_service.py:133:        lifespan="on",
corpus/v4-double16__shyhurricane/shyhurricane/mcp_server/__init__.py:173:    lifespan=app_lifespan,
```

2 行見つかりましたが、**MCP のサーバに lifespan の関数を渡しているのは 2 行目だけ**です。
1 行目の `mcp_service.py:133` は、`uvicorn`（HTTP でサーバを公開するための別のライブラリ）の設定 `Config(..., lifespan="on", ...)` の一部です。
右辺は関数ではなく、`"on"` という文字列です。
同じファイルの 138 行の `Server(uv_cfg)` も、`from uvicorn import Config, Server`（14 行）で持ってきた uvicorn の `Server` で、MCP の `Server` ではありません。

**shyhurricane で `FastMCP(` か `Server(` を探す**（テストのファイルを除いた 3 行）:

```
corpus/v4-double16__shyhurricane/mcp_service.py:138:    uv_server = Server(uv_cfg)
corpus/v4-double16__shyhurricane/shyhurricane/mcp_server/__init__.py:116:class ShyHurricaneFastMCP(FastMCP):
corpus/v4-double16__shyhurricane/shyhurricane/mcp_server/__init__.py:171:mcp_instance = ShyHurricaneFastMCP(
```

- 1 行目: 上で見た uvicorn の `Server` です。MCP のサーバではありません。
- 2 行目: `class ShyHurricaneFastMCP(FastMCP):` は、`FastMCP` をもとに**新しいクラスを作る**行です。サーバを作る行ではありません。`FastMCP(` という文字が含まれるので当たりました。
- 3 行目: `ShyHurricaneFastMCP(` も、`FastMCP(` を含むので当たりました。これが本当にサーバを作る行です。この呼び出しの 173 行に、上の `lifespan=app_lifespan` があります。

#### lifespan が「必ず」済ませるかを読む — 条件と失敗

lifespan を見つけたら、問題の初期化が `yield` より前で**必ず**走るかを読みます。
次の 3 つの作例を比べてください。

```python
# 作例 A: 条件なしで呼ぶ
@asynccontextmanager
async def app_lifespan(server):
    _ensure_index()                       # 必ず走る
    yield {}

# 作例 B: 環境変数があるときだけ呼ぶ
@asynccontextmanager
async def app_lifespan(server):
    if os.environ.get("PREBUILD"):        # 運用者が PREBUILD を設定したときだけ
        _ensure_index()
    yield {}

# 作例 C: 失敗しても先に進む
@asynccontextmanager
async def app_lifespan(server):
    try:
        _ensure_index()
    except Exception:
        pass                              # 失敗を握りつぶして、何もしない
    yield {}
```

- 作例 A: `yield` の前で、条件なしに `_ensure_index()` を呼びます。失敗すれば、上で見た SDK の 663 行で失敗が伝わり、サーバは受付を始めません。だから、受付が始まったなら初期化は済んでいます。
- 作例 B: `if os.environ.get("PREBUILD"):` の中だけで呼びます。`os.environ.get("PREBUILD")` は「環境変数 `PREBUILD` の値を取る。無ければ `None`」という意味です。運用者が `PREBUILD` を設定しなければ、lifespan は初期化を呼ばずに `yield` に進みます。そのときは、最初のツールの呼び出しで初期化が走りえます。
- 作例 C: `try:` の中で呼び、`except Exception: pass` で失敗を**握りつぶして**います（`pass` は「何もしない」という文）。初期化が途中で失敗しても、lifespan は `yield` に進み、サーバは受付を始めます。そのときも、最初のツールの呼び出しで初期化がもう一度試されえます。

手引きの下書きは、「lifespan が初期化を**必ず**済ませるか（例外で抜けたら受付が始まらないか、条件つきではないか）も見る。条件つきなら、条件が偽のときはツールの呼び出しで届くので『到達する』」と書いています。
作例 B のような形の扱いは、[第 49 章](ch49.md)で学びます。
（出典: `docs/drafts/final_judging_guide_draft.md:293-294`）

#### なぜそうするのか — 判定の規則（D67 の 2）とのつながり

[第 3 章](ch03.md) 3.8 節で見たとおり、最終評価の判定では、「一度だけの初期化」がどこで先に済んでいるかで、「到達するか」の答えを分けると決めました（D67 の 2）。

- `main()` の中だけ、または `if __name__ == "__main__":` の中だけで先に済ませている → ④ の起動では `main()` を通らないので、最初のツールの呼び出しで初期化が走りうる（到達する）。
- lifespan の中で先に済ませている → どの起動の形でも受付より前に走る（到達しない）。
- モジュールの読み込み時に済ませている → 読み込んだ時点で走る（到達しない）。
- 読み切れない → 不明。

この規則を当てるには、「その初期化は lifespan の `yield` の前で、必ず呼ばれているか」を、コードから正確に読む必要があります。
しかも、手引きは「起動の方法はコードだけから決める」としています。README の説明や、作者の意図は使いません。
だから、この節の 4 つの印を読めることが、判定の前提になります。
（出典: `docs/decisions.md:3773`（D67 の 2）、`docs/drafts/final_judging_guide_draft.md:281`（起動の方法はコードだけから決める）、`:283-288`（表））

#### よくある誤解・つまずき

- **誤解: 「`await` の付いた行は、ふつうの呼び出しとは別物」**
  `await f(x)` は「`f(x)` を呼んで、終わるのを待つ」です。呼び出しであることは同じです。道筋をたどるときは、`await` を外して読んで構いません。
- **誤解: 「`async def` の関数を呼べば、その場で中身が走る」**
  呼んだだけでは走りません（小さな例 1）。ただし実際のコードでは、ほとんどが `await f()` と書いて、その場で走らせます。`asyncio.create_task(f())` のように「別の仕事として始める」書き方もあります。
- **誤解: 「`lifespan=` と書いてあれば、MCP の lifespan」**
  uvicorn の `lifespan="on"`（文字列の設定）や、FastAPI の `lifespan=` もあります。渡している相手が MCP のサーバ（`FastMCP(...)`・`Server(...)`、またはそれをもとに作ったクラス）かを確かめます。
- **誤解: 「`lifespan` という名前の関数があれば、それが lifespan」**
  名前は関係ありません。サーバを作るときに `lifespan=` で**渡されている**関数だけが、そのサーバの lifespan です。逆に、`_lifespan` や `app_lifespan` のように、名前が少し違うこともあります。
- **つまずき: 「`yield` の後に書いた初期化も、起動時に走る」**
  `yield` の後は終了時です。lifespan の中にあっても、`yield` の後（`finally:` の中など）の処理は、ツールの受付が終わった後に走ります。
- **つまずき: 「サーバは 1 つだけ」**
  overleaf のように、子のサーバを `mount` でつなぐ木があります。ツールが登録されているサーバの lifespan を読みます。

#### 手作業ではどう使うか

判定の手順 D で道筋の途中に「一度だけの初期化」（9.2 節）を見つけ、その初期化がツールの受付より前に済んでいるかを確かめるときに、この節を使います。

1. `grep -rn 'lifespan=' corpus/<木> --include='*.py'` で、lifespan を渡している行を探す。
2. 見つかった行を 1 行ずつ開き、渡している相手が MCP のサーバかを確かめる（uvicorn・FastAPI などを除く）。
3. ツールがどのサーバに登録されているかを確かめる（`@mcp.tool` の `mcp` がどのサーバか。`mount` で子のサーバがあれば、その lifespan も）。
4. そのサーバの lifespan の関数を開き、`yield` より**前**に、問題の初期化を呼んでいるかを読む。
5. その呼び出しが条件つき（`if` の中）でないか、失敗を握りつぶしていないかを読む。
6. lifespan が見つからなければ、`main()` や `if __name__ == "__main__":`、モジュールの一番上で初期化していないかを読む（9.2 節）。

結論の付け方（到達する / しない / 不明）は[第 49 章](ch49.md)で学びます。
ここでは、**根拠として、lifespan のファイルと行、`yield` の行、初期化を呼ぶ行を書き留める**ことを覚えてください。

#### この節のまとめ

`async def` は「待てる関数」、`await` は「呼んで待つ」、`yield` は「値を渡して一時停止」、`@asynccontextmanager` は「`yield` の前を入るとき、後を出るときにする道具」。
lifespan はこの組み合わせで、サーバは lifespan に入ってから要求を読み始めるので、`yield` の前はツールの受付より前に必ず済む。
grep の `lifespan=` は uvicorn・FastAPI にも当たるので、見つかった行は相手を確かめる。初期化が条件つきか、失敗を握りつぶしていないかも読む。

### 9.2 一度だけの初期化 — `global`、`is None`、`@lru_cache`、シングルトン

#### 一言で言うと

「最初の 1 回だけ準備して、2 回目からは準備済みのものを使う」書き方には、いくつかの形があります。
代表は、`global` と `if _x is None:` の組み合わせ、`@functools.lru_cache`、シングルトン、キャッシュを返す関数の 4 つです。
判定では、**その準備がツールの呼び出しより前に必ず済んでいるか**と、**どこかで準備前の状態に戻されないか**を確かめます。

#### たとえ話 — 職場のポットのお湯

職場の給湯室にポットがあるとします。
朝いちばんに来た人は、ポットが空なので、お湯を沸かします。
2 人目からは、もう沸いているお湯をそのまま使います。

ここで大事なのは、次の 2 点です。

- **誰が最初に沸かすか**: 早出の当番が始業前に沸かしておく日もあれば、当番が来ない日もあります。当番が来ない日は、最初にお茶を飲みに来た人が沸かします。
- **お湯が捨てられることはないか**: 誰かが途中でお湯を捨てたら、次に来た人がまた沸かします。

コードの「一度だけの初期化」も同じです。
「沸かす」がディレクトリの作成やデータベースの準備のような**環境を変える操作**だと、それを「誰が・いつ」するかで、判定の答えが変わります。
始業前の当番が lifespan（9.1 節）や `main()`（[第 3 章](ch03.md) 3.8 節）、最初にお茶を飲みに来た人が最初のツールの呼び出しにあたります。

#### 小さな例 — `global` と `is None`

判定の手引きの下書きが例に挙げている形です（作例）。

```python
1  _memory = None                 # モジュールの一番上: 最初は「まだ無い」
2
3  def _ensure_memory():
4      global _memory             # この関数の中の _memory は、モジュールの _memory のこと
5      if _memory is None:        # まだ作っていなければ
6          _init()                # ← 効果（ディレクトリの作成など）はこの中
7      return _memory
```

#### 一歩ずつ — 1 行ずつの意味

- 1 行目: モジュールの一番上で、`_memory` に `None` を入れます。「まだ準備していない」という印です。名前の先頭の `_` は「このモジュールの中だけで使う」という作者の目印で、動作には影響しません。
- 3 行目: 準備を確かにする関数 `_ensure_memory` を作ります。
- 4 行目: `global _memory` は、「この関数の中で `_memory` という名前を使ったら、モジュールの一番上の `_memory` のことだ」という宣言です。
- 5 行目: `_memory` がまだ `None` なら、6 行目を実行します。この `if` が「**守り**」です。
- 6 行目: `_init()` で準備をします。手引きの作例では、この中でディレクトリを作るなどの効果が起きる、としています。`_init()` の中で `_memory` に準備済みのオブジェクトが入ります。
- 7 行目: 準備済みの `_memory` を返します。

この関数を 2 回呼ぶと、次のように動きます。

| 呼び出し | 5 行目の `_memory is None` | 6 行目の `_init()` |
|---|---|---|
| 1 回目（まだ誰も準備していない） | 真 | **走る**（効果が起きる） |
| 2 回目以降 | 偽 | 走らない |
| 誰かが `_memory = None` に戻した後の、次の 1 回 | 真 | **また走る** |

表の読み方: 1 行目は「まだ誰も準備していない状態で 1 回目に呼ぶと、守りの条件が真になり、`_init()` が走って効果が起きる」と読みます。
3 行目は、準備した後でも、どこかで `None` に戻されれば、次の呼び出しでもう一度効果が起きる、という意味です。
（出典: `docs/drafts/final_judging_guide_draft.md:272-278`（作例のコード）、`:295-296`（`None` に戻すと再び届く））

#### 言葉の整理 — 大域変数・`global`・守り

- **大域変数**（モジュール水準の変数）
  - やさしい言い換え: そのファイルのどの関数からも見える変数。
  - 正確な定義: モジュールの一番上（どの関数の中でもない位置）で値を入れた変数。そのモジュールが読み込まれているあいだ、値が残り続ける。
  - 例: 上の 1 行目の `_memory`。
- **`global` 文**
  - やさしい言い換え: 「この名前は、関数の外の大域変数のことだ」という宣言。
  - 正確な定義: 関数の中で `global 名前` と書くと、その関数の中でその名前に代入したとき、関数の中だけの変数を作らずに、モジュールの大域変数を書き換える。読むだけなら `global` は要らない。
  - 例: 上の 4 行目。
- **守り**（この教科書での呼び方）
  - やさしい言い換え: 「まだなら準備する」の `if`。
  - 正確な定義: 準備済みかどうかを調べる条件で、一度だけの初期化を囲むもの。`if _x is None:`、`if not self._initialized:` などの形がある。
  - 例: 上の 5 行目。手引きの下書きは、こうした形をまとめて「一度だけ」の守りと呼んでいる。

#### `global` を忘れるとどうなるか

作例です。

```python
1  _x = None
2
3  def no_global():
4      if _x is None:      # ← ここで失敗する
5          _x = 1
```

`global _x` を書かずに、関数の中で `_x = 1` と代入すると、Python は「`_x` はこの関数の中だけの変数だ」と決めます。
すると、4 行目で `_x` を読もうとした時点では、関数の中の `_x` にはまだ何も入っていないので、失敗（`UnboundLocalError`）になります。
本記録者が動かして確かめたところ、`no_global()` を呼ぶと実際に `UnboundLocalError` になりました（2026-10-01、Python 3.11）。

判定で大事なのは逆の向きです。
**`global` が書いてあれば、その関数は大域変数を書き換えています**。
`global _memory` の後に `_memory = None` と書いてある関数は、準備済みの状態を「まだ準備していない」に戻す関数です。

#### 同じ働きの別の書き方 1 — `@functools.lru_cache`

作例です。

```python
1  import functools
2
3  @functools.lru_cache(maxsize=1)
4  def get_engine():
5      os.makedirs(DB_DIR, exist_ok=True)     # 環境を変える操作
6      return create_engine(DB_DIR)
```

- 3 行目: `@functools.lru_cache` は、「関数の結果を覚えておき、同じ引数でもう一度呼ばれたら、中身を走らせずに覚えた結果を返す」デコレータです。`maxsize=1` は「1 つ分だけ覚える」という指定です。
- 4〜6 行目: 引数の無い関数なので、「同じ引数」は毎回同じです。だから、**中身が走るのは最初の 1 回だけ**です。

本記録者が動かして確かめたところ、`@functools.lru_cache(maxsize=1)` を付けた引数の無い関数を 2 回呼ぶと、中身は 1 回だけ走りました。
その後で `関数名.cache_clear()` を呼んで覚えた結果を消すと、次の呼び出しで中身がもう一度走りました（2026-10-01、Python 3.11）。
つまり、`cache_clear()` は、`_memory = None` と同じく「準備前に戻す」操作です。

実物は v4 の wikimind です（短くしたものです）。

- 108〜116 行: `get_engine` は、SQLite を使う設定なら、115 行で DB のディレクトリを作ります。
- 119〜122 行: `get_async_engine` に `@functools.lru_cache(maxsize=1)` が付いています。最初の 1 回だけ `get_engine()` が走り、2 回目からは覚えた結果が返ります。説明文にも「シングルトン（ただ 1 つ）のエンジン」とあります。

#### 同じ働きの別の書き方 2 — シングルトン

作例です。

```python
1  class Store:
2      _instance = None
3
4      def __new__(cls):
5          if cls._instance is None:                 # 最初の 1 回だけ
6              cls._instance = super().__new__(cls)
7              cls._instance._setup()                # ← ここで初期化（ファイルの作成など）
8          return cls._instance                      # 2 回目からは同じものを返す
```

- 1〜2 行目: `Store` というクラスを作り、クラスに付いた値 `_instance` を `None` で始めます。
- 4 行目: `__new__` は、`Store()` と書いてオブジェクトを作るときに、最初に呼ばれる特別なメソッドです。
- 5〜7 行目: まだ作っていなければ、オブジェクトを作り、`_setup()` で初期化します。
- 8 行目: 作ったオブジェクトを返します。2 回目からは 5 行目が偽なので、同じオブジェクトをそのまま返します。

**シングルトン**とは、「そのクラスのオブジェクトをプログラム全体で 1 つしか作らない」作り方です。
`Store()` を何回書いても、初期化（7 行目）は最初の 1 回だけです。
書き方は違っても、「`None` なら作る」という守りは同じです。

#### もう一度走る場合 — `None` に戻す・期限が切れる

一度だけの初期化が、**ツールの呼び出しの途中でもう一度走る**形もあります。
実物は v4 の pronote です。

```python
# src/pronote_mcp/client.py

16   _cached: tuple[pronotepy.Client, float] | None = None
 ...

65       global _cached
66
```

この形は、手引きの条件の種類の表にある「失敗・期限切れ（トークンの更新、再試行、エラー時の後始末）」に近い形です。条件の種類の付け方は[第 49 章](ch49.md)で学びます。

#### なぜそうするのか — 手引きが「一度だけ」の守りを名指しする理由

解析器は、各ツールの呼び出しを、**サーバの状態（どの変数に何が入っているか）を仮定せずに**読みます。
だから、`if _memory is None:` の守りがあっても、「`_init()` に届く道がある」と読みます。
これは静的解析としては筋の通った読み方ですが、実際には起動時に済んでいて、ツールの呼び出しでは届かないことがあります。
v4 では、本記録者が判定した D1・D2 の矛 60 件のうち、誤（解析器の誤り）14 件の中の 9 件が、この「起動時の初期化」の類でした（ccr 6 件、shyhurricane 3 件。数は抜き取りのもので、母集団の割合の推定ではありません。v4 の数字は論文に使いません）。

そこで手引きの下書きは、手順 D の 4 で「道筋の途中に『一度だけ』の守り（`if self._x is None:`、`@lru_cache`、`global _initialized`）があれば、その初期化がツールの呼び出しより前に必ず済んでいるかを確かめる」と名指ししています。
さらに、「初期化が済んでいても、その後にどこかで `None` に戻すなら、ツールの呼び出しで再び届く。戻す箇所が無いかを grep で確かめる」と書いています。
この節の 4 つの書き方は、どれもこの確かめの対象です。
（出典: `docs/open_questions.md:1188`（O43 の起動時の初期化の類。V2 の誤 9）、`docs/population_v4.md:87-101`（[第 3 章](ch03.md) 3.8 節で引用した数）、`docs/decisions.md:3754`（D66 の 5、論文に使わない）、`docs/drafts/final_judging_guide_draft.md:141-142`（手順 D の 4）、`:295-296`（`None` に戻す））

#### よくある誤解・つまずき

- **誤解: 「守りがあるから、効果は最初の 1 回しか起きない。だから気にしなくてよい」**
  「最初の 1 回」がツールの呼び出しの中で起きうるなら、そこで環境が変わります。判定では「何回起きるか」ではなく「ツールの呼び出しで起きうるか」を問います（[第 49 章](ch49.md)）。
- **誤解: 「`_memory = None` という行が見つかったら、必ずもう一度走る」**
  その行が**いつ**走るかを確かめます。shyhurricane のように `@atexit.register` の中なら、プロセスの終了時だけです。wikimind の `cache_clear()` も、終了時の後片付けの中でした。
- **誤解: 「`global` が無い関数は、大域変数に触れていない」**
  読むだけなら `global` は要りません（ccr の 550 行）。また、`_srv._memory = None` のように**モジュールの名前を付けて**書き換える形には `global` は要りません。grep では `_memory = None` の形で探します（9.10 節）。
- **つまずき: `if not _cache:` と `if _cache is None:` の違い**
  `if not _cache:` は、`_cache` が `None` のときだけでなく、空の辞書 `{}` や空のリスト `[]` のときにも真になります。だから、準備した結果が空のままなら、**毎回**準備が走ることがあります。守りの条件は正確に読みます。
- **つまずき: 「`@lru_cache` は引数があっても 1 回だけ」**
  引数があるときは、**引数の組ごとに** 1 回です。`maxsize` を超えると古いものを忘れ、また走ります。引数の無い関数なら、`cache_clear()` されない限り 1 回です。

#### 手作業ではどう使うか

判定の手順 D で、道筋の途中に一度だけの守りを見つけたら、次の順で確かめます。

1. **守りの形を特定する**: `global` と `is None`・`@lru_cache`・シングルトン・キャッシュを返す関数のどれか。守りの変数の名前（`_memory`・`_server_context` など）を書き留める。
2. **先に済ませている場所を探す**: lifespan（9.1 節）、`main()`・`if __name__ == "__main__":`（[第 3 章](ch03.md) 3.7 節）、モジュールの一番上。grep で守りの関数の名前（`_init(`・`get_server_context(` など）を探し、呼び出し元を全部見る（9.10 節）。
3. **戻す場所を探す**: `grep -rn '_memory = None' corpus/<木> --include='*.py'` や `grep -rn 'cache_clear' corpus/<木> --include='*.py'` で、準備前に戻す行を探す。見つかったら、その行が**いつ**走るか（ツールの道筋の中か、終了時か、テストか）を確かめる。
4. **根拠を書き留める**: 守りの行、先に済ませる行、戻す行（または「戻す行は無い」と確かめた grep の命令）を、ファイルと行で書く。

### 9.3 `open` のモード — 読むのか、消して書くのか、足すのか

#### 一言で言うと

`open(パス, モード)` の**モード**は、ファイルをどう開くかを決める 1〜3 文字の指定です。
`'r'` は読む、`'w'` は**中身を全部消してから**書く、`'a'` は末尾に足す、`'x'` は新しく作る（あれば失敗）、`'r+'` は読み書き（消さずに上書き）です。
判定では、モードを見て「読むだけか」「前の中身を壊すか」「繰り返すと増えるか」の 3 つを区別します。

#### たとえ話 — ノートの使い方

1 冊のノートを、5 通りの使い方で使うことを考えます。

- `'r'`: ノートを**読むだけ**。何も書かない。ノートが無ければ読めない。
- `'w'`: ノートの全ページを**破り捨ててから**、1 ページ目から書く。ノートが無ければ新しく買う。
- `'a'`: 書いてある最後のページの**続きに書き足す**。前のページはそのまま。ノートが無ければ新しく買う。
- `'x'`: **新しいノートを買って**書く。同じ名前のノートがもう棚にあれば、買わずにやめる（失敗）。
- `'r+'`: 今あるノートの 1 ページ目から、**上から重ね書き**する。破らないので、書かなかった所は前のまま残る。ノートが無ければやめる（失敗）。

「破り捨てるか」「続きに書くか」「新しく買うか」は、ノートの持ち主にとって大きな違いです。
ファイルも同じで、前からある中身が消えるか残るかが、宣言（とくに「壊さない」という D2）への反し方を決めます。

#### 小さな例 — `open` のいろいろな書き方

作例です。

```python
1  open(path)                     # モードを書かなければ 'r'（読む）
2  open(path, "w")                # 書く（中身を消してから）
3  open(path, mode="a")           # キーワードでも書ける
4  with open(path, "wb") as f:    # 'b' はバイト列として扱う
5      f.write(data)
6  Path(path).write_text(text)    # pathlib の書き方。'w' と同じ
7  Path(path).open("a")           # pathlib の open。モードは 1 つ目の引数
8  shutil.copy(src, dst)          # src を dst にコピーする
```

#### 一歩ずつ — 1 行ずつの意味

- 1 行目: モードを書かないと、`'r'`（読む）になります。
- 2 行目: 2 つ目の引数 `"w"` がモードです。
- 3 行目: `mode="a"` のように、名前を付けて渡すこともできます。2 つ目の位置ではなく、離れた位置に書かれることもあるので、`mode=` を見落とさないようにします。
- 4〜5 行目: `"wb"` の `b` は、文字ではなく**バイト列**（0〜255 の数の並び。画像や pickle のデータなど）として扱う、という意味です。`w` の意味（消してから書く）は変わりません。
- 6 行目: `pathlib`（パスをオブジェクトとして扱う、Python に最初から入っている部品の箱）の `write_text` は、`'w'` で開いて書くのと同じです。前の中身は消えます。`write_bytes` も同じです。
- 7 行目: `Path(path).open("a")` は、`pathlib` の `open` です。**モードが 1 つ目の引数**になる点が、組み込みの `open(path, mode)` と違います。
- 8 行目: `shutil.copy(src, dst)` は、`dst` が無ければ作り、あれば上書きします。

#### モードの表

| モード | 意味 | ファイルが無いとき | ファイルがあるとき | 前の中身 |
|---|---|---|---|---|
| `'r'`（既定） | 読む | 失敗する | 開く | そのまま |
| `'w'` | 書く | 作る | 開く | **全部消してから書く** |
| `'a'` | 末尾に足す | 作る | 開く | そのまま。**末尾に足す** |
| `'x'` | 新しく作って書く | 作る | **失敗する** | （あれば失敗するので触れない） |
| `'r+'` | 読み書き | 失敗する | 開く | 消さない。**書いた所だけ上書き** |
| `'w+'` | 読み書き | 作る | 開く | **全部消す** |
| `'a+'` | 読む + 末尾に足す | 作る | 開く | そのまま。末尾に足す |

表の読み方: 1 行が 1 つのモードです。左から、意味、ファイルが無いときの動き、あるときの動き、前の中身がどうなるか、を書いています。
たとえば `'x'` の行は「`'x'` で開くと、ファイルが無ければ新しく作って書く。もうあれば失敗して、何も書かない。だから前からある中身には触れない」と読みます。

`'b'` の付いた形（`'rb'`・`'wb'`・`'ab'`・`'xb'`・`'r+b'` など）は、バイト列として扱うだけで、上の意味は変わりません。
`'t'`（文字として扱う）は既定なので、ふつうは書きません。
`'+'` は「読み書きの両方」を表し、`'r+'`・`'w+'`・`'a+'` の形で使います。

#### 動かして確かめた 5 つの事実

本記録者は、表のうち間違えやすい所を、作業用の場所で実際に動かして確かめました（2026-10-01、Python 3.11、Linux）。

1. 中身のあるファイルを `'x'` で開くと、`FileExistsError`（ファイルがもうある、という失敗）になった。
2. 無いファイルを `'r+'` で開くと、`FileNotFoundError`（ファイルが無い、という失敗）になった。
3. 中身が `abc` のファイルを `'r+'` で開いて `Z` を書くと、中身は `Zbc` になった。つまり、先頭から重ね書きし、残りは消えない。
4. 中身が `abc` のファイルを `'w'` で開いて、**何も書かずに**閉じると、中身は空になった。つまり、`'w'` は開いた時点で中身を消す。
5. 中身が `abc` のファイルを `'a'` で開き、先頭に戻る命令（`f.seek(0)`）をしてから `Q` を書いても、中身は `abcQ` になった。つまり、`'a'` で書いたものは、いつも末尾に足される。

4 番目は、判定で大事です。
`open(path, "w")` の行があれば、その後に `write` が無くても、**開いた時点で前の中身は消えます**。

#### 解析器はモードをどう読むか

本記録者は、凍結版の解析器（`analyzer-freeze-3`。`git diff analyzer-freeze-3 -- authgap/` が空であることを確かめてから）で、モードだけを変えた作例のツールを走査しました（2026-10-01）。
書き先はどれも定数のパス（`"/tmp/fixed_w.txt"` のような、コードに書いた決まった場所）です。
結果は次のとおりでした。

| モード | 効果の種類 | D1（読むだけ） | D2（壊さない） | D4（繰り返しても同じ） |
|---|---|---|---|---|
| `'r'`（既定） | FS_READ（読み取り） | 何も出ない | 何も出ない | 何も出ない |
| `'w'` | FS_WRITE（書き込み） | 矛（`fs_write`） | 不（`fs_writeout`） | 何も出ない |
| `'r+'` | FS_WRITE | 矛（`fs_write`） | 不（`fs_writeout`） | 何も出ない |
| `'a'` | FS_WRITE | 矛（`fs_write`） | 何も出ない | 矛（`fs_append`） |
| `'x'` | FS_WRITE | 矛（`fs_write`） | 何も出ない | 何も出ない |
| 変数（`"a" if append else "w"`） | FS_READ と FS_WRITE の 2 つ | 矛（`fs_write`） | 不（`fs_unknown`） | 不（`fs_mode_unknown`） |

表の読み方: 1 行が 1 つのモードで、右の 3 列が、宣言ごとに解析器が出したものです。かっこの中は、解析器が付けた理由のコード（[第 17 章](ch17.md)）です。
たとえば `'a'` の行は「`'a'` で書くと、D1 のツールでは矛（理由 `fs_write`）、D2 のツールでは何も出ない（追加だけなので内）、D4 のツールでは矛（理由 `fs_append`。繰り返すと追記が重なる）」と読みます。
`'w'` の D2 が不（`fs_writeout`）なのは、書き先が定数のとき、そこに呼び出しの前からファイルがあるか（上書きか新規作成か）が、静的には分からないからです。

最後の行のように、**モードが変数で決まる**形では、解析器はモードを読めません。
そのため、読み取りと書き込みの両方の可能性を出し、D2 と D4 では不（理由に `unknown` が付く）にしました。
この扱いは、判定表（`docs/contradiction_principles.md` §7）の「mode 不明」の行と合っています。
なお、D1 の列は、`readOnlyHint=True` だけを書いた作例で、D2・D4 の列は `readOnlyHint=False, destructiveHint=False, idempotentHint=True` と書いた作例で確かめました（D1 があると D2・D4 は意味を持たないため。[第 4 章](ch04.md)）。
（出典: 判定表は `docs/contradiction_principles.md:166`（D1 の FS_WRITE すべて → 矛）、`:185`（D2 の追記型 `open('a' / 'x')` → 内）、`:187`（D2 の書き出し `open('w' / '+')` → 書き先が MODEL 由来なら矛、それ以外は不）、`:188`（mode 不明）、`:220-221`（D4 の `'a'` → 矛、mode 不明 → 不）。理由のコードの一覧は `docs/drafts/final_judging_guide_draft.md:208-212`。sink 表で `builtins.open` の既定が `'r'` でモードを 2 つ目の引数から読むことは `authgap/catalog/sinks.py:313-321`）

#### なぜそうするのか — モードで 3 つのことが決まる

判定では、モードを見て次の 3 つを区別します。
詳しい規則は、効果の種類（[第 13 章](ch13.md)）、判定表（[第 17 章](ch17.md)）、宣言ごとの問い（[第 50 章](ch50.md)）で学びます。

1. **読むのか、書くのか**。`'r'` なら書き込みではありません。手引きの下書きも、手順 C で「`builtins.open` なら開くモード（`'w'`・`'a'`・`'x'`・`'r+'` など）。読み取り（`'r'`）なら書き込みではない」と書いています。D1（読むだけ）のツールでは、書き込みならどのモードでも宣言に反する、と手引きは決めています（ログ・キャッシュ・一時ファイルも含む）。
2. **前からあるものを壊すか**。`'w'`・`'w+'` は前の中身を消し、`'r+'` は書いた所を上書きし、`'a'`・`'x'` は消しません。D2（壊さない）の問いは「呼び出しの前からあったものを消す・上書きする・変えるか。新しく足すだけなら反しない」なので、この差が効きます。
3. **繰り返すと増えるか**。`'a'` で同じ行を書けば、2 回呼ぶと 2 行になります。`'w'` で同じ内容を書けば、2 回呼んでも結果は同じです。`'x'` は 2 回目に失敗します。D4（同じ引数で繰り返しても追加の効果が無い）の問いでは、この差が効きます。
（出典: `docs/drafts/final_judging_guide_draft.md:122`（手順 C のモード）、`:315`（D1 の表。FS_WRITE すべて）、`:335`（D2 の問い）、`:367-381`（D4 の問いと表））

#### よくある誤解・つまずき

- **誤解: 「`'r+'` は `r` が付いているから読むだけ」**
  `'r+'` は読み書きです。書き込みもでき、書いた所は上書きされます（事実 3）。`r` の字に引かれて読み取りと取り違えやすいので注意します。
- **誤解: 「`'w'` で開いても、`write` しなければ何も変わらない」**
  `'w'` は開いた時点で中身を消します（事実 4）。
- **誤解: 「`'a'` は前の中身を変えないから、どの宣言にも反しない」**
  D2 には反しませんが、D1（読むだけ）には反します（書き込みなので）。D4 では、繰り返すと追記が重なるなら反します。宣言ごとに答えが違います。
- **つまずき: `mode=` のキーワードを見落とす**
  `open(path, encoding="utf-8", mode="w")` のように、`mode=` が後ろのほうにあることがあります。2 つ目の位置に無いからといって、既定の `'r'` だと思い込まないようにします。
- **つまずき: 条件でモードが変わる形を片方だけ見る**
  `open(path, "a" if append else "w")` は、`append` が真なら `'a'`、偽なら `'w'` です。両方を考えます。
- **つまずき: `flock` のために `'a'` で開く形**
  ファイルの錠（`fcntl.flock`。同時に書かないための印）を取るためだけに `'a'` で開き、何も書かない形があります。v3 では、解析器がこれを D4 の追記として矛にした誤りが 1 件ありました。これを宣言に反しないとする扱いは[第 50 章](ch50.md)で学びます。
（出典: `flock` の誤りは `docs/open_questions.md:1067`（O41））

#### 手作業ではどう使うか

判定の手順 C（効果の行を開き、本当にその操作かを確かめる）で、site が `builtins.open`（または `pathlib.Path.open`・`io.open`）の組に出会ったら、次を確かめます。

1. **モードの引数を特定する**: 組み込みの `open` なら 2 つ目の位置か `mode=`、`Path.open` なら 1 つ目の位置か `mode=`。
2. **モードが定数か変数か**: 変数なら、その変数に何が入りうるかをさかのぼって読む。
3. **モードの表に当てる**: 読むだけか、前の中身を消すか、足すか、新しく作るか。
4. **書き先を確かめる**: 1 つ目の引数のパスが、モデルの引数から作られるか、定数か。これは D2 の判定で効きます（[第 50 章](ch50.md)）。

もし開いた行が `'r'` で、解析器の言う書き込みではなかったら、それは解析器の読み違いです。
誤の原因の分類（[第 51 章](ch51.md)）の E8 には「読み取りのモード」が例として挙がっています。
（出典: `docs/drafts/final_judging_guide_draft.md:122`、`:442`（E8））

#### この節のまとめ

`'r'` 読む、`'w'` 開いた時点で中身を消して書く、`'a'` 末尾に足す、`'x'` 新しく作る（あれば失敗）、`'r+'` 消さずに上書き。`'b'` はバイト列にするだけで意味は変えない。
判定ではモードで「読むか書くか」（D1）、「前の中身を壊すか」（D2）、「繰り返すと増えるか」（D4）を分ける。
モードが変数なら解析器は読めず不にする。`mode=` のキーワードと `Path.open` の引数の位置に注意する。

### 9.4 ファイルとディレクトリの作成・削除・置き換え

#### 一言で言うと

ファイルやディレクトリを作る・消す・名前を変える・置き換える関数には、決まった名前があります（`os.makedirs`・`os.remove`・`shutil.rmtree`・`os.rename`・`os.replace` など）。
関数ごとに、「前からあるものを消すか」が違います。
また、**解析器の一覧（sink 表）に載っていない関数**（`tempfile.mkstemp`・`Path.touch`・`Path.rename` など）もあり、それは解析器の出力に出てきません。

#### たとえ話 — 引っ越しの片付け

引っ越しの片付けを考えます。

- 新しい段ボール箱を組み立てる（ディレクトリを作る）。前からある箱には触れません。
- 要らない物を 1 つ捨てる（ファイルを消す）。
- 押し入れの中身を、箱ごと全部捨てる（ディレクトリを中身ごと消す）。
- 箱の名札を「台所」から「物置」に付け替える（名前を変える）。もし「物置」という箱がもうあったら、そちらは捨てることになります（置き換え）。

もう 1 つ、上手な片付けの技があります。
新しい本棚を、**まず別の部屋で組み立てておき**、できあがってから古い本棚と一気に入れ替えるやり方です。
組み立ての途中で手を止めても、部屋には「古い本棚」か「新しい本棚」のどちらかがあり、組み立てかけの本棚が置かれることはありません。
これが、後で見る **atomic write** の考え方です。

#### 小さな例 — 作る・消す・置き換える

作例です。

```python
1  os.makedirs(d, exist_ok=True)     # d を作る（途中のディレクトリも作る）。あってもエラーにしない
2  os.remove(p)                      # ファイル p を消す（os.unlink も同じ）
3  shutil.rmtree(d)                  # ディレクトリ d を中身ごと消す
4  os.rename(a, b)                   # a を b という名前に変える
5  os.replace(a, b)                  # a を b という名前に変える。b があれば置き換える
6  fd, tmp = tempfile.mkstemp()      # 他と重ならない名前の一時ファイルを作り、(番号, パス) を受け取る
```

#### 一歩ずつ — 1 行ずつの意味

- 1 行目: `os.makedirs(d, exist_ok=True)` は、ディレクトリ `d` を作ります。`d` が `a/b/c` のように深い場所なら、途中の `a` や `a/b` も作ります。`exist_ok=True` は「もうあってもエラーにしない（何もしない）」という指定です。
- 2 行目: `os.remove(p)` は、ファイル `p` を消します。`os.unlink(p)` も同じ働きです。
- 3 行目: `shutil.rmtree(d)` は、ディレクトリ `d` を、中のファイルやディレクトリごと全部消します。`shutil` は、ファイルのまとまった操作をする、Python に最初から入っている部品の箱です。
- 4 行目: `os.rename(a, b)` は、`a` を `b` という名前に変えます（別のディレクトリへ移すこともできます）。
- 5 行目: `os.replace(a, b)` も名前を変えますが、`b` がもうあれば、それを**置き換えます**。
- 6 行目: `tempfile.mkstemp()` は、ほかと重ならない名前で一時ファイルを作り、2 つの値を返します。1 つ目はファイルの番号（OS がファイルを指すために使う数）、2 つ目はパスです。`fd, tmp = ...` は、2 つの値をそれぞれ `fd` と `tmp` に入れる書き方です。

本記録者が Linux で動かして確かめたところ、`os.rename(a, b)` は、`b` がもうあるとき、何も言わずに `b` を置き換えました（`b` の中身が `a` の中身になり、`a` は無くなった）。
`os.replace(a, b)` と `shutil.copy(c, b)` も、`b` を上書きしました（2026-10-01、Python 3.11）。
なお、Python の説明書によれば、Windows では `os.rename` は `b` があると失敗し、`os.replace` はどの OS でも置き換えます。

#### 言葉の整理 — ディレクトリ・一時ファイル・atomic write

- **ディレクトリ**
  - やさしい言い換え: フォルダ。
  - 正確な定義: ファイルや別のディレクトリを入れる入れ物。パスの `/` で区切られた途中の部分。
  - 例: `/home/user/.aws/aws-api-mcp` は、`.aws` の中の `aws-api-mcp` というディレクトリ。
- **一時ファイル**
  - やさしい言い換え: 作業のあいだだけ使う、使い捨てのファイル。
  - 正確な定義: 処理の途中のデータを置くために作り、処理が終わったら消すことを前提にしたファイル。`tempfile` の関数は、OS の一時領域（Linux ではふつう `/tmp`）に、ほかと重ならない名前で作る。
  - 例: `tempfile.mkstemp(prefix="ozon-sync-worker-", suffix=".pkl")`。
- **atomic write**（不可分な書き込み）
  - やさしい言い換え: 途中で止まっても、ファイルが中途半端にならない書き方。
  - 正確な定義: まず一時ファイルに全部書き、最後に `os.replace` で本物のファイルと入れ替える書き方。入れ替えは一瞬で起きるので、読む側からは「古い中身」か「新しい中身」のどちらかしか見えない。
  - 例: 下の ccr の `_atomic_write`。

#### なぜそうするのか — 同じ呼び出しで作って消すものの扱い

同じ呼び出しの中で作って消す一時ファイルは、宣言によって扱いが分かれます。
手引きの下書きは、次のように書いています。

- **到達はする**。ツールの呼び出しで起きる操作だからです。
- **D1（読むだけ）では反する**。手引きの D1 の表では、「ファイルの書き込み・作成・削除・移動・権限の変更（FS_WRITE すべて）」が「反する」とされ、注に「ログ・キャッシュ・一時ファイル・ディレクトリの作成も含む」とあります。
- **D2（壊さない）では反しない**。D2 の問いは「呼び出しの前からあったものを消す・上書きする・変えるか」です。自分が同じ呼び出しで作った一時ファイルは、呼び出しの前には無かったからです。ただし、**前の呼び出しが残したファイル**を消すなら、それは呼び出しの前からあったものなので反します。

v4 の判定（本記録者が付けた考え方の例）では、ru-marketplace の `os.remove`（233 行）は、D1 のツール `ozon_reviews` の組（M58）として「正」とされ、手引きの例の表には「D2 なら E2 で誤になる形」と書かれています。
E2 は、人が判定して解析器の誤りとしたときに付ける原因の記号の 1 つで、「同じ呼び出しで作った一時ファイル・ロックの後始末（D2）」です（[第 51 章](ch51.md)）。

#### よくある誤解・つまずき

- **誤解: 「`os.makedirs(..., exist_ok=True)` は、もうあれば何もしないから、環境を変えない」**
  無ければ作ります。最初の 1 回は環境が変わります。D1（読むだけ）のツールでは、ディレクトリの作成も「反する」に含まれます（手引きの D1 の表の注）。
- **誤解: 「`os.rename` は名前を変えるだけだから、何も消さない」**
  行き先 `b` がもうあれば、Linux などでは `b` の前の中身が消えます。`os.replace` はどの OS でも置き換えます。
- **誤解: 「一時ファイルは環境を変えないから、どの宣言にも反しない」**
  D1 では反し、D2 では（同じ呼び出しで作ったものなら）反しない、と宣言で分かれます。どちらかに決めつけません。
- **誤解: 「解析器の出力に何も出ていないなら、ファイルを作っていない」**
  `Path.touch`・`tempfile.mkstemp`・`Path.rename`・`shutil.copytree`・`wave.open` などは、解析器の一覧に無いので出てきません。コードに書いてあれば、自分で気づく必要があります。
- **つまずき: atomic write の 2 つの書き込みを 1 つと数える**
  atomic write には、一時ファイルへの書き込み（367 行）と、本物の置き換え（371 行）があります。本物の前の中身が消えるのは 371 行です。判定のときは、どちらの行の話かを分けて書きます。

#### 手作業ではどう使うか

- **手順 C**（効果の行を開く）: site が `os.replace`・`os.remove` などなら、**何を**消す・置き換えるのかを読みます。それが「同じ呼び出しで作った一時ファイル」か「呼び出しの前からあるファイル」かで、D2 の答えが変わります（[第 50 章](ch50.md)）。
- **手順 D**（道筋をたどる）: 一時ファイルの名前がどこで作られたか（`mkstemp` か、決まった名前の `path + ".tmp"` か）をさかのぼります。決まった名前の一時ファイルは、前の呼び出しが失敗して残したものと重なる可能性があります。
- **見落としの判定**（[第 52 章](ch52.md)）: 解析器の一覧に無い関数（表の「無い」の行）が、ツールの道筋にあれば、解析器の出力に無くても書き出します。見落としの原因の分類では「語彙」（sink の語彙に無いライブラリ）に当たる形です。
（出典: 見落としの原因の分類は `docs/drafts/final_judging_guide_draft.md:473-475`）

#### この節のまとめ

`makedirs`・`mkdir` は作るだけ、`remove`・`unlink`・`rmtree` は消す、`rename`・`replace`・`copy`・`move` は行き先を上書きしうる。
atomic write は一時ファイルに書いてから `os.replace` で本物を置き換える。本物の前の中身が消えるのは置き換えの行。
同じ呼び出しで作って消す一時ファイルは、D1 では反し、D2 では反しない（前の呼び出しが残したものは別）。`mkstemp`・`Path.touch`・`Path.rename` などは解析器の一覧に無く、出力に出ない。

### 9.5 ログの出力先 — ファイルか、標準エラーか

#### 一言で言うと

ログ（プログラムが残す記録）は、**出力先の設定**によって、ファイルに書かれることも、標準エラーに流れるだけのこともあります。
ログを書く行（`logger.info(...)` など）だけを見ても、どちらかは分かりません。
設定は、ツールの関数の中ではなく、**モジュールの一番上や設定用のファイル**にあることが多いので、そこまで探します。

#### たとえ話 — 声に出すか、日誌に書くか

仕事の途中で「今、A さんの注文を受けました」と記録したいとします。
方法は 2 つあります。

- **声に出して言う**: その場にいる人には聞こえますが、何も残りません。部屋の中の物は何も変わりません。
- **業務日誌に書く**: 日誌のページに 1 行増えます。後から読み返せます。日誌という物が変わります。

ログも同じです。
**標準エラー**に流すのは「声に出す」ことで、ディスクのファイルは変わりません。
**ファイル**に書くのは「日誌に書く」ことで、ファイルが変わります。
そして、「声に出すか、日誌に書くか」は、記録する人（`logger.info` の行）ではなく、**事前の決まり（出力先の設定）**で決まります。

#### 言葉の整理 — 標準の出入り口とログの仕組み

- **標準出力・標準エラー・標準入力**（[第 3 章](ch03.md) 3.7 節の復習）
  - やさしい言い換え: プログラムの「口」（2 つ）と「耳」（1 つ）。
  - 正確な定義: プログラムが起動したときに最初から用意されている 3 つの通り道。標準出力は結果を出す口、標準エラーはエラーや記録を出すもう 1 つの口、標準入力は外からデータを受け取る耳。どれも**ファイルではなく、プロセスの出入り口**で、画面や、別のプログラム（パイプの先）につながる。
  - 例: stdio で動く MCP サーバでは、標準出力と標準入力が MCP のやり取りそのものに使われる。そのため、ログは標準エラーに出すのがふつう。
- **ログとロガー**
  - やさしい言い換え: 記録と、記録係。
  - 正確な定義: ログは、プログラムが動作の様子を残す記録。ロガーは、ログを受け取って出力先に渡すオブジェクトで、`logging.getLogger(名前)` で取り出す。`logger.info(...)`・`logger.error(...)` などで記録を渡す。
  - 例: `log = logging.getLogger(__name__)` の後の `log.info("called")`。
- **ハンドラ**（出し口）
  - やさしい言い換え: 記録をどこに出すかを決める部品。
  - 正確な定義: ロガーに付ける部品で、受け取った記録を実際に書き出す。`logging.FileHandler(パス)` はファイルに、`logging.StreamHandler()` は（引数が無ければ）標準エラーに書く。1 つのロガーに複数のハンドラを付けられ、そのときは全部に書かれる。
  - 例: `logger.addHandler(logging.FileHandler("app.log"))`。
- **loguru**（ログル）
  - やさしい言い換え: `logging` とは別の、人気のあるログのライブラリ。
  - 正確な定義: `from loguru import logger` で使う。`logger.add(出力先)` で出し口を足し、出力先が `sys.stderr` なら標準エラー、**パスならファイル**に書く。最初から標準エラーの出し口が 1 つ付いている。
  - 例: `logger.add("/var/log/app.log", rotation="10 MB")`。

#### 小さな例 — 出力先を決める 7 つの書き方

作例です。

```python
1  import logging, sys
2
3  logging.basicConfig(level=logging.INFO)                    # 出力先の指定なし → 標準エラー
4  logging.basicConfig(filename="app.log")                    # filename あり → ファイル
5  handler = logging.FileHandler("app.log")                   # ファイルに書く出し口
6  handler = logging.StreamHandler()                          # 標準エラーに書く出し口（既定）
7  handler = logging.StreamHandler(sys.stdout)                # 標準出力に書く出し口
8
9  from loguru import logger
10 logger.add(sys.stderr, level="INFO")                       # loguru: 標準エラー
11 logger.add("/var/log/app.log", rotation="10 MB")           # loguru: ファイル
```

#### 一歩ずつ — 1 行ずつの意味

- 3 行目: `logging.basicConfig(...)` は、ログの基本の設定をまとめてする関数です。`filename=` を渡さないと、**標準エラー**に書く出し口を付けます。`level=logging.INFO` は「INFO 以上の重さの記録を出す」という指定です。
- 4 行目: `filename="app.log"` を渡すと、`app.log` という**ファイル**に書く出し口を付けます。
- 5 行目: `logging.FileHandler("app.log")` は、`app.log` に書く出し口を作ります。作っただけでは使われず、`ロガー.addHandler(handler)` で付けて初めて使われます。
- 6 行目: `logging.StreamHandler()` は、引数が無ければ標準エラーに書く出し口です。
- 7 行目: `logging.StreamHandler(sys.stdout)` は、標準出力に書く出し口です。
- 10 行目: loguru で、標準エラーに書く出し口を足します。
- 11 行目: loguru で、ファイル `/var/log/app.log` に書く出し口を足します。`rotation="10 MB"` は「10 MB を超えたら新しいファイルに切り替える」という指定です。

#### 動かして確かめた 5 つの事実

本記録者は、作業用の場所で次のことを確かめました（2026-10-01。`logging` は Python 3.11、loguru は 0.7.3）。

1. `logging.basicConfig(level=logging.INFO)` だけを呼ぶと、ルートのロガーに付いた出し口は `StreamHandler` 1 つで、その出力先は標準エラーだった。
2. すでに出し口が付いた後で `logging.basicConfig(filename="ignored.log")` を呼んでも、**何も起きず**、ファイルは作られなかった。`basicConfig` は、出し口がまだ無いときだけ働く。

#### 解析器はログをどう扱うか

**解析器の一覧（sink 表）には、`logging` や loguru によるファイルへの書き込みが入っていません**。
本記録者が 2026-10-01 に `authgap/catalog/sinks.py` を `logging`・`FileHandler`・`loguru`・`basicConfig` で検索すると、0 件でした。
さらに、モジュールの一番上で `logging.basicConfig(filename=...)`・`FileHandler`・`logger.add(<パス>)` を設定し、ツールの中で `log.info(...)` と `logger.info(...)` を呼ぶ作例を凍結版の解析器で走査すると、そのツールには効果が 1 つも出ませんでした。

だから、ログのファイルへの書き込みは、**解析器の出力にまず出てきません**。
見落としの判定で、人が気づくべき代表的な形です。
v4 の中間検証でも、この形が「sink 語彙に無いログの出力先」として O43 に記録されました。
O43 は同時に、「ログの枠組みの書き込みを宣言違反に数えるかは原理で明示されていない」とも書いています。
これに対して手引きの下書きは、D1 の迷いやすい形として「標準出力・標準エラーへのログ: ファイルではないので反しない（`logging` の出力先がファイルなら反する。出力先の設定を確かめる）」と書いています。
ログの書き込みを違反として扱うことの是非（実世界での扱い）は、[第 43 章](ch43.md)で見ます。
（出典: `docs/open_questions.md:1193`（O43 のログの出力先）、`docs/drafts/final_judging_guide_draft.md:329`（D1 の迷いやすい形））

#### なぜそうするのか — モジュール水準の設定まで探す理由

ログの設定は、プログラム全体で 1 回だけ行うのがふつうです。
だから、ツールの関数の中ではなく、モジュールの一番上、設定用のファイル（bugasura の `config.py`）、`main()` などに置かれます。
ツールの本体と、その呼び出し先を深さ 4 までたどっても、**設定の行はその道筋に出てきません**。
それでも、ツールの中の `logger.info(...)` の 1 行が、設定によってはファイルへの追記になります。

手引きの下書きは、見落としの判定の注意として「ログの出力先がファイルかどうかは、`logging.basicConfig(filename=…)`、`FileHandler`、loguru の `logger.add(<パス>)` など、**モジュール水準の設定**も確かめる（v4 の R19 はモジュールの一番上で設定していた）」と書いています。
（出典: `docs/drafts/final_judging_guide_draft.md:490-491`）

#### よくある誤解・つまずき

- **誤解: 「`logger.info(...)` はファイルに書く命令」**
  出力先は設定で決まります。標準エラーだけなら、ファイルは変わりません。
- **誤解: 「`logging.basicConfig(level=...)` があるから、ログはファイルに書かれる」**
  `filename=` が無ければ標準エラーです（事実 1）。
- **誤解: 「ツールの関数の中にログの設定が無いから、ファイルには書かない」**
  設定はモジュールの一番上や別のファイルにあることが多いです（mcp-aws・bugasura）。
- **誤解: 「`print(...)` はログだからファイルに書く」**
  `print` は、`file=` を指定しなければ標準出力に書きます。ファイルではありません。ただし `print(..., file=f)` で `f` が開いたファイルなら、ファイルに書きます。
- **つまずき: 「ロガーの名前が違えば、設定も無関係」**
  `logging` のロガーには親子の関係があり、名前の付いたロガーの記録は、ふつうルートのロガー（`basicConfig` が出し口を付ける相手）にも渡ります。ルートに付いた出し口がファイルなら、名前の付いたロガーの記録もファイルに書かれます。設定を探すときは、ルートの設定（`basicConfig`・`logging.getLogger()`）も見ます。
- **つまずき: 水準で落とされる記録**
  事実 4 のとおり、水準より軽い記録は書かれません。ただし、水準が環境変数などで変えられるなら、設定しだいで書かれます。手引きの下書きは、水準については名指しで書いていません。この点で判定が決まらない事例に出会ったら、事実を `evidence` と `note` に書き、手引きの 22 節（手引きで決まらない事例）の扱いに従います（[第 52 章](ch52.md)）。

#### 手作業ではどう使うか

ツールの道筋にログの呼び出し（`logger.xxx(...)`・`log.xxx(...)`・`logging.xxx(...)`）を見つけたら、次の順で出力先を確かめます。

1. **ロガーの出どころを確かめる**: その `logger` は、`logging.getLogger(...)` か、`from loguru import logger` か、別のファイルから import したものか。たとえば bugasura では、`tools/testpert.py` が `from client import logger`（22 行）、`client.py` が `from config import API_BASE, logger`（9 行）と、2 段で `config.py` のロガーを持ってきています。import をさかのぼって、設定のあるファイルにたどり着きます。
2. **出力先の設定を探す**: 木の中を `grep -rn 'basicConfig\|FileHandler\|RotatingFileHandler\|logger.add(' corpus/<木> --include='*.py'` で探す。見つかった行のファイル・場所（モジュールの一番上か、関数の中か）・条件（`if` の中か）を書き留める。
3. **出力先を決める**: 標準エラー・標準出力だけならファイルを変えない。ファイルなら、そのパス（どのディレクトリの、どの名前か）を書く。
4. **条件を書く**: bugasura のように環境変数で有効になるなら、その名前（`LOG_PATH`）を書く（[第 49 章](ch49.md)の運用者の設定）。
5. **解析器の出力と比べる**: 解析器はこれを出さないので、見落としの判定では「見落とし（原因は語彙）」の候補になります（[第 52 章](ch52.md)）。

#### この節のまとめ

ログの書き込み先は、書く行ではなく出力先の設定で決まる。`basicConfig` は `filename=` が無ければ標準エラー、`FileHandler` と loguru の `logger.add(<パス>)` はファイル。
設定はモジュールの一番上や設定用のファイルにあることが多いので、そこまで探す。標準出力・標準エラーならファイルは変わらない。
解析器の一覧にはログの書き込みが無く、出力にまず出ないので、見落としの判定で人が気づく必要がある。

### 9.6 子プロセス — 起動、標準入力への書き込み、`shlex.quote`

#### 一言で言うと

プログラムは、別のプログラム（**子プロセス**）を起動できます。
起動のしかたには、「リストで渡す」形と、「1 本の文字列をシェルに渡す」形（`shell=True`）があります。
子の**標準入力**にデータを流し込む書き込み（`proc.stdin.write(...)`・`proc.communicate(input=...)`）は、**それ自体はファイルの書き込みではありません**。
子がそのデータで何をするかで決まります。

#### たとえ話 — 下請けに仕事を頼む

あなたが、下請けの業者に仕事を頼むとします。

- **指示書の決まった欄に書いて渡す**（リストで渡す形）: 「作業名」の欄に「棚の組み立て」、「場所」の欄に「2 階の倉庫」と書きます。欄が分かれているので、「場所」の欄に何を書いても、それが作業名として読まれることはありません。
- **電話で一続きに伝える**（`shell=True` の形）: 「2 階の倉庫で棚の組み立て」と一続きに話し、相手が区切って解釈します。もし場所の名前に「、それから 1 階の荷物を全部捨てて」と紛れ込んでいたら、相手はそれも作業として聞き取ってしまうかもしれません。
- **材料を手渡す**（標準入力に流す）: 業者に材料の箱を渡します。箱を渡しただけでは、あなたの倉庫は何も変わりません。業者がその材料で何を作るか、どこに置くかで、結果が決まります。

`shlex.quote` は、電話で伝えるときに「ここからここまでが場所の名前です」と、かぎかっこで囲んで伝える工夫にあたります。

#### 言葉の整理 — 子プロセス・シェル・パイプ・引用

- **子プロセス**
  - やさしい言い換え: プログラムが起動した、別のプログラム。
  - 正確な定義: あるプロセス（動いているプログラム）が OS に頼んで起動した、別のプロセス。起動した側を親と呼ぶ。Python では `subprocess.run`・`subprocess.Popen`・`asyncio.create_subprocess_exec` などで起動する。
  - 例: `subprocess.run(["git", "log"])` は、`git` を子プロセスとして起動する。
- **シェル**
  - やさしい言い換え: コマンドの文字列を読んで、区切って実行する係のプログラム。
  - 正確な定義: `sh`・`bash` など、コマンドの文字列を解釈するプログラム。`;`・`&&`・`|` などの記号で、複数のコマンドを続けたりつないだりできる。
  - 例: `ls; rm -rf x` は、シェルにとって「`ls` を実行し、次に `rm -rf x` を実行する」の 2 つのコマンド。
- **パイプ**
  - やさしい言い換え: プロセスどうしをつなぐ管。
  - 正確な定義: 一方が書いたデータを、もう一方が読めるようにする OS の仕組み。`stdin=subprocess.PIPE` と指定すると、子の標準入力が親とパイプでつながり、親が `proc.stdin.write(...)` や `proc.communicate(input=...)` で書いたデータを、子が標準入力から読む。
  - 例: 下の ru-marketplace の `proc.stdin.write(payload)`。
- **引用**（`shlex.quote`）
  - やさしい言い換え: 値を「ひとかたまり」としてシェルに渡すための囲み。
  - 正確な定義: `shlex.quote(値)` は、値をシェルにとって 1 つの引数になるように、必要なら引用符 `'…'` で囲んだ文字列を返す。値の中に `;` などがあっても、別のコマンドとして解釈されない。
  - 例: `shlex.quote("a; rm -rf x")` は `'a; rm -rf x'` を返す。

#### 小さな例 — 4 つの形

作例です（3 行目と 4 行目は、実行してはいけない危ない例を説明するためのもので、動かしていません）。

```python
1  subprocess.run(["git", "log"])                                  # リストで渡す
2  proc = subprocess.Popen(["sort"], stdin=subprocess.PIPE)
3  proc.communicate(input=b"b\na\n")                               # 子の標準入力にデータを流す
4  subprocess.run("ls " + path, shell=True)                        # 1 本の文字列をシェルに渡す
5  subprocess.run("op item get " + shlex.quote(name), shell=True)  # 値を引用してから渡す
```

#### 一歩ずつ — 1 行ずつの意味

- 1 行目: **リスト**で渡すと、最初の要素（`"git"`）が起動するプログラム、残り（`"log"`）がその引数になります。シェルは使いません。最初の要素を、この教科書では **argv0**（起動するプログラムの名前）と呼びます（[第 13 章](ch13.md)）。
- 2 行目: `sort`（受け取った行を並べ替えて出すプログラム）を起動し、`stdin=subprocess.PIPE` で子の標準入力を親とパイプでつなぎます。`proc` には、起動した子を扱うオブジェクトが入ります。
- 3 行目: `proc.communicate(input=...)` で、子の標準入力に `b"b\na\n"`（`b`、改行、`a`、改行のバイト列）を流し込み、子が終わるのを待ちます。`sort` は受け取った行を並べ替えて標準出力に出すだけで、ファイルは作りません。
- 4 行目: `shell=True` では、`"ls " + path` という 1 本の文字列を、シェルが読みます。もし `path` が `"x; rm -rf ~"` なら、シェルは `ls x` の後に `rm -rf ~`（ホームディレクトリを全部消す）も実行してしまいます。
- 5 行目: `shlex.quote(name)` で値を引用してから文字列につなぐと、`name` に `;` が入っていても、`op item get` の 1 つの引数として渡されます。起動されるコマンドの種類（`op`）は変わりません。

本記録者が動かして確かめたところ、`shlex.quote("a; rm -rf x")` は `'a; rm -rf x'`（引用符で囲まれた形）を、`shlex.quote("plain")` は `plain`（囲む必要が無いのでそのまま）を返しました。
また、`cat`（受け取ったものをそのまま出すプログラム）を `stdin=subprocess.PIPE` で起動し、`communicate(input=b"hi")` を呼ぶと、子の出力は `b'hi'` でした。`communicate(input=None)` を呼ぶと、子の出力は空（`b''`）でした。つまり、`input=None` のときは、子の標準入力には**何も書かれません**（2026-10-01、Python 3.11）。

#### 解析器は子の標準入力をどう扱うか

解析器は、`subprocess.Popen(...)`・`asyncio.create_subprocess_exec(...)`・`asyncio.create_subprocess_shell(...)` で起動した子のオブジェクトに対する `stdin.write(...)` と `communicate(input=...)` を、**パイプの効果**として記録します。
site 名は `pipe:write`・`pipe:communicate` です。

そのうえで、次のように種類を分けます。

- 起動が `shell=True`、または argv0 が**インタプリタ**（`sh`・`bash`・`python`・`python3`・`node`・`psql` など、受け取った文字をコードとして実行するプログラム）だと読めたとき → **EXEC**（コードの実行）。
- それ以外 → **FS_WRITE** の情報行（ファイルの書き込みの一種として扱う）。

ru-marketplace では argv0 が `sys.executable`（中身は Python ですが、コードの上では変数）で、解析器はそれを文字として読めないので、FS_WRITE の側に落ちました。
gemini の 204 行も、FS_WRITE の側として出ています（実物の例 2）。argv0 は、枝によって `"cmd"`（インタプリタの一覧に無い）か `GEMINI_PATH`（変数）です。

なぜ解析器は、ただのデータの受け渡しかもしれないものを「書き込み」として扱うのでしょうか。
理由は、**標準入力に流したデータが、子の中でファイルの書き込みやコードの実行に届く例がある**からです。
D61 の改訂は、インタプリタの一覧に無い argv0 でも、`env python3`（`env` を通して Python を起動する）、`xargs -0 rm`（受け取った名前のファイルを消す）、`tee /etc/app.conf`（受け取ったものをファイルに書く）のように、標準入力のデータがコードの実行やファイルの書き込みに届く例を挙げています。
v3 の確認の後、この扱いを直そうとした変更（D61 の G1）は、この理由で取り消され、「情報行は子プロセスがデータで何をしうるかの保守的な上界として正しい」とされました。
人の判定では、**子が何者で、受け取ったものをどう使うか**を調べて決めます。
（出典: `authgap/effects.py:803-851`（`_pipe`。`shell=True` かインタプリタなら EXEC、それ以外は FS_WRITE）、`authgap/catalog/sinks.py:623-625`（インタプリタの一覧）、`:648-650`（`stdin.write`・`communicate` の行）、`docs/decisions.md:3463-3467`（D61 の改訂。G1 の取り消し）、`docs/open_questions.md:1068-1070`（O41））

#### なぜそうするのか — 判定の手引きの考え方

手引きの下書きは、子プロセスについて 3 つのことを書いています。

1. **子の標準入力への書き込み**: 「それ自体はファイルを変えない。子プロセスがそれを受けて何をするかで決める」（D1 の迷いやすい形）。
2. **プロセスの起動（SPAWN）**: D1 では、「起動するコマンドをモデルが決められるなら反する。コマンドが定数なら、そのコマンドが実際に何をするかを調べ、環境を変えるなら反する・変えないなら反しない・分からなければ不明」。解析器は定数のコマンドを不にしますが、人は調べられる範囲で調べます。
3. **`shlex.quote` の誤り**: 誤の原因の E7 は「モデルが決められないのに決められるとした」で、例として「固定のコマンドに `shlex.quote` した値だけを渡す spawn など」が挙がっています。v3 では、解析器がこの形を「モデルが決めるコマンド」と読んだ誤りが 2 件ありました。`shlex.quote` で引用された値は、コマンドの引数にはなっても、**コマンドの種類を変えられない**からです。
（出典: `docs/drafts/final_judging_guide_draft.md:317`（D1 の SPAWN の行）、`:330`（子の標準入力）、`:441`（E7）、`docs/open_questions.md:1063`（O41。誤 2））

#### よくある誤解・つまずき

- **誤解: 「`pipe:write`・`pipe:communicate` はファイルへの書き込み」**
  子の標準入力への書き込みです。ファイルが変わるかは、子が何をするかで決まります。解析器は保守的に FS_WRITE として扱っています。
- **誤解: 「子の標準入力に流すだけなら、何をしても安全」**
  子が `tee 設定ファイル` なら受け取ったものをファイルに書き、子が `python3` ならコードとして実行します。子が何者かを必ず確かめます。
- **誤解: 「`communicate(...)` があれば、何かが書き込まれている」**
  `input=None`（または引数なし）なら、標準入力には何も書かれません。gemini の Windows 以外の枝がこの形です。v3 の helm / kubectl の誤り 4 件も、`communicate(input=None)` を書き込みの情報行にしたものでした。
- **誤解: 「`shell=True` なら必ずモデルがコマンドを決められる」**
  文字列の中身が定数なら、モデルは決められません。文字列のどの部分が、誰の決める値から来るかを読みます（[第 14 章](ch14.md)）。
- **つまずき: `*full_cmd` の `*`**
  `f(*xs)` は「リスト `xs` の要素を、1 つずつ別の引数として渡す」という書き方です。`asyncio.create_subprocess_exec(*full_cmd)` の argv0 は、`full_cmd` の最初の要素です。
（出典: helm / kubectl は `docs/open_questions.md:1068`）

#### 手作業ではどう使うか

- **手順 C**（効果の行を開く）: site が `pipe:write`・`pipe:communicate` なら、まず「子は何か」（argv0）を読み、次に「流すのはデータか、コードか」「`input` が `None` になる枝はあるか」を読みます。ファイルを変えるのが子の中なら、子が何をするかを調べて決めます（[第 50 章](ch50.md)の D1 の迷いやすい形、[第 51 章](ch51.md)の E5）。
- **SPAWN の不の組**（[第 52 章](ch52.md)の不の中身）: argv0 が定数なら、そのコマンドの説明書（`--help` や公式の文書）で、何をするプログラムかを調べます。調べても分からなければ「不明」にして理由を書きます。
- **`shlex.quote` を見たら**: 引用された値が、コマンドの種類（argv0 やシェルの文字列の先頭）を変えられるかを読みます。変えられないのに解析器が「モデルが決めるコマンド」としていたら、E7 の候補です（[第 51 章](ch51.md)）。

#### この節のまとめ

子プロセスはリストで渡す形と `shell=True` の形で起動する。`shell=True` では値の中の `;` が別のコマンドになりうるので、`shlex.quote` で引用する。
`proc.stdin.write(...)`・`communicate(input=...)` は子の標準入力への書き込みで、それ自体はファイルを変えない。`input=None` なら何も書かない。
解析器は保守的に FS_WRITE（シェル・インタプリタなら EXEC）として扱う。人は子が何者で、受け取ったものをどう使うかを調べて決める。

### 9.7 DB と HTTP の呼び出しの形

#### 一言で言うと

DB（データベース）への命令は、多くが `接続.execute(SQL の命令, 値)` の形です。
HTTP（ウェブの通信）は、多くが `requests.メソッド名(URL, ...)` か `クライアント.メソッド名(URL, ...)` の形です。
この節では、**呼び出しの形**と、**どの引数が何を決めるか**だけを覚えます。
SQL の命令や HTTP のメソッドの**意味**（読むだけか、相手を変えるか）は、[第 10 章](ch10.md)で説明します。

#### たとえ話 — 窓口の申込用紙と手紙

DB への命令は、役所の窓口に出す**申込用紙**に似ています。
用紙には「申込みの種類」（閲覧・登録・変更・削除）の欄と、「対象」（氏名・番号など）の欄が分かれています。
種類の欄を見れば、窓口の人は何をすればよいか分かります。
対象の欄に何が書いてあっても、それが「種類」として読まれることはありません。
SQL の命令が「種類」の欄、`?` に入る値が「対象」の欄にあたります。

HTTP の通信は、**手紙**に似ています。
宛先（URL）、用件の種類（メソッド: 見せてください・登録してください・消してください など）、同封する中身（本体）があります。
相手が何をするかは、用件の種類と、相手の決まり（API の文書）で決まります。

#### 小さな例 1 — sqlite3 で DB を使う

作例です。

```python
1  import sqlite3
2  conn = sqlite3.connect("notes.db")
3  rows = conn.execute("SELECT body FROM notes WHERE title = ?",
4                      (query,)).fetchall()
5  conn.execute("INSERT INTO log (q) VALUES (?)", (query,))
6  conn.commit()
7  conn.executescript("""CREATE TABLE IF NOT EXISTS t (x TEXT);
8                        CREATE INDEX IF NOT EXISTS i ON t(x);""")
```

#### 一歩ずつ — 1 行ずつの意味

- 1 行目: `sqlite3` は、ファイル 1 つで動く小さな DB（SQLite）を使うための、Python に最初から入っている部品の箱です。
- 2 行目: `sqlite3.connect("notes.db")` で、DB のファイル `notes.db` につなぎます。**ファイルが無ければ作ります**。返ってくる `conn` を「接続」と呼びます。
- 3〜4 行目: `conn.execute(SQL の命令, 値の組)` で命令を実行します。1 つ目の引数 `"SELECT body FROM notes WHERE title = ?"` が SQL の命令、2 つ目の `(query,)` が `?` の位置に入る値です（`(query,)` は値が 1 つだけの組の書き方）。`.fetchall()` で結果の行を全部受け取ります。
- 5 行目: 別の命令（`INSERT`）を実行します。
- 6 行目: `conn.commit()` で、ここまでの変更を DB に**確定**します。
- 7〜8 行目: `conn.executescript(...)` は、`;` で区切った**複数の命令をまとめて**実行します。`"""…"""` は、複数行にわたる文字列の書き方です。

本記録者が動かして確かめたところ、無いファイルを `sqlite3.connect(...)` でつなぐと、その時点でファイルが作られました（2026-10-01、Python 3.11）。

値を 2 つ目の引数で別に渡す書き方（**パラメータ**）には、大事な意味があります。
値の中に SQL の命令のような文字が入っていても、命令として解釈されません。
逆に、`conn.execute("SELECT ... WHERE title = '" + query + "'")` のように**値を命令の文字列につなぐ**と、値の中身が命令の一部になりえます。

#### 言葉の整理 — DB の言葉

- **DB（データベース）と SQL**
  - やさしい言い換え: 表の形でデータを貯める仕組みと、それに出す命令の言葉。
  - 正確な定義: DB は行と列の表（テーブル）でデータを保存する仕組み。SQL はその DB に命令する言葉で、命令の最初の語（`SELECT`・`INSERT`・`UPDATE`・`DELETE`・`CREATE`・`PRAGMA` など）で種類が決まる（[第 10 章](ch10.md)）。
  - 例: `SELECT body FROM notes WHERE title = ?`。
- **パラメータ**
  - やさしい言い換え: 命令とは別に渡す値。
  - 正確な定義: SQL の命令の `?`（DB によっては `%s` や `:name`）の位置に入る値。命令とは別の引数で渡し、命令の一部として解釈されない。
  - 例: `conn.execute("... WHERE title = ?", (query,))` の `(query,)`。
- **commit**（コミット）
  - やさしい言い換え: 変更の確定。
  - 正確な定義: それまでの変更を DB に確定させる操作。確定する前に接続を閉じると、変更は取り消されることがある。
  - 例: `conn.commit()`。

#### 実物の例 1 — v4 の geox

```python
91   def _get_connection() -> sqlite3.Connection:
92       """Get a connection to the resource registry database."""
93       conn = sqlite3.connect(REGISTRY_DB_PATH)
94       conn.row_factory = sqlite3.Row
95       conn.execute("PRAGMA journal_mode=WAL")
96       conn.execute("PRAGMA foreign_keys=ON")
97       return conn
```

- 93 行: 決まった場所の DB ファイルにつなぎます。
- 94 行: 結果の行を、列の名前で取り出せる形にする設定です。
- 95 行: `PRAGMA journal_mode=WAL` という命令を実行します。
- 96 行: `PRAGMA foreign_keys=ON` という命令を実行します。
- 97 行: 接続を返します。

95 行と 96 行は、どちらも `PRAGMA`（SQLite の設定の命令）ですが、**意味が違います**。
片方は DB のファイルに残る設定、もう片方はこの接続のあいだだけの設定です。
どちらがどちらで、それが判定にどう効くかは、[第 10 章](ch10.md)で説明します。
（出典: `corpus/v4-ariffazil__geox/src/geox_mcp/resource_registry.py:91-97`）

#### 解析器の表示名に注意 — sqlite3 なのに psycopg と出る

解析器の出力では、sqlite3 の `execute` が `psycopg.Cursor.execute` と表示されます。
psycopg は、PostgreSQL という別の DB を使うためのライブラリです。

これは、解析器の一覧の 1 行に、sqlite3 と psycopg の受け手の型（`sqlite3.Cursor`・`sqlite3.Connection`・`psycopg.Cursor`・`psycopg2.cursor`）を**まとめて**載せていて、効果の site 名を、その行の型の名前を並べ替えた最初のもの（`sorted(recv_types)[0]`）から取るためです。
4 つの名前を文字の順に並べると、`psycopg.Cursor` が最初に来ます。
つまり、表示名が psycopg でも、実際に呼んでいるのは sqlite3 の `execute` かもしれません。

手引きの下書きは、手順 C の注意として、「site 名のライブラリが違っていても（sqlite3 を psycopg と表示）、**動作の種類（kind）が合っていれば判定には影響しない**。その場合は `note` に書いておく」と書いています。
（出典: `authgap/catalog/sinks.py:504-510`（sqlite3 と psycopg をまとめた行）、`:514-517`（site 名は `sorted(recv_types)[0]` で決まるというコメント）、`docs/drafts/final_judging_guide_draft.md:126-127`）

#### 小さな例 2 — requests と httpx で HTTP を使う

作例です。

```python
1  import requests, httpx
2  requests.get(url, params={"q": q})               # GET
3  requests.post(url, json=payload)                 # POST（json= や data= で中身を送る）
4  requests.put(url, data=body)                     # PUT
5  requests.delete(url)                             # DELETE
6  requests.request("PATCH", url, json=p)           # メソッドを文字列で渡す形
7
8  client = httpx.AsyncClient(base_url="https://api.example.com/v1")
9  resp = await client.get("/items/" + item_id)     # 相対の URL。宛先は base_url につながる
10 resp = await client.request(method, url, json=p) # メソッドを変数で渡す形
```

#### 一歩ずつ — 1 行ずつの意味

- 2〜5 行目: `requests` の**関数の名前**が、そのまま HTTP の**メソッド**です（`get` → GET、`post` → POST、`put` → PUT、`delete` → DELETE）。1 つ目の引数が URL（宛先）です。`params=` は URL に付ける問い合わせの値、`json=`・`data=` は送る中身（本体）です。
- 6 行目: `requests.request("PATCH", url, ...)` は、メソッドを**1 つ目の引数の文字列**で渡す形です。URL は 2 つ目です。
- 8 行目: `httpx.AsyncClient(base_url=...)` で、通信の部品（クライアント）を作ります。`base_url` は、相対の URL の前に付ける基本の URL です。
- 9 行目: `client.get("/items/" + item_id)` は、`base_url` に相対の URL をつないだ先に GET を送ります。本記録者が httpx 0.28.1 で確かめたところ、`base_url="https://api.example.com/v1"` のクライアントで `"/items/42"` への要求を作ると、宛先は `https://api.example.com/v1/items/42` になりました（2026-10-01）。
- 10 行目: `client.request(method, url, ...)` は、メソッドを**変数**で渡す形です。`method` に何が入るかは、さかのぼって読まないと分かりません。

#### 実物の例 2 — v4 の bugasura（メソッドを呼び出し元が決める）

```python
# client.py
348  async def make_api_request(method: str, endpoint: str, api_key: str, **kwargs) -> dict:
 ...
```

- `client.py` の 348 行: `make_api_request` は、メソッド `method` と行き先 `endpoint` を引数で受け取ります。`**kwargs` は「残りの名前付きの引数をまとめて受け取る」書き方です。
- 478 行: `_get_http_client()`（同じファイルの 340 行。`httpx.AsyncClient` を返す関数）で通信の部品を取ります。
- 482 行: `client.request(method, url, ...)` で送ります。**この行だけでは、メソッドが何か分かりません**。

このように、**メソッドや宛先がどこで決まるか**は、呼び出し元までさかのぼって読みます。

#### 解析器の一覧にある HTTP、無い HTTP

解析器の一覧（sink 表）には、HTTP の書き方の**一部だけ**が入っています。

| 書き方 | 一覧にあるか |
|---|---|
| `requests.get`・`post`・`put`・`patch`・`delete`・`head`・`request` | ある |
| `httpx.get`・`httpx.post`・`httpx.request` | ある |
| `httpx.Client`・`httpx.AsyncClient`・`requests.Session` の `.get`・`.post`・`.request` | ある |
| 同じクライアントの `.put`・`.patch`・`.delete`・`.head`・`.options` | **無い** |
| `httpx.put`・`httpx.patch`・`httpx.delete` などのモジュールの関数 | **無い** |

表の読み方: 3 行目は「`httpx.AsyncClient` などのクライアントのオブジェクトの `.get`・`.post`・`.request` は、解析器が知っている」と読みます。4 行目は「同じクライアントでも、`.put`・`.delete` などは知らない。だから、これらを通る送信は効果として出てこない」と読みます。

本記録者は、凍結版の解析器で作例を走査して、この表を確かめました（2026-10-01）。
`readOnlyHint=True` のツールで `requests.delete(...)` を呼ぶと、D1 の矛（理由 `net_modify`）が出ました。
同じ宣言のツールで `httpx.Client().delete(...)` や `requests.Session().put(...)` を呼んでも、効果は 1 つも出ませんでした。

これは既知の限界 O39 です。
O39 は、「`DELETE` は D2（`destructiveHint`）の矛盾の典型なので、D2 の矛は下限になる（誤 clear の向き）」と書いています。
sink の語彙は凍結されているので、足しません（第 32・42 章）。
（出典: `authgap/catalog/sinks.py:379-399`（requests・httpx の関数の行）、`:537-559`（クライアントの `.get`・`.post`・`.request` の行）、`docs/open_questions.md:1041-1050`（O39））

#### なぜそうするのか — 形と意味を分けて読む理由

判定では、DB の効果なら「**どんな SQL の命令か**」が、HTTP の効果なら「**どのメソッドで、どこへ送るか**」が答えを分けます（[第 10 章](ch10.md)・[第 17 章](ch17.md)）。
そのためには、まず**どの引数が命令で、どの引数がメソッドで、どの引数が宛先か**を、形から正しく取り出せる必要があります。
`execute` の 1 つ目と 2 つ目を取り違えたり、`requests.request` の 1 つ目（メソッド）を URL と読んだりすると、意味の判断の前で間違えます。
この節で形を覚え、[第 10 章](ch10.md)で意味を覚える、という 2 段にしているのは、そのためです。

#### よくある誤解・つまずき

- **誤解: 「`sqlite3.connect(...)` は読むだけ」**
  ファイルが無ければ作ります。また、接続しただけでは何も変えなくても、その後の `execute` の命令しだいで DB が変わります。
- **誤解: 「`execute` の 2 つ目の引数が命令」**
  1 つ目が命令、2 つ目が `?` に入る値です。命令の種類は 1 つ目の最初の語で読みます。
- **誤解: 「site 名が psycopg だから、PostgreSQL の DB」**
  sqlite3 でも psycopg と表示されます。受け手（`conn` や `cursor`）が何から作られたかを見ます（`sqlite3.connect(...)` なら sqlite3）。
- **誤解: 「`client.request(method, ...)` は GET」**
  メソッドは変数です。呼び出し元までさかのぼって、何が渡るかを読みます。
- **誤解: 「解析器の出力に HTTP の効果が無いから、通信していない」**
  クライアントの `.put`・`.delete` などは一覧に無いので出てきません（O39）。
- **つまずき: `base_url` を見落とす**
  `client.get("/items/1")` だけを見ると、宛先のホストが分かりません。クライアントを作った行の `base_url=` まで戻ります。宛先が外か内か（D3）の判断に効きます（[第 50 章](ch50.md)）。

#### 手作業ではどう使うか

- **手順 C**（効果の行を開く）: DB の効果なら、`execute` の 1 つ目の引数（命令）を読み、命令の最初の語を書き留めます。命令が変数なら、さかのぼって中身を読みます。site 名のライブラリが違っていても、動作の種類が合っていれば `note` に書くだけにします。
- **手順 C**（HTTP の効果）: メソッド（関数名か、`request` の 1 つ目の引数）と宛先（URL と `base_url`）を書き留めます。
- **手順 D**（道筋をたどる）: メソッドや宛先が引数で渡ってくるなら、呼び出し元までさかのぼります（bugasura の 483 行のように）。
- **見落としの判定**（[第 52 章](ch52.md)）: クライアントの `.put`・`.delete` などが道筋にあれば、解析器の出力に無くても書き出します（原因は「語彙」の候補）。

#### この節のまとめ

DB は `接続.execute(命令, 値)`。命令の最初の語で種類が決まり、値は別に渡す。`connect` は無いファイルを作る。`executescript` は複数の命令をまとめて実行する。
HTTP は `requests.メソッド(URL, ...)` か `クライアント.メソッド(URL, ...)`。メソッドが変数なら呼び出し元までさかのぼり、宛先は `base_url` まで戻る。
sqlite3 の `execute` は psycopg と表示されるが、動作の種類が合えば判定に影響しない。クライアントの `.put`・`.delete` などは解析器の一覧に無い（O39）。

### 9.8 デコレータの wrapper — 本体より先に走るコード

#### 一言で言うと

デコレータは、**関数を受け取って、別の関数（wrapper、包み）を返す関数**です。
デコレータを付けた関数を呼ぶと、実際に走るのは wrapper で、wrapper の中の「本体を呼ぶ行」より前のコードは、**本体より先に**走ります。
解析器は、任意のデコレータの wrapper を呼び出しとしてたどりません。だから、wrapper の中の操作は、人が読んで見つける必要があります。

#### たとえ話 — 診察の前の受付

病院で「先生に診てもらう」とき、いきなり診察室に入るわけではありません。
まず受付で、看護師さんが検温や保険証の確認をします。
熱が高すぎれば、そこで別の窓口に回されて、先生には会いません。
問題が無ければ、診察室に通されます。

診察室の扉には先生の名札が掛かっていて、外から見ると「先生のところへ行く」ように見えます。
けれども、実際に最初に起きるのは受付での手続きです。

デコレータの wrapper は、この**受付**です。
本体（先生の診察）より先に走り、場合によっては本体を呼ばずに終わります。
`functools.wraps` は、受付の扉に先生の名札を掛けておく道具にあたります。

#### 小さな例 — ログインを確かめるデコレータ

作例です。

```python
1  import functools
2
3  def ensure_session(func):                     # デコレータの定義
4      @functools.wraps(func)
5      async def wrapper(*args, **kwargs):       # ← 本当に呼ばれるのはこの wrapper
6          await refresh_session_if_needed()     # ← 本体より先に走る
7          return await func(*args, **kwargs)    # ← ここで初めて本体が走る
8      return wrapper
9
10 @ensure_session
11 async def coupon_clipped(limit: int = 20):    # 本体
12     ...
```

#### 一歩ずつ — 1 行ずつの意味

- 3 行目: `ensure_session` は、関数 `func` を 1 つ受け取る関数です。これがデコレータです。
- 4 行目: `@functools.wraps(func)` は、次に作る `wrapper` に、本体 `func` の名前や説明文を写す道具です（下の「言葉の整理」）。
- 5 行目: `wrapper` という関数を、`ensure_session` の**中で**作ります（入れ子の関数）。`*args, **kwargs` は「どんな引数でもそのまま受け取る」書き方です。
- 6 行目: 本体を呼ぶ前に、`refresh_session_if_needed()`（説明用の名前。ログインの状態を確かめ、必要なら更新する関数だと思ってください）を呼びます。
- 7 行目: ここで初めて、本体 `func` を、受け取った引数のまま呼びます。
- 8 行目: 作った `wrapper` を返します。**本体ではなく wrapper を返す**のが要点です。
- 10〜11 行目: `@ensure_session` を本体 `coupon_clipped` に付けます。

10〜11 行目は、次の 2 行と**同じ意味**です。

```python
async def coupon_clipped(limit: int = 20): ...
coupon_clipped = ensure_session(coupon_clipped)
```

つまり、`coupon_clipped` という名前には、本体ではなく **wrapper** が入ります。
後で `coupon_clipped(...)` と呼ぶと、wrapper が走り、6 行目が先に、7 行目で本体が走ります。

本記録者が動かして確かめたところ、同じ形のデコレータ（`async` を外したもの）を付けた関数を呼ぶと、「wrapper の中の前処理」→「本体」の順に文字が出ました。
また、呼ばれた関数の `__name__`（名前）は本体の名前のままで、`__wrapped__`（包んだ元の関数を指す属性）が付いていました（2026-10-01、Python 3.11）。

#### 言葉の整理 — デコレータ・wrapper・`functools.wraps`

- **デコレータ**（[第 3 章](ch03.md) 3.3 節では「名札」と説明した）
  - やさしい言い換え: 関数に `@名前` で付けて、関数を加工する道具。
  - 正確な定義: 関数を 1 つ受け取り、何かを返す関数。`@d` を `def f` の上に書くと、`f = d(f)` と同じ意味になる。返すものが元の関数そのままなら「登録だけ」、別の関数なら「包む（wrap する）」デコレータ。
  - 例: `@mcp.tool()`（登録だけ）、`@ensure_session`（包む）。
- **wrapper**（包み）
  - やさしい言い換え: 本体の前後に処理を足すために、本体を包んだ関数。
  - 正確な定義: デコレータの中で作られ、本体の代わりに返される関数。中で本体を呼ぶことが多いが、条件によっては呼ばないこともある。
  - 例: 上の 5〜7 行目の `wrapper`。
- **`functools.wraps`**
  - やさしい言い換え: wrapper に本体の名札を付け替える道具。
  - 正確な定義: `@functools.wraps(func)` を wrapper に付けると、本体の `__name__`（名前）・`__doc__`（説明文）などを wrapper に写し、`__wrapped__` に本体を記録する。外から見ると本体のように見えるが、呼ばれるのは wrapper。
  - 例: 上の 4 行目。

#### 登録のデコレータとの違い

`@mcp.tool()`（[第 3 章](ch03.md) 3.3 節）もデコレータですが、`@ensure_session` とは働きが違います。
公式 SDK 1.30.0 の `FastMCP.tool` は、中で `self.add_tool(fn, ...)` を呼んでツールを登録し、**受け取った関数をそのまま返します**。
つまり、`@mcp.tool()` は本体を包みません。
（出典: SDK 1.30.0 の `mcp/server/fastmcp/server.py:509-522`（`def decorator(fn)` が `add_tool` を呼んで `return fn`）。repo の外のファイル。解析器の入口の規則のコメントも同じことを書いている: `authgap/catalog/entries.py:136-137`）

#### 重ねる順番で、wrapper が道筋に乗るかが変わる

デコレータを 2 つ重ねると、**下（本体に近いほう）から順に**掛かります。

```python
# 形 1: 登録が上、包みが下
@mcp.tool()
@ensure_session
async def f(): ...

# 形 2: 包みが上、登録が下
@ensure_session
@mcp.tool()
async def g(): ...
```

- 形 1: まず `ensure_session(f)` で wrapper ができ、次に `mcp.tool()` が**その wrapper を**登録します。ツールが呼ばれると、wrapper が先に走ります。
- 形 2: まず `mcp.tool()` が**本体の `g` を**登録し、そのまま返します。次に `ensure_session` が包みますが、包んだものは `g` という名前に入るだけで、サーバに登録されたのは本体です。ツールが呼ばれても、wrapper は走りません。

本記録者は、MCP の代わりに「受け取った関数を一覧に入れて、そのまま返す」だけの登録のデコレータを作り、この 2 つの形を動かして確かめました。
形 1 では、一覧に入ったのは wrapper で、呼ぶと wrapper の前処理が先に走りました。
形 2 では、一覧に入ったのは本体で、呼んでも wrapper の前処理は走りませんでした（2026-10-01、Python 3.11）。

判定では、**サーバに登録されたのが wrapper か本体か**を、デコレータの順番と登録の行から読みます。

この限界は、3 つの場所に記録されています。

- O42 の RC5: 「任意のデコレータで置き換わる def を def として解く」。つまり、デコレータが付いていても、その関数を**本体のまま**として扱う近似です。
- U16: 「暗黙に呼ばれる木内コード（`__call__` / `with` の `__enter__`・`__exit__` / `@property` の getter / 木内デコレータの wrapper）」。誤 clear の向き。

（出典: `docs/open_questions.md:1194`（O43）、`:1167`（O42 の RC5）、`:1110`（U16））

#### なぜそうするのか — 人が wrapper を読む理由

解析器を作るとき、デコレータの中身まで正しくたどるのは難しい問題です。
デコレータは、wrapper を返すことも、本体をそのまま返すことも、まったく別の関数を返すこともあります。
すべてを正しく扱えないので、解析器は「本体のまま」という近似を選び、その近似が見落としを生むことを限界として記録しました（RC5）。
凍結の後なので、直しません（D66）。

だから、見落としの判定で、人が wrapper を読みます。
手引きの下書きは、見落としの原因の分類の 1 つとして「その他（デコレータの wrapper の中など）」を挙げています。
（出典: `docs/drafts/final_judging_guide_draft.md:473-475`）

#### よくある誤解・つまずき

- **誤解: 「デコレータは名札だから、動作には関係ない」**
  登録だけのデコレータ（`@mcp.tool()`）はそうですが、包むデコレータは、本体より先にコードを走らせます。デコレータの定義を開くまで、どちらかは分かりません。
- **誤解: 「`functools.wraps` が付いているから、呼ばれるのは本体」**
  `wraps` は名前と説明文を写すだけで、呼ばれるのは wrapper です。
- **誤解: 「wrapper の中の処理は、本体を呼ぶたびに必ず走るから、本体の一部」**
  解析器から見ると、本体の一部ではありません。本体から降りる道には出てきません。
- **つまずき: デコレータの順番**
  登録のデコレータが包むデコレータより**下**にあると、wrapper はツールの道筋に乗りません（形 2）。順番と登録の行を確かめます。
- **つまずき: 標準ライブラリのデコレータ**
  `@functools.lru_cache`（9.2 節）や `@asynccontextmanager`（9.1 節）もデコレータです。これらは働きが決まっているので、それぞれの節の読み方で読みます。木の中で定義されたデコレータ（`def ensure_session(func):` のように、その木のコードにあるもの）は、定義を開いて中を読みます。

#### 手作業ではどう使うか

1. ツールの関数の上に、`@mcp.tool(...)` 以外のデコレータが付いていないかを見ます。`mcp.tool(...)(f)` の形で登録されているときは、`f` の定義の上も見ます。
2. 見慣れないデコレータがあれば、その定義を grep で探して開きます（`grep -rn 'def ensure_session' corpus/<木> --include='*.py'`）。
3. 定義の中で、wrapper を返しているか、本体をそのまま返しているかを読みます。
4. wrapper なら、本体を呼ぶ行より**前**（と後）の処理を、本体と同じように深さを数えてたどります。
5. 見落としの判定で、wrapper の中に宣言に反しうる動作があり、解析器が何も出していなければ、原因は「その他（デコレータの wrapper の中）」の候補です（[第 52 章](ch52.md)）。条件（いつ走るか）も書き留めます。

#### この節のまとめ

デコレータは関数を受け取って何かを返す関数で、`@d def f` は `f = d(f)` と同じ。包むデコレータは wrapper を返し、wrapper の中の前処理は本体より先に走る。`functools.wraps` は名前を写すだけ。
`@mcp.tool()` は本体をそのまま返す登録のデコレータ。重ねる順番で、wrapper がツールの道筋に乗るかが変わる。
解析器は任意のデコレータの wrapper をたどらない（O43・RC5・U16）。見慣れないデコレータは定義を開いて人が読む。

### 9.9 名前の取り違え — 組み込みのメソッドと、木の中の同名のメソッド

#### 一言で言うと

`set()`・`dict.get()`・`list.append()` のような**組み込みの型**のメソッドと、木の中のクラスの**同じ名前のメソッド**（たとえばファイルに書く `CacheManager.set`）は、名前が同じでも別物です。
どちらが呼ばれるかは、**受け手の型**（9.0 節）で決まります。
名前だけで結ぶと、ありもしない書き込みを報告したり（取り違え）、逆に呼び出し先が解けずに本当の操作を見失ったりします。

#### たとえ話 — 同じ名字の人への電話

会社の受付に「佐藤さんにつないでください」と電話がかかってきたとします。
社内に佐藤さんが 3 人いて、取引先にも佐藤さんがいます。
名字だけでつなぐと、別の佐藤さんにつながるかもしれません。
「営業部の佐藤さん」「〇〇社の佐藤さん」のように、**どこの誰か**まで確かめて初めて、正しい人につながります。

プログラムの呼び出しも同じです。
`x.set(...)` の `set` という名前だけでは、どのクラスの `set` か決まりません。
`x` が**何のオブジェクトか**（受け手の型）を確かめて初めて、呼び出し先が決まります。

#### 小さな例 — 組み込みの型のメソッド

作例です。

```python
1  visited: set[str] = set()      # 組み込みの set()（集合）を作っている
2  visited.add("User")            # 集合に要素を足す
3  d = {}                         # 組み込みの dict（辞書）
4  d.get("key")                   # 辞書から値を取る
5  rows = []                      # 組み込みの list（リスト）
6  rows.append(x)                 # リストに要素を足す
```

#### 一歩ずつ — 1 行ずつの意味

- 1 行目: `set()` は、組み込みの**集合**（同じ要素を 2 つ持たない入れ物）を空で作ります。`: set[str]` は「文字列の集合」という型の注釈で、動作には影響しません。
- 2 行目: `visited.add("User")` で、集合に `"User"` を足します。メモリの中の入れ物が変わるだけで、ファイルにも DB にも触れません。
- 3〜4 行目: `{}` は空の辞書（名前と値の組を入れる入れ物）、`d.get("key")` は辞書から値を取ります。
- 5〜6 行目: `[]` は空のリスト、`rows.append(x)` はリストの末尾に `x` を足します。

どれも、**プログラムの中の入れ物を操作するだけ**です。
ツールの外の世界には触れません。

#### 言葉の整理 — 組み込みの型・名前だけの解決

- **組み込みの型**
  - やさしい言い換え: Python に最初から入っている、基本の入れ物や値の種類。
  - 正確な定義: `int`（整数）・`str`（文字列）・`list`・`dict`・`set`・`bytearray` など、import しなくても使える型。それらのメソッド（`append`・`get`・`add`・`update` など）は、メモリの中の値を扱うだけで、外の世界に触れない。
  - 例: `set()`・`[]`・`{}`。
- **名前だけの解決**（[第 15 章](ch15.md)では「末尾名の解決」と呼ぶ）
  - やさしい言い換え: 呼び出し先を、名前の最後の部分だけで探すこと。
  - 正確な定義: `x.set(...)` のような呼び出しの受け手の型が分からないとき、木の中で `set` という名前のメソッドを持つクラスを探して、それに結ぶやり方。受け手の型で裏付けられないので、取り違えが起きうる。
  - 例: 下の rails-lens で、`set()` を `CacheManager.set` に結んだもの。

#### なぜ解析器は名前で結ぶのか — 直さなかった理由

解析器は、Python の型を調べる仕組み（型の環境）を作らず、ソースコードだけで読みます（[第 7 章](ch07.md)）。
そのため、受け手の型が分からない呼び出しでは、名前だけで木の中のメソッドに結ぶことがあります。
これは取り違えを生みますが、**結ぶのをやめると、本当に木の中のメソッドを呼んでいる道まで消えてしまいます**（見落とし、誤 clear の向き）。

v3 の確認の後、本記録者は「受け手の値が `[]`・`{}`・`""` のようなリテラル（組み込みの型の値）なら、木の中の同名のメソッドに結ばない」という直し方（D61 の G2）を試みました。
けれども、敵対的レビュー（自分の直し方を壊しに行く確かめ。[第 24 章](ch24.md)）で、**値の形は型の証明ではない**と分かりました。
たとえば、大域で `SINK = ""` と空の文字列を入れた後で、別の場所で木の中のオブジェクトに入れ直す形や、`global` で書き換える形では、この直し方が**本当の効果を消して**しまいました。
だから取り消し、既知の限界として残しています。
（出典: `docs/decisions.md:3468-3471`（D61 の改訂。G2 の取り消し）、`docs/open_questions.md:1071-1072`）

- **モジュール水準のインスタンス**
  - やさしい言い換え: ファイルの一番上で作って、大域変数に入れたオブジェクト。
  - 正確な定義: モジュールの一番上の文で、クラスからオブジェクトを作って大域変数に入れたもの。ほかのモジュールからは `モジュール名.変数名` で使える。
  - 例: jahrik の `lsp_client = LSPClient(...)`。
- **コールバック**
  - やさしい言い換え: 「後でこれを呼んでね」と渡しておく関数。
  - 正確な定義: 関数を値として別の関数やライブラリに渡し、渡された側が、必要なときにその関数を呼ぶ仕組み。渡す側のコードには、その関数を呼ぶ行が現れない。
  - 例: pronote の `ent=monlycee_ent`。

#### よくある誤解・つまずき

- **誤解: 「解析器の道筋に `CacheManager.set` と出ているから、ツールはキャッシュに書く」**
  道筋の各段で、**その行の受け手が本当にそのクラスのオブジェクトか**を確かめます。rails-lens では、道筋の段は組み込みの `set()` でした。
- **誤解: 「組み込みの型の名前（`set`・`get`・`append`・`update`・`add`）が出たら、必ず取り違え」**
  木の中のクラスのオブジェクトを受け手にして、本当に同名のメソッドを呼んでいることもあります（rails-lens の `get_routes` などは本当に `cache.set(...)` を呼んでいます）。決めつけずに、受け手をさかのぼります。
- **誤解: 「解析器の出力に何も出ていないツールは、何もしない」**
  モジュール水準のインスタンスやコールバックの先に、操作が隠れていることがあります。
- **つまずき: かっこの無い関数名を見落とす**
  `ent=monlycee_ent` のように、かっこの無い関数名は「呼んでいない」のではなく「**渡している**」のかもしれません。渡した先で呼ばれます。grep で探すときも、`monlycee_ent(` では定義しか当たりません（9.10 節）。

#### 手作業ではどう使うか

- **手順 C**（効果の行を開く）: site の関数が本当に呼ばれているかを確かめます。手引きの下書きは、「組み込みの `set()`・`dict.get()`・`list.append()` を、木の中の同名のメソッド（`CacheManager.set` など）と取り違えていないか（第 17 節 E3）」を名指ししています。
- **手順 D**（道筋をたどる）: 解析器の道筋（[第 18 章](ch18.md)で見る `witness_chain`。ツールの本体から効果までに通った関数の名前の並び）の各段について、その段を呼んでいる行を本体の側から探し、**受け手に何が代入されたか**を見ます。
- **見落としの判定**（[第 52 章](ch52.md)）: モジュール水準のインスタンスのメソッドや、ライブラリに渡したコールバックを見つけたら、その先を自分で読みます。木の外のライブラリが呼び戻す形で、反するかを決められなければ「不明」にします（手引きの見落としの結果の表の「不明」の例）。
（出典: `docs/drafts/final_judging_guide_draft.md:124-125`（手順 C の取り違え）、`:471`（見落としの「不明」の例: 木の外のライブラリが木の中の関数を呼び戻す形））

#### この節のまとめ

組み込みの型のメソッド（`set`・`get`・`append` など）と、木の中の同名のメソッドは別物で、どちらが呼ばれるかは受け手の型で決まる。
解析器は名前だけで結ぶことがあり、rails-lens では組み込みの `set()` を `CacheManager.set` に結んだ（v4 の M04、E3）。直し方は誤 clear を作るので取り消された（D61 の改訂）。
逆に、モジュール水準のインスタンス（jahrik）やコールバック（pronote）の先は解けずに見えないことがある。道筋の各段で受け手を確かめ、出力に無いものはコードから探す。

### 9.10 呼び出し元と定義を探す道具 — grep とエディタ

#### 一言で言うと

ある関数が「どこから呼ばれているか」を確かめるには、木の中を **grep**（文字列を探すコマンド）で探し、出てきた行を**全部**読みます。
grep もエディタの「定義へ移動」も、**名前（文字の並び）で当てている**だけのことがあります。
だから、出てきた行が本当にその関数の呼び出しか（定義か、コメントか、テストか、同じ名前の別の関数か、受け手は何か）を、1 行ずつ見分けます。

#### たとえ話 — 本の索引

分厚い本の巻末の索引で「キャッシュ」という言葉を引くと、その言葉が出てくるページの一覧が出ます。
ただし、索引は**字面**で引いているだけです。

- 「キャッシュ」を説明したページも、「キャッシュの話は後で」と予告しただけのページも、同じように載ります（定義とコメントの違い）。
- 「キャッシュレス決済」のように、別の意味の言葉が載ることもあります（似た名前の違い）。
- 「一時保存」のように**言い換えた**ページは載りません（関数を別の名前で渡した場合や、かっこを付けずに渡した場合）。

grep の結果も同じです。
結果の一覧は、「調べるべき場所の候補」であって、答えそのものではありません。

#### 言葉の整理 — grep・正規表現・単語の境目・定義へ移動

- **grep**（グレップ）
  - やさしい言い換え: ファイルの中から、指定した文字の並びを含む行を探すコマンド。
  - 正確な定義: 指定したパターン（文字の並び、または正規表現）に合う行を、ファイルの名前と（`-n` を付ければ）行番号つきで出す。`-r` でディレクトリの中を全部探す。
  - 例: `grep -rn '_save_cache(' corpus/<木> --include='*.py'`。
- **正規表現**
  - やさしい言い換え: 「こういう形の文字」を表す書き方。
  - 正確な定義: 文字の並びの型を表す記法。`\b` は単語の境目、`\(` はかっこそのもの（かっこは正規表現では特別な意味を持つので `\` で打ち消す）、`\|` や `|` は「または」。`grep -E` を付けると拡張の記法（`|` をそのまま「または」に使える）になる。
  - 例: `\b_init\(` は「単語の境目の後に `_init(` が続く」形。
- **単語の境目**（`\b`）
  - やさしい言い換え: 単語の始まりや終わりの位置。
  - 正確な定義: 英数字と `_`（単語の文字）と、それ以外の文字の間の位置。`rlm_init(` の `_init(` の前は `m` と `_` の間で、どちらも単語の文字なので、境目ではない。
  - 例: `\b_init\(` は ` _init(`（前が空白）には当たり、`rlm_init(` には当たらない。
- **エディタの「定義へ移動」**
  - やさしい言い換え: 名前を選ぶと、その名前の定義の場所に飛ぶ機能。
  - 正確な定義: VS Code などのエディタが、コードを解析して、選んだ名前の定義の候補へ移動する機能。受け手の型が分からないときは、名前で候補を選ぶことがある。
  - 例: `visited.add` を選んで「定義へ移動」すると、木の中の同名のメソッドに飛ぶことがありうる。

#### 小さな例 — 呼び出し元を探す 3 つの命令

```bash
grep -rn '_save_cache(' corpus/<木> --include='*.py'                      # (1) 名前とかっこで探す
grep -rnE '\b_init\(' corpus/<木> --include='*.py'                        # (2) 単語の境目を付けて探す
grep -rnE '\b_init\(' corpus/<木> --include='*.py' | grep -v '/tests/'    # (3) テストのファイルを除いて見る
```

- (1): `-r` はディレクトリの中を全部、`-n` は行番号を付ける、`--include='*.py'` は Python のファイルだけ、という指定です。`'_save_cache('` を含む行を全部出します。
- (2): `-E` で拡張の正規表現を使い、`\b` で単語の境目を付けます。`_init(` には当たり、`rlm_init(` には当たりません。
- (3): `|` は、前の命令の出力を次の命令に渡す記号（パイプ。9.6 節の言葉と同じ）です。`grep -v '/tests/'` は「`/tests/` を**含まない**行だけを残す」という意味です。テストのファイルを除いて、本番のコードだけを見ます。

#### エディタの「定義へ移動」の注意

VS Code などのエディタで木を開き、呼び出し先へ飛ぶ機能を使うと、判定は速くなります。
けれども、手順書と手引きの下書きは、次のように注意しています。

> エディタの「定義へ移動」も名前で当てていることがあるので、呼び出し先が本当にその関数かは、受け手の型（その変数に何が入っているか）で確かめる。

9.9 節の rails-lens の `visited` のような形では、エディタが名前を頼りに、木の中の `CacheManager` のメソッドへ飛ぶこともありえます。
飛んだ先をうのみにせず、**その変数に何が代入されたか**（`visited = set()`）を自分で見ます。
（出典: `docs/final_evaluation_procedure.md:767-768`、`docs/drafts/final_judging_guide_draft.md:85-86`）

#### なぜそうするのか — 「全部読む」理由

手順書は、到達しない形の 1 つ「死んだコード（効果のある関数がツールの道筋からは呼ばれていない。別の入口 = CLI・テスト・スクリプトからだけ呼ばれる）」について、「『別の入口からしか呼ばれない』ことは、木の中を検索して確かめる（関数名で grep し、呼び出し元をすべて見る）」と書いています。

「すべて見る」のは、**1 行でもツールの道筋から呼ぶ行があれば、結論が変わる**からです。
たとえば、10 行の呼び出し元のうち 9 行が CLI やテストでも、残りの 1 行がツールの本体から呼んでいれば、その効果には到達します。
逆に、ツールの道筋から呼ぶ行が無いと言うには、出てきた行を全部確かめ、かっこの無い形や別の名前での受け渡しも探す必要があります。
（出典: `docs/final_evaluation_procedure.md:918-923`（到達しない形の表と、grep で確かめる規則））

#### よくある誤解・つまずき

- **誤解: 「grep で出なければ、どこからも呼ばれていない」**
  かっこの無い形（コールバック、`getattr` で名前の文字列から取り出す形、別名での import）では、`名前(` の grep に出ません。かっこを外して、名前だけでも探します。
- **誤解: 「grep で出た行は全部呼び出し」**
  定義（`def`）、コメント（`#` の後）、説明文（`"""…"""` の中）、文字列、import、テストが混ざります。
- **誤解: 「テストのファイルは除いてよい」**
  判定で「ツールの道筋から呼ばれるか」を見るときは、テストの呼び出しは数えません。けれども、テストの行は「この関数がどう使われるか」の手がかりになります（ccr のコメントのように）。除いて見るのは、確認を速くするためです。
- **誤解: 「エディタで飛んだ先が呼び出し先」**
  名前で当てていることがあります。受け手の型で確かめます。
- **つまずき: `\b` の後の `_`**
  `_` は単語の文字なので、`\b_init` は `rlm_init` の中の `_init` には当たりません。逆に、`grep -w` も `_` を単語の文字として扱います。

#### 手作業ではどう使うか

「この効果のある関数は、ツールの道筋からしか呼ばれないか、CLI やテストからだけ呼ばれるか」（[第 49 章](ch49.md)の到達しない形）、「初期化を `None` に戻す行が無いか」（9.2 節）、「見慣れないデコレータの定義はどこか」（9.8 節）を確かめるときに、次の順で使います。

1. **定義を探す**: `grep -rn 'def 関数名' corpus/<木> --include='*.py'`。同じ名前の定義が複数あれば、どれの話かを受け手の型で決めます。
2. **呼び出し元を探す**: `grep -rnE '\b関数名\(' corpus/<木> --include='*.py'`。
3. **かっこの無い形も探す**: `grep -rnw '関数名' corpus/<木> --include='*.py'`。値として渡す・別名で import する・文字列で指す形を拾います。
4. **1 行ずつ見分ける**: 定義・呼び出し・コメント・文字列・import・テストのどれか。呼び出しなら、**どの関数の中か**を開いて確かめます。
5. **ツールの道筋につながるかをたどる**: 呼び出しを含む関数について、2〜4 をくり返し、ツールの本体まで（または CLI・テストまで）さかのぼります。
6. **根拠に書く**: 使った命令と、出た行の見分けの結果を `evidence` に書きます。たとえば「`grep -rnE '\b_save_cache\(' ...` で 2 行。server.py:10 は定義、server.py:19 は `_lookup` の中の呼び出し」。

#### この節のまとめ

呼び出し元は grep で探し、出た行は全部、定義・呼び出し・コメント・文字列・import・テストに見分ける。呼び出しなら、どの関数の中かを確かめる。
`\b` で似た名前を除き、`grep -v '/tests/'` でテストを除いて見る。かっこの無い形（コールバック・別名）も `-w` などで探す。
grep もエディタの「定義へ移動」も名前で当てているだけのことがあるので、受け手の型で確かめる。1 行でもツールの道筋から呼ぶ行があれば結論が変わるので、全部読む。

### この章のまとめ

- コードは「名前に値を入れる」「関数を呼ぶ」「オブジェクトのメソッドを呼ぶ」の組み合わせ。`X.m(...)` の `X` を受け手と呼び、どの `m` が呼ばれるかは受け手の型で決まる（9.0）。
- `async def` は待てる関数、`await` は呼んで待つ、`yield` は一時停止、`@asynccontextmanager` は `yield` の前を入るとき・後を出るときにする道具。lifespan はこの組み合わせで、`yield` の前はどの起動の形でもツールの受付より前に必ず済む（SDK 1.30.0 の 663 行が 681 行より前）。`lifespan=` の grep は uvicorn・FastAPI にも当たる。条件つき・失敗を握りつぶす形に注意（9.1）。
- 一度だけの初期化は `global` と `is None`・`@lru_cache`・シングルトン・キャッシュを返す関数で書かれる。先に済ませる場所と、`None` に戻す・`cache_clear()`・期限切れの場所（とそれがいつ走るか）を確かめる（9.2）。
- `open` のモード: `'r'` 読む、`'w'` 開いた時点で消して書く、`'a'` 足す、`'x'` 新しく作る、`'r+'` 消さずに上書き。読むか（D1）、壊すか（D2）、増えるか（D4）を分ける。モードが変数なら解析器は不にする（9.3）。
- 作る・消す・置き換えるの関数ごとに前の中身への影響が違う。atomic write は `os.replace` で本物を置き換える。同じ呼び出しで作って消す一時ファイルは D1 では反し、D2 では反しない。`mkstemp`・`Path.touch`・`Path.rename` などは解析器の一覧に無い（9.4）。
- ログの書き込み先は出力先の設定で決まり、設定はモジュールの一番上などにある。`basicConfig` は `filename=` が無ければ標準エラー、`FileHandler` と loguru の `logger.add(<パス>)` はファイル。解析器はログの書き込みを見ない（v4 の R19）（9.5）。
- 子の標準入力への書き込みはそれ自体はファイルを変えず、子が何をするかで決まる。`input=None` なら何も書かない。解析器は保守的に FS_WRITE（シェル・インタプリタなら EXEC）として扱う。`shlex.quote` した値はコマンドの種類を変えられない（E7）（9.6）。
- DB は `execute(命令, 値)`、HTTP はメソッド・宛先（`base_url` まで）・本体を読む。sqlite3 は psycopg と表示される。クライアントの `.put`・`.delete` などは一覧に無い（O39）（9.7）。
- 包むデコレータの wrapper は本体より先に走り、解析器はたどらない（O43・RC5・U16、v4 の R16）。重ねる順番で wrapper が道筋に乗るかが変わる（9.8）。
- 組み込みの `set()` などと木の中の同名のメソッドを取り違えない（v4 の M04、E3）。逆に、モジュール水準のインスタンスやコールバックの先は解けずに見えない（R11・R25）（9.9）。
- 呼び出し元は grep で全部探し、1 行ずつ見分ける。`\b`・`-v '/tests/'`・`-w` を使い分け、かっこの無い形も探す。エディタの飛び先も受け手の型で確かめる（9.10）。
- この章の v3・v4 の判定の例は、どれも本記録者（AI）が付けた考え方の例で、正解ではない。v4 の数字は論文に使わない（D66 の 5）。最終評価の判定は学生 1 人が行い、AI（LLM）には判定させない（AI は事実を調べる補助にだけ使える。D70 の 3）。
