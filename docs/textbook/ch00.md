## 第 0 章 この教科書の読み方 — 表記・誰が何をしたか・読む順番

> **この章で分かること**: この教科書の目的と、判定のときにどの文書がいちばん偉いか。表記のきまり（決定の番号・ファイルの行番号の読み方）。数字と事実の確かさの示し方。決まっていないものの書き方。この研究で「誰が何をしたか」（学生と本記録者の分担）。そして目的別の読む順番。

<a id="s0-1"></a>
### この章の位置づけ

第 0 章は、本文に入る前の「取扱説明書」です。研究の中身はまだ出てきません。けれども、この章で決める約束は、後のすべての章で使います。

たとえば[第 37 章](ch37.md)では「v4 の精度 76.7%」という数字が出てきます。この数字を誰が出したのか、論文に使ってよいのかは、この章の「誰が何をしたか」の節を読んでいないと判断できません。[第 46 章](ch46.md)では「保留」「【確認】」という言葉がたくさん出てきます。その意味の違いは、この章の「決まっていないものの書き方」で決めます。

手作業（最終評価の手動判定）との関係も強い章です。判定では、手引きを開き、原典の行を開き、理由を記録します。そのときの「どの文書に従うか」「行番号をどう書くか」「決まっていないものに出会ったらどうするか」「AI を使ってよいか」の答えが、この章にあります。

### この章で先回りして使う言葉

第 0 章は教科書全体の案内なので、本文で詳しく説明する言葉にどうしても触れます。先に、短い説明を表にしておきます。詳しい説明はそれぞれの章で行います。

| 言葉 | やさしい言い換え | 正確な定義 | 例 | 詳しくは |
|---|---|---|---|---|
| **解析器** | プログラムを読んで調べるプログラム | この研究で作った AuthGap の本体（`authgap/` の下のコード）。調べる相手のコードを動かさずに読み、宣言（ツールが自分について書く約束。[第 4 章](ch04.md)）に反しうる動作を探す | `python -m authgap scan <木>` で走らせる | 第 7・11 章 |
| **原ソース** | 調べる相手の、手を加えていないコード | 調べる相手のリポジトリのソースコードそのもの。解析器の出力ではなく、元のファイル | `corpus/<木>/server.py` | 第 47・48 章 |
| **木** | 調べる 1 つのリポジトリ | 解析する 1 つのリポジトリ。この研究では、1 つの MCP サーバ（AI が使う道具をまとめて提供するプログラム。[第 3 章](ch03.md)）にあたる | v4 の木 `v4-qbit-glitch__ccr`（GitHub のリポジトリ `qbit-glitch/ccr` を v4 で取得したもの。`docs/corpus_sample_v4.json:827-828`） | [第 11 章](ch11.md) |

| **コミット** | 変更を履歴に記録すること | git で、ファイルの変更を日時つきで repo の履歴に記録すること。後から消したり日付を変えたりしにくい | 事前登録の文書をコミットしてからデータに触れる | [第 22 章](ch22.md) |

| **封** | 決めた文書を、それ以後変えないこと | 文書を決まった時点でコミットし、その後は変えないと約束すること | 事前登録と判定の手引きを同じコミットで封をする | [第 22 章](ch22.md) |

<a id="s0-3"></a>
### この教科書の目的と、いちばん偉い文書

**一言で言うと**: この教科書は、学生が研究を理解し、最終評価の判定を理由を説明しながら行えるようになるための本です。ただし、判定のときに従う正本は、この教科書ではなく、封をした事前登録と判定の手引きです。

**たとえ話**: 自動車教習所の教本と、道路交通法の関係に似ています。教本は、法律をやさしく説明し、図や例を付けて、運転できるようにしてくれます。けれども、教本と法律が食い違ったら、従うのは法律です。教本は「理解するための本」で、法律は「従う決まり」です。この研究では、この教科書が教本、封をした事前登録と判定の手引きが法律にあたります。

**小さな例**: 文書の「偉さ」の順を表にします。

| 順 | 文書 | 役割 | 状態（2026-10-01） |
|---|---|---|---|
| 1 | 事前登録 `docs/preregistration.md` の §2.12 と、判定の手引き `docs/final_judging_guide.md` | 判定の規則そのもの（正本） | まだ無い。下書き（`docs/drafts/prereg_2_12_draft.md`、`docs/drafts/final_judging_guide_draft.md`）を学生が承認し、同じコミットで封をすると正本になる |
| 2 | 決定の記録 `docs/decisions.md`（D1〜D71） | 規則の出どころと理由 | D67〜D70 が最終評価の決め事 |
| 3 | 手順書 `docs/final_evaluation_procedure.md` | 作業の流れの地図 | 「規則そのものではない」と自分で書いている |
| 4 | この教科書 | 理解するための説明 | 第 4 版 |

**一歩ずつ**: 表を上から読みます。

1. 1 行目の正本は、まだ存在しません。今あるのは下書きです。下書きの冒頭には「この文書は下書きで、まだ封をしていない」とあります。学生が読んで承認したら、事前登録の §2.12 として写し、判定の手引きと同じコミットで封をします。封をしてから、最終評価のデータに触れます（出典: `docs/drafts/prereg_2_12_draft.md:1-5`、`docs/drafts/final_judging_guide_draft.md:1-4`）。
2. 2 行目の決定の記録は、規則が「なぜそう決まったか」を残す文書です。下書きは「中身は D67〜D70 の決定を写しただけ」と書いています。つまり、規則の根拠をたどると、ここに着きます（出典: `docs/drafts/prereg_2_12_draft.md:7`）。
3. 3 行目の手順書は、自分のことを「手順の地図であって、規則そのものではない」と書いています。規則は事前登録と判定の手引きに書いてコミットし、それが正本になる、とも書いています（出典: `docs/final_evaluation_procedure.md:5-7`）。
4. 4 行目のこの教科書は、上の 3 つをやさしく説明するものです。規則を新しく作ることはしません。

**なぜそうするのか**: 判定の規則は、データを見る前に決めて封をし、後から変えないことに意味があります（[第 22 章](ch22.md)）。教科書は説明のために何度も書き直します。もし教科書が正本だと、書き直すたびに規則が動いてしまいます。だから、動かない文書（封をした事前登録と手引き）を正本にし、教科書はそれを説明する側に置きます。仕様書（`AUTHGAP_BRIEF_v3.md`、1210 行）と実データが食い違ったときも、同じ考え方をします。実データを採り、仕様書の値も残し、決定は `docs/decisions.md` に根拠つきで書きます。仕様書の本体は書き換えません（出典: `CLAUDE.md` の規則 6）。

**よくあるつまずき**:

- 「教科書に書いてあるから、それが規則だ」と思ってしまう。違います。教科書と手引きが食い違ったら、手引きに従い、食い違いを記録してください。
- 「手順書に書いてあるから決まっている」と思ってしまう。手順書には「下書き」や「決定の前の検討の記録」も入っています。たとえば手順書の 0-9 の節には、決定（D70 の 3）の後に「以下は決定の前の検討の記録」と書いて、古い選択肢が残っています。決まったのは見出しの「決定」の部分だけです（出典: `docs/final_evaluation_procedure.md:235-248`）。
- 「下書きでも、ほとんど決まっているから正本と同じ」と思ってしまう。下書きには、学生がまだ承認していない細部（【確認】）や、まだ決まっていない項目（【保留】）が入っています。封をするまでは正本ではありません。

**手作業ではどう使うか**: 判定の最中に「教科書ではこう説明していたが、手引きの文面は少し違う」と気づくことがあるはずです。そのときは次の順で動きます。

1. 手引き（封をした正本）の文面に従って判定します。
2. 食い違いを、判定表の `note` 欄（迷った点を書く欄。[第 48 章](ch48.md)）に書きます。
3. 手引きで決まらない事例なら、手引き第 22 節の手順に従います。その件は「不明」にし、理由に「手引きで決まらない」と書き、事前登録の §5（逸脱の記録）に事例を書きます。手引きを判定の途中で変えてはいけません（出典: `docs/drafts/final_judging_guide_draft.md:701-709`。詳しくは[第 52 章](ch52.md)）。

**この節のまとめ**: この教科書の目的は、研究を理解し、判定を自分の言葉で説明できるようになること。判定で従う正本は、封をした事前登録と判定の手引き。教科書・手順書・手引きが食い違ったら、正本に従って食い違いを記録する。

<a id="s0-4"></a>
### 表記のきまり

**一言で言うと**: この教科書は、太字・等幅の文字・決定の番号・ファイルの行番号という 4 種類の印を使います。とくに「ファイル名:行番号」は、原典の該当の行を自分で開いて確かめるための住所です。

**たとえ話**: 地図の記号を思い浮かべてください。地図を読む前に凡例（記号の一覧）を見ておけば、「この記号は郵便局」「この線は県境」とすぐ分かります。この節は、この教科書の凡例です。とくに「ファイル名:行番号」は、本の「○ページ○行目」と同じで、そこを開けば誰でも同じ文を見られます。

**小さな例**: 次の 1 文を見てください。

> v4 の数字は論文に使いません（D66 の 5、`docs/decisions.md:3754`）。

この 1 文に、印が 3 つ入っています。原典のその行を開くと、次のように書いてあります。

```
5. v3 と並べてよいが、版もデータも違うので「改善」「悪化」とは書かない。論文には使わない。
```

**一歩ずつ**: 印を 1 つずつ読みます。

1. **太字**は、その段落でいちばん大事な点です。急いで読むときは、太字だけ拾えば要点が分かるように書いています。
2. `等幅の文字`は、プログラムの名前・ファイル名・コードの一部です。打ち間違えると意味が変わるもの、と思ってください。
3. 「D66」は、`docs/decisions.md`（決定の記録）の 66 番目の決定です。「D66 の 5」は、その決定の中の 5 番目の項目です。同じように「O45」は `docs/open_questions.md`（未決事項・既知の限界の記録）の 45 番目の項目で、「O45 の 4」はその 4 番目の項目です。
4. `docs/decisions.md:3754` は、「`docs/decisions.md` というファイルの 3754 行目」という意味です。`:3800-3801` なら 3800 行目から 3801 行目まで、`:11-12,248` なら 11〜12 行目と 248 行目です。
5. 上の引用は、実際に 3754 行目を開いて写したものです。D66 は v4 の中間検証の決定で、その 5 番目の項目が「論文には使わない」です。

ほかにも、次の書き方が出てきます。

- 「§2.12」の `§` は、文書の中の節の番号です。たとえば「事前登録の §2.12」は `docs/preregistration.md` の 2.12 節です。判定の話で「§6（採った原理）」「§7（判定表）」と出てきたら、多くは食い違いの原理の文書 `docs/contradiction_principles.md` の節です（[第 17 章](ch17.md)）。ただし仕様書 `AUTHGAP_BRIEF_v3.md` にも §6 があるので、どの文書の節かは前後の文で確かめてください。
- 「逸脱 #26」は、事前登録 `docs/preregistration.md` の §5（逸脱の記録。先に決めたことから外れたときの記録）の 26 番目の行です。凍結の後で解析器を直してしまい、凍結をやり直した件です（出典: `docs/preregistration.md:577`。経緯は[第 36 章](ch36.md)）。
- 「run24」のような名前は、解析器をデータに走らせた回の名前です。run の後の番号が大きいほど後の回です（[第 11 章](ch11.md)）。
- 「第 3 版 1790 行」は、この教科書の第 3 版（`docs/textbook_v3.md`、2026-09-29、2,736 行）の行番号です。第 4 版の中から第 3 版を指すときに使います。

**なぜそうするのか**: この研究の一番の約束は、確かめていないことを確かめたように書かないことです（`CLAUDE.md` の規則 1「未検証の統計を引用しない」）。行番号まで書けば、読む人が自分でその行を開き、本当にそう書いてあるかを確かめられます。数字にはさらに「何を数えたか（分母）」と出典を添えます。閾値には測り方と分母の定義を付ける、という約束があるからです（`CLAUDE.md` の規則 3。[第 22 章](ch22.md)）。分母の無い「80%」は、何の 80% なのかが分からず、確かめようがありません。

**よくあるつまずき**:

- **宣言の「D1」と、決定の「D1」を取り違える。** これがいちばん多いつまずきです。この研究では、ツールの宣言 4 つを D1〜D4 と呼びます（D1 は `readOnlyHint: true` など。第 4・16 章）。ところが、決定の記録にも D1〜D4 という番号の決定があります（たとえば `docs/decisions.md:1231` の D1 は語彙を広げた決定です）。この教科書と判定の手引きで「D1」「D1 の矛」「D1〜D4」と書いたら、**宣言**のことです。決定の D1〜D4 を指すときは、紛らわしいので「決定 D1」と書きます。見分けの目安として、最終評価の決め事は D60 より大きい番号（D67〜D71 など）に集まっていて、「D67 の 1」のように項目の番号が付くことが多い、と覚えておくと楽です。
- **原典の「教科書 第 N 章」を、第 4 版の番号で読んでしまう。** 原典は第 3 版の番号で書かれています。目次の直後の対応表で読み替えてください。
- **行番号がずれる。** 行番号は、その文書のその時点の行です。後で文書に行が足されると、行番号はずれます。この教科書の行番号は 2026-10-02 の版（D70 の 3 の改訂を反映した後の、コミット `84fcf15` の時点）のものです。ずれていたら、引用の文字列で検索してください。
- **番号を全部覚えようとする。** 番号は「後で原典を引くための目印」です。読み流して構いません。中身はこの教科書で説明します。

**手作業ではどう使うか**: 判定の記録でも、まったく同じ書き方を使います。判定表の `evidence` 欄（根拠を書く欄。[第 48 章](ch48.md)）には、ファイルと行の連なりを書きます。手引きの例は次のような形です（出典: `docs/drafts/final_judging_guide_draft.md:186-195`）。

```
server.py:703-826（generate_cost_report_wrapper、引数 output_file をそのまま generate_cost_report に渡す）→
report_generator.py:1164-1186（format で分岐）→ report_generator.py:778 with open(output_file, 'w')
```

1 行目は「`server.py` の 703〜826 行目にあるツールの本体が、引数を次の関数に渡している」、2 行目は「`report_generator.py` の 1164〜1186 行目で分岐し、778 行目でファイルを書き込み用に開いている」という意味です。手引きは、悪い例として「open で書いているので正」（どの行か、どう届くかが無い）を挙げています。`evidence` は、判定を見ていない第三者がその行を開けば同じ結論に着けるように書きます。2 人目の判定者がいない分、これが信頼性の担保になるからです（D67 の 4）。この節で覚えた「ファイル名:行番号」の書き方が、そのまま判定の記録の書き方になります。

**この節のまとめ**: 太字は要点、等幅はコード、D と O は決定と未決の番号、「ファイル名:行番号」は原典の住所。宣言の D1〜D4 と決定の番号を取り違えない。判定の記録でも同じ「ファイル名:行番号」で根拠を書く。

<a id="s0-5"></a>
### 確かさの印

**一言で言うと**: 外の資料から持ってきた事実には、「誰がどこまで確かめたか」を示す 3 つの印 **[確認]**・**[agent]**・**[未確認]** を付けます。印を見れば、その事実をどこまで信じて使ってよいかが分かります。

**たとえ話**: 友だちから話を聞く場面を考えてください。「自分の目で見た」話、「別の友だちが見たと言っていた」話、「うわさで聞いた」話では、同じ内容でも信じ方が違うはずです。自分の目で見た話なら人に伝えられます。又聞きなら「〜らしい」と付けて伝えます。うわさなら、人には伝えません。確かさの印は、この 3 段階をはっきり書いたものです。

**小さな例**: 「AI のアプリ（[第 2 章](ch02.md)で説明するクライアント）が、読み取り専用と宣言されたツール（[第 4 章](ch04.md)）を、利用者に確認せずに実行するか」という事実を調べた記録から、3 行を抜き出します（出典: `docs/incidental_writes_practice.md:96,99,103`）。

| アプリ | 調べた結果（短くしたもの） | 印 |
|---|---|---|
| VS Code（Copilot のエージェントモード） | v1.100 のリリースノートに「`readOnlyHint: true` のツールは利用者の確認なしで実行される」とある | [確認] |
| Claude の connectors | 「読み取り専用のツールは呼び出しごとの確認なしで実行でき、破壊的なツールは必ず確認する」とある | [agent] |
| Claude Code | 公式文書に記述が無い。第三者の報告は食い違う | [未確認] |

**一歩ずつ**: 3 つの印の意味と使い方を表にします。この印は `docs/incidental_writes_practice.md:12-15` で定めたもので、この教科書では主に[第 4 章](ch04.md)と[第 43 章](ch43.md)で使います。

| 印 | 意味 | 使い方 |
|---|---|---|
| **[確認]** | 本記録者（この章の「誰が何をしたか」の節で説明します）が原文を取得して、引用した文字列が原文にあることを照合したもの | 根拠として使ってよい |
| **[agent]** | agent（本記録者が仕事を分けて渡した、別の AI の実行）が「原文を読んだ」と報告したもので、本記録者は照合していないもの | 傾向として読む。論文に書く前に、学生が原文で確かめる |
| **[未確認]** | 検索結果の抜粋だけ、または開けなかったもの | 使わない。数値は特に使わない |

この表で上の例を読み直します。

1. VS Code の行は [確認] です。本記録者がリリースノートの原文を取得し、引用の文字列が原文にあることを照合しました。だから「VS Code の v1.100 のリリースノートに、読み取り専用のツールは確認なしで実行されると書いてある」ことは、根拠として使ってよい、ということです。
2. Claude の connectors の行は [agent] です。agent が「そう書いてあった」と報告しましたが、本記録者は原文と照合していません。だから「そういう傾向があるようだ」として読み、論文に書くなら先に学生が原文を開いて確かめます。
3. Claude Code の行は [未確認] です。公式文書に記述が見つからず、第三者の報告も食い違っています。だから、この行を根拠に何かを主張してはいけません。

もう 1 つ、「未検証」という言葉も使います。この教科書で「**未検証**」と書いた数や記述は、原典で確かめられなかったものです。**論文には使いません**（出典: `CLAUDE.md` の規則 1。`docs/related_work.md:5-6` も「一次資料を読んだ項目だけ確認済みと書き、二次情報から書いた項目は未検証と明示する」という同じ規則を書いています）。

**なぜそうするのか**: この研究の主張の 1 つは「解析器は LLM を判定に使わず、決まった手順で動く」ことです（[第 7 章](ch07.md)）。その研究が、AI の要約や又聞きの事実を、確かめたもののように論文に書いたら、主張の土台が崩れます。実際に、仕様書は、ある先行研究について AI の自動要約が「意味的データフロー解析」と述べたのに、原文は「キーワードと正規表現の照合」だった例を挙げています。要約が判断を左右する向きに誤っていたのです（出典: `AUTHGAP_BRIEF_v3.md:82`）。印を付けておけば、どこが確かで、どこがまだ確かでないかが、後から誰にでも分かります。

**よくあるつまずき**:

- **[確認] を「内容が正しい」と読んでしまう。** [確認] は「その資料にそう書いてある」ことの確認であって、「その資料の内容が正しい」ことの確認ではありません。たとえば、ある公式ブログには利用者の割合の数字が書いてあり、「ブログにそう書いてある」ことは [確認] です。けれども、その数字自体は本記録者が測っていません（出典: `docs/incidental_writes_practice.md:46` に「ブログの記載で、本記録者は検証していない」とあります）。そうした数字は、この教科書では写しません。
- **文書ごとに印が違うことを忘れる。** 別の文書では別の印を使います。`docs/llm_judgment_survey.md:14-18` は「高・中・低」の 3 段階です（高 = agent が repo のコードや結果を読んだ、中 = 第三者の逐語の抜き書き、低 = 検索の要約だけ）。仕様書は「◎・◎'・○・△」を使い、「◎' は ◎ ではない」とわざわざ書いています（出典: `AUTHGAP_BRIEF_v3.md:82`）。原典を読むときは、その文書の冒頭で印の定義を確かめてください。
- **調査の文書そのものが AI の出力だということを忘れる。** たとえば `docs/llm_judgment_survey.md` は、agent を 7 体使った調査で、「この調査の報告そのものが LLM の出力なので、論文に載せる前に学生が原典で確かめる」と自分で書いています（出典: `docs/llm_judgment_survey.md:6-10,20`）。

**手作業ではどう使うか**: 最終評価の判定そのものには、この 3 つの印は付けません。判定の根拠は原ソースの行で、あなたが自分で開いて読んだものだけを書くからです。つまり、判定表の `evidence` 欄はすべて「自分の目で見た」＝ [確認] に相当するものでなければなりません。「たぶんこの関数がファイルを書いているはず」という推測を、見ていないまま `evidence` に書いてはいけません。読み切れなかったら、それは「不明」の理由として書きます（[第 52 章](ch52.md)）。

印が役に立つのは、判定の後で論文を書くとき（[第 55 章](ch55.md)）と、[第 43 章](ch43.md)のように外の資料を根拠にして「なぜこう決めたか」を説明するときです。そのとき、[agent] の事実を論文に使いたければ、まず自分で原文を開いて照合し、[確認] に上げてから使います。

**この節のまとめ**: [確認] は本記録者が原文で照合したもの、[agent] は agent の報告で照合していないもの、[未確認] は使わないもの。[確認] は「そう書いてある」の確認で、内容の正しさの確認ではない。判定の `evidence` には、自分で開いた行だけを書く。

<a id="s0-6"></a>
### 決まっていないものの書き方

**一言で言うと**: 「まだ決まっていない」には種類があります。この教科書では **未決**・**保留**・**【確認】**・**下書き・未承認** の 4 つの言葉で書き分けます。黙ってどちらかに倒さないのが、この研究の約束です。

**たとえ話**: 家族旅行の計画を考えてください。

- 行き先は、まだ誰も決めていないし、いつ決めるかも決めていない。これは「**未決**」です。
- ホテルは、「来週の金曜までに決める。それまでは空けておく」と期限を決めて待っている。これは「**保留**」です。
- 子どもが「2 日目は水族館がいい」と提案したが、親はまだ「いいよ」と言っていない。これは「**【確認】**」（提案はあるが承認されていない）です。
- 旅のしおりは全体がまだ書きかけで、家族の誰も「これで行こう」と言っていない。これは「**下書き・未承認**」です。

どれも「決まっていない」のですが、次に何をすればよいかが違います。

**小さな例**: この研究の実例で 4 つを並べます。

| 書き方 | 意味 | 例 |
|---|---|---|
| **未決** | まだ誰も決めていない。決める時期も決まっていない | 最終評価で CodeQL（既存の解析ツールの 1 つ。[第 26 章](ch26.md)）を見落とし探しの補助に使うかどうか（D71 の「任意の案（未決）」） |
| **保留** | 決める時期（期限）を決めて、それまで待っている | 判定の一貫性の確認と 2 人目の判定者（D70 の 8）。期限は「データを見る前、遅くとも段階 6 の抜き取りのコミットの前」。O2 も同じ |
| **【確認】** | 本記録者が提案した細部で、学生がまだ承認していない | 事前登録の下書きの 2 点。判定の順序を並べ替えるための 5 つ目の乱数の種（seed ⑤）と、木の数が 10 未満の宣言では区間（数字の幅。[第 38 章](ch38.md)）を出さないこと |
| **下書き・未承認** | 文書全体がまだ下書きで、学生が承認していない。封もしていない | `docs/drafts/prereg_2_12_draft.md` と `docs/drafts/final_judging_guide_draft.md` の 2 つ |

（出典: 未決は `docs/decisions.md:3953`。保留は `docs/decisions.md:3925-3931` と `docs/open_questions.md:10`。【確認】は `docs/drafts/prereg_2_12_draft.md:52,111`。下書き・未承認は `docs/drafts/prereg_2_12_draft.md:1-5` と `docs/drafts/final_judging_guide_draft.md:1-4`。）

**一歩ずつ**: 表の 4 行を、「次に何をするか」の目で読みます。

1. **未決**の CodeQL の案は、D71 に「任意の案（未決）」と書かれ、「やるなら事前登録に足してからにする」と添えられています。つまり、やらないまま進んでも約束違反ではありません。やるなら、データを見る前に事前登録に書く必要があります。
2. **保留**の 2 人目の判定者は、D70 の 8 で「2 人目を用意できるかもしれないが、まだ分からない」とされました。決まるまでは、D67 の 4（判定者は学生 1 人）が既定として残ります。期限を過ぎて結果を見た後に足すなら、事前登録に逸脱として理由とともに書き、事後の分析として扱います。
3. **【確認】**の 2 点は、決定（D67〜D70）に書かれていない細部を、本記録者が下書きの中で提案したものです。学生が下書きを承認するときに、この 2 点を採るかどうかも一緒に決めます。
4. **下書き・未承認**の 2 文書は、学生が読んで承認したら、事前登録の §2.12 と判定の手引き（`docs/final_judging_guide.md`）に移し、同じコミットで封をします。

事前登録の下書きは「【保留】」という印も使っています（`docs/drafts/prereg_2_12_draft.md:8`「【保留】は D70 の 8 のとおり未定」）。これは上の表の「保留」と同じ意味です。判定の手引きの下書きでも、判定し直し（21 の 5）に「保留: D70 の 8」と書いてあります（出典: `docs/drafts/final_judging_guide_draft.md:674`）。

**なぜそうするのか**: `CLAUDE.md` の規則 4 は「解決できなかったものは『不明』として記録する。黙って安全側に倒さない」です。「まだ決まっていない」ものを、書き手の都合でどちらかに決めたことにしてしまうと、後で誰かがそれを「決定」だと思って使います。そうなると、学生が決めていないことが、学生の決定として論文に入ってしまいます。

書き分けるもう 1 つの理由は、**取るべき行動が違う**ことです。判定や集計の途中で「まだ決まっていない」ものに出会ったとき、それが「誰かがもう決めたのに自分が知らない」のか、「本当にまだ誰も決めていない」のかで、行動が変わります。前者なら原典（`docs/decisions.md`）を探します。後者なら、判定を「不明」にして理由を記録し、決めるのは学生です（[第 52 章](ch52.md)）。

**よくあるつまずき**:

- **保留を「やらない」と読む。** 保留は「期限までに決める」です。やらないと決めたわけではありません。2 人目の判定者は、用意できれば足す方向で検討されています（D70 の 8）。
- **【確認】を「本記録者が確認した」と読む。** 逆です。【確認】は「学生が確認（承認）する必要がある」という印です。本記録者の提案にすぎません。確かさの印の [確認]（本記録者が原文で照合した）とは別物なので、括弧の形（【】と []）で見分けてください。
- **下書きの中身を、決まったことの証拠に使う。** 下書きの中身の多くは D67〜D70 の決定を写したものですが、写し間違いや、【確認】のような未承認の細部も入りえます。決まったかどうかは、`docs/decisions.md` で確かめてください。
- **未決を放っておくと、自然に「やらない」に決まると思う。** 未決のまま論文を書くなら、論文でも「決めていない」「行っていない」と書きます。黙って消えるわけではありません。

**手作業ではどう使うか**: 判定の最中に、この 4 つの言葉はこう効いてきます。

- 手引きに「保留」と書かれた作業（たとえば判定し直し）は、**事前登録に書いた場合だけ**行います。書いていないのに思いつきで判定し直すと、事前に決めていない手続きを足したことになります（出典: `docs/drafts/final_judging_guide_draft.md:674-676`）。
- 手引きの規則がどれにも当てはまらない事例は、あなたがその場で規則を作って決めてはいけません。その件は「不明」にし、理由に「手引きで決まらない: <事例の説明>」と書きます（出典: `docs/drafts/final_judging_guide_draft.md:701-706`）。これは「決まっていないものを黙ってどちらかに倒さない」の、判定の中での形です。
- 封をする前に、下書きの【確認】と【保留】の箇所を 1 つずつ見て、採るか・いつ決めるかを決めます。封の後に残った【確認】は、判定が始まった後では変えられません。

**この節のまとめ**: 未決は「誰も決めていない」、保留は「期限を決めて待っている」、【確認】は「本記録者の提案で学生が未承認」、下書き・未承認は「文書全体が封の前」。どれも黙って決めたことにしない。判定で決まらない事例に出会ったら「不明」にして理由を書く。

<a id="s0-7"></a>
### 誰が何をしたか — 学生と本記録者

**一言で言うと**: この研究には 2 人の主な登場人物がいます。決める人である**学生**と、解析器を作り、決定の推奨と記録を書いてきた AI の**本記録者**です。v3・v4 の判定は本記録者が行いました。最終評価の判定は学生 1 人が行い、AI は使いません。

**たとえ話**: 料理コンテストを思い浮かべてください。新しいレシピを考えた人が、試作品を自分で味見して「80 点」と付けたとします。この点数は、レシピを直すための手がかりにはなります。けれども、コンテストの公式の審査結果には使えません。作った本人の味見は、身内の評価で、独立していないからです。公式の審査は、別の審査員が、まだ誰も味見していない新しい皿で行います。

この研究では、レシピを考えた人が本記録者、試作品の味見が v4 の判定、公式の審査員が学生、新しい皿が最終評価のデータにあたります。

**小さな例**: まず、登場人物を 3 つの言葉で定めます。

- **学生**: この研究の主体で、論文を書く人です。研究の方針と、最終評価の決め事を決めます。
- **本記録者**: **この repo（リポジトリ。プログラムのファイル一式を、変更の履歴ごと保管したもの）で解析器を作り、決定の推奨と記録を書いてきた AI（Claude）**です。決定の記録やこの教科書を書いた「記録者」なので、こう呼びます。「本」は「この」という意味です。原典（`docs/decisions.md` の D66〜D70、`docs/open_questions.md` の O45、手順書の 249〜252 行など）には、この言葉がたくさん出てきます。
- **agent**: 本記録者が作業を分けて渡した、別の AI の実行です。たとえば v4 では、原ソースの確認を木ごとに agent に分けました（出典: `docs/population_v4.md:15-16`）。

**第 3 版の教科書で「私」と書いたのは、すべて本記録者のことです**（第 3 版 1790 行「根拠（ファイルと行）を私が見直して採りました」、1905 行「私（この記録を書いている作業者）」、ほかに 1970・1996・2064・2128・2439 行）。

**一歩ずつ**: 表の中で、とくに大事な行を順に読みます。

1. **「決める」は学生です。** 本記録者は、選択肢を並べて推奨を示します。たとえば最終評価の規模（D69）では、本記録者が A・B・C の 3 つの規模を示し、学生が「判定の時間より研究の価値を優先する」としたうえで C を選びました（出典: `docs/decisions.md:3818-3819`）。推奨と決定は別物です。
2. **v3 と v4 の判定は本記録者です。** 判定の中の「原ソースを読んで根拠の行を探す」作業は、木ごとに agent に分けました。agent の報告した根拠を、本記録者が見直して採りました。
3. **v4 では、人は見直していません。** ここは一度、文書の誤りがあった箇所です。手順書には以前「根拠を人が見直した」と書かれていました。これは誤りで、見直したのは本記録者（AI）でした。誤りの向きは「AI の関与を小さく見せる」向きで、2026-10-01 に訂正されました（出典: `docs/final_evaluation_procedure.md:251-252`、`docs/llm_judgment_survey.md:174-175`）。
4. **最終評価の判定は学生 1 人が行い、AI には判定させません。** AI は、コードについての事実（この関数はどこから呼ばれるか、このライブラリの関数は何をするか、など）を調べる補助としてだけ使ってよいことになっています。AI が示した行は自分で開いて確かめ、記録には確かめた行だけを書きます（D70 の 3）。

この表から、2 つの大事な約束が出てきます。

**約束 1: v4 の数字は論文に使いません**（D66 の 5、`docs/decisions.md:3754`「論文には使わない」）。たとえば v4 の「D1 / D2 の矛の精度 76.7%」は、抜き取った 60 件のうち本記録者が「正」とした 46 件の割合です。事後の分析で出した「reaper-mcp という 1 つの木を除くと 36.4%（22 件中 8 件）」も同じです。どちらも AI が付けた判定から出た数字です（出典: `docs/population_v4.md:93,124`、`docs/llm_judgment_survey.md:161`）。

使わない理由は 2 つあります。

- v4 の判定は本記録者（AI）が行ったもので、独立した人の判定ではありません。しかも、解析器を作ったのも本記録者です。たとえ話の「レシピを考えた人の味見」にあたります。
- v4 は本記録者が結果を見たデータです。だから、v2・v3 と同じく、学生の最終評価のデータから除く約束になっています（D66 の 3、`docs/decisions.md:3752`）。

v4 の数字は、この教科書では「凍結した解析器がどう振る舞うかの手がかり」として扱います（[第 37 章](ch37.md)）。v3 も同じく開発用で、論文の評価ではありません（出典: `docs/population_v3.md:6-12`）。

**約束 2: 研究の遂行に AI を使ったことは、論文で開示します**（O45 の 4、`docs/open_questions.md:1270-1272`。D70 の 3 の `docs/decisions.md:3885-3888` も同じ）。開示の対象は、v4 の判定、手順書と手引きの下書き、決定の推奨、コミットの共著者などです。最終評価の判定で AI を事実の補助に使った範囲（`ai_used` が「あり」の件数）も、開示の対象に加わりました。これとは別に、「**解析器は LLM を使わない**」は、解析器を走らせたときの性質として書きます。この 2 つ（研究を進める作業に AI を使ったこと / 解析器そのものは AI を使わないこと）を混ぜないでください（出典: `docs/llm_judgment_survey.md:165-168`）。

**なぜそうするのか**: 判定を学生が決め、AI には事実だけを聞く理由は、D70 の 3 に書かれています。この決定には経緯があります。2026-10-01、学生は最終評価の判定で AI を一切使わない（原ソースを読む補助にも使わない）と決めました。判定に LLM を混ぜた先行研究は、決められないものを黙って消すか、どちらかに倒しています。また、LLM の答えは揺れ、モデルを変えると結果が変わります。この研究の芯は「解析できなかったもの・決められなかったものを、理由つきで数える」こと（D40。[第 6 章](ch06.md)）と、「同じ入力から同じ結果が出る」こと（決定性。[第 7 章](ch07.md)）だからです。

2026-10-02、学生は最終評価のデータを見る前に、この決定を改めました。判定者は Python と、MCP サーバがよく使うライブラリに慣れていません。AI なしでは、ライブラリの関数の意味や呼び出し先を調べるのに時間がかかり、読み違いがそのまま判定に入ります。そこで「判定は人が行い、AI は事実を調べる補助としてだけ使う」に変えました。前の心配には、次のように答えています。AI に判定させないので、決められないものは人が「不明」と記録します。記録に入るのは人が開いて確かめた行だけなので、AI の答えが揺れても記録は揺れません。前の決定は誤りだったのではなく、学生の判断が変わったのです（出典: `docs/decisions.md:3872-3879`、改訂前の文面は `:3895-3904`）。

もう 1 つの理由は、評価データを本記録者が一度も見ないという約束です（D60 の「評価データを本記録者が一度も見ない・開発に使わない」、`docs/decisions.md:3400`。v4 については D66 の 3）。学生がこの repo の文脈を読み込んだ AI を最終評価で使うと、本記録者が評価データを見たことになりかねません。だから D70 の 3 は、**この repo の文脈を持たない AI** だけを使ってよいとしています。この repo を開いた Claude Code、この repo の文書を読み込ませた会話、本記録者そのものは使いません。こうして、最終評価で本記録者が評価データを見ることはなく、この約束とぶつかりません（出典: `docs/decisions.md:3866-3868`、`docs/open_questions.md:1265-1269`）。

**よくあるつまずき**:

- **v4 の判定を「正解」として扱う。** v4 の判定は、本記録者の判定で、正解ではありません。判定の手引きも「v4 の例は本記録者（AI）の判定で、正解ではなく考え方の例」と書いています（出典: `docs/drafts/final_judging_guide_draft.md:26,647`）。
- **「解析器は LLM を使わない」から「研究に AI は関わっていない」と考える。** 違います。解析器を作ったのも、v4 を判定したのも、手順書を書いたのも AI（本記録者）です。だから開示が要ります。
- **「AI を補助に使ってよいなら、AI に『これは違反か』と聞いてもよい」と考える。** 違います。AI に聞いてよいのは事実（「この関数はどこから呼ばれる？」「`open(path, "a")` は何をする？」など）だけです。「このツールは読み取り専用か」「これは正か誤か」は聞きません。宣言の値と解析器の答え（矛 / 不 / 理由コード）も AI に渡しません（D70 の 3 の条件 2）。2026-10-01 の決定は「読む補助にも使わない」で、2026-10-02 に今の形に改められました。手順書の 0-9 に残っている選択肢は「決定の前の検討の記録」です。
- **「本記録者」を学生や指導教員のことだと思う。** 本記録者は AI です。原典に「本記録者が判定した」とあれば、それは AI の判定です。

**手作業ではどう使うか**: 最終評価に入る前に、判定の練習をします（手順書の 6.8。第 53・54 章）。練習では、v4 の判定済みの組を 10 件ほど選び、**v4 の判定を見ずに**自分で判定し、その後で v4 の判定と比べます（出典: `docs/final_evaluation_procedure.md:540-553`）。このとき、この節の知識が効きます。

- v4 の判定は AI の判定です。食い違ったとき、「AI の答えが正しいはずだから自分が間違えた」と考えてはいけません。食い違いは**手引きの穴**として扱い、どちらが手引きに合っているかを考えます。学生の判定を AI に合わせると、正解に AI の解釈が入ってしまうからです（出典: `docs/llm_judgment_survey.md:163-164`）。
- 手引きが曖昧で食い違ったなら、段階 1 に戻って手引きを直します。まだ最終評価のデータを見ていないので、この時点なら直してよいのです（出典: `docs/final_evaluation_procedure.md:549-550`）。
- 練習でも本番でも、AI は事実を調べる補助にだけ使えます（練習で v4 の判定を AI に見せないのは当然です）。AI を使っても使わなくても、`evidence` 欄には、自分で開いて確かめた根拠のファイルと行を、第三者がたどれるように全件書きます。2 人目の判定者がいない分、これが信頼性の担保になります（D67 の 4）。AI を使ったかどうかは、1 件ごとに `ai_used` 欄に書きます（D70 の 3。[第 48 章](ch48.md)）。

**この節のまとめ**: 本記録者 = この repo で解析器を作り、決定の推奨と記録を書いてきた AI（Claude）。決めるのは学生。v3・v4 の判定は本記録者が行い、v4 の数字は論文に使わない。最終評価の判定は学生 1 人が決めて記録し、AI は repo の文脈を持たない AI に事実を聞く補助にだけ使う（2026-10-02 の D70 の 3。10-01 の「使わない」から改めた）。研究の遂行に AI を使ったことは論文で開示する。

<a id="s0-8"></a>
### コード例について

**一言で言うと**: この教科書のコード例は 3 種類あります。**実物を短くしたもの**・**ライブラリの実物**・**説明用**です。どれなのかを必ず書くので、そのコードが本当にどこかで動いているものかどうかが分かります。

**たとえ話**: 料理本の写真の横に、小さく「写真はイメージです」と書いてあることがあります。イメージ写真は分かりやすさのために作ったもので、実際に出てくる料理とは少し違うかもしれません。この教科書の「説明用」は、この「イメージです」の印にあたります。反対に、出典のファイルと行が書いてあるコードは「実物の写真」です。

**小さな例**: 3 種類を 1 つずつ見ます。

1 つ目は**説明用**です。実在のサーバのものではありません。

```python
# 説明用
def greet(name):
    return "こんにちは、" + name
```

- 1 行目の `# 説明用` は、Python の**コメント**（`#` から行の終わりまでは、プログラムとして実行されないメモ）です。この教科書では、説明用のコードの先頭にこの印を付けます。
- 2 行目の `def greet(name):` は、「`greet` という名前の**関数**（処理のまとまりに名前を付けたもの）を作る。外から `name` という値を 1 つ受け取る」という意味です。
- 3 行目の `return "こんにちは、" + name` は、「`"こんにちは、"` という文字列の後ろに `name` をつないだものを、呼び出した側に返す」という意味です。たとえば `greet("花子")` と呼ぶと `"こんにちは、花子"` が返ります。

2 つ目は**実物を短くしたもの**です。出典のファイルと行を書きます。次は、判定の手引きの下書きにある練習用のサーバ（手引きのために書いた小さなサーバで、解析器で実際に走査したもの）の 10〜13 行目です（出典: `docs/drafts/final_judging_guide_draft.md:565,579-582`）。

```
10  def _save_cache(name, text):
11      os.makedirs(CACHE_DIR, exist_ok=True)
12      with open(os.path.join(CACHE_DIR, name), "w") as fh:
13          fh.write(text)
```

- 左端の `10`〜`13` は、元のファイルの**行番号**です。プログラムの一部ではありません。手引きも「写して使うときは行番号を消す」と書いています（出典: `docs/drafts/final_judging_guide_draft.md:567`）。
- 10 行目は、`_save_cache` という関数を作り、`name`（ファイル名）と `text`（書く中身）の 2 つを受け取る、という意味です。
- 11 行目は、`CACHE_DIR` という場所にディレクトリ（フォルダ）を作ります。`exist_ok=True` は「もうあっても、エラーにしない」という指定です。
- 12 行目は、`CACHE_DIR` の中の `name` という名前のファイルを、書き込み用（`"w"`）に開きます。
- 13 行目は、開いたファイルに `text` を書き込みます。

この 4 行が何を意味するのか（ディレクトリを作ること・ファイルに書くことが、なぜ研究で問題になるのか）は、[第 1 章](ch01.md)から少しずつ説明します。Python の書き方の詳しい説明は[第 9 章](ch09.md)です。

3 つ目は**ライブラリの実物**です。MCP の公式の Python SDK（MCP のサーバを Python で書くための部品集。[第 3 章](ch03.md)）のように、この repo の外のファイルを読んだものは、版と場所を書きます。次は MCP Python SDK 1.30.0 の `mcp/types.py:1262-1266` です。

```python
    readOnlyHint: bool | None = None
    """
    If true, the tool does not modify its environment.
    Default: false
    """
```

- 1 行目は、`readOnlyHint` という欄があり、値は「真偽（`True` か `False`）」か「何も無い（`None`）」で、書かなければ `None` になる、という意味です。
- 2〜5 行目は、その欄の説明文です。「true なら、そのツールは自分の環境を変えない。既定は false」と書いてあります。
- この欄が何のためにあり、研究でどう使うのかは、[第 4 章](ch04.md)で詳しく説明します。

**一歩ずつ**: 3 種類を見分ける手がかりをまとめます。

| 種類 | 見分け方 | 信じてよい範囲 |
|---|---|---|
| 説明用 | 先頭に `# 説明用`、または本文に「説明用」とある | 考え方を示すためのもの。実在のサーバがこう書いているとは限らない |
| 実物を短くしたもの | 出典のファイルと行がある | 書いてある行は実物どおり。省いた行があることに注意 |
| ライブラリの実物 | ライブラリの名前・版・ファイルと行がある | その版では実物どおり。版が変わると中身が変わりうる |

**なぜそうするのか**: 説明用の例は、分かりやすさのために余計なものを削っています。それを実物だと思ってしまうと、「実際のサーバはこんなに単純だ」と誤解します。反対に、実物の例を説明用だと思ってしまうと、「これは作り話だから、本当には起きない」と誤解します。どちらの誤解も、判定で原ソースを読むときの勘を狂わせます。ライブラリの版を書くのは、版によって中身が変わるからです。

**よくあるつまずき**:

- **行番号ごとコピーして動かそうとする。** 行番号はプログラムの一部ではありません。消してから使います。
- **説明用の例で「解析器はこれを見つける」と書いてあるのを、実際に走らせた結果だと思う。** 実際に走らせた結果のときは、そう書きます。練習用のサーバは、実際に走査した例です（出典: `docs/drafts/final_judging_guide_draft.md:565`）。
- **ライブラリの説明文を「必ずそう動く」と読む。** たとえば上の SDK のクラスの説明文には、「これらの欄はすべてヒントで、ツールの振る舞いを忠実に表すとは限らない」とも書いてあります（出典: MCP Python SDK 1.30.0 の `mcp/types.py:1251-1253`）。この意味は[第 4 章](ch04.md)で考えます。

**手作業ではどう使うか**: 最終評価の判定で読むのは、いつも**実物**、つまり取得した原ソースです。この教科書の説明用の例で覚えた形が、実物では少し崩れた形で出てきます（変数の名前が違う、間に別の処理が挟まる、別のファイルに分かれている、など）。[第 53 章](ch53.md)では、この練習用のサーバで判定を一通り練習します。自分で写して解析器で走らせてみるときは、行番号を消すのを忘れないでください。

**この節のまとめ**: コード例は、説明用・実物を短くしたもの・ライブラリの実物の 3 種類。説明用は「イメージです」、出典つきは「実物の写真」。判定で読むのはいつも実物。

### どこから読めばよいか

**一言で言うと**: 目的によって、読む章の順番が違います。最終評価の判定をする人には、決まった道順があります。

**たとえ話**: 旅行のガイドブックには、「半日で回る」「歴史を見る」「食べ歩き」のような目的別のモデルコースが載っています。全部の名所を順に回るのがいちばん確かですが、時間が限られているときは、目的に合ったコースをたどります。この節は、この教科書のモデルコースです。

**小さな例**: 目的別の道順です。

- 研究の全体像だけ知りたい → 第 1〜8 章と[第 44 章](ch44.md)。
- 解析器の仕組みを知りたい → 第 11〜20 章（特に[第 20 章](ch20.md)の通しの例）。
- これまでの作業で何をしたかを知りたい → 第 21〜37 章。
- 結果を知りたい → 第 38〜44 章。
- **最終評価の判定をする** → 第 3・4 章 → 第 9・10 章 → 第 13〜20 章 → 第 21・22 章 → [第 37 章](ch37.md) → [第 39 章](ch39.md) → [第 43 章](ch43.md) → 第 45〜52 章 → 第 53・54 章（演習）→ [第 55 章](ch55.md) → [付録 E](appendix-e.md)・F。

**一歩ずつ**: 最後の道順（判定をする人の道順）の理由を、1 つずつ書きます。右の列は、その章の知識が手順書や判定の手引きのどこで効くかです。手順書は最終評価の作業を「段階 0〜9」に分けていて、段階 7 が判定です（[第 45 章](ch45.md)）。

| 順 | 読む章 | なぜ読むか | 手順書・手引きのどこで効くか |
|---|---|---|---|
| 1 | 第 3・4 章 | サーバの起動のしかた（「起動時の初期化」の規則の前提）と、宣言の意味・既定値 | 手引き 14.4（起動時の初期化）、15（宣言ごとの問い） |
| 2 | 第 9・10 章 | 原ソースを読むための Python と、HTTP・SQL の最小限 | 手順 C・D（効果の行を開き、道筋をたどる）、15.1・15.2 の POST や SQL の扱い |
| 3 | 第 13〜20 章 | 解析器が何を「効果」とし、どう道をたどり、どう判定し、何を出力するか。判定の対象（組）は解析器の出力なので、出力が読めないと判定できない | 手順 A・B（判定表と manifest を読む）、13.1（理由コードの読み方） |
| 4 | 第 21・22 章 | 誤りの 2 つの向きと、「先に決めて後から変えない」。判定の作法の土台 | 手引き 21・22（ぶれさせない工夫、決まらない事例） |
| 5 | [第 37 章](ch37.md) | v4 で実際に出た誤りの類（起動時の初期化など）。最終評価でも出る見込みが高い類 | 手引き 20.2（v4 の例）、17（誤の原因 E1〜E9） |
| 6 | [第 39 章](ch39.md) | 判定した結果がどんな数字になるか（分母と下限）。数字の意味を知ってから判定すると、記録すべき欄が分かる | 手順書 23（集計） |
| 7 | [第 43 章](ch43.md) | 裏方の書き込みを違反に数えるかの考え方と、重みを付けない決定 | 手引き 11.3（字義どおりに当てる）、16（書き込み先の種類） |
| 8 | 第 45〜52 章 | 判定の規則そのもの | 手引き 11〜22 の全体 |
| 9 | 第 53・54 章 | 演習 | 手順書 6.8（判定の練習） |
| 10 | [第 55 章](ch55.md) | 集計と論文 | 手順書 23・24 |
| 11 | [付録 E](appendix-e.md)・F | 判定の最中に引く早見表と対照表 | 判定の全体 |

表の読み方を 1 行で確かめます。2 行目は「第 9・10 章を読むのは、原ソースの Python と HTTP・SQL を読むためで、その知識は手順 C・D で効く」と読みます。手順 C は「効果の行を開き、本当にその操作かを確かめる」、手順 D は「ツールの入口から効果まで、自分で道筋をたどる」です（出典: `docs/drafts/final_judging_guide_draft.md:116,131`。[第 48 章](ch48.md)）。

**なぜそうするのか**: 判定は長い作業です。D69 の見込みでは、判定は約 170〜380 時間かかります（これは見込みで、測った値ではありません。出典: `docs/decisions.md:3833`）。途中で規則を変えることはできないので（[第 22 章](ch22.md)）、始める前に、規則の意味と理由を理解しておく必要があります。道順は、規則を理解するのに要る順に並べています。たとえば「起動時の初期化は到達するか」という規則（[第 49 章](ch49.md)）は、サーバの起動のしかた（[第 3 章](ch03.md)）を知らないと意味が分かりません。

**よくあるつまずき**:

- **第 45〜52 章だけ読めば判定できると思う。** 規則は読めても、原ソースの Python が読めなければ（[第 9 章](ch09.md)）、解析器の出力が読めなければ（第 18・19 章）、規則を当てられません。
- **[第 37 章](ch37.md)の v4 の例を「答え」として覚える。** v4 の判定は本記録者（AI）の判定で、考え方の例です（この章の「誰が何をしたか」の節）。
- **[付録 E](appendix-e.md)・F だけを見て判定する。** 早見表は、規則を一度理解した人が思い出すためのものです。理由を説明できないまま早見表に従うと、表に無い形に出会ったときに判断できません。

**手作業ではどう使うか**: 判定の準備（手順書の段階 2）に入る前に、この道順を一度通して読みます。判定の最中に迷ったら、[付録 E](appendix-e.md)（早見表）で規則を思い出し、それでも迷ったら、規則を説明した章（第 48〜52 章）に戻ります。それでも決まらなければ、20〜30 分を目安に「不明」にして理由を書きます（出典: `docs/drafts/final_judging_guide_draft.md:550`。[第 52 章](ch52.md)）。

**この節のまとめ**: 目的別に道順がある。判定をする人は、第 3・4 章 → 第 9・10 章 → 第 13〜20 章 → 第 21・22 章 → [第 37 章](ch37.md) → [第 39 章](ch39.md) → [第 43 章](ch43.md) → 第 45〜52 章 → 第 53・54 章 → [第 55 章](ch55.md) → [付録 E](appendix-e.md)・F の順に読む。早見表は、理解した後で思い出すための道具。

### この章のまとめ

- この教科書の目的は、研究を理解し、最終評価の手動判定を理由を説明しながら行えるようになること。判定の正本は、封をした事前登録と判定の手引き。教科書・手順書は説明と地図。
- 原典は第 3 版の章番号で教科書を引いているので、目次の直後の対応表で読み替える。
- 「D66 の 5」は決定 D66 の 5 番目の項目、「`docs/decisions.md:3754`」はそのファイルの 3754 行目。宣言の D1〜D4 と、決定の番号を取り違えない。
- 外の資料の事実には [確認] / [agent] / [未確認] の印を付ける。未検証の数は論文に使わない。
- 決まっていないものは、未決・保留・【確認】・下書き・未承認と書き分け、黙ってどちらかに倒さない。
- 本記録者 = この repo で解析器を作り、決定の推奨と記録を書いてきた AI（Claude）。決めるのは学生。v3・v4 の判定は本記録者が行い、v4 の数字は論文に使わない。最終評価の判定は学生 1 人が決めて記録し、AI はこの repo の文脈を持たない AI に事実を聞く補助にだけ使う（D70 の 3、2026-10-02 に改訂）。研究の遂行に AI を使ったことは論文で開示する。
- コード例は、説明用・実物を短くしたもの・ライブラリの実物の 3 種類。判定で読むのはいつも実物。
- 判定をする人は、第 3・4 章 → 第 9・10 章 → 第 13〜20 章 → 第 21・22 章 → [第 37 章](ch37.md) → [第 39 章](ch39.md) → [第 43 章](ch43.md) → 第 45〜52 章 → 第 53・54 章 → [第 55 章](ch55.md) → [付録 E](appendix-e.md)・F の順に読む。
