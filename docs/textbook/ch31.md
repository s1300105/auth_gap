## 第 31 章 検証の穴（O34）と A2 の 7/8

> **この章で分かること**:
> - ゲート（付録の仕組み）の「**主語一致**」が、値の材料になった引数（root）の**どれか 1 つ**が検査されていれば、値**全体**を「検査済み」にしていた誤り（O34）。攻撃者は検査されていない引数を使えばよいので、これは**誤 clear** だったこと。
> - 直し方は「root ごとに採点し、**いちばん弱い**ものを採る」（D58 の厳格版）。ゲートは付録の仕組みなので、矛（核）の数は変わらず、付録の判定 `GAP_INJECT` が増える向きだったこと。
> - **較正対**（本物の脆弱性の修正前と修正後のコードの組）と**両側比較**（修正前と修正後を解析器が見分けられるか）の意味。両側比較の 7/8 は、本物の CVE の修正前後を見分けられるかの検査で、[第 23 章](ch23.md)の B3a・B3b（付録のゲートの仕組みのために作った小さなプログラムの検査）とは**別のもの**であること。
> - O34 を直すと、較正対 **A2**（git のフラグ混入）の修正後のコードで、検査されていない別の引数 `context_lines` が見えるようになり、両側比較が **8/8 → 7/8** に下がったこと。
> - A2 に合わせた例外を足せば 8/8 に戻せたが、学生の「**あまり綺麗ではない**」という指摘で取り下げ、**規則は変えずに 7/8 と報告する**と決めたこと。それまでの 8/8 は O34 の誤 clear に一部支えられていたこと。argv の分解は**未決の問い O35** として残したこと。
> - A2 の 7/8 と O35 は、最終評価の論文で**限界として書く**ものであること（手順書の 24.2 節、第 42・55 章）。人の判定でも、「値が複数の引数からできているときは、引数ごとにモデルが決められるかを見る」という同じ考え方を使うこと。

### 31.1 問題 — 1 つの引数の検査が、値全体を「検査済み」にしていた（O34）

#### 一言で言うと

効果に入る値が、**2 つ以上のツール引数**から作られていることがあります。
以前の解析器のゲートの判定は、そのうちの**どれか 1 つ**の引数が検査されていれば、値**全体**を「検査済み」として扱っていました。
けれども攻撃者（モデルを操る人）は、検査されていない方の引数に、好きな値を入れられます。
検査されていない値を「検査済み」と言うのは、問題があるのに何も言わない誤り、つまり**誤 clear** です。
これが O34 です。

#### たとえ話 — 2 つの鞄のうち 1 つだけを検査する

空港の手荷物検査で、旅行者が鞄を 2 つ持ってきたとします。
係員は 1 つ目の鞄を開けて確かめ、問題が無かったので、**2 つとも**「検査済み」のシールを貼りました。
2 つ目の鞄は開けていません。

危ない物を持ち込みたい人は、2 つ目の鞄に入れれば済みます。
「どれか 1 つが検査済みなら全部検査済み」という規則は、持ち込みたい人にとって一番都合のよい規則です。
正しい規則は、「**全部の鞄**を開けて、1 つでも開けていない鞄があれば、検査済みとは言わない」です。

#### 言葉の整理 — 検査（値検証）・主語一致

- **検査**（記録の言葉では「値検証」）
  - やさしい言い換え: 値を使う前に、許してよい値かどうかを確かめること。
  - 正確な定義: ゲートのうち、効果に入る値そのものを条件で確かめ、だめなら先に進ませないもの。許可リスト（`if name not in ALLOWED: raise ...`）、先頭の文字の検査（`if target.startswith("-"): raise ...`）など。
  - 例: `if name not in ALLOWED: raise ValueError()` は、`name` の検査。
- **主語一致**（しゅごいっち）
  - やさしい言い換え: 検査が確かめている値と、効果に入る値が、同じものかどうか。
  - 正確な定義: ゲートの候補が、その効果の位置（slot）の値、またはその値から導かれる値を確かめているときだけ、その位置の要求主体を引き上げる、という条件。解析器は、検査が確かめている値の root と、slot の値の root を比べて決める（`authgap/gate.py` の `subject_ok`）。
  - 例: `name` を検査して、`name` だけから作った値を使うなら主語一致。`name` を検査して、`body` だけから作った値を使うなら主語が違う。

主語一致そのものは、正しい考え方です。
`name` を検査しても、`body` の安全には何も言えないからです。
O34 は、この主語一致を、root が**2 つ以上**ある値に当てるときの誤りでした。

（出典: `authgap/gate.py:1124-1140`（`subject_ok` の説明の文書: 「ゲートしていても、述語のオペランドが当該効果の当該制御位置の値、または前向き def-use でその値から導かれる値でなければ `req` を引き上げない」「照合は root 集合を優先する」））

#### 小さな例 — `name` だけを検査して、`name` と `body` をつなぐ

本書の執筆時に、次の作例を 2 つの版で走らせました。

```python
 1  import os
 2
 3  from mcp.server.fastmcp import FastMCP
 4
 5  mcp = FastMCP("toy31")
 6
 7  ALLOWED = ("alice", "bob")
 8
 9
10  @mcp.tool()
11  def greet(name: str, body: str) -> str:
12      if name not in ALLOWED:              # name だけを検査している
13          raise ValueError("unknown name")
14      os.system("echo " + name + body)     # body は検査されていない
15      return "ok"
16
17
18  @mcp.tool()
19  def greet_one(name: str) -> str:
20      if name not in ALLOWED:
21          raise ValueError("unknown name")
22      os.system("echo " + name)            # name だけを使う
23      return "ok"
```

行ごとに見ます。

- 7 行目: 許してよい名前の一覧（許可リスト）です。タプルのリテラルにしてあります。
- 11 行目: ツール `greet` は、モデルから `name` と `body` を受け取ります。
- 12〜13 行目: `name` が一覧に無ければ、例外で止めます。ここが**検査**です。`body` は検査していません。
- 14 行目: `"echo " + name + body` をシェルのコマンドとして実行します（`os.system`）。この文字列の root は `{name, body}` の 2 つです。モデルが `body` に `; rm -rf ~` のような文字列を入れれば、別のコマンドが走ります。
- 19〜22 行目: ツール `greet_one` は、`name` だけを検査し、`name` だけを使います。root は `{name}` の 1 つです。

2 つの版の答えは次のとおりでした。

| ツール | 値の root | O34 を直す前（`860aa93`） | 凍結版（O34 を直した後） |
|---|---|---|---|
| `greet` | `{name, body}` | ゲートは効いている（`DOM`）、要求主体 `OP`、**`GAP_INJECT` なし** | ゲートは効いていない（`NODOM`、理由 `non_binding_gate`）、要求主体 `MODEL`、**`GAP_INJECT` あり** |
| `greet_one` | `{name}` | ゲートは効いている（`DOM`）、`GAP_INJECT` なし | 同じ（`DOM`、`GAP_INJECT` なし） |

表の読み方: 1 行目は「`greet` では、直す前は `name` の検査が `body` まで含めた値全体に効いたことにされ、危険な位置への注入（`GAP_INJECT`）を出さなかった（誤 clear）。直した後は、`body` が検査されていないので、ゲートは効かないとされ、`GAP_INJECT` を出した（正しい）」と読みます。
2 行目は「root が 1 つだけの `greet_one` では、直す前も後も、検査が効いていると判定する」と読みます。

ここで言う「O34 を直す前」の版 `860aa93` は、O31 の最初の実装のコミットで、O34 の直しはまだ入っていません（[第 23 章](ch23.md)の時刻の表）。
`DOM`・`NODOM` はゲートの判定の印で、`DOM` は「そのゲートが効果を守っている」、`NODOM` は「守っていない」という意味です。
`non_binding_gate` は、`NODOM` の理由の 1 つで、「ゲートの候補はあるが、主語一致に失敗した（この位置の値を縛っていない）」という意味です（[第 14 章](ch14.md) 14.6 節の、ゲートの側の語彙）。

（出典: 本書の執筆時に `git archive 860aa93 authgap` と凍結版の `authgap/` で走らせた結果。manifest の `gate`・`req_val`・`rows` の `verdicts` の欄。`authgap/gate.py:11`（「主語一致に失敗した述語は `NODOM(non_binding_gate)`」））

#### 一歩ずつの説明 — 直す前の解析器は、どう判断していたか

`greet` の 14 行目について、直す前の解析器は次のように考えていました。

1. 14 行目の `os.system` は、コマンドを実行する効果（SPAWN）。危険な位置は、シェルの文字列（`shell_string`）。
2. その位置の値は `"echo " + name + body`。主体は `MODEL`、root は `{name, body}`。
3. 12 行目の `if name not in ALLOWED: raise` は、ゲートの候補。確かめている値の root は `{name}`。
4. 主語一致を確かめる。候補の root `{name}` と、値の root `{name, body}` が**重なっている**（`name` が共通）ので、「主語一致あり」とする。
5. ゲートが効いているので、その位置の要求主体を `OP` に引き上げる（運用者が許可リストで絞った値）。
6. 要求主体が `OP` なので、`GAP_INJECT` は出さない。

誤りは 4 にあります。
「重なっている」ことは、「全部が検査されている」ことではありません。
`body` は 1 度も検査されていないのに、`name` と同じ値の中にいるというだけで、「検査済み」の側に入れられてしまいました。

#### 実物の例 — canvas-mcp の `update_syllabus`

O34 は、[第 29 章](ch29.md)で見たとおり、O30 の直しで表に出ました。
open_questions の記録は、実例として canvas-mcp の `update_syllabus` を挙げています。

- `update_syllabus` の POST の本体（`body`）の値は、root が `syllabus_body`（検査されていない）と `course_identifier` の 2 つ。
- `course_id` を主語にするゲートの候補（`make_canvas_request` の中。運用者の設定の値 `ANONYMIZE_NONE` で等級 `OP`）が、`body` 全体を `OP` に引き上げていた。
- その結果、モデルが自由に決める `syllabus_body` まで「検査済み」になり、`GAP_INJECT` が消えていた。

規模の目安として、記録は「run13 で 41 位置（canvas-mcp 39 / paper-access 2）、run14 で 66 位置」と書いています。
ただし、これは「名前の主語で数えた**上限の目安**」で、manifest のゲートの候補が root ではなく名前しか持たないので、正確な数ではない、と断っています。

（出典: `docs/open_questions.md:972-986`（O34）、`docs/decisions.md:3123-3131`（D57 の「O30 の修正が表に出した既存の誤 clear」））

#### なぜ誤 clear なのか — 攻撃者は弱いところを選ぶ

O34 の記録は、誤りの向きを「**誤 clear**（`GAP_INJECT` が消える）」と書いています。
問題がある（検査されていないモデルの値が、コマンドや送信の本体に入る）のに、何も言わないからです。

なぜ「1 つでも検査されていればよい」ではだめなのでしょうか。
解析器が守りたいのは、「モデルを操る人が、危険な位置に好きな値を入れられないこと」です。
操る人は、守りが**いちばん弱い**入口を選びます。
2 つの引数のうち 1 つが検査されていても、もう 1 つが開いていれば、そこから入れます。
だから、値全体の守りの強さは、**いちばん弱い引数**の守りの強さで決まります。

この考え方は、解析器の別の場所にも既にありました。
要求主体の合流（`req_meet`）は「経路の集合では最弱を採る。攻撃者が最弱経路を選ぶから」と説明されています。
また D25 は、パスの検査（strong-path）を裏付けるときに「MODEL の root **すべて**」を見ることにしていました。
O34 は、同じ考え方を主語一致には入れていなかった、という抜けでした。

（出典: `authgap/ir.py:106-110`（`req_meet` の説明の文書）、`docs/open_questions.md:976-978`（「D25 は strong-path の裏付けにだけ『MODEL の根すべて』を入れ、主語一致には入れていなかった」））

#### よくある誤解・つまずき

- **「O34 は、矛の判定の誤り」**: 違います。ゲートは付録の仕組みで、O34 が変えるのは付録の判定 `GAP_INJECT` です。矛（核）の判定は、宣言と効果だけを入力にしていて、ゲートの結果（要求主体・等級）を使いません。だから、O34 を直しても矛の数は変わりません（31.2 節）。
- **「`name` を許可リストで検査しているのだから、このツールは安全」**: `name` の位置は安全ですが、`body` の位置は開いています。値全体の安全は、いちばん弱い引数で決まります。
- **「root が重なれば主語一致、という規則そのものが間違い」**: root が 1 つなら、重なりは一致と同じなので問題ありません（`greet_one`）。問題は root が 2 つ以上のときだけでした。

#### 手作業ではどう使うか

最終評価の判定では、ゲートの判定（`GAP_INJECT`）を使いません。
けれども、O34 の考え方は、人の判定の「**モデルが決められるか**」を確かめる場面で、そのまま役に立ちます。
宛先・書き先・コマンドが、複数の引数を**つないで**作られているとき、1 つの引数が許可リストで検査されていても、ほかの引数でモデルがその宛先などを動かせるかもしれません。
「どれか 1 つが検査されているから大丈夫」と考えず、**引数ごとに**確かめます（31.7 節の例）。

#### この節のまとめ

以前のゲートの判定は、値の root のどれか 1 つが検査されていれば、値全体を検査済みにしていた（O34）。攻撃者は検査されていない引数を使うので、これは誤 clear（`GAP_INJECT` が消える）。
O30 の直しで canvas-mcp の `update_syllabus` に表に出た。作例でも、直す前の版だけが `GAP_INJECT` を出さないことを確かめた。

### 31.2 直し方 — root のすべてに検査を求める（D58 の O34 の規則）

#### 一言で言うと

学生は、凍結の前に O34 も直すと決めました（D58）。
直し方は、「値に root が 2 つ以上あるときは、**root ごとに**ゲートを採点し、要求主体が**いちばん弱い**結果を採る」です。
検査されていない root が 1 つでもあれば、その root の「ゲートなし」が値全体の答えになります。
すべての root に検査を求めるので、記録はこれを「**厳格版**」と呼んでいます。

#### たとえ話 — 鎖の強さは、いちばん弱い輪で決まる

鎖は、どれか 1 つの輪が切れれば、全体が切れます。
ほかの輪がどれほど太くても、鎖の強さは**いちばん弱い輪**の強さです。

値の守りも同じです。
`name` という太い輪（許可リストの検査）と、`body` という細い輪（検査なし）でできた鎖は、`body` のところで切れます。
厳格版は、輪を 1 つずつ確かめて、いちばん弱い輪の強さを鎖全体の強さにする、という規則です。

#### 言葉の整理 — 厳格版・いちばん弱いものを採る

- **厳格版**
  - やさしい言い換え: すべての材料が検査されているときだけ「検査済み」と言う、きびしい規則。
  - 正確な定義: D58 の O34 の規則。制御位置の値に root が 2 つ以上あるとき、`score_gates` を root ごとに呼び、要求主体はその最も弱いもの（`req_meet`）にする。表示するゲートの結果と等級も最も弱い root のものを使う。root が 1 つ以下のときは今までと同じ。
  - 例: `greet` の `"echo " + name + body` は、`name` の結果（`OP`）と `body` の結果（`MODEL`）のうち、弱い `MODEL` になる。
- **いちばん弱いものを採る**（`req_meet`）
  - やさしい言い換え: いくつかの答えのうち、守りがいちばん弱い答えを選ぶこと。
  - 正確な定義: 要求主体の順序（`MODEL < OP < USER`。右ほど強い守り）で、いちばん下を採る操作。解析器の説明の文書は「経路の集合では最弱を採る。攻撃者が最弱経路を選ぶから」と書いている。
  - 例: `OP` と `MODEL` なら `MODEL`。

（出典: `docs/decisions.md:3155-3160`（D58 の O34 の規則）、`authgap/ir.py:106-110`（`req_meet`））

#### 小さな例 — 凍結版の実装

凍結版の `authgap/analyze.py` の、O34 の部分です（593〜601 行）。

```python

594          if len(value.roots) > 1:
595              # **主語一致は MODEL の根すべてに要求する**（D58、O34）。根ごとに採点し、最も弱い
596              # 要求主体を採る（攻撃者は検証されていない根を使う）。どれか 1 つの根との一致で
597              # slot 全体を引き上げると、検証済みの引数と未検証の引数が合流した値で誤 clear になる
598              # （canvas-mcp `update_syllabus` の `body`）。D25 が strong-path の裏付けに入れた規則と同じ。
```

- 593 行目: まず、値の root の全体（`subjects`）を主語にして、ゲートを一度採点します（`score_gates`）。結果を `sc` に入れます。直す前は、この結果をそのまま使っていました。
- 594 行目: その位置の値の root（`value.roots`）が 2 つ以上あるときだけ、下の処理をします。1 つ以下なら、593 行目の結果をそのまま使います。

- **「`GAP_INJECT` が増えたので、直しで悪くなった」**: 誤 clear が直って、出すべきものが出るようになったのです。増減の向きだけで良し悪しは決まりません。1 件ずつ理由を確かめます（第 21・23 章）。
- **「厳格版は、きびしすぎる規則」**: 「きびしい」のは、検査されていない root を見逃さないという意味です。root が 1 つの値（`greet_one`）は、今までどおり検査が効きます。
- **「矛の数が変わらないなら、O34 は最終評価と関係ない」**: 矛の数は変わりませんが、A2 の 7/8 は論文の限界に書きます（31.7 節）。また、「いちばん弱い引数で決まる」という考え方は、人の判定でも使います。

#### 手作業ではどう使うか

最終評価の判定では、`GAP_INJECT` も要求主体も使いません（付録の印で、判定では読み飛ばします。[第 14 章](ch14.md)）。
manifest で `gate` や `req_val` の欄を見かけても、矛の正誤の根拠にはしません。
ただし、宛先・書き先・コマンドを「モデルが決められるか」を人が考えるときには、「材料のうち**いちばん弱い**ものを見る」という同じ考え方を使います（31.7 節）。

#### この節のまとめ

### 31.3 較正対と両側比較 — 何を確かめる道具か

#### 一言で言うと

**較正対**（こうせいつい）は、公開された本物の脆弱性について、**修正前**と**修正後**のコードを並べた組です。
**両側比較**は、解析器がその 2 つを**見分けられるか**（修正前では問題があり、修正後では問題の形が事前に予想したとおりに変わるか）を数える検査です。
数え方は「8 件中いくつ」で、その中心の列が**事前登録照合**です。
両側比較の 7/8 は、本物の CVE の修正前後のコード（較正対）を使う検査で、[第 23 章](ch23.md)の B3a・B3b（付録のゲートの仕組みのために作った小さなプログラムの検査）とは別のものです。

#### たとえ話 — 答えの分かっている答案で、採点者を確かめる

新しい採点者を雇ったとします。
いきなり本番の答案を任せる前に、**答えの分かっている答案**で確かめるでしょう。
「この答案は 1 か所まちがっていて、直した答案ではそこが正しくなっている」と分かっている組を渡し、採点者が「直す前は × で、直した後は ○」と見分けられるかを見ます。

さらに、確かめる側が**先に**「どこが、どう変わるはず」と書いておけば、後から「この見分け方でも合格にしよう」と基準をずらすことができません。
較正対は「答えの分かっている答案の組」、両側比較は「見分けられたかの採点」、事前登録照合は「先に書いた予想と照らす採点」に当たります。

#### 言葉の整理 — 較正対・両側比較・事前登録照合・座標一致・any-change

- **較正対**
  - やさしい言い換え: 解析器の目盛りを合わせるための、答えの分かっている本物のコードの組。
  - 正確な定義: 公開された脆弱性（CVE）を持つ実際のコードの、修正前（`__vuln`）と修正後（`__fixed`）の木の組。repo では `corpus/A2__vuln`・`corpus/A2__fixed` のように置き、取り出す版を `docs/corpus_spec.json` で固定している。[第 8 章](ch08.md)で見た「両側」を、解析器の確認に使うもの。
  - 例: A2（git の MCP サーバのフラグ混入、CVE-2025-68144）。
- **両側比較**
  - やさしい言い換え: 修正前と修正後を、解析器の出力で見分けられるかの検査。
  - 正確な定義: `scripts/two_sided.py` が、較正対の両方の木を解析器で走らせ、両方にある同じ効果の位置で、決めた座標（効果の種類・値の主体・ゲートの等級と理由・要求主体など）の値が変わったかを比べる検査。
  - 例: A1 では、8 つのツールの道筋で、`cwd`（コマンドを走らせるディレクトリ）の等級が「なし」から `strong-path` に、要求主体が `MODEL` から `OP` に変わる。
- **事前登録照合**（両側比較の主指標）
  - やさしい言い換え: 先に書いておいた「ここが、こう変わるはず」と、実際の変化が合っているかの照合。
  - 正確な定義: `docs/expected_tuples.json` に事前に登録した変化が、その**向き**（修正前の `from` → 修正後の `to`）で、期待した位置に `min_sites` 件以上起きていれば通る。逆向き（修正後 → 修正前）は通らない。期待値は採点器より先にコミットしてある（CLAUDE.md 規則 5）。
  - 例: A2 の期待は「`argv[*]` の等級が、`git_checkout` と `git_diff` の 2 つの道筋で『なし → `strong-token`』、要求主体が `MODEL → OP`（2 か所以上）」。
- **座標一致**
  - やさしい言い換え: 期待した場所の、期待した項目が動いたか（向きと値は問わない）。
  - 正確な定義: 期待した座標が、期待した位置で変化していれば通る。事前登録照合より緩い。
- **any-change**
  - やさしい言い換え: とにかく何かが変わったか。
  - 正確な定義: 8 つの座標のどれかの値が違えば通る、旧来の数え方。`open` を `Path.read_text` に書き換えただけの対や逆向きの対も通すので、「修正を検出した」とは読めない。併記のためだけに残している。

3 つの列の間には、「事前登録照合で通る ⊆ 座標一致で通る ⊆ any-change で通る」という関係があります。

（出典: `scripts/two_sided.py:1-50`（冒頭の説明の文書）、`docs/expected_tuples.json`（`_semantics` と A2 の期待）、`docs/corpus_spec.json`（較正対の版））

### 31.4 8/8 から 7/8 へ — A2 で何が起きたか

#### 一言で言うと

厳格版 O34 を入れると、A2 の**修正後**のコードで、`git diff` に渡すもう 1 つの引数 `context_lines`（差分の前後に何行表示するか）が、**検査されていない root** として見えるようになりました。
修正で入った検査は `target`（比べる相手のブランチ名など）だけに効き、`context_lines` には効きません。
そのため、`git_diff` の道筋では「修正後は強い検査あり」と言えなくなり、事前登録した変化が起きず、両側比較が **8/8 → 7/8** に下がりました。
言い換えると、**それまでの 8/8 は、O34 の誤 clear（`target` の検査が `context_lines` の位置にも付いていた）に一部支えられていた**のです。

#### たとえ話 — 2 人連れの訪問者

ビルの入口に、新しく受付を置いたとします（修正）。
受付は、訪問者の名札（`target`）が偽物でないかを確かめます。
ところが、この入口からは、名札の人と一緒に**付き添いの人**（`context_lines`）も入れます。
付き添いの人は、何も確かめられません。

以前の点検係（O34 の前の解析器）は、「名札を確かめた人と一緒に入ったのだから、付き添いも確かめ済み」と記録していました。
新しい点検係（厳格版）は、「付き添いは確かめられていない」と記録します。
すると、「この入口は修正で完全に守られるようになった」という、前もって書いておいた予想（事前登録）と合わなくなりました。

#### 小さな例 — A2 の修正後のコード

A2 の修正後の木（`corpus/A2__fixed/src/git/src/mcp_server_git/server.py`）から、関係する部分を抜き出します（行番号は原ソースのもの）。

- 123 行目: `target` が本当にある git の参照（ブランチ名など）かも確かめます。

#### 一歩ずつの説明 — それまでの 8/8 は何に支えられていたか

O34 を直す前の解析器では、A2 は 8/8 の側に入っていました。
なぜでしょうか。

直す前の主語一致は、「root のどれか 1 つが検査されていれば、位置全体を検査済み」でした。
124 行目の `argv[*]` の root `{target, context_lines}` のうち、`target` が検査されているので、位置全体が `strong-token`・`OP` になりました。
つまり、`target` の検査が、`context_lines` の位置にも**付いて**いたのです。
これは O34 の誤 clear そのものです。

その誤 clear のおかげで、`git_diff` の道筋でも「なし → `strong-token`」「`MODEL → OP`」が観測され、事前登録した期待が満たされていました。
決定の記録は、このことを隠さずに、「**これまでの A2 の 8/8 は、O34 の誤 clear（`target` の検証が `context_lines` の位置にも付いていた）に一部支えられていた。これ自体を結果として書く**」と決めています。

ここに、この章のいちばん大事な教訓があります。
**解析器の誤りを直すと、成績が下がることがある**のです。
それは、それまでの成績の一部が、誤りに支えられていたからです。
成績が下がったことは、直しが間違っている証拠にはなりません。

（出典: `docs/decisions.md:3178-3181`（D58 の追記の決定 1））

#### `context_lines` は本当に危ないのか — O35 の論点

ここで、自然な疑問が湧きます。
「`context_lines` は `--unified=` の**後ろ**に付くだけだから、新しいオプションは作れないのでは」。

O35 の記録は、まさにこの点を論じています。

- フラグ混入（CWE-88）の危険は、モデルが `-` で始まる**要素**を送り込み、コマンドに新しいオプションとして読ませることにある。
- `f"--unified={x}"` のように、先頭が定数の `--opt=` になっている要素では、`x` はオプションの**値**にしかならず、新しいオプションは作れない。
- 解析器は、コマンドの引数の 1 つの要素を 1 つの位置として扱い、要素のどこかに検査されていないモデルの root があれば `GAP_INJECT` を出す。
- ただし、値の位置でも、オプションによっては**値そのものが危険**（`--output=`、`--upload-pack=` など）なので、「値の位置なら安全」とは言えない。

つまり、A2 の `context_lines` は、`--unified=` の値なので、たぶん危なくありません。
けれども、「`--opt=` の値の位置は数えない」という規則を一般に入れると、`--output=` のような危ない値まで見逃します。
どちらが正しいかは、A2 だけを見ても決められません。

（出典: `docs/open_questions.md:988-1003`（O35））

#### よくある誤解・つまずき

- **「A2 の修正は不十分だった（本当は脆弱）」**: そうとは言っていません。`context_lines` は `--unified=` の値なので、新しいオプションは作れない、という見方が有力です（O35）。7/8 は「解析器が、この修正を事前登録した形で見分けられなかった」という意味で、「修正が失敗した」という意味ではありません。
- **「O34 の直しが A2 を壊した」**: 壊したのではなく、それまで O34 の誤 clear に隠れていた `context_lines` を見えるようにしたのです。
- **「型の注釈が `int` なのだから、`context_lines` は検査されている」**: このハンドラでは、`GitDiff` の型はツールの一覧で知らせるのに使われるだけで、ハンドラの中では確かめていません（D58 の追記）。注釈は約束であって、検査ではありません。

#### 手作業ではどう使うか

- 人の判定でも、1 つのコマンドや 1 つの宛先が**複数の引数から組み立てられている**ときは、引数ごとに「モデルが何を決められるか」を見ます。`target` が検査されていても、`context_lines` は開いています。開いている引数が、**どの位置に**入るか（新しい要素になるのか、決まったオプションの値になるのか、URL のどの部分になるのか）で、モデルにできることが変わります。
- 「型の注釈がある」「検査らしい行がある」だけで、検査済みと決めません。その検査が、**その値**を確かめているかを読みます（主語一致の考え方）。

#### この節のまとめ

A2 の修正後の `repo.git.diff(f"--unified={context_lines}", target)` で、修正の検査は `target` にしか効かず、`context_lines` は検査されていない root として残る。厳格版 O34 は弱いほうを採るので、`git_diff` の道筋で事前登録した変化が起きず、A2 は事前登録照合で落ちた（7/8）。
それまでの 8/8 は、`target` の検査が `context_lines` の位置にも付いていた O34 の誤 clear に、一部支えられていた。`--opt=` の値の位置を数えるべきかは O35 の論点。

### 31.5 例外を足さなかった理由 — 学生の「あまり綺麗ではない」

#### 一言で言うと

「`--unified=` のように、定数のオプション名の後ろに値が付く形だけは数えない」という例外を足せば、A2 は 8/8 に戻せました。
けれども、それは「**A2 が落ちたのを見てから、A2 の形に合わせて規則を足す**」ことです。
学生の「あまり綺麗ではない」という指摘で、この案は取り下げました。
代わりに、**規則は変えずに 7/8 と報告し**、それまでの 8/8 が O34 の誤 clear に一部支えられていたことも結果として書き、argv の分解は**未決の問い O35** として残すと決めました（D58 の追記）。

#### たとえ話 — 矢を射た後で的を描く

[第 22 章](ch22.md)で、「矢を射た後で的を描く」というたとえを学びました。
矢を射てから、刺さった場所を中心に的を描けば、どんな矢も真ん中に当たったように見えます。

A2 に合わせた例外は、これの小さな形です。
「7/8 になった」という結果を見てから、「その 1 件が通るように、規則に穴を開ける」のです。
穴を開けた後の 8/8 は、「解析器が A2 を見分けられた」ことを示しません。
「A2 が通るように規則を作った」ことを示すだけです。

#### 言葉の整理 — `xfail(strict=True)`・期待値ファイルの凍結

- **`xfail(strict=True)`**（失敗を予期したテスト、厳密）
  - やさしい言い換え: 「このテストは今は落ちる。落ちるのが正しい状態だ」と印を付けたテスト。もし通ってしまったら、それを失敗として知らせる。
  - 正確な定義: Python のテストの道具 `pytest` の印。印を付けたテストが落ちれば「予期した失敗（xfailed）」として成功扱い、通れば `strict=True` のときは「予期しない成功（XPASS）」として**失敗**扱いになる。
  - 例: A2 を期待する 2 つのテスト（`test_two_sided_calibration` の A2 と、`test_preregistered_direction_passes[A2]`）。理由の欄に「D58 の追記: 厳格版 O34 で A2 の git_diff が落ちる（O35）」と書いてある。
- **期待値ファイルの凍結**
  - やさしい言い換え: 事前に書いた「こうなるはず」の表を、結果を見た後で書き換えないこと。
  - 正確な定義: `fixtures/*/expected.json` と `docs/expected_tuples.json` は、採点器より先にコミットし、凍結した項目として扱う（CLAUDE.md 規則 5）。結果が合わなくても、期待値のほうを結果に合わせて変えない。
  - 例: A2 の期待「`git_diff` の道筋でも `strong-token`」は、7/8 になった後も消していない。

（出典: `tests/test_two_sided_calibration.py:21-31`、`tests/test_two_sided_preregistered.py:98-115`、`CLAUDE.md` の規則 5）

#### 小さな例 — 取り下げた案と、決めたこと

決定の記録（D58 の追記）を、表にします。

| | 中身 | 扱い |
|---|---|---|
| 案 1 | argv の要素が定数の `--opt=` で始まるときは、その中の root を数えない例外を足す | **取り下げ**。A2 が落ちたのを見てから、A2 の形に合わせて足す規則で、CLAUDE.md 規則 5（凍結した項目を結果を見て変えない）に反する。逸脱として開示しても、較正に合わせた調整であることは変わらない。学生の指摘（「あまり綺麗ではない」）で取り下げた |
| 決定 1 | 規則は上のまま（厳格版）で実装する。A2 の両側比較は **7/8** と報告する | **これまでの A2 の 8/8 は、O34 の誤 clear に一部支えられていた**。これ自体を結果として書く。期待値ファイルは凍結済みなので変えない。A2 を期待する 2 つのテストは `xfail(strict=True)` にし、理由に D58 の追記を引く（通るようになれば落ちて気づく。期待値そのものは消さない） |
| 決定 2 | 「argv の要素は、先頭（どのオプションか）と値（`=` の後ろ）に分けて主体を見るべきでは」は、O35 に**未決**として置く | URL を host / path に、SQL を先頭の文と残りに分けたのと同じ種類の分解で、筋のある一般論。けれども **A2 を見て思いついた**ので、今は入れない |
| 決定 3 | **採るなら、規則を先にコミットし、A2 を含まないデータ（母集団 v3）で確かめる** | A2 で作って A2 で確かめても証拠にならない。凍結後の変更なので逸脱として記録する |

表の読み方: 決定 3 の行は「もし将来 argv の分解を入れるなら、まず規則を文章で書いてコミットし、A2 とは関係の無いデータで、増える行・減る行と誤りを測る。A2 で確かめるのでは、A2 に合わせて作った規則を A2 で合格させるだけになる」と読みます。

（出典: `docs/decisions.md:3171-3188`（D58 の追記の「検討した案」と「決定」））

#### 一歩ずつの説明 — なぜ案 1 は「結果に合わせた調整」なのか

案 1 の中身は、筋が悪いわけではありません。
O35 の記録が言うとおり、`--unified=3` の `3` は新しいオプションにはなれないので、「値の位置は別に扱う」という考えには一理あります。
それでも取り下げた理由を、順に見ます。

1. **思いついたきっかけが、A2 の失敗だった。** 規則を書く前に「どんな形を数えるべきか」を考えたのではなく、A2 が落ちたのを見て、A2 を通す方法として思いついた。
2. **形が A2 にぴったり合っている。** 「定数の `--opt=` で始まる要素」という条件は、A2 の `f"--unified={context_lines}"` の形そのもの。ほかの較正対や母集団で、この例外が何を変えるかは確かめていない。
3. **A2 で確かめると、循環する。** A2 を通すために作った規則を、A2 で確かめて「通った」と言っても、何の証拠にもならない。
4. **開示しても、調整であることは変わらない。** 「逸脱として正直に書けばよい」という考えもあるが、書いたところで、較正の数字が較正に合わせて作られたことは消えない。

だから決定 3 は、採るとしても「規則を先に書き」「A2 を含まないデータで」確かめる、という条件を付けています。
これは、事前登録（[第 22 章](ch22.md)）と、開発用と評価用のデータを分けること（[第 25 章](ch25.md)）の、両方の考え方です。

#### O35 のその後 — 未決のまま、限界として残った

O35 の見出しは、今も「**未決**（D58 の追記で見つけた。凍結後、v3 で事前登録して確かめる）」です。
けれども、その後の記録をたどると、次のようになっています。

- D59 で解析器を凍結したとき、決定の記録は O35 を「**残した限界（凍結後は直さない）**」の 1 つに挙げた。
- 本書の執筆時に `docs/` の中を検索した範囲では、O35 の規則を書いて v3 で確かめた記録は見当たらない。
- 最終評価の手順書は、論文の限界として「**A2 の 7/8 と O35**」を書く、と決めている（31.7 節）。

つまり、O35 は「問いとしては未決」で、「解析器は O35 を入れないまま凍結され、限界として報告する」という状態です。
最終評価では解析器を変えないので（手順書の冒頭）、O35 が最終評価の前に採られることはありません。

（出典: `docs/open_questions.md:988`（O35 の見出し）、`docs/decisions.md:3380-3381`（D59 の「残した限界（凍結後は直さない）: O35（argv の分解）」）、`docs/final_evaluation_procedure.md:13`（解析器は `analyzer-freeze-3` のまま使う）、`:1415`）

#### 逸脱の記録 — 両方の値を残す

この変更は、事前登録からの**逸脱 #21** として、`docs/preregistration.md` §5 に記録されています。
記録は、変更前（run14）と変更後（run16）の両方の値を並べています。

- 変更前: 効果 10,193 / CONTRADICTION 191 / D1 + D2 の矛 154 / D3 の矛 38 / D4 の矛 0 / `GAP_INJECT` の行 2,810 / 両側比較 事前登録照合 **8/8**。
- 変更後: 7,915 / 189 / 151 / 39 / 0 / 1,705 / **7/8**（A2 が落ちる。これまでの 8/8 は O34 の誤 clear に一部支えられていた。規則は変えずに報告する。O35）。

どちらか一方だけを書くのではなく、両方を並べて、なぜ変わったかを書く。
これが[第 22 章](ch22.md)で学んだ逸脱の記録の形です。

（出典: `docs/preregistration.md:572`（逸脱 #21））

#### なぜそうするのか

- **較正の数字を信じてもらうため**です。もし案 1 で 8/8 に戻していたら、読者は「この 8/8 は、落ちた件に合わせて規則を足した後の数字ではないか」と疑うことができます。7/8 のまま、理由と一緒に出したほうが、数字の意味がはっきりします。
- **誤りを直したことで下がった数字は、正直な数字**だからです。8/8 のほうが見た目はよくても、その一部は O34 の誤 clear に支えられていました。誤りに支えられた 8/8 より、誤りを直した 7/8 のほうが、道具の本当の姿に近いのです。
- **後の人が、同じ判断をたどれるように**するためです。案 1 も、取り下げた理由も、記録に残しています。将来だれかが O35 を採るとき、どこから始めればよいか（規則を先に書き、A2 を含まないデータで確かめる）が分かります。

#### よくある誤解・つまずき

- **「7/8 と書くと道具が悪く見えるので、8/8 に戻す工夫をするのが研究者の務め」**: 逆です。結果に合わせて基準を変えないことが、研究者の務めです（[第 22 章](ch22.md)）。7/8 になった理由を書けば、読者は道具の確かさを正しく判断できます。
- **「`xfail` にしたのは、落ちるテストを黙らせたのと同じ」**: 違います。`strict=True` なので、もし将来 A2 が通るようになれば、テストは「予期しない成功」として失敗し、気づけます。期待値も消していません。
- **「O35 は凍結の後に v3 で試された」**: 記録には見当たりません。D59 で、O35 は「凍結後は直さない」限界に入りました。
- **「案 1 は筋が悪いから取り下げた」**: 筋の良し悪しではなく、**作り方**（A2 を見てから、A2 に合わせて作った）が問題でした。考えそのものは O35 として残しています。

#### 手作業ではどう使うか

最終評価の判定でも、同じ場面が来ます。

- 判定の途中で、手引きの規則を当てると「ちょっと変な結果」になる事例に出会うかもしれません。そのとき、その事例に合わせて規則を足したくなります。手引きの第 22 節は、**判定の途中で手引きを変えない**、どうしても足すなら日時を記録し、足す前と後の判定を分けて報告し、主の結果は事前登録した手引きのままにする、と決めています。D58 の追記と同じ考え方です。
- 結果が気に入らないからといって、走査を取り直したり、抜き取りの対象・seed・分母を変えたりしません（手順書の第 25 節「やってはいけないこと」）。
- 論文では、気に入らない数字も、理由と一緒に出します。A2 の 7/8 は、その練習になります。

（出典: `docs/drafts/final_judging_guide_draft.md:701-709`（第 22 節）、`docs/final_evaluation_procedure.md:1433-1442`（第 25 節 やってはいけないこと））

#### この節のまとめ

A2 に合わせて「定数の `--opt=` の値は数えない」例外を足す案は、A2 の失敗を見てから A2 の形に合わせて作る規則なので、学生の「あまり綺麗ではない」という指摘で取り下げた。規則は変えずに 7/8 と報告し、それまでの 8/8 が O34 の誤 clear に一部支えられていたことも書き、期待値は変えず、2 つのテストは `xfail(strict=True)` にした（逸脱 #21）。
argv の分解は O35 に未決として残したが、D59 の凍結で「凍結後は直さない」限界になり、v3 で確かめた記録は見当たらない。

#### たとえ話 — 健康診断の同じ項目を、毎年同じ方法で測る

健康診断で、ある年に 1 つの数値が基準から外れたとします。
翌年以降も、その項目を**同じ方法**で測り続ければ、外れたままか、戻ったかが分かります。
測り方を年ごとに変えていたら、比べられません。

#### 一歩ずつの説明 — 人の判定での考え方：材料ごとに「モデルが決められるか」

最終評価の矛の判定では、ゲートの判定（`GAP_INJECT`）を使いません。
けれども、宣言に反するかを決めるとき、手引きは「**モデルが決める値は取りうる値の全体で考える**」（原理 3-a）と言います。
宛先・書き先・コマンドが、いくつもの引数から組み立てられているとき、その「取りうる値の全体」を考えるには、**引数ごとに**何が入りうるかを見る必要があります。
これが、O34 の考え方を人の判定に当てたものです。

作り話の例で見ます。
どちらのツールも「関わる範囲は閉じている」（D3、`openWorldHint: False`）と宣言しています。

```python
LOCAL_HOSTS = ("127.0.0.1", "localhost")


@mcp.tool(annotations={"openWorldHint": False})
def fetch_a(host: str, path: str) -> str:
    if host not in LOCAL_HOSTS:
        raise ValueError("host not allowed")
    return httpx.get(f"http://{host}/{path}").text      # host の後に "/" がある


@mcp.tool(annotations={"openWorldHint": False})
def fetch_b(host: str, path: str) -> str:
    if host not in LOCAL_HOSTS:
        raise ValueError("host not allowed")
    return httpx.get(f"http://{host}{path}").text       # host の後に "/" が無い
```

- どちらも、`host` を許可リストで検査しています。`host` に入れられるのは、`127.0.0.1` か `localhost` だけです。
- `path` は、どちらも検査していません。モデルが好きな文字列を入れられます。
- 違いは、`host` と `path` の間に `/` があるかどうかだけです。

`fetch_a` では、`/` の後ろはパスなので、`path` に何を入れても、宛先のホストは `127.0.0.1` か `localhost` のままです。
たとえば `path` が `@evil.example` なら、URL は `http://127.0.0.1/@evil.example` で、ホストは `127.0.0.1` です。
宛先の取りうる値の全体はローカルだけなので、D3 には**反しません**。

`fetch_b` では、`path` が `host` のすぐ後ろにつながります。
`path` が `@evil.example/x` なら、URL は `http://127.0.0.1@evil.example/x` です。
URL の決まりでは、`@` の前は利用者の情報で、`@` の後ろがホストなので、宛先のホストは `evil.example` になります。
モデルは `path` を使って、外部のホストを宛先にできるのです。
宛先をモデルが決められるので、D3 に**反します**（手引きの 15.3 節）。

本書の執筆時に、Python の標準の `urllib.parse.urlsplit` でこの 2 つの URL を分けると、ホストはそれぞれ `127.0.0.1` と `evil.example` でした。
また、凍結版の解析器は、`fetch_a` と `fetch_b` の**両方に** D3 の矛（理由 `net_model_host`）を出しました。
解析器の矛の判定はゲート（`host` の許可リスト）を見ないので、`fetch_a` にも矛が出るのです。

人の判定では、次のようになります。

| ツール | 宛先の取りうる値の全体 | D3 に反するか | 解析器の矛の判定 |
|---|---|---|---|
| `fetch_a` | `127.0.0.1` か `localhost` だけ | 反しない | **誤**。解析器は「宛先をモデルが決められる」と読んだが、取りうる値はローカルだけ。誤の原因は E7（モデルが決められないのに決められるとした）が近い。迷ったら E9 にして説明を書く |
| `fetch_b` | `@` を使えば任意のホスト | 反する | **正**（到達するなら）。`host` の検査は、`path` から入る宛先を止めない |

表の読み方: 2 行目は「`fetch_b` は `host` を検査しているが、`path` という検査されていない材料で、宛先のホストを外部に変えられる。だから D3 に反し、解析器の矛は正しい」と読みます。
これは、O34 の「`name` を検査しても、`body` から入れられる」と同じ形です。

（出典: 本書の執筆時に作った作例を凍結版で走らせた結果と、`urllib.parse.urlsplit` で確かめた結果。`docs/drafts/final_judging_guide_draft.md:56-71`（11.3 採った原理。原理 3-a）、`:354-365`（15.3 D3）、`:428-445`（17 誤の原因の分類）、`authgap/verdict.py:261-268`）

#### なぜそうするのか

- **論文の限界に書くのは**、道具の確かさを読者が判断できるようにするためです。7/8 の理由が書かれていれば、読者は「この解析器は、決まったオプションの値の位置にある検査されていない引数を、危険な位置として数える」と知ったうえで、結果を読めます。
