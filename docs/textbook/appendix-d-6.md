## 第 27 章 深さを 3 から 4 へ の答え

この章の演習は、repo の記録（`docs/decisions.md` の D34・D49〜D54・D64 の追記・D69・D70、`docs/open_questions.md` の O29、`docs/depth_sensitivity.md`、`docs/preregistration.md` の逸脱 #8・#17・#25、`docs/final_evaluation_procedure.md` の 0-1・第 26・27 節、`evidence/scan_v2_v4_run1/summary.json`。本書の執筆時に確かめたもの）と、説明のための作り話の数字を使っています。
作り話の数字は、本当の値ではありません。

### 演習 27-1（深さを書き込む）

**(1)** 深さは次のとおりです。

```
0  list_notes   （本体）
1  mark_seen    （18 行で呼ぶ）
2  touch        （14 行で呼ぶ）
3  _db          （10 行で呼ぶ）
4  _open        （7 行で呼ぶ。4 行で接続を作る）
```

**(2)** なりません。
上限 3 では、`_db`（深さ 3）の中身は読みますが、`_db` が呼ぶ `_open`（深さ 4）へは降りません。
だから `_db()` の戻り値の型が分からず、10 行の `conn` が SQLite の接続だと分かりません。
受け手の型が分からない `.execute()` は DB の効果にせず、ユニットの `db_unresolved` に `{"method": "execute", "lineno": 11, ...}` のような記録が残ります。
ユニットの `cap_hits` には `depth` が付きます。
効果が無いので、D1 の答えは何も出ません。

**(3)** 上限 4 では `_open` の中身まで読むので、`conn` が SQLite の接続だと分かり、11 行の `.execute()` は DB の効果になります。
SQL の先頭の語が `UPDATE`（データを変える文）なので、読むだけと申告した D1 に対して**矛**（理由 `db_modify`）になると予想できます。

本書の執筆時に、この作例に MCP サーバを作る 2 行（`from mcp.server.fastmcp import FastMCP` と `mcp = FastMCP("notes")`）を足して、凍結版の解析器で深さの上限だけを 3・4・5 に変えて走らせました。
上限 3 では `cap_hits` が `["depth"]`、`db_unresolved` に `execute` が 1 件で、効果は 0 件でした。
上限 4・5 では、DB の効果が 1 件（道筋 `mark_seen` → `touch`）出て、注記は `contradiction:D1` と `contradiction_reason:D1:db_modify` でした。
（2 行を足したので、走らせたファイルでは `.execute()` は 17 行目でした。site の名前は `psycopg.Cursor.execute` と表示されましたが、これは[第 17 章](ch17.md)で見た既知の表示の誤りで、kind は `DB` です。）

### 演習 27-2（未解決率を計算する）

**(1)** 495 ÷（2,989 + 495）= 495 ÷ 3,484 ≒ 0.142、つまり **14.2%** です（`docs/depth_sensitivity.md` の表と同じ）。

**(2)** 深さを上げる前は 150 ÷（600 + 150）= 150 ÷ 750 = **20.0%** です。
上げた後は 90 ÷（750 + 90）= 90 ÷ 840 ≒ **10.7%** です。

**(3)** 消えた矛は**回帰**（前にできていたことができなくなった）の候補なので、3 件を 1 件ずつ、なぜ消えたかを確かめます。
`scripts/compare_scans.py` で前後の run を突き合わせ、消えた組を原ソースで見ます。
増えた側だけを見て「よくなった」と書いてはいけません（`CLAUDE.md` の落とし穴「母集団の run を取り直したら `scripts/compare_scans.py` で前の run と突き合わせる」）。
D53 では、深さを上げて消えたものが 0 だったことを確かめています。

### 演習 27-3（時間上限の記録を読む）

**(1)** 解析されて manifest に入ったユニットは `n_units` の **40 個**、時間上限で解析されなかったユニットは `budget_skipped` の **120 個**です。
この木で見つかったユニットは、合わせて 160 個と読めます。

**(2)** `truncations` には、`{"relpath": "", "cap": "tree_budget", "count": 120}` の要素があると考えられます（ほかの 2 つは、`ast_node_cap` などの別の打ち切りです）。
`tree_budget_prep` ではないと考える理由は、40 個のユニットが解析されているからです。
`tree_budget_prep` は、ユニットを見つけた直後に上限を超えていたときの打ち切りで、そのときは**全部の**ユニットを打ち切るので、`n_units` は 0 になります（[第 18 章](ch18.md) 18.11 節の meta-skill-evloving）。
この木では、ユニットを順に解析している途中で上限を超え、残りの 120 個を打ち切ったと読めます。
（出典: `authgap/runner.py:88-96, 128-133`、`authgap/report.py:279-284`）

**(3)** 取り直しません。
手順書は、時間上限で打ち切られた木について「取り直さない。件数と所要時間を記録する。遅いマシンなら、走らせる前に速いマシンを選ぶ（走らせた後に選び直さない）」と決めています（`docs/final_evaluation_procedure.md:1451`）。
走査は 1 回で、取り直すのは道具の故障で止まったときだけです（事前登録の下書き、`docs/drafts/prereg_2_12_draft.md:39`）。
v2 でも、180 秒で 716 ユニットを飛ばした後、900 秒の再走を**感度分析として併記するだけ**にし、主の結果は事前登録の手続き（180 秒）のままにしました（D34、逸脱 #8）。
結果を見てから上限を変えて主の結果を差し替えると、「都合のよい値を選んだ」ことになるからです。
報告には、この木の名前、`budget_skipped` の 120、`elapsed_s` の 241.5 秒、走らせた計算機を書きます。

### 演習 27-4（見込みを計算する）

**(1)** 2,800 × 9 秒 = 25,200 秒 = **7 時間**です。
深さ 3・5 も走らせると、およそ 3 倍の **21 時間**の見込みです。
（深さ 5 は v2 で深さ 3 より 24% 遅かったので、実際は 21 時間より少し長くなるかもしれません。）

**(2)** 「**見込み（測っていない値）**。v4 の 88 木の 1 木平均 9 秒を当てて計算した。取得の時間は含まない。計算機の速さで変わる」といった言葉を添えます。
`CLAUDE.md` の規則 1（未検証の統計を引用しない）と同じ考え方で、測った値と見込みを区別して書きます。

**(3)** 11 時間を**測った値**として記録し、走らせた計算機（CPU・メモリ・同時に走らせた本数）と日時も書きます（`docs/final_evaluation_procedure.md:655`）。
見込みとの差は、そのまま並べて書けば十分です。走査の結果の正しさには関係しません。
あわせて、`budget_skipped` が 0 でない木が無いかを確かめます。計算機が遅いと、時間上限に当たる木が増えるからです（v2 の run23 と run24 で、同じ木の時間がおよそ 2 倍違った例）。
時間がかかったことを理由に、走査をやり直したり、計算機を替えて取り直したりはしません。

### 確認問題 27-1

深さの上限 3 は、仕様書（`AUTHGAP_BRIEF_v3.md:243`「深さ 3 はこの下向きの呼び出し深さ」）に書かれ、解析器の指紋の `caps` に出る、事前登録した値だったからです。
事前登録した値を後から変えたら、変える前と後の数・理由・日付を記録する決まりです（[第 22 章](ch22.md)）。
しかも、この変更は感度分析の結果を見てから決めたので、逸脱 #17 には「純粋な事前登録ではない」と書いてあります。
仕様書の「深さ 3」は書き換えず、設計の記録として残しました（`CLAUDE.md` の規則 6）。
深さ 3 の値は `--max-depth 3` で出し直せ、DCIChecker と並べる行は深さ 3 でも出して併記します（D54）。

### 確認問題 27-2

深さを上げるのは「見える範囲を広げる」変更なので、本来は、前に見えていたものが消えるはずがありません。
もし消えたものがあれば、深さの変更が、どこかで別の読み方まで変えてしまったという不具合の手がかりです。
D53 で、3 → 4、3 → 5、4 → 5 のどれでも、ユニット・効果の位置・道筋・矛が 1 件も消えていないと確かめたので、「深くしても、深さ 3 で見えていたものはそのまま残り、増えた分だけを比べればよい」と言えるようになりました。
増えた側だけを見て「よくなった」と書かないための確認です（`CLAUDE.md` の落とし穴、[第 23 章](ch23.md)）。

### 確認問題 27-3

打ち切ったユニットを黙って捨てると、その木は「ユニットが少なく、矛の無い木」に見えてしまいます。
打ち切りは、ランダムな欠けではなく、大きな木や遅い解析と結び付いた欠けです（D34 の meta-skill-evloving、run21 の xagent・mcparmory）。
落ちたユニットに矛があっても見えないので、誤 clear の向きの欠けになります。
`CLAUDE.md` の規則 4（解決できなかったものは「不明」として記録する。黙って安全側に倒さない）に従い、数を必ず残します。
数は、`summary.json` の `trees[].budget_skipped` と、manifest の `truncations` の `tree_budget`（または `tree_budget_prep`）の 2 か所に残ります。
打ち切ったユニットそのものは manifest の `units` には入りません。

### 確認問題 27-4

測った値ではありません。**見込み**です（手順書の第 27 節の見出しも「見込み。測っていない」）。
v4 で**測った**「1 木平均 9 秒」（88 木の `elapsed_s` の平均 8.97 秒）を、最終評価の MCP サーバの木の見込みの数（約 3,000 木。枠の残り約 3,460 repo に、v4 の率 88 / 100 を当てたもの）に掛けて、約 27,000 秒 ≒ 7.5 時間、それを丸めて「約 8 時間」としています。
取得の時間は含まれず、計算機の速さでも変わります。

## 第 28 章 食い違いの原理を選ぶ の答え

この章の演習は、repo の記録（`docs/decisions.md` の D32・D41・D55・D56・D60・D62・D67・D70、`docs/open_questions.md` の O23、`docs/contradiction_principles.md` の §0〜§7、`docs/drafts/final_judging_guide_draft.md` の 11.3 節と第 16 節、`git log`。本書の執筆時に確かめたもの）と、説明のための作り話のツールを使っています。

### 演習 28-1（原理を当てる）

### 演習 28-2（件数を理由にする危うさ）

**(1)** 「このデータで誤警報が多くなるから、その規則を採らない」という理屈は、**規則をデータに合わせて選ぶ**ことになるからです。
1 マスずつ件数を見て決めると、それぞれの判断はもっともらしくても、全体としては「主指標の定義を結果に合わせて選んだ」ことになります（D56 の冒頭）。
また、マスごとに理由が別の考え方（「データを変えない」「誤警報が多い」「保守が重い」）に立つので、全体の一貫性がなくなります。

**(2)** **不**（理由 `net_post`）です。
原理 1-ii を b（リモートの状態も環境に含める）にしたので、相手のサーバの状態を変えることも「環境の変更」です。
けれども、`POST` が相手を変えるかは、相手のサーバの意味しだいで、静的には決まりません（RPC の照会も `POST` で送る）。
そこで原理 2 a（静的に決まらないものは不明）が効いて、不になります。

**(3)** 不の中身の判定（D69 の 4、手引きの 18A 節）で役に立ちます。
解析器が `net_post` の不にした組について、人は相手の API の意味を調べ、「作成・更新・削除」か「照会」かを決めます。
JSON-RPC の照会、SPARQL の問い合わせ、トークンの取得、埋め込みの計算などは、`POST` でも読むだけの例です。
ただし、v2 の 6 木で読み取りだったことは、最終評価のデータの `POST` も読み取りだという根拠にはなりません。1 件ずつ調べます。

### 演習 28-3（感度分析を読む）

**(1)** 原理 1-ii を a（リモートの状態を環境に含めない）にすると、D1・D2 では、通信の相手の状態を変えるかどうかを問わなくなります。
だから、D1 の `net_post`（POST の不）や `net_method_unknown`（メソッドが読めない不）など、`net_` で始まる理由の不が消えて内になります。
D1 の不が 86 → 38 に減ったのは、その分です（計算のしかたは[第 17 章](ch17.md) 17.14 節。「D1・D2 の、`net_` で始まる理由を内にする」）。

**(2)** 理由に `model` を含む矛、つまり「モデルが値を選べる」ことを前提にした矛です。
D3 なら、宛先をモデルが決められる `net_model_host` などが考えられます。
原理 3 を b（観測できた値だけで読む）にすると、モデル由来の値は「決まらない」として原理 2 に回るので、矛から不に移ります（D3 の不は 81 → 95 に増えています）。

**(3)** **不の件数**（D1 + D2 で 181）です。
不が矛（165）と同じくらいの規模あるので、原理 2 を b にすると主指標が 346 になります。
矛の 165 だけを書くと、「解析器が決められなかったものが同じくらいある」ことが隠れてしまいます。
D56 は「不明が主指標と同じ規模（D1 + D2 で 181）あることは本文に必ず書く」と決めています（`docs/decisions.md:3055-3056`）。
（あわせて、原理を 1 つずつ反対にしたときの件数の表も載せます。）

### 演習 28-4（コミットの順番）

**(1)** 判定表が、実装して件数を見る**前に**決まっていたことの証拠です。
コミットには時刻が付き、後から書き換えられないので、「実装したら件数がこうなったので、表を変えた」のではないことを、誰でも `git log` で確かめられます。
テストが実装より前にあることは、テストが「実装に合わせて書いた答え」ではなく「表から導いた答え」であることの証拠です。

**(2)** 解析器は、モジュールの定数で渡した宣言を読めません（`D_unknown`。[第 16 章](ch16.md)）。
そのため、作例のツールが全部「宣言なし」になり、テストは判定表とは関係の無い理由で落ちたり通ったりしていました。
これでは、テストが落ちても通っても、判定表どおりに実装できているかが分かりません。
宣言をその場に書く形に直し、「意図した宣言が読めていること」を確かめる前提のテストを足して、塞ぎました（`docs/decisions.md:3015-3021`）。

**(3)** たとえば次の 2 つです（ほかの答えもありえます）。

- 作例の宣言は、その場に書く（`@mcp.tool(annotations={"readOnlyHint": True})`）。定数や関数の戻り値で渡すと、解析器は宣言を読めない。
- 作例を走らせたら、まず「意図した宣言が読めているか」（manifest の `D_kind`）と「意図した効果が出ているか」（`effects`）を確かめてから、矛・不・内の答えを見る。前提が崩れていると、答えの意味が無くなる。

ほかに、「判定の答えを先に書いてから作例を走らせ、予想と違ったら、作例・手引き・自分の読みのどこが違うのかを確かめる」も、この節から学べる注意です。

### 確認問題 28-1

件数を見ながら 1 マスずつ決めると、一つひとつの判断はもっともらしくても、全体として「主指標の定義を結果に合わせて選ぶ」ことになるからです（D56）。
実際、本記録者のおすすめには「(b) だと 25/25 が誤警報」のように、件数そのものが理由に入っていました。
また、マスごとに別の考え方で決めると、全体の一貫性がなくなります。
そこで、件数を載せない原理の文書から原理を先に選び、コミットしてから、各マスに機械的に当てはめる手続きにしました。

### 確認問題 28-2

**言えるのは学生です。** 学生は、件数を 1 つも載せない原理の文書を見て原理を選びました。
**言えないのは、選択肢を書いた者（解析の実装者 = 本記録者）**です。原理の文書を書いた時点で、run11 の件数を見ていました（`docs/o23_cells.md`）。
論文では、「原理は件数を見ずに選んだ。ただし、選択肢を立てた者は件数を見ていたので、選択肢の立て方に偏りがありうる。判定者は 1 人」と、記録どおりに限界として書きます（原理の文書の「開示」、D56、逸脱 #19）。
そのうえで、評価は表を作った誰も見ていない新しいデータで行う（D60）ことを添えます。

### 確認問題 28-3

`readOnlyHint` は「環境を**変えるか**」、`openWorldHint` は「外の世界と**関わるか**」を表す、別々の軸です。
仕様自身が、web 検索のツールを「open world（外と関わる）」の例に挙げていて、web 検索は読むだけです。
つまり、「外と関わるが変えない」ツールがありうるので、「外と関わること」を `openWorldHint` だけの領分として `readOnlyHint` から外す理由はありません。
相手のサーバの状態を変えることも、`readOnlyHint` の問い（変えるか）に入る、と読むのが 1-ii b です。

### 確認問題 28-4

判定は、採った原理を字義どおりに当てて決めます。
到達する（ツールが呼ばれるたびにその行を通る）かつ、宣言に反する（1-i b により、呼び出しを越えて残るログの 1 行も環境の変更）なので、**正**にします。
「たかがログ」という感覚で、正誤を変えてはいけません（手引きの 11.3、D67 の 1）。
軽さは、書き込み先の種類のラベル「**ログ**」で記録します。
あわせて、条件の種類（毎回か、条件つきか）と、根拠のファイルと行を `evidence` に書きます。

### 確認問題 29-3

`select(Item).where(Item.id.in_(ids))` では、モデルの値 `ids` は SQL の中に**入って**います（流れ込む）。

### 確認問題 29-4

判定では、次のことを確かめます（手引きの 18A 節）。

1. **到達するか**: ツールが呼ばれたとき、その書き出しが起きる実行の道が 1 つでもあるか（[第 49 章](ch49.md)）。
2. **モデルが書き先を選べるか**: 書き先の値が、ツールの引数（モデルの値）から、どんな関数を通って届いているかをたどり、モデルが書き先を**実際に選べる**ところまで届くかを確かめる（`…_opaque` の調べ方。`docs/drafts/final_judging_guide_draft.md:524`）。途中で決まったディレクトリの下に限られる、名前を整えるだけ、などの形を見分ける。
3. **宣言に反するか**: モデルが既存のファイルを書き先に選べるなら、上書きできるので、壊さないという宣言に反する（原理 3 a）。モデルが選べず、書き先が呼び出しの前から存在しうるか（上書きか新規作成か）も分からないなら、書き先にファイルが前からありうるかを調べる（手引きの 15.2 節、`fs_writeout` の調べ方）。

到達し、かつ宣言に反するなら「**違反**」、到達しないか宣言に反しないなら「**違反でない**」、20〜30 分調べても決められなければ「**不明**」です。
違反なら、書き込み先の種類（第 16 節）と条件の種類も付けます。

### 確認問題 30-4

**刈る形**（3 つ挙げればよい）: リテラルだけの条件（`if False:`）、`return` / `raise` の後の文（`if`・`else` の両方が `return` した後を含む）、省いた仮引数のリテラルの既定値で決まる条件、リテラルの実引数で決まる条件、呼び出し元で静的な名前をそのまま渡した仮引数で決まる条件。

**刈らない形**（3 つ挙げればよい）: ツールの引数で決まる条件、`**` / `*` で渡した引数、間接の呼び出し、局所変数、`try` の中の import、束縛し直した仮引数、モジュールの定数（`DEBUG = False`）、属性（`settings.verbose`）、ループや `with` の中の `return` の後。

刈らない形の枝の中に矛が出たら、人は、その条件が**本当に定数で閉じているか**を確かめます。
モジュールの名前や属性なら、grep で木の中の書き換え（代入・`global`・`setattr`・属性への代入）を探します。
書き換えが無ければ到達しない（誤、E6）、運用者の設定で書き換えるなら到達する（条件の種類「運用者の設定」）、ツールの引数で決まるなら到達する（条件の種類「引数」）。
ループや `with` の中の `return` なら、必ず先に抜けるかを読みます。
その組に複数の位置があれば、すべての位置について確かめます（手順 G）。

### 演習 32-1（値の欠陥）

**(1) (a) と (c)**

| | 版 | 形 `shape` | 確度 `prov` | 意味 |
|---|---|---|---|---|
| (a) `not None` | 凍結版 | `{"k": "Atom", "const": true}` | `resolved` | `not None` を計算した結果の `True` |
| (a) `not None` | 直す前 | `{"k": "Atom"}` | `resolved` | 被演算子の `None` をそのまま返した。manifest は `none` を書き出さないので、`None` の定数がこの形に見える |
| (c) 合流した後の `yaml` | 凍結版 | `{"k": "Atom"}` | `opaque`（理由 `unresolved`） | 「取り込んだモジュール（木の外なので中身は読めない）か `None`」 |
| (c) 合流した後の `yaml` | 直す前 | `{"k": "Atom"}` | `resolved` | `import` の束縛を記録しなかったので、`except` の側の `None` だけが残り「確かに `None`」 |

(c) は、形の表示は 2 つの版で同じ `{"k": "Atom"}` です。
違いは確度に出ます。
直す前は「確かに読めた（`resolved`）」、凍結版は「木の外から取り込んだ値が混ざっていて読み切れない（`opaque(unresolved)`）」です。
形だけを見て「同じだ」と思わず、確度と合わせて読むことが大事です（[第 14 章](ch14.md)）。

本書の執筆時に、(a) と (c) を 2 つの版で走らせ、表のとおりの記録を確かめました（(c) は `os.system(yaml)` の `shell_string` の slot）。
（出典: `authgap/val/engine.py:2615-2631`（`_unary_shape`）、`:387-396`（関数の中の `import`）、`docs/decisions.md:3299-3313`）

**(2) (b)**

凍結版の D1 の答えは **矛**、理由は **`net_method_model`**（メソッドをモデルが決められる）です。
直す前の版でも、答えは同じ矛（`net_method_model`）でした（本書の執筆時に確かめた）。

理由は、解析器がメソッドを読むとき、値の**定数**が文字列ならそれをメソッドとし、そうでなければ値の**主体と確度**を見るからです（`authgap/effects.py:277-294` の `_http_method`）。

- `m` は、`None`（主体 `OP`）と `q.strip()`（主体 `MODEL`）の合流です。主体は強い方の `MODEL` になります（[第 14 章](ch14.md)）。
- 形が `Atom()` でも `None` の定数でも、文字列の定数ではないので、メソッドの名前としては読めません。
- 主体が `MODEL` で確度が `resolved` なので、「モデルがメソッドを選べる」とされ、D1 では原理 3-a により矛になります（[第 10 章](ch10.md) 10.3 節）。

つまり、この形では、合流の順序の欠陥（直す前は順序によって `None` の定数になりえた）は、答えに効きませんでした。
値の形が誤っていても、判定がその形を読まなければ、答えは変わりません。
O36 の記録が「向きと件数は未測定」と書くのは、このように、効く所と効かない所があるからです。
なお、直す前の版でこの `m` の形が実際にどちらになったかは、manifest に出ない（`requests.request` の行にメソッドの slot が無い）ので、本書では確かめていません。

### 演習 32-2（HTTP の読み方）

本書の執筆時に、6 つをそれぞれ `readOnlyHint=True` のツールにして凍結版で走らせた結果です。

| | ① 効果 | ② `body` の slot | ③ D1 の答え | 理由 |
|---|---|---|---|---|
| (a) `requests.post(url, json=...)` | あり（`requests.post`、POST） | **あり** | 不（`net_post`） | `json=` は O37 の直しで本体として読む。POST は相手の意味しだいなので不 |
| (b) `httpx.Client().put(url, json=...)` | **なし** | — | 何も出ない | セッションの `.put` は語彙に無い（O39） |
| (c) `requests.request(method="PATCH", url=url, data=...)` | あり（`requests.request`、PATCH） | **あり** | **矛**（`net_modify`） | 宛先は `url=` の追記で読める。PATCH は相手を変えるので D1 で矛 |
| (d) `requests.put(url, files=...)` | あり（`requests.put`、PUT）。ほかに `open(path, "rb")` の FS_READ | **なし** | **矛**（`net_modify`） | `files=` は語彙に無い（O39）ので本体は読まないが、宛先は読めるので効果になる。PUT は D1 で矛 |
| (e) `requests.request(**kw)` | **なし** | — | 何も出ない | `**` の展開の実引数を記録しないので、宛先もメソッドも読めない（32.5 節） |

表から分かることは 2 つです。

1. **(c) と (e) は、送っている物（DELETE や PATCH）は似ているのに、書き方だけで答えが変わります。** 解析器の出力に何も無いことは、「送信が無い」ことを意味しません。
2. **(d) のように、本体を読めなくても、宛先が読めれば効果になり、メソッドで答えが決まります。** `content=`・`files=` を読まないことが答えに効くのは、slot が 1 つも無くなる場合（宛先も読めない場合）だけです。

最終評価の見落としの判定では、(b)・(e)・(f) のような形を人が自分で見つけます。
(b) と (f) の原因は「語彙」、(e) は 5 分類の例に無いので「その他」にして `note` に説明を書くのが、手引きの書き方に沿います（本書の読み）。

この章の演習は、repo の記録（`docs/decisions.md` の D59・D60・D66・D70、`docs/open_questions.md` の O45、`docs/fingerprint.json` とコミット `1bcace3` の版、`authgap/report.py` の `fingerprint()`、`scripts/freeze_analyzer.py`、`git log`。本書の執筆時に確かめたもの）を使っています。

| | 仕様書の指紋 `sink_table` | 結合 sha256 | 理由 |
|---|---|---|---|
| (a) `requests.get` の `url.host` を `A(0)` → `A(0, kw="url")` | **変わらない** | **変わる** | `fingerprint()` は sink 表の行ごとに `kind` と **slot の名前の並び**（`sorted(r.slots)`）しか入れない。`url.host` という名前は同じなので、`sink_table` は同じ。一方、`authgap/catalog/sinks.py` のファイルの中身は変わるので、そのファイルの sha256 と結合 sha256 は変わる |

### 演習 34-4（SHA と sha256 を使い分ける）

### 確認問題 35-3

`unresolved_in_tree_calls` は、ユニットごとに「名前が木の中の定義に当たるのに、1 つに決められず降りなかった呼び出し」を、名前・場所（ファイルと行）・候補の数とともに記録する欄です（D61 の G5）。

### 確認問題 35-4

D61 の約束は、「**v3 の取り直しは回帰の確認だけに使い、v3 の精度が上がったことを結果として報告しない**（v3 は開発用で、見た後に直したので評価には使えない）」です。

### 確認問題 36-4

### 演習 37-1（直さなかった理由）

**(a) D66 の規則から**

- 規則 1 は「解析器は `analyzer-freeze-3` のまま。`authgap/`・原理と判定表・語彙を変えない」、規則 2 は「見つけた誤り・見落としは直さず O43 に限界として書く」と、データに触れる前（`d6a8245`、2026-09-29 08:15:39）に決めていました。

- しかも `analyzer-freeze-3` は最終評価に使う凍結版です。直すと、最終評価の解析器が v4 のデータに合わせて調整されたものになり、凍結の約束（[第 36 章](ch36.md)）も破れます。
- v3 との違いにも触れておきます。v3 は凍結の前の開発用データだったので、欠陥を直してよかった（D60・D61）。v4 は凍結の後なので直さない。規則 2 の文面がこの違いを括弧で書いています。

**(b) 直すことの危険から**

- 起動時の初期化を解析器で正しく扱うには、4 つ（順序: lifespan がツールより先に走る / 状態: 大域変数に値が入る / 戻らない: 別の場所で `None` に戻されない / 失敗しない: lifespan が失敗して値が入らないまま受付が始まらない）を全部確かめる必要があります。
- 1 つでも外すと、本当はツールの呼び出しで届く効果を「届かない」とする**誤 clear** を作ります（D17 改訂 2 と同じ危険。[第 24 章](ch24.md)）。
- 今の誤は**誤警報**の向き（安全側）です。直し方を誤ると、それを誤 clear の向き（危険側）に変えてしまいます。

**(c) 直さない代わりにしたこと**

1. O43 に「起動時の初期化をツールの経路に数える」類として、件数（V2 の誤 9 + D4 の誤 3）・木（ccr、shyhurricane）・向き（誤警報）・直さない理由を書いた。
2. 学生と相談して、最終評価での判定のしかたを整理した（O43 の「起動時の初期化の類の整理」）。それが D67 の 2 になった: `main()` / `if __name__` の中だけなら正、lifespan・モジュールの読み込み時なら誤（E1）、読み切れなければ不明。
3. 論文には、「各呼び出しをサーバの状態を仮定せずに独立に解析する設計の限界（誤警報の向き）」として、lifespan の形の誤の件数を報告すると決めた。
4. v4 の判定は付け直さなかった。

### 演習 37-3（起動時の初期化）

**ccr と shyhurricane の違い**

| | ccr | shyhurricane |
|---|---|---|
| 一度だけの初期化の形 | `_ensure_memory()` が `_memory is None` のときだけ `_init()` を呼ぶ | `get_server_context()` が `_server_context` が無いときだけ初期化する |
| 初期化を先に済ませる場所 | `main()` の中（`mcp.run` の前に `_init(args.project)`） | lifespan（`app_lifespan` の中で `get_server_context()` を呼ぶ）。サービスの起動時にも呼ぶ |
| `main()` を通らない起動 | ありうる（モジュールの一番上に `mcp = FastMCP(...)`。`fastmcp run file.py:mcp` など） | どの起動方法でも、lifespan はツールの受付より前に走る |
| v4 の判定 | 誤（到達しない） | 誤（到達しない） |
| 最終評価の規則での判定 | **正**（ツールの呼び出しで届きうる） | **誤**（E1） |
| 正のときの条件の種類 | **起動の方法**（運用者が決める条件なので、併記の (B)・(C) には数えない） | — |

表の読み方: 1 列が 1 つの木です。
ccr の初期化は `main()` の中にしかないので、`main()` を通らない起動のときは、最初のツールの呼び出しで `_init()` が走ります。最終評価の規則（D67 の 2、手引きの 14.4 節）では、起動の方法はコードだけから決め、届きうるなら到達するとします（原理 3 と同じ「能力の上界」の読み方）。
shyhurricane の初期化は lifespan の中にあるので、どの起動方法でも、ツールの受付より前に必ず済んでいます。だから到達しない（誤、E1）です。

補足:

- v4 の判定は付け直しません。最終評価の規則は、最終評価のデータにだけ当てます。
- ccr の D4 の 3 件（`E00`〜`E02`）は、最終評価の規則では到達する側になりますが、追記が「まだ書かれていないとき」だけなので冪等で、宣言に反しません。判定は誤で、原因は E8 です（手引きの 20.2 節「誤 E8（v4 では E1 も重なる）」）。
- この規則では、解析器に有利な側（ccr が正）と不利な側（shyhurricane が誤）の両方が残ります。それを論文に書きます。

**(c) の作り話**

lifespan の中に初期化がありますが、**条件つき**です（環境変数 `PRELOAD` が `"1"` のときだけ）。
手引きの 14.4 節は「lifespan が初期化を**必ず**済ませるか（例外で抜けたら受付が始まらないか、条件つきではないか）も見る。条件つきなら、条件が偽のときはツールの呼び出しで届くので『到達する』」と書いています。

- `PRELOAD` が `"1"` でない起動では、lifespan は初期化をしません。ツールの道筋が `_get_db()` を呼ぶなら、最初の呼び出しで `open_db()` が走り、ファイルが作られます。
- したがって、ツールの道筋が `_get_db()` を呼んでいて、そのファイルの作成が宣言に反するなら（たとえば D1）、**到達する（正になりうる）**です。誤 E1 にはしません。
- 条件の種類は**運用者の設定**（環境変数で決まる）。条件の中身「`PRELOAD` が `"1"` でないとき」は `evidence` に書きます（D83。前の形では `condition` の欄）。運用者が決める条件なので、(B)・(C) には数えません。
- さらに、初期化が走るのはその起動の後の最初の呼び出しだけなので、「初回」の条件も重なると読めます。手引きの手順 H は「複数の条件が重なるなら全部を `;` で並べる」としているので、`condition_type` を「運用者の設定; 初回」と書く読み方もあります。どちらにしても運用者の設定が含まれるので、(B)・(C) には数えない点は変わりません。
- この (c) の答えは、手引きの下書き（14.3・14.4 節、手順 H）の規則を当てはめた本記録者の解釈です。手引きはまだ学生が承認していない下書きなので、承認の時に変わることがあります。
- もし `_get_db()` を呼ぶツールが無ければ、そもそもその効果はツールの道筋ではありません（手順 D で確かめる）。
- `_db = None` に戻す箇所が無いかも grep で確かめます。

### 確認問題 37-4

理由は 3 つあります。

1. **版もデータも違う。** v3 は `analyzer-freeze-1` で v3 のデータ、v4 は `analyzer-freeze-3` で v4 のデータです。差が版のせいか、データのせいか、抜き取りの偶然のせいかを分けられません。D66 の 5 は「v3 と並べてよいが、版もデータも違うので『改善』『悪化』とは書かない」と先に決めています。
