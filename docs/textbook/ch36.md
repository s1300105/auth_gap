## 第 36 章 最終凍結 — 凍結前の添削（D62〜D64）とタグの手違い

> **この章で分かること**:
> - 第 2 版の時点では、run20 の結果をもって解析器を凍結する予定だったこと（`analyzer-freeze-2`）。けれども、タグを打つ前に「添削」（最終凍結の前の点検）をすることになったこと。
> - 添削のやり方。目的・範囲・採否の基準・止める条件を、所見を見る前にコミットしたこと（2026-09-26）。5 つの担当に分けて探し、3 つの観点で「本当に誤りか」を崩しに行き、所見 151 件を 55 の単位にまとめ、学生が 16 単位を選んで直したこと（D64）。
> - 直した誤りの中身と、それぞれの**向き**（誤 clear・誤警報・数え落とし・非決定）。
> - 直した所にもう一度敵対的レビューを通し、段階 B は 3 巡で打ち切ったこと。「見つけ尽くしてはいない」と記録に残したこと。
> - テストの期待（正しい答え）を実装より先に書き、後で改めたものには理由を残したこと。
> - 解析が遅くなり、run21 で 548 ユニットが時間上限で落ちた数え落とし。結果を変えない速度の直しで戻したこと。時間はマシンの速さで変わるので、最終評価の段階 5 で何を記録するか（手順書 9.2・9.3）。
> - N9（URL の読み違い）の直しと、凍結のタグの手違い（逸脱 #26）。最終評価に使う凍結は `analyzer-freeze-3` であること。`docs/fingerprint.json` の `freeze.tag` の欄の食い違い。
> - 同じ時期の決定 D62・D63。凍結の後の約束と、その約束が後で守られたことの確認（D65 の 2・D66・D71）。

### 36.1 予定していた凍結 — run20 で凍結するはずだった

#### 一言で言うと

D61 の直しを終えて取り直した run20 で、消えた効果も消えた矛も 0 件でした。
そこで第 2 版の時点では、run20 の版で解析器を最終凍結し、学生がタグ `analyzer-freeze-2` を打つ予定でした。
凍結の記録（`docs/fingerprint.json`）は書きましたが、**タグはまだ打たれていませんでした**。

#### たとえ話 — 旅行かばんに鍵をかける前

旅行の前の晩、荷物をかばんに詰め終えたとします。
「全部入った」と思って、鍵をかけようとしたところで、ふと「持ち物リストをもう一度見よう」と思い立ちます。
見直すと、充電器を入れ忘れていたり、同じ服を 2 枚入れていたりします。
鍵をかけた後に気づくより、かける前に気づくほうがずっと楽です。

この章の凍結は、この「鍵をかける前の見直し」から始まります。
run20 で荷物は詰め終わった（消えたものは 0）。
けれども、鍵（タグ）をかける前に、持ち物リスト（解析器と集計の道具）をもう一度まとめて点検したのです。

#### 一歩ずつの説明 — 「消えた 0」が凍結の条件だった

- 「消えた 0」は、[第 23 章](ch23.md)で見た突き合わせ（`scripts/compare_scans.py`）の結果です。前の run にあって、新しい run に無いものを数えます。
- この研究では、**消えたユニット・消えた矛は回帰（退行）とみなし、1 件ずつ理由を確かめる**決まりです（CLAUDE.md の落とし穴）。増えた側だけを見て「直った」とは書きません。
- run20 では、消えたものが 0 件だったので、確かめるべき回帰はありませんでした。増えた 2 件の矛も、原ソースで確かめてありました。
- そこで、D61 の結果の記録は「D61 の結果をもって解析器を凍結する（`docs/fingerprint.json`、タグ `analyzer-freeze-2`。**タグは学生が打つ**）」と書きました。
- このときの解析器の指紋（結合 sha256）は `f23619738ad1…` で始まる値で、`authgap/` は 94c40b4 から変えていませんでした。

ここで大事なのは、**記録は書いたが、タグはまだ打たれていなかった**ことです。
添削の計画の冒頭は、この状態を「`docs/fingerprint.json` は `analyzer-freeze-2` を記録しているが、タグはまだ打たれていない（GitHub 上のタグは `analyzer-freeze-1` = `1bcace3` だけ）」と書いています。

（出典: `docs/decisions.md:3508-3509`（「最終凍結」）、`docs/review_plan.md:5-6`（位置づけ）、`:96`（基準点の指紋））

#### なぜそうするのか — 凍結は「記録 + タグ」

[第 22 章](ch22.md)で見たとおり、仕様書は「凍結 = コミットしてタグを打つこと」と定めています。
この研究では、さらに「**タグは人（学生）が打つ**」と決めています（[第 33 章](ch33.md)）。
本記録者が記録（`docs/fingerprint.json`）を書き、学生がそれを確かめてタグを打つ。
2 段に分けることで、「AI が勝手に凍結した」ことにならず、凍結の時点を学生が自分で決められます。

だから、タグが打たれる前なら、点検を挟む余地がありました。
添削は、まさにこの「記録は書いたが、タグはまだ」という時間に入りました。

#### よくある誤解・つまずき

- **誤解: 「第 2 版の『run20 で凍結した』は嘘だった」**
  嘘ではなく、予定でした。記録は「凍結する」と書きましたが、凍結の最後の手続き（タグ）は済んでいませんでした。予定が変わった理由と経緯は、この章のとおり記録に残っています。
- **誤解: 「`docs/fingerprint.json` に書けば凍結が済む」**
  済みません。記録は「この版を凍結する」という申告です。タグが打たれて初めて、git の上で「この版」を名前で指せるようになります。
- **つまずき: 記録の文言と、実際の状態を取り違える**
  記録には予定も書かれます。今の状態を知るには、記録の文言ではなく `git tag -l` を見ます。

#### 手作業ではどう使うか

最終評価の段階 5 の前に、凍結のタグを確かめるときは、文書の記述ではなく **git そのもの**を見ます。

```bash
git fetch --tags && git tag -l
```

- 1 行目の前半 `git fetch --tags`: GitHub にあるタグを手元に取り込みます。
- 後半 `git tag -l`: 手元にあるタグの一覧を表示します。`analyzer-freeze-3` が一覧にあることを確かめます。

文書に「凍結した」と書いてあっても、タグが無ければ凍結は済んでいません。
逆に、文書のタグの名前が古くても（36.11 節の `freeze.tag`）、git のタグと指紋が正しければ、凍結版を使えます。
（出典: `docs/final_evaluation_procedure.md:632-638`（9.1））

#### この節のまとめ

run20 で消えた効果・消えた矛は 0 件で、第 2 版の時点では run20 の版で凍結する予定だった（記録は `analyzer-freeze-2`）。
けれども、タグはまだ打たれておらず、この「記録は書いたが、タグはまだ」の時間に添削が入った。
凍結の状態は、文書の文言ではなく `git tag -l` で確かめる。

### 36.2 なぜ添削をしたのか — 目的は 1 つだけ

#### 一言で言うと

タグを打つ前に、解析器と集計の道具をもう一度まとめて点検することにしました。
これを**添削**と呼びます。
目的は 1 つだけで、「**学生の最終評価を、誤った解析器・誤った集計・誤った説明のまま始めないこと**」です。
目的・範囲・採否の基準・止める条件は、所見を 1 つも見ないうちにコミットしました（2026-09-26）。

#### 言葉の 3 点セット

- **添削**
  - やさしい言い換え: 凍結の前に、解析器と集計の道具を「最終評価を壊しうる誤り」に絞って点検すること。
  - 正確な定義: `docs/review_plan.md` に書いた手続き。目的（最終評価の結果を壊しうるものだけを探す）・範囲（探さないものの一覧）・探し方（5 つの担当・受け付ける条件・止める条件）・確かめ方（3 つの観点）・採否（学生が決める）・直し方（規則 → 反例テスト → 実装）を、始める前に決めた点検。
  - 例: 2026-09-26 から 09-29 までの点検で、所見 151 件を見つけ、16 単位を直した。
- **所見**
  - やさしい言い換え: 点検で見つけた「ここが誤っているのでは」という指摘 1 件。
  - 正確な定義: 小さな再現コード、規則から決まる期待の出力、誤りの向き、一般に言える理由の 4 つがそろった指摘（36.3 節）。`R3-r1-2` のような番号が付く（担当 R3 の第 1 回の 2 件目）。
  - 例: 「SQL の先頭にコメントがあると、先頭の語を `--` と読み、DELETE を矛にできない」（R3-r1-2）。

#### たとえ話 — 車検

車検では、車の全部を見るわけではありません。
ボディの小さな傷や、カーナビの古さは見ません。
見るのは、ブレーキ、ライト、タイヤ、排ガスのように「**このまま走ると危ないもの**」だけです。
見る項目が先に決まっているから、点検には終わりがあり、「どこまで見たか」を記録に書けます。

添削も、この車検と同じ考え方です。
見るのは「最終評価の結果を壊しうるもの」だけ。
文体や速さ（性能）は見ません。
そして、見る項目を、点検を始める前に紙（コミット）に書いておきます。

#### 小さな例 — 3 つの壊し方

添削の計画は、探す誤りを次の 3 種類に限りました。

| 記号 | 壊し方 | 例 | 影響 |
|---|---|---|---|
| (a) | 解析器が**一般に**誤る | 入口の見落としでツールが丸ごと消える。主体を取り違える | 精度・再現率の系統的なずれ |
| (b) | 書いた規則と実装が違う | `docs/contradiction_principles.md` §7 の判定表と、`dparse.py`・`verdict.py` の判定が食い違う | 論文の主張そのものが誤りになる |
| (c) | 評価の道具が黙って数え落とす | parse の失敗・時間切れの扱い、分母の定義、重複の除去、非決定 | 数字が静かに変わり、誰も気づかない |

表の読み方: 1 行が 1 種類の壊し方です。
たとえば 3 行目は「解析器そのものは正しくても、結果を数える道具が、読めなかったファイルや時間切れのユニットを黙って数えずにいると、数字が静かに変わる。しかも誰も気づかない」と読みます。
（出典: `docs/review_plan.md:10-21`（§1 目的））

#### 一歩ずつの説明 — 3 つの壊し方を 1 つずつ

**(a) 解析器が一般に誤る。**
「一般に」がついているのは、特定のサーバだけに起きる誤りではなく、**同じ書き方をすればどのサーバでも起きる**誤りを探すからです。
たとえば、ツールの登録の書き方を 1 つ見落とすと、その書き方をしたサーバのツールは、どれも丸ごと解析の対象から消えます。

**(b) 書いた規則と実装が違う。**
論文で「矛はこの判定表で決める」と書くなら、実装はその判定表どおりに動いていなければなりません。
判定表と実装が食い違っていれば、論文に書いた主張と、実際に数えた数が別物になります。

**(c) 評価の道具が黙って数え落とす。**
ここで新しい言葉を 2 つ定義します。

- **数え落とし**（count-loss）
  - やさしい言い換え: 数えるべきものを、何の印も残さずに数えないこと。
  - 正確な定義: 解析や集計の途中で、ユニット・効果・矛などを落とし、落としたことが件数や印として残らない誤り。落ちたものに矛があっても見えないので、多くは誤 clear の向きになる。
  - 例: 時間上限で打ち切ったユニットの印が、ユニットごとの記録に残らない（U49）。
- **非決定**（nondeterminism）
  - やさしい言い換え: 同じ入力で走らせても、走らせるたびに（または走らせる順番で）結果が変わること。
  - 正確な定義: 入力（木と解析器の版と設定）が同じなのに、処理の順番やプロセスの履歴など、入力の外のものに結果が左右される性質。
  - 例: 1 つのプロセスで木を続けて解析すると、前の木のクラスの中身を使い回すことがあった（U25。36.6 節）。

（c）が怖いのは、「静かに」起きることです。
解析器が誤った矛を出せば、手で判定したときに気づけます。
けれども、数える道具が黙って 1 件落とせば、その 1 件はどの表にも出てこないので、誰も気づけません。

#### 一歩ずつの説明 — 探さないもの

添削の計画は、**探さないもの**も先に書きました。

- 文体・リファクタリング（書き直し）・性能。最終評価の結果を変えないから。
- 付録の語彙（ゲートの等級・weak 理由・validator 形状）。核の主張には使っていないから（D36・D37）。
- 既に記録済みの限界。同じものを再発見しても所見にしない。
- v2・v3 の特定のツールにだけ効く直し方（D61 の方針。[第 35 章](ch35.md)）。
- D3・D4 だけに効く誤り（このときは「探索的な指標」だったので、記録するだけで直さない）。**この項目は後で D62 によって取り下げられました**（36.12 節）。
- sink の語彙や入口の規則の**追加**（月 3 に凍結した語彙なので）。ただし、語彙にある sink が当たらないのは対象。

さらに、計画は「変更が多い場所ほど誤りが多い」と考え、重点を決めていました。
最初の凍結 `analyzer-freeze-1`（1bcace3）の後に `authgap/` で変わったのは、`val/engine.py`（+220 行）と `analyze.py`（+5 行）だけでした。
そこは O31 の改訂・O36・D61 の G3〜G5 の新しいコードで、敵対的レビューの回数もまだ少なかったからです。

（出典: `docs/review_plan.md:23-31`（§2 添削しないもの）、`:32-45`（§3 重点））

#### なぜそうするのか — 先に書いてコミットする理由

計画の冒頭には、「所見を見てから基準を動かせないように、目的・範囲・採否の基準・止める条件をここに先に書く（期待値ファイルを採点器より先にコミットするのと同じ考え方）」と書かれています。

[第 22 章](ch22.md)で見たとおり、研究でいちばん起こりやすい失敗は「結果を見てから基準を選ぶ」ことです。
添削でも同じことが起きえます。
たとえば、所見を見た後で「この種類は範囲の外だった」と決めれば、都合の悪い所見を消せてしまいます。
所見を見る前に範囲を書いてコミットしておけば、そうした後出しはできません。
コミットの時刻（2026-09-26 01:32）が、所見の最初の記録（09-27 04:26）より前であることが、その証拠になります。

もう 1 つの理由は、**目的を 1 つに絞ると、終わりが決まる**ことです。
「よりよい解析器にする」という目的なら、点検は永遠に終わりません。
「最終評価を壊しうるものだけ」なら、範囲の外のものは探さなくてよく、見つけても記録するだけで済みます。

（出典: `docs/review_plan.md:5-8`、`git log -1 896eb47`）

#### よくある誤解・つまずき

- **誤解: 「添削は、解析器の誤りを全部探す作業だった」**
  全部ではありません。最終評価を壊しうる 3 種類に限りました。文体や性能、付録の語彙は、最初から見ていません。
- **誤解: 「探さないものに入っていた誤りは、無い」**
  無いのではなく、見ていないだけです。とくに D3・D4 は、当初は探さない側に入っていたので、後で回を 1 つ足しました（36.3 節）。
- **つまずき: 「性能は見ない」と決めたのに、後で速度を直している**
  計画が除いたのは「性能を良くすること」です。36.10 節の速度の直しは、遅くなったせいで時間上限に当たり、ユニットが**数え落とされた**（壊し方 (c)）ので入れたものです。目的は結果を守ることで、速さそのものではありません。

#### 手作業ではどう使うか

最終評価でも、同じ考え方を使います。
判定の手引きは、判定を始める前に封をして（コミットして）、判定の途中で変えません（[第 22 章](ch22.md)）。
判定の途中で「手引きのこの規則は甘いのでは」と気づいても、その場で規則を変えずに、気づいたことを記録します。
「何を見るか」を先に決めておくのは、判定をぶれさせないためです。

もう 1 つ、(c) の考え方は、学生が段階 8 で集計するときにもそのまま使えます。
集計のスクリプトが、判定の記録の行を黙って落としていないか（たとえば `verdict` の欄が空の行を数えていないか）を、件数の合計で確かめます。

#### この節のまとめ

添削の目的は 1 つ: 最終評価を、誤った解析器・集計・説明のまま始めないこと。探す誤りは (a) 解析器が一般に誤る、(b) 規則と実装が違う、(c) 道具が黙って数え落とす、の 3 種類に限った。
目的・範囲・採否の基準・止める条件は、所見を見る前の 2026-09-26 にコミットした。後から基準を動かせないようにするためで、事前登録と同じ考え方。

### 36.3 どうやって探したか — 5 つの担当と、止める条件

#### 一言で言うと

探す作業を **5 つの担当**（R1〜R5）に分け、AI のエージェントに並行して探させました。
所見として受け付けるのは、**再現コード・期待の出力・誤りの向き・一般に言える理由**がそろったものだけです。
止める条件は「同じ担当で 2 回続けて新しい所見が出なくなるまで。**ただし上限は 4 回**」でした。
実際には、所見は回を重ねても減らず、上限で止めました。
だから「**所見は出尽くしていない**」と記録しています。

#### 言葉の 3 点セット — 担当（レーン）

- やさしい言い換え: 探す範囲を分けた「持ち場」。
- 正確な定義: 解析器と道具のファイルを 5 つの範囲に分け、それぞれに「探すもの」と「壊し方の種類」を割り当てたもの。記録では R1〜R5 と書き、後で D3・D4 を探す追加の担当（R1d・R3d）を足した。
- 例: R3 は「判定表（§7）と実装の突き合わせ」を受け持ち、壊し方 (b) を探した。

#### たとえ話 — 山の捜索隊

山で落とし物を探すとき、捜索隊は区域を分けます。
1 つの班が山全体を歩くより、班ごとに持ち場を決めたほうが、見落としが減るからです。
見つけたら、「どこで」「何を」見つけたかを写真と地図で持ち帰ります。
「このあたりにあった気がする」という話は、証拠にならないので受け付けません。

そして、捜索の終わり方も先に決めます。
「2 日続けて何も見つからなければ終わる。ただし、どんなに長くても 4 日で終わる」。
終わり方を決めずに始めると、いつまでも終わらないか、疲れたところで何となく終わってしまうからです。

添削の探し方は、この捜索隊とそっくりです。
持ち場（担当）を分け、証拠（再現コード）がそろった所見だけを受け付け、終わり方（止める条件）を先に決めました。

#### 小さな例 1 — 5 つの担当

| 担当 | 範囲 | 探すもの | 壊し方 |
|---|---|---|---|
| R1 | `authgap/val/engine.py`（値の追跡。最初の凍結の後の差分が中心） | 主体・出自・形の誤り。とくに誤 clear | (a) |
| R2 | `authgap/dparse.py`（宣言の読み取り）、`authgap/entries.py` と `catalog/entries.py`（入口） | 宣言の読み違い、入口の見落とし・二重登録 | (a)(b) |
| R3 | 判定表 §7 と、`dparse.py` の `_d1`〜`_d4`・`catalog/statements.py`・`verdict.py` | 判定表と実装の食い違い。SQL の先頭語・HTTP のメソッド・破壊的かどうかの分類 | (b) |
| R4 | `authgap/effects.py`・`catalog/sinks.py`・`catalog/transfers.py`（効果） | 語彙にある sink の取りこぼし、slot の位置の誤り、受け手の型 | (a) |
| R5 | `scripts/scan_v2.py` などの集計・突き合わせ・凍結の道具と、`authgap/runner.py`・`report.py` | 黙った数え落とし、分母、同じ鍵の衝突、非決定、指紋の抜け | (c) |

表の読み方: 1 行が 1 つの担当です。
たとえば 5 行目は「R5 は、走査をまとめる道具や突き合わせの道具を受け持ち、読めなかったファイルや時間切れを黙って数え落としていないか、実行のたびに結果が変わらないか、などを探した」と読みます。
（出典: `docs/review_plan.md:36-43`（§3 の担当の表））

#### 小さな例 2 — 受け付けた所見の実物

所見として受け付ける条件は、次の 4 つです。
1 つでも欠けたら捨てます。

1. **最小の再現コード**（MCP ツールの短い Python）と、`scripts/repro_scan.py` で走らせた出力。そして、規則から決まる**期待の出力**。
2. **誤りの向き**: 誤 clear・誤警報・数え落とし のどれか。
3. **一般性の説明**: Python の意味・ライブラリの仕様・書いた規則から導けること。v2・v3 は影響の件数の見積もりにだけ使う。
4. D1・D2 の判定、または評価の道具に影響すること（D3・D4 だけなら記録止まり。後で D62 により変わった）。

実物の所見を 1 つ見ます。
担当 R3 の第 1 回の 2 件目（R3-r1-2）の再現コードです（記録から、ツール 1 つ分を抜き出しました）。

```python
import sqlite3

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("t")


@mcp.tool(annotations={"readOnlyHint": True})
async def d1_line_comment_delete(p: str) -> str:
    sqlite3.connect("x.db").execute("-- remove stale rows\nDELETE FROM t WHERE a = ?", (p,))
    return "x"
```

行ごとに見ます。

- 1 行目: Python に最初から入っている SQLite（小さなデータベース）の部品を読み込みます。
- 3 行目: MCP のサーバを作る部品 `FastMCP` を読み込みます（[第 3 章](ch03.md)）。
- 5 行目: サーバを 1 つ作り、`mcp` という名前を付けます。
- 8 行目: 次の関数をツールとして登録し、宣言 `readOnlyHint: True`（D1「読むだけ」）を付けます。
- 9 行目: ツールの本体の関数です。モデルが選ぶ引数 `p` を受け取ります。
- 10 行目: データベースに SQL を送ります。SQL の文字列は「`-- remove stale rows`」という**説明のコメント**の行で始まり、改行（`\n`）の後に `DELETE FROM t WHERE a = ?`（表 `t` から行を消す）が続きます。
- 11 行目: 文字列を返して終わります。

このツールは「読むだけ」と宣言しながら、データベースの行を消しています。
だから、規則から決まる期待の出力は「D1 の**矛**」です。

ところが、解析器の出力（再現の出力の一部）は次のとおりでした。

```
E DB  psycopg.Cursor.execute  proxy  L10  server.py  resolved  sql_head=-- sub_kind=DB_WRITE db_rule=db
R {"kind": "DB", "notes": ["select_manifest_only(assumed_trig)", "contradiction_unknown:D1:db_unknown_statement"], ...}
```

- 1 行目（`E`）は効果の行です。`sql_head=--` に注目します。解析器は、SQL の**先頭の語**を `--`（コメントの記号）と読んでいました。
- 2 行目（`R`）は判定の行です。`contradiction_unknown:D1:db_unknown_statement` は「D1 は**不**。理由は『分類に無い先頭語』」という意味です（[第 18 章](ch18.md)）。

つまり、本当は矛なのに不に落ちていました。
所見の記録には、向き `false_clean`（誤 clear）、影響 `D1+D2`、重大度 `medium`、関係するファイルと行（`authgap/effects.py:359` など）も書かれています。
4 つの条件がそろっているので、受け付けられました。

（出典: `docs/review_plan.md:51-57`（§4.1 の受け付ける条件）、`evidence/review/explore_r1_r2.json` の R3-r1-2（再現コード・出力・向き））

#### 一歩ずつの説明 — 実際に何回走ったか

止める条件は「同じ担当を、2 回続けて新しい所見が出なくなるまで繰り返す。上限 4 回」でした。
実際の経過は次のとおりです。

| 回 | 走った担当 | 候補 | 重複を除いた新規 | 累計 |
|---|---|---|---|---|
| 1 | R1〜R5 | 54 | 51 | 51 |
| 2 | R1〜R5 | 35 | 31 | 82 |
| 3・4（最初にまとめて走らせた試み） | （全担当） | 0（利用枠の上限で 10 本すべて失敗） | — | 82 |
| 3（やり直し） | R1〜R5 | 27 | 25 | 107 |
| 4 | R1〜R5（R2 は、ほかの担当が利用枠で走らなかった 1 度目の結果を使った） | 29 | 27 | 134 |
| 5 | R1・R2 だけ（他は利用枠で走らず） | 9 | 9（重複除去は走っていない） | 143 |
| 6 | なし（全担当が利用枠で走らず） | — | — | 143 |
| D3・D4 の回（範囲の変更による追加） | R3d・R1d | 10 | 8 | **151** |

表の読み方: 1 行が 1 回の探索です。
たとえば 4 行目は「第 3 回をやり直したとき、5 つの担当が合わせて 27 件の候補を出し、すでに出た所見と重なるものを除くと新しい所見は 25 件で、ここまでの合計は 107 件になった」と読みます。
「利用枠」は、AI のエージェントを使える量の上限のことです。

この表から、4 つのことが読み取れます。

**1. 所見は減らなかった。**
止める条件の「2 回続けて新しい所見が 0」に近づくどころか、第 3 回 25 件、第 4 回 27 件と、むしろ増えました。
止める条件を満たしたからではなく、**上限に達したから**止めたのです。

**2. 上限を超えて第 5 回を走らせてしまった。**
上限は 4 回でしたが、第 3 回からの続きを走らせるスクリプトに、本記録者が上限を「6 回」と書いてしまいました。
そのため第 5 回が走り、9 件の所見が出ました。
この 9 件は「**事前登録の手続きの外**」の所見として印（†）を付け、検証はしたうえで、表では分けて示しています。
捨ててもいませんし、手続きの中の所見と混ぜてもいません。

**3. 走らなかった回は「出なかった」と数えない。**
第 3・4 回を最初にまとめて走らせた試みは、利用枠の上限で 10 本（5 つの担当 × 2 回）すべてが失敗しました。
このとき、エージェントを動かす仕組み（ワークフロー）の止める条件「2 回続けて新規 0」が、**見かけの上では**満たされてしまいました。
けれども記録は「候補 0 は『出なかった』ではなく『走らなかった』」と書き、計画の止める条件は満たしていないとして、第 3 回からやり直しました。

**4. D3・D4 を探す回を 1 回足した。**
途中で D62 が決まり、D3・D4 も主指標になりました（36.12 節）。
それまでの探索は「D3・D4 だけに効く誤りは直さない」前提で、D3・D4 をほとんど探していませんでした。
そこで、D3・D4 の判定だけを対象にした担当 R3d・R1d を立てて 1 回探し、新しい所見 8 件（D3 7 件・D4 1 件）を得ました。
これは「上限 4 回」とは別の、**範囲の変更に伴う追加の 1 回**として記録されています。

（出典: `docs/review_plan.md:105-118`（§7.1）、`:138-153`（§7.3）、`:166-182`（§7.5・§7.6））

#### なぜそうするのか

- **受け付ける条件を厳しくする理由**: 「なんとなく怪しい」という指摘を受け付けると、確かめる手間が増えるうえ、本当の誤りと区別できません。再現コードと期待の出力があれば、誰でも同じ手順で確かめられます。向きが書いてあれば、直したときに数字がどちらに動くかが分かります（[第 21 章](ch21.md)）。一般性の説明があれば、v2・v3 の特定のツールに合わせた直し（D61 で禁じたもの）を避けられます。
- **上限を決める理由**: [第 24 章](ch24.md)で見たとおり、上限が無いと終わりません。そのうえ、「よい結果が出た回で止める」ことができてしまいます。
- **「出尽くしていない」と書く理由**: 上限で止めた以上、まだ見つかっていない誤りが残っていると考えるのが正直です。記録は「この添削で見つからなかった誤りが残っていると考えるべきで、『添削で直すものは直した』とは書かない」と明記しています。

（出典: `docs/review_plan.md:149-153`（探索を止めること））

#### よくある誤解・つまずき

- **誤解: 「所見が減らなかったのは、解析器がとても悪いから」**
  そうとは限りません。回を重ねるたびに、まだ誰も見ていない書き方を探しに行くので、新しい所見が出続けることはよくあります。分かるのは「まだ出尽くしていない」ということで、解析器の良し悪しの量ではありません。
- **誤解: 「上限を超えた第 5 回の 9 件は、手続き違反なので捨てた」**
  捨てていません。検証もしました。ただし、手続きの外の所見として印を付け、分けて示しています。捨てれば、見つかった誤りを無かったことにすることになります。
- **誤解: 「利用枠で走らなかった回は、所見 0 として数えてよい」**
  数えてはいけません。「調べていない」と「調べて無かった」は別のことです。
- **つまずき: 151 件は「解析器の誤りの総数」だと思う**
  151 件は、この手続きで見つけた数です。母集団の中でその形がどれだけ起きるかの推定ではありません（O42 の読み方の注意）。

#### 手作業ではどう使うか

最終評価の判定でも、「調べていない」と「調べて無かった」を分けることが大事です。

- 原ソースを 20〜30 分調べても、到達するか・反するかを決められなければ、正にも誤にもせず「**不明**」にし、理由を書きます（判定の手引きの下書き 19 節）。これは「走らなかった回を 0 と数えない」のと同じ考え方です。
- 自分の作業に上限を設けたら、上限で止めたことを記録します。たとえば「この件は 30 分で打ち切った」と `note` に書いておけば、後で読み手が割り引いて読めます。
- 判定の途中で手引きの外のことに気づいたら（担当の範囲の外の所見のように）、捨てずに、手引きの外の気づきとして別に書き留めます。

（出典: `docs/drafts/final_judging_guide_draft.md:547-559`（19 「不明」にするとき））

#### この節のまとめ

5 つの担当（R1〜R5）で並行して探し、再現コード・期待の出力・向き・一般性がそろった所見だけを受け付けた。止める条件は「2 回続けて新規 0、上限 4 回」。
所見は減らず（第 3 回 25、第 4 回 27）、上限で止めた。誤って第 5 回まで走らせた 9 件は手続きの外として分け、利用枠で走らなかった回は「出なかった」と数えなかった。D62 の後に D3・D4 を探す回を 1 回足し、所見は 151 件になった。**所見は出尽くしていない。**

### 36.4 3 つの観点で確かめる — 「本当に誤りか」を崩しに行く

#### 一言で言うと

受け付けた所見も、そのまま「誤り」とはしません。
1 件ずつ、**実行・設計・一般性**の 3 つの観点で「本当は誤りではないのでは」と崩しに行き、**2 つ以上の観点を生き延びたものだけ**を残しました。
結果は、所見 151 件のうち**生き残り 150 件、落ちたもの 1 件**でした。

#### たとえ話 — 家電の不具合の報告

家電のメーカーに「ボタンを押すと止まる」という報告が来たとします。
メーカーは、次の 3 つを確かめます。

1. 同じ操作をすると、本当に止まるか（再現するか）。
2. それは説明書に書いた仕様の動きではないか（たとえば「安全のために止まる」設計ではないか）。
3. 直すと、別の使い方が壊れないか。

1 で再現しなければ、報告の勘違いかもしれません。
2 で仕様どおりなら、不具合ではありません。
3 で別の使い方が壊れるなら、その直し方は採れません。

添削の 3 つの観点は、この 3 つの確かめ方と同じです。

#### 小さな例 — 3 つの観点と捨てる条件

| 観点 | 問い | 捨てる条件 |
|---|---|---|
| 実行 | 再現コードを解析器にかけると、主張どおりの出力になるか | 再現しない |
| 設計 | その挙動は、決定（D 番号）・判定表 §7・仕様書で**意図したもの**ではないか | 意図どおり（既知の設計判断） |
| 一般性 | 「直すと別の正しい場合が壊れる」反例を作れるか | 反例が作れ、直し方が一般に正しくない |

表の読み方: 1 行が 1 つの観点です。
たとえば 3 行目は「一般性の観点では、その所見を直したときに、今は正しく判定できている別の書き方が壊れる例（反例）を作れるかを試す。作れて、しかも直し方が一般に正しくないなら、その所見は捨てる」と読みます。
3 行目の考え方は、[第 24 章](ch24.md) 24.4 節で見た D61 の G1・G2 の取り消しと同じです。
（出典: `docs/review_plan.md:59-65`（§4.2））

#### 一歩ずつの説明 — 確かめた結果

| まとまり | 実行の観点 | 生き残り / 落ちた |
|---|---|---|
| 第 1〜3 回の 111 件 | 111/111 が再現 | 110 / 1 |
| 第 4〜5 回の新規 32 件 | 32/32 が再現 | （合わせて 143 件で 142 / 1） |
| D3・D4 の回の 8 件 | 8/8 が再現 | （合わせて 151 件で 150 / 1） |

表の読み方: 1 行が 1 つのまとまりです。
たとえば 1 行目は「第 1〜3 回で受け付けた 111 件は、再現コードを走らせ直すと 111 件すべてが主張どおりの出力になった。3 つの観点で確かめた結果、110 件が生き残り、1 件が落ちた」と読みます。
（111 件は、第 1〜3 回の 107 件に、第 4 回の 1 度目（ほかの担当が利用枠で走らず、R2 だけが走った）で出た 4 件を足した数です。この 4 件は、36.3 節の表の第 4 回の 27 件に含まれます。）

落ちた 1 件は **R2-r1-10** です。
これは「ツールの引数 `ctx`（クライアントへの連絡口。[第 3 章](ch03.md)）を、モデルが選ぶ値（MODEL）ではなく、運用者の値（OP）として扱うべきだ」という所見でした。
設計と一般性の両方の観点で反証されました。
`ctx` を MODEL として種を置くのは、わざと安全側に倒した**保守的な扱い**で、誤りではない、という判断です。
O42 は、この所見について「検証で落ちた唯一の所見で、限界ではない」と書いています。

生き残った 150 件の重大度（探索役・設計の検証役・一般性の検証役の 3 つの意見の真ん中の値）は、**高 15・中 58・低 77** でした。

（出典: `docs/review_plan.md:128-136`（§7.2）、`:155-164`（§7.4）、`:176-192`（§7.6・§7.7）、`docs/open_questions.md:1148`（R2-r1-10））

#### 一歩ずつの説明 — 正直に書いたこと 3 つ

記録は、この確かめ方について、正直に 3 つのことを書いています。

**1. 実質の基準が変わった。**
規則は「2 つ以上の観点を生き延びたものだけ残す」でした。
ところが、実行の観点では所見が**すべて**再現しました。
すると、捨てられるのは「設計と一般性の**両方**で反証されたもの」だけになります。
設計の観点だけで反証された所見が 12 件、一般性の観点だけで反証された所見が 2 件ありましたが（第 1〜3 回の 111 件の中）、これらは表に ✗ の印を残して生き残りに数えました。
記録は「基準は事前登録どおりで動かさない」とし、採否のときにこの ✗ の列を見ることにしました。

**2. 検証役の AI のモデルが途中で変わった。**
検証役は、重大度が高・中の所見を上位のモデル（記録では Fable の max）、低の所見を Opus が受け持ちました。
D3・D4 の回の残り 4 件は、Fable の利用枠が切れたため、学生の指示で Opus（effort max）で検証し、判定に `_model: opus` の印を付けました。

**3. 検証役への指示に、古い文言が残っていた。**
検証役への指示には「D3・D4 だけに効くなら重大度を low にし記録のみ」という、D62 より前の文言がありました。
D3・D4 の回の 4 件では、これを「D1〜D4 は 4 つとも主指標で、D3・D4 だけに効くことは重大度を下げる理由にならない」に直しました。
けれども、第 1〜5 回の 143 件の検証は、古い文言のままで行われています。
記録は、143 件の探索役の自己申告には D3・D4 だけの所見は無いとしたうえで、検証役がこの文言で重大度を下げた所見が無いかを採否の表を作るときに確かめる、と書きました。

（出典: `docs/review_plan.md:132-136`（注意（正直に書く））、`:184-191`（§7.7））

#### なぜそうするのか

- **再現しただけでは誤りと言えない**: 解析器がその出力を出すのは、設計で意図した動きかもしれません。たとえば R2-r1-10 の `ctx` は、出力は再現しましたが、意図した保守的な扱いでした。
- **一般性を確かめる理由**: 素朴な直し方で、今正しく動いている別の書き方が壊れることがあります。D61 の G1・G2 がそうでした（[第 24 章](ch24.md)）。直す前に反例を探しておけば、直し方の条件（「避ける条件」）が分かります。実際、検証役が作った反例は、後で反例テストとして直しのテストに入りました（36.9 節）。
- **複数の観点にする理由**: 1 つの観点だけだと、その観点の見落としがそのまま残ります。観点を分ければ、1 人の検証役の思い込みに結果が左右されにくくなります。

#### よくある誤解・つまずき

- **誤解: 「生き残った所見は、全部直すことになった」**
  なりません。生き残ったのは「誤りらしい」という確かめで、直すかどうかは次の段階で学生が決めました（36.5 節）。150 件のうち、直した単位に入ったのは一部です。
- **誤解: 「✗ の付いた所見は、落ちた所見」**
  落ちていません。片方の観点だけで反証された所見に付けた印で、生き残りに数えています。採否のときに注意して見る印です。
- **誤解: 「検証役が AI なので、結果は信用できない」**
  信用の度合いを判断できるように、どのモデルがどの所見を検証したかと、指示の文言の食い違いを記録しています。研究の遂行に AI を使ったことは、論文で開示します（O45 の 4）。

#### 手作業ではどう使うか

判定で「解析器が誤っているのでは」と思ったときも、3 つの観点で自分の考えを崩しに行くと、判断がぶれにくくなります。

1. **実行（再現）**: manifest で、本当にその出力が出ているかを確かめる（[第 19 章](ch19.md)）。思い込みで「出ているはず」と判断しない。
2. **設計（意図）**: その扱いは、判定表や手引きで意図したものではないかを確かめる。たとえば `ctx` を MODEL として扱うのは意図どおりです。意図どおりなら、解析器の誤りではありません。
3. **一般性（ほかの件に当てても困らないか）**: 自分の判断の理由を、似た別の件に当てても、矛盾した答えにならないかを考える。

ただし、判定では解析器を直さないので、3 つの観点の結果は「判定の理由」と「限界の記録」に書くだけです。

#### この節のまとめ

所見 1 件ずつに、実行（再現するか）・設計（意図した動きではないか）・一般性（直すと別の正しい場合が壊れないか）の 3 つの観点で反証を試み、2 つ以上を生き延びたものを残した。結果は 151 件中 生き残り 150・落ちた 1（R2-r1-10、`ctx` の扱い）。
実行の観点ですべて再現したので、実質は「設計と一般性の両方で崩れたものだけ捨てる」になったことや、検証役のモデルと指示の文言のずれも、正直に記録した。

### 36.5 単位にまとめて、学生が選ぶ

#### 一言で言うと

150 件を 1 件ずつ直すのは大変ですし、同じ原因の所見がたくさんあります。
そこで、所見 151 件（落ちた 1 件を含む）を、**根本原因ごとに 55 の「単位」**にまとめました。
本記録者は単位を段階 A（12）・B（11）・C（32）に分けて提案し、**学生が採否を決めました**（D64）。
直したのは段階 A の 12 単位と、段階 B のうちの 4 単位（U38・U40・U09・U23）です。
残りの 39 単位は直さず、限界として O42 に記録しました。

#### 言葉の 3 点セット

- **単位**
  - やさしい言い換え: 同じ原因から出た所見をまとめた「直す 1 まとまり」。
  - 正確な定義: 所見を根本原因（解析器や道具の、どの処理のどんな欠けか）ごとに束ねたもの。U01〜U55 の番号が付く。すべての所見が、ちょうど 1 つの単位に入る（コードで確かめた。欠け 0・重複 0）。
  - 例: U33「SQL の先頭語の読み方」には、先頭のコメント（R3-r1-2）・定数の複文（R3-r1-1）・PRAGMA の括弧形（R3-r1-3）・書式の穴（R3-r4-3）の 4 つの所見が入る。どれも「SQL を先頭の 1 語だけで分類する」という同じ原因から出ている。
- **段階**
  - やさしい言い換え: 単位を、直す急ぎ具合で 3 つに分けたもの。
  - 正確な定義: 本記録者の提案した分け方。A は「最終評価の数字を直接狂わせるもの」（評価の道具・非決定・打ち切りの痕跡・判定表との食い違い）。B は「新しいデータで出やすい書き方で、D1〜D4 の判定が系統的に変わる重いもの。直すかは学生が選ぶ」。C は「それ以外。既定では限界として記録」。
  - 例: U25（`_self_fields` の cache の非決定）は A、U01（INDIRECT 形の降下）は B、U18（ジェネレータの yield）は C。

#### たとえ話 — 雨漏りの修理

古い家で、天井に雨漏りのしみが 10 か所あったとします。
しみを 1 つずつ拭いても、また雨が降れば、しみは戻ってきます。
屋根に上がって調べると、10 か所のしみの原因は、屋根の 3 か所の割れでした。
直すべきなのは、しみ 10 か所ではなく、割れ 3 か所です。

所見は「しみ」、単位は「屋根の割れ」にあたります。
同じ原因の所見をまとめれば、直す数が減り、1 つの直しで複数の所見が同時に閉じます。

さらに、屋根の割れにも急ぎ具合があります。
寝室の真上の割れは今すぐ直す（段階 A）。
物置の上の割れは、梅雨の前に直すかを家族で相談する（段階 B）。
軒先の小さな割れは、記録しておいて次の改修のときに考える（段階 C）。
どれを直すかは、家の持ち主が決めます。
この研究では、家の持ち主は学生です。

#### 小さな例 1 — 段階ごとの単位の数

| 段階 | 中身 | 単位の数 | 学生の決定（D64） |
|---|---|---|---|
| **A** | 最終評価の数字を直接狂わせるもの（評価の道具、非決定、打ち切りの痕跡、判定表との食い違い） | 12 | 12 単位を直す（U55 は直す所見が無く記録だけ） |
| **B** | 新しいデータで出やすい書き方で、判定が系統的に変わる重いもの | 11 | 4 単位（U38・U40・U09・U23）だけ直す |
| **C** | それ以外 | 32 | 直さず、限界として記録 |

表の読み方: 1 行が 1 つの段階です。
たとえば 2 行目は「段階 B の 11 単位は、新しいデータで出やすい重い誤りだが、直すかどうかは学生が選ぶ。学生は、そのうち 4 単位だけを直すと決めた」と読みます。

整理役（単位にまとめた AI のエージェント。Opus）は、単位ごとに推奨も付けました。
推奨の内訳は「直す 17・一部直す 26・限界として記録 12」です。
重大度と推奨を掛け合わせると、次のようになります。

| 重大度 | 直す | 一部直す | 限界として記録 |
|---|---|---|---|
| 高 | 4 | 8 | 0 |
| 中 | 10 | 18 | 0 |
| 低 | 3 | 0 | 12 |

表の読み方: たとえば 1 行目は「重大度が高い単位は 12 あり、整理役はそのうち 4 単位を『直す』、8 単位を『一部直す』と推奨した。『限界として記録』を推奨した高の単位は無い」と読みます。
推奨は整理役のもの、段階は本記録者の提案で、**採否は学生が決める**、と表の冒頭に書かれています。

（出典: `docs/review_triage.md:1-12`、`docs/review_plan.md:194-201`（§7.8））

#### 小さな例 2 — 採否の表の 1 行を読む

`docs/review_triage.md` の採否の表から、U33 の行を抜き出します。

| 段階 | 単位 | 重大度 | 推奨 | 向き | 宣言 | 一般に正しい直し方 | 解決率↑ | 規模 | 語彙の追加 | scripts だけ | 所見 | 名前 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| **A** | U33 | 中 | 一部直す | 混在 | D1 D2 D4 | 条件つきである | ○ | M |  |  | 4 | SQL の先頭語の読み方 |

欄ごとに見ます。

段階 A は、この 3 つを先に直す段階です。
はかりと記録帳が狂っていたら、どんなに丁寧に料理を見ても、最後の表は正しくなりません。

#### 小さな例 2 — U33: SQL の先頭のコメント

36.3 節で見た所見 R3-r1-2 は、U33 に入ります。
直した後のテストから、同じ種類の例を 3 つ並べます。

```python
# (1) 先頭のコメントの後に DELETE
db().execute("-- remove stale rows\nDELETE FROM t WHERE a = ?", (p,))
# (2) MySQL の「実行されるコメント」の中に DROP
db().execute("/*!50000 DROP TABLE t */ SELECT 1")
# (3) idempotentHint: True のツールで、コメントの後に INSERT
db().execute("-- c\nINSERT INTO t VALUES (1)")
```

行ごとに見ます（どれも、データベースに SQL の文字列を送る 1 行です）。

- (1): コメントの行の後に、行を消す `DELETE` があります。`readOnlyHint: True`（D1）のツールなら、規則から決まる答えは**矛**です。直す前は先頭の語を `--` と読み、**不**にしていました（36.3 節）。
- (2): `/*!50000 ... */` は MySQL では**中身が実行される**特別なコメントです。つまり、表を消す `DROP TABLE t` が実行されます。素朴に「コメントを全部剥がす」と、`SELECT 1`（読むだけ）が残り、D1 で**内**になってしまいます。これは検証役（一般性の観点）が作った反例で、`/*!` で始まるコメントは剥がさないことにしました。剥がさないので先頭の語は読めず、答えは**不**（決められない）になります。危険な文を「読むだけ」と言い切るよりは、ずっと安全です。
- (3): `INSERT` は、何度も実行すると行が増えるので「冪等とは限らない」操作です。`idempotentHint: True`（D4）のツールなら、規則から決まる答えは**不**です。直す前は、先頭の語 `--` が D4 の分類に無かったので、**何の印も無く内**になっていました。D4 の黙った誤 clear です。

直した後の規則（§9.6 の 1）は、「先頭の空白・`--` の行コメント・`/* */` のブロックコメントを剥がしてから先頭の語を取る。ただし `/*!` で始まるコメントは剥がさない。剥がした後が空なら読めない（不）」です。

（出典: `tests/test_d64_u33_sql_heads.py:91-140`（(1)・(2)・(3) のツール）、`:183-205`（期待。(2) は不）、`docs/contradiction_principles.md:357-360`（§9.6 の 1））

#### 小さな例 3 — U36: URL の宛先の取り出し方

D3（`openWorldHint: False`、外の世界と通信しない）は、通信の宛先が手元（localhost や社内の網）か外部かで決まります（第 10・17 章）。
宛先を URL の文字列から取り出すとき、直す前の解析器は**手書きの分け方**をしていました。
直した後のテストから、例を 3 つ並べます。

| URL | 本当の宛先 | 直す前 | 直した後 |
|---|---|---|---|
| `http://user:pass@localhost:8080/x` | localhost（手元） | 外部と読み **矛**（誤警報） | **内** |
| `http://localhost:pw@evil.example/x` | evil.example（外部） | localhost と読み **内**（誤 clear） | **矛** |
| `http://evil.example\@localhost/x` | クライアントのライブラリによって読みが割れる | — | **不** |

表の読み方: 1 行が 1 つの URL です。
たとえば 2 行目は「`@` の前の `localhost:pw` は、利用者の名前とパスワード（userinfo）で、宛先ではない。本当の宛先は `@` の後の evil.example（外部）。直す前の解析器は先頭の localhost を宛先と読み、手元宛てだから内としていた（危険を見落とす誤 clear）。直した後は外部宛てと読み、矛にする」と読みます。

直した後の規則（§9.6 の 7）は、「宛先のホストは、URL の正式な文法（**RFC 3986**。インターネットの技術の決まりを書いた文書の 1 つで、URL の書き方を定める）の『権威部』（authority。`//` の後から、次の `/` `?` `#` までの部分）から取り出す。利用者の名前・ポート・角括弧を正しく外す。`\` があるものと、分解に失敗したものは読めない（不）」です。
3 行目が不になるのは、`\` の扱いがクライアントのライブラリによって違い、どちらの宛先になるかを解析器が決められないからです。

（出典: `tests/test_d64_u36_url_authority.py:111`・`:129`・`:134`（例の 3 つの URL と期待）、`docs/contradiction_principles.md:382-385`（§9.6 の 7））

#### 小さな例 5 — U25: 番地の使い回しによる非決定

U25 は、段階 A でただ 1 つ、重大度が**高**の単位でした。
解析器は、クラスの `__init__` の中で `self.conn = ...` のように作った欄の中身を、一度計算したら覚えておく仕組み（cache）を持っていました。
覚えるときの鍵に、木の索引のオブジェクトの `id`（Python がオブジェクトに付ける番号。中身はメモリの番地）を使っていました。

ところが、Python は、使い終わって片付けたオブジェクトの番地を、次のオブジェクトに**使い回す**ことがあります。
1 つのプロセスで木 A、木 B と続けて解析すると、木 B の索引が、片付けられた木 A の索引と同じ番号になることがあります。
すると、木 B の `Store` クラスの欄を引いたつもりで、木 A の `Store` クラスの欄の中身が返ってきます。

所見の再現コードでは、木 A の `Store` は `self.conn = httpx.Client(...)`（通信）、木 B の `Store` は `self.conn = sqlite3.connect(...)`（データベース）でした。
木 B を単独で解析すれば D1 の矛が出るのに、木 A の後に解析すると、木 A の中身を使い回して矛が消えることがありました。
しかも、同じ木を 3 回続けて解析して結果が同じかを見る決定論の検査（`--determinism`）は、同じ木を繰り返すだけなので、この非決定を見つけられませんでした。

直した後は、cache を索引ごとに持つようにしました（ファイルの場所を鍵にする案は、同じ場所の木を書き換えて解析し直すと古い中身が残るので採りませんでした）。

（出典: `git show 7f8356e` のコミットのメッセージ（U25 の説明）、`evidence/review/explore_r1_r2.json` の R5-r1-1（再現コード））

#### 一歩ずつの説明 — §9.6 の規則

判定表の抜けは、実装より先に `docs/contradiction_principles.md` の §9.6 として書き、コミットしました。
7 つの規則を、やさしく言い換えて並べます。

1. SQL の先頭の空白・コメントを剥がしてから先頭の語を取る。ただし `/*!` で始まるコメントは剥がさない（例 2）。
2. 定数の複文（`CREATE ...; DELETE ...` のように 1 つの文字列に文を 2 つ以上並べたもの）は、文ごとに分類して、いちばん厳しい結果（矛 > 不 > 内）を採る。分けられない形（SQLite のトリガの本体、PostgreSQL の `$tag$...$tag$` の引用など）は矛にせず不にする。
3. `PRAGMA 名前(値)` の括弧の形は、`PRAGMA 名前 = 値`（設定の変更）と同じに扱う。
4. D4 で、先頭の語が分類に無いもの（`NOTIFY`・`CALL`・`COPY` など）は不にする（今までは内だった）。
5. 確度が resolved の MODEL の SQL でも、先頭の語が変更の文なら、理由の名前を `db_modify` にする（判定は矛のまま。感度分析が、定数の DELETE だけで矛と決まる形まで不に数えていたのを正す）。
6. 先頭の語に書式の穴（`%` や `{`）があれば、先頭の語を決めない（読めない、不）。
7. URL の宛先は RFC 3986 の権威部の文法で取り出す（例 3）。

規則は「原理の選択（§6）は変えない。表の導出の漏れを直す」と書いています。
つまり、[第 17 章](ch17.md)で見た「宣言に反するか」の原理はそのままで、原理から判定表を作るときに当て忘れていた形を補った、という位置づけです。

（出典: `docs/contradiction_principles.md:352-385`（§9.6））

#### なぜそうするのか

- **道具（scripts/）の直しを先に入れた理由**: D64 の手順は「段階 A の `scripts/` だけの修正（U50・U51・U52・U53・U54・U32）を先に入れる。run21 の突き合わせにこの道具を使うため」と書いています。解析器を直した後に結果を突き合わせる道具が狂っていたら、直しの良し悪しを判断できないからです。
- **規則を実装より先に書いた理由**: [第 23 章](ch23.md)の手順どおりです。規則を先に書けば、「実装がこう動いたから、規則をこう書いた」という後付けを防げます。
- **U49 は「印を足すだけ」にした理由**: 打ち切りや読めなかったファイルの扱いそのものを変えると、判定が変わります。U49 の目的は「黙って落とさない」ことなので、判定・効果の行は変えず、印と記録だけを足しました。

（出典: `docs/decisions.md:3595-3600`（D64 の手順 1〜3））

#### よくある誤解・つまずき

- **誤解: 「`scripts/` の直しは、凍結と関係ない」**
  凍結の指紋（`authgap/` の sha256）には関係しません。けれども、最終評価の**数字**には直接効きます。候補表の列がずれていれば（U51）、学生の判定そのものが狂います。だから段階 A に入れました。
- **誤解: 「U32 で、同じ効果の行を 1 本に畳んだ」**
  畳んでいません。解析器は変えず、道具の側で「一意の件数」（`n_effects_unique`）を併記するようにしただけです。run20 では、効果の行 8,337 本のうち 3,876 本が、中身がまったく同じ行の重複で、一意の件数は 4,461 でした。
- **つまずき: 「U36 は誤警報の直しなので、敵対的レビューは要らない」**
  要ります。U36 は、宛先を読めるようにする（解決率を上げる）変更でもあるので、新しい誤 clear を作りえます。実際に、レビューで IPv6 の一部の書き方を手元宛てと読む誤 clear が見つかりました（36.8 節）。

#### 手作業ではどう使うか

- **候補表（`contradictions.json`）の位置**: U51 の直しで、候補表の行の位置（`relpath` と `lineno`）は、組の中の対応する行から取るようになりました。それでも判定では、原ソースの該当の行を必ず開き、manifest の効果の行と見比べます（[第 19 章](ch19.md)）。
- **SQL の判定**: 先頭にコメントがある SQL、複文、`PRAGMA` の括弧の形に出会ったら、§9.6 の規則で読まれていることを思い出します。`/*!` のコメント、`$$` の引用、`;` の無い T-SQL のバッチ（`SET NOCOUNT ON` の後の改行で別の文が続く形。O42 の N11）などは、解析器が不にするか、読み違えている可能性があります。
- **`summary.json` の表紙**: 段階 5 の後に、`implementation_sha256_combined`・`authgap_dirty`・`python` を確かめます（手順書 9.3）。これは U54 の直しで書かれるようになった欄です。

#### この節のまとめ

段階 A では、評価の道具（U50〜U54・U32）、非決定（U25）、打ち切りの痕跡（U49）、判定表との食い違い（U33・U34・U36）を直した。道具の直しを先に入れ、判定表の抜けは実装より先に §9.6 として書いた（原理は変えない）。
例: SQL の先頭のコメントで DELETE の矛が不に落ちていた（U33）、URL の `@` の前を宛先と読んでいた（U36）、番地の使い回しで別の木のクラスの中身を使い回していた（U25）。

### 36.7 何を直したか (2) — 段階 B: 新しいデータで出やすい 4 つの書き方

#### 一言で言うと

段階 B では、新しいデータで特に出そうな 4 つの単位を直しました。
**U38**（MCP の SDK 2.x の宣言の書き方）、**U40**（呼び出しの形の登録）、**U09**（モジュールやクラスに置いた値）、**U23**（入口の引数の型。pydantic・`Path`・lifespan）です。
4 つとも、直す前は**誤 clear**（矛が内・不に落ちる、ツールや効果が丸ごと消える）の向きでした。
4 つとも、解決率を上げる変更なので、敵対的レビューを通しました（36.8 節）。

#### たとえ話 — 新しい書式の申込書

役所の窓口が、申込書の読み方の手引きを持っているとします。
ところが、新しい年度から、申込書の書式が少し変わりました。
欄の名前が「ふりがな」から「フリガナ」に変わった、別紙で申し込める、住所を別のページに書く、などです。
手引きが古いままだと、新しい書式の申込書は「読めない」か「何も書いていない」と扱われ、受付から漏れます。

段階 B の 4 つの単位は、この「新しい書式」への対応です。
とくに U38 の SDK 2.x は、文字どおり新しい版の書き方です。
最終評価のデータは、v2・v3 より後に作られたサーバも含みうるので、新しい書き方が増えている見込みがありました。

#### 小さな例 1 — U38: snake_case の宣言

[第 16 章](ch16.md)で見たとおり、宣言のキーは本来 `readOnlyHint` のような camelCase（単語の区切りを大文字で表す書き方）です。
MCP の Python SDK の 2.x では、`read_only_hint` のような snake_case（単語の区切りを `_` で表す書き方）でも書けるようになりました。

所見 R2-r1-1 の再現コード（一部）です。

```python
# uv.lock（依存の版を固定する記録）に mcp 2.1.1
from mcp.types import ToolAnnotations

@server.tool(annotations=ToolAnnotations(read_only_hint=True))
def snake_ro(path: str, text: str) -> str:
    with open(path, "w") as f:
        f.write(text)
    return "ok"
```

行ごとに見ます。

- 1 行目（コメント）: この木の依存の記録（`uv.lock`）では、mcp の版が 2.1.1 に固定されています。
- 2 行目: 宣言を作る部品 `ToolAnnotations` を読み込みます。
- 4 行目: ツールを登録し、宣言を snake_case の `read_only_hint=True`（読むだけ）で付けます。
- 5 行目: ツールの本体です。引数 `path` と `text` を受け取ります。
- 6〜7 行目: `path` のファイルを書き込み用（`"w"`）で開き、`text` を書き込みます。
- 8 行目: 終わります。

mcp 2.x では、この宣言はクライアントに `readOnlyHint: true` として届きます。
だから、規則から決まる答えは D1 の**矛**です。
ところが直す前の解析器は、版を見ずに snake_case を**いつも**「届かない書き方」（`D_malformed`）として扱い、宣言が無いのと同じ（⊥）にして、D1 を判定していませんでした。

直した後の規則は「**mcp の版で条件づける**」です。

| 木の mcp の版 | snake_case の扱い |
|---|---|
| 2.0 以上と決まる | 宣言として読む（camelCase に直す） |
| 2.0 未満と決まる | 今までどおり `D_malformed`（届かない） |
| 決まらない | `D_unknown`（どちらにも倒さない） |

表の読み方: たとえば 3 行目は「依存の記録から mcp の版が決められないときは、届くとも届かないとも決めず、`D_unknown` という別の印を付ける」と読みます。
版は、木全体で 1 つではなく、ツールのファイルにいちばん近い依存の記録（サブツリー）ごとに決めます。1 つの repo に、依存の記録の違う複数のパッケージが入っている形（monorepo。36.9 節）があるからです。

この直しで、開発用の v2 で snake_case の `D_malformed` を持つユニットは、run20 の 130 から run24 で **0** になりました（宣言 124・`D_unknown` 6 に移った。130 のうち 108 は canvas-mcp という 1 つの木）。
run23 で増えた矛 2 件のうち 1 件は、canvas-mcp の D1 の矛（mcp 2.1.1 の lock の木の `read_only_hint=True` が宣言になった）でした。

（出典: `evidence/review/explore_r1_r2.json` の R2-r1-1（再現コード）、`tests/test_d64_u38_mcp_v2.py:1-12`（版の規則）、`docs/decisions.md:3642-3646`（U38 で採った規則）、`:3682-3684`（run23 の増えた矛）、`:3710-3713`（`D_malformed` 130 → 0））

#### 小さな例 2 — U40: 呼び出しの形の登録

ツールの登録は、ふつうはデコレータ（`@mcp.tool(...)`）で書きます（第 3・12 章）。
けれども Python では、デコレータは「関数を受け取って登録する関数の呼び出し」の書き方を短くしたものにすぎません。
`@d(...)` を付けた `def f` は、`f = d(...)(f)` と書いたのと同じです（PEP 318。Python の機能の提案書の 1 つ）。
SDK の `tool` の中身も、受け取った関数を `add_tool` に渡しているだけです。

だから、次の 2 つの書き方も、デコレータと同じ登録です。

```python
def via_add_tool(path: str) -> str:
    shutil.rmtree(path)
    return "ok"


def via_direct_call_named(path: str, text: str) -> str:
    with open(path, "w") as f:
        f.write(text)
    return "ok"


mcp.add_tool(via_add_tool, annotations=ToolAnnotations(readOnlyHint=True))
mcp.tool(name="renamed", annotations=ToolAnnotations(readOnlyHint=True))(via_direct_call_named)
```

行ごとに見ます（直した後のテストの再現の木から抜き出しました）。

- 1〜3 行目: ふつうの関数 `via_add_tool` を定義します。デコレータは付いていません。本体では `shutil.rmtree(path)` でフォルダを丸ごと消します。
- 6〜9 行目: もう 1 つのふつうの関数 `via_direct_call_named` を定義します。本体ではファイルに書き込みます。
- 12 行目: `mcp.add_tool` に関数 `via_add_tool` を直接渡し、「読むだけ」の宣言を付けて登録しています（`add_tool` の形）。
- 13 行目: `mcp.tool(...)` を呼んで返ってきた関数に、`via_direct_call_named` を渡しています（呼び出しの形）。ツールの名前は `renamed`、宣言は「読むだけ」です。デコレータを付けたのと同じ登録です。

どちらのツールも「読むだけ」と宣言しながら、消したり書き込んだりしているので、規則から決まる答えは D1 の矛です。

直す前の解析器は、どちらもツールの入口として見つけられませんでした。
入口が見つからなければ、そのツールは丸ごと解析の対象から消えます（**数え落とし**。宣言があれば、矛が出ないので**誤 clear**）。

直した後は、`fn`（渡した関数）を、登録の文があるスコープで Python の意味どおりに厳密に解き、解けたものだけを入口にします。
束縛が 2 つ以上ある、呼び出し式、lambda、`partial`、ループの変数などで解けないものは採りません（誤警報を作らないため）。
`add_tool` は、凍結した入口の語彙（`ENTRY_RULES`）に名前を足すことになるので、逸脱 #25 に含めて記録しました。

run20 から run23 で増えたユニット 58 は、**すべて** U40 の呼び出しの形の登録でした（登録の文を抜き出して確かめた）。

（出典: `tests/test_d64_u40_call_registration.py:1-20`（PEP 318 と SDK の `tool` の説明、直すべき形）、`:104-145`（再現の木。`via_add_tool` と `via_direct_call`）、`docs/decisions.md:3647-3652`（U40 で採った規則）、`:3682`（増えたユニット 58））

#### 小さな例 3 — U09: モジュールやクラスに置いた値

設定やデータベースの接続を、別のファイル（モジュール）にまとめて置くのは、よくある書き方です。
次は、説明のために短くした例です（U09 の所見とテストの形をまねたもの）。

```python
# db.py
import sqlite3
conn = sqlite3.connect("app.db")

# server.py
import db

@mcp.tool(annotations={"destructiveHint": False})
def reindex() -> str:
    db.conn.execute("DELETE FROM excerpts")
    return "ok"
```

行ごとに見ます。

- 2〜3 行目（`db.py`）: モジュールの一番外側で、データベースへの接続 `conn` を作ります。
- 6 行目（`server.py`）: `db` モジュールを丸ごと読み込みます。
- 8 行目: ツールを登録し、「破壊的な操作はしない」（D2、`destructiveHint: False`）と宣言します。
- 10 行目: `db.conn`（`db` モジュールの `conn`）に、表の行を消す SQL を送ります。

直す前の解析器は、`from db import conn` と書いた形なら `conn` を読めましたが、`db.conn` のように**モジュールを丸ごと読み込んで属性で読む**形は読めませんでした（opaque）。
受け手が `sqlite3` の接続だと分からないので、データベースの効果の行が丸ごと消えていました（誤 clear）。
同じように、`pkg/__init__.py` での再公開、`A, B = ...` のタプル代入、関数の中の `global` で後から入れた接続、`class Settings: ROOT = ...` のクラス属性も読めませんでした。

直した後は、これらを `from ... import` の形と同じ候補と検査で読みます。
クラス属性は、36.5 節の規則 B（型と主体だけを付け、確度は opaque）で読みます。

run23 で増えた矛 2 件のもう 1 件は、write-like-me という木の D2 の矛でした。
`destructiveHint=False` のツールの再索引の処理にある `DELETE FROM excerpts` に、U09 で受け手の型が付いたものです。
上の例は、この形をまねて短くしたものです（実物のコードではありません）。

（出典: `docs/review_triage.md:322-330`（U09 の記述）、`tests/test_d64_u09_module_values.py:1-25`（読む形の一覧）、`docs/decisions.md:3653-3655`（U09 で採った規則）、`:3683-3684`（write-like-me の増えた矛））

#### 小さな例 4 — U23: 入口の引数の型（pydantic・`Path`・lifespan）

ツールの引数に型の注釈（`path: Path` のような、引数の型の書き添え）が付いていれば、その型から「この引数で何ができるか」が分かります。
直す前の解析器は、仕様書の「その他 → Atom」（中身の分からない 1 つの値として扱う）に従って、注釈の型を使っていませんでした。
学生は、3 つの型をすべて直すと決めました。

**(1) `Path` の注釈。**
直した後のテストの例です。

```python
from pathlib import Path

@mcp.tool(annotations={"readOnlyHint": True})
def write_p(path: Path, text: str) -> str:
    path.write_text(text)
    return "ok"

@mcp.tool(annotations={"readOnlyHint": True})
def write_str_control(path: str, text: str) -> str:
    Path(path).write_text(text)
    return "ok"
```

- 1 行目: ファイルの場所を扱う標準の部品 `Path` を読み込みます。
- 3〜5 行目: 「読むだけ」と宣言したツールで、引数 `path` に `Path` の注釈を付け、`path.write_text(text)` でファイルに書き込みます。
- 8〜10 行目: 対照です。引数は文字列で、本体で `Path(path)` と作ってから書き込みます。

どちらも同じファイルの書き込みで、D1 の矛が正しい答えです。
直す前は、対照（8〜10 行目）だけが矛になり、注釈の形（3〜5 行目）は `pathlib` の書き込みとして認識されず、矛になりませんでした（テストでは、直す前に落ちる側）。
**書き方を変えただけで、結果が変わっていた**のです。
直した後は、注釈の `Path` が `from pathlib import Path` か `import pathlib` に**厳密に**解けるときだけ、`Path` の形として扱います。
木の中に自分で `class Path` を定義している場合（たとえば、遠隔の保存場所の鍵を表す別物の `Path`）は、標準の `Path` として扱いません（検証役の反例 ce6_intree_path）。

**(2) pydantic のモデルの引数。**
[第 14 章](ch14.md) 14.8 節で見た **pydantic** を、1 文で思い出します。
pydantic は、型付きのデータの入れ物（モデル）を作る Python のライブラリで、MCP のツールの引数の型によく使われます。
たとえば `class SaveReq(BaseModel): path: str` と書くと、`SaveReq` の値は文字列の `path` 欄を持ちます。

直した後は、引数の型が木の中の pydantic・dataclass・NamedTuple のクラスに厳密に解け、しかも**構築時のフック**（値を検査したり書き換えたりする仕組み。`@field_validator`、`__post_init__` など）が無いときだけ、欄ごとに「主体 MODEL・確度 resolved・root は欄ごと（`req.path`）」として種を置きます。
フックがあるときは、今までどおり欄を区別しません。
フックがあれば、モデルが渡した値がそのまま欄に入るとは限らないからです（[第 14 章](ch14.md) 14.8 節の場合 2 と場合 3）。

**(3) lifespan で用意した値。**
[第 3 章](ch03.md)の lifespan（サーバの起動時に 1 回だけ走り、ツールの受付より前に準備をする関数）で、データベースの接続などを用意し、`yield` でツールに渡す書き方があります。
直した後は、サーバを作る式（`FastMCP(...)` など）と `lifespan=` に渡した関数が厳密に解けるときだけ、`yield` で渡した値に**受け手の型**を付けます。
ただし、値の主体と確度は、直す前と同じ「ctx の根の MODEL・確度 opaque」に保ちます。
記録の言葉では「共有状態へのモデルの書き込みを見落とさないため」です。共有の状態に置いた値を定数として「確か」と読むと、別のツールがモデルの値でその状態を書き換える形を見落とします（検証役の反例 ce_lifespan_rebound は、共有の状態に置いた定数を内にしないことを確かめるテスト）。

（出典: `tests/test_d64_u23_entry_seeding.py:1-30`（3 つの規則と反例）、`:735-799`（`Path` の例）、`:803-821`（反例 ce6_intree_path）、`docs/decisions.md:3656-3662`（U23 で採った規則））

#### 一歩ずつの説明 — 4 つの単位に共通すること

4 つの単位の直しには、共通する考え方があります。

1. **厳密に解けるときだけ読む。** `Path` は `pathlib` に厳密に解けるときだけ、`fn` は登録の文のスコープで厳密に解けるときだけ、lifespan はサーバを作る式が厳密に解けるときだけ、です。名前が似ているだけで読むと、別物を取り違えて誤警報を作るからです。
2. **解けないときは、今までどおり（opaque・決めない）に倒す。** 解けないものを無理に読まないことで、新しい誤 clear を作らないようにします。「分からないものは、分からないと残す」のは、CLAUDE.md の規則 4（解決できなかったものは「不明」として記録する）と同じ考え方です。
3. **manifest に印を残す。** U38 では、manifest に `mcp_version`（版の類と根拠）と `unresolved_handler`（解けなかった登録の件数と位置）を足しました。判定は変えず、「なぜそう読んだか」を後から確かめられるようにしたのです。
4. **逸脱として記録する。** U40 の `add_tool`（入口の語彙の追加）、U38 の snake_case（仕様書 322 行目の「常に malformed」と食い違う）、U23（仕様書 §2.6:517 の「その他 → Atom」からの逸脱）は、どれも仕様書や凍結した語彙から離れるので、逸脱 #25 に含めて記録しました。

（出典: `docs/decisions.md:3605-3606`（逸脱になるもの）、`:3641-3662`（段階 B で採った規則）、`docs/preregistration.md:576`（逸脱 #25））

#### なぜそうするのか

- **この 4 つを選んだ理由**: 学生は段階 B を「新しいデータで特に出そうなもの」に絞りました（36.5 節）。SDK 2.x の書き方（U38）は新しいサーバほど増えると見込まれ、呼び出しの形の登録（U40）・設定モジュールや共有の接続（U09）・引数の型の注釈（U23）は、どれも MCP のサーバでよく見る書き方です。
- **4 つとも誤 clear の直しだった理由と、その危うさ**: 直す前は、どれも「分からない」側に倒れていて、本当の矛を見落としていました。直すと「分かる」側が増えます。これは解決率を上げる変更で、[第 24 章](ch24.md)で見たとおり、新しい誤 clear や誤警報を作りやすい種類の変更です。だから「厳密に解けるときだけ」という条件を付け、反例テストを先に置き、敵対的レビューを通しました。

#### よくある誤解・つまずき

- **誤解: 「snake_case の宣言は、いつも宣言として読むようになった」**
  いつもではありません。mcp の版が 2.0 以上と決まったときだけです。2.0 未満なら届かない書き方（`D_malformed`）、決まらなければ `D_unknown` です。判定では、manifest の `D_kind` と、原ソースの依存の記録（lock など）を見比べます（[第 16 章](ch16.md)）。
- **誤解: 「`Path` という名前の注釈なら、どれも標準の `Path`」**
  違います。`pathlib` に厳密に解けるときだけです。木の中の別物の `Path` は、標準の `Path` として扱いません。
- **誤解: 「pydantic の引数は、どれも欄ごとに読む」**
  構築時のフックがあるときは、欄を区別しません（root は引数全体、確度は opaque）。[第 14 章](ch14.md) 14.10 節の gemini の例がそうでした。
- **つまずき: U40 で増えた 58 ユニットを「解析器が見つけすぎた誤り」と思う**
  58 ユニットは、すべて呼び出しの形の登録の文を抜き出して確かめたものです。今まで数え落としていたツールが、正しく入口になったのです。

#### 手作業ではどう使うか

- **入口の確かめ**: 判定の対象のツールが `mcp.add_tool(fn, ...)` や `mcp.tool(...)(fn)` で登録されていることがあります。manifest のユニットの `registration.form` で、呼び出しの形の登録だと分かります（`entry_kind` はデコレータと同じ `decorator`）。原ソースでは、`def` の上にデコレータが無くても慌てずに、登録の文を探します。
- **見落としの判定**: `for spec in specs: server.add_tool(spec.handler)` のようなループの中の登録、木の外のサブクラスでの登録などは、解析器が採らない形として O42 に記録されています。こうした形のツールが manifest に無ければ、見落としの原因の手がかりになります。
- **宣言の確かめ**: snake_case の宣言を見たら、mcp の版を依存の記録（`uv.lock`・`requirements.txt`・`pyproject.toml`）で確かめます。manifest の `mcp_version` に、解析器が決めた版の類と根拠が残っています。

（出典: `docs/decisions.md:3650`（`unit.registration.form`）、`docs/open_questions.md:1168`（ループの変数の登録の限界））

#### この節のまとめ

段階 B では、U38（SDK 2.x の snake_case の宣言を版で条件づけて読む）、U40（`mcp.tool(...)(fn)` と `add_tool` の登録を入口にする）、U09（モジュールやクラスに置いた値を読む。クラス属性は規則 B）、U23（`Path`・pydantic・lifespan の型を使う）を直した。
4 つとも直す前は誤 clear の向きで、直した後は「厳密に解けるときだけ読み、解けなければ今までどおり」という条件を付けた。run23 で増えたユニット 58 はすべて U40、増えた矛 2 は U38 と U09 によるもので、手で確かめた。

### 36.8 直した所をさらに壊しに行く — 敵対的レビュー

#### 一言で言うと

直した所の多くは、「今まで分からなかったものを分かるようにする」変更（解決率を上げる変更）でした。
こうした変更は、突き合わせだけでは正しさが分からないので、**敵対的レビュー**（[第 24 章](ch24.md)）を通しました。
段階 A は 1 回、段階 B は「直す → レビュー」を **3 巡**行い、3 巡目で打ち切りました。
レビューのたびに、**直しが新しく作った誤り**が見つかりました。
所見は巡ごとに減りましたが、0 にはなっていません。

#### たとえ話 — 繕い物の点検

服の破れを繕うと、繕った糸の周りが新しくほつれることがあります。
だから、繕った後にもう一度、繕った場所の周りを引っ張って確かめます。
そこでまたほつれを見つけたら、また繕い、また確かめます。
けれども、いつまでも続けるわけにはいかないので、「3 回確かめたら終わり。終わったことと、まだほつれが残るかもしれないことを書いておく」と決めます。

段階 B の 3 巡は、この繕い物の点検と同じです。

#### 小さな例 1 — 段階 A のレビューで見つかったもの

段階 A では、SQL と URL の直し（U33・U36）に、敵対的レビューを 1 回通しました。
U33・U36 の直しは、「読めなかった SQL や URL を読めるようにする」変更で、解決率を上げる向きだったからです。
見つかったのは、次のものです。

| 見つかったもの | 例 | 向き |
|---|---|---|
| 入れ子のブロックコメント | `/* a /* b */ SELECT */ DELETE FROM t` を、直した版は `SELECT` と読んだ | 新しい誤 clear |
| MariaDB の実行されるコメント | `/*M!` で始まるコメント（`/*!` と同じく中身が実行される）を剥がした | 新しい誤 clear |
| `\r` で終わる行コメント | PostgreSQL は `\r` でも `--` の行コメントを終えるのに、直した版は次の `\n` までをコメントとして剥がした（PostgreSQL では実行される文まで剥がしうる） | 新しい誤 clear |
| 分割に失敗したときの退行 | `DELETE … 'O\'Brien';` のように複文に分けられないと、先頭の DELETE の矛まで不に落とした | 矛を不に落とす退行 |
| IPv6 の一部の書き方 | 6to4（`2002::/16`）などを、Python の `is_private` に従って手元宛てと読んだ | 誤 clear |

表の読み方: 1 行が 1 つの見つかったものです。
たとえば 1 行目は「PostgreSQL などはブロックコメントを入れ子にできるので、`/* a /* b */ SELECT */` 全体がコメントで、実行されるのは `DELETE FROM t`。ところが直した版は最初の `*/` でコメントが閉じたと読み、`SELECT` を先頭の語にして、D1 を内にしてしまった」と読みます。

どれも、**方言**（データベースの製品ごとの、SQL の書き方の違い）によって読み方が割れる形です。
そこで、「方言によって読み方が割れる形は、読めない（不）にする」という規則の改訂を、**先に**書いてコミットしました（§9.6 の改訂 1'・2'・7'）。
その次に反例テストをコミットし（この時点で 30 件が落ちた）、それから実装しました。
直しの範囲の外にあった古い穴（N9〜N11、A1、A2）は、O42 に記録しました。
このうちの N9 が、後で凍結の手違いにつながります（36.11 節）。

（出典: `docs/decisions.md:3610-3614`（段階 A の敵対的レビュー）、`docs/contradiction_principles.md:387-421`（§9.6 の改訂 1'・2'・7'）、`git log -1 545524a`（「この時点で 30 件が落ちる」）、`docs/open_questions.md:1150-1159`（差分の外の既存の穴））

#### 一歩ずつの説明 — 3 巡目で何を確かめ、何を確かめなかったか

3 巡目では、「直した 9 件の所見が、反例テストで閉じたか」**だけ**を確かめ、新しい所見は探しませんでした。
記録は、これを「添削の探索の上限と同じ考え」による打ち切りと書き、「巡ごとに所見は減っているが 0 にはなっていないので、**段階 B の新しいコードも見つけ尽くしてはいない**」と明記しています。

3 巡目の直しには、もう 1 つ注意点があります。

- U09・U38・U40 の 3 巡目の直しは、どれも**解決率を下げる側**（opaque にする・決めない・広く見る側）だけでした。新しい誤 clear を作りにくい向きです。
- ところが U23 の 3 巡目の直し（R1・R2）は、**解決率を上げる側**でした。たとえば R2 は、pydantic の `Field` の説明だけの引数と、記述子のメソッドを持たない木内の Enum の既定値を「静的」とみなす直しです。
- 解決率を上げる直しには敵対的レビューが必須（[第 24 章](ch24.md)）ですが、ここでは本記録者が差分を読んで条件を確かめただけでした。
- 記録は、これを隠さず「探索の打ち切りにより、3 巡目の差分には別の敵対的レビューを通していない（限界として記録する）」と書き、O42 の段階 B の限界の表にも「3 巡目の差分（とくに U23 の R1 / R2）には別の敵対的レビューを通していない（本記録者が読んだだけ）」という行を残しています。

#### なぜそうするのか

- **レビューを通す理由**: 解決率を上げる変更は、「分かった」と言いすぎて、本当の効果や不の印を消す向きに誤りやすいからです（[第 24 章](ch24.md) 24.1 節）。突き合わせ（`compare_scans.py`）は「前と比べて何が変わったか」は教えてくれますが、「変わった結果が正しいか」は教えてくれません。
- **巡を重ねる理由**: 直しそのものが新しい変更です。2 巡目の「直しが作ったもの 6」のとおり、直しはまた誤りを作ります。
- **打ち切る理由**: 所見が 0 になるまで続けると終わりません。上限を決めて止め、止めたことと、残りがあることを記録します（[第 24 章](ch24.md) 24.7 節）。

#### よくある誤解・つまずき

- **誤解: 「3 巡で 0 にならなかったのは、直し方が下手だったから」**
  新しいコードには新しい誤りが入りうるものです。大事なのは、見つけ尽くしていないと正直に書くことです。
- **誤解: 「レビューで見つかった古い穴（N9 など）は、そのとき全部直した」**
  直したのは、直しの範囲の中のもの（§9.6 の改訂の分）だけです。範囲の外の古い穴は、O42 に記録しました。N9 だけは、後で学生の判断で凍結の前に直すことになりました（36.11 節）。
- **つまずき: 「3 巡目の直しも全部レビュー済み」と思う**
  3 巡目は、閉じたかの確認だけです。U23 の R1・R2 は、本記録者が読んだだけで、別のレビューを通していません。

#### 手作業ではどう使うか

- **見落としの判定で疑う場所**: 段階 B の新しいコード（U09・U23・U38・U40 の読み方）は、見つけ尽くしていません。判定の途中で、モジュールの別名の属性、pydantic の引数、lifespan の値、snake_case の宣言、呼び出しの形の登録に関わる所で解析器の出力がおかしいと感じたら、限界の記録（O42）と見比べ、気づいたことを記録します。
- **自分の判定の見直し**: 判定でも、迷った件の見直しが別の迷いを生むことがあります。見直しは 1 回までにして、見直したことを `note` に書き、先へ進みます（手順書 21 節の工夫と同じ）。

#### この節のまとめ

解決率を上げる直しには敵対的レビューを通した。段階 A は 1 回で、直しが作った誤 clear 3 種・退行 1 種・IPv6 の誤 clear が見つかり、§9.6 の改訂（方言で読みが割れる形は不）を先にコミットして直した。
段階 B は 3 巡（所見 25 → 再点検で新しく 12 → 9 件を直して打ち切り）。見つけ尽くしてはいない。U23 の 3 巡目の直しは解決率を上げる側なのに別のレビューを通していないことも、限界として記録した。

### 36.9 テストを先に書く — と、期待を改めたもの

#### 一言で言うと

直すときは、いつもどおり **規則 → 反例テスト → 実装** の順にコミットしました（[第 23 章](ch23.md)）。
テストの期待（正しい答え）を実装より先に書けば、「実装の出力に合わせて答えを決めた」ことにならないからです。
それでも、先に書いた期待を後で改めたものが少しだけあります。
どれも、改めた理由をテストに書いて残しました。

#### たとえ話 — 試験の模範解答

先生が試験を作るとき、模範解答は採点の**前**に作ります。
採点の後で模範解答を作ると、「多くの生徒が書いた答え」に合わせて模範解答を変えたくなるからです。

それでも、採点の途中で「問題文に誤りがあった」と気づくことがあります。
そのときは、模範解答を黙って書き換えるのではなく、「問題文の○○に誤りがあったので、解答を△△に改めた」と掲示します。
そうすれば、生徒は「自分に不利なように変えられたのではないか」を自分で確かめられます。

#### 小さな例 1 — 先に書いたテストは、まず落ちる

テストを先に書くと、実装の前には、そのテストは**落ちる**（失敗する）はずです。
落ちることを確かめてから実装し、実装の後で通ることを確かめます。
添削のコミットのメッセージには、その様子が記録されています。

| コミット | 中身 | メッセージの言葉 |
|---|---|---|
| 545524a | §9.6 の改訂の反例テスト（実装より先） | 「この時点で 30 件が落ちる」 |
| 91554a5 | N9 の規則と反例テスト（実装より先） | 「2 件が落ちる」 |
| b87c022 | N9 の実装 | 「反例テスト（91554a5）の 2 件が通る」 |

表の読み方: たとえば 2 行目は「N9 の規則とテストを実装より先にコミットした時点では、直すべき 2 件のテストが落ちていた」と読みます。
3 行目で、実装の後にその 2 件が通ったことが分かります。

（出典: `git log -1 545524a`、`git log -1 91554a5`、`git log -1 b87c022`（コミットのメッセージ））

#### 小さな例 2 — 期待を改めた 4 種類

それでも、先に書いた期待を後で改めたものがあります（D64 の追記。改めたコミットは主に b877e03）。

| テスト | 最初の期待 | 改めた期待 | 理由 |
|---|---|---|---|
| U38 の monorepo のテスト 4 件 | 依存の記録（lock）が食い違う monorepo では、版を決めない（`D_unknown`） | ツールのファイルにいちばん近い依存の記録で版を決める（宣言として読み、D1 の矛） | 最初の期待は「木全体で 1 つの lock を適当に選ぶ」ことへの守りだった。敵対的レビューの直しで、いちばん近い依存の記録で決めるようにしたので、適当に選ぶことが無くなった |
| U23 のテスト 1 件（`test_fix_ls_rebound_unreadable_const`） | 不（理由 `db_sql_unreadable`） | 不のまま、理由が `db_sql_model_opaque` に | lifespan の値の主体と確度を、直す前と同じに保ったため |
| 既知の欠陥の印を付けたテスト 1 件（`test_known_deep_module_dict_url_is_not_op_resolved`） | 「既知の欠陥」の印つき | 印を外す | 深い所の定数を「確か」と読み続けていた既知の欠陥が、U23 の直しで直った |
| N9 の反例テストの対照 1 件 | 矛 | 不 | 規則から導くと不だった（モジュールに置いたクライアントの宛先は D17 で確度 opaque）。**実装の前に**改めた |

表の読み方: 1 行が 1 種類の改めです。
たとえば 4 行目は「N9 のテストの対照の 1 件は、書いた当初は矛と見込んだ。けれども、決定 D17 の規則から導くと不が正しかったので、実装を始める前に期待を不に改めた」と読みます。

言葉を 2 つ補います。

- **monorepo**
  - やさしい言い換え: 1 つの箱（repo）に、別々の荷物（パッケージ）がいくつも入っている形。
  - 正確な定義: 1 つの repo の中に、それぞれ別の依存の記録を持つ複数のパッケージ（サブツリー）が入っている形。
  - 例: たとえば、repo の根の依存の記録では mcp 1.x、`servers/new/` の下の別の依存の記録では mcp 2.x、という木。どちらの版で snake_case を読むかが、ファイルの場所によって変わる。
- **lock**（依存の固定の記録）
  - やさしい言い換え: 「このライブラリは、この版を使う」と正確に書いた控え。
  - 正確な定義: `uv.lock` のように、使うライブラリの版を、範囲ではなく 1 つの版に固定して書いたファイル。
  - 例: 36.7 節の U38 の再現の木の `uv.lock` には、mcp の版が 2.1.1 と書かれていた。

1 行目の改めは、**矛を足す向き**です。
最初の期待（版を決めない）なら、宣言が `D_unknown` になって矛は出ません。
改めた期待では、宣言として読むので、矛が出ます。
元の守りの考え（どこにも属さないファイルは版を決めない）は、どのサブツリーにも属さないファイル（`MONOREPO_ROOT_UNIT`）のテストで残しました。

3 行目の改めには、もう 1 つ意味があります。
`_opaque_deep`（共有の値を深くまで opaque にする処理）を深さで打ち切らない変更は、D17 のモジュール水準の経路にも効き、3 段目より深い定数が resolved のまま残っていた既存の誤 clear が、内から不に動きます。
記録は、この波及も書いています。

（出典: `docs/decisions.md:3630-3640`（実装より先に書いた期待値を改めたもの）、`git log -1 91554a5`（N9 の対照を実装の前に改めた）、`tests/test_d64_n9_url_scheme.py:90-101`（対照の期待と注記））

#### 一歩ずつの説明 — N9 の対照を改めた理由

4 行目の N9 の対照を、もう少しくわしく見ます。
対照のツールは次の形です。

```python
client = httpx.Client(base_url="https://api.example.com")

@mcp.tool(annotations={"openWorldHint": False})
def keep_relative_slash(p: str) -> str:
    client.get("/items?q=" + p)
    return "x"
```

- 1 行目: モジュールの一番外側で、宛先の基本（`base_url`）が外部の `api.example.com` のクライアントを作ります。
- 3 行目: 「外の世界と通信しない」（D3）と宣言します。
- 5 行目: `/items?...` という `/` で始まる相対の URL に送ります。宛先は `base_url` の api.example.com です。

素直に考えると、外部に送っているので D3 の矛に見えます。
けれども、決定 D17 は、モジュールの一番外側に置いた値は、どこかで書き換えられうるので、確度を opaque（確かめられない）にすると決めています。
確度が opaque なら、宛先を「確かに外部」とは言えないので、判定表の規則から導く答えは**不**です。
テストを書いた当初は矛と見込みましたが、規則から導き直して不に改め、それを**実装の前に**コミットしました。
実装の出力を見てから改めたのではない、という点が大事です。

（出典: `tests/test_d64_n9_url_scheme.py:39`・`:72-75`（対照のツール）、`:96-98`（注記と期待））

#### なぜそうするのか

- **先に書く理由**: 実装の後に期待を書くと、実装が出した答えをそのまま「正しい」と書きたくなります。先に書けば、規則から導いた答えと、実装の答えを、独立に比べられます。
- **改めたときに理由を残す理由**: 期待を改めるのは避けたいことです。それでも、規則の読み違いや、直し方の改善で、最初の期待が正しくなくなることはあります。理由を残せば、読み手が「結果に合わせて答えを変えたのではないか」を自分で確かめられます。
- **向きを書く理由**: U38 の monorepo の改めは「矛を足す向き」でした。期待を改めた結果、数字がどちらに動くかを書いておけば、読み手は「解析器に有利なように変えたのでは」という疑いを自分で確かめられます。

#### よくある誤解・つまずき

- **誤解: 「テストを先に書いたなら、期待は二度と変えてはいけない」**
  変えてよい場合があります。ただし、理由を書き、変えたことを記録に残します。黙って変えるのが問題です。
- **誤解: 「期待を改めたテストは、結果に合わせたテスト」**
  理由を読めば区別できます。N9 の対照は実装の前に改めたので、実装の結果に合わせたものではありません。U38 の monorepo は、直し方そのものが変わった（任意の選び方が無くなった）ので、守りの対象が無くなったものです。
- **つまずき: 「期待を改めたのは 4 件」と数える**
  4 種類で、U38 の monorepo のテストは 4 件あります。数を言うときは、何を数えたか（テストの件数か、改めの種類か）を添えます。

#### 手作業ではどう使うか

判定の手引きも、判定を始める前に封をします（[第 22 章](ch22.md)）。
これは「期待を先に書く」ことの判定版です。
判定の途中で、手引きの規則が事例に合わないと気づいたら、次のようにします。

1. その場で手引きを書き換えない。
2. 手引きのとおりに判定し、合わないと思った理由を `note` に書く。
3. 手引きの穴として、後でまとめて記録する（手引きの下書き 22 節）。

「改めるなら理由と一緒に残す」という添削の約束は、判定の記録にもそのまま当てはまります。

#### この節のまとめ

規則 → 反例テスト → 実装の順にコミットし、テストが実装の前に落ちることを確かめた（§9.6 の改訂で 30 件、N9 で 2 件）。
先に書いた期待を改めたものが 4 種類あり（U38 の monorepo 4 件・U23 の理由の名前・既知の欠陥の印・N9 の対照）、どれも理由をテストと記録に残した。N9 の対照は実装の前に改めた。

### 36.10 時間の問題 — run21 の数え落とし

#### 一言で言うと

直した後で母集団 v2 を取り直すと（**run21**）、ユニットが **2,231 から 1,741 に減りました**。
判定が変わったのではありません。
段階 B の追加で解析が遅くなり（87 木の合計で 729 秒 → 1,894 秒）、**木ごとの時間上限（180 秒）**で大きな 2 木が打ち切られたのです。
打ち切られたユニットの矛は見えないので、**誤 clear の向きの数え落とし**でした。
結果を変えない速度の直しで、run23 では元に戻りました。
ただし、時間は**マシンの速さで変わる**ので、最終評価では走らせたマシンと打ち切りを必ず記録します。

#### たとえ話 — 制限時間のある試験

1 科目 3 時間の試験で、受験生が問題を順に解くとします。
3 時間を過ぎたら、残りの問題は白紙のまま回収されます。
白紙の問題は 0 点ですが、それは「分からなかった」からではなく、「時間が無くて解かなかった」からです。

ここで、問題用紙の字が小さくなって読むのに時間がかかるようになると（解析が遅くなると）、同じ受験生でも、白紙の問題が増えます。
答案だけを見て「この受験生は、前より成績が落ちた」と判断するのは誤りです。
問題を解いた数が減っただけかもしれないからです。

run21 で起きたのは、まさにこれでした。
答案（manifest）だけでなく、「時間切れで解かなかった問題の数」（`budget_skipped`）を見ることで、何が起きたかが分かりました。

#### 一歩ずつの説明 — なぜ「判定の変化」ではないと言えるのか

ユニットが 490 も減ったと聞くと、「段階 B の直しで解析器が壊れたのでは」と心配になります。
記録（D64 の追記と逸脱 #25）と各 run の `summary.json` から、判定の変化ではなく時間上限の打ち切りだと言える根拠を、手順の形に並べ直すと次のようになります。

1. 消えたユニットが、どの木から消えたかを見る。→ xagent と mcparmory の 2 木に集中していた。
2. その 2 木の `elapsed_s`（所要時間）を見る。→ どちらも 180 秒をわずかに超えていた。
3. その 2 木の `budget_skipped`（時間上限で解析しなかったユニットの数）を見る。→ xagent 351、mcparmory 197。
4. run22 では、消えた 131 ユニットが、manifest の `tree_budget` の件数（mcparmory 109 + xagent 22）と**一致**し、消えた矛は 0 だった。

4 の「manifest の `tree_budget` の件数」は、段階 A の **U49** で manifest に足した印です（36.6 節）。
U49 の直しの前は、ユニットを順に解析している途中で時間上限に当たった打ち切りは、manifest の `truncations` には残っていませんでした（`summary.json` の `budget_skipped` には出ていました）。
同じ日（UTC）の 10 時台に足した印が、20 時台の run22 の突き合わせで役に立ったことになります。

（出典: `docs/decisions.md:3675-3681`、`authgap/report.py:279-284`（`truncations` の `tree_budget`。D64 / U49、R5-r1-6））

#### 一歩ずつの説明 — 結果を変えない速度の直し

速度を戻すために入れた直しは、どれも「**同じ計算を何度もしていた所で、1 回の結果を覚えて使い回す**」ものでした。

| コミット | 直したこと（やさしく言い換え） | 確かめたこと |
|---|---|---|
| fd4384c | import の文の表を、ファイルごとに 1 回だけ作る（呼び出しのたびにファイルの全ノードを歩き直していた。dynare-lsp では 311 回）。スコープごとに名前の束縛の表を 1 回で作る。関係する名前が 1 つも無いファイルは飛ばす | 新しい表と、名前ごとに歩く元の方法が、5 つの木の約 140 万組で一致。xagent の入口探しは 56 秒 → 約 30 秒（段階 B の前は 14 秒） |
| d851e3a | lifespan や mount を使わない木では、それを探す全ノードの走査を飛ばす。import は文だけをたどる | 同じマシンで mcparmory の 1 木: 段階 B の前 166 秒、run21 の版 220 秒 → 190 秒 |
| 1744f3a | 関数のスコープの情報を、関数ごとに 1 回だけ作って覚える（関数に降りるたびに本体を歩き直していた） | mcparmory の 1 木: 190 秒 → 179 秒。全 test 1,618 件が通り、B3a 8/8・B3b 15/15 |

表の読み方: 1 行が 1 つの速度の直しです。
たとえば 2 行目は「d851e3a では、lifespan や mount を使っていない木で、それを探すための全体の走査を省いた。同じマシンで測ると、mcparmory の 1 木の解析は、run21 の版の 220 秒から 190 秒に縮んだ（段階 B の前の版は 166 秒）」と読みます。

ここで大事なのは、どの直しも**結果を変えない**ことを確かめている点です。
たとえば fd4384c は、新しく作った名前の表と、元の「名前ごとに歩く」方法の結果を、約 140 万組で突き合わせて一致を確かめました。
そして run20 と run23 を突き合わせると、**消えたユニット 0・消えた矛 0**、不 → 内の移動も 0 でした。

（出典: `git log -1 fd4384c`・`d851e3a`・`1744f3a`（コミットのメッセージ）、`docs/decisions.md:3675-3685`）

#### 一歩ずつの説明 — 時間はマシンの速さで変わる

速度を戻した後も、記録は「時間はマシンの速さで変わる」ことを、4 つの事実で書いています。

1. **run20 は、別の速いマシンで取った。** run20 の xagent・mcparmory は 85 秒・90 秒でしたが、添削を行ったマシンでは、段階 B の**前**の版でも mcparmory の 1 木に約 166 秒かかりました。だから、run20 の 729 秒と run21 の 1,894 秒は、同じマシンで比べた数ではありません。
2. **同じマシンで比べた段階 B の遅れは、約 8%。** mcparmory の 1 木で 166 秒 → 179 秒（速度を戻した後の版）でした。
3. **run23 の xagent は 179.1 秒で、上限の 180 秒ぎりぎりだった。** 打ち切りは無かったものの、あと 1 秒遅ければ打ち切られていました。
4. **同じコンテナで取った run24 では、xagent は 89.9 秒だった（約半分）。** 解析器の違いは N9 の 1 か所（URL の読み方）だけで、速さにはほぼ関係しません。それでも時間が半分になりました。記録は「翌日」と書いていますが、記録のコミットの時刻（UTC）で見ると、run23 の記録（9 月 28 日 21 時 07 分）から run24 の記録（9 月 29 日 0 時 07 分）までは約 3 時間です。**同じ入れ物（コンテナ）でも、マシンの速さは時によって変わる**のです。

つまり、**学生の最終評価のマシンが遅ければ、大きな木は打ち切られうる**ということです。
打ち切りは manifest と `summary.json` に件数つきで残るので、最終評価では必ず確かめます。

（出典: `docs/decisions.md:3686-3689`（時間上限はマシンの速さに依存する）、`:3699-3702`（run24 の 89.9 / 86.6 秒）、`docs/preregistration.md:576`（逸脱 #25 の「翌日」）、`git log -1 4c63482`・`git log -1 3167b20`（記録のコミットの時刻））

#### なぜそうするのか

- **速度を直した理由**: 計画は「性能は添削しない」と決めていました（36.2 節）。けれども、遅くなった結果ユニットが数え落とされたのは、壊し方 (c)（道具が黙って数え落とす）そのものです。だから、結果を守るために速度を直しました。
- **時間上限を延ばさなかった理由**: 時間上限（180 秒）は、事前登録した手続きの一部です（§2.1、D34）。結果を見てから上限を延ばすと、「都合のよい値を選んだ」ことになります（[第 27 章](ch27.md) 27.5 節）。だから、上限はそのままにして、解析器の側の無駄を省きました。
- **結果を変えないことを確かめた理由**: 速度の直しは、凍結の直前の解析器の変更です。速くするつもりで判定を変えてしまえば、別の問題を作ります。だから、元の方法との一致（約 140 万組）と、run20 との突き合わせ（消えた 0）で確かめました。

#### よくある誤解・つまずき

- **誤解: 「run21 でユニットが減ったのは、段階 B の直しが誤っていたから」**
  判定の変化ではなく、時間上限による打ち切りでした。消えたユニットは 2 木に集中し、`budget_skipped` の数と一致しました。
- **誤解: 「run20 の 729 秒と run21 の 1,894 秒の差が、段階 B の遅れ」**
  2 つは別のマシンで取った数です。同じマシンで比べた遅れは、mcparmory の 1 木で約 8%（166 → 179 秒）でした。
- **誤解: 「`status` が `ok` なら、木の全部のユニットを解析した」**
  違います。時間上限で打ち切っても、`status` は `ok` のままです（[第 18 章](ch18.md) 18.10 節）。`budget_skipped` を必ず見ます。
- **誤解: 「打ち切られたユニットは、manifest に空のユニットとして残る」**
  残りません。manifest の `units` には入らず、数だけが `truncations` と `summary.json` に残ります（[第 27 章](ch27.md)）。だから、見落としの抜き取りの元の一覧にも出てきません。
- **つまずき: 「v4 で打ち切りが 0 だったから、最終評価でも 0」と考える**
  分かりません。v4 の最長は 96.8 秒でしたが（[第 27 章](ch27.md) 27.7 節）、木の数が増えれば、もっと大きな木が混ざりえます。マシンが遅ければ、xagent のように 180 秒すれすれの木も出ます。

#### 手作業ではどう使うか — 手順書 9.2・9.3

最終評価の段階 5（走査）で、この節の教訓は、手順書の次の項目になっています。

**走査のとき（手順書 9.2）**: 「走らせたマシン（CPU・メモリ・同時に走らせた本数）と日時を記録する。木ごとの時間はマシンの速さで変わる（D64 の追記）」。

- **CPU**: 計算をする部品。種類とコアの数を書きます。
- **メモリ**: 計算の途中の情報を置く場所の大きさ。
- **同時に走らせた本数**: 同じマシンで、ほかの走査や重い作業を同時に走らせていたか。同時に走らせると、1 本あたりの速さが落ちます。
- **日時**: 走らせ始めと終わりの日時。run23 と run24 のように、同じ入れ物でも時によって速さが変わるからです。

**走査の後（手順書 9.3）**: `summary.json` を開いて、表の欄を確かめます。時間に関係する欄は次のとおりです。

| 欄 | 確かめること |
|---|---|
| `trees[].budget_skipped` | **時間上限で打ち切ったユニットの数**。0 でない木を全件書き出し、その木の `elapsed_s` も書く |
| `trees[].elapsed_s` | その木の解析にかかった秒数。180 秒を超えることもある（ユニットの途中では止めないため） |
| `trees[].status` | `ok` 以外の木を全件書き出す。ただし `ok` でも打ち切りはありうる |

表の読み方: たとえば 1 行目は「`budget_skipped` が 0 でない木は、時間上限でユニットを解析しなかった木。全部を書き出し、それぞれ何秒かかったかも書く」と読みます。
run21 の記録に当てはめると、「xagent: `budget_skipped` 351、`elapsed_s` 185.0」「mcparmory: `budget_skipped` 197、`elapsed_s` 181.2」「meta-skill-evloving: `budget_skipped` 716、`elapsed_s` 782.2」と書くことになります。

そして、手順書は次のように決めています。

- 打ち切りがあっても**取り直さない**。件数を報告に書く（9.3）。
- 遅いマシンなら、**走らせる前に**速いマシンを選ぶ。走らせた後に選び直さない（26 節「時間上限で打ち切られた木がある」）。
- 事前登録の下書きも、「走査の後、manifest の `tree_budget` で時間上限による打ち切りの件数を確かめ、打ち切った木と所要時間を報告する」と書いています。

最後の点は大事です。
打ち切りの結果を見てからマシンを変えて取り直すと、「結果が気に入らないから取り直した」のと同じことになります。
マシンを選ぶのは、走らせる前だけです。

（出典: `docs/final_evaluation_procedure.md:655`（9.2 のマシンと日時）、`:657-671`（9.3 の表と「取り直さない」）、`:1451`（26 節）、`docs/drafts/prereg_2_12_draft.md:39-40`）

#### この節のまとめ

run21 でユニットが 2,231 → 1,741 に減ったのは、判定の変化ではなく、段階 B で解析が遅くなり、時間上限で 548 ユニット（xagent 351・mcparmory 197）が打ち切られた数え落とし（誤 clear の向き）だった。結果を変えない速度の直し（同じ計算の覚え忘れを直す）で、run23 で元に戻した（消えたユニット 0・消えた矛 0）。

### 36.11 N9 と、凍結のタグの手違い

#### 一言で言うと

段階 A の敵対的レビューで、直しの範囲の外の古い穴として記録に回したものの 1 つに **N9** がありました。
URL の**クエリ**（`?` の後ろ）の中の `://` を区切りと読み、宛先を手元（localhost）と取り違える誤 clear です。
学生の「進めて」で、凍結の前に直すことになりました。
ところが、学生はその前に、run23 の版（f3c02e8）に `analyzer-freeze-2` を打っていました。
本記録者はタグを確かめずに N9 を直したので、**凍結の後に解析器を変えた**ことになりました（**逸脱 #26**）。
学生は「戻す / 新しいタグ / 付け替え」の 3 つから**新しいタグ**を選び、`analyzer-freeze-3` を 9dc3bc3（run24 の版）に打ちました。
**これが最終評価に使う凍結です。**

[第 22 章](ch22.md) 22.4 節でも、この出来事を「凍結が破れかけたときの扱い方」の例として見ました。
この節では、N9 の中身と、手違いの経緯を、もう一段くわしく追います。

#### たとえ話 — 入稿の後の差し替え

本の著者が、原稿のデータを印刷所に渡した（入稿した）とします。
その後、著者は誤字に気づき、「まだ直せるだろう」と思って、印刷所に確かめずに手元のデータを直しました。
ところが印刷所は、受け取ったデータで、すでに版を作っていました。

このとき、取れる手は 3 つです。

1. 直したデータを捨て、入稿したデータに戻す（**戻す**）。
2. 直したデータで「第 2 刷」の版を新しく作り、第 1 刷の版も記録として残す（**新しいタグ**）。
3. 第 1 刷の版を、こっそり直したデータの版に差し替える（**付け替え**）。

3 は、名前が増えないので一見きれいです。
けれども、「第 1 刷は何だったか」という記録が書き換わり、後から誰も確かめられなくなります。
この研究で学生が選んだのは 2 でした。

#### 小さな例 1 — URL の 4 つの部分

N9 を理解するために、URL の部分の名前を確かめます（[第 10 章](ch10.md)）。
例として `https://api.example.com/x?next=http://localhost/` を分けます。

| 部分 | この例では | 意味 |
|---|---|---|
| scheme | `https` | 通信の方式。`://` の前に書く |
| 権威部（authority） | `api.example.com` | 宛先のホスト（と、ポートや利用者の名前）。`//` の後から、次の `/` `?` `#` まで |
| パス | `/x` | 宛先の中の場所 |
| クエリ | `next=http://localhost/` | `?` の後ろ。宛先に渡す追加の情報 |

表の読み方: たとえば 4 行目は「`?` の後ろはクエリで、宛先に渡す情報にすぎない。この例のクエリには `http://localhost/` という別の URL が入っているが、通信の宛先は権威部の api.example.com で、localhost ではない」と読みます。

RFC 3986（36.6 節）は、scheme の書き方を「英字で始まり、英字・数字・`+`・`-`・`.` が続く」と決めています。
つまり、`?` や `/` や `=` を含む文字列は、scheme にはなれません。

#### 小さな例 2 — N9 の誤り

N9 の所見の例です。

```python
client.get("oauth/authorize?redirect_uri=http://localhost:8080/cb")
```

- `client` は、宛先の基本（`base_url`）を持つ HTTP のクライアントです。
- `"oauth/authorize?redirect_uri=http://localhost:8080/cb"` は、`/` で始まらない**相対の URL**です。宛先は `client` の `base_url` が決めます。
- クエリの `redirect_uri=http://localhost:8080/cb` は、ログインの後に戻ってくる先を相手に伝える情報で、通信の宛先ではありません。

直す前の解析器（`_split_url`）は、文字列の中の最初の `://` を見つけると、その前が何であっても scheme の区切りと読んでいました。
すると、次のように読み違えます。

| 部分 | 直す前の読み | 正しい読み |
|---|---|---|
| scheme | `oauth/authorize?redirect_uri=http` | （無い。相対の URL） |
| 宛先のホスト | `localhost` | `client` の `base_url` が決める |

宛先を localhost（手元）と読んだので、`openWorldHint: False`（D3）と宣言したツールを**内**にしていました。
本当は外部に送っているかもしれないのに「外とは通信しない」と認めてしまう、**誤 clear** です。

（出典: `docs/open_questions.md:1154`（N9 の行）、`git show b87c022` のコミットのメッセージ）

#### 小さな例 3 — 直した差分

N9 の直しは、`authgap/effects.py` の数行だけでした。
差分の要点です（`-` が消した行、`+` が足した行）。

```diff
+#: RFC 3986 の scheme（`ALPHA *( ALPHA / DIGIT / "+" / "-" / "." )`）。
+_URL_SCHEME = re.compile(r"[A-Za-z][A-Za-z0-9+.-]*")
 ...
         i = text.find("://")
-        if i < 0:
+        if i < 0 or not _URL_SCHEME.fullmatch(text[:i]):
             return {"url.host": v}
```

行ごとに見ます。

- 1 行目（`+#: ...`）: 説明のコメントを足しました。RFC 3986 の scheme の文法を書いています。
- 2 行目（`+_URL_SCHEME = ...`）: scheme の文法を、正規表現（文字の並びの型を書く記法）で表した部品を足しました。`[A-Za-z]` は英字 1 文字、`[A-Za-z0-9+.-]*` は英字・数字・`+`・`.`・`-` の 0 文字以上の並びです。
- 4 行目（`i = text.find("://")`）: 文字列の中で、最初の `://` の位置を探します（変えていない行）。
- 5 行目（`-if i < 0:`）: 直す前は、「`://` が無いときだけ」分けずに返していました。
- 6 行目（`+if i < 0 or not ...:`）: 直した後は、「`://` が無いとき、**または** `://` の前の部分（`text[:i]`）が scheme の文法に**丸ごと**合わないとき」に、分けずに返します。`fullmatch` は「全体が型に合うか」を調べる関数です。
- 7 行目（`return {"url.host": v}`）: 分けずに、値全体を宛先の slot に入れて返します（変えていない行）。

N9 の例では、`://` の前は `oauth/authorize?redirect_uri=http` で、`/` や `?` や `=` を含むので scheme の文法に合いません。
だから、直した後は分けずに、文字列全体を宛先の slot（`url.host`）に入れます。
`/` で始まらない相対の URL の宛先は、今までどおり「読まない」側に倒れます（§9.6 の改訂 7'' は「不の側に倒れる」と書いています）。

本書の執筆時に、凍結版の解析器で確かめると、次のとおりでした。

- 文字列が定数だけ（`client.get("oauth/authorize?redirect_uri=http://localhost:8080/cb")`）なら、宛先を決められないので D3 は**不**（理由 `net_host_unknown`）。
- 文字列にモデルの値がつながっている（テストの形 `... + p`）なら、宛先の位置にモデルの値が入るので D3 は**矛**（理由 `net_model_host`）。

どちらにしても、もう**内**にはなりません。
コミットのメッセージは、この直しを「**解決率を下げる側だけの変更**」と書いています。
「分かる」（宛先は localhost）を「分からない」に戻す変更なので、新しい誤 clear を作りにくい向きです。

（出典: `git show b87c022 -- authgap/effects.py`、`authgap/effects.py:469-504`（今の `_split_url`）、`docs/contradiction_principles.md:422-426`（§9.6 の改訂 7''）、凍結版の解析器を scratchpad の小さな木に走らせた結果（本書の執筆時。`authgap/` は変えていない））

たとえば 6 行目は「解析器全体の指紋は、freeze-2 では 4e6123f19ce2 で始まる値、freeze-3 では 35606ba9c9dd で始まる値で、N9 の直しの分だけ違う」と読みます。

ここから、3 つのことが分かります。

1. **2 つの版の解析器の違いは、`authgap/effects.py` の 1 ファイルだけ**です（`git diff --stat f3c02e8 9dc3bc3 -- authgap/` の結果は、`effects.py` の 9 行の追加と 1 行の削除）。
2. **freeze-3 の記録の `freeze.tag` は `analyzer-freeze-2` のまま**です。D64 の記録と逸脱 #26 は、「タグの付いたコミットのファイルなので書き換えない（実装の結合 sha256 35606ba9… は freeze-3 の版と一致する）」と書いています。書き換えれば、タグが指すコミットの中身が変わってしまうからです。
3. **`git_commit` がタグのコミットと 1 つずれる**のは、記録を書いた時点の HEAD（直前のコミット）を書き、その記録をコミットすると 1 つ進むからです。[第 33 章](ch33.md)で見た `analyzer-freeze-1` と同じ形で、`authgap/` の中身は同じです。

まとめると、凍結のタグは **3 つ**あり、最終評価に使うのは `analyzer-freeze-3` です。

#### なぜそうするのか — 「新しいタグ」を選んだ理由

逸脱 #26 の「理由」の欄は、次のことを書いています。

- 本記録者がタグの有無を確かめずに N9 を直した（凍結の後は直さない約束に反した）。
- 学生が「戻す / 新しいタグ / 付け替え」から**新しいタグ**を選んだ。

この選択が成り立つための大事な条件は、「最終評価のデータを誰も見ていない時点」だったことです。

### 36.12 同じ時期に決めたこと — D62 と D63

#### 一言で言うと

添削の途中で、学生は 2 つのことを決めました。

#### たとえ話 — 健康診断の項目

健康診断で、これまで「血圧」と「血糖」を主な項目にし、「視力」と「聴力」は参考の項目にしていたとします。
参考にしていた理由は「視力と聴力の基準は、去年の受診者の結果を見てから決めたから」でした。

それなら、4 つとも主な項目にしてよいはずです。
ただし、4 つの数を足し合わせて「健康度」にはしません。意味の違う数を足しても、解釈できないからです。

D62 は、この「4 つとも主な項目にする。足し合わせない」という決定です。

#### 一歩ずつの説明 — D62 の理由

この決定は、事前登録の逸脱 #24 として記録されました。

#### 一歩ずつの説明 — D63

D63 の背景は、学生の懸念でした。
査読で「仕様が『宣言を信頼するな』と言っているのに、宣言の食い違いを測って何になるのか」と問われうる。
答えの 1 つとして、「この道具は、作者がより正確な宣言を書くのを助ける」と書けます。

D63 の決定は 3 つです。

1. 論文では**応用の 1 つ**として書く。主張の芯は測定（宣言 D と実効の権限 M の食い違い）のまま変えない。
2. **実装は変えない。** 矛盾の行は、そのまま「この宣言は直すべき」という提案として読める（仕様書 636 行目の「ポリシーの生成器は作らない」を守る）。

- **D62 を最終評価の前に決めた理由**: 主指標を何にするかは、結果を見る前に決めておく必要があります。結果を見てから「D3 の数字がよいから主指標にする」と決めれば、後出しになります。D62 は、学生の最終評価のデータを誰も見ていない時点の決定でした。
- **D63 で実装を変えなかった理由**: 応用のために新しい機能（宣言の修正案を作る機能など）を足すと、凍結の直前に解析器を変えることになり、新しい誤りを作りえます。今ある矛盾の行で十分に提案として読めるので、変える必要がありませんでした。

#### よくある誤解・つまずき

- **誤解: 「D62 で D3・D4 の判定の規則が変わった」**
  変わっていません。判定表（§7.3・§7.4）はそのままで、位置づけ（呼び方）だけが変わりました。
- **誤解: 「4 つとも主指標なら、4 つを足した数がいちばん大事」**
  足しません。4 つの宣言は意味が違うので、足した数は解釈できません（[第 16 章](ch16.md)）。
- **誤解: 「D63 で、矛の出ないツールには『安全』と言えるようになった」**
  言えません。効果が見つからないことを、`readOnlyHint: true` を付けてよい根拠にはしません。

#### この節のまとめ

### 36.13 凍結の後の約束 — そして、それが守られたこと

#### 一言で言うと

**`analyzer-freeze-3` の後、学生の最終評価が終わるまで、解析器は変えません。**
変える必要が出たら、`docs/preregistration.md` に逸脱として記録し、評価の結果は凍結した解析器のものを主とします。
解析器を変える前には、必ず `git tag -l` で凍結のタグを確かめます（タグの手違いから足した約束）。
この約束は、その後の 3 つの場面（D65 の 2、D66、D71）で、実際に守られています。

#### たとえ話 — 公式記録の計測器

陸上競技の大会では、記録を測る計時の装置を、シーズンの途中で勝手に取り替えません。
取り替えれば、取り替える前と後の記録を比べられなくなるからです。
もし装置の不具合が見つかったら、すぐに直すのではなく、「この装置にはこういう癖がある」と記録に残し、そのシーズンの公式記録は、その装置で測った値のままにします。

凍結の後の約束も同じです。
凍結版の解析器にも、まだ見つかっていない誤りがあると考えます（36.3 節・36.8 節）。
見つかっても直さず、限界として記録し、最終評価の主の数字は凍結版で出します。

#### なぜそうするのか

[第 22 章](ch22.md)で見た凍結の 3 つの理由が、そのまま当てはまります。

1. **再現できるようにするため**: 凍結版と同じ Python の版があれば、誰が走らせても同じ結果になります（D71 の理由の 3 も「凍結した版と Python の版が揃えば誰でも再現できる」）。
2. **結果を見て解析器を直すのを防ぐため**: 最終評価のデータを見た後で直せば、「そのデータでよい数字が出るように直した」と疑われます。
3. **どの版の数字かをはっきりさせるため**: v3 は `analyzer-freeze-1`、v4 と最終評価は `analyzer-freeze-3` の数字です。

そして、この章の手違いから学んだのは、「約束を書くだけでは足りず、**変える前に確かめる手順**を約束に入れる」ことです。
`git tag -l` を確かめる一手間が、凍結を守る仕組みになります。

#### よくある誤解・つまずき

- **誤解: 「凍結の後に誤りを見つけたら、直すのが誠実」**
  この研究では、直さずに限界として記録するのが誠実です。直すと、凍結の前後で数字を比べられなくなり、結果を見て直したかどうかを外から確かめられなくなります。
- **誤解: 「v4 で誤りが見つかったのに直さないのは、怠慢」**
  D66 の規則の 2 で、最初から「直さず O43 に書く」と決めていました。規則どおりです。
- **誤解: 「D71 で、解析器を作り直すことになった」**
  作り直しません。D71 は「自前のまま、凍結のまま」を追認した決定です。
- **誤解: 「凍結の後は、どんな理由があっても変えられない」**
  変えることはありえます。そのときは逸脱として記録し、主の数字は変える前の版で出します（手順書 25 節）。ただし、最終評価のどの段階でも `authgap/` を変えない、というのが手順書の約束です。
- **つまずき: 「`authgap/` 以外なら変えてよい」**
  手順書 25 節は、走査の後で「`authgap/`・判定の表・原理・語彙・手引き」を変えることを、やってはいけないこととして挙げています。凍結の考え方は、解析器のコードだけのものではありません。

#### 手作業ではどう使うか

最終評価で、学生がこの約束を守るためにすることは、次のとおりです。

1. **段階 5 の前**: 36.11 節の 3 つのコマンドで、タグ・diff・未コミットの変更を確かめ、出力を記録する。

#### この節のまとめ

`analyzer-freeze-3` の後、最終評価が終わるまで解析器は変えない。変える必要が出たら逸脱として記録し、主の数字は凍結版で出す。変える前には `git tag -l` を確かめる。
