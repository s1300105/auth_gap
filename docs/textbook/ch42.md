## 第 42 章 限界の一覧

> **この章で分かること**:
> - 「限界」とは何か。限界を、数をどちらにずらすかという「**向き**」（誤警報 / 誤 clear（見落とし）/ 数え落とし / 不明 / 混在）で整理する理由。
> - 凍結した解析器 `analyzer-freeze-3` の既知の限界の全体の地図。記録の番号（O35・O38・O39・O41・O42・O43）と、それぞれの向き。
> - 第 3 版の一覧から直した 2 点。「論文で深さ 3・4・5 を比べて評価する」は、**深さ 3・5 は矛の件数だけを探索的に出し、判定しない**（D69 の 5）に変わった。「判定の独立性: v3 の判定は開発者側」は、**v3・v4 は本記録者（AI）が判定し、最終評価は学生 1 人が LLM なしで判定する。κ は出せない。2 人目は保留**（D67 の 4、D70 の 3・8）に変わった。
> - 第 4 版で足した行。v4 の中間検証で見つけた O43 の 6 つの形（起動時の初期化、デコレータの wrapper、ライブラリからの呼び戻し、モジュール水準のインスタンス、loguru、`wave.open`）。
> - **lifespan の形の誤警報は、設計の選択による限界**であること。解析器は、各呼び出しをサーバの状態を仮定せずに独立に解析する。正しく扱うには 4 つの条件をすべて確かめる必要があり、1 つでも外すと誤 clear を作る。だから誤の原因 **E1** は直されずに残り、件数を報告する。
> - 研究の設計からくる限界。対象は Python の MCP サーバだけ。枠は 2026-09-20 の列挙で、その後に作られたサーバは入らない。木の割合は下限（[第 39 章](ch39.md)）。
> - 論文の限界の節に書くもの（手順書 24.2 節の 7 項目）と、この章の各行の対応。判定の記録（誤の原因 E1〜E9、見落としの原因）が、どのように限界の節の材料になるか。

#### この章で使う言葉の思い出し

この章では、前の章で学んだ言葉をたくさん使います。
先に短く思い出しておきます。

- **矛・不・内**（[第 17 章](ch17.md)）: 解析器の 3 つの答え。矛 = 宣言に反する効果がある。不 = 静的には決められない。内 = 宣言の範囲内。
- **正・誤・不明**（第 17・38 章）: 人が矛を確かめた結果。
- **誤警報**（[第 21 章](ch21.md)）: 本当は違反でないのに、解析器が矛を出すこと。精度を下げる向きの誤り。
- **誤 clear（false-clean）**（[第 21 章](ch21.md)）: 本当は違反なのに、解析器が矛も不も出さず「問題なし」に見せること。見落としとも言う。CLAUDE.md の約束で、この向きの誤りは特に明記する。
- **数え落とし**（[第 36 章](ch36.md)）: 解析器が、ユニットや効果を数えること自体をやめてしまうこと（時間上限の打ち切りなど）。数えられなかったものの中の矛も見えないので、結果は誤 clear と同じ向きに働く。
- **混在**（[第 36 章](ch36.md)）: 同じ単位の中に、誤警報の形と誤 clear の形の両方があること。
- **凍結**（第 22・36 章）: 解析器を `analyzer-freeze-3` の版から変えないという約束。
- **O 番号**: `docs/open_questions.md` の項目の番号。「既知の限界」と書かれた O は、直さないと決めたものの記録。
- **単位（U01 など）**（[第 36 章](ch36.md)）: 凍結前の添削で、見つけた所見を根本原因ごとに束ねたもの。
- **下限・上限の目安**（[第 39 章](ch39.md)）: 下限 = 本当の数はこれより小さくない。上限の目安 = 誤警報を含む機械の数。
- **lifespan**（[第 3 章](ch03.md)）: サーバの起動時に 1 回だけ走る関数。`FastMCP(..., lifespan=...)` で登録し、どの起動方法でもツールの受付より前に走る。
- **条件の種類（`condition_type`）**（[第 39 章](ch39.md)で名前を見た。詳しくは[第 49 章](ch49.md)）: 効果が条件つきで届くとき、その条件を「なし / 引数 / 初回 / 失敗・期限切れ / 外部の状態 / 運用者の設定 / 起動の方法」から選んで記録する欄。

- **やさしい言い換え**: 解析器の矛を人が確かめて「誤」にしたとき、「なぜ誤だったか」を 9 つの箱のどれかに入れて記録する記号。

### 42.1 限界とは何か — 「向き」で整理する

#### 一言で言うと

**限界**とは、解析器や研究の手順が持つ、分かっていて直さない（または直せない）弱点のことです。
この研究では、限界を書くときに必ず「**向き**」を添えます。
向きとは、その弱点が数を**多く見せるのか、少なく見せるのか、決められなくするのか**のことです。

#### 言葉の 3 点セット — 限界

- **やさしい言い換え**: 「この道具には、ここが見えない（または、ここを見間違える）」という、あらかじめ分かっている弱点。
- **正確な定義**: 解析器・判定の手順・標本の選び方のうち、結果の数を真の値からずらしうるもので、凍結の後は直さないと決め、`docs/open_questions.md`（「既知の限界」と書いた O）や決定の記録に、向きと理由を添えて書いたもの。
- **例**: 解析器は入口から深さ 4 までしか呼び出しを降りない。だから深さ 5 より奥の書き込みは見えない（誤 clear の向き）。

#### たとえ話 — 空港の金属探知機

空港の金属探知機を思い浮かべてください。
この機械には、よく知られた弱点がいくつかあります。

- ベルトのバックルや靴の金具にも反応します。危ないものを持っていないのに鳴ります。これは**誤警報**の向きの弱点です。
- 金属でできていない刃物には反応しません。危ないものを持っていても鳴りません。これは**見落とし（誤 clear）**の向きの弱点です。
- 機械が混んで止まり、一部の人を検査しないまま通してしまうことがあるとします。検査しなかった人は「鳴らなかった人」として数えられてしまいます。これは**数え落とし**です。
- 鳴ったけれど、何に反応したのか機械には分からないことがあります。これは「**不明**」です。人が手で確かめるしかありません。

空港の係の人は、こうした弱点を知っています。
だから、鳴ったら手で確かめ、機械の弱点を補う別の検査も組み合わせます。
そして、検査の結果を報告するときには「この機械は非金属の刃物を見つけられない」と書き添えます。
この研究の「限界の一覧」は、この「書き添え」にあたります。

#### 小さな例 — 4 つの向きと、数への効き方

| 向き | 解析器は何をするか | 矛の件数への効き方 | 最終評価の数への効き方 | 人の判定での現れ方 |
|---|---|---|---|---|
| **誤警報** | 本当は違反でないのに矛を出す | 多く見せる | 精度（正の割合）を下げる | 矛を判定して「誤」になる |
| **誤 clear（見落とし）** | 本当は違反なのに矛も不も出さない | 少なく見せる | 違反のある木の数を少なく見せる（下限の理由の 1 つ） | 見落としの判定で「見落とし」になる |
| **数え落とし** | ユニットや効果を数えること自体をやめる | 少なく見せる | 誤 clear と同じ向き | manifest の打ち切りの印で分かる |
| **不明**（不の欠け・過不足） | 決められないものに不を出さない、または出しすぎる | 不の件数がずれる | 不の中身の判定の分母がずれる | 不の中身の判定や見落としの判定で分かる |
| **混在** | 同じ根本原因から、形によって両方の向きの誤りが出る | どちらにもずれうる | 向きを 1 つに決められない | どちらの判定にも現れる |

表の読み方: 1 行が 1 つの向きです。
たとえば 2 行目は「誤 clear の向きの限界は、解析器が本当の違反に何の印も付けない形で現れる。だから矛の件数を少なく見せ、最終評価の『違反のある木の数』も少なく見せる。人の判定では、矛の判定ではなく、見落としの判定のほうで『見落とし』として見つかる」と読みます。

#### 一歩ずつの説明 — 表の列を 1 つずつ

- **「解析器は何をするか」の列**は、その向きの弱点が、解析器の出力にどう現れるかです。
- **「矛の件数への効き方」の列**は、解析器が出す生の数（[第 40 章](ch40.md)の数字の一覧の数）がどちらにずれるかです。
- **「最終評価の数への効き方」の列**は、人が判定した後の数（精度や、違反のある木の割合）がどちらにずれるかです。誤警報は、人が判定すれば「誤」として取り除かれます。だから違反のある木の数そのものは水増しされません。そのかわり、精度を下げます。
- **「人の判定での現れ方」の列**は、判定のどの場面でその弱点に出会うかです。誤警報には矛の判定で、誤 clear には見落としの判定で出会います。

ここで大事なのは、**誤警報と誤 clear では、出会う場面が違う**ことです。
矛の判定だけをしていると、誤 clear の限界には一度も出会いません。
解析器が何も出していない所に違反があっても、矛の一覧には載っていないからです。
だから最終評価では、矛の判定とは別に、見落としの判定（200 件）を行います（D69 の 3）。

（出典: `docs/decisions.md:3827`（D69 の 3））

#### なぜ向きを書くのか

向きを書く理由は 3 つあります。

1. **読み手が、数をどう割り引けばよいかが分かるからです。**
   たとえば「D2 の矛は下限」と書いてあれば、読み手は「本当の D2 の違反はこれより多いかもしれない」と読めます。向きが書いていなければ、多いのか少ないのか分かりません。
2. **この repo の約束だからです。**
   CLAUDE.md のコミットの約束は、「何を直したかだけでなく、なぜそれが誤りだったか（どちらの方向に間違っていたか）を書く。誤 clear（false-clean）方向の誤りは特に明記する」と定めています。限界の記録も同じ考え方で書きます。
3. **誤 clear の向きは、黙っていると見えなくなるからです。**
   誤警報は、矛の一覧に載るので、判定すればいずれ見つかります。
   誤 clear は、解析器が「問題なし」と見せたまま、何の痕跡も残しません。
   だから書いておかないと、「解析器が何も言わなかった = 違反は無かった」と読まれてしまいます。
   これは CLAUDE.md の規則 4「解決できなかったものは『不明』として記録する。黙って安全側に倒さない」と同じ心配です。

（出典: `CLAUDE.md` の「コミットの約束」と「この repo で守る規則」の 4）

#### よくある誤解・つまずき

- **誤解: 「限界を書くのは、研究がうまくいかなかったことを認めることだ」**
  違います。限界を書くと、読み手は「どこまで信じてよいか」を自分で判断できます。何も書いていない研究のほうが、読み手は疑います。
- **誤解: 「限界は、時間をかければ全部なくせる」**
  一部はそうですが、全部ではありません。静的解析（プログラムを動かさずに読む方法、[第 7 章](ch07.md)）には、深さや外部ライブラリの中身のように、構造的についてまわる弱点があります。また、凍結した後に直すと、凍結の約束（[第 22 章](ch22.md)）を破ることになります。
- **誤解: 「誤警報は精度で測られるので、限界として書かなくてよい」**
  精度は「どれくらい誤ったか」を示しますが、「なぜ誤ったか」は示しません。原因の形（E1〜E9）を書いておくと、読み手は「この形のサーバでは誤警報が出やすい」と分かります。
- **つまずき: 「向き」と「重大度」を混ぜる**
  O42 には「重大度（高・中・低）」の列もあります。重大度は、その誤りが結果にどれだけ効きそうかという添削のときの見立てで、向きとは別の欄です。

#### 手作業ではどう使うか

判定の記録を書くときに、次のように使います。

- 矛を**誤**にしたら、`error_class` の欄に E1〜E9 のどれかを書きます。その E が、この章のどの限界の現れかを思い出すと、分類が確かになります（42.6・42.7 節）。
- 見落としの判定で**見落とし**を見つけたら、原因を 5 分類で書きます。この章の 42.3〜42.5 節の形と照らし合わせます。
- どちらにも当てはまらない形なら、E9（その他）や「その他」にし、`note` に形を説明します。

#### この節のまとめ

限界とは、分かっていて直さない弱点のことで、必ず「向き」（誤警報・誤 clear・数え落とし・不明・混在）を添えて書く。
誤警報には矛の判定で、誤 clear には見落としの判定で出会う。誤 clear は黙っていると見えなくなるので、特に明記する。

### 42.3 見えないもの (1) — 深さの上限 4

#### 一言で言うと

解析器は、ツールの本体（深さ 0）から呼び出しをたどって、**深さ 4 の関数の中身まで**を読みます。
深さ 5 より奥にある書き込みは見えません。
これは誤 clear の向きの限界です。

#### たとえ話 — 伝言ゲームを 4 人目まで追う

伝言ゲームで、最初の人が言ったことが最後にどうなったかを調べるとします。
調べる人は、時間の都合で「4 人目まで」しか話を聞かないと決めました。
5 人目より先で伝言が変わっていても、この調べ方では分かりません。
「4 人目までは正しく伝わっていた」とは言えますが、「最後まで正しく伝わった」とは言えません。

#### 小さな例 — 深さ 5 の書き込み（作例）

次は、説明のために作ったコードです。
実際の v4 の mcp-atlassian の件（深さ 7）を、短くしたものです。

```python
# 説明用（作例）
@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def get_page(page_id: str) -> str:
    client = make_client()                 # 本体（深さ 0）が make_client を呼ぶ
    return client.fetch(page_id)

def make_client():                         # 深さ 1
    return Client(load_auth())

def load_auth():                           # 深さ 2
    return refresh_if_expired()

def refresh_if_expired():                  # 深さ 3
    token = current_token()
    if token.expired:
        token = request_new_token()
        save_token(token)
    return token

def save_token(token):                     # 深さ 4
    write_token_file(token)

def write_token_file(token):               # 深さ 5（解析器はここに降りない）
    with open(TOKEN_PATH, "w") as f:
        f.write(token.text)
```

#### 一歩ずつの説明

- 2 行目: このツールは `readOnlyHint=True`（D1。読むだけ）と宣言しています。
- 3〜5 行目: ツールの本体です。深さ 0 と数えます（[第 15 章](ch15.md)）。本体は `make_client()` を呼びます。
- 7〜8 行目: `make_client` は、本体から直接呼ばれるので深さ 1 です。
- 10〜11 行目: `load_auth` は深さ 2 です。
- 13〜18 行目: `refresh_if_expired` は深さ 3 です。トークン（ログインの証明のデータ）の期限が切れていたら、新しいトークンをもらい、`save_token` で保存します。
- 20〜21 行目: `save_token` は深さ 4 です。解析器は深さ 4 の関数の**中身は読みます**。中にあるのは `write_token_file(...)` の呼び出しだけです。
- 23〜25 行目: `write_token_file` は深さ 5 です。解析器は**ここへは降りません**。だから 24 行目の `open(TOKEN_PATH, "w")`（ファイルの書き込み）は見えません。

結果として、解析器はこのツールに D1 の矛を出しません。
けれども実際には、トークンの期限が切れていれば、読み取り専用と宣言したツールがファイルを書き換えます。
これが誤 clear です。

#### 実物の例 — v4 の mcp-atlassian（R04・R05）

v4 の見落としの抜き取りでは、mcp-atlassian の 2 つのツール（`get_page` と `get_issue_history`）で同じ形が見つかりました。
判定の記録によると、`get_page` の道筋は次のとおりです。
ツールの本体 → 取得役（fetcher）の用意 → クライアントの構築 → OAuth のセッションの設定 → トークンの確かめ → トークンの更新 → トークンの保存 → ファイルへの保存。
ファイルへの書き込み（ホームディレクトリの下にディレクトリを作り、トークンのファイルを `'w'` で開く）は**深さ 7** にあります。
解析器はこのユニットに効果を 1 つも出していません（打ち切りの印は `depth`）。
書き込みは条件つきです。OAuth の設定があり、トークンの期限が切れているときだけ起きます。

#### 最終評価での扱い — 2 つの決まり

最終評価では、深さについて 2 つの決まりがあります。

**決まり 1: 見落としの判定で読むのは深さ 4 まで（D68 の 2）。**
人が見落としを判定するときも、解析器と同じ数え方で深さ 4 まで読みます。
偶然それより奥に宣言に反する動作を見つけたら、「**見落とし（深さ 4 の外）**」として別に記録します。
主の見落としの数には入れず、併記します。

理由は 2 つあります。
1 つ目に、普通の見落としに数えると、数が判定者の読んだ深さで変わってしまいます。
ある日は深さ 6 まで読み、別の日は深さ 4 で止めた、ということが起きると、数の意味が揃いません。
2 つ目に、「反する動作は無い」にすると、知っている違反を安全側に倒すことになります（CLAUDE.md の規則 4）。
v4 の R04・R05 が、ちょうどこの形でした。
v4 では見落としに数えましたが、最終評価の決まりでは「見落とし（深さ 4 の外）」になります。

（出典: `docs/decisions.md:3805-3808`（D68 の 2）、`docs/drafts/final_judging_guide_draft.md:661`（R04 の考え方））

**決まり 2: 深さ 3・5 は件数だけ（D69 の 5）。**
主の結果は深さ 4（凍結の設定）です。
時間があれば、深さ 3 と深さ 5 でも走らせて、**矛の件数の変化だけ**を探索的に出します。
深さ 3・5 で出た矛は、人が判定しません。
事前登録の下書き（未承認）では、この感度分析を「する」としています。

（出典: `docs/decisions.md:3832`（D69 の 5）、`docs/final_evaluation_procedure.md:257-260`（0-10）、`docs/drafts/prereg_2_12_draft.md:41`）

#### なぜ深さ 4 で止めるのか

深さを上げれば見える範囲は広がりますが、時間がかかり、木の時間上限（42.8 節）に当たりやすくなります。
深さは、仕様書では 3 でした。
それを 4 に上げたのは D54 の決定で、深さ 3・4・5 の感度分析を見てから決めたので、純粋な事前登録ではありません（[第 27 章](ch27.md)）。
凍結した後は、深さ 4 のまま変えません。
深さ 5 の件数を出すのは、「深さを上げたら矛がどれくらい増えそうか」の目安を読み手に示すためです。
判定しないのは、判定の時間を主の結果（深さ 4）に使うためです。

（出典: `docs/preregistration.md:568`（逸脱 #17。深さ 3 → 4）、`docs/decisions.md:2908`（D54））

#### よくある誤解・つまずき

- **誤解: 「深さ 5 の件数を出すので、深さ 5 の精度も分かる」**
  分かりません。深さ 5 の矛は判定しないので、増えた矛のうち何件が本当の違反かは分かりません。件数だけです。
- **誤解: 「深さ 4 の外の違反は、見落としではないので、無かったことにする」**
  無かったことにはしません。「見落とし（深さ 4 の外）」として別に記録し、併記します。
- **つまずき: 深さを 1 から数える**
  ツールの本体が深さ 0 です。本体が呼ぶ関数が深さ 1 です。manifest の `witness_chain`（道筋）の長さが、そのまま効果の深さです（[第 15 章](ch15.md)）。

#### 手作業ではどう使うか

- **矛の判定では**: 深さは問題になりません。解析器が出した矛は、深さ 4 以内で見つけたものだからです。
- **見落としの判定では**: 深さ 4 まで読みます。深さ 4 の関数の中で、さらに奥の関数を呼んでいたら、そこで止めます。止めた先に違反があると分かっていても（たとえば関数の名前が `save_token_file` で、明らかに書きそうでも）、確かめに行くのは任意です。行って違反を見つけたら「見落とし（深さ 4 の外）」です。
- 手引きの下書きの 18.3 節は、「深さ 4 より奥を**探しに行く必要はない**（読む範囲は深さ 4 まで）」と書いています。だから、奥を読むかどうかで判定者ごとに数が変わることはありません。
- 深さ 4 の中にも外にも反する動作があるときは、中のものを主として「見落とし」（または「解析器が不として出している」）にし、外のものは `note` に書きます。深さ 4 の外にだけあるときが「見落とし（深さ 4 の外）」です（18.3 節）。
- 記録の欄 `depth` には、見つけた動作の深さ（本体 = 0）を書きます（18.4 節）。

（出典: `docs/drafts/final_judging_guide_draft.md:482-491`（18.3 節）、`:493-504`（18.4 節））

#### この節のまとめ

解析器は深さ 4 の関数の中身までしか読まないので、深さ 5 より奥の書き込みは見えない（誤 clear）。v4 では mcp-atlassian の深さ 7 のトークンの保存がこの形だった。
最終評価では、深さ 4 の外で見つけた違反は「見落とし（深さ 4 の外）」として別に数え、深さ 3・5 は矛の件数だけを探索的に出して判定しない。

<a id="s42-5"></a>
### 42.4 見えないもの (2) — 語彙の外

#### 一言で言うと

解析器は、「外の世界に触れる操作」の一覧（**sink の語彙**、[第 13 章](ch13.md)）に載っている関数の呼び出しだけを効果にします。
一覧に無い関数で書き込みや送信をしても、効果になりません。
語彙は仕様書の段階で凍結したので、足しません。
これは誤 clear の向きの限界です。

#### たとえ話 — 持ち込み禁止品のリスト

空港の荷物検査の係の人が、「持ち込み禁止品のリスト」だけを見て検査しているとします。
リストに「はさみ」はあっても「カッターの替え刃」が無ければ、替え刃は通ってしまいます。
係の人は、リストに無いものを止める権限がありません。
後からリストに足したくなっても、検査の途中でリストを書き換えると、前に検査した人と後の人で基準が違ってしまいます。
だから「リストに無いものは通る」ことを、検査の報告に書き添えます。

#### 小さな例 — 語彙に無い 3 つの書き方（作例）

```python
# 説明用（作例）
import httpx
import wave
from loguru import logger

logger.add("server.log")                         # (1) ログの出力先をファイルにする

client = httpx.Client(base_url="https://api.example.com")

@mcp.tool(annotations=ToolAnnotations(destructiveHint=False))
def remove_item(item_id: str) -> str:
    client.delete(f"/items/{item_id}")          # (2) セッションの .delete
    logger.info("removed {}", item_id)           # (3) loguru のログはファイルに追記される
    return "ok"

@mcp.tool(annotations=ToolAnnotations(destructiveHint=False))
def save_recording(directory: str, frames: bytes) -> str:
    w = wave.open(f"{directory}/output.wav", "wb")   # (4) wave.open で書き出す
    w.writeframes(frames)
    w.close()
    return "saved"
```

#### 一歩ずつの説明

- 2〜4 行目: HTTP の道具 `httpx`、音声ファイルの道具 `wave`、ログの道具 `loguru` を読み込みます。
- 6 行目 **(1)**: モジュールの一番上で、loguru のログの出力先に `server.log` というファイルを足しています。これ以降、`logger.info(...)` などを呼ぶたびに、このファイルに 1 行ずつ追記されます。
- 8 行目: `httpx.Client` は、同じ相手に何度も要求を送るための「セッション」です（[第 10 章](ch10.md)）。
- 10〜11 行目: `remove_item` は `destructiveHint=False`（D2。追加するだけで、壊さない）と宣言しています。
- 12 行目 **(2)**: セッションの `.delete(...)` で、相手のサーバに `DELETE` の要求を送ります。相手の資源を消すので、D2 の違反の典型です。けれども、仕様書の proxy の HTTP の行は `.get`・`.post`・`.request` だけを定めているので、`.delete` は効果になりません。
- 13 行目 **(3)**: `logger.info` は、6 行目で足したファイルに追記します。loguru の `logger.add` によるファイルへの書き込みも語彙に無いので、効果になりません。
- 17〜18 行目: `save_recording` も D2 と宣言しています。
- 19 行目 **(4)**: `wave.open(..., "wb")` は、ファイルを書き込み用に開きます。書き先 `directory` はモデルが決める引数なので、既存のファイルを指せば上書きできます。けれども `wave.open` は語彙に無いので、効果になりません。

結果として、解析器はこの 2 つのツールに、(2)〜(4) についての矛も不も出しません。

#### 実物の記録 — 語彙の外の 4 つの形

| 形 | どこで見つかったか | 向き | 記録 |
|---|---|---|---|
| HTTP のセッションの `.put`・`.patch`・`.delete`・`.head`・`.options`、`httpx.put` などのモジュール関数、本体の `content=`・`files=` | 最初の凍結（D59）のときに、語彙を点検して見つけた | 誤 clear。**D2 の矛は下限** | O39 |
| 語彙に無いライブラリ（zvec の `upsert`、arcpy など） | v3 の見落とし 1（zvec の `upsert_documents`） | 誤 clear | O41・O39 |
| loguru の `logger.add` でファイルに追記するログ | v4 の見落とし 1（mcp-aws の `get_execution_plan`、R19） | 誤 clear | O43 |
| `wave.open(..., "wb")` | v4 の見落としの抜き取りの 1 件の中（audio-transcriber、R13）。同じユニットの別の書き込みで不は出ていた | 部分的な見落とし | O43 |

表の読み方: 1 行が 1 つの形です。
たとえば 3 行目は「v4 の見落としの抜き取りで、mcp-aws の `get_execution_plan` が loguru でログファイルに毎回追記していた。loguru のファイル出力は語彙に無いので解析器は何も出さず、見落とし（誤 clear）になった。記録は O43」と読みます。

4 行目は少し特別です。
audio-transcriber のツールでは、別の書き込み（`open(export_path, 'w')`）について解析器は不を出していました。
だから、そのツールの判定の結果は「解析器が不として出している」です。
ただ、同じツールの中の `wave.open` は解析器に全く見えていませんでした。
「ツール全体では印が付いているが、一部の書き込みは見えていない」ので、部分的な見落としと呼んでいます。

（出典: `docs/open_questions.md:1041-1049`（O39）、`:1066`（O41 の語彙の行）、`:1193`（O43 の loguru の行）、`:1197`（O43 の `wave.open` の行）、`evidence/population_v4/v4_judgments.json` の `v3` の R13・R19）

#### O39 の大きさ — 構文で数えた上限

O39 の形がどれくらいあるかは、最初の凍結の前に、開発用の v2（87 木、run16）で**構文で**数えてあります。
「構文で数えた」とは、`.delete(` のような書き方の箇所を数えただけで、それが本当に HTTP のセッションかは確かめていない、という意味です。
だから、これは**上限**（多くてもこれくらい）です。

| 数えたもの | 呼び出し箇所 | その書き方のある木 |
|---|---|---|
| セッションの `.put`・`.patch`・`.delete`・`.head` | 150（`delete` 66、`head` 46、`put` 21、`patch` 17） | 12 木 |
| 本体の `content=`・`files=` | 143 | 12 木 |
| `httpx.put` などのモジュール関数 | 0 | 0 木 |

表の読み方: 1 行が 1 つの書き方です。
たとえば 1 行目は「v2 の 87 木の中に、セッションの `.put` などと読める呼び出しの箇所が 150 あり、そのうち 66 が `.delete` だった。それらは 12 木に散らばっていた」と読みます。
ただし、150 のうち 93 は 1 つの木（meta-skill-evloving）にあります。
件数は 1 木に偏っているので、木の数（12）のほうも合わせて読みます。

この数は開発用のデータのもので、最終評価のデータでの数ではありません。
O39 は「件数を併記する」と書いているので、最終評価のデータで同じ数え方をするかは、学生が決めることです（本書は決めません）。

（出典: `docs/o39_count.json`（`run` = `evidence/scan_v2_run16`、`n_trees` = 87、`total` と `trees_with`）、`docs/decisions.md:3381-3382`（D59 の残した限界））

#### なぜ語彙を足さないのか

語彙は仕様書が「月 3 に凍結する」と決めたものです。
凍結した語彙を、結果を見た後に変えると、「見たデータに合わせて定義を変えた」ことになります。
そうなると、結果の数が「解析器がもともと測ろうとしたもの」なのか「結果に合わせて作り直したもの」なのか、読み手に区別がつきません。
だから語彙は足さず、どれくらい見落としているかを数えて、限界として報告します。
O39 は、学生が語彙の拡張を決めるなら、逸脱として記録し、拡張の前後を併記するとも書いています。
今のところ、拡張は決まっていません。

（出典: `AUTHGAP_BRIEF_v3.md:229`（proxy の HTTP の行）、`:841`（月 3 の凍結）、`docs/open_questions.md:1047-1049`（O39 の「なぜ直さないか」「要る判断」））

#### D2 の矛は「下限」— なぜ D2 なのか

O39 は特に「D2 の矛は下限になる」と書いています。
なぜ D1 ではなく D2 なのでしょうか。

- D1（読むだけ）のツールが `DELETE` を送るのは、もちろん違反です。けれども、D1 のツールが相手を変える要求を送ることは、そもそも多くありません。
- D2（壊さない）のツールは、もともと書き込みをするツールです。その中で、相手の資源を消す `DELETE` を送るのは、D2 の違反の典型です（[第 10 章](ch10.md)、[第 50 章](ch50.md)）。

つまり、語彙の穴がちょうど「D2 の違反が一番起きやすい書き方」と重なっているのです。
だから D2 の矛の件数は、本当の D2 の違反の数より少なく出ます。

#### よくある誤解・つまずき

- **誤解: 「loguru の件は見落としなので、最終評価でも必ず違反に数える」**
  最終評価では、判定の手引き（下書き・未承認）の 15.1 節が、D1 について「`logging` の出力先がファイルなら反する」と書いています。ログのファイルへの追記は、採った原理（字義どおり）では違反です（[第 43 章](ch43.md)）。v4 の R19 の記録には「ログの枠組みの書き込みを宣言違反に数えるかは原理で明示されていない」と書かれていましたが、これは D67 の 1 の前の記録です。手引きが承認されれば、手引きのほうに従います。
- **誤解: 「`.delete` は語彙に無いので、`.request("DELETE", ...)` も見えない」**
  `.request` は語彙にあります。O39 の穴は、メソッドの名前そのものが `.delete` などのときです（[第 32 章](ch32.md)）。
- **つまずき: 語彙の外と、呼び出しの解決の失敗を混ぜる**
  語彙の外は「解析器がその関数を知らない」こと、呼び出しの解決の失敗は「解析器がどの関数を呼んでいるか分からない」ことです。見落としの原因の分類では、前者が「語彙」、後者が「呼び出しの解決」や「受け手の型」になります。

（出典: `docs/drafts/final_judging_guide_draft.md:329`（15.1 の迷いやすい形）、`evidence/population_v4/v4_judgments.json` の `v3` の R19 の `note`）

#### 手作業ではどう使うか

- **見落としの判定で**: 書き込みや送信をする関数が、解析器の効果に出ていなかったら、まず「その関数は語彙にあるか」を考えます。セッションの `.delete`、`wave.open`、loguru のファイル出力などなら、見落としの原因は「**語彙**」です。
- **ログの出力先は、ツールの本体だけでなくモジュールの一番上の設定も見ます**。手引きの下書きの 18.3 節は、ログの出力先がファイルかどうかを、`logging.basicConfig(filename=…)`、`FileHandler`、loguru の `logger.add(<パス>)` など**モジュール水準の設定**でも確かめる、と書いています。v4 の R19 は、ツールの本体には `logger.info(...)` しか無く、ファイルへの出力先はモジュールの一番上（`server.py:66-72`）で設定していました。本体だけを読むと、ファイルへの書き込みは無いと誤って読みかねません。（出典: `docs/drafts/final_judging_guide_draft.md:490-491`、`evidence/population_v4/v4_judgments.json` の `v3` の R19）
- **矛の判定で**: 語彙の外は矛の判定には現れません。ただし、ある組を判定する途中で、同じツールの語彙の外の書き込みに気づくことがあります。その組の判定には入れず、`note` に書いておきます（組は (木, ユニット, site, kind, 宣言) の単位なので、別の site の書き込みは別の話です）。
- **不の中身の判定で**: 解析器が不を出したツールに、語彙の外の書き込みもあることがあります。判定する 1 組に関係なければ、`note` に書くだけにします。

#### この節のまとめ

解析器は sink の語彙にある関数の呼び出しだけを効果にする。セッションの `.delete` など（O39）、zvec や arcpy（O41）、loguru のファイル出力と `wave.open`（O43）は語彙に無く、見落とされる（誤 clear）。
語彙は月 3 に凍結したので足さず、件数を併記して限界とする。`DELETE` の穴は D2 の違反の典型と重なるので、D2 の矛は下限になる。

<a id="s42-6"></a>
### 42.5 見えないもの (3) — 呼び出しをたどれない形

#### 一言で言うと

解析器は、ツールの本体から**書かれた呼び出し**をたどります。
けれども、「書かれていないのに実際には呼ばれる」コードや、「どの関数かを決められない」呼び出しは、たどれません。
v3・v4 では、5 つの形が見つかっています。

1. デコレータの wrapper（包む関数）
2. 木の外のライブラリが、木の中の関数を呼び戻す形
3. モジュール水準のインスタンスを経由するメソッド
4. 関数が返すモジュール
5. 原因の分からない見落とし（O38 の `unlink`）

#### たとえ話 — 電話の取り次ぎ

会社で、ある部長が「私は誰にも電話をかけていない」と言ったとします。
部長の発信の記録を調べても、確かに部長は電話をかけていません。
けれども実際には、次のようなことが起きているかもしれません。

- 部長の電話はすべて、**秘書が先に受けて**、ついでに別の用事を済ませてから部長に回している（デコレータの wrapper）。
- 部長は取引先に「何かあったらこの番号にかけて」と**番号を渡しておき**、取引先がその番号に電話をかけてくる（ライブラリからの呼び戻し）。
- 部長は「**担当者**に頼んで」と言うだけで、担当者が誰なのかは記録に残っていない（モジュール水準のインスタンス）。

部長の発信の記録だけを見ていると、どれも見えません。
解析器が「本体から書かれた呼び出しをたどる」のは、この「発信の記録だけを見る」ことにあたります。

#### 小さな例 1 — デコレータの wrapper（作例）

```python
# 説明用（作例。v4 の texas-grocery-mcp を短くしたもの）
def ensure_session(fn):
    def wrapper(*args, **kwargs):
        refresh_session_if_needed()       # ← 本体より先に走り、認証状態ファイルを上書きしうる
        return fn(*args, **kwargs)
    return wrapper

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
@ensure_session
def coupon_clipped() -> str:
    return fetch_coupons()                # 本体は読み取りだけ
```

**一歩ずつ**:

- 2〜6 行目: `ensure_session` はデコレータです。デコレータとは、関数を受け取って、それを包んだ別の関数（wrapper）を返す関数のことです（[第 9 章](ch09.md)）。
- 3 行目: `wrapper` は、元の関数 `fn` の代わりに呼ばれる関数です。
- 4 行目: `wrapper` は、まず `refresh_session_if_needed()` を呼びます。セッションの期限が近ければ、ブラウザを動かしてログインし直し、認証状態のファイルを上書きします。
- 5 行目: そのあとで、元の関数 `fn` を呼びます。
- 8〜9 行目: ツールの関数 `coupon_clipped` に、`@mcp.tool(...)`（ツールとして登録する）と `@ensure_session`（包む）の 2 つのデコレータが付いています。
- 10〜11 行目: 本体は `fetch_coupons()` を呼ぶだけです。

ツールが呼ばれると、実際には `wrapper` が先に走り、4 行目の書き込みが起きえます。
けれども解析器は、本体（10〜11 行目）から降りた効果だけを見ます。
木の中のデコレータの wrapper は、呼び出しとしてたどりません。
だから 4 行目の書き込みは見えません。

v4 の texas-grocery-mcp の `coupon_clipped`（R16）がこの形でした。
wrapper の中のセッションの更新が、一時的なスクリーンショットの削除、ディレクトリの作成、認証状態ファイルの上書き、ファイルの権限の変更をしていました。
書き込みは条件つきです（自動更新が有効、認証ファイルがある、期限切れか期限が近い、など）。
記録では、深さは wrapper から 2〜3 段で、深さ 4 の中に収まっていました。
だから深さの問題ではなく、見落としの原因は「その他」（wrapper をたどらない）に分類されました。

O43 は、この形を「O42 の RC5（任意のデコレータ）と同じ近似」と書いています。
O42 の単位 U16（暗黙に呼ばれる木内コード。`__call__`・`with` の `__enter__`・`__exit__`・`@property` の getter・木内デコレータの wrapper）も同じ仲間です。

（出典: `evidence/population_v4/v4_judgments.json` の `v3` の R16（`tools/coupon.py:330` と `auth/session.py:741-765` から `auth/browser_refresh.py` までの道筋）、`docs/open_questions.md:1194`（O43 のデコレータの行）、`:1110`（O42 の U16）、`:1167`（O42 の RC5））

#### 小さな例 2 — ライブラリからの呼び戻し（作例）

```python
# 説明用（作例。v4 の pronote-mcp を短くしたもの）
import somelib                                # 木の外のライブラリ

def my_login(session, url, user, password):   # 木の中の関数
    session.post(url, data={"user": user, "pw": password})   # ← ログインの POST

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def get_homework() -> str:
    client = somelib.Client(URL, login=my_login)   # 関数を渡すだけ。呼ぶのはライブラリ
    return client.homework()
```

**一歩ずつ**:

- 2 行目: `somelib` は木の外のライブラリです。解析器は、木の外のライブラリの中身を読みません。
- 4〜5 行目: `my_login` は木の中の関数で、ログインのための `POST` を送ります。
- 9 行目: ツールの本体は、`my_login` を**呼ばずに**、ライブラリに渡しているだけです。ライブラリが、後で `my_login` を呼び戻します。このような関数を**コールバック**（呼び戻される関数）と言います。
- 10 行目: ライブラリの関数で宿題を取り出します。

解析器は、本体から `my_login` への呼び出しを見つけられません。
本体の中には `my_login(...)` という呼び出しが書かれていないからです。
だから 5 行目の `POST` は、ツールの効果になりません。

v4 の pronote-mcp の `pronote_get_homework`（R25）がこの形でした。
判定では「不明」になりました。
D1 の判定表では、`POST` は「不」（相手を変えるかは、相手のサーバの意味による）です（[第 17 章](ch17.md)）。
つまり、表どおりなら解析器は不を出すべきでした。
出していないので、**不の件数が 1 つ少ない**ことになります。
これは「見落とし」とは少し違います。
本当の違反があったと確かめられたわけではなく、「決められないもの」の印が欠けた、という形です。

（出典: `evidence/population_v4/v4_judgments.json` の `v3` の R25、`docs/open_questions.md:1195`（O43 の呼び戻しの行）、`docs/population_v4.md:109-110`）

#### 小さな例 3 — モジュール水準のインスタンス（作例）

```python
# 説明用（作例。v4 の jahrik/mcp-servers を短くしたもの）
# utils.py
lsp_client = None                             # モジュール水準の変数

def setup():
    global lsp_client
    lsp_client = LSPClient(...)               # 起動時にインスタンスを入れる

# tools.py
import utils

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def lsp_document_highlight(path: str) -> str:
    return utils.lsp_client.send_request("highlight", path)   # 受け手の型が分からない
```

**一歩ずつ**:

- 3 行目: `utils.py` のモジュールの一番上で、`lsp_client` を `None` にしています。
- 5〜7 行目: 起動時に `setup()` が呼ばれると、`lsp_client` に `LSPClient` のインスタンスが入ります。
- 13〜14 行目: ツールの本体は `utils.lsp_client.send_request(...)` を呼びます。

解析器は、`utils.lsp_client` の中身が `LSPClient` のインスタンスだと分かりません。
モジュール水準の変数に、別の場所で後から入れた値の型を追い切れないからです（[第 15 章](ch15.md)の「受け手の型」）。
だから `send_request` がどのクラスのメソッドか解けず、その中を読みません。

v4 の jahrik/mcp-servers の `lsp_document_highlight`（R11）がこの形でした。
実際の `send_request` の先では、言語サーバ（プログラムの解析をする別のプログラム）を子プロセスとして起動し、その標準入力に要求を書いていました。
起動するコマンドは定数なので、判定表では SPAWN は「不」です。
つまり、解析器は本来「不」を出すべきでしたが、それも出していません。
そして、言語サーバが実際に何かを変えるかは、子プロセスの動作によるので、静的には決められません。
だから判定は「**不明**」でした。

O43 は、この形を「O42 の U40 の『モジュール水準のインスタンスのメソッド』と同じ」と書いています。

（出典: `evidence/population_v4/v4_judgments.json` の `v3` の R11、`docs/open_questions.md:1196`（O43 のモジュール水準のインスタンスの行）、`:1168`（O42 の U40 の数え落としの行））

#### ほかの 2 つの形

- **関数が返すモジュール**（O41）: `_, m = _load_backend(); m.f()` のように、関数がモジュールを返し、そのモジュールの関数を呼ぶ形です。解析器は `m` がどのモジュールか解決しません。v3 の見落とし 1 件がこの形でした（誤 clear）。
- **原因の分からない見落とし**（O38）: tg-note の `convert_document_from_content` で、`finally` 節の `tmp_path.unlink()` が効果に出ていません。`pathlib.Path.unlink` は sink の表にあります。出ない理由は**不明**のままです（受け手の型が `Path` に解決されていない可能性がある、とだけ書かれています）。原因が分からないものを、分からないまま記録しているのは、CLAUDE.md の規則 4 に従っているからです。

（出典: `docs/open_questions.md:1064`（O41 の関数が返すモジュール）、`:1035-1037`（O38 の tg-note））

#### なぜ直さないのか

どの形も、直すには解析器の「呼び出しのたどり方」そのものを広げる必要があります。

- デコレータの wrapper をたどるには、任意のデコレータが何を返すかを読む必要があります。O42 の RC5 は「任意のデコレータで置き換わる def を def として解く」近似を、そのまま限界として残しました。
- ライブラリからの呼び戻しをたどるには、木の外のライブラリの中を読む必要があります。静的解析では、解析する木の外は読みません。
- モジュール水準のインスタンスを解くには、「起動時にどの値が入り、その後に書き換えられないか」を確かめる必要があります。これは 42.6 節の lifespan と同じ種類の難しさで、うかつに解くと誤 clear を作ります。

しかも、v4 の形は凍結の後に見つけたものです。
凍結した後は、結果を見て解析器を変えません（D66）。

（出典: `docs/open_questions.md:1167`（O42 の RC5）、`docs/decisions.md:3748-3754`（D66 の規則））

#### よくある誤解・つまずき

- **誤解: 「デコレータの件は深さの問題だ」**
  texas-grocery の件は、wrapper から 2〜3 段で、深さ 4 の中に収まっていました。深さを上げても見えません。原因は「wrapper をたどらない」ことです。
- **誤解: 「呼び戻しの件は見落としだ」**
  pronote の件は、判定では「不明」です。本当の違反だと確かめられたわけではありません。欠けていたのは「不」の印で、限界の向きは「不が 1 つ少ない」です。
- **つまずき: 「解析器が何も出していない = 安全」と読む**
  この節の 3 つの形は、どれも解析器が何も出していないツールです。何も出していないことは「問題なし」の証明ではありません。だから見落としの判定（200 件）があります。

#### 手作業ではどう使うか

見落としの判定では、ツールの本体だけでなく、次の 3 か所も必ず見ます。

1. **ツールの関数に付いているデコレータ**（`@mcp.tool` 以外のもの）。木の中で定義されたデコレータなら、その wrapper の中を読みます。wrapper の中の書き込みも、ツールの呼び出しで起きます。
2. **ライブラリに渡している関数**（引数に関数の名前だけを渡している所）。その関数が木の中にあれば、中を読みます。
3. **モジュール水準の変数を経由する呼び出し**（`utils.xxx.method(...)` のような形）。その変数に何が入るかを、木の中を検索して確かめます。

見落としの原因の分類は、次のように付けます（第 41・52 章）。

| 形 | 見落としの原因 |
|---|---|
| デコレータの wrapper | その他（v4 の R16 と同じ） |
| ライブラリからの呼び戻し | 呼び出しの解決（違反が確かめられないなら判定は不明） |
| モジュール水準のインスタンス | 受け手の型（違反が確かめられないなら判定は不明） |
| 関数が返すモジュール | 呼び出しの解決 |

表の読み方: 1 行が 1 つの形です。
たとえば 3 行目は「モジュール水準のインスタンスを経由する呼び出しの先に違反があり、解析器が何も出していなかったら、見落としの原因は『受け手の型』と書く。ただし、違反かどうか決められなければ、判定そのものは『不明』にする」と読みます。

#### この節のまとめ

解析器は本体から書かれた呼び出しをたどるので、デコレータの wrapper、ライブラリからの呼び戻し、モジュール水準のインスタンス、関数が返すモジュールは見えない。原因の分からない見落とし（O38）も、不明のまま記録してある。
見落としの判定では、デコレータ・渡した関数・モジュール水準の変数を必ず見る。

### 42.6 余計に出すもの (1) — 起動時の初期化（設計の選択による限界）

#### 一言で言うと

サーバには、起動時に一度だけ走る初期化があります。
その初期化の中の書き込みを、解析器は「ツールの呼び出しで起きる」ものとして矛にすることがあります。
本当は起動時に済んでいて、ツールの呼び出しでは起きないなら、それは誤警報です。
v4 の誤の大半（14 件中 9 件）がこの形でした。
最終評価では、初期化が**どこで**済むかで判定が分かれます（D67 の 2）。
特に **lifespan の形の誤警報は、解析器の設計の選択から来る限界**で、直さずに残し、件数を報告します。

#### たとえ話 — お店の開店準備

あるお店では、毎朝の開店前に、店長がレジに釣り銭を入れます。
レジの係の人の手順書には「レジにお金が無ければ、金庫から釣り銭を入れる」と書いてあります。

この手順書だけを読んだ人は、「係の人は、お客さんが来るたびに金庫を開けるかもしれない」と考えます。
けれども実際には、開店前に店長が必ず釣り銭を入れているので、営業中に係の人が金庫を開けることはありません。

ただし、それが本当かどうかは「店長が**必ず**開店前に釣り銭を入れるか」によります。

- 開店前の準備が、店の決まりで**必ず行われる**なら（どの店員が鍵を開けても、開店の前に必ず済む）、営業中に金庫は開きません。これが lifespan の形です。
- 開店前の準備が「**店長が自分で店を開けた日だけ**」行われるなら、別の人が店を開けた日は、営業中に金庫が開くかもしれません。これが `main()` の形です。

解析器は「手順書」だけを読む人にあたります。
開店前の準備のことは考えずに、営業中の手順だけを、毎回それぞれ独立に読みます。

#### 小さな例 — 2 つの形（作例）

v4 の ccr と shyhurricane を短くした作例です。

**形 1: `main()` の中で先に初期化する（ccr に似た形）**

```python
# 説明用（作例）
mcp = FastMCP("demo")
_memory = None

def _init(project):
    global _memory
    os.makedirs(".ccr", exist_ok=True)   # ← 効果（ディレクトリの作成）
    _memory = Memory(project)

def _ensure_memory():
    if _memory is None:                  # まだ初期化していなければ
        _init(None)                      # ここで初期化する
    return _memory

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def recall(query: str) -> str:
    return _ensure_memory().search(query)

def main():
    _init(args.project)                  # mcp.run の前に初期化を済ませる
    mcp.run()

if __name__ == "__main__":
    main()
```

**形 2: lifespan の中で先に初期化する（shyhurricane に似た形）**

```python
# 説明用（作例）
_ctx = None

async def get_context():
    global _ctx
    if _ctx is not None:                 # すでにあれば
        return _ctx                      # それを返す
    os.makedirs(CACHE_PATH, exist_ok=True)   # ← 効果（キャッシュのディレクトリの作成）
    _ctx = Context(CACHE_PATH)
    return _ctx

@asynccontextmanager
async def app_lifespan(server):
    await get_context()                  # 起動時に必ず初期化する
    yield

mcp = FastMCP("demo", lifespan=app_lifespan)

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
async def find_urls(q: str) -> str:
    ctx = await get_context()            # ツールでは、もうできたものを受け取るだけ
    return ctx.find(q)
```

#### 一歩ずつの説明 — 形 1

- 2 行目: モジュールの一番上で、サーバの本体 `mcp` を作っています。
- 3 行目: `_memory` は、まだ初期化していないことを表す `None` で始まります。
- 5〜8 行目: `_init` は初期化の関数です。7 行目でディレクトリを作ります（効果）。8 行目で `_memory` に値を入れます。
- 10〜13 行目: `_ensure_memory` は、`_memory` が `None` なら `_init` を呼ぶ「一度だけ初期化する」形です。
- 15〜17 行目: ツール `recall` は `readOnlyHint=True`（D1）と宣言しています。本体は `_ensure_memory()` を呼びます。
- 19〜21 行目: `main()` は、`mcp.run()`（ツールの受付を始める）の**前に** `_init` を呼びます。
- 23〜24 行目: このファイルを直接実行したときだけ `main()` が走ります。

解析器は、ツールの本体 → `_ensure_memory` → `_init` → `os.makedirs` という道筋を見つけ、D1 の矛を出します。
`main()` が先に `_init` を済ませていることは考えません。

#### 一歩ずつの説明 — 形 2

- 2 行目: `_ctx` は `None` で始まります。
- 4〜10 行目: `get_context` は、`_ctx` がすでにあればそれを返し（6〜7 行目）、無ければディレクトリを作って（8 行目、効果）、`_ctx` に値を入れます。
- 12〜15 行目: `app_lifespan` は **lifespan** です。lifespan とは、サーバの起動時に 1 回だけ走る関数のことで、`yield` より前が起動時の処理、後が終了時の処理です（[第 3 章](ch03.md)）。ここでは起動時に `get_context()` を呼びます。
- 17 行目: `FastMCP(..., lifespan=app_lifespan)` で、サーバに lifespan を登録しています。
- 19〜22 行目: ツール `find_urls` も D1 と宣言しています。本体は `get_context()` を呼びますが、起動時にもう `_ctx` ができているので、7 行目で返るだけです。

解析器は、ツールの本体 → `get_context` → `os.makedirs` という道筋を見つけ、D1 の矛を出します。
lifespan が先に初期化を済ませていることは考えません。

#### 最終評価の判定の決まり（D67 の 2）

最終評価では、「その初期化がツールの受付より前に**必ず**済んでいるか」で決めます。
起動の方法は、コードだけから決めます。

| 初期化を先に済ませている場所 | 判定 | 理由 |
|---|---|---|
| `main()` の中だけ、または `if __name__ == "__main__":` の中だけ（形 1） | **到達する（正になりうる）** | モジュールの一番上の `mcp = FastMCP(...)` は、`fastmcp run file.py:mcp` などで `main()` を通らずに起動できる。そのときは最初のツールの呼び出しで初期化が走る |
| lifespan の中（形 2） | **到達しない（誤、E1）** | どの起動方法でも、ツールの受付より前に必ず走る |
| モジュールの読み込み時（モジュールの一番上の文） | **到達しない（誤、E1）** | import した時点で走る |
| どこで先に済ませるか読み切れない | **不明** | |

表の読み方: 1 行が 1 つの場所です。
たとえば 1 行目は「初期化が `main()` の中だけにあるなら、`main()` を通らない起動のしかたがありうるので、ツールの呼び出しで初期化が走りうる。だから到達する、とする。この読み方は、原理 3（できることの上界で考える）と同じ」と読みます。
2 行目は「lifespan の中なら、どう起動してもツールの受付より前に必ず走るので、ツールの呼び出しでは到達しない。判定は誤で、誤の原因は E1」と読みます。

この決まりで、v4 の 2 つの木は次のようになります。

- **ccr**（形 1）: `main()` で初期化しているので、到達する。到達の理由では誤になりません（宣言に反するかは別に見ます。たとえば v4 の E00 は、冪等な追記なので E8 で誤になります）。
- **shyhurricane**（形 2）: lifespan とサービスの起動時に初期化しているので、到達しない。誤（E1）。

解析器に**有利な側**（ccr）と**不利な側**（shyhurricane）の両方が残ります。
O43 は、この決まりが「解析器に都合のよいルール」だと見られないように、事前登録に 2 点を書くとしています。
決まりは原理 3 から導いたこと、そして解析器に不利な側（lifespan の形）も誤として残ること、です。

（出典: `docs/decisions.md:3773-3778`（D67 の 2）、`docs/open_questions.md:1199-1217`（O43 の起動時の初期化の整理）、`docs/drafts/final_judging_guide_draft.md:267-300`（14.4 節）、`evidence/population_v4/v4_judgments.json` の `v2` の M01・M07・M08・E00）

#### v4 での件数

#### なぜ解析器を直さないのか — 4 つの条件

「lifespan の形を正しく扱えば、誤警報が減るのに、なぜ直さないのか」と思うかもしれません。
理由は 2 つあります。

**理由 1: 正しく扱うには、4 つの条件をすべて確かめる必要があり、1 つでも外すと誤 clear を作るからです。**

lifespan の形で「ツールの呼び出しでは初期化の効果は起きない」と言い切るには、次の 4 つが全部そろっていなければなりません。

| 条件 | 中身 | 外したときに何が起きるか（作例） |
|---|---|---|
| **順序** | lifespan がツールより先に走る | lifespan を登録していない別の起動口があれば、ツールの呼び出しで初期化が走る |
| **状態** | 大域変数に値が入る | lifespan の中で値を入れる先が別の変数なら、ツールの側では `None` のまま |
| **戻らない** | 別の場所で `None` に戻されない | あるツールが `_ctx = None` に戻すと、次の呼び出しで初期化が再び走る |
| **失敗しない** | lifespan が失敗して、値が入らないまま受付が始まることがない | lifespan の中で例外を握りつぶすと、値が `None` のまま受付が始まる |

表の読み方: 1 行が 1 つの条件です。
たとえば 3 行目は「解析器が lifespan の形を『到達しない』と読むなら、どこかで `None` に戻す書き方が無いことも確かめなければならない。それを確かめずに『到達しない』とすると、実際には戻された後の呼び出しで書き込みが起きるのに、解析器は何も出さない。つまり誤 clear になる」と読みます。

これは、CLAUDE.md の落とし穴に書かれている D17 改訂 2 と同じ危険です。
D17 では、モジュール水準の束縛を「解決できた」と読む変更が、`global` による再束縛や、同じ関数での書き込みの読み戻しを見落として、誤 clear を作っていました。
「解決できた（resolved）」にしてよい根拠を 1 つでも確かめ損ねると、本当の違反が黙って消えます。
誤警報を減らすつもりの変更が、もっと見つけにくい誤 clear を生むのです。

**理由 2: v4 の結果を見て気づいた変更だからです。**
v4 は「結果を見て解析器を変えない」と決めて行った中間検証でした（D66）。
v4 で lifespan の形の誤警報を見つけ、それに合わせて解析器を直すと、この約束を破ることになります。

（出典: `docs/open_questions.md:1207-1213`（4 つの条件と、解析器を変えない理由）、`CLAUDE.md` の「よく踏む落とし穴」（D17 改訂 2）、`docs/decisions.md:3743-3754`（D66））

#### 設計の選択としての限界 — 各呼び出しを独立に解析する

解析器は、**各ツールの呼び出しを、サーバの状態を何も仮定せずに、独立に解析します**。
「起動時に何が済んでいるか」「前の呼び出しで何が変わったか」は考えません。
これは、解析器の「できることの上界」（原理 3）を推定するための設計です。
サーバの状態を仮定しなければ、「状態によっては起きうる」書き込みを見落としません。
そのかわり、「実際には状態のせいで起きない」書き込みまで矛にしてしまいます。
lifespan の形の誤警報は、この設計の裏返しです。

だから論文では、lifespan の形の誤警報を「解析器のバグ」ではなく、「**各呼び出しをサーバの状態を仮定せずに独立に解析する設計の限界（誤警報の向き）**」として書きます。
D67 の 2 は、「lifespan の形の誤りは設計の選択による限界（誤警報の向き）として件数を報告する。判定の手引きの誤の原因の欄に、この類を設ける」と決めました。
その欄が **E1** です。
E1 が直されずに残り、件数として報告されるのは、このためです。

（出典: `docs/decisions.md:3777-3778`（D67 の 2 の最後の項目）、`docs/open_questions.md:1213`、`docs/final_evaluation_procedure.md:1413`（24.2 節の lifespan の項目））

#### よくある誤解・つまずき

- **誤解: 「`main()` の形も lifespan の形も、起動時に初期化しているのだから同じ扱いにすべきだ」**
  違います。`main()` の形は、`main()` を通らない起動（`fastmcp run file.py:mcp`）がありうるので、ツールの呼び出しで初期化が走りえます。lifespan は、どの起動方法でも受付より前に必ず走ります。
- **誤解: 「ccr を正にするのは、解析器に都合のよい決め方だ」**
  決まりは原理 3（できることの上界）から導いたもので、解析器に不利な側（shyhurricane の誤）も同じ決まりで残ります。両方の側があることを論文に書きます。
- **誤解: 「E1 が多く出たら、解析器を直すべきだ」**
  最終評価では解析器を変えません。E1 は設計の限界として件数を報告します。
- **つまずき: lifespan を見つけたら、すぐに E1 にする**
  lifespan が初期化を**必ず**済ませるかを確かめます。条件つきなら、条件が偽のときはツールの呼び出しで届くので「到達する」です。後で `None` に戻す箇所があれば、それも「到達する」です（[第 49 章](ch49.md)）。

#### 手作業ではどう使うか

矛の道筋の途中に「一度だけ初期化する」形（`if _x is None:`、`@lru_cache`、`global _initialized`）があったら、次の順に確かめます。

1. `FastMCP(` や `Server(` の引数の `lifespan=` を探し、その関数の中で初期化を呼んでいるかを見る。
2. `main()` や `if __name__ == "__main__":` の中で初期化を呼んでいるかを見る。
3. 初期化の後に、値を `None` に戻す箇所が無いかを grep で確かめる。
4. lifespan が条件つきで初期化していないか、例外を握りつぶしていないかを見る。
5. 判定と記録: lifespan かモジュールの読み込み時で必ず済む → 誤、`error_class` は `E1: <どこで済むか>`。`main()` の中だけ → 到達する、`condition_type` は `起動の方法`。読み切れない → 不明、`unknown_reason` に理由。

（出典: `docs/drafts/final_judging_guide_draft.md:290-300`（14.4 節の見分け方）、`:251-260`（14.3 節の条件の種類の表））

#### この節のまとめ

解析器は各呼び出しをサーバの状態を仮定せずに独立に解析するので、起動時に済む初期化の中の書き込みも矛にする（誤警報）。最終評価では、`main()` の中だけなら到達する、lifespan とモジュールの読み込み時なら誤（E1）、読み切れなければ不明と決めた（D67 の 2）。
lifespan の形を解析器で正しく扱うには順序・状態・戻らない・失敗しないの 4 つを全部確かめる必要があり、1 つでも外すと誤 clear を作る。しかも v4 の結果を見て気づいた変更なので、直さずに設計の限界として件数を報告する。

### 42.7 余計に出すもの (2) — 決まった形の誤警報

#### 一言で言うと

起動時の初期化のほかにも、解析器が矛を出しすぎる「決まった形」が 6 つあります。
v3 の確認（O41）と v4 の中間検証（O43）で、同じ形が繰り返し見つかりました。
どれも「一般に正しい直し方が無い」か、「直そうとしたら誤 clear を作った」ので、直さずに残しています。
最終評価の判定では、これらは「誤」になり、誤の原因 **E2・E3・E5・E7・E8** として記録します。

#### たとえ話 — 慎重すぎる火災報知器

台所の火災報知器が、魚を焼いた煙でも鳴るとします。
「煙だけで鳴る」という作りなので、本物の火事の煙と、料理の煙を区別できません。
感度を下げれば料理では鳴らなくなりますが、本物の火事でも鳴るのが遅れるかもしれません。
だから「料理の煙でも鳴ることがある」と分かったうえで、感度はそのままにしておく。
この節の形は、この「慎重すぎる報知器」にあたります。

#### 小さな例 — 6 つの形と E の記号

| 形 | 解析器のふるまい | 本当は | 記録（v3・v4 の件数） | 判定での E |
|---|---|---|---|---|
| 自分で作った一時ファイル・ロックの後始末 | D2 の矛（破壊的な削除）にする | 呼び出しの前からあったものを消していないので、D2 には反しない | O41（v3 の誤 3）、O43（v4 の誤 2、ccr） | **E2** |
| 末尾名の解決 | 組み込みの `bytearray.append`・`set()` を、木の中の同名メソッドに結ぶ | 呼んでいるのは組み込みのメソッドで、書き込みは無い | O41（v3 の誤 2）、O43（v4 の誤 2、rails-lens） | **E3** |
| 子プロセスの標準入力 | 標準入力への書き込みを FS_WRITE の情報行にする | 子が受け取ったものでファイルを変えなければ、反しない | O41（v3 の誤 4、helm・kubectl）、O43（v4 の誤 1、ru-marketplace） | **E5** |
| `shlex.quote` の固定コマンド | モデルが決めるコマンドとみなす | コマンドは固定で、モデルは引用された値しか渡せない | O41（v3 の誤 2） | **E7** |
| `flock` のための `"a"` | 追記（D4 の矛）とみなす | ロックのために開くだけで、何も書かない | O41（v3 の D4 の誤 1） | **E8** |
| argv の分解 | 引数の要素のどこかに未検証のモデルの値があれば、フラグ混入の座標に数える | 先頭が定数の `--opt=` の要素なら、値は新しいオプションを作れない（ただし値そのものが危険なオプションもある） | O35（A2 の 7/8） | 誤警報の可能性（42.9 節） |

表の読み方: 1 行が 1 つの形です。
たとえば 2 行目は「解析器は、名前の末尾（`set` など）だけを手がかりに、組み込みの `set()` を木の中の `CacheManager.set` だと思い込むことがある。本当は組み込みのメソッドで書き込みは無いので、誤警報。v3 で 2 件、v4 で 2 件（rails-lens）見つかった。最終評価の判定では誤にし、原因は E3」と読みます。

（出典: `docs/open_questions.md:1059-1073`（O41）、`:1189-1191`（O43 の一時ファイル・`set()`・標準入力の行）、`:988-1004`（O35）、`docs/drafts/final_judging_guide_draft.md:428-445`（第 17 節の E1〜E9）、`docs/population_v3.md:85-88`）

#### コードで見る — E2・E3・E5・E7・E8（作例）

**E2: 自分で作った一時ファイルの後始末（D2）**

```python
# 説明用（作例）
@mcp.tool(annotations=ToolAnnotations(destructiveHint=False))
def convert(text: str) -> str:
    fd, tmp = tempfile.mkstemp()          # 新しい一時ファイルを作る
    with os.fdopen(fd, "w") as f:
        f.write(text)                     # 中身を書く
    out = run_converter(tmp)              # 別の関数に読ませる
    os.remove(tmp)                        # 自分が作った一時ファイルを消す
    return out
```

- 2 行目: このツールは D2（壊さない）と宣言しています。
- 4 行目: `tempfile.mkstemp()` は、まだ無い名前の一時ファイルを新しく作ります。
- 5〜6 行目: その一時ファイルに `text` を書きます。
- 7 行目: 別の関数に一時ファイルを読ませます。
- 8 行目: 最後に、同じ呼び出しの中で自分が作った一時ファイルを消します。

解析器は、8 行目の `os.remove` を「ファイルの削除」として、D2 の矛にします。
けれども D2 の問いは「**呼び出しの前からあったもの**を消すか」です（[第 50 章](ch50.md)）。
消したのは、この呼び出しで作ったものなので、D2 には反しません。
だから誤で、原因は E2 です。

ただし、**同じ形でも D1 なら反します**。
D1 の問いは「環境を変えるか」で、判定の手引きの下書きの 15.1 節は、一時ファイルの作成・削除も「反する」としています。
v4 の M58（ru-marketplace の `ozon_reviews`、D1）は、同じ呼び出しで `mkstemp` した一時ファイルの削除でしたが、正と判定されています。
また、**前の呼び出しが残したファイル**を消すなら、それは呼び出しの前からあったものなので、D2 にも反します（[第 43 章](ch43.md)の reaper-mcp の例）。

（出典: `docs/drafts/final_judging_guide_draft.md:348-350`（15.2 の迷いやすい形）、`:656`（M58 の考え方））

**E3: 末尾名の解決**

```python
# 説明用（作例。v4 の rails-lens を短くしたもの）
class CacheManager:
    def set(self, key, value):
        with open(self._path(key), "w") as f:    # キャッシュをファイルに書く
            f.write(value)

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def dependency_graph(root: str) -> str:
    visited: set[str] = set()                   # 組み込みの set() で空の集合を作るだけ
    return walk(root, visited)
```

- 2〜5 行目: 木の中に `CacheManager` というクラスがあり、その `set` メソッドはファイルに書きます。
- 7〜10 行目: ツールの本体は、9 行目で組み込みの `set()` を呼んで空の集合を作っているだけです。`CacheManager` は使っていません。

解析器は、名前の末尾が `set` という手がかりだけで、9 行目の `set()` を `CacheManager.set` に結びつけ、4 行目の書き込みをこのツールの効果にしました。
本当は組み込みの `set()` なので、書き込みはありません。
誤で、原因は E3 です。

D61 で、この形を直そうとしたことがあります（G2）。
けれども、「値の形（たとえば `bytearray` で作った値）を、型の証明として使う」直し方は、別の所で誤 clear を作りました。
だから取り消し、限界として残しました（[第 35 章](ch35.md)）。

（出典: `evidence/population_v4/v4_judgments.json` の `v2` の M04（`dependency_graph.py:183-248` と `cache/manager.py:90`）、`docs/open_questions.md:1071-1072`（O41 の末尾名の行と D61 G2 の取り消し））

**E5: 子プロセスの標準入力**

```python
# 説明用（作例。v4 の ru-marketplace を短くしたもの）
proc = subprocess.Popen([sys.executable, "-c", WORKER_CODE, out_path],
                        stdin=subprocess.PIPE)
proc.stdin.write(pickle.dumps(args))     # 子プロセスの標準入力にデータを流す
```

- 2〜3 行目: Python の子プロセスを起動し、その標準入力をパイプにつなぎます。
- 4 行目: 子プロセスの標準入力に、データ（pickle で固めた引数）を流し込みます。

解析器は、4 行目の書き込みを、ファイルの書き込み（FS_WRITE）の情報行にして、D1 の矛を出しました。
けれども標準入力への書き込みは、それ自体ではファイルを変えません。
子プロセスがそれを受け取って何をするかで決まります。

D61 でこの形も直そうとしました（G1）。
けれども、解析器がインタプリタだと分からないコマンド（argv0）でも、`env python3` や `tee` のように、標準入力からコードを実行したりファイルに書いたりするものがあります。
だから「標準入力への書き込みは書き込み相当」と扱うのは、**保守的な上界として正しい**と判断し、取り消しました。

（出典: `evidence/population_v4/v4_judgments.json` の `v2` の M59、`docs/open_questions.md:1068-1070`（O41 の標準入力の行と D61 G1 の取り消し））

**E7: `shlex.quote` の固定コマンド**

```python
# 説明用（作例）
@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def git_log_by(author: str) -> str:
    cmd = f"git log --author {shlex.quote(author)}"
    return subprocess.run(cmd, shell=True, capture_output=True, text=True).stdout
```

- 4 行目: `shlex.quote(author)` は、`author` をシェルが 1 つの文字列としてしか読めないように引用符で包みます。だから、モデルが `author` に `; rm -rf ~` と書いても、それはただの名前として扱われます。
- 5 行目: シェルを通してコマンドを実行します。

解析器は、シェルの文字列にモデルの値が流れ込んでいるので、「モデルが決めるコマンド」とみなし、D1 の矛を出します。
けれども実際に走るコマンドは、いつも `git log` です。
モデルが決められるのは、引用された値だけです。
誤で、原因は E7（モデルが決められないのに、決められるとした）です。

ただし、走る `git log` そのものが環境を変えるかは別に考えます（定数のコマンドの SPAWN。判定の手引きの 15.1 節）。

**E8: `flock` のための `"a"`（D4）**

```python

@mcp.tool(annotations=ToolAnnotations(idempotentHint=True))
def sync_index() -> str:
    with open(LOCK_PATH, "a") as lf:          # 追記モードで開くが、何も書かない
```

- 2 行目: このツールは D4（同じ引数で繰り返しても追加の効果が無い）と宣言しています。
- 4 行目: ロック用のファイルを追記モード `"a"` で開きます。ファイルが無ければ作りますが、中身は書きません。
- 5 行目: そのファイルでロックを取ります。

解析器は、定数の `"a"` で開く `open` を、D4 の「追記」として矛にします。
けれども、何も書かないので、繰り返しても追記は重なりません。
誤で、原因は E8（宣言に反しない）です。
`rebuild_index()` の中身が D4 に反するかは、別の組として判定します。

#### O35 — argv の分解（未決のまま、限界として書く）

最後の形は、誤警報の「可能性」です。

```python
# A2 の修正後のコード（第 31 章）
repo.git.diff(f"--unified={context_lines}", target)
```

フラグ混入（CWE-88）の危険は、モデルが `-` で始まる**要素**を送り込んで、コマンドに新しいオプションとして読ませることにあります。
`f"--unified={x}"` のように、先頭が定数の `--opt=` になっている要素では、`x` はオプションの**値**にしかなりません。
新しいオプションは作れません。
けれども解析器は、argv の要素を 1 つのまとまりとして扱い、要素のどこかに検査されていないモデルの値があれば、フラグ混入の座標に数えます。
だから誤警報の可能性があります。

ただし、値の位置でも、オプションによっては値そのものが危険です（`--output=` や `--upload-pack=` など）。
だから「値の位置なら安全」とも言えません。
O35 は、A2 が落ちたのを見て思いついた分解なので、A2 で作って A2 で確かめても証拠にならない、としています。
凍結の後、母集団 v3 で事前登録して確かめる案と、採らずに限界に書く案が並び、**未決**のままです。
論文では、A2 の 7/8 と O35 を並べて限界に書きます（42.9 節、手順書 24.2 節）。

（出典: `docs/open_questions.md:988-1004`（O35）、`docs/final_evaluation_procedure.md:1415`（24.2 節の A2 の項目））

#### なぜ直さないのか — 「一般に正しい直し方」が無い

v3 の確認のとき、D61 は「検証データに合わせて直さない。一般に正しい直し方だけを入れる」と決めました（[第 35 章](ch35.md)）。
この節の形は、どれもその基準を通りませんでした。

- E2（一時ファイルの後始末）: MCP 仕様の「追加か破壊か」で読めば破壊的ではありません。けれども、それは採った原理（§6）の読み替えになるので、直しませんでした。
- E3（末尾名）と E5（標準入力）: 直そうとしたら、別の所で誤 clear を作ることが分かり、取り消しました。
- E7・E8: 「引用したから安全」「ロックだから書かない」を一般に判定するには、値の意味やファイルの使い方を読む必要があり、まれな形のために解析器を広げることになります。

そして v4 の形は凍結の後に見つけたので、D66 の規則で直しません。

（出典: `docs/open_questions.md:1061-1062`（O41 の一時ファイルの行）、`docs/decisions.md:3408`（D61 の見出し））

#### よくある誤解・つまずき

- **誤解: 「一時ファイルの削除はいつも E2 で誤だ」**
  E2 は D2 のときだけです。D1 では、一時ファイルの作成・削除も環境の変更として「反する」です。また、前の呼び出しが残したファイルを消すなら、D2 でも反します。
- **誤解: 「site 名のライブラリが違っていたら、E4 にする」**
  E4 は「受け手の型の読み違いで、**動作の種類（kind）まで違う**」ときだけです。sqlite3 を psycopg と表示していても、DB の書き込みであることが同じなら、判定には影響しません（`note` に書くだけ）。
- **つまずき: 標準入力の件を、子プロセスの中身を見ずに E5 にする**
  子プロセスが標準入力からコードを実行したり、ファイルに書いたりするなら、反することもあります。子が何をするかを確かめてから決めます。

（出典: `docs/drafts/final_judging_guide_draft.md:438`（E4 の行）、`:126`）

#### 手作業ではどう使うか

矛を判定して「違反でない」と分かったら、まずこの節の 6 つの形のどれかに当てはまるかを見ます。
当てはまれば、対応する E を `error_class` に書き、1 文の説明を添えます。

例: `E2: server.py:203 で mkstemp した一時ファイルを :233 で消すだけ。呼び出しの前からあったものではない（D2）`

当てはまらなければ、E4（kind まで違う読み違い）、E6（到達しない、E1 以外）、E9（その他）を考えます（[第 51 章](ch51.md)）。

#### この節のまとめ

起動時の初期化のほかに、自分で作った一時ファイルの後始末（E2、D2 だけ）、末尾名の解決（E3）、子プロセスの標準入力（E5）、`shlex.quote` の固定コマンド（E7）、`flock` の `"a"`（E8）の 5 つの決まった形の誤警報と、argv の分解（O35、未決）がある。
どれも一般に正しい直し方が無いか、直すと誤 clear を作るので、直さずに残した。判定では E の記号で記録し、その内訳が論文の限界の材料になる。

### 42.8 両方の向き — 添削で直さなかった 39 単位と、探索・時間の限界

#### 一言で言うと

最終凍結の前の添削（D64、[第 36 章](ch36.md)）で見つけた誤りのうち、**直さなかったものが 39 単位**あります（O42）。
向きは、混在 19、誤 clear 13、誤警報 5、数え落とし 2 です。
さらに、添削の探索は見つけ尽くしておらず、木ごとの時間上限による打ち切りはマシンの速さで変わります。

#### たとえ話 — 家の点検の報告書

家を売る前に、専門家に点検してもらったとします。
点検で見つかった不具合のうち、雨漏りなど重いものはいくつか直しました。
けれども全部は直せませんでした。
良い報告書には、次の 3 つが書いてあります。

- 見つかったけれど**直さなかった不具合**の一覧。
- 点検は**決めた時間で打ち切った**ので、見つかっていない不具合があるかもしれないこと。
- 点検の道具（たとえば湿気の測定器）は、**天気によって測れる範囲が変わる**こと。

O42 は、ちょうどこの報告書にあたります。

#### 小さな例 — 39 単位の内訳

| 向き | 単位の数 |
|---|---|
| 混在 | 19 |
| 誤 clear | 13 |
| 誤警報 | 5 |
| 数え落とし | 2 |
| **計** | **39** |

| 重大度 | 単位の数 |
|---|---|
| 高 | 7 |
| 中 | 22 |
| 低 | 10 |

表の読み方: 1 つ目の表は、直さなかった 39 単位を、その単位の代表の向きで分けたものです。
たとえば 2 行目は「39 単位のうち 13 単位は、主に誤 clear（本当の違反を見落とす）の向きの誤りだった」と読みます。
2 つ目の表は、添削のときに付けた重大度（結果にどれだけ効きそうかの見立て）で分けたものです。

この数は、O42 の表の 39 行を本書の執筆時に数え直して、O42 の本文の数と一致することを確かめました。

（出典: `docs/open_questions.md:1083`（向きと重大度の内訳）、`:1092-1134`（直さない 39 単位の表））

#### 一歩ずつの説明 — 39 はどこから来たか

1. 添削では、5 つの担当が解析器と道具を調べ、検証役が崩しに行って生き残った**所見が 150** ありました。
2. 所見を根本原因ごとに束ねると、**55 単位**になりました。
3. 学生は、段階 A の **12 単位**（最終評価の数字を直接狂わせるもの）と、段階 B の **4 単位**（U38・U40・U09・U23。新しいデータで特に出そうなもの）を直すと決めました。
4. 残りの **55 − 16 = 39 単位**が、直さなかった単位です。

39 単位のうち 7 単位（U01・U02・U03・U06・U12・U13・U26）は、段階 B の候補でしたが、学生が選びませんでした。
O42 は、「どれも重大度が高いか新しいデータで出うる書き方で、直し方も（条件つきで）ある。**直さなかったのは範囲の判断で、直せないからではない**」と書いています。
残りの 32 単位は、段階 C（既定で記録）です。

（出典: `docs/open_questions.md:1077-1080`（O42 の前書き）、`:1088-1089`（段階 B で選ばなかった 7 単位））

#### 1 つの単位を見る — 同じ関数の 2 度の登録（作例）

直した単位の中にも、限界が残っています。
段階 B の U40（呼び出し形の登録）の実装で残した限界 R7 を、作例で見てみます。

```python
# 説明用（作例）
def save(path: str, body: str) -> str:
    with open(path, "w") as f:
        f.write(body)
    return "ok"

mcp.tool(name="save", annotations=ToolAnnotations(destructiveHint=False))(save)
mcp.tool(name="save_preview", annotations=ToolAnnotations(readOnlyHint=True))(save)
```

- 2〜5 行目: `save` は、モデルが決めた `path` にファイルを書く関数です。
- 7 行目: `save` を、`save` という名前で、D2 の宣言を付けて登録します。
- 8 行目: 同じ `save` を、`save_preview` という名前で、**D1（読むだけ）**の宣言を付けて、もう一度登録します。

8 行目の `save_preview` は、読むだけと宣言しているのにファイルを書くので、D1 の違反です。
けれども解析器は、ユニット（解析の単位）を**関数ごと**に作るので、同じ関数の 2 度の登録を 1 つのユニットに畳み、2 つ目の宣言を捨てます。
だから `save_preview` の D1 の違反は見えません。
誤 clear です。

O42 は、この形を「ユニットは関数ごと（デコレータ 2 段重ねと同じ既存の設計）」として、直さない理由を書いています。

（出典: `docs/open_questions.md:1166`（U40 の R7）、`:1167`（U40 の RC5））

#### そのほかの限界の記録

O42 には、39 単位のほかに、次のものも限界として記録されています。

- **直した単位の中で、記録に回した所見 7 件**（付録の道具だけに効くもの、まれなもの、素朴に直すと反例があるもの）。
- **段階 A の修正の敵対的レビューで見つけた、差分の外の古い穴**（N10・N11・A1・A2 など）。このうち **N9 は凍結の前に直しました**（[第 36 章](ch36.md)）。
- **段階 B の実装で残した限界**（ループの中の登録を入口にしない、多重継承の読み、lifespan の種付けの条件など）。
- **3 巡目の差分には、別の敵対的レビューを通していない**（本記録者が読んだだけ）。

（出典: `docs/open_questions.md:1136-1148`（記録に回した所見）、`:1150-1159`（差分の外の穴）、`:1161-1178`（段階 B の限界））

#### 探索は尽きていない

O42 は、所見の件数を「探索の標本で、母集団での頻度の推定ではない」と書いています。
探索は 4 巡の上限を 5 巡目まで超えて止めたので、**見つけ尽くしてはいません**。
つまり、「150 所見・55 単位」は「解析器の誤りの全部」ではなく、「決めた範囲で探して見つかったもの」です。
最終評価の判定で、まだ記録されていない形に出会う可能性は十分にあります（42.11 節）。

（出典: `docs/open_questions.md:1086-1087`）

#### 木ごとの時間上限 — マシンの速さで変わる数え落とし

解析器には、1 つの木にかける時間の上限（tree budget、180 秒）があります。
上限を超えた木は、残りのユニットを打ち切ります。
打ち切られたユニットの矛は見えないので、誤 clear の向きの**数え落とし**です。

かかる時間は、マシンの速さで変わります。
D64 の記録では、同じコンテナでも、run23 で xagent・mcparmory に 179.1 秒・169.5 秒かかったのに、run24 では 89.9 秒・86.6 秒で、約半分でした。
つまり、同じ解析器・同じ木でも、遅いマシンでは打ち切られ、速いマシンでは打ち切られないことがあります。
v4（88 木）では打ち切りは 0 で、最長は 96.8 秒でした。

打ち切りは manifest に件数つきで残ります（黙って落としません）。
最終評価では、走査の後に manifest の `tree_budget` で打ち切りの件数を確かめ、打ち切った木と所要時間を報告します。
また、見落としの抜き取りの対象に、打ち切りの印（`truncated`）のあるユニットを**含めます**（D70 の 2）。
判定で解析器の打ち切りが原因と分かったものは、「不明（打ち切り）」に分けて数えます。
除いてしまうと、解析器が苦手な大きいツールが見落としの抜き取りから消え、見落としの率を低く見せる（誤 clear の向きを隠す）からです。

（出典: `docs/decisions.md:3700-3702`（run24 と run23 の時間）、`docs/population_v4.md:73-74`、`docs/drafts/prereg_2_12_draft.md:39-40`、`docs/decisions.md:3846-3848`（D70 の 2））

#### なぜ件数の補正をしないのか

O42 は、「誤 clear と数え落としの単位があるので、矛の件数は下の形の分だけ下限寄りになる」と書く一方で、「件数の補正はしない」とも書いています。
補正するには、それぞれの形が母集団にどれだけあるかを知る必要があります。
けれども、それは測っていません。
測っていない数で補正すると、根拠の無い数字を作ることになります（CLAUDE.md の規則 1）。
だから補正はせず、向きだけを書きます。

#### よくある誤解・つまずき

- **誤解: 「39 単位は、直せなかった欠陥だ」**
  7 単位は、直し方があったのに範囲の判断で直さなかったものです。直せる・直せないと、直した・直さないは別のことです。
- **誤解: 「打ち切りの件数が 0 なら、時間上限は関係ない」**
  そのマシンでは関係ありませんでした。最終評価のマシンでは変わりうるので、必ず manifest で確かめます。
- **つまずき: 打ち切りのあるユニットを見落としの抜き取りから外す**
  外しません（D70 の 2）。外すと見落としの率を低く見せます。

#### 手作業ではどう使うか

- 判定の前に、そのユニットの manifest の打ち切りの印（`cap_hits`、`truncated`）を見ます（手引きの手順 B）。
- 見落としの判定で、違反が見つからず、しかもユニットが打ち切られていたら、「反する動作は無い」とは言えないことがあります。打ち切りが原因で判定できないなら「不明（打ち切り）」です。
- 判定の途中で、O42 の単位に当たる形（例: 同じ関数の 2 度の登録）に気づいたら、`note` に「O42 の U40 R7 と同じ形」のように書いておくと、限界の節を書くときに件数を数えられます。

（出典: `docs/drafts/final_judging_guide_draft.md:108-114`（手順 B））

#### この節のまとめ

添削で直さなかった 39 単位（混在 19・誤 clear 13・誤警報 5・数え落とし 2）は O42 にあり、7 単位は範囲の判断で直さなかった。探索は見つけ尽くしておらず、件数の補正もしない。
木ごとの時間上限（180 秒）による打ち切りはマシンの速さで変わるので、最終評価では manifest で必ず確かめ、打ち切りのあるユニットも見落としの抜き取りに含める（D70 の 2）。

### 42.9 研究の設計からくる限界

#### 一言で言うと

解析器をどう直しても変わらない限界があります。
判定者の数、対象の選び方、枠の時期、数の性質（下限）、手続きの透明さ、そして A2 の 7/8 です。
これらは、研究の設計で選んだことの裏返しです。

#### たとえ話 — アンケート調査の但し書き

ある町でアンケートを取ったとします。
報告書の最後には、たいてい次のような但し書きがあります。

- 集計は 1 人で行い、別の人による確かめはしていない。
- 対象は、この町の、ある名簿に載っている人だけである。
- 名簿は 9 月 20 日の時点のもので、その後に引っ越してきた人は入っていない。
- 回答しなかった人の意見は数えていないので、ある意見の人の数は「少なくともこれだけ」である。

この但し書きは、調査の質が低いことを示すものではありません。
読み手が、結果をどこまで広げて読んでよいかを判断するための情報です。

#### (1) 判定者は 1 人 — κ は出せない

| 誰の判定か | 判定した人 | 原典 |
|---|---|---|
| v3 の判定 | 本記録者（AI）。原ソースの確認は木ごとに agent に分け、根拠を本記録者が見直した | `docs/population_v3.md:72-73` |
| v4 の判定 | 本記録者（AI）。原ソースの確認は木ごとに agent に分け、根拠を本記録者が見直した。**人は見直していない** | `docs/population_v4.md:15-16,68`、`docs/final_evaluation_procedure.md:250-251` |
| 最終評価の判定 | **学生 1 人**。AI（LLM）は、判定・原ソースを読む補助・記録のどれにも使わない | D67 の 4、D70 の 3 |

表の読み方: 1 行が 1 つの判定です。
たとえば 2 行目は「v4 の判定は本記録者（この repo で解析器を作ってきた AI）が行った。原ソースの確認は別の AI の実行（agent）に分けたが、人は見直していない。だから v4 の数字は論文に使わない（D66 の 5）」と読みます。

最終評価の判定者は学生 1 人です。
2 人目の判定者がいないので、2 人の判定が偶然を超えてどれだけ一致したかを表す **κ（カッパ）**（第 8・38 章）は出せません。
D67 の 4 は、「信頼性が下がることを認め、論文の限界に書く」「判定者間の一致（κ）に依存する主張はしない」と決めています。

その代わりに、次のことをします。

- **判定の根拠（ファイルと行）を全件残して公開する**。第三者が後から同じ行を開いて確かめられるようにする（手引きの手順 H の `evidence`）。
- **判定の手引きを先にコミットする**（封）。結果を見てから基準を変えていないことを示す。
- **1 人の中でのぶれを減らす工夫**をする。判定の順序を無作為にする、判定の途中で集計を見ない、1 日の件数に上限を決める、迷った件は翌日に見直す（手引きの第 21 節）。

2 人目の判定者と、判定し直し（判定の一貫性の確認）は、**保留**です（D70 の 8）。
2 人目を用意できるかもしれないが、まだ分からない、という状態です。
用意できたら、判定の一部を独立に判定してもらう案を、判定し直しより先に検討します。
用意できなければ、判定し直し（2 週間以上あけて 5〜10%）をするかを決めます。
**決める期限**は、データを見る前、遅くとも段階 6（抜き取りのコミット）の前です。
それより後に足すなら、事前登録に逸脱として書き、事後の分析として扱います。

（出典: `docs/decisions.md:3783-3788`（D67 の 4）、`:3849-3899`（D70 の 3）、`:3920-3926`（D70 の 8）、`docs/drafts/final_judging_guide_draft.md:666-699`（第 21 節）、`:169-196`（手順 H））

#### (2) 対象は Python の MCP サーバ、しかも宣言を持つものだけ

母集団は「宣言（MCP の ToolAnnotations）を持つ、公開の Python の MCP サーバ」です（D29）。
だから、結果は次の 2 つの意味で、範囲が限られます。

- **Python だけ**: TypeScript などで書かれた MCP サーバについては、何も言えません。解析器は Python の `ast` で読むので、ほかの言語は読めません。
- **宣言を持つものだけ**: 宣言を書くサーバは、丁寧に作られている可能性があります。選び方のせいで結果が偏ることを**選択効果**と呼びます（[第 25 章](ch25.md)）。結果は「宣言を持つサーバについて」の主張で、MCP サーバ全体には一般化しません。

（出典: `docs/decisions.md:589-596`（D29）、`:617-619`（選択効果を本文に書く）、`docs/population_v2.md:65-69`、`docs/final_evaluation_procedure.md:1416`）

#### (3) 枠は 2026-09-20 の列挙

最終評価は、2026-09-20 に列挙した枠（抽出スクリプトの母集団 3,764 repo）から、v2・v3・v4 の 300 件を除いた残りを全部走査します（D69 の 1）。
列挙はやり直しません。
列挙のスクリプトが repo に無く、手で回したためです。

だから、**2026-09-20 より後に作られたサーバは入りません**。
「時期が違っても同じ結果になるか」は言えません。
手順書は、これを「限界に書く」としています。
なお、枠の数には、文書の 3,827 と抽出スクリプトの 3,764 の食い違いがあります（O40）。差の 63 件のうち 4 件は説明がつきますが、残りの 59 件の原因は不明のままです。
報告する枠の大きさは、抽出に実際に使った 3,764 が正しい可能性が高い、とされています。

（出典: `docs/final_evaluation_procedure.md:204`（0-6 の弱み）、`docs/decisions.md:3822-3824`（D69 の 1）、`docs/open_questions.md:1051-1057`（O40））

#### (4) 木の割合は下限

最終評価の主な数（違反のある木の割合 (a)(c) と参考の (b)）は、どれも**下限**です（[第 39 章](ch39.md)）。
「少なくともこれだけの木に違反があった」と書きます。
事前登録の下書きは、理由を 2 つ挙げています。

- 1 木 3 件までしか判定しない（判定しなかった件に違反があっても数えていない）。
- 矛の出なかった木の見落としを数えていない。

[第 39 章](ch39.md)で見たとおり、さらに語彙の外（O39）のように、向きの分かった見落としの原因もあります。
論文の例は「宣言したサーバのうち、少なくとも約 X%」です（D70 の 4）。

### 42.11 判定の途中で、新しい限界を見つけたら

#### 一言で言うと

最終評価の判定の途中で、この章のどの行にも当てはまらない解析器の誤りや見落としに出会うことがあります。

#### たとえ話 — 試験の採点中に、問題の誤りに気づいたら

試験の採点の途中で、ある問題の文に誤りがあることに気づいたとします。
採点の途中で問題を書き換えると、前に採点した答案と後の答案で基準が変わってしまいます。

**演習 42-2**（起動時の初期化を判定する）: 次の作例のコードについて、ツール `read_notes` の `os.makedirs` × D1 の組を判定してください。到達するか、判定（正・誤・不明）、誤なら E の記号、正なら `condition_type` を書き、理由を 2〜3 文で説明してください。さらに、`main()` を消して、代わりに lifespan の中で `_setup()` を呼ぶように書き換えたら、判定はどう変わるかも答えてください。

```python
# 説明用（作例）
mcp = FastMCP("notes")
_store = None

def _setup():
    global _store
    os.makedirs(NOTES_DIR, exist_ok=True)
    _store = Store(NOTES_DIR)

def _get_store():
    if _store is None:
        _setup()
    return _store

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))

    return _get_store().read_all()

def main():
    _setup()
    mcp.run()

if __name__ == "__main__":
    main()
```
