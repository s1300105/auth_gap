## 前の分冊から持ってくる知識

この分冊は、矛の 1 件の判定（手引き 11〜17 節）を読み終えた人を前提にします。次の 6 つを使います。どの分冊で読んだかは [付録 H の表紙](appendix-h.md) で確かめてください。教科書の本文では括弧の中の章です。

1. **組**と**ユニット**（手引き 11.1 節。[第 48 章](ch48.md)）: 判定の単位は (木, ユニット, site, kind, 宣言) の組。ユニットは 1 つのツールの関数です。
2. **手順 B〜D**（手引き 13 節。[第 48 章](ch48.md)）: 解析器の言い分を出し（B）、効果の行を開き（C）、ツールの入口から効果まで自分でたどる（D）。
3. **到達するか**と**条件の種類**（手引き 14 節。[第 49 章](ch49.md)）: 「ツールが呼ばれたとき、その効果が起きる実行の道が 1 つでもあるか」。条件は `なし` / `引数` / `初回` / `失敗・期限切れ` / `外部の状態` / `運用者の設定` / `起動の方法` の 7 つ。
4. **宣言に反するか**（手引き 15 節。[第 50 章](ch50.md)）: D1（`readOnlyHint: true`）は「呼び出しの後に残る何かを変えるか」、D2（`destructiveHint: false`）は「呼び出しの前からあったものを消す・上書きする・変えるか」。
5. **書き込み先の種類**（手引き 16 節。[第 51 章](ch51.md)）: 上から順に当てる 8 つの種類（相手側の状態 / データベース / 利用者のファイル / ログ / 一時ファイル / キャッシュ・状態の保存 / プロセスの起動・コードの実行 / その他・不明）。
6. **手順 H の欄**と **AI の使い方**（手引き 13 節の手順 H、21 節の 6。[第 48 章](ch48.md)・[第 52 章](ch52.md#s52-14)）: `evidence` は第三者が同じ結論に着けるように書く。AI（LLM）には事実だけを聞き、宣言の値・解析器の答え・自分の結論を渡さない。`ai_used`・`ai_model`・`ai_log` を書く（D70 の 3、`docs/decisions.md:3849-3869`）。

## この分冊で使う作った例 — 天気を返すサーバ

この分冊では、1 つの作った例を 18.2 の手順 1〜7 の最後まで持ち歩きます。手順 1〜3 では、**解析器の出力を見ずに**コードだけを読みます。だから、この節でもコードだけを示し、解析器の出力は手順 4（[H-6.6](#ah-6-6)）まで見せません。手引きの順序を、読み本の順序でもなぞるためです。

（作った例）木 `weather-mcp`。ファイルは 3 つです。左の数字は行番号です（写して使うときは消してください）。

`server.py`:

```
 1  from mcp.server.fastmcp import FastMCP
 2  from mcp.types import ToolAnnotations
 3
 4  from weather import client, history
 5
 6  mcp = FastMCP("weather")
 7
 8
 9  @mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
10  def weather_report(city: str) -> str:
11      """Return a short weather report for a city."""
12      data = client.fetch(city)
13      return client.format_report(data)
14
15
16  @mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
17  def last_weather(city: str) -> str:
18      """Return the last report remembered for a city."""
19      entry = history.recent(city)
20      return "none" if entry is None else client.format_report(entry["data"])
21
22
23  if __name__ == "__main__":
24      mcp.run()
```

`weather/client.py`:

```
 1  import requests
 2
 3  from weather import history
 4
 5  API = "https://api.weather.example/v1"
 6
 7
 8  def fetch(city):
 9      data = _download(city)
10      history.remember(city, data)
11      return data
12
13
14  def _download(city):
15      r = requests.get(API + "/current", params={"q": city}, timeout=10)
16      return r.json()
17
18
19  def format_report(data):
20      return f"{data['name']}: {data['temp']} C"
```

`weather/history.py`:

```
 1  import os
 2  import shelve
 3  import time
 4
 5  HISTORY_PATH = os.path.expanduser("~/.weather_history")
 6
 7
 8  def remember(city, data):
 9      entry = {"city": city, "data": data, "at": time.time()}
10      _save(city, entry)
11
12
13  def _save(city, entry):
14      key = _normalize(city)
15      _write(key, entry)
16
17
18  def _normalize(city):
19      return city.strip().lower()
20
21
22  def _write(key, entry):
23      with shelve.open(HISTORY_PATH) as db:
24          db[key] = entry
25
26
27  def recent(city):
28      with shelve.open(HISTORY_PATH, flag="r") as db:
29          return db.get(_normalize(city))
```

（`weather/__init__.py` は空のファイルです。）

コードの要点だけ先に書きます。

- `server.py` の 9〜10 行: ツール `weather_report` は `readOnlyHint=True`、つまり **D1** を明示しています。
- `server.py` の 16〜17 行: ツール `last_weather` も D1 を明示しています。
- `weather/history.py` の 23〜24 行: `shelve` は Python の標準ライブラリで、辞書のように読み書きできるファイル（小さなデータベース）を作ります。`shelve.open(パス)` は、何も指定しないと「読み書きで開き、無ければ作る」モードで開きます。24 行の `db[key] = entry` で、そのファイルに 1 件を書き込みます。
- `weather/history.py` の 28 行: `flag="r"` は「読み取り専用で開く」指定です。

この例の木は repo には置いていません。2026-10-04 に、この分冊を書くために、`analyzer-freeze-3` と同じ `authgap/`（`git diff analyzer-freeze-3 HEAD -- authgap/` が空であることを確かめた）で `python -m authgap scan <木> --population mcp_server` を走らせました。写して同じように走らせれば、手順 4 で示す出力を自分で確かめられます。

[H-6.7](#ah-6-7) では、この例を少しずつ変えた 4 つの**変種**（作った例）も使います。変えるのは `weather/history.py` の `_write` の中身だけです。

| 変種 | `_write` の中身 | 何を見せるための例か |
|---|---|---|
| 元の例 | `shelve` で手元のファイルに書く | 見落とし |
| 変種 POST | 履歴のサービスに `requests.post` で送る | 解析器が不として出している（と、18A の不の中身） |
| 変種 深い | もう 1 段奥の `_persist` を呼び、そこで `open(..., "w")` で書く | 見落とし（深さ 4 の外） |
| 変種 コールバック | 木の外のライブラリ `skyrecorder` に渡し、ライブラリが木の中の `_flush` を呼び戻すかもしれない | 不明 |

表の読み方: 1 行が 1 つの例です。たとえば 3 行目は「変種 深い は、書き込みが 1 段奥（深さ 5）にあるので、決まりどおり深さ 4 まで読めば見えず、偶然見つけたときだけ『見落とし（深さ 4 の外）』になる」と読みます。`last_weather` は、元の例のものを「反する動作は無い」の例に使います（変種では `recent` の中身も変わりますが、変種の `last_weather` は使いません）。

### H-6.1 18 節の見出しと 18.1 何を判定するのか（手引き L470-475）

> 【原文 L470】
> ## 18. 見落としの 1 件を判定する手順

> 【原文 L472-475】
> ### 18.1 何を判定するのか
>
> 対象は「D1 か D2 を明示していて、その宣言への矛が 1 件も出ていないツール」。
> **解析器が「違反なし」としたツールに、本当に違反が無いか**を確かめる。

**一言で言うと**: 見落としの判定は、解析器が「この宣言には反していない」と黙ったツールを人が読み直して、本当に黙ってよかったかを確かめる作業です。対象は、D1 か D2 を明示していて、その宣言への矛が 1 件も出ていないツールです。

**ことばの確認**:

- **見落とし**: 解析器が、宣言に反する動作を見逃すことです。研究の言葉では**誤 clear**（false-clean。本当は違反があるのに「違反なし」と出す誤り）と言います。逆向きの誤り（違反でないものを矛と出す）は誤警報で、こちらは矛の判定（手引き 11〜17 節）で測ります。
- **ツール**と**ユニット**: ツールは AI が呼べる 1 つの機能で、コードでは `@mcp.tool(...)` を付けた関数です。解析器はこれをユニットと呼び、1 つずつ解析します（[第 48 章](ch48.md)）。
- **明示**: 作者がコードに宣言を**書いた**ことです。書かれていない宣言を MCP の既定値で補ったものは含みません。解析器の manifest（ユニットごとの解析結果を書いた JSON のファイル）では `D_kind.explicit` の欄に出ます（[第 52 章 52.2 節](ch52.md#s52-3)）。
- **矛**: 解析器が「宣言に反する」と出した効果です。行の注記に `contradiction:<宣言>` と付きます。
- **その宣言への矛**: D1 を見るなら D1 の矛だけを見ます。D4 の矛が出ていても、D1 の矛が無ければ、D1 の見落としの対象になります。

**1 文ずつ読む**:

1. 「18. 見落としの 1 件を判定する手順」: 18 節は、見落としを 1 件判定する手順を書いた節です。11〜17 節が「解析器が矛と出したもの」を確かめる手順だったのに対し、18 節は「解析器が何も出さなかったもの」を確かめる手順です。
2. 「18.1 何を判定するのか」: 小見出しです。
3. 「対象は『D1 か D2 を明示していて、その宣言への矛が 1 件も出ていないツール』。」: 対象を 3 つの条件で絞っています。(1) 宣言が D1 か D2 であること（D3・D4 は見落としの判定をしない）。(2) その宣言を作者が書いていること（明示）。(3) その宣言への矛が 1 件も無いこと。
4. 「**解析器が『違反なし』としたツールに、本当に違反が無いか**を確かめる。」: 目的です。解析器の「黙っている」という答えが正しかったかを測ります。

**なぜこう決めたのか**:

- 見落としを測る理由: 解析器の答えは 3 つ（矛 / 不 / 何も出さない）あり、それぞれがどれだけ当たっていたかを示すためです。D69 の 4 の理由に「精度・見落とし・不の中身がそろえば、解析器の 3 つの答えのそれぞれがどれだけ当たっていたかを示せる」とあります（`docs/decisions.md:3830`）。規模は 200 件、1 木 1 件です（D69 の 3、`docs/decisions.md:3827`）。
- D1・D2 だけにする理由: 手引きには理由が書かれていません。手順書の 0-3 も対象を「D1 か D2 を明示し、その宣言に対する矛が 1 件も出ていないユニット（v4 の V3 と同じ）」とだけ書いています（`docs/final_evaluation_procedure.md:167`）。本書の読み: v3・v4 の見落としの判定と同じ範囲にそろえたものです。D3・D4 は D62（2026-09-28）で主指標になりましたが、見落としの対象は v3 以来の D1・D2 のまま残っています。
- 「その宣言への矛が 1 件も無い」ツールだけにする理由: 矛が 1 件でもあるツールは、矛の判定の抜き取りで確かめられるからです（[第 52 章 52.2 節](ch52.md#s52-3)）。

**例で確かめる**:

（作った例）天気のサーバの 2 つのツールに当てます。

| ツール | D1 か D2 を明示 | その宣言（D1）への矛 | 対象か |
|---|---|---|---|
| `weather_report` | D1 を明示（`server.py:9`） | まだ分からない（出力を見ていない） | 抜き取りの道具が「D1 の矛なし」として選んだなら対象 |
| `last_weather` | D1 を明示（`server.py:16`） | 同上 | 同上 |

表の読み方: 1 行が 1 つのツールです。判定者は、抜き取りの道具が選んだユニットを受け取るので、「その宣言への矛が無い」ことは**選ばれた時点で決まっています**。判定者が矛の有無を調べる必要はありません。

逆に、次のツール（作った例）は対象になりません。

```python
@mcp.tool(annotations=ToolAnnotations(openWorldHint=False))
def ping_local() -> str:
    return requests.get("http://localhost:8080/health").text
```

宣言が D3（`openWorldHint: false`）だけで、D1 も D2 も書いていないからです（18.1 の条件 (1)）。

**迷いやすいところ**:

- 「矛が 1 件も無い」は「解析器が何も出していない」とは限りません。**不**（`contradiction_unknown`）の注記は出ていることがあります。不は矛ではないので、不があっても対象に入ります。v4 の R01（bugasura の `update_project`）がこの形です（手引き L686）。
- 「対象である」ことを知った時点で、判定者は「解析器はこのツールの、この宣言への矛を出さなかった」ことをすでに知っています。これは避けられない前提の知識です。手順 1 の「出力を見る前に」は、それ以上の出力（効果の一覧・不の注記・打ち切りの印）を見ない、という意味に読めます（本書の読み）。

**承認の前に自分に問うこと**:

1. 「見落としの判定は、解析器の答えのうち『何も出さない』を確かめるもの」と、自分の言葉で説明できるか。
2. D3・D4 を明示したツールの見落としを測らないことに、納得できるか（理由は手引きに書かれていない）。
3. 矛のあるツールの別の動作に見落としがあっても数えないこと（数えるのは「矛の無いツールの中での見落とし」）を、論文の限界として書く覚悟があるか。

**この節で手引きが決めていないこと**: 見つからなかった（D1・D2 に絞る理由が書かれていない点は、規則の穴ではなく説明の欠けなので、穴には数えません）。

### H-6.2 18.2 の題と前置き — 順序と、AI を使ってよい時点（手引き L477-479）

> 【原文 L477-479】
> ### 18.2 順序（先入観を避けるため、コードを先に読む）
>
> **1〜7 は AI を使わずに行い、`outcome`・`cause` などを記録してから** AI に点検させてよい（8。D70 の 3 の条件 3）。

**一言で言うと**: 見落としの判定は、**コードを先に読み、解析器の出力は後で見る**順序で行います。手順 1〜7 は AI を使わずに行い、結果を記録してから、手順 8 で AI に点検させてもかまいません。

**ことばの確認**:

- **先入観**: 先に与えられた情報が、後の判断をその方向に引き寄せる働きです。ここでは「解析器の出力」と「AI の答え」が、先に与えられる情報にあたります。
- **`outcome`・`cause`**: 見落としの記録の欄です（18.4。[H-6.13](#ah-6-13)）。`outcome` は 5 つの結果のどれか、`cause` は見落としの原因です。
- **AI に点検させる**: 自分の判定を記録した後で、repo の文脈を持たない AI に、事実の問いで「書き込む行はどれか」などを聞き、自分が見落とした動作が無いかを確かめることです（18.2 の 8。[H-6.10](#ah-6-10)）。

**1 文ずつ読む**:

1. 「18.2 順序（先入観を避けるため、コードを先に読む）」: 題の中に理由が書いてあります。順序を決めるのは、先入観を避けるためです。
2. 「**1〜7 は AI を使わずに行い、`outcome`・`cause` などを記録してから** AI に点検させてよい（8。D70 の 3 の条件 3）。」: 手順 1〜7 のあいだは AI を使いません。`outcome`・`cause`（と書き込み先の種類・条件）を記録し終えたら、手順 8 で AI に点検させてよい、という意味です。「させてよい」なので、点検は任意です。

**なぜこう決めたのか**:

- D70 の 3 の条件 3（`docs/decisions.md:3860-3862`）: 「見落としの判定では、最初は自分で読む（手引き 18.2 の 1〜5 を AI なしで終える。続く 6・7 の原因とラベルも、AI の点検の前に AI なしで記録する）」。主の見落としの数は人だけで読んだ結果にし、AI の点検を足した数は併記します。
- 理由は、AI に先に聞くと、人の目が AI の挙げた行に集まり、AI が挙げなかった所を軽く見るからです。そうなると、見落としの率がモデル（どの AI を使ったか）に左右されます。D70 の 3 の改訂の理由は「先入観: 宣言の値と解析器の答えを渡さない（条件 2）。見落としは自分で先に読む（条件 3。調査 §3.2 と同じ）」と書いています（`docs/decisions.md:3879`。調査 §3.2 は `docs/llm_judgment_survey.md:149-150` の「最初の読みでは使わない（0-3。先に見ると引っぱられ、見落としの率がモデルに依存する）」）。
- 誤りの向き: 主の数を AI なしの結果にすると、AI の点検で見つかる見落としは主の数に入らないので、主の見落とし率は**小さく出る向き（誤 clear を少なく見せる向き）**になりえます。だから AI の点検を足した数を必ず併記します（`docs/decisions.md:3880-3882`）。

**例で確かめる**:

（作った例）`weather_report` を判定するときの時間の流れです。

| 時点 | してよいこと | しないこと |
|---|---|---|

### H-6.3 18.2 の 1 — 解析器の出力を見る前に、ツールの本体を読む（手引き L481）

> 【原文 L481】
> 1. **解析器の出力を見る前に**、ツールの本体を読む（`relpath:lineno`）。

**一言で言うと**: 最初にするのは、ツールの関数そのもの（本体）を開いて読むことです。解析器の出力は、まだ開きません。

**ことばの確認**:

- **本体**: ツールとして登録された関数の中身です。`relpath:lineno` は、その関数が定義されているファイル（木の根からの相対パス）と行番号です。判定表の行にこの 2 つが書いてあります。
- **解析器の出力**: manifest（ユニットごとの効果・注記・打ち切りの印）と、それを見やすくする道具（手順書 6.5 の `show_target.py` の形）の表示です。

**1 文ずつ読む**:

1. 「**解析器の出力を見る前に**、ツールの本体を読む（`relpath:lineno`）。」: 2 つのことを言っています。(1) 読む場所はツールの本体で、判定表の `relpath:lineno` で開く。(2) そのとき解析器の出力をまだ見ない。

**なぜこう決めたのか**:

- 手順書 0-3（`docs/final_evaluation_procedure.md:169`）: 「**解析器の出力を見る前に判定する**（先に原ソースを読んで自分で決め、その後で解析器の出力と照らす）。先に見ると引っぱられる」。D69 の 3（`docs/decisions.md:3827`）も「解析器の出力を見る前に判定する」と決めています。
- なぜ「引っぱられる」と困るのかは、誤りの向きで説明できます（[第 52 章 52.2 節](ch52.md#s52-3)、[第 21 章](ch21.md)）。解析器が見落とすのは、解析器に見えにくい所（sink 表に無いライブラリ、深い呼び出し、デコレータの中など）です。出力を先に見ると、人の目も「解析器が見た所」に集まり、人も同じ所を見落とします。すると見落としの数が実際より少なく出て、解析器を良く見せる向き（誤 clear の向き）に偏ります。この研究は、この向きの偏りを特に嫌います（`CLAUDE.md` 規則 4「黙って安全側に倒さない」）。

たとえ話を 1 つだけ置きます。答え合わせのとき、先に模範解答を読んでから自分の答案を見直すと、模範解答と同じ所しか点検しなくなります。模範解答が間違えている所ほど、自分も見逃します。見落としの判定では、解析器の出力が「模範解答」にあたり、しかもその模範解答の誤りを探すのが目的です。

**例で確かめる**:

（作った例）`weather_report` の本体（`server.py:9-13`）を読みます。

```
 9  @mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
10  def weather_report(city: str) -> str:
11      """Return a short weather report for a city."""
12      data = client.fetch(city)
13      return client.format_report(data)
```

- 9 行: 宣言は `readOnlyHint=True`（D1）。判定表の `decl` が D1 であることと一致します。
- 12 行: 木の中の `weather/client.py` の `fetch` を呼びます（深さ 1 へ。次の節）。
- 13 行: 同じく `format_report` を呼びます（深さ 1）。
- 本体の中に、ファイル・DB・通信を直接触る行はありません。

ここで書くメモは「本体（深さ 0）: 直接の書き込みなし。木の中の呼び出し 2 つ（`client.fetch`、`client.format_report`）」です。

**迷いやすいところ**:

- 本体を読むときは、デコレータも見ます。`@mcp.tool(...)` 以外のデコレータが木の中で定義されていれば、その wrapper（本体の代わりに走る関数）は毎回走ります（[第 52 章 52.3 節](ch52.md#s52-4)。v4 の R16）。
- 判定表に解析器から来た欄（効果の数 `n_effects`、打ち切りの印 `truncated`）が並んでいると、本体を開く前に目に入ります。これは下の穴 H-6-2 です。

**承認の前に自分に問うこと**:

1. 判定表の行を開いたとき、`tree`・`unit`・`relpath`・`lineno`・`decl` 以外を見ないでいられるか。
2. 同じ木の別のツールの矛を、少し前に判定したばかりだったら、それは「出力を見た」ことになると思うか。

**この節で手引きが決めていないこと**:

【穴 H-6-1】**同じ木・同じユニットを、先に別の判定で見てしまったときの順序**

- 何が決まっていないか: 見落としの抜き取り（D69 の 3）と、矛の抜き取り（D69 の 2）・不の中身の抜き取り（D69 の 4）は、別々の seed で選びます。同じ木が両方に入ることも、同じユニットが見落としと不の中身の両方に入ることもありえます（見落としの対象のユニットにも不の注記はありうるので。v4 の R01 は見落としの対象で、`net_post` の不を持っていました。手引き L686）。判定の順序は seed ⑤ で並べ替えると決まっています（21 の 1、D73 の 4、`docs/decisions.md:4029`）が、矛・見落とし・不の中身の判定表を混ぜて並べるのか、見落としを先に済ませるのかは書かれていません。
- どんな事例で困るか（作った例）: 変種 POST の `weather_report` が、不の中身の抜き取り（`requests.post` × D1、`net_post`）にも、見落としの抜き取り（D1 の矛なし）にも選ばれたとします。不の中身を先に判定すると、手順 B で解析器の言い分（道筋・注記）をすでに見ています。その後で見落としの判定をすると、18.2 の 1「出力を見る前に」を守れません。
- 考えられる選択肢: (a) 見落としの判定を、ほかの判定より先に全部済ませる。(b) 判定の順序は seed ⑤ のままにし、同じユニットが重なったときだけ見落としを先にする。(c) 重なりはそのまま許し、「先にほかの判定で出力を見た」ことを `note` に書いて、集計で区別できるようにする。
- 関係する決定: D69 の 2〜4（`docs/decisions.md:3826-3829`）、D73 の 4（seed ⑤ の並べ替え）、手順書 0-3（`docs/final_evaluation_procedure.md:169`）。

【穴 H-6-2】**見落としの判定表に、解析器から来た欄を載せるか**

- 何が決まっていないか: 手順書 6.3 は、見落としの抜き取りの出力に「効果の数・`truncated` の印」を入れると書き（`docs/final_evaluation_procedure.md:460`）、6.4 は判定表を「抜き取りの出力の欄に、空の判定の欄を足したもの」と書いています（`:468-469`）。これだと、判定表を開いた時点で解析器の出力の一部（効果が何件あったか、打ち切ったか）が目に入ります。手引き 18.2 の 1 は「出力を見る前に」と書くだけで、判定表の欄については何も言っていません。一方、深さの予備調査の候補（D74）の一覧は「n_effects と truncated は解析器の情報なので、判定表（miss_sheet.csv）には載せない」としていました（`evidence/v4pilot_depth/miss_targets.json` の `_note`）。
- どんな事例で困るか（作った例）: 元の例の `weather_report` の行に「効果の数 1」が見えていると、「解析器は `GET` くらいしか見ていない。どこかに見落としがあるのでは」と分かったうえで読むことになります。逆に効果の数が多ければ「よく見えているツール」と思って軽く読むかもしれません。`truncated` の欄が見えれば、「解析器が途中で止めた」ことを先に知ります。
- 考えられる選択肢: (a) 判定表から解析器の欄を外し、別のファイルに分けて手順 4 で開く（予備調査の候補と同じ形）。(b) 判定表には載せるが、右端に寄せて隠す。(c) 載せたままにし、見えることを限界として書く。
- 関係する決定: D69 の 3、D70 の 2（打ち切りの印のあるユニットも含める。`docs/decisions.md:3846-3847`）。[第 52 章 52.2 節](ch52.md#s52-3)の「つまずき」は (a)・(b) を本書の提案として挙げています。

### H-6.4 18.2 の 2 — 木の中の呼び出し先を、深さ 4 までたどる（手引き L482-484）

> 【原文 L482-484】
> 2. 本体から、**木の中の**呼び出し先を**深さ 4 まで**たどる（本体 = 深さ 0、本体が呼ぶ関数 = 深さ 1、…）。
>    木の外のライブラリ（pip で入るもの）の中は読まない。ただし、**ライブラリの関数そのもの**が環境を変えるもの
>    （`requests.put`、`sqlite3` の `execute("DELETE …")`、`shutil.rmtree` など）は、呼んでいれば違反の候補として数える。

**一言で言うと**: 本体を深さ 0 として、木の中で定義された関数の呼び出しを 1 段ずつ降り、**深さ 4 の関数の中身まで**読みます。木の外のライブラリの中は読みませんが、ライブラリの関数そのものが環境を変えるなら、呼んでいれば違反の候補に数えます。

**ことばの確認**:

- **深さ**: 本体から何段の呼び出しを降りたか、の数です。本体 = 深さ 0、本体が呼ぶ（木の中の）関数 = 深さ 1、深さ 1 の関数が呼ぶ（木の中の）関数 = 深さ 2、…と数えます。
- **木の中**: 関数の定義が、取得した木（`corpus/<木>/`）の中のファイルにあることです。
- **木の外のライブラリ**: 定義が木の中に無い関数です。pip で入るもの（`requests` など）と、Python に付いてくる標準ライブラリ（`os`、`shelve` など）です。
- **違反の候補として数える**: 手順 3 の「書き出し」に入れる、という意味です。

**1 文ずつ読む**:

1. 「本体から、**木の中の**呼び出し先を**深さ 4 まで**たどる（本体 = 深さ 0、本体が呼ぶ関数 = 深さ 1、…）。」: 数え方の定義です。数えるのは**呼び出しの段**で、ファイルの数ではありません。同じファイルの中の関数でも 1 段呼べば 1 増え、別のファイルの関数でも本体から直接呼べば深さ 1 です。「深さ 4 まで」は、深さ 4 の関数を開いて中身を読むところまで、という意味です（下の「解析器の数え方」と同じ範囲）。
2. 「木の外のライブラリ（pip で入るもの）の中は読まない。」: `requests.get` の中で何が起きるかを、ライブラリのソースまで追いません。
3. 「ただし、**ライブラリの関数そのもの**が環境を変えるもの（`requests.put`、`sqlite3` の `execute("DELETE …")`、`shutil.rmtree` など）は、呼んでいれば違反の候補として数える。」: 中は読まないが、外から見た働きは数えます。例の 3 つは、それぞれ HTTP の `PUT`（相手のサーバの状態を変える）、DB の行の削除、ディレクトリの丸ごとの削除です。「呼んでいれば」は、深さ 0〜4 の関数の中でその関数を呼んでいれば、という意味です。

**深さの数え方を正確に**:

手で数えるときの手続きです（[第 52 章 52.3 節](ch52.md#s52-4)の手続きと同じ。番号は本書の整理）。

1. 本体の定義の行に「深さ 0」と書きます。
2. 本体の中で、**木の中で定義された関数**の呼び出しを見つけたら、その定義へ飛び、「深さ 1」と書きます。
3. 深さ 1 の関数の中で、さらに木の中の関数の呼び出しを見つけたら、「深さ 2」と書きます。
4. これを深さ 4 まで繰り返し、**深さ 4 の関数の中身は読みます**。
5. 深さ 4 の関数の中で、さらに木の中の関数を呼んでいたら、名前だけを「深さ 5（読まない）」とメモし、中には入りません。
6. ライブラリの関数の呼び出しは、深さを増やしません。深さ k の関数の中で `shelve.open(...)` を呼んでいれば、その動作の深さは k です（本書の読み。18.4 の `depth` 欄「見つけた動作の深さ（本体 = 0）」をこう読みます。解析器でも、効果の深さは道筋 `witness_chain` の長さ、つまり効果のある関数の深さです。[第 15 章 15.3 節](ch15.md#s15-4)）。

**解析器の数え方**（`authgap/` は凍結。読むだけです）:

- 深さの上限は `authgap/ir.py:42` の `MAX_DEPTH = 4` です。その上のコメント（`authgap/ir.py:38-41`）に「木内ユーザ定義の被呼び出しにのみ加算する」「仕様書 §（243 行目）は 3。2026-09-24 に学生の決定で 4 に上げた」とあります。
- 降りるかどうかの判断は `authgap/val/engine.py:1065-1068` です。呼び出し先の本体に降りる前に `depth + 1 > self.opt.max_depth` を確かめ、超えるなら降りずに、値を `opaque("depth")` にし、`cap_hits` に `"depth"` を足します。本体を深さ 0 とすると、深さ 3 の関数から深さ 4 の関数へは `3 + 1 = 4` で上限を超えないので降りて中身を実行し、深さ 4 の関数から深さ 5 の関数へは `4 + 1 = 5 > 4` なので降りません。つまり**解析器も深さ 4 の関数の中身までを読み、深さ 5 には入りません**。手引きの「深さ 4 まで」と同じ範囲です。
- 仕様書の深さの規則（`AUTHGAP_BRIEF_v3.md:244`）: 「木内ユーザ定義の被呼び出しにのみ加算する。カタログ化ライブラリ呼び出し（`TRANSFER` 表）は深さを消費しない。間接 target 形（`threading.Thread` / `asyncio.to_thread` など）は 1 段として数える」「深さ超過は `opaque(depth)` … 決して drop しない」。
- 解析器は、木の中のクラスの構築（`Store(root)` から `__init__` へ）も 1 段と数え、デコレータの wrapper・`@property`・`with` の `__enter__` のような「書かれていないのに走るコード」はたどりません（[第 15 章 15.4 節](ch15.md#s15-5)）。人の数え方がこれとずれると、人が「深さ 4」と読んだ所が解析器には深さ 5 になる、ということが起きます（下の穴 H-6-3）。

**なぜこう決めたのか**:

深さ 4 という数と、人が読む深さを 4 にしたことには、4 つの決定が関わります。順に読みます。

1. **D54（2026-09-24）— 解析器の深さを 3 から 4 に上げた**（`docs/decisions.md:2908-2919`）。仕様書は深さ 3 でした。D53 の感度分析で、深さ 3 → 4 で矛が 85 → 146 に増え、消えたものが 0、時間は +7% でした。深さ 5 はさらに矛 +47 だが時間 +24% で、学生は 4 を選びました（事前登録の逸脱 #17）。
2. **D68 の 2（2026-09-30）— 人が見落としの判定で読む範囲も深さ 4 まで**（`docs/decisions.md:3805-3808`）。「偶然それより奥に宣言に反する動作を見つけたら『見落とし（深さ 4 の外）』として別に記録し、主の見落としの数には入れず併記する」。理由は 2 つ書かれています。「普通の見落としに数えると、数が判定者の読んだ深さで変わる」「『反する動作は無い』にすると、知っている違反を安全側に倒すことになる（CLAUDE.md 規則 4）」。v4 の R04・R05（深さ 7）がこの形でした。
3. **D74（2026-10-03）— 深さを測って決め直す予備調査**（`docs/decisions.md:4042-4062`）。学生の問い「どの深さにするかは実際に測定して決めるべきでは」がきっかけです。このとき大事な点が直されました。**見落としの判定で人が読む深さは、解析器の深さ以上でなければ、深い段の取りこぼしを数えられない**（本記録者が前に「人が読む深さは解析器と別に決められる」と答えたのは誤りで、学生の指摘で直した。`:4046-4047`）。
4. **D75（2026-10-03）— 主の深さは 4 のまま**（`docs/decisions.md:4069-4105`）。
   - 決めたこと（`:4078-4091`）: (1) 主の深さは 4 のまま（D54。`--max-depth` を付けない走査）。見落としの判定で人が読む深さも 4 のまま（D68 の 2）。(2) 深さ 3・5 は感度分析で、矛の件数だけを出し、判定しない。深さ 6 以上は走らせない。(3) 深さ 5 以上に対応する新しい仕組みは作らない。(4) メモリや時間の上限に当たった木は、黙って消さず、限界として書く。(5) 予備調査の判定の候補（矛 75 組・見落とし 10 件）は判定の練習に使う。

### H-6.5 18.2 の 3 — 宣言に反しうる動作を、条件つきで全部書き出す（手引き L485）

> 【原文 L485】
> 3. 宣言（D1 なら 15.1、D2 なら 15.2）に反しうる動作を**すべて**書き出す。到達の条件（第 14 節）も書く。

**一言で言うと**: 深さ 4 までに読んだコードの中から、宣言に反しうる動作を**すべて**メモに書き出し、それぞれに到達の条件を添えます。まだ解析器の出力は見ません。

**ことばの確認**:

- **反しうる動作**: その宣言の問い（D1 は 15.1 節、D2 は 15.2 節の表）に照らして、反する、または調べないと分からない動作です。たとえば D1 では、ファイルの書き込み・作成・削除、DB の変更、HTTP の `PUT`・`PATCH`・`DELETE` は反する動作、HTTP の `POST` や定数のコマンドの起動は「調べないと分からない」動作です。`GET` やファイルの読み取りは反しません。
- **到達の条件**: その動作が、どんなときに起きるかです。14 節の条件の種類（`なし` / `引数` / `初回` / …）で書きます。

**1 文ずつ読む**:

1. 「宣言（D1 なら 15.1、D2 なら 15.2）に反しうる動作を**すべて**書き出す。」: 照らす表を宣言で選びます。「すべて」なので、1 つ見つけたところで止めません。矛の判定の手順 G（1 つ正が見つかれば止めてよい）とは違います。
2. 「到達の条件（第 14 節）も書く。」: 動作ごとに、毎回起きるのか、引数しだいか、初回だけか、などを書きます。

**なぜこう決めたのか**: 手引きに理由は書かれていません。本書の読み: (1) 手順 5 で解析器の出力と 1 つずつ照らすので、照らす相手が全部そろっている必要がある。1 つだけ書いて止めると、その 1 つに解析器が不を出していた場合に、ほかの見落としを取りこぼす。(2) 手順 7 で書き込み先の種類と条件の種類を付けるので、条件を先に書いておくと後で迷わない。[第 52 章 52.4 節](ch52.md#s52-5)も同じ説明をしています。

**例で確かめる**:

（作った例）`weather_report`（D1）の書き出しのメモです。[H-6.4](#ah-6-4) の番号の列を上から見ていきます。

- `weather/history.py:19` の文字列の変換、`weather/client.py:20` の文字列の組み立て: 外の世界に触れない。

表の読み方: 1 行が 1 つの「反しうる動作」です。1 行目は「深さ 4 の `_write` の中で `shelve` のファイルに書き込む。読み取り専用の宣言に反する。取得に成功した呼び出しでは毎回起きる」と読みます。

条件を「なし」にした理由を書いておきます。`_download` が例外で抜ければ（通信の失敗、応答が JSON でないとき）書き込みは起きません。けれども、14.1 の基本は「その効果が起きる実行の道が 1 つでもあるか。毎回起きる必要はない」で、普通に応答が返る呼び出しでは毎回届きます。失敗したときに**届かなくなる**だけなので、条件の種類は「なし」と読みました（本書の読み。14.3 の `失敗・期限切れ` は「失敗したときに起きる効果」の条件で、この形ではありません）。

- **ライブラリの名前で判断しない。** `shelve` は解析器の sink 表に無い（`authgap/catalog/sinks.py` を `shelve` で検索しても 0 件。2026-10-04 に確かめた）が、人の判定では関係ありません。動作で決めます。

**承認の前に自分に問うこと**:

**この節で手引きが決めていないこと**: 見つからなかった（条件の読み分けの迷いは 14.3 節の範囲で、14 節を読む分冊で扱います）。

1. 「ここで初めて解析器の出力を見る」: 手順 1〜3 の後、という順序の確認です。

1. 出力を見て「自分のメモに無い効果」が出ていたら、どう扱うか（たとえば解析器が見つけた `POST` に不が出ていて、自分はその `POST` を見落としていた）。

### H-6.8 18.2 の 6 — 見落としの原因を 5 つに分ける（手引き L496-498）

> 【原文 L496-498】
> 6. 見落としなら原因を分類する: **深さ**（深さ 4 を超えるところにある）/ **呼び出しの解決**（呼び出し先を解決できていない。
>    `opaque` に `receiver` / `unresolved`）/ **受け手の型** / **語彙**（sink の語彙に無いライブラリ。例: loguru の
>    `logger.add` のファイル出力）/ **その他**（デコレータの wrapper の中など）。

**一言で言うと**: 見落としにしたら、解析器が見逃した理由を 5 つのどれかに分けて `cause` に書きます。深さ / 呼び出しの解決 / 受け手の型 / 語彙 / その他、です。

**ことばの確認**:

- **`opaque`**: 解析器が、値や呼び出しを解決しきれなかった印です。ユニットの `opaque_reasons` に理由が並びます。`unresolved` は「呼び出し先を木の中で解決できなかった」、`receiver` は「メソッドの持ち主（`x.f()` の `x`）の型が分からなかった」です。
- **受け手の型**: `x.f()` の `x` に何が入っているか（どのクラスの実体か）です。分からないと、`f` がどの関数か決められません（[第 15 章 15.8 節](ch15.md#s15-9)）。
- **sink の語彙**: 解析器が「この関数は外の世界に触れる」と知っている関数の一覧（`authgap/catalog/sinks.py`）です。ここに無い関数の動作は、効果になりません。
- **デコレータの wrapper**: `@deco` を付けた関数の代わりに走る関数です。解析器はたどりません（[第 15 章 15.4 節](ch15.md#s15-5)）。

**1 文ずつ読む**:

1. 「見落としなら原因を分類する:」: 原因を書くのは、結果が見落としのときだけです。
2. 「**深さ**（深さ 4 を超えるところにある）」: 解析器が深さの上限で降りなかった所に動作がある。
3. 「**呼び出しの解決**（呼び出し先を解決できていない。`opaque` に `receiver` / `unresolved`）」: 解析器が、その動作のある関数への呼び出しを結べなかった。手がかりとして `opaque` の `receiver` / `unresolved` が挙がっています。
4. 「**受け手の型**」: メソッドの持ち主の型を読み違えた、または読めなかった。
5. 「**語彙**（sink の語彙に無いライブラリ。例: loguru の `logger.add` のファイル出力）」: 道筋はたどれていたが、最後の関数が sink 表に無かった。
6. 「**その他**（デコレータの wrapper の中など）」: 上のどれでもない。

**なぜこう決めたのか**: 手引きに理由は書かれていません。本書の読み: 原因の内訳は、論文の限界の節で「解析器はどんな所を見逃すか」を事実で示す材料になります（誤の原因 E1〜E9 と同じ役割。手引き 17 節の末尾「分類は集計で『誤の原因の内訳』になり、論文の限界の節の材料になる」）。事前登録の下書き (g) は、見落としの原因の内訳を報告すると書いています（`docs/drafts/prereg_2_12_draft.md:145`）。

**例で確かめる**:

| 原因 | 例 | 出力での手がかり |
|---|---|---|
| 深さ | 打ち切りのあるユニットで、深さの上限で読まなかった所に違反があった（18.3。[H-6.11](#ah-6-11)） | ユニットの `cap_hits` に `depth` |
| 呼び出しの解決 | 変種 コールバック で、文書から `_flush` が呼ばれると分かった場合（作った例） | 木の中の `_flush` に降りた跡が無い（`witness_chain` に出ない） |
| 受け手の型 | （作った例）`self.store.save(entry)` の `self.store` に何が入るかを解析器が読めず、`save` の中の書き込みに降りなかった | `opaque_reasons` に `receiver` |
| 語彙 | **元の例**: `shelve` の書き込み。道筋（`fetch -> remember -> _save -> _write`）は深さ 4 の中で、たどれる形。`shelve` が sink 表に無い | その行に効果が無い。道筋はたどれている |
| その他 | （作った例）木の中のデコレータ `@audit` の wrapper が毎回ファイルに追記する | どこにも印が出ないことが多い |

表の読み方: 1 行が 1 つの原因です。たとえば 4 行目は「元の例は、解析器がたどれる道筋の上にある書き込みだが、`shelve` が sink 表に無いので効果にならなかった。だから原因は語彙」と読みます。

元の例で「語彙」と決める手順を書いておきます（[第 52 章 52.6 節](ch52.md#s52-7)の順序。本書の整理）。

1. その動作は深さ 4 より奥か → 深さ 4（`_write`）なので、奥ではない。
2. その動作の関数は sink 表にあるか → `authgap/catalog/sinks.py` に `shelve` は無い → **語彙**。
3. （念のため）解析器はその関数までたどれたか → 変種 POST の道筋 `fetch -> remember -> _save -> _write` が示すとおり、同じ形の道筋をたどれている。

**迷いやすいところ**:

- **「深さ」が主の見落としに付くことは少ない。** 深さ 4 を超えた所にだけある違反は、結果が「見落とし（深さ 4 の外）」になるからです（D68 の 2）。主の見落としに「深さ」が付くのは、人と解析器の深さの数え方がずれた場合（穴 H-6-3）や、打ち切りのあるユニットの場合（18.3）です（[第 52 章 52.6 節](ch52.md#s52-7)の本書の読み）。
- `opaque: ['unresolved']` は、ほとんどのユニットに付きます。これがあるだけで「呼び出しの解決」と決めてはいけません。その動作のある関数への呼び出しが、本当に解決されていなかったかを見ます。

**承認の前に自分に問うこと**:

1. 元の例の原因を「語彙」にすることに同意するか。
2. 2 つの原因が重なるとき（道筋も解決できず、最後の関数も sink 表に無い）、どちらを書くか。

**この節で手引きが決めていないこと**:

【穴 H-6-7】**原因が重なるときに、どれを書くか**

- 何が決まっていないか: `cause` には 1 つを書く形ですが、2 つ以上の理由が重なるときの選び方が書かれていません。
- どんな事例で困るか（作った例）: `self.store.save(entry)`（受け手の型が読めない）の先の `save` が、`shelve` で書いている（語彙）。受け手の型が読めても、`shelve` で効果にはなりません。
- 考えられる選択肢: (a) 解析器が最初につまずいた所（入口に近い所）を書く（[第 52 章 52.6 節](ch52.md#s52-7)の本書の読み）。(b) 全部を `;` で並べる（`condition_type` と同じ書き方）。(c) 決まった順（たとえば 語彙 ＞ 受け手の型 ＞ 呼び出しの解決 ＞ 深さ ＞ その他）で 1 つを選ぶ。
- 関係する決定: なし（手引き 18.2 の 6 だけ）。

【穴 H-6-8】**「見落とし（深さ 4 の外）」に `cause` を書くか**

- 何が決まっていないか: 18.2 の 6 は「見落としなら原因を分類する」と書きますが、「見落とし（深さ 4 の外）」にも原因を書くのか（書くなら「深さ」か）が書かれていません。
- どんな事例で困るか（作った例）: 変種 深い で `_persist` の書き込みを偶然見つけたとき、`cause` を空にするか「深さ」にするか。
- 考えられる選択肢: (a) 「深さ」と書く。(b) 空にする（結果の名前に深さが入っているので）。(c) 深さ 5 の動作に解析器が降りていたとしても見えたか（語彙など）を別に書く。
- 関係する決定: D68 の 2。[第 52 章 52.14 節の表](ch52.md#s52-15)の 5。

> 【原文 L500-503】

**この節で手引きが決めていないこと**:

### H-6.11 18.3 の注意 1〜3 — 打ち切り・深さ 4 の外・中と外の両方（手引き L505-512）

> 【原文 L505-512】
> ### 18.3 注意
>
> - 打ち切りの印（`truncated`）があるユニットで、解析器が途中で読むのをやめた部分に違反があったら、見落としとして原因を
>   「深さ」または「その他（打ち切り）」にする。読み切れないなら「不明（打ち切り）」。
> - **深さ 4 より奥の違反を偶然見つけたら、`outcome` を「見落とし（深さ 4 の外）」にする**（D68 の 2）。主の見落としの数には
>   入れず、別に数えて併記する。深さ 4 より奥を**探しに行く必要はない**（読む範囲は深さ 4 まで）。
> - 深さ 4 の中に「反する動作」が無く、深さ 4 の外にだけあるなら `見落とし（深さ 4 の外）`、深さ 4 の中にもあれば、中のものを
>   主として `見落とし`（または `解析器が不として出している`）にし、外のものは `note` に書く。

**一言で言うと**: 解析器が途中で読むのをやめたユニット（打ち切り）での扱い、深さ 4 より奥で偶然見つけた違反の扱い、中と外の両方にあるときの扱いを決めています。深さ 4 より奥は、探しに行く必要はありません。

**ことばの確認**:

- **打ち切りの印（`truncated`）**: 抜き取りの道具が、ユニットの注記 `TRUNCATED(...)` を写した欄です（`TRUNCATED(recursion)` など。[第 52 章 52.7 節](ch52.md#s52-8)）。深さの上限での打ち切り（`cap_hits` の `depth`）とは別の欄です。
- **見落とし（深さ 4 の外）**: 深さ 4 より奥にだけある、宣言に反する動作を偶然見つけたときの結果です（D68 の 2）。
- **主の見落としの数**: 論文の主の結果として報告する見落としの数です。「見落とし（深さ 4 の外）」はここに入れず、別に数えて並べます。

**1 文ずつ読む**:

1. 「18.3 注意」: 小見出しです。
2. 「打ち切りの印（`truncated`）があるユニットで、解析器が途中で読むのをやめた部分に違反があったら、見落としとして原因を『深さ』または『その他（打ち切り）』にする。」: 打ち切った部分の違反は、解析器が見ていない所の違反なので、見落としです。原因は 2 つのどちらか。
3. 「読み切れないなら『不明（打ち切り）』。」: 人も読み切れない（大きすぎるなど）なら、不明で、打ち切りが理由であることを括弧で示します。
4. 「**深さ 4 より奥の違反を偶然見つけたら、`outcome` を『見落とし（深さ 4 の外）』にする**（D68 の 2）。」: 「偶然」が大事です。見つけた違反を消さず、別の結果として記録します。
5. 「主の見落としの数には入れず、別に数えて併記する。」: 主の数の意味（深さ 4 の中の見落とし）を保ちます。
6. 「深さ 4 より奥を**探しに行く必要はない**（読む範囲は深さ 4 まで）。」: 読む範囲は 18.2 の 2 のとおり。
7. 「深さ 4 の中に『反する動作』が無く、深さ 4 の外にだけあるなら `見落とし（深さ 4 の外）`、」: 外にだけあるとき。
8. 「深さ 4 の中にもあれば、中のものを主として `見落とし`（または `解析器が不として出している`）にし、外のものは `note` に書く。」: 中にもあるときは、中のもので結果を決め、外のものは `note` に残します。

**なぜこう決めたのか**:

- D68 の 2（`docs/decisions.md:3805-3808`）: 普通の見落としに数えると数が判定者の読んだ深さで変わる。「反する動作は無い」にすると知っている違反を安全側に倒す。
- 打ち切りのあるユニットを対象に含めるのは D70 の 2（`docs/decisions.md:3846-3848`）: 除くと、解析器が苦手な大きいツールが抜き取りから消え、見落としの率を低く見せる（誤 clear の向きを隠す）。

**例で確かめる**:

（作った例）変種 深い と、それをさらに変えたものです。

| 深さ 4 の中 | 深さ 4 の外 | 結果 | 外のもの |
|---|---|---|---|
| 反する動作なし（変種 深い） | `_persist` の書き込み（深さ 5）を偶然見つけた | 見落とし（深さ 4 の外）、`depth` = 5 | — |

**迷いやすいところ**:

### H-6.12 18.3 の注意 4 — ログの出力先は、モジュール水準の設定まで確かめる（手引き L513-514）

> 【原文 L513-514】
> - ログの出力先がファイルかどうかは、`logging.basicConfig(filename=…)`、`FileHandler`、loguru の `logger.add(<パス>)` など、
>   **モジュール水準の設定**も確かめる（v4 の R19 はモジュールの一番上で設定していた）。

**一言で言うと**: ツールの道筋でログを書く呼び出しを見つけたら、そのログがファイルに行くかを、モジュールの一番上（関数の外）の設定までさかのぼって確かめます。

**ことばの確認**:

- **モジュール水準の設定**: 関数の外、ファイルの一番上に書かれ、モジュールを読み込んだときに 1 回走るコードです。ログの出力先の設定は、ここに書かれることが多いです。
- **`logging.basicConfig(filename=…)`・`FileHandler`**: Python の標準の `logging` で、出力先をファイルにする書き方です。
- **loguru の `logger.add(<パス>)`**: loguru というライブラリで、出力先にファイルを足す書き方です。
- **R19**: v4 の判定の見落としの 1 件（mcp-aws の `get_execution_plan`、D1、見落とし（語彙））です（手引き L685）。

**1 文ずつ読む**:

1. 「ログの出力先がファイルかどうかは、`logging.basicConfig(filename=…)`、`FileHandler`、loguru の `logger.add(<パス>)` など、**モジュール水準の設定**も確かめる」: ログの呼び出し（`log.info(...)`）そのものには出力先が書かれていないので、設定の場所まで見ます。
2. 「（v4 の R19 はモジュールの一番上で設定していた）。」: 実例です。R19 では、モジュールの一番上で loguru の `logger.add(<ファイル>)` を設定し、ツールが毎回ログを追記していました（手引き L685）。

**なぜこう決めたのか**: 15.1 の「迷いやすい形」は、標準出力・標準エラーへのログは反しないが、「`logging` の出力先がファイルなら反する。出力先の設定を確かめる」と書いています（手引き L332）。ログの呼び出しは深さ 0〜4 の関数の中にあっても、出力先の設定は深さの数え方の外（モジュール水準）にあるので、深さ 4 まで関数をたどるだけでは見えません。だから注意として書き足したものと読めます（本書の読み）。

**例で確かめる**:

（作った例）元の例の `weather/history.py` の上に、次の 2 行があったとします。

```
 4  logging.basicConfig(filename=os.path.expanduser("~/.weather.log"), level=logging.INFO)
 5  log = logging.getLogger(__name__)
 …
10  def remember(city, data):
11      log.info("remember %s", city)
```

- 11 行（深さ 2 の `remember`）: `log.info(...)` を呼びます。これだけでは出力先が分かりません。
- 5 行 → 4 行とさかのぼると、出力先は `~/.weather.log` というファイルで、水準は INFO です。`info` の記録は書かれます。
- だから、呼び出しのたびに `~/.weather.log` に 1 行追記されます。D1 に反する動作で、手順 3 の書き出しに加えます（ラベルは「ログ」、条件は「なし」）。

逆に、4 行が `logging.basicConfig(level=logging.INFO)`（`filename` なし）なら、出力先は標準エラーで、反しません。

**迷いやすいところ**:

- 設定がほかのファイル（`logging_setup.py` など）にあることもあります。`basicConfig`・`FileHandler`・`addHandler`・`logger.add` で木の中を検索します。
- 水準に注意します。`log.debug(...)` は、水準が INFO なら書かれません。
- 標準の `logging` も loguru も、解析器の sink 表には無いので、ファイルに書いていても解析器は効果にしません（[第 52 章 52.7 節](ch52.md#s52-8)）。見つけて解析器が黙っていれば、見落とし（語彙）です。

**承認の前に自分に問うこと**:

1. ログを 1 行追記するだけのツールを、「読み取り専用」の宣言への違反（見落とし）として数えることに、自分は同意するか（手引き 11.3 の「字義どおり」。軽重はラベル「ログ」で表す）。
2. 出力先の設定が `main()` の中だけにあったら、どう読むか（下の穴）。

**この節で手引きが決めていないこと**:

【穴 H-6-14】**ログの出力先の設定が `main()` の中だけにあるとき**

- 何が決まっていないか: 14.4 と 14.3 の「起動の方法」は、「**初期化が** `main()` の中だけにあり、`main()` を通らない起動（`fastmcp run file.py:mcp` など）で、ツールの呼び出しで効果に届く」形を扱います。ログの出力先の設定は向きが逆で、`main()` の中で `logging.basicConfig(filename=…)` をしていると、`main()` を**通る**起動のときだけ、ログがファイルに行きます。`main()` を通らない起動では標準エラーに行き、反しません。この形の条件の種類（`起動の方法` か `運用者の設定` か）は書かれていません。
- どんな事例で困るか（作った例）: `server.py` の 23〜24 行が `if __name__ == "__main__": logging.basicConfig(filename="weather.log"); mcp.run()` だったとします。`python server.py` で起動すればファイルに書き、`fastmcp run server.py:mcp` で起動すれば書きません。
- 考えられる選択肢: (a) 到達する（届きうる起動の方法がある）とし、条件の種類を `起動の方法` にする（(B) に数えない）。(b) `運用者の設定` にする（起動の方法を選ぶのは運用者なので）。(c) 14.3 の `起動の方法` の定義を「`main()` を通る起動でだけ届く形」にも広げる。
- 関係する決定: D67 の 2（起動の方法はコードだけから決める、`docs/decisions.md:3773-3778`）、D68 の 1（条件の種類）。

### H-6.15 18A 節の見出しと 18A.1 何を判定するのか — 解析器の「不」とは（手引き L530-535）

> 【原文 L530】
> ## 18A. 不の中身の 1 組を判定する手順（D69 の 4、0-14）

> 【原文 L532-535】
> ### 18A.1 何を判定するのか
>
> 対象は、解析器が「不」（静的に決まらない）を出した組（ユニット, 効果, 宣言）。D1・D2 のそれぞれで 50 木、1 木 1 組（計 100 組）。
> **解析器が決められなかったものの中に、本当の違反がどれだけあるか**を確かめる。D3・D4 の不は判定しない（件数と理由だけ）。

**一言で言うと**: 不の中身の判定は、解析器が「反するかは静的に決まらない」（不）と出した組を人が読み、その中に本当の違反がどれだけあるかを確かめる作業です。D1・D2 のそれぞれで 50 木、1 木 1 組を判定します。D3・D4 の不は判定しません。

**ことばの確認**:

- **不**（`contradiction_unknown`）: 解析器の答えの 1 つで、「この効果が、この宣言に反するかは、コードだけからは決まらない」という意味です。下で、解析器のどこで作られるかを読みます。
- **組（ユニット, 効果, 宣言）**: 判定の単位です。11.1 の「組 = (木, ユニット, site, kind, 宣言)」と同じもので、効果を site（効果を起こす関数）と kind（効果の種類）で表します。
- **0-14**: 手順書の段階 0 の 14 番目の項目で、不の中身の判定を決めた所です（`docs/final_evaluation_procedure.md:289-297`）。
- **D69 の 4**: 不の中身の判定を足した決定です（`docs/decisions.md:3828-3830`）。

**解析器の「不」は、どこで、どう作られるか**（`authgap/` は凍結。読むだけです）:

1. **効果ごと・宣言ごとに判定する**: `authgap/verdict.py:150` で、効果 1 つごとに `_contradiction_findings(dk, eff)` を呼びます（中身は `authgap/dparse.py:573-601` の `contradiction_findings`）。明示された宣言ごとに、`readOnlyHint` があれば D1（`dparse.py:584-588`）、無くて `destructiveHint` があれば D2（`:589-592`）、ほかに D3・D4 を判定し、`(宣言, 結果, 理由)` の列を返します。結果は `CONTRA`（矛）か `CONTRA_UNKNOWN`（不。値は `"unknown"`、`dparse.py:241-242`）です。宣言の内側（反しない）なら何も返しません。
2. **D1 で不になる場所**（`authgap/dparse.py:372-394` の `_d1`）:
   - プロセスの起動で、コマンドをモデルが選べない（定数など）→ `spawn_command`（`:378`）。モデルの値が流れ込むが選べるとまで言えない → `spawn_model_opaque`（`_by_choice`、`:265-272`）。
   - DB で、SQL が読めない・分類に無い・文に分けられない・モデルの値が流れ込む → `db_sql_unreadable`・`db_unknown_statement`・`db_sql_unsplittable`・`db_sql_model_opaque`（`_db`、`:449-470` と `:499`）。
   - HTTP の `POST` → `net_post`（`:389-390`）。メソッドが読めない → `net_method_unknown`（`:393`）。
   - ファイルの書き込みは、D1 では必ず矛（`fs_write`、`:379-380`）なので、D1 のファイルの不はありません。
3. **D2 で不になる場所**（`authgap/dparse.py:397-427` の `_d2`）: 上の D1 の不（ファイル以外）に加えて、書き出しで書き先をモデルが決めない → `fs_writeout`、開くモードが読めない → `fs_unknown`（`:410`）。DB に残る設定 → `db_persistent`（`:412`。D1 では矛）。宛先の決まった `PUT` → `net_put`（`:421`）。
4. **注記にする**: `authgap/verdict.py:161-165` で、矛なら `contradiction:<宣言>` と `contradiction_reason:<宣言>:<理由>` の 2 つ、不なら `contradiction_unknown:<宣言>:<理由>` の 1 つを、その効果の行の注記に足します。
5. **不は矛に数えない**: 行が CONTRADICTION になるかは、結果が矛のものだけで決まります（`authgap/verdict.py:151` の `contradiction_flag`）。不は矛にも宣言内にも倒さず、注記として別に数えます。

この扱いは、原理の文書の**原理 2-a**（`docs/contradiction_principles.md:60-68`）です。「静的に決まらない性質をどう扱うか」の 3 つの案（a 不明とする / b 矛盾に倒す / c 宣言内に倒す）から、学生が a を選びました（`:139`「規則 4。b / c は測定を既知の向きに偏らせる。不明の件数は必ず併記する」）。§7 の判定表は、不を「CONTRADICTION に数えず、行の注記 `contradiction_unknown:<宣言>:<理由>` として数える」と定めています（`:147-148`）。末尾が `_opaque` の不は、§9.3（`docs/contradiction_principles.md:296-301`）の「モデル由来は『選べる』ではなく『流れ込む』」から来ます。

**取り違えやすい 3 つの「分からない」**:

| 名前 | 誰の答えか | どこに出るか | 意味 |
|---|---|---|---|
| 不（`contradiction_unknown`） | 解析器 | 行の注記 | この効果が、この宣言に反するかは静的に決まらない |
| 行の `UNKNOWN` | 解析器 | 行の `verdicts` | その行の効果や slot の値が解決しきれていない（`authgap/verdict.py:156, 171-172, 180-181`）。宣言とは別の話 |
| 不明 | 判定者（人） | 判定表の `outcome` / `verdict` | 人が原ソースを読んでも決められない（手引き 19 節） |

表の読み方: 1 行が 1 つの「分からない」です。たとえば 2 行目は「行の `UNKNOWN` は、解析器が値を解決しきれなかった印で、宣言に反するかどうかの答えではない」と読みます。変種 POST の `requests.post` の行は、manifest の `verdicts` の欄に `UNKNOWN`（3 つの slot の行のどれにも。効果の解決の確度が resolved でないため。`authgap/verdict.py:156, 180-181`）を持ち、注記に `contradiction_unknown:D1:net_post` を持っていました（2026-10-04 に manifest で確かめた。6.5 の道具は注記だけを出すので、`verdicts` は表示されません。[H-6.7](#ah-6-7)）。不の中身の判定の対象は、注記の不です。

**1 文ずつ読む**:

1. 「18A. 不の中身の 1 組を判定する手順（D69 の 4、0-14）」: 18A 節の題です。根拠は D69 の 4 と手順書 0-14。

> 【原文 L548-556】
> 4. 次のどれかに決める。
>
> | 結果 | 条件 |
> |---|---|
> | **違反** | 到達し、かつ宣言に反する |
> | **違反でない** | 到達しない、または宣言に反しない |

**1 文ずつ読む**:

1. 「4. 次のどれかに決める。」: 結果は表の 3 つから選びます。
2. 表の 1 行目「**違反** | 到達し、かつ宣言に反する」。
3. 表の 2 行目「**違反でない** | 到達しない、または宣言に反しない」: どちらか一方で「違反でない」です。
4. 表の 3 行目「**不明** | 判定者が原ソースを読んでも決められない（第 19 節）」。
5. 「5. 違反なら、正と同じく**書き込み先の種類**（第 16 節）と**条件の種類**（14.3）を付ける。」: 正の矛・見落としと同じラベルです。
6. 「違反でないなら、理由を 1 文で書く。」: どちらの理由で違反でないのか（到達しない / 反しない）を 1 文で。

|---|---|---|

| いいえ | — | 違反でない |

| 決められない | — | 不明 |
| はい | 決められない | 不明 |

表の読み方: 1 行が 1 つの組み合わせです。たとえば 5 行目は「その効果は届くが、相手の API の意味が分からず反するかを決められないなら、不明」と読みます（この 5 行の表は手引き 18A には無く、11.2 の表を当てはめた本書の整理です。[第 52 章 52.11 節](ch52.md#s52-12)も同じ表を置いています）。

**なぜこう決めたのか**: 結果の名前を矛の判定（正 / 誤）と変えたのは、不の中身では解析器が答えを出していないからと読めます（理由は書かれていない。本書の読み）。違反にラベルを付けるのは、D68 の 3 と事前登録の下書き（`docs/drafts/prereg_2_12_draft.md:113`「D1・D2・D4 の正と見落とし、不の中身の違反には、書き込み先の種類を付ける」）です。集計は、宣言ごとに違反だった木の割合と、不の理由ごとの内訳です（手順書 0-14、`docs/final_evaluation_procedure.md:297-298`）。

**例で確かめる** — 変種 POST の組を、相手の API の 3 つの場合で:

**場合 A — 違反**: 相手の文書に「`POST /v1/entries` は、送られた記録を新しく保存する」と書いてあったとします。

**問 6**: 元の例の見落とし（`shelve` の書き込み）の原因は 5 つのどれですか。その理由も答えてください。

<details><summary>答え</summary>

語彙です。書き込みは深さ 4 の中にあり（深さではない）、道筋は解析器がたどれる形（変種 POST で同じ道筋 `fetch -> remember -> _save -> _write` に効果が出た）ですが、`shelve` が解析器の sink 表（`authgap/catalog/sinks.py`）に無いので、効果になりませんでした（[H-6.8](#ah-6-8)）。

</details>

**問 7**: 18.2 の 8 の AI の点検で、AI が挙げた行のうち `ai_found` に書くのは、どんな条件を満たすものですか。点検の後で `outcome` を変えてよいですか。

<details><summary>答え</summary>

自分で開いて確かめたうえで、(1) 深さ 4 の中、(2) 宣言に反する、(3) 手順 1〜7 でまだ書いていない、の 3 つをすべて満たすものだけです。`outcome` と `cause` は変えません。主の見落としの数は AI なしの結果で、AI の点検を足した数は併記します（[H-6.10](#ah-6-10)）。

</details>

**問 8**: 「不」「行の `UNKNOWN`」「不明」の 3 つは、それぞれ誰の答えで、何を意味しますか。

<details><summary>答え</summary>

不（`contradiction_unknown`）は解析器の答えで、「この効果がこの宣言に反するかは静的に決まらない」という行の注記（`authgap/verdict.py:165`）。行の `UNKNOWN` は解析器の答えで、その行の効果や slot の値が解決しきれていない印（`authgap/verdict.py:171-172, 180-181`）。宣言に反するかとは別の話です。不明は判定者（人）の答えで、原ソースを読んでも決められないもの（手引き 19 節）です（[H-6.15](#ah-6-15)）。

</details>

**問 9**: 不の中身の判定で、`net_post` の不を持つ組の `POST` が、相手の文書で「新しい記録を保存する」と分かりました。宣言が D1 のとき、D2 のときの結果をそれぞれ答えてください（到達はするものとします）。

<details><summary>答え</summary>

D1 なら違反です（呼び出しの後に相手のサーバに記録が残る。原理 1-ii-b。書き込み先の種類は「相手側の状態」）。D2 なら違反でないです（新しく作るだけで、呼び出しの前からあったものを消す・上書きする・変えるわけではない。15.2）。同じ動作でも、照らす宣言で結果が変わります（[H-6.16](#ah-6-16)・[H-6.17](#ah-6-17)）。

</details>

**問 10**: 練習の材料 `evidence/v4pilot_depth/` で、手順 1〜3 のあいだに開いてよいファイルと、開かないファイルはどれですか。

<details><summary>答え</summary>

開いてよいのは `miss_sheet.csv`（埋まっているのは `id`・`tree`・`tool`・`unit`・`decl` だけ）と、`tree`・`unit` で開く v4 の木の原ソースです。`miss_targets.json` は解析器の情報（`n_effects`）を含むので、手順 4 まで開きません。走査の結果（manifest）も手順 4 で初めて見ます（[H-6.14](#ah-6-14)）。

</details>
