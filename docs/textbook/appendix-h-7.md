### H-7.1 19 節「『不明』にするとき」の前半 — 倒さない約束と、時間の目安（手引き L570-573）

> 【原文 L570-573】
> ## 19.「不明」にするとき
>
> 不明は失敗ではない。**分からないものを黙って正や誤に倒さないこと**が、この研究の約束である（CLAUDE.md 規則 4）。
> ただし、調べれば分かるものを不明にしない。目安として、**20〜30 分調べても決められなければ不明**にし、理由を書く。

**一言で言うと**: 分からないものは「不明」と書いてよく、それは失敗ではありません。けれども、調べれば分かるものを不明にしてはいけません。その境目の目安が「20〜30 分調べても決められなければ」です。

**ことばの確認**:

- **不明**: 判定の 3 つ目の値です。矛の判定では `verdict` の「正 / 誤 / 不明」の 1 つ（`:174`）、見落としの判定では `outcome` の 5 つの値の 1 つ（`:520`）、不の中身の判定では `outcome` の「違反 / 違反でない / 不明」の 1 つ（`:562`）です。
- **倒す**: 決められないものを、どちらかの答えに寄せて書くことです。たとえば、決められない組を「たぶん誤」として誤に書くのが「誤に倒す」です。
- **CLAUDE.md 規則 4**: この repo の規則の 4 番目「解決できなかったものは『不明』として記録する。黙って安全側に倒さない」（`CLAUDE.md:13`）。
- **目安**: きっちりした締め切りではなく、判断の拠り所になる大きさのことです。

**1 文ずつ読む**:

1. 「## 19.「不明」にするとき」— 節の題です。19 節は、矛・見落とし・不の中身の**3 つの判定すべて**に効く節です。18A 節の表は「不明: 判定者が原ソースを読んでも決められない（第 19 節）」と、この節を名指ししています（`:554`）。
2. 「不明は失敗ではない。」— 不明と書くことは、判定者の力不足の印ではない、と先に言い切っています。不明を恥ずかしいものと感じると、判定者は無理にどちらかに決めたくなります。それを防ぐための 1 文です。
3. 「**分からないものを黙って正や誤に倒さないこと**が、この研究の約束である（CLAUDE.md 規則 4）。」— 「黙って」が大事です。不明をどちらかに寄せたいなら、それは集計の段階で、誰にでも見える形で行います（下の「なぜ」）。判定の段階で、判定者の頭の中だけで寄せてはいけません。
4. 「ただし、調べれば分かるものを不明にしない。」— 反対側の約束です。不明が「楽な逃げ道」にならないようにしています。
5. 「目安として、**20〜30 分調べても決められなければ不明**にし、理由を書く。」— 境目の目安と、不明にしたときの義務（理由を書く）です。理由は `unknown_reason` 欄に書きます（`:181`、`:565`）。

**なぜこう決めたのか**:

- **倒さない理由（研究の芯）**: 食い違いの原理の文書は、原理 2「静的に決まらない性質をどう扱うか」で、(a) 不明とする / (b) 矛盾に倒す / (c) 宣言内に倒す、の 3 つを並べ、**(a) を選んでいます**。理由は「規則 4。b / c は測定を既知の向きに偏らせる。不明の件数は必ず併記する」です（`docs/contradiction_principles.md:60-68`、`:139`）。手引きも、採った原理の表で「解析器は『不』を出す。**人の判定でも、決められなければ『不明』にする**」と書いています（`docs/drafts/final_judging_guide_draft.md:72`）。つまり、解析器に課した「倒さない」を、人の判定にも同じように課しています。
- **AI を補助に使うようになっても変わらない**: D70 の 3 は、AI を事実を調べる補助に使ってよいと改めたときに、「AI には判定させないので、決められないものは人が『不明』と記録する（D40 の芯は変わらない）」と書いています（`docs/decisions.md:3876`）。
- **不明をどう数えるか（D70 の 5）**: 「判定『不明』の扱い（0-5）: 精度の分母から除いた値を主にする（正 / (正 + 誤)）。不明を誤とみなした値（正 / (正 + 誤 + 不明)）と、不明の件数を併記する。片方だけだと、読み手がもう片方を疑うため」（`docs/decisions.md:3917-3918`）。事前登録の下書きも同じ文面です（`docs/drafts/prereg_2_12_draft.md:137`）。
  - ここが「黙って倒さない」の集計での形です。不明を**分母から除く**値と、不明を**誤に寄せた**値の両方を、件数と一緒に出します。寄せるのは集計の段階で、しかも両方を並べるので、誰にでも見えます。
  - 木ごとの精度も同じです。手順書は p_t = c_t / (c_t + w_t) を主にし、「全部不明の木は除き、その数を書く」、不明を誤とみなした p'_t = c_t / (c_t + w_t + u_t) を併記すると書いています（`docs/final_evaluation_procedure.md:1376-1378`）。
- **調べれば分かるものを不明にしない理由**: 手引きには書かれていません。本書の読みでは、精度の主の値は不明を分母から除くので、難しい件を不明にするほど、残った易しい件だけで精度が計算され、見かけが良くなりうるからです（[第 52 章](ch52.md#s52-13) 52.12 節も同じ読み）。
- **20〜30 分という数の理由**: 手引きにも決定の記録にも、この数の根拠は書かれていません（本書が `docs/decisions.md` を「20〜30 分」「30 分」で検索して 0 件。repo の文書で見つかったのは手引きと手順書の 19 節と、教科書の説明だけ）。本書の読み: 判定の全体の見込みは「約 170〜380 時間」（D69 の 6、`docs/decisions.md:3833`。「測っていない」と明記された見込み）で、1 件に際限なく時間をかけると全体が終わらないこと、そして件ごとに調べる深さが大きく違うと判定がぶれること、の 2 つが理由として考えられます。

**例で確かめる**:

（作った例 1 — 調べれば分かるので、不明にしない）

```python
@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def disk_usage() -> str:
    return subprocess.run(["du", "-sh", "."], capture_output=True, text=True).stdout
```

- 解析器は、定数のコマンドなので `spawn_command` の不を出します（`docs/drafts/final_judging_guide_draft.md:209`、`authgap/dparse.py:378`）。
- 人は、`du` の説明書を読めば「大きさを読むだけで、何も書かない」と分かります。15.1 節の SPAWN の行「コマンドが定数なら、そのコマンドが実際に何をするかを調べ、環境を変えるなら反する・変えないなら反しない・分からなければ不明」（`:320`）で、**反しない**に決まります。5 分で決まるので、不明にしません。

（作った例 2 — 調べても決められないので、不明にする）

```python
@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
async def sync_board(board_id: str) -> str:
    r = await client.post("https://rpc.example.invalid/rpc",
                          json={"method": "board.sync", "id": board_id})
    return r.text
```

- 宛先の API の文書がどこにも無く、`board.sync` という名前からも「照会」か「更新」か決まらない、とします。15.1 節の POST の行は「分からなければ不明」です（`:326`）。
- 20〜30 分、開発元のサイト・README・同じ木の別のツールの使い方を調べても決められなければ、`verdict` を `不明`、`unknown_reason` を「相手の API の意味が文書にもコードにも無い: `POST /rpc` の `board.sync`。開発元の README と同じ木の他のツールを調べた」のように書きます。

（作った例 3 — 迷う例。5 分で「原理的に決められない」と分かる）

- 書き先のパスが、木の外のライブラリの関数 `vendor_lib.pick_path()` の戻り値で決まり、そのライブラリのソースも文書も手に入らない、とします。この場合は 20 分待たなくても、決め手がどこにも無いことは分かります。手引きの文面は「20〜30 分調べても決められなければ」なので、「20 分たたないうちに不明にしてよいか」は文面からは直接は決まりません（下の穴 H-7-1）。[第 52 章](ch52.md#s52-13)は「5 分で原理的に決められないと分かったら 20 分待たずに不明にしてかまいません」と読んでいます（本書の読み。手引きの明文ではない）。

**迷いやすいところ**:

- **不と不明を混ぜる**: 解析器の不は人の出発点にすぎません。不の組の多くは、人が調べれば決まります（`:539-547` の「不の理由ごとの調べ方」）。
- **不明は「倒さない」の唯一の形ではない**: 手引きには、時間ではなく**規則で**不明と決めてある行もあります。D2 の「DB に残る設定の変更 → 不明（解析器と同じ）」（`:347`）、D3 の「宛先が local でもグローバルでもない IP → 不明」（`:364`）です。これらは 20〜30 分調べる必要がありません。
- **AI に聞いた時間も 20〜30 分に入るか**: `minutes` には「AI に聞いた時間を含む」と書かれています（`:93-94`、`:184`）。けれども 19 節の 20〜30 分に入るかは書かれていません（穴 H-7-1）。
- **AI の言い切りは決め手にならない**: AI に「この POST 先は照会です」と言われても、自分で資料を開いて確かめられなければ決め手になりません（21 節の 6、`:706-708`。AI が示した資料は自分で開いたものだけを `evidence` に書く、`:566`）。

**承認の前に自分に問うこと**:

1. 自分は、20 分調べて決められない件に出会ったとき、「あと 10 分で決まりそうだ」と「これは原理的に決められない」を見分けられるか。
2. 不明を分母から除く主の値（D70 の 5）が、自分の不明の付け方で見かけ良くなる向きに動きうることを、受け入れられるか。
3. 「20〜30 分」を、1 件の全体の時間で数えるのか、決められない問いに入ってからの時間で数えるのか、自分はどちらのつもりでいるか。
4. 規則で不明と決まっている行（D2 の DB の設定、D3 の予約の IP）を、時間の目安と混同していないか。

**この節で手引きが決めていないこと**:

【穴 H-7-1】**「20〜30 分」の測り方**

- 何が決まっていないか: 目安の時間を、どこから数えるか（1 件の判定を始めたときから / 決められない問いに入ってから）、何を含めるか（AI に聞いた時間、資料を探す時間、中断した時間）、20 分と 30 分のどちらを境にするか。CLAUDE.md 規則 3「閾値には必ず測定手続きと分母の定義を付ける」（`CLAUDE.md:12`）から見ると、測定の手続きが書かれていない閾値です。
- 困る事例（作った例）: 本体と道筋をたどるのに 25 分かかり、そこで初めて「POST の先の意味」という決められない問いに出会った件。1 件の全体で数えるならもう目安を超えています。問いに入ってから数えるなら、まだ 0 分です。
- 考えられる選択肢: (a) 1 件の `minutes` の全体で数える / (b) 決められない問いに入ってからの時間で数え、`note` に書く / (c) 時間は目安にとどめ、代わりに「何を調べたか」を `unknown_reason` に書くことを条件にする。
- 関係する決定: D69 の 6（見込み。`docs/decisions.md:3833`）、手引き 12.3 節（`:91-94`）。

### H-7.2 19 節「不明にしてよい典型」（手引き L575-580）

> 【原文 L575-580】
> 不明にしてよい典型:
>
> - 書き先・宛先・コマンドが、木の外のライブラリの戻り値や実行時の外部の状態で決まり、読み切れない。
> - 相手の API（`POST` の先）の意味が、文書にもコードにも無い。
> - 起動の方法・初期化の場所が読み切れない（第 14.4 節）。
> - 動的な呼び出し（`getattr(obj, name)()`、プラグインの読み込み）で、呼び出し先が決まらない。

**一言で言うと**: 不明にしてよい形の典型が 4 つ並んでいます。どれも「決め手がコードの外にあって、読めない」形です。

**ことばの確認**:

- **木の外のライブラリ**: `pip` で入れる部品など、取得したリポジトリ（木）の中に無いコードです。見落としの判定では、その中は読みません（`:483-484`）。
- **戻り値**: 関数が返す値です。「書き先が戻り値で決まる」は、`path = lib.pick()` のように、どこに書くかを外の関数が決める形です。
- **実行時の外部の状態**: サーバを動かしたときのマシンや相手の状態です。ファイルがあるか、相手がどう応答するか、など。
- **動的な呼び出し**: 呼ぶ関数を、実行するときに名前などで選ぶ形です。`getattr(obj, name)()` は「`obj` の中の、`name` という名前のものを取り出して呼ぶ」という意味です。**プラグインの読み込み**は、設定やフォルダの中身を見て、実行時にモジュールを読み込む形です。
- **起動の方法・初期化の場所**: 14.4 節の話です（[第 49 章](ch49.md#s49-5)）。

**1 文ずつ読む**:

1. 「不明にしてよい典型:」— 「典型」なので、これで全部ではありません（下の穴 H-7-2）。

### H-7.3 19 節の最後「不明の内訳」（手引き L582）

> 【原文 L582】
> 不明の理由は、集計で「不明の内訳」として報告する。

**一言で言うと**: 不明にした理由は捨てずに、集計で「何が決められなかったか」の内訳として報告します。

**ことばの確認**:

- **集計**: 判定が全部終わった後に、数を数えて表にする段階です（手順書の 23 節、段階 8）。
- **内訳**: 全体を種類ごとに分けた数です。「不明 12 件のうち、API の意味が 5 件、打ち切りが 3 件…」のような表です（数は作った例）。

**1 文ずつ読む**:

1. 「不明の理由は、集計で『不明の内訳』として報告する。」— `unknown_reason` 欄（`:181`、`:565`）は、判定の記録だけでなく、論文の数字の材料になります。だから、後で数えられる書き方で書く必要があります（悪い例「よく分からない」）。

**なぜこう決めたのか**: 手引きはこの行に理由を書いていません。本書の読み: 原理 2-a を選んだときの条件が「不明の件数は必ず併記する」でした（`docs/contradiction_principles.md:139`）。件数だけでなく理由の内訳を出せば、読み手は「何が静的にも人にも決められなかったか」を知ることができ、それ自体が研究の結果になります。事前登録の下書きも、矛の判定の件数として「正 / 誤 / 不明」を、見落としの内訳に「不明」を、不の中身の結果に「違反 / 違反でない / 不明」を挙げています（`docs/drafts/prereg_2_12_draft.md:140`、`:144`、`:146`）。

**不明は集計でどう数えられるか**（3 つの判定ごと。手引きの外の文書から）:

| 判定 | 不明の位置 | 数え方 | 出典 |
|---|---|---|---|
| 矛 | `verdict` | 精度の主の値（正 / (正 + 誤)）では分母から除く。不明を誤とみなした値と不明の件数を併記 | `docs/decisions.md:3917-3918`（D70 の 5） |
| 矛（木の単位） | c_t・w_t・u_t の u_t | 木ごとの精度は全部不明の木を除き、その数を書く。不明を誤とみなした p'_t を併記。「本当の矛が 1 件以上あった木」は c_t ≥ 1 の木 | `docs/final_evaluation_procedure.md:1360-1378` |
| 見落とし | `outcome` | 5 つの値の内訳の 1 つ。「不明（打ち切り）」は分けて数える | `docs/drafts/prereg_2_12_draft.md:144`、`docs/decisions.md:3846-3847` |
| 不の中身 | `outcome` | 違反 / 違反でない / 不明の件数 | `docs/drafts/prereg_2_12_draft.md:146` |

表の読み方: 1 行が 1 つの判定の不明の扱いです。たとえば 2 行目は「木を単位にした数字では、不明は u_t として木ごとに数えられ、全部が不明の木は木ごとの精度の平均から除かれ、その数が書かれる」と読みます。

**例で確かめる**（作った例。数は説明のための作りもの）:

ある宣言で、木 X の 3 組が「正・不明・不明」、木 Y の 3 組が「不明・不明・不明」、木 Z の 3 組が「誤・誤・不明」だったとします。

- 件数の精度（主）: 正 1 / (正 1 + 誤 2) = 1/3。不明を誤とみなした値: 1 / (1 + 2 + 5) = 1/8。不明 5 件を併記。
- 木ごとの精度: X は 1/1、Y は除く（全部不明。除いた数 1 を書く）、Z は 0/2。平均 = (1 + 0) / 2 = 0.5。不明を誤とみなした p'_t は X が 1/3、Y が 0/3、Z が 0/3 で、平均 1/9。
- 本当の矛が 1 件以上あった木: X だけ（c_t ≥ 1）。k = 1、n = 3。Y は全部不明なのに、k の数では「本当の矛は無かった」側に入ります（下の穴 H-7-3）。

**迷いやすいところ**:

- **不明の件数は「主の値に入らない」が「消えない」**: 分母から除くのは主の値の計算だけで、件数は必ず並べて出します。
- **見落としの「不明」は、解析器の向きを隠しうる**: 見落としの判定で「不明」にした件は、見落としの数に入りません。見落としの率は誤 clear の向きの数字なので、不明が多いと率が小さく見えます。だから D70 の 2 は打ち切りを「不明（打ち切り）」に分けて数えるとしました（`docs/decisions.md:3846-3847`）。

**承認の前に自分に問うこと**:

1. 自分の付けた不明が、主の精度・見落としの率のそれぞれを、どちらの向きに動かしうるか言えるか。
2. 「全部不明の木」が出たとき、それが木の単位の数字のどこに入り、どこから除かれるか、説明できるか。

**この節で手引きが決めていないこと**:

【穴 H-7-3】**木の単位の主指標 (a) で、不明だけの木がどちらに入るか**

- 何が決まっていないか: 手順書の式では、k は「c_t ≥ 1 の木の数」、n は「判定した木の数」です（`docs/final_evaluation_procedure.md:1362-1364`）。全部が不明の木は n に入り k に入らないので、(a) = k / n では「本当の矛が無かった木」と同じ側に数えられます。式としては決まっていますが、(a) が「下限」である理由として手順書が挙げるのは「1 木 3 件までしか判定しない」「矛の出なかった木の見落としを数えていない」の 2 つで（`:1372-1374`）、**不明は理由に挙がっていません**。また、件数の精度と違い、「不明を正とみなした k」のような併記も決まっていません。手引きの 19 節が言う「不明の内訳」は件数の話で、木の単位の数字への効き方には触れていません。
- 困る事例（作った例）: 上の木 Y。調べても決められなかった 3 件が、論文の主の数字では「違反が見つからなかった木」として数えられます。
- 考えられる選択肢: (a) 今の式のまま、下限の理由に「不明」を足して書く / (b) 不明だけの木の数を (a) と並べて書く / (c) 不明を正とみなした k の値（上限側）も併記する。
- 関係する決定: D70 の 4・5（`docs/decisions.md:3908-3918`）、D67 の 3（`:3779-3782`）。**これは手引きではなく事前登録と手順書の集計の話**なので、承認の前に事前登録の下書きと一緒に見てください。

### H-7.z 確認問題

**問 1**: 「不」と「不明」の違いを、誰の答えか・どの欄に出るか、の 2 点で説明してください。

<details><summary>答え</summary>

「不」は解析器の答えで、行の注記 `contradiction_unknown:<宣言>:<理由>` に出ます（`docs/contradiction_principles.md:147-149`）。「不明」は人の判定の結果で、判定表の `verdict`（矛）や `outcome`（見落とし・不の中身）に書きます。解析器が不でも、人が調べて決められれば不明にしません（H-7.1 節）。

</details>

**問 2**: 矛の判定で、正 6・誤 2・不明 2 だったとき、主の精度と、併記する値は何ですか。

<details><summary>答え</summary>

主の精度は不明を分母から除いた 正 / (正 + 誤) = 6/8。併記するのは、不明を誤とみなした 正 / (正 + 誤 + 不明) = 6/10 と、不明の件数 2 です（D70 の 5、`docs/decisions.md:3917-3918`）。片方だけだと、読み手がもう片方を疑うためです。

</details>

**問 3**: 19 節の「不明にしてよい典型」を 4 つ挙げてください。また、典型に当たらないが手引きのほかの節で不明にする形を 1 つ挙げてください。

<details><summary>答え</summary>

典型: (1) 書き先・宛先・コマンドが木の外のライブラリの戻り値や実行時の外部の状態で決まり読み切れない、(2) 相手の API（POST の先）の意味が文書にもコードにも無い、(3) 起動の方法・初期化の場所が読み切れない、(4) 動的な呼び出しで呼び出し先が決まらない（`:577-580`）。典型に当たらない例: 打ち切りで読み切れない「不明（打ち切り）」（`:507-508`）、手引きのどの規則にも当てはまらない「不明（手引きで決まらない）」（`:733`）、D2 の DB に残る設定の変更（`:347`、規則で不明）など。

</details>

**問 4**: 練習用のサーバの組 1 のラベルが「キャッシュ・状態の保存」ではなく「その他・不明」になるのはなぜですか。何で確かめますか。

<details><summary>答え</summary>

16.1 節の 6 番「キャッシュ・状態の保存」の定義は「ツールの動作のために自分で保存し、後で読み返す」（`:422`）で、このサーバには書いたファイルを読み返す行がどこにも無いからです。`grep -n "CACHE_DIR\|demo_cache" server.py` で 7・11・12 行だけ、ファイルを開く行も 12・32 行の `"w"` だけであることで確かめます。1〜7 番のどれにも当たらないので 8 番です。名前ではなく動作で決めます（`:652-655`）。

</details>

**問 5**: 組 2（`export_note` × `builtins.open` × D2）が正になる理由を、原理の名前を使って説明してください。書き先が固定の `~/notes_export.txt` だったら、解析器と人の答えはどうなりますか。

<details><summary>答え</summary>

書き先 `path` はモデルが決める引数で、原理 3-a（取りうる値の全体）により、既存のファイルを指せば上書きできるので D2 に反します（`:665`、`:344`）。書き先が固定なら、解析器は主体が MODEL でないので `fs_writeout` の不を出します（`authgap/dparse.py:410`）。人は 15.2 節の書き出しの行の後半で、「毎回同じファイルを `"w"` で書き直す」ので 2 回目が 1 回目の内容を消す → 反する、と決めます（作った例。H-7.8 節）。

</details>

**問 6**: 手引きの中で、練習用のサーバの組 1 の道筋が 2 通りに書かれています。どこと、どこですか。どちらがコードと合いますか。

<details><summary>答え</summary>

13 節の手順 D の 5 の例は `server.py:26 → server.py:18 → server.py:12`（`:146`）、20.1 節の組 1 は `server.py:26 → server.py:19 → server.py:12`（`:649`、`:656`）です。`_save_cache` を呼ぶのは 19 行で、18 行は `SELECT` の行なので、20.1 節の書き方がコードと合います（H-7.7 節の【食い違い】）。

</details>

**問 7**: v4 の E00 は、v4 では「到達しない」と「冪等」の 2 つの理由で誤でした。最終評価の規則では、なぜ理由が 1 つになりますか。`error_class` には何を書きますか。

<details><summary>答え</summary>

ccr の初期化は `main()` の中だけ（`ccr/mcp/server.py:678`）で、lifespan は無く、サーバはモジュールの一番上で作られる（`:68`）ので、14.4 節の表の 1 行目で「到達する」になるからです（`:288`）。残る理由は「書く前に内容を確かめ、すでにあれば書かない追記は冪等」（`:398`）なので、`error_class` は E8 です（`:681`）。

</details>

**問 8**: 20.2 節の M59 の理由「ファイルの変更は M58 で別に数えている」は、手引きのどの規則に基づいていますか。コードと照らすと、何が問題になりますか。

<details><summary>答え</summary>

「別の組で数えた変更は、この組では数えない」という規則は、手引きのどこにも書かれていません。また、15.1 節は「子プロセスがそれを受けて何をするかで決める」（`:333`）としますが、子は標準入力を読んだ後に `out_path` にファイルを書きます（`ozon_connector/server.py:187-194`）。M58 が数えるのは親の `os.remove`（`:233`）で、子の書き込みではありません。だから、手引きの文面だけでは M59 の正・誤が 1 つに決まりません（【食い違い】と穴 H-7-8）。

</details>

**問 9**: R04 の条件の種類を、14.3 節の規則を字義どおりに当てて書くとどうなりますか。20.2 節の書き方とどう違い、どの数に効きますか。

<details><summary>答え</summary>

設定の認証の方式が OAuth であること（運用者の設定。`confluence/client.py:36`）と、トークンの期限切れ（失敗・期限切れ）が重なるので、14.3 節の「重なれば全部を `;` で並べる」（`:267-268`）により `運用者の設定;失敗・期限切れ` です。20.2 節は `失敗・期限切れ` だけ（`:684`）。運用者の設定を含むと (B) に数えないので、(B) の併記の数に効きます（R04 は深さ 4 の外なので、主の見落としの数には入りません）。

</details>

**問 10**: 不明の件が多いと、矛の精度の主の値はどちらの向きに動きうりますか。それを抑えるための約束を 2 つ挙げてください。

<details><summary>答え</summary>

主の値は不明を分母から除くので、難しい件を不明にするほど、残った易しい件だけで計算され、見かけが良くなる向きに動きえます（本書の読み）。抑える約束は、(1) 調べれば分かるものを不明にしない（目安 20〜30 分。`:573`）、(2) 不明を誤とみなした値と不明の件数を必ず併記する（D70 の 5）。加えて、不明の理由を書き、集計で内訳を報告します（`:582`）。

</details>
