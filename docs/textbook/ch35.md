## 第 35 章 一般に正しい修正だけを入れる（D61）

> **この章で分かること**:
> - v3 の結果（[第 34 章](ch34.md)）を見た学生が示した方針「**検証データを見て変更するのはきりがないし、研究的によくない。その誤りの修正が一般的に役立つものなら改善して欲しい**」と、それを規則にした D61 の 2 つの基準（正解が v3 と無関係に決まる・一般的に効く）。
> - その基準で、v3 の所見を「直すもの」（G1〜G5）と「直さないもの」（O41 の既知の限界）に振り分けたこと。
> - 規則 → 反例テスト → 実装 → 敵対的レビュー → 改訂 → 取り直し、の順に進めたこと。G1（標準入力はファイルではない）と G2（組み込みの型の値のメソッド）は、レビューで**一般に正しくない**と分かって取り消し、G3（再公開と別名つきの import）と G4（型の注釈による受け手の型）は条件を足して残し、G5（解決できなかった呼び出しの列）は判定を変えない列として入れたこと。
> - 同じ作り話のサーバを 3 つの版（D61 の前・D61 の最初の実装・凍結版）で走らせると、何が見え、何が消えるか。
> - **D61 の約束: v3 の取り直しは回帰の確認だけに使い、v3 の数字の改善を報告しない**。この約束は、凍結版での確かめ直し（D65 の 2）でも「改善としても悪化としても報告しない」として守られたこと。
> - 最終評価の判定で、この章の知識をどう使うか（凍結版に残った形の見分け方、`unresolved_in_tree_calls` の読み方、「データに合わせて規則を変えない」の当てはめ方）。

### 35.1 学生の方針 — 検証データに合わせて直さない

#### 一言で言うと

v3 の結果を見て、次に何を直すかを決める場面で、学生が方針を示しました。
「**検証データを見て変更するのはきりがないし、研究的によくない。その誤りの修正が一般的に役立つものなら改善して欲しい。**」
つまり、v3 の誤りを 1 件ずつ潰すのではなく、**v3 と無関係に正しいと言える直し方だけ**を入れる、という方針です。

#### たとえ話 — 過去問の答えを覚える

数学の過去問を解いて、間違えた問題があったとします。
直し方は 2 通りあります。

1. その問題の答えの数字を覚える。「問 3 の答えは 42」。
2. なぜ間違えたかを調べ、解き方の誤り（たとえば、符号の付け方の思い違い）を直す。

1 は、同じ過去問が出れば満点になりますが、別の問題には効きません。
しかも、過去問の点数は上がるので、「実力が上がった」と勘違いしやすくなります。
2 は、どの問題にも効く直し方です。

v3 の誤りを 1 件ずつ「この木のこの書き方は除く」と直すのは、1 にあたります。
v3 の点数（精度）はいくらでも上がりますが、新しいデータでの実力は上がりません。
学生の方針は、2 だけを入れる、ということです。

#### 小さな例 — 同じ誤りに対する 2 つの直し方

[第 34 章](ch34.md) 34.7 節の形 1（子プロセスの標準入力）を例にします。
agentic-infra の helm / kubectl の起動で、`communicate(input=None)` が `FS_WRITE` の行になり、D1 の誤が 4 件出ました。
これを直す案を 2 つ並べます。

| 案 | 中身 | 何から決まるか |
|---|---|---|
| 案 1 | `helm` と `kubectl` を「標準入力を受けてもファイルを書かないコマンド」の一覧に入れる | v3 に出てきたコマンドの名前（v3 の事例） |
| 案 2 | 子プロセスの標準入力への書き込みは、パイプへの書き込みで、ファイルシステムを変えない。だから `FS_WRITE` の行にしない | パイプとは何かという、OS の仕組み（v3 と無関係） |

表の読み方: 1 行が 1 つの案です。
たとえば 1 行目は「案 1 は、v3 で誤になった 2 つのコマンドの名前を一覧に入れる直し方で、その根拠は v3 の事例そのものだ」と読みます。

案 1 は、v3 の 4 件の誤をちょうど消しますが、v3 に出てこなかったコマンドには何も言えません。
案 2 は、v3 と無関係な理由（パイプの仕組み）から導いた直し方で、どの木にも同じように効く、と**主張できます**。
D61 は、案 2 の型の直し方（G1）を選びました。
ただし、35.5 節で見るとおり、案 2 の主張は敵対的レビューで崩れ、取り消すことになります。

#### 一歩ずつの説明 — 方針の 3 つの部分

1. **「検証データを見て変更するのはきりがない」**: 新しいデータを見るたびに、新しい書き方の木が出てきます。1 件ずつ例外を足していけば、例外の一覧は終わりなく伸びます。
2. **「研究的によくない」**: v3 に合わせて直すと、v3 の数字は「解析器の実力」ではなく「v3 への合わせ込みの度合い」を表すようになります。[第 25 章](ch25.md)で見た「見たデータで測ると甘くなる」の、直し方の側の現れです。
3. **「一般的に役立つものなら改善して欲しい」**: すべてを禁じているのではありません。v3 で**見つけた**誤りでも、その直し方が v3 と無関係に正しく、どの木にも効くなら、入れてよい。見つけるきっかけと、直す理由を分けて考える、ということです。

（出典: `docs/decisions.md:3408-3410`（D61 の見出しと学生の方針）、第 3 版の教科書 `docs/textbook_v3.md:1820`（学生の言葉。decisions.md の文面は要約））

#### なぜそうするのか — 見つけるきっかけと、直す理由を分ける

v3 は、D60 で開発用と決まったデータです。
だから、v3 で欠陥を見つけて直すこと自体は、評価を汚しません（評価は学生の別のデータで行うので）。
それでも合わせ込みを避けるのは、**解析器そのものの質**のためです。

v3 に合わせた例外は、最終評価のデータには効きません。
それどころか、例外が別の木で誤った答えを出すこともありえます。
最終評価で測るのは「新しいデータでの実力」なので、v3 だけに効く直しは、その実力を上げないうえに、壊すおそれだけを持ち込みます。
一般に正しい直し方なら、最終評価のデータにも同じように効くはずです。

#### よくある誤解・つまずき

- **「v3 は開発用なのだから、どう直してもよい」**: D60 で直してよいことにはなりましたが、D61 で「一般に正しい直し方だけ」という歯止めが付きました。開発用でも、合わせ込みは解析器の質を下げます。
- **「v3 で見つけた誤りは、直してはいけない」**: 直してよいのです。ただし、直す**理由**が v3 と無関係でなければなりません。見つけるきっかけが v3 でも、理由が Python の言語の意味やライブラリの仕様なら、直せます。
- **「一般に正しいかどうかは、v3 の誤りが消えたかで分かる」**: 分かりません。v3 の誤りが消えるのは、合わせ込みでも起きます。一般に正しいかは、v3 以外の例（とくに、壊しに行く反例）で確かめます（35.5 節）。

#### 手作業ではどう使うか

最終評価の判定でも、同じ誘惑が来ます。
たとえば、判定の途中で「この形は、手引きの規則だと正になるけれど、どうも違反と言いにくい」と感じる件が続くかもしれません。
そのとき、手引きの規則をその場で変えると、「判定しているデータに合わせて規則を変える」ことになります。
手引きの第 22 節は、手引きで決まらない事例は不明にして事前登録の逸脱に書き、規則を足すなら日時を記録して前後を分けて報告し、主の結果は事前登録した手引きのままにする、と決めています。
これは D61 の考え方を、人の判定に当てはめたものです。

（出典: `docs/drafts/final_judging_guide_draft.md:701-709`（第 22 節））

#### この節のまとめ

学生の方針は「検証データに合わせて直さない。一般的に役立つ直し方だけを入れる」。v3 の誤りを 1 件ずつ潰せば v3 の数字は上がるが、新しいデータでの実力は上がらない。
見つけるきっかけ（v3）と、直す理由（v3 と無関係な正しさ）を分ける。最終評価では、同じ考え方で、判定の手引きをデータに合わせて変えない。

### 35.2 D61 の 2 つの基準と、v3 の所見の振り分け

#### 一言で言うと

D61 は、v3 の所見ごとに、次の**両方**を満たすものだけを直す、と決めました。
(1) **正解が v3 と無関係に決まる**（Python の言語の意味・ライブラリの仕様・既存のカタログから導ける。v3 の件数や個々の事例に合わせた閾値・例外ではない）。
(2) **一般的に効く**（特定の木の書き方への対応ではなく、同じ形がどの木にも現れうる）。
この基準で、直すもの 5 つ（G1〜G5）と、直さないもの 6 つ（O41）に分けました。

#### たとえ話 — 辞書の訂正

辞書を作っていて、読者から「この単語の説明がおかしい」という手紙が来たとします。
訂正してよいのは、その単語の本来の意味（言語の決まり）から正しい説明が決まるときです。
「この読者がこう使っていたから」という理由で説明を変えるのは、辞書の訂正ではなく、1 人の読者への合わせ込みです。
また、訂正は、同じ間違いをしている別の単語にも同じように当てはまるべきです。

D61 の基準 (1) は「本来の意味から決まるか」、基準 (2) は「同じ形の別の単語にも当てはまるか」にあたります。

#### 小さな例 — D61 の基準の文面

> **基準**（v3 の所見ごとに、次の両方を満たすものだけを直す）:
> 1. **正解が v3 と無関係に決まる**: Python の言語の意味・ライブラリの仕様・既存のカタログから導ける。v3 の件数や個々の事例に合わせた閾値・例外ではない。
> 2. **一般的に効く**: 特定の木の書き方への対応ではなく、同じ形がどの木にも現れうる。

（出典: `docs/decisions.md:3412-3415`）

#### 一歩ずつの説明 — 直すもの（G1〜G5）

| 修正 | 中身 | 元になった v3 の所見 | 基準 (1) の根拠（v3 と無関係な正しさ） |
|---|---|---|---|
| **G1** | 子プロセスの標準入力への書き込みは、ファイルシステムを変えない。`FS_WRITE` の行にしない | 誤 4（helm / kubectl） | パイプはファイルではない、という OS の仕組み |
| **G2** | 受け手の値がリテラル（`[]`・`""` など）か組み込みの構築子（`list()`・`bytearray()` など）から来るなら、`x.append(...)` を木の中のクラスのメソッドに結ばない | 誤 2（`bytearray.append`） | そのメソッドは組み込みの型のメソッドである、という Python の意味 |
| **G3** | パッケージの `__init__.py` が `from .mod import name` と再公開しているとき、`name` を `pkg.mod.name` に解決する。別名つきの import（`from m import f as g` の `g()`）は import 先を元の名前 `f` で引く | 見落とし 2（inkscape の再公開） | import の意味そのもの |
| **G4** | 型の注釈で受け手の型を付ける対象を、DB の型だけの手書きの一覧から、sink 表の proxy の受け手の型すべてに広げる（一覧は sink 表から機械的に作る） | 見落とし 1（rovo の `-> httpx.AsyncClient`） | 注釈による型付けの理由は kind によらない。既存のカタログ（sink 表）から導ける |
| **G5** | 名前が木の中の定義に当たるのに降りられなかった呼び出しを、ユニットごとに manifest に出す。**判定には使わない** | 構造的な所見（未解決のツールは黙って「矛盾なし」に見える） | `CLAUDE.md` の規則 4「黙って安全側に倒さない」 |

表の読み方: 1 行が 1 つの修正です。
たとえば 4 行目は「G4 は、型の注釈から受け手の型を付ける仕組みを、DB だけでなく HTTP のクライアントなどにも広げる直しで、きっかけは v3 の rovo の見落としだが、直す理由は『注釈で型を付ける理由は効果の種類によらない』という、v3 と無関係な理屈だ」と読みます。

G3 には、もう 1 つの意味がありました。
別名つきの import を元の名前で引けないことは、最初の解析器からある**既知の欠陥 K7** で、F0a の 98 木のうち 32 木・693 箇所に構文上の候補がありました（[第 24 章](ch24.md) 24.7 節、[第 20 章](ch20.md)）。
テストを書く途中で、別名つきで import した関数が一度も pin されていなかったことが分かり、G3 の一部として直しました。
`tests/test_f0a_defects.py` の `test_known_aliased_from_import_descends_into_in_tree_function` に付いていた `xfail(strict=True)`（「この欠陥がある限り落ちる」という印）を外しました。

（出典: `docs/decisions.md:3417-3444`（直すもの）、`:3434-3437`（K7））

#### 一歩ずつの説明 — 直さないもの（O41）

| v3 の所見 | 件 | 直さない理由 |
|---|---|---|
| 自分で作った一時ファイルの削除を破壊的（D2 の矛）とみなす | 誤 3 | 「破壊的」の定義の読み方の問題で、採った原理（§6）を v3 を見た後に読み替えることになる |
| `shlex.quote` した値だけを渡す固定のコマンド | 誤 2 | 「モデルがコマンドを決める」の読み方と、引用されたコマンドの意味の判断が要る |
| 関数が返すモジュール（`_, m = _load_backend(); m.f()`） | 見落とし 1 | 珍しい書き方への対応になる |
| 深さの上限 | 見落とし 2 | O38 と同じ。論文で深さを変えて評価する |
| sink の語彙に無いライブラリ（zvec・arcpy など） | 見落とし 1 | sink の語彙は月 3 に凍結した（O39 と同じ扱い） |
| `flock` のための `"a"` | D4 の誤 1 | （記録は理由を個別に書いていない。一般に正しい直し方が無いものとして O41 に入れた） |

表の読み方: 1 行が 1 つの所見です。
たとえば 1 行目は「同じ呼び出しで作った一時ファイルの削除を D2 の矛にする誤 3 件は、直すと『破壊的』という原理の読み方を v3 を見た後で変えることになるので、直さない」と読みます。

1 行目は、とくに大事です。
MCP の仕様の「追加か破壊か」で読めば、同じ呼び出しで作ったものを消すのは破壊的ではありません。
けれども、解析器の判定表は、学生が件数を見ずに選んだ原理から機械的に導いたものです（[第 17 章](ch17.md)）。
v3 の誤を見た後で、その原理の読み方を変えれば、それは「結果を見てから基準を選ぶ」ことになります（[第 22 章](ch22.md)）。
だから解析器は直さず、人の判定の側で「D2 では、同じ呼び出しで作ったものの削除は反しない（E2）」と扱う、という形になりました（手引きの 15.2 節）。

D61 は、最後にこう書いています。
「**この後は v3 を見て直さない。** G1〜G5 を終えたら最終凍結し、学生の評価に渡す。」

（出典: `docs/decisions.md:3446-3457`（直さないもの）、`docs/open_questions.md:1059-1073`（O41））

#### なぜそうするのか — 2 つの基準が両方要る理由

基準 (1) だけでは足りません。
たとえば「v3 の lore の書き方に対応する」直しは、Python の意味から正しく導けても、lore の書き方にしか効かないなら、基準 (2) を満たしません。
合わせ込みの度合いは低くても、v3 に偏った直しになります。

基準 (2) だけでも足りません。
たとえば「`opaque(unresolved)` の効果だけに支えられた矛は不にする」は、どの木にも効きますが、その線引きが正しいかは v3 の件数を見て決めることになります（[第 34 章](ch34.md) 34.8 節の数字では、正しい矛の大半を捨てます）。
v3 の件数に合わせた閾値は、基準 (1) を満たしません。

両方を満たして初めて、「v3 で見つけたが、v3 と無関係に、どの木にも正しい直し方」と言えます。

#### よくある誤解・つまずき

- **「直さないもの＝重要でないもの」**: 違います。一時ファイルの削除（誤 3）は、v3 の誤の中で 2 番目に多い形でした。重要でも、一般に正しい直し方が無い（原理の読み替えになる）ので直さなかったのです。直さないものは、既知の限界として記録し、論文に書きます（[第 42 章](ch42.md)）。
- **「G1〜G5 は、v3 の誤と見落としを全部消すための直し」**: 違います。G1・G2 は誤、G3・G4 は見落とし、G5 は構造的な所見に対応しますが、v3 の誤の 4 つの形のうち 2 つ（一時ファイル・`shlex.quote`）と、見落とし 7 件のうち 4 件（関数が返すモジュール・深さ 2・語彙）は、最初から直す対象に入っていません。
- **「既知の欠陥 K7 を直したのは、v3 に合わせたから」**: K7 は最初の解析器から記録されていた欠陥で、v3 とは無関係に分かっていたものです。v3 で G3 のテストを書く途中で改めて気づき、import の意味から決まる直し方なので入れました。

#### 手作業ではどう使うか

- 判定で O41 の形（同じ呼び出しの一時ファイルの削除・`shlex.quote` の固定コマンド・`flock` の `"a"`）に出会ったら、それは「解析器が直さずに残した既知の誤りの形」です。手引きの規則（15.2 節の E2、17 節の E7・E8）で判定します。
- 判定の `note` や、判定の後の限界の整理で、「これは O41 の形」と書いておくと、論文の限界の節を書くときに、既知の限界と新しく見つけた限界を分けられます。
- 判定の途中で「この誤りは解析器を直せば消える」と思っても、最終評価では直しません。直すべきかの議論は、`docs/open_questions.md` に限界として書くところまでです（手引きの第 22 節の 4）。

#### この節のまとめ

D61 の基準は (1) 正解が v3 と無関係に決まる、(2) 一般的に効く、の両方。直すものは G1〜G5、直さないもの（一時ファイルの削除・`shlex.quote` の固定コマンド・関数が返すモジュール・深さ・語彙・`flock`）は O41 に既知の限界として書いた。
とくに一時ファイルの削除は、直すと原理を v3 の後に読み替えることになるので直さず、人の判定の側で E2 として扱う。D61 は「この後は v3 を見て直さない」と結んだ。

### 35.3 D61 の進め方 — 規則・反例テスト・実装・レビュー・改訂

#### 一言で言うと

D61 は、[第 23 章](ch23.md)の「直すときの手順」どおりに進みました。
**規則を先にコミット → 反例テストを先にコミット（直す前の版で落ちることを確かめる）→ 実装 → 敵対的レビュー → 改訂の規則とテストを先にコミット → 改訂の実装 → 取り直しと突き合わせ → 結果と逸脱の記録 → 凍結**、です。
とくに、レビューで穴が見つかった後も、いきなりコードを直さず、**改訂の規則とテストを先に**コミットしています。

#### たとえ話 — 建物の改修工事

建物を改修するとき、まず設計図（規則）を書き、検査の項目（テスト）を決めてから工事（実装）をします。
工事の後、別の検査員が、わざと弱そうな所を叩いて回ります（敵対的レビュー）。
弱い所が見つかったら、その場で継ぎはぎせず、設計図を描き直し、検査の項目を足してから、工事をやり直します。
こうすると、「何を直すつもりだったか」と「何が直ったか」を、後から誰でも照らし合わせられます。

#### 一歩ずつの説明 — 各段階の意味

1. **規則を先に（`cd74f04`）**: 何を、どういう基準で直すかを、コードを書く前に文章で固定しました。後で「実装してみたらこうなったので、こういう規則だったことにする」ができなくなります（[第 23 章](ch23.md) 23.2 節）。
2. **反例テストを先に（`1100319`）**: テストのファイル `tests/test_fix_d61.py` の冒頭には、こう書かれています。「**期待値はこのテストで、`authgap/` を直す前に書いた。** v3 の事例ではなく、言語の意味・ライブラリの仕様から決まる形だけを入れる（D61 の基準）。『変えない』側を反例として入れる。」

5. **改訂の規則とテストを先に（`a0d9304`・`b78315a`・`155aa7d`）**: レビューの結果を、まず規則の文章（D61 の改訂）にし、そのテストを書いて落ちることを確かめてから、実装しました。改訂の追記（`155aa7d`）は、改訂版をレビューの再現の木**すべて**で比べ直して見つけた穴です。
6. **改訂の実装（`94c40b4`）**: これが D61 の最終の版です。
7. **取り直しと突き合わせ、記録（`89101ed`）**: v2 を走査し直し（run20）、run18 と突き合わせました。v3 も走査し直しましたが、それは回帰の確認だけに使いました（35.8・35.9 節）。結果を D61 の結果として書き、事前登録に逸脱 #23 として記録しました。

（出典: `tests/test_fix_d61.py:1-5`（冒頭の説明）、`docs/decisions.md:3459-3461`（レビューの方法）、`:3487-3491`（改訂の追記）、`:3505-3506`（D61 の経過））

#### なぜそうするのか — 規則とテストを先に書く理由

直す前に規則とテストを書くと、2 つのことが守られます。

1. **直した結果に合わせて、直す目的を書き換えられない**。規則がコミット済みなので、「何を直すつもりだったか」が後から動きません。
2. **テストが本当に効いているかが分かる**。直す前の版でテストが落ちることを確かめるので、「直す前から通ってしまうテスト」（何も確かめていないテスト）を避けられます。

レビューの後の改訂でも同じ順序を守ったのは、改訂も「直し」の 1 つだからです。
改訂の実装だけを急ぐと、改訂が新しい穴を作っても気づけません。
実際、改訂の追記（`155aa7d`）は、改訂版をもう一度すべての再現の木で比べて初めて見つかりました。

#### よくある誤解・つまずき

- **「テストを先に書くのは、テストを書くのが好きな人の流儀」**: この研究では、テストを先に書くことが「結果に合わせて目的を変えない」ための仕組みです。好みの問題ではありません。
- **「レビューで見つかった穴は、すぐに直すのがよい」**: すぐに直すと、直しの目的が文章に残らず、直しが新しい穴を作っても気づきにくくなります。D61 では、改訂の規則とテストを先にコミットしてから直しました。
- **「レビューの再現の木は v3 の木」**: 違います。決定の記録は「入力を作って」2 つの版を走らせ比べた、と書いています。再現の木は、反例を作るために書いた小さな木で、改訂に挙がった例（`env python3`・`tee /etc/app.conf`・`DOCS[name].strip().save()` など）も、言語やコマンドの意味から作った形です。

#### 手作業ではどう使うか

最終評価でも、同じ「先に書く」の順序を守ります。

- 判定の規則（手引き）と事前登録 §2.12 を、データに触れる前に封をします（第 22・46 章）。
- 判定の対象の一覧を、判定の前にコミットします（段階 6）。
- 判定で手引きの規則に無い事例が出たら、その場で規則を足さず、まず不明にして逸脱に書きます（手引きの第 22 節）。

D61 で解析器に対して行った順序を、判定の規則に対して行う、と考えると覚えやすいでしょう。

#### この節のまとめ

D61 は、規則 → 反例テスト（直す前の版で落ちることを確かめる）→ 実装 → 敵対的レビュー → 改訂の規則とテスト → 改訂の実装 → 取り直しと記録、の順に進んだ。
反例テストは v3 の事例ではなく言語の意味から作り、「変えない」側の例も入れた。レビューの後も、規則とテストを先にコミットしてから直した。

### 35.4 3 つの版で、同じサーバを走らせる — G1・G2・G3 の前と後

#### 一言で言うと

D61 で何が起きたかを、作り話のサーバ 1 つで確かめます。
**D61 の前**（`1100319`）・**D61 の最初の実装**（`672f0f0`）・**D61 の改訂後と凍結版**（`94c40b4`・`analyzer-freeze-3`）の 3 つの版で走らせると、G1・G2 は「一度消えて、また戻った」、G3 は「見えなかったものが見えるようになり、そのまま残った」ことが分かります。

#### たとえ話 — 同じ患者を、3 つの時期の検査機器で診る

新しい検査機器を導入するとき、同じ患者を、古い機器・新しい機器の試作版・新しい機器の完成版で診てみると、それぞれの機器が何を見つけ、何を見落とすかがはっきりします。
同じ患者を使うので、違いは機器の違いだけです。

#### 小さな例 — 作り話のサーバ

本書の執筆時に、次のサーバを、3 つの版の `authgap/` を `git archive` で取り出して走らせました。

`helpers.py`:

```python
1  from pathlib import Path
2
3
4  def save_note(text):
5      Path("/tmp/notes.txt").write_text(text)
```

- 1 行目: ファイルを扱う部品 `Path` を読み込みます。
- 4〜5 行目: 受け取った文字列を `/tmp/notes.txt` に書き込む関数です。

`server.py`:

```python
1   import asyncio
2   from pathlib import Path
3
4   from mcp.server.fastmcp import FastMCP
5
6   from helpers import save_note as persist
7
8   mcp = FastMCP("toy")
9
10
11  class AuditLog:
12      def append(self, event):
13          Path("/tmp/audit.log").write_text(str(event))
14
15
16  @mcp.tool(annotations={"readOnlyHint": True})
17  def make_png(width: int) -> bytes:
18      rows = bytearray()
19      rows.append(0)
20      return bytes(rows)
21
22
23  @mcp.tool(annotations={"readOnlyHint": True})
24  def remember(text: str) -> str:
25      persist(text)
26      return "ok"
27
28
29  @mcp.tool(annotations={"readOnlyHint": True})
30  async def helm_history(release: str) -> str:
31      proc = await asyncio.create_subprocess_exec(
32          "helm", "history", release, stdout=asyncio.subprocess.PIPE
33      )
34      out, _ = await proc.communicate(input=None)
35      return out.decode()
```

- 6 行目: `helpers.py` の `save_note` を、**別名** `persist` で読み込みます（別名つきの import）。
- 11〜13 行目: 木の中のクラス `AuditLog` です。`append` というメソッドは、ファイルに書き込みます。
- 16〜20 行目: ツール `make_png`。18 行目で組み込みの `bytearray` を作り、19 行目でその `append` を呼びます。これはメモリの中の操作で、ファイルには何も書きません（[第 34 章](ch34.md)の形 3 を短くしたもの）。
- 23〜26 行目: ツール `remember`。25 行目で `persist`（本当は `save_note`）を呼び、ファイルに書き込みます。`readOnlyHint: True` と宣言しているので、本当の違反です。
- 29〜35 行目: ツール `helm_history`。31〜33 行目で `helm history <release>` を起動し、34 行目で標準入力に**何も流さずに**（`input=None`）終わるのを待ちます（[第 34 章](ch34.md)の形 1 を短くしたもの）。

3 つのツールは、どれも `readOnlyHint: True`（D1）です。
人が判定すると、本当に D1 に反するのは `remember` だけです。

#### 一歩ずつの説明 — 3 つの版の出力

| ツール | 本当は | D61 の前（`1100319`） | D61 の最初の実装（`672f0f0`） | D61 の改訂後（`94c40b4`）と凍結版 |
|---|---|---|---|---|
| `make_png` | 書き込みなし | `AuditLog.append` に結び、13 行目の書き込みで **D1 の矛**（確度 `opaque(unresolved)`）→ **誤警報** | 効果なし（G2 で組み込みのメソッドと判断） | **D1 の矛**に戻る（G2 を取り消した）→ 誤警報 |
| `remember` | 書き込みあり（違反） | **効果なし** → **誤 clear**（K7） | `helpers.py:5` の書き込みで **D1 の矛**（確度 `resolved`） | **D1 の矛**のまま（G3 は残した） |
| `helm_history` | 書き込みなし | 34 行目の `pipe:communicate` を `FS_WRITE` にして **D1 の矛** → 誤警報。起動そのものは不（`spawn_command`） | `pipe:communicate` の行が消える（G1）。起動は不のまま | **D1 の矛**に戻る（G1 を取り消した）→ 誤警報 |

表の読み方: 1 行が 1 つのツールです。
たとえば 2 行目は「`remember` は本当にファイルを書くツールだが、D61 の前の解析器は別名つきの import をたどれず、効果を 1 つも出さなかった（誤 clear）。D61 の最初の実装で書き込みが見えるようになり、改訂後も凍結版もそのまま見えている」と読みます。

（出典: 本書の執筆時に `git archive 1100319 authgap`・`git archive 672f0f0 authgap`・`git archive 94c40b4 authgap`・`git archive analyzer-freeze-3 authgap` で取り出した 4 つの版で走査したもの。`94c40b4` と凍結版は、このサーバで同じ出力だった）

#### 一歩ずつの説明 — 表から読み取れること

1. **G3 は、純粋な改善だった**: `remember` の誤 clear が消え、改訂後も残りました。別名つきの import を元の名前で引くのは import の意味そのもので、一般に正しい直し方でした。
2. **G1・G2 は、このサーバでは改善に見えた**: 最初の実装では、`make_png` と `helm_history` の誤警報が消えました。このサーバだけを見れば、G1・G2 は「良い直し」に見えます。
3. **それでも G1・G2 は取り消された**: 改訂後と凍結版では、2 つの誤警報が戻っています。なぜなら、G1・G2 は、**このサーバでは**正しく働いても、**別の書き方のサーバでは**本当の効果を消す（誤 clear を作る）ことが、敵対的レビューで分かったからです（35.5 節）。
4. **だから凍結版には、誤警報の 2 つの形が残っている**: [第 34 章](ch34.md)の形 1（標準入力）と形 3（組み込みの型のメソッド）は、凍結版でも矛として出ます。これが、最終評価の判定で E5・E3 を疑う理由です。

#### なぜそうするのか — 誤警報が増えても、誤 clear を作らない側を選ぶ

G1・G2 を取り消すと、誤警報（`make_png`・`helm_history`）が戻ります。
精度の数字は下がる方向です。
それでも取り消したのは、誤警報と誤 clear の重さが違うからです（[第 21 章](ch21.md)）。

- 誤警報は、人が判定すれば「誤」と分かります。最終評価の精度の判定で見つかり、数えられます。
- 誤 clear は、解析器が何も言わないので、人が見落としの抜き取りで偶然選ばない限り、気づかれません。

「黙って安全側に倒さない」（`CLAUDE.md` の規則 4）を守るには、疑わしいときに「効果がありうる」と言う側に倒す必要があります。
G1・G2 は、疑わしいときにも「効果は無い」と言う側に倒していたので、取り消しました。

#### よくある誤解・つまずき

- **「`make_png` の誤警報が戻ったのは、凍結版の欠陥が増えたということ」**: D61 の前と同じ状態に戻っただけです。新しい欠陥ではなく、O41 に記録した既知の限界です。
- **「`remember` が D61 の前に効果なしだったのは、深さが足りなかったから」**: 違います。`save_note` は深さ 1 です。原因は、別名 `persist` を元の名前 `save_note` で引けなかったこと（K7）でした。
- **「3 つの版で出力が違うのだから、どれが正しいかは分からない」**: 人が原ソースを読めば分かります。本当に違反なのは `remember` だけで、`make_png` と `helm_history` は違反ではありません。解析器の版ごとの違いは、どの版がどの向きの誤りを持つかを示しています。

#### 手作業ではどう使うか

- 判定で、道筋（`witness_chain`）に `AuditLog.append` のような「組み込みの型のメソッドと同じ名前の、木の中のメソッド」があり、確度が `opaque(unresolved)` なら、受け手の正体（`bytearray()`・`list()`・`[]` などから来ていないか）を確かめます。組み込みなら誤（E3）です。
- 効果の行が `pipe:communicate` / `pipe:write` なら、標準入力に本当にデータを流しているか、流すならそのコマンドが受け取ったデータで何をするかを確かめます。何も流さない、または流しても環境を変えないなら誤（E5）です。
- 別名つきの import や、パッケージの `__init__.py` を通る道筋は、凍結版ではたどれるようになっています（G3）。道筋の関数の名前は、呼び名（`persist`）ではなく本名（`save_note`）で記録されるので、判定で道筋をたどるときは、本体の中では呼び名で、呼び出し先のファイルの中では本名で探します（[第 20 章](ch20.md)）。

#### この節のまとめ

同じサーバを 3 つの版で走らせると、G3（別名つきの import）は誤 clear を消して残り、G1（標準入力）・G2（組み込みの型のメソッド）は誤警報を一度消したが、取り消して戻った。
凍結版は、標準入力と組み込みの型のメソッドの形で誤警報を出すが、誤 clear は作らない側に倒している。判定では、この 2 つの形に出会ったら E5・E3 を疑う。

### 35.5 G1・G2 を取り消した — 「一般に正しい」は、1 つの反例で崩れる

#### 一言で言うと

G1「子プロセスの標準入力はファイルではない」と G2「受け手の値の形が組み込みの型なら、組み込みのメソッドだ」は、どちらも「**どの木でも正しい**」という主張でした。
敵対的レビューは、それぞれに反例を次々に示しました。
「どの木でも正しい」という主張は、反例が 1 つあれば崩れます。
だから 2 つとも取り消し、コードを D61 の前の形に戻しました。

#### たとえ話 — 「白鳥はみな白い」

「白鳥はみな白い」という主張は、白い白鳥を何羽見つけても証明できません。
けれども、黒い白鳥を 1 羽見つければ、崩れます。
「この直し方は、どの木でも正しい」も同じです。
v3 の誤を何件消しても証明にはなりませんが、本当の効果を消す木を 1 つ作れれば崩れます。
敵対的レビューは、黒い白鳥を探しに行く作業です（[第 24 章](ch24.md)）。

#### 小さな例 1 — G1 の実装の形と、最初のつまずき

G1 の実装の形は、次のように決めてありました。

> `effects._pipe` は argv0 がインタプリタでない（または分からない）とき「FS_WRITE(content) 相当の情報行」を出していた。**argv0 が定数でインタプリタでなく、`shell` が False と分かるときだけ**これを出さない。

つまり、「起動するコマンド（argv0）がはっきり分かっていて、`python` や `bash` のようなインタプリタ（コードを読んで実行するプログラム）ではなく、シェルも通さない」ときだけ、標準入力の行を出さない、という狭い直し方です。

ところが、最初の実装は、argv0 や `shell` が**決まらない**ときにも行を消していました。
すると、インタプリタかもしれない子プロセスへのコードの流し込みが、跡形もなく消えました（新しい誤 clear）。
これは、既存のテスト `test_known_pipe_precondition` が落ちて分かりました。
決まらないときに `EXEC`（コードの実行）を出す案もありましたが、判定表では `EXEC` は常に矛なので言い過ぎになり、表の変更が要ります。
そこで、決まるときだけに狭めました。

（出典: `docs/decisions.md:3420-3427`）

#### 小さな例 2 — G1 を崩した反例

狭めた G1 も、レビューで崩れました。
argv0 が定数で、インタプリタの一覧に**無い**コマンドでも、標準入力のデータはコードの実行やファイルの書き込みに届くからです。
決定の記録が挙げた例を、意味とともに並べます。

| 例 | 標準入力のデータで何が起きるか |
|---|---|
| `env python3` | `env` はインタプリタの一覧に無いが、`python3` を起動する。データは Python のコードとして実行される |
| `/usr/bin/env bash` | 同じく、`bash` のスクリプトとして実行される |
| `sudo sh` | `sudo` を通して `sh` を起動する。データはシェルのコマンドとして実行される |
| `xargs -0 rm` | 標準入力から受け取った名前のファイルを消す |
| `tee /etc/app.conf` | 標準入力をそのまま `/etc/app.conf` に書く |
| `zsh`・`ruby` | インタプリタの一覧に入っていなかった別のインタプリタ |
| `sqlite3 db` | 標準入力の SQL を DB に対して実行する |
| `ssh host bash -s` | 別のマシンで `bash` を起動し、データをスクリプトとして実行する |
| `patch -p1` | 標準入力の差分で、ファイルを書き換える |
| `executable="/bin/bash"` | `subprocess` の引数で、実際に起動するプログラムを別に指定する |
| `uv run python -` | `uv` を通して `python` を起動し、標準入力をコードとして読む |

表の読み方: 1 行が 1 つの反例です。
たとえば 5 行目は「`tee /etc/app.conf` は、標準入力に流したデータを、そのまま `/etc/app.conf` というファイルに書くので、標準入力への書き込みがファイルの書き込みになる」と読みます。

決定の記録の結論は、「以前の『FS_WRITE(content) 相当の情報行』は、**子プロセスがデータで何をしうるかの保守的な上界**として正しかった。**取り消す**（コードを戻す）」でした。
v3 の誤 4 件（helm / kubectl への `communicate(input=None)`）は、既知の限界（O41）に戻しました。

（出典: `docs/decisions.md:3463-3467`、`docs/open_questions.md:1068-1070`）

#### 小さな例 3 — G2 を崩した反例

G2 は、「受け手の値がリテラルや組み込みの構築子から来るなら、そのメソッドを木の中の同名のメソッドに結ばない」という直し方でした。
レビューは、「値の**形**は、型の**証明**ではない」ことを示しました。
反例の 1 つを、テストのファイルから短くして示します。

```python
1   class Remote:
2       def upload(self, v):
3           with open("/tmp/up", "w") as f:
4               f.write(v)
5
6
7   class Server:
8       def __init__(self):
9           self.remote = ""
10
11      def connect(self):
12          self.remote = Remote()
13
14      def send(self, x):
15          self.remote.upload(x)
```

- 1〜4 行目: `Remote` は、`upload` でファイルに書き込むクラスです。
- 8〜9 行目: `Server` を作るとき、`self.remote` には、とりあえず空の文字列 `""` を入れておきます（置き場所としての初期値）。
- 11〜12 行目: `connect` を呼ぶと、`self.remote` を本物の `Remote` のオブジェクトに入れ替えます。
- 14〜15 行目: `send` は、`self.remote.upload(x)` を呼びます。`connect` の後なら、これは `Remote.upload` で、ファイルに書き込みます。

G2 は、9 行目の `""`（文字列のリテラル）を見て、「`self.remote` は文字列だから、`upload` は組み込みの型のメソッドだ。木の中の `Remote.upload` には結ばない」と判断しました。
その結果、3〜4 行目の本当の書き込みが消えました（誤 clear）。

決定の記録は、ほかにも次の形で本当の効果を消したと書いています。

- 未知の受け手への `strip()` などの変換の結果（`DOCS[name].strip().save()`。`DOCS[name]` が木の中の `Document` なら、`strip()` の結果も `Document` でありうる。[第 24 章](ch24.md) 24.1・24.4 節）
- `+` の結果（文字列どうしの `+` に見えても、木の中のクラスが `+` を定義していれば別の型になりうる）
- 大域の `SINK = ""` の後で、木の中のオブジェクトに束縛し直す形
- 閉包・`global`・`builtins.list = ...`・`for list in ...` による `list` という名前の束縛し直し（`list()` が組み込みの `list` とは限らない）

結論は「G2 は健全でない。**取り消す**（コードを戻す）」でした。
v3 の誤 2 件（`bytearray.append`）は、既知の限界（O41）に戻しました。

（出典: `docs/decisions.md:3468-3471`、`tests/test_fix_d61.py` の `G2_REVIEW`（`placeholder_field` の作例）、`docs/open_questions.md:1071-1072`）

#### 一歩ずつの説明 — なぜ「狭めて残す」ではなく「取り消す」なのか

G1 も G2 も、反例を 1 つずつ除外する条件を足せば、残せたかもしれません。
たとえば G1 なら「`env`・`sudo`・`xargs`・`tee`… は除く」、G2 なら「置き場所の `""` は除く」です。
けれども、それをしなかった理由は 2 つあります。

1. **反例の一覧は、閉じていない**: G1 の反例は、インタプリタを起動するコマンドや、標準入力をファイルに書くコマンドなら何でもなりえます。一覧に入れ忘れたコマンドがあれば、そこで誤 clear が起きます。一覧を作る作業そのものが、「見つけた例に合わせて足していく」こと（D61 が避けたかったこと）になります。
2. **以前の扱いが、もともと正しかった**: G1 の前の「ファイル書き込み相当の情報行」は、「子プロセスがデータで何をしうるかの保守的な上界」として、一般に正しい扱いでした。G2 の前の「型で裏付けられない末尾名の解決は、確度 `opaque(unresolved)` で降りる」も、`CLAUDE.md` の落とし穴（「末尾名だけの解決を『やめる』と真の経路が消える」）が言うとおりの、正しい扱いでした。直す前が正しかったのだから、戻すのが正しい直し方です。

#### なぜそうするのか — 取り消しも、記録に残る成果

G1・G2 を取り消したことで、凍結版に誤 clear を入れずに済みました。
代わりに、v3 の誤 6 件（標準入力 4・`bytearray.append` 2）は、凍結版に残る誤警報の形として、O41 に記録されました。
誤警報は人の判定で見つかるので、精度の数字には表れますが、隠れはしません。
「直そうとしたが、一般に正しくないと分かったので取り消した」という経緯そのものが、論文の限界の節の材料になります。

#### よくある誤解・つまずき

- **「G1・G2 は、v3 の誤警報を減らしたのだから成功だった」**: D61 の成功の基準は、v3 の誤警報が減ったかではなく、一般に正しいかです。一般に正しくなかったので、取り消しが正しい判断でした。
- **「反例は珍しい書き方だから、無視してよい」**: `tee` や `sudo sh` は珍しくありません。それに、解析器が誤 clear を作ると、人の判定でも気づきにくくなります。珍しさで無視するのは、「黙って安全側に倒す」ことです。
- **「取り消したのだから、v3 の誤 6 件は解決していない」**: そのとおりで、解決していません。既知の限界として記録し、凍結版でも残っています（v4 でも同じ類が出ました。[第 37 章](ch37.md)）。

#### 手作業ではどう使うか

- 判定で `pipe:communicate` / `pipe:write` の矛に出会ったら、上の反例の表を思い出します。起動するコマンドが `tee`・`sudo sh`・`xargs rm`・`sqlite3` などなら、標準入力のデータは本当に環境を変えうるので、誤ではなく正になりえます。`helm history` のように値を読むだけのコマンドで、しかも何も流していないなら誤（E5）です。
- 道筋に組み込みの型と同じ名前のメソッドがあるとき、受け手の正体を確かめる際は、初期値だけを見て決めないようにします。上の `self.remote = ""` のように、後で本物のオブジェクトに入れ替わることがあります。入れ替える箇所を grep で探し、ツールの呼び出しのときに何が入っているかを確かめます。

#### この節のまとめ

G1（標準入力はファイルではない）は `env python3`・`tee`・`xargs rm` などの反例で、G2（値の形が組み込みなら組み込みのメソッド）は `self.remote = ""` の置き場所や `strip()` の結果などの反例で崩れた。
反例の一覧は閉じておらず、以前の扱い（保守的な上界・`opaque(unresolved)` で降りる）がもともと正しかったので、狭めずに取り消した。v3 の誤 6 件は O41 に戻り、凍結版に誤警報の形として残っている。

### 35.6 G3・G4 を条件つきで残した — 穴を塞ぐ条件

#### 一言で言うと

G3（パッケージの `__init__.py` の再公開と、別名つきの import）と G4（型の注釈による受け手の型）は、直し方そのものは import や注釈の意味から正しく導けました。
けれども、レビューで「**1 つに確定してはいけない場面で、1 つに確定してしまう**」穴が見つかりました。
そこで、確定してよい場面を狭める条件を足して残しました。
確定できないときは、黙って 1 つを選ばず、「分からない」の印（`opaque(unresolved)` と G5 の列）を残します。

#### たとえ話 — 転送の届け出

郵便の転送の届け出が 1 通だけなら、その住所に届ければよいでしょう。
けれども、同じ人について「A に転送」と「B に転送」の 2 通の届け出があり、どちらが有効か分からないなら、勝手に片方に届けてはいけません。
「どちらか分からない」と記録して、確かめるべきです。

G3 の穴は、`__init__.py` の中で同じ名前が 2 回以上決められている（届け出が 2 通ある）のに、片方に確定してしまう形でした。

#### 小さな例 1 — G3 の効き目と穴（作り話）

本書の執筆時に、次の 2 つの形を、3 つの版で走らせました。
どちらも、`app/main.py` の中で `from .tools import save` として `save(p)` を呼ぶ、`readOnlyHint: True` のツール `remember` です。
木の中には、ほかに `app/other.py` にも `save` という名前の関数（何もしない）があります。

形 A（再公開が 1 つ）の `app/tools/__init__.py`:

```python
1  from .impl import save
```

- 1 行目: 同じパッケージの `impl.py` の `save` を、`app.tools` の名前として再公開します。`impl.py` の `save` は、ファイルに書き込みます。

形 B（`try` / `except` の予備の import）の `app/tools/__init__.py`:

```python
1  try:
2      from .fast import save
3  except ImportError:
4      from .slow import save
```

- 1〜2 行目: まず `fast.py` の `save` を読み込もうとします。`fast.py` の `save` は、ファイルに書き込みます。
- 3〜4 行目: 読み込みに失敗したら（`ImportError`）、代わりに `slow.py` の `save`（何もしない）を読み込みます。
- つまり、`save` という名前が 2 回束縛されうる形です。ふつうの環境では 2 行目が成功するので、実行時の `save` は `fast.save`（書き込む）です。

| 形 | D61 の前（`1100319`） | D61 の最初の実装（`672f0f0`） | D61 の改訂後と凍結版 |
|---|---|---|---|
| A（再公開が 1 つ） | 効果なし（`save` の候補が木の中に 2 つあり、決められない） | `impl.py` の書き込みで **D1 の矛** | **D1 の矛**（同じ） |

表の読み方: 1 行が 1 つの形です。

#### 一歩ずつの説明 — G3 の 3 つの条件

D61 の改訂は、G3 を次の条件で残しました。

1. **再公開をたどるのは、束縛がちょうど 1 つのときだけ**: 再公開するモジュール（`__init__.py`）で、その名前の束縛が**ちょうど 1 つ**で、それが**モジュール直下の `from ... import`** であり、関数の中で書き換えられないときだけ、たどります。形 B（`try` / `except`）のように 2 つあるとき、`if` で分かれた条件つきの import、import の後で代入し直す形（`save = _danger`）は、たどりません。
2. **たどる先は、その `ImportFrom` の `level` で解く**: `from .x import f` の点の数（`level`）が 1 以上なら相対 import、0 なら絶対 import として、厳密に解きます。`__init__.py` の中の絶対 import（`from helpers import run`）を、うっかり相対（同じパッケージの `helpers`）として解く穴があったからです。
3. **読む側で呼ぶ名前が書き換えられるなら、確定しない**: 読む側のモジュールで、呼ぶ名前（別名つきなら別名）が 2 回以上束縛されるか、関数の中で書き換えられる（`global g; g = danger` など）なら、候補を「あいまい」にします（全候補へ降りて `opaque`）。

（出典: `docs/decisions.md:3472-3480`）

1. **G4 の条件**: 受け手の型のうち、モジュールの部分が木の中に無い dotted 名（`requests.Session` のような外部の型）は、木の中のクラスへの絞り込みと、継承の家族に使いません。外部の型のオブジェクトが、木の中の同名のクラスのインスタンスであることはないからです。決定の記録は、この条件が D50 の DB の型にも同じくかかる（一般の規則）と書いています。

#### なぜそうするのか — 「確定」の条件を狭め、確定できないときは印を残す

G3・G4 の穴は、どちらも「1 つに確定する」ときの誤りでした。
確定すると、確度が `resolved`（読み切れた）になり、読み手は疑いません。
誤った確定は、誤警報（形 D）にも、誤 clear（形 B）にもなります。

そこで、確定してよい条件を、言語の意味から確実に言える場面だけに狭めました。
確定できない場面では、黙って 1 つを選ばず、`opaque(unresolved)` と G5 の列で「ここは分からない」と残します。
これは G1・G2 の取り消しと同じ考え方です。
分からないときに、分かったふりをしない。

#### よくある誤解・つまずき

- **「G3・G4 で、v3 の見落としは全部見つかるようになった」**: 違います。D65 の 2 の確かめ直しで、v3 の見落とし 7 件のうち、G3・G4 で効果が見えるようになった 3 件（inkscape の 2 件・rovo の 1 件）も、判定は**不**で、矛にはなりませんでした（35.9 節。表は[第 41 章](ch41.md)）。
- **「型の注釈は正しいものだから、信じてよい」**: 注釈は宣言で、証明ではありません（解析器のコードの注記も「注釈は宣言であって証明ではない」と書いています。`authgap/analyze.py:178-180`）。[第 34 章](ch34.md) 34.5 節の作り話の `Outbox` のように、注釈が古いまま残っていることもあります。解析器は注釈を受け手の型の手がかりに使いますが、manifest の `annotation_typed` の欄に、どの関数のどの引数（戻り値なら `<return>`）で、どの型の注釈を使ったかを出しています。形 C なら `{"function": "_client", "param": "<return>", "type": "httpx.AsyncClient"}` です（本書の執筆時に凍結版で確かめた）。
- **「条件を足したので、G3・G4 は完全になった」**: 条件は、レビューで見つかった穴を塞いだものです。レビューは差分の外の古い欠陥を系統的には拾わないので（[第 24 章](ch24.md) 24.7 節）、見つかっていない穴が無いとは言えません。

#### 手作業ではどう使うか

- 道筋がパッケージの `__init__.py` を通るときは、その `__init__.py` を開き、名前の束縛が 1 つだけかを確かめます。`try` / `except` や `if` で 2 つあるなら、実行時にどちらが選ばれるか（ふつうの環境で、どちらの import が成功するか）を自分で決めます。決められなければ、手引きの第 19 節の目安で不明にします。
- 効果が型の注釈に頼っているかは、manifest の `annotation_typed` で分かります。注釈に頼った効果を判定するときは、手順 C で「受け手は本当にその型か」を確かめます。違えば、kind まで違うかを見て E4 かどうかを決めます（[第 34 章](ch34.md) 34.5 節）。
- 見落としの判定で、解析器が効果を出していないツールの呼び出しが `__init__.py` の再公開や注釈を通っていたら、見落としの原因は「呼び出しの解決」か「受け手の型」です（手引きの 18 節の 6）。

#### この節のまとめ

G3・G4 は、import や注釈の意味から正しく導ける直しだったが、1 つに確定してはいけない場面（束縛が複数・読む側の書き換え・外部の型と木の中の同名クラス・木の中のモジュールの `httpx`）で確定する穴があった。
確定の条件を狭め、確定できないときは `opaque(unresolved)` と G5 の列で印を残す形にして残した。G4 は効果を見えるようにする直しで、D2 の `POST` は矛ではなく不になる。

### 35.7 G5 — 判定を変えずに、見失った場所を記録する

#### 一言で言うと

G5 は、ユニットごとに「**名前が木の中の定義に当たるのに、どれか決められず降りなかった呼び出し**」を、manifest の `unresolved_in_tree_calls` の欄に出す直しです。
**矛・不・内の判定には使いません。**
「矛盾なし」と出たツールが、本当に矛盾なしなのか、解析器が道を見失っただけなのかを、読み手が判断するための材料です。

#### たとえ話 — 地図に「未調査」の印を付ける

カーナビが「この先に危険な場所はありません」と言うとき、地図に載っていない道を通る区間には「未調査」の印を付けておく、という工夫です。
印があっても、カーナビの答え（危険なし）は変えません。
けれども、運転する人は「この区間は、カーナビが本当は知らない」と分かり、自分の目で確かめられます。

#### 小さな例 — 欄の中身

35.6 節の形 B を凍結版で走らせたときの欄は、次のとおりでした。

```
"unresolved_in_tree_calls": [
  {"name": "save", "relpath": "app/main.py", "lineno": 10, "n_candidates": 3}
]
```

- `name`: 降りられなかった呼び出しの名前です。ここでは `save`。
- `relpath`・`lineno`: その呼び出しがある場所です。`app/main.py` の 10 行目（`save(p)`）。
- `n_candidates`: 名前が当たった木の中の定義の数です。ここでは 3（`fast.save`・`slow.save`・`other.save`）。2 つ以上あって 1 つに決められなかったので、降りませんでした。

この欄があるので、形 B の `remember` は、効果が 0 でも「10 行目の `save` で道を見失った」と分かります。
人が判定するときは、10 行目から自分でたどり、`fast.save` の書き込みを見つけられます。

（出典: 本書の執筆時に凍結版で走査したもの。`authgap/analyze.py:173-177`（欄を書き出すコード。凍結版））

#### 一歩ずつの説明 — なぜ判定に使わないのか

[第 34 章](ch34.md) 34.8 節で見た、v3 の構造的な所見を思い出します。

1. 呼び出しを解決できなかったツールは、宣言に対して何の印も残さず「矛盾なし」に見える（規則 4 の「黙って安全側に倒す」形）。
2. ただし、D1・D2 を明示したユニットのうち、何らかの未解決を持つものは、v2 の run18 で 1,026 / 1,036、v3 で 846 / 859 ある。
3. 確度 `opaque(unresolved)` の効果だけに支えられた矛は、run18 で 114 / 190、v3 で 64 / 89 あるが、v3 の判定での誤はそのうち 2 だけ。

2 から、「未解決が 1 つでもあれば不」にすると、明示したユニットのほとんどが不になります。
3 から、「未解決に支えられた矛は不」にすると、正しい矛の大半を捨てます。
どちらも、判定を一律に変えるには向きません。

そこで G5 は、判定は変えず、**見失った場所だけを記録する**ことにしました。
これなら、判定の数字は変わらず、「矛盾なし」の確からしさを読み手が自分で判断できます。
決定の記録は、G5 を「『矛盾なし』の確からしさを読み手が判断するための列であり、verdict には使わない」と書いています。

（出典: `docs/decisions.md:3442-3444`、`docs/population_v3.md:95-98`）

#### 一歩ずつの説明 — v2 の run20 での規模

D61 の結果の記録によれば、v2 の run20 で、解決できなかった木の中の呼び出しを持つユニットは **1,510**、呼び出しは **16,047** でした。
この数は、解析器がどれだけの場所で道を見失っているかの目安です。
判定に使わないので、矛・不の件数は G5 で 1 件も変わっていません。

（出典: `docs/decisions.md:3499`）

#### なぜそうするのか — 規則 4 と、判定の安定の両立

`CLAUDE.md` の規則 4 は「解決できなかったものは『不明』として記録する。黙って安全側に倒さない」です。
G5 の前は、解決できなかった呼び出しは、確度 `opaque(unresolved)` を除けば、どこにも記録されませんでした。
G5 で、その場所が manifest に残るようになりました。
一方で、判定（矛・不・内）は変えないので、v2・v3 で積み上げた判定の意味は崩れません。
「記録する」と「判定を変える」を分けたのが、G5 の要点です。

#### よくある誤解・つまずき

- **「`unresolved_in_tree_calls` に何かあれば、そのツールは不」**: 違います。この欄は判定に使いません。欄に何かあっても、矛・不・内は変わりません。
- **「`unresolved_in_tree_calls` が空なら、見落としは無い」**: 違います。この欄に出るのは「名前が木の中の定義に当たるのに、降りられなかった呼び出し」だけです。深さの上限で打ち切ったもの（`cap_hits` の `depth`）、木の外のライブラリの中、デコレータの wrapper の中などは、この欄には出ません（[第 15 章](ch15.md)）。
- **「この欄に何かあると、そのツールの矛は信用できない」**: 矛は、見つかった効果に基づいています。道を見失った場所が別にあっても、見つかった矛の正しさとは別の話です（[第 15 章](ch15.md) 15.6 節）。

#### 手作業ではどう使うか

- **矛の判定（手順 B）**: `unresolved_in_tree_calls` を見て、解析器がどこで道を見失ったかを知ります。正の判定には直接は関係しませんが、同じツールのほかの位置を読むときの手がかりになります。
- **見落としの判定**: 手引きの 18.2 節は、まずツールの本体を自分で読み、深さ 4 まで呼び出し先をたどり、宣言に反しうる動作を書き出してから、解析器の出力を見る、という順序です。出力を見る段階で、自分が見つけた違反への道が `unresolved_in_tree_calls` の行を通っていれば、見落としの原因は「呼び出しの解決」です。
- **論文の限界**: 解析器が道を見失う場所がどれだけあるかは、この欄の件数で示せます（判定とは別の、解析器の性質の記述として）。

#### この節のまとめ

G5 は、降りられなかった木の中の呼び出しを `unresolved_in_tree_calls` に出す直しで、判定には使わない。v3 の数字のとおり、未解決を一律に不にすると解析器が役に立たなくなるので、「記録する」と「判定を変える」を分けた。
v2 の run20 では 1,510 ユニット・16,047 呼び出し。判定では、見失った場所から自分でたどる手がかりにする。

### 35.8 確かめ方と結果 — 再現の木・v2 の run20・v3 の回帰の確認

#### 一言で言うと

D61 の改訂後の版（`94c40b4`）は、3 つの方法で確かめました。
(1) レビューの再現の木 60 余りで、D61 の前の版と比べ、違いはすべて改善だった。
(2) v2（開発用）を走査し直した run20 で、run18 と比べて**消えた効果・消えた矛は 0**、増えた矛 2 件は原ソースで正しいと確かめた。
(3) v3 も走査し直した（v3_run2）が、それは**回帰（悪くなった所）が無いかの確認だけ**に使い、消えた矛は 0 だった。

#### たとえ話 — 改修工事の後の 3 つの検査

建物の改修工事の後、3 つの検査をします。
(1) 検査員がわざと叩いた弱そうな所を、もう一度全部叩き直す。
(2) いつも使っている部屋（v2）を全部回り、改修の前にあった設備が 1 つも無くなっていないかを確かめる。新しく付いた設備は、本当に付けるべきものかを確かめる。
(3) 改修のきっかけになった部屋（v3）も回るが、それは「壊れた所が無いか」を見るためだけで、「きれいになった」とは報告しない。きっかけになった部屋がきれいになるのは、そこに合わせて直したのだから当然だからです。

#### 小さな例 — v2 の run18 → run20

| 項目 | run18（D61 の前） | run20（D61 の後） | 変化 |
|---|---|---|---|

#### なぜそうするのか — 3 つの確かめ方が、それぞれ違うことを見る

| 確かめ方 | 何を見るか | 見えないもの |
|---|---|---|
| レビューの再現の木 | 直しが、作った反例で本当の効果を消さないか | 反例として思いつかなかった形 |
| v2 の取り直し | 実際の木で、何も消えていないか。増えたものは正しいか | v2 に無い形 |
| v3 の取り直し | 直しのきっかけになったデータで、何も壊れていないか | v3 の数字の「改善」（合わせ込みと区別できないので、見ない） |

表の読み方: 1 行が 1 つの確かめ方です。
たとえば 3 行目は「v3 の取り直しは、何も壊れていないかを見るためのもので、v3 の数字がよくなったかどうかは、合わせ込みと区別できないので見ない」と読みます。

1 つの確かめ方だけでは、見えないものがあります。
3 つを組み合わせて、ようやく「少なくとも、見える範囲では何も壊していない」と言えます。
それでも、レビューは差分の外の古い欠陥を系統的には拾わない（[第 24 章](ch24.md) 24.7 節）ので、「欠陥が無い」とまでは言えません。

#### よくある誤解・つまずき

- **「消えたものが 0 なら、直しは正しい」**: 「何も壊していない（見える範囲で）」とは言えますが、「直しが一般に正しい」の証明にはなりません。G1・G2 を取り消したのは、取り直しの結果ではなく、敵対的レビューの反例によってでした。

- **「v3 の矛が 87 → 89 に増えたので、検出力が上がった」**: v3 の取り直しは回帰の確認だけに使う約束です。増えたことを改善として報告しません（35.9 節）。

#### 手作業ではどう使うか

最終評価では、解析器を直さないので、取り直しと突き合わせはしません（走査は 1 回）。
けれども、「消えたものを 1 件ずつ確かめる」「増えた側だけ見て『直った』と書かない」という考え方は、判定の記録を見直すときにも使えます。
たとえば、手引きの第 21 節の 4 は、迷った件に印を付けて翌日に見直し、見直したことを `note` に書く、と決めています。
本書の提案として、見直して判定を変えたときは、変える前と後の判定、なぜ変えたか、どちらの向きに変えたか（正 → 誤か、誤 → 正か）も書いておくと、後で偏りを確かめられます。

D61 の改訂後の版は、レビューの再現の木 60 余り（違いはすべて改善）、v2 の run20（消えた効果・矛 0、増えた矛 2 件は正しい）、v3 の回帰の確認（消えた矛 0、消えた効果 22 件は誤った経路）で確かめた。

### 35.9 「改善としても悪化としても報告しない」— D61 の約束と、D65 の 2 の確かめ直し

#### 一言で言うと

D61 は、「**v3 の取り直しは回帰の確認だけに使い、v3 の精度が上がったことを結果として報告しない**」と約束しました。
理由は、「v3 は開発用で、見た後に直したので、評価には使えない」からです。
この約束は、後に凍結版で v3 の見落としを確かめ直したとき（D65 の 2）にも、「**v3 を見た後の確認なので、改善としても悪化としても報告しない**」という形で守られました。

#### たとえ話 — 答えを見た後の再テスト

小テストで間違えた問題の答えを見て、解き方を直したとします。
そのあと同じ小テストを解き直せば、点数は上がるでしょう。
けれども、その点数の上がり方は「実力が上がった証拠」にはなりません。
答えを見た後で、その問題に合わせて直したからです。

解き直しに意味があるのは、「直したせいで、前は解けていた問題が解けなくなっていないか」を確かめるときだけです。
D61 の約束は、v3 の取り直しを、この「前は解けていた問題の確認」だけに使う、ということです。

そして、点数が**下がって**いても、同じ理由で「実力が下がった証拠」とも言えません。
解き直しの点数は、上がっても下がっても、評価の数字には使わないのです。

#### 小さな例 — 約束の文面

D61 の規則（実装より先にコミット）:

> **直すもの**（それぞれ規則 → 反例テスト → 実装 → v2 と v3 の取り直しの順。**v3 の取り直しは回帰の確認だけ**に使い、v3 の精度が上がったことを結果として報告しない — v3 は開発用で、見た後に直したので評価には使えない）

D61 の結果:

> **v3（回帰の確認だけ。改善として報告しない）v3_run1 → v3_run2**: …

逸脱 #23:

> v3 は開発用で、v3 の数値の改善は報告しない。

D65 の 2（2026-09-29）:

> 段階 B（U09 / U23 / U38 / U40）は、この 9 件のどれの判定も変えなかった。v3 を見た後の確認なので、**改善としても悪化としても報告しない**（[第 31 章](ch31.md) / D61 の約束のまま）。

（出典: `docs/decisions.md:3417-3418`、`:3501`、`docs/preregistration.md` §5 の逸脱 #23、`docs/decisions.md:3740-3741`）

D65 の文面の「[第 31 章](ch31.md)」は、第 3 版の教科書の章の番号で、本書のこの章（第 35 章）にあたります（前付けの対応表（目次の直後））。

#### 一歩ずつの説明 — 約束が言っていること・言っていないこと

1. **言っていること 1 — v3 の取り直しは回帰の確認だけ**: v3 を走査し直すのは、「直しが何かを壊していないか」を見るためです。消えたものを 1 件ずつ確かめます（35.8 節）。
2. **言っていること 2 — v3 の数字の改善を、結果として報告しない**: v3 の精度や見落としが良くなっても、それを「解析器が良くなった」証拠として書きません。v3 は、見た後に、それに合わせて（少なくともそれをきっかけに）直したデータだからです。
3. **言っていること 3（D65 で明確になった） — 悪化としても報告しない**: 逆に、v3 の数字が悪くなって見えても、それを「解析器が悪くなった」証拠としては書きません。開発用で、見た後のデータであることは、どちらの向きでも同じだからです。悪くなった所があれば、それは回帰の確認の対象（1 件ずつ理由を確かめる）で、評価の数字ではありません。
4. **言っていないこと — v3 を見てはいけない**: v3 を見ることも、v3 で確かめることも許されています。禁じているのは、v3 の数字の変化を「改善」「悪化」という**評価**に使うことです。

#### 予告 — D65 の 2 の確かめ直し（詳しくは第 41 章）

2026-09-29、学生の決定で、v3 の見落とし 7 件と不明 2 件を、最終凍結の版（`analyzer-freeze-3`）で確かめ直しました（D65 の 2）。
解析器は変えず、見るだけで、走らせる前に `git diff analyzer-freeze-3 -- authgap/` が 0 行であることを確かめています。
結果は「run20 の版での記述と同じ」で、G3・G4 で効果が見えるようになった 3 件（inkscape の 2 件・rovo の 1 件）は不、残りの 6 件は内（効果 0）のままでした。
その後の添削（D64 の段階 B）も、この 9 件のどれの判定も変えませんでした。
そして、この確かめ直しも「v3 を見た後の確認なので、改善としても悪化としても報告しない」と書かれています。
1 件ずつの表（`evidence/population_v3/v3_miss_recheck_freeze3.json`）は、[第 41 章](ch41.md)で見ます。

（出典: `docs/decisions.md:3724-3741`、`evidence/population_v3/v3_miss_recheck_freeze3.json`）

#### なぜそうするのか — 評価の数字を、汚さない

この研究は、データを 5 種類に分けています（[第 25 章](ch25.md)）。
v3 は開発用で、v4 は凍結版の中間検証、評価は学生の最終評価のデータで行います。
もし v3 の「改善」を報告すれば、読み手は「解析器は良くなった」と受け取ります。
けれども、その改善は、v3 を見て直した結果なので、新しいデータでの実力を表していません。
報告すること自体が、甘い評価を紛れ込ませることになります。

D66 の 5（v4 について「v3 と並べてよいが、版もデータも違うので『改善』『悪化』とは書かない」）も、同じ考え方です（[第 37 章](ch37.md)）。
v3・v4 の数字は、どちらも、論文の評価の数字とは別のものとして扱います。

#### よくある誤解・つまずき

- **「D65 の 2 で、v3 の見落としのうち 3 件は不になったのだから、凍結版の見落としは 4 件」**: そう書いてはいけません。v3 を見た後の確認なので、改善としても悪化としても報告しない約束です。凍結版の見落としの評価は、最終評価のデータで行います。
- **「悪化を報告しないのは、都合の悪いことを隠すこと」**: 隠してはいません。回帰（悪くなった所）は、1 件ずつ理由を確かめて記録します（35.8 節）。報告しないのは、v3 の数字の変化を「解析器の評価」として書くことです。
- **「v3 で何も報告しないなら、v3 は無駄だった」**: v3 で見つけた誤りと見落としは、D61 の直し（G3・G4・G5）と、既知の限界（O41）と、最終評価の誤の原因の分類（E2・E3・E5・E7・E8）になりました。評価の数字にはしませんが、解析器と判定の手引きの両方に、大きく効いています。

#### 手作業ではどう使うか

- **論文を書くとき**: 最終評価の結果を、v3（81.7%）や v4（76.7%）と並べて「改善した」「悪化した」と書きません。v3・v4 は開発用・中間検証のデータで、判定したのも本記録者（AI）です。経緯として触れるなら、「開発の途中の確認」としてだけ書きます。
- **判定の途中**: 判定の途中で集計を見ないのも、同じ考え方です（手引きの第 21 節の 2）。途中の数字を見て「精度が低すぎる」「高すぎる」と感じると、境界の判断が傾きます。
- **最終評価の後**: 最終評価で見つけた解析器の誤りは、直さずに限界として書きます。仮に将来、解析器を直して同じデータで走らせ直しても、その数字は「改善」として報告できません。最終評価のデータは、見た後のデータになるからです。

#### この節のまとめ

D61 の約束は、v3 の取り直しを回帰の確認だけに使い、v3 の数字の改善を結果として報告しないこと。D65 の 2 で凍結版で v3 の見落としを確かめ直したときも、「改善としても悪化としても報告しない」として守られた（結果は run20 の版での記述と同じ。表は[第 41 章](ch41.md)）。
見た後に直したデータの数字は、上がっても下がっても評価に使わない。最終評価の結果も、v3・v4 と並べて「改善」「悪化」とは書かない。

### この章のまとめ

- 学生の方針は「検証データを見て変更するのはきりがないし、研究的によくない。一般的に役立つ直し方なら改善して欲しい」。D61 は、(1) 正解が v3 と無関係に決まる、(2) 一般的に効く、の両方を満たすものだけを直すと決めた。
- 直すもの G1〜G5（標準入力・組み込みの型の値のメソッド・再公開と別名つきの import・注釈による受け手の型・解決できなかった呼び出しの列）を選び、直さないもの（一時ファイルの削除・`shlex.quote` の固定コマンド・関数が返すモジュール・深さ・語彙・`flock`）は O41 に既知の限界として書いた。「この後は v3 を見て直さない」。
- 規則 → 反例テスト（言語の意味から作り、「変えない」側の例も入れ、直す前の版で落ちることを確かめる）→ 実装 → 敵対的レビュー → 改訂の規則とテスト → 改訂の実装 → 取り直し、の順に進んだ。
- G1・G2 は、`env python3`・`tee`・`xargs rm` や、`self.remote = ""` の置き場所などの反例で崩れ、取り消した。以前の扱い（保守的な上界・`opaque(unresolved)` で降りる）がもともと正しかった。凍結版には、この 2 つの形の誤警報が残っている（判定では E5・E3 を疑う）。
- G3・G4 は、1 つに確定してはいけない場面で確定する穴を、確定の条件を狭めて塞ぎ、確定できないときは印を残す形で残した。G3 は既知の欠陥 K7（別名つきの import）も直した。G5 は判定を変えない列 `unresolved_in_tree_calls`。
- 確かめ方は、レビューの再現の木 60 余り（違いはすべて改善）、v2 の run20（消えた効果・矛 0、増えた矛 2 件は正しい）、v3 の回帰の確認（消えた矛 0、消えた効果 22 件は誤った経路）。逸脱 #23 に記録し、最終凍結を決めた（後に `analyzer-freeze-3` に打ち直し）。
- **D61 の約束: v3 の取り直しは回帰の確認だけに使い、v3 の数字の改善を報告しない。** D65 の 2 で凍結版で v3 の見落としを確かめ直したときも、「改善としても悪化としても報告しない」として守られた（表は[第 41 章](ch41.md)）。
- 最終評価では、解析器も判定の手引きも途中で変えない。同じ考え方（データに合わせて規則を変えない）を、人の判定に当てはめる。
