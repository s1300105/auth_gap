#### この章で使う言葉の思い出し

- **木**（[第 11 章](ch11.md)）: 解析する 1 つのリポジトリ。この章では、練習用のサーバの 1 つのファイル `server.py` が、1 本の木です。

- **効果・kind・site・slot**（[第 13 章](ch13.md)）: 外の世界に触れる操作 / その種類（`FS_WRITE`・`DB` など）/ その操作をする関数の名前（`builtins.open` など）/ その操作の中の位置（書き先の `path` など）。
- **主体・確度**（[第 14 章](ch14.md)）: slot の値を誰が決めたか（`MODEL` = モデル、`OP` = 運用者や定数）/ 追いかけが確かか（`resolved` = 確か）。
- **深さ・`witness_chain`・`entry_lineno`**（第 15・18 章）: ツールの本体を深さ 0 とし、本体が呼ぶ関数を深さ 1 と数える / 本体から効果までにたどった関数の並び / 本体の中で、その道筋に入る呼び出しの行。

- **組**（第 18・48 章）: 判定の単位 =（木, ユニット, site, kind, 宣言）。
- **正・誤・不明**（[第 48 章](ch48.md)）: 矛の組への人の判定。
- **条件の種類**（[第 49 章](ch49.md)）: なし / 引数 / 初回 / 失敗・期限切れ / 外部の状態 / 運用者の設定 / 起動の方法。
- **書き込み先の種類**（[第 51 章](ch51.md)）: 相手側の状態 / データベース / 利用者のファイル / ログ / 一時ファイル / キャッシュ・状態の保存 / プロセスの起動・コードの実行 / その他・不明。上から順に当てはめる。
- **見落としの判定の 5 つの結果**（[第 52 章](ch52.md)）: 反する動作は無い / 解析器が不として出している / 見落とし / 見落とし（深さ 4 の外）/ 不明。

#### この章の進め方 — 問題、自分で判定、解答と解説

53.3 節から 53.8 節は、どれも次の形で書いてあります。

1. **問題**: コードと、判定表の 1 行（または判定の対象）。
2. **自分で判定してみる**: 書く欄の一覧。ここで**一度止まって、自分の答えを紙か CSV に書いてください**。
3. **区切りの線**（`---`）と「ここから解答」の印。
4. **解答と解説**: 手順ごとに、どの規則・どの決定から答えが出るか。

解答を先に読むと、練習の意味が半分になります。
人は、答えを見た後では「自分もそう考えたはずだ」と思いやすいからです。
自分の答えを先に書いておけば、食い違ったところが、そのまま「自分が規則を読み違えやすいところ」の一覧になります。

もう 1 つ、**1 問ごとに、かかった分数を測ってください**。
手引きは、判定ごとに分数を記録すると決めています（12.3 節）。

最後に、練習でも**本番と同じ条件**で判定してください。
最終評価の判定は学生 1 人で行います。AI（LLM）に判定はさせず、記録もさせません。AI は、コードについての事実を調べる補助としてだけ使ってよい、と決まっています（D70 の 3。2026-10-02 に改訂。前日の 2026-10-01 には「使わない」でした）。
練習でも、同じ条件で AI を使ってかまいません。使うなら、次のことを本番と同じに守ります。

- 自分で手順を通して、答えを先に書く。AI に「この組は正か誤か」とは聞かない。
- AI に聞くのは事実だけ（「この関数はどこから呼ばれる？」「この POST 先の API は何をする？」など）。宣言の値・解析器の出力・自分の答えは渡さない。この章の問題文や解答も、この repo の文書なので渡さない（渡すのはコードだけ）。

- 見落としの練習（53.7 節）では、手引き 18.2 の 1〜7 を AI なしで終えてから、点検に使う。
- AI が示した行は自分で開いて確かめ、`ai_used`・`ai_model`・`ai_log` を書く。

本番で AI を使うつもりなら、練習でも同じように使って分数を測ると、本番の見積もりに近い分数になります（手引きは AI に聞いた時間も分数に含めると書いています）。

だから、判定の信頼性を支えるのは、まずあなた 1 人の手順と `evidence` です。

#### 一歩ずつ — 1 行ずつの意味

判定では、このサーバのどの行も読みます。

### 53.2 解析器の出力を読む — 3 つの矛の組と、出ない効果

#### 一言で言うと

解析器は、このサーバに**矛の組を 3 つ**出します（D1 が 2 組、D2 が 1 組）。
`SELECT`（DB の読み取り）は、効果としては見つけていますが、矛にも不にもしません（内）。
判定の対象になるのは 3 組で、`SELECT` は「出ない例」として、見落としの判定の練習に使えます。

#### たとえ話 — 健康診断の結果票

健康診断の結果票には、「要精密検査」の印が付いた項目と、「異常なし」の項目が並びます。
医師がまず見るのは「要精密検査」の項目です。
けれども、「異常なし」の項目にも、検査の値は書いてあります。
印が付いていないからといって、検査をしなかったわけではありません。

解析器の出力も同じです。
「矛」は要精密検査の印、「内」は異常なしの印です。
`SELECT` の行は、検査はしたが印が付かなかった項目です。

#### 手作業ではどう使うか

- **読み返しの grep は、木の全体で**: 本番の木では、キャッシュを書く関数と読む関数が、別のファイル、別のツールにあることがよくあります。`grep -rn '<場所の名前>' corpus/<木> --include='*.py'` のように、木の全体を探します。別のツールが読み返していても、「サーバの動作のために後で読み返す」ので、キャッシュ・状態の保存に当たります。

#### よくある誤解・つまずき

- **誤解: 「ツールの名前も説明も『書き出す』なので、書くのは当たり前。違反ではない」**
  書くこと自体は D2 で許されています（足すだけなら反しない）。問題は、前からあるものを上書き**できる**ことです。ツール本来の仕事であることは、正誤に関係しません。v4 の M18（「読み取り専用」と宣言してレポートを書き出す）も、本来の仕事として正でした。
- **誤解: 「書き込み先の種類は D1 の正にだけ付ける」**
  D1・D2・D4 の正（と見落とし、不の中身の違反）に付けます。D3 の正には、代わりに通信先の種類を付けます（D68 の 3）。
- **誤解: 「`"w"` で開くなら、D2 はいつでも反する」**
  書き先が固定の 1 つのファイルなら、解析器は不にし、人は「呼び出しの前からファイルがありうるか」で決めます。呼び出しごとに新しい名前（時刻や乱数の名前）なら、反しません（演習 53-2）。
- **誤解: 「`destructive: true` と出ているので、解析器はもう正と判定している」**
  `destructive` は、効果の種類の分類の印です。判定は人が原ソースで行います。
- **つまずき: 「モデルが渡す `path` が存在しないディレクトリの下だと失敗する。条件の種類は引数では？」**
  条件の種類は、効果に**届く**ための道筋の条件を書きます。32 行は毎回実行されます（失敗するのは `open` の中です）。だから「なし」です。

#### 手作業ではどう使うか

- **書き先の出どころを確かめる**: 本番の木では、`path` がツールの引数からそのまま来るとは限りません。途中で固定のディレクトリと `os.path.join` でつないだり、`os.path.basename` で名前だけにしたりします。そのときも、**モデルがその中の既存のファイルを指せるか**を考えます。たとえば固定のディレクトリの下で、名前をモデルが決めるなら、そのディレクトリの中の前の書き出しを指して上書きできる、と読むのが 3-a の素直な当て方です（本記録者の考え方の例）。迷ったら `note` に書きます。
- **モードを確かめる**: `"w"`・`"w+"`・`"r+"`・`write_text`・`write_bytes` は書き出し（上書きしうる）、`"a"`・`"x"` は足すだけです（§7.2）。モードが変数で渡される形もあります（[第 9 章](ch09.md)）。
- **ラベルは動作で**: 「エクスポート」「保存」「ダウンロード」など名前はいろいろですが、モデル（利用者）が書き先を指定するなら、利用者のファイルです。

#### この節のまとめ

- 組 2 は、到達する（条件なし）・D2 に反する → **正**。反するのは、`path` をモデルが決め、`"w"` が既存のファイルを上書きできるから（原理 3-a、15.2 節、§7.2）。

駅の自動改札は、切符に問題があると扉を閉めます。

#### なぜそうするのか

- **コードを先に読む理由**: 先に出力を見ると、「解析器が出していないものは無い」という思い込みで読んでしまいます（先入観）。見落としの判定は、まさに解析器が見ていないものを探す作業なので、解析器の見方に引っぱられると意味がありません（手引き 18.2 節の見出し「先入観を避けるため、コードを先に読む」）。
- **深さ 4 まで読む理由**: 解析器も深さ 4 までたどります（凍結の設定）。人も同じ範囲を読めば、「解析器が読める範囲で見落としたもの」を数えられます。それより奥で見つけたものは「見落とし（深さ 4 の外）」として別に数えます（D68 の 2）。
- **木の外のライブラリの中を読まない理由**: ライブラリの中まで読むと、1 件の判定が終わらなくなります。ただし、ライブラリの関数**そのもの**が環境を変えるもの（`requests.put`、`shutil.rmtree` など）は、呼んでいれば候補に数えます（18.2 節の 2）。`sqlite3.connect` がファイルを作るのも、この「関数そのものの働き」の話です。
- **前の版で決まっていない点を表に並べた理由**: どの決め方でどの答えになるかを先に見ておけば、封の前に学生が決めるときの材料になります。この点は D76 で学生が決めました（(Y)）。

### 53.9 判定表の CSV に書き込み、分数を測る

#### 一言で言うと

#### たとえ話 — 実験ノート

理科の実験では、結果だけでなく、条件・手順・かかった時間を実験ノートに書きます。

for path in sys.argv[1:]:

#### 一歩ずつ — 分数の測り方

手引きは、1 件ごとに「かかった分数」を記録すると決めていますが、測り方（どこからどこまでか、休憩を含めるか）は書いていません（[第 48 章](ch48.md) 48.4 節）。
本書の提案は、次のとおりです。**練習のうちに自分の測り方を決め、本番では変えない**ことが大事です。

1. **始め**: 判定表の行を開き、手順 A（または見落としの 1、不の中身の 1）を始めた時刻。
2. **終わり**: 手順 H（記録）を書き終え、CSV を保存した時刻。
3. **途中の中断**: 5 分を超える中断（休憩、別の用事）は、時計を止めて差し引く。
4. **書き方**: 分の単位の整数（半角）。30 秒以上は切り上げる、など、丸め方も決めておく。
5. **含めるもの**: 原ソースを読む時間、grep の時間、相手の API の文書を探す時間、AI に事実を聞いた時間、`evidence` を書く時間。全部が判定の手間です（AI に聞いた時間を含めることは、手引きの 12.3 節が決めています）。

測った分数には、3 つの使い道があります。

- **不明にする目安との関係**: 手引きは「20〜30 分調べても決められなければ不明」としています（19 節）。時計を見ていれば、目安に達したことに気づけます。
- **見積もりの確かめ**: 手順書の 27 節は、矛は 1 木 3 件で 10〜25 分、見落としは 1 件 20〜40 分、不の中身は 1 件 10〜20 分と**仮に置き**、合計を約 170〜380 時間と見込んでいます。この数は**測っていません**。練習で測った分数で、見込みが合うかを確かめます（D69 の 6）。
- **論文の手続きの記述**: 「1 件の判定に平均何分かかったか」を論文に書けます。

手引きの 21 節の 3 は、1 日の判定の件数に上限を決める（例: 1 日 10〜15 件）ことを勧めています。疲れると判断が雑になるからです。

#### なぜそうするのか

- **CSV にする理由**: 手で判定するので、表計算ソフトで開ける形が扱いやすく、最後に集計のスクリプトが読めます（手順書 6.4 節）。
- **空欄を機械で確かめる理由**: 何百件も書くと、欄の書き忘れは必ず起きます。集計のときに見つかると、何週間も前の判定を思い出して埋めることになり、記録の信頼性が下がります。書いたその日に確かめるのが一番です。
- **分数を測る理由**: 見込み（170〜380 時間）は測った数ではありません。練習で測って初めて、日程と件数が現実に合うかが分かります。合わなければ、段階 6 のコミットの**前**に、事前登録に逸脱として理由を書いて件数を減らします（手順書 26 節、D69 の 6）。

#### よくある誤解・つまずき

- **誤解: 「`evidence` にカンマがあると CSV が壊れるので、カンマを使わない」**
  カンマを含む欄は `"` で囲めば正しく読めます。表計算ソフトで保存すれば自動で囲まれます。読みやすさを犠牲にしてまで避ける必要はありません。
- **誤解: 「空欄の道具が何も言わなければ、判定は正しい」**
  道具は空欄を探すだけです。判定の中身が正しいかは確かめません。
- **誤解: 「分数は、だいたいでよいので最後にまとめて書く」**
  後から思い出した分数は不正確です。1 件ごとに、手順 H で書きます（[第 48 章](ch48.md) 48.4 節）。
- **誤解: 「この章の練習問題で時間を測れば、本番の見込みに使える」**
  答えを読んだ問題や、45 行の小さなサーバの時間は、本番の木の時間より短くなります。見込みの確かめには、答えを見ていない v4 の件（6.8 節）の分数を使います。
- **つまずき: 「`minutes` に『15分』と書いたら、道具に整数でないと言われた」**
  数字だけ（半角）を書きます。単位は欄の名前で決まっています。

#### 手作業ではどう使うか

- **毎日の終わりに**: その日に書いた行について空欄の道具を走らせ、「直す行 0」を確かめてからコミットします（手順書 3 節: こまめにコミット）。
- **分数の測り方を書き残す**: 練習で決めた測り方（始め・終わり・中断・丸め）を、判定の記録のどこか（たとえば判定表と同じディレクトリの説明のファイル）に書いておきます。論文で「1 件の平均の分数」を書くとき、何を測ったかを説明できます。
- **6.8 節の練習の結果は、手引きの見直しの材料**: 食い違った件は、手引きのどこが曖昧だったかを書き出し、封の前に手引きを直すかを学生が決めます（[第 54 章](ch54.md)）。

#### この節のまとめ

- 判定表は 3 種類（矛・見落とし・不の中身）で、書く欄が違う。カンマや `"` を含む欄は `"` で囲み、中の `"` は `""` と重ねる。表計算ソフトで UTF-8 の CSV として保存し、値が勝手に直されていないかを確かめる。
- 空欄の道具で、結果ごとに要る欄が埋まっているかを確かめる。道具は判定をしない。
- 分数は練習で測り方を決めて変えない。見積もり（170〜380 時間は見込み）の確かめには、答えを見ていない v4 の件の分数を使う。
