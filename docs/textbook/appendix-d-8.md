### 演習 45-2（V4 と V6）

1. **何を数えるか・決めるか**: V4 は、解析器が出した不の**全件**を、宣言ごとに**数え**、理由コードごとの内訳を出すだけです。V6 は、不の組を**抜き取り**、人が原ソースを読んで、その組が本当に宣言に反するか（違反 / 違反でない / 不明）を**決めます**。
2. **人が判定するか**: V4 はしません（`scripts/contradiction_by_decl.py` が機械的に数える）。V6 はします。
3. **対象の宣言と規模**: V4 は D1〜D4 の全部の不。V6 は D1 と D2 だけで、それぞれ不の組を持つ木から 50 木を選び、1 木 1 組、計 100 組です。D3・D4 の不は V4（件数と理由）にだけ入ります。
4. **3 つの答えとの関係**: 解析器の答えは、矛・何も出さない・不の 3 つです。矛の当たり方は V2（精度）、何も出さないの当たり方は V3（見落とし）で確かめます。不は、V4 で件数と理由を数えるだけでは、中に本当の違反がどれだけ混じっているかが分かりません。V6 を足したことで、3 つの答えのそれぞれがどれだけ当たっていたかを示せるようになりました。D69 の 4 は「これまで不の中身は一度も測っていない」と書いています。

なお、呼び名について: V4 は v3 の規則（`docs/population_v3.md:50`）からあり、D66 の 4 も V1〜V4 を挙げます。V6 は手順書の表（`docs/final_evaluation_procedure.md:70`）で名付けられました。手順書の表は V4 の呼び名を使わず、「判定しない数」とまとめて書いています。

（出典: `docs/decisions.md:3828-3831`（D69 の 4）、`docs/final_evaluation_procedure.md:64-76`、`:275-285`）

## 第 46 章 データを見る前に決めたこと（D67〜D70）と、まだ決まっていないこと の答え

この章の演習と確認問題は、`docs/decisions.md` の D65〜D71、`docs/final_evaluation_procedure.md`（手順書。地図であって規則ではない）、`docs/drafts/prereg_2_12_draft.md` と `docs/drafts/final_judging_guide_draft.md`（どちらも下書き・未承認）、`docs/open_questions.md`、`authgap/dparse.py` に基づきます。
v4 の数は本記録者（AI）の判定や開発用の値で、論文には使いません（D66 の 5）。答えの中では、説明の材料としてだけ使います。

### 演習 46-1（不の中身を足した理由）

1. D69 の 4 は、理由を次のように書いています。
   - 「精度・見落とし・不の中身がそろえば、解析器の 3 つの答えのそれぞれがどれだけ当たっていたかを示せる。」
   - 「これまで不の中身は一度も測っていない。」
   （出典: `docs/decisions.md:3830-3831`）
2. 解析器の 3 つの答えは、**矛**（宣言に反する）、**何も出さない**（反する動作は見つからない）、**不**（静的には決められない）です。それぞれを確かめる問いは、矛 → **V2 精度**、何も出さない → **V3 見落とし**、不 → **V6 不の中身**です。
3. 不の中にどれだけ本当の違反が混じっているかが分からないので、「解析器が見つけた違反（矛）は、実際の違反のどれくらいの部分なのか」「不は気にしなくてよい答えなのか、違反の多くが隠れている答えなのか」を、読み手は知ることができません。たとえば v4（開発用の数。論文には使わない）では、D2 の矛が 155 件に対して不が 257 件ありました（`docs/population_v4.md:81`）。不の中身を測らなければ、この 257 件の重みが分かりません。
4. D3・D4 の不は、件数と理由の内訳だけを出し（V4）、判定はしません（D69 の 4、`docs/decisions.md:3829`）。

### 演習 46-2（宣言をまたいで 3 件を選ぶと）

1. 宣言ごとに選ぶので、D1 は 4 組から seed ① で 3 件、D2 は 1 組しかないので全件の 1 件、D3 も 1 組で全件の 1 件。合わせて **5 件**です（各宣言で、Y が 200 木の上限の中で選ばれている場合）。
2. 宣言をまたいで 6 組から 3 件を選ぶと、くじの結果 3 件とも D1 になることがありえます。そのとき、Y の D2 と D3 は 1 件も判定されません。D1〜D4 は別々の主張として、宣言ごとに報告します（D62）。そして主な数字は、宣言ごとの木の単位の数字（本当の矛が 1 件以上あった木の割合、木ごとの精度の平均。D67 の 3）です。宣言をまたいで選ぶと、Y は「D2 の矛が出た木」「D3 の矛が出た木」なのに、D2・D3 の木の単位の数字から欠けてしまいます。とくに D3 のように矛の出る木が少ない宣言では、1 木欠けるだけでも数字への影響が大きくなりえます（本書の補足）。
3. D69 とのつながり:
   - 木の数の上限（200）も宣言ごと（D69 の 2）なので、宣言ごとに 3 件を選べば単位が揃う。
   - D69 の判定時間の見込みは、もともとこの選び方（宣言ごと）で計算している。
   （出典: `docs/decisions.md:3843-3845`）

### 演習 46-3（保留の項目の期限）

どの項目を選んでもかまいません。3 つの例を示します。

**例 1: (1) 2 人目の判定者と判定し直し（保留）**

1. 2 人目の判定者を置くか（置くなら件数・対象の抜き方・裁定のしかた・一致の指標）、置かないなら判定し直し（2 週間以上あけて 5〜10%）をするか、を決めるものです。
2. 期限は、データを見る前、遅くとも段階 6 の抜き取りのコミットの前です（`docs/decisions.md:3881-3882`、`docs/drafts/prereg_2_12_draft.md:67-68`）。
3. 期限を過ぎて足すなら、事前登録の §5 に逸脱として理由とともに書き（変更前・変更後・理由・日付・その時点で見ていた数値）、事後の分析として主の結果と分けて扱います。
4. 決めないまま進むと、D67 の 4（判定者 1 人）の既定のまま判定することになります。それ自体は約束どおりですが、後から判定し直しを足すと事後の分析になり、「結果を見てから信頼性の確認を足した」と読まれえます。量（5〜10% か 10% か）や seed の番号も決まらないままになります。

**例 2: (5) D3・D4 の M_d（未決）**

1. 分母 (c) の M_d（宣言 d を明示したユニットを持つ木の数）を、D3・D4 について、解析器のどの欄で数えるかを決めるものです。
2. 原典の期限は「封の前」と明記されてはいませんが、分母は値を見る前に決める約束（`CLAUDE.md` の規則 3。事前登録 §2.10 も、NET の分母について「値を見てから主分母を替えない」と書いています。`docs/preregistration.md:481`）なので、事前登録 §2.12 を封する前に決めます。
3. 期限を過ぎて決めたら、§5 に逸脱として書き、その数え方で出した (c) は事後の分析として扱います。
4. 決めないまま集計すると、D70 の 4 の文面（`D_kind.explicit`）どおりなら、D3 は逆の申告（`openWorldHint: true`）の木を数え、D4 は 0 になって割合が計算できません。黙って `closed_world`・`idempotent` で数えれば、事前登録に無い数え方を使ったことになります。

**例 3: (9) 抽出のコマンドの書き方（未決）**

1. 手順書 §7 の `--n <抽出数> --seed <抽出用の seed>` を、D69（全部を走査）と D70 の 7（抽出用の seed は要らない）に合わせてどう書くか、出力に残る seed の記録をどう扱うかを決めるものです。
2. 原典に期限は書かれていません。段階 3 でこのコマンドを走らせるので、自分なら段階 3 の前（できれば封の前）に決めます。
3. 段階 3 の後で気づいたら、走らせたコマンドと出力をそのまま残し、「抽出していないので seed は使っていない。出力の `seed` の欄は既定値が書き込まれたもの」と記録します（本書の提案）。抽出をやり直すことはしません。
4. `--seed` を渡さずに走らせると、乱数を使っていないのに、出力の `seed` の欄と各木の `note` に v2 の seed（20260920）が書き込まれます（`scripts/sample_population_v2.py:40`、`:75`、`:80`）。後から記録を読んだ人が、「v2 と同じ seed で抽出したのか」と誤解しえます。

まだ決まっていない細部: `--seed` を省くと既定の 20260920（v2 の seed）が出力の `seed` の欄と各 target の `note` に書き込まれ、記録だけを見ると v2 と同じ seed で抽出したように読めること。8.1 節の spec の `note` も「seed=<抽出用の seed>」のままであること。どう書いて揃えるかは、事前登録 §2.12 の (b) を書くときに決めます（[第 46 章](ch46.md)の未決の一覧の (9)）。

### 確認問題 48-2

- 判定の目的は、**解析器の主張が、現実のコードの動作として当たっているか**を確かめることです。だから、site の名前や理由のような解析器の説明が間違っていても、2 つの問い（到達するか・宣言に反するか）の答えが「はい」なら正です（手引き 11.2、`docs/drafts/final_judging_guide_draft.md:51-52`）。
- 作例 2 では、11 行の接続は `sqlite3` なのに、site は `psycopg.Cursor.execute` と表示されました。site の名前は、受け手の型の候補を並べ替えた先頭から作るためです（[第 13 章](ch13.md) 13.6 節）。けれども、13 行の動作（DB に `DELETE` を送って行を消す）は同じで、kind（`DB`）も合っています。13 行は毎回届き、読み取り専用のツールが DB の行を消すので、正です。名前の違いは `note` に書きます。
- site の名前の違いが判定に影響するのは、受け手の型の読み違いの結果、**動作の種類（kind）まで違う**ときです。そのときは、解析器の言う操作が実際には起きていないので、誤で、原因は **E4** です（`docs/drafts/final_judging_guide_draft.md:432`）。

### 確認問題 48-3

- 「この程度は違反と言えない」と感じても、**自分の感覚では判断しません**。D1 の問い「呼び出しの後に残る何かを変えるか」に事実で答えます。ログファイルは呼び出しの後にも残るので、採った原理 1-i-b（呼び出しを越えて残るものはすべて環境）により、**D1 に反します**。届くなら、正です（手引き 11.3）。
- **D67 の 1**: 重大度の重みは付けない。主指標の精度は今の原理の 1 本だけにし、正の各件に「書き込み先の種類」を事実のラベルとして記録して、内訳を表で示す。軽重の判断は読み手に任せる（`docs/decisions.md:3767-3772`）。
- 理由の 3 つ:
  1. 研究の問いは「宣言は正しいか」で、「危ないか」ではない。
  2. 重みの線引きには正解が無い。実世界でも割れている（OpenAI の提出ガイドはログを書くツールを `readOnlyHint: false` にせよと言い、RFC 9110 はアクセスログへの追記を「安全」に含める）。
  3. v4 の結果を見た後の区別で数字を作り直すと、恣意的に見える。
- 違反の軽い・重いは、**書き込み先の種類のラベル**（`write_target`。この例なら「ログ」）で表します。正誤には持ち込みません。`note` には、感想ではなく事実（「`access.log` に 1 行追記。ツールの動作では読み返さない」など）を書きます。

### 確認問題 48-4

- `evidence` は、**ファイルと行の連なり**と、**各段で何が起きるかを 1〜3 文**で書きます。**判定を見ていない第三者が、その行を開けば同じ結論に着ける**ように書くと決められています（手引き 13 の手順 H、`docs/drafts/final_judging_guide_draft.md:176`、`:188-189`）。
- 悪い例「open で書いているので正」には、**どの行か**（ファイルと行）と、**どう届くか**（ツールの入口から効果までの道筋と条件）がありません。だから、第三者が確かめられません。
- **D67 の 4** は、判定を学生 1 人で行うと決めました。2 人目の判定者は用意できず（2 人目は D70 の 8 で保留）、判定者間の一致（κ）に依存する主張はしません。その代わりに、第三者が後から検証できるように、判定の根拠（ファイルと行）を全件残して公開し、判定の手引きを先にコミットします（`docs/decisions.md:3783-3786`）。2 人目による確かめが無い分、**誰でも後から確かめられる `evidence` が、判定の信頼性の担保**になります。

### 確認問題 50-2

- **D1**（呼び出しの後に残る何かを変えるか）: 相手のサーバに新しいメッセージが残るので **反する**（作成も環境の変更。原理 1-ii-b）。
- **D2**（前からあったものを消す・上書きする・変えるか）: 新しいメッセージを足すだけで、前からあったものは変えないので **反しない**。
- **D4**（同じ引数で 2 回呼んだとき、2 回目がさらに変えるか）: 同じ文で 2 回送れば 2 通になるので **反する**（相手の API がそういう意味なら。手引きは「相手の API の意味で決める」）。

分かれる理由: 3 つの宣言は問いが違うからです。D1 は「変えるか」、D2 は「前からあるものを壊すか」、D4 は「繰り返しでさらに変わるか」を問うので、同じ「新しく作る」動作でも答えが違います。

### 確認問題 50-3

D3 と D4 について人が判定するのは、**矛の判定**の場面だけです（不の中身と見落としの判定は D1・D2 だけ。不の中身は D69 の 4 と手引き 18A.1 節、見落としは手引き 18.1 節と事前登録 §2.12 の下書き）。
- D3 の矛の組: 理由が `net_external_host`（定数の外部ホスト）・`net_model_host`（モデルが決める宛先）・`exec_model`・`spawn_model`（モデルが決めるコード・コマンド）の 4 つのどれかの組。
- D4 の矛の組: 理由は **`fs_append`** だけです（`open` の仲間で、モードの定数に `a` が入っている行）。だから D4 の判定は、毎回書き足すか（正）、書く前に確かめるか・開くだけで書かないか（誤、E8）を見分けることになります。

### 確認問題 50-4

`violates` 欄は **`決められない`**、結果（`outcome`）は **`不明`** です。`unknown_reason` には「手引き 15.2: DB に残る設定の変更は『追加か破壊か』が当てはまらない」と書きます。
理由: D2 の問いは「追加の更新だけか（前からあるものを壊さないか）」で、`PRAGMA journal_mode=WAL` はデータを足すのでも消すのでもなく、DB の設定を変えるものです。問いの物差しが当てはまらないので、手引きは「不明（解析器と同じ）」と先に決めています。調べても答えは変わりません。（D1 なら「変えるか」で答えられるので反します。）

## 第 51 章 結果に付ける印 — 書き込み先・通信先のラベルと誤の原因 E1〜E9 の答え

### 演習 51-1（ラベルを付ける）

どれも、51.3 節の手順で 1 番から順に当て、最初に当てはまったものを付けます。

1. **相手側の状態**。
   1 番の「NET の効果で、通信相手のサーバの状態を変える」に当たります。Slack のチャンネルにメッセージが 1 つ増えるので、相手のサーバの状態が変わります。ここで終わりです。
   （「記録のためのメッセージだからログ」と考えても、1 番が 4 番より先に当たるので、相手側の状態です。）
   この組は矛ではなく不の中身の判定ですが、「違反」にしたものには正と同じ書き込み先の種類を付けます（手引き 18A.2 の 5）。書く欄も同じ `write_target` です。
2. **データベース**。
   1 番（NET）には当たりません。2 番の「DB の行を変える」に当たります（`cache` 表に `INSERT` で行を足す）。次の呼び出しで読み返すので 6 番（キャッシュ・状態の保存）にも当てはまりますが、上から順に見ると 2 番が先です。手引きの境界の例「SQLite のキャッシュ DB への書き込み → データベース（順 2 が順 6 より先）」と同じ形です。
3. **利用者のファイル**。
   1 番・2 番には当たりません。書く場所は、モデルが渡した `path` から作られる（`path` の隣）ので、3 番の「利用者（またはモデル）が指定した場所のファイル」に当たります。
4. **ログ**。
   関数の名前は `_write_cache` ですが、名前ではなく動作で決めます。1〜3 番には当たりません（ファイルの場所はサーバが決めていて、利用者の文書でもない）。書いているのは時刻と検索語の 1 行（いつ・何をしたかの記録）で、木のどこにも読む行が無いので、4 番の「記録のためだけに書き、ツールの動作では読み返さない」に当たります。`note` に「キャッシュの名前だが、中身は時刻つきの記録で、読み返しは無い（grep で確かめた）」と書いておきます。
5. **プロセスの起動・コードの実行**。
   モデルが決めたコマンドを起動する SPAWN の正です。コマンドが何を書くかはモデルしだいで、1〜6 番のどれの書き先かは決まりません。7 番の「SPAWN / EXEC の正」に当たります（D68 の 3 が、まさにこの形のために足した種類です）。

### 演習 51-2（誤の原因を付ける）

1. **E2**。説明の例: `E2: os.unlink(tmp) は、同じ呼び出しで open(tmp, "w") で作った一時ファイル（NOTE + ".tmp"）を、失敗したときに消す後始末。呼び出しの前からあったものではない`。
   注意: この組は `os.unlink` の位置だけの判定です。同じツールの `os.replace(tmp, NOTE)` は、既存の `NOTE` を置き換える別の組で、D2 に反しうる（その組は別に判定する）ことを `note` に書いておくとよいです。
2. **E5**。説明の例: `E5: communicate() は子（kubectl get pods）の終わりを待って出力を受け取るだけで、標準入力に何も渡していない（stdin を PIPE にしていない）。kubectl get は読み取り`。
3. **E7**。説明の例: `E7: コマンドは固定の ls -la で、sub は shlex.quote で 1 つの引数に閉じ込められる。ls は一覧を表示するだけで、引数（選択肢を含む）しだいで書き込みに変わることもない`。
   E7 にできるのは、固定のコマンド（`ls`）が環境を変えないと確かめられたからです。固定のコマンドが環境を変えるもの（たとえば `rm`）なら、モデルがコマンドを選べなくても正です。
4. **E1**。説明の例: `E1: 効果は init_db() の CREATE TABLE で、lifespan の app_lifespan が起動時に必ず先に済ませ、_db is None の守りで、ツールの呼び出しでは届かない。_db を None に戻す行は無い`。
   site は `psycopg.Cursor.execute` と表示されていますが、実際は `sqlite3` の接続です。けれども kind は DB で合っているので、**E4 にはしません**。名前の違いは `note` に書きます。誤の原因は、到達しないこと（起動時の初期化）です。
5. **E4**。説明の例: `E4: frame は tinyquery.Frame（メモリに読み込んだ CSV の表）で、execute はメモリの中の写しを絞り込むだけ。DB にもファイルにも書かない。site の psycopg.Cursor.execute は受け手の読み違い`。
   （5 の解析器の出力は練習のための仮のものです。本書の試験では、凍結版はこの形に効果を出しませんでした。）
   **4 と 5 の違い**: どちらも site は `psycopg.Cursor.execute` で、実際のライブラリと違います。4 は、実際の動作も DB の操作で、**kind（DB）は合っている**ので、名前の違いは判定にも誤の原因にも影響せず（`note` に書くだけ）、誤の原因は別の理由（E1）で決まります。5 は、実際の動作が DB の操作ですらなく、**kind まで違う**ので、受け手の読み違いそのものが誤の原因で、E4 です。

### 演習 51-3（通信先の種類）

1. **定数の外部ホスト**。宛先のホスト（`api.github.com`）はコードの定数です。モデルが決めるのはパスの部分（`owner`・`repo`）だけで、「モデルが決める宛先」の定義（宛先のホストをモデルが決められる）には当たりません。
2. **モデルが決める宛先**。`base_url` はツールの引数なので、宛先のホストをモデルが決められます。
3. **その他・不明**。宛先は環境変数 `SEARCH_URL`（運用者の設定）で決まり、既定値が外部のものです。手引きの 15.3 節では、既定値が外部を想定しているので D3 に反する（正）と読めますが、通信先の 4 つの種類に「運用者の設定」は無いので、「その他・不明」です（手引き 16.3 節の表の例と同じ形）。
4. **モデルが決めるコード・コマンド**。実行するコード `expr` をモデルが決められます。モデルは通信するコードも実行させられます。

### 演習 51-4（note を書く）

- `write_target`: **その他・不明**
- `note` の例: `境界の事例: 前の呼び出しが残した応答ファイル（孤児）の削除（reaper_mcp_server.py:368）。同じ呼び出しで作ったものではなく、mailbox は OS の一時領域でもないので 5（一時ファイル）に当たらない。ツールが自分で保存して読み返すものでもないので 6（キャッシュ・状態の保存）にも当たらない。16.2 に扱いが無い`

理由: 手引きの 16.2 節の最後は、判定の途中で境界の事例が出て決められないときは「その他・不明」にし、事例を `note` に書く、途中で定義を足さない、と決めています。この位置の扱いは、手引きの境界の例にはっきり書かれていません（[第 43 章](ch43.md) 43.12 節、本章 51.5 節の境界 1）。ただし、学生が**封の前に**この位置の扱いを境界の例に書き足していれば、それに従います。

### 確認問題 51-1

- 書き込み先の種類（D3 は通信先の種類）は `write_target` 欄に書きます。書くのは、D1・D2・D4（D3）の矛の判定で**正**にしたときと、見落としの判定で宣言に反する動作が見つかったとき、不の中身の判定で**違反**にしたときです。
- 誤の原因は `error_class` 欄に、E1〜E9 の記号と 1 文の説明を書きます。書くのは、矛の判定で**誤**にしたときです。
- **不明**のときは、どちらも書きません。E9 も付けません。`unknown_reason` 欄に決められない理由を書きます。

### 確認問題 51-2

**データベース**を付けます。
SQLite のキャッシュ DB への書き込みは、2 番の「DB の行・スキーマ・DB に残る設定を変える」にも、6 番の「ツールの動作のために自分で保存し、後で読み返す」にも当てはまります。
規則では、1 番から順に見て最初に当てはまったものを付けるので、6 番より先にある 2 番の「データベース」になります。
手引きの 16.2 節の境界の例も「データベース。順 2 が順 6 より先」と書いています。
目的（キャッシュ）ではなく、書き先（DB の行）で決まります。

### 確認問題 51-3

「キャッシュ・状態の保存」の定義は「ツールの動作のために自分で保存し、**後で読み返す**」です。
練習用サーバの `_save_cache` は、名前はキャッシュですが、書いたファイルを読む行が木のどこにもありません（grep で確かめると、`CACHE_DIR` が出てくるのは 7・11・12 行だけ）。
だから、定義どおりなら当てはまりません。
ほかの種類にも当てはまらないので、**その他・不明**にし、`note` に「キャッシュの名前だが読み返しが無い」と書きます。
名前ではなく動作で決める、という例です。

### 確認問題 51-4

- **E1 になる形**: 効果が「一度だけの初期化」の中にあり、その初期化を先に済ませる場所が **lifespan の中**か**モジュールの読み込み時**（v4 の shyhurricane）。どの起動の方法でも、ツールの受付より前に必ず走るので、ツールの呼び出しでは届きません。
- **E1 にならない形**: 初期化を先に済ませる場所が **`main()` の中だけ**（または `if __name__ == "__main__":` の中だけ）（v4 の ccr）。`fastmcp run file.py:mcp` のように `main()` を通らずに起動すれば、最初のツールの呼び出しで初期化が走るので、「到達する」側です（条件の種類は「起動の方法」）。
- **E6 から分ける理由**: **D67 の 2** で、lifespan の形の誤りは、解析器を変えず、設計の選択による限界（誤警報の向き）として**件数を報告する**と決め、判定の手引きの誤の原因の欄に、この類を設けるとしたからです。E6 にまとめると、その件数が数えられなくなります。

| `minutes` | かかった分数 |

**3. 「最初から不明」の問題**

- 文書が見つからないことは、調べてみるまで分かりません。パス・名前・本体・同じ木の別のツールの使い方から決められることもあります（52.10 節の `retitle_ticket`）。調べれば分かるものを不明にしないのが約束です（手引き 19 節）。
- 調べずに不明にすると、`unknown_reason` に「何を調べて、なぜ決められなかったか」が書けず、第三者が確かめられません。
- 不明が増えると、不の中身の結果（不の中に違反がどれだけあったか）が、判定者の手間の掛け方で動いてしまいます。

**4. README に説明がある場合**

「手元の写しで相手の板を丸ごと置き換える」なら、相手のサーバにある前からの板を上書きします。D2 の問い（呼び出しの前からあったものを上書きするか）に照らして**反する**ので、結果は**違反**です。`write_target` は「相手側の状態」、`condition_type` は「なし」、`evidence` に README のファイルと行を足します。手引きの 15.2 節の POST の行（既存の資源を更新・削除するなら反する）に当たります。

### 演習 52-3（手引きで決まらない事例）

**1. 確かめること（順の例）**

1. 手引きの該当の節: 到達（14 節）、宣言の問いと表と**迷いやすい形**（15 節）、書き込み先の境界の例（16.2 節）、誤の原因の例（17 節）。
2. 手引き 11.3 節: 採った原理を字義どおりに当てる。原理に戻れば決まらないか。
3. `docs/contradiction_principles.md` の §6（採った原理）と §7（判定表）。
4. `docs/decisions.md` の決定（D67〜D70 など）。
5. 迷っているのが**判定**（正・誤、反するか、到達するか）か、**印**（書き込み先の種類）か。

（ログファイルへの追記のように、前は決まっていなかったが今の手引きでは決まっている形もある。52.14 節）

**2. 記録**

- その組の判定を**不明**にする（矛の判定なら `verdict`、不の中身なら `outcome`）。
- `unknown_reason` に「手引きで決まらない: <事例の説明>」と書く。見落としの判定表には `unknown_reason` の欄が無いので、封の前に決めた書き方に従う（決まっていなければ `note` に書く。52.8 節、未決）。
- `evidence` にファイルと行、`note` に迷った点（手引きのどの文とどの文が食い違うか）、`minutes`。
- 事前登録の **§5（逸脱の記録）** に事例を書く。欄の例: 日付、対象（手引きの節と組）、変更前（手引きのまま）、変更後（変えない。その件を不明にした）、理由、その時点で見ていた数値（集計は見ていない）。

**3. 規則を足したくなったら**

- 原則として、**手引きは判定の途中で変えない**。
- どうしても足すなら、(1) 足した日時を記録し、(2) 足す前に判定した件と後の件を分けて報告し、(3) 足した規則で前の件を付け直した結果も併記する。
- **主の結果は、事前登録した（封をした）手引きのままの判定**。つまり、前の 2 件も、足した後の件も、主の結果では手引きのまま（この形は不明）で数え、足した規則での結果は事後の分析として分けて並べる。

**4. 解析器の読み違いに気づいたら**

直しません（凍結。事前登録の下書き §2.12 の (a)・(h)）。その組は手引きどおりに判定し（誤なら E1〜E9、決まらなければ不明）、`docs/open_questions.md` に限界として書きます（v4 の O43 と同じ扱い）。

**5. 迷っているのが書き込み先の種類だけなら**

判定（正・違反など）はそのままにし、`write_target` を「その他・不明」にして、事例を `note` に書きます（手引き 16.2 節の最後）。判定を不明にする 22 節の手続きにはしません。途中で定義を足さないのは同じです。

### 演習 52-4（不の中身の判定。4 つの組）

**1. 対象になりうる組**

- 対象になりうる: `open_ticket`（D2 の不 `net_post`）、`check_tool`（D1 の不 `spawn_command`）、`run_named`（D1 の不 `db_sql_unreadable`）。
- なりえない: `export_note`。D2 の**矛**（`fs_writeout_model_path`）なので、不の中身ではなく、**矛の判定（V2）**で扱われます。
- 補足: 4 つは同じ木のツールです。不の中身は 1 木 1 組なので、この木が選ばれても、実際に判定するのは宣言ごとに 1 組だけです（D1 なら `check_tool` と `run_named` のどちらか 1 組、D2 なら `open_ticket`）。

**2. 3 組の判定**

| 組 | `outcome` | `reachable` | `violates` | 違反なら / 違反でないなら |
|---|---|---|---|---|
| `open_ticket` × NET × D2 | 違反でない | はい | いいえ | 理由: 「`POST /api/tickets` は新しい課題を作るだけで、前からある課題を消す・上書きする・変えない（手引き 15.2 の POST の行。文書の URL を evidence に）」 |
| `check_tool` × SPAWN × D1 | 違反でない | はい | いいえ | 理由: 「起動するのは定数の `which` で、PATH の中からコマンドの場所を探すだけ。モデルが決めるのは探す名前だけで、そのコマンドを起動はしない。出力は捨てている」 |
| `run_named` × DB × D1 | 違反 | はい | はい | `write_target`: データベース。`condition_type`: 運用者の設定; 引数。`condition`: 「環境変数 `STATS_ADMIN` を設定して起動し、かつ `kind="reset"` を渡したとき」 |

考え方:
- `open_ticket`: 同じ `POST` でも、D1 と宣言していたら、相手に課題が増えるので違反でした（52.9 節）。宣言を必ず確かめます。
- `check_tool`: `argv[*]` の主体は `MODEL`（`name`）ですが、`argv0` は定数の `which` です。`which` の説明書で働きを確かめ、URL を `evidence` に書きます。
- `run_named`: `QUERIES` の値を読むだけだと `SELECT` しか見えません。木の中を grep すると、13〜14 行で、環境変数があるときだけ `DELETE FROM events` が足されることが分かります。取りうる SQL に `DELETE` が入るので、D1 に反します。辞書や定数の書き換えを grep で確かめる、という 52.10 節のつまずきの例です。

**3. (B) に数えるか**

(B) は「運用者が決める条件（運用者の設定・起動の方法）でしか届かないもの」を除いた数です。`run_named` は「運用者の設定」を含むので、条件の定義（手引き 14.3 節: 1 つでも運用者が決める条件があれば (B) に数えない）に当てはめると、**(B) には数えません**。(C)（条件なしだけ）にも数えません。
ただし、手順書と事前登録の下書きが (B)(C) の数を出すと書いているのは、矛の判定の正についてです（手順書 23.5 の「条件の内訳」、事前登録の下書き (g)）。不の中身の違反について (B)(C) を出すかは、書かれていません（本書の読み。未決）。

### 確認問題 52-1

- 理由: 先に解析器の出力（「矛が無い」「効果 0 件」など）を見ると、その内容に引っぱられ、解析器が見ていないところ（sink 表に無いライブラリ、深い呼び出し、デコレータの中）を、人も同じように見落としやすくなる（先入観）。すると見落としの数が実際より少なく出て、解析器を実際より良く見せる**誤 clear の向き**に偏る。手順書 0-3 は「先に見ると引っぱられる」と書き、D69 の 3 は「解析器の出力を見る前に判定する」と決めている。
- 出力を見る段（18.2 の 4）では、そのユニットの行に付いた、対象の宣言の **`contradiction_unknown:<宣言>:<理由>`**（不）の注記を探し、書き出した動作の 1 行ずつと照らす。

### 確認問題 52-2

- 5 つの結果: **反する動作は無い / 解析器が不として出している / 見落とし / 見落とし（深さ 4 の外）/ 不明**。
- 「見落とし（深さ 4 の外）」を別に数える理由（D68 の 2）:
  1. 普通の見落としに数えると、見落としの数が、判定者がどこまで深く読んだかで変わる（熱心に読むほど増え、同じ手引きで判定し直しても同じ数にならない）。
  2. 「反する動作は無い」にすると、判定者が知っている違反を安全側に倒すことになる（CLAUDE.md 規則 4 に反する）。
- だから、主の見落としの数は「深さ 4 の中」という決まった範囲の数にし、深さ 4 の外は消さずに別に数えて併記する。

### 確認問題 52-3

- 対象と規模: 解析器が不を出した組（ユニット, 効果, 宣言）。**D1・D2 のそれぞれで、不の組を持つ木から 50 木**（50 木に満たなければ全木）を seed ③ で選び、**各木から 1 組**（計 100 組）。D69 の 4。
- D3・D4 の不: 判定しない。件数と理由だけを報告する（D69 の 4）。
- E1〜E9 を付けない理由: E1〜E9 は、解析器が「矛」と言ったのに違反ではなかったとき（解析器の誤り）の原因の分類。不の中身の「違反でない」は、解析器が「決められない」と言ったものが調べたら違反ではなかった、というもので、解析器は誤っていない。だから記号ではなく、違反でない理由を 1 文で書く（手引き 18A.2 の 5）。

### 確認問題 52-4

- (a) 保留のもの: **判定の一貫性の確認（判定し直し）**と、**2 人目の判定者**（D70 の 8）。決めるなら、データを見る前（遅くとも段階 6 の抜き取りのコミットの前）に事前登録へ書く。後から足すなら逸脱として理由を書き、事後の分析にする。
- (b) 使わないと決まったもの: **AI（LLM）**。判定・原ソースを読む補助・記録のどれにも使わない（D70 の 3）。
- 手順書の 21 節の 5・6 に従ってはいけない理由: どちらも **D70 の前の文面**だから。21 の 5 は判定し直しを「事前登録に書いた場合」に行う前提で書いていて保留になっておらず、21 の 6 は「AI を読む補助に使う場合」の注意を書いていて、D70 の 3（読む補助にも使わない）と合わない。手引きの下書きは、この 2 点を D70 に合わせて直してある（下書きの冒頭の「直したのは次の 4 点」）。判定では手引きの下書き（承認後は `docs/final_judging_guide.md`）に従う。
