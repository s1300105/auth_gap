## 第 16 章 宣言を読む

> **この章で分かること**:
> - 解析器が、ツールに書かれた宣言（`annotations`）をどう読み取り、manifest の **`D_kind`** という欄にどうまとめるか。
> - `D_kind` の 9 つの欄（`explicit`・`present_no_bound`・`upper`・`bottom`・`open_world`・`closed_world`・`idempotent`・`malformed`・`unknown`）の正確な意味。
> - とくに、**`explicit` は「作者が書いたキーの一覧」ではない**こと。入るのは `readOnlyHint`（true のとき）・`destructiveHint`（false で、`readOnlyHint: true` が無いとき）・`openWorldHint`（true のとき）の 3 つだけです。第 3 版の説明はここが不正確でした。
> - 1 つの効果に、D1〜D4 のどれを当てるかの決まり方。D2・D4 は「`readOnlyHint: true` が無いとき」だけ当てること。`readOnlyHint` が明示の `false` でも、書いていなくても、扱いは同じであること。
> - **D3 は `closed_world`、D4 は `idempotent` という別の欄に表れ、`explicit` には入らない**こと。それが、最終評価の分母 (c) の数え方に**未決**の問題を生むこと。
> - D3・D4 を以前は「探索的」と呼んでいたが、今は D1〜D4 の 4 つとも主指標であること（D62）。
> - snake_case の宣言（`read_only_hint=True`）が、MCP の Python SDK の版によって届いたり届かなかったりすること。解析器の 3 通りの扱い（宣言として読む・`D_malformed`・`D_unknown`）。
> - 届かない宣言の率 **`r_malformed`** の定義・値・古い値の注意。最終評価で数えて報告すること（D65）。
> - 判定の手順 A・B、見落としの抜き取り、集計の場面で、この章の知識をどう使うか。

### この章の位置づけ

[第 11 章](ch11.md)で、解析器が 1 本の木を処理する 7 つの段階を見ました。
入口を探す（①）→ 中をたどる（②）→ 効果を見つける（③）→ 値を追いかける（④）→ 宣言を読む（⑤）→ 照合する（⑥）→ 書き出す（⑦）、です。
この章は、そのうちの **⑤ 宣言を読む** の章です。

①〜④で、解析器は「このツールは実際に何をしうるか」を集めました。
⑤は、もう一方の材料である「このツールは自分について何を約束しているか」を読む段階です。
⑥の照合（[第 17 章](ch17.md)）は、この 2 つを突き合わせます。
つまり、この章は「突き合わせる片方の材料を、どう用意するか」の章です。

[第 11 章](ch11.md)で見たとおり、実際のプログラムの中では、宣言を読むのはユニットごとの解析のいちばん最初です。

#### この章で使う言葉の思い出し

この章は、前の章で定義した言葉を使います。忘れていたら、ここで思い出してください。

- **宣言**（[第 4 章](ch04.md)）: ツールが自分の性質について申告する欄（MCP の ToolAnnotations）。`readOnlyHint`・`destructiveHint`・`idempotentHint`・`openWorldHint`・`title` の 5 つの項目がある。
- **D1〜D4**（[第 4 章](ch04.md)）: 約束をしている側の値に付けた記号。D1 = `readOnlyHint: true`（環境を変えない）、D2 = `destructiveHint: false`（壊さない。足すだけ）、D3 = `openWorldHint: false`（外の世界と関わらない）、D4 = `idempotentHint: true`（同じ引数で繰り返しても追加の効果が無い）。
- **既定値**（[第 4 章](ch04.md) 4.4 節）: 項目を書かなかったときにクライアントが受け取るべき値。4 つとも「何も約束しない側」の値。
- **ユニット**（[第 12 章](ch12.md)）: 解析の単位になる 1 つのツール。**木**（第 5・12 章）: 1 つのリポジトリ（1 つの MCP サーバ）。
- **`annotation_form`・`annotations`**（[第 12 章](ch12.md)）: manifest の `unit` の欄。宣言を書いた形（`dict`・`ToolAnnotations`・`unreadable` など）と、読み取った値。
- **kind**（[第 13 章](ch13.md)）: 効果の種類。`FS_READ`・`FS_WRITE`・`NET`・`DB`・`SPAWN`・`EXEC`・`DISPATCH` の 7 つ。
- **矛・不・内**（[第 11 章](ch11.md)）: 解析器の 3 つの答え。矛 = 宣言に反する動作がある。不 = 静的には決まらない。内 = 宣言の範囲内。
- **分母 (c)**（[第 4 章](ch04.md) 4.4 節）: 「宣言を書いたサーバのうち、違反が見つかった木の割合」の分母。その宣言を明示的に書いたユニットを 1 つ以上持つ木の数。
- **誤 clear**（[第 14 章](ch14.md)）: 解析器が「問題なし」としたのに、本当は問題がある誤り。

### 16.1 いろいろな書き方と、既定値を補わないこと

#### 一言で言うと

宣言は、辞書・`ToolAnnotations` というクラス・低レベルの `Tool(...)` など、いろいろな形で書けます。
解析器はどの形も読み、**書いた形**を `annotation_form` に、**読み取った値**を `annotations` に写します。
何も書いていなければ「宣言は無い」とし、MCP の既定値で埋めません。

#### たとえ話 — 役所への届け出

役所への届け出は、紙の様式に書いても、電子申請で出しても、窓口で用紙を渡しても、中身は同じです。
受付の人は「どの方法で出されたか」を記録し、それとは別に「何が書いてあるか」を読みます。

受付の人は、**空欄を空欄のまま**受け付けます。
「この欄は空欄だから、『いいえ』と書いたのと同じだろう」とは扱いません。
空欄は「答えていない」であって、「いいえと答えた」ではないからです。
[第 4 章](ch04.md)の 4.4 節で、申込書の空欄を「ペットは飼わない」と読む誤りのたとえを見ました。
解析器も、これと同じ受付の人のように振る舞います。

#### 小さな例 — 6 つの書き方と、manifest に写る値

次の作例は、同じ `os.remove(path)`（ファイルを消す）を本体に持つツールを、宣言の書き方だけ変えて並べたものです（作例を走査して確かめた。一部を抜粋）。

```python
 1  READ_ONLY = ToolAnnotations(readOnlyHint=True)
 2
 3  @mcp.tool(annotations=ToolAnnotations(readOnlyHint=True, destructiveHint=False))
 4  def t_j(path: str) -> str: ...
 5  @mcp.tool(annotations={"readOnlyHint": True, "openWorldHint": False, "title": "検索"})
 6  def t_b(q: str) -> str: ...
 7  @mcp.tool(annotations=ToolAnnotations(**{"readOnlyHint": True}))
 8  def t_i(path: str) -> str: ...
 9  @mcp.tool(annotations=READ_ONLY)
10  def t_g(path: str) -> str: ...
11  @mcp.tool(annotations=None)
12  def t_h(path: str) -> str: ...
13  @mcp.tool()
14  def t_f(path: str) -> str: ...
```

manifest に写った値は、次のとおりでした。

| ツール | 書き方 | `annotation_form` | `annotations` |
|---|---|---|---|
| `t_j` | `ToolAnnotations(...)` | `ToolAnnotations` | `{"destructiveHint": false, "readOnlyHint": true}` |
| `t_b` | 辞書 `{...}` | `dict` | `{"openWorldHint": false, "readOnlyHint": true, "title": "検索"}` |
| `t_i` | `ToolAnnotations(**{...})` | `unpack` | `{"readOnlyHint": true}` |
| `t_g` | 変数 `READ_ONLY` | `unreadable` | （欄なし） |
| `t_h` | `annotations=None` | `absent` | （欄なし） |
| `t_f` | `annotations=` を書いていない | （欄なし） | （欄なし） |

表の読み方: 1 行が 1 つのツールです。
たとえば 4 行目は「`annotations=READ_ONLY` のように変数で渡したツールは、`annotation_form` が `unreadable`（読めない形）になり、`annotations` の欄は出ない。1 行目で `READ_ONLY` に `readOnlyHint=True` を入れていても、解析器はその中身を見に行かない」と読みます。

#### 一歩ずつ

コードを 1 行ずつ見ます。

- 1 行目: `READ_ONLY` という変数に、`ToolAnnotations(readOnlyHint=True)` を入れています。宣言を前もって作っておき、後で使い回す書き方です。
- 3 行目: `@mcp.tool(...)` は、すぐ下の関数をツールとして登録するデコレータです（第 9・12 章）。`annotations=` の後ろが宣言です。ここでは `ToolAnnotations(...)` という専用のクラスを呼んで作っています。
- 5 行目: 同じ宣言を、辞書（`{"キー": 値, ...}`）で書いています。キーは文字列で、`"readOnlyHint"` のように引用符で囲みます。
- 7 行目: `ToolAnnotations(**{...})` は、辞書を `**` で「ほどいて」キーワード引数として渡す書き方です。`ToolAnnotations(readOnlyHint=True)` と同じ意味になります。
- 9 行目: 1 行目の変数を渡しています。人が読めば中身は分かりますが、解析器は `annotations=` の後ろに直接書かれた式しか読みません。
- 11 行目: `annotations=None` は、「宣言は無い」と明示した書き方です。
- 13 行目: `annotations=` そのものを書いていません。

解析器の読み方（[第 12 章](ch12.md)で見た内容の思い出し）は、次のとおりです。

- `annotations=` の後ろが `ToolAnnotations(...)` の呼び出しなら、形は `ToolAnnotations`。中に `**{...}` があれば `unpack`。
- `{...}` の辞書なら、形は `dict`。
- `None` なら、形は `absent`。
- それ以外（変数・別の関数の呼び出しなど）は、形は `unreadable`。中身は読まない。
- `annotations=` が無ければ、形の欄そのものが出ない。

低レベルの書き方（`Tool(name="list", annotations=ToolAnnotations(readOnlyHint=True))`）も、同じ読み方です。
`Tool(...)` に書かれた宣言は、ツールの名前でユニットと結び付けられます（[第 12 章](ch12.md)）。
（出典: `authgap/entries.py:2712-2796`（`_read_annotations`）、`:2803-2852`（`join_annotations`）。作例は本書の執筆時に走査して確かめた）

#### `annotations` は原ソースの写しではない

ここで大事な注意があります。
`annotations` の欄は、原ソースに書かれた宣言を**そのまま写したものではありません**。
解析器は、次の 3 つを通してから写します。

1. **5 つの項目だけを残す。** `title`・`readOnlyHint`・`destructiveHint`・`idempotentHint`・`openWorldHint` 以外のキー（たとえば仕様に無い `category`）は捨てます。仕様書も「仕様外の `category` も D ではない」と書いています。
2. **値がリテラル（その場に書かれた定数）のときだけ残す。** `{"readOnlyHint": FLAG}` のように値が変数なら、そのキーを捨てます。
3. **snake_case のキー（`read_only_hint` など）は、mcp の版によって、camelCase に直して残すか、別の欄に移す。** これは 16.8 節で詳しく見ます。

作例で確かめると、`ToolAnnotations(readOnlyHint=True, category="files")` の `annotations` は `{"readOnlyHint": true}` になり、`category` は消えていました。
`{"readOnlyHint": FLAG}`（`FLAG = True` をモジュールの一番上で定義）の `annotations` は `{}`（空）で、`D_kind` は「宣言なし」になりました。
2 つ目は、作者の意図（読むだけ）が照合に使われない形です。
これは添削で見つかり、直さない限界として O42 の U41（「宣言の読み取りが SDK の署名と pydantic の変換どおりでない」）に記録されています。
U41 の説明には「`readOnlyHint=IS_RO` のように値が変数になっている形」「`readOnlyHint=1` や `"true"` のように、実行時に真偽値へ変換される値」が並び、「こうした宣言は『宣言なし』（⊥）として扱われ、仕様にある『読めないものは D_unknown（不明）』にもなりません」と書かれています。
（出典: `authgap/entries.py:2754-2759`（5 つの項目とリテラルだけを残す）、`AUTHGAP_BRIEF_v3.md:322`（`category`）、`docs/open_questions.md:1127`（U41）、`docs/review_triage.md:2020`（U41 の説明）。作例は本書の執筆時に走査して確かめた）

#### 既定値を補わない

**何も書いていなければ、宣言は無いとみなします。MCP の既定値を勝手に補いません。**

[第 4 章](ch04.md)の 4.4 節の表を思い出してください。
既定値は `readOnlyHint` が false、`destructiveHint` が true、`idempotentHint` が false、`openWorldHint` が true で、4 つとも「何も約束しない側」の値でした。
D1〜D4 はどれも既定値の**反対側**の値なので、既定値を補っても D1〜D4 は 1 つも生まれません。

仕様書は、この取り決めを「既定値による補完を禁止し、当該フィールドが明示的に存在する場合のみ D_kind とする。annotation の不在は『非破壊の宣言』ではない」と書いています。
解析器のコードにも、宣言を表す型の説明に「既定値による補完を禁止する」と書いてあります。
（出典: `AUTHGAP_BRIEF_v3.md:316`、`authgap/dparse.py:55-60`（`DKind` の説明）。既定値の表は[第 4 章](ch04.md) 4.4 節）

#### なぜそうするのか

理由は 3 つあります。

1. **「書いていない」を「安全だと言った」と読み違えないため。** 「`destructiveHint` を書いていないから、壊さないツールなのだろう」と読むのは、空欄を「いいえ」と読むのと同じ誤りです。何も書いていないツールは、何も約束していません。約束していないのだから、「約束を破った」とも言えません。
2. **論文の結論の分母を正しく作るため。** 最終評価の分母 (c) は、「その宣言を明示的に書いたユニットを 1 つ以上持つ木」で、「既定値で補ったものは数えない」と決まっています（D70 の 4）。既定値で埋めると、「宣言を書いたサーバのうち」という問いに答えられなくなります。
3. **読めないものを黙って片方に倒さないため。** 変数で渡した宣言（`unreadable`）は、「宣言なし」とも「読むだけ」とも決めず、「読めない」（`unknown`）として残します（16.2 節）。この研究の芯は「分からないものを分からないと数える」ことです（[第 6 章](ch06.md)）。

（出典: `docs/decisions.md:3904`（D70 の 4）、`AUTHGAP_BRIEF_v3.md:322`（「読めない形は `D_unknown` とし `⊥` と混ぜない」））

#### よくある誤解・つまずき

- **誤解: 「manifest の `annotations` は原ソースの宣言の写しだ」**
  違います。5 つの項目、リテラルの値だけが残り、snake_case は版によって直されたり外されたりします。判定では、必ず原ソースの宣言も見比べてください。
- **誤解: 「`annotation_form` の欄があれば、宣言がある」**
  `absent` は「宣言は無い」と明示したもの、`unreadable` は読めなかったものです。どちらも照合には使われません。
- **誤解: 「何も書いていないツールは、`readOnlyHint: false` と書いたのと同じだ」**
  D2・D4 を当てるかどうか（16.5 節）では、結果は同じになります。けれども manifest の欄は違います。`readOnlyHint: false` と書けば、その名前が `present_no_bound`（16.2 節）に残ります。何も書かなければ残りません。「書いたが約束しない値だった」と「書いていない」は、記録の上では区別されます。
- **誤解: 「`readOnlyHint=1` は true と同じなので D1 だ」**
  実行時の pydantic は `1` を `True` に変換しますが、解析器は Python の `True` そのものしか D1 と読みません（16.3 節）。既知の限界 U41 です。

#### 手作業ではどう使うか

- **手順 C・D で原ソースを開いたとき**: ツールの `def` の行の上にあるデコレータの `annotations=` を読み、manifest の `annotations`（道具の出力の「宣言:」の行）と見比べます。食い違っていたら（変数・`1`・snake_case・`category` など）、判定表の `note` に書き留めます。
- **宣言そのものが疑わしいとき**: 判定するのは「その組の宣言に反するか」です。解析器が読み落とした宣言（変数で渡したもの）に、人が勝手に D1 を当てて判定し直すことはしません。判定の対象は、解析器が出した組だけです（[第 48 章](ch48.md)）。
- **集計のとき**: 分母 (c) の木を数えるときに、「宣言を書いたか」を既定値で補って数えないでください（[第 39 章](ch39.md)）。

#### この節のまとめ

宣言の書き方は `dict`・`ToolAnnotations`・`unpack`・`unreadable`・`absent` などの形に分かれ、`annotation_form` に記録される。
`annotations` は 5 つの項目のリテラルの値だけを写したもので、原ソースの写しではない。
何も書いていなければ宣言は無いとし、既定値で補わない（「書いていない」を「安全だと言った」と読まない）。

### 16.2 `D_kind` — 宣言の読み取り結果の欄

#### 一言で言うと

**`D_kind`** は、解析器が `annotations` から作る「このツールは何を約束しているか」のまとめです。
manifest のユニットごとに 1 つ書かれます。
判定（⑥）は、`annotations` ではなく `D_kind` を見て、どの宣言（D1〜D4）で照らすかを決めます。

#### たとえ話 — 問診票とカルテ

病院では、患者が問診票に答えを書きます。
医師は、問診票を読んで、カルテに「この患者に当てはまる注意」を決まった欄に書き写します。
たとえば「運動の制限: あり」「この薬は避ける: あり」のような欄です。

問診票に書いたことが、全部カルテの「制限」の欄に入るわけではありません。
「名前の読み方」のように、制限とは関係ない答えもあります。
それは「問診票に書いてあったが、制限には効かない」として、別の所にメモされます。

宣言で言えば、問診票が `annotations`（作者が書いたもの）、カルテが `D_kind`（解析器が決まった規則でまとめたもの）です。
`title`（表示名）は「名前の読み方」のようなもので、書いてあっても何も制限しません。

#### 小さな例 — v4 の gemini の `gemini_prompt`

v4 の実物から、1 つのツールの `annotations` と `D_kind` を並べます（`server.py:251` のツール）。

```json
"annotations": {"title": "Delegate to Gemini (Google AI)", "readOnlyHint": true,
                "destructiveHint": false, "idempotentHint": false, "openWorldHint": true},
"D_kind": {"bottom": false, "explicit": ["openWorldHint", "readOnlyHint"], "open_world": true,
           "present_no_bound": ["destructiveHint", "idempotentHint", "title"],
           "upper": ["FS_READ", "NET"]}
```

作者は 5 つの項目を全部書いています。
けれども `explicit` に入ったのは 2 つだけで、残りの 3 つは `present_no_bound` に入りました。
（出典: `evidence/scan_v2_v4_run1/v4-ankitdotgg__making-gemini-useful-with-claude.json` の `gemini_prompt`。本書の執筆時に確かめた。v4 の数字は論文に使わない）

#### 欄の一覧

`D_kind` の欄は 9 つです。

| 欄 | やさしく言うと | 正確な意味 | 欄が出るとき |
|---|---|---|---|
| `explicit` | 約束として効く明示の名前 | **上界を動かす明示**（`readOnlyHint: true`、`readOnlyHint: true` が無いときの `destructiveHint: false`）と、`openWorldHint: true` の名前の一覧 | いつも（空の一覧もある） |
| `present_no_bound` | 書いてあるが、上界を動かさない名前 | 書かれているが上界を動かさないキーの名前の一覧。`readOnlyHint: false`、`destructiveHint: true`、`readOnlyHint: true` と一緒の `destructiveHint: false`、`openWorldHint: false`、`idempotentHint`（値によらず）、`title` | いつも（空の一覧もある） |
| `upper` | してよいことの範囲 | 宣言が許す効果の kind の**上界**（集合） | 上界があるときだけ |
| `bottom` | 範囲の約束が無い | 上界が**無い**こと（記号 ⊥）。`true` / `false` | いつも |
| `open_world` | 外と関わると申告した | `openWorldHint: true` を明示した | true のときだけ |
| `closed_world` | 外と関わらないと申告した（**D3**） | `openWorldHint: false` を明示した | true のときだけ |
| `idempotent` | 繰り返しても同じと申告した（**D4**） | `idempotentHint: true` を明示し、`readOnlyHint: true` が無い | true のときだけ |
| `malformed` | 届かない書き方の名前 | snake_case で書かれ、mcp の版が 2.0 より前と決まったために届かないキー（16.8 節） | あるときだけ |
| `unknown` | 読めなかった | 読めない形（`annotation_form` が `unreadable`）か、snake_case で mcp の版が決まらない（16.8 節） | true のときだけ |

表の読み方: 1 行が 1 つの欄です。左から「欄の名前」「やさしい言い換え」「正確な意味」「その欄が manifest に出るとき」です。
たとえば 6 行目は「`closed_world` の欄は、作者が `openWorldHint: false` と書いたときだけ `true` で出る。これが D3 の印である。書いていなければ、欄そのものが出ない」と読みます。
（出典: `authgap/dparse.py:55-85`（`DKind` の欄の定義と説明）、`:87-105`（`to_json`。欄の出し方））

#### 一歩ずつ — 新しい言葉「上界」と「⊥」

`upper`（上界）は、この章で初めて出てくる言葉です。3 点セットで説明します。

- **やさしく言うと**: その宣言の下で、ツールが「してよい」効果の種類の上限です。
- **正確な定義**: 宣言が許す効果の kind の集合です。この集合に入っていない kind の効果は、宣言の外です。仕様書の Def 6（宣言の層の定義）が、`D_kind` を「効果 kind の上界」と定めています。
- **例**: `readOnlyHint: true` の上界は `{FS_READ, NET}` です。ファイルを読むことと通信することは許されるが、書き込み・DB・プロセスの起動・コードの実行は許されない、という意味です。`destructiveHint: false`（`readOnlyHint: true` が無いとき）の上界は `{DB, FS_READ, FS_WRITE, NET}` です。`SPAWN`・`EXEC` が外れています。

**⊥**（`bottom`）は、「上界が無い」ことの記号です。

- **やさしく言うと**: 「してよいことの範囲」について、何も約束していない状態です。
- **正確な定義**: `upper` が決まらない（Python では `None`）こと。`bottom: true` で表します。
- **例**: 何も書いていないツール、`title` だけのツール、`destructiveHint: true` だけのツールは、どれも `bottom: true` です。

ここで注意があります。
`bottom: true` は「範囲の約束が無い」という意味で、「D1〜D4 のどれも当たらない」という意味ではありません。
D3 と D4 は上界を動かさない宣言なので、`bottom: true` のツールにも当たりえます（16.5 節で作例を見ます）。
（出典: `AUTHGAP_BRIEF_v3.md:309, 316-320`（Def 6 の D_kind と規則）、`authgap/dparse.py:45-49`（`READ_ONLY_UPPER`・`DESTRUCTIVE_KINDS`）、`:79-85`（`is_bottom`・`covers`））

#### 一歩ずつ — 欄をどう書き出すか（`to_json` を読む）

manifest に `D_kind` を書き出すコードを、短くして読みます。

```python
 1  def to_json(self) -> dict:
 2      d = {
 3          "bottom": self.is_bottom,
 4          "explicit": list(self.explicit),
 5          "present_no_bound": list(self.present_no_bound),
 6      }
 7      if self.upper is not None:
 8          d["upper"] = sorted(self.upper)
 9      if self.malformed:
10          d["malformed"] = list(self.malformed)
11      if self.unknown:
12          d["unknown"] = True
13      if self.open_world:
14          d["open_world"] = True
15      if self.closed_world:
16          d["closed_world"] = True
17      if self.idempotent:
18          d["idempotent"] = True
19      return d
```

- 1 行目: `D_kind` を、manifest に書ける辞書の形にする関数の始まりです。
- 2〜6 行目: `bottom`・`explicit`・`present_no_bound` の 3 つは、**いつも**書きます。中身が空でも、空の一覧として出ます。
- 3 行目: `self.is_bottom` は「上界が無いか」です。上界が無ければ `true` です。
- 7〜8 行目: 上界があるときだけ `upper` を書きます。`sorted` は名前を辞書順に並べる関数なので、`["FS_READ", "NET"]` のように並びます。
- 9〜10 行目: snake_case の届かないキーがあるときだけ `malformed` を書きます。
- 11〜18 行目: `unknown`・`open_world`・`closed_world`・`idempotent` は、**true のときだけ**書きます。false のときは欄そのものが出ません。
- 19 行目: できた辞書を返します。

このコードから、manifest を読むときの大事なことが分かります。
**`closed_world` や `idempotent` の欄が見当たらないのは、「false」という意味です。** 「書き忘れ」ではありません。
（出典: `authgap/dparse.py:87-105`）

#### `explicit` に `openWorldHint` が入る理由

`explicit` の中で、`openWorldHint` だけは上界を動かしません。
それでも `explicit` に入るのは、仕様書が `openWorldHint: true` の明示に、付録の判定のための別の役割を与えているからです。
仕様書は「`openWorldHint==true` 明示 → NET の宛先が定数でないことの宣言であり P0 の private-range 制限のみを解除する」と書いています。
これは[第 8 章](ch08.md)で見た付録（降ろした主張）の側の仕組みで、核の判定（D1〜D4）には使いません。
解析器のコードの説明も、「`openWorldHint==true` 単独の明示は `explicit` に残るが上界を動かさない」と書いています。

`openWorldHint: true` は「外の世界と関わる」という申告で、何かを約束する側の値ではありません。
既定値（true）と同じ値です。
ですから、**`explicit` に `openWorldHint` があっても、それは D1〜D4 のどれでもありません。**
とくに、**D3（`openWorldHint: false`）とは逆の申告**です。
（出典: `AUTHGAP_BRIEF_v3.md:318`、`authgap/dparse.py:182-191`（`d_kind_from` の説明）、`:72-73`（`open_world` の欄の説明））

#### なぜ `explicit` と `present_no_bound` を分けるのか

仕様書は「上界を動かさないフィールドは D_kind を構成しない」と定め、`title`・`idempotentHint`・`readOnlyHint==false` 単独・`destructiveHint==true` 単独・`openWorldHint==false` 単独を挙げています。
これらは「明示されていても `D_kind = ⊥` のまま」とし、「annotation あり・上界寄与なし」として記録すると書いています。
`present_no_bound` は、この「記録」の欄です。

分けておくと、2 つの違う数を区別して出せます。

- **上界を動かす宣言を書いたユニット**（`D_kind ≠ ⊥`）: 「範囲の約束をしたツール」の数。学生は、この数え方を `r_D`（宣言を書いたユニットの割合）の分子にすると決めました（D32、O15）。
- **何かしら注釈を書いたユニット**: 「注釈を書く習慣」の数。`present_no_bound` に名前があるユニットも含みます。

`closed_world` と `idempotent` の欄は、D3・D4 の判定規則を作ったとき（D56）に足されたものです。
上界は動かさないので `explicit` には入れず、別の欄にしました。
この「別の欄にした」ことが、16.7 節の未決の問題につながります。
（出典: `AUTHGAP_BRIEF_v3.md:320`、`docs/decisions.md:449-457`（D32）、`authgap/dparse.py:74-77`（`closed_world`・`idempotent` の説明に D56 とある））

#### よくある誤解・つまずき

- **誤解: 「`explicit` には、値が true でも false でも、書かれたキーが全部入る」**
  誤りです。第 3 版の「明示された宣言（`D_kind.explicit`）」という説明は、こう読めてしまうものでした。`readOnlyHint: false` や `openWorldHint: false` は、書かれていても `explicit` に入りません。
- **誤解: 「`explicit` に `openWorldHint` がある = D3 のツール」**
  逆です。`explicit` の `openWorldHint` は `openWorldHint: true`（外と関わる）です。D3 は `closed_world: true` を見ます。
- **誤解: 「`bottom: true` なら、D1〜D4 のどれとも照合されない」**
  D3・D4 は `bottom` によらず当たります（16.5 節）。
- **誤解: 「`closed_world` の欄が無いのは、解析器が見落としたからだ」**
  `closed_world` は true のときだけ出ます。欄が無いのは false という意味です。

#### 手作業ではどう使うか

判定の手順 B で使う「1 件の情報を出す道具」（手順書 6.5 節）は、2 行目に次のように出します。

```
ツール: search_notes  定義: server.py:24  宣言: {'readOnlyHint': True}
明示された宣言: ['readOnlyHint']  打ち切り: []  opaque: ['unresolved']
```

- 1 行目の「宣言:」は `unit.annotations` です（16.1 節の注意のとおり、原ソースの写しではない）。
- 2 行目の「明示された宣言:」は `D_kind.explicit` です。

D1・D2 の組なら、「明示された宣言:」に `readOnlyHint` か `destructiveHint` が出ます。
けれども **D3・D4 の組では、「明示された宣言:」にその宣言は出てきません**。
D3 なら `closed_world`、D4 なら `idempotent` の欄を、manifest の `D_kind` で確かめるか、「宣言:」の行と原ソースから自分で決めてください（16.5 節の規則）。
「明示された宣言」に `openWorldHint` が出ていても、それは D3 ではありません。

同じ注意は、`contradictions.json`（解析器の矛の一覧）の各行にある `D_explicit` の欄にも当てはまります。
`D_explicit` は `D_kind.explicit` の写しで、どの宣言の矛かは `declarations` の欄に書かれます（16.4 節の ccr の例）。
（出典: `docs/final_evaluation_procedure.md:466-508`（道具のコードと出力の例）、`scripts/scan_v2.py:90`（`D_explicit` は `explicit` の写し））

#### この節のまとめ

`D_kind` は、`annotations` から作った「約束のまとめ」で、9 つの欄を持つ。
`explicit` は上界を動かす明示と `openWorldHint: true` の名前だけで、それ以外の書かれたキーは `present_no_bound` に入る。
`upper` は許す kind の上界、`bottom` は上界が無いこと。D3 は `closed_world`、D4 は `idempotent` に表れ、どちらも true のときだけ欄が出る。

### 16.3 キーごとの振り分け — `d_kind_from` を 1 行ずつ読む

#### 一言で言うと

`annotations` の各キーを `D_kind` のどの欄に入れるかは、`d_kind_from` という 1 つの関数が決めています。
規則は短く、「`readOnlyHint` は `True` のときだけ」「`destructiveHint` は `False` で、しかも `readOnlyHint: True` が無いときだけ」「`openWorldHint` は `True` のときだけ」`explicit` に入れ、それ以外の書かれたキーは `present_no_bound` に入れる、です。
D3・D4 の印（`closed_world`・`idempotent`）は、最後に別に立てます。

#### たとえ話 — 郵便局の仕分け棚

郵便局では、手紙を宛先で仕分けます。
「速達」の札が付いた手紙は速達の棚へ、それ以外は普通の棚へ入れます。
さらに、「割れ物注意」のシールが貼ってあれば、どちらの棚に入れるかとは別に、荷物に赤い印を付けます。

`d_kind_from` も同じです。
`explicit` の棚と `present_no_bound` の棚があり、キーと値の組み合わせで、どちらの棚に入るかが決まります。
`closed_world` と `idempotent` は「赤い印」にあたり、棚とは別に立ちます。
たとえば `openWorldHint: false` は `present_no_bound` の棚に入り、**それとは別に** `closed_world` の印が立ちます。

#### 小さな例 — 関数の本体（短くしたもの）

```python
 1  if form == "unreadable":
 2      return DKind(unknown=True)
 3  if not ann:
 4      return DKind()
 5  explicit, no_bound, upper, open_world = [], [], None, False
 6  read_only = ann.get("readOnlyHint")
 7  destructive = ann.get("destructiveHint")
 8  open_world_hint = ann.get("openWorldHint")
 9
10  if read_only is True:
11      explicit.append("readOnlyHint")
12      upper = {"FS_READ", "NET"}
13  elif "readOnlyHint" in ann:
14      no_bound.append("readOnlyHint")
15
16  if destructive is False and read_only is not True:
17      explicit.append("destructiveHint")
18      upper = (upper or set()) | {"FS_READ", "NET", "FS_WRITE", "DB"}
19  elif "destructiveHint" in ann:
20      no_bound.append("destructiveHint")
21
22  if open_world_hint is True:
23      explicit.append("openWorldHint")
24      open_world = True
25  elif "openWorldHint" in ann:
26      no_bound.append("openWorldHint")
27
28  for f in ("title", "idempotentHint"):
29      if f in ann:
30          no_bound.append(f)
31
32  return DKind(upper=upper, explicit=explicit, present_no_bound=no_bound,
33               open_world=open_world,
34               closed_world=open_world_hint is False,
35               idempotent=ann.get("idempotentHint") is True and read_only is not True)
```

（原典はもう少し長く、18 行目の後に `EXEC`・`SPAWN` を上界から除く行があり、32 行目で一覧を名前順に並べ直しています。意味は変わらないので省きました。）

#### 一歩ずつ

Python に慣れていない人のために、1 行ずつ説明します。

- 1〜2 行目: 宣言の形が `unreadable`（読めない形）なら、ほかは何も見ずに「読めない」（`unknown=True`）の `D_kind` を返します。上界も無いので `bottom: true` です。
- 3〜4 行目: `ann`（`annotations` の辞書）が空か無いなら、何も入っていない `D_kind` を返します。上界が無いので `bottom: true` です。何も書いていないツールや `absent` は、ここで終わります。
- 5 行目: これから使う入れ物を用意します。`explicit` と `no_bound` は空の一覧、`upper` は「まだ上界が無い」（`None`）、`open_world` は false です。
- 6〜8 行目: `ann.get("readOnlyHint")` は、辞書から `readOnlyHint` の値を取り出します。キーが無ければ `None`（何も無い）を返します。3 つのキーの値を、それぞれ変数に入れておきます。
- 10 行目: `read_only is True` は「値が Python の `True` **そのもの**か」を確かめる書き方です。`1` や `"true"` は `True` そのものではないので、ここは通りません。
- 11〜12 行目: `True` なら、`explicit` に `readOnlyHint` を入れ、上界を `{FS_READ, NET}` にします。
- 13〜14 行目: `elif` は「そうでなく、もし〜なら」です。`"readOnlyHint" in ann` は「辞書にそのキーがあるか」です。つまり、「キーはあるが値が `True` ではない」（`false` や `1`）なら、`present_no_bound` に入れます。
- 16 行目: `destructive is False and read_only is not True` は、「値が `False` そのもので、しかも `readOnlyHint` が `True` ではない」という条件です。
- 17〜18 行目: そのときだけ、`explicit` に `destructiveHint` を入れ、上界に `FS_READ`・`NET`・`FS_WRITE`・`DB` を足します。
- 19〜20 行目: それ以外で `destructiveHint` のキーがあれば（`true` のとき、または `readOnlyHint: true` と一緒に `false` を書いたとき）、`present_no_bound` に入れます。
- 22〜24 行目: `openWorldHint` が `True` なら、`explicit` に入れ、`open_world` を true にします。
- 25〜26 行目: それ以外で `openWorldHint` のキーがあれば（`false` のとき）、`present_no_bound` に入れます。
- 28〜30 行目: `title` と `idempotentHint` は、値が何であっても、キーがあれば `present_no_bound` に入れます。**この 2 つは決して `explicit` に入りません。**
- 32〜35 行目: 結果をまとめて返します。34 行目で、`openWorldHint` が `False` そのものなら `closed_world` を true にします（D3 の印）。35 行目で、`idempotentHint` が `True` そのもので、しかも `readOnlyHint` が `True` ではないなら `idempotent` を true にします（D4 の印）。

（出典: `authgap/dparse.py:179-237`（`d_kind_from`））

作例を走査して、表のとおりになるかを確かめました（`analyzer-freeze-3`）。

| `t_e` | `{"readOnlyHint": 1}` | （空） | `readOnlyHint` | `bottom: true` | なし |

たとえば 4 行目の `t_d` は「`readOnlyHint: false` と `openWorldHint: false` を書いた。`explicit` は空で、`bottom: true`（範囲の約束は無い）。それでも `closed_world` が立つので D3 で照らされ、外部ホストへの通信が D3 の矛になった」と読みます。

（出典: 作例は本書の執筆時に走査して確かめた。`docs/open_questions.md:1127`（U41））

#### なぜそうするのか

- **`readOnlyHint` を `True` のときだけ `explicit` に入れる理由**: `readOnlyHint: false` は既定値と同じで、「環境を変えうる」という申告です。何も約束していないので、上界を作りようがありません。
- **`destructiveHint: false` を `readOnlyHint: true` があるときに外す理由**: SDK の説明文は、`destructiveHint` について「この項目は `readOnlyHint` が false のときだけ意味を持つ」と書いています。読むだけのツールに「壊すか」を問う意味はありません。上界も、`readOnlyHint: true` の `{FS_READ, NET}` の方が狭いので、そちらで足ります。
- **値を `True` / `False` そのもので比べる理由**: 解析器は、原ソースを動かさずに読みます（[第 7 章](ch07.md)）。`1` や `"true"` を真偽値に直す規則（pydantic の変換）まで写すと、読み方の規則がその分だけ増えます。添削（D64）で「pydantic の変換どおりでない」ことは見つかりましたが、出現がまれで重大度が低いので、直さない限界として記録されました（U41）。
- **`idempotentHint` を `explicit` に入れない理由**: 仕様書は、`idempotentHint` を「再実行可否であり効果 kind の上界ではない」と書いています。上界を動かさないものは `explicit` に入れない、という規則に従っています。

（出典: SDK 1.30.0 の `mcp/types.py:1272, 1280`（「meaningful only when `readOnlyHint == false`」）、`AUTHGAP_BRIEF_v3.md:320`、`docs/open_questions.md:1127`、`docs/review_triage.md:2020`）

#### よくある誤解・つまずき

- **誤解: 「`explicit` は、作者が書いたキーの一覧だ」**
  誤りです。`explicit` に入りうるのは `readOnlyHint`・`destructiveHint`・`openWorldHint` の 3 つだけで、それぞれ決まった値のときだけです。`idempotentHint` と `title` は、どんな値でも決して入りません。
- **誤解: 「`destructiveHint: false` を書けば、いつも `explicit` に入る」**
  `readOnlyHint: true` と一緒に書いたときは入りません（`t_j`）。
- **誤解: 「`openWorldHint: false` は書いても無視される」**
  `explicit` には入りませんが、`closed_world` が立ち、D3 で照らされます（`t_b`・`t_d`）。
- **つまずき: 「`present_no_bound` に名前があるのに、なぜ D3・D4 が当たるのか」**
  `present_no_bound` は「上界を動かさない」という意味で、「照合しない」という意味ではありません。D3・D4 は上界ではなく、`closed_world`・`idempotent` の印で照合されます。

#### 手作業ではどう使うか

- **手順 A で判定表の `decl` を読んだとき**: 原ソースの宣言を見て、表の「振り分け」のとおりにその宣言が当たるかを、自分でも確かめます。たとえば `decl` が D2 なのに、原ソースに `readOnlyHint=True` もあれば、何かがおかしいので `note` に書きます（解析器の規則では起きないはずです）。
- **手順 C・D で宣言の値に気づいたとき**: `readOnlyHint=1` のような値は、解析器が D1 として照らしていません。その組は判定表に出てこないので、矛の判定には関係しません。気づいたことは `note` に残すだけにします。
- **見落としの抜き取りの対象を確かめるとき**: 対象は「D1 か D2 を明示した（`D_kind.explicit`）ユニット」です。`explicit` に `readOnlyHint` か `destructiveHint` があるユニットが入ります。`explicit` に `openWorldHint` しか無いユニットは入りません。

#### この節のまとめ

`d_kind_from` は、`readOnlyHint: True`、`readOnlyHint: True` が無いときの `destructiveHint: False`、`openWorldHint: True` の 3 つだけを `explicit` に入れ、ほかの書かれたキーは `present_no_bound` に入れる。
`openWorldHint: False` は `closed_world`（D3）、`readOnlyHint: True` が無いときの `idempotentHint: True` は `idempotent`（D4）を立てる。
値は Python の `True` / `False` そのもので比べるので、`1` や `"true"` は宣言として読まれない（U41）。

### 16.4 実物で読む — v4 の gemini・bugasura・ccr

#### 一言で言うと

v4 の実物の 5 つのツールで、`annotations` から `D_kind` と「当たる宣言」を読む練習をします。
とくに、「`explicit` に `openWorldHint` があるのに D3 ではない」形と、「`explicit` が空なのに D4 の矛が出る」形を見ます。

#### たとえ話 — 見本の答案

数学の問題集には、規則の説明の後に「見本の答案」が載っています。
規則を読んだだけでは分からないことも、見本を 1 つずつ追うと分かります。
この節は、16.3 節の規則の「見本の答案」です。

#### 小さな例 1 — gemini の `gemini_list_models`

16.2 節で見た `gemini_prompt` と同じ木の、もう 1 つのツールです（`server.py:309`）。

```json
"annotations": {"title": "List Gemini model aliases", "readOnlyHint": true,
                "destructiveHint": false, "idempotentHint": true, "openWorldHint": false},
"D_kind": {"bottom": false, "closed_world": true, "explicit": ["readOnlyHint"],
           "present_no_bound": ["destructiveHint", "idempotentHint", "openWorldHint", "title"],
           "upper": ["FS_READ", "NET"]}
```

一歩ずつ読みます。

1. `readOnlyHint: true` → `explicit` に入り、上界は `FS_READ`・`NET`。**D1** が当たります。
2. `destructiveHint: false` → `readOnlyHint: true` があるので `present_no_bound` に入ります。D2 にはなりません。
3. `idempotentHint: true` → `present_no_bound` に入ります。`readOnlyHint: true` があるので、`idempotent` は立ちません。D4 にはなりません。
4. `openWorldHint: false` → `present_no_bound` に入り、**`closed_world: true`** が立ちます。**D3** が当たります。
5. `title` → `present_no_bound` に入ります。
6. 当たる宣言は **D1 と D3** です。

同じ木の `gemini_prompt`（16.2 節）は、`openWorldHint: true` なので D3 は当たらず、**D1 だけ**でした。
2 つのツールは、`openWorldHint` の値だけで、当たる宣言の数が違います。
（出典: `evidence/scan_v2_v4_run1/v4-ankitdotgg__making-gemini-useful-with-claude.json` の `gemini_list_models`・`gemini_prompt`。本書の執筆時に確かめた）

#### 小さな例 2 — bugasura の `bugasura_find_project_by_name`

bugasura の木の、プロジェクトを名前で探すツールです（`tools/discovery.py:82`。manifest の `tool_name` は `bugasura_find_project_by_name`）。

```json
"annotations": {"destructiveHint": false, "idempotentHint": true, "openWorldHint": true, "readOnlyHint": true},
"D_kind": {"bottom": false, "explicit": ["openWorldHint", "readOnlyHint"], "open_world": true,
           "present_no_bound": ["destructiveHint", "idempotentHint"], "upper": ["FS_READ", "NET"]}
```

`explicit` に `openWorldHint` が入っています。
けれども、これは **`openWorldHint: true`**（外の世界と関わる、という申告）です。
D3（`openWorldHint: false`）の対象では**ありません**。`closed_world` の欄もありません。
当たる宣言は **D1 だけ**です。
「`explicit` に `openWorldHint` がある = D3」と読むのは誤りだ、ということを、この実物が示しています。

#### 小さな例 3 — bugasura の `bugasura_update_project`

同じ木の、プロジェクトを更新するツールです（`tools/projects.py:350`）。

```json
"annotations": {"destructiveHint": false, "idempotentHint": true, "openWorldHint": true, "readOnlyHint": false},
"D_kind": {"bottom": false, "explicit": ["destructiveHint", "openWorldHint"], "idempotent": true,
           "open_world": true, "present_no_bound": ["idempotentHint", "readOnlyHint"],
           "upper": ["DB", "FS_READ", "FS_WRITE", "NET"]}
```

一歩ずつ読みます。

1. `readOnlyHint: false` が**明示**されていて、`present_no_bound` に入っています。
2. `readOnlyHint: true` が無いので、`destructiveHint: false` は `explicit` に入ります。**D2** が当たります。
3. `idempotentHint: true` で、`readOnlyHint: true` が無いので、`idempotent: true` が立ちます。**D4** が当たります。
4. `openWorldHint: true` は `explicit` に入りますが、D3 ではありません。
5. 当たる宣言は **D2 と D4** です。

このツールの行の注記には、同じ効果（`httpx.AsyncClient.request`、つまり HTTP の送信）について、宣言ごとに別の答えが出ていました。
D2 では不（理由 `net_post`）、D4 でも不（理由 `net_nonidempotent_method`）です。
1 つの効果が、2 つの宣言で別々に照らされていることが分かります（16.5 節）。

このツールは、v4 の見落としの判定で R01 として取り上げられたものです。
手引きの下書きの例の表では、「`POST /v1/projects/update` で既存のプロジェクトを更新する。解析器は `net_post` の不を出している。人の判定では D2 に反する動作と書き留める」とされています。
この判定は本記録者（AI）が v4 で行ったもので、最終評価の正解ではなく、考え方の例です。
（出典: `evidence/scan_v2_v4_run1/v4-appachhi__bugasura-mcp-server.json`。本書の執筆時に確かめた。`docs/drafts/final_judging_guide_draft.md:663`（R01））

#### 小さな例 4 — ccr の `gcc_todo_delete` — `explicit` が空なのに D4 の矛

最後は、ccr の木の、TODO を消すツールです（`ccr/mcp/gcc_todo_tools.py:181`）。
原ソースでは、宣言は `ToolAnnotations(readOnlyHint=False, destructiveHint=True, idempotentHint=True)` です。

```json
"annotations": {"destructiveHint": true, "idempotentHint": true, "readOnlyHint": false},
"D_kind": {"bottom": true, "explicit": [], "idempotent": true,
           "present_no_bound": ["destructiveHint", "idempotentHint", "readOnlyHint"]}
```

一歩ずつ読みます。

1. `readOnlyHint: false` → `present_no_bound`。D1 ではありません。
2. `destructiveHint: true` → `present_no_bound`。「壊しうる」と正直に申告しているので、D2 ではありません。
3. `idempotentHint: true` で、`readOnlyHint: true` が無い → `idempotent: true`。**D4** が当たります。
4. `explicit` は**空**で、上界も無いので **`bottom: true`** です。
5. 当たる宣言は **D4 だけ**です。

このツールについて、解析器は D4 の矛を 1 つ出しています。
場所は `ccr/core/memory_pkg/memory_file_io.py:83` の `open(..., 'a')`（追記）で、道筋は `_ensure_memory -> _init -> InitMixin.ensure_structure -> FileIOMixin._add_to_gitignore` でした。
理由は `fs_append`（追記は繰り返すと 2 回書かれる）です。
`contradictions.json` のこの組の行は、`D_explicit` が `[]`（空）、`declarations` が `["D4"]` になっていました。

つまり、**「明示された宣言」が空でも、D4 の矛は出ます。**
`explicit` が空だからといって「このツールは何も宣言していない」と読むと、目の前の D4 の組の意味が分からなくなります。

この矛が本当に違反か（正か誤か）は、この章の範囲の外です。
参考までに、同じ木の兄弟のツール `gcc_todo_update` の同じ種類の組（`open('a')` × D4）は、v4 で本記録者が「誤」（原因 E8: 追記は『まだ書かれていないとき』だけなので、繰り返しても 2 回目は書かない）と判定しています。
判定の考え方は第 48〜51 章で学びます。
（出典: `evidence/scan_v2_v4_run1/v4-qbit-glitch__ccr.json` の `gcc_todo_delete`、`evidence/scan_v2_v4_run1/contradictions.json`。本書の執筆時に確かめた。`docs/drafts/final_judging_guide_draft.md:658`（E00））

v4 の 3,696 ユニット（88 木）で、`D_kind` の欄ごとのユニットの数を数えました（本書の執筆時に manifest から数えた。v4 の数字は論文に使わない）。

#### なぜ実物で確かめるのか

規則は 16.3 節の表で尽きています。
それでも実物を読むのは、**実物には「規則の境目」の形が出てくる**からです。
`openWorldHint: true` と `false` が同じ木に混ざる（gemini）、`readOnlyHint: false` を明示する（bugasura・ccr）、正直に `destructiveHint: true` と書いたうえで `idempotentHint: true` を書く（ccr）、といった形です。
判定で出会うのも、こうした形です。

#### よくある誤解・つまずき

- **誤解: 「同じ木のツールは、同じ宣言で照らされる」**
  宣言はツールごとに書くので、同じ木でもツールごとに違います（gemini の 2 つのツール）。
- **誤解: 「`contradictions.json` の `D_explicit` が空の行は、宣言の無いツールの行だ」**
  D3・D4 の組では、`D_explicit` が空でも行が出ます（ccr）。どの宣言の組かは `declarations` を見ます。
- **誤解: 「`destructiveHint: true` と正直に書いたツールは、照合の対象外だ」**
  D2 の対象外なだけです。`idempotentHint: true` も書いていれば D4 の対象です（ccr）。

#### 手作業ではどう使うか

- **手順 A**: 判定表の `decl` の欄と、原ソースの宣言を見比べます。`decl` が D4 なら、原ソースに `idempotentHint=True` があり、`readOnlyHint=True` が**無い**ことを確かめます。
- **手順 B**: 道具の「明示された宣言:」が `[]` でも慌てません。D3・D4 の組では、それがふつうにありえます。
- **[第 50 章](ch50.md)の「宣言に反するか」**: 照らす宣言は、組ごとに 1 つです。bugasura の `update_project` のように 1 つのツールに D2 と D4 が当たる場合、D2 の組と D4 の組は別の組で、別々に判定します。

#### この節のまとめ

gemini の 2 つのツールは `openWorldHint` の値だけで当たる宣言が違い（D1 と、D1・D3）、bugasura の `find_project_by_name` は `explicit` に `openWorldHint` があっても D1 だけ、`update_project` は D2 と D4。
ccr の `gcc_todo_delete` は `explicit` が空で `bottom: true` なのに D4 が当たり、D4 の矛が出ている。
v4 の全体でも、`idempotentHint` が `explicit` に入ったユニットは 0 で、`bottom: true` のうち 77 に D3・D4 の印があった。

### 16.5 D1〜D4 — どの宣言を当てるかの決まり方

#### 一言で言うと

1 つの効果を、どの宣言で照らすかは、`D_kind` の 3 つの所で決まります。
**D1** は `explicit` に `readOnlyHint` があるとき、**D2** は（D1 でなく）`explicit` に `destructiveHint` があるとき、**D3** は `closed_world` が true のとき、**D4** は `idempotent` が true で D1 でないときです。
1 つの効果が、2 つ以上の宣言で別々に照らされることもあります。

#### たとえ話 — 空港の検査台

空港では、荷物に貼られた申告ごとに、別の検査台で調べます。
「液体は入っていません」の申告があれば液体の検査台へ、「電池は入っていません」の申告があれば電池の検査台へ回します。
1 つの荷物が、2 つの検査台を通ることもあります。
それぞれの検査台は、自分の申告についてだけ合格・不合格を出します。2 つの結果を足し合わせて 1 つの点数にはしません。

ただし、もっと強い申告がある場合は、弱い申告の検査を省きます。
たとえば「この荷物は空です」と申告した荷物に、「液体は入っていません」の検査を重ねても意味がありません。
宣言で言えば、`readOnlyHint: true`（環境を何も変えない）が「空です」にあたり、D2（壊さない）・D4（繰り返しても同じ）はそれに含まれてしまうので、重ねて調べません。
一方、D3（外と関わらない）は「変えるか」とは別の向きの申告なので、D1 と一緒でも調べます。

#### 小さな例 — `contradiction_findings` を読む

宣言ごとに照らす関数は、短いので全体を読みます（説明文を除く）。

```python
 1  def contradiction_findings(dk: DKind, e) -> list[tuple[str, str, str]]:
 2      explicit = set(dk.explicit)
 3      out = []
 4      read_only = "readOnlyHint" in explicit
 5      if read_only:
 6          r = _d1(e)
 7          if r:
 8              out.append(("D1", *r))
 9      elif "destructiveHint" in explicit:
10          r = _d2(e)
11          if r:
12              out.append(("D2", *r))
13      if dk.closed_world:
14          r = _d3(e)
15          if r:
16              out.append(("D3", *r))
17      if dk.idempotent and not read_only:
18          r = _d4(e)
19          if r:
20              out.append(("D4", *r))
21      return out
```

#### 一歩ずつ

- 1 行目: 関数の名前と引数です。`dk` はユニットの `D_kind`、`e` は 1 つの効果です。返す値は「(宣言, 結果, 理由)」の組の一覧です。
- 2 行目: `explicit` の一覧を、集合（`set`。中に何があるかを速く調べられる入れ物）にします。
- 3 行目: 結果を入れる空の一覧を用意します。
- 4 行目: `explicit` に `readOnlyHint` があるかを、`read_only` という変数に入れておきます。16.3 節の規則から、これは「`readOnlyHint: True` を明示した」と同じ意味です。
- 5〜8 行目: あれば D1 の判定表（`_d1`）で効果を照らします。`_d1` は、矛か不なら「(結果, 理由)」を返し、内なら何も返しません。何か返ってきたら、`"D1"` を付けて一覧に足します。
- 9〜12 行目: `elif` なので、**D1 でないときだけ**、`explicit` に `destructiveHint` があるかを見て、あれば D2 の判定表（`_d2`）で照らします。16.3 節の規則から、`explicit` の `destructiveHint` は、もともと `readOnlyHint: True` が無いときにしか入りません。ここでも念のため D1 と排他にしています。
- 13〜16 行目: `if` なので、**D1 かどうかに関係なく**、`closed_world` が true なら D3 の判定表（`_d3`）で照らします。
- 17〜20 行目: `idempotent` が true で、しかも D1 でないなら、D4 の判定表（`_d4`）で照らします。16.3 節の規則で、`idempotent` はもともと `readOnlyHint: True` が無いときにしか立ちません。
- 21 行目: 集めた一覧を返します。内のときは何も足されないので、**一覧に出てくるのは矛と不だけ**です。

`_d1`〜`_d4` の中身（どの効果が矛・不・内になるか）は、[第 17 章](ch17.md)の判定表です。
（出典: `authgap/dparse.py:573-601`（`contradiction_findings`）。D1〜D4 の判定表は `docs/contradiction_principles.md` §7）

#### 当て方の表

| 記号 | 宣言 | `D_kind` のどこを見るか | 当てる条件 |
|---|---|---|---|
| **D1** | `readOnlyHint: true` | `explicit` に `readOnlyHint` | いつも |
| **D2** | `destructiveHint: false` | `explicit` に `destructiveHint` | `readOnlyHint: true` が**無い**とき |
| **D3** | `openWorldHint: false` | `closed_world: true` | いつも（D1 と一緒でもよい） |
| **D4** | `idempotentHint: true` | `idempotent: true` | `readOnlyHint: true` が**無い**とき |

表の読み方: 1 行が 1 つの宣言です。「`D_kind` のどこを見るか」の列が、manifest で確かめる場所です。
たとえば 3 行目は「D3 は、`explicit` ではなく `closed_world` の欄を見る。`readOnlyHint: true` があっても当てる」と読みます。

**D1〜D4 は 4 つとも主指標です**（D62）。
**主指標**とは、「研究の主な結果として報告する測定」のことです。
4 つは**宣言ごとに分けて報告し、足し合わせません。**
4 つの宣言は意味が違う（「書き換えない」「壊さない」「外と通信しない」「何度呼んでも同じ」）ので、足した数は何を数えたのか説明できないからです。
過去の run と比べるために「D1 + D2 の矛」の列を残している表もありますが、それは比較のためだけの数で、主指標ではありません。
（出典: `docs/decisions.md:3511-3540`（D62）、`evidence/population_v4/contradiction_by_decl_v4_run1.md` の冒頭の注記）

#### `readOnlyHint` が明示の false でも、書いていなくても、同じ

D2 と D4 の条件「`readOnlyHint: true` が無いとき」には、2 つの場合が入ります。
`readOnlyHint: false` と明示した場合と、`readOnlyHint` を何も書かなかった場合です。
**どちらでも、D2・D4 を当てる点は同じです。**

作例と実物で確かめると、次のとおりです。

| ツール | `readOnlyHint` | `destructiveHint` | `idempotentHint` | 当たる宣言 |
|---|---|---|---|---|
| bugasura `update_project`（実物） | `false`（明示） | `false` | `true` | D2・D4 |
| 作例 `t_k` | 書いていない | `false` | `true` | D2・D4 |
| 作例 `t_a` | `false`（明示） | `false` | `true` | D2・D4 |

表の読み方: 2 行目は「`readOnlyHint` を何も書かずに `destructiveHint: false` と `idempotentHint: true` を書いた作例も、1 行目の `readOnlyHint: false` を明示した実物と同じく、D2 と D4 で照らされる」と読みます。

手順書の用語の表も、D2・D4 に「**`readOnlyHint: true` が無いときだけ**当てる」と書いています。
「`readOnlyHint: false` のときだけ」ではない点に注意してください。
（出典: `docs/final_evaluation_procedure.md:89-91`、[第 4 章](ch04.md) 4.2 節。作例は本書の執筆時に走査して確かめた）

#### 同じ効果でも、宣言によって答えが違う

1 つのツールに D2 と D4 が当たるとき、同じ効果が 2 回、別々の判定表で照らされます。
作例で見ると、答えが逆になることがあります。

| 作例 | 効果 | D2 の答え | D4 の答え |
|---|---|---|---|
| `t_a` | `os.remove(path)`（ファイルを消す） | **矛**（`fs_remove`。消すのは壊す変更） | 内（消した後にもう一度消しても、状態は同じ） |
| `t_k` | `open(path, "a")` で追記 | 内（追記は足すだけの変更） | **矛**（`fs_append`。2 回呼ぶと 2 回書かれる） |

表の読み方: 1 行目は「ファイルを消す効果は、D2（壊さない）には反するが、D4（繰り返しても同じ）には反しない」と読みます。
2 行目はその逆です。

だから、宣言ごとに分けて判定し、分けて報告する必要があります。
「D2 か D4 のどちらかで矛」と 1 つにまとめると、どちらの約束が破れたのかが分からなくなります。
（出典: 作例は本書の執筆時に走査して確かめた。判定表は `docs/contradiction_principles.md` §7.2・§7.4。D2 で追記を矛に数えない決定は `docs/decisions.md:449-460`（D32 の O16））

#### `bottom: true` でも D3・D4 は当たる

D3・D4 は上界を動かさないので、上界が無い（`bottom: true`）ツールにも当たります。
作例 `t_d` は `{"readOnlyHint": False, "openWorldHint": False}` と書いたツールで、`explicit` は空、`bottom: true` でした。
それでも `closed_world: true` なので D3 で照らされ、定数の外部ホストへの `requests.get` に D3 の矛（`net_external_host`）が出ました。
16.4 節の ccr の `gcc_todo_delete` も、`bottom: true` で D4 の矛が出ている実物です。
（出典: 作例は本書の執筆時に走査して確かめた）

#### 低レベルの書き方のハンドラ

[第 12 章](ch12.md)で見た低レベルの書き方では、1 つのハンドラ（ユニット）が、名前で分岐して複数のツールを受け持ちます。
このとき解析器は、ツールごとの `D_kind`（manifest の `D_kind_by_tool`）を作り、ユニットの `D_kind` は、それらを「最も厳しく」合わせたものにします。
合わせ方は、`explicit` と `present_no_bound` は和（どれかのツールにあれば入る）、`closed_world` と `idempotent` はどれか 1 つのツールで立てば立つ、上界は積（どれか 1 つでも ⊥ なら ⊥）です。
効果ごとにどのツールの宣言で照らすかは、事前登録 §2.9 の規則（効果を支配する名前の分岐）で決まります。
どの向きでも、あるはずの矛を消す側（誤 clear の側）には倒さない、と設計されています。
v4 では、この形のユニットは 2 つでした（本書の執筆時に数えた）。
（出典: `authgap/dparse.py:108-130`（`parse_d_kind`）、`:143-176`（`meet_d_kind`）、`docs/preregistration.md:427-466`（§2.9））

#### なぜそうするのか

- **D2・D4 を `readOnlyHint: true` のときに外す理由**: SDK の説明文は、`destructiveHint` と `idempotentHint` について「この項目は `readOnlyHint` が false のときだけ意味を持つ」と書いています。仕様書も同じことを書いています。読むだけのツールに「壊すか」「繰り返すと増えるか」を問う意味はありません。D1 の判定表が、書き込み全般をすでに見ています。
- **D3 を D1 と一緒でも当てる理由**: 学生が選んだ原理の 1-ii の説明に、「readOnly は『変更するか』、openWorld は『外と関わるか』で別の軸（仕様の例: web 検索は open world かつ読み取り）」とあります。読むだけのツールでも、外部と通信しないと約束したなら、その約束は別に確かめる価値があります。gemini の `gemini_list_models` は D1 と D3 の両方を約束しています。
- **宣言ごとに報告する理由**: 上の「同じ効果でも、宣言によって答えが違う」のとおり、宣言ごとに約束の中身が違うからです（D62）。

（出典: SDK 1.30.0 の `mcp/types.py:1272, 1280`、`AUTHGAP_BRIEF_v3.md:316`、`docs/contradiction_principles.md:138`（原理 1-ii））

#### よくある誤解・つまずき

- **誤解: 「`readOnlyHint: true` と `destructiveHint: false` の両方を書いたツールには、D1 と D2 の両方を当てる」**
  D1 だけです。D2 は `readOnlyHint: true` が無いときだけです（作例 `t_j`、実物の gemini・bugasura の `find_project_by_name`）。
- **誤解: 「`readOnlyHint: false` を書いたツールは、D2・D4 の対象外だ」**
  逆です。`true` でなければ、明示の `false` でも、書いていなくても、D2・D4 を当てます。
- **誤解: 「D3 は D1 と一緒には当たらない」**
  当たります（gemini の `gemini_list_models`、作例 `t_b`）。D1 と排他なのは D2・D4 です。
- **誤解: 「1 つのツールの矛と不を、宣言をまたいで足せば、そのツールの違反の数になる」**
  足しません。宣言ごとに別の約束で、同じ効果が宣言によって矛にも内にもなります。

#### 手作業ではどう使うか

- **手順 A**: 判定表の 1 行は「組 = (木, ユニット, site, kind, 宣言)」です。`decl` の欄が、その組を照らす宣言です。同じツールの同じ効果が、D2 の組と D4 の組として 2 行に出ることがあります。それぞれ別に判定します。
- **[第 50 章](ch50.md)の「宣言に反するか」**: 問いは宣言ごとに違います（D1「環境を変えるか」、D2「追加の更新だけか」、D3「関わる範囲が閉じているか」、D4「同じ引数で繰り返しても追加の効果が無いか」）。組の `decl` に合わせて、問いを選びます。別の宣言の問いで判定しないでください。
- **見落としの判定（[第 52 章](ch52.md)）**: 抜き取られたユニットの宣言が D1 か D2 かを、`D_kind.explicit` で確かめます。D1 のツールなら D1 の問いで、D2 のツールなら D2 の問いで、本体と呼び出し先を読みます。

（出典: `docs/drafts/final_judging_guide_draft.md:33-36`（組の定義）、`:307-382`（宣言ごとの問い））

#### この節のまとめ

D1 は `explicit` の `readOnlyHint`、D2 は（D1 でなく）`explicit` の `destructiveHint`、D3 は `closed_world`、D4 は（D1 でなく）`idempotent` で当てる。
D2・D4 は `readOnlyHint: true` が無いときだけで、明示の `false` でも書いていなくても同じ。D3 は D1 と一緒でも当てる。
D1〜D4 は 4 つとも主指標で、宣言ごとに判定・報告し、足し合わせない（D62）。

### 16.6 以前は D3・D4 を「探索的」と呼んでいた

#### 一言で言うと

第 2 版までは、D1・D2 だけを主指標にし、D3・D4 は「探索的」（参考のための分析）として別の列で報告していました。
学生の指摘を受けて、D3・D4 も主指標にしました（D62）。
変えたのは**呼び方（位置づけ）だけ**で、判定の規則も件数も変わっていません。

#### たとえ話 — 練習問題と本番の問題

ある解き方を、練習問題の答えを見ながら作ったとします。
その解き方で**同じ練習問題**を解き直して「よく当たる」と言っても、説得力はありません。答えを見て作ったのですから。

けれども、その解き方で**まだ誰も見ていない本番の問題**を解くなら、話は違います。
本番の問題から見れば、解き方は「問題を見る前に決まっていた」ことになります。
練習問題の答えを見て作ったかどうかは、本番の結果の信頼性には関係しません。

#### 小さな例 — 経緯の年表

| 日付 | 決定 | 内容 |
|---|---|---|
| 2026-09-24 | D56 | 学生が選んだ原理から判定表を導いた。**D3・D4 の規則は、開発用のデータ（母集団 v2）の結果を見た後で作った**ので、「探索的な分析」として別の列にし、D1・D2 と合算しない（逸脱 #19） |
| 2026-09-24 | D60 | 論文の評価は、学生が v2・v3 を含まない別の新しいデータで行う |
| 2026-09-28 | D62 | 学生の決定で、**D1〜D4 を 4 つとも主指標**にする。宣言ごとに報告し、合算しない（逸脱 #24） |
| 2026-09-29 | D66 の 3 | 中間検証の v4 の repo も、学生の最終評価のデータから除く |

表の読み方: 1 行が 1 つの決定です。上から時間の順です。
たとえば 3 行目は「9 月 28 日に、学生が D1〜D4 を 4 つとも主指標にすると決めた。これは事前登録からの逸脱 #24 として記録されている」と読みます。
**逸脱**とは、事前登録（データを見る前に書いた計画。[第 22 章](ch22.md)）から変えたことを、日付と理由とともに記録したものです。記録は `docs/preregistration.md` の逸脱の表に番号つきで並んでいます。
（出典: `docs/decisions.md:2989`（D56）、`:3392-3400`（D60）、`:3511-3540`（D62）、`:3743-3754`（D66）、`docs/preregistration.md:575`（逸脱 #24））

#### 一歩ずつ — 何が起きたか

1. **D56 の理由**: 判定表は、原理を先に選んでコミットし、そこから機械的に導いたものです。ただし、D3・D4 の規則を書いた時点で、表を書いた者は v2 の run11 の件数を見ていました。「結果を見てから作った規則で、同じデータを測ると、甘い結果になりうる」ので、D3・D4 を主指標から外しました（[第 22 章](ch22.md)で、この考え方を正式に学びます）。
2. **D60 で前提が変わった**: 論文の評価は、v2・v3 を含まない新しいデータで、学生が行うと決まりました。
3. **学生の指摘**: 学生は、次のように指摘しました。

   > 結果を見た後で規則を作ったのは、開発用のデータの話だ。論文の評価は、まだ誰も見ていない新しいデータで行う。そのデータから見れば、D1〜D4 の規則はどれも見る前に決まっている。

4. **本記録者も同意した**: D3・D4 の規則も解析器の凍結に入り、評価のデータを見る前に固定されています。**新しいデータから見れば、D1〜D4 の間に「先に決めたか」の差はありません。** 正しい書き方は「開発用のデータで規則を作り、別の新しいデータで確かめる」です。

### 16.7 分母 (c) との関係 — D3・D4 の M_d は未決

#### 一言で言うと

論文の結論になる割合の分母 (c) は、「その宣言を明示的に書いた（`D_kind.explicit`）ユニットを 1 つ以上持つ木」と書かれています。
D1・D2 はこの書き方で正しく数えられます。
けれども **D3・D4 は `explicit` に入らない**ので、文字どおりに数えると、D3 は逆の申告の木を数え、D4 は 0 になります。
**D3・D4 の分母を何で数えるかは、まだ決まっていません（未決）。** 事前登録を封する前に、学生が決める必要があります。

#### たとえ話 — アンケートの集計で、別の欄を数えてしまう

クラスで「放課後に外で遊ばない人のうち、何人が宿題を忘れたか」を調べるとします。
分母は「外で遊ばない人」の数です。

ところが、アンケートの集計表には「外で遊ぶ: はい」の欄しかなく、「いいえ」は別のメモ欄に書かれていたとします。
集計の手順書に「集計表の欄で数える」と書いてあったら、どうなるでしょう。
「外で遊ぶ: はい」と答えた人を、「外で遊ばない人」の分母として数えてしまいます。
正反対の人を数えているのですから、出てくる割合には意味がありません。

D3 の分母で起きうるのは、これと同じことです。
`explicit` の `openWorldHint` は「外と関わる」（true）で、D3 は「外と関わらない」（false）です。

#### 小さな例 — 3 つの文書の書き方

分母 (c) の定義は、3 つの文書に書かれています。

| 文書 | 書き方 |
|---|---|
| 決定 D70 の 4 | 「(c) の分母は、その宣言を明示的に書いた（`D_kind.explicit`）ユニットを 1 つ以上持つ木。既定値で補ったものは数えない」 |
| 手順書 23.2 節 | 「M_d は宣言 d を明示した（`D_kind.explicit`）ユニットを 1 つ以上持つ走査した木の数」 |
| 事前登録 §2.12 の下書き | 「宣言 d を明示したユニットを 1 つ以上持つ走査した木の数を M_d とする」 |

表の読み方: 1 行が 1 つの文書です。
1 行目と 2 行目は、数える欄を `D_kind.explicit` と名指ししています。
3 行目（下書き）は「明示した」とだけ書き、欄を名指ししていません。

ここで **M_d** は、この章で初めて出てくる記号です。

- **やさしく言うと**: 宣言 d（D1〜D4 のどれか）について、「その宣言を書いたサーバ」の数です。
- **正確な定義**: 走査した木のうち、宣言 d を明示したユニットを 1 つ以上持つ木の数。分母 (c) の値そのものです（d には D1〜D4 が入る）。
- **例**: D1 なら、`readOnlyHint: true` と書いたツールを 1 つでも持つサーバの数が M_D1 です。

（出典: `docs/decisions.md:3904`（D70 の 4）、`docs/final_evaluation_procedure.md:1340`、`docs/drafts/prereg_2_12_draft.md:101`）

#### 一歩ずつ — 宣言ごとに当てはめる

この章で学んだことを、4 つの宣言に当てはめます。

| 宣言 | 文字どおり「`explicit` にその名前がある」で数えると | 問題 |
|---|---|---|
| D1 | `explicit` に `readOnlyHint` = `readOnlyHint: true` を書いた | 問題なし（D1 の定義と一致する） |
| D2 | `explicit` に `destructiveHint` = `destructiveHint: false` を書き、`readOnlyHint: true` が無い | 問題なし（D2 の定義と一致する） |
| D3 | `explicit` に `openWorldHint` = **`openWorldHint: true`** を書いた | **D3（`openWorldHint: false`）とは逆の申告を数えてしまう**。D3 は `closed_world` の欄に表れる |
| D4 | `explicit` に `idempotentHint` が入ることは**無い** | **M_d がいつも 0 になる**。D4 は `idempotent` の欄に表れる |

表の読み方: 1 行が 1 つの宣言です。
たとえば 4 行目は「D4 について文字どおり `explicit` で数えると、`idempotentHint` は決して `explicit` に入らないので、どの木も数えられず、分母が 0 になる」と読みます。

#### v4 で数えるとどうなるか

規模の感じをつかむために、v4 の 88 木で、両方の数え方の木の数を数えました（本書の執筆時に manifest から数えた。v4 の数字は論文に使わない）。

| 数え方 | 木の数（88 木のうち） |
|---|---|
| D1: `explicit` に `readOnlyHint` | 62 |
| D2: `explicit` に `destructiveHint` | 35 |
| `explicit` に `openWorldHint`（文字どおりの「D3」。実は `openWorldHint: true`） | 39 |
| `closed_world: true` のユニットを持つ（本当の D3） | 40 |
| 上の 2 つの両方に当てはまる | 22 |
| `explicit` に `idempotentHint`（文字どおりの「D4」） | 0 |
| `idempotent: true` のユニットを持つ（本当の D4） | 23 |

表の読み方: 1 行が 1 つの数え方で、右の列がその数え方で数えた木の数です。
3 行目と 4 行目を比べてください。
文字どおりの数え方（39 木）と本当の D3（40 木）は、数はほぼ同じなのに、**中身が違います**。

#### 何が決まっていないのか

**D3・D4 の M_d を何で数えるかは、まだ決まっていません（未決）。**

たとえば「D3 は `closed_world`、D4 は `idempotent` の欄が立ったユニットを持つ木で数える」という案が考えられます。
けれども、これは本書が説明のために挙げた例で、**決定ではありません**。
決めるのは学生です。
本書の執筆時に `docs/` と `docs/drafts/` を `closed_world` で検索しましたが、M_d の定義でこの欄に触れた文書はありませんでした。

この点は、[第 46 章](ch46.md)の「まだ決まっていないこと」の一覧に入れます。
期限は、事前登録 §2.12 を**封する前**です。
**封**とは、事前登録の文面（何をどう数えるか）を、データを見る前にコミットして固定し、その後は変えないことです（[第 22 章](ch22.md)で正式に学びます）。

#### なぜ封の前に決める必要があるのか

分母を、結果を見てから選べるとしたら、都合のよい割合が出る数え方を選べてしまいます。
この研究は、それを防ぐために、分母を値を見る前に決めて書き残すことにしています（CLAUDE.md の規則 3「閾値には必ず測定手続きと分母の定義を付ける」）。

D3・D4 の M_d が決まらないまま最終評価のデータを見ると、この約束を守れません。

もう 1 つ、黙って片方に倒さないことも大事です。
集計の段階で「`explicit` と書いてあるから `explicit` で数えた」と文字どおりに進めると、D3 は意味の無い割合、D4 は計算できない割合になります。
逆に「意図はこうだろう」と黙って `closed_world` で数えると、事前登録に書いていない数え方を使ったことになります。
どちらも避けるために、未決として記録し、封の前に決めます（CLAUDE.md の規則 4「解決できなかったものは『不明』として記録する。黙って安全側に倒さない」）。
（出典: `docs/preregistration.md:480-481`（§2.10）、`CLAUDE.md` の規則 3・4）

- **つまずき: 「見落としの抜き取りの対象も `D_kind.explicit` で決めているが、問題ないのか」**
  見落としの抜き取りの対象は「D1 か D2 を明示した」ユニットで、D3・D4 を含みません。D1・D2 は `explicit` で正しく決まるので、この問題は起きません。

（出典: `docs/final_evaluation_procedure.md:452`）

### 16.8 snake_case の宣言と mcp の版

#### 一言で言うと

`read_only_hint=True` のように単語を `_` でつないだ書き方（snake_case）の宣言が、相手（クライアント）に届くかどうかは、MCP の Python SDK（`mcp` パッケージ）の版で違います。
2.0 以上なら届き、2.0 より前なら届きません。
解析器は、木の中の手がかりから版を決め、**2.0 以上なら宣言として読み、2.0 より前なら `D_malformed`（届かない宣言）として記録だけし、決まらなければ `D_unknown`（分からない）にします**（D64 の U38）。

#### たとえ話 — 新しい書式の宛名と、2 種類の仕分け機

郵便局に、新しい書式の宛名も読める新型の仕分け機と、古い書式しか読めない旧型の仕分け機があるとします。
新しい書式で宛名を書いた手紙は、新型の機械を通れば届き、旧型の機械を通れば届きません。

封筒を見ただけでは、どちらの機械を通るかは分かりません。
そこで、消印や差出人の地区などの**手がかり**から、どちらの機械の地区かを推理します。
手がかりが新型を指していれば「届く」、旧型を指していれば「届かない」、手がかりが無いか食い違っていれば「分からない」と記録します。
解析器が snake_case の宣言にしていることは、これと同じです。

#### 言葉の確認 — camelCase と snake_case

- **camelCase**
  - やさしく言うと: 単語の 2 つ目から先頭を大文字にしてつなぐ書き方です。ラクダのこぶのように大文字が出っ張るので、この名前があります。
  - 正確な定義: MCP の仕様（プロトコルの決まり）が使う、宣言のキーの書き方です。
  - 例: `readOnlyHint`、`destructiveHint`。
- **snake_case**
  - やさしく言うと: 単語を `_`（下線）でつなぐ書き方です。Python ではこちらがふつうです。
  - 正確な定義: Python の変数や引数の名前でよく使われる書き方で、MCP の仕様のキーの書き方ではありません。
  - 例: `read_only_hint`、`destructive_hint`。

解析器が snake_case として扱うキーは、`read_only_hint`・`destructive_hint`・`idempotent_hint`・`open_world_hint` の 4 つです（`title` には別名がありません）。
（出典: `authgap/entries.py:2657-2663`（`ANNOTATION_FIELDS`・`SNAKE_ALIASES`））

#### 小さな例 — SDK の 1.x と 2.x

MCP の Python SDK には、大きく 1.x と 2.x の版があります。
解析器のコードの説明と、本書の執筆時に手元の SDK（1.30.0 と 2.2.0）のソースで確かめた違いは、次のとおりです。

| | mcp 1.x（2.0 より前） | mcp 2.x（2.0 以上） |
|---|---|---|
| サーバのクラス | `mcp.server.fastmcp` の `FastMCP` | `mcp.server.mcpserver` の `MCPServer` |
| 古いクラスを import すると | — | `mcp.server.fastmcp` の import は例外になる（「2.x では `FastMCP` は `MCPServer` に改名された」という説明つき） |
| `ToolAnnotations(read_only_hint=True)` | 仕様のフィールドにならない。`extra="allow"`（知らないキーも余分なものとして持つ）の設定なので、余分なキーとして持つだけ → **相手に `readOnlyHint` として届かない** | 属性名そのものとして受け付け、相手には camelCase（`readOnlyHint`）で届く |

表の読み方: 3 行目が、この節の要点です。「同じ `ToolAnnotations(read_only_hint=True)` でも、1.x では相手に届かず、2.x では `readOnlyHint: true` として届く」と読みます。

2.x の振る舞い（3 行目の右）は、解析器のコードの説明に「mcp 2.2.0 で `ToolAnnotations(read_only_hint=True).model_dump(by_alias=True) == {"readOnlyHint": True}`、辞書の `annotations={"read_only_hint": True}` も同じ」と書かれているものです。
本書では、この 2.x の変換そのものは動かして確かめていません。
（出典: `authgap/entries.py:2385-2392`、`:2712-2734`（`_read_annotations` の説明）。1.30.0 の `mcp/types.py:1247-1293`（`ToolAnnotations` と `model_config = ConfigDict(extra="allow")`）と 2.2.0 の `mcp/server/fastmcp.py`（import すると `ModuleNotFoundError`）は、本書の執筆時に手元のパッケージで確かめた）

#### 一歩ずつ — 仕様書との食い違いと、その扱い

1. **仕様書の書き方**: 仕様書は「snake_case 表記（`read_only_hint` 等）は `ToolAnnotations` に deserialize されず protocol に届かないので `D_malformed` として別行で報告する」と書いていました。**deserialize** は「受け取った形を、決まったクラスの値に組み立て直す」ことです。つまり「snake_case は正しいフィールドに組み立てられないので、相手に届かない」という意味です。
2. **D48（2026-09-23）**: 解析器はもともと、snake_case を読んでも、その結果を捨てていました。D48 で、仕様書どおり `D_malformed` として記録するように直しました。この時点では、snake_case は**いつも**届かない扱いでした。
3. **D64 の U38（2026-09-28）**: 凍結前の添削で、「仕様書の前提（届かない）は 1.x でだけ正しい。2.x では届く」と分かりました。そこで、**mcp の版で条件づける**ことにしました。
4. **逸脱として記録**: 仕様書と食い違うので、事前登録の逸脱 #25 に記録しました。仕様書の文面は書き換えていません（CLAUDE.md の規則 6「仕様書と実データが食い違ったら、実データを採り、仕様書の値も残す」）。

（出典: `AUTHGAP_BRIEF_v3.md:322`、`docs/decisions.md:2458-2478`（D48）、`:3590`（U38 の行）、`docs/preregistration.md:576`（逸脱 #25）、`authgap/dparse.py:119-129`（コメントに「仕様書 322 行目の前提『protocol に届かない』は 1.x でだけ真」））

#### 版で 3 つに分ける

| 版の判定 | snake_case のキーの扱い | manifest での見え方 |
|---|---|---|
| 2.0 以上（`ge2`） | **宣言として読む**（camelCase に写す） | `annotations` に `readOnlyHint` が入り、`D_kind.explicit` にも入る |
| 2.0 より前（`lt2`） | **届かない宣言**として記録だけする（`D_malformed`） | `unit.malformed_fields` と `D_kind.malformed` に `read_only_hint`。`annotations` には入れない。上界にも `explicit` にも入れない |
| 決まらない（`unknown`） | どちらにも倒さない（`D_unknown`） | `unit.undetermined_fields` に `read_only_hint`、`D_kind.unknown: true` |

表の読み方: 1 行が 1 つの版の判定です。
たとえば 2 行目は「版が 2.0 より前と決まった所で `read_only_hint=True` と書いても、宣言は無い扱いになる。ただし `D_kind.malformed` に名前が残るので、『届かない書き方をした』ことは数えられる（16.9 節の `r_malformed`）」と読みます。

同じ注釈に camelCase と snake_case の両方があれば、**camelCase が勝ちます**。
2.x では camelCase の値が使われ、1.x では snake_case が無視されるので、どちらの版でも宣言は camelCase の値になるからです。
（出典: `authgap/entries.py:2712-2734`、`:2761-2771`）

#### 版をどう決めるか

解析器は、木の中の 2 種類の手がかりから版を決めます。

| 手がかり | 2.0 以上（`ge2`）の印 | 2.0 より前（`lt2`）の印 |
|---|---|---|
| API の形（import など） | `mcp.server.mcpserver`・`mcp.server.MCPServer` の import、SDK の `Server(on_call_tool=)`、3 引数の `add_request_handler` | `mcp.server.fastmcp`・`mcp.server.FastMCP` の import、`@<x>.call_tool()` のデコレータ |
| 依存の記載（`requirements*.txt`・`pyproject.toml`・`setup.cfg`・`setup.py`・lock ファイル） | `mcp==2.x`、`mcp>=2` など。独立の `fastmcp` パッケージの版が 4 以上 | `mcp<2` など。`fastmcp` の lock の版が 4 より前、または指定の上限が 4 より前 |

表の読み方: 1 行が 1 種類の手がかりです。
たとえば 2 行目の右は「依存の記載に `fastmcp>=2.10,<3` のような、上限が 4 より前の `fastmcp` の指定があれば、2.0 より前の印と数える」と読みます。
`fastmcp` の版が `mcp` の版の印になるのは、解析器のコードの注記によれば、独立の `fastmcp` パッケージの 2.x・3.x が `mcp` の 2.0 より前に依存しているからです（注記は、これを敵対的レビューの役が確認したもので、その修正では確かめていない、と書いています）。

決め方の規則は、次のとおりです。

- **版はサブツリーごとに決める。** 1 つの木に複数のサーバ（サブプロジェクト）が入っていることがあるからです。各ファイルは、いちばん近い「版の手がかりを持つ依存の記載」のあるフォルダのサブツリーに属します。
- **両方の向きの印があれば、決めない**（`unknown`）。移行の途中の木などでは、どちらで動くか分からないからです。
- **どちらの印も無ければ、決めない**（`unknown`）。既定でどちらかに仮定しません。

manifest の最上位の `mcp_version` の欄には、木全体の版の判定と根拠が出ます。
たとえば v4 の gemini の木は `{"class": "lt2", "evidence": ["lt2:import:server.py:mcp.server.fastmcp"]}` でした。
bugasura の木は `{"class": "lt2", "evidence": ["lt2:spec:pyproject.toml:fastmcp>=2.14.2,<3.0.0", "lt2:spec:requirements.txt:fastmcp>=2.14.2,<3.0.0"]}` で、`fastmcp` の指定から 2.0 より前と判定されていました。
ただし、最上位の `mcp_version` は木全体のまとめで、サブツリーの版がすべて同じときだけその版になり、そうでなければ `unknown` になります。
個々のユニットの snake_case の読み方は、そのユニットのファイルのサブツリーの版で決まります。
（出典: `authgap/entries.py:2441-2531`（`_mcp_versions`）、`:2399-2403`（`_version_class`）、`:2558-2564`（`mcp_version_for`）、`:2567-2582`（`mcp_version_class`）、`authgap/enforcement.py:252-306`（`mcp_major_votes_by_file`）。gemini と bugasura の `mcp_version` は本書の執筆時に確かめた）

#### 作例で確かめる

同じ `ToolAnnotations(read_only_hint=True)` のツール（本体で `os.remove(p)`）を、import だけ変えた 3 つの作例で走査しました。

```text
(1) from mcp.server.fastmcp import FastMCP（版 lt2）
    mcp_version: lt2（根拠 lt2:import:server.py:mcp.server.fastmcp）
    annotations: {}   malformed_fields: ["read_only_hint"]
    D_kind: {"bottom": true, "explicit": [], "malformed": ["read_only_hint"], "present_no_bound": []}
    → 宣言は無い扱い。os.remove に矛は出ない

(2) from mcp.server.mcpserver import MCPServer（版 ge2）
    mcp_version: ge2（根拠 ge2:import:server.py:mcp.server.mcpserver）
    annotations: {"readOnlyHint": true}
    D_kind: {"bottom": false, "explicit": ["readOnlyHint"], "present_no_bound": [], "upper": ["FS_READ", "NET"]}
    → D1 として読む。os.remove に contradiction:D1（理由 fs_write）

(3) from fastmcp import FastMCP（独立の fastmcp。依存の記載なし。版 unknown）
    mcp_version: unknown（根拠なし）
    annotations: {}   undetermined_fields: ["read_only_hint"]
    D_kind: {"bottom": true, "explicit": [], "present_no_bound": [], "unknown": true}
    → 宣言は無い扱い。矛は出ない
```

一歩ずつ読みます。

- (1): `mcp.server.fastmcp` の import が 2.0 より前の印です。snake_case のキーは `annotations` に入らず、`malformed` に移りました。`bottom: true` で、照合される宣言はありません。
- (2): `mcp.server.mcpserver` の import が 2.0 以上の印です。snake_case のキーは camelCase の `readOnlyHint` に写され、`explicit` に入りました。D1 の矛が出ました。
- (3): `from fastmcp import FastMCP` は、解析器の import の印の表に入っていません（独立の `fastmcp` パッケージは、依存の記載の版で判断するため）。依存の記載も無いので、版は決まりません。snake_case のキーは `undetermined_fields` に入り、`D_kind.unknown: true` になりました。

ほかにも、次の形を作例で確かめました。

- `from fastmcp import FastMCP` に、`requirements.txt` の `fastmcp>=2.10,<3` を足すと、版は `lt2`（根拠 `lt2:spec:requirements.txt:fastmcp>=2.10,<3`）になり、辞書の `{"read_only_hint": True}` は `malformed` になりました。
- 1 つのファイルで `mcp.server.fastmcp` と `mcp.server.mcpserver` の両方を import すると、版は `unknown`（根拠に `ge2` と `lt2` の両方）になりました。
- 版 `ge2` で `{"readOnlyHint": False, "read_only_hint": True}` と書くと、camelCase が勝って `annotations` は `{"readOnlyHint": false}` になり、D1 は当たりませんでした。
- 版 `ge2` で `{"destructive_hint": False, "idempotent_hint": True}` と書くと、`destructiveHint`・`idempotentHint` に写され、D2 と D4 が当たりました（本体の追記に D4 の矛 `fs_append`）。

（出典: 作例は本書の執筆時に走査して確かめた）

#### なぜそうするのか

この研究が照らしたいのは、「クライアントが受け取った約束」です。
だから、届くかどうかで扱いを変えます。どちらの向きに間違えても困ります。

- **2.x で届く宣言を「届かない」と扱うと**: 作者が本当にした約束が照合されず、あるはずの矛が消えます（誤 clear の向き）。U38 の前の run20 では、版が 2.0 以上の木の宣言 124 ユニットが、届かない扱いになっていました（16.9 節）。
- **1.x で届かない宣言を「宣言」と扱うと**: クライアントが受け取っていない約束を「破った」と数えることになります（誤警報の向き）。
- **版が決まらないものを、どちらかに倒すと**: どちらかの誤りを黙って作ります。だから `D_unknown` として残し、件数を数えます（16.9 節）。

（出典: `docs/decisions.md:3711-3712`、`docs/open_questions.md:698`（O27 の注記））

#### よくある誤解・つまずき

- **誤解: 「snake_case の宣言は、いつも届かない」**
  mcp 2.x では届きます。manifest の `mcp_version` と、ユニットの `D_kind`・`malformed_fields`・`undetermined_fields` を見ます。
- **誤解: 「manifest の `annotations` に `readOnlyHint` があるから、原ソースも camelCase で書いてある」**
  版 `ge2` では、snake_case が camelCase に写されて `annotations` に入ります。原ソースを見ると `read_only_hint` かもしれません。
- **誤解: 「`D_kind.unknown: true` は、変数で渡した宣言（`unreadable`）だけだ」**
  snake_case で版が決まらないときも `unknown: true` になります。どちらかは `annotation_form` と `undetermined_fields` で見分けます。
- **誤解: 「木の `mcp_version` が `lt2` なら、その木の snake_case は全部 `malformed`」**
  版はサブツリーごとです。最上位の欄は木全体のまとめなので、ユニットごとの欄で確かめます。
- **誤解: 「`malformed` の宣言は、作者が『読むだけ』と約束したのだから D1 で照らすべきだ」**
  1.x では、その約束はクライアントに届いていません。届かない約束を「破った」とは数えず、`r_malformed` として別に数えます。

#### 手作業ではどう使うか

- **手順 C・D で原ソースを開いたとき**: 原ソースが `read_only_hint=True` なのに、道具の「宣言:」の行が `{'readOnlyHint': True}` なら、版 `ge2` で写されたものです。manifest の最上位の `mcp_version` の根拠（`evidence`）を見て、どの手がかりで決まったかを確かめます。
- **版の判定が怪しいと思ったとき**: たとえば、依存の記載と import が別の版を指しているように見える場合です。手引きの下書きには、snake_case の版の読み違いをどう判定に反映するかが書かれていません（本書の執筆時に検索して確かめた）。気づいたら、判定表の `note` に根拠（依存の記載のファイルと行など）を書き留め、黙ってどちらかに倒さないでください。この扱いを封の前に手引きに足すかは、学生が決めることです（本書の気づきで、原典の決定は無い）。
- **集計のとき**: snake_case で版が決まらないユニットは、照合されていません。その件数は `r_malformed` の併記の欄（16.9 節）に出ます。

#### この節のまとめ

snake_case の宣言は、mcp 1.x では届かず、2.x では camelCase として届く。
解析器は import と依存の記載からサブツリーごとに版を決め、2.0 以上なら宣言、2.0 より前なら `D_malformed`、決まらなければ `D_unknown` とする（D64 の U38、逸脱 #25。仕様書 322 行は 1.x の前提で、書き換えていない）。
同じ注釈に camelCase があれば camelCase が勝つ。

### 16.9 `r_malformed` — 届かない宣言の率

#### 一言で言うと

**`r_malformed`** は、「snake_case で書かれ、mcp 2.0 より前では相手に届かない宣言」を持つユニットの率です。
分子は `D_kind.malformed` が空でないユニット、主の分母は「注釈を書いたユニット」（`annotation_form` が `ToolAnnotations`・`dict`・`unreadable`）です。
学生の決定で、**最終評価のデータで数えて報告します**（D65 の 1）。人が判定する数ではなく、機械が数える数です。

#### たとえ話 — 書き損じで届かなかった年賀状の割合

「宛名の書式を間違えて届かなかった年賀状の割合」を出すとします。
分母は「年賀状を出した人」にするのが自然です。
町の全住民を分母にすると、年賀状を出さなかった人の多さで、割合が薄まってしまいます。
書き損じは、年賀状を**書いた人にしか**起こりえないからです。

`r_malformed` も同じです。
snake_case の誤りは、注釈を**書いた**ユニットにしか起こりえません。
だから、主の分母は「注釈を書いたユニット」で、全ユニットを分母にした率は併記にとどめます。

#### 小さな例 — 定義の表

| 項目 | 定義 |
|---|---|
| 分子 | `D_kind.malformed` が空でないユニット（版が 2.0 より前と決まったサブツリーで、snake_case の注釈を書いたもの） |
| 主の分母 | **注釈を書いたユニット** = `unit.annotation_form` が `ToolAnnotations` / `dict` / `unreadable` のもの |
| 併記 | 全ユニットを分母にした率、分子のある木の数、版が決まらない snake_case のユニット（`unit.undetermined_fields` が空でない。`D_unknown`）の件数と木の数 |
| 手続き | `analyzer-freeze-3` の full scan（集めた木を全部走査すること）の run のディレクトリに `scripts/r_malformed.py <run>` を当てる |
| 報告 | 最終評価のデータで数えて報告する。開発用の v2・v3 の値は報告しない |

表の読み方: 1 行が定義の 1 項目です。
たとえば 2 行目は「主の分母に入るのは、`annotation_form` が 3 つの値のどれかのユニットだけ。`annotations=` を書いていないユニット（欄が無い）や、`absent` のユニットは入らない」と読みます。

この定義は、学生が決め（D65 の 1）、最終評価のデータを見る前に、事前登録の §2.11 に書いてコミットしてあります。
集計のスクリプト `scripts/r_malformed.py` も、同時にコミットされました。
（出典: `docs/decisions.md:3717-3722`（D65 の 1）、`docs/preregistration.md:483-495`（§2.11））

#### 一歩ずつ — スクリプトを読む

数える部分を、短くして読みます。

```python
 1  ANNOTATED_FORMS = frozenset({"ToolAnnotations", "dict", "unreadable"})
 2
 3  for tree, path in manifests:
 4      for u in load_manifest(path).get("units", []):
 5          n += 1
 6          un = u["unit"]
 7          if un.get("annotation_form") in ANNOTATED_FORMS:
 8              annotated += 1
 9          if u.get("D_kind", {}).get("malformed"):
10              malformed += 1
11              trees_mal.add(tree)
12          if un.get("undetermined_fields"):
13              undetermined += 1
14              trees_und.add(tree)
```

- 1 行目: 主の分母に入れる `annotation_form` の値を、3 つ決めています。`frozenset` は、後から変えられない集合です。
- 3 行目: run のディレクトリの manifest（木ごとのファイル）を、1 つずつ取り出します。
- 4 行目: その manifest のユニットを、1 つずつ取り出します。
- 5 行目: 全ユニットの数 `n` を 1 つ増やします（併記の分母）。
- 6〜8 行目: ユニットの `annotation_form` が 3 つの値のどれかなら、主の分母 `annotated` を 1 つ増やします。
- 9〜11 行目: `D_kind.malformed` が空でなければ、分子 `malformed` を 1 つ増やし、その木を「分子のある木」の集合に入れます。
- 12〜14 行目: `undetermined_fields` が空でなければ、版が決まらない snake_case のユニットとして数え、その木を記録します。

最後に、`malformed / annotated`（主の率）と `malformed / n`（全ユニットでの率）などを JSON で出します。
（出典: `scripts/r_malformed.py:23-55`）

なお、このスクリプトの冒頭の説明文は、定義の場所を「`docs/preregistration.md` §2.10」と書いています。
事前登録の今の節番号では、`r_malformed` は §2.11 で、§2.10 は「NET 込み / 除きの分母」です。
説明文の節番号が古いだけで、数え方（主の分母の 3 つの値）は §2.11 と一致しています（本書の執筆時に見比べた）。
（出典: `scripts/r_malformed.py:3`、`docs/preregistration.md:467, 483`）

#### 主の分母に入るもの・入らないもの

`annotation_form` の値ごとに整理します。

| `annotation_form` | 書き方 | 主の分母 |
|---|---|---|
| `ToolAnnotations` | `ToolAnnotations(...)` | 入る |
| `dict` | `{...}` | 入る |
| `unreadable` | 変数・別の関数の呼び出しなど | 入る |
| `unpack` | `ToolAnnotations(**{...})` | **入らない**（§2.11 の一覧に無い） |
| `absent` | `annotations=None`、または宣言の無い `Tool(...)` と名前で結び付いた | 入らない |
| （欄なし） | `annotations=` を書いていない | 入らない |

表の読み方: 4 行目は「`ToolAnnotations(**{...})` と書いたユニットは、注釈を書いてはいるが、§2.11 の主の分母の一覧に `unpack` が無いので、主の分母に入らない」と読みます。

`unpack` については、注意があります。
§2.11 の一覧にも、スクリプトの `ANNOTATED_FORMS` にも、`unpack` は入っていません。
v2 run24 と v4 では、`unpack` のユニットは 0 件だったので、下の値には影響しません（本書の執筆時に数えた）。
§2.11 の定義どおりに数えれば、最終評価のデータで `unpack` が出ても分母に入りません。
意図して外したのか、書き落としなのかは、原典に書かれていません。
本書では判断せず、気づいた点として書いておきます。§2.11 はコミット済みの定義なので、変えるかどうかは学生が決めることです。

もう 1 つ、低レベルの書き方のハンドラ（16.5 節）のユニットは、ユニット自身に `annotation_form` の欄がありません（宣言の形は、ツールごとの `dispatch_annotations` の中に入る）。
そのため、主の分母に入りません。
v4 の vision-mcp の木の `handle_call_tool` で、ユニットに `annotation_form` が無いことを確かめました。
v4 では、この形のユニットは 2 つでした。
（出典: `scripts/r_malformed.py:23`、`authgap/entries.py:2803-2852`（`join_annotations`）、`evidence/scan_v2_v4_run1/v4-itzfaisal__vision-mcp.json`。本書の執筆時に確かめた）

#### 値

| データ | 分子 / 主の分母 | 全ユニット | 版が決まらない snake_case | 出典 |
|---|---|---|---|---|
| v2 run24（開発用） | **0 / 1,678** | 2,289 | 6 ユニット / 2 木 | `docs/preregistration.md:493` |
| v4（中間検証） | **0 / 1,290** | 3,696 | 0 | `docs/population_v4.md:114` |

表の読み方: 1 行目は「開発用の v2 の run24 では、注釈を書いたユニット 1,678 のうち、届かない snake_case の宣言を持つものは 0 だった。全ユニットは 2,289。版が決まらない snake_case は 6 ユニットで、2 つの木にあった」と読みます。

#### 「130」という古い値に注意

古い記録には、`r_malformed` の分子として **130** という値が出てきます。

- D48 の「**130 / 1,602 = 8.1%**」は、**run6 の版で、mcp の版を見ずに数えた値**です。当時は snake_case をいつも「届かない」と扱っていました。
- run20 でも、`malformed` を持つユニットは 130 でした。
- U38 の版の条件を入れた run24 では、**0** になりました。130 のうち 124 は版が 2.0 以上の木の宣言（上界あり 94・上界なし 30）に、6 は `D_unknown` に移りました。124 のうち 108 は canvas-mcp という 1 つの木のものです。

**130 は今の定義の値ではありません。**
論文や判定で引くときは、必ず今の版（`analyzer-freeze-3`）で数えた値を使います。

#### なぜ数えるのか

`r_malformed` は、「作者が宣言を書こうとしたのに、書き方のせいでクライアントに届いていない」という、具体的な失敗の形を数えます。
D48 の記録は、これを「『読み取り専用のつもりで宣言したが protocol に届いていない』という具体的な失敗形」と呼び、以前は「注釈なしのツールと区別できていなかった」と書いています。
宣言の誤り（言っていることとやっていることのずれ）とは別の種類の、宣言の書き方の問題です。
開発用の v2・中間検証の v4 では 0 でしたが、最終評価のデータでいくつになるかは、数えてみないと分かりません。
（出典: `docs/decisions.md:2471-2473`）

- **誤解: 「`r_malformed` の値は 130 / 1,602 = 8.1%」**

- **誤解: 「主の分母は全ユニット」**
  主の分母は注釈を書いたユニットです。全ユニットは併記です。
- **誤解: 「`unreadable` は宣言が読めないので、分母から外す」**
  §2.11 は `unreadable` を主の分母に入れています。注釈を書いたことは確かだからです。
- **誤解: 「`r_malformed` も手で判定する」**
  判定しません。スクリプトで数えるだけです。
- **誤解: 「版が決まらない snake_case も分子に入る」**
  分子は `malformed`（版が 2.0 より前と決まったもの）だけです。版が決まらないもの（`D_unknown`）は、件数と木の数を併記します。

### この章のまとめ

- 解析器は、いろいろな形で書かれた宣言を読み、形を `annotation_form`、値を `annotations` に写す。`annotations` は 5 つの項目のリテラルの値だけで、原ソースの写しではない。何も書いていなければ宣言は無いとし、既定値で補わない（[第 4 章](ch04.md) 4.4 節の表）。
- 読み取った宣言は `D_kind` にまとめる。`explicit` は「上界を動かす明示」と `openWorldHint: true` の名前の一覧で、入るのは `readOnlyHint`（true）・`destructiveHint`（false で `readOnlyHint: true` が無い）・`openWorldHint`（true）だけ。ほかの書かれたキーは `present_no_bound`。
- `upper` は宣言が許す kind の上界、`bottom` は上界が無いこと（⊥）。D3 は `closed_world: true`、D4 は `idempotent: true`（`readOnlyHint: true` が無いとき）として表れ、どちらも true のときだけ欄が出る。ほかに `open_world`・`malformed`・`unknown`。
- 判定の対象: D1 = `explicit` に `readOnlyHint`、D2 = `explicit` に `destructiveHint`（`readOnlyHint: true` が無いとき）、D3 = `closed_world`、D4 = `idempotent` で `readOnlyHint: true` が無い。`readOnlyHint` が明示の false でも書いていなくても、D2・D4 を当てる点は同じ。D3 は D1 と一緒でも当てる。
- D1〜D4 は 4 つとも主指標で、宣言ごとに報告し、足し合わせない（D62）。以前は D3・D4 を探索的と呼んでいたが、評価は新しいデータで行うので区別の理由が無くなった。変えたのは呼び方だけ。
- 分母 (c) の M_d は「`D_kind.explicit` を持つ木」と書かれているが、D3・D4 は `explicit` に入らない。文字どおりに数えると D3 は逆の申告の木、D4 は 0 になる。**D3・D4 の M_d の定義は未決**で、事前登録を封する前に学生が決める（[第 46 章](ch46.md)）。
- snake_case の宣言は、mcp の版が 2.0 以上なら宣言、2.0 より前なら `D_malformed`、決まらなければ `D_unknown`（D64 の U38、逸脱 #25）。版は import と依存の記載から、サブツリーごとに決める。
- `r_malformed` = `D_kind.malformed` のあるユニット / 注釈を書いたユニット（`ToolAnnotations`・`dict`・`unreadable`）。全ユニットでの率と、版が決まらないものの件数・木の数を併記する。v2 run24 は 0 / 1,678、v4 は 0 / 1,290（どちらも論文に使わない）。最終評価で数えて報告する（D65 の 1、§2.11）。D48 の 130 / 1,602 は版を見ない古い数え方。
- 判定では、手順 A で `decl` と原ソースの宣言を見比べ、手順 B で「明示された宣言:」に D3・D4 が出ないことに注意する。見落としの抜き取りの対象は D1・D2 を `explicit` に持つユニット。
