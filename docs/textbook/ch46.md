### 46.1 決定を読む型 — 5 段と、決定の日付の順

#### 一言で言うと

この章では、決定を 1 つずつ、**決めた中身 / 理由 / 退けた案・やらないこと / 判定や集計でどう効くか / 原典** の 5 段で読みます。
決定の番号（D67 の 1 など）は、原典を引くための目印です。
番号を覚える必要はありません。

#### たとえ話 — 法律の条文と、その解説書

法律の本には、条文だけが並んだものと、条文ごとに「この条文は何を定めているか」「なぜこう定めたか」「ほかにどんな案があったか」「実際にどう使われるか」を書いた解説書（逐条解説と呼ばれます）があります。
条文だけを読んでも、何をしてよくて何をしてはいけないかは分かります。
けれども、条文に書いていない場面に出会ったときには、解説書の「なぜ」が頼りになります。

事前登録 §2.12 と判定の手引きが条文、この章が解説書にあたります。

#### 小さな例 — 決定の年表

| 日付 | 決定 | 一言で | 誰が決めたか | 今の状態 |
|---|---|---|---|---|
| 2026-09-29 | D65 の 1 | `r_malformed` を最終評価で数える | 学生（分母は本記録者の推奨どおり） | 事前登録 §2.11 にコミット済み（`a032d7d`） |
| 2026-09-29 | D66 | v4 の中間検証（[第 37 章](ch37.md)） | 学生の依頼で本記録者が行った | 終わった |
| 2026-09-29 | D67 の 1〜4 | 判定と報告の決め事（重みなし、起動時の初期化、木の単位、判定者 1 人） | 学生 | §2.12 の下書きに写した（未承認） |
| 2026-09-30 | D68 の 1〜3 | 判定の決め事の追加（条件つきの到達、深さ 4 の外、ラベル） | 本記録者が挙げて推奨を示し、学生が 3 点とも賛成した | 同上 |
| 2026-09-30 | D69 | 規模（案 C） | 本記録者が 3 案を示し、学生が C を選んだ | 同上 |

（出典: `docs/decisions.md:3717-3722`（D65）、`:3743`（D66）、`:3762-3765`（D67）、`:3790-3794`（D68）、`:3816-3819`（D69）、`:3836-3839`（D70）、`:3884-3890`（D71）、`git log` の `a032d7d`（2026-09-29））

表の読み方: 1 行が 1 つの決定です。
たとえば 4 行目は「2026-09-30 の D68 は、手順書の段階 0 の 0-11〜0-13 で、D67 の文面では決まらない点として本記録者が 3 つ挙げ、推奨を示した。学生が 3 点とも推奨に賛成して決まった。中身は事前登録 §2.12 の下書きに写してあるが、下書きはまだ承認されていない」と読みます。

#### 一歩ずつの説明 — 5 段の読み方

5 段のそれぞれで、何を読むかを説明します。

1. **決めた中身**: 決定の文面そのものです。判定や集計で、何をするか・何をしないかが書いてあります。この段は、事前登録と手引きの下書きに写されています。
2. **理由**: なぜそう決めたかです。この章の各節の型でいえば、「なぜそうするのか」にあたります。多くは決定の本文に書いてあります。本文に無いときは、関連する未決事項（O の番号）や手順書から引きます。そのときは、どこから引いたかを書きます。
3. **退けた案・やらないこと**: 検討したが採らなかった案と、この決定のもとでしないことです。判定の途中で「こうしたほうがいいのでは」と思ったら、まずここを見ます。
4. **判定や集計でどう効くか**: この決定が、段階 6〜8 のどの作業の、どの欄や計算に効くかです。
5. **原典**: 決定の本文と、それを写した事前登録・手引きの下書きの行です。

この 5 段は、この章の各節の「一歩ずつの説明」の後に置きます。
節の型（一言で → たとえ話 → 小さな例 → 一歩ずつ → 5 段 → 誤解 → 手作業 → まとめ）のうち、「なぜそうするのか」は 5 段の 2 番目（理由）に入れてあります。

#### なぜこの型で読むのか

決定の記録（`docs/decisions.md`）は、決めた順に書かれています。
そのため、1 つの決定の中に、中身と理由と退けた案が混ざって書かれていたり、理由が別の文書（未決事項や手順書）にあったりします。
同じ型で並べ直すと、決定どうしを比べやすくなり、「この決定には退けた案が書かれていない」「この理由は本文ではなく別の文書から来ている」といったことにも気づけます。

#### よくある誤解・つまずき

- **誤解: 「決定は本記録者（AI）が決めた」**
  決めたのは学生です。本記録者は、決めるべき点を挙げ、案と推奨を示し、決まったことを記録しました。表の「誰が決めたか」の列で確かめてください（[第 0 章](ch00.md)の「誰が何をしたか」）。
- **誤解: 「『データを見る前』というのは、v4 のデータも見ていないということ」**
  v4 のデータは、本記録者がすでに見ています（[第 37 章](ch37.md)）。D67 の 1 は、まさに v4 の結果を受けて決まりました。「データを見る前」は、**最終評価のデータ**を見る前、という意味です。
- **誤解: 「宣言の D1 と、決定の D1 は同じもの」**
  違います。この章の D65〜D71 は、`docs/decisions.md` の決定の番号です。宣言の D1〜D4（`readOnlyHint: true` など）とは別物です（[第 0 章](ch00.md)）。
- **誤解: 「決まったことは、もう下書きに写したので、正本だ」**
  下書きは未承認です。封をするまでは正本ではありません（[第 45 章](ch45.md) 45.4 節）。

#### 手作業ではどう使うか

判定の最中に規則の文面で迷ったら、次の順に読みます。

1. 封をした手引きの該当の節を読み直す。
2. その節の元になった決定（この章の節）を開き、5 段の「理由」と「退けた案」を読む。
3. それでも決められなければ「不明」にし、`unknown_reason` に「手引きで決まらない: <事例>」と書き、事前登録の §5 に事例を書く（[第 52 章](ch52.md)）。

#### この節のまとめ

- 決定は「決めた中身 / 理由 / 退けた案・やらないこと / 判定や集計でどう効くか / 原典」の 5 段で読む。
- D65 の 1（2026-09-29）、D67（09-29）、D68・D69（09-30）、D70（10-01）。どれも最終評価のデータを見る前に、学生が決めた。D70 の 8 だけは保留。
- 決定の番号は原典を引く目印。宣言の D1〜D4 と取り違えない。

### 46.2 D65 の 1 — `r_malformed` を最終評価で数える

#### 一言で言うと

書き方を誤って protocol に届かない宣言の率 `r_malformed` を、**最終評価のデータで数えて報告します**。
分母の主は「注釈を書いたユニット」、併記は「全ユニット」と、版が決まらない snake_case のユニットの件数です。
定義と集計のスクリプトは、最終評価のデータを見る前に、事前登録の §2.11 としてコミットしました。

#### たとえ話 — 書式を誤って受理されなかった申込書

市役所に申込書を出すとき、「生年月日は西暦で書く」という決まりがあったとします。
和暦で書いた申込書は、内容は正しくても、機械が読めずに受理されません。
出した人は「申し込んだつもり」なのに、市役所の記録では「申し込んでいない」と同じ扱いになります。

この「書式を誤って受理されなかった申込書」が、どれくらいあるかを数えておくと役に立ちます。
「申し込まなかった人」と「申し込んだつもりで届かなかった人」は、記録の上では区別できないからです。
`r_malformed` は、MCP の宣言についての、この数です。

#### 小さな例 — 開発用の値と、分母の 2 つ

`r_malformed` の値を、開発用のデータで出したものを並べます（どちらも論文には使いません）。

| データ | 分子（届かない宣言を持つユニット） | 分母の主（注釈を書いたユニット） | 併記の分母（全ユニット） | 版が決まらない snake_case |
|---|---|---|---|---|
| v2 run24 | 0 | 1,678 | 2,289 | 6 ユニット / 2 木 |
| v4 | 0 | 1,290 | 3,696 | 0 |

（出典: `docs/preregistration.md:493`（v2 run24）、`docs/population_v4.md:114`（v4 の 0 / 1,290）。v4 の全ユニット 3,696 と版が決まらない 0 は、本書の執筆時に `scripts/r_malformed.py evidence/scan_v2_v4_run1` を走らせて確かめた）

表の読み方: 1 行が 1 つのデータです。
たとえば 1 行目は「開発用の v2（run24）では、届かない宣言を持つユニットは 0 で、分母の主（注釈を書いたユニット）は 1,678、全ユニットは 2,289。版が決まらない snake_case のユニットが 2 木に 6 つあった」と読みます。

#### 一歩ずつの説明

**分子**は、`D_kind.malformed` が空でないユニットです。
mcp の版が 2.0 より前と決まったサブツリーで、`read_only_hint` のような snake_case（単語を下線でつなぐ書き方）で注釈を書いたものです。
このような宣言は、その版の mcp では `ToolAnnotations` に読み込まれず、クライアントに届きません（[第 16 章](ch16.md) 16.8・16.9 節）。

**分母の主**は、注釈を書いたユニット（`unit.annotation_form` が `ToolAnnotations` / `dict` / `unreadable` のもの）です。
「注釈を書こうとした人のうち、どれだけが書き方を誤ったか」を表します。

**併記**は 3 つです。全ユニットを分母にした率、分子のある木の数、版が決まらない snake_case のユニット（`D_unknown`）の件数と木の数です。

開発用の値がどちらも 0 なのは、D64（U38）で snake_case の読み方を mcp の版で条件づけたからです。
それより前の版では、snake_case を版に関係なく `D_malformed` にしていて、v2 の run20 では 130 ユニットが `malformed` でした。
D48 の「130 / 1,602」（run6 の版）も、版を見ずに数えた値です。
（出典: `docs/decisions.md:3711-3713`、`:3722`、`docs/open_questions.md:698`）

#### 5 段で読む

**1. 決めた中身**

学生の決定で、`r_malformed` を最終評価のデータで数えて報告する。
分母は本記録者の推奨どおり「注釈を書いたユニット」を主、全ユニットを併記する。
版が決まらない snake_case（`D_unknown`）の件数も併記する。

### 46.3 D67 の 1 — 重みを付けない。書き込み先の種類をラベルにする

#### 一言で言うと

違反の重さ（重大度）で重みを付けることはしません。
主の精度は、今の原理（字義どおり）で数えた 1 本だけにします。
そのうえで、正の各件に「**書き込み先の種類**」を事実のラベルとして記録し、種類ごとの内訳を表で示します。
軽いか重いかの判断は、読み手に任せます。

#### たとえ話 — 交通違反の記録

「一時停止の標識で止まらなかった」違反の記録を考えてください。
同じ違反でも、人通りの多い住宅街で起きたものと、誰もいない農道で起きたものがあります。
記録係が「農道のは軽いから半分に数えよう」と重みを付け始めると、数字が記録係の感覚で変わってしまいます。
しかも、どこから「軽い」とするかの線引きには、決まった正解がありません。

そこで記録係は、重みは付けずに 1 件は 1 件として数え、そのかわりに「どこで起きたか」（住宅街・幹線道路・農道・駐車場）を事実として書き添えることにします。
報告を読む人は、場所ごとの内訳を見て、自分の基準で重さを判断できます。
D67 の 1 は、この記録係のやり方です。

#### 小さな例 — v4 の正の中身と、ラベルの一覧

v4 の中間検証（本記録者の判定。論文には使わない）では、D1・D2 の正 46 件のうち、ツール本来の動作は 3 件、裏側・補助的な書き込みは 43 件でした。
43 件のうち 38 件は reaper-mcp という 1 つの木の、別のプロセスとファイルを受け渡すための IPC ファイルの削除と作成でした。
（出典: `docs/population_v4.md:96-98`）

このような正を「軽い」として割り引くか、「違反は違反」として数えるかで、精度は大きく変わります。
D67 の 1 は、割り引かずに数え、中身はラベルで示すことにしました。
ラベルは、D67 の 1 で 7 種類が決まり、D68 の 3 で 1 種類が足されて 8 種類になりました。

| 順 | 書き込み先の種類 | 定義（短く） | 決めた決定 |
|---|---|---|---|
| 1 | 相手側の状態 | 通信相手のサーバの状態を変える | D67 の 1 |
| 2 | データベース | DB の行・スキーマ・DB に残る設定を変える | D67 の 1 |
| 3 | 利用者のファイル | 利用者（またはモデル）が指定した場所のファイルなど | D67 の 1 |
| 4 | ログ | 記録のためだけに書き、ツールの動作では読み返さない | D67 の 1 |
| 5 | 一時ファイル | 同じ呼び出しの中で作って消す、または OS の一時領域に作る | D67 の 1 |
| 6 | キャッシュ・状態の保存 | ツールの動作のために自分で保存し、後で読み返す | D67 の 1 |
| 7 | プロセスの起動・コードの実行 | SPAWN / EXEC の正 | **D68 の 3 で足した** |
| 8 | その他・不明 | 上のどれにも当てはまらない、または決められない | D67 の 1 |

（出典: `docs/decisions.md:3769`（D67 の 1 のラベル）、`:3809-3810`（D68 の 3）、`docs/drafts/final_judging_guide_draft.md:382-395`（16.1 の定義と順））

表の読み方: 1 行が 1 つの種類です。
「順」は、手引きで当てはめる順番です。上から順に当てはめ、最初に当てはまったものを付けます。
たとえば 2 行目は「DB の行・スキーマ・DB に残る設定を変える正には『データベース』を付ける。SQLite のキャッシュ DB への書き込みは、6 番の『キャッシュ・状態の保存』にも見えるが、2 番が先に当てはまるので『データベース』になる」と読みます（手引き 16.2 の境界の例）。

#### 一歩ずつの説明

D67 の 1 の要点は 3 つです。

1. **主の精度は 1 本だけ**: 今の原理（`docs/contradiction_principles.md` の §6、字義どおり）で正・誤を決め、その 1 本の精度を主にします。原理 1-i-b（呼び出しを越えて残るものは、すべて環境）により、ログの 1 行の追記も、読み取り専用の宣言への違反です（第 28・43 章）。
2. **ラベルは事実**: 「書き込み先の種類」は、重さの評価ではなく、「何に書いたか」という事実です。重みは付けません。どの種類も、違反であることは同じです。
3. **内訳は表で示す**: 段階 8 で、宣言ごとに、正の各件の種類の件数を表にします。読み手は、その表を見て、軽重を自分で判断できます。

#### 5 段で読む

**1. 決めた中身**

重大度の重みは付けない（O44 の決着）。主指標の精度は、今の原理（§6、字義どおり）の 1 本だけにする。正の各件に「書き込み先の種類」を事実のラベルとして記録し、内訳を表で示す。軽重の判断は読み手に任せる。
ラベル: 利用者のファイル / データベース / 相手側の状態 / キャッシュ・状態の保存 / ログ / 一時ファイル / その他・不明（D68 の 3 で「プロセスの起動・コードの実行」を足す）。

**2. 理由**

D67 の 1 は、理由を 3 つ書いています。

- 研究の問いは「宣言は正しいか」で、「危ないか」ではない。
- 重みの線引きには正解が無い。実世界でも割れている（`docs/incidental_writes_practice.md`。[第 43 章](ch43.md)で見た、OpenAI の提出ガイドと RFC 9110 が逆を向く例など）。

そして、内訳を出す理由を「『見つけた違反は些細では』という問いに事実で答えるため」と書いています。

### 46.4 D67 の 2 — 起動時の初期化

#### 一言で言うと

ツールの道筋の途中に「一度だけ初期化する」形があり、効果（ディレクトリの作成など）がその初期化の中にあるとき、**その初期化がツールの受付より前に必ず済んでいるか**を、**コードだけ**から決めます。
初期化が `main()` / `if __name__ == "__main__":` の中だけにあるなら「到達する」（正になりうる）、lifespan の中やモジュールの読み込み時にあるなら「到達しない」（誤、E1）、読み切れなければ「不明」です。
解析器は変えません。

#### たとえ話 — お店の開店準備

あるお店では、毎朝、開店前に必ず床を掃除します（開店の手順書に書いてある）。
この場合、お客さんの注文で掃除が始まることはありません。
これが lifespan の形です。サーバが受付を始める前に、必ず初期化が済みます。

別のお店では、「店長が出勤したら、まず床を掃除する」という決まりになっています。
店長が出勤した日は、開店前に掃除が済みます。
けれども、店長が休みで、アルバイトの人が店を開けた日は、掃除がされないまま開店します。
そして、最初のお客さんの注文を受けたときに「あ、掃除がまだだ」と掃除が始まります。
これが `main()` の形です。`main()` を通らない起動の方法があると、最初のツールの呼び出しで初期化が走ります。

#### 小さな例 — 一度だけ初期化する形と、判定の表

```python
_memory = None

def _ensure_memory():
    global _memory
    if _memory is None:
        _init()            # ← 効果（ディレクトリの作成など）はこの中
    return _memory
```

（出典: `docs/drafts/final_judging_guide_draft.md:265-273`）

このコードを 1 行ずつ読みます。

- 1 行目 `_memory = None`: モジュール水準（ファイルの一番上の段）の変数 `_memory` に、「まだ何も無い」を表す `None` を入れます。
- 3 行目 `def _ensure_memory():`: 「メモリを用意してから返す」関数を定義します。ツールの道筋の途中で呼ばれるとします。
- 4 行目 `global _memory`: この関数の中の `_memory` は、モジュール水準の変数を指す、という宣言です。
- 5 行目 `if _memory is None:`: まだ用意されていなければ、という条件です。
- 6 行目 `_init()`: 用意する関数を呼びます。効果（ディレクトリの作成など）はこの中にあります。
- 7 行目 `return _memory`: 用意したものを返します。

（このコードは手引きの説明用の抜粋で、`_init()` の中で `_memory` に値を入れる行は省かれています。）

判定は、`_init()` を先に済ませている場所で決まります。

| 初期化を先に済ませている場所 | 判定 | 理由 |
|---|---|---|
| `main()` の中だけ、または `if __name__ == "__main__":` の中だけ | **到達する（正になりうる）** | `fastmcp run file.py:mcp` などで `main()` を通らずに起動できる。そのときは最初のツールの呼び出しで初期化が走る |
| lifespan の中（`FastMCP(..., lifespan=...)` に渡した関数の中） | **到達しない（誤、E1）** | どの起動方法でも、ツールの受付より前に必ず走る |
| モジュールの読み込み時（モジュールの一番上の文） | **到達しない（誤、E1）** | import した時点で走る |
| どこで先に済ませるか読み切れない | **不明** | |

（出典: `docs/drafts/final_judging_guide_draft.md:275-282`、`docs/final_evaluation_procedure.md:950-955`）

表の読み方: 1 行が初期化の場所の 1 つの形です。
たとえば 2 行目は「初期化が lifespan の中で済んでいるなら、どの起動の方法でもツールより先に初期化が走るので、ツールの呼び出しでは効果が起きない。だから解析器の矛は誤で、誤の原因は E1（起動時の初期化）」と読みます。

#### 一歩ずつの説明

なぜ `main()` の形だけ「到達する」になるのでしょうか。
MCP のサーバは、起動のしかたが 1 つではありません（[第 3 章](ch03.md)）。
`python server.py` のように起動すれば `if __name__ == "__main__":` の中が走り、`main()` が呼ばれます。
けれども、`fastmcp run file.py:mcp` のように、モジュールの一番上の `mcp = FastMCP(...)` を直接使って起動する方法では、`main()` は呼ばれません。
そのとき、初期化は済んでいないので、最初のツールの呼び出しで `_ensure_memory()` が `_init()` を呼び、効果が起きます。

この研究は、「モデルが渡しうる値は、取りうる値の全体で考える」（原理 3。能力として読む）を採っています。
起動の方法も同じように、「届きうるなら届く」と読みます。
そして、どの起動の方法が実際に使われるかは、運用の様子を見ないと分からないので、**コードだけから**決めます。

lifespan は違います。
lifespan は、サーバの起動時に 1 回だけ走る関数で（[第 3 章](ch03.md)）、どの起動の方法でも、ツールの受付より前に必ず走ります。
だから、lifespan の中で済ませた初期化は、ツールの呼び出しでは起きません。

v4 では、この扱いの違いが判定を分けました。
ccr という木は `main()` で初期化していて、最終評価の規則では「到達する」になります。
shyhurricane という木は lifespan で初期化していて、「到達しない」（誤）になります。
（出典: `docs/final_evaluation_procedure.md:966-967`）

#### 5 段で読む

**1. 決めた中身**

起動時の初期化は、起動方法をコードだけで決める（O43 の整理）。
- 初期化が `main()` / `if __name__ == "__main__":` の中だけにある形は、ツールの呼び出しで届きうるので正（原理 3）。
- lifespan の中やモジュールの読み込み時にある形は誤。
- 読み切れないときは不明。
- 解析器は変えず、lifespan の形の誤りは設計の選択による限界（誤警報の向き）として件数を報告する。判定の手引きの誤の原因の欄に、この類を設ける。

**2. 理由**

v4 で、誤 14 件のうち 9 件（ccr 6、shyhurricane 3）が、起動時の初期化をツールの経路に数える類でした。
v3 では見えなかった、新しい類の誤りです。
最終評価でも出ることが見込まれるので、判定の規則を先に決めておく必要がありました。

規則の中身の理由は、「届きうるなら届く」という原理 3 の読み方です。
`main()` を通らない起動の方法がある以上、`main()` の中の初期化は「ツールより先に必ず済む」とは言えません。
lifespan と読み込み時は、どの起動の方法でも先に済むので、ツールの呼び出しでは起きません。

解析器を直さない理由は、v4 の規則（D66 の 2）と同じです。
v4 で見つけた誤りは直さずに O43 に書く、と決めていたからです。
解析器は、各呼び出しを、サーバの状態を仮定せずに独立に解析する設計で、lifespan の形の誤りはこの設計の選択からくる限界です（[第 42 章](ch42.md) 42.6 節）。
（出典: `docs/population_v4.md:99-104`、`docs/decisions.md:3751`、`docs/final_evaluation_procedure.md:1401`）

**3. 退けた案・やらないこと**

- **解析器を直して、lifespan の初期化をツールの経路から外す**: しません。凍結の後で、しかも v4 の結果を見た後なので、直さずに限界として件数を報告します。
- **README や運用の様子から、起動の方法を推し量る**: しません。起動の方法はコードだけから決めます。
- **v4 の判定を付け直す**: しません。v4 では ccr の `main()` の形も誤にしていましたが、v4 の判定と数字はそのままです（[第 37 章](ch37.md)）。

**4. 判定や集計でどう効くか**

- **到達の判定（[第 49 章](ch49.md)）**: 道筋の途中に「一度だけ」の守り（`if self._x is None:`、`@lru_cache`、`global _initialized` など）があれば、初期化を先に済ませている場所を探します（手順書 13 の手順 D の 4）。
- **誤の原因**: lifespan と読み込み時の形の誤には E1 を付けます（[第 51 章](ch51.md)）。
- **条件の種類**: `main()` の形で「到達する」にした正は、条件の種類を「起動の方法」として記録します（D68 の 1）。「起動の方法」は運用者が決める条件なので、(B) と (C) の数からは外れます（46.7 節）。
- **集計と論文**: lifespan の形の誤を件数で報告します。解析器に有利な側（ccr の形）と不利な側（shyhurricane の形）の両方があることを、論文に書きます。

（出典: `docs/final_evaluation_procedure.md:811-812`、`:926-927`、`:966-967`、`docs/drafts/prereg_2_12_draft.md:77-80`）

#### 手作業ではどう使うか

1. 道筋の途中に「一度だけ」の守りがあったら、立ち止まります。

### 46.5 D67 の 3 — 報告の単位は木

#### たとえ話 — 1 人で 38 件の口コミ

あるお店の口コミが 60 件あり、46 件が「おいしい」でした（76.7%）。

件数で数えると、1 人の熱心なお客さんの意見に大きく引っぱられます。
お客さん 1 人ずつに束ねてから数えれば、引っぱられにくくなります。

- 判定者間の一致（κ）に依存する主張はしない。
- 第三者が後から検証できるように、判定の根拠（ファイルと行）を全件残して公開する。判定の手引きを先にコミットする。
- 将来 2 人目を用意できたら、追加の検証として足す。

**2. 理由**

2 人目の判定者を用意できない（決定の時点）、ということです。
仕様書の計画どおりに 2 人目と κ を書いておくと、実際にはできないことを約束したことになります。
黙って計画を消すと、読み手は「なぜ κ が無いのか」を知れません。
そこで、実際（判定者 1 人）を採り、計画との差を限界として論文に書く形にしました（`CLAUDE.md` の規則 6 の「実データを採り、仕様書の値も残す」の考え方。[第 8 章](ch08.md)）。

**3. 退けた案・やらないこと**

- **仕様書の計画（2 人目のラベラーと κ）**: 今回は採りません。ただし D70 の 8 で、2 人目を用意できる可能性が出てきたので、保留になりました（46.15・46.16 節）。
- **O2 の古い「暫定」**: O2 の本文には、仕様書の縮退の案（30 ツールに縮め、指導教員による裁定の標本、test-retest で κ を代える）を既定として事前登録する、という古い方針が残っています。見出しが今の状態（保留）で、本文の段落は D67・D70 より前の記述です（[第 8 章](ch08.md) 8.8 節）。
- **AI を 2 人目の判定者にする**: しません（D70 の 3）。

**4. 判定や集計でどう効くか**

### 46.7 D68 の 1 — 条件つきの到達

#### 一言で言うと

特定の条件のときだけ届く効果（引数を渡したときだけ、環境変数があるときだけ、など）は、**ツールの呼び出しで届きうるなら「到達する」**とし、正になりえます。
これが主の数 **(A)** です。
そのうえで、条件の種類を 1 組ごとに 7 種類のどれかで記録し、**(B)** 運用者が決める条件でしか届かないものを除いた数と、**(C)** 条件なしで届くものだけの数を併記します。

#### たとえ話 — 「火を使いません」と書いた部屋

「この部屋では火を使いません」と張り紙をした部屋があるとします。
ところが、その部屋の人は、「お茶を頼まれたときだけ」コンロでお湯を沸かします。
毎日ではありませんが、頼まれれば火を使います。
この張り紙は正しいでしょうか。

張り紙を見た管理人が「火を使わない部屋だから、見回りは省こう」と決めていたら、困ります。
お茶を頼まれた日に、見回りの無いまま火が使われるからです。
だから、「頼まれたときだけ」でも、張り紙は守られていないと考えます。

クライアントは、`readOnlyHint: true` を見て、呼び出しごとの確認を省きます。
確認を省いたどれか 1 回で書き込みが起きるなら、宣言は守られていません。
これが D68 の 1 の考え方です。

#### 小さな例 — 引数を渡したときだけ書く（作例）

```python
@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def make_report(query: str, output_file: str = "") -> str:
    text = build_report(query)
    if output_file:
        with open(output_file, "w") as fh:
            fh.write(text)
    return text
```

このコードは、本書が説明のために書いた作例です（v4 の M18 の形を短くしたもの）。
1 行ずつ読みます。

- 1 行目: このツールは `readOnlyHint=True`（読み取り専用）と宣言しています。
- 2 行目: ツールの関数 `make_report` を定義します。引数は `query`（検索の言葉）と `output_file`（書き出し先。省略すると空の文字列 `""`）です。どちらもモデルが渡す値です。
- 3 行目: レポートの文章を作ります。
- 4 行目: `if output_file:` は「`output_file` が空でなければ」という条件です。空の文字列は偽として扱われます。
- 5〜6 行目: その条件のときだけ、`output_file` のパスを書き込み用（`"w"`）で開き、文章を書きます。
- 7 行目: 文章を返します。

モデルが `output_file` を渡さなければ、書き込みは起きません。
けれども、モデルは `output_file` を渡すことを**選べます**。
だから、この書き込みはツールの呼び出しで届きうるので「到達する」、D1 に反するので**正**です。
条件の種類は「引数」で、(A) と (B) には数え、(C) には数えません。

条件の種類は、次の 7 つです。

| 条件の種類 | 例 | (B) に数えるか | (C) に数えるか |
|---|---|---|---|
| なし | 毎回届く | 数える | 数える |
| 引数 | モデルが渡す引数の値による（`if output_file:`） | 数える | 数えない |
| 初回 | 初回だけ・キャッシュが無いときだけ | 数える | 数えない |
| 失敗・期限切れ | トークンの更新、再試行、エラー時の後始末 | 数える | 数えない |
| 外部の状態 | ファイルが無いとき、相手が特定の応答を返したとき | 数える | 数えない |
| 運用者の設定 | 環境変数・設定ファイル・起動の引数で有効になる | **数えない** | 数えない |
| 起動の方法 | 初期化が `main()` の中だけにあり、`main()` を通らない起動で届く（D67 の 2） | **数えない** | 数えない |

（出典: `docs/drafts/final_judging_guide_draft.md:241-259`（14.3）、`docs/final_evaluation_procedure.md:919-928`）

表の読み方: 1 行が 1 つの条件の種類です。
たとえば 6 行目は「環境変数などの運用者の設定で有効になるときだけ届く正は、(A) では正に数えるが、(B) と (C) では数えない」と読みます。
「運用者の設定」と「起動の方法」の 2 つが、**運用者が決める条件**です。
条件が何で決まるか読み切れないときは、「決められない」として不明にします。

#### 一歩ずつの説明 — (A)(B)(C) の 3 つの読み方

- **(A) 主**: 条件を問わず、ツールの呼び出しで届きうるなら到達する。
- **(B) 併記**: 運用者が決める条件（運用者の設定・起動の方法）でしか届かない正を除く。「運用者がその設定にしなければ起きない書き込みは、宣言の責任の外かもしれない」という読み方に答えるための数です。
- **(C) 併記**: 条件なしで毎回届く正だけを数える。いちばん厳しい読み方です。

(B)・(C) で数え直すときは、その読み方で届かない正を、**誤に置き換えて**計算し直します。
除いて分母を小さくするのではありません。
計算のしかたは、[第 39 章](ch39.md) 39.6 節で手を動かして確かめました。
（出典: `docs/decisions.md:3804`、`docs/final_evaluation_procedure.md:1372`）

#### 5 段で読む

**1. 決めた中身**

条件つきで届く効果は、ツールの呼び出しで届きうるなら「到達する」とし、正になりうる（案 A を主）。
条件の種類を 1 組ごとに記録する: なし（毎回）/ 引数（モデルが渡す値）/ 初回 / 失敗・期限切れ / 外部の状態 / 運用者の設定 / 起動の方法（D67 の 2 の `main()` の形）。
併記: (B) 運用者が決める条件（運用者の設定・起動の方法）でしか届かないものを除いた数、(C) 条件なしで届くものだけの数。
1 組に複数の位置があるときは、B・C もそれぞれ「条件を満たす位置が 1 つでもあれば数える」。
B・C で精度を計算し直すときは、その読み方で届かない正を誤に置き換える。

**2. 理由**

D68 の 1 は、理由を 2 つ書いています。

- クライアントは `readOnlyHint: true` を見て、呼び出しごとの確認を省く（`docs/incidental_writes_practice.md` の結論 4）。確認を省いたどれか 1 回で起きるなら、宣言は守られていない。D67 の 2（起動時の初期化は「届きうる」なら正、原理 3）と同じ読み方。
- B・C を事前に併記と決めておくことで、後から出しても結果を見て選んだことにならない。

2 つ目の理由は大事です。
もし (B)・(C) を決めずにおいて、結果を見た後で「条件なしの正だけで数えると、こうなる」と出すと、それは事後の分析になります。
しかも、都合のよい読み方を選んだと疑われます。
先に「(A) を主、(B)(C) を併記」と決めておけば、3 つとも事前登録した数として出せます。
（出典: `docs/decisions.md:3800-3802`、`docs/incidental_writes_practice.md:29-31`）

**3. 退けた案・やらないこと**

- **(B) や (C) を主にする読み方**: 主は (A) と決め、(B)(C) は併記にしました。
- **条件つきの到達を一律に「不明」や「誤」にする**: しません。モデルが選べる条件（引数）や、いつか起きる条件（初回・失敗）で届くなら、宣言は守られていないからです。
- **やらないこと**: 判定の途中で「この条件はめったに起きないから誤にしよう」と考えること。めったに起きなくても、届きうるなら到達します。

**4. 判定や集計でどう効くか**

- **判定（段階 7）**: 到達するかを決めるとき（[第 49 章](ch49.md)）、条件つきなら `condition_type` に種類を、`condition` に中身を 1 文で書きます（例: 「引数 output_file を渡したとき」）。条件が重なるときは全部を `;` で並べ、1 つでも運用者が決める条件があれば (B) に数えません。
- **1 組に複数の位置があるとき（手順 G）**: 正にできる位置のうち、条件の一番弱いものを記録します。弱い順は「なし」→ 運用者が決めない条件 → 運用者が決める条件です。条件つきの位置で正が見つかっても、条件なしの位置がありそうなら、そこまで読むと (C) の数が正しくなります。
- **集計（段階 8）**: 主指標を (A) で出し、(B)・(C) の読み方でも計算し直して併記します。条件の種類ごとの件数も表にします。

（出典: `docs/drafts/final_judging_guide_draft.md:150-161`（手順 G）、`:241-259`（14.3）、`docs/final_evaluation_procedure.md:1372`）

**5. 原典**

- 決定: `docs/decisions.md:3796-3804`（D68 の 1）
- 手順書: `docs/final_evaluation_procedure.md:253-260`（0-11）
- 写した先: `docs/drafts/prereg_2_12_draft.md:72-76`、`docs/drafts/final_judging_guide_draft.md:241-259`
- くわしい章: [第 39 章](ch39.md) 39.6 節（計算）、[第 49 章](ch49.md)（判定）

#### よくある誤解・つまずき

- **誤解: 「条件つきなら、到達するかどうかは『不明』」**
  条件の中身が読めるなら、届きうるので「到達する」です。不明にするのは、条件が何で決まるか読み切れないときだけです。
- **誤解: 「(B)(C) は結果を見てから出す事後の分析」**
  事前に併記と決めてあるので、事前登録した数です。
- **誤解: 「(B)(C) では、届かない正を数から除く」**
  除くのではなく、誤に置き換えます。分母は変わりません。
- **誤解: 「大文字の (A)(B)(C) と小文字の (a)(b)(c) は同じもの」**
  大文字は到達の読み方、小文字は木の割合の分母です（46.13 節）。組み合わせて「(B) の読み方での (c)」のように使います（[第 39 章](ch39.md)）。

#### 手作業ではどう使うか

1. 効果の行までたどる途中で `if` があったら、その条件を書き留めます。
2. 条件がモデルの引数で決まるなら「引数」、初回だけなら「初回」、環境変数などなら「運用者の設定」…と、7 つのどれかを選びます。
3. 1 組に複数の位置があれば、正にできる位置のうち条件の一番弱いものを記録します。
4. 条件が読み切れなければ、到達は「決められない」で、判定は不明です。

#### この節のまとめ

- 条件つきで届く効果は、届きうるなら到達する（(A) が主。D68 の 1）。条件の種類を 7 つのどれかで記録する。
- 併記は (B) 運用者が決める条件でしか届かないものを除く、(C) 条件なしだけ。数え直すときは、届かない正を誤に置き換える。
- 理由はクライアントが確認を省くこと。(B)(C) を先に決めたので、後から出しても結果を見て選んだことにならない。

### 46.8 D68 の 2 — 深さ 4 より奥で見つけた違反

#### 一言で言うと

見落としの判定で読む範囲は、ツールの本体から**深さ 4 まで**です。
偶然それより奥に宣言に反する動作を見つけたら、「**見落とし（深さ 4 の外）**」として別に記録し、主の見落としの数には入れず、併記します。

#### たとえ話 — 2 階までと決めた家の点検

家の点検を頼んだとき、「1 階と 2 階を見る」と決めて契約したとします。
点検の人が 2 階の天井を見上げたら、たまたま屋根裏から水がしみているのに気づきました。
屋根裏は点検の範囲の外です。

このとき、「範囲の外なので、何も無かったことにする」のはよくありません。
知っている問題を黙って消すことになるからです。
かといって、「2 階までの点検で見つかった問題」として数えると、点検の結果が「たまたま見上げたかどうか」で変わってしまいます。
そこで、「範囲の外で見つけたもの」として別の欄に書きます。
D68 の 2 は、このやり方です。

#### 小さな例 — v4 の R04

v4 の見落としの抜き取りで、mcp-atlassian の `get_page`（D1）を調べたとき、OAuth のトークンの更新と保存（ファイルへの書き込み）が、ツールの本体から**深さ 7** の位置にありました。
v4 では「見落とし（深さ）」と判定しましたが、最終評価の規則（D68 の 2）では「見落とし（深さ 4 の外）」になり、主の見落としの数には入りません。
条件の種類は「失敗・期限切れ」（トークンの期限が切れたとき）です。
v4 の判定は本記録者の判定で、正解ではなく考え方の例です。
（出典: `docs/drafts/final_judging_guide_draft.md:646`、`docs/decisions.md:3808`）

見落としの判定の結果（`outcome`）は、次の 5 つのどれかです。

| `outcome` | 意味 |
|---|---|
| 反する動作は無い | 深さ 4 まで読んで、宣言に反する動作が見つからなかった |
| 解析器が不として出している | 見つけた動作に、解析器が不を出している |
| 見落とし | 深さ 4 までの中に、解析器が矛も不も出していない、宣言に反する動作があった |
| **見落とし（深さ 4 の外）** | 深さ 4 の中には無く、深さ 4 より奥にだけ、宣言に反する動作を偶然見つけた |
| 不明 | 反するかを決められない |

（出典: `docs/drafts/final_judging_guide_draft.md:485`）

表の読み方: 1 行が 1 つの結果です。
たとえば 4 行目は「深さ 4 までの中には反する動作が無かったが、たまたま深さ 4 より奥に反する動作を見つけたときは、『見落とし（深さ 4 の外）』にして、主の見落としとは別に数える」と読みます。

#### 一歩ずつの説明

深さの数え方は、ツールの本体が深さ 0、本体が呼ぶ関数が深さ 1、その関数が呼ぶ関数が深さ 2、…です（手引き 18.2）。
解析器も深さ 4 で凍結されています（[第 27 章](ch27.md)）。
だから、深さ 4 までに見落としがあれば、それは解析器が「同じ範囲を読んだのに見逃した」ものです。
深さ 4 より奥の違反は、解析器がそもそも読んでいない範囲のものです。
2 つは意味が違うので、分けて数えます。

深さ 4 の中にも外にも反する動作があるときは、中のものを主として「見落とし」（または「解析器が不として出している」）にし、外のものは `note` に書きます。
深さ 4 より奥を**探しに行く必要はありません**。
（出典: `docs/drafts/final_judging_guide_draft.md:474-477`）

#### 5 段で読む

**1. 決めた中身**

見落としの判定で読む範囲は深さ 4 まで。偶然それより奥に宣言に反する動作を見つけたら「見落とし（深さ 4 の外）」として別に記録し、主の見落としの数には入れず併記する。

**2. 理由**

D68 の 2 は、理由を 2 つ書いています。

- 普通の見落としに数えると、数が判定者の読んだ深さで変わる。
- 「反する動作は無い」にすると、知っている違反を安全側に倒すことになる（`CLAUDE.md` の規則 4）。

v4 の R04・R05（深さ 7）がこの形でした。
（出典: `docs/decisions.md:3807-3808`）

**3. 退けた案・やらないこと**

- **普通の見落としに数える**: 判定者がどこまで読んだかで数が変わるので、採りません。
- **「反する動作は無い」にする**: 知っている違反を黙って消すことになるので、採りません。
- **やらないこと**: 深さ 4 より奥を探しに行くこと。読む範囲は深さ 4 までです。

**4. 判定や集計でどう効くか**

- **判定（段階 7）**: 見落としの判定（[第 52 章](ch52.md)）で、`outcome` に「見落とし（深さ 4 の外）」を書き、`depth` の欄に見つけた深さを書きます。
- **集計（段階 8）**: 見落としの内訳の表で、「見落とし（深さ 4 の外）」を主の見落としに入れずに別の行で書きます。

**5. 原典**

#### よくある誤解・つまずき

- **誤解: 「深さ 4 の外の違反は、見落としではないので書かなくてよい」**
  書きます。別の欄に記録し、併記します。
- **誤解: 「念のため、深さ 7 くらいまで読んでおけば安心」**

#### この節のまとめ

- 理由は、数が判定者の読んだ深さで変わらないようにするためと、知っている違反を安全側に倒さないため。
- 奥を探しに行く必要はない。

### 46.9 D68 の 3 — 書き込みでない違反のラベル

#### 一言で言うと

D67 の 1 のラベルは「書き込み先の種類」だったので、プロセスの起動やコードの実行（SPAWN・EXEC）の正を入れる場所がありませんでした。

また、D3（`openWorldHint: false`）の正には、書き込み先の種類ではなく「**通信先の種類**」を付けます。

#### たとえ話 — 忘れ物の分類箱

駅の忘れ物センターに、「傘」「かばん」「衣類」「その他」の 4 つの箱があるとします。
財布が届いたら、どこに入れるでしょうか。
「その他」に入れると、財布もハンカチもボールペンも同じ箱に入り、大事な財布が目立たなくなります。
そこで、「貴重品」の箱を足します。
D68 の 3 は、この「貴重品」の箱を足す決定です。

#### 小さな例 — 足したラベルと、D3 の通信先の種類

読み取り専用と宣言したツールが、モデルの決めたコマンドを起動する例（作例）です。

```python
@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def run_check(cmd: str) -> str:
    return subprocess.run(cmd, shell=True, capture_output=True, text=True).stdout
```

- 1 行目: 読み取り専用と宣言しています。
- 2 行目: ツールの関数 `run_check` の引数 `cmd` は、モデルが渡す文字列です。
- 3 行目: `subprocess.run(cmd, shell=True, ...)` は、`cmd` をシェルのコマンドとして起動し、その出力を返します。

モデルはどんなコマンドでも渡せるので、ファイルを消すコマンドも起動できます。
D1 に反するので、到達すれば正です。
このとき、D67 の 1 の 7 種類のどれに入れればよいでしょうか。
ファイルを書いているわけではないので、どの種類にも当てはまらず、「その他・不明」に入るしかありませんでした。
D68 の 3 で足した「プロセスの起動・コードの実行」に入れます。

D3 の正に付ける通信先の種類は、次の 4 つです。

| 通信先の種類 | 定義 | 例 |

| 定数の外部ホスト | コードに書かれた外部のホストと通信する | `requests.get("https://api.example.com/…")` |
| モデルが決める宛先 | 宛先のホストをモデルが決められる | `httpx.get(url)`（`url` はツールの引数） |
| モデルが決めるコード・コマンド | 実行するコード・起動するコマンドをモデルが決められる（通信しうる） | `subprocess.run(cmd, shell=True)` |
| その他・不明 | 上のどれにも当てはまらない、または決められない | 宛先が運用者の設定で、既定値が外部のもの |

（出典: `docs/drafts/final_judging_guide_draft.md:411-420`（16.3））

### 46.11 D70 の 1・2 — 宣言ごとに 3 件、打ち切りのあるユニットも含める

#### 一言で言うと

D70 の 1: 矛の抜き取りの「1 木 3 件まで」は、**宣言ごと**に数えます。同じ木から D1 で 3 件、D2 で 3 件、… を選びます。
D70 の 2: 見落としの抜き取りの対象に、解析器が途中で打ち切った印（`truncated`）のあるユニットも**含めます**。判定で打ち切りが原因と分かったものは「不明（打ち切り）」に分けて数えます。

#### たとえ話 — 科目ごとの抜き打ちテスト

学校で、クラスごとに「1 クラス 3 人まで」抜き打ちテストをするとします。
科目が国語・算数・理科の 3 つあるとき、「科目ごとに 3 人」なら、どのクラスもどの科目でも 3 人ずつテストされます。
「科目をまたいで 3 人」だと、くじの結果、あるクラスでは 3 人とも国語になり、そのクラスの算数と理科の成績が 1 つも分からない、ということが起きます。
科目ごとに成績を報告するなら、科目ごとに選ぶほうが筋が通ります。

打ち切りのほうは、こう考えます。
健康診断で「時間が足りず、途中までしか検査できなかった人」を、結果の集計から外したとします。
すると、検査に時間のかかる、体の大きな人や持病のある人ほど集計から消え、「みんな健康」に見えてしまいます。
だから、途中までしか検査できなかった人も数に入れ、「途中まで」と印を付けて分けておきます。

#### 小さな例 — 宣言ごと と 宣言をまたぐ（作例）

ある木 X で、矛が次のように出たとします（本書の作例）。

| 宣言 | X の矛の組の数 |
|---|---|
| D1 | 5 |
| D2 | 2 |
| D4 | 1 |

- **宣言ごとに 3 件（決定 (a)）**: D1 から 3 件（5 件から seed で選ぶ）、D2 は 2 件しかないので全件の 2 件、D4 は 1 件。X からは合わせて 6 件を判定します。D1・D2・D4 のどれについても、X の判定があります。
- **宣言をまたいで 3 件（退けた (b)）**: 8 件の中から seed で 3 件を選びます。くじの結果、3 件とも D1 になることがありえます。そのとき、X の D2 と D4 は 1 件も判定されません。

### 46.12 D70 の 3 — 判定で LLM（AI）を使わない

#### 一言で言うと

最終評価の判定（矛・見落とし・不の中身）では、LLM（AI）を使いません。
原ソースを読む補助にも、不の組への LLM の対照腕にも、2 人目の判定者の代わりにも使いません。
判定と記録は、すべて学生が行います。
くわしい背景は[第 26 章](ch26.md)で見ました。

#### たとえ話 — 手書きと決めた試験

ある試験で、「電卓も辞書も使わず、自分の頭と手だけで解く」と決めたとします。
答えを書くのはもちろん、「途中の計算だけ電卓で確かめる」のも禁止です。
理由は、この試験で確かめたいのが「本人がどう考えたか」だからです。
途中で道具を使うと、どこまでが本人の考えか分からなくなります。

この研究の最終評価も、「人が原ソースを読んで決めた結果」を示すためのものです。
途中で AI を使うと、どこまでが人の判断か分からなくなります。

#### 小さな例 — 使わない 3 つの使い方

| 使い方 | 決める前の位置づけ | D70 の 3 |
|---|---|---|
| 原ソースを読む補助（行を探す、要約する） | 手順書 0-9 の選択肢「読む補助に使う（判定と記録は本人）」 | 使わない |
| 不の組への LLM の対照腕 | 調査（`docs/llm_judgment_survey.md`）の候補 2。「任意。採るなら条件つき」 | 使わない |
| 2 人目の判定者の代わり | — | 使わない |

（出典: `docs/final_evaluation_procedure.md:241`、`docs/llm_judgment_survey.md:108`、`docs/decisions.md:3849-3850`）

表の読み方: 1 行が 1 つの使い方です。
たとえば 2 行目は「解析器が不と出した組について、LLM にも判定させて、人の判定と並べる別の列を作る案（対照腕）が調査で候補 2 として挙がっていたが、D70 の 3 で使わないと決めた」と読みます。

#### 一歩ずつの説明 — 3 つの使い方を 1 つずつ

**対照腕**という言葉を、先に説明します。
やさしく言うと「比べるための、もう 1 本の列」です。
正確には、同じ対象を別のやり方（ここでは LLM）でも判定させ、主の結果（人の判定）とは混ぜずに、横に並べて比べるための列のことです。
たとえば、不の 100 組のそれぞれについて、人の判定の列の隣に「LLM ならどう答えたか」の列を置く、という形です（調査の §3.1 の候補 2）。

ここから、表の 3 行を順に読みます。

1. **原ソースを読む補助**: 決める前の手順書 0-9 には「使わない」と「原ソースを読む補助に使う（判定と記録は本人）」の 2 つの選択肢がありました。調査は、読む補助にするなら、矛・見落とし・不の中身で使い方を分ける案（たとえば見落としの最初の読みでは使わない）を出していました。D70 の 3 は、このどれも採らず、「使わない」を選びました。
2. **不の組への対照腕**: 調査は「任意。採るなら条件つき」としていました。採るなら、学生が「不明」とした組で LLM が断定した割合（過信の量）、LLM が「反しない」・学生が「違反」とした件数（誤 clear の向き）、繰り返したときに答えが食い違った割合（決定性の量）を、主指標に混ぜずに出す、という案でした。D70 の 3 は、これも採りませんでした。
3. **2 人目の判定者の代わり**: 調査の時点で、すでに「使えない（参考の κ も出さない）」とされていました。同じ系統のモデルどうしでは一致が膨らみ、妥当性の証拠にならないからです。D70 の 3 は、これを改めて書き込みました。

3 つとも「使わない」になったので、最終評価の判定の流れの中に、LLM が入る場所は 1 つもありません。
（出典: `docs/final_evaluation_procedure.md:241`、`docs/llm_judgment_survey.md:106-110`、`:118-126`、`docs/open_questions.md:1250-1257`）

#### なぜ「補助」まで禁じるのか

「判定は人がするのだから、行を探すくらいは手伝わせてもよいのでは」と思うかもしれません。
けれども、読む補助に使うと、「どの行を読むか」を LLM が選ぶことになります。
LLM が見せなかった行を、人は読まないかもしれません。
そうすると、判定の根拠のうち、どこまでが人の読みで、どこからが LLM の選択か、第三者には区別がつきません。
D67 の 4 は、判定者が 1 人であることを、根拠の全件公開で補うと決めていました（46.6 節）。
根拠に LLM の選択が混じると、その補いが弱くなります。
もう 1 つ、本記録者（Claude）が評価データを見ないという約束（D60 の 2、D66 の 3）があります。
repo の文脈を読み込んだ AI を補助に使うと、その約束とぶつかるおそれがありました（O45 の 3）。
「使わない」に決めれば、この問題は起きません。
（出典: `docs/open_questions.md:1259-1263`、`docs/decisions.md:3853-3854`）

### 46.13 D70 の 4・5 — 分母は (a)(c) が主、不明は分母から除いた値が主

#### 一言で言うと

D70 の 4: 「本当の矛が 1 件以上あった木の割合」の分母は、**(a) その宣言の矛が出た木**と **(c) その宣言を明示したユニットを持つ木**の 2 つを主にし、(b) 走査した全部の木を参考にします。どれも**下限**です。
D70 の 5: 判定「不明」は、精度の分母から除いた値（正 / (正 + 誤)）を主にし、不明を誤とみなした値（正 / (正 + 誤 + 不明)）と不明の件数を併記します。

#### たとえ話 — 健康診断の「要再検査」の割合

ある会社で健康診断をし、「要再検査」の人の割合を報告するとします。
分母の取り方は 3 つ考えられます。

- (a) 一次検査で「異常の疑い」と出た人のうち、再検査で本当に異常だった人の割合。一次検査の機械がどれだけ当たるかを表します。
- (b) 社員全員のうち、異常が見つかった人の割合。検査を受けていない部署の人まで分母に入るので、薄まります。
- (c) 検査を申し込んだ人のうち、異常が見つかった人の割合。「申し込んだ人の中で、どれだけ問題があったか」という、知りたいことに一番近い数です。

さらに、再検査を全員にはできず、一部の人だけを再検査したなら、「少なくともこれだけの人に異常があった」という下限になります。
D70 の 4 は、(a) と (c) を主にし、(b) を参考にしました。

#### 小さな例 — 分母 (a)(b)(c) の計算（作例）

ある宣言 d について、次のような数だったとします（**架空の数**です）。

| 記号 | 意味 | 値 |
|---|---|---|
| N | 宣言 d の矛が出た木の総数 | 300 |
| n | 判定した木の数（200 を超えたので 200） | 200 |
| k | 判定した木のうち、正が 1 件以上あった木の数 | 120 |
| M_d | 宣言 d を明示したユニットを 1 つ以上持つ、走査した木の数 | 1,000 |
| 走査した木の数 | — | 3,000 |

```
(a) 主   = k / n             = 120 / 200         = 60.0%
K̂       = (k / n) × N       = 0.6 × 300         = 180 木（推定）
(c) 主   = K̂ / M_d          = 180 / 1,000       = 18.0%
(b) 参考 = K̂ / 走査した木の数 = 180 / 3,000       = 6.0%
```

1 行目は「判定した 200 木のうち 120 木で本当の矛があったので、(a) は 60.0%」です。
2 行目は「判定しなかった 100 木にも同じ割合で本当の矛があると見て、矛の出た 300 木全体では約 180 木と推定する」です。
3 行目は「宣言 d を明示した 1,000 木のうち、約 180 木で本当の矛があった。つまり宣言したサーバのうち、少なくとも約 18%」です。
4 行目は「走査した 3,000 木全体では 6.0%」です。宣言していない木も分母に入るので薄まります。

（式の出典: `docs/drafts/prereg_2_12_draft.md:90-94`、`docs/final_evaluation_procedure.md:1324-1329`。計算のしかたと区間は[第 39 章](ch39.md) 39.3 節）

#### 一歩ずつの説明 — 前の式の誤り

D70 の 4 は、手順書の 23.2 の式を、この推定の形に直しました。
前の式は、判定した木の数をそのまま分子にしていました。
上の作例でいえば、(c) の分子に k = 120 をそのまま使い、120 / 1,000 = 12.0% としていたことになります。
矛の出た木が 300 あるのに、判定した 200 木の分しか数えないので、本当の割合を**小さく見積もる**向きの誤りです。
D70 の 4 は、これを「(b)(c) を大きく小さく見積もる向きの誤りだった」と書いています。
「大きく小さく」は読みにくい言い方ですが、「大幅に小さく」という意味です。
作例では、本当は約 18.0% と推定すべきところを 12.0% としていたので、3 分の 2 に縮んでいます。
縮み方は n / N（作例では 200 / 300）で決まるので、矛の出た木が多い宣言ほど、前の式の誤りは大きくなります。
矛の出た木が 200 以下なら n = N で、K̂ = k になるので、前の式と今の式は同じ値になります。
（出典: `docs/decisions.md:3864-3865`、`docs/final_evaluation_procedure.md:1327`）

#### 不明の扱い（D70 の 5）の作例

ある木で、判定した 10 件が正 6・誤 3・不明 1 だったとします（架空の数）。

```
主  （不明を分母から除く）   = 正 / (正 + 誤)         = 6 / 9  ≒ 66.7%
併記（不明を誤とみなす）     = 正 / (正 + 誤 + 不明)   = 6 / 10 = 60.0%
併記                         不明の件数 = 1
```

不明が多いほど、2 つの値の差が広がります。
片方だけを出すと、読み手はもう片方を疑います。
「不明を除いたから高く見せたのでは」「不明を誤にしたから低く見せたのでは」と。
だから両方を出します。

### 46.14 D70 の 6・7 — 中身の重複を除く、seed は 4 つ

#### 一言で言うと

D70 の 6: v2〜v4 の木と中身が同じ木と、最終評価の中で中身が同じ木を、ツールの定義を含む `.py` ファイルの sha256 で比べて**除きます**。走査の前に当て、補充はしません。
D70 の 7: 乱数の種（seed）は、事前登録を書く日を YYYYMMDD として、**① 矛 YYYYMMDD1・② 見落とし YYYYMMDD2・③ 不の中身 YYYYMMDD3・④ bootstrap YYYYMMDD4** の 4 つを別々に使います。

#### たとえ話 — 同じ答案のコピーと、くじ引きの箱

**重複**: 採点する答案の中に、同じ答案のコピーが 5 枚混ざっていたとします。
そのまま採点すると、1 つの間違いが 5 回数えられ、「間違えた人」が 5 人いるように見えます。
しかも、そのうち 1 枚が、前の年の練習で先生がすでに見た答案だったら、先生は答えを知っていることになります。
だから、中身が同じ答案は 1 枚だけ残し、前に見た答案と同じものは外します。

**seed**: くじ引きを 4 回するとき、4 回とも同じ箱を使って、前の回に引いた紙を戻して混ぜ直さずに引くと、1 回目の結果が 2 回目の結果に影響します。
用途ごとに別の箱（別の seed）を使えば、くじどうしがつながりません。

#### 小さな例 — 重複を除く 5 つの規則

| 規則 | 中身 |
|---|---|
| 1 | 取得した木ごとに、ツールの定義（入口の規則に当たるユニット）を含む `.py` ファイルの sha256 を取る |
| 2 | **v2〜v4 との重複**: そのファイルの 1 つでも、v2〜v4 の木のどれかのファイルと一致した木は除く。v2・v3 の中身は手元に無いので、`docs/corpus_sample_v{2,3,4}.json` の pin から取り直してハッシュだけを残す |
| 3 | **今回の中の重複**: ツールの定義を含むファイルが一致する木どうしは、repo 名（小文字）の辞書順で最初の 1 木だけを残し、残りを除く |
| 4 | 除いた木の数と、どの木と一致したかを記録する。全部を走査する設計（D69）なので、補充はしない |
| 5 | この規則は走査の前（段階 4 の取得後の条件）に当てる。走査の結果を見てから除く木を選ばない |

（出典: `docs/final_evaluation_procedure.md:213-220`）

表の読み方: 1 行が 1 つの規則です。
たとえば 3 行目は「最終評価の中で、ツールの定義を含むファイルが同じ木が 2 つあれば、repo 名を小文字にして辞書の順に並べ、先に来るほうだけを残す。乱数は使わないので、誰がやっても同じ木が残る」と読みます。

sha256 は、ファイルの中身から計算する 64 桁の 16 進数の「指紋」です（[第 22 章](ch22.md)の指紋と同じ考え方）。
中身が 1 文字でも違えば、まったく違う値になります。
だから、sha256 が一致すれば、中身が同じファイルだと見なせます。

seed の 4 つは、次のとおりです。

| 番号 | 値 | 用途 |
|---|---|---|
| ① | YYYYMMDD1 | 矛の抜き取り |
| ② | YYYYMMDD2 | 見落としの抜き取り |
| ③ | YYYYMMDD3 | 不の中身の抜き取り |
| ④ | YYYYMMDD4 | bootstrap |
| （⑤） | YYYYMMDD5 | **【確認】** 判定表の順序の並べ替え（本記録者の提案。未承認） |

（出典: `docs/decisions.md:3873-3875`、`docs/drafts/prereg_2_12_draft.md:44-52`）

表の読み方: 1 行が 1 つの seed です。
たとえば 1 行目は「封をする日が 2026 年 10 月 20 日なら、矛の抜き取りの seed は 202610201」と読みます（日付は例です）。

#### 一歩ずつの説明 — 重複の除去を 3 つの木で追う

架空の 3 つの木で、重複の規則 1〜5 を順に当ててみます（本書の作例）。

| 木（repo 名） | ツールの定義を含む `.py` | そのファイルの sha256（先頭 4 桁だけ） |
|---|---|---|
| `bob/notes-mcp` | `server.py` | `a1b2` |
| `alice/notes-mcp` | `server.py` | `a1b2` |
| `carol/todo-mcp` | `main.py` | `c3d4` |

#### たとえ話 — 期限つきの「あとで決める」

旅行の計画で、「ホテルは来週の金曜までに決める。それまでは空けておく」と決めたとします。

金曜を過ぎてから決めると、計画の他の部分（電車の切符など）をもう買ってしまっているので、「後から決めた」として扱わなければなりません。

#### 一歩ずつの説明 — 2 つの確かめ方の違い

この節には、似た言葉が 2 つ出てきます。

`CLAUDE.md` の規則 4 は、「解決できなかったものは『不明』として記録する。黙って安全側に倒さない」です。
決まっていないものを一覧にしないと、作業の途中で「なんとなく」どちらかに倒してしまいます。
しかも、倒したことに気づかないまま、封をしてしまうかもしれません。
一覧にして、期限と原典を並べておけば、封の前に 1 つずつ片付けられます。

もう 1 つの理由は、事前登録の意味を守るためです。
封の前に決めておけば、どちらに決めても「データを見る前に決めた」ことになります。
封の後、とくにデータを見た後に決めると、「結果を見てから都合のよい方を選んだ」と疑われます（[第 22 章](ch22.md)）。

#### よくある誤解・つまずき

- **誤解: 「未決のものは、判定の途中で決めればよい」**
  途中で決めると、前に判定した件と後の件で基準が変わります。封の前に決めます。決まらない事例が判定の途中で出たら、その件は「不明」にして記録します。
- **誤解: 「本書が挙げた案（D3 は `closed_world` で数える、など）を使えばよい」**
  本書の案は、説明のための例です。決めるのは学生で、決めたら事前登録に書いてから使います。
- **誤解: 「【確認】は本記録者の提案なので、無視してよい」**
  承認するかどうかを決める必要があります。決めずに封をすると、【確認】の印が付いたまま、何が決まったのか分からなくなります。
- **誤解: 「O46 や開示は、判定に関係ないので、一覧に載せなくてよい」**
  判定の規則には効きませんが、論文の書き方に効きます。決まっていないことは、決まっていないと記録しておきます。

#### 手作業ではどう使うか

段階 1（封の前）に、この一覧を 1 行ずつ見て、次のどれかにします。

1. **決めた**: 決めた中身を、事前登録の §2.12 か判定の手引きに書きます。理由は `docs/decisions.md` に、学生の決定として書きます（`CLAUDE.md` の規則 6）。
2. **期限つきで残す**（保留）: 期限と、期限までに決めなかったときの扱いを、事前登録に書きます（(1) のように）。
3. **判定には効かないので、論文を書くときに決める**: (6)・(8) です。一覧に「論文を書くとき」と残しておきます。

#### この節のまとめ

- まだ決まっていないことは 9 つ。(1) 2 人目と判定し直し（保留）、(2) 【確認】2 点、(3) §2.12 と手引きの承認と封、(4) local の範囲、(5) D3・D4 の M_d、(6) O46、(7) CodeQL を補助に使う案、(8) O45 の 4、(9) 抽出のコマンドの書き方。

### 46.17 未決を片付ける順番と、期限を過ぎたときの扱い

#### 一言で言うと

未決の項目は、期限の早い順に片付けます。
**封の前**（段階 1）に (2)(3)(4)(5) と本書の指摘の細部、(7) を採るならその中身、**段階 3 の前**に (9)、**段階 6 の抜き取りのコミットの前**に (1)、**論文を書くとき**に (6)(8) です。
期限を過ぎてから決めたものは、事前登録の §5 に逸脱として書き、事後の分析として扱います。

#### たとえ話 — 試験の前日までに決めること

学校の試験で、「問題用紙の印刷の前に、問題を確定する」「試験の前日までに、採点の分担を決める」「成績表を配るときに、保護者への説明文を書く」と、決める期限がそれぞれ違うことがあります。
問題を印刷の後に変えると、刷り直しになります。
採点の分担を答案を見た後で決めると、「難しい答案を避けた」と疑われます。
期限ごとに片付けるのが、いちばん無理がありません。

たとえば 3 行目は「2 人目の判定者と判定し直しは、遅くとも段階 6 の抜き取りのコミットの前に決めて、事前登録の §2.12 に追記する。抜き取る件数を日程に合わせて減らすなら、それもこのコミットの前に、§5 に逸脱として書いてから減らす」と読みます。

#### 一歩ずつの説明 — 期限を過ぎたときの扱い

期限を過ぎてから決めたものは、どう扱うのでしょうか。
原典は、D70 の 8（保留）について、はっきり書いています。

> 判定や集計の結果を見た後に足すなら、事前登録に逸脱として理由とともに書き、事後の分析として扱う。

（出典: `docs/decisions.md:3881-3882`）

事前登録の §2.12 の下書きも、「それより後に足すなら §5 に逸脱として書き、事後の分析とする」と書いています。
（出典: `docs/drafts/prereg_2_12_draft.md:67-68`）

ほかの項目も、同じ考え方で扱います（本書の整理。[第 22 章](ch22.md)の逸脱と事後の分析の考え方を当てたもの）。

1. **事前登録の §5 に逸脱として書く**: 変更前の定義・変更後の定義・理由・日付・その時点で見ていた数値を書きます（事前登録の §5 の決まり）。
2. **主の結果は、封をしたときの規則で出す**: 期限の後に決めた規則による数は、主の結果にしません。
3. **事後の分析として、主の結果と分けて書く**: 「事前登録していない。結果を見た後に計算した」と明記します。
4. **黙って倒さない**: 期限を過ぎたからといって、どちらかに黙って決めて、事前登録したことのように書くことはしません。

（出典: `docs/preregistration.md:544-545`、`docs/final_evaluation_procedure.md:1381-1384`）

判定の途中で、手引きで決まらない事例に出会ったときも、同じ考え方です。
その件は「不明」にし、`unknown_reason` に「手引きで決まらない: <事例の説明>」と書き、事前登録の §5 に事例を書きます。
手引きを判定の途中で変えません（[第 52 章](ch52.md)）。
（出典: `docs/drafts/final_judging_guide_draft.md:664-672`）

#### なぜ期限があるのか

決める期限は、どれも「その決定が、データや結果に引っぱられない最後の時点」に置かれています。
(1) の期限が「段階 6 の抜き取りのコミットの前」なのは、判定し直しや 2 人目の判定の対象をどう抜くかが、抜き取りと関係するからです。
抜き取りの結果（どの木のどの組が選ばれたか）を見てから決めると、判定しやすい対象を選べてしまいます。
封の前の項目は、判定の規則そのものなので、データに触れる前に決まっていなければなりません。

#### よくある誤解・つまずき

- **誤解: 「期限を過ぎたら、その分析はもうできない」**
  できます。事後の分析として、主の結果と分けて書きます。
- **誤解: 「期限が書いていない項目は、いつ決めてもよい」**
  原典に期限が書いていない項目（(6)・(9) など）も、判定や集計の数に効くものは、効く前に決めるのが安全です。効かないもの（(6)・(8)）は、論文を書くときでかまいません。
- **誤解: 「保留を残したままでは封ができない」**
  下書きは、保留を残したまま、期限と書き足しの条件を書いて封をする形になっています（[第 22 章](ch22.md) 22.8 節）。期限までに決めればよいのです。
