### 32.1 全体像 — D59 で直した 3 つと、足さなかった 1 つ

#### 一言で言うと

凍結の直前に、解析器が値や HTTP の呼び出しを**読み違えていたもの**を 3 種類直しました（O36・O37・追記）。
一方で、仕様書の語彙に**無い** HTTP のメソッドなどは、足さずに件数を数えて限界にしました（O39）。

#### たとえ話 — レシートを読み取る家計簿の機械

レシートを読み取って、家計簿を自動で付ける機械を考えます。
動かしてみると、4 種類の困りごとが見つかりました。

1. 「値引き −500 円」を「500 円」と読んでいた。符号が落ちています。
2. 支払いの欄が「現金」と「カード」の 2 つあるのに、店によって片方しか見ていなかった。
3. 店名が決まった位置ではなく、「店名:」という札の後ろに書いてあると、店名を読めなかった。
4. 機械の「店の種類の一覧」に無い店（たとえば、一覧を作った後に開店した種類の店）のレシートは、読み飛ばしていた。

1〜3 は、機械の**読み取りの誤り**です。
正しい読み方ははっきりしているので、直せばよいだけです。

4 は事情が違います。
「店の種類の一覧」は、家計簿を付け始める前に「この一覧で数える」と決めて固定したものです。
付けている途中で「この店が抜けていた」と一覧を書き足すと、書き足す前と後で数え方が変わってしまいます。
だから一覧は書き足さず、「一覧に無い店のレシートが何枚あったか」を別に数えて記録しておきます。

この章の 4 つは、このたとえの 1〜4 にそれぞれ対応します。
1 が O36、2 が O37、3 が追記、4 が O39 です。

#### なぜそうするのか — 「仕様からのずれを直す」と「語彙を足す」を分ける

4 つのうち 3 つは直し、1 つは足しませんでした。
分かれ目は、**正しい答えが、結果を見る前から決まっていたか**です。

- **O36**: 正しい答えは **Python の意味**で決まります。`not True` は `False` で、`-5` は `-5` です。解析器の作り手が選べることではありません。だから直します。
- **O37 と追記**: 正しい答えは**仕様書**（`AUTHGAP_BRIEF_v3.md`）に書いてありました。229 行目は、HTTP のクライアントの行を「`NET { url ← arg0, body ← data|json }`」と決めています。実装がこれとずれていたので、仕様に合わせます。仕様書の語彙を変えるのではなく、**仕様書どおりに実装する**だけです。
- **O39**: 仕様書の語彙に**載っていません**。足すなら、語彙そのものを変えることになります。語彙は計画の「月 3」に凍結しました（仕様書 841 行目。[第 13 章](ch13.md) 13.12 節）。結果を見た後に語彙を足すと、「的を後から描く」（[第 22 章](ch22.md)）ことになります。だから足しません。

つまり、「直す」と「足さない」の線は、**直す後の姿が事前に決まっていたかどうか**で引かれています。
件数が多いか少ないか、直すと矛が増えるか減るかでは、決めていません。

#### よくある誤解・つまずき

- **誤解: 「O37 も O39 も HTTP の話なのだから、同じように直すべきだった」**
  違います。O37 は「仕様書に書いてあるのに実装していなかった」もの、O39 は「仕様書に書いていない」ものです。前者を直すのは仕様に合わせること、後者を足すのは仕様を変えることです。
- **誤解: 「直したのは誤警報を減らすため」**
  この章の 3 つの直しは、どれも**誤 clear**（見落とし）の向きの誤りを直すものでした。直すと効果が**増える**向きです。誤 clear は、件数が少なく見えるので気づきにくい誤りです（[第 21 章](ch21.md)）。
- **つまずき: 「O36 は 3 つと書いてあるのに、この章では 4 つある」**
  O36 の見出しは「値の欠陥 3 つ（`not` の値・None との合流の順序・片側だけの束縛）」です。D59 の規則を書くときに、3 つ目の「片側だけの束縛」は欠陥ではなく、本当の欠陥は「関数の中の `import`」だと分かりました。さらに同じレビューで、`except` 節の入口の欠陥が見つかり、O36 に含めました。だから D59 の規則では 4 項目になっています（32.3 節）。

（出典: `docs/open_questions.md:1005`（O36 の見出し）、`docs/decisions.md:3305-3317`（D59 の O36 の 3・4））

#### 手作業ではどう使うか

- 最終評価で使う凍結版には、O36・O37・追記の直しが入っています。manifest の `shape` の定数（[第 14 章](ch14.md) 14.7 節）や、効果の `body` の slot は、直した後の意味で読めます。
- O39 の形は今も効果になりません。だから、**解析器の出力に何も無いことを「その送信は無い」と読まない**でください。見落としの判定では、コードを先に読みます（[第 52 章](ch52.md)）。そのとき、HTTP のセッションの `.delete` や `.put` を見つけたら、解析器の出力にそれが無いのは O39 のせいだと分かります。
- 見落としの原因の欄（`cause`）には、「語彙」と書きます（32.8 節）。

#### この節のまとめ

D59 では、値の計算の欠陥（O36）、HTTP の本体の読み方（O37）、宛先の `url=`（追記）の 3 つを直した。どれも誤 clear の向き。
直す後の姿が Python の意味や仕様書で事前に決まっていたものは直し、仕様書の語彙に無いもの（O39）は足さずに限界として数えた。
作業は、規則 → テスト → 実装 → 取り直し → 記録の順で進み、最後に解析器を凍結した。

### 32.2 O36 その 1 — 単項演算の値と、合流の順序

#### 一言で言うと

val エンジンは、`not x` や `-5` の値を、演算をせずに中身のまま（`x` や `5`）にしていました。
また、2 つの値を合流するとき、どちらを先に渡すかで結果が変わることがありました。
どちらも、Python の意味どおりに直しました。

#### 言葉の確認 — 単項演算・合流・可換

- **単項演算**
  - やさしい言い換え: 1 つの値だけに付ける演算。
  - 正確な定義: Python の `not x`（否定）、`-x`（符号を反対に）、`+x`（符号そのまま）、`~x`（ビットの反転）の 4 つ。演算の対象の値を**被演算子**と呼びます。
  - 例: `not True` の結果は `False`。`-5` は、`5` に `-` を付けた単項演算で、結果は `-5`。
- **合流**（[第 14 章](ch14.md)で見た言葉）
  - やさしい言い換え: 2 つの道から来た値を、1 つにまとめること。
  - 正確な定義: `if` の両側や `try` と `except` のように、実行の経路が分かれて再び合わさる所で、それぞれの経路の値を 1 つの値（「どちらかかもしれない」値）にまとめる操作。解析器では `value_join`（値の合流）と `_shape_join`（形の合流）が行います。
  - 例: `if c: x = "a"` / `else: x = "b"` の後の `x` は、「`"a"` か `"b"`」。定数としては 1 つに決まらないので、形は中身の無い `Atom` になります。
- **可換**
  - やさしい言い換え: 順番を入れ替えても、答えが同じこと。
  - 正確な定義: 2 つを合わせる操作 ⊔ について、どんな a・b でも `a ⊔ b` と `b ⊔ a` が等しいこと。
  - 例: 足し算は可換（`2 + 3` と `3 + 2` は同じ 5）。引き算は可換ではない（`2 - 3` と `3 - 2` は違う）。

#### たとえ話 — 「ではない」を書き落とすメモ係

会議のメモ係が、「明日は雨**ではない**」という発言を「明日は雨」とメモしたとします。
「ではない」の 3 文字が落ちただけで、意味は逆になります。
単項演算の欠陥は、これと同じです。
`not True` の `not` を落として `True` と記録すると、真偽が逆になります。

次に、2 人の係が別々に取ったメモを 1 つにまとめる場面を考えます。
A さんのメモには「出席者: 空欄（誰もいなかった）」、B さんのメモには「出席者: 読めない字」とあります。
まとめ役が、先に手に取ったメモの方を正しいとしてしまうと、A さんのメモを先に読めば「誰もいなかった」、B さんのメモを先に読めば「読めない」になります。
まとめる順番で記録が変わるのは、まとめ方がおかしいからです。
合流の順序の欠陥は、これと同じです。

#### 一歩ずつの説明 — 単項演算を直したコード

凍結版の、単項演算の結果の形を決める関数です。

```python
2615  def _unary_shape(op: ast.unaryop, s: Shape) -> Shape:
2616      """単項演算の結果の形（D59、O36）。定数で決まるときだけ定数、ほかは `Atom()`。"""
2617      if isinstance(s, Atom) and s.formal is None:
2618          if isinstance(op, ast.Not):
2619              if s.none:
2620                  return Atom(const=True)

2623          elif isinstance(s.const, (int, float)) and not s.none:
2624              c = s.const
2625              if isinstance(op, ast.USub):

2627              if isinstance(op, ast.UAdd):

2629              if isinstance(op, ast.Invert) and isinstance(c, int):

```

行ごとに見ます。

- 2615 行: 関数 `_unary_shape` を定義します。`op` はどの単項演算か（`not`・`-`・`+`・`~`）、`s` は被演算子の形です。結果として、新しい形を返します。
- 2617 行: 被演算子が `Atom`（1 つの値）で、しかも仮引数そのもの（`formal`）でないときだけ、中身を計算します。仮引数（モデルが渡す値など）は中身が分からないからです。
- 2618〜2620 行: 演算が `not` で、被演算子が `None` なら、結果は定数 `True` です（Python では `not None` は `True`）。
- 2621〜2622 行: 被演算子が真偽・数・文字列の定数なら、Python の `not` をそのまま当てた結果を定数にします（`not "abc"` は `False`、`not 0` は `True`）。
- 2623 行: 演算が `not` 以外（`-`・`+`・`~`）で、被演算子が数の定数なら、次の行で計算します。
- 2625〜2630 行: `-` なら符号を反対に、`+` ならそのまま、`~` なら（整数のときだけ）ビットを反転した定数を返します。
- 2631 行: それ以外（中身が分からない値など）は、中身の無い `Atom()`（「1 つの値だが定数としては読めない」）を返します。

この関数を呼ぶ側（`_ev_UnaryOp`）は、**主体・確度・root は被演算子のものを保ち、属性（`attrs`）は落とす**ようにしています。
主体と root を保つのは、「誰が決めた値か」は演算をしても変わらないからです。
たとえば、モデルが渡した `n` から作った `-n` も、モデルが決めた値です。
属性を落とすのは、「検査済み」などの印（[第 8 章](ch08.md)の付録の話）を、演算で作った別の値に持ち越さないためです。

#### 一歩ずつの説明 — 合流の順序

2 つ目の欠陥は、形の合流（`_shape_join`）にありました。
2 つの `Atom` を「同じもの」とみなす条件が緩すぎたのです。

直す前は、`none`（`None` の定数かどうか）を比べていませんでした。
そのため、`Atom(none)`（`None` の定数）と `Atom()`（中身の分からない値）を同じものとみなし、**先に渡された方**をそのまま返していました。
さらに、Python の `==` は `True == 1` を真とするので、真偽の `True` と数の `1` も同じ定数とみなしていました。

本書の執筆時に、2 つの版の `value_join` に同じ組を順番を変えて渡した結果です。

| 合わせる組 | 直す前（`04cd69b`） | 凍結版 |
|---|---|---|
| `Atom(none)` ⊔ `Atom()` | `Atom(none)`（`None` の定数） | `Atom()` |
| `Atom()` ⊔ `Atom(none)` | `Atom()` | `Atom()` |
| `Atom(const=True)` ⊔ `Atom(const=1)` | `Atom(const=True)` | `Atom()` |
| `Atom(const=1)` ⊔ `Atom(const=True)` | `Atom(const=1)` | `Atom()` |

表の読み方: 1 行目と 2 行目は、同じ 2 つを順番だけ入れ替えて合流したものです。
直す前は、1 行目では「`None` の定数」、2 行目では「中身の分からない値」と、答えが変わっています。
凍結版は、どちらの順でも `Atom()` です。
つまり、直す前の合流は**可換ではなかった**のです。

凍結版のコードは、次のとおりです。

```python
479  def _shape_join(a: Shape, b: Shape) -> Shape:
480      # Atom は `==` より先に見る（dataclass の `==` は `True == 1` を等しいとみなす。D59、O36）。
481      if isinstance(a, Atom) and isinstance(b, Atom):
482          # **none と定数の型も比べる**（D59、O36）。（483 行のコメントの続きは省略）
484          if (
485              a.none == b.none
486              and a.formal == b.formal
487              and type(a.const) is type(b.const)
488              and a.const == b.const
489          ):
490              return a
491          return Atom()
```

- 479 行: 2 つの形 `a` と `b` を合流する関数です。
- 481 行: 両方が `Atom` のときの扱いを、ほかの比べ方より先に書きます。
- 484〜489 行: 4 つ全部が等しいときだけ、「同じ値」とみなします。① `None` の定数かどうか（`none`）、② どの仮引数から来たか（`formal`）、③ 定数の**型**（`True` は真偽、`1` は数なので違う）、④ 定数の値。
- 490 行: 4 つとも等しければ、その値を返します（同じ値どうしの合流は、その値のまま）。
- 491 行: 1 つでも違えば、「どちらかかもしれない」ので、中身の無い `Atom()` を返します。

（出典: `authgap/ir.py:479-491`、`docs/decisions.md:3303-3304`（D59 の O36 の 2）、`tests/test_fix_o36_o37.py:166-185`（順序を入れ替えて同じになることのテスト）。2 つの版の比較は本書の執筆時に行った）

#### なぜそうするのか — 正解は Python の意味で決まり、答えは順序に依らない

1. **正解が決まっている。** `not True` が `False` なのは、Python の決まりです。解析器の作り手の好みで選ぶものではありません。だから「件数がどう動くか」を見ずに直せます。
2. **答えが、コードの意味ではなく書き方に依存してしまう。** 合流の順序は、コードの書き方（`if` と `else` のどちらに書いたか、どの文が先か）で変わります。順序で答えが変わると、`if` と `else` の中身を入れ替えただけの、意味の同じコードに違う答えを出してしまいます。解析の答えは、コードの意味だけで決まるべきです。
3. **`True` と `1` は、意味が違う。** たとえば、`open(path, mode)` のモードや HTTP のメソッドのように、値の**種類**で意味が決まる所では、真偽と数を取り違えると判定を誤ります。

#### 誤りの向き — 定数を誤る誤 clear

D59 は、O36 の 4 つの欠陥の向きを、まとめて次のように書いています。

- 4 つとも、値を**誤って定数にする**誤りです。1 つ目（単項演算）は逆の真偽、2 つ目（合流の順序）と 3 つ目（関数の中の `import`）は `None`、4 つ目（`except` の入口）は古い値になります。
- 誤った定数は、**誤 clear** を生みます。たとえば、受け手が `None` の定数に見えると受け手の型が落ちて効果が消えます。定数に見えると、矛盾の分類（SQL の文の先頭の語、HTTP のメソッドの名前など）が変わります。
- 直すと、効果が**増える**向き（4 つ目）と、定数が `Atom()` に変わって**矛が不になる**向き（2 つ目・3 つ目）がありえます。だから `compare_scans.py`（[第 23 章](ch23.md)）で、両方の向きを 1 件ずつ見ることにしました。

実害が出たのは、[第 30 章](ch30.md)の O31（到達しない枝を刈る直し）でした。
run15 では、`cache_optimized = not raw_results` が `raw_results` と同じ真偽になったり、モデルの値（`extract_mode`）が `if` の後で `None` の定数になったりして、到達する枝が捨てられていました。
run15 の誤 clear は、memory-hub の 22 行と auto_grocer の 1 行の計 23 行で、その原因の一部がこの値の欠陥でした（ほかの原因は、`**kwargs` で渡す引数を既定値の定数とみなしたことなど）。
D58 の改訂で、枝を刈るときは「束縛し直さない仮引数」しか読まないことにしたので、それ以降、O36 の欠陥は枝刈りには効かなくなりました。
それでも、値の表示と、それを読む判定には効きうるので、D59 で直しました。
O36 の記録は、その件数と向きを「**未測定**」と書いています。

（出典: `docs/decisions.md:3319-3322`（D59 の O36 の誤りの向き）、`:3194-3216`（run15 の誤 clear の原因 (B)(C)(D)）、`docs/open_questions.md:1010-1012`（O36 の影響。「向きと件数は未測定」））

#### よくある誤解・つまずき

- **誤解: 「作例で答えが変わらなかったのだから、直す意味は無かった」**
  答えに効くのは、値の定数を読む判定（SQL の先頭の語、HTTP のメソッドなど）と、値で受け手の型を決める所です。それに、人は manifest の `shape` を読んで判断します（[第 19 章](ch19.md)）。表示が逆の真偽になっていれば、人を誤らせます。
- **誤解: 「`{"k": "Atom"}` に `const` が無ければ `None` の定数ではない」**
  [第 14 章](ch14.md)で見たとおり、manifest の JSON は `none` を書き出しません。`None` の定数も `{"k": "Atom"}` に見えます。確度（`prov`）と合わせて読みます。
- **誤解: 「合流で `Atom()` になるのは、解析器が値を見失ったということ」**
  見失った（確度が `opaque`）のではありません。「2 つのうちのどちらか」で、定数としては 1 つに決まらない、という意味です。確度は `resolved` のままでありえます。
- **つまずき: 「入れ子の値（リストの中の値）の合流も直ったのか」**
  直っていません。D59 の結果は、`Seq` などの入れ子の値の等値比較は dataclass の `==`（`True == 1`）のままで、入れ子の中の `Atom` の合流には同じ非可換が残る、と書いています（件数は**未測定**）。凍結後の限界です。

（出典: `docs/decisions.md:3382-3383`（入れ子の値の非可換が残る）、`authgap/ir.py:405-413`（`_shape_json`。`none` を JSON に書かない。[第 14 章](ch14.md)））

#### 手作業ではどう使うか

- **manifest の `shape` の定数を読むとき**（[第 19 章](ch19.md)、手引きの手順 B〜D）: 凍結版では、`not` や `-` の結果は演算した後の値です。直す前の記録（v2 の run16 以前）と見比べるときは、値が違うことがありえると知っておきます。
- **定数を信じすぎない**: 確度が `opaque` なら、`const` があっても確かな定数として使いません（[第 14 章](ch14.md) 14.3 節）。合流で `Atom()` になった値は、「どちらかの値」なので、原ソースで両方の経路を自分で読みます。
- **人が読むときも同じ考え方を使う**: `if` の両側で値が違うときは、両方の値を書き出してから判断します。片方だけを見て「この値だ」と決めると、解析器が直す前にしていたのと同じ誤りをすることになります。

#### この節のまとめ

O36 の 1 つ目は単項演算（`not x`・`-5`）の値を中身のままにしていた欠陥、2 つ目は `None` と定数の型を比べずに合流が順序に依存していた欠陥。
どちらも Python の意味どおりに直し、作例でも直る前と後で `shape` が変わることを確かめた。
向きは誤 clear。O31 の枝刈りで実害が出たが、D58 の改訂で枝刈りには効かなくなった後も、値の表示と判定のために直した。入れ子の値の非可換は限界として残る。

### 32.3 O36 その 2 — 関数の中の `import` と、`except` 節の入口

#### 一言で言うと

val エンジンは、関数の中の `import` の文で名前が決まることを記録していませんでした。
また、`except` 節に入るときの状態を「`try` の前」から始めていて、`try` の中で代入した値を見ていませんでした。
どちらも、実行時には起きる「名前への値の割り当て」を見落とす欠陥で、Python の意味どおりに直しました。

#### 言葉の確認 — 束縛・env・`try` と `except`

- **束縛**
  - やさしい言い換え: 名前に値をひも付けること。
  - 正確な定義: Python で、ある名前がある値を指すようにすること。代入 `x = 1`、`import requests`（名前 `requests` がモジュールを指す）、`for x in ...`、`except E as e` などが、どれも束縛です。
  - 例: `from shlex import quote as q` は、名前 `q` を `shlex.quote` という関数に束縛します。
- **env**（環境）
  - やさしい言い換え: 解析器が持っている「今、どの名前がどの値を指しているか」のメモ帳。
  - 正確な定義: val エンジンが、関数の中を 1 文ずつ読み進めながら更新する、名前から値への対応表。合流のときは、2 つの env を `env_join` でまとめます。
  - 例: `c = httpx.Client()` を読むと、env に「`c` → `httpx.Client` の物」が書き込まれます。この後の `c.post(...)` は、env を見て `c` の型を知り、proxy の sink（[第 13 章](ch13.md)）に結び付けます。
- **`try` と `except`**（[第 9 章](ch09.md)で見た形）
  - やさしい言い換え: 「やってみて、失敗したらこちらを実行する」という書き方。
  - 正確な定義: `try:` の中の文を順に実行し、途中のどこかで例外（エラー）が起きたら、残りを飛ばして、合う `except` 節の中を実行する。
  - 例: `try: import requests` / `except ImportError: requests = None` は、「`requests` が入っていれば使い、入っていなければ `None` にしておく」という、任意の依存の書き方です（CLAUDE.md の落とし穴「条件つき import を落とさない」）。

#### たとえ話 — 書き忘れるメモ係と、途中で失敗した料理

関数の中の `import` の欠陥は、メモ係が「`○○ = …`」という形の発言だけをメモし、「`○○` を持ってきた」という言い方の発言をメモしない、という状態です。
「メモに無い名前は、外（モジュールの一番上）で決まった値を使う」という規則があるので、たいていは困りません。
けれども、「持ってきた。もし持ってこられなかったら空っぽにする」という 2 通りの話をまとめるときに困ります。
「持ってきた」の方はメモに無く、「空っぽにする」の方だけがメモにあるので、まとめると「空っぽ」しか残らないのです。

`except` 節の入口の欠陥は、料理の途中で失敗したときの片付けにたとえられます。
材料を切って、鍋に入れて、火にかける途中で鍋が焦げたとします。
片付けの係が「料理を始める**前**の台所」を思い浮かべて片付けると、鍋が火にかかっていることに気づきません。
本当は、「どこまで進んだところで失敗したか」はいろいろありうるので、「始める前」「材料を切った後」「鍋に入れた後」…のどの状態からでも片付けられるように考える必要があります。

#### 一歩ずつの説明 — 変えなかったこと: 片側だけの束縛

O36 の最初の記録は、3 つ目の欠陥を「片側だけの束縛」としていました。
`env_join` は、片側の経路にしか無い名前を、その側の値のまま残します。
ところが、説明の文（docstring）は「分からない値（`Unknown`）と合流する」と書いていて、実装と食い違っていました。

D59 で考え直した結果、**実装の方が正しく、説明の文が誤っていた**と分かりました。
次の形で考えます。

```python
1  async def one_sided_kept(url: str, flag: bool) -> str:
2      if flag:
3          c = httpx.Client()
4      c.post(url)
```

- 2〜3 行目: `flag` が真のときだけ、`c` を束縛します。
- 4 行目: `c.post(url)` を呼びます。もし `flag` が偽なら、`c` はどこにも束縛されていないので、Python はここで `NameError`（または `UnboundLocalError`）を出して止まります。
- つまり、4 行目に**届く**のは、`flag` が真で `c` がクライアントになった経路だけです。

だから、4 行目の `c` は「クライアント」と読むのが正しいのです。
もし説明の文のとおり「分からない値」と合流すると、`c` の型が落ちて、`c.post` は sink に結び付かず、効果が消えます。
これは誤 clear です。
D59 は、`env_join` の実装を変えず、説明の文を直しました。
そして、本当の欠陥は「実行時には束縛されるのに、エンジンが束縛を記録しない文」、つまり関数の中の `import` だったと書き直しました。
テストにも、この形を「変えない」側の反例として入れています。

#### 実際に効いた所

- **関数の中の `import`**: auto_grocer と napjon で、`try: from m import f` / `except: f = None` の後の `f` が `None` の定数になっていました。run15 では、auto_grocer の `if f and f(url):` の枝が、この誤った `None` のせいで「到達しない」と刈られ、`requests.get` の効果が消えていました（[第 30 章](ch30.md)の誤 clear 23 行のうちの 1 行）。
- **`except` 節の入口**: apk-preview で、`proc = None` / `try: proc = Popen(...)` / `except: proc.kill()` の `proc` が `None` のままになり、`kill` の効果が消えていました。

この形では、直す前の版でも凍結版でも `requests.delete` の効果が出ました。
つまり、関数の中の `import` の欠陥は、いつも効果を消すわけではありません。
記録が挙げている実害は、値を読んで枝を刈る所（D58 の改訂の前の O31）と、値の表示でした。

（出典: `docs/decisions.md:3214-3216`（auto_grocer）、`:3309-3316`（napjon・apk-preview）、作例の走査は本書の執筆時に行った）

#### なぜそうするのか

1. **正解は Python の意味で決まる。** `import` は名前を束縛します。例外は `try` の中のどの文の後でも起きえます。どちらも Python の決まりです。
2. **任意の依存の書き方は、MCP のサーバでよく使われる。** `try: import X` / `except ImportError: X = None` は、ライブラリが入っていなくてもサーバが起動できるようにする定番の書き方です。CLAUDE.md の「よく踏む落とし穴」にも「条件つき import を落とさない」とあります。この形で値を誤ると、同じ誤りが多くの木で繰り返されます。
3. **「分からない」にするのが、いつも安全とは限らない。** 片側だけの束縛の話のとおり、値を「分からない」にすると受け手の型が落ち、効果が消えることがあります。この研究で安全な側とは、「誤 clear を作らない側」です（[第 21 章](ch21.md)）。

#### よくある誤解・つまずき

- **誤解: 「片側の経路でしか束縛されない名前は、『分からない』にするのが慎重なやり方」**
  逆です。もう一方の経路では、その名前を読んだ時点で Python が止まります。届く経路での値は、束縛した側の値だけです。「分からない」にすると受け手の型が落ちて効果が消え、誤 clear になります。
- **誤解: 「`except` 節は、`try` が失敗したときだけ走るのだから、`try` の中の代入は無かったことになる」**
  ならないのです。例外が起きる前に済んだ代入は、そのまま残ります。5 行目の代入が済んだ後に 6 行目で失敗すれば、`except` 節では `client` はクライアントです。
- **つまずき: 「`else` 節や `finally` 節はどうなっているのか」**
  凍結版は、`else` 節と `finally` 節を、`try` の後と各 `except` 節の後を合流した状態から読みます（377〜378 行）。本当は、`else` 節は `try` が無事に終わったときだけ走りますが、合流した状態から読むのは「起きうる状態を広めに取る」近似です。

#### 手作業ではどう使うか

- **到達するかを決めるとき**（[第 49 章](ch49.md)）: `except` 節の中の効果は、`try` の中の**どの文の後でも**起きうると考えて読みます。`try` の中で作ったクライアントやファイルは、`except` 節では「作られた後」のこともあります。
- **任意の依存の形**: `try: import X` / `except ImportError: X = None` の後に `if X is None: return` がある形は、「ライブラリが入っていれば、その後の効果に届く」と読みます。条件つきで届く効果として扱い、条件の種類（[第 49 章](ch49.md)の一覧）を記録します。この形をどの種類に入れるかの明文は、手引きの下書きにはありません。迷ったら `note` に書いておきます。
- **manifest の確度を見るとき**: `try` / `except` で値が 2 通りになる名前は、確度が `opaque` になっていることがあります。その理由（`prov_reasons`）が `unresolved` なら、木の外のライブラリから取り込んだ値が混ざっている、と読めます（[第 14 章](ch14.md) 14.4 節）。

#### この節のまとめ

O36 の 3 つ目は関数の中の `import` が名前を束縛することを記録しなかった欠陥、4 つ目は `except` 節の入口で `try` の中の代入を見なかった欠陥。どちらも、実行時に起きる束縛を見落とす誤 clear で、Python の意味どおりに直した。
「片側だけの束縛はその側の値を残す」は欠陥ではなく正しい実装で、誤っていたのは説明の文だった。
人が読むときも、`except` 節は `try` のどの文の後でも走りうる、と考える。

### 32.4 O37 — HTTP の本体を `data=` と `json=` の両方から読む

#### 一言で言うと

HTTP で送る中身（本体）は、`requests` や `httpx` では `data=` か `json=` のキーワードで渡します。
仕様書は「本体は `data=` か `json=` から読む」と決めていたのに、実装は行ごとに片方しか読んでいませんでした。
仕様どおり、両方から読むように直しました。

#### 言葉の確認 — 本体・キーワード引数・`data=` と `json=`

- **本体**（`body`）
  - やさしい言い換え: HTTP の要求で送る「中身」。手紙でいえば便箋に書く本文。
  - 正確な定義: HTTP の要求のうち、メソッド・URL・ヘッダの後に続くデータの部分（[第 10 章](ch10.md) 10.1 節）。解析器では、NET の効果の slot の 1 つ `body` として記録します。
  - 例: `requests.post(url, json={"text": "こんにちは"})` の `{"text": "こんにちは"}`。
- **キーワード引数**
  - やさしい言い換え: 引数を「名前 = 値」の形で渡すこと。
  - 正確な定義: Python で、関数を呼ぶときに `f(x=1)` のように仮引数の名前を書いて渡す引数。名前を書かずに順番で渡すものを**位置引数**と呼びます（`f(1)`）。
  - 例: `requests.post("https://a.example/x", json=d)` では、`"https://a.example/x"` が位置引数（1 つ目）、`json=d` がキーワード引数です。
- **`data=` と `json=`**
  - やさしい言い換え: 本体の渡し方の 2 種類。`data=` はフォームの形やバイト列、`json=` は Python の辞書を JSON という形式に直して送る。
  - 正確な定義: `requests` と `httpx` の送信の関数・メソッドが受け取るキーワード引数。どちらで渡しても、要求の本体になります。ほかに `content=`（バイト列や文字列をそのまま）と `files=`（ファイルの添付）もありますが、仕様書の語彙には入っていません（32.7 節）。
  - 例: `requests.post(url, data={"q": "x"})` はフォームの形（`q=x`）、`requests.post(url, json={"q": "x"})` は JSON（`{"q": "x"}`）で送ります。

#### たとえ話 — 宅配便の伝票の 2 つの欄

宅配便の伝票に、荷物の中身を書く欄が「品名」と「備考」の 2 つあるとします。
規則では、「中身は品名か備考のどちらかに書いてあるので、両方を見ること」と決まっていました。
ところが、ある受付は品名の欄だけを、別の受付は備考の欄だけを見ていました。
備考の欄に「危険物」と書いた荷物は、品名の欄だけを見る受付を素通りします。

O37 は、この状態でした。
仕様書（規則）は両方を見ると決めていたのに、実装（受付）は行ごとに片方しか見ていなかったのです。

#### 小さな例 — 仕様書の 1 行と、直した sink 表

仕様書の 229 行目は、HTTP のクライアントの行を次のように決めています。

```text
httpx / requests の Client/Session の .get / .post / .request
  → NET { url ← arg0, body ← data|json }（httpx.Client(base_url=b) は { url.base ← b }）
```

- 「`NET`」は、効果の種類（kind）が通信であること（[第 13 章](ch13.md)）。
- 「`url ← arg0`」は、宛先を url の引数から読むこと（32.5 節で、この意味をもう一度見ます）。
- 「`body ← data|json`」は、本体を `data=` か `json=` から読むこと。`|` は「または」の意味です。

直す前の sink 表は、行ごとに次のようになっていました。

| 行（関数・メソッド） | 直す前の `body` | 直した後の `body` |
|---|---|---|
| `requests.post`・`put`・`patch`・`request` | `data=` だけ | `data=` か `json=` |
| `httpx.post` | `json=` だけ | `data=` か `json=` |
| `httpx.request` | 無し | `data=` か `json=` |
| セッションの `.post`（`httpx.Client` など） | `json=` だけ | `data=` か `json=` |
| セッションの `.request` | `data=` だけ | `data=` か `json=` |
| セッションの `.get` | 無し | `data=` か `json=`（仕様書どおり足した） |

表の読み方: 1 行目は「`requests.post` などは、直す前は `data=` で渡した本体しか読まず、`json=` で渡した本体を見落としていた。直した後は、どちらで渡しても本体として読む」と読みます。
同じ「本体」なのに、`requests` は `data=`、`httpx` は `json=` と、行によってばらばらだったことが分かります。

凍結版の sink 表で、この「両方」を表す部分のコードです。

```python
117  def KWS(*kws: str) -> ArgRef:
118      """キーワードの合流（渡された分だけを join する。D59、O37）。"""
119      return ArgRef(kws=tuple(kws))
（120〜121 行は空行）
122  #: HTTP の本体（仕様書 229 行目 `body ← data|json`。`content=` / `files=` は仕様に無いので含めない。O39）。
```

- 117 行: `KWS` は、いくつかのキーワードの名前を受け取り、「そのどれかで渡された値」を表す引数の指定（`ArgRef`）を作る関数です。
- 118 行: 説明の文です。「渡された分だけを合流する」とは、`data=` だけが渡されれば `data=` の値、両方が渡されれば 2 つの値を合流した値（32.2 節）、という意味です。
- 119 行: キーワードの名前の組を持つ `ArgRef` を返します。
- 122 行: コメントです。仕様書の 229 行目に従うこと、`content=`・`files=` は仕様に無いので入れないこと（O39）が書いてあります。

- **誤解: 「本体を読めないと、D1 や D2 の矛が消える」**

- **誤解: 「`content=` も一緒に直った」**

#### 手作業ではどう使うか

- **不の中身の判定**（[第 52 章](ch52.md)）で `net_post` に出会ったとき、本体の slot は、モデルが何を送れるかの手がかりになります。ただし、POST が相手を変えるかどうかは、本体ではなく**相手の API の意味**で決めます（[第 10 章](ch10.md) 10.4 節）。本体の slot があるかないかで、判定を変えないでください。
- **原ソースを読むとき**、送信の行に `json=`・`data=`・`content=`・`files=` のどれが使われているかを見ます。`content=`・`files=` で送る本体は、manifest の `body` には出ていません。

#### この節のまとめ

O37: 仕様書 229 行目は本体を `data|json` から読むと決めていたのに、実装は行ごとに片方しか読んでいなかった。仕様どおり両方から読むように直した（`HTTP_BODY` を 1 か所で決めた）。
D1・D2・D4 の答えは HTTP ではメソッドで決まるので、直しが効くのは主に `body` の slot と付録の `GAP_INJECT`。`content=`・`files=` は仕様に無いので足さなかった（O39）。

### 32.5 追記 — 宛先を `url=` のキーワードでも読む

#### 一言で言うと

`requests.request(method=..., url=..., json=...)` のように、宛先を `url=` のキーワードで渡す書き方では、解析器は宛先を読めていませんでした。
本体も宛先も読めない呼び出しは、効果そのものが出ていませんでした。
O37 と同じ「仕様と実装のずれ」なので、D59 の追記として、位置に無ければ `url=` からも読むように直しました。

#### たとえ話 — 宛名の書き方が違う封筒

郵便の仕分け係が、「宛名は封筒の真ん中に書いてある」と決めて、真ん中だけを読んでいたとします。
ある会社は、封筒の隅に「宛先：○○様」と札を付けて宛名を書いていました。
仕分け係は真ん中に何も無いので、その封筒を「宛名なし」として脇へ置きました。
脇へ置かれた封筒は、配達の記録にも載りません。

解析器の宛先の読み方は、これと同じでした。
「宛先は位置引数の 1 つ目（`.request` なら 2 つ目）」とだけ決めていたので、`url=` という札を付けて渡された宛先を読めなかったのです。

#### 一歩ずつの説明 — 直した規則

追記の規則は、次のとおりです。

- 仕様書 229 行目の「`url ← arg0`」は、「1 つ目の位置引数」ではなく、**url の引数**を指す（`.request` では 2 つ目）。
- `requests` と `httpx` の関数・メソッドの url の仮引数の名前は、どれも `url` である。
- だから、HTTP の行の `url.host` は、**位置に無ければ `url=` のキーワードからも読む**（`A(pos, kw="url")`）。
- HTTP 以外の行は変えない。上の測定で、ほかの種類への影響は無視できる大きさだった（`Popen` 4 件・pipe 1 件は既知の限界として記録する）。

凍結版の sink 表の行は、たとえば次のようになっています。

```python
396      SinkRow("requests.request", "NET", {"url.host": A(1, kw="url"), "body": HTTP_BODY}),
```

- `"requests.request"`: この行が当てはまる関数の名前です。
- `"NET"`: 効果の種類です。
- `"url.host": A(1, kw="url")`: 宛先は、位置の 2 つ目（`A(1)`。数えは 0 から）から読む。そこに無ければ `url=` のキーワードから読む。
- `"body": HTTP_BODY`: 本体は `data=` か `json=` から読む（32.4 節）。

この仕組み（位置に無ければキーワードで読む）は、新しく作ったものではありません。
前に F8 で、`crawler.arun(url=u)` のような呼び出しのために入れていたものを、HTTP の行にも使っただけです。

- **D3 の判定**（[第 50 章](ch50.md)）で宛先を確かめるときは、送信の行（`url=` を含む）だけでなく、クライアントを作った行の `base_url` まで見ます。`**kwargs` で渡されていれば、辞書を作っている所までさかのぼります。
- **見落としの判定**（[第 52 章](ch52.md)）で、送信の行が `**` の辞書の展開で書かれていたら、解析器の出力に効果が無くても不思議ではありません。人が宛先とメソッドを読み、宣言に反するかを決めます。見落としなら、原因の 5 分類のどれに入れるかの例は手引きにありません。「その他」にして、`note` に「`**` の展開で引数を読めない」と書くのが、手引きの書き方（迷ったら説明を書く）に沿います（本書の読み）。

#### この節のまとめ

D59 の追記: 宛先を `url=` のキーワードで渡す書き方を読めず、run17 で宛先の無い通信の効果が 1,693 件あった。全部をキーワードで渡す呼び出しは、run16 では効果そのものが出ていなかった。
位置に無ければ `url=` からも読むようにし、run18 では宛先の無い効果は 6 件（相対の URL で `base_url` を取れない形）になった。
`**` の辞書の展開で渡す形は、今も読めない。

### 32.6 結果 — run16 → run18 と、消えたものの確かめ

#### 一言で言うと

D59 の直しの前（run16）と後（run18）を突き合わせると、効果は 339 件増え、消えた効果・矛・ユニットは 0 でした。
増えた効果は、すべて xagent の、全部をキーワードで渡す HTTP の呼び出しでした。
主指標の D1 + D2 の矛は 151 のままでした。

#### たとえ話 — 棚卸しで、増えた物と減った物を両方数える

倉庫の在庫の数え方を直したとします。
直した後に在庫を数え直したら、合計が増えました。
ここで「数え方を直したら増えた。だから直った」と書くのは早すぎます。
数え方を変えたせいで、前は数えていた物が数えられなくなっていないかも、確かめる必要があるからです。
増えた物と減った物の**両方**を、1 つずつ理由まで確かめて、初めて「直った」と言えます。

この研究の約束も同じです。
CLAUDE.md は、「消えたユニットと消えた CONTRADICTION は回帰なので 1 件ずつ理由を確かめる。増えた側だけ見て『直った』と書かない」と書いています（[第 21 章](ch21.md) 21.7 節、[第 23 章](ch23.md)の段階 ⑤）。

#### 一歩ずつの説明 — 消えたものと、増えたものの確かめ

D59 の結果は、run16 → run18 の突き合わせ（`scripts/compare_scans.py`）を、次のように書いています。

1. **消えた効果 0、消えた CONTRADICTION 0、消えたユニット 0。** 回帰（前は見えていた物が見えなくなる）は 1 つもありませんでした。
2. **増えた効果 339 件は、すべて xagent の `requests.request` と `httpx.AsyncClient.request`。** 全部をキーワードで渡す呼び出しが、`json=` と `url=` を読めるようになって効果になったものです。原ソースで確かめています（`slack.py:241` ほか。32.5 節で見た行）。

けれども、[第 14 章](ch14.md)で見たとおり、深さの上限で降りなかった関数の戻り値は、「主体 `OP`・確度 `opaque(depth)`・root は残す」という形で返す設計です。
今回は、その形の値が `url.path` に入る呼び出しが、宛先を読めるようになって新しく効果になったので、件数が 4 増えました。
だから、直しが新しい誤りを生んだのではない、と確かめられたのです。

#### 一歩ずつの説明 — 矛の数が変わらなかったこと

効果が 339 件も増えたのに、矛の組の数（189）と D1 + D2 の矛（151）は変わりませんでした。
変わったのは、D2 の不（107 → 108）と D4 の不（71 → 72）が 1 件ずつ増えたことだけです。
つまり、増えた効果の大半は、宣言への矛を生む形ではなかったことになります。
なぜそうなったかの内訳は、記録には書かれていません。

ここで大事なのは、「矛が増えなかったのだから、直しは効いていない」とは読まないことです。
この章の直しは、効果・slot・`GAP_INJECT` を正しく数えるためのもので、矛を増やすことが目的ではありません。
矛の数は、その結果として、たまたま動かなかっただけです。

#### なぜそうするのか

1. **誤 clear の直しでも、消えたものは確かめる。** 「見落としを減らす直しなのだから、消えるものは無いはず」と思い込むと、思わぬ回帰に気づきません。実際に、前の直し（[第 29 章](ch29.md)の O30）では、消えたものを確かめたことで、別の誤り（O34）が見つかりました。
2. **増えたものも、理由まで確かめる。** 増えた効果が「本当にある送信」か「解析器の新しい読み違い」かは、原ソースを見ないと分かりません。D59 は、増えた 339 件を原ソースで確かめています。
3. **変更の前と後の両方の数を記録する。** 事前登録（`docs/preregistration.md`）の逸脱の表には、変更前（run16）と変更後（run18）の両方の値を並べて書きました（逸脱 #22）。後から「どの版の数か」が分かるようにするためです（[第 22 章](ch22.md)）。

#### よくある誤解・つまずき

- **誤解: 「効果が 339 件増えたので、見落としが 339 件減った」**
  効果の数は、見落としの数ではありません。増えた効果の中には、宣言の無いツールのものや、宣言に反しない動作のものも含まれます。見落としは、宣言に反する動作を解析器が何も出さなかったものだけを指します（[第 52 章](ch52.md)）。
- **誤解: 「`GAP_INJECT` が増えたのは悪くなったということ」**
  `GAP_INJECT` は付録の判定で、「検査されていないモデルの値が危険な位置に入る」座標の数です。読めていなかった本体や宛先を読めるようになって増えたので、数え漏れが減った向きです。
- **つまずき: 「run17 の D1 + D2 の矛が `—` なのはなぜか」**
  run17 は中間の記録で、D59 の結果の表は run17 の宣言ごとの数を載せていません。D59 の結果は「run17（追記の前）は中間の記録」と書いています。

#### 手作業ではどう使うか

- 最終評価では、解析器を直さないので、このような取り直しはしません（[第 23 章](ch23.md) 23.9 節）。けれども、**数字を読むときに、どの版・どの run の数かを確かめる習慣**は同じです。この章の数（run18）は `analyzer-freeze-1` の版の数で、最終評価で使う `analyzer-freeze-3` の版の数（run24。[第 36 章](ch36.md)）とは違います。
- v2〜v4 の数を最終評価の数と並べて「改善」「悪化」と書かないのも、版とデータが違うからです（手順書 24.3）。

#### この節のまとめ

run16 → run18 で効果は 7,915 → 8,254（+339）。消えた効果・CONTRADICTION・ユニットは 0。増えた 339 件はすべて xagent の全部をキーワードで渡す HTTP の呼び出しで、原ソースで確かめた。
矛の組（189）と D1 + D2 の矛（151）は変わらず、D2 と D4 の不が 1 件ずつ増えた。`GAP_INJECT` は 1,705 → 2,290、宛先の無い NET の効果は 1,693（run17）→ 6。
増えた側だけでなく消えた側も 1 件ずつ確かめるのが、この研究の約束。

### 32.7 O39 — 語彙を足さなかったもの

#### 一言で言うと

HTTP のセッション（`httpx.Client`・`httpx.AsyncClient`・`requests.Session`）の `.put`・`.patch`・`.delete`・`.head`・`.options` と、`httpx.put` などのモジュールの関数、本体の `content=`・`files=` は、仕様書の sink の語彙に入っていません。
これらは足さず、件数を構文で数えて、既知の限界として記録しました（O39）。
そのため、**セッションで送る DELETE は効果にならず、D2 の矛は少なめに出ます**。

#### 言葉の確認 — 語彙・凍結・上限

- **語彙**（[第 13 章](ch13.md) 13.12 節で見た言葉）
  - やさしい言い換え: 解析器が知っている言葉の一覧。一覧に無い言葉は、解析器には見えない。
  - 正確な定義: sink 表（直接・proxy・pipe）、slot の種類、副 kind など、仕様書が計画の「月 3」に凍結すると決めたもの（仕様書 841 行目）。
  - 例: `requests.delete` は sink 表の直接の sink の行にあるので語彙に入っています。`requests.Session` の `.delete` は proxy の sink の行に無いので、語彙に入っていません。
- **凍結**（[第 22 章](ch22.md)）
  - やさしい言い換え: 「この版から変えない」と決めて、印を付けること。
  - 正確な定義: 決めたものを後から変えないと約束し、記録とタグで固定すること。変えるなら、事前登録に逸脱として記録する。
  - 例: sink の語彙は月 3 に凍結。解析器全体は、この章の直後に `analyzer-freeze-1` で凍結（[第 33 章](ch33.md)）。
- **上限**（ここでの意味）
  - やさしい言い換え: 「多くてもこれくらい」という数。本当の数はこれ以下。
  - 正確な定義: 数え方が「当てはまるかもしれないものを全部数える」形になっているときの数。当てはまらない物も混ざりうるので、本当の数はこの数以下になる。
  - 例: 「`httpx` か `requests` を取り込むファイルの中の、`○○.delete(...)` の呼び出し」を数えると、`○○` が HTTP のセッションでない物（たとえばキャッシュの `.delete`）も数えてしまう。だから上限です。

#### たとえ話 — 図鑑に無い鳥

野鳥の数を数える調査で、「この図鑑に載っている鳥だけを数える」と、調査を始める前に決めたとします。
調査の途中で、図鑑に載っていない鳥を何度も見かけました。
ここで図鑑に書き足して数え始めると、書き足す前と後で、数えている物が変わってしまいます。
「この鳥が多いから足そう」と、見た結果で決めることにもなります。

そこで、図鑑は書き足しません。
代わりに、「図鑑に無い鳥を、どの場所で何回見かけたか」を別の表に記録しておきます。
報告書には、「この調査の数には、図鑑に無い鳥は入っていない。別に数えると、多くてもこれくらい見かけた」と書きます。

O39 は、この扱いです。
図鑑が sink の語彙、図鑑に無い鳥がセッションの `.delete` などです。

#### 小さな例 — 作例で、何が効果になり、何がならないか

本書の執筆時に、凍結版で次のツールを走らせました（どれも宛先は `https://api.example.com/items/` ＋ モデルが渡す `item_id`）。

| ツール | 送信の書き方 | 宣言 | 効果 | 解析器の答え |
|---|---|---|---|---|
| `delete_module_fn` | `requests.delete(url)` | D1 | **あり**（DELETE） | 矛（`net_modify`） |
| `delete_by_request` | `requests.request(method="DELETE", url=url)` | D1 | **あり**（DELETE） | 矛（`net_modify`） |
| `delete_session` | `s = requests.Session()` → `s.delete(url)` | D1 | **なし** | （何も出ない） |
| `delete_httpx_client` | `client = httpx.Client()` → `client.delete(url)` | D1 | **なし** | （何も出ない） |
| `delete_httpx_fn` | `httpx.delete(url)` | D1 | **なし** | （何も出ない） |
| `d2_delete_module_fn` | `requests.delete(url)` | D2 | **あり**（DELETE） | 矛（`net_modify`） |
| `d2_delete_session` | `s = requests.Session()` → `s.delete(url)` | D2 | **なし** | （何も出ない） |
| `post_content` | `requests.post(url, content=note)` | D1 | **あり**（POST）。`body` の slot は無い | 不（`net_post`） |

表の読み方: 1 行目と 3 行目を比べてください。
どちらも「読み取り専用」と宣言したツールが DELETE を送っています。
ところが、モジュールの関数 `requests.delete` で送る 1 行目は矛になり、セッションの `.delete` で送る 3 行目は何も出ません。
送っている物は同じなのに、**書き方で解析器の答えが変わる**のが、O39 の限界です。

表の「宣言」の列の D2 は、`readOnlyHint=False, destructiveHint=False`（読み取り専用ではないが、破壊しない）と書いたツールです。
`destructiveHint` は `readOnlyHint` が偽のときにだけ意味を持ち、解析器も `readOnlyHint: true` のツールには D2 を当てないので（第 4・16 章）、D2 を試すツールは `readOnlyHint=False` にしてあります。

最後の行の `post_content` は、効果は出ています。
`content=` は本体として読みませんが、宛先は読めるので slot があり、効果になるのです。
POST なので答えは不で、`content=` を読まないことは答えには効いていません（32.4 節）。

#### 一歩ずつの説明 — 語彙に入っているもの、いないもの

ここで、よくある誤解を先に解いておきます。
O39 の記録は「`DELETE` は D2 の矛盾の典型なので、D2 の矛は下限になる」と書いています。
けれども、**DELETE がすべて見えないわけではありません**。
`requests.delete(url)` や `requests.request("DELETE", url)` は見えます。
見えないのは、セッションのメソッドと `httpx` のモジュールの関数で送る DELETE です。

#### 一歩ずつの説明 — どれくらいあるかを数えた（`docs/o39_count.json`）

D59 は、O39 の形が「どれくらいあるか」を、凍結の前に構文で数えると決めました。
数えたのは `scripts/o39_count.py` で、結果は `docs/o39_count.json` にあります。

数え方（手続きと分母）は次のとおりです。

- **対象**: run16 で走査した母集団 v2 の木（87 木）。テストのファイルは除く。ソースは `ast.parse` にバイト列で渡す（CLAUDE.md の落とし穴「ソースは `ast.parse` にバイト列で渡す」）。
- **(a) モジュールの関数**: `httpx.put|patch|delete|head|options(...)` と `requests.options(...)`。
- **(b) セッションのメソッドの上限**: `httpx` か `requests` を取り込むファイルの中の、`<式>.put|patch|delete|head|options(...)` の呼び出し。**受け手の型は確かめない**。
- **(c) 本体の引数の上限**: (a)(b) と sink 表にある HTTP の呼び出しの形で、キーワード `content=` か `files=` を持つもの。
- **分母**: 木の数（87）と、(a)〜(c) が 1 件以上ある木の数を併記する。

結果です。

| 数えたもの | 呼び出し箇所 | 1 件以上ある木 |
|---|---|---|
| (a) モジュールの関数 | 0 | 0 |
| (b) セッションのメソッド（上限） | **150**（`delete` 66、`head` 46、`put` 21、`patch` 17） | 12 |
| (c) 本体の `content=`・`files=`（上限） | **143** | 12 |

表の読み方: 2 行目は「`httpx` か `requests` を取り込むファイルで、`○○.delete(...)` などの形の呼び出しが 150 か所あった。そのうち `delete` が 66 か所。受け手の型は確かめていないので、150 は上限で、本当のセッションの送信はこれ以下。こうした呼び出しが 1 か所以上ある木は 87 木のうち 12 木」と読みます。

偏りもあります。
(b) の 150 のうち 93 は 1 つの木（meta-skill-evloving）、(c) の 143 のうち 79 は mcparmory でした。
件数を木の数で読むことの大切さは、第 37・39 章で詳しく見ます。

この数は、**効果の件数でも、宣言違反の件数でもありません**。
宣言の無いツールの中の呼び出しも、宣言に反しない呼び出し（`head` は安全なメソッド）も含まれます。
「O39 の形が、どれくらいの規模でありうるか」の目安です。

（出典: `docs/o39_count.json`、`scripts/o39_count.py:1-16`（手続きと分母の説明）、`docs/decisions.md:3380-3382`（「構文で数えた上限: 呼び出し箇所 150 と 143」））

#### なぜ足さないのか

1. **語彙は月 3 に凍結した。** 仕様書は、sink の語彙を計画の月 3 に凍結すると決めています（841 行目）。
2. **足すと、結果を見た後に語彙を変えることになる。** O39 に気づいたのは、v2 の走査の結果を調べている最中でした。ここで足すのは、[第 22 章](ch22.md)の「的を後から描く」と同じ形です。
3. **足さなくても、限界として正直に報告できる。** 件数を数えて記録しておけば、読み手は「この抜けがどれくらい効きうるか」を自分で判断できます。

O39 の記録は、「要る判断: 無し（限界として件数を併記する）」と書いています。
そのうえで、「学生が語彙の拡張を決めたら、逸脱として記録し v3 で拡張前後を併記する」という道も書き残しています。
学生は、この拡張を決めていません。
その後、解析器は `analyzer-freeze-3` で最終凍結され（[第 36 章](ch36.md)）、D71 でも「解析器は凍結のまま変えない」と追認されました。
だから、最終評価でも O39 の形は効果になりません。

（出典: `docs/open_questions.md:1047-1049`（O39 の「なぜ直さないか」「要る判断」）、`docs/decisions.md:3900`（D71: 解析器は凍結のまま））

#### 「下限」という言葉の読み方

O39 の記録は、「D2 の矛は下限になる（誤 clear の向き）」と書いています。
この「下限」は、正確には次の意味です。

- O39 の抜けは、本当はある DELETE などの送信を数えない向き、つまり矛を**少なく**数える向きの誤りです。
- だから、**この抜けについては**、解析器の数は本当の数より少なめに出ます。

一方で、解析器の矛には、誤警報（本当は違反でないのに矛にしたもの。[第 21 章](ch21.md)）もまざります。
だから、「解析器の D2 の矛の数は、どんな意味でも本当の違反の数以下」とまでは言えません。
「下限」は、「O39 の抜けの向きは、少なく見せる向き」と読みます。

同じ理屈は D1 にも当てはまります。
D1 では PUT・PATCH・DELETE が矛なので（[第 10 章](ch10.md) 10.3 節）、セッションで送るこれらが見えなければ、D1 の矛も少なめに出ます。
O39 の記録が D2 を挙げているのは、DELETE が「破壊しない」という D2 の宣言に反する**典型**だからです。

#### よくある誤解・つまずき

- **誤解: 「DELETE は効果にならない」**
  なります。`requests.delete(url)` と `requests.request("DELETE", url)`（キーワードでも）は効果になり、D1・D2 の矛が出ます。ならないのは、セッションのメソッドと `httpx` のモジュールの関数の DELETE です。
- **誤解: 「150 件の見落としがある」**
  150 は、受け手の型を確かめずに数えた呼び出し箇所の上限です。宣言の無いツールの中の呼び出しや、HTTP でない物の `.delete` も含みえます。見落としの件数ではありません。
- **誤解: 「`head` や `options` も抜けているので、D1 の矛が減る」**
  `HEAD`・`OPTIONS` は安全なメソッドで、D1・D2・D4 では内です（[第 10 章](ch10.md)）。見えなくても、この 3 つの答えは変わりません。効くのは、宛先で決まる D3（外と関わらない）の方です。
- **つまずき: 「直せば済むのに、なぜ直さないのか」**
  直し方は簡単でも、直すこと自体が「結果を見た後に語彙を変える」ことになるからです。凍結の約束は、「正しいか」ではなく「変えない」ことの約束です（[第 13 章](ch13.md) 13.12 節、[第 22 章](ch22.md)）。

#### 手作業ではどう使うか

- **見落としの判定**（[第 52 章](ch52.md)）で、HTTP のセッションの `.put`・`.patch`・`.delete` を見つけたら、その送信が宣言に反するかを決めます（D1 なら PUT・PATCH・DELETE は反する、D2 なら PATCH・DELETE は反する、PUT は宛先しだい。手引きの下書きの 15.1・15.2 節、[第 50 章](ch50.md)）。反するのに解析器が何も出していなければ「見落とし」で、原因は「語彙」です。書き込み先の種類（[第 51 章](ch51.md)）は「相手側の状態」です。
- 手引きの下書きの見落としの手順は、木の外のライブラリの中は読まないが、「ライブラリの関数そのものが環境を変えるもの（`requests.put` など）は、呼んでいれば違反の候補として数える」と書いています。セッションの `.delete` は、まさにこれに当たります。
- 論文の限界の節には、O39 の件数（上限 150 と 143）を書きます。

（出典: `docs/drafts/final_judging_guide_draft.md:451-453`（18.2 の 2）、`:465-467`（18.2 の 6）、`:382-395`（16.1 の書き込み先の種類））

#### この節のまとめ

O39: セッションの `.put`・`.patch`・`.delete`・`.head`・`.options`、`httpx` のモジュールの関数、本体の `content=`・`files=` は仕様書の語彙に無いので、足さずに限界とした。月 3 の凍結を、結果を見た後に変えないため。
構文で数えた上限は、呼び出し箇所 150（セッションのメソッド。うち `delete` 66）と 143（本体の引数）。効果や違反の件数ではない。
この抜けは矛を少なく数える向きで、記録は「D2 の矛は下限」と書く。見落としの判定でこの形に出会ったら、原因を「語彙」とする。

### 32.8 見落としの原因「語彙」— O39・R19・`wave.open`

#### 一言で言うと

解析器の語彙（sink 表）に無いライブラリの呼び出しは、効果になりません。
だから、それが宣言に反する動作でも、解析器は矛も不も出しません。
最終評価の見落としの判定で、この形に出会ったら、見落としの原因を「**語彙**」と記録します。
O39 のセッションの `.delete`、v4 の R19（loguru の `logger.add` で設定したログファイルへの書き込み）、`wave.open(..., 'wb')` が、その典型です。
v3 の見落とし 7 件のうちの 1 件（zvec というライブラリの `upsert`）も、同じ「語彙」の類でした（v3 の判定も本記録者が行ったもの。[第 34 章](ch34.md)）。

（出典: `docs/population_v3.md:91-92`）

#### 言葉の確認 — 見落とし・見落としの原因

- **見落とし**（[第 21 章](ch21.md)で見た誤 clear の、判定での呼び名）
  - やさしい言い換え: 本当は宣言に反する動作があるのに、解析器が何も言わなかったもの。
  - 正確な定義: 最終評価の見落としの判定（D1 か D2 を明示し、その宣言への矛が 1 件も出ていないツールを人が読む作業）で、人が見つけた宣言に反する動作に、解析器が矛も不も出していないもの（手引きの下書き 18.2 節）。
  - 例: 「読み取り専用」と宣言したツールが、セッションの `.delete` で相手の資源を消すのに、解析器が何も出していない。
- **見落としの原因**
  - やさしい言い換え: 解析器が、なぜそれを見落としたのか。
  - 正確な定義: 見落としの記録の `cause` の欄に書く、次の 5 つのどれか。**深さ**（深さ 4 を超える所にある）/ **呼び出しの解決**（呼び出し先を解決できていない）/ **受け手の型**（受け手の型が分からない）/ **語彙**（sink の語彙に無いライブラリ）/ **その他**（デコレータの wrapper の中など）。
  - 例: R19（loguru のログファイル）は「語彙」、v4 の R04（深さ 7 の OAuth のトークンの保存）は「深さ」。

（出典: `docs/drafts/final_judging_guide_draft.md:441-446`（18.1）、`:458-467`（18.2 の 5・6）、`docs/final_evaluation_procedure.md:1138-1140`、`docs/drafts/prereg_2_12_draft.md:109`）

#### たとえ話 — 外国語の看板

外国の町で、自分の知っている単語だけを頼りに「危険」の看板を探しているとします。
知っている単語の看板は見つけられます。
けれども、知らない単語で書かれた「危険」の看板は、目に入っても危険だと分かりません。
これは、目が悪い（深さ）のでも、道に迷った（呼び出しの解決）のでもありません。
**単語を知らない**（語彙）のです。

見落としの原因を分けるのは、直し方や限界の書き方が原因ごとに違うからです。
「語彙」の見落としは、解析器の単語帳（sink 表）に単語を足せば見えるようになりますが、単語帳は凍結しているので足しません。
だから、論文には「語彙の限界でこれだけ見落とした」と書くことになります。

#### 小さな例 1 — v4 の R19（loguru のログファイル）

v4（[第 37 章](ch37.md)で見る中間検証。判定は本記録者（AI）が行い、数字は論文に使わない）で、見落としの抜き取り 30 件のうち 4 件が見落としでした。
その 1 件が R19 です。
mcp-aws の `get_execution_plan` という、`readOnlyHint=True`（D1）と宣言したツールです。

モジュールの一番上（`server.py` の 66〜72 行）に、次の設定があります（本書の執筆時に原ソースで確かめた行）。

```python
66  logger.remove()
67  logger.add(sys.stderr, level=FASTMCP_LOG_LEVEL)
68
69  log_dir = Path.home() / '.aws' / 'aws-api-mcp'
70  log_dir.mkdir(parents=True, exist_ok=True)
71  log_file = log_dir / 'aws-api-mcp-server.log'
72  logger.add(log_file, rotation='10 MB', retention='7 days')
```

- 66 行: loguru（Python のログのライブラリの 1 つ）の `logger` から、最初から付いている出力先を外します。
- 67 行: 出力先に標準エラー（画面に出す先。ファイルではない）を足します。
- 69 行: ホームのディレクトリの下の `.aws/aws-api-mcp` というディレクトリのパスを作ります。
- 70 行: そのディレクトリを作ります（`exist_ok=True` は、すでにあっても失敗しない指定）。これはモジュールを読み込むとき、つまりサーバの起動時に 1 回だけ走ります。
- 71 行: ログファイルのパス `aws-api-mcp-server.log` を作ります。
- 72 行: **出力先にログファイルを足します。** `rotation='10 MB'` は 10 MB を超えたら新しいファイルに切り替える、`retention='7 days'` は 7 日より古いファイルを消す、という指定です。

ツールの本体は、成功すると `logger.info(...)`、見つからないと `logger.error(...)` を呼びます。
72 行の設定があるので、**呼ぶたびにログファイルに 1 行追記されます**。
これは、D1（環境を変えない）に反するファイルの書き込みです。

ところが、解析器の語彙には loguru がありません（`logging` の `FileHandler` もありません）。
だから、このツールには効果が 1 つも出ていませんでした（v4 の判定の記録の `n_effects` は 0）。
v4 の判定は、これを「見落とし」、原因を「語彙」としました。

#### 一歩ずつの説明 — R19 は「ログでも違反か」の問題も含んでいた

v4 の判定の記録には、R19 について次の注記があります。

- 反する動作は、ログファイルへの追記だけ。
- 採った原理（§7.1 の「FS_WRITE はすべて矛」）と、当時の重大度の定義に従って見落としとした。
- けれども、**ログの出力の枠組みの書き込みを、宣言違反に数えるかは、原理で明示されていない**。本記録者が数えないと決めたら、「反する動作は無い」になる。

この問いは、その後、学生の決定 D67 の 1 で片付きました（[第 43 章](ch43.md)）。

- 重みは付けない。判定は、採った原理を字義どおりに当てる。
- そのうえで、正（と見落とし）には、「書き込み先の種類」を事実のラベルとして付ける。ラベルの 1 つが「**ログ**」。

手引きの下書きも、「読み取り専用のツールがログファイルに 1 行追記するのは、採った原理では違反である。軽重は書き込み先の種類のラベルで表し、判定の正誤には持ち込まない」と書いています。
そして、判定の考え方の例（手引き 20.2 節）に、R19 を「**見落とし（語彙）**」として載せています。

ここで注意が 1 つあります。
v4 の判定は本記録者（AI）が行ったもので、手引きの下書きは「考え方の例で、最終評価の判定の正解ではない」と書いています。
最終評価では、学生が自分で読み、自分で決めます（D70 の 3。AI は使わない）。

#### 小さな例 2 — `wave.open(..., 'wb')`

もう 1 つの実例は、v4 の audio-transcriber の `transcribe_audio`（`destructiveHint=False`、D2）です。
録音の経路で、次の関数が呼ばれます（本書の執筆時に原ソースで確かめた行）。

```python
352      def save_stream(self) -> None:
353          """Save the recorded frames to a WAV file."""
354          if not self.frames:
355              self.logger.warning("No audio frames to save.")
356              return
357          with wave.open(str(self.file_path), "wb") as wave_file:
358              wave_file.setnchannels(self.channels)
（359〜362 行: 形式を設定し、録音したデータを書き込む）
```

- 352 行: 録音したデータを WAV のファイルに保存するメソッドです。
- 354〜356 行: 録音したデータが無ければ、警告を出して何もせずに戻ります。
- 357 行: `wave.open(パス, "wb")` は、Python に元から入っている `wave` モジュールで、音声のファイルを書き込み用に開きます。`"wb"` は「書き込み・バイナリ」で、`open(path, "wb")` と同じく、**同じ名前のファイルがあれば中身を消して書き直します**（[第 9 章](ch09.md) 9.3 節）。パス（`self.file_path`）は、モデルが渡す引数 `directory` などから作られます。

D2（前からあるものを壊さない）では、「書き先をモデルが決められる書き出し」は反します（モデルは既存のファイルを指して上書きさせられるから。手引きの下書きの 15.2 節）。
ところが、`wave.open` は解析器の語彙にありません。
だから、この書き込みは効果になりませんでした。

ただし、このツールは、別の書き込み（`export` の `open(export_path, 'w')`）に対して、解析器がすでに不（`fs_writeout_model_path_opaque`）を出していました。
v4 の判定は、ツール全体の結果を「解析器が不として出している」とし、`wave.open` の方は「語彙の部分的な見落とし」として `note` に書きました。
O43 の表にも、「sink 語彙に無い `wave.open(..., "wb")`（同じユニットの別の書き込みで不は出ている）」として、向き「部分的な見落とし」で載っています。

（出典: `evidence/population_v4/v4_judgments.json`（`id` が R13 の項目）、`docs/open_questions.md:1197`（O43 の `wave.open` の行）、`corpus/v4-knuckles-team__audio-transcriber/audio_transcriber/audio_transcriber.py:352-362`（本書の執筆時に読んだ）、`docs/drafts/final_judging_guide_draft.md:333`（15.2 の書き出しの行））

#### 一歩ずつの説明 — 原因の 5 分類の中で、「語彙」をどう見分けるか

見落としを見つけたら、原因を 5 つのどれかに決めます。
似た見た目の見落としでも、原因は違うことがあります。
次の表で比べます（例はすべて作り話。どれも、宣言に反する動作に解析器が何も出していない、とします）。

| 原因 | 何が起きているか | 例 | 見分け方 |
|---|---|---|---|
| **深さ** | 動作が、本体から深さ 4 を超える所にある | 本体 → a → b → c → d → e の e の中の `os.remove` | 本体を深さ 0 として数え、動作が深さ 5 以上にある（[第 15 章](ch15.md)） |
| **呼び出しの解決** | 呼び出し先の関数を、解析器が決められていない | `handler = HANDLERS[name]` → `handler(path)` の先の書き込み | 呼び出し先が表や変数から選ばれる。manifest の `opaque` の理由に `receiver` や `unresolved` |
| **受け手の型** | sink 表にあるメソッドなのに、受け手の型が分からず結び付かない | `self._client.post(url)` で、`self._client` が何で作られたか解析器に分からない | メソッドの名前は sink 表にある（`.post` は語彙にある）。受け手を作った行が、別のモジュールの水準などにある |
| **語彙** | ライブラリの関数・メソッドが、そもそも sink 表に無い | `httpx.Client()` の `.delete`、loguru の `logger.add(パス)`、`wave.open(p, "wb")` | sink 表（`authgap/catalog/sinks.py`）を grep しても、その関数・メソッドの行が無い |
| **その他** | 上のどれでもない | デコレータの wrapper の中の動作、`**` の辞書の展開で渡す送信 | 説明を `note` に書く |

表の読み方: 3 行目と 4 行目を比べてください。
`self._client.post(url)` と `client.delete(url)` は、どちらも「クライアントのメソッドで送る」形で、見た目は似ています。
けれども、`.post` は proxy の sink の行にあるので、見落としたのは「受け手の型が分からなかった」からです。
`.delete` は、受け手が `httpx.Client` だと分かっていても、行が無いので結び付きません。
だから原因は「語彙」です。

見分けるときの手順を、具体的に書きます。

1. 見落とした動作の**関数・メソッドの名前**を書き出す（例: `httpx.Client.delete`、`loguru.logger.add`、`wave.open`）。
2. sink 表を検索する。たとえば `grep -n '"wave' authgap/catalog/sinks.py` や `grep -n 'method="delete"' authgap/catalog/sinks.py`。
3. **行が無ければ「語彙」**。行があれば、受け手の型か、呼び出しの解決か、深さを疑う。

grep は、同じ入力にいつも同じ答えを返す決定的な道具なので、最終評価で使ってよい道具です（[第 26 章](ch26.md)。AI は使わない）。

（出典: `docs/drafts/final_judging_guide_draft.md:465-467`（18.2 の 6。5 つの原因）、`docs/open_questions.md:1194-1196`（O43 のデコレータ・呼び戻し・モジュール水準のインスタンスの行））

#### 一歩ずつの説明 — 見落としの記録に書くこと

R19 の形を、最終評価の記録の欄（手引きの下書き 18.4 節）に当てはめると、次のようになります。
欄の名前と中身の書き方は、手引きの下書きのものです。

|---|---|
| `outcome` | `見落とし` |
| `cause` | `語彙` |

| `depth` | 本体の `logger.info(...)` の呼び出しは深さ 0。ただし、出力先はモジュールの一番上の設定で決まる |

ツールの関数の中だけを読んでいると、`logger.info(...)` は「画面に出すだけ」に見えてしまうからです。
標準出力・標準エラーへのログは、ファイルではないので反しません（[第 9 章](ch09.md) 9.5 節）。

#### 手引きで決まっていないこと — 不が出ている動作と、何も出ていない動作が並ぶとき

`wave.open` の例（R13）では、1 つのツールの中に、

- 解析器が不を出している動作（`export` の書き出し）と、
- 解析器が何も出していない動作（`wave.open`）

の両方がありました。
手引きの下書きの 18.2 節の表は、ツールの結果を 1 つに決める作りです。
「解析器が不として出している」は「見つけた動作に不を出している」、「見落とし」は「見つけた宣言に反する動作に、矛も不も出していない」と書かれています。
この 2 つが同じツールの中で同時に当てはまるとき、どちらを結果にするかは、手引きの下書きに書かれていません（本書の観察。**未決**）。
手引きの下書きが決めているのは、深さ 4 の中と外に動作があるときの扱い（中のものを主にし、外のものは `note` に書く）だけです。

v4 の R13 では、本記録者が「解析器が不として出している」を結果にし、`wave.open` を `note` に書きました。
これは 1 つの考え方の例で、正解ではありません。
封をする前に決めておかないと、判定の途中でこの形に出会ったとき、手引きの 22 節（手引きで決まらない事例）により、その件は「不明」にして「手引きで決まらない」と書くことになります（[第 52 章](ch52.md)）。

（出典: `docs/drafts/final_judging_guide_draft.md:456-463`（18.2 の 5 の表）、`:476-477`（18.3 の深さの中と外）、`:664-673`（22 節））

#### なぜそうするのか — 原因を分けて数える理由

1. **論文の限界の節の材料になる。** 手引きの下書きは、誤の原因の分類について「集計で内訳になり、論文の限界の節の材料になる」と書いています。見落としの原因も同じです。「語彙」が多ければ、「凍結した語彙の抜けで、これだけ見落とした」と書けます。
2. **直し方が原因ごとに違う。** 深さなら深さの上限を変える、語彙なら sink 表に行を足す、受け手の型なら型の推論を強める、と、仮に将来直すとしたときの道が違います。混ぜて数えると、どこが弱いのかが読めません。
3. **最終評価の事前登録の下書きにも書いてある。** §2.12 の下書きは、見落としの原因を「深さ / 呼び出しの解決 / 受け手の型 / 語彙 / その他」と書いています（下書き・未承認）。

（出典: `docs/drafts/final_judging_guide_draft.md:439`（分類は限界の節の材料）、`docs/drafts/prereg_2_12_draft.md:109`）

#### よくある誤解・つまずき

- **誤解: 「解析器の出力に何も無いツールは、環境を変えない」**
  変えることがあります。語彙に無いライブラリの書き込みは、出力に何も残りません。だから、見落としの判定では、**解析器の出力を見る前に**コードを読みます（手引きの下書き 18.2 の 1。[第 21 章](ch21.md) 21.11 節）。
- **誤解: 「ログは軽い書き込みなので、見落としに数えない」**
  数えます。採った原理では、呼び出しの後に残るファイルの書き込みはすべて環境の変更です。軽重は「ログ」のラベルで表し、正誤には持ち込みません（D67 の 1）。
- **誤解: 「`self._client.delete(url)` は受け手の型の問題」**
  `.delete` は、受け手の型が分かっても sink 表に無いので結び付きません。原因は「語彙」です。迷ったら、まず sink 表を grep します。
- **つまずき: 「`log_dir.mkdir(...)` も書き込みなのに、なぜ R19 の違反に入らないのか」**
  70 行の `mkdir` は、モジュールの読み込み時、つまりサーバの起動時に走ります。ツールの呼び出しで走る動作ではありません。起動時の初期化の扱い（lifespan やモジュールの読み込み時の初期化は、ツールの呼び出しでは到達しない）は、第 37・49 章で見ます。

#### 手作業ではどう使うか

最終評価の見落としの判定（200 件。D69 の 3）では、次の順で使います。

1. ツールの本体を読み、深さ 4 まで、宣言に反しうる動作をすべて書き出す。**ライブラリの関数そのものが環境を変えるもの**（セッションの `.delete`、`wave.open(..., 'wb')`、ログファイルへの書き込み）も候補に入れる。
2. ログの行があれば、モジュールの一番上の `logger.add(...)`・`FileHandler`・`basicConfig(filename=...)` を探す。
3. 解析器の出力を見る。その動作に矛も不も無ければ「見落とし」。
4. 原因を決める。sink 表を grep して、行が無ければ「語彙」。
5. 書き込み先の種類（ログ・相手側の状態・利用者のファイルなど）と、条件の種類を付ける。

[第 41 章](ch41.md)では、v3・v4 の見落としの中身を、この 5 分類で整理し直します。
[第 52 章](ch52.md)では、見落としの判定の手順の全体を見ます。

#### この節のまとめ

語彙に無いライブラリの書き込み・送信は効果にならず、解析器は何も出さない。見落としの判定でこれに出会ったら、原因を「語彙」と記録する。典型は O39 のセッションの `.delete`、v4 の R19（loguru の `logger.add` で設定したログファイル）、`wave.open(..., 'wb')`。
「語彙」は sink 表を grep して行が無いことで見分ける。`.post` のように行があるのに結び付かないなら「受け手の型」などを疑う。
ログもラベル「ログ」を付けて見落としに数える（D67 の 1）。不と見落としが同じツールに並ぶときの決め方は手引きの下書きに無く、未決。

### この章のまとめ

- D59（2026-09-24）で、解析器の読み違いを 3 種類直した。O36（値の計算の欠陥 4 つ）、O37（HTTP の本体を `data=`・`json=` の片方しか読まない）、追記（宛先を `url=` で渡されると読めない）。3 つとも誤 clear の向き。作業は、規則 → 反例テスト（15 件と 3 件が落ちる）→ 実装 → 取り直し → 記録の順で進め、最後に解析器を凍結した（[第 33 章](ch33.md)）。
- **O36**: `not x`・`-5` の値を中身のままにしていた / 合流が `None` と定数の型を比べず順序に依存していた / 関数の中の `import` の束縛を記録しなかった / `except` 節の入口で `try` の中の代入を見なかった。Python の意味どおりに直した。「片側だけの束縛はその側の値を残す」は正しい実装で、誤っていたのは説明の文だった。入れ子の値の合流の非可換は限界として残る。
- **O37**: 仕様書 229 行目の `body ← data|json` に合わせ、本体を両方から読むようにした（`HTTP_BODY` を 1 か所で決めた）。HTTP の D1・D2・D4 はメソッドで決まるので、効くのは主に `body` の slot と付録の `GAP_INJECT`。

- **O39**: セッションの `.put`・`.patch`・`.delete`・`.head`・`.options`、`httpx` のモジュールの関数、本体の `content=`・`files=` は、仕様書の語彙（月 3 凍結）に無いので足さなかった。構文で数えた上限は呼び出し箇所 150 と 143（run16 の 87 木）。この抜けは矛を少なく数える向き（記録の言葉では「D2 の矛は下限」）。
