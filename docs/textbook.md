# 第 1 部 背景

## 第 1 章 プログラムが「言っていること」と「やっていること」

ソフトウェアには、**自分が何をするかを説明する文章**がよく付いています。
たとえばスマートフォンのアプリは「位置情報を使います」と許可を求めます。
関数には「この関数はファイルを読むだけです」という説明（コメント）が付いていることがあります。

ところが、**説明と実際の動きが一致している保証はどこにもありません**。

- 説明を書いた人が、実装を変えた後に説明を直し忘れる。
- 実装が、説明を書いた人の知らない別の関数を呼んでいて、その先でファイルを書き換える。
- そもそも説明が雑。

この研究が扱うのは、この「**言っていること**」と「**やっていること**」のずれです。
ただし、どんなプログラムでもよいわけではなく、次の章で説明する **AI エージェントのツール**に的を絞っています。

## 第 2 章 AI エージェントと「ツール」

ChatGPT や Claude のような大規模言語モデル（**LLM**。文章を読んで文章を書く AI）は、それだけでは文章を返すことしかできません。
ファイルを開いたり、データベースを検索したり、メールを送ったりはできません。

そこで、LLM に「**道具（ツール）**」を渡す仕組みが広く使われています。

- ツールは普通のプログラムの関数です。たとえば `read_file(path)`、`search_issues(query)`、`delete_branch(name)` など。
- LLM は会話の中で「`read_file` を `path="report.txt"` で呼びたい」と**依頼**を出します。
- 周りのプログラムが実際にその関数を動かし、結果を LLM に返します。

このように LLM がツールを使いながら仕事を進める仕組みを **AI エージェント**と呼びます。

ここで大事な点が 2 つあります。

1. **ツールの引数（`path` や `query` の値）は LLM が決めます。** LLM は利用者の指示や、読み込んだ文書の内容に影響されます。
   悪意ある文書に「このファイルを消して」と書いてあれば、LLM がそれに従ってしまう恐れがあります（これを「プロンプトインジェクション」と呼びます）。
   ですから、**ツールの引数は「信用できない入力」として扱うべき**です。
2. **ツールは、LLM に渡した「権限」そのものです。** `delete_branch` を渡せば、LLM はブランチを消せます。
   ツールの中で何が起きるかは、LLM にどんな力を与えたかと同じ意味を持ちます。

## 第 3 章 MCP — ツールをつなぐ共通の決まり

ツールを LLM につなぐ方法はいろいろありましたが、今は **MCP（Model Context Protocol）** という共通の決まりが広く使われています。

- MCP では、ツールを提供するプログラムを **MCP サーバ**と呼びます。
- MCP サーバは「私はこういうツールを持っています」と一覧を出し、LLM 側（のアプリ）がそれを呼びます。
- Python では、公式の `mcp` パッケージや `fastmcp` パッケージを使って、たとえば次のように書きます。

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("files")

@mcp.tool()
def read_file(path: str) -> str:
    """ファイルの中身を返す。"""
    return open(path).read()
```

`@mcp.tool()` という一行（**デコレータ**と呼ばれる、関数の上に付ける印）で、関数 `read_file` がツールとして登録されます。

## 第 4 章 ツールの「自己申告」— 宣言（annotations）

MCP には、ツールが**自分の性質を申告する**ための欄があります。これを **ToolAnnotations**（ツールの注記）と呼びます。
この研究では、これを**宣言**と呼びます。代表的なものは次の 4 つです。

| 宣言 | 意味 | 例 |
|---|---|---|
| `readOnlyHint: true` | 「私は環境を変えません（読むだけです）」 | 検索、一覧表示 |
| `destructiveHint: false` | 「変えるとしても、追加するだけで壊しません」 | メモの追加 |
| `idempotentHint: true` | 「同じ引数で何度呼んでも、2 回目以降は何も変わりません」 | 設定値を同じ値に上書き |
| `openWorldHint: false` | 「外の世界（インターネットなど）とはやり取りしません」 | 手元の計算だけ |

書き方の例です。

```python
@mcp.tool(annotations={"readOnlyHint": True})
def list_courses() -> str:
    ...
```

**宣言は、ツールを使う側（LLM のアプリや利用者）が「このツールは安全か」を判断する材料になります。**
たとえばアプリは、`readOnlyHint: true` のツールなら確認なしで実行し、そうでないツールは利用者に「実行してよいですか」と尋ねる、という使い方ができます。

ただし、名前に `Hint`（ヒント）と付いているとおり、**宣言は自己申告であって、誰も検査していません**。

## 第 5 章 自己申告が嘘だと何が困るか

`readOnlyHint: true` と宣言したツールが、実は裏でファイルを書き換えていたとします。

- アプリは「読むだけだから安全」と判断し、利用者に確認せずに実行します。
- LLM が悪意ある文書に操られていれば、利用者の知らないうちにファイルが書き換わります。

つまり、**宣言が実装より弱い（安全側に偏っている）と、宣言を信じて作った安全の仕組みがすり抜けられます**。
実際、この研究で調べた公開の MCP サーバでも、`readOnlyHint: true` なのにファイルや DB を書き換えるツールが見つかっています（第 31 章）。

逆向きのずれ（宣言が実装より強い。たとえば `readOnlyHint` を付けていないが実際は読むだけ）は、安全上はあまり困りません。
この研究は主に**前者（宣言が実装を過小申告している）**を探します。

# 第 2 部 研究の問い

## 第 6 章 この研究の一文

この研究（AuthGap）の問いを一文で書くと、こうなります。

> **Python で書かれた MCP サーバについて、各ツールの宣言（D）と、そのツールが実際にできること（M）を、プログラムを動かさずに照らし合わせ、食い違いを見つける。**

ここで 2 つの記号を導入します。

- **D（Declared）** = 宣言。第 4 章の `readOnlyHint` など。
- **M（effective permissions、実効の権限）** = ツールが実際にできること。「ファイルを書ける」「外部に通信できる」など。

**D と M を比べて、M が D を超えている所（宣言より多くのことができる所）を「食い違い」として報告する**のが、この研究の中心です。
この食い違いを、以下では **CONTRADICTION**（矛盾）、日本語では短く「**矛**」と呼びます。

## 第 7 章 静的解析 — プログラムを動かさずに読む

M（ツールが実際にできること）を調べる方法は、大きく 2 つあります。

1. **動かして観察する**（動的解析）。ツールを実際に呼び出し、何が起きたかを記録する。
2. **動かさずにソースコードを読む**（**静的解析**）。コードの書き方から、何が起こりうるかを推論する。

この研究は 2 を選んでいます。理由は次のとおりです。

- **動かすと危険です。** ファイルを消すツールを動かせば、本当に消えます。
- **動かすには準備が要ります。** API の鍵、データベース、外部サービスなど、各サーバごとの環境を用意するのは現実的ではありません。
- **動かすと、その回に通った道しか見えません。** 静的解析なら、「こう呼ばれればここに届く」という**起こりうる道**を網羅的に考えられます。

一方で、静的解析には弱点もあります。

- **実際には起こらない道まで数えてしまう**ことがある（誤警報。第 17 章）。
- **プログラムの書き方が複雑すぎて、道を追い切れない**ことがある（見落とし。第 17 章）。

この研究では、解析のやり方をさらに次のように限定しています（仕様書 `AUTHGAP_BRIEF_v3.md` の決まりです）。

- **入力はパッケージのソースコードだけ**。インストールも、型の環境の構築もしない。
- **LLM を判定に使わない**。同じ入力には必ず同じ結果を返す（**決定的**）。

この解析を行うプログラムを、以下では**解析器**と呼びます。解析器の本体は `authgap/` の下にあります。

## 第 8 章 研究が今の形になるまで

この研究は、最初はもっと大きな主張をしていました。仕様書の元の計画では、次の 3 つを組み合わせて判定することを目指していました。

1. **誰がツールを起動できるか**（trig と呼んでいた）
2. **危険な操作に、誰の決めた値が入るか**（val）
3. **その値を検査する仕組み（ゲート）があるか、どれくらい強いか**（gate）

そして「既知の脆弱性の**修正前**と**修正後**のコードを、この 3 つの組み合わせで見分けられる」ことを主張する予定でした。

ところが、実際の MCP サーバで測ると、1 の「誰が起動できるか」をきちんと追えるものが全体の 0.6%（2,231 ユニット中 14）しかありませんでした。
仕様書自身が「20% 未満なら、この主張は野外では成り立たないので格下げする」と事前に決めていたので、**その決まりに従って主張を絞りました**（決定 D36）。

現在の主張は、第 6 章の一文、つまり「**宣言 D と実効 M の照合**」の 1 本です。
2 と 3 のための仕組み（ゲートの等級づけなど）は解析器に残っていますが、論文では**付録**の扱いです。
この教科書でも、必要な範囲でしか扱いません。

> **ここまでのまとめ**: MCP のツールは自分の性質を宣言するが、誰も検査していない。
> AuthGap は、ソースコードを動かさずに読んで、宣言より多くのことができるツールを見つける。

# 第 3 部 解析器の仕組み

## 第 9 章 全体の流れ

解析器は、1 つのパッケージ（**木**と呼びます。フォルダの木構造のことです）を受け取ると、次の順に処理します。

```
① 入口を探す      … どの関数がツールか（第 10 章）
② 中をたどる      … ツールの関数から呼ばれる関数を、決まった深さまで順に読む（第 13 章）
③ 効果を見つける  … ファイル書き込み・通信などの操作を見つける（第 11 章）
④ 値を追いかける  … その操作に入る値を、誰が決めたか（第 12 章）
⑤ 宣言を読む      … そのツールの宣言（第 14 章）
⑥ 照合する        … 宣言と効果を比べて、矛・不・内を決める（第 15 章）
⑦ 書き出す        … 結果をファイル（manifest）に書く（第 16 章）
```

②③④は実際には同時に進みます。順に説明します。

## 第 10 章 入口を見つける

解析器はまず、「**どの関数がツールか**」を見つけます。ツールとして登録された関数を**入口**と呼び、1 つの入口を**ユニット**と呼びます。

ツールの登録の書き方はいくつもあります。

```python
@mcp.tool()                        # FastMCP のデコレータ
def read_file(path: str): ...

@server.call_tool()                # 低レベルの書き方: 1 つの関数で全ツールを受ける
async def call_tool(name, arguments):
    if name == "read_file": ...
```

解析器は、こうした書き方を **ENTRY_RULES**（入口の規則）という一覧で知っています（`authgap/catalog/entries.py`、14 規則）。
この一覧が「MCP サーバのどこがツールか」を知っていることが、**この研究の領域に固有の貢献の中心**です。

低レベルの書き方では、1 つの関数の中で `if name == ...` と分岐してツールを振り分けます。
解析器はその分岐を読み、宣言（`Tool(name=..., annotations=...)`）と各分岐を結び付けます。

## 第 11 章 「効果」— 外の世界に触れる操作

次に、ツールの中で**外の世界に触れる操作**を探します。これを**効果**（effect）と呼びます。効果には 7 種類（**kind**）あります。

| kind | 意味 | 例 |
|---|---|---|
| `FS_READ` | ファイルを読む | `open(p).read()` |
| `FS_WRITE` | ファイルを書く・作る・消す・動かす | `open(p, "w")`、`os.remove(p)`、`shutil.copy(a, b)` |
| `NET` | ネットワークに通信する | `requests.get(url)`、`httpx.AsyncClient().post(url)` |
| `DB` | データベースに命令を送る | `cursor.execute("DELETE FROM t")` |
| `SPAWN` | 別のプログラムを起動する | `subprocess.run(["git", "log"])` |
| `EXEC` | 文字列をプログラムとして実行する | `eval(code)`、`exec(code)` |
| `DISPATCH` | 名前で関数を呼び分ける | `getattr(obj, name)()` |

効果を起こす関数の呼び出しを **sink**（シンク。流れが行き着く先、という意味）と呼びます。
解析器は、どの呼び出しが sink かを **sink 表**（`authgap/catalog/sinks.py`）で知っています。sink 表には 3 つの形があります。

1. **直接の sink**: `os.remove(p)` のように、関数の名前だけで決まるもの。
2. **proxy の sink**: `client.post(url)` のように、**受け手**（`client`）の型によって決まるもの。
   `client` が `httpx.AsyncClient` なら NET の sink、そうでなければ違う。受け手の型を知る必要があります（第 13 章）。
3. **pipe の sink**: 起動した子プロセスの標準入力に書き込むもの（`proc.communicate(input=data)`）。

### slot — 効果の中の「位置」

効果には、値が入る**位置**があります。これを **slot**（スロット）と呼びます。

- `FS_WRITE` の slot: `path`（どのファイルか）、`content`（何を書くか）
- `NET` の slot: `url.host`（どこへ）、`url.path`、`url.query`、`body`（何を送るか）、`headers`
- `DB` の slot: `sql`（どんな命令か）、`params`
- `SPAWN` の slot: `argv0`（どのプログラムか）、`argv[*]`（引数）、`shell_string`、`cwd`、`env`、`stdin`
- `EXEC` の slot: `code_text`（どんなコードか）

たとえば `requests.post(url, json=payload)` なら、`url` が `url.host` の slot に、`payload` が `body` の slot に入ります。

> **注意（凍結された語彙）**: sink 表と slot の種類は、仕様書が「月 3 に凍結する」と決めた語彙です。
> 後から足すと「結果を見てから定義を変えた」ことになるので、今は足していません（第 18 章、第 33 章の O39）。

## 第 12 章 値を追いかける — 誰が決めた値か

効果を見つけただけでは不十分です。**その効果の slot に入る値を、誰が決めたのか**が大事です。
たとえば同じ `os.remove(p)` でも、

- `p` が `"/tmp/cache.txt"` という定数なら、消すファイルは開発者が決めています。
- `p` がツールの引数そのものなら、**LLM が消すファイルを選べます**。

解析器は、値ごとに次の情報を持って追いかけます。この部分を **val エンジン**（`authgap/val/engine.py`）と呼びます。

### 主体（誰が決めたか）

値を決めた**主体**を、3 段階で表します。

| 主体 | 意味 |
|---|---|
| `MODEL` | LLM が決めた（ツールの引数から来た） |
| `OP` | 運用者が決めた（定数、設定ファイル、環境変数） |
| `USER` | 利用者が決めた（この研究ではあまり使いません） |

ツールの引数は `MODEL` から始まります。`"ls " + p` のように `MODEL` の値を混ぜた値は `MODEL` になります。

### 確度（どれくらい確かか）

値の追跡が**確かかどうか**を、**確度**として持ちます。

| 確度 | 意味 |
|---|---|
| `resolved` | 解析器が理解できる操作だけで届いた（確か） |
| `opaque` | 途中に解析器が理解できない所があった（不確か）。理由も記録する |
| `remote` | 値が別のプロセスやネットワークの向こうから来た |

`opaque` の理由の例: `unresolved`（呼び出し先が分からない）、`depth`（深さの上限で読むのをやめた）、`receiver`（受け手の型が分からない）、`dynamic`（動的な書き方）。

**確度が大事なのは、「分からない」を「安全」と取り違えないため**です（第 17 章）。

### 形（どんな値か）

値の**形**も持ちます。

- `Atom`: 1 つの値。定数なら中身（`"ls"` や `5`）も持つ。
- `Str`: 文字列を連結したもの。部分ごとに主体を持つ（`"https://api.example.com/" + p` の `"https://api.example.com/"` の部分は OP、`p` の部分は MODEL）。
- `Seq`: リスト。`Map`: 辞書。`Path`: ファイルのパス。`Obj`: オブジェクト（クラスの名前と、属性の値を持つ）。
- `Unknown`: 分からない。

形があるおかげで、たとえば URL の「宛先（host）」と「パス（path）」を分けて、「宛先は定数だがパスはモデルが決める」のように細かく判断できます。

### root（根）

値が**どのツール引数から来たか**の記録を **root** と呼びます。`name` と `body` の 2 つの引数から作った値なら、root は `{name, body}` です。
root は「どの引数が検査されたか」を正しく対応させるために使います（第 25 章の O34）。

## 第 13 章 呼び出しをたどる

ツールの関数は、たいてい別の関数を呼び、その関数がさらに別の関数を呼びます。効果はその奥にあることが多いです。

```python
@mcp.tool(annotations={"readOnlyHint": True})
def list_courses():
    client = _authed()          # 深さ 1
    ...

def _authed():
    paths.ensure_dirs()         # 深さ 2
    ...

class AppPaths:
    def ensure_dirs(self):
        os.chmod(self.root, 0o700)   # ← 効果（ファイルの権限を変える）
```

解析器は、呼び出し先の関数の中に**降りて**読みます。

### 深さの上限

どこまでも降りると時間がかかりすぎるので、**深さの上限**を決めています。仕様書は 3 でしたが、測定の結果 **4** にしました（第 22 章）。
上限より深い所の効果は見えません。これは既知の限界です（第 33 章）。

### 呼び出し先の決め方（解決）

`foo(x)` と書いてあるとき、どの `foo` が呼ばれるかを決めることを**解決**と呼びます。解析器は次の順に解決します。

1. **import で決まるもの**: `from pkg.util import foo` とあれば、`pkg/util.py` の `foo`。
2. **同じファイルの定義**: 同じファイルに `def foo` があればそれ。
3. **受け手の型で決まるもの**: `client.post(...)` で `client` の型が分かっていれば、その型の `post`。
4. **末尾名だけで探す**: 上のどれでも決まらなければ、木の中から名前が `foo` の関数を探す。
   候補が 1 つならそこへ降りますが、**確かではない**ので、その先の効果には確度 `opaque(unresolved)` を付けます。
   候補が 2 つ以上なら降りません（どれか分からないので）。

4 の「末尾名だけで探す」は便利ですが、間違えることがあります。たとえばローカル変数の `rows.append(0)`（Python 組込みのリストのメソッド）を、木の中にある別のクラスの `AuditLog.append` と取り違えることがあります（第 28 章）。

### 受け手の型

`client.post(url)` が NET の sink かどうかは、`client` の型で決まります（第 11 章の proxy の sink）。解析器は次の方法で型を知ります。

- `client = httpx.AsyncClient()` のように、作った所が見えるとき。
- 関数の**型注釈**（`def f(client: httpx.AsyncClient)` や `def make() -> httpx.AsyncClient`）があるとき（D50、D51、第 29 章の G4）。

## 第 14 章 宣言を読む

次に、そのツールの**宣言**を読みます。宣言の書き方もいくつもあります。

```python
@mcp.tool(annotations={"readOnlyHint": True})                    # 辞書で書く
@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))         # 専用のクラスで書く
Tool(name="list", annotations=ToolAnnotations(readOnlyHint=True)) # 低レベルの書き方
```

解析器は、これらをすべて読み、**明示された宣言**（`D_kind.explicit`）を取り出します。
この研究では、宣言を次の 4 つに分けて扱います。

| 記号 | 宣言 | 扱い |
|---|---|---|
| **D1** | `readOnlyHint: true` | **主指標**（事前に登録した） |
| **D2** | `destructiveHint: false`（`readOnlyHint: true` でないとき） | **主指標** |
| **D3** | `openWorldHint: false` | 探索的（別の列で報告） |
| **D4** | `idempotentHint: true`（`readOnlyHint: true` でないとき） | 探索的 |

D3 と D4 の判定規則は、結果を一度見た後で作ったので、**探索的**（参考の分析）として D1・D2 と合算しません（第 18 章）。

## 第 15 章 食い違いの判定 — 4 つの原理と判定表

いよいよ、宣言と効果を照らし合わせます。ここで難しいのは、**「どの効果が、どの宣言に反するか」が自明ではない**ことです。

- `readOnlyHint: true`（環境を変えない）のツールが、**ログファイルに 1 行書く**のは違反か？
- データベースの**接続の設定**（`PRAGMA`）を変えるのは違反か？
- **外部のサービスに POST を送る**のは、「自分の環境」を変えたことになるか？

こうした判断を 1 件ずつ場当たり的に決めると、結果を見て都合のよい方に倒してしまう恐れがあります。
そこで、**先に原理を 4 つ決め、判定表はその原理から機械的に導く**ことにしました（`docs/contradiction_principles.md`、決定 D56）。

### 原理 1 — 「環境」に何を含めるか

- **1-i 永続する設定**（データではないが呼び出しを越えて残るもの。DB のジャーナル形式など）を含めるか → **含める**（採用: b）
- **1-ii リモートの状態**（通信相手の側の状態）を含めるか → **含める**（採用: b）

理由: 仕様の文言 "does not modify its environment" を字義どおりに読むと、データに限る根拠はないため。

### 原理 2 — 静的に決まらない性質をどう扱うか

たとえば「POST 先が何をするか」はコードからは分かりません。こうしたものを

- a: **不明**として別に数える（採用）
- b: 矛盾に倒す
- c: 宣言どおりとみなす

のどれにするか。**a を選びました**。b や c は、測定を既知の向きに偏らせるからです。この「不明」を短く「**不**」と呼びます。

### 原理 3 — 値をモデルが決められるとき

`os.remove(p)` の `p` をモデルが決められるなら、「モデルは任意のファイルを消せる」と読むか？
→ **読む**（採用: a）。M は「できること」の上限だからです。

ただし、モデルの値が**流れ込むだけ**（決められるとは限らない）ときがあります（第 24 章の O33）。
そこで「**決められる**」= 主体が MODEL **かつ** 確度が resolved、と定義しました。MODEL でも確度が opaque なら「不」です。

### 原理 4 — どの宣言を対象にするか

→ **4 つすべて**（D1〜D4）。宣言ごとに分けて報告します（採用: a）。

### 判定表（抜粋）

原理から導いた表の一部です（全体は `docs/contradiction_principles.md` §7）。

| 宣言 | 効果 | 判定 |
|---|---|---|
| D1 readOnly | ファイルを書く・作る・消す | **矛**（`fs_write`） |
| D1 readOnly | DB のデータを変える命令（INSERT / UPDATE / DELETE …） | **矛**（`db_modify`） |
| D1 readOnly | DB の永続する設定（`PRAGMA journal_mode`） | **矛**（`db_persistent`。原理 1-i） |
| D1 readOnly | 通信の GET | 内（宣言どおり） |
| D1 readOnly | 通信の PUT / DELETE | **矛**（`net_modify`。原理 1-ii） |
| D1 readOnly | 通信の POST | **不**（`net_post`。相手が何をするか分からない） |
| D1 readOnly | 起動するプログラムをモデルが決める | **矛**（`spawn_model`。原理 3） |
| D1 readOnly | 起動するプログラムが定数 | **不**（そのプログラムが何をするか名前からは分からない） |
| D2 destructive=false | ファイルを消す・移動する・置き換える | **矛**（`fs_remove`） |
| D2 destructive=false | 追記 | 内 |
| D2 destructive=false | DB の DELETE / DROP / UPDATE | **矛** |
| D3 openWorld=false | 定数の外部ホストへの通信 | **矛**（`net_external_host`） |
| D4 idempotent | `open(p, "a")` で追記 | **矛**（`fs_append`。2 回呼べば 2 回追記される） |

判定の結果は 3 種類です。

- **矛**（CONTRADICTION）: 宣言に反する効果に届く。
- **不**（不明）: 反するかどうかが静的に決まらない。**件数は必ず併記**します。
- **内**: 宣言の範囲内。

原理を 1 つずつ反対側にしたら件数がどう変わるか（**感度分析**）も、毎回出しています（`docs/contradiction_by_decl.md`）。

## 第 16 章 出力の読み方

解析器は、木ごとに **manifest**（マニフェスト。結果の一覧ファイル）を書きます。ユニット（ツール）ごとに次のものが入っています。

- `effects`: 見つけた効果の一覧。kind、sink の名前（`site`）、ファイルと行、slot ごとの値（主体・確度・形・root）、呼び出しの経路（`witness_chain`）、確度（`resolution`）。
- `rows`: 効果ごとの判定。**verdict**（判定の種類）と注記（`contradiction:D1` など）。
- `D_kind`: 読み取った宣言。
- `opaque_reasons`、`cap_hits`: 分からなかった理由、上限に当たったか。
- `unresolved_in_tree_calls`: 名前が木の中の定義に当たるのに解決できなかった呼び出し（第 29 章の G5）。

verdict にはいくつか種類があります。核の主張に関わるのは **CONTRADICTION** です。

| verdict | 意味 | 位置づけ |
|---|---|---|
| `CONTRADICTION` | 宣言に反する効果 | **核** |
| `GAP_INJECT` | 危険な slot に、検査されていないモデルの値が入る | 付録 |
| `GAP_SELECT` | 危険な効果の実行をモデルが選べる | 付録 |
| `UNKNOWN` | 判定に要る情報が分からない | 付録 |
| `INVENTORY` | 運用者の許可リストなどで覆われている | 付録 |

数えるときの単位は、多くの場合「**ユニット × site × kind**」です。同じツールの同じ sink の同じ kind は、経路が何本あっても 1 件と数えます。

母集団をまとめて走らせる仕組みが `scripts/scan_v2.py` で、結果は `evidence/scan_v2_<ラベル>/` に入ります（`summary.json`、`contradictions.json`。木ごとの manifest は大きいので git では追跡しません）。

> **ここまでのまとめ**: 解析器は、ツールの入口から呼び出しを深さ 4 までたどり、外の世界に触れる操作（効果）を見つけ、
> その値を誰が決めたかを追い、4 つの原理から導いた判定表で宣言と照らし合わせ、矛・不・内に分ける。

# 第 4 部 研究の作法

この研究は、解析器を作ること以上に、**結果を信じてもらえる手順**を重視してきました。第 5 部の出来事を理解するには、この作法を先に知っておく必要があります。

## 第 17 章 誤りには 2 つの向きがある

解析器の誤りには、向きが 2 つあります。

| 誤り | 意味 | 例 | どちらが怖いか |
|---|---|---|---|
| **誤警報**（false alarm） | 問題が無いのに「矛」と言う | 実行されない枝のファイル書き込みを数える | 読む人の手間が増える |
| **誤 clear**（false-clean） | 問題があるのに「矛盾なし」と言う | 呼び出しを追い切れず、書き込みを見落とす | **安全だと誤解させる** |

**この研究では、誤 clear を特に警戒します。** 「このツールは宣言どおりです」という誤った保証は、誤警報より害が大きいからです。
そのため、

- 分からないときは「安全」ではなく「**不明**」にする（原理 2、CLAUDE.md 規則 4「黙って安全側に倒さない」）。
- 解析器を変えるたびに、**消えた効果・消えた矛**を 1 件ずつ確かめる（増えた側だけ見て「直った」と言わない）。
- コミットのメッセージには、直した誤りがどちらの向きだったかを必ず書く。

## 第 18 章 先に決めて、後から変えない — 事前登録・凍結・逸脱

研究でいちばん起こりやすい失敗は、**結果を見てから、都合のよい規則や閾値を選んでしまう**ことです。
本人に悪意がなくても、何度も試して「うまくいった」やり方を選べば、偶然に合わせた結果になります。これを防ぐために、次の 3 つの仕組みを使っています。

1. **事前登録**（`docs/preregistration.md`）: 何をどう測り、何をもって成功とするかを、**測る前に**書いてコミットする。
2. **凍結**: 規則や語彙を「この時点以降は変えない」と決める。仕様書は、sink の語彙を月 3、ゲートの語彙を月 6、解析器全体を月 10 に凍結すると決めていました。
   凍結の記録は `docs/fingerprint.json` に、ファイルの指紋（sha256。中身が 1 文字でも違えば変わる値）と一緒に書きます。
3. **逸脱の記録**: やむを得ず、結果を見た後に規則を変えるときは、**変えたことと、変える前後の両方の値**を `docs/preregistration.md` §5 に書く（今回までに 23 件）。

閾値（合格の基準）には、必ず**測り方と分母**を付けます（CLAUDE.md 規則 3）。

## 第 19 章 直すときの手順

解析器を直すときは、毎回同じ順番を守りました。

```
① 規則を文章で書いて、先にコミットする        （docs/decisions.md）
② 反例のテストを書いて、コミットする
     ・直す前の解析器で「落ちる」ことを確かめる   ← 本当に誤りを再現している証拠
     ・「変えてはいけない形」のテストも入れる     ← 直しすぎを防ぐ
③ 実装する
④ 検証する
     ・全テスト、ゲートの検査（B3a 8/8・B3b 15/15）、変異試験（生存 ≤ 2）
     ・較正対の両側比較（第 25 章）、較正対の効果行の突き合わせ（diff_effects）
⑤ 母集団を取り直して、前の結果と突き合わせる（compare_scans）
     ・消えた効果・消えた矛を 1 件ずつ原ソースで確かめる
⑥ 結果と逸脱を記録して、コミットする
```

①を先にするのは、**実装してみて都合がよかった規則を後付けで書く**のを防ぐためです。
②で「直す前に落ちる」ことを確かめるのは、**テストが本当にその誤りを捉えている**ことの証拠になるからです。

**変異試験**とは、解析器にわざと小さなバグを入れて（15 種類）、テストがそれを見つけられるかを調べるものです。
見つけられなかったバグ（生存）が 2 個以下なら合格、と決めています。

## 第 20 章 自分の仕事を壊しに行く — 敵対的レビュー

「解決できる範囲を広げる」変更（今まで分からなかった呼び出し先を分かるようにする、など）は、**突き合わせだけでは正しさが分かりません**。
正しく解決できた所と、**間違った相手に確定してしまった所**が、どちらも「増えた」として見えるからです。後者は誤 clear を生みます。

そこで、こうした変更のたびに**敵対的レビュー**を行いました。これは、変更を**壊しに行く**立場で、

- わざと紛らわしい入力（小さなプログラム）を作り、
- 変更の**前と後**の解析器で走らせ比べ、
- 変更のせいで悪くなった所（退行）を探す、

という作業です。今回、このレビューで 2 回、自分の変更の誤りが見つかっています（第 25 章の O31、第 29 章の G1・G2）。

## 第 21 章 開発に使うデータと評価に使うデータ

解析器を直すために見たデータで、そのまま解析器の性能を測ると、**甘い結果**になります（試験問題を見て勉強してから、同じ問題で試験を受けるようなもの）。
そこで、データを役割で分けています。

| データ | 中身 | 役割 |
|---|---|---|
| **較正対** | 既知の脆弱性の修正前後のコード 8 対（A1〜A18 のうち採点に使う対） | 解析器の基本的な動きの確認 |
| **母集団 v2** | 宣言を持つ公開 MCP サーバ 87 木 | 開発用。何度も見て直した |
| **母集団 v3** | v2 と重ならない 91 木 | 開発用の中間確認（第 28 章）。確認の後で修正に使ったので、今は開発用 |
| **最終評価のデータ** | v2・v3 と重ならない新しいデータ | **論文の評価**。学生が手動で行う（第 35 章） |

「母集団」とは、調べたい対象全体のことです。v2 の母集団は「**宣言（ToolAnnotations）を持つ公開の Python MCP サーバ**」で、GitHub の検索で列挙した 3,764 の repo から、乱数で 100 を選び、そのうち本当に MCP サーバだった 87 木を使っています。

> **ここまでのまとめ**: 誤 clear を特に警戒し、規則は先に書き、直す前に落ちるテストを書き、
> 消えたものを 1 件ずつ確かめ、解決を広げる変更は壊しに行き、開発用と評価用のデータを分ける。

# 第 5 部 今回の作業で何が起きたか

ここからは、今回の一連の作業を時系列で説明します。数字は、その時点の母集団 v2 の取り直し（**run** と呼びます。run14、run15… の番号付き）の結果です。

## 第 22 章 深さを 3 から 4 へ

**問題**: 仕様書は、呼び出しをたどる深さの上限を 3 としていました。しかし深さ 3 では、DB の命令の受け手の型を解決できない割合が高く、見落としが多いことが分かりました。

**やったこと**: 深さ 3・4・5 で同じ母集団を走らせ、比べました（感度分析。`docs/depth_sensitivity.md`）。

| 深さ | DB の受け手の型が解決できない割合 | CONTRADICTION | 時間 |
|---|---|---|---|
| 3 | 24.6% | 85 | 基準 |
| 4 | 17.6% | 146 | +7% |
| 5 | 14.2% | 193 | +24% |

（この表は当時の解析器での値です。その後の修正で件数は変わっています。）

**決定**: 学生が**深さ 4** を選びました（D54）。仕様書の値（3）とは違うので、逸脱として記録しています。
また、時間のかかりすぎる木を打ち切る仕組み（`prep_budget_exit`、D52）も入れました。

## 第 23 章 食い違いの原理を選ぶ

**問題**: それまでの矛の判定は、場面ごとに決めた規則の寄せ集めでした（D32、D41、D55）。「ログの書き込みは違反か」「POST は違反か」に一貫した答えがありませんでした。

**やったこと**: 第 15 章の 4 つの原理を立て、選択肢ごとに「どのマスがどう変わるか」を件数を見ずに書き出しました。
学生は「**研究の観点を優先し、実務の観点（出力の見せ方、雑音の多さ）は判断に使わない**」という方針で原理を選びました（1-i b、1-ii b、2 a、3 a、4 a）。
判定表は原理から機械的に導き、実装とテストをその表に合わせました（D56、run13）。

## 第 24 章 小さな誤りを 3 つ直す（O30・O32・O33）

run13 の手での確認で見つけた誤検出を直しました（D57、run14）。

- **O30**: 末尾名だけの解決で、**テストファイル**の中の同名の関数に結び付いていた。本体のコードからテストのコードに届くことはないので、テストファイルを候補から外した。
- **O32**: `client.get("/items/" + id)` のような**相対 URL**（`/` で始まる、宛先を含まない URL）を、値全体を「宛先」と読んでいた。宛先は `client` を作ったときの `base_url` で決まるので、パスとして読むようにした。
- **O33**: 原理 3 の「モデルが決められる」を、主体が MODEL というだけで判定していた。モデルの値が**流れ込むだけ**の場合（SQL のバインド変数など）もあるので、「MODEL かつ確度 resolved」に絞った（第 15 章）。

このとき、O30 の修正が、既存の別の誤り（O34）を表に出しました。次の章で扱います。

## 第 25 章 到達しない枝と検証の穴（O31・O34）

「凍結の前に直す」と学生が決めた 2 つです（D58）。

### O31 — 実行されない枝の効果を数えていた（誤警報）

```python
def write_text(path, text):
    if not path:
        return None          # path が None ならここで終わる
    Path(path).write_text(text)

@mcp.tool(annotations={"readOnlyHint": True})
def fetch(...):
    write_text(None, data)   # None を渡しているので、書き込みには届かない
```

以前の解析器は `if` の両方の枝を常に実行していたので、届かない書き込みまで効果に数え、誤警報を出していました。
そこで、**定数で決まる `if` は、取られる側の枝だけを実行する**ようにしました。

**ところが**、取り直し（run15）で消えた効果 2,424 件を 1 件ずつ確かめる**敵対的レビュー**を行うと、**23 行が誤 clear**（本当は届く効果を消した）でした。原因は、「定数に見える値」の中に、実は定数ではないものが混ざっていたことです。

- `f(p, **kwargs)` で実際に渡された値を見落とし、既定値の定数で置き換えていた。
- `cached = not raw` の `not` を解析器が無視していた（逆の真偽になる）。
- 分岐の合流で、`None` が他方の値に勝ってしまう順序の問題があった。

そこで規則を狭め、「**静的に決まる名前は、関数の仮引数のうち、リテラル（定数）から来て、関数の中で書き換えられないものだけ**」にしました。
改訂後の取り直し（run16）で、**誤 clear だった 23 行はすべて戻り、新しく消えた効果は 0** でした。
run16 で消えた 2,346 件はすべて、レビューで正しいと確かめた集合に入っています（大半は canvas-mcp の、既定値で届かない POST の枝）。

### O34 — 検証の穴（誤 clear）

```python
def tool(name, body):
    if name not in ALLOWED:        # name だけを検査している
        raise ValueError()
    os.system("echo " + name + body)   # body は検査されていない
```

以前の解析器は、値の root（第 12 章）の**どれか 1 つ**が検査されていれば、値全体を「検査済み」にしていました。
攻撃者は検査されていない `body` を使えば済むので、これは誤 clear です。**root のすべてが検査されていることを求める**ように直しました。

### A2 の較正が 8/8 から 7/8 に

**較正対**とは、既知の脆弱性について「修正前」と「修正後」のコードを並べたものです。解析器が修正を見分けられるか（**両側比較**。修正前では問題あり、修正後では問題なしになるか）を確かめる基準にしています。

O34 を直すと、較正対の 1 つ **A2**（git の MCP サーバのフラグ混入）の修正後のコードで、別の検査されていない引数（`context_lines`）が見えるようになり、両側比較が **8/8 → 7/8** に下がりました。

「A2 の形に合わせた例外を足せば 8/8 に戻せる」案もありましたが、学生の「**あまり綺麗ではない**」という指摘で取り下げました。
**これまでの 8/8 は、O34 の誤りに一部支えられていた**ことが分かったので、規則は変えずに 7/8 と報告します（D58 の追記）。
「argv の要素を『オプション名』と『値』に分けて見るべきでは」という論点は、未決の問い（O35）として残しました。

## 第 29 章 一般に正しい修正だけを入れる（D61）

1. **正解が v3 と無関係に決まる**（Python の言語の意味、ライブラリの仕様、既存のカタログから導ける）。
2. **どの木にも現れうる形である**（特定の木の書き方への対応ではない）。

この基準で 5 つの修正（G1〜G5）を選び、実装し、**敵対的レビュー**にかけました。すると、

| 修正 | 内容 | 結果 |
|---|---|---|
| G1 | 子プロセスの標準入力は「ファイル書き込み」ではない | **取り消し**。`env python3`、`sudo sh`、`tee`（標準入力をファイルに書く）のように、インタプリタ（コードを実行するプログラム）の一覧に無いコマンドでも、標準入力はコード実行やファイル書き込みに届く。以前の扱い（書き込み相当として残す）が、保守的な上限として正しかった |
| G2 | 組込み型（リストや文字列）の値のメソッドを、木の中の同名メソッドに結ばない | **取り消し**。値の「形」は型の証明にならない。未知の値に `.strip()` を呼んだ結果も文字列の形になり、本当の効果を消していた（誤 clear） |
| G3 | パッケージの `__init__.py` の再公開（`from .impl import f` を `from .tools import f` で使う形）と、`as` の別名つき import を正しく解く | **条件つきで採用**。同じ名前が 2 回以上束縛される形（try/except の予備の import、条件つき import、代入し直し）では 1 つに確定しない。別名つき import の修正は、最初の解析器から既知だった欠陥（K7）の修正にもなった |
| G4 | 型注釈（`-> httpx.AsyncClient`）から受け手の型を付ける対象を、sink 表の型すべてに広げる | **条件つきで採用**。外部の型（`requests.Session`）を木の中の同名クラス（`Session`）と取り違えない。注釈の名前が木の中の定義や相対 import を指す場合は付けない |
| G5 | 解決できなかった木の中の呼び出しを、ツールごとの列として出す | 採用（判定は変えない。「矛盾なし」の確からしさを読むための情報） |

**v3 の取り直しは「回帰（悪くなった所）が無いか」の確認だけに使い、v3 の数字の改善は報告しません。** v3 は見た後に直したデータだからです。

直さなかったもの（一時ファイルの削除、`shlex.quote` の固定コマンドなど）は、既知の限界として記録しました（O41）。

## 第 34 章 良い結果になりそうか — 正直な見通し

### 良いと言える点

- **現実の MCP サーバで、宣言と実装の食い違いがはっきり見つかっている。** 宣言を持つサーバのおよそ 8 つに 1 つで、`readOnlyHint: true` のツールが何かを書き換えている。この所見自体に意味がある。
- **精度はそこそこ高く、誤りの原因が絞れている**（v3 で 81.7%、誤りは 4 種類の決まった形）。
- **頑健**（新しい 91 木で 1 度も落ちない）。
- **手続きが堅い**（事前登録、敵対的レビュー、消えたものの確認、逸脱の記録）。

### 楽観できない点

1. **見落とし（再現率）が大きいかもしれない。** 矛の無いツールの約 17% に見落としがあった。単純に掛け算すると、見つけた数と同じくらい見落としている可能性がある。
2. **判定の基準で精度が大きく変わる。** v3 の「正」49 件のうち 14 件は、初回だけの DB の作成などの**裏側の初期化の書き込み**。採った原理では矛だが、「ツール本来の動作による違反だけを数える」基準では 49/60 → 35/60（約 58%）になる。
3. **判定が独立していない。** v3 の判定は開発者側が行った。
4. **件数が少数の木に偏っている。** 件数より「木の数」で報告するほうが頑健。

### 見通し

| 判定の基準 | 精度の見込み（v3 からの推定） |
|---|---|
| 採った原理どおり（環境を変える書き込みはすべて矛） | 70〜90% 程度 |
| ツール本来の動作による違反だけを正とする | 50〜70% 程度 |

**「宣言と実装の食い違いは現実にあり、静的解析でかなりの精度で見つけられる」は強く言える見込みが高い。一方、「漏れなく見つけられる」は言えない可能性が高い。** 再現率の限界を原因（深さ・解決・語彙）とともに正直に示せば、研究として十分に強い形になる。

   - 正 / 誤 / 不明の基準（第 15 章の原理どおり）。
   - **重大度**の列（ツール本来の動作か / 補助的な書き込みか）。境界の事例（初回の初期化、ログ、キャッシュ、一時ファイル、条件つきの書き込み）の扱いを例で決めておく。
   - 判定の根拠（ファイルと行）を必ず残す（2 人目の判定者がいない分、第三者が後から検証できるように）。
3. **凍結した解析器で走らせる**
   - 走らせる前に、解析器の指紋が `docs/fingerprint.json` と一致することを確かめる（`analyzer-freeze-2`）。
4. **精度を測る**: 矛を抜き取って判定。信頼区間を付ける。
5. **再現率を測る**: 矛の出なかったツールから無作為に抜き取り、手で読む。見落としを「深さ・解決・語彙・その他」に分類する。
6. **深さ 3 / 4 / 5 を比べる**: 再現率の議論の材料にする。
7. **主な数字は「木の数・ツールの数」で報告する**（件数は少数の木に偏るため）。
8. 「矛」と「不」を必ず併記し、原理を 1 つずつ反対にしたときの感度分析も付ける（`scripts/contradiction_by_decl.py`）。
