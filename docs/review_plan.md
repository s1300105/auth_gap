| 記号 | 壊し方 | 例 | 影響 |

## 4. 手順

### 4.1 探索（R1〜R5 を並列。同じ担当を、2 回続けて新しい所見が出なくなるまで繰り返す。上限 4 回）

所見として**受け付ける条件**（1 つでも欠けたら捨てる）:

1. **最小の再現コード**（MCP ツールの短い Python。`scripts/repro_scan.py` で走らせた出力を添える）と、
   規則から決まる**期待される出力**。
2. **誤りの向き**: 誤 clear（false-clean）/ 誤警報（false-alarm）/ 数え落とし（count-loss）。
3. **一般性の説明**: 言語の意味・ライブラリの仕様・書いた規則から導けること。v2 / v3 は影響件数の見積もりにだけ使う。
4. **D1 / D2 の判定、または評価の道具に影響する**こと（D3 / D4 だけなら記録止まり）。

### 4.2 検証（所見 1 件ごとに 3 観点で反証を試みる。**2 観点以上を生き延びたものだけ残す**）

| 観点 | 問い | 捨てる条件 |
|---|---|---|
| 実行 | 再現コードを解析器にかけると、主張どおりの出力になるか | 再現しない |
| 設計 | その挙動は D 番号の決定・§7 の表・仕様書で**意図されたもの**ではないか | 意図どおり（= 既知の設計判断） |
| 一般性 | 「直すと別の正しいケースが壊れる」反例を作れるか。G1 / G2 を取り消したときと同じ確認 | 反例が作れ、直し方が一般に正しくない |

### 4.3 採否（学生が決める）

生き残った所見を「重大度 × 向き × 直し方が一般に正しいか」の表で示す。所見ごとに
**直す / 限界として記録（O42 以降）** を学生が選ぶ。直すと凍結の中身が変わるので、ここは学生の判断。

### 4.4 直す（今までと同じ手順）

1. 規則 → 反例テスト → 実装 の順にコミット。
2. `scan_v2_run21` を取り、`scripts/diff_effects.py` と `scripts/compare_scans.py` で**消えた行を 1 件ずつ確かめる**。
3. 修正そのものを敵対的レビューにかける（解決率を上げる変更は特に）。
4. `docs/preregistration.md` に逸脱 #24 として記録。
5. `docs/fingerprint.json` を作り直し、**その後で学生が `analyzer-freeze-2` を打つ**。
1 件も直さなかった場合も「点検したが直すものは無かった」を記録してから同じようにタグを打つ。
